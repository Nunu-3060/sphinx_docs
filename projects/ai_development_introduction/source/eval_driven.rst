評価駆動開発
==========================================

本書の定義
------------------------------------------

:term:`評価駆動開発`\ とは、AI の出力の品質を測る評価（:term:`Evals`）を先に用意し、プロンプト、コンテキスト、ハーネスの変更を、その評価の結果に基づいて判断する開発の進め方である。テスト駆動開発が「テストを先に書き、テストの成功を目指して実装する」のと同じように、評価駆動開発では「評価を先に用意し、評価の結果の改善を目指して AI の使い方を変える」。

AI の振る舞いは確率的であり、プロンプトや規約ファイルの小さな変更が、思わぬ箇所に影響することがある。数回試して「よくなった気がする」で判断していると、ある問題を直したつもりで別の問題を生んでいても気付けない。評価は、この「気がする」を数字に置き換える。

評価駆動開発が役立つ場面は、大きく 2 つある。

* **AI 機能を持つ製品の開発**：分類、要約、抽出、対話などの機能の品質を測る。
* **AI を使った開発そのものの改善**：規約ファイル、スキル、フックなど、自分たちのハーネスの変更が、コーディングエージェントの成果を本当に改善したかを測る。

評価の構成要素
------------------------------------------

.. list-table:: 評価の構成要素
   :header-rows: 1
   :widths: 20 45 35

   * - 要素
     - 内容
     - 例
   * - タスク
     - 評価に使う入力。1 件の入力を評価ケースと呼ぶ
     - 不具合報告の文章、修正を依頼する課題
   * - 期待結果
     - 正解、または合否の基準
     - 正しい重大度、修正後に成功すべきテスト
   * - 採点器
     - 出力を期待結果と比べて採点する仕組み
     - 文字列の比較、テストの実行、LLM による採点
   * - 試行
     - 1 つのタスクを実行すること。出力が確率的なため、同じタスクを複数回試行することがある
     - 各タスクを 5 回ずつ実行する
   * - 指標
     - 採点結果を集計した値
     - 正解率、pass@k、費用、所要時間

採点器の種類
------------------------------------------

.. list-table:: 採点器の種類
   :header-rows: 1
   :widths: 20 40 40

   * - 種類
     - 内容
     - 長所と短所
   * - コードによる採点
     - 完全一致、正規表現、JSON スキーマの検証、テストの実行、静的解析
     - 速く、安く、結果が確実。意味的な良し悪し（説明の分かりやすさなど）は測りにくい
   * - LLM による採点
     - 採点基準を与えた LLM に採点させる（LLM-as-a-judge）
     - 意味的な評価ができる。費用がかかり、採点自体が揺らぐ。採点の偏りに注意が必要
   * - 人間による採点
     - 人間が出力を読んで採点する
     - 最も信頼できるが、遅く、高い。他の採点器の妥当性の確認に使う

コーディングの評価では、テストの実行による採点が中心になる。生成されたコードが、あらかじめ用意したテストに成功するかどうかで採点する方式である。公開されているベンチマークとして、実在する OSS の課題を解かせ、その課題のテストで採点する SWE-bench がよく知られている :ref:`[Jimenez2023] <ref-jimenez2023>`。

LLM による採点は、強力なモデルに採点させると人間の判断とよく一致する一方で、長い回答を高く評価する、自分と似た出力を好むなどの偏りがあることも報告されている :ref:`[Zheng2023] <ref-zheng2023>`。LLM による採点を使う場合は、採点基準を具体的に書き、一部を人間が採点して一致度を確かめる。

指標
------------------------------------------

出力が確率的な場合、1 回の試行の合否だけでは実力を測れない。そこで、複数回の試行の結果をまとめた指標を使う。

:math:`\mathrm{pass@}k` は、:math:`k` 回試行して 1 回以上成功する確率である。あるタスクを :math:`n` 回試行して :math:`c` 回成功したとき、次の式で推定する :ref:`[Chen2021] <ref-chen2021>`。

.. math::

   \mathrm{pass@}k = 1 - \frac{\binom{n-c}{k}}{\binom{n}{k}}

この式の右辺の分数は、:math:`n` 回の試行から :math:`k` 回分を選んだとき、すべてが失敗である確率を表す。複数のタスクで評価する場合は、タスクごとの値を平均する。

これに対し、:math:`\mathrm{pass}^k` は、:math:`k` 回の試行がすべて成功する確率である :ref:`[Anthropic-Evals] <ref-anthropic-evals>`。1 回の試行の成功率を :math:`p` とすると、:math:`p^k` で見積もれる。例えば、成功率 75% のエージェントが 3 回連続で成功する確率は、:math:`0.75^3 \approx 0.42` である。

.. list-table:: 指標の使い分け
   :header-rows: 1
   :widths: 20 40 40

   * - 指標
     - 意味
     - 重視する場面
   * - :math:`\mathrm{pass@}k`
     - :math:`k` 回のうち 1 回でも成功すればよい
     - 複数の案を生成し、人間やテストがよいものを選べる場面
   * - :math:`\mathrm{pass}^k`
     - :math:`k` 回すべて成功する必要がある
     - 毎回確実に成功してほしい場面（無人で動く自動化など）

成功率が 0 でなければ、:math:`k` を増やすと :math:`\mathrm{pass@}k` は 100% に近づき、:math:`\mathrm{pass}^k` は 0% に近づく。同じエージェントでも、どちらの指標を見るかで評価が大きく変わるため、用途に合った指標を選ぶ。また、品質だけでなく、費用（トークン数）と所要時間も合わせて記録しておくと、モデルや設定の選択に役立つ。

評価のサイクル
------------------------------------------

評価駆動開発は、:numref:`fig-eval-cycle` のサイクルで進める。

.. _fig-eval-cycle:

.. graphviz::
   :caption: 評価駆動開発のサイクル
   :align: center

   digraph eval {
     rankdir=LR;
     graph [fontsize=11, nodesep=0.35];
     node [shape=box, style="rounded,filled", fillcolor="#EEF3FA", color="#4C78A8", fontsize=10];
     edge [color="#555555", fontsize=9];

     collect [label="失敗の収集\n実際に起きた失敗"];
     cases   [label="評価ケース化\n入力と期待結果"];
     change  [label="変更\nプロンプト・規約・ツール"];
     run     [label="評価の実行\n全ケースを採点"];
     decide  [label="比較・判断\n改善なら採用", fillcolor="#E8F5E9", color="#2E7D32"];

     collect -> cases -> change -> run -> decide;
     decide -> change [label="悪化・不十分", style=dashed];
     decide -> collect [label="運用で新たな失敗", style=dashed];
   }

#. **失敗を集める**：実際の利用で起きた失敗を記録する。評価ケースは、想像で作るより実際の失敗から作るほうが効果的である。
#. **評価ケースにする**：失敗した入力と、期待する結果の組を評価データに加える。最初から数百件を用意する必要はなく、実際の失敗から作った 20 〜 50 件程度でも始められる :ref:`[Anthropic-Evals] <ref-anthropic-evals>`。
#. **変更する**：プロンプト、規約ファイル、ツールなどを変更する。
#. **評価を実行する**：新しく加えたケースだけでなく、すべてのケースを採点する。以前は成功していたケースが失敗するようになっていないか（回帰）を確かめるためである。
#. **比較して判断する**：変更前と比べて改善していれば採用し、悪化していれば元に戻す。

このサイクルは、:doc:`loop_engineering`\ で述べたハーネス改善のループを、定量的に回すための方法でもある。

注意点
------------------------------------------

* **評価データへの過剰適合**：評価データの個々のケースに合わせてプロンプトを調整し続けると、評価の点数は上がっても、評価データにない入力では性能が上がらないことがある。評価データの一部を調整に使わない確認用として取り分けておくとよい。
* **採点器の誤り**：採点器自体が誤っていると、評価の結果は意味をなさない。特に LLM による採点は、定期的に人間の採点と照らし合わせる。
* **評価の陳腐化**：エージェントの能力が上がると、既存の評価ケースはすべて成功するようになり、改善を測れなくなる。新しい失敗を継続的に評価データに加える。
* **出力だけでなく過程も見る**：エージェントの評価では、最終的な結果が正しくても、不要なファイルを変更した、テストを書き換えたなど、過程に問題がある場合がある。作業の記録（どのツールをどう使ったか）も確認する。
