プロンプトエンジニアリング
==========================================

本書の定義
------------------------------------------

:term:`プロンプトエンジニアリング`\ とは、LLM への指示文（:term:`プロンプト`）を工夫して、意図した出力を得る技術である。4 つの層のうち最も内側にあり、他のすべての層の土台になる。エージェントを使う場合でも、最終的にモデルに届くのはテキストであり、その書き方の良し悪しが結果を左右する。本章の内容は、各 AI 企業が公開しているプロンプトの指針 :ref:`[Anthropic-Prompt] <ref-anthropic-prompt>` などを、開発作業の観点で整理したものである。

プロンプトの構成要素
------------------------------------------

よいプロンプトには、:numref:`table-prompt-elements` の要素が含まれていることが多い。すべてを毎回書く必要はないが、出力が期待と違うときは、どの要素が欠けているかを確認するとよい。

.. _table-prompt-elements:

.. list-table:: プロンプトの構成要素
   :header-rows: 1
   :widths: 18 42 40

   * - 要素
     - 内容
     - 例
   * - 役割
     - モデルにどの立場で答えてほしいか
     - あなたは Python のコードレビューを担当するシニアエンジニアである
   * - タスク
     - 何をしてほしいか
     - 次の関数の不具合の可能性を指摘せよ
   * - 背景
     - なぜそれが必要か、成果物を誰が何に使うか
     - リリース前の最終確認であり、不具合だけを洗い出したい
   * - 入力
     - 処理の対象となるデータ
     - レビュー対象のコード
   * - 制約
     - 守るべき条件、してはいけないこと
     - 命名やスタイルには触れない
   * - 例
     - 期待する入力と出力の組
     - 指摘の例を 1 つ示す
   * - 出力形式
     - 出力の構造や形式
     - JSON 配列で返す

多くの API や対話型 AI では、プロンプトを\ :term:`システムプロンプト`\ と、利用者からのメッセージ（ユーザーメッセージ）に分けて渡せる。システムプロンプトには会話全体を通じて変わらない役割・制約・出力形式を、ユーザーメッセージには個々のタスクと入力を書くのが一般的である。

基本的なテクニック
------------------------------------------

明確かつ具体的に書く
^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^

モデルは、書かれていないことを推測で補う。推測が外れないよう、対象・範囲・完了の条件を具体的に書く。目安は「このプロジェクトを知らない優秀な同僚に依頼する文面として十分か」である。

.. list-table:: 曖昧な指示と具体的な指示
   :header-rows: 1
   :widths: 40 60

   * - 曖昧な指示
     - 具体的な指示
   * - テストを書いて
     - ``src/order.py`` の ``calculate_total`` に、割引率が 100% の場合と数量が 0 の場合のテストを ``tests/test_order.py`` に追加して。既存のテストの書き方に合わせること
   * - このコードを速くして
     - ``load_users`` は 1 万件で 8 秒かかる。プロファイルの結果では DB への問い合わせが件数分発生している。問い合わせを 1 回にまとめて、1 秒以内にしたい
   * - いい感じにリファクタリングして
     - ``report.py`` の ``export`` 関数（約 200 行）を、データの取得・整形・出力の 3 つの関数に分割して。外部から見た振る舞いは変えず、既存のテストがすべて成功すること

理由を伝える
^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^

制約には理由を添える。「``float`` を使うな」とだけ書くより、「金額の計算で丸め誤差が出るため ``float`` ではなく ``Decimal`` を使う」と書くほうが、モデルは規則の意図を理解し、明示していない似た場面にも正しく適用しやすい。

例を示す
^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^

期待する出力の例をいくつか示すと、出力の形式や判断の基準がそろいやすい。例を含むプロンプトを :term:`few-shot プロンプト`\ と呼ぶ :ref:`[Brown2020] <ref-brown2020>`。例は、典型的なものだけでなく境界的なものも含め、互いに十分異なるものを選ぶ。似た例ばかりだと、モデルが例の表面的な特徴（文の長さや言い回し）まで真似てしまう。

考える手順を与える
^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^

複雑な問題では、答えを出す前に考える過程を書かせると精度が上がることが知られており、これを :term:`Chain-of-Thought` という :ref:`[Wei2022] <ref-wei2022>`。現在の主要なモデルの多くは、回答の前に内部で推論する機能（拡張思考、推論モードなど）を備えているため、「段階的に考えよ」と書く必要性は以前より小さい。それでも、「まず原因の候補を列挙し、次にそれぞれをログと照合し、最後に最も可能性の高いものを選ぶ」のように、作業の手順を示すことは有効である。

入力と指示を区別する
^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^

長い入力を含めるときは、XML 風のタグや見出しで指示と入力を区切る。区切りがないと、入力の中の文（例えばレビュー対象のコードのコメント）を指示と取り違えることがある。入力が信頼できない外部のデータである場合には、この区別はセキュリティ上も重要になる（:doc:`risks`\ 参照）。

出力形式を指定する
^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^

出力をプログラムで処理する場合は、JSON などの形式と、含めるキーを明示する。多くの API は、出力が指定した JSON スキーマに必ず従うようにする\ :term:`構造化出力`\ の機能を備えている。プログラムで処理する用途では、プロンプトでの指定よりも構造化出力を使うほうが確実である。

してほしいことを書く
^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^

「Markdown を使うな」のような否定形の指示より、「段落に分けた平文で書け」のように、望む状態を肯定形で書くほうが伝わりやすい。禁止事項が必要な場合は、代わりにどうすべきかを併記する。

   </example>
   </examples>

開発作業でのプロンプトの例
------------------------------------------

開発作業の種類ごとに、プロンプトに含めるべき情報をまとめる。

.. list-table:: 開発作業ごとにプロンプトに含める情報
   :header-rows: 1
   :widths: 18 82

   * - 作業
     - 含める情報
   * - 実装
     - 実現したい振る舞い、対象のファイルやモジュール、従うべき既存の設計、完了条件（どのテストが成功すればよいか）
   * - リファクタリング
     - 変えてよいもの（内部構造）と変えてはいけないもの（外部から見た振る舞い、公開 API）、確認の方法
   * - レビュー
     - 観点（不具合、セキュリティ、性能など）、指摘の粒度、重要度の付け方、指摘しなくてよいこと
   * - テストの作成
     - 対象の関数、確かめたい条件（正常系、境界値、異常系）、使うテストフレームワークと既存のテストの書き方
   * - デバッグ
     - 期待した動作と実際の動作、エラーメッセージとスタックトレースの全文、再現手順、すでに試したこと

デバッグでは、エラーメッセージを要約せず、そのまま渡すことが特に重要である。人間が要約すると、原因の手がかりになる情報が落ちることが多い。

アンチパターン
------------------------------------------

.. list-table:: プロンプトのアンチパターン
   :header-rows: 1
   :widths: 25 40 35

   * - アンチパターン
     - 問題
     - 対策
   * - 曖昧な指示
     - モデルが推測で補い、意図と違う結果になる
     - 対象・範囲・完了条件を明示する
   * - 矛盾する指示
     - 「簡潔に」と「詳しく」のような指示が混在し、どちらかが無視される
     - 優先順位を明示する。プロンプトを見直して矛盾を除く
   * - 過剰な強調
     - 「絶対に」「必ず」を多用すると、その指示を過剰に適用し、他の指示との釣り合いが崩れる
     - 強調は本当に重要な箇所に限り、理由を添える
   * - 詰め込みすぎ
     - 1 つのプロンプトで多くの作業を頼むと、一部が抜け落ちる
     - 作業を分割し、1 回の依頼で 1 つの目的に絞る
   * - 試行錯誤の放置
     - 変更の効果を確かめずにプロンプトを書き換え続け、改善したのか悪化したのか分からなくなる
     - 評価データを用意し、変更ごとに採点する（:doc:`eval_driven`）

プロンプトだけでは解決できないこと
------------------------------------------

プロンプトの工夫には限界がある。例えば、次のような問題は指示文をいくら工夫しても解決しない。

* モデルがプロジェクトの規約や既存のコードを知らない。→ 必要な情報を渡す（:doc:`context_engineering`）。
* モデルが書いたコードが動くかどうか、モデル自身には分からない。→ テストを実行できる環境を与える（:doc:`harness_engineering`）。
* 1 回で正しい答えにたどり着けない。→ 検証と修正を繰り返させる（:doc:`loop_engineering`）。

このように、プロンプトエンジニアリングは外側の層と組み合わせて初めて力を発揮する。
