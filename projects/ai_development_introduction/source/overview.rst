AI を用いた開発の全体像
==========================================

本章では、まず開発者が知っておくべき LLM の性質を説明する。次に、AI の利用形態がどう変わってきたかを振り返り、本書で扱う各手法の関係を示す。

開発者が知っておくべき LLM の性質
------------------------------------------

現在の AI 開発支援の中心にあるのは、:term:`LLM`\ （大規模言語モデル）である。LLM の内部構造を知らなくても使えるが、次の性質を知っておくと、後の章で説明する手法がなぜ必要なのかを理解しやすい。

テキストを続けて生成する
^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^

LLM は、入力されたテキストに続くテキストを生成する。テキストは\ :term:`トークン`\ という単位に分割して扱われ、モデルは「次に来るトークン」を 1 つずつ予測して出力を組み立てる。トークンは英語ではおおむね単語や単語の一部に、日本語では 1 文字から数文字に相当する。API の料金や処理できる量も、トークン数で数える。

一度に扱える量に上限がある
^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^

モデルが一度に読める入力と出力の合計には上限があり、これを\ :term:`コンテキストウィンドウ`\ という。2026 年時点の主要なモデルでは数十万〜百万トークン程度であり、中規模のリポジトリのソースコード全体に相当する量を読める場合もある。

ただし、上限まで詰め込めばよいわけではない。入力が長くなるほど、情報が見落とされやすくなる。何をどれだけ入れるかの設計が\ :doc:`context_engineering`\ の主題である。

記憶を持たない
^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^

LLM は呼び出しをまたいで記憶を保持しない。対話型 AI が会話の流れを覚えているように見えるのは、アプリケーションが毎回それまでの会話履歴をすべて入力に含めているからである。したがって、モデルが「知っている」のは、学習時に得た知識と、今回の入力に含まれる情報だけである。

出力は確率的である
^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^

同じ入力を与えても、出力が毎回同じになるとは限らない。また、事実と異なる内容をもっともらしく出力することがあり、これを\ :term:`ハルシネーション`\ という。存在しない関数や引数を使ったコードを書くのは、その典型である。

このため、AI の出力は「正しいかもしれない案」として扱い、テストや型検査などの機械的な手段で検証する必要がある。この検証の仕組みを整えることが、:doc:`harness_engineering`\ と\ :doc:`loop_engineering`\ の中心的な課題になる。

知識に期限がある
^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^

モデルの知識は学習データを集めた時点までのものであり、この時点を\ :term:`知識のカットオフ`\ という。カットオフより後に公開されたライブラリの新しい版や API の変更は知らない。必要な情報は、文書を読ませるなどして入力に含める。

ツールを呼び出せる
^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^

現在の LLM は、テキストを返す代わりに「このツールをこの引数で呼び出してほしい」という要求を出力できる。これを\ :term:`ツール呼び出し`\ という。ツールを実際に実行するのはモデルではなく、モデルを呼び出しているアプリケーションである。アプリケーションはツールの実行結果をモデルに返し、モデルはその結果を読んで次の行動を決める。

ツール呼び出しによって、LLM はファイルを読む、コマンドを実行する、Web を検索するといった、外部の世界に働きかける作業ができるようになった。これが次に説明するエージェントの基盤である。

AI の利用形態の変遷
------------------------------------------

開発における AI の利用形態は、:numref:`fig-evolution` のように変わってきた。右に進むほど AI に任せる範囲が広がり、人間の役割は「書く」から「指示し、検証する」へ移っていく。

.. _fig-evolution:

.. graphviz::
   :caption: 開発における AI の利用形態の変遷
   :align: center

   digraph evolution {
     rankdir=LR;
     node [shape=box, style="rounded,filled", fillcolor="#EEF3FA", color="#4C78A8", fontsize=11];
     edge [color="#555555"];

     completion [label="コード補完\n入力中のコードの\n続きを提案する"];
     chat       [label="チャット\n質問に答え、\nコードを提示する"];
     agent      [label="エージェント\nファイルの編集や\nコマンドの実行まで行う"];
     autonomous [label="自律的なループ・並列化\n長時間・複数の作業を\n人間の監督下で進める", fillcolor="#E8F5E9", color="#2E7D32"];

     completion -> chat -> agent -> autonomous;
   }

.. list-table:: 利用形態ごとの特徴
   :header-rows: 1
   :widths: 18 30 26 26

   * - 形態
     - AI が行うこと
     - 人間が行うこと
     - 主な課題
   * - コード補完
     - 数行〜関数単位のコードの提案
     - 設計、実装の大部分、採否の判断
     - 提案の範囲が狭い
   * - チャット
     - 質問への回答、コードの生成、説明
     - 必要な情報の貼り付け、結果の転記と実行
     - 情報の受け渡しが手作業になる
   * - エージェント
     - 調査、編集、テストの実行、修正
     - 目的と制約の提示、レビュー、承認
     - 誤った方向に進んだときの検出
   * - 自律的なループ・並列化
     - 長時間の作業、複数作業の並行処理
     - 目標と完了条件の設定、監督、最終判断
     - 品質の担保、コスト、安全性

:term:`エージェント`\ とは、目標を与えられると、どのツールをどの順で使うかを自ら判断しながら作業を進める仕組みである。ソフトウェア開発用のエージェントを特に\ :term:`コーディングエージェント`\ と呼ぶ。Claude Code、GitHub Copilot のエージェント機能、Cursor、OpenAI Codex などがこれにあたる。

各エンジニアリングの関係
------------------------------------------

AI を使いこなすための技術は、「モデルに何を渡し、どのような環境で動かし、どう反復させるか」という観点で、:numref:`fig-layers` のような層構造に整理できる。内側の層は外側の層に含まれる。

.. _fig-layers:

.. graphviz::
   :caption: 本書で扱う 4 つのエンジニアリングの関係
   :align: center

   digraph layers {
     graph [compound=true, fontsize=12, labeljust=l, nodesep=0.3];
     node [shape=box, style="rounded,filled", fontsize=10];

     subgraph cluster_loop {

       style="rounded,filled"; fillcolor="#F3EEF9"; color="#7B5EA7";
       subgraph cluster_harness {
         label="ハーネスエンジニアリング：ツール・権限・テスト・フック・CI";
         style="rounded,filled"; fillcolor="#EAF4EA"; color="#2E7D32";
         subgraph cluster_context {
           label="コンテキストエンジニアリング：何を、どれだけ、どの順で渡すか";

             label="プロンプトエンジニアリング：指示文の書き方";

   }

.. list-table:: 4 つのエンジニアリングの比較
   :header-rows: 1
   :widths: 22 26 26 26

   * - 手法
     - 中心となる問い
     - 主な対象
     - 主な手段
   * - プロンプトエンジニアリング
     - どう頼むか
     - 1 回の指示文
     - 明確な指示、例示、出力形式の指定
   * - コンテキストエンジニアリング
     - 何を知らせるか
     - モデルに渡す情報全体
     - 規約ファイル、検索、要約、記憶
   * - ハーネスエンジニアリング
     - どんな環境で働かせるか
     - ツールと実行環境
     - ツール設計、権限、テスト、フック、CI
   * - ループエンジニアリング
     - どう繰り返し、いつ止めるか
     - 反復の構造と終了条件
     - 自己修正、終了条件、人間による承認

この順序は、技術が注目された歴史的な順序とも一致する。対話型 AI が普及した当初は、指示文の工夫（プロンプトエンジニアリング）が注目された。エージェントが長い作業をするようになると、入力全体の管理（コンテキストエンジニアリング）が重要になった。さらに、エージェントに任せる範囲が広がると、エージェントを取り巻く道具と制約（ハーネスエンジニアリング）や、反復の設計（ループエンジニアリング）が課題になった。

外側の層は、内側の層を置き換えるものではない。よいハーネスの中でも指示が曖昧であれば結果は悪くなるし、よい指示を書いても検証の仕組みがなければ誤りに気付けない。4 つの層はすべて必要であり、問題が起きたときに「どの層の問題か」を切り分けることが重要である。

AI に任せる部分と人間が責任を持つ部分
------------------------------------------

AI に任せる範囲が広がっても、ソフトウェアに対する責任は人間にある。本書では、次の役割分担を前提とする。

.. list-table:: 役割分担の原則
   :header-rows: 1
   :widths: 30 70

   * - 担い手
     - 役割
   * - 人間
     - 何を作るか（目的・要求）を決める。完了条件と制約を示す。設計上の重要な判断をする。最終的な成果物を確認し、責任を持つ
   * - AI
     - 調査、実装、テストの作成、修正、文書化など、示された目的と制約の範囲での作業を行う
   * - 仕組み（ハーネス）
     - テスト、型検査、権限、フックなどにより、AI の作業を機械的に検証し、逸脱を防ぐ

AI の作業量が増えるほど、人間がすべての出力を目で確認することは難しくなる。そこで、人間の確認を「仕組みによる自動の検証」で補い、人間は判断が必要な箇所に集中する。これが本書全体を通じた考え方である。
