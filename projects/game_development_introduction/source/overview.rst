ゲーム制作の全体像
==================

この章では、ゲームが企画されてから公開・運用されるまでの工程を概観する。各工程の詳細は後の章で扱う。

ゲーム制作の工程
----------------

商業ゲームの制作は、一般に次の工程に分けて語られる。名称や区切り方は会社によって異なるが、大まかな流れは共通している。

.. graphviz::
   :caption: ゲーム制作の工程
   :name: fig-overview-workflow

   digraph workflow {
       rankdir=LR;
       node [shape=box, style="rounded,filled", fillcolor="#eef2ff", color="#6070a0"];
       edge [color="#6070a0"];
       planning [label="企画"];
       pre [label="プリプロダクション\n（試作）"];
       production [label="プロダクション\n（本制作）"];
       post [label="ポストプロダクション\n（仕上げ・検証）"];
       release [label="リリース\n（公開）"];
       ops [label="運用"];
       planning -> pre -> production -> post -> release -> ops;
       pre -> planning [style=dashed, label="見直し", fontsize=10];
       ops -> production [style=dashed, label="アップデート", fontsize=10];
   }

.. list-table:: 各工程の目的と成果物
   :header-rows: 1
   :widths: 22 40 38

   * - 工程
     - 目的
     - 主な成果物
   * - 企画
     - 何を、誰のために、どの規模で作るかを決める
     - 企画書
   * - プリプロダクション
     - 試作を通じて、面白さと技術的な実現性を確かめる
     - プロトタイプ、ゲームデザインドキュメント（GDD）
   * - プロダクション
     - ゲームの中身（ステージ、アセット、機能）を量産する
     - アルファ版、ベータ版
   * - ポストプロダクション
     - 不具合を直し、調整し、公開できる品質に仕上げる
     - 製品版（リリース候補）
   * - リリース
     - 配布先に登録し、プレイヤーに届ける
     - ストアページ、配布物
   * - 運用
     - 不具合修正や追加要素の配信、プレイヤーとの交流を行う
     - アップデート、パッチノート

プリプロダクションで面白くないと分かれば、企画に戻ってやり直す。この「早く作って、遊んで、直す」という反復が、ゲーム制作で最も重要な考え方である。プロダクションに入ってから根本的な面白さの問題に気付くと、作ったものの大半が無駄になるためである。

開発途中の版には、次のような呼び名がある。

- **プロトタイプ**: 核となる遊びだけを確かめるための試作品。見た目は仮のものでよい。
- **バーティカルスライス**: ゲームの一部分（例えば 1 ステージ）だけを、製品と同じ品質まで作り込んだもの。完成形の品質と作業量を見積もるために作る。
- **アルファ版**: 主要な機能がひととおり遊べる状態。内容の追加はまだ続く。
- **ベータ版**: 内容がほぼ出そろい、不具合修正と調整を中心に進める状態。

個人・小規模開発の特徴
----------------------

本書が想定する個人や数人の小規模チームでの開発には、商業開発と比べて次の特徴がある。

.. list-table:: 商業開発と小規模開発の比較
   :header-rows: 1
   :widths: 22 39 39

   * - 観点
     - 商業開発（中・大規模）
     - 個人・小規模開発
   * - 人員
     - 職種ごとの専門家が数十人から数百人
     - 1 人がプログラム・絵・音・宣伝を兼ねることが多い
   * - 期間
     - 数年
     - 数日（ゲームジャム）から 1、2 年
   * - 予算
     - 数億円以上になることもある
     - ほぼゼロから数十万円程度
   * - 強み
     - 物量と品質
     - 尖ったアイデア、意思決定の速さ
   * - 主なリスク
     - 予算超過、市場の変化
     - 完成しないこと、知ってもらえないこと

小規模開発で最も多い失敗は「完成しないこと」である。作業を進めるうちに作りたいものが膨らんでいく現象は\ :term:`スコープクリープ`\ と呼ばれ、完成しない原因の多くはこれである。作る範囲を小さく保つ方法は\ :doc:`planning`\ で扱う。

最初の 1 本は小さく作る
-----------------------

初めてゲームを作るなら、最初の 1 本は「数時間から数日で完成し、数分で遊び終わる」規模にするのがよい。具体的には、ブロック崩し、シューティング、横スクロールのアクションの 1 ステージなどの、ルールがすでに広く知られているゲームである。

既存のゲームを題材にすると、ゲームデザインに悩まずに、ゲームループ、入力、当たり判定、画面遷移、ビルド、公開という一連の工程を経験できる。本書の\ :doc:`practice`\ でブロック崩しを題材にするのもこのためである。1 本を完成させて公開まで経験しておくと、2 本目以降で自分のアイデアを形にするときに、どこに時間がかかるかを見積もれるようになる。
