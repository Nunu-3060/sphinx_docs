品質を高める
============

遊べる状態になったゲームを、面白く、快適で、不具合の少ないものに仕上げていくのがこの章の内容である。業務ソフトウェアと同じく、テストとデバッグは欠かせない。それに加えてゲームでは、他人に遊んでもらって面白さを確かめるプレイテストが重要になる。

プレイテスト
------------

:term:`プレイテスト`\ とは、自分以外の人にゲームを遊んでもらい、その様子を観察して改善点を見つけることである。作った本人は、操作にもルールにも慣れきっているため、初めて遊ぶ人がどこで戸惑うかが分からない。

プレイテストは次のように行う。

- **説明しない**: 遊び方を口で説明したくなるのをこらえる。説明が必要なら、それはゲームの中で伝えるべき情報が不足しているということである。
- **観察する**: どこで迷ったか、どこで笑ったか、どこで退屈そうにしたかを記録する。可能なら画面と表情を録画する。
- **後で聞く**: 遊び終わってから、面白かった点、分かりにくかった点、もっと遊びたいと思ったかを聞く。
- **意見と事実を分ける**: 「ここをこう変えてほしい」という提案よりも、「ここで困った」という事実の方が価値がある。解決策は作り手が考える。

プレイテストは完成間近になってから行うのではなく、:doc:`planning`\ のプロトタイプの段階から何度も行う。早い段階ほど、見つかった問題を安く直せる。

バランス調整
------------

ボールの速さ、敵の強さ、得られる得点など、ゲームの手応えを決める数値を調整することを\ :term:`バランス調整`\ と呼ぶ。:doc:`practice`\ のサンプルで設定値をファイルの先頭に定数としてまとめたのは、この調整をしやすくするためである。調整する数値が多くなったら、JSON などのデータファイルに分けて、プログラムを変えずに調整できるようにするとよい。

難易度は、簡単すぎると退屈になり、難しすぎると挫折される。プレイヤーの上達に合わせて少しずつ難しくなる流れ（難易度曲線）を作るのが基本である。開発者自身は誰よりもそのゲームが上手くなっているため、自分にとって適度な難易度は、初めて遊ぶ人には難しすぎることが多い。難易度はプレイテストの結果を基に決める。

手触りを良くする
----------------

同じルールのゲームでも、操作したときの反応の気持ちよさによって、面白さの感じ方は大きく変わる。この操作の気持ちよさを\ **ゲームフィール**\ （game feel）と呼び、ルールを変えずに反応を豊かにして気持ちよさを高める演出は、英語で\ :term:`ジュース`\ （juice）と呼ばれる。

.. list-table:: 手触りを良くする演出の例
   :header-rows: 1
   :widths: 25 75

   * - 演出
     - 内容
   * - 効果音
     - 操作や出来事のすべてに音を付ける。音の高さを少しずつ変えると単調にならない
   * - パーティクル
     - 破壊や着地の瞬間に、小さな粒を飛び散らせる
   * - 画面の揺れ
     - 強い衝撃のときに、画面全体を短時間だけ揺らす
   * - ヒットストップ
     - 攻撃が当たった瞬間に、ごく短い時間（数フレーム）だけ動きを止めて、手応えを強調する
   * - イージング
     - 物を一定の速さではなく、加速や減速を付けて動かす。UI の出入りなどが自然に見える
   * - 先行入力
     - 動作中に押されたボタンを覚えておき、動作が終わった瞬間に実行する。操作が「効かなかった」という不満を減らす

:doc:`practice`\ の Step 7 では、効果音とパーティクルを加えた。Step 6 と Step 7 を遊び比べると、ルールは同じでも手応えがまったく違うことが分かるはずである。ただし、演出は足しすぎると画面が見づらくなり、かえって遊びにくくなる。これもプレイテストで確かめる。

自動テスト
----------

ゲームでも、画面や入力に依存しない計算部分には単体テストを書ける。当たり判定、得点計算、ダメージ計算、セーブデータの読み書きなどは、テストしやすく、不具合が起きると影響が大きい部分である。

次の例は、:doc:`practice`\ で作ったパドルの反射の計算をテストする。

.. literalinclude:: ../examples/test_breakout.py
   :language: python
   :linenos:
   :pyobject: PaddleBounceVelocityTest
   :caption: examples/test_breakout.py の PaddleBounceVelocityTest クラス

.. code-block:: powershell
   :linenos:
   :caption: 単体テストの実行

   py -m unittest test_breakout

テストの全体は\ :download:`test_breakout.py <../examples/test_breakout.py>`\ からダウンロードできる。ボールがブロックを壊して跳ね返るか、壁で跳ね返るかを確かめるテストも含めている。

一方、「操作が気持ちよいか」「難しすぎないか」は自動テストでは確かめられない。自動テストは計算の正しさを守るために使い、面白さはプレイテストで確かめる、という分担になる。

デバッグ
--------

ゲームの不具合は、特定のタイミングや操作の組み合わせでしか起きないことが多い。次のような工夫で、調査しやすくしておく。

- **デバッグ表示**: 当たり判定の範囲を枠で描く、FPS や物の数を画面の隅に表示するなど、目に見えない情報を見えるようにする。キーを 1 つ押すと表示が切り替わるようにしておくと便利である。
- **ログ**: 重要な出来事（シーンの切り替え、ステージの開始と終了）を ``logging`` モジュールで記録する。毎フレームの出力は量が多すぎるので避ける。
- **デバッガー**: Visual Studio Code などのデバッガーで、ブレークポイントを置いて変数の値を調べる。
- **再現性の確保**: :doc:`programming_basics`\ で述べたように乱数のシードを固定すると、同じ状況を再現できる。
- **デバッグ用の操作**: 好きなステージから始める、無敵になるなど、確認したい場面にすぐ行ける操作を用意しておく。公開版では無効にすることを忘れない。

パフォーマンスの計測
--------------------

処理落ちが起きたら、推測で直す前に、どこに時間がかかっているかを計測する。pygame-ce では ``clock.get_fps()`` で直近のフレームレートを取得できる。処理ごとの時間は、Python 標準のプロファイラー cProfile で調べられる。

.. code-block:: powershell
   :linenos:
   :caption: cProfile による計測

   py -m cProfile -s cumtime step07_polish.py

ゲームを終了すると、関数ごとの累積の実行時間が長い順に表示される。小規模な 2D ゲームでよくある原因は次のとおりである。

- 画像やフォントを毎フレーム読み込んでいる。起動時やシーンの開始時に一度だけ読み込む。
- 読み込んだ画像に ``convert`` または ``convert_alpha`` を呼んでいない。画面の形式と異なる画像は描画のたびに変換されるため遅い。
- 物の数が多いのに、すべての組み合わせで当たり判定を行っている。物が :math:`n` 個あれば組み合わせは約 :math:`n^2/2` 通りになる。画面を格子に区切り、近くにある物どうしだけを判定するなどの工夫で減らせる。
