実装上の落とし穴
================

安全なアルゴリズムを選んでも、使い方や実装を誤れば安全性は失われる。実際、暗号に関する脆弱性の多くは、アルゴリズムそのものではなく実装や運用の誤りから生じている。本章では、代表的な落とし穴と、その対策を扱う。

乱数
----

random モジュールを使ってはならない
^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^

暗号では、鍵、IV、ナンス、ソルト、トークンなど、多くの場面で乱数を使う。これらの乱数は、攻撃者にとって予測不可能でなければならない。

Python の ``random`` モジュールは、メルセンヌ・ツイスタ（MT19937）という擬似乱数生成器を使っている。メルセンヌ・ツイスタは統計的な性質に優れ、シミュレーションには適しているが、暗号用途には使えない。出力 624 個（32 ビットずつ）を観測すれば内部状態を完全に復元でき、それ以降の出力を全て予測できるからである。また、シードが同じなら毎回同じ列を出力する。

暗号用途には、予測不可能性が保証された\ :term:`暗号論的擬似乱数生成器`\ を使う。Python では ``secrets`` モジュール、または ``os.urandom()`` を使う。これらは OS が提供する乱数源（Linux の ``getrandom()``、Windows の ``BCryptGenRandom()`` など）から乱数を得る。

乱数生成の失敗事例
^^^^^^^^^^^^^^^^^^

乱数の不具合は、暗号を根本から破壊する。2008 年には、Debian の OpenSSL パッケージで、乱数源を混ぜ込む処理が誤って削除されていたことが発覚した（CVE-2008-0166）。その結果、生成される鍵がプロセス ID だけで決まるようになり、鍵の種類とサイズごとに高々 32768 通りしか生成されなくなっていた。:doc:`signature`\ で述べた ECDSA のナンスの重複による事件も、乱数生成の不具合が原因である。

タイミング攻撃
--------------

サイドチャネル攻撃
^^^^^^^^^^^^^^^^^^

暗号処理の入力と出力だけでなく、処理時間、消費電力、電磁波、キャッシュの状態など、処理に付随して漏れる情報を利用する攻撃を\ :term:`サイドチャネル攻撃`\ と呼ぶ。その中で、処理時間の違いを利用するものをタイミング攻撃と呼ぶ。タイミング攻撃はネットワーク越しにも行えるため、特に注意が必要である。

比較処理への攻撃
^^^^^^^^^^^^^^^^

最も身近な例は、MAC のタグやトークンの比較である。次のような素朴な比較関数は、先頭から 1 バイトずつ比べ、一致しないバイトが見つかった時点で終了する。

.. code-block:: python
   :linenos:

   def naive_equal(a: bytes, b: bytes) -> bool:
       if len(a) != len(b):
           return False
       for x, y in zip(a, b):
           if x != y:
               return False  # ここで終了するため、一致した長さによって処理時間が変わる
       return True

攻撃者は、先頭の 1 バイトだけを変えた候補を 256 通り送り、最も処理時間が長かったものを選べば、正しい先頭のバイトが分かる。これを 1 バイトずつ繰り返せば、全体を総当たりするよりはるかに少ない試行で正しい値を求められる。16 バイトのタグなら、総当たりでは :math:`256^{16} = 2^{128}` 通りだが、この攻撃では高々 :math:`256 \times 16 = 4096` 通りで済む（実際には、時間差の測定のために各候補を何度も試す必要がある）。

:numref:`code-timing-attack` は、この攻撃のシミュレーションである。実際の比較の時間差はナノ秒単位であり観測には多数の試行が必要になるため、ここでは 1 文字の比較ごとに待ち時間を入れて差を誇張している。

.. code-block:: text

   秘密の文字列: a91b23
     1 文字目: 'a'（202 μs）
     2 文字目: '9'（302 μs）
     3 文字目: '1'（405 μs）
     4 文字目: 'b'（505 μs）
     5 文字目: '2'（608 μs）
     6 文字目: '3'（比較結果が True になった）
   推定結果    : a91b23（一致: True）
   compare_digest による比較: True

対策は、データの内容によらず処理時間が一定になる比較関数を使うことである。Python では ``hmac.compare_digest()`` がこの目的のために用意されている。秘密の値（タグ、トークン、パスワードのハッシュ値など）を比較するときは、必ず ``hmac.compare_digest()`` を使う。

定数時間の実装
^^^^^^^^^^^^^^

タイミング攻撃の対象は比較処理だけではない。秘密の値によって分岐やメモリアクセスのパターンが変わる処理は、全て時間差を生む可能性がある。例えば、表を引いて実装した AES はキャッシュの状態から鍵が漏れることがあり、繰り返し二乗法で秘密鍵のビットが 1 のときだけ掛け算をする RSA の実装は、処理時間や消費電力から秘密鍵のビットが漏れる。暗号ライブラリは、こうした攻撃を防ぐために、秘密の値に依存しない一定の手順で処理する定数時間（constant-time）の実装を採用している。本書のおもちゃ実装はこの配慮をしていない。これも、おもちゃ実装を実際のシステムで使ってはならない理由の 1 つである。

パディングオラクル攻撃
----------------------

攻撃の原理
^^^^^^^^^^

パディングオラクル攻撃は、2002 年に Serge Vaudenay が発表した、CBC モードに対する選択暗号文攻撃である。サーバーが、受け取った暗号文を復号した結果のパディングが正しいかどうかを、エラーの種類や応答時間の違いによって漏らしてしまう場合に成立する。このように、攻撃者の問い合わせに対して特定の情報を答えてくれる存在を\ :term:`オラクル`\ と呼ぶ。

CBC モードの復号は :math:`P_i = D_K(C_i) \oplus C_{i-1}` である。攻撃者は、復号したい暗号文ブロック :math:`C_i` の直前に、自分で作ったブロック :math:`C'` を置いた 2 ブロックの暗号文 :math:`C' \| C_i` をサーバーに送る。サーバーが復号して得る平文は :math:`P' = D_K(C_i) \oplus C'` である。

攻撃者は、:math:`C'` の最後のバイトを 0 から 255 まで変えながら送る。パディングが正しいと判定されるのは、ほとんどの場合 :math:`P'` の最後のバイトが ``01`` になったときである。そのときの :math:`C'` の最後のバイトを :math:`g` とすると、:math:`D_K(C_i)` の最後のバイトは :math:`g \oplus \mathtt{01}` だと分かる。元の平文の最後のバイトは、これと本来の直前のブロック :math:`C_{i-1}` の最後のバイトとの排他的論理和で求まる。

次に、:math:`P'` の最後のバイトが ``02`` になるように :math:`C'` の最後のバイトを設定し、最後から 2 番目のバイトを 0 から 255 まで変えて、パディング ``02 02`` が正しいと判定される値を探す。これを繰り返せば、1 ブロックあたり高々 :math:`256 \times 16` 回の問い合わせで、鍵を知らずにブロック全体を復号できる。

実際の事例と対策
^^^^^^^^^^^^^^^^

パディングオラクル攻撃は、ASP.NET（2010 年）、SSL 3.0 に対する POODLE 攻撃（2014 年）など、多くの実システムで問題となった。2013 年の Lucky Thirteen 攻撃は、TLS の CBC 暗号スイートで、パディングの検査と MAC の計算にかかる時間のわずかな差をオラクルとして利用した。

根本的な対策は、:doc:`aead`\ で述べたとおり、AEAD または Encrypt-then-MAC を使い、改ざんされた暗号文を復号する前に拒否することである。エラーメッセージを統一するだけでは、処理時間の差などから情報が漏れることがある。

鍵の管理
--------

どれほど強力な暗号でも、鍵が漏れれば意味がない。鍵の管理では、次の点に注意する。

* 鍵をソースコードに直接書き込まない。ソースコードはリポジトリや配布物を通じて多くの人の目に触れる。鍵は環境変数、OS の鍵ストア、クラウドの鍵管理サービス（KMS）、シークレット管理サービスなどに保管する。
* 特に重要な鍵は、HSM（hardware security module）など、鍵を外部に取り出せない専用のハードウェアで管理する。
* 1 つの鍵を複数の用途（暗号化と MAC、暗号化と署名など）に使い回さない。必要な鍵は、HKDF などで用途ごとに導出する。
* 鍵を定期的に更新（ローテーション）し、漏洩時に備えて鍵を無効化・交換する手順を決めておく。
* 不要になった鍵は確実に消去する。

暗号を自作しない
----------------

本書では学習のために多くのアルゴリズムを実装したが、実際のシステムでは、暗号アルゴリズムやプロトコルを自作してはならない。これまで見てきたように、暗号の安全性は、パディングの検査方法、ナンスの生成方法、比較関数の処理時間といった細部に左右される。専門家が設計し、長年の解析に耐えてきたアルゴリズムと、多くの利用者によって検証されてきたライブラリを使うべきである。

Python では、次のライブラリを使うのが基本である。

* 標準ライブラリの ``hashlib`` [PyHashlib]_、``hmac``、``secrets`` [PySecrets]_、``ssl``
* ``cryptography`` [PyCrypto]_：AEAD、公開鍵暗号、署名、証明書などを幅広く提供する。本書のサンプルコードでも使用した。
* ``PyNaCl``：NaCl / libsodium のバインディング。安全な選択肢をあらかじめ選んだ、誤用しにくい API を提供する。
