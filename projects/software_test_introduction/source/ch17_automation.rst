17. テストの自動化と継続的インテグレーション
============================================

テストは、書いただけでは役に立たない。変更のたびに実行されて初めて、欠陥を早く知らせるという効果を発揮する。この章では、テストと静的解析を、人が意識しなくても実行される仕組みにする方法を学ぶ。

17.1 自動化の目的
-----------------

テストを手作業で実行する運用には、次の問題がある。

* 忙しいときほど実行が省かれ、欠陥が見逃される。
* 人によって、実行するテストやコマンドのオプションが異なる。
* 自分の環境でだけ成功し、ほかの人の環境では失敗することに気付けない。

テストの実行を自動化し、決まったタイミングで決まった方法で実行されるようにすると、これらの問題を解消できる。自動化の対象には、pytest によるテストだけでなく、13 章の flake8 と mypy、14 章のカバレッジの計測も含める。

17.2 設定をファイルにまとめる
-----------------------------

自動化の第一歩は、実行の方法をファイルに書き、誰が実行しても同じ結果になるようにすることである。本書のサンプルコードでは、次の 3 つのファイルに設定をまとめている。

.. list-table::
   :header-rows: 1
   :widths: 30 70

   * - ファイル
     - 内容
   * - ``pyproject.toml``
     - pytest、mypy、coverage.py の設定
   * - ``setup.cfg``
     - flake8 の設定（flake8 は ``pyproject.toml`` を読まないため）
   * - ``requirements-dev.txt``
     - テストと静的解析に使うパッケージの一覧

.. literalinclude:: ../examples/pyproject.toml
   :language: toml
   :caption: pyproject.toml
   :linenos:

.. literalinclude:: ../examples/requirements-dev.txt
   :language: text
   :caption: requirements-dev.txt
   :linenos:

``requirements-dev.txt`` を使うと、必要なパッケージを 1 つのコマンドでインストールできる。

.. code-block:: console
   :linenos:

   $ python -m pip install -r requirements-dev.txt

この例ではパッケージのバージョンを指定していないため、インストールする時期によって異なるバージョンが入る。新しいバージョンで検査の規則が変わり、昨日まで成功していた検査が失敗することもある。結果の再現性を重視する場合は、``pytest==9.1.1`` のようにバージョンを固定する。

設定が揃えば、すべての検査は次の 4 つのコマンドで実行できる。

.. code-block:: console
   :linenos:

   $ python -m flake8 .
   $ python -m mypy .
   $ python -m coverage run -m pytest
   $ python -m coverage report --fail-under=90

``--fail-under=90`` は、カバレッジが 90 % を下回ったときに、コマンドを失敗（終了コード 2）させるオプションである。

17.3 コミットの前に検査する
---------------------------

Git には、コミットなどの操作の前後に、決まった処理を実行するフックという仕組みがある。pre-commit というツールを使うと、コミットの前に実行する検査を設定ファイルで管理できる。

.. literalinclude:: ../examples/ch17_automation/pre-commit-config.yaml
   :language: yaml
   :caption: ch17_automation/pre-commit-config.yaml
   :linenos:

このファイルを、リポジトリのルートに ``.pre-commit-config.yaml`` という名前で置き、次のコマンドを実行する。

.. code-block:: console
   :linenos:

   $ python -m pip install pre-commit
   $ python -m pre_commit install

以降、``git commit`` を実行するたびに flake8、mypy、pytest が実行され、いずれかが失敗するとコミットが中止される。欠陥のあるコードがリポジトリに入る前に止められる。

コミットのたびに実行するため、時間のかかる検査を含めると開発の妨げになる。テストが多くなり、実行に時間がかかるようになったら、コミットの前には速いテストだけを実行し（8 章の ``-m "not slow"`` など）、すべてのテストは次の継続的インテグレーションで実行するとよい。

17.4 継続的インテグレーション
-----------------------------

:term:`継続的インテグレーション`\ （Continuous Integration、CI）は、開発者が変更を頻繁に共有のリポジトリに統合し、統合のたびに自動でビルドとテストを行う開発の方法である。各開発者の環境に依存せず、決まった環境でテストが実行されるため、「自分の環境では動く」という問題も見つけられる。

CI を行うための仕組みには、大きく分けて次の 2 種類がある。

.. list-table::
   :header-rows: 1
   :widths: 30 70

   * - 種類
     - 例
   * - リポジトリのサービスに組み込まれたもの
     - GitHub Actions（GitHub）、GitLab CI/CD（GitLab）
   * - 自分たちで運用する CI サーバー
     - Jenkins

どの仕組みでも、「リポジトリの変更をきっかけに、決まった手順を実行し、結果を知らせる」という点は変わらない。手順の中身は、17.2 節の 4 つのコマンドそのものである。この章では、GitHub Actions と Jenkins の 2 つを例に、設定の書き方を紹介する。

17.5 GitHub Actions
-------------------

GitHub では、GitHub Actions という機能で CI を行える。次の設定ファイルを、リポジトリの ``.github/workflows/test.yml`` に置くと、``main`` ブランチへの push と、pull request のたびにテストが実行される。

.. literalinclude:: ../examples/ch17_automation/test.yml
   :language: yaml
   :caption: ch17_automation/test.yml
   :linenos:

設定の内容は次のとおりである。

.. list-table::
   :header-rows: 1
   :widths: 20 80

   * - 行
     - 内容
   * - 7～10
     - 実行のきっかけ。``main`` ブランチへの push と、すべての pull request で実行する。
   * - 14
     - 実行する環境。GitHub が用意する Ubuntu の最新版を使う。
   * - 15～17
     - Python の 3 つのバージョンで、同じ手順を並行して実行する。
   * - 19～22
     - リポジトリのコードを取得し、Python をインストールする。
   * - 23～32
     - パッケージをインストールし、17.2 節の 4 つのコマンドを順に実行する。いずれかが失敗すると、以降の手順は実行されず、全体が失敗となる。

pull request の画面には、CI の結果が表示される。レビューの前に CI が成功していることを確かめる運用にすると、レビューする人は、flake8 や mypy で見つかる問題やテストの失敗を気にせずに、設計や仕様の観点に集中できる。

17.6 Jenkins
------------

Jenkins は、オープンソースの CI サーバーである。自分たちのサーバーにインストールして運用するため、次のような場合に使われる。

* ソースコードを社外のサービスに置けない。
* 社内のネットワークにあるデータベースや検証用の機器を、テストで使う必要がある。
* GitHub 以外のバージョン管理システムを使っている。

Jenkins では、実行する手順をパイプラインと呼び、``Jenkinsfile`` という名前のファイルに書く。``Jenkinsfile`` をリポジトリに含めておくと、手順の変更もコードと同じようにバージョン管理とレビューの対象にできる。次の例は、17.5 節の GitHub Actions と同じ検査を行う ``Jenkinsfile`` である。

.. literalinclude:: ../examples/ch17_automation/Jenkinsfile
   :language: groovy
   :caption: ch17_automation/Jenkinsfile
   :linenos:

``Jenkinsfile`` は、Groovy という言語をもとにした構文で書く。この例で使っている Declarative Pipeline は、決まった形のブロックを組み合わせて手順を書く書き方である。設定の内容は次のとおりである。

.. list-table::
   :header-rows: 1
   :widths: 20 80

   * - 行
     - 内容
   * - 7
     - 手順を実行するエージェント（ビルドを実行するマシン）。``any`` は、使えるエージェントのどれでもよいことを表す。
   * - 9～12
     - 実行時間の上限（30 分）と、保存しておく過去のビルドの数（20 件）。テストが止まらなくなった場合に、エージェントを占有し続けることを防ぐ。
   * - 14～17
     - 環境変数 ``PY`` に、仮想環境の Python のパスを設定する。
   * - 19～42
     - 4 つのステージ（段階）。Install で仮想環境を作ってパッケージをインストールし、Lint、Type check、Test で 17.2 節の 4 つのコマンドを実行する。あるステージが失敗すると、以降のステージは実行されない。
   * - 38
     - ``--junitxml`` オプションで、テストの結果を JUnit 形式の XML ファイルに書き出す。
   * - 44～49
     - ``post`` の ``always`` は、成功しても失敗しても最後に実行される処理である。``junit`` ステップで 38 行目の XML ファイルを読み込む。

GitHub Actions の例と異なり、Python をインストールする手順がない。Jenkins では、エージェントにあらかじめ必要なソフトウェアを用意しておくのが一般的だからである。また、1 つのエージェントは複数のジョブで共有されることが多いため、ジョブの作業フォルダー（ワークスペース）に仮想環境を作ってパッケージをインストールし、ほかのジョブが使うパッケージと混ざらないようにしている。本書のサンプルコードの ``setup.cfg`` と ``pyproject.toml`` では、flake8 と mypy がこの ``.venv`` フォルダーを検査しないように除外している。

``junit`` ステップは、Jenkins の初期設定で推奨されるプラグインに含まれる JUnit プラグインが提供する。読み込んだテストの結果は、Jenkins の画面で、テストの件数や失敗したテストの名前、ビルドごとの件数の推移として表示される。失敗したテストの出力も画面から確かめられるため、エージェントのログを探す必要がない。

エージェントが Windows の場合は、``sh`` ステップの代わりに ``bat`` ステップを使い、仮想環境の Python のパスを ``.venv\Scripts\python`` に変える。

実行のきっかけは、Jenkins のジョブの設定で指定する。リポジトリのサービスから変更を通知する Webhook を使う方法や、一定の間隔でリポジトリの変更を確かめる方法がある。ブランチごとに同じ ``Jenkinsfile`` を実行したい場合は、Multibranch Pipeline という種類のジョブを使う。Jenkins のインストールやジョブの作り方は、付録 D に挙げた公式文書を参照してほしい。

17.7 CI の仕組みの選び方
------------------------

GitHub Actions と Jenkins の主な違いを次に示す。

.. list-table::
   :header-rows: 1
   :widths: 25 37 38

   * - 観点
     - GitHub Actions
     - Jenkins
   * - 運用
     - GitHub が運用する。サーバーの管理は不要である。
     - 自分たちでサーバーをインストールし、更新やバックアップを行う。
   * - 実行する環境
     - GitHub が用意する仮想マシン。自分たちのマシン（セルフホストランナー）も使える。
     - 自分たちで用意したエージェント。
   * - 設定ファイル
     - ``.github/workflows/*.yml``\ （YAML）
     - ``Jenkinsfile``\ （Groovy をもとにした構文）
   * - 機能の拡張
     - 公開されているアクションを組み合わせる。
     - プラグインを追加する。
   * - 向いている場合
     - コードを GitHub で管理しており、特別な実行環境を必要としない。
     - 社内のネットワークや特定の機器が必要である。GitHub 以外のバージョン管理システムを使っている。

どちらを使う場合も、CI の手順の中身は 17.2 節のコマンドと同じにしておくとよい。開発者が手元で実行する検査と CI で実行する検査が一致していれば、CI で失敗したときに、手元で同じコマンドを実行して原因を調べられる。また、CI の仕組みを乗り換えるときにも、設定ファイルを書き直すだけで済む。

17.8 回帰テストの運用
---------------------

CI で回帰テストを継続的に実行するときは、次の点に注意する。

* **失敗したら最優先で直す**：CI の失敗を放置すると、その後の変更による新たな失敗が埋もれてしまう。失敗したら、原因となった変更を直すか、いったん取り消す。
* **不安定なテストを放置しない**：16 章で述べたとおり、不安定なテストは CI の信頼性を損なう。見つけたら優先して直す。
* **実行時間を監視する**：CI の結果が出るまでに時間がかかると、開発者は結果を待たずに次の作業に移り、失敗への対応が遅れる。``pytest --durations=10`` で遅いテストを見つけて改善する。
* **遅いテストは分けて実行する**：時間のかかる結合テストや E2E テストは、マーカーで区別し、夜間にまとめて実行するなどの方法をとる。
* **欠陥を直したら、再現するテストを追加する**：見つかった欠陥を再現するテストを書き、それが失敗することを確かめてから修正する。以降は、同じ欠陥の再発を回帰テストが検出する。

17.9 まとめ
-----------

* テストと静的解析の実行方法を設定ファイルにまとめ、誰が実行しても同じ結果になるようにする。
* pre-commit を使うと、コミットの前に検査を自動で実行できる。
* 継続的インテグレーションでは、変更を統合するたびに決まった環境でテストを実行する。GitHub では GitHub Actions を、自分たちでサーバーを運用する場合は Jenkins などを使える。
* どの CI の仕組みでも、手元で実行する検査と同じコマンドを実行するようにしておく。
* CI の失敗は最優先で直し、不安定なテストや遅いテストを放置しない。
