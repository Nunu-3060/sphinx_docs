3. テストの分類
===============

テストにはさまざまな種類があり、「単体テスト」「回帰テスト」「ブラックボックステスト」のように、異なる観点の名前が混在して使われる。この章では、テストを分類する主な観点を整理する。

3.1 テストレベル
----------------

:term:`テストレベル`\ は、テストする対象の大きさによる分類である。小さな部品から始めて、組み合わせた全体へと対象を広げていく。

.. list-table::
   :header-rows: 1
   :widths: 18 27 35 20

   * - テストレベル
     - 対象
     - 主な目的
     - 主な実施者
   * - :term:`単体テスト`
     - 関数、クラス、モジュールなど、単独でテストできる最小の部品
     - 部品が仕様どおりに動くことを確かめる。
     - 開発者
   * - :term:`結合テスト`
     - 複数の部品の組み合わせ、データベースや外部サービスとの接続
     - 部品間のインターフェースややり取りが正しいことを確かめる。
     - 開発者、テスト担当者
   * - :term:`システムテスト`
     - システム全体
     - システムが要求仕様を満たしていることを、利用者に近い視点で確かめる。
     - テスト担当者
   * - :term:`受け入れテスト`
     - システム全体と、それを使う業務
     - 利用者や発注者が、システムを業務で使えることを確かめる。
     - 利用者、発注者

単体テストはコンポーネントテスト、結合テストは統合テストとも呼ばれる。本書の第 II 部では、主に単体テストと結合テストを扱う。これらは開発者自身が書き、自動で実行することが多いテストである。

3.2 テストタイプ
----------------

:term:`テストタイプ`\ は、何を確かめるかによる分類である。どのテストレベルでも、複数のテストタイプを組み合わせて行う。

.. list-table::
   :header-rows: 1
   :widths: 25 75

   * - テストタイプ
     - 内容
   * - 機能テスト
     - ソフトウェアが「何をするか」を確かめる。送料が正しく計算されるか、注文を取り消せるかなど。
   * - 非機能テスト
     - ソフトウェアが「どのように動くか」を確かめる。性能（応答時間や処理量）、セキュリティ、使いやすさ、信頼性、移植性などを対象とする。
   * - 確認テスト
     - 欠陥を修正した後、その欠陥が確かに直ったことを確かめる。再テストとも呼ぶ。
   * - :term:`回帰テスト`
     - 変更によって、変更していない部分の機能が壊れていないことを確かめる。

確認テストと回帰テストは混同されやすい。確認テストは「直したものが直ったか」を、回帰テストは「直していないものが壊れていないか」を確かめる。変更のたびに回帰テストを手作業で行うのは大きな負担であるため、回帰テストはテストの自動化の効果が特に大きい分野である。

3.3 静的テストと動的テスト
--------------------------

:term:`動的テスト`\ は、ソフトウェアを実行して確かめるテストである。本書で書くテストコードの多くはこれに当たる。

:term:`静的テスト`\ は、ソフトウェアを実行せずに確かめるテストである。仕様書やコードのレビュー、静的解析ツールによる検査が含まれる。静的テストは、実行できるコードがまだない段階でも行えるうえ、動的テストでは見つけにくい欠陥（使われていない変数、保守しにくい構造、仕様の矛盾など）を見つけられる。Python での静的解析は 13 章で扱う。

3.4 ブラックボックステストとホワイトボックステスト
--------------------------------------------------

テストケースを何に基づいて設計するかによって、テストは次のように分類される。

.. list-table::
   :header-rows: 1
   :widths: 30 70

   * - 分類
     - 内容
   * - :term:`ブラックボックステスト`
     - テスト対象の内部構造を見ずに、仕様（入力と期待される出力）に基づいてテストケースを設計する。仕様ベースのテストとも呼ぶ。4 章で扱う。
   * - :term:`ホワイトボックステスト`
     - テスト対象の内部構造（コードの分岐や条件）に基づいてテストケースを設計する。構造ベースのテストとも呼ぶ。5 章で扱う。
   * - 経験ベースのテスト
     - テスト担当者の知識や経験に基づいてテストケースを設計する。過去に欠陥が多かった入力を試すエラー推測などがある。4 章で扱う。

ブラックボックステストは、仕様に書かれているのに実装されていない機能を見つけられる。一方、ホワイトボックステストは、仕様からは想像しにくい内部の分岐のテスト漏れを見つけられる。両者は補い合う関係にあり、どちらか一方だけで十分ということはない。

3.5 V 字モデル
--------------

:term:`V 字モデル`\ は、開発の各工程とテストレベルの対応を V 字の形で表したモデルである。左側を上から下へ進むにつれて設計が詳細になり、右側を下から上へ進むにつれてテストの対象が大きくなる。

.. graphviz::
   :caption: V 字モデル

   digraph vmodel {
       rankdir=TB;
       nodesep=0.6;
       node [shape=box, style="rounded,filled", fillcolor="#e8f0fe", width=1.8];
       edge [color="#555555"];

       req  [label="要求定義"];
       sys  [label="システム設計"];
       arch [label="方式設計"];
       det  [label="詳細設計"];
       code [label="実装", fillcolor="#fff4d6"];
       ut   [label="単体テスト", fillcolor="#e6f4ea"];
       it   [label="結合テスト", fillcolor="#e6f4ea"];
       st   [label="システムテスト", fillcolor="#e6f4ea"];
       at   [label="受け入れテスト", fillcolor="#e6f4ea"];

       req -> sys -> arch -> det -> code;
       code -> ut -> it -> st -> at;

       {rank=same; req; at;}
       {rank=same; sys; st;}
       {rank=same; arch; it;}
       {rank=same; det; ut;}

       edge [style=dashed, arrowhead=none, color="#999999"];
       req -> at;
       sys -> st;
       arch -> it;
       det -> ut;
   }

点線は、左側の工程の成果物が、右側のテストの基準になることを表す。たとえば、受け入れテストは要求定義に基づいて、単体テストは詳細設計に基づいて行う。V 字モデルは図の形から、設計がすべて終わってからテストを始めるものと誤解されやすい。しかし、テストの設計は左側の各工程と並行して始められる。要求定義の段階で受け入れテストのテストケースを考えれば、要求の曖昧さを早く見つけられる（2 章の原則 3）。

3.6 テストピラミッド
--------------------

:term:`テストピラミッド`\ は、自動化するテストの数の望ましい配分を表したモデルである。

.. graphviz::
   :caption: テストピラミッド

   digraph pyramid {
       rankdir=TB;
       nodesep=0.2;
       ranksep=0.05;
       node [shape=box, style=filled, fixedsize=true, height=0.6, fontsize=13];
       edge [style=invis];

       e2e  [label="E2E テスト\n（少ない・遅い・壊れやすい）", width=2.6, fillcolor="#fde2e1"];
       it   [label="結合テスト", width=4.2, fillcolor="#fff4d6"];
       unit [label="単体テスト\n（多い・速い・安定）", width=5.8, fillcolor="#e6f4ea"];

       e2e -> it -> unit;
   }

土台となる単体テストを最も多く書き、上の層ほど数を減らす。上の層ほど、次の理由でテストの費用が大きくなるためである。

* 準備が大がかりになる（データベースやブラウザーの起動など）。
* 実行に時間がかかる。
* 環境や通信の影響を受けて、コードに問題がなくても失敗することがある。
* 失敗したときに、原因の箇所を特定しにくい。

ただし、単体テストだけでは、部品を組み合わせたときの問題は見つけられない。ピラミッドの形は「上の層は不要」という意味ではなく、「それぞれの層で確かめるべきことを、最も安い層で確かめる」という方針を表している。

E2E テスト（End-to-End テスト）は、利用者の操作を最初から最後まで模倣して、システム全体を通して確かめるテストである。

3.7 まとめ
----------

* テストレベルは対象の大きさによる分類であり、単体テスト、結合テスト、システムテスト、受け入れテストがある。
* テストタイプは確かめる内容による分類である。変更のたびに行う回帰テストは、自動化の効果が大きい。
* ソフトウェアを実行する動的テストと、実行しない静的テストがある。
* 仕様に基づくブラックボックステストと、内部構造に基づくホワイトボックステストは補い合う。
* テストピラミッドは、速く安定した単体テストを土台にするという、自動テストの配分の方針を表す。
