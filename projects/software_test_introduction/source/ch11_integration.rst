11. 結合テスト
==============

9 章のテストダブルを使うと、依存先から切り離してテスト対象をテストできる。しかし、実際のファイルやデータベースと組み合わせたときに正しく動くかは、テストダブルでは確かめられない。この章では、部品と外部の資源を組み合わせて確かめる結合テストの書き方を学ぶ。

11.1 結合テストで確かめること
-----------------------------

結合テストでは、単体テストでは確かめられない、部品の間や外部の資源との「つなぎ目」を確かめる。たとえば、次のような欠陥は結合テストで見つかる。

* ファイルの文字コードや改行コードの扱いの誤り
* SQL の文法の誤りや、テーブルの制約の違反
* 外部の API の応答の形式についての思い込み
* 部品の間での、引数の順序や単位（円とドルなど）の食い違い

結合テストは、単体テストより準備が大がかりで、実行にも時間がかかる。テストピラミッド（3 章）に従い、ロジックの細かな場合分けは単体テストで確かめ、結合テストはつなぎ目の確認に絞るとよい。

この章では、自動テストとして手軽に扱える外部の資源として、ファイル、SQLite のデータベース、HTTP の API を取り上げる。

.. literalinclude:: ../examples/ch11_integration/test_order_repository.py
   :language: python
   :caption: ch11_integration/test_order_repository.py
   :linenos:

``repo`` fixture（11～18 行目）は、8.3 節の ``yield`` を使う fixture である。テストの前にデータベースとテーブルを作り、テストの後に接続を閉じる。

``test_duplicate_id_is_rejected`` と ``test_negative_amount_is_rejected`` は、テーブルの主キーと ``CHECK`` 制約が働くことを確かめている。これらは SQL とデータベースが実際に動いて初めて確かめられる性質であり、データベースをテストダブルに置き換えた単体テストでは確かめられない。また、``test_duplicate_id_is_rejected`` の最後の ``assert`` は、失敗した ``INSERT`` がロールバックされ、データベースに不完全なデータが残らないことを確かめている。

本番で PostgreSQL や MySQL などを使う場合、SQLite でのテストだけでは、SQL の方言や型の違いによる欠陥を見逃すおそれがある。その場合は、本番と同じ種類のデータベースをテスト用に起動して結合テストを行う。コンテナーを使うと、テストのたびに同じ状態のデータベースを用意しやすい。

11.4 HTTP の API を使うテスト
-----------------------------

為替レートを Web API から取得するクライアントを題材にする。

.. literalinclude:: ../examples/ch11_integration/exchange_client.py
   :language: python
   :caption: ch11_integration/exchange_client.py
   :linenos:

``ExchangeClient`` は、HTTP クライアントの ``httpx.Client`` をコンストラクターで受け取る（17～18 行目）。10 章の依存性の注入である。

外部の API を使うテストで本物のサーバーに接続すると、ネットワークの状態や API の利用制限によってテストが不安定になる。httpx には、実際の通信の代わりに関数で応答を返す ``httpx.MockTransport`` が用意されている。これを使うと、HTTP のリクエストの組み立てと応答の解析は本物の httpx で行いながら、通信の部分だけを差し替えられる。

.. literalinclude:: ../examples/ch11_integration/test_exchange_client.py
   :language: python
   :caption: ch11_integration/test_exchange_client.py
   :linenos:

``fake_api``\ （11～20 行目）は、リクエストを受け取って応答を返す関数で、本物の API の代わりを務めるフェイクである。サポートしない通貨に対しては、ステータスコード 400 の応答を返す。これにより、``test_error_response_raises``\ （40～42 行目）で、API がエラーを返した場合の動作を確かめられる。本物の API では、エラーの応答を意図して返させるのが難しいことが多い。

``test_request_parameters``\ （45～59 行目）は、送信されたリクエストを記録するスパイとして ``handler`` を使い、クエリーのパラメーターが正しく組み立てられていることを確かめている。

この方法でも、本物の API の応答の形式が想定と異なれば、欠陥は見つからない。本物の API に接続するテストも用意しておき、8 章のマーカーで区別して、普段の実行からは除外する運用がよく行われる。

11.5 テストデータの管理
-----------------------

結合テストでは、テストデータの管理が重要になる。次の点に注意する。

* **テストごとに独立したデータを用意する**：あるテストが作ったデータを、別のテストが前提にしてはならない。実行の順序を変えたり、1 つのテストだけを実行したりしたときに失敗するようになる。
* **後始末を確実に行う**：``tmp_path`` や ``yield`` を使う fixture を使い、テストが失敗しても後始末が実行されるようにする。
* **必要最小限のデータにする**：テストに関係のないデータが多いと、テストの意図が読み取りにくくなり、実行も遅くなる。
* **本番のデータをそのまま使わない**：個人情報などを含む可能性があるうえ、データが変わるとテストの結果も変わる。

11.6 まとめ
-----------

* 結合テストでは、部品の間や外部の資源とのつなぎ目を確かめる。ロジックの場合分けは単体テストに任せる。
* ファイルを使うテストでは ``tmp_path`` を使い、テストごとに独立した一時フォルダーで読み書きする。
* SQLite のインメモリデータベースを使うと、テストごとに空のデータベースを手軽に用意できる。
* HTTP の API は ``httpx.MockTransport`` で通信の部分だけを差し替え、エラーの応答なども再現する。
* テストデータはテストごとに独立させ、後始末を確実に行う。
