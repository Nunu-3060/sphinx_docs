コード品質と静的解析
====================

:term:`静的解析`\ とは、プログラムを実行せずに、ソースコードを解析して問題を見つける手法です。静的解析は、レビューよりも速く、テストよりも早い段階で、機械的に見つけられる問題を確実に見つけます。この章では、Python での静的解析の代表的なツールとその使い方を説明します。

コーディング規約
----------------

:term:`コーディング規約`\ とは、コードの書き方についてチームで合意した決まりです。書き方がそろっていると、読む人は書き方の違いに気を取られず、処理の内容に集中できます。また、レビューで書き方の好みについて議論する時間を減らせます。

Python では、PEP 8（Style Guide for Python Code）が標準的なコーディング規約として広く使われています。PEP 8 には、例えば次のような決まりがあります。

* インデントは空白 4 文字にします。
* 1 行の長さは 79 文字以内にします。
* トップレベルの関数とクラスの定義の前後には、空行を 2 行入れます。
* ``import`` 文は 1 行に 1 つのモジュールを書きます。
* ``None`` との比較には、``==`` ではなく ``is`` を使います。
* 関数名と変数名は小文字のスネークケース（``calc_total``）、クラス名はキャメルケース（``WeatherSource``）にします。

ただし、PEP 8 自身が述べているとおり、規約に従うこと自体が目的ではありません。プロジェクトに独自の規約がある場合はそちらを優先し、規約に従うとかえって読みにくくなる場合は例外を認めます。大切なのは、チームの中で一貫していることです。

リンターとフォーマッター
------------------------

コーディング規約を人の目だけで守るのは困難です。規約違反や欠陥の可能性がある書き方を自動で検出するツールを\ :term:`リンター`\ と呼び、規約に沿ってコードを自動で整形するツールをフォーマッターと呼びます。

.. list-table:: Python の代表的なリンターとフォーマッター
   :header-rows: 1
   :widths: 20 80

   * - ツール
     - 説明
   * - flake8
     - PEP 8 の違反を検出する pycodestyle、未使用の変数や import などを検出する pyflakes、関数の複雑さを測る mccabe をまとめたリンターです。本書のサンプルコードは flake8 で検査しています。
   * - Ruff
     - Rust で実装された高速なリンター兼フォーマッターです。flake8 とその拡張機能、isort（import 文の並べ替え）、Black（フォーマッター）などに相当する機能を 1 つのツールで提供します。新しく始めるプロジェクトでは有力な選択肢です。
   * - Black
     - 設定項目をほとんど持たないフォーマッターです。整形の結果が 1 通りに決まるため、書き方の議論をなくせます。

   ch04_before.py:3:1: F401 'sys' imported but unused
   ch04_before.py:3:10: E401 multiple imports on one line
   ch04_before.py:4:1: E302 expected 2 blank lines, found 0

   ch04_before.py:4:23: E251 unexpected spaces around keyword / parameter equals
   ch04_before.py:5:10: E225 missing whitespace around operator
   ch04_before.py:8:13: E711 comparison to None should be 'if cond is None:'
   ch04_before.py:12:1: E302 expected 2 blank lines, found 1

各行は「ファイル名:行番号:列番号: エラーコード メッセージ」の形式です。エラーコードの先頭の文字は、検出したツールを表します。

.. list-table::
   :header-rows: 1
   :widths: 15 25 60

   * - 先頭の文字
     - 検出したツール
     - 主な内容
   * - E、W
     - pycodestyle
     - PEP 8 の違反（E はエラー、W は警告）
   * - F
     - pyflakes
     - 未使用の import や変数、未定義の名前など、欠陥の可能性が高い書き方
   * - C9
     - mccabe
     - 循環的複雑度が設定した上限を超えた関数

E で始まる指摘の多くは見た目の問題ですが、F で始まる指摘は欠陥につながることがあります。例えば、F821（未定義の名前）は、実行するとその行で ``NameError`` が発生することを意味します。

型検査
------

Python は動的型付けの言語であり、型の誤りは実行するまで分かりません。関数やクラスに型ヒントを書き、:term:`型検査`\ のツールで検査すると、型の誤りを実行前に見つけられます。代表的な型検査器が mypy です。

先ほどの ch04_before.py を mypy で検査すると、次の結果が得られます。サンプルコードの setup.cfg では、mypy の strict モード（型ヒントの省略を許さない、最も厳しい設定）を有効にしています。

.. code-block:: console
   :linenos:

   $ mypy ch04_before.py
   ch04_before.py:4: error: Function is missing a type annotation  [no-untyped-def]
   ch04_before.py:13: error: Incompatible return value type (got "float", expected "str")  [return-value]
   Found 2 errors in 1 file (checked 1 source file)

2 行目は、``calc`` 関数に型ヒントがないことを指摘しています。3 行目は、``label`` 関数が ``str`` を返すと宣言しているのに、実際には ``float`` を返していることを指摘しています。この欠陥はテストでも見つけられますが、テストを書く前に、しかも数秒で見つけられる点が型検査の利点です。

型検査を既存のプロジェクトに導入する場合は、最初から strict モードを有効にすると大量の指摘が出て対応しきれません。まず標準の設定で導入し、新しく書くコードから型ヒントを付け、モジュールごとに段階的に厳しくしていく方法が現実的です。

複雑度の測定
------------

関数の中の分岐が多いと、読みにくく、テストしにくく、欠陥が入り込みやすくなります。関数の複雑さを測る代表的な指標が、T. J. McCabe が提案した\ :term:`循環的複雑度`\ です。循環的複雑度 :math:`M` は、関数の制御の流れを表すグラフの辺の数 :math:`E`、節点の数 :math:`N`、連結成分の数 :math:`P` を使って、次の式で求めます。

.. math::

   M = E - N + 2P

1 つの関数については :math:`P = 1` であり、:math:`M` は「分岐の数 + 1」に等しくなります。例えば、``if`` 文を 4 つ含む関数の循環的複雑度は 5 です。循環的複雑度は、その関数のすべての分岐を通すために必要な、独立した経路の数を表します。そのため、テストケースの数の目安にもなります。

flake8 では ``--max-complexity`` オプションで上限を設定でき、上限を超えた関数を C901 として報告します。次の例では、説明のために上限を 3 に下げて、第 7 章のサンプルコードを検査しています。

.. code-block:: console
   :linenos:

   $ flake8 --max-complexity 3 ch07_fee.py
   ch07_fee.py:17:1: C901 'admission_fee' is too complex (5)

McCabe は上限の目安として 10 を提案しており、本書のサンプルコードの setup.cfg でも 10 を設定しています。上限を超えた関数は、処理の一部を別の関数に切り出す、条件の組み合わせを表（辞書など）で表すといった方法で分割を検討します。

セキュリティ観点の静的解析
--------------------------

静的解析は、セキュリティ上の問題を見つけるためにも使えます。Python の代表的なツールが bandit です。bandit は、セキュリティ上の危険がある書き方を検出し、重大度と確信度を付けて報告します。

.. list-table:: bandit が検出する問題の例
   :header-rows: 1
   :widths: 15 40 45

   * - 検査 ID
     - 検出する書き方
     - 危険の内容
   * - B105
     - パスワードらしき文字列をコードに直接書いている
     - ソースコードの漏えいがパスワードの漏えいにつながります。
   * - B301
     - ``pickle`` で外部のデータを読み込んでいる
     - 細工されたデータで任意のコードを実行されるおそれがあります。
   * - B602
     - ``subprocess`` で ``shell=True`` を指定している
     - 外部の入力がコマンドに混入すると、任意のコマンドを実行されるおそれがあります（コマンドインジェクション）。

bandit は次のように実行します。

.. code-block:: console
   :linenos:

   $ python -m pip install bandit
   $ bandit -r src/

静的解析によるセキュリティの検査は、問題の一部しか見つけられません。設計段階での脅威の分析、依存パッケージの脆弱性の検査（第 12 章を参照）、セキュリティテストと組み合わせて使います。

docstring とドキュメントの品質
------------------------------

コードの品質には、そのコードを説明するドキュメントの品質も含まれます。関数やクラスの docstring には、次の内容を書きます。

* その関数が何をするのか（どのように実装しているかではなく）
* 引数と戻り値の意味、取りうる値の範囲
* 送出する例外と、その条件
* 必要であれば使い方の例

docstring の書き方には、Google スタイル、NumPy スタイル、reStructuredText スタイルなどがあります。本書のサンプルコードは Google スタイル（``Args:``、``Returns:``、``Raises:`` の見出しを使う書き方）で書いています。どのスタイルを使うかはチームで決め、統一してください。

ドキュメントの品質で最も問題になるのは、コードの変更にドキュメントが追従せず、内容が古くなることです。古いドキュメントは、ドキュメントがない状態よりも害が大きいことがあります。これを防ぐ方法として、次のようなものがあります。

* docstring に書いた使い方の例を、doctest で自動的に実行して確認します。
* コードレビューの観点に「ドキュメントが更新されているか」を含めます（第 5 章を参照）。
* 完了の定義にドキュメントの更新を含めます（第 2 章を参照）。

この章のまとめ
--------------

* コーディング規約は、書き方をそろえて読みやすくし、レビューの負担を減らします。
* flake8 や Ruff などのリンターで規約違反と欠陥の可能性を、mypy で型の誤りを、実行前に機械的に見つけられます。
* 循環的複雑度は関数の複雑さの指標であり、10 程度を上限の目安にします。
* bandit を使うと、セキュリティ上の危険がある書き方を検出できます。
* ドキュメントもコードの品質の一部です。コードの変更に追従させる仕組みを作ります。
