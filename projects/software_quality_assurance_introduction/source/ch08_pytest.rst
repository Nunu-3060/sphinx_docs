.. _ch08:

Python によるテストの実践
=========================

この章では、Python で自動テストを書くための実践的な方法を、テストフレームワーク pytest を中心に説明します。第 6 章と第 7 章で学んだ考え方を、実際のコードに落とし込みます。

pytest の基本
-------------

Python の標準ライブラリには unittest というテストフレームワークがありますが、現在は pytest が広く使われています。pytest では、テストを普通の関数として書け、確認には Python の ``assert`` 文をそのまま使えます。

テストの書き方と実行
^^^^^^^^^^^^^^^^^^^^

pytest は、名前が ``test_`` で始まるファイル（または ``_test.py`` で終わるファイル）の中にある、名前が ``test_`` で始まる関数をテストとして実行します。

.. code-block:: python
   :linenos:

   from ch08_rle import encode


   def test_encode_example() -> None:
       assert encode("aaab") == [("a", 3), ("b", 1)]

``assert`` 文が失敗すると、pytest は比較した値の違いを詳しく表示します。そのため、unittest の ``assertEqual`` のような専用の確認メソッドを覚える必要がありません。

テストは次のように実行します。

.. code-block:: console
   :linenos:

   $ pytest              # カレントディレクトリ以下のテストをすべて実行します。
   $ pytest -v           # テストケースごとの結果を表示します。
   $ pytest -x           # 最初に失敗したところで止めます。
   $ pytest -k advice    # 名前に「advice」を含むテストだけを実行します。
   $ pytest --lf         # 前回失敗したテストだけを実行します。

例外の確認
^^^^^^^^^^

例外が送出されることを確認するには、``pytest.raises`` を ``with`` 文で使います。

.. code-block:: python
   :linenos:

   import pytest

   from ch07_fee import admission_fee


   def test_negative_age_raises_value_error() -> None:
       with pytest.raises(ValueError, match="範囲外"):
           admission_fee(-1)

7 行目の ``match`` 引数には正規表現を指定し、例外のメッセージがそれに一致することも確認できます。

パラメーター化
^^^^^^^^^^^^^^

同じ手順のテストを、入力と期待値だけを変えて繰り返す場合は、``@pytest.mark.parametrize`` を使います。第 7 章のサンプルコード（test_ch07_fee.py）は、この方法で境界値のテストを記述しています。パラメーター化を使うと、テストケースの追加が表に 1 行を加えるだけで済み、どの値で失敗したかも結果に表示されます。

フィクスチャ
^^^^^^^^^^^^

複数のテストで共通の準備（テストデータの作成、一時ファイルの用意、データベースへの接続など）が必要な場合は、:term:`フィクスチャ`\ を使います。フィクスチャは ``@pytest.fixture`` を付けた関数として定義し、テスト関数の引数に同じ名前を書くと、pytest がその戻り値を渡します。

.. code-block:: python
   :linenos:

   from collections.abc import Iterator
   from pathlib import Path

   import pytest


   @pytest.fixture
   def order_file(tmp_path: Path) -> Iterator[Path]:
       path = tmp_path / "order.csv"
       path.write_text("price,qty\n100,2\n300,1\n", encoding="utf-8")
       yield path
       # yield より後の処理は、テストの終了後に実行されます（後片付け）。


   def test_read_order(order_file: Path) -> None:
       assert order_file.read_text(encoding="utf-8").startswith("price")

8 行目の ``tmp_path`` は pytest が標準で提供するフィクスチャで、テストごとに新しい一時ディレクトリを用意します。テストが実際のファイルを書き換えたり、テスト同士が同じファイルを共有して影響し合ったりすることを防げます。

複数のテストファイルで使うフィクスチャは、conftest.py という名前のファイルに書くと、同じディレクトリ以下のすべてのテストから使えます。

テストダブル
------------

テスト対象が外部のシステム（Web API、データベース、メールサーバーなど）に依存していると、テストが遅くなり、外部の状態によって結果が変わり、異常系（通信エラーなど）を再現しにくくなります。そこで、テストのときだけ外部の部品を偽物に差し替えます。この偽物を\ :term:`テストダブル`\ と呼びます。

.. list-table:: テストダブルの種類
   :header-rows: 1
   :widths: 20 80

   * - 種類
     - 説明
   * - ダミー
     - 引数を埋めるためだけに渡す、実際には使われないオブジェクトです。
   * - スタブ
     - 呼び出されると、あらかじめ決めた値を返します。テスト対象への「入力」を制御するために使います。
   * - スパイ
     - 呼び出された回数や引数を記録します。
   * - モック
     - 期待する呼び出され方を事前に設定し、テスト対象が外部の部品を正しく呼び出したかを検証します。テスト対象からの「出力」を確認するために使います。
   * - フェイク
     - 本物と同じように動く、簡易な実装です。例えば、データベースの代わりに辞書でデータを保持するリポジトリです。

この節では、降水確率に応じて傘の要否を助言する関数 ``umbrella_advice`` を例にします。この関数は、天気情報の取得元（``WeatherSource``）を引数として受け取ります。コード全体は、この章の最後に示します。

テストダブルを使いすぎないこと
^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^

テストダブルは便利ですが、使いすぎると次の問題が起きます。

* テストダブルの振る舞いが本物とずれていると、テストは成功するのに本番では故障します。
* 内部の呼び出し方をモックで細かく検証すると、振る舞いを変えないリファクタリングでもテストが壊れます。

テストダブルは、外部のシステムや、時刻・乱数のように制御しにくいものとの境界に限って使います。テストダブルで置き換えた部分が本物と正しく連携するかは、結合テストで別に確認します。

カバレッジ測定
--------------

第 7 章で説明したカバレッジは、coverage.py で測定できます。pytest と組み合わせる場合は、プラグインの pytest-cov を使うと便利です。サンプルコードの setup.cfg では、分岐網羅（ブランチカバレッジ）も測定するように設定しています。

.. code-block:: console
   :linenos:

   $ pytest --cov=. --cov-report=term-missing
   （途中省略）
   Name              Stmts   Miss Branch BrPart  Cover   Missing
   -------------------------------------------------------------
   ch04_after.py         9      0      2      0   100%
   ch07_fee.py          12      0      8      0   100%
   ch08_rle.py           9      0      4      0   100%
   ch08_weather.py      30      7      8      1    79%   27-28, 31-35
   -------------------------------------------------------------
   TOTAL                60      7     22      1    90%

各列の意味は次のとおりです。

.. list-table::
   :header-rows: 1
   :widths: 20 80

   * - 列
     - 意味
   * - Stmts、Miss
     - 命令の数と、そのうち実行されなかった命令の数です。
   * - Branch、BrPart
     - 分岐の方向の数と、両方向のうち片方しか実行されなかった分岐の数です。
   * - Cover
     - 命令と分岐を合わせたカバレッジです。
   * - Missing
     - 実行されなかった行の番号です。

ch08_weather.py の 27 行目～28 行目と 31 行目～35 行目は、HTTP で実際に天気情報を取得する ``HttpWeatherSource`` の処理です。単体テストではスタブとモックに置き換えているため、実行されていません。この部分は、テスト用の API サーバーを使った結合テストで確認すべき箇所だと分かります。

カバレッジの解釈
^^^^^^^^^^^^^^^^

カバレッジは、テストされていない箇所を見つけるための道具として使います。カバレッジの数値を扱う際は、次の点に注意してください。

* **カバレッジが高くても、テストの質が高いとは限りません。**\ 極端な例として、``assert`` 文を 1 つも書かずにすべての関数を呼び出すだけのテストでも、カバレッジは 100 % になります。カバレッジは「実行されたか」を測るだけで、「正しく確認されたか」は測りません。
* **カバレッジが低い箇所は、確実にテストが不足しています。**\ 実行すらされていないコードの欠陥は、テストでは見つかりません。
* **100 % を目標にすると、費用対効果が悪くなります。**\ 実行されることのない防御的なコードや、単純な委譲のためだけのコードのテストに時間をかけるよりも、重要な箇所のテストを充実させるほうが効果的です。

カバレッジの目標値は、プロジェクトの性質によって決めます。目安として 80 % 前後を設定することが多く、本書のサンプルコードでも、第 10 章の CI で 80 % を下回ったら失敗にする設定にしています。ただし、目標値を設定すると、数値を上げること自体が目的になりやすい点に注意が必要です（第 13 章を参照）。

プロパティベーステスト
----------------------

これまでのテストは、具体的な入力と期待値の組（例）を人が選んで書くものでした。これを例示によるテストと呼びます。これに対して、:term:`プロパティベーステスト`\ では、「どのような入力に対しても成り立つはずの性質（プロパティ）」を書き、入力はツールに自動で大量に生成させます。Python では Hypothesis というライブラリが使えます。

例として、ランレングス符号化（連続する同じ文字を「文字と個数」の組で表す圧縮）を考えます。

   :linenos:

:download:`ch08_rle.py をダウンロード <../examples/ch08_rle.py>`

この関数には、次の性質が成り立つはずです。

* 符号化してから復号すると、元の文字列に戻る（往復の性質）
* 符号化の結果では、隣り合う組の文字が異なる

この性質を Hypothesis で書くと、次のようになります。

   :language: python
   :linenos:

20 行目の ``@given(st.text())`` は、任意の文字列を生成してテスト関数の引数 ``text`` に渡すことを表します。Hypothesis は、空文字列、1 文字の文字列、絵文字や制御文字を含む文字列など、人が思いつきにくいものも含めて、多数の入力でテストを実行します。

プロパティベーステストの効果を確かめるため、``encode`` 関数に「最後の連続部分を結果に追加し忘れる」という欠陥を入れて実行すると、次のように失敗します。

.. code-block:: text
   :linenos:

   text = '0'

       @given(st.text())
       def test_decode_restores_original(text: str) -> None:
   >       assert decode(encode(text)) == text
   E       AssertionError: assert '' == '0'
   E
   E         - 0
   E       Failing test case: test_decode_restores_original(
   E           text='0',
   E       )

Hypothesis は、失敗する入力を見つけると、その入力をできるだけ単純な形に縮小（シュリンク）してから報告します。この例では、欠陥を再現する最小の入力である 1 文字の文字列 ``'0'`` が報告されています。

プロパティベーステストは、往復の性質（符号化と復号、保存と読み込み）、不変条件（並べ替えても要素の数は変わらない）、別の実装との比較（高速な実装と単純な実装の結果が一致する）などを確認する場合に特に効果があります。例示によるテストの代わりではなく、それを補うものとして使います。

ミューテーションテストによるテストの評価
----------------------------------------

カバレッジは「テストでコードが実行されたか」を測りますが、「テストが欠陥を検出できるか」は測りません。テスト自体の質を評価する手法として、:term:`ミューテーションテスト`\ があります。

ミューテーションテストでは、テスト対象のコードに小さな変更（ミュータント）を自動で加え、そのたびにテストを実行します。変更の例は、``<=`` を ``<`` に、``+`` を ``-`` に、``True`` を ``False`` に置き換えるといったものです。

* テストが失敗すれば、そのミュータントを「殺した」（変更を検出できた）ことになります。
* テストが成功してしまえば、そのミュータントは「生き残った」ことになり、テストが不十分である可能性を示します。

殺したミュータントの割合を、ミューテーションスコアと呼びます。

.. math::

   \text{ミューテーションスコア} = \frac{\text{殺したミュータントの数}}{\text{全ミュータントの数} - \text{等価ミュータントの数}} \times 100 \ (\%)

等価ミュータントとは、コードを変更しても振る舞いが変わらないミュータントのことで、どのようなテストでも殺せないため、分母から除きます。

例えば、第 7 章の ``admission_fee`` 関数の ``if age <= 5:`` を ``if age < 5:`` に変えたミュータントは、5 歳の境界値のテストがあれば殺せます。代表値（3 歳）のテストしかなければ生き残ります。ミューテーションテストは、境界値分析の重要性を数値で示してくれます。

Python では mutmut や Cosmic Ray などのツールがあります。mutmut は次のように実行します。

.. code-block:: console
   :linenos:

   $ python -m pip install mutmut
   $ mutmut run        # ミュータントを生成してテストを実行します。
   $ mutmut results    # 生き残ったミュータントを一覧表示します。

ミューテーションテストは、ミュータントの数だけテストを繰り返すため、実行に長い時間がかかります。すべてのコードに対して毎回実行するのではなく、重要なモジュールに絞って定期的に実行するのが現実的です。

テストデータの管理と不安定なテストへの対処
------------------------------------------

テストデータの管理
^^^^^^^^^^^^^^^^^^

テストの結果は、使うデータによって左右されます。テストデータを扱う際は、次の点に注意します。

* **テストごとに必要なデータを用意します。**\ 複数のテストが同じデータを共有して書き換えると、実行の順序によって結果が変わります。フィクスチャを使って、テストごとに新しいデータを用意します。
* **テストに必要な項目だけを明示します。**\ 項目の多いデータを毎回すべて書くと、何を確認したいテストなのかが分かりにくくなります。標準の値を持つデータを作る関数（ファクトリー）を用意し、テストでは確認に関係する項目だけを指定します。Python では factory_boy などのライブラリも使えます。
* **本番環境の個人情報を使いません。**\ 本番のデータを複製してテストに使うと、情報漏えいの原因になります。必要な場合は、氏名や住所を架空の値に置き換える（マスキングする）か、Faker などのライブラリで架空のデータを生成します。

不安定なテストへの対処
^^^^^^^^^^^^^^^^^^^^^^

コードを変更していないのに、成功したり失敗したりするテストを、:term:`不安定なテスト`\ （flaky test）と呼びます。不安定なテストがあると、テストが失敗しても「またいつものことだ」と無視されるようになり、本当の故障を見逃す原因になります。

.. list-table:: 不安定なテストの主な原因と対策
   :header-rows: 1
   :widths: 30 70

   * - 原因
     - 対策
   * - 現在時刻への依存
     - 時刻を引数で受け取る設計にするか、テストで時刻を固定します。
   * - 乱数への依存
     - 乱数のシードを固定するか、乱数の生成器を引数で受け取る設計にします。
   * - 実行順序への依存
     - テスト間でデータや状態を共有しないようにします。pytest-randomly などのプラグインで順序を毎回変えて実行すると、依存を発見できます。
   * - 外部のシステムへの依存
     - 単体テストではテストダブルに置き換えます。
   * - 非同期処理の待ち時間
     - 固定の時間だけ待つのではなく、条件が満たされるまで待つようにします。

失敗したテストを自動で再実行するプラグイン（pytest-rerunfailures）もありますが、これは原因を隠すだけです。不安定なテストを見つけたら、一時的に隔離して記録し、原因を調べて修正します。

テストしやすいコードの書き方
----------------------------

テストを書きにくいと感じたら、それはコードの設計に問題があるという合図であることが多くあります。テストしにくいコードの典型は、関数の内部で外部のシステムに直接接続したり、現在時刻を直接取得したりしているコードです。

.. code-block:: python
   :linenos:

   def umbrella_advice(city: str) -> str:
       source = HttpWeatherSource("https://weather.example.com/api")
       probability = source.precipitation_probability(city)
       ...

このコードでは、2 行目で関数の内部が特定の実装（``HttpWeatherSource``）を作っているため、テストのときにスタブに差し替えられません。

これを解決する方法が\ :term:`依存性の注入`\ （DI: Dependency Injection）です。依存する部品を関数の内部で作るのではなく、引数として外から受け取るようにします。

.. code-block:: python
   :linenos:

   def umbrella_advice(source: WeatherSource, city: str) -> str:
       probability = source.precipitation_probability(city)
       ...

1 行目の引数の型 ``WeatherSource`` は、``typing.Protocol`` で定義したインターフェースです。``precipitation_probability`` メソッドを持つオブジェクトであれば何でも受け取れるため、本番では ``HttpWeatherSource`` を、テストではスタブを渡せます。また、mypy は、スタブが ``WeatherSource`` のインターフェースを満たしているかも検査します。

依存性の注入は、第 3 章で説明した「結合度を下げる」設計の具体的な方法の 1 つです。テストしやすい設計は、変更しやすい設計でもあります。

この章のまとめ
--------------

* pytest では、普通の関数と ``assert`` 文でテストを書けます。パラメーター化とフィクスチャを使うと、テストを簡潔に保てます。
* テストダブルを使うと、外部のシステムに依存するコードもテストできます。ただし、使いすぎると本番との違いを見逃します。
* カバレッジはテストされていない箇所を見つける道具です。カバレッジが高くても、テストの質が高いとは限りません。
* プロパティベーステストは、人が思いつきにくい入力で欠陥を見つけます。ミューテーションテストは、テスト自体の質を評価します。
* 不安定なテストは放置せず、原因を調べて修正します。
* 依存性の注入を使うと、テストしやすく、変更しやすいコードになります。
