要求と設計の品質
================

第 1 章で説明したとおり、欠陥は早く見つけるほど修正のコストが小さくなります。そして、多くの欠陥は要求と設計の段階で作り込まれます。この章では、品質の出発点となる要求と設計の品質を高める方法を説明します。

よい要求の条件
--------------

要求とは、ソフトウェアが満たすべき条件や能力のことです。要求が曖昧だったり誤っていたりすると、どれほど丁寧に実装とテストをしても、利用者の必要を満たすソフトウェアにはなりません。よい要求には、次のような条件があります。

.. list-table::
   :header-rows: 1
   :widths: 20 40 40

   * - 条件
     - 説明
     - 悪い例
   * - 明確である
     - 読む人によって解釈が分かれません。
     - 「検索結果を適切な順序で表示する」
   * - 検証できる
     - 満たしているかどうかを、テストや検査で判定できます。
     - 「画面の応答が速いこと」
   * - 一貫している
     - ほかの要求と矛盾しません。
     - ある箇所では「会員のみ購入可」、別の箇所では「ゲスト購入可」
   * - 完全である
     - 必要な場合分け（正常時、異常時、境界）が漏れていません。
     - 入力が空の場合や上限を超えた場合の扱いが書かれていない
   * - 実現できる
     - 技術、予算、期間の制約の中で実現できます。
     - 「障害がまったく発生しないこと」

特に重要なのは「検証できる」ことです。「画面の応答が速いこと」は、何秒なら速いのかが分からないため、テストで合否を判定できません。「検索画面で検索ボタンを押してから結果が表示されるまでの時間が、95 % の要求で 1 秒以内であること」と書けば、測定によって判定できます。

要求の曖昧さは、要求のレビュー（第 5 章）で見つけるのが効果的です。また、テストの担当者が要求の段階からテストケースを考えると、「この場合はどう動くべきか」という問いを通じて、要求の漏れや曖昧さが見つかります。

受け入れ基準の書き方
--------------------

:term:`受け入れ基準`\ とは、ある要求が満たされたと判断するための具体的な条件です。アジャイル開発では、ユーザーストーリーごとに受け入れ基準を書くことが一般的です。

受け入れ基準を書く形式として、Given-When-Then 形式がよく使われます。Given に前提条件、When に操作やきっかけとなる出来事、Then に期待する結果を書きます。次の例は、第 7 章で扱う入場料金の計算についての受け入れ基準です。

.. code-block:: gherkin
   :linenos:

   Feature: 入場料金の計算

     Scenario: シニア料金が適用される
       Given 来場者の年齢が 65 歳である
       When 入場料金を計算する
       Then 料金は 700 円である

     Scenario: 範囲外の年齢は受け付けない
       Given 来場者の年齢が 121 歳である
       When 入場料金を計算する
       Then 年齢が不正であるというエラーになる

この形式には、次の利点があります。

* 前提・操作・結果が分かれているため、記述の漏れに気付きやすくなります。
* 開発者、テスト担当者、プロダクトオーナーが同じ文書を読んで合意できます。
* そのままテストケースに変換できます。behave や pytest-bdd などのツールを使うと、この形式の文書を自動テストとして実行することもできます。

トレーサビリティ
----------------

:term:`トレーサビリティ`\ とは、要求、設計、コード、テストの間の対応関係を追跡できる性質のことです。トレーサビリティがあると、次のような問いに答えられます。

* すべての要求に、対応するテストがあるか（テストの漏れの確認）
* ある要求が変更されたとき、どの設計、コード、テストに影響するか（影響範囲の分析）
* あるテストが失敗したとき、どの要求が満たされていないか（リリース判定の材料）

対応関係は、次のような表（トレーサビリティマトリクス）で管理します。

.. list-table:: トレーサビリティマトリクスの例
   :header-rows: 1
   :widths: 15 35 25 25

   * - 要求 ID
     - 要求
     - 実装
     - テスト
   * - REQ-01
     - 年齢に応じて入場料金を決める
     - ch07_fee.admission_fee
     - test_valid_age_boundaries
   * - REQ-02
     - 範囲外の年齢はエラーにする
     - ch07_fee.admission_fee
     - test_invalid_age_raises_value_error
   * - REQ-03
     - 降水確率に応じて傘の要否を助言する
     - ch08_weather.umbrella_advice
     - test_advice_by_probability

規模の大きなプロジェクトでは、表計算ソフトで管理すると更新が追いつかなくなります。課題管理システムのチケット番号をコミットメッセージやプルリクエストに書く、テスト関数の docstring に要求 ID を書くなど、日々の作業の中で対応関係が自然に残る仕組みを作ることが大切です。

設計の品質
----------

設計の品質は、主に保守性（第 1 章を参照）に影響します。設計の良し悪しを判断する代表的な観点は次のとおりです。

.. list-table::
   :header-rows: 1
   :widths: 25 75

   * - 観点
     - 説明
   * - 凝集度
     - 1 つのモジュール（関数、クラス、パッケージ）の中の要素が、どれだけ 1 つの目的に集中しているかを表します。凝集度は高いほどよい設計です。
   * - 結合度
     - モジュール同士がどれだけ強く依存し合っているかを表します。結合度は低いほどよい設計です。結合度が高いと、1 か所の変更が多くの箇所に波及します。
   * - 責務の分離
     - 異なる関心事（画面表示、業務ロジック、データの保存、外部との通信など）を別のモジュールに分けることです。
   * - テスト容易性
     - テストの書きやすさです。外部への依存を差し替えられる設計にすると、テストしやすくなります（第 8 章を参照）。

これらの観点は互いに関係しています。例えば、業務ロジックと外部 API の呼び出しが 1 つの関数に混ざっていると、凝集度が低く、結合度が高く、テストもしにくくなります。第 8 章のサンプルコードでは、天気情報の取得と助言の判断を分けることで、助言の判断だけを独立してテストできるようにしています。

契約による設計と型ヒント
------------------------

関数やクラスの仕様を明確にする考え方として、:term:`契約による設計`\ があります。これは、モジュールの利用者と提供者の間の取り決めを「契約」として明示するもので、次の 3 つの条件から成ります。

.. list-table::
   :header-rows: 1
   :widths: 20 80

   * - 条件
     - 説明
   * - 事前条件
     - 関数を呼び出す側が満たすべき条件です。例えば「年齢は 0 以上 120 以下」です。
   * - 事後条件
     - 関数が処理を終えたときに保証する条件です。例えば「戻り値は 0 以上」です。
   * - 不変条件
     - オブジェクトが常に満たすべき条件です。例えば「口座の残高は負にならない」です。

Python には契約を記述する専用の構文はありませんが、型ヒント、docstring、実行時の検査を組み合わせて契約を表現できます。

.. code-block:: python
   :linenos:

   def admission_fee(age: int) -> int:
       """年齢に対応する入場料金（円）を返します。

       Args:
           age: 年齢です。0 以上 120 以下でなければなりません。

       Raises:
           ValueError: 年齢が範囲外の場合に送出します。
       """
       if age < 0 or age > 120:
           raise ValueError(f"年齢が範囲外です: {age}")
       ...

1 行目の型ヒントは「整数を受け取り、整数を返す」という契約の一部を表しており、mypy などの型検査器（第 4 章を参照）で機械的に確認できます。4 行目～8 行目の docstring は、型では表せない事前条件と、条件を満たさない場合の振る舞いを人に伝えます。10 行目～11 行目は、事前条件を実行時に検査しています。

事前条件の検査に ``assert`` 文を使う例も見かけますが、``assert`` 文は Python を ``-O`` オプション付きで実行すると無効になります。外部から受け取る値の検査には、``assert`` 文ではなく、例外を送出する ``if`` 文を使ってください。``assert`` 文は「ここでは必ずこの条件が成り立つはずだ」という開発者の前提を確認する目的で使います。

.. note::

   契約や仕様を数学的に記述し、その正しさを証明や網羅的な探索で確かめる手法を、形式手法と呼びます。鉄道や航空、半導体など、高い信頼性が求められる分野で使われています。本書では、存在を紹介するにとどめます。

この章のまとめ
--------------

* よい要求は、明確で、検証でき、一貫しており、完全で、実現できるものです。
* Given-When-Then 形式の受け入れ基準は、関係者の合意とテストケースの作成に役立ちます。
* トレーサビリティがあると、テストの漏れや変更の影響範囲を確認できます。
* 設計は、凝集度を高く、結合度を低くし、関心事を分けることで、保守しやすく、テストしやすくなります。
* 型ヒント、docstring、実行時の検査を組み合わせると、関数の契約を明確にできます。
