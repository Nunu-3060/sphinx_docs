.. _ch11:

リリースと運用における品質
==========================

品質保証は、ソフトウェアをリリースしたら終わりではありません。どれほど入念にテストしても、本番環境では予想しなかった使われ方や負荷、外部のシステムの変化によって故障が起きます。この章では、リリースまでの変更を管理する方法、安全にリリースする方法、そしてリリース後の本番環境で品質を守り、その情報を開発に戻す方法を説明します。第 1 章で触れたシフトライトの考え方を、具体的に見ていきます。

バージョン管理とブランチ戦略
----------------------------

ソフトウェアの品質を保つには、「いつ、誰が、何を、なぜ変更したか」を追跡できることが前提になります。そのための基盤がバージョン管理システム（Git など）です。ソースコードだけでなく、設定ファイル、CI の定義、テストデータ、インフラの構成を定義するファイルなども、バージョン管理の対象にします。このように、ソフトウェアを構成する要素とその変更を管理する活動を\ :term:`構成管理`\ と呼びます。

複数の開発者が並行して作業する場合は、ブランチの使い方（ブランチ戦略）をチームで決めておきます。代表的なブランチ戦略は次のとおりです。

.. list-table::
   :header-rows: 1
   :widths: 25 45 30

   * - ブランチ戦略
     - 概要
     - 向いている場面
   * - GitHub Flow
     - main ブランチを常にリリースできる状態に保ち、作業ごとに短命のブランチを作って、プルリクエストでレビューしてから main に統合します。
     - Web サービスのように頻繁にリリースする開発
   * - Git Flow
     - 開発用（develop）、リリース準備用（release）、緊急修正用（hotfix）など、役割の異なるブランチを使い分けます。
     - リリースの時期が決まっている製品や、複数のバージョンを並行して保守する開発
   * - トランクベース開発
     - ほぼすべての変更を、短い間隔（1 日以内）で main ブランチ（トランク）に直接統合します。未完成の機能は、後述するフィーチャーフラグで無効にしておきます。
     - CI が成熟しており、自動テストが充実しているチーム

どの戦略を選ぶ場合でも、ブランチを長く維持するほど統合のときの衝突が増え、品質のリスクが高まります。ブランチはできるだけ短命に保つことが、第 10 章で説明した継続的インテグレーションの考え方とも一致します。

依存関係の固定と再現可能な環境
------------------------------

Python のソフトウェアは、多くの外部パッケージに依存しています。依存パッケージのバージョンを固定していないと、次のような問題が起きます。

* 昨日まで成功していたテストが、コードを変更していないのに、依存パッケージの新しいバージョンが公開されたことで失敗するようになります。
* 開発者の手元、CI、本番環境で、異なるバージョンのパッケージが使われ、「手元では動くのに本番では動かない」状態になります。
* 問題が起きたときに、どのバージョンの組み合わせで動いていたのかを再現できません。

これを防ぐために、使用するすべてのパッケージのバージョンを固定し、どの環境でも同じ組み合わせをインストールできるようにします。本書のサンプルコードでは、開発用のツールのバージョンを requirements-dev.txt で固定しています。

.. literalinclude:: ../examples/requirements-dev.txt
   :language: text
   :linenos:
   :caption: requirements-dev.txt

:download:`requirements-dev.txt をダウンロード <../examples/requirements-dev.txt>`

このファイルでは、直接使うパッケージのバージョンだけを固定しています。より厳密には、それらのパッケージがさらに依存しているパッケージ（間接的な依存）のバージョンも固定する必要があります。間接的な依存まで含めて固定したファイルを\ :term:`ロックファイル`\ と呼び、次のようなツールで生成します。

.. list-table::
   :header-rows: 1
   :widths: 25 75

   * - ツール
     - 説明
   * - pip-tools
     - 直接の依存を書いたファイル（requirements.in）から、間接的な依存まで固定した requirements.txt を ``pip-compile`` コマンドで生成します。
   * - uv
     - 高速なパッケージ管理ツールです。``uv lock`` コマンドで、pyproject.toml の依存関係から uv.lock を生成します。
   * - Poetry
     - 依存関係の管理とパッケージの作成を行うツールです。poetry.lock を生成します。

また、Python のロックファイルの標準形式（pylock.toml）が PEP 751 として定められ、対応するツールが増えています。

依存関係を固定したら、それで終わりではありません。固定したままにすると、依存パッケージの脆弱性の修正を取り込めなくなります。Dependabot や Renovate などのツールを使って、依存パッケージの更新を定期的にプルリクエストとして作成し、CI で検査してから取り込むのが一般的です。依存パッケージの脆弱性の検査については第 12 章で説明します。

Python 自体のバージョンや OS の違いも、動作の違いの原因になります。CI と本番環境で同じコンテナーイメージを使うと、環境の違いをさらに減らせます。

セマンティックバージョニングとリリース判定
------------------------------------------

バージョン番号の付け方
^^^^^^^^^^^^^^^^^^^^^^

ライブラリや API を提供する場合、バージョン番号は利用者に「この更新で何が変わったか」を伝える手段になります。広く使われている規則が\ :term:`セマンティックバージョニング`\ です。バージョン番号を「MAJOR.MINOR.PATCH」（例えば 2.4.1）の形式で表し、次の規則で番号を上げます。

.. list-table::
   :header-rows: 1
   :widths: 20 80

   * - 番号
     - 上げる場合
   * - MAJOR
     - 互換性のない変更をした場合（既存の利用者のコードが動かなくなる可能性がある変更）
   * - MINOR
     - 互換性を保ったまま機能を追加した場合
   * - PATCH
     - 互換性を保ったまま欠陥を修正した場合

この規則が守られていれば、利用者は「PATCH と MINOR の更新は安全に取り込め、MAJOR の更新には対応が必要」と判断できます。逆に、PATCH の更新で互換性のない変更をすると、利用者のソフトウェアが故障し、信頼を失います。互換性を保っているかどうかを確認することも、品質保証の一部です。

なお、Python のパッケージのバージョン番号の形式は PEP 440 で定められています。MAJOR.MINOR.PATCH の基本的な形式は PEP 440 でも有効ですが、プレリリース版などの表記の規則は両者で異なります。

リリース判定
^^^^^^^^^^^^

リリース判定は、ソフトウェアをリリースしてよいかどうかを判断する活動です。第 9 章で説明した終了基準の達成状況をもとに、次のような観点で判断します。

* 終了基準を満たしているか。満たしていない場合、残っているリスクは受け入れられるか。
* 未解決の欠陥の内容と、その回避策は明確か。
* リリース後に問題が起きた場合に、元に戻す手順（ロールバック）が用意され、確認されているか。
* 利用者への告知、運用担当者への引き継ぎ、問い合わせの対応体制は整っているか。

判定の結果と根拠（特に、受け入れたリスク）は記録に残します。リリース後に問題が起きた場合に、判断の妥当性を振り返る材料になります。

継続的デリバリーと段階的リリース
--------------------------------

:term:`継続的デリバリー`\ （CD: Continuous Delivery）は、継続的インテグレーションをさらに進め、どの変更もいつでも本番環境にリリースできる状態を保つ手法です。ビルド、テスト、リリースの準備までを自動化し、リリースの作業を「ボタンを押すだけ」にします。さらに、本番環境へのリリースまで自動化したものを、継続的デプロイメントと呼びます。

リリースの頻度を上げると、1 回のリリースに含まれる変更が小さくなり、問題が起きたときの影響と原因の調査範囲も小さくなります。リリースの手順を自動化すると、手作業の誤りによる故障も防げます。

それでも、本番環境でしか見つからない問題は残ります。そこで、新しいバージョンを一度にすべての利用者に公開するのではなく、段階的に公開して影響を限定する手法が使われます。

.. list-table::
   :header-rows: 1
   :widths: 25 75

   * - 手法
     - 説明
   * - カナリアリリース
     - 新しいバージョンを、まず一部の利用者（例えば 5 %）にだけ公開し、エラー率や応答時間に問題がないことを確認しながら、公開の範囲を広げていきます。
   * - ブルーグリーンデプロイメント
     - 現在のバージョン（ブルー）と新しいバージョン（グリーン）の 2 つの環境を用意し、利用者の接続先を切り替えます。問題があれば、接続先を元に戻すだけで復旧できます。
   * - フィーチャーフラグ
     - 新しい機能を設定で有効・無効にできるようにしておき、コードのリリースと機能の公開を分けます。問題が起きた場合は、再リリースせずに機能だけを無効にできます。

これらの手法は、「本番環境で問題が起きることを前提に、その影響を小さくし、すばやく回復する」という考え方に基づいています。リリース前の品質保証を軽くしてよいという意味ではありません。

監視と SLI / SLO
----------------

本番環境の品質の状態を知るために、システムを継続的に監視します。何を監視し、どの水準を目指すかを定めるために、:term:`SLI` と :term:`SLO` という考え方が使われます。

.. list-table::
   :header-rows: 1
   :widths: 25 45 30

   * - 用語
     - 説明
     - 例
   * - SLI（Service Level Indicator、サービスレベル指標）
     - サービスの品質を表す、測定可能な指標です。
     - 全リクエストのうち、正常に応答したリクエストの割合
   * - SLO（Service Level Objective、サービスレベル目標）
     - SLI が満たすべき目標値です。
     - 30 日間で、正常に応答したリクエストの割合が 99.9 % 以上
   * - SLA（Service Level Agreement、サービスレベル合意）
     - 顧客との契約として合意した品質の水準です。達成できない場合の返金などを定めます。
     - 月間の稼働率が 99.5 % を下回った場合、利用料金の 10 % を返金する

SLO は、通常 SLA よりも厳しい値に設定します。SLO を守っていれば、SLA に違反する前に問題に気付いて対処できるからです。

SLO を 100 % にしないことにも意味があります。SLO を 99.9 % とすると、残りの 0.1 % は「許容される失敗の量」と考えられます。これを\ :term:`エラーバジェット`\ と呼びます。例えば、30 日間の可用性の SLO が 99.9 % の場合、許容される停止時間は次のように計算できます。

.. math::

   30 \times 24 \times 60 \ (\text{分}) \times (1 - 0.999) = 43.2 \ (\text{分})

エラーバジェットが残っている間は新しい機能を積極的にリリースし、使い切りそうになったら新機能のリリースを止めて信頼性の改善に集中する、というように、開発の速さと品質のバランスを数値で判断できます。

監視では、SLI のほかに、エラーのログ、応答時間の分布、資源の使用量などを収集します。異常を検知したら担当者に通知（アラート）しますが、対応の必要のない通知が多すぎると、本当に重要な通知が見落とされます。通知は、利用者に影響がある、または影響が出そうな状況に絞ります。

インシデント対応とポストモーテム
--------------------------------

インシデント対応
^^^^^^^^^^^^^^^^

本番環境でサービスの停止や品質の低下が起きた状態を、インシデントと呼びます。インシデントが起きたときは、次の順序で対応します。

#. **検知と報告:** 監視の通知や利用者からの問い合わせでインシデントを検知し、関係者に知らせます。
#. **影響の把握:** どの機能が、どの範囲の利用者に、どの程度の影響を与えているかを把握します。
#. **復旧:** 原因の究明よりも、サービスの復旧を優先します。直前のリリースが原因と疑われる場合は、まずロールバックします。
#. **原因の調査と恒久対策:** 復旧した後で、原因を調査し、再発を防ぐ対策を行います。

インシデントの対応中は、指揮を執る人、調査と復旧の作業をする人、関係者への連絡をする人などの役割を分けると、混乱を防げます。

ポストモーテム
^^^^^^^^^^^^^^

インシデントが収束した後は、その経緯と原因、対策を文書にまとめて振り返ります。この文書と振り返りの活動を\ :term:`ポストモーテム`\ と呼びます。ポストモーテムには、一般に次の内容を記載します。

* 概要（何が起きたか、影響の範囲と期間）
* 時系列（検知、判断、対応の記録）
* 根本原因（第 13 章で説明する根本原因分析の結果）
* うまくいったこと、うまくいかなかったこと
* 再発防止の対策（担当者と期限を明記します）

ポストモーテムで最も重要なのは、個人の責任を追及しない（ブレームレスな）姿勢です。「担当者が手順を誤った」で終わらせるのではなく、「なぜ誤りやすい手順だったのか」「なぜ誤りが検知されなかったのか」を問い、仕組みを改善します。個人が責められる文化では、失敗が隠されるようになり、組織が学ぶ機会が失われます。

ポストモーテムで得られた教訓は、開発に戻します。例えば、インシデントの原因となった欠陥を再現するテストを追加する、レビューのチェックリストに項目を加える、監視の項目を増やすといった対策です。これが、本番環境の情報を開発に戻すシフトライトの実践です。

この章のまとめ
--------------

* ソースコードだけでなく、設定や CI の定義も含めて構成管理を行い、ブランチは短命に保ちます。
* 依存パッケージのバージョンをロックファイルで固定すると、どの環境でも同じ組み合わせを再現できます。固定したバージョンは定期的に更新します。
* セマンティックバージョニングは、利用者に変更の影響を伝えます。リリース判定では、受け入れたリスクを記録に残します。
* 継続的デリバリーと段階的リリースによって、本番環境での問題の影響を小さくし、すばやく回復できます。
* SLI と SLO で本番環境の品質を測り、エラーバジェットで開発の速さと品質のバランスを判断します。
* インシデントの対応では復旧を優先し、ポストモーテムで個人ではなく仕組みを改善します。
