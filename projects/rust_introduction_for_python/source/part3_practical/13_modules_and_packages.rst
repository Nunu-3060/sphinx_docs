モジュールとパッケージ
======================

プログラムが大きくなってくると、すべてのコードを1つのファイルに書き続けるのは現実的ではありません。Python では ``.py`` ファイルをモジュールとして分割し、複数のモジュールをまとめたものをパッケージと呼びますが、Rust にも似たような、しかしもう少し厳密な仕組みがあります。本章では ``mod`` によるモジュール分割、クレートとパッケージの違い、``pub`` による公開範囲の制御、``use`` によるパスの読み込みを学びます。

モジュールによるコードの整理
------------------------------

Rust では ``mod`` キーワードを使って、関連する関数や構造体を1つの名前空間にまとめられます。

.. code-block:: rust

    mod front_of_house {
        pub mod hosting {
            pub fn add_to_waitlist() {
                println!("待ちリストに追加しました");
            }
        }
    }

    fn main() {
        front_of_house::hosting::add_to_waitlist();
    }

モジュールは入れ子にでき、``::`` でつないだパスによって内部の要素にアクセスします。この例のようにモジュールをファイル内で定義することもできますが、コードが増えてくるとファイルを分割したくなります。

ファイル分割: mod foo; と foo.rs
------------------------------------

Rust では、``mod foo;`` と書くことで、``foo`` モジュールの中身を別ファイル ``foo.rs`` に分離できます。例えば ``src/lib.rs`` に次のように書くと、

.. code-block:: rust

    // src/lib.rs
    mod front_of_house;

    pub fn eat_at_restaurant() {
        front_of_house::hosting::add_to_waitlist();
    }

``front_of_house`` モジュールの中身は ``src/front_of_house.rs`` というファイルに書きます。

.. code-block:: rust

    // src/front_of_house.rs
    pub mod hosting;

さらに ``hosting`` サブモジュールの中身は、 ``src/front_of_house/hosting.rs`` というファイルに書きます。

.. code-block:: rust

    // src/front_of_house/hosting.rs
    pub fn add_to_waitlist() {
        println!("待ちリストに追加しました");
    }

このように、モジュールの階層構造がそのままディレクトリ構造に対応するため、大きなプロジェクトでも見通しよくコードを整理できます。

クレートとパッケージ
--------------------

Rust の「クレート」はコンパイルの単位で、大きく分けて2種類あります。

- **バイナリクレート**: ``fn main()`` を持ち、実行可能ファイルになるクレート。``src/main.rs`` がエントリポイントです。
- **ライブラリクレート**: 他のクレートから使われることを目的としたクレート。``src/lib.rs`` がエントリポイントで、それ自体は実行できません。

「パッケージ」は、``Cargo.toml`` によって管理される1つ以上のクレートの集まりです。1つのパッケージには、ライブラリクレートは最大1つまでですが、バイナリクレートは複数含めることができます。

``Cargo.toml`` には、パッケージ自体の情報を書く ``[package]`` セクションと、外部クレートへの依存を書く ``[dependencies]`` セクションが登場します。

.. code-block:: toml

    [package]
    name = "my_project"
    version = "0.1.0"
    edition = "2024"

    [dependencies]
    rand = "0.8"

この例では ``rand`` という外部クレートに依存しており、``cargo build`` を実行すると自動的にダウンロードされます。追加したクレートは、``use`` 文で取り込むことでプログラムから利用できます。

.. code-block:: rust

    use rand::Rng;

外部クレートの追加方法や feature フラグなど、Cargo とエコシステムについての詳細は後の章で扱います。

pub による公開範囲の制御
----------------------------

Rust では、モジュール内のアイテム(関数・構造体・列挙型など)はデフォルトで非公開です。外部のモジュールから使えるようにするには、 ``pub`` キーワードを明示的に付ける必要があります。

.. code-block:: rust

    mod front_of_house {
        pub mod hosting {
            pub fn add_to_waitlist() {}

            fn seat_at_table() {
                // このモジュール内からは呼び出せるが、外部には非公開
            }
        }
    }

親モジュールから子モジュールの非公開アイテムを見ることはできませんが、子モジュールから親モジュールのアイテムは(それが公開されていなくても)参照できます。これは「非公開はデフォルトで隠す」という Rust の設計思想に基づいています。

大きなプロジェクトでは、``pub`` と非公開の2択だけでは公開範囲の調整が難しい場面が出てきます。そこで ``pub(crate)`` (現在のクレート全体からは見えるが、クレートの外には公開しない)や ``pub(super)`` (親モジュールからのみ見える)といった、より細かく公開範囲を指定できる修飾子もよく使われます。これらは「クレート内部の実装では共有したいが、外部には見せたくない」といった中間的な公開範囲を表現するのに便利です。

use によるパスの読み込みと再エクスポート
--------------------------------------------

深い階層のパスを毎回フルで書くのは面倒です。``use`` を使うと、パスをスコープに読み込んで短い名前で使えるようになります。

.. code-block:: rust

    mod front_of_house {
        pub mod hosting {
            pub fn add_to_waitlist() {}
        }
    }

    use front_of_house::hosting;

    pub fn eat_at_restaurant() {
        hosting::add_to_waitlist();
    }

さらに ``pub use`` と書くと、読み込んだパスを自分のモジュールの公開アイテムとして「再エクスポート」できます。これにより、利用する側は内部の詳細なモジュール構造を知らなくても、再エクスポートされた場所から直接アイテムを使えるようになります。

.. code-block:: rust

    pub use front_of_house::hosting;

絶対パスと相対パス: crate:: と super::
--------------------------------------------

``use`` や関数呼び出しで書くパスには、絶対パスと相対パスの2種類があります。

- ``crate::`` から始まるパスは、現在のクレートの「ルート」からたどる絶対パスです。どのモジュールの中からでも、クレート全体の同じ場所を指し示せます。
- ``super::`` は、現在のモジュールから見て1つ上の親モジュールを指す相対パスです。Python の相対インポート(``from . import foo`` の ``.`` や ``..``)に近い感覚です。
- ``self::`` は、現在のモジュール自身を指す相対パスです。省略した場合と同じ意味になるため使う頻度は高くありませんが、パスの先頭を明示したい場合などに使われます。

.. code-block:: rust

    mod front_of_house {
        pub mod hosting {
            pub fn add_to_waitlist() {}
        }
    }

    // クレートルートからの絶対パス
    fn eat_at_restaurant_absolute() {
        crate::front_of_house::hosting::add_to_waitlist();
    }

    mod back_of_house {
        fn fix_incorrect_order() {
            cook_order();
            // super:: で親モジュール(クレートルート)に定義された
            // 関数を呼び出す
            super::serve_order();
        }

        fn cook_order() {}
    }

    fn serve_order() {}

``super::`` は、あるモジュールが親モジュールの機能に依存していることを明示しつつ、モジュールを移動・リネームしても親子関係さえ保たれていれば書き換えずに済むという利点があります。

``use`` には、このほかにも実務でよく使われる書き方がいくつかあります。

- **グループ化**: 同じモジュールから複数のアイテムを読み込むときは、``use std::{fmt, io};`` のように波括弧でまとめて書けます。
- **``as`` によるリネーム**: ``use foo::Bar as Baz;`` のように書くと、読み込んだアイテムに別名を付けられます。名前の衝突を避けたいときに便利です。
- **グロブインポート**: ``use foo::*;`` のように書くと、``foo`` モジュール内の公開アイテムをまとめて読み込めます。手軽な反面、どの名前が読み込まれたか分かりにくくなるため、テストコードなど限られた場面で使われることが多い書き方です。

.. admonition:: Python 経験者向けメモ
   :class: tip

   Rust の「クレート」は Python の「パッケージ」、Rust の「モジュール」は Python の「モジュール(``.py`` ファイル)」に近い概念です。``mod foo;`` によるファイル分割は、Python で ``import foo`` するために ``foo.py`` を用意する感覚に似ています。

   大きく異なるのは公開範囲のデフォルトです。Python ではアンダースコアの命名規則こそあるものの、基本的にはどのモジュールからでも属性にアクセスできます。一方 Rust では、``pub`` を付けない限りすべてのアイテムはデフォルトで非公開になります。「公開したいものだけを明示的に選ぶ」設計のため、意図しない内部実装への依存を防ぎやすくなっています。

まとめ
------

- ``mod`` を使うと、関連するコードを名前空間としてまとめられます。
- ``mod foo;`` と書くことで、モジュールの中身を ``foo.rs`` などの別ファイルに分割できます。
- クレートにはバイナリクレートとライブラリクレートがあり、パッケージは ``Cargo.toml`` で管理される1つ以上のクレートの集まりです。
- モジュール内のアイテムはデフォルトで非公開であり、``pub`` を付けたものだけが外部に公開されます。
- ``use`` でパスを読み込んで短く参照でき、``pub use`` で再エクスポートすることもできます。
- ``crate::`` はクレートルートからの絶対パス、``super::`` は親モジュールを指す相対パスです。
