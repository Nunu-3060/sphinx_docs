テスト
======

Rust はテストの仕組みを言語とツールチェインに標準で組み込んでいます。この章では、テスト関数の書き方と ``cargo test`` によるテストの実行方法を学びます。

テスト関数の書き方
------------------

Rust では、通常の関数に ``#[test]`` という属性を付けるだけでテスト関数になります。特別なフレームワークをインストールする必要はありません。

.. code-block:: rust

    fn add(a: i32, b: i32) -> i32 {
        a + b
    }

    #[test]
    fn test_add() {
        assert_eq!(add(2, 3), 5);
    }

このコードを ``cargo test`` で実行すると、Cargo は ``#[test]`` の付いた関数を自動的に見つけ出し、それぞれを個別に実行して結果(成功・失敗)を報告してくれます。

.. code-block:: console

    $ cargo test
    running 1 test
    test test_add ... ok

    test result: ok. 1 passed; 0 failed; 0 ignored; 0 measured; 0 filtered out

アサーションマクロ
------------------

テストの中で結果を検証するには、主に次の3つのマクロを使います。

- ``assert!(式)``: 式が ``true`` でなければパニックしてテストを失敗させます。
- ``assert_eq!(左辺, 右辺)``: 両辺が等しくなければ失敗し、両辺の値を表示します。
- ``assert_ne!(左辺, 右辺)``: 両辺が等しければ失敗します。

.. code-block:: rust

    #[test]
    fn test_assertions() {
        assert!(1 + 1 == 2);
        assert_eq!(2 + 2, 4);
        assert_ne!(2 + 2, 5);
    }

``assert_eq!`` や ``assert_ne!`` は失敗した際に両辺の値を自動的に出力してくれるため、単に ``assert!(a == b)`` と書くよりもデバッグがしやすくなります。

パニックを期待するテスト: should_panic
------------------------------------------

「不正な値を渡したら panic することを確認したい」という場合には、``#[test]`` に加えて ``#[should_panic]`` という属性を付けます。テスト関数の中で実際にパニックが発生すればテストは成功し、逆にパニックが発生しなければ失敗になります。

.. code-block:: rust

    pub fn divide(a: i32, b: i32) -> i32 {
        if b == 0 {
            panic!("0で割ることはできません");
        }
        a / b
    }

    #[test]
    #[should_panic]
    fn test_divide_by_zero() {
        divide(1, 0);
    }

ただし、この書き方では「何らかの理由でパニックしさえすれば」テストが成功してしまうため、意図とは違う原因のパニックを見逃してしまう可能性があります。パニックメッセージの一部を指定したい場合は、``#[should_panic(expected = "...")]`` のように書きます。

.. code-block:: rust

    #[test]
    #[should_panic(expected = "0で割ることはできません")]
    fn test_divide_by_zero_with_message() {
        divide(1, 0);
    }

こうすることで、パニックメッセージに指定した文字列が含まれている場合にのみテストが成功するようになり、より厳密な検証が行えます。

ドキュメンテーションテスト
----------------------------

Rust では、``///`` で書いたドキュメンテーションコメントの中にコード例を含めると、そのコード例が ``cargo test`` の実行時に自動的にコンパイル・実行され、正しく動くかどうかが検証されます。これを「ドキュメンテーションテスト(doctest)」と呼びます。

.. code-block:: rust

    /// 2つの整数を加算します。
    ///
    /// # Examples
    ///
    /// ```
    /// let result = my_crate::add(2, 3);
    /// assert_eq!(result, 5);
    /// ```
    pub fn add(a: i32, b: i32) -> i32 {
        a + b
    }

このコード例はドキュメントとして ``cargo doc`` で読めるだけでなく、``cargo test`` を実行するたびに自動的に検証されるため、ドキュメントとコードの実装がずれてしまうことを防いでくれます。

単体テストの配置場所
--------------------

Rust では、テスト対象のコードと同じファイルの末尾に、``#[cfg(test)]`` を付けた ``mod tests`` というモジュールを置くのが慣例です。``#[cfg(test)]`` は「テスト時にのみコンパイルする」という意味の属性で、通常のビルド(``cargo build`` や ``cargo run``)にはこのコードが含まれなくなります。

.. code-block:: rust

    pub fn multiply(a: i32, b: i32) -> i32 {
        a * b
    }

    #[cfg(test)]
    mod tests {
        // 親モジュールの要素を使えるようにする
        use super::*;

        #[test]
        fn test_multiply() {
            assert_eq!(multiply(3, 4), 12);
        }
    }

このように本体のコードとテストを同じファイルに書けるため、実装とテストの対応関係が分かりやすくなります。なお、より大規模な結合テストは ``tests`` ディレクトリに置くこともできますが、まずはこの ``mod tests`` の形に慣れるとよいでしょう。

ここで登場した ``mod tests`` によるテストは「単体テスト」と呼ばれ、テスト対象と同じファイル(同じクレート)に置かれるため、``pub`` が付いていないプライベートな関数や構造体にも ``use super::*;`` を通じて直接アクセスできます。一方、プロジェクト直下の ``tests`` ディレクトリに置くテストは「結合テスト」と呼ばれ、ファイルごとに独立した別クレートとしてコンパイルされます。そのため結合テストからは、``pub`` として公開されているクレートの公開 API しか呼び出すことができません。実装の細部まで検証したいときは単体テスト、外部から見た振る舞いを利用者目線で検証したいときは結合テスト、というように使い分けるとよいでしょう。

テストで外部クレートを使う(dev-dependencies)
------------------------------------------------

Cargo とエコシステムの章では、テストなど開発時にのみ使うクレートを ``[dev-dependencies]`` に書けることを紹介しました。ここでは実際にその仕組みを使って、``rand`` クレートをテストの中で利用してみましょう。

.. code-block:: toml

    [dev-dependencies]
    rand = "0.8"

.. code-block:: rust

    pub fn roll_die() -> u32 {
        use rand::Rng;
        rand::thread_rng().gen_range(1..=6)
    }

    #[cfg(test)]
    mod tests {
        use super::*;

        #[test]
        fn test_roll_die_in_range() {
            let n = roll_die();
            assert!((1..=6).contains(&n));
        }
    }

``rand`` は ``[dependencies]`` ではなく ``[dev-dependencies]`` に書かれているため、本体のライブラリやバイナリには組み込まれず、``cargo test`` でテストをコンパイルするときにだけ利用されます。乱数のように毎回結果が変わる値をテストする場合、``assert_eq!`` で特定の値と比較することはできませんが、このように「期待する範囲に収まっているか」を ``assert!`` で検証することはできます。

cargo test のよく使うオプション
------------------------------------------------

pytest に慣れている方向けに、``cargo test`` でよく使うオプションをいくつか紹介します。

- ``cargo test test_add`` のように名前の一部を指定すると、名前が一致するテストだけを実行できます。
- テスト中の ``println!`` の出力は、テストが成功すると既定では表示されません。出力を確認したい場合は ``cargo test -- --nocapture`` を使います。
- pytest がデフォルトでテストを逐次実行するのに対し、``cargo test`` は既定でテストを並列に実行します。グローバルな状態やファイル、環境変数などをテスト間で共有している場合は、この違いによって思わぬ干渉が起きることがあります。
- テストを直列に実行したい場合は ``cargo test -- --test-threads=1`` を指定します。
- 実行に時間がかかるテストには ``#[ignore]`` 属性を付けておくと、通常の ``cargo test`` ではスキップされます。``#[ignore]`` を付けたテストだけを実行したい場合は ``cargo test -- --ignored`` を使います。

.. admonition:: Python 経験者向けメモ
   :class: tip

   ``cargo test`` は pytest のように、プロジェクト内のテスト関数を自動的に検出して実行してくれます。pytest が ``test_`` で始まる関数名を探すのに対し、Rust では ``#[test]`` 属性という明示的な目印を使う点が異なりますが、「特別な設定なしにテストを見つけて走らせてくれる」という体験はよく似ています。また ``assert_eq!`` は Python の ``assert a == b`` に近いものですが、失敗時に両辺の値を自動的に表示してくれる分、デバッグ情報がやや親切です。

まとめ
------

- ``#[test]`` 属性を付けた関数はテスト関数として扱われます。
- ``cargo test`` を実行すると、プロジェクト内のテストが自動的に検出・実行されます。
- ``assert!`` / ``assert_eq!`` / ``assert_ne!`` マクロで期待する結果を検証します。
- ``#[should_panic]`` を付けたテストは、パニックが発生することを期待し、パニックしなければ失敗になります。``expected`` パラメータでパニックメッセージの内容まで検証できます。
- ``///`` のドキュメンテーションコメント内のコード例は、ドキュメンテーションテスト(doctest)として ``cargo test`` で自動的に検証されます。
- テストは ``#[cfg(test)] mod tests { use super::*; ... }`` という形で実装コードと同じファイルに置くのが一般的です。
- ``#[cfg(test)]`` により、テストコードは通常のビルドには含まれません。
- 単体テストは同じクレート内のプライベートな要素にアクセスでき、``tests`` ディレクトリの結合テストは公開 API のみを利用できます。
- ``[dev-dependencies]`` に追加したクレートは、``cargo test`` のときだけコンパイルされます。
- ``cargo test`` は名前によるフィルタリング、``--nocapture``、``--test-threads=1``、``#[ignore]`` など、pytest に近い使い勝手のオプションを備えています。
