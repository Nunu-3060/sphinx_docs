Cargo とエコシステム
====================

ここまでの章では、標準ライブラリの範囲で Rust の基本を学んできました。この章では、Rust のパッケージ管理・ビルドツールである Cargo を通じて、外部のライブラリ(クレート)を活用するエコシステムについて紹介します。

crates.io とは何か
------------------

`crates.io <https://crates.io/>`_ は Rust における公式のパッケージレジストリで、世界中の開発者が公開したクレート(Rust のライブラリやパッケージのこと)を検索・ダウンロードできる場所です。Cargo はデフォルトでこの crates.io を参照するように設定されており、依存関係を追加すると自動的にここからソースコードがダウンロードされます。

外部クレートの追加
------------------

プロジェクトに外部クレートを追加するには、``Cargo.toml`` の ``[dependencies]`` セクションにクレート名とバージョンを書き加えます。

.. code-block:: toml

    [package]
    name = "my_project"
    version = "0.1.0"
    edition = "2024"

    [dependencies]
    rand = "0.8"

この状態で ``cargo build`` を実行すると、``rand`` クレートが自動的にダウンロードされ、コンパイルに組み込まれます。

``Cargo.toml`` を手で編集する代わりに、``cargo add`` コマンドを使うこともできます。

.. code-block:: console

    $ cargo add rand

このコマンドを実行すると、crates.io から最新の安定版バージョンが調べられ、 ``Cargo.toml`` の ``[dependencies]`` セクションに自動的に追記されます。

追加したクレートは、``use`` 文でモジュールを取り込むことでプログラムから利用できます。

.. code-block:: rust

    use rand::Rng;

    fn main() {
        let mut rng = rand::thread_rng();
        let n: u32 = rng.gen_range(1..=6);
        println!("サイコロの目: {}", n);
    }

バージョン指定とセマンティックバージョニング
------------------------------------------------

先ほどの ``rand = "0.8"`` のようなバージョン指定は、実は ``^0.8`` というキャレット要件(caret requirement)の省略記法です。これは「``0.8.0`` 以上、``0.9.0`` 未満」の範囲にある最新のバージョンを使う、という意味になります。Rust のクレートは多くの場合、``MAJOR.MINOR.PATCH`` という形式のバージョン番号(セマンティックバージョニング、semver)に従っており、後方互換性を壊す変更をする際には MAJOR を、後方互換性を保ったまま機能を追加する際には MINOR を、バグ修正のみの場合には PATCH を上げる、という慣習になっています。

ただし ``0.x`` 系のバージョンには特別な扱いがあります。まだ安定版に達していない(``1.0.0`` 未満の)クレートでは、MINOR のバージョンアップも互換性を壊す変更とみなされます。そのため ``^0.8`` は ``0.8.x`` の範囲だけを指し、``0.9.0`` が公開されても自動的には採用されません。逆に ``^1.2`` であれば、``1.x`` の範囲(``2.0.0`` 未満)であれば MINOR が上がっても自動的に採用されます。バージョン番号だけを見て、そのアップデートが安全かどうかをある程度判断できるようになっている、というのが semver の考え方です。

``Cargo.toml`` に書くのは、あくまでこのような「バージョンの範囲」という要件であり、実際にビルドで使われた正確なバージョンは ``Cargo.lock`` というファイルに記録されます。``cargo build`` を実行すると、要件を満たす範囲で解決された具体的なバージョンの組み合わせが ``Cargo.lock`` に書き込まれ、以後は(明示的に更新しない限り)常に同じバージョンが使われるようになります。これにより、チームの他のメンバーや CI 環境でビルドしても同じ依存関係のバージョンが再現されます。要件を満たす新しいバージョンに更新したい場合は、``cargo update`` コマンドを実行します。

ドキュメントの生成
------------------

Rust のエコシステムでは、クレートの作者がソースコード中のコメントからドキュメントを自動生成する文化が根付いています。手元のプロジェクトで次のコマンドを実行すると、依存クレートも含めたドキュメントがビルドされ、ブラウザで開かれます。

.. code-block:: console

    $ cargo doc --open

``cargo doc`` は ``///`` で書かれたドキュメンテーションコメントを解析して HTML を生成します。crates.io に公開されているクレートについては、 `docs.rs <https://docs.rs/>`_ というサイトで同様のドキュメントが誰でも閲覧できるようになっています。

よく使われるクレート
--------------------

Rust の標準ライブラリは比較的小さく保たれており、多くの機能は外部クレートとして提供されています。代表的なものをいくつか紹介します。

- ``serde``: 構造体やデータを JSON などの形式にシリアライズ・デシリアライズするためのクレートです。``serde_json`` と組み合わせてよく使われます。
- ``rand``: 乱数を生成するためのクレートです。標準ライブラリには乱数生成器が含まれていないため、多くのプロジェクトで利用されています。
- ``clap``: コマンドライン引数を解析するためのクレートです。オプションやサブコマンドを宣言的に定義できます。

これらはあくまで一例であり、汎用の非同期ランタイムである ``tokio``、それを土台にした Web フレームワークの ``actix-web``、エラー処理を助ける ``anyhow`` など、目的に応じたさまざまなクレートが crates.io で公開されています。``tokio`` はネットワーク通信全般やバックグラウンド処理など、Web サーバーに限らず幅広い非同期処理の基盤として使われており、``actix-web`` のような Web フレームワークはこうした非同期ランタイムの上に構築されています。何かを実装したくなったときは、まず crates.io で検索してみるとよいでしょう。

feature フラグ
--------------

クレートの中には、機能ごとに ``feature`` (フィーチャーフラグ)を分けて提供しているものがあります。すべての機能を常に有効にするとコンパイル時間や依存関係が増えてしまうため、必要な機能だけを選んで有効化できるようになっています。``Cargo.toml`` では次のように書きます。

.. code-block:: toml

    [dependencies]
    tokio = { version = "1", features = ["full"] }

この例では、``tokio`` クレートの ``full`` という feature を有効にしています。多くのクレートでは、何も指定しなければ最小限の機能だけが有効になり、``features`` に必要な名前を追加することで、対応する機能(追加のモジュールや依存クレートなど)が使えるようになります。どのような feature が用意されているかは、それぞれのクレートのドキュメント(docs.rs など)で確認できます。

dev-dependencies
------------------

``Cargo.toml`` には ``[dependencies]`` とは別に、``[dev-dependencies]`` というセクションを書くこともできます。ここに書いたクレートは、テストやベンチマーク、サンプルコード(``examples``)をコンパイルするときにのみ使われ、ライブラリ本体や通常のバイナリターゲットには一切含まれません。これはデバッグビルドかリリースビルドかとは関係なく、``cargo build`` と ``cargo test`` のどちらでコンパイルされるか、という違いによるものです。

.. code-block:: toml

    [dev-dependencies]
    rand = "0.8"

例えばテストの中だけでランダムな値を使いたい場合、``rand`` を ``[dev-dependencies]`` に加えておけば、本番のビルドサイズに影響を与えずに済みます。次のテストの章では、この ``[dev-dependencies]`` を使う場面にも触れます。

ワークスペース
------------------

複数の関連するパッケージ(クレート)を1つのリポジトリでまとめて管理したい場合には、Cargo の「ワークスペース」という仕組みが使えます。リポジトリの最上位に置いた ``Cargo.toml`` に ``[workspace]`` セクションを書き、そこに含めるメンバークレートを列挙します。ワークスペースに属するクレートは ``Cargo.lock`` と ``target`` ディレクトリを共有するため、依存関係のバージョンがクレート間で揃い、ビルドの重複も避けられます。大きめのアプリケーションを複数のクレートに分割したいときや、ライブラリ本体とそれを使うサンプル・CLI ツールを同じリポジトリで管理したいときによく使われます。

.. code-block:: toml

    [workspace]
    members = [
        "app",
        "core",
    ]

.. admonition:: Python 経験者向けメモ
   :class: tip

   crates.io は Python でいう PyPI に相当し、``Cargo.toml`` は ``requirements.txt`` や ``pyproject.toml`` に相当します。また ``cargo add rand`` は ``pip install rand`` に近い感覚で使えるコマンドです。違いとして、Cargo はバージョン情報や依存関係の解決結果を ``Cargo.lock`` というファイルに自動的に記録するため、``pip freeze`` を手動で行うような手間がかからず、チーム全員が同じバージョンの依存関係を再現しやすくなっています。

まとめ
------

- ``crates.io`` は Rust の公式パッケージレジストリで、世界中のクレートが公開されています。
- 外部クレートは ``Cargo.toml`` の ``[dependencies]`` セクションに追記するか、 ``cargo add`` コマンドで追加できます。
- ``rand = "0.8"`` は ``^0.8`` の省略記法で、semver に基づき「``0.8.0`` 以上 ``0.9.0`` 未満」を意味します。実際に使われたバージョンは ``Cargo.lock`` に記録され、再現可能なビルドを支えます。
- ``cargo doc --open`` によって、依存クレートを含むドキュメントを手元で生成・閲覧できます。
- ``serde``、``rand``、``clap`` など、目的別によく使われる定番クレートが存在します。
- ``features = ["full"]`` のように feature フラグを指定すると、クレートの一部機能だけを選んで有効化できます。
- ``[dev-dependencies]`` には、テストなど開発時にのみ使うクレートを ``[dependencies]`` とは別に書きます。
- 複数のクレートをまとめて管理したい場合は、``[workspace]`` を使ったワークスペースが便利です。
- crates.io は PyPI、``Cargo.toml`` は ``requirements.txt``/``pyproject.toml`` に相当し、``cargo add`` は ``pip install`` に近い感覚で使えます。
