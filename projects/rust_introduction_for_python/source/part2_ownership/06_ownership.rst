所有権(Ownership)
==================

Rust を学ぶうえで避けて通れないのが「所有権(ownership)」という考え方です。他の多くの言語では、メモリ管理はガベージコレクション(GC)や参照カウントによって実行時に自動的に行われます。Python もその一つで、変数がオブジェクトをどれだけ参照しているかを実行時にカウントし、参照が 0 になったら自動的に解放します。

一方 Rust には GC がありません。その代わりに「所有権」という一連のルールをコンパイラがコンパイル時にチェックすることで、ガベージコレクションなしで安全にメモリを管理します。実行時のオーバーヘッドがないため高速に動作しますが、その分「誰がいつまでその値を持っているか」をプログラマ自身(そしてコンパイラ)が把握しておく必要があります。これは Python 経験者にとって最初の、そして最大の壁になりますが、この章を丁寧に理解することが Rust 習得の近道です。

所有権の3つのルール
----------------------------------------

Rust の所有権システムは、次の3つのシンプルなルールから成り立っています。

- Rust の各値には、その値の所有者(owner)と呼ばれる変数がただ1つだけ存在する
- 所有者がスコープ(``{}`` で囲まれた範囲)を抜けると、値は自動的に破棄される
- 代入や関数呼び出しによって所有権が別の変数へ移動(move)することはあるが、移動したあとは元の変数を通じてその値にアクセスすることはできない

たったこれだけのルールですが、これがコンパイル時に厳密にチェックされることで、Rust はガベージコレクタなしで「二重解放(double free)」や「解放済みメモリへのアクセス」といったバグをコンパイル時に防いでいます(なお、意図的なメモリリークを引き起こす一部の操作は、この所有権システムの対象外であり防ぐことはできません。詳しくは後の「スマートポインタ」の章で扱います)。

例えば、次のコードでは変数 ``s`` はブロックの中でのみ有効です。

.. code-block:: rust

    fn main() {
        {
            let s = String::from("hello"); // s がここから有効になる
            println!("{}", s);
        } // このスコープが終わると s は無効になり、値は自動的に破棄される(drop)

        // println!("{}", s); // ※これはコンパイルエラーになります(s はスコープ外)
    }

``String::from`` はヒープ上に文字列データを確保します。変数 ``s`` がスコープを抜けるタイミングで、Rust は自動的にそのメモリを解放する関数(``drop``)を呼び出します。この仕組みについては本章の最後で改めて説明します。

ムーブセマンティクス
----------------------------------------

所有権の3つ目のルール「所有権は一度に1つの変数だけが持てる」は、変数の代入時に具体的な形で現れます。整数のような単純な値と違い、``String`` のようにヒープ上にデータを持つ型を別の変数に代入すると、データがコピーされるのではなく所有権が移動(move)します。

.. code-block:: rust

    fn main() {
        let s1 = String::from("hello");
        let s2 = s1; // s1 の所有権が s2 に移動する(ムーブ)

        println!("s2 = {}", s2); // OK: 所有権を持つ s2 は有効
    }

この代入が行われた瞬間、``s1`` はもう無効な変数として扱われます。そのため、以下のように ``s1`` を使おうとするコードはコンパイルエラーになります。

.. code-block:: rust

    fn main() {
        let s1 = String::from("hello");
        let s2 = s1; // s1 の所有権が s2 に移動する

        println!("s1 = {}", s1); // ※これはコンパイルエラーになります
        // error[E0382]: borrow of moved value: `s1`
    }

なぜこのような制限があるのでしょうか。``String`` は内部的に、ヒープ上のデータへのポインタ・長さ・確保済み容量という情報を持つ小さな構造体です。もし ``s1`` を ``s2`` に代入したときにこのポインタなどの情報だけを単純にコピーしたとすると、``s1`` と ``s2`` の両方が同じヒープ領域を指すことになります。もし両方がスコープを抜けるときにそれぞれ ``drop`` が呼ばれると、同じメモリを2回解放してしまう「二重解放(double free)」というバグになり、深刻なメモリ破壊の原因になります。

Rust はこの問題を、代入時に元の変数を無効化する(ムーブする)ことで解決しています。これにより、常にただ1つの変数だけがヒープデータの所有者であることが保証され、スコープを抜けるときに ``drop`` が呼ばれるのは常に1回だけになります。

クローンとコピー
----------------------------------------

「データを複製したいが、元の変数もそのまま使い続けたい」という場合には、``clone`` メソッドを使ってヒープデータそのものをディープコピーします。

.. code-block:: rust

    fn main() {
        let s1 = String::from("hello");
        let s2 = s1.clone(); // ヒープ上のデータを複製(ディープコピー)する

        println!("s1 = {}, s2 = {}", s1, s2); // 両方とも有効
    }

``clone`` はヒープ上のデータを実際に複製するため、ムーブと違って処理コストがかかる場合があります。そのため Rust ではデータの複製を自動的には行わず、``clone`` を明示的に呼び出す必要があり、「見えないところでコストのかかるコピーが発生する」ことを防いでいます。

Python には、任意のオブジェクトに対する軽量な「浅いコピー」という組み込みの概念はありません。``copy`` モジュールの ``copy.copy``/``copy.deepcopy`` を明示的に使わない限り、代入は同じオブジェクトへの参照を共有するだけです。この意味で、Rust の ``clone()`` に最も近い Python の操作は ``copy.deepcopy()`` だと言えます。

一方、整数や真偽値のように、あらかじめサイズが決まっていてスタックにすべてのデータを収められる型は ``Copy`` トレイトを実装しています(スタックは関数呼び出しのたびに確保される、サイズがコンパイル時に分かるデータ向けの領域で、サイズが実行時まで確定しないデータは代わりにヒープと呼ばれる領域に置かれます)。``Copy`` を実装した型を代入すると、ムーブではなく自動的にビット単位でコピーされ、元の変数もそのまま使い続けることができます。

.. code-block:: rust

    fn main() {
        let x = 5;
        let y = x; // i32 は Copy トレイトを実装しているため自動的にコピーされる

        println!("x = {}, y = {}", x, y); // 両方とも有効
    }

``i32`` や ``bool``、``char``、そしてこれらだけで構成されたタプルなどが ``Copy`` の代表例です。逆に ``String`` や ``Vec<T>`` のようにヒープ上にデータを持つ型は ``Copy`` を実装していないため、代入するとムーブになります。

関数と所有権の移動
----------------------------------------

所有権の移動は、変数の代入だけでなく、値を関数に渡すときや関数から値を返すときにも発生します。値を関数に渡すと、``Copy`` を実装していない型であれば所有権は関数の引数に移動します。

.. code-block:: rust

    fn main() {
        let s = String::from("hello");

        takes_ownership(s); // s の所有権が関数に移動する
        // println!("{}", s); // ※これはコンパイルエラーになります(s はもう無効)

        let x = 5;
        makes_copy(x); // i32 は Copy なのでムーブされず、コピーされる
        println!("x = {}", x); // OK: x はまだ有効
    }

    fn takes_ownership(some_string: String) {
        println!("{}", some_string);
    } // ここで some_string がスコープを抜け、drop が呼ばれる

    fn makes_copy(some_integer: i32) {
        println!("{}", some_integer);
    }

逆に、関数から値を返すことで所有権を呼び出し元に戻すこともできます。

.. code-block:: rust

    fn main() {
        let s1 = gives_ownership(); // 戻り値の所有権が s1 に移動する

        let s2 = String::from("hello");
        let s3 = takes_and_gives_back(s2); // s2 の所有権が関数に移動し、
                                            // 戻り値の所有権が s3 に移動する

        println!("{} {}", s1, s3);
    }

    fn gives_ownership() -> String {
        let some_string = String::from("yours");
        some_string // 所有権を呼び出し元に返す
    }

    fn takes_and_gives_back(a_string: String) -> String {
        a_string // 受け取った所有権をそのまま呼び出し元に返す
    }

毎回このように所有権を渡したり返したりするのは冗長に感じるかもしれません。次章で学ぶ「参照と借用」を使うと、所有権を移動させずに値を関数に貸し出すことができるようになります。

スコープと解放処理
----------------------------------------

所有権のルールの2つ目「所有者がスコープを抜けると値は破棄される」は、Rust の ``Drop`` トレイトによって実現されています。変数がスコープを抜けるとき、コンパイラはその型が ``Drop`` トレイトを実装していれば ``drop`` メソッドを自動的に呼び出し、確保していたリソース(ヒープメモリ、ファイルハンドル、ネットワーク接続など)を解放します。

このタイミングはコンパイル時に静的に決まるため、実行時にガベージコレクタが動作するタイミングを気にする必要がありません。プログラマは ``free`` や ``delete`` を明示的に呼ぶ必要もなく、かといって実行時にいつ解放されるか分からない不安からも解放されます。``Drop`` トレイト自体を自分で実装する方法は本書の範囲を超えますが、「スコープを抜ける=リソース解放のタイミング」という対応関係を覚えておくとよいでしょう。

.. admonition:: Python 経験者向けメモ
   :class: tip

   Python はオブジェクトの参照カウントによってメモリを自動管理しており、変数へ代入しても基本的に元の変数がそのまま使えなくなることはありません。``a = [1, 2, 3]`` のあとに ``b = a`` としても ``a`` は引き続き有効です。誰がそのオブジェクトを参照しているかを意識しなくても、参照カウントが 0 になった時点で GC がこっそり片付けてくれます。

   一方 Rust では、値の所有者は常にただ1つであり、代入や関数呼び出しのたびに所有権が移動する可能性があります。これは実行時のコストを一切かけずにメモリ安全性を保証するための仕組みですが、「値が今どの変数に所有されているか」を常に意識する必要がある、という点が Python との決定的な違いです。最初は窮屈に感じるかもしれませんが、借用(次章)を使いこなせるようになると、所有権の移動を最小限に抑えつつ自然にコードが書けるようになります。

まとめ
------

- Rust の所有権には「所有者は1つだけ」「スコープを抜けると破棄される」「所有権は同時に1つの変数だけが持てる」という3つのルールがあります
- ヒープデータを持つ型(``String`` など)を別の変数に代入すると所有権が「ムーブ」し、元の変数は無効になります
- 元の変数もそのまま使いたい場合は ``clone`` によるディープコピーを行います
- ``i32`` などの ``Copy`` トレイトを実装した型は代入時に自動的にコピーされ、ムーブされません
- 値を関数に渡す・関数から返すときにも所有権は移動し、スコープを抜けるときに ``Drop`` によって自動的にリソースが解放されます
