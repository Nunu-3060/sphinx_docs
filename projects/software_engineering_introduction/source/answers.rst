各章の演習問題と発展課題の解答例を示す。記述式の問題は、ここに示した以外の解答も考えられる。考え方が合っていれば正解としてよい。

第 1 章の解答例
---------------

**問題 1-1**\ ：例えば次の 2 つが挙げられる。1 つ目は、OS やライブラリ、ハードウェアなどの実行環境が変化し、それに対応しなければ動作しなくなるためである。2 つ目は、利用者の業務や法制度が変化し、ソフトウェアに求められる機能が変わるためである。このほか、リリース後に発見された不具合の修正も必要になる。

**問題 1-2**\ ：例えば、ソースコードの規模（LOC）やファンクションポイントを測定して工数を見積もること、テストのカバレッジや発見された不具合の数を測定して品質を評価することが挙げられる（第 10 章、第 11 章）。

**問題 1-3**\ ：(a) と (c) は本質的な困難（(a) は複雑性、(c) は可変性）であり、(b) は偶有的な困難である。(b) はビルド環境の改善などの道具の改良で解消できるが、(a) と (c) はソフトウェアが扱う問題そのものに由来するため、道具の改良では解消できない。

**発展課題 1-A**\ ：解答は調べた事例によって異なる。次の観点で整理するとよい。

* 本質的な困難の例: 業務や制度が複雑で要求を正しく定義できなかった（複雑性）、開発中に要求が大きく変わった（可変性）、進捗や品質の問題が見えないまま終盤まで進んだ（不可視性）。
* 偶有的な困難の例: 開発環境やツールが不十分であった、テストの自動化ができておらず回帰テストに時間がかかった。
* 防げた可能性がある技法の例: 要求の検証とトレーサビリティ（第 3 章）、反復型開発による早期のフィードバック（第 2 章）、継続的インテグレーション（第 8 章）、メトリクスによる進捗と品質の可視化（第 10 章）、見積もりの不確実性を考慮した計画とリスク管理（第 11 章）。

本質的な困難は技法によって「なくす」ことはできず、「早く見つけて小さく対処する」ことしかできない点に注意して論じるとよい。

第 2 章の解答例
---------------

**問題 2-1**\ ：(a) はウォーターフォールモデルまたは V 字モデルが適している。要求が安定しており、規制のために工程ごとの文書が必要だからである。特に V 字モデルを用いると、各工程に対応するテストの計画を早い段階で立てられる。(b) はアジャイル開発が適している。要求が不確実であり、短い反復で動くソフトウェアを提供して利用者からのフィードバックを得る必要があるからである。

**問題 2-2**\ ：ドキュメントが不要という意味ではない。宣言には「左記のことがらに価値があることを認めながらも、私たちは右記のことがらにより価値をおく」とあり、ドキュメントにも価値があることを認めたうえで、動くソフトウェアをより優先するという優先順位を示している。

**問題 2-3**\ ：スプリントレビューは、スプリントで作成した成果物（インクリメント）を対象とし、利害関係者に示してフィードバックを得るイベントである。スプリントレトロスペクティブは、チームの進め方（プロセス、人間関係、ツールなど）を対象とし、次のスプリントに向けた改善策を決めるイベントである。前者は「何を作ったか」、後者は「どのように作ったか」を振り返る。

**発展課題 2-A**\ ：利点と欠点の例を次に示す。

.. list-table:: スプリントの長さの比較
   :header-rows: 1
   :widths: 20 40 40

   * - 長さ
     - 利点
     - 欠点
   * - 1 週間
     - フィードバックを頻繁に得られ、方向の修正が早い。計画の誤差が小さく、問題が早く表面化する。
     - スプリントプランニングやレビューなどのイベントの時間が開発時間に対して相対的に大きくなる。1 週間で完成させられる大きさに作業を分割する必要がある。
   * - 4 週間
     - まとまった機能を 1 つのスプリントで完成させやすい。イベントにかかる時間の割合が小さい。
     - フィードバックが得られるまでの期間が長く、誤った方向に進んだ場合の損失が大きい。スプリントの途中で要求が変わりやすい。

要求が頻繁に変わる新規の Web サービスでは、1 週間（または 2 週間）を選ぶのが妥当である。利用者の反応を早く確認し、プロダクトバックログの優先順位を頻繁に見直すことの価値が、イベントにかかる時間の負担を上回るからである。

第 3 章の解答例
---------------

**問題 3-1**\ ：(a) と (c) は機能要求、(b) と (d) は非機能要求である。(b) は性能効率性、(d) はセキュリティに関する非機能要求である。

**問題 3-2**\ ：「曖昧でない」と「検証可能である」を満たしていない。何をもって「使いやすい」とするかが人によって異なり、満たしているかを判定できないからである。例えば「初めて利用する会員の 90 % 以上が、説明書を読まずに 3 分以内に商品の注文を完了できる」のように、測定できる形に書き換える。

**問題 3-3**\ ：ユーザーストーリーの例を次に示す。

.. code-block:: text
   :linenos:

   ポイント会員として、ポイントを使うかどうかを決めるために、買い物の前に自分のポイント残高を確認できる機能がほしい。

受け入れ基準の例を次に示す。

.. code-block:: text
   :linenos:

   Given ポイント会員のポイント残高が 1200 ポイントである
   When  会員がマイページを開く
   Then  「ポイント残高: 1200 ポイント」と表示される

**発展課題 3-A**\ ：要求の例を次に示す。

* 機能要求の例: 利用者は書名、著者名、ISBN で蔵書を検索できる。利用者は検索結果から蔵書の所在（館と書架）と貸出状況を確認できる。利用者は貸出中の蔵書を予約できる。利用者は自分の貸出・予約の状況を確認できる。職員は蔵書を登録・削除できる。
* 非機能要求の例: 検索結果は 95 % の要求について 2 秒以内に表示する。開館時間中の稼働率は 99.5 % 以上とする。利用者の貸出履歴は職員のうち権限を持つ者だけが閲覧できる。

自己レビューでは、例えば「検索が速いこと」は検証可能でないため、上の例のように時間と割合で書き直す。「利用者は蔵書を検索・予約できる」のように 1 つの要求に複数の事柄が含まれている場合は、「単一である」を満たすように分ける。ユースケース図では、アクターとして「利用者」「職員」を、ユースケースとして上の機能要求に対応するものを描く。他の図書館システムと連携する場合は、それも外部システムのアクターとして描く。

第 8 章の解答例
---------------

**問題 8-1**\ ：(b) がよいコミットメッセージである。何を変更したかに加えて、なぜ変更したかが書かれている。(a) と (c) は、変更の内容も理由も分からず、後から履歴を調べるときに役に立たない。また、(c) は 1 つの目的ではなく作業した期間でコミットをまとめており、コミットの単位としても適切でない。

**問題 8-2**\ ：main ブランチとの差が大きくなり、マージの際に多くのコンフリクトが発生する。また、他の開発者の変更との不整合が統合するまで発見されず、統合の段階でまとめて問題が見つかるため、原因の特定と修正に時間がかかる。継続的インテグレーションは、変更を小さく頻繁に統合することでこの問題を防ぐ慣行である。

**問題 8-3**\ ：継続的デリバリーは、すべての変更をいつでも本番環境にリリースできる状態に保つが、本番環境へのリリースは人が判断して実行する。継続的デプロイは、パイプラインのすべての段階に合格した変更を、人の判断を介さずに自動的に本番環境に配置する。

**発展課題 8-A**\ ：解答例を次に示す。リポジトリの ``.github/workflows/check.yml`` として保存する。``strategy.matrix`` によって、2 つのバージョンの Python で同じ検査を並行して実行する。

.. code-block:: yaml
   :linenos:
   :caption: .github/workflows/check.yml

   name: check

   on:
     push:
       branches: [main]
     pull_request:

   jobs:
     check:
       runs-on: ubuntu-latest
       strategy:
         matrix:
           python-version: ["3.12", "3.13"]
       steps:
         - uses: actions/checkout@v4
         - uses: actions/setup-python@v5
           with:
             python-version: ${{ matrix.python-version }}
         - run: python -m pip install flake8 mypy
         - run: python adv06_check.py .
           working-directory: examples

検査が失敗すると ``adv06_check.py`` が終了コード 1 を返し、ワークフローが失敗として表示される。リポジトリの設定で、このワークフローの成功をプルリクエストのマージの条件にすると、検査に合格しない変更が main ブランチに入ることを防げる。

**問題 11-1**\ ：経路は A → B → D → E → F（3 + 4 + 2 + 3 + 2 = 14 日）と A → C → E → F（3 + 7 + 3 + 2 = 15 日）の 2 つである。したがって、クリティカルパスは A → C → E → F であり、プロジェクト全体の所要日数は 15 日である。クリティカルパス上にない作業 B と D には 1 日の余裕がある。ただし、この余裕は B と D で共有しているため、B が 1 日遅れると D の余裕はなくなる。

**問題 11-2**\ ：工数と開発期間は次のとおりである。

.. math::

   E = 2.4 \times 100^{1.05} \approx 302.1 \text{（人月）}, \qquad D = 2.5 \times 302.1^{0.38} \approx 21.9 \text{（月）}

50 KLOC の場合の工数は約 145.9 人月であるから、規模が 2 倍になると工数は :math:`2^{1.05} \approx 2.07` 倍になる。規模に比例する以上に工数が増える、規模の不経済の例である。

**問題 11-3**\ ：6 人のときは :math:`6 \times 5 / 2 = 15` 本、9 人のときは :math:`9 \times 8 / 2 = 36` 本であり、15 本から 36 本に増える。人数は 1.5 倍であるが、経路の数は 2 倍以上になる。

実行結果を次に示す（乱数の種を 1 に固定した場合）。

.. code-block:: text
   :linenos:

   最頻値だけで計算した所要日数: 15.0 日
   シミュレーションの平均: 17.5 日
   50 % の確率で終わる日数: 17.5 日
   90 % の確率で終わる日数: 19.8 日
   最頻値の日数以内に終わる確率: 6.9%

最頻値だけで計算した 15 日以内に終わる確率は、わずか 7 % 程度である。これには 2 つの理由がある。1 つ目は、各作業の見積もりが悲観値の側に長く伸びた非対称な分布であり、平均が最頻値より大きいことである。2 つ目は、作業 E の開始が C と D の両方の完了を待つため、どちらか一方が遅れるだけで E が遅れることである（遅いほうの経路に合わせて進むため、経路が合流するたびに遅れやすくなる）。このように、最もありそうな値を積み上げた見積もりは楽観的になりやすい。見積もりは「90 % の確率で 20 日以内」のように、確率と幅を伴って示すことが望ましい。
