仕上げとテスト
==============

ゲームは、動くようになってからが本番である。何度も遊んで数値を調整し、不具合を直すことで、ようやく人に遊んでもらえる品質になる。この章では、テストプレイによる調整と、単体テストによる確認の方法を説明する。

テストプレイ
------------

確かめる観点
^^^^^^^^^^^^

テストプレイでは、ただ遊ぶのではなく、:numref:`table-playtest` の観点を意識して遊ぶ。

.. _table-playtest:

.. list-table:: テストプレイで確かめる観点
   :header-rows: 1
   :widths: 25 75

   * - 観点
     - 確かめること
   * - 操作
     - 思ったとおりに動くか。移動が速すぎたり遅すぎたりしないか。連射は気持ちよいか。
   * - 難易度
     - 最初の数十秒で操作に慣れられるか。慣れたころに難しくなるか。理不尽にやられないか。
   * - 分かりやすさ
     - 自機と敵と弾を見分けられるか。なぜやられたかが分かるか。今どのシーンにいるか分かるか。
   * - 音
     - 効果音がうるさすぎないか。BGM と効果音の音量のバランスはよいか。
   * - 長時間のプレイ
     - ステージを何周しても動き続けるか。だんだん処理が重くならないか。

自分で作ったゲームは、作った本人には易しく感じられる。操作に慣れているうえに、敵がどこから出てくるかを知っているからである。可能なら、ほかの人に遊んでもらい、横で黙って見る。どこで迷い、どこでやられるかを観察すると、自分では気付けない問題が見つかる。

難易度を調整する
^^^^^^^^^^^^^^^^

難易度は、少しずつ上がっていくのが理想である。題材ゲームでは、:numref:`table-difficulty` の値で難易度を決めている。``level`` はステージをクリアするたびに 1 増える。

.. _table-difficulty:

.. list-table:: 難易度を決める主な値（完成版）
   :header-rows: 1
   :widths: 35 35 30

   * - 値
     - 計算式
     - level 0 → 1 → 2
   * - 敵の出現間隔（フレーム）
     - max(10, 30 - level × 5)
     - 30 → 25 → 20
   * - 敵 A の速さ（ピクセル／フレーム）
     - 1.5 + 0.2 × level
     - 1.5 → 1.7 → 1.9
   * - 敵 C の弾の速さ
     - 1.5 + 0.2 × level
     - 1.5 → 1.7 → 1.9
   * - ボスの体力
     - 50 + 20 × level
     - 50 → 70 → 90

調整するときは、次のことに気を付ける。

* **一度に 1 つの値だけを変える。**\ 複数の値を同時に変えると、どれが効いたのか分からなくなる。
* **最初は易しくする。**\ 最初の 10 秒間は、まっすぐ進むだけの敵 A しか出ないようにしている。プレイヤーはここで操作を覚える。
* **やられた理由が分かるようにする。**\ 画面の外から突然速い弾が飛んでくると、プレイヤーは理不尽に感じる。敵 C が止まってから弾を撃つまで間を空けているのは、撃たれる前に身構えられるようにするためである。

調整のたびにボスまで遊ぶのは時間がかかる。開発中だけ ``BOSS_FRAME`` を小さくする、残機を増やすといった工夫をすると効率がよい。ただし、公開する前に必ず元の値に戻す。

手触りを良くする工夫
--------------------

数値の調整に加えて、細かな工夫の積み重ねが、ゲームの手触り（遊んでいて気持ちよいかどうか）を良くする。題材ゲームで使った工夫を\ :numref:`table-game-feel` にまとめる。

.. _table-game-feel:

.. list-table:: 題材ゲームで使った手触りの工夫
   :header-rows: 1
   :widths: 35 65

   * - 工夫
     - 効果
   * - 自機の当たり判定を小さくする
     - ぎりぎりで避けたときに「うまく避けた」と感じられる（第 6 章）。
   * - 無敵時間と点滅
     - やられた直後に連続でやられる理不尽さを防ぐ（第 6 章）。
   * - 被弾した敵を白く光らせる
     - 体力のある敵に弾が当たっていることが分かる（第 7 章）。
   * - 画面の揺れ
     - やられたときやボスを倒したときの衝撃を伝える（第 7 章）。
   * - ゲームオーバー後の入力待ち
     - 連打していてもゲームオーバー画面を読み飛ばさない（第 7 章）。

さらに手触りを良くする方法として、**ヒットストップ**\ がある。大きな敵を倒した瞬間に、ゲームの進行を数フレームだけ止める演出である。止まることで、倒した瞬間が強く印象に残る。題材ゲームには入れていないが、``PlayScene`` に次のように加えれば実現できる。

.. code-block:: python
   :linenos:

   def update(self) -> Scene:
       # ヒットストップ中は、残りフレーム数を減らすだけで何も動かさない
       if self.hitstop > 0:
           self.hitstop -= 1
           return self
       ...  # これまでの処理

``self.hitstop`` は ``__init__()`` で 0 にしておき、ボスを倒したときに 10 程度の値を設定する。``draw()`` は普段どおり呼ばれるので、物体は止まった位置で表示され続ける。ただし、``pyxel.frame_count`` からコマを決めているアニメーションと、``update()`` で減らしている画面の揺れは止まらない。完全に止めたい場合は、アニメーションのコマを物体ごとのカウンター（``Explosion`` の ``age`` など）で決め、ヒットストップ中は画面を揺らさないようにする。

性能を確かめる
--------------

Pyxel は高速に動くので、題材ゲームの規模で処理が重くなることはまずない。それでも、物体を消し忘れるとリストが増え続け、長く遊ぶうちに重くなる。

実行中に Alt + 0 を押すと、画面にパフォーマンスモニターが表示される。fps と、``update()`` と ``draw()`` にかかった時間が分かる。プログラムから表示したい場合は ``pyxel.perf_monitor(True)`` を呼ぶ。

当たり判定は、弾の数と敵の数を掛けた回数だけ行われる。弾が 30 発、敵が 20 体なら 1 フレームに 600 回である。この程度なら問題にならないが、数千の物体を扱うゲームを作る場合は、画面を格子に区切って近くの物体だけを調べるなどの工夫が必要になる。

単体テスト
----------

テストする部分を選ぶ
^^^^^^^^^^^^^^^^^^^^

ゲームの面白さは遊んで確かめるしかないが、当たり判定や体力の計算のようなロジックは、自動テストで確かめられる。特に、後から当たり判定の仕組みを変えたときに、以前の動きが壊れていないかを一瞬で確かめられるのは大きな利点である。

自動テストに向いているのは、描画や入力に依存しない部分である。題材ゲームでは、``Entity``、``overlaps()``、``Enemy.damage()`` などがこれにあたる。第 3 章で ``update()`` と ``draw()`` を分けた理由の 1 つがここにある。状態を変える処理が描画と混ざっていると、画面を用意しなければテストできない。

テストを書く
^^^^^^^^^^^^

テストには pytest を使う。

.. code-block:: console
   :linenos:

   > pip install pytest

:numref:`list-test` が完成版のテストである。

.. _list-test:

.. literalinclude:: ../examples/tests/test_cosmo_rush.py
   :language: python
   :linenos:
   :caption: tests/test_cosmo_rush.py

:download:`test_cosmo_rush.py をダウンロード <../examples/tests/test_cosmo_rush.py>`

* 17 ～ 21 行目では、辺がちょうど接しているだけの場合に当たらないことを確かめている。このような境界の値は、不等号の向きの誤りが出やすいところである。
* 24 ～ 29 行目では、``margin`` によって当たり判定が小さくなることを確かめている。
* 最後の 2 つのテストでは、敵が体力の分だけ弾に耐えることを確かめている。

7 行目で完成版の ``main.py`` を ``main`` モジュールとして読み込んでいる。``main.py`` の最後は ``if __name__ == "__main__":`` で囲んであるので、読み込んでもゲームは起動しない。``main`` モジュールが見つかるのは、``setup.cfg`` の ``[tool:pytest]`` の節で、``cosmo_rush`` ディレクトリを読み込み先に加えているからである（``pythonpath = cosmo_rush``）。mypy のために、``[mypy]`` の節にも ``mypy_path = cosmo_rush`` を指定している。

テストを実行する
^^^^^^^^^^^^^^^^

``examples`` ディレクトリで ``pytest`` を実行する。

.. code-block:: console
   :linenos:

   > pytest
   ....... [100%]
   7 passed in 0.64s

テストのファイルも、ゲームのコードと同じく flake8 と mypy で検査する。

.. code-block:: console
   :linenos:

   > mypy tests/test_cosmo_rush.py
   Success: no issues found in 1 source file

よくある不具合と対処
--------------------

ゲーム制作で初心者がつまずきやすい不具合を\ :numref:`table-common-bugs` にまとめる。

.. _table-common-bugs:

.. list-table:: よくある不具合と対処
   :header-rows: 1
   :widths: 35 65

   * - 症状
     - 原因と対処
   * - 一部の敵に弾が当たらない
     - for 文でリストをたどりながら ``remove()`` で要素を取り除くと、次の要素が読み飛ばされる。``alive`` を False にしておき、フレームの最後に新しいリストを作り直す（第 3 章、第 6 章）。
   * - 長く遊ぶと重くなる
     - 画面の外に出た物体を消していない。リストの長さを画面に表示して確かめる（第 6 章）。
   * - 動く物体の残像が残る
     - ``draw()`` の最初で ``pyxel.cls()`` を呼んでいない（第 3 章）。
   * - 絵の周りが黒い四角形になる
     - ``pyxel.blt()`` の引数 colkey に透明色を指定していない（第 7 章）。
   * - 一部の描画だけがずれる、色が変わる、間引かれる
     - ``pyxel.camera()``、``pyxel.pal()``、``pyxel.dither()`` の設定を元に戻していない（第 7 章）。
   * - リソースファイルが見つからない
     - 相対パスは実行したスクリプトのあるディレクトリが基準になる。ファイルの置き場所とパスを確かめる。
   * - BGM の一部が途切れる
     - BGM が使っているチャンネルで効果音を鳴らしている。効果音は空いているチャンネルで鳴らす（第 5 章）。
   * - キーを押し続けると何度も反応する
     - 1 回だけ反応してほしい処理に ``pyxel.btn()`` を使っている。``pyxel.btnp()`` を使う（第 3 章）。
   * - 速い弾が敵をすり抜ける
     - 1 フレームで動く距離が当たり判定の大きさより大きいと、前後のフレームで重ならずに通り過ぎる。弾の速さを当たり判定の大きさより小さくするか、1 フレームを何回かに分けて動かして判定する。題材ゲームでは、自機の弾の速さ（5）を敵の当たり判定の高さ（12）より小さくしている。

まとめ
------

* テストプレイでは観点を決めて遊び、数値は 1 つずつ調整する。ほかの人に遊んでもらうと、自分では気付けない問題が見つかる。
* 当たり判定の大きさ、無敵時間、被弾の表現、画面の揺れなどの小さな工夫が、手触りを良くする。
* 描画に依存しないロジックは pytest で自動テストする。そのためにも、状態の更新と描画を分けておく。
