第 4 章 GPU とレンダリングパイプライン
======================================

GPU は、メッシュのデータを受け取ってから画面のピクセルに色を書き込むまでを、決まった段階の流れで処理する。この流れをレンダリングパイプラインという。この章では、各段階の役割と、シェーダーがどの段階で実行されるかを説明する。最後に、レンダリングパイプラインの外で GPU に計算をさせるコンピュートシェーダーも紹介する。

CPU と GPU の役割
-----------------

CPU は、何をどの順番で描画するかを決め、GPU に描画の命令を送る。この命令をドローコールという。GPU は、ドローコールを受け取ると、メッシュの頂点やピクセルを大量に並列で処理する。

GPU は、同じ処理を多数のデータに同時に適用するのが得意である。頂点シェーダーは頂点の数だけ、フラグメントシェーダーはピクセルの数だけ実行されるが、GPU はこれらを数千単位で並列に実行する。一方で、1 つの処理の中で条件によって異なる処理を行う（分岐する）と、並列処理の効率が下がることがある。この点は第 17 章で詳しく説明する。

パイプラインの流れ
------------------

レンダリングパイプラインの主な段階を、処理の順に示す。「プログラム可能」の列が「はい」の段階は、シェーダーで処理の内容を書ける。

.. list-table::
   :header-rows: 1
   :widths: 25 15 60

   * - 段階
     - プログラム可能
     - 内容
   * - 入力アセンブラー
     - いいえ
     - メッシュの頂点データ（位置、法線、UV 座標など）とインデックスを読み込む。
   * - 頂点シェーダー
     - はい
     - 頂点ごとに実行され、頂点の位置をクリップ空間に変換する。法線や UV 座標など、あとの段階で使うデータも出力する。
   * - クリッピング
     - いいえ
     - 視錐台の外にある三角形を取り除き、境界をまたぐ三角形を切り取る。
   * - 透視除算とビューポート変換
     - いいえ
     - クリップ空間の座標を NDC に、さらにスクリーン空間の座標に変換する（第 3 章を参照）。
   * - カリング
     - いいえ
     - カメラから見て裏を向いている三角形を取り除く（設定で変更できる）。
   * - ラスタライズ
     - いいえ
     - 三角形が覆うピクセルを求め、ピクセルごとのフラグメントを生成する。頂点シェーダーの出力は、三角形の内部で補間される。
   * - フラグメントシェーダー
     - はい
     - フラグメントごとに実行され、その色を計算する。ピクセルシェーダーとも呼ぶ。
   * - 深度テストとステンシルテスト
     - いいえ
     - すでに描画されているものより奥にあるフラグメントなどを破棄する（設定で変更できる）。
   * - ブレンド
     - いいえ
     - フラグメントの色と、画面にすでに描かれている色を合成して書き込む（設定で変更できる）。

「設定で変更できる」と書いた段階は、処理の内容をシェーダーのコードとしては書けないが、ShaderLab のコマンド（第 6 章を参照）で動作を選べる段階である。

この表のほかに、頂点シェーダーとクリッピングの間には、テッセレーションとジオメトリシェーダーという省略できる段階がある。これらは本資料では扱わない。理由は、この章の最後で説明する。

.. note::

   フラグメントは、最終的にピクセルの色になる候補のデータである。1 つのピクセルに複数の三角形が重なっている場合、そのピクセルには複数のフラグメントが生成され、深度テストやブレンドを経て最終的な色が決まる。本資料では、フラグメントシェーダーの処理の単位を説明するときに、分かりやすさのため「ピクセルごと」と表現することがある。

頂点シェーダー
--------------

頂点シェーダーは、メッシュの頂点ごとに 1 回実行される。入力は 1 つの頂点のデータで、出力はその頂点のクリップ空間の位置と、フラグメントシェーダーに渡すデータである。頂点シェーダーからは、ほかの頂点のデータを参照できない。

頂点シェーダーで頂点の位置を変えると、メッシュの形を変えられる。第 13 章では、この性質を使って波打つ表面を作る。

ラスタライズと補間
------------------

ラスタライズでは、三角形が覆うピクセルを求める。このとき、頂点シェーダーが出力した値（法線や UV 座標など）は、三角形の 3 つの頂点の値から、ピクセルの位置に応じて補間される。例えば、3 つの頂点の色が赤、緑、青の三角形では、内部のピクセルの色はそれらが混ざった色になる。

透視投影では、画面上で単純に線形補間すると、奥行きのある面でテクスチャーが歪んでしまう。GPU は、透視投影を考慮した補間（パースペクティブ補正）を自動的に行う。

補間された方向ベクトルは、長さが 1 でなくなる。例えば、長さ 1 の 2 つの法線の中間を線形補間すると、長さは 1 より短くなる。そのため、フラグメントシェーダーでは、補間された法線を ``normalize`` 関数で正規化し直してから使う。

フラグメントシェーダー
----------------------

フラグメントシェーダーは、フラグメントごとに 1 回実行され、そのフラグメントの色を出力する。入力は、頂点シェーダーの出力を補間した値である。テクスチャーの読み取り（サンプリング）やライティングの計算は、主にフラグメントシェーダーで行う。

フラグメントシェーダーは、画面の解像度が高いほど多く実行される。例えば、1920×1080 の画面全体を覆うオブジェクトでは、1 回の描画で約 200 万回実行される。そのため、フラグメントシェーダーの処理の重さは、描画の速度に大きく影響する。

深度テスト
----------

深度テストは、手前のものが奥のものを正しく隠すようにする処理である。GPU は、画面のピクセルごとの深度（カメラからの奥行き）を、深度バッファーと呼ばれる領域に記録している。新しいフラグメントの深度を深度バッファーの値と比べ、奥にあれば破棄し、手前にあれば色を書き込んで深度バッファーを更新する。

深度テストを行えば、描画の順序に関係なく、手前のものが奥のものを隠すようになる。ただし、半透明のものは奥のものを隠さずに透かして見せる必要があるため、深度テストだけでは正しく描画できない。この問題は第 12 章で扱う。

.. note::

   多くの GPU は、フラグメントシェーダーを実行する前に深度テストを行い、隠れることが分かっているフラグメントのシェーダーの実行を省く（Early-Z）。ただし、フラグメントシェーダーで ``clip`` 関数（第 12 章を参照）を使うなど、実行してみないと描画されるかどうかが決まらない場合は、この最適化が働かないことがある。

ブレンド
--------

ブレンドは、フラグメントシェーダーが出力した色と、画面にすでに描かれている色を合成する処理である。不透明なオブジェクトでは、ブレンドを行わずに色をそのまま上書きする。半透明のオブジェクトでは、アルファ（不透明度）に応じて 2 つの色を混ぜる。ブレンドの方法は、ShaderLab の ``Blend`` コマンドで指定する（第 12 章を参照）。

テッセレーションとジオメトリシェーダー
--------------------------------------

レンダリングパイプラインには、頂点シェーダーのあとに、次の 2 つの省略できる段階がある。どちらも、三角形を増やしたり作り変えたりするための段階である。

.. list-table::
   :header-rows: 1
   :widths: 25 75

   * - 段階
     - 内容
   * - テッセレーション
     - 三角形を細かく分割して、頂点を増やす。分割の細かさを決めるハルシェーダー、実際に分割する固定機能のテッセレーター、分割で増えた頂点の位置を決めるドメインシェーダーの 3 つの段階からなる。カメラに近い部分だけを細かくする、高さのテクスチャーで表面を凹凸に変形する（ディスプレースメント）などに使われる。
   * - ジオメトリシェーダー
     - 三角形などの図形（プリミティブ）ごとに実行され、図形を増やしたり、消したり、別の形の図形に作り変えたりする。1 つの点から板ポリゴンを作る、ワイヤーフレームを描く、草の葉を生やすなどに使われる。

Unity でも、``#pragma hull``、``#pragma domain``、``#pragma geometry`` でこれらの段階を使うシェーダーを書ける。しかし、本資料では次の理由から扱わない。

* 動作する環境が限られる。Metal（iOS、macOS）はジオメトリシェーダーに対応していない。WebGL は、テッセレーションとジオメトリシェーダーのどちらにも対応していない。URP は幅広い環境で動かすためのレンダーパイプラインであり（第 5 章を参照）、この制限と相性が悪い。
* URP の標準のシェーダーは、どちらの段階も使っていない。URP 用の Shader Graph でも、これらの段階は使えない。
* ジオメトリシェーダーは、GPU によっては処理が遅く、特にスマートフォンで性能が大きく落ちることがある。
* 多くの場合、ほかの方法で同じ表現ができる。

代わりに使われる主な方法を、次の表に示す。

.. list-table::
   :header-rows: 1
   :widths: 35 65

   * - 目的
     - 代わりの方法
   * - 頂点を増やして細かく変形する
     - 頂点の多いメッシュを用意し、頂点シェーダーで変形する（第 13 章を参照）。距離に応じて細かさを変えたい場合は、LOD Group で距離ごとにメッシュを切り替える。
   * - 1 つの点から板ポリゴンを作る
     - 板ポリゴンのメッシュを用意し、頂点シェーダーでカメラの方に向ける（第 13 章のビルボードを参照）。大量に描画する場合は、GPU インスタンシングや、Particle System、VFX Graph を使う。
   * - 草など、大量の図形を GPU で生成する
     - コンピュートシェーダーで図形のデータを作り、C# の ``Graphics.RenderPrimitives`` などの関数で描画する。

.. note::

   HDRP には、標準の Lit シェーダーや Shader Graph でテッセレーションを使う機能がある。高性能な PC や家庭用ゲーム機向けに、テッセレーションによる細かい凹凸を使いたい場合は、HDRP を検討するとよい。

コンピュートシェーダー
----------------------

これまでに説明したシェーダーは、すべてレンダリングパイプラインの段階の 1 つとして実行され、頂点やフラグメントを処理する。一方、コンピュートシェーダーは、レンダリングパイプラインの外で、GPU に汎用の計算をさせるためのシェーダーである。三角形やピクセルとは関係なく、指定した数のスレッドを並列に実行する。

主な用途を、次の表に示す。

.. list-table::
   :header-rows: 1
   :widths: 30 70

   * - 用途
     - 例
   * - シミュレーション
     - 大量のパーティクル、群衆、流体、布などの動きの計算。Unity の VFX Graph も、内部でコンピュートシェーダーを使っている。
   * - 図形の生成
     - 草や岩などの大量の図形の位置や形のデータの生成（この章の「テッセレーションとジオメトリシェーダー」の表を参照）。
   * - 画像処理
     - テクスチャーのぼかし、縮小、ヒストグラムの集計など。
   * - 描画の準備
     - 見えないオブジェクトを GPU で描画の対象から外す処理（GPU カリング）など。

コンピュートシェーダーの基本
~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Unity では、コンピュートシェーダーを ``.compute`` という拡張子のファイルに書く。Project ウィンドウで右クリックし、:menuselection:`Create --> Shader --> Compute Shader` で作成できる。ShaderLab は使わず、HLSL だけで書く。

次のコードは、テクスチャーの各ピクセルに、位置に応じたグラデーションの色を書き込む例である。

.. code-block:: hlsl

   // コンピュートシェーダーの入り口の関数（カーネル）を指定する
   #pragma kernel FillGradient

   // 書き込み先のテクスチャー（RW は読み書きできることを表す）
   RWTexture2D<float4> Result;

   // 1 つのスレッドグループに含まれるスレッドの数（8 × 8 × 1 = 64）
   [numthreads(8, 8, 1)]
   void FillGradient(uint3 id : SV_DispatchThreadID)
   {
       // id.xy は、このスレッドが担当するピクセルの位置
       Result[id.xy] = float4(id.x / 255.0, id.y / 255.0, 0.0, 1.0);
   }

コンピュートシェーダーは、C# のスクリプトから実行する。次のコードは、256×256 ピクセルのテクスチャーに対して、上のカーネルを実行する例である。

.. code-block:: csharp

   // _computeShader には、Inspector ウィンドウで .compute のアセットを設定しておく
   int kernel = _computeShader.FindKernel("FillGradient");

   RenderTexture texture = new RenderTexture(256, 256, 0);
   // コンピュートシェーダーから書き込めるようにする
   texture.enableRandomWrite = true;
   texture.Create();

   _computeShader.SetTexture(kernel, "Result", texture);
   // 8 × 8 スレッドのグループを、縦横に 256 / 8 = 32 個ずつ実行する
   _computeShader.Dispatch(kernel, 256 / 8, 256 / 8, 1);

コードのポイントは、次のとおりである。

* ``#pragma kernel`` で、C# から呼び出す関数（カーネル）を指定する。
* ``[numthreads(8, 8, 1)]`` で、1 つのスレッドグループのスレッドの数を指定する。C# の ``Dispatch`` 関数では、スレッドの数ではなく、スレッドグループの数を指定する。この例では 32 × 32 個のグループが実行され、合計で 256 × 256 個のスレッドが 1 ピクセルずつ担当する。
* ``SV_DispatchThreadID`` セマンティクスの引数には、全体の中でのスレッドの番号が入る。
* 結果は GPU のメモリ（テクスチャーやバッファー）に残る。結果のテクスチャーをマテリアルに設定すれば、そのまま描画に使える。結果を CPU に読み戻す処理は時間がかかるため、必要な場合は ``AsyncGPUReadback`` による非同期の読み戻しを使う。

対応する環境
~~~~~~~~~~~~

コンピュートシェーダーは、Direct3D 11 以降（シェーダーモデル 5.0）、Metal、Vulkan、OpenGL 4.3 以降、OpenGL ES 3.1 以降で使える。WebGL では使えない。実行時に使えるかどうかは、C# の ``SystemInfo.supportsComputeShaders`` で確認できる。

本資料で扱う範囲
~~~~~~~~~~~~~~~~

コンピュートシェーダーを効果的に使うには、スレッドグループの大きさの決め方や、スレッド間でのデータの共有と同期など、並列処理のアルゴリズムの知識が必要になる。これは、本資料の主題である「オブジェクトを描画するシェーダー」とは別の分野である。そのため、本資料ではこの節の紹介にとどめる。詳しくは、付録 C の Unity マニュアルを参照してほしい。
