GPU のアーキテクチャ
====================

**GPU**\ （Graphics Processing Unit）は、もともと 3 次元グラフィックスの描画を高速に行うための専用プロセッサでした。しかし、その本質である「大量のデータに同じ処理を並列に適用する能力」は、科学技術計算や深層学習にもそのまま役立ちます。現在では、スーパーコンピューターの演算性能の大部分や、大規模言語モデルの学習と推論を支えているのは GPU です。

この章では、GPU が CPU とどのように異なる設計思想に基づいているかを出発点に、GPU の歴史、ハードウェアの構成、SIMT と呼ばれる実行モデル、レイテンシの隠し方、分岐やメモリアクセスが性能に与える影響、CUDA によるプログラミング、行列積の高速化、そして性能の見積もり方までを順に説明します。「:doc:`15_parallel`」で説明した SIMD やマルチコアの知識を前提とし、両者の違いもこの章で整理します。具体的な製品の数値は世代によって変わるので、仕組みを理解するための目安として読んでください。

GPU とは何か
------------

レイテンシ重視とスループット重視
^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^

CPU と GPU は、どちらも命令を実行するプロセッサですが、最適化している目標が異なります。

CPU は、1 つのスレッドをできるだけ早く終わらせること、つまり\ **レイテンシ**\ （latency）を短くすることを重視しています。「:doc:`10_pipeline`」から「:doc:`12_memory_hierarchy`」で見た、分岐予測、アウトオブオーダー実行、投機実行、大きなキャッシュは、すべて 1 つの命令の流れの待ち時間を減らすための仕組みです。プログラムの多くは逐次的な部分を含み、ユーザーは応答の速さを求めるので、これは合理的な選択です。

GPU は、一定時間内に処理できる仕事の総量、つまり\ **スループット**\ （throughput）を重視しています。画面のピクセルや行列の要素のように、独立した仕事が数百万個ある場合、1 つ 1 つの仕事が終わるまでの時間はそれほど重要ではありません。重要なのは、全体がどれだけ早く終わるかです。そこで GPU は、1 つのスレッドを速くする仕組みを省き、その分のトランジスタと電力を演算器の数に回しています。メモリの遅さは、キャッシュで隠すのではなく、多数のスレッドを切り替えて実行することで隠します（後の節で説明します）。

この違いを、乗り物にたとえて説明することがあります。CPU は少人数を高速に運ぶスポーツカー、GPU は大勢をまとめて運ぶバスの列です。1 人を目的地に運ぶならスポーツカーが早く着きますが、1 万人を運ぶならバスの列のほうが早く運び終わります。

トランジスタの使い方の比較
^^^^^^^^^^^^^^^^^^^^^^^^^^

設計思想の違いは、チップの面積（トランジスタ）の使い方に表れます。

.. list-table:: CPU と GPU の設計の比較（典型的な傾向）
   :header-rows: 1
   :widths: 24 38 38

   * - 項目
     - CPU（レイテンシ重視）
     - GPU（スループット重視）
   * - コアの数
     - 数個〜百数十個の複雑なコア
     - 数十〜百数十個の SM に、合計で数千〜1 万数千個の単純な演算器
   * - 1 コアの制御
     - 分岐予測、アウトオブオーダー実行、投機実行など大規模
     - 基本的にインオーダー実行で、制御は単純。1 つの命令をワープの 32 スレッドで共有します。
   * - キャッシュ
     - コアあたり数 MB と大きく、レイテンシを隠す主役
     - 演算器あたりでは小さいです。帯域を補うのが主な役割。
   * - 同時に保持するスレッド
     - 1 コアあたり 1〜2 個（SMT）
     - 1 SM あたり最大 2048 個程度
   * - レジスタ
     - 1 コアあたり数百個の物理レジスタ
     - 1 SM あたり 256 KB 程度の巨大なレジスタファイル
   * - メモリ帯域の目安
     - 数十〜数百 GB/s（DDR）
     - 約 1〜8 TB/s（GDDR、HBM）
   * - 得意な処理
     - 分岐が多く逐次的な処理、低レイテンシの応答
     - 大量のデータに同じ処理を行う、データ並列な処理

CPU のコアは、命令 1 個あたりに大きな制御回路を使います。たとえば、アウトオブオーダー実行のための命令ウィンドウやリネーム、分岐予測器は、実際の演算器よりも大きな面積と電力を使います。GPU では、1 つの命令の取り出しとデコードの結果を 32 個のスレッドで共有するので、制御のコストが 32 分の 1 になり、その分を演算器に回せます。

GPU の歴史
----------

固定機能のグラフィックスアクセラレーター
^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^

1990 年代には、パソコン向けに 3 次元グラフィックスを高速化する\ **グラフィックスアクセラレーター**\ が登場しました。3dfx の Voodoo Graphics（1996 年）などが代表です。これらは、三角形をピクセルに分解し（ラスタライズ）、テクスチャ（画像）を貼り付ける処理を専用回路で行いました。処理の内容は回路で固定されており、決められた計算しかできない\ **固定機能**\ （fixed-function）のハードウェアでした。頂点の座標変換などの幾何計算は、まだ CPU が担当していました。

GeForce 256 と「GPU」という名前
^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^

1999 年に NVIDIA は GeForce 256 を発表し、これを「世界初の GPU」と宣伝しました。GeForce 256 は、頂点の座標変換と光源計算（Transform and Lighting：T&L）をハードウェアで行い、幾何計算まで CPU から引き受けました。「GPU」という言葉はこのときのマーケティングで広まり、グラフィックス用のプロセッサを指す一般的な名前になりました。ただし、この時点でも処理の内容は固定機能でした。

プログラマブルシェーダー
^^^^^^^^^^^^^^^^^^^^^^^^

2001 年ごろ、DirectX 8 に対応した GeForce 3 などで、頂点やピクセルの処理を短いプログラムで記述できる\ **プログラマブルシェーダー**\ （programmable shader）が登場しました。頂点を処理する\ **頂点シェーダー**\ と、ピクセルの色を計算する\ **ピクセルシェーダー**\ （フラグメントシェーダー）は、それぞれ専用の処理ユニットで実行されました。その後、シェーダーで使える命令数や浮動小数点数の精度が拡大し、GPU は「プログラムできる並列プロセッサ」へと変わっていきました。

この時期、研究者たちは、行列やベクトルのデータをテクスチャとして GPU に与え、ピクセルシェーダーで計算させるという方法で、グラフィックス以外の計算に GPU を使い始めました。これを **GPGPU**\ （General-Purpose computing on GPUs）と呼びます。ただし、計算をグラフィックスの言葉に置き換える必要があり、プログラミングは困難でした。

統合シェーダーアーキテクチャ
^^^^^^^^^^^^^^^^^^^^^^^^^^^^

頂点シェーダーとピクセルシェーダーを別々のユニットで実行すると、描く画面によってどちらかのユニットが遊んでしまいます。そこで、同じ汎用の処理ユニットが、頂点の処理もピクセルの処理も実行する\ **統合シェーダーアーキテクチャ**\ （unified shader architecture）が生まれました。2005 年の Xbox 360 の GPU（ATI 製）に続いて、パソコン向けでは 2006 年に NVIDIA が GeForce 8800（G80）を発表しました。G80 は 128 個のスカラーの処理ユニット（ストリーミングプロセッサ）を持ち、これを 8 個ずつまとめてストリーミングマルチプロセッサ（SM）を構成していました。この構成は、現在の NVIDIA の GPU の基本形になっています。

CUDA と GPGPU
^^^^^^^^^^^^^

統合シェーダーによって GPU の処理ユニットが汎用になったことで、グラフィックスを経由せずに直接プログラムする道が開けました。NVIDIA は 2007 年に、C 言語を拡張した言語で GPU をプログラムできる環境 **CUDA**\ （Compute Unified Device Architecture）を公開しました。CUDA では、数千のスレッドが同じ関数（カーネル）を実行するという単純なモデルで、行列計算やシミュレーションを書けます。これにより GPGPU は一部の研究者の技法から、広く使われる計算手段になりました。2008 年には、ベンダーに依存しない標準として OpenCL の仕様が公開されています。

2010 年の Fermi アーキテクチャでは、倍精度浮動小数点数の性能の強化、L1 と L2 のキャッシュ階層、メモリの誤り訂正（ECC）など、科学技術計算に必要な機能が加わりました。

科学技術計算とスーパーコンピューター
^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^

演算性能あたりの消費電力と価格が小さいことから、GPU はスーパーコンピューターにも採用されました。2010 年 11 月のスーパーコンピューターの性能ランキング TOP500 で 1 位になった中国の天河一号 A は、NVIDIA の GPU を搭載していました。その後も、米国オークリッジ国立研究所の Titan（2012 年）、Summit（2018 年）が NVIDIA の GPU を使い、2022 年に初めて 1 エクサ FLOPS を超えたと認定された Frontier は AMD の GPU を使っています。現在の TOP500 の上位の多くは GPU を搭載したシステムです。

深層学習
^^^^^^^^

GPU の役割を決定的に変えたのが深層学習です。2012 年、トロント大学の Alex Krizhevsky、Ilya Sutskever、Geoffrey Hinton の **AlexNet** は、画像認識のコンテスト ILSVRC で従来の手法を大きく上回る精度を達成しました。AlexNet は、2 枚の NVIDIA GeForce GTX 580 を使って学習されました。ニューラルネットワークの学習と推論は、大部分が行列積であり、GPU が最も得意とする計算です。これ以降、深層学習の研究と GPU の発展は互いを加速し合うことになりました。

Tensor コアと大規模言語モデル
^^^^^^^^^^^^^^^^^^^^^^^^^^^^^

2017 年の Volta アーキテクチャ（V100）で、NVIDIA は小さな行列の積和演算を 1 命令で行う専用の演算器 **Tensor コア**\ を導入しました。Tensor コアは FP16 などの低い精度の演算を前提とし、通常の演算器より桁違いに高い行列演算性能を実現します。その後の世代では、BF16、TF32、FP8 などの形式への対応や、疎な行列への対応が追加されていきました。

同じ 2017 年には、現在の大規模言語モデルの基礎となる Transformer が発表されています。2020 年代に入ると、数千〜数万個の GPU を高速なネットワークでつないで、巨大なモデルを数か月かけて学習することが行われるようになりました。GPU はもはや「グラフィックス用のチップ」ではなく、AI のための計算基盤の中心になっています。一方で、GPU は今でもグラフィックスの処理も担っており、リアルタイムのレイトレーシングを行う専用ユニット（RT コア）や、AI を使った画像の高解像度化も取り入れています。

グラフィックスパイプライン
--------------------------

GPU がなぜ大量並列の構成になったのかは、3 次元グラフィックスの処理の流れ（\ **グラフィックスパイプライン**\ ）を見ると理解できます。

.. graphviz::
   :caption: グラフィックスパイプラインの概略
   :align: center

   digraph gfx {
     rankdir=LR;
     node [shape=box, style=rounded, fontsize=11];
     v [label="頂点データ"];
     vs [label="頂点処理\n（頂点シェーダー）", style="rounded,filled", fillcolor="#e8f0fe"];
     pa [label="プリミティブ\n組み立て"];
     ra [label="ラスタライズ"];
     fs [label="フラグメント処理\n（フラグメント\nシェーダー）", style="rounded,filled", fillcolor="#e8f0fe"];
     om [label="深度テスト・\n合成"];
     fb [label="フレーム\nバッファ"];
     v -> vs -> pa -> ra -> fs -> om -> fb;
   }

1. **頂点処理**\ ：3 次元の物体は、三角形の集まり（ポリゴン）で表されます。頂点処理では、各頂点の座標に 4×4 の行列を掛けて、物体の座標系から画面の座標系に変換し、光の当たり方などを計算します。
2. **ラスタライズ**\ ：画面上の三角形が、どのピクセルを覆うかを求め、ピクセルごとの断片（フラグメント）を生成します。頂点の属性（色やテクスチャ座標）は三角形の内部で補間されます。
3. **フラグメント処理**\ ：フラグメントごとに、テクスチャを読み出し、光の計算を行って色を決めます。最後に、奥行き（深度）を比較して手前のものだけを残し、半透明の合成をしてフレームバッファに書き込みます。

この処理には、大量並列に向いた次の性質があります。

* 仕事の数が非常に多いことです。1920×1080 の画面は約 207 万ピクセル、3840×2160（4K）なら約 830 万ピクセルあり、毎秒 60 フレーム描くなら、4K では毎秒約 5 億個のフラグメントを処理します。1 個あたり数百命令を実行すれば、毎秒 :math:`10^{11}` 命令を超えます。
* 仕事が互いに独立していることです。ある頂点の変換や、あるピクセルの色の計算は、ほかの頂点やピクセルの結果を必要としません。
* すべての仕事に同じプログラム（シェーダー）を適用することです。命令の取り出しと解読を多数のデータで共有できます。
* 個々の仕事のレイテンシは問題にならないことです。1 フレーム（60 fps なら約 16.7 ms）の中ですべてが終わればよく、1 つのピクセルが遅れてもかまいません。

つまり、グラフィックスは典型的なデータ並列でスループット重視の処理です。GPU のアーキテクチャはこの性質に合わせて発展し、同じ性質を持つ行列計算や深層学習にも適していたのです。

GPU の構成
----------

ここでは NVIDIA の GPU を例に、ハードウェアの構成を説明します。AMD や Intel の GPU も、名前は異なりますが基本的な考え方は同じです。

全体の構成
^^^^^^^^^^

GPU のチップは、多数の\ **ストリーミングマルチプロセッサ**\ （Streaming Multiprocessor：SM）と、すべての SM が共有する L2 キャッシュ、メモリコントローラ、ホスト（CPU）とのインターフェースからなります。SM は、CPU のコアに相当する単位です。SM はいくつかずつまとめられて GPC（Graphics Processing Cluster）を構成します。ホストから起動された仕事は、ブロック単位で SM に割り振られます。

ストリーミングマルチプロセッサ（SM）
^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^

Volta 以降の SM は、4 つの\ **処理ブロック**\ （processing block、サブパーティション）に分かれています。各処理ブロックは、ワープスケジューラ、レジスタファイル、演算器を持ち、1 サイクルに 1 つのワープの命令を発行できます。SM 全体では、L1 キャッシュと共有メモリ（後述）を共有します。

.. graphviz::
   :caption: SM の内部構成（Volta 以降の NVIDIA の GPU を簡略化）
   :align: center

     subgraph cluster_sm {

       subgraph cluster_pb {
         label="処理ブロック（SM に 4 個）"; style=dashed;

主な要素は次のとおりです。

* **CUDA コア**\ ：NVIDIA が FP32 や INT32 の演算器の 1 レーンを指して使う名前です。CPU の「コア」とは異なり、独自の命令の取り出しやデコードの機能は持たず、ワープの 1 スレッド分の演算を担当する演算器です。製品の「CUDA コア数」は、SM 数と SM あたりの FP32 演算器の数の積です。
* **Tensor コア**\ ：小さな行列の積和演算 :math:`D = A \times B + C` を行う専用の演算器です（後の節で説明します）。
* **SFU**\ （Special Function Unit）：sin、cos、逆数、平方根などを近似計算する演算器です。
* **ロード／ストアユニット**\ ：メモリアクセスのアドレスを計算し、L1 キャッシュや共有メモリにアクセスします。
* **ワープスケジューラ**\ ：実行可能なワープの中から、毎サイクル 1 つを選んで命令を発行します。

非常に大きなレジスタファイル
^^^^^^^^^^^^^^^^^^^^^^^^^^^^

GPU の大きな特徴の 1 つが、巨大な\ **レジスタファイル**\ です。Volta、Ampere、Hopper の SM は、32 ビットのレジスタを 65,536 個（256 KB）持ちます。1 スレッドは最大 255 個のレジスタを使えます。H100 の 132 個の SM の合計では約 33 MB になり、L2 キャッシュ（約 50 MB）に匹敵する容量がレジスタに使われています。CPU のコアの物理レジスタファイルが数 KB〜数十 KB 程度であるのと比べると、桁違いの大きさです。

なぜこれほど大きなレジスタファイルが必要なのでしょうか。GPU は、メモリのレイテンシを隠すために、多数のスレッドを SM 上に同時に置いておき、待たされたスレッドの代わりに別のスレッドを実行します（後の節で説明します）。スレッドを切り替えるたびにレジスタの内容を退避・復元していたら間に合わないので、SM 上のすべてのスレッドのレジスタを同時にレジスタファイルに保持しています。このおかげで、GPU のスレッドの切り替えには時間がかかりません。

実行モデル
----------

スレッド・ブロック・グリッドの階層
^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^

CUDA では、GPU で実行する関数を\ **カーネル**\ （kernel）と呼びます。カーネルを起動すると、多数の\ **スレッド**\ （thread）が同じカーネルを実行します。スレッドは次のように階層的にまとめられます。

* **スレッドブロック**\ （thread block、単にブロック）：最大 1024 個のスレッドの集まりです。1 つのブロックは 1 つの SM で実行され、ブロック内のスレッドは共有メモリを使ってデータを交換し、バリア同期（\ ``__syncthreads()``\ ）で足並みを揃えられます。
* **グリッド**\ （grid）：1 回のカーネル起動で生成されるブロックの集まりです。ブロックは互いに独立で、どの順序で、どの SM で実行されてもよいことになっています。

各スレッドは、組み込み変数 ``threadIdx``\ （ブロック内の番号）、``blockIdx``\ （ブロックの番号）、``blockDim``\ （ブロックの大きさ）を使って、自分が担当するデータを決めます。これらは 3 次元まで指定でき、画像や行列を自然に分割できます。

SIMT とワープ
^^^^^^^^^^^^^

ハードウェアの中では、ブロック内のスレッドは連続する 32 個ずつの\ **ワープ**\ （warp）にまとめられて実行されます。ワープの 32 スレッドは、同じ命令を同時に（それぞれ自分のレジスタとデータに対して）実行します。命令の取り出しと発行はワープ単位で 1 回だけ行われます。このように、プログラマーには独立したスレッドとして見せながら、ハードウェアでは複数のスレッドに同じ命令を実行させる方式を、NVIDIA は **SIMT**\ （Single Instruction, Multiple Threads）と呼んでいます。「ワープ」という名前は、機織りの縦糸（warp）に由来します。

ワープの大きさは、NVIDIA の GPU では一貫して 32 スレッドです。AMD の GPU では同じ単位を\ **ウェーブフロント**\ （wavefront）と呼び、GCN アーキテクチャやデータセンター向けの CDNA アーキテクチャでは 64 スレッド、グラフィックス向けの RDNA アーキテクチャでは 32 スレッド（64 スレッドのモードも持つ）です。ワープの大きさはハードウェアの実装に依存するので、移植性の高いプログラムでは、決め打ちせずに問い合わせて使います。

ブロックの大きさは、ワープの大きさの倍数（たとえば 128 や 256）にするのが普通です。ブロックが 100 スレッドだと、4 つ目のワープは 4 スレッドしか持たず、残りの 28 レーンは何もしないまま命令の発行枠を使ってしまうからです。

SIMD と SIMT の違い
^^^^^^^^^^^^^^^^^^^

SIMT のハードウェアは、物理的には「:doc:`15_parallel`」で説明した SIMD とよく似ています。1 つの命令で 32 レーン分の演算を行うので、32 要素の SIMD ユニットと見ることもできます（実装によっては、16 レーンの演算器で 2 サイクルかけて 1 ワープ分を処理します）。違いは、主にプログラミングモデルと、それを支えるハードウェアの機能にあります。

.. list-table:: SIMD 命令と SIMT の比較
   :header-rows: 1
   :widths: 22 39 39

   * - 観点
     - SIMD 命令（AVX、NEON など）
     - SIMT（GPU）
   * - プログラムの書き方
     - 1 つのスレッドが幅の広いベクトルレジスタを操作します。プログラマーかコンパイラがベクトル化します。
     - 1 つのスレッドの処理をスカラーのコードとして書きます。ハードウェアがスレッドをワープにまとめます。
   * - 幅
     - 命令に現れます（128、256、512 ビットなど）。SVE や RVV では実装が選びます。
     - プログラムには現れません（実際にはワープの大きさを意識した最適化が多いです）。
   * - 分岐
     - マスク付き命令や選択（blend）命令で、プログラマーかコンパイラが明示的に処理します。
     - スレッドごとに普通に if 文を書けます。ハードウェアがアクティブマスクを管理します。
   * - メモリアクセス
     - 連続するアドレスのロード・ストアが基本。ばらばらのアドレスには gather／scatter 命令を使います。
     - 各スレッドが任意のアドレスにアクセスできます。ハードウェアがまとめて（合体して）処理します。
   * - レイテンシの隠し方
     - アウトオブオーダー実行とキャッシュ
     - 多数のワープの切り替え
   * - スレッドの状態
     - ベクトルの各要素は独立したスレッドではありません。
     - 各スレッドが自分のレジスタと（論理的には）自分のプログラムカウンタを持ちます。

まとめると、SIMT は「SIMD のハードウェアに、スレッドとして書けるプログラミングモデルを組み合わせたもの」といえます。SIMD 命令でも AVX-512 のマスクレジスタや SVE の述語レジスタによって分岐を扱いやすくなっており、逆に、SPMD 形式のプログラムを SIMD 命令に変換するコンパイラ（Intel の ISPC など）もあります。両者は同じ考え方の、異なる見せ方だといえます。

レイテンシの隠蔽
----------------

多数のワープを切り替える
^^^^^^^^^^^^^^^^^^^^^^^^

GPU のデバイスメモリへのアクセスには、数百サイクルのレイテンシがかかります（目安として 400〜800 サイクル程度）。CPU は大きなキャッシュとアウトオブオーダー実行でこれを隠しますが、GPU は別の方法を使います。

SM には、同時に多数のワープが割り当てられています（V100、A100、H100 では SM あたり最大 64 ワープ、2048 スレッド。ゲーム向けの製品ではこれより少ないものもあります）。ワープスケジューラは毎サイクル、オペランドが揃って実行できる状態のワープを 1 つ選んで命令を発行します。あるワープがメモリの読み出しを待っている間は、別のワープの命令を発行します。前の節で述べたとおり、すべてのワープのレジスタがレジスタファイルにあるので、ワープの切り替えにはコストがかかりません。十分な数のワープがあれば、演算器は休まずに働き続け、メモリのレイテンシはほかのワープの実行の陰に隠れます。これを\ **レイテンシの隠蔽**\ （latency hiding）と呼びます。

これは、複数のスレッドの状態をハードウェアに保持しておき、命令を発行するスレッドをサイクルごとに切り替えるハードウェアマルチスレッディングを、大規模にしたものと考えられます。「:doc:`11_ilp`」で説明した CPU の同時マルチスレッディング（SMT）も同じ考え方ですが、SMT が 1 コアあたり 2 スレッド程度なのに対し、GPU は 1 つの処理ブロックあたり最大 16 ワープ（512 スレッド）を切り替えます。

必要な並列度の見積もり
^^^^^^^^^^^^^^^^^^^^^^

どれだけのワープがあればレイテンシを隠せるかは、\ **リトルの法則**\ （Little's law）で見積もれます。

.. math::

   \text{同時に処理中の量} = \text{レイテンシ} \times \text{スループット}

たとえば、メモリ帯域が 3 TB/s、メモリアクセスのレイテンシが約 500 ns の GPU では、帯域を使い切るために、常に :math:`3 \times 10^{12} \times 500 \times 10^{-9} = 1.5 \times 10^{6}` バイト、つまり約 1.5 MB のデータを読み出し中にしておく必要があります。SM が 132 個なら、SM あたり約 11 KB です。1 つのワープが 1 回のロード命令で 128 バイト（32 スレッド×4 バイト）を読むとすれば、SM あたり約 90 個のロード命令が常に処理中でなければなりません。1 ワープが同時に複数のロードを発行できるとしても、数十のワープが必要なことが分かります。GPU が SM あたり数十のワープを保持する理由はここにあります。

占有率
^^^^^^

SM に同時に割り当てられているワープの数の、最大数に対する割合を\ **占有率**\ （オキュパンシー、occupancy）と呼びます。占有率は、SM の資源のうち最も厳しいものによって制限されます。

* レジスタ：SM のレジスタは 65,536 個です。1 スレッドが 32 個のレジスタを使うなら :math:`65536 / 32 = 2048` スレッド（64 ワープ）を置けて、占有率は 100% です。64 個使うと 1024 スレッド（32 ワープ）で 50%、128 個使うと 512 スレッド（16 ワープ）で 25% に下がります。
* 共有メモリ：ブロックが 48 KB の共有メモリを使い、SM の共有メモリが 100 KB 程度なら、SM に置けるブロックは 2 個までです。
* ブロック数とスレッド数の上限：SM に置けるブロック数（たとえば 32 個）とスレッド数（2048 個）にも上限があります。

占有率が低いと、レイテンシを隠すためのワープが足りなくなります。ただし、占有率は高いほどよいとは限りません。1 スレッドがより多くのレジスタを使って、データを再利用したり、独立した命令を多く並べたり（命令レベル並列性）すれば、少ないワープでもレイテンシを隠せることがあります。高性能な行列積のカーネルは、あえて占有率を下げて、レジスタを多く使う設計になっていることがよくあります。

分岐ダイバージェンス
--------------------

マスクによる実行
^^^^^^^^^^^^^^^^

ワープの 32 スレッドは同じ命令を実行します。では、スレッドごとに条件が異なる if 文はどう実行されるのでしょうか。

.. code-block:: cuda
   :linenos:

   if (x[i] > 0) {
       y[i] = sqrtf(x[i]);   /* then 側 */
   } else {
       y[i] = 0.0f;          /* else 側 */
   }

ワープ内のスレッドの条件の結果が分かれることを\ **分岐ダイバージェンス**\ （branch divergence、ワープダイバージェンス）と呼びます。このとき GPU は、ワープの各レーンが実行中かどうかを表す\ **アクティブマスク**\ （active mask）を使い、まず条件が真のスレッドだけを有効にして then 側を実行し、次に条件が偽のスレッドだけを有効にして else 側を実行します。無効なレーンは命令を受け取っても結果を書き込みません。両方の経路が終わると、ワープは再び 32 スレッド揃って実行を続けます（再収束）。

結果として、ダイバージェンスが起きると、ワープは then 側と else 側の\ **両方の**\ 命令の時間を使います。ワープのすべてのスレッドが同じ側に進めば、もう一方の経路は丸ごと飛ばせるので、ダイバージェンスは起きません。重要なのは、分岐の条件がスレッド全体でばらばらかどうかではなく、\ **1 つのワープの中で**\ 揃っているかどうかです。

性能への影響を確かめる
^^^^^^^^^^^^^^^^^^^^^^

サンプル :download:`gpu_simt_sim.py <../examples/gpu_simt_sim.py>` は、ワープが if 文を含むカーネルを実行するときのサイクル数を、マスク付き実行のモデルで数えます。分岐の前後に 10 命令ずつの共通部分があり、then 側と else 側がそれぞれ 20 命令であるとし、4 ワープ（128 スレッド）分の合計を比べます。

.. literalinclude:: ../examples/gpu_simt_sim.py
   :language: python
   :linenos:
   :caption: gpu_simt_sim.py

要点は次のとおりです。

* 30〜35 行目：ワープの各レーン（スレッド）について条件を評価し、条件が真のレーンのビットを立てたアクティブマスクを作ります。
* 38〜43 行目：実行する区間の列を作ります。マスクが 0 でなければ then 側を、すべてのビットが立っていなければ else 側を、それぞれのマスクで実行します。どちらかのマスクが空なら、その経路は飛ばします。
* 46〜50 行目：各区間の命令数をサイクル数に加え、有効なレーン数×サイクル数を数えて、レーンの利用率を求めます。
* 56〜59 行目：比べる 4 つの条件です。「ワープ単位」の条件はワープ番号だけで決まるので、ワープ内では全員が同じ側に進みます。

実行結果は次のとおりです。

.. code-block:: text
   :linenos:

   ワープ 0 の実行の様子（偶奇で分岐する場合）
     マスク 0xFFFFFFFF  10 サイクル  共通
     マスク 0x55555555  20 サイクル  then
     マスク 0xAAAAAAAA  20 サイクル  else
     マスク 0xFFFFFFFF  10 サイクル  共通

   4 ワープ（128 スレッド）の合計
      160 サイクル  レーン利用率 100.0%  分岐なし（全員 then）
      240 サイクル  レーン利用率  66.7%  半分ずつ（レーン < 16）
      240 サイクル  レーン利用率  66.7%  偶奇（tid % 2 == 0）
      160 サイクル  レーン利用率 100.0%  ワープ単位（warp % 2 == 0）

偶奇で分岐する場合、ワープ 0 では偶数番のレーン（マスク ``0x55555555``\ ）が then 側を、奇数番のレーン（``0xAAAAAAAA``\ ）が else 側を実行し、それぞれの区間では半分のレーンが遊んでいます。ワープあたり :math:`10 + 20 + 20 + 10 = 60` サイクルかかり、分岐しない場合の 40 サイクルの 1.5 倍です。

注目すべきは、「半分ずつ」と「ワープ単位」の違いです。どちらもスレッド全体のちょうど半分が then 側に進みますが、レーン番号 16 未満で分けるとすべてのワープの中でダイバージェンスが起きるのに対し、ワープ番号で分けるとワープ内の条件が揃うので、分岐しない場合と同じ 160 サイクルで済みます。条件の判定がスレッド番号に依存する場合は、ワープ単位で揃うようにデータや仕事の割り当てを工夫すると、ダイバージェンスを避けられます。

then 側と else 側の命令数が少ない場合は、コンパイラが分岐を使わずに両方を計算して結果を選ぶ命令（述語付き実行、選択命令）に変換することもあります。また、ループの繰り返し回数がスレッドごとに異なる場合も、最も長いスレッドが終わるまでワープ全体が付き合うことになり、同じ問題が起きます。

独立スレッドスケジューリング
^^^^^^^^^^^^^^^^^^^^^^^^^^^^

従来の GPU は、分岐した経路の一方を最後まで実行してから他方に移るため、ワープ内のスレッド同士がロックなどで互いを待つと、デッドロックすることがありました。Volta 以降の NVIDIA の GPU は、スレッドごとにプログラムカウンタと呼び出しスタックを持つ\ **独立スレッドスケジューリング**\ （independent thread scheduling）を採用し、分岐した経路を交互に進められるようになりました。これにより、ワープ内のスレッド間で同期するアルゴリズムも正しく動きます。ただし、異なる経路を同時に実行するわけではないので、ダイバージェンスによる性能の低下はなくなりません。

メモリ階層
----------

GPU のメモリ階層を、性能の目安とともにまとめます。数値は世代や製品によって大きく異なるので、桁の感覚をつかむための\ **目安**\ です。

.. list-table:: GPU のメモリ階層（数値はすべて目安）
   :header-rows: 1
   :widths: 18 18 22 18 24

   * - 階層
     - 共有する範囲
     - 容量の目安
     - レイテンシの目安
     - 帯域の目安
   * - レジスタ
     - スレッド
     - SM あたり 256 KB
     - 数サイクル
     - 演算器に直結
   * - 共有メモリ／L1
     - ブロック／SM
     - SM あたり 128〜256 KB 程度（共用）
     - 約 20〜30 サイクル
     - SM あたり 128 バイト／サイクル
   * - L2 キャッシュ
     - GPU 全体
     - 数 MB〜数十 MB
     - 約 200 サイクル
     - 数 TB/s〜10 TB/s 程度
   * - グローバルメモリ（HBM、GDDR）
     - GPU 全体とホスト
     - 数 GB〜百数十 GB
     - 約 400〜800 サイクル
     - 約 1〜8 TB/s
   * - ホストの主記憶（PCIe 経由）
     - CPU と GPU
     - 数十 GB〜数 TB
     - 数 µs
     - 約 32〜64 GB/s（片方向）

各階層の役割は次のとおりです。

* **レジスタ**\ ：各スレッドの局所変数が置かれます。最も高速ですが、使いすぎると占有率が下がります。足りない分はローカルメモリ（実体はグローバルメモリ）にあふれ（スピル）、遅くなります。
* **共有メモリ**\ （shared memory）：ブロック内のスレッドが共有する、プログラムで明示的に管理する SRAM です。CPU のキャッシュとは違い、何をいつ置くかをプログラマーが決める「手動のキャッシュ」であり、\ **スクラッチパッドメモリ**\ （scratchpad memory）とも呼ばれます。L1 キャッシュと同じ SRAM を共用しており、その割合を設定できます。
* **L1 キャッシュ**\ ：SM ごとのキャッシュです。グローバルメモリのアクセスを、128 バイトのキャッシュラインと 32 バイトの\ **セクタ**\ （sector）の単位で扱います。
* **L2 キャッシュ**\ ：全 SM が共有するキャッシュで、すべてのグローバルメモリのアクセスが通ります。SM の間のデータの一貫性は、L2 で保たれます。GPU の L1 は CPU のようなハードウェアのコヒーレンスを持たないことが多く、ブロックをまたいだデータの受け渡しには、アトミック操作やメモリフェンス、カーネルの終了を使います。
* **グローバルメモリ**\ （global memory）：GPU のボードやパッケージ上の DRAM で、すべてのスレッドとホストからアクセスできます。

HBM と GDDR
^^^^^^^^^^^

GPU は膨大な数の演算器にデータを供給するため、CPU の DDR メモリよりはるかに広い帯域のメモリを使います。

* **GDDR**\ （Graphics DDR）：グラフィックス向けに高いクロックで動かす DRAM です。チップ 1 個のデータ幅は 32 ビット程度で、GPU の周りの基板上に多数のチップを並べ、上位の製品では合計で 256〜512 ビット程度のバス幅にします。GDDR6、GDDR6X、GDDR7 などの世代があり、ゲーム向けの GPU で使われます。ハイエンドのゲーム向け GPU で約 1〜2 TB/s の帯域が得られます。
* **HBM**\ （High Bandwidth Memory）：複数の DRAM のダイを積み重ねて GPU と同じパッケージに収め、1 つの積層あたり 1024 ビット以上という非常に広いデータ幅で接続するメモリです。配線が短く本数が多いので、低いクロックでも広い帯域が得られ、ビットあたりの電力も小さくなります。データセンター向けの GPU では、数個の HBM の積層を並べて約 2〜8 TB/s の帯域を実現しています。製造が難しく高価で、容量も GDDR より増やしにくいという欠点があります。積層と実装の構造は「:doc:`17_accelerators`」で説明します。

メモリアクセスの合体とバンクコンフリクト
----------------------------------------

GPU の性能は、メモリをどれだけ効率よく使えるかに大きく依存します。ここでは、グローバルメモリと共有メモリのそれぞれで、ワープの 32 スレッドのアクセスのしかたが性能にどう影響するかを説明します。

メモリアクセスの合体（コアレッシング）
^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^

ワープの 32 スレッドがロード命令を実行すると、ハードウェアは 32 個のアドレスを調べ、同じセクタ（またはキャッシュライン）に入るものをまとめて、できるだけ少ない数のメモリトランザクションにします。これを\ **メモリアクセスの合体**\ （memory coalescing、コアレッシング）と呼びます。

たとえば、スレッド ``i`` が ``a[i]``\ （4 バイトの ``float``\ ）を読むと、32 スレッドのアクセスは連続する 128 バイトに収まり、32 バイトのセクタ 4 個で済みます。一方、スレッド ``i`` が ``a[32*i]`` を読むと、アドレスは 128 バイトずつ離れるので、32 個のセクタが必要になります。転送するのは 1024 バイトなのに、使うのは 128 バイトだけで、帯域の 8 分の 7 が無駄になります。

このため GPU では、2 次元の配列を処理するとき、連続するスレッドが連続するアドレス（行優先の配列なら同じ行の隣り合う列）にアクセスするように仕事を割り当てます。構造体の配列（Array of Structures：AoS）より、要素ごとの配列を持つ構造体（Structure of Arrays：SoA）が好まれるのも同じ理由です。AoS では、各スレッドが構造体の同じメンバを読むと、アクセスが構造体の大きさのストライドになってしまいます。

共有メモリのバンクコンフリクト
^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^

共有メモリは、同時に多数のアクセスを処理できるように、32 個の\ **バンク**\ （bank）に分けられています。各バンクの幅は 4 バイトで、連続する 4 バイトのワードが順に別のバンクに割り当てられます。つまり、ワード番号を 32 で割った余りがバンクの番号です。ワープの 32 スレッドが異なる 32 個のバンクにアクセスすれば、1 サイクル（1 回の処理）ですべてのアクセスが終わります。

同じバンクの\ **異なる**\ ワードに複数のスレッドがアクセスすると、そのアクセスは順番に処理されます。これを\ **バンクコンフリクト**\ （bank conflict）と呼びます。:math:`k` 個のスレッドが同じバンクの異なるワードにアクセスすると、処理に :math:`k` 回かかります（:math:`k`-way のバンクコンフリクト）。ただし、複数のスレッドが同じワードを読む場合は、1 回の読み出しで全員に配られる（ブロードキャスト）ので、コンフリクトになりません。

典型的な問題は、32×32 の ``float`` の 2 次元配列 ``tile[32][32]`` を列方向に読む場合です。スレッド ``i`` が ``tile[i][0]`` を読むと、ワード番号は ``32*i`` で、すべて 32 の倍数なので全員がバンク 0 にアクセスし、32-way のコンフリクトになります。配列を ``tile[32][33]`` のように 1 列余分に確保すると、ワード番号が ``33*i`` になり、バンク番号が ``i`` ずつずれるので、コンフリクトがなくなります。行列の転置などでよく使われる、このパディングの技法は、「:doc:`15_parallel`」の false sharing の対策と似た発想です。

* 23〜30 行目：各スレッドが読む 4 バイトの先頭と末尾のアドレスを 32 で割り、触れたセクタの番号を集合に入れて数えます。要素がセクタの境界をまたぐ場合も考慮しています。

グローバルメモリでは、連続アクセスなら効率は 100% です。先頭が 4 バイトずれただけでも、128 バイトが 5 個のセクタにまたがり、効率は 80% に下がります。ストライドが 2、4 と倍になるごとに効率は半分になり、ストライドが 8 要素（32 バイト）以上になると、各スレッドが別々のセクタを使うので効率は 12.5% で底を打ちます。ランダムなアクセスも同じで、必要な 8 倍のデータを転送することになります。メモリ帯域で性能が決まるカーネルでは、これはそのまま 8 倍の速度の差になります。

共有メモリでは、``s[2*tid]`` のように 2 ワードおきにアクセスすると、スレッド 0 と 16 がバンク 0 を、スレッド 1 と 17 がバンク 2 を使うというように 2 スレッドずつが同じバンクに当たり、2-way のコンフリクトになります。全員が同じワードを読む場合はブロードキャストなのでコンフリクトはありません。32 列の配列の列方向のアクセスは 32-way のコンフリクトで 32 倍の時間がかかりますが、1 列のパディングで解消されます。

プログラミングモデル
--------------------

ホストとデバイス
^^^^^^^^^^^^^^^^

CUDA のプログラムでは、CPU とその主記憶を\ **ホスト**\ （host）、GPU とそのメモリを\ **デバイス**\ （device）と呼びます。典型的な処理の流れは次のとおりです。

1. ホストの主記憶に入力データを用意します。
2. デバイスのメモリを確保し、入力データをホストからデバイスに転送します。
3. カーネルを起動し、GPU で計算します。
4. 結果をデバイスからホストに転送します。
5. デバイスのメモリを解放します。

ホストとデバイスは、通常は別々のメモリを持ち、PCIe などのバスでつながっているので、2 と 4 の転送には無視できない時間がかかります。これについては後の節で見積もります。

ベクトル加算の例
^^^^^^^^^^^^^^^^

2 つのベクトルの和を計算する CUDA のプログラムを示します。CUDA C++ は C++ を拡張した言語です。エラー処理は省略しています。

.. code-block:: cuda
   :linenos:

   #include <cstdio>
   #include <cstdlib>
   #include <cuda_runtime.h>

   // カーネル：GPU の各スレッドが 1 要素を担当する
   __global__ void vec_add(const float *a, const float *b, float *c, int n)
   {
       int i = blockIdx.x * blockDim.x + threadIdx.x;  // 全体での通し番号
       if (i < n) {                                    // 範囲外のスレッドは何もしない
           c[i] = a[i] + b[i];
       }
   }

   int main()
   {
       const int n = 1 << 20;                  // 約 100 万要素
       const size_t bytes = n * sizeof(float);

       // 1. ホストのメモリを確保して初期化する
       float *h_a = (float *)malloc(bytes);
       float *h_b = (float *)malloc(bytes);
       float *h_c = (float *)malloc(bytes);
       for (int i = 0; i < n; i++) {
           h_a[i] = 1.0f * i;
           h_b[i] = 2.0f * i;
       }

       // 2. デバイスのメモリを確保し、入力を転送する
       float *d_a, *d_b, *d_c;
       cudaMalloc(&d_a, bytes);
       cudaMalloc(&d_b, bytes);
       cudaMalloc(&d_c, bytes);
       cudaMemcpy(d_a, h_a, bytes, cudaMemcpyHostToDevice);
       cudaMemcpy(d_b, h_b, bytes, cudaMemcpyHostToDevice);

       // 3. カーネルを起動する（256 スレッドのブロックを必要な数だけ）
       int threads = 256;
       int blocks = (n + threads - 1) / threads;
       vec_add<<<blocks, threads>>>(d_a, d_b, d_c, n);

       // 4. 結果をホストに転送する（カーネルの終了を待ってから転送される）
       cudaMemcpy(h_c, d_c, bytes, cudaMemcpyDeviceToHost);
       printf("c[100] = %f\n", h_c[100]);      // 300.000000 と表示される

       // 5. メモリを解放する
       cudaFree(d_a); cudaFree(d_b); cudaFree(d_c);
       free(h_a); free(h_b); free(h_c);
       return 0;
   }

要点は次のとおりです。

* 6 行目：``__global__`` は、ホストから起動されてデバイスで実行される関数（カーネル）であることを示します。
* 8 行目：各スレッドは、ブロックの番号、ブロックの大きさ、ブロック内の番号から、自分が担当する要素の番号 ``i`` を計算します。連続するスレッドが連続する要素を担当するので、メモリアクセスは合体されます。
* 9 行目：要素数がブロックの大きさの倍数でない場合、最後のブロックには担当する要素がないスレッドができるので、範囲を確認します。この if 文によるダイバージェンスは、最後のワープだけで起きるので問題になりません。
* 30〜34 行目：``cudaMalloc`` でデバイスのメモリを確保し、``cudaMemcpy`` でホストからデバイスに転送します。
* 37〜39 行目：``<<<ブロック数, ブロックあたりのスレッド数>>>`` という記法でカーネルを起動します。:math:`2^{20} / 256 = 4096` 個のブロック、合計約 100 万個のスレッドが生成されます。カーネルの起動は非同期で、ホストは完了を待たずに次に進みます。
* 42 行目：結果をデバイスからホストに転送します。この転送は、先に起動したカーネルの完了を待ってから行われます。

CPU のプログラムなら 1 つのループで書く処理を、「1 要素を処理する関数」として書き、それを要素の数だけのスレッドで実行するのが CUDA の考え方です。100 万個のスレッドは、ハードウェアの数千個の演算器よりはるかに多いですが、これでよいのです。ハードウェアはブロックを SM に順次割り振り、多数のワープを切り替えながら実行します。

メモリ転送の工夫
^^^^^^^^^^^^^^^^

ホストとデバイスの間の転送の効率を上げるために、次のような工夫が使われます。

* **ピン留めメモリ**\ （pinned memory、ページロックメモリ）：ホストのメモリをページアウトされないように固定すると、GPU の DMA コントローラが直接転送でき、転送が速くなります。通常のメモリからの転送では、いったんピン留めされた一時領域にコピーされます。
* **非同期転送とストリーム**\ ：データを分割し、ある部分の転送と別の部分の計算を同時に行うことで、転送時間を隠します。CUDA では、順序を持つ処理の列を\ **ストリーム**\ （stream）と呼び、複数のストリームを使って転送と計算を重ねます。
* **データを GPU に置いたままにする**\ ：複数のカーネルを続けて実行する場合、途中の結果をホストに戻さずにデバイスのメモリに置いたまま処理します。

行列積の高速化
--------------

行列積は、深層学習や科学技術計算の中心的な計算であり、GPU の性能を最も引き出せる処理です。:math:`n \times n` の行列 :math:`A`\ 、:math:`B` の積 :math:`C = AB` は、:math:`2n^3` 回の浮動小数点演算（乗算と加算）を必要とし、入出力のデータは :math:`3n^2` 要素です。データの量に対して計算の量が多いので、うまく実装すれば演算性能を使い切れます。

素朴な実装
^^^^^^^^^^

最も素朴な実装では、1 つのスレッドが :math:`C` の 1 要素を担当し、:math:`A` の 1 行と :math:`B` の 1 列の内積を計算します。内側のループの 1 回の繰り返しで、:math:`A` と :math:`B` から 1 要素ずつ（合計 8 バイト）を読み、乗算と加算の 2 回の演算をします。グローバルメモリの読み出し 1 バイトあたりの演算は :math:`2 / 8 = 0.25` 回にすぎません。同じ要素をほかのスレッドも何度も読むので、キャッシュに当たる分はありますが、メモリ帯域が性能を制限します。

タイリングと共有メモリ
^^^^^^^^^^^^^^^^^^^^^^

そこで、行列を小さな正方形の\ **タイル**\ （tile）に分け、ブロック内のスレッドが協力してタイルを共有メモリに読み込み、それを繰り返し使います。これを\ **タイリング**\ （tiling）と呼びます。

.. code-block:: cuda
   :linenos:

   #define TILE 32

   // C = A * B（n×n、行優先、n は TILE の倍数とする）
   // ブロックは TILE×TILE スレッドで、C の 1 つのタイルを計算する
   __global__ void matmul_tiled(const float *A, const float *B, float *C, int n)
   {
       __shared__ float As[TILE][TILE];   // A のタイル（共有メモリ）
       __shared__ float Bs[TILE][TILE];   // B のタイル（共有メモリ）
       int tx = threadIdx.x, ty = threadIdx.y;
       int row = blockIdx.y * TILE + ty;
       int col = blockIdx.x * TILE + tx;
       float sum = 0.0f;

       for (int t = 0; t < n / TILE; t++) {
           // ブロックの全スレッドで 1 要素ずつ読み込み、タイルを作る
           As[ty][tx] = A[row * n + t * TILE + tx];
           Bs[ty][tx] = B[(t * TILE + ty) * n + col];
           __syncthreads();               // タイルが揃うまで待つ

           for (int k = 0; k < TILE; k++) {
               sum += As[ty][k] * Bs[k][tx];
           }
           __syncthreads();               // 全員が使い終わるまで待つ
       }
       C[row * n + col] = sum;
   }

要点は次のとおりです。

* 7〜8 行目：``__shared__`` で宣言した配列は、ブロック内のスレッドが共有する共有メモリに置かれます。2 つのタイルで 8 KB です。
* 16〜17 行目：ブロックの 1024 スレッドが 1 要素ずつ読み込み、:math:`A` と :math:`B` のタイルを作ります。``tx`` が連続するスレッド（同じワープ）は連続するアドレスを読むので、グローバルメモリのアクセスは合体されます。
* 18 行目と 23 行目：``__syncthreads()`` はブロック内のすべてのスレッドが到達するまで待つバリア同期です。タイルが揃う前に計算を始めたり、使い終わる前に次のタイルで上書きしたりしないようにします。
* 20〜22 行目：共有メモリ上のタイルを使って部分和を計算します。``As[ty][k]`` はワープ内の全スレッドが同じワードを読む（同じワープは ``ty`` が同じ）のでブロードキャストになり、``Bs[k][tx]`` は連続するワードなので、どちらもバンクコンフリクトは起きません。

タイリングの効果を計算します。:math:`T \times T` のタイルを 1 組読み込むと、グローバルメモリから :math:`2T^2` 要素（:math:`8T^2` バイト）を読み、:math:`T^2` 個のスレッドがそれぞれ :math:`T` 回の積和、合計 :math:`2T^3` 回の演算をします。読み出し 1 バイトあたりの演算は :math:`2T^3 / 8T^2 = T/4` 回になり、:math:`T = 32` なら 8 回です。素朴な実装の 0.25 回の 32 倍で、グローバルメモリへのアクセスが 32 分の 1 に減ったことになります。実用的なライブラリ（NVIDIA の cuBLAS や CUTLASS など）では、さらに各スレッドが複数の要素をレジスタに保持して計算する\ **レジスタタイリング**\ 、次のタイルの読み込みと計算を重ねるダブルバッファリング、Tensor コアの利用などを組み合わせて、ピークに近い性能を得ています。

Tensor コア
^^^^^^^^^^^

**Tensor コア**\ は、小さな行列の積和演算 :math:`D = A \times B + C` を専用に行う演算器です。Volta の Tensor コアは、1 サイクルに :math:`4 \times 4` の FP16 の行列 :math:`A`\ 、:math:`B` の積を求め、FP16 または FP32 の :math:`C` に加えます。これは 64 回の積和演算に相当します。プログラムからは、ワープ全体で 1 つの命令を実行し、ワープの 32 スレッドのレジスタに分散して置かれた、たとえば :math:`16 \times 16` の行列の積和を計算するという形で使います。

通常の FP32 の演算器は、1 つの命令で 1 回の積和しか行いません。Tensor コアは、行列積の構造を利用して、オペランドを読み出す回数あたりの演算回数を増やし、レジスタファイルからのデータの供給やデコードのコストを多数の演算で分け合います。この結果、同じ面積と電力でずっと多くの演算ができます。たとえば A100 の約 19.5 TFLOPS の FP32 の演算性能に対し、Tensor コアの FP16 の行列演算性能は約 312 TFLOPS（疎行列の機能を使わない場合）と、約 16 倍です。これは「:doc:`17_accelerators`」で説明するドメイン特化型アーキテクチャの考え方を GPU の中に取り込んだものといえます。

低精度演算
^^^^^^^^^^

深層学習では、数値の精度を下げても学習や推論の結果がほとんど変わらないことが知られています。精度を下げると、乗算器の回路が小さくなり（乗算器の面積は仮数部のビット数のおよそ 2 乗に比例します）、同じメモリ帯域でより多くの数を運べます。そこで GPU は、さまざまな低精度の浮動小数点数の形式に対応してきました。浮動小数点数の形式については「:doc:`05_data_representation`」を参照してください。

   :widths: 16 12 12 12 48

   * - 形式
     - 符号
     - 指数部
     - 仮数部
     - 特徴
   * - FP32
     - 1
     - 8
     - 23
     - IEEE 754 の単精度。従来の標準。
   * - TF32
     - 1
     - 8

   * - FP16
     - 1
     - 5
     - 10
     - IEEE 754 の半精度。表せる範囲が狭く（最大約 65504）、学習では値の大きさを調整する工夫が必要です。

精度が半分になるごとに、Tensor コアの演算性能はおおむね 2 倍になります。Blackwell 世代（2024 年発表）では、さらに 4 ビットの浮動小数点数形式にも対応しています。また、推論では INT8 や INT4 などの整数形式も使われます。乗算は低精度で行い、積の累積はより高い精度（FP32 など）で行う\ **混合精度**\ （mixed precision）の演算が一般的です。

性能を考える
------------

ルーフラインモデル
^^^^^^^^^^^^^^^^^^

GPU のプログラムの性能を見積もるのに便利なのが\ **ルーフラインモデル**\ （roofline model）です。2009 年に Samuel Williams、Andrew Waterman、David Patterson が提案しました。このモデルでは、プログラムの性質を\ **演算強度**\ （arithmetic intensity：メモリから読み書きする 1 バイトあたりの演算回数、単位は FLOP/byte）で表し、到達可能な性能を次の式で見積もります。

.. math::

   \text{到達可能な性能} = \min\left(\text{ピーク演算性能},\ \text{メモリ帯域} \times \text{演算強度}\right)

演算強度が低いプログラムは、メモリ帯域で性能が決まり（\ **メモリ律速**\ 、memory-bound）、演算強度が高いプログラムは、演算性能で性能が決まります（\ **演算律速**\ 、compute-bound）。両者の境界の演算強度は、ピーク演算性能をメモリ帯域で割った値です。グラフに描くと、境界より左が斜めの直線、右が水平の直線となり、屋根（roof）のような形になることが名前の由来です。

数値例で考えます。ピーク演算性能が 60 TFLOPS（FP32）、メモリ帯域が 3 TB/s の GPU を仮定します。境界の演算強度は次のとおりです。

.. math::

   \frac{60 \times 10^{12}\ \text{FLOP/s}}{3 \times 10^{12}\ \text{byte/s}} = 20\ \text{FLOP/byte}

つまり、メモリから 1 バイト読むごとに 20 回以上の演算をしなければ、演算器を使い切れません。いくつかの処理に当てはめてみます。

.. list-table:: 仮想的な GPU（60 TFLOPS、3 TB/s）での到達可能な性能
   :header-rows: 1
   :widths: 34 22 22 22

   * - 処理
     - 演算強度（FLOP/byte）
     - 到達可能な性能
     - ピークに対する割合
   * - ベクトル加算 ``c[i] = a[i] + b[i]``
     - 1/12 ≈ 0.083
     - 約 0.25 TFLOPS
     - 約 0.4%
   * - 素朴な行列積（キャッシュを無視）
     - 0.25
     - 約 0.75 TFLOPS
     - 約 1.3%
   * - タイリングした行列積（:math:`T = 32`\ ）
     - 8
     - 約 24 TFLOPS
     - 約 40%
   * - 行列積の理論値（:math:`n = 8192`\ ）
     - 約 1365
     - 60 TFLOPS
     - 100%

ベクトル加算は、1 要素ごとに 12 バイト（2 つ読んで 1 つ書く）を転送して 1 回の加算しかしないので、どれほど演算器が速くてもピークの 0.4% しか出ません。このような処理では、メモリ帯域の何割を使えているかで性能を評価すべきです。行列積は、入出力 :math:`3n^2 \times 4` バイトに対して :math:`2n^3` 回の演算をするので、理論上の演算強度は :math:`n/6` と非常に高く、演算律速にできます。ただし、それはデータを再利用する実装（タイリング）をした場合に限られます。

Tensor コアを使うと、ピーク演算性能が 1 桁以上上がるので、境界の演算強度も数百 FLOP/byte に上がります。演算器が速くなるほど、メモリ律速になる処理が増えるのです。大規模言語モデルの推論で、1 トークンずつ生成する処理がその典型です。バッチの大きさが 1 なら、モデルのすべての重みを 1 回読むごとに、重み 1 個あたり 1 回の積和（2 回の演算）しかしません。FP16（2 バイト）の重みなら演算強度は約 1 FLOP/byte で、完全にメモリ律速です。たとえば 70 億パラメータのモデルの重みは FP16 で約 14 GB なので、帯域 3 TB/s の GPU でも 1 トークンの生成に少なくとも約 4.7 ms かかり、毎秒約 200 トークンが上限になります。推論でバッチを大きくしたり、重みを 8 ビットや 4 ビットに量子化したりするのは、この演算強度を上げる、またはデータ量を減らすためです。

PCIe 転送のボトルネック
^^^^^^^^^^^^^^^^^^^^^^^

ルーフラインモデルは GPU のメモリの中での話ですが、データがホストにある場合は、PCIe の転送も考えなければなりません。PCIe 4.0 の x16 の帯域は片方向で約 32 GB/s（実効では 25 GB/s 程度）で、GPU のメモリ帯域の 100 分の 1 程度しかありません。

1 億要素（:math:`10^8` 個）の ``float`` のベクトル加算を考えます。入力の 2 つのベクトル（800 MB）をホストからデバイスに送り、結果（400 MB）を戻すと、合計 1.2 GB の転送に、25 GB/s で約 48 ms かかります。一方、GPU の中での計算は、1.2 GB のメモリアクセスを 3 TB/s で行うので約 0.4 ms です。転送の時間が計算の 100 倍以上になり、CPU で計算したほうが速いことすらあります（CPU のメモリ帯域が 100 GB/s なら約 12 ms）。

GPU を有効に使うには、転送したデータに対して十分な量の計算をすること、データを GPU に置いたまま多くの処理を続けること、転送と計算を重ねることが重要です。行列積なら、:math:`n = 8192` で転送は約 800 MB（約 32 ms）ですが、演算は約 :math:`1.1 \times 10^{12}` 回で、60 TFLOPS でも約 18 ms かかるので、転送に見合う計算量があります。

CPU と GPU の接続
-----------------

GPU と CPU、あるいは GPU 同士の接続は、性能に大きく影響します。

* **PCIe**\ ：パソコンやサーバーで、拡張カードの GPU を CPU と接続する標準的なバスです。x16 の帯域は、PCIe 4.0 で片方向約 32 GB/s、PCIe 5.0 で約 63 GB/s です。PCIe については「:doc:`14_io`」で説明しています。
* **NVLink**\ ：NVIDIA が開発した、GPU 同士（一部の製品では CPU と GPU）を接続する高速なリンクです。2016 年の Pascal 世代（P100）で導入されました。H100 の第 4 世代 NVLink は、GPU あたり合計約 900 GB/s（双方向の合計）の帯域を持ちます。NVSwitch という専用のスイッチを使うと、サーバー内の 8 個などの GPU が互いに全帯域で通信できます。大規模な学習では、多数の GPU の間で重みや勾配をやりとりするので、この帯域が重要になります。
* **統合メモリ**\ （Unified Memory）：CUDA 6（2014 年）で導入された、ホストとデバイスが 1 つのアドレス空間を共有する仕組みです。プログラマーは ``cudaMallocManaged`` で確保したメモリを、ホストとデバイスのどちらからも同じポインタで使えます。実際には、アクセスされたページがドライバによって必要に応じて移動されます（ページフォールトを利用したページの移動。仮想記憶については「:doc:`13_virtual_memory`」を参照）。プログラムは書きやすくなりますが、物理的な転送がなくなるわけではありません。
* **物理メモリの共有**\ ：Apple シリコン（2020 年の M1 以降）などでは、CPU と GPU が同じチップ（パッケージ）にあり、同じ物理メモリを共有します。Apple はこれをユニファイドメモリと呼んでいますが、上の CUDA の統合メモリ（ページを移動して 1 つのアドレス空間に見せる仕組み）とは異なり、物理的に同じメモリを使います。データを転送する必要がなく、CPU が準備したデータを GPU がそのまま使えます。GPU が使えるメモリが大きいことから、大きなモデルの推論にも使われます。ただし、メモリ帯域は CPU と GPU で分け合うことになり、データセンター向けの HBM を使った GPU より小さくなります。
* **統合 GPU**\ （integrated GPU）：パソコン向けの多くの CPU は、同じチップに GPU を内蔵しており、主記憶を CPU と共有します。拡張カードの\ **ディスクリート GPU**\ （discrete GPU）に比べて性能は低いですが、消費電力と価格が小さく、画面表示や動画の再生、軽い計算には十分です。

データセンター向けでも、CPU と GPU の距離を縮める製品が登場しています。AMD の MI300A（2023 年）は CPU と GPU を 1 つのパッケージに収めて HBM を共有し、NVIDIA の Grace Hopper は CPU と GPU を NVLink-C2C という高速なリンクで接続して、互いのメモリにキャッシュコヒーレントにアクセスできるようにしています。

GPU のプログラミング環境
------------------------

GPU をプログラムする環境には、次のようなものがあります。

.. list-table:: GPU の主なプログラミング環境
   :header-rows: 1
   :widths: 22 20 58

   * - 名前
     - 提供元
     - 特徴
   * - CUDA
     - NVIDIA
     - NVIDIA の GPU 専用。C++ を拡張した言語と、cuBLAS（線形代数）、cuDNN（深層学習）などの豊富なライブラリを持ちます。事実上の標準になっています。
   * - ROCm、HIP
     - AMD
     - ROCm は AMD の GPU 向けのソフトウェア基盤。HIP は CUDA とほぼ同じ書き方ができる言語で、CUDA のコードを変換するツールもあります。
   * - OpenCL
     - Khronos Group
     - ベンダーに依存しない標準。CPU、GPU、FPGA などで動きますが、最適化はベンダーごとの差が大きいです。
   * - SYCL
     - Khronos Group
     - 標準の C++ で異種のプロセッサをプログラムする仕様。Intel の oneAPI（DPC++）が代表的な実装。
   * - コンピュートシェーダー
     - Vulkan、Metal、DirectX
     - グラフィックス API の中で汎用の計算を行う仕組み。ゲームなどでグラフィックスと計算を組み合わせるときに使います。Metal は Apple のプラットフォームの標準です。
   * - Python のライブラリ
     - 各種
     - CuPy（NumPy 互換の GPU 配列）、PyTorch や JAX（深層学習のフレームワーク）、Numba（Python の関数を GPU のカーネルにコンパイル）、Triton（ブロック単位でカーネルを書く言語）など

多くのエンジニアにとって、GPU を使う最も身近な方法は、CUDA のカーネルを自分で書くことではなく、PyTorch や CuPy などのライブラリを使うことです。たとえば CuPy では、NumPy の配列を CuPy の配列に置き換えるだけで、行列演算が GPU で実行されます。ただし、この章で説明したメモリアクセスや転送の性質を理解しておくと、なぜ遅いのか、どこを直せば速くなるのかを判断できます。

CUDA が NVIDIA の GPU にしか対応しないにもかかわらず広く使われていることは、ハードウェアの性能だけでなく、ライブラリやツール、開発者のコミュニティを含むソフトウェアの蓄積が、プロセッサの競争力を左右することを示しています。この点は「:doc:`17_accelerators`」でも取り上げます。

GPU が向く処理と向かない処理
----------------------------

この章の内容をもとに、GPU が向く処理と向かない処理を整理します。

.. list-table:: GPU が向く処理と向かない処理
   :header-rows: 1
   :widths: 30 35 35

   * - 観点
     - 向く処理
     - 向かない処理
   * - 並列度
     - 数万以上の独立した仕事があります（大きな配列、画像、行列）。
     - 並列度が小さいか、逐次的な依存関係が強いです。
   * - 分岐
     - すべての要素に同じ処理をします。
     - 要素ごとに処理の流れが大きく異なります（ダイバージェンス）。
   * - メモリアクセス
     - 連続した規則的なアクセスで、データの再利用が多いです。
     - ポインタをたどるような不規則なアクセス（連結リスト、木の探索）
   * - 演算強度
     - 高いです（行列積、畳み込み、物理シミュレーション）。
     - 低い処理を単独で行います（転送の時間に見合いません）。
   * - データの大きさと転送
     - データを GPU に置いたまま多くの処理を続けられます。
     - 小さなデータを頻繁に CPU と行き来させます。
   * - レイテンシの要求
     - 全体のスループットが重要です（バッチ処理、学習）。
     - 1 件ごとの応答時間が非常に短いことが求められます。
   * - 例
     - 深層学習、画像・動画処理、流体や分子のシミュレーション、暗号資産の採掘、レイトレーシング
     - OS やコンパイラ、データベースのトランザクション処理、構文解析、多くの業務アプリケーション

実際のシステムでは、CPU が全体の制御や逐次的な処理を担当し、データ並列の重い計算を GPU に任せる、という分担が一般的です。このように性質の異なるプロセッサを組み合わせる構成については、「:doc:`17_accelerators`」で説明します。

この章のまとめ
--------------

* CPU は 1 つのスレッドのレイテンシを短くすることを、GPU は全体のスループットを高めることを目標にしています。GPU は複雑な制御やキャッシュを減らし、そのトランジスタを多数の演算器に回しています。
* GPU は固定機能のグラフィックスアクセラレーターから始まり、プログラマブルシェーダー、統合シェーダーアーキテクチャ（2006 年）、CUDA（2007 年）を経て汎用の並列プロセッサになりました。2012 年の AlexNet 以降は深層学習の中心となり、2017 年には Tensor コアが導入されました。
* グラフィックスの処理は、大量の独立した仕事に同じプログラムを適用し、個々のレイテンシが問題にならないという、大量並列に向いた性質を持っています。
* NVIDIA の GPU は多数の SM からなり、各 SM はワープスケジューラ、巨大なレジスタファイル、FP32 の演算器（CUDA コア）、Tensor コア、共有メモリを持ちます。
* プログラムはスレッド・ブロック・グリッドの階層で書かれ、ハードウェアは 32 スレッドのワープ単位で同じ命令を実行します（SIMT）。SIMT は SIMD のハードウェアにスレッドとして書けるプログラミングモデルを組み合わせたものです。
* GPU は多数のワープを切り替えてメモリのレイテンシを隠します。必要なワープの数はリトルの法則で見積もれ、占有率はレジスタや共有メモリの使用量で制限されます。
* ワープ内で分岐の条件が分かれると、両方の経路をマスク付きで実行するため性能が下がります。条件をワープ単位で揃えることが重要です。
* ワープのメモリアクセスが連続していれば少数のトランザクションに合体されますが、ストライドやランダムなアクセスでは効率が大きく下がります。共有メモリでは、同じバンクの異なるワードへのアクセスがバンクコンフリクトになり、パディングで避けられます。
* 行列積は、タイリングで共有メモリやレジスタ上のデータを再利用することで演算強度が上がり、Tensor コアと低精度の形式（FP16、BF16、FP8 など）で桁違いの性能が得られます。
* ルーフラインモデルで、演算強度から性能の上限とメモリ律速か演算律速かを判断できます。ホストとの PCIe 転送は GPU のメモリより桁違いに遅く、ボトルネックになりやすいので注意が必要です。
* CPU と GPU は PCIe や NVLink で接続され、統合メモリや物理メモリの共有によって 1 つのアドレス空間で扱えるようになってきています。プログラミング環境は CUDA が中心で、ROCm/HIP、OpenCL、コンピュートシェーダー、Python のライブラリなどがあります。
