セキュリティと信頼性
====================

これまでの章では、主に「どうすれば速くなるか」という観点からアーキテクチャを見てきました。しかし実際のコンピューターには、速さと同じくらい重要な 2 つの要求があります。1 つは、悪意のあるプログラムがほかのプログラムや OS のデータを盗んだり壊したりできないようにする\ **セキュリティ**\ （security）、もう 1 つは、ハードウェアに故障や一時的な誤りが起きても正しく動き続ける\ **信頼性**\ （reliability）です。

この章では、まず特権モードやページ単位の保護といった、ハードウェアによる保護の基本を確認します。次に、キャッシュという高速化の仕組みそのものが情報漏えいの経路になるサイドチャネル攻撃を取り上げ、投機実行に起因する Spectre と Meltdown、その対策と性能への影響を説明します。さらに、DRAM の物理的な性質に関わる Rowhammer、ソフトエラーと誤り訂正符号（ECC）、冗長化とチェックポイント、信頼できる実行環境（TEE）、メモリ安全性のハードウェア支援を順に紹介します。OS 側の実装の詳細は扱いません。

ハードウェアによる保護の基本
----------------------------

複数のプログラムを安全に同時実行するには、「ユーザーのプログラムは OS のデータを直接読み書きできない」「あるプロセスはほかのプロセスのメモリに触れない」といった約束を守らせる必要があります。この約束をソフトウェアだけで守らせることはできません。命令は CPU が直接実行するので、CPU 自身が「この命令をいま実行してよいか」を判定する仕組みが必要です。そのための 2 本柱が、特権モードとページ単位の保護です。

特権モード
^^^^^^^^^^

CPU は、現在どの程度の権限で命令を実行しているかを表す状態を持っています。これを\ **特権モード**\ （privilege mode）または特権レベルと呼びます。権限の高いモードでは、ページテーブルの切り替え、割り込みの設定、入出力装置の制御などを行う\ **特権命令**\ を実行できます。権限の低いモードで特権命令を実行したり、許されていないメモリにアクセスしたりすると、CPU は例外（「:doc:`09_datapath`」）を発生させ、制御を権限の高いモードのコード（OS など）に移します。

**RISC-V** では、権限の高い順に次の 3 つのモードが定義されています。

* **M モード**\ （Machine mode）：最も権限が高く、すべての RISC-V 実装に必須のモード。電源投入直後はこのモードで動き、ファームウェア（たとえば OpenSBI）が動作します。
* **S モード**\ （Supervisor mode）：OS のカーネルが動作するモード。仮想記憶（ページテーブル）の設定などを行います。
* **U モード**\ （User mode）：アプリケーションが動作するモード。

U モードのプログラムが OS の機能を使いたいときは、``ecall`` 命令を実行します。``ecall`` は例外を発生させ、CPU は（OS が動く通常の構成では）S モードに切り替わってカーネルの例外ハンドラに飛びます。処理が終わるとカーネルは ``sret`` 命令で U モードに戻ります。M モードから下位のモードに戻るときは ``mret`` を使います。どのモードでどの制御・状態レジスタ（CSR）にアクセスできるかは、CSR のアドレスの一部のビットで決まっています。さらに、M モードには\ **PMP**\ （Physical Memory Protection：物理メモリ保護）という仕組みがあり、S モードや U モードがアクセスできる物理アドレスの範囲を、ページテーブルとは独立に制限できます。仮想化のためには、H 拡張（Hypervisor 拡張）によってハイパーバイザー用のモードが追加されます。

**x86-64** では、特権レベルは 0 から 3 の 4 段階で、\ **リング**\ （ring）と呼ばれます。リング 0 が最も権限が高く、OS のカーネルが動作します。アプリケーションはリング 3 で動作し、リング 1 と 2 は現在の主要な OS ではほとんど使われていません。現在の特権レベル（CPL）は、コードセグメントレジスタ（CS）の下位 2 ビットに保持されます。システムコールには ``syscall`` 命令、カーネルからの復帰には ``sysret`` 命令を使います。仮想化のためには、リングとは別に、Intel VT-x では VMX root / non-root という動作モードがあります（AMD の AMD-V にも同様の仕組みがあります）。

**AArch64** では、特権レベルを\ **例外レベル**\ （Exception Level：EL）と呼び、EL0（アプリケーション）、EL1（OS カーネル）、EL2（ハイパーバイザー）、EL3（セキュアモニタ）の 4 段階があります。EL0 から EL1 へは ``svc`` 命令、EL1 から EL2 へは ``hvc`` 命令、EL3 へは ``smc`` 命令で移ります。

ページ単位の保護
^^^^^^^^^^^^^^^^

特権モードだけでは「どのメモリを誰が触ってよいか」を細かく指定できません。そこで、仮想記憶のページテーブルの各エントリ（PTE）に保護用のビットを持たせ、ページ単位でアクセスを許可・禁止します。仮想記憶の仕組みそのものは「:doc:`13_virtual_memory`」で説明しました。ここでは保護に関わるビットに注目します。

RISC-V の Sv39 方式の PTE には、次のようなビットがあります。

.. list-table:: RISC-V（Sv39）の PTE の主な保護ビット
   :header-rows: 1
   :widths: 15 85

   * - ビット
     - 意味
   * - V
     - エントリが有効（Valid）であること。0 ならアクセスするとページフォールト。
   * - R / W / X
     - 読み出し（Read）、書き込み（Write）、命令の実行（eXecute）を許可するかどうか。
   * - U
     - U モードからアクセスできるページかどうか。U = 1 のページは、S モードからは原則としてアクセスできず（``sstatus`` の SUM ビットを 1 にしたときだけ読み書き可能）、S モードで実行することは決してできません。
   * - A / D
     - アクセスされた（Accessed）、書き込まれた（Dirty）ことを示すビット。保護ではなく、ページの置き換えや書き戻しの判断に使います。

x86-64 の PTE にも、書き込み許可を表す R/W ビット、ユーザーモードからのアクセスを許可する U/S ビット、そして実行を禁止する NX ビットがあります。AArch64 では AP ビットでアクセス権を、UXN・PXN ビットでユーザー・特権モードそれぞれの実行禁止を指定します。保護に違反するアクセスはページフォールトとなり、OS がプロセスを停止させる（Linux なら Segmentation fault）などの処理を行います。

NX ビット
^^^^^^^^^

初期の x86 のページテーブルには「実行禁止」を表すビットがなく、読み出せるページはすべて実行もできました。このため、バッファオーバーフローでスタックに機械語を書き込み、戻りアドレスをそこに書き換えて実行させる攻撃（コードインジェクション）が容易でした。これを防ぐのが、ページを実行禁止にする\ **NX ビット**\ （No-eXecute bit）です。AMD が AMD64 で導入し、Intel は XD ビット（eXecute Disable）という名前で同等の機能を採用しました。x86-64 では PTE の最上位ビット（ビット 63）が NX ビットです。

NX ビットを使うと、OS は「書き込めるページは実行させない、実行できるページには書き込ませない」という\ **W^X**\ （Write XOR Execute）の方針を実現できます。スタックやヒープは書き込み可・実行不可、プログラムのコードは実行可・書き込み不可にするわけです。RISC-V では最初から R / W / X が独立したビットなので、同じ方針を自然に表現できます。

さらに、カーネルが誤ってユーザー空間のコードを実行したりデータを参照したりすることを防ぐ機能もあります。x86-64 の\ **SMEP**\ （Supervisor Mode Execution Prevention）と\ **SMAP**\ （Supervisor Mode Access Prevention）、AArch64 の PXN と PAN（Privileged Access Never）がそれにあたり、RISC-V の U ビットと SUM ビットも同じ役割を果たします。

なお、NX ビットで実行可能な領域を限定しても、攻撃者は既存のコードの断片（ガジェット）をつなぎ合わせて実行させる\ **ROP**\ （Return-Oriented Programming）という手法に移りました。これへのハードウェアによる対策は、この章の後半の「メモリ安全性のハードウェア支援」で紹介します。

サイドチャネル攻撃
------------------

特権モードとページ保護は、正規の経路での不正なアクセスを確実に防ぎます。しかし情報は、処理にかかる時間、消費電力、電磁波といった副次的な経路からも漏れることがあります。こうした副次的な情報から秘密を推測する攻撃を\ **サイドチャネル攻撃**\ （side-channel attack）と呼びます。アーキテクチャの観点で特に重要なのは、キャッシュの状態が時間差として観測できてしまう\ **キャッシュタイミング攻撃**\ です。

キャッシュにヒットすれば数サイクルで済む読み出しが、主記憶まで行くと数百サイクルかかります（「:doc:`12_memory_hierarchy`」）。キャッシュは複数のプロセスやコアで共有されているため、あるプログラムのメモリアクセスがキャッシュの状態を変え、その変化が別のプログラムからアクセス時間の差として見えてしまうことがあります。ISA の仕様にはキャッシュの状態は現れませんが、マイクロアーキテクチャの状態は時間という形で外に漏れるわけです。

学術研究では、観測の仕方によって主に 2 つの考え方が知られています。

.. list-table:: キャッシュタイミング攻撃の 2 つの考え方
   :header-rows: 1
   :widths: 20 40 40

   * - 名称
     - 考え方
     - 前提と観測の粒度
   * - Flush+Reload
     - 共有しているデータをキャッシュから追い出しておき、あとでそのデータが再びキャッシュに載っているかどうかで、相手がそれを使ったかを知ります。
     - 相手と同じ物理ページ（共有ライブラリなど）を共有している必要があります。粒度はキャッシュライン。
   * - Prime+Probe
     - あるキャッシュセットを自分のデータで埋めておき、それが追い出されたかどうかで、相手がそのセットを使ったかを知ります。
     - メモリの共有は不要です。粒度はキャッシュセット。

Flush+Reload は Yarom と Falkner（2014 年）、Prime+Probe は Osvik、Shamir、Tromer（2006 年）の研究で知られるようになりました。どちらも、暗号の実装が秘密鍵の値によって異なるメモリ位置にアクセスする場合に、鍵の情報が漏れうることを示しています。

ソフトウェア側の基本的な対策は、秘密の値によって分岐の向きやメモリアクセスのアドレスが変わらないように書く\ **定数時間プログラミング**\ （constant-time programming）です。主要な暗号ライブラリはこの方針で実装されています。ハードウェア側では、キャッシュをセキュリティの境界ごとに分割する方式なども研究されています。

投機実行に起因する脆弱性
------------------------

2018 年 1 月、プロセッサの投機実行に起因する脆弱性として **Spectre** と **Meltdown** が公表されました。Google の Project Zero と複数の大学の研究者がそれぞれ独立に発見したもので、過去 20 年ほどの間に設計された多くの高性能プロセッサが影響を受けることが分かり、大きな衝撃を与えました。

背景にある考え方
^^^^^^^^^^^^^^^^

**投機実行**\ は、分岐の結果などが確定する前に予測に基づいて先の命令を実行し、予測が外れたら結果を取り消す仕組みです（「:doc:`11_ilp`」）。取り消された命令の結果はレジスタにもメモリにも残らず、ISA の仕様の上では「なかったこと」になります。ところが、取り消された命令が実行中にキャッシュへ読み込んだデータは、そのまま残ります。キャッシュの状態は ISA の外にあるマイクロアーキテクチャの状態なので、取り消す必要はないと考えられてきたからです。

Spectre と Meltdown の本質は、「本来は実行されないはずの命令が、取り消されるまでの短い間に秘密のデータに触れ、その痕跡がキャッシュに残り、前節のタイミングの差として観測できる」という点にあります。投機的に実行されて最終的に取り消される命令の実行を\ **過渡的実行**\ （transient execution）と呼び、これを利用する一連の問題を\ **過渡的実行攻撃**\ と総称します。

.. graphviz::
   :caption: 投機実行の痕跡がキャッシュに残る仕組み（概念図）
   :align: center

   digraph transient {
     rankdir=LR;
     node [shape=box, style=rounded];
     pred [label="予測に基づいて\n先の命令を実行"];
     touch [label="取り消し前に\nデータがキャッシュに載る"];
     squash [label="予測ミスが判明\n結果を破棄"];
     remain [label="アーキテクチャの状態は元どおり\nキャッシュの状態は残る"];
     pred -> touch -> squash -> remain;
   }

Spectre
^^^^^^^

**Spectre** は、分岐予測を誤らせることで、被害者のプログラム自身に「本来は通らない経路」を投機的に実行させる種類の問題です。たとえば\ **変種 1**\ （境界チェック回避：bounds check bypass）は、配列の添字が範囲内かを確かめる条件分岐が誤って予測され、範囲チェックの内側の処理が一時的に実行されてしまう、という問題です。ソースコードとしては正しく境界チェックをしていても、投機実行の間はチェックが「まだ効いていない」状態になりうる点が重要です。

Spectre は特定の製品の欠陥というより、分岐予測と投機実行を行うほぼすべての高性能プロセッサに共通する性質に根ざしています。攻撃者が用意したコードを同じプロセス内で実行する環境、たとえばブラウザの JavaScript エンジンでは特に問題になりました。

Meltdown
^^^^^^^^

**Meltdown** は、ユーザーモードのプログラムから、本来アクセスできないカーネルのメモリの内容が漏れうるという問題です。当時の主要な OS は、システムコールのたびにページテーブルを切り替える負担を避けるため、各プロセスのアドレス空間にカーネルの領域もマッピングし、PTE のビットで「ユーザーモードからはアクセス不可」にしていました。影響を受けたプロセッサでは、権限違反の判定が確定する前に、読み出した値が後続の命令で一時的に使われてしまうことがありました。

Spectre が「被害者自身の命令を投機的に実行させる」問題であるのに対し、Meltdown は特定の実装で「権限の検査と値の受け渡しの順序」に問題があったものです。主に当時の Intel のプロセッサが影響を受け、Arm の一部のコアや IBM の POWER も影響を受けました。AMD のプロセッサは影響を受けないとされました。

対策と性能への影響
------------------

Spectre や Meltdown の原因は、性能を高めるための仕組み（投機実行、キャッシュ、カーネル領域の常時マッピング）そのものです。そのため対策は、多かれ少なかれ性能を犠牲にします。

.. list-table:: 主な対策と性能への影響
   :header-rows: 1
   :widths: 20 14 40 26

   * - 対策
     - 主な対象
     - 仕組み
     - 性能への影響
   * - KPTI（Kernel Page-Table Isolation）
     - Meltdown
     - ユーザーモード用のページテーブルにはカーネルの領域を（入口となるごく一部を除いて）マッピングせず、カーネルに入るたびにページテーブルを切り替えます。
     - システムコールや割り込みの多い処理で大きく、計算主体の処理ではほとんどありません。
   * - 投機の制限（``lfence`` の挿入、添字のマスク）
     - Spectre 変種 1
     - 境界チェックの直後に投機を止める命令を入れるか、添字を範囲内に丸める演算を入れて、範囲外の値で処理が進まないようにします。
     - 対策した箇所だけに限られますが、必要な箇所を漏れなく特定するのが難しいという課題があります。
   * - レトポリン（retpoline）
     - Spectre 変種 2
     - 間接分岐を ``call`` と ``ret`` を組み合わせた命令列に置き換え、間接分岐の分岐先予測器（BTB）が使われないようにします。投機実行は、リターンアドレススタックの予測によって無害な無限ループに閉じ込められます。
     - 間接分岐の多いコードで増加します。
   * - 分岐予測器の制御（IBRS、IBPB、STIBP など）
     - Spectre 変種 2
     - マイクロコードの更新などで追加された機能で、特権レベルの切り替え時などに分岐予測器を隔離・消去します。
     - 初期の実装では大きいものがありました。
   * - SMT の無効化
     - L1TF、MDS など
     - コアの資源を共有するスレッド間での漏えいを防ぐため、SMT を止めます。
     - SMT による性能向上を失います。
   * - ハードウェアの修正
     - 各種
     - 新しく設計されたプロセッサでは、権限の検査を値の受け渡しより先に行う、分岐予測器を特権レベルごとに分離するなどの修正が入っています。
     - ソフトウェアによる対策が不要になる分、低下は小さくなります。

KPTI は、学術研究で提案された KAISER という手法を Linux に取り入れたものです。ページテーブルを切り替えると通常は TLB の内容が無効になるため、カーネルに入るたびに TLB ミスが増えます。x86-64 の PCID（Process-Context Identifier）のように TLB のエントリにアドレス空間の識別子を付ける機能があれば、TLB を捨てずに済むので影響を小さくできます。それでも、システムコールを頻繁に発行する処理では、数 % から条件によっては数十 % の性能低下が報告されました。

レトポリンという名前は return と trampoline を組み合わせたもので、Google が考案しました。ソフトウェアだけで実装でき、当時のマイクロコードによる対策より軽いことが多かったため、広く使われました。

現在の OS は CPU の種類に応じて必要な対策だけを有効にします。Linux では ``/sys/devices/system/cpu/vulnerabilities/`` ディレクトリのファイルを見ると、その CPU がどの問題の影響を受け、どの対策が有効になっているかを確認できます。ベンチマークの結果を比べるときは、こうした対策の有無が結果に影響することを意識しておく必要があります。

過渡的実行の問題は「投機実行の痕跡がマイクロアーキテクチャに残る」という高速化の本質に根ざしているため、根本的な解決は難しいと考えられています。実際の対策は、セキュリティの境界をプロセスの境界に合わせる（たとえばブラウザでサイトごとにプロセスを分ける）方向と、特定の箇所で投機を制限する方向の組み合わせになっています。

Rowhammer
---------

ここまでの問題はプロセッサの論理的な動作に関わるものでしたが、**Rowhammer** は DRAM の物理的な性質に関わる問題です。

DRAM の 1 ビットは、1 つのトランジスタと 1 つのコンデンサでできたセルに、電荷の有無として記憶されます。セルは 2 次元の格子状に並べられ、横 1 列を\ **行**\ （row）と呼びます。データを読むときは、まず行全体を活性化して行バッファ（センスアンプの列）に読み出し、そこから必要な列を取り出します。コンデンサの電荷は時間とともに漏れるため、DRAM は一定時間ごと（DDR4 では通常 64 ms 以内）にすべての行を読み出して書き戻す\ **リフレッシュ**\ を行います（DRAM の構造は「:doc:`12_memory_hierarchy`」も参照してください）。

微細化によってセルどうしの間隔が狭くなると、ある行を短時間に非常に多くの回数活性化したとき、その電気的な干渉で隣接する行のセルの電荷が失われ、リフレッシュが来る前にビットが反転することがあります。これが Rowhammer です。Kim らは 2014 年に、市販の DDR3 モジュールの多くでこの現象が起きることを示しました。翌 2015 年には Google の Project Zero が、この現象がページテーブルなどの重要なデータを壊すことで、特権の昇格につながりうることを示しました。メモリが正しく値を保持するという、ソフトウェアのあらゆる保護の前提が崩れうる点で深刻な問題です。

主な対策には次のようなものがあります。

* リフレッシュの間隔を短くする：ビットが反転する前に電荷を回復させます。消費電力が増え、リフレッシュ中はアクセスできないので性能も低下します。
* ECC：1 ビットの反転なら訂正できます（次節）。ただし同じワードの複数ビットが反転すると訂正できないため、完全な対策にはなりません。
* **TRR**\ （Target Row Refresh）：DRAM やメモリコントローラが、頻繁に活性化される行を検出して、その隣の行を追加でリフレッシュします。DDR4 の世代で導入されましたが、2020 年には TRR の検出をすり抜けるアクセスパターンがあることが報告されました。
* DDR5 の RFM（Refresh Management）など：メモリコントローラと DRAM が協調して、活性化の回数に応じた追加のリフレッシュを行う仕組みが規格に加えられています。

微細化が進むほど、ビットの反転に必要な活性化の回数は少なくなる傾向が報告されており、Rowhammer は DRAM の設計上の継続的な課題になっています。

信頼性
------

セキュリティが悪意のある攻撃に備えるのに対し、信頼性は偶発的な故障や誤りに備えるものです。故障には、一度起きると直らない\ **ハードエラー**\ （hard error：配線の断線、トランジスタの劣化など）と、一時的にビットが反転するだけで回路自体は壊れない\ **ソフトエラー**\ （soft error）があります。

ソフトエラー
^^^^^^^^^^^^

ソフトエラーの主な原因は、宇宙線が大気と衝突して生じる中性子や、パッケージの材料に微量に含まれる放射性物質から出るアルファ線です。これらの粒子が半導体を通過すると電荷が生じ、SRAM や DRAM のセル、フリップフロップの値が反転することがあります。微細化でセル 1 つあたりの電荷が小さくなるほど、反転は起きやすくなります。1 個のセルで起きる確率は非常に小さくても、メモリ全体では膨大な数のビットがあるため、大規模なシステムでは無視できません。

故障の頻度は、\ **FIT**\ （Failures In Time）という単位で表すことがあります。1 FIT は、:math:`10^9` 時間あたり 1 回の故障です。

また 2021 年ごろには、大規模なデータセンターを運用する企業から、ごく一部の CPU コアが特定の命令で誤った結果を例外も出さずに返す\ **サイレントデータ破損**\ （Silent Data Corruption：SDC）が、無視できない頻度で見つかるという報告がありました。誤りを「検出できる」ことの重要性を示す例です。

パリティ
^^^^^^^^

最も簡単な誤り検出は\ **パリティ**\ （parity）です。データの各ビットの XOR を 1 ビット追加し、1 の個数が必ず偶数（偶数パリティ）になるようにします。読み出したときに 1 の個数が奇数なら、どこかのビットが反転したと分かります。ただし、どのビットが反転したかは分からないので訂正はできず、2 ビットが同時に反転すると検出もできません。

L1 キャッシュのように、誤りを検出したら下位の階層から読み直せばよい場所では、パリティだけで十分なことがあります。

ハミング符号
^^^^^^^^^^^^

誤りを訂正するには、複数のパリティビットを組み合わせて、誤りの位置まで特定できるようにします。その代表が、Richard Hamming が 1950 年に発表した\ **ハミング符号**\ （Hamming code）です。

ハミング (7,4) 符号では、4 ビットのデータに 3 ビットのパリティを加えて 7 ビットの\ **符号語**\ を作ります。ビットの位置を 1 から 7 で数え、2 のべき乗の位置（1、2、4）をパリティ、残りの位置（3、5、6、7）をデータに使います。位置 :math:`p` のパリティは、位置番号を 2 進数で表したときに重み :math:`p` の桁が 1 になる位置（位置番号と :math:`p` の AND が 0 でない位置）をまとめて担当します。たとえば位置 1 のパリティは位置 1、3、5、7 の XOR が 0 になるように決めます。

こうすると、正しい符号語では「1 が立っている位置の番号をすべて XOR すると 0 になる」という性質が成り立ちます。位置 :math:`e` のビットが 1 つだけ反転すると、この XOR の結果はちょうど :math:`e` になります。この値を\ **シンドローム**\ （syndrome）と呼びます。シンドロームが 0 なら誤りなし、0 以外ならその値が誤りの位置を直接示すので、そのビットを反転すれば訂正できます。

データを :math:`m` ビット、パリティを :math:`r` ビットとすると、シンドロームは「誤りなし」と「:math:`m + r` 通りの誤り位置」を区別できなければならないので、次の条件が必要です。

.. math::

   2^r \ge m + r + 1

:math:`m = 4` なら :math:`r = 3`\ 、:math:`m = 64` なら :math:`r = 7` です。

ハミング符号は 1 ビットの誤りを訂正できますが、2 ビットが反転すると、シンドロームが別の位置を指してしまい、誤った訂正をします。そこで、符号語全体のパリティを 1 ビット追加します。すると、1 ビットの誤りなら全体パリティが合わなくなり、2 ビットの誤りなら全体パリティは合うのにシンドロームは 0 でない、という形で区別できます。これを\ **SECDED**\ （Single Error Correction, Double Error Detection：1 ビット誤り訂正・2 ビット誤り検出）と呼びます。サーバー向けのメモリで広く使われてきた ECC は、64 ビットのデータに 8 ビットの検査ビットを加えた (72,64) の SECDED 符号です。検査ビットの割合は :math:`8 / 64 = 12.5\,\%` で、ECC 付きの DIMM が 72 ビット幅になっているのはこのためです。

* 25〜31 行目：パリティの計算です。位置 ``p``\ （1、2、4）のパリティは、位置番号との AND が 0 でない位置（``pos & p``）のビットの XOR として求めます。

* 116〜119 行目：2 ビット誤りを (7,4) 符号だけで復号した場合です。実行結果の 19 行目のように、シンドローム 6 が無関係な位置を指し、誤ったデータに「訂正」してしまいます。全体パリティを加える意味がここにあります。

実際のメモリシステムでは、さらに DRAM チップ 1 個がまるごと故障しても訂正できる方式（Chipkill などと呼ばれます）や、メモリ全体を定期的に読んで 1 ビット誤りを早めに訂正しておく\ **パトロールスクラブ**\ が使われます。DDR5 では DRAM チップの内部にも ECC が組み込まれましたが、これはチップ内部の誤りを補うためのもので、システム側の ECC の代わりにはなりません。訂正できない誤りが見つかると、CPU は x86-64 のマシンチェック例外のような仕組みで OS に通知します。

冗長化
^^^^^^

ECC がデータに冗長な情報を加えるのに対し、装置そのものを複数用意して故障に備えることを\ **冗長化**\ （redundancy）と呼びます。

* **TMR**\ （Triple Modular Redundancy：三重冗長）：同じ回路を 3 つ用意し、多数決で出力を決めます。1 つが故障しても正しい結果を出せます。宇宙機や航空機などで使われます。
* **ロックステップ**\ （lockstep）：2 つのコアで同じ命令列を同時に実行し、結果を比較します。不一致を検出したら安全な状態に移ります。自動車向けのマイクロコントローラなどで使われます。
* ストレージやネットワークの冗長化：RAID によるディスクの冗長化や、通信経路の二重化などです。

TMR で、各モジュールが一定期間正しく動作する確率（信頼度）を :math:`R` とすると、3 つのうち 2 つ以上が正しければよいので、全体の信頼度は次のようになります。

.. math::

   R_{\text{TMR}} = R^3 + 3R^2(1 - R) = 3R^2 - 2R^3

:math:`R = 0.9` なら :math:`R_{\text{TMR}} = 3 \times 0.81 - 2 \times 0.729 = 0.972` となり、信頼度が上がります。ただし :math:`R < 0.5` では逆に下がるので、もともと信頼度の高いモジュールを組み合わせることが前提です。

チェックポイント
^^^^^^^^^^^^^^^^

部品の数が増えるほど、システムのどこかが故障する頻度は高くなります。各部品が独立に、一定の確率で故障し、故障するまでの平均時間（Mean Time To Failure：MTTF）が同じ :math:`M` であるとすると、:math:`n` 個の部品からなるシステムの MTTF はおよそ :math:`M / n` になります。たとえば MTTF が 5 年（約 43,800 時間）のノードを 10,000 台つないだスーパーコンピューターでは、システムのどこかで約 4.4 時間に 1 回故障が起きる計算です。数日かかる計算を、故障のたびに最初からやり直すわけにはいきません。

そこで、計算の途中の状態を定期的にストレージに保存し、故障したら最後に保存した状態から再開します。これを\ **チェックポイント・リスタート**\ （checkpoint/restart）と呼びます。保存の間隔が短すぎると保存の時間が無駄になり、長すぎると故障時にやり直す量が増えます。保存 1 回にかかる時間を :math:`\delta`\ 、システムの MTTF を :math:`M` とすると、最適な間隔 :math:`\tau` のおおよその値として、Young による次の式が知られています。

.. math::

   \tau \approx \sqrt{2 \delta M}

上の例で :math:`M = 4.4` 時間（約 264 分）、保存に 5 分かかるとすると、:math:`\tau \approx \sqrt{2 \times 5 \times 264} \approx 51` 分ごとに保存するのがよいことになります。大規模な AI の学習でも、同じ考え方でチェックポイントが使われています。

信頼できる実行環境
------------------

クラウドでは、利用者のプログラムが他人の管理するサーバーの上で動きます。このとき、OS やハイパーバイザー、さらには物理的にサーバーに触れられる人からもデータを守りたいという要求があります。そのために、CPU が特別に保護された実行環境を作り、その中のコードとデータを、権限の高いソフトウェアからも読み書きできないようにする仕組みが\ **信頼できる実行環境**\ （Trusted Execution Environment：TEE）です。TEE を使った計算は\ **コンフィデンシャル・コンピューティング**\ （confidential computing）とも呼ばれます。

多くの TEE は、メモリに書き出すデータを CPU 内部の鍵で暗号化することで、主記憶を直接読まれても中身が分からないようにしています。また、TEE の中で動いているのが確かに意図したコードであることを、CPU が署名した報告によって外部に証明する\ **リモートアテステーション**\ （remote attestation）の仕組みを備えています。

.. list-table:: 主な TEE
   :header-rows: 1
   :widths: 22 14 64

   * - 名称
     - 提供元
     - 概要
   * - SGX（Software Guard Extensions）
     - Intel
     - プロセスの中に\ **エンクレーブ**\ （enclave）と呼ぶ保護領域を作り、OS からも読めないようにします。保護の単位がアプリケーションの一部なので、アプリケーションの改修が必要です。近年はおもにサーバー向けの製品で提供されています。
   * - TDX（Trust Domain Extensions）
     - Intel
     - 仮想マシン全体を保護の単位とし、ハイパーバイザーから隔離します。既存のアプリケーションをそのまま動かしやすい方式です。
   * - SEV（Secure Encrypted Virtualization）
     - AMD
     - 仮想マシンごとに異なる鍵でメモリを暗号化します。レジスタの状態も暗号化する SEV-ES、メモリの完全性の保護を加えた SEV-SNP へと拡張されてきました。
   * - TrustZone
     - Arm
     - CPU の動作を通常の OS が動く Normal world と、保護された Secure world に分けます。スマートフォンでの鍵の管理や決済などに広く使われています。
   * - CCA（Confidential Compute Architecture）
     - Arm
     - Armv9-A で導入された仕組みで、\ **Realm**\ と呼ぶ保護された実行環境を作り、仮想マシンをハイパーバイザーから隔離します。

TEE は万能ではありません。TEE も同じ CPU のキャッシュや投機実行の仕組みを使うため、前述のサイドチャネル攻撃や過渡的実行攻撃の影響を受けうることが研究で示されてきました。どのような攻撃者を想定し、何を守るのか（脅威モデル）を理解したうえで使う必要があります。

メモリ安全性のハードウェア支援
------------------------------

C や C++ で書かれたソフトウェアでは、バッファオーバーフローや解放後のメモリの使用（use-after-free）といった\ **メモリ安全性**\ （memory safety）の欠陥が、セキュリティ上の問題の大きな割合を占めています。Microsoft や Google の Chromium プロジェクトは、深刻な脆弱性の約 70% がメモリ安全性に関するものだと報告しています。Rust のようなメモリ安全な言語への移行と並行して、ハードウェアで欠陥を検出する仕組みも導入されつつあります。

* **MTE**\ （Memory Tagging Extension）：Armv8.5-A で導入された機能です。メモリの 16 バイトごとに 4 ビットのタグを付け、ポインタの上位の使われていないビットにも同じタグを入れておきます。ロード・ストアのときにポインタのタグとメモリのタグが一致しなければ、エラーとして報告します。メモリを確保するたびに異なるタグを割り当てておけば、範囲外アクセスや解放後の使用を高い確率で検出できます。タグは 4 ビットなので、偶然一致してしまう確率は 1/16 です。タグの保存に必要な容量は :math:`4 / 128 \approx 3\,\%` です。一部のスマートフォンなどで利用できるようになっています。
* **CHERI**\ （Capability Hardware Enhanced RISC Instructions）：ケンブリッジ大学と SRI International が研究している方式で、ポインタを、アドレスに加えて参照してよい範囲（境界）と権限を持つ\ **ケーパビリティ**\ （capability）に置き換えます。ケーパビリティは ISA のレベルで偽造できないように保護され、範囲外のアクセスはハードウェアが確実に止めます。Arm は CHERI を取り入れた試作プロセッサ Morello を開発し、RISC-V 向けの実装も進められています。
* 制御フローの保護：前述の ROP のように、戻りアドレスなどを書き換えて実行の流れを乗っ取る攻撃への対策として、Arm の PAC（Pointer Authentication：ポインタに暗号的な署名を付ける）と BTI（Branch Target Identification）、Intel の CET（Control-flow Enforcement Technology：戻りアドレスを別に保存するシャドウスタックなど）が導入されています。

これらはいずれも、「ポインタやメモリに追加の情報を持たせ、ハードウェアが毎回検査する」という考え方に基づいています。わずかな面積と性能を費やして、ソフトウェアの欠陥が悪用される前に止めようとするものです。

この章のまとめ
--------------

* 特権モード（RISC-V の M / S / U モード、x86-64 のリング、AArch64 の EL）とページ単位の保護ビット（R / W / X、U、NX など）が、ハードウェアによる保護の基本です。
* NX ビットによって W^X の方針が実現でき、コードインジェクションを防げます。ただし ROP のような攻撃には別の対策が必要です。
* キャッシュのヒットとミスの時間差は、ほかのプログラムのメモリアクセスを推測する手がかりになりえます（キャッシュタイミング攻撃）。ソフトウェアでの基本的な対策は定数時間プログラミングです。
* Spectre と Meltdown は、投機実行で取り消された命令の痕跡がキャッシュに残ることに起因します。ISA の仕様の外にあるマイクロアーキテクチャの状態も、セキュリティに影響することを示しました。
* KPTI、レトポリン、投機の制限、SMT の無効化などの対策は性能を犠牲にし、その影響は処理の性質によって大きく異なります。新しいプロセッサではハードウェアでの修正が進んでいます。
* Rowhammer は DRAM の行の頻繁な活性化が隣接する行のビットを反転させる現象です。リフレッシュの強化、ECC、TRR、DDR5 の RFM などで対処されています。
* ソフトエラーに対しては、パリティによる検出、ハミング符号による訂正、全体パリティを加えた SECDED（メモリでは (72,64) 符号）が使われます。
* 装置の冗長化（TMR、ロックステップ）や、大規模システムでのチェックポイント・リスタートも信頼性を高める手段です。部品が増えるほどシステムの MTTF は短くなります。
* TEE（Intel SGX / TDX、AMD SEV、Arm TrustZone / CCA）は、権限の高いソフトウェアからもデータを守る実行環境を提供します。
* Arm の MTE や CHERI は、メモリ安全性の欠陥をハードウェアで検出・防止する仕組みです。
