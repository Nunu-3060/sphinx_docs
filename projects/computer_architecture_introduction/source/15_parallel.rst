並列アーキテクチャ
==================

これまでの章では、1 つのプロセッサが 1 つの命令の流れをいかに速く実行するかを見てきました。「:doc:`11_ilp`」で説明した命令レベル並列性も、プログラムからは見えない形で並列に実行する工夫です。この章では、プログラマーが明示的に並列性を書き表し、複数の演算器やコアで同時に処理する\ **並列アーキテクチャ**\ （parallel architecture）を扱います。

まず、2000 年代半ばに並列化が避けられなくなった理由（電力の壁）を説明し、並列性の種類とフリンの分類を整理します。次に、1 命令で複数のデータを処理する SIMD 命令を見たあと、マルチコアプロセッサが共有メモリを正しく扱うための仕組みであるキャッシュコヒーレンス、メモリ一貫性モデル、アトミック命令を説明します。最後に、NUMA、アムダールの法則、分散メモリのクラスタに触れます。GPU は「:doc:`16_gpu`」で、専用のアクセラレーターは「:doc:`17_accelerators`」で詳しく扱います。

並列化が必要になった背景
------------------------

CMOS 回路の消費電力のうち、トランジスタがスイッチするときに消費する\ **動的電力**\ （dynamic power）は、次の式で表されます。

.. math::

   P_{\text{dynamic}} = \alpha \, C \, V^2 f

ここで :math:`\alpha` はスイッチする割合（活性化率）、:math:`C` は負荷容量、:math:`V` は電源電圧、:math:`f` はクロック周波数です。1970 年代から 2000 年代初めまでは、トランジスタを微細化すると寸法とともに電源電圧も下げられたので、面積あたりの消費電力（電力密度）をほぼ一定に保ったままクロック周波数を上げられました。これを\ **デナード・スケーリング**\ （Dennard scaling）と呼びます。

ところが、電源電圧を下げるとトランジスタのしきい値電圧も下げる必要があり、しきい値電圧を下げるとオフのときに流れる\ **リーク電流**\ （leakage current）が急に増えます。このため 2000 年代半ばには電圧をそれ以上下げられなくなり、デナード・スケーリングは終わりました。電圧が下がらないまま周波数を上げると、:math:`V^2 f` に比例して電力が増え、チップの冷却が追いつきません。これを\ **電力の壁**\ （power wall）と呼びます。実際に、デスクトップ向けプロセッサのクロック周波数は 2000 年代半ばに 3〜4 GHz 程度で伸びが止まりました。

一方で、ムーアの法則によるトランジスタ数の増加はその後も続きました。増えたトランジスタを 1 つのコアの高速化に使っても、「:doc:`11_ilp`」で見たように命令レベル並列性には限界があり、効果は小さくなっていました。そこで、増えたトランジスタを使って 1 つのチップに複数のコアを載せる\ **マルチコア**\ （multicore）プロセッサが主流になりました。

電圧と周波数を下げることの効果を数値で確かめます。電圧と周波数をともに 20% 下げると、動的電力は :math:`0.8^2 \times 0.8 = 0.512` 倍、つまり約半分になります。性能（周波数）は 0.8 倍です。そこで同じコアを 2 つ並べると、電力は :math:`2 \times 0.512 \approx 1.02` 倍とほぼ元のままで、並列に動く仕事に対しては :math:`2 \times 0.8 = 1.6` 倍の性能が得られます。ただし、この性能を引き出すには、ソフトウェアが仕事を並列に分割しなければなりません。電力の壁は、性能向上の責任の一部をハードウェアからソフトウェアに移したといえます。

並列性の種類
------------

プログラムに含まれる並列性は、大きく次の 2 つに分けられます。

* **データ並列性**\ （data parallelism）：多数のデータ要素に同じ処理を適用する並列性です。配列の各要素の加算、画像の各ピクセルの処理、行列積などが典型です。データの数に比例して並列度が大きくなるので、大規模な並列化に向いています。
* **タスク並列性**\ （task parallelism）：異なる処理を同時に実行する並列性です。Web サーバーが複数のリクエストを別々のスレッドで処理する場合や、パイプライン状に処理を分担する場合が該当します。

並列性を実行するハードウェアの側から見ると、次の階層があります。

.. list-table:: 並列性の階層と、それを利用するハードウェア
   :header-rows: 1
   :widths: 25 40 35

   * - 並列性
     - 内容
     - 主なハードウェア
   * - 命令レベル並列性（ILP）
     - 1 つの命令の流れの中の独立な命令を同時に実行します。
     - パイプライン、スーパースカラ、アウトオブオーダー実行
   * - データレベル並列性（DLP）
     - 1 命令で複数のデータ要素を処理します。
     - SIMD 命令、ベクトルプロセッサ、GPU
   * - スレッドレベル並列性（TLP）
     - 複数の命令の流れ（スレッド）を同時に実行します。
     - マルチコア、同時マルチスレッディング（SMT）
   * - リクエストレベル並列性
     - 独立した多数の要求を別々の計算機で処理します。
     - サーバーのクラスタ、データセンター

フリンの分類
------------

1966 年に Michael Flynn は、命令の流れ（instruction stream）とデータの流れ（data stream）がそれぞれ 1 つか複数かによって、計算機を 4 種類に分類しました。これを\ **フリンの分類**\ （Flynn's taxonomy）と呼びます。

.. list-table:: フリンの分類
   :header-rows: 1
   :widths: 15 25 30 30

   * - 分類
     - 命令の流れ／データの流れ
     - 説明
     - 例
   * - SISD
     - 単一／単一
     - 1 つの命令の流れが 1 つのデータを処理する、従来の逐次計算機です。
     - 単一コアのプロセッサ（ILP は内部で利用）
   * - SIMD
     - 単一／複数
     - 1 つの命令が複数のデータに同じ演算を適用します。
     - SIMD 命令、ベクトルプロセッサ（GPU もこれに近い）
   * - MISD
     - 複数／単一
     - 複数の命令の流れが 1 つのデータを処理します。
     - 実用例はほとんどありません（シストリックアレイや多重化した冗長系を当てはめる説もあります）。
   * - MIMD
     - 複数／複数
     - 独立した複数の命令の流れが、それぞれのデータを処理します。
     - マルチコア、マルチプロセッサ、クラスタ

現在の計算機の多くは MIMD であり、さらに各コアが SIMD 命令を持つという組み合わせになっています。GPU は SIMD の一種ですが、プログラムからはスレッドの集まりに見えるように工夫されており、これを SIMT と呼びます。SIMD と SIMT の違いは「:doc:`16_gpu`」で整理します。

SIMD 命令
---------

**SIMD 命令**\ は、幅の広いレジスタに複数のデータ要素を詰めて、1 命令でまとめて演算します。たとえば 256 ビットのレジスタには 32 ビットの単精度浮動小数点数が 8 個入るので、1 回の加算命令で 8 組の加算ができます。命令の取り出しやデコードの手間は 1 命令分なので、演算あたりの電力と命令数を減らせます。

主な SIMD 命令セットを次の表にまとめます。

.. list-table:: 主な SIMD 命令セット
   :header-rows: 1
   :widths: 20 15 20 45

   * - 名前
     - ISA
     - レジスタ幅
     - 特徴
   * - SSE（1999 年〜）
     - x86
     - 128 ビット
     - Pentium III で導入。単精度 4 個を同時に処理します。SSE2 で倍精度と整数に拡張されました。
   * - AVX、AVX2（2011 年〜）
     - x86-64
     - 256 ビット
     - 3 オペランド形式を導入。AVX2 で整数演算も 256 ビットになり、FMA（積和演算）命令も同じ時期に加わりました。
   * - AVX-512
     - x86-64
     - 512 ビット
     - 32 本の 512 ビットレジスタと、要素ごとの演算の有無を指定するマスクレジスタ（k0〜k7）を持ちます。
   * - NEON（Advanced SIMD）
     - Arm（Armv7-A、AArch64）
     - 128 ビット
     - スマートフォン向けプロセッサで広く使われます。
   * - SVE、SVE2
     - AArch64
     - 128〜2048 ビット（実装で決定）
     - ベクトル長に依存しないプログラムを書けます。スーパーコンピューター「富岳」の A64FX が最初の実装。
   * - V 拡張（RVV）
     - RISC-V
     - 実装で決定（VLEN）
     - ベクトル長に依存しない設計。仕様 1.0 は 2021 年に承認されました。

x86 の SIMD は、新しい世代のたびにレジスタ幅が倍になり、そのたびに新しい命令が追加されてきました。この方式では、幅の広い命令を使うためにプログラムを作り直す必要があります。これに対し、SVE や RISC-V の V 拡張は、ベクトルの長さをハードウェアの実装に任せ、同じ機械語のプログラムが 128 ビットの実装でも 512 ビットの実装でも動くように設計されています。これは 1970 年代の Cray-1 などのベクトルプロセッサの考え方を受け継いだものです。

自動ベクトル化
^^^^^^^^^^^^^^

SIMD 命令は、組み込み関数（intrinsics）やアセンブリで直接書くこともできますが、多くの場合はコンパイラが通常のループを SIMD 命令に変換します。これを\ **自動ベクトル化**\ （auto-vectorization）と呼びます。次の C の関数を考えます。

.. code-block:: c
   :linenos:

   void vadd(float *restrict c, const float *restrict a,
             const float *restrict b, int n)
   {
       for (int i = 0; i < n; i++) {
           c[i] = a[i] + b[i];
       }
   }

GCC や Clang で最適化（``-O3``\ 。GCC 12 以降と Clang では ``-O2`` でも自動ベクトル化が有効）を指定し、x86-64 で AVX2 を使う指定（``-mavx2``\ ）をすると、ループの本体は 256 ビットのロード命令 ``vmovups``\ 、加算命令 ``vaddps``\ 、ストア命令 ``vmovups`` の組になり、1 回の繰り返しで 8 要素を処理します。要素数が 8 の倍数でない場合の残りは、通常のスカラー命令で処理するコードが付け加えられます。

1〜2 行目の ``restrict`` は、配列 ``c`` と ``a``\ 、``b`` が重ならないことをコンパイラに約束するものです。重なっている可能性があると、``c[i]`` への書き込みが後の ``a[i+1]`` の読み出しに影響するかもしれないので、コンパイラは安全のためベクトル化を控えたり、実行時に重なりを調べるコードを追加したりします。ループの繰り返しの間に依存関係があるもの（たとえば ``a[i] = a[i-1] + b[i]``\ ）は、そのままではベクトル化できません。

RISC-V の V 拡張では、同じループを次のように書けます。``vsetvli`` 命令が「残りの要素数」と「ハードウェアが一度に処理できる要素数」の小さいほうを ``t0`` に設定するので、ベクトル長が異なる実装でも同じプログラムが動き、端数処理も不要です。

.. code-block:: text
   :linenos:

   # a0 = c, a1 = a, a2 = b, a3 = n（要素数）
   loop:
       vsetvli  t0, a3, e32, m1, ta, ma  # 今回処理する要素数 t0 を決める
       vle32.v  v0, (a1)                 # a から t0 要素をロード
       vle32.v  v1, (a2)                 # b から t0 要素をロード
       vfadd.vv v2, v0, v1               # 要素ごとに加算
       vse32.v  v2, (a0)                 # c にストア
       sub      a3, a3, t0               # 残りの要素数を減らす
       slli     t1, t0, 2                # 進めるバイト数 = t0 * 4
       add      a1, a1, t1
       add      a2, a2, t1
       add      a0, a0, t1
       bnez     a3, loop

3 行目の ``e32`` は要素が 32 ビットであること、``m1`` はベクトルレジスタを 1 本ずつ使うことを表します。このように、ハードウェアの幅に合わせてループを区切って処理する方法を\ **ストリップマイニング**\ （strip mining）と呼びます。

マルチコアと共有メモリ
----------------------

マルチコアプロセッサでは、各コアが独立した命令の流れ（スレッド）を実行します。各コアは通常、自分専用の L1 キャッシュと L2 キャッシュを持ち、L3 キャッシュと主記憶をほかのコアと共有します。すべてのコアが同じアドレス空間を読み書きできる構成を\ **共有メモリ型マルチプロセッサ**\ （shared-memory multiprocessor）と呼びます。プログラマーから見ると、スレッド間でデータを受け渡すにはメモリに書いて読むだけでよいので、プログラムを書きやすい方式です。

主記憶へのアクセス時間がどのコアからも同じものを **UMA**\ （Uniform Memory Access）、コアによって異なるものを **NUMA**\ （Non-Uniform Memory Access）と呼びます。NUMA については後の節で説明します。

共有メモリを正しく、かつ高速に動かすには、次の 3 つの問題を解決する必要があります。

* キャッシュコヒーレンス：あるコアが書き込んだ値を、別のコアのキャッシュに残った古いコピーが隠してしまわないようにすること。
* メモリ一貫性：異なるアドレスへの読み書きが、ほかのコアからどの順序で見えるかを定めること。
* 同期：複数のコアが同じデータを不可分に（途中で割り込まれずに）更新できるようにすること。

以下では、この順に説明します。

キャッシュコヒーレンス
----------------------

問題の例
^^^^^^^^

「:doc:`12_memory_hierarchy`」で説明したキャッシュは、主記憶のデータのコピーを持ちます。コアが 1 つなら問題はありませんが、複数のコアがそれぞれのキャッシュに同じアドレスのコピーを持つと、次のような不整合が起きます。ここではライトバック方式のキャッシュを仮定し、変数 ``x`` の初期値を 0 とします。

.. list-table:: キャッシュの不整合の例
   :header-rows: 1
   :widths: 10 40 15 15 20

   * - 時刻
     - 出来事
     - コア 0 のキャッシュ
     - コア 1 のキャッシュ
     - 主記憶
   * - 1
     - コア 0 が ``x`` を読みます。
     - 0
     - なし
     - 0
   * - 2
     - コア 1 が ``x`` を読みます。
     - 0
     - 0
     - 0
   * - 3
     - コア 0 が ``x = 1`` を書きます。
     - 1
     - 0
     - 0
   * - 4
     - コア 1 が ``x`` を読みます。
     - 1
     - **0（古い値）**
     - 0

時刻 4 でコア 1 は、コア 0 がすでに書き換えた後なのに古い値 0 を読んでしまいます。ライトスルー方式にして主記憶を更新しても、コア 1 のキャッシュに残ったコピーは古いままなので、問題は解決しません。

複数のキャッシュがあっても、プログラムからは 1 つのメモリしかないように見えることを\ **キャッシュコヒーレンス**\ （cache coherence）と呼びます。正確には、次の 2 つの条件が成り立つことです。

* 1 つのアドレスへの書き込みが、いずれすべてのコアから見えるようになること（書き込みの伝播）。
* 1 つのアドレスへの複数の書き込みが、すべてのコアから同じ順序で見えること（書き込みの直列化）。

コヒーレンスを保つ代表的な方法は、ほかのコアが持つコピーを書き込みの前に無効にする\ **無効化型**\ （write-invalidate）のプロトコルです。これを実現する方式には、スヌープ方式とディレクトリ方式があります。

スヌープ方式
^^^^^^^^^^^^

**スヌープ方式**\ （snooping）では、すべてのキャッシュが共有バスにつながっており、各キャッシュのコントローラは、ほかのコアがバスに出す要求を常に監視（スヌープ）します。あるコアがキャッシュラインに書き込むときは、バスに無効化の要求を出し、同じラインのコピーを持つほかのキャッシュはそれを見て自分のコピーを無効にします。バスは一度に 1 つの要求しか運べないので、すべてのコアが要求を同じ順序で観測でき、書き込みの直列化が自然に実現されます。

最も単純なプロトコルは、各キャッシュラインに次の 3 つの状態を持たせる **MSI プロトコル**\ です。

* **M**\ （Modified）：このキャッシュだけが持ち、主記憶より新しい値に書き換えられた状態。
* **S**\ （Shared）：主記憶と同じ値を持ち、ほかのキャッシュも同じラインを持っている可能性がある状態。
* **I**\ （Invalid）：このラインを持っていない（無効な）状態。

MSI では、ほかのコアが持っていないデータを読んだ場合も S になるので、その後に書き込むと、誰も持っていないのに無効化の要求をバスに出さなければなりません。スレッドの私有データでは「読んでから書く」が頻繁に起こるので、これは無駄です。そこで、「自分だけが持っていて、まだ書き換えていない」状態 **E**\ （Exclusive）を加えたものが **MESI プロトコル**\ です。E の状態のラインには、バスを使わずに書き込めます。MESI は 1984 年に Papamarcos と Patel が提案したことから、イリノイプロトコルとも呼ばれます。

ディレクトリ方式
^^^^^^^^^^^^^^^^

スヌープ方式では、すべての要求をすべてのキャッシュに知らせる必要があります。コアが数個のうちはよいのですが、コア数が増えるとバスの帯域と、各キャッシュがスヌープを処理する負担が問題になります。そこで、多数のコアを持つシステムでは\ **ディレクトリ方式**\ （directory-based）が使われます。

ディレクトリ方式では、キャッシュラインごとに「どのコアがコピーを持っているか」と「状態」を記録した\ **ディレクトリ**\ を用意します。コアはラインが必要になると、そのラインを管理するディレクトリ（ホームノード）に要求を送り、ディレクトリはコピーを持っているコアにだけ無効化やデータの転送を依頼します。要求を全員に知らせる必要がないので、リングやメッシュなど、バス以外の相互接続網でも使えます。

最も単純なディレクトリは、ラインごとにコア数と同じビット数の\ **存在ビットベクトル**\ （presence bit vector）を持ちます。64 コアで 64 バイト（512 ビット）のラインなら、ラインごとに 64 ビットが必要で、記憶容量のオーバーヘッドは :math:`64 / 512 = 12.5\%` になります。コア数が増えるとこのオーバーヘッドも比例して増えるので、実際には、コピーを持つコアが少数であることを利用して記録を圧縮するなどの工夫が使われます。現在のサーバー向けプロセッサでは、チップ内部はディレクトリやスヌープフィルタ（どのコアがラインを持ち得るかを記録してスヌープを絞り込む仕組み）を使い、メッシュ状の相互接続網でコアをつないでいます。

MESI シミュレーター
^^^^^^^^^^^^^^^^^^^

サンプル :download:`mesi_sim.py <../examples/mesi_sim.py>` は、共有バスでつながった複数のコアの MESI プロトコルをシミュレーションします。読み書きの列を与えると、各コアのキャッシュラインの状態とバスの動作を表示します。

.. literalinclude:: ../examples/mesi_sim.py
   :language: python
   :linenos:
   :caption: mesi_sim.py

要点は次のとおりです。

* 24 行目：各コアのキャッシュを「ライン番号から状態への辞書」で表します。キャッシュの容量は無限とし、追い出しは考えません。
* 36〜46 行目：読み出しです。ラインを持っていれば（M、E、S なら）ヒットです。持っていなければ BusRd を出し、ほかのコアが M で持っていれば書き戻し（Flush）をさせます。ほかのコアのコピーは S になり、自分は、ほかに持つコアがいなければ E、いれば S になります。
* 47〜60 行目：書き込みです。M か E ならバスを使わずに M になります。S なら BusUpgr、I なら BusRdX を出し、ほかのコアのコピーをすべて無効にして、無効化の回数を数えます。
* 80〜87 行目：false sharing の実験です（後の節で説明します）。2 つのコアが交互に、自分の変数を読んで書く（``x += 1``\ ）操作を繰り返します。

実行結果は次のとおりです。

.. code-block:: text
   :linenos:

   === 3 コアでの状態遷移（アドレス 0〜63 はライン 0）===
   手順 操作       バスの動作            C0 C1 C2
     1  C0 R    0  BusRd                 E  I  I
     2  C0 W    0  hit                   M  I  I
     3  C1 R    8  BusRd + Flush(C0)     S  S  I
     4  C2 R   16  BusRd                 S  S  S
     5  C2 W   16  BusUpgr               I  I  M
     6  C0 R    0  BusRd + Flush(C2)     S  I  S
     7  C1 W    8  BusRdX                I  M  I
     8  C1 R    8  hit                   I  M  I
   バストランザクション 6 回、無効化 4 回

   === false sharing の比較（各コアが 1000 回ずつ x += 1）===
   同じライン（0 と 8）: バストランザクション  3999 回、無効化  1999 回
   別のライン（0 と 64）: バストランザクション     2 回、無効化     0 回

手順 1 でコア 0 は、ほかに誰も持っていないラインを読んだので E になり、手順 2 の書き込みはバスを使わずに M になります。MSI ならここで無効化の要求が必要でした。手順 3 でコア 1 が読むと、コア 0 は最新の値を書き戻して S に変わります。手順 5 でコア 2 が書くと、コア 0 と 1 のコピーが無効になります。手順 6 と 7 のように、異なるコアが同じラインを交互に読み書きすると、そのたびにバストランザクションが発生します。この結果の後半については、次の節で説明します。

false sharing
-------------

コヒーレンスはキャッシュライン単位で管理されます。このため、2 つのコアが同じキャッシュラインに載った\ **別々の変数**\ を書き換えると、データとしては共有していないのに、ラインがコアの間を行き来して無効化が繰り返されます。これを **false sharing**\ （偽共有）と呼びます。

次の例では、2 つのスレッドがそれぞれ自分のカウンタを増やします。``a`` と ``b`` は 8 バイトずつ隣り合っているので、64 バイトのキャッシュラインに一緒に載ります。

.. code-block:: c
   :linenos:

   struct counters {
       long a;   /* スレッド 0 だけが使う */
       long b;   /* スレッド 1 だけが使う */
   };
   struct counters cnt;   /* a と b は同じキャッシュラインに載る */

   void *worker0(void *arg) {
       for (long i = 0; i < 100000000; i++) cnt.a++;
       return NULL;
   }
   void *worker1(void *arg) {
       for (long i = 0; i < 100000000; i++) cnt.b++;
       return NULL;
   }

論理的には 2 つのスレッドは何も共有していませんが、``cnt.a++`` のたびにコア 0 はラインを M にするためにコア 1 のコピーを無効にし、``cnt.b++`` のたびに逆のことが起きます。上の MESI シミュレーターの後半の結果では、同じラインに置くと 1000 回ずつの更新で無効化が 1999 回、バストランザクションが 3999 回発生したのに対し、別のラインに置くと最初の 2 回の BusRd だけで、無効化は 0 回でした。実際のマルチコアプロセッサでも、false sharing があると、それぞれのスレッドを単独で動かす場合より何倍も遅くなることがあります。

対策は、別々のスレッドが書き換える変数を別のキャッシュラインに置くことです。C11 では ``_Alignas`` を使って、メンバをキャッシュラインの境界に合わせられます。

.. code-block:: c
   :linenos:

   struct padded_counter {
       _Alignas(64) long value;   /* 64 バイト境界に置く */
   };                             /* 構造体の大きさも 64 バイトになる */
   struct padded_counter cnt[2];  /* cnt[0] と cnt[1] は別のラインに載る */

   /* スレッド t は cnt[t].value だけを更新する */

2 行目の指定によって、構造体の大きさが 64 バイトに切り上げられ、配列の各要素が別のキャッシュラインに載ります。これを\ **パディング**\ （padding）と呼びます。メモリは余分に使いますが、頻繁に書き換える変数に対しては効果があります。キャッシュラインの大きさはプロセッサによって異なり（64 バイトが多いが、128 バイトのものもある）、C++17 にはこの目安を表す ``std::hardware_destructive_interference_size`` が用意されています。さらに根本的な対策は、各スレッドがローカル変数で集計し、最後に 1 回だけ共有の変数に書き込むことです。

メモリ一貫性モデル
------------------

キャッシュコヒーレンスは、1 つのアドレスへの読み書きの順序を保証します。しかし、異なるアドレスへの読み書きが、ほかのコアからどの順序で見えるかは別の問題です。これを定めるのが\ **メモリ一貫性モデル**\ （memory consistency model）です。

逐次一貫性
^^^^^^^^^^

最も直観的なモデルは、1979 年に Leslie Lamport が定義した\ **逐次一貫性**\ （sequential consistency：SC）です。逐次一貫性では、すべてのコアのメモリ操作が、何らかの 1 つの順序に並べられ、その順序の中で各コアの操作はプログラムに書かれた順に現れます。つまり、各コアの操作を、順序を保ったまま交互に混ぜ合わせた結果と同じになります。

次の例を考えます。``x`` と ``y`` は共有変数で、初期値はどちらも 0 です。これは、相互排除のための Dekker のアルゴリズムの核心部分（自分の旗を立ててから相手の旗を見る）を取り出したものです。

.. code-block:: c
   :linenos:

   /* 初期値: x = 0, y = 0 */

   /* スレッド 0 */          /* スレッド 1 */
   x = 1;                     y = 1;
   r0 = y;                    r1 = x;

逐次一貫性のもとでは、``r0 == 0 && r1 == 0`` という結果はあり得ません。どちらかのスレッドの書き込みが先に起きるので、後から読む側は必ず 1 を読むからです。Dekker のアルゴリズムは、この性質を利用して 2 つのスレッドが同時に臨界区間に入らないようにしています。

TSO
^^^

しかし、逐次一貫性を厳密に守ると、ハードウェアの最適化の多くが使えなくなります。特に重要なのが\ **ストアバッファ**\ （store buffer）です。ストアはキャッシュに書き込むまで時間がかかることがあるので、プロセッサはストアをいったんストアバッファに入れ、完了を待たずに後続の命令を実行します。すると、上の例では、スレッド 0 の ``x = 1`` がまだストアバッファにある間に ``r0 = y`` が実行され、0 を読むことがあります。スレッド 1 でも同じことが起きると、``r0 == 0 && r1 == 0`` という逐次一貫性ではあり得ない結果になります。

x86 のメモリモデルは、このストアバッファの効果だけを許したモデルで、\ **TSO**\ （Total Store Order）と呼ばれます。TSO では「先行するストアと、後続の別のアドレスへのロード」の順序の入れ替わりだけが見えることがあり、ストア同士、ロード同士、ロードと後続のストアの順序は保たれます（自分のコアのストアは、ストアバッファから先に読むことができます）。SPARC も TSO を採用していました。

弱いメモリモデル
^^^^^^^^^^^^^^^^

Arm（AArch64）と RISC-V は、さらに多くの入れ替えを許す\ **弱いメモリモデル**\ （weak memory model、relaxed memory model）を採用しています。依存関係のない異なるアドレスへのロードとストアは、基本的にどの組み合わせでも順序が入れ替わって見えることがあります。RISC-V のメモリモデルは **RVWMO**\ （RISC-V Weak Memory Ordering）と呼ばれます。弱いモデルではハードウェアの自由度が大きく、性能や電力の面で有利ですが、順序が必要な箇所はプログラムで明示しなければなりません。

メモリバリア
^^^^^^^^^^^^

順序を強制するための命令を\ **メモリバリア**\ （memory barrier）または\ **フェンス**\ （fence）と呼びます。上の例では、ストアとロードの間にフェンスを入れると、``r0 == 0 && r1 == 0`` という結果は起きなくなります。

.. list-table:: 主なメモリバリア命令
   :header-rows: 1
   :widths: 20 30 50

   * - ISA
     - 命令の例
     - 説明
   * - x86-64
     - ``mfence``\ 、\ ``lock`` 付きの命令
     - 先行するロードとストアがすべて完了してから後続を実行します。
   * - AArch64
     - ``dmb ish``\ 、\ ``ldar``\ 、\ ``stlr``
     - ``dmb`` は前後のメモリ操作の順序を保証します。\ ``ldar``\ （獲得）と ``stlr``\ （解放）は、片方向の順序だけを保証する軽いロード・ストア。
   * - RISC-V
     - ``fence rw, rw``
     - 前の読み書き（rw）が、後の読み書き（rw）より先に完了したように見えることを保証します。前後の種類を指定できます。

ただし、通常のプログラムでメモリバリアを直接書くことはまれです。C11 や C++11 の ``atomic`` 型、または pthread のミューテックスなどの同期機構を使えば、コンパイラとライブラリが ISA に応じた適切な命令を出力します。たとえば C11 の ``atomic_store`` と ``atomic_load`` は、既定の ``memory_order_seq_cst`` を使う限り、プログラムからは逐次一貫性があるように見えます。弱いメモリモデルの ISA に移植したときにだけ現れる不具合を避けるためにも、共有変数には必ずこうした仕組みを使うことが大切です。

アトミック命令
--------------

ロック（ミューテックス）やカウンタなどの同期機構を作るには、「読んで、変更して、書く」という一連の操作を、ほかのコアに割り込まれずに不可分に行う\ **アトミック命令**\ （atomic instruction）が必要です。通常のロード、加算、ストアの 3 命令で ``counter++`` を実行すると、2 つのコアが同じ値を読んでしまい、更新が 1 回分失われることがあります。

主な方式は次の 2 つです。

**CAS**\ （Compare-And-Swap）
   メモリの値が期待値と等しいときだけ新しい値を書き込み、等しくなければ何もしない、という操作を不可分に行います。x86-64 の ``lock cmpxchg`` や、AArch64 の ``cas``\ （Armv8.1 の LSE 拡張）がこれに当たります。CAS を使うと、値を読んで新しい値を計算し、CAS で書き込み、失敗したらやり直す、という形で任意の更新を不可分に行えます。

**LL/SC**\ （Load-Linked / Store-Conditional）
   LL 命令でメモリを読むと同時に、そのアドレスを「予約」します。その後 SC 命令で書き込むとき、予約してから誰もそのアドレスに書き込んでいなければ書き込みに成功し、書き込まれていれば失敗します。割り込みやコンテキストスイッチなどで予約が失われた場合にも失敗することがあるので、SC が失敗したら LL からやり直すループとして使います。予約の監視には、キャッシュコヒーレンスの無効化の通知が利用されます。AArch64 の ``ldxr``/``stxr``\ 、RISC-V の ``lr``/``sc`` がこの方式です。CAS には「値が A から B に変わって A に戻った」ことを検出できない ABA 問題がありますが、LL/SC は書き込みの有無を見るので、この問題が起きません。

RISC-V の A 拡張
^^^^^^^^^^^^^^^^

RISC-V では、アトミック命令は **A 拡張**\ （Atomic extension）で定義されています。A 拡張には LL/SC 型の ``lr.w``/``sc.w`` と、加算や交換などをメモリ上で不可分に行う AMO（Atomic Memory Operation）命令があります。次は ``lr.w``/``sc.w`` を使って CAS を実現する例です。

.. code-block:: text
   :linenos:

   # a0 = アドレス, a1 = 期待値, a2 = 新しい値
   # 成功したら a0 = 0、失敗したら a0 = 1 を返す
   cas:
       lr.w    t0, (a0)        # 値を読み、アドレスを予約する
       bne     t0, a1, fail    # 期待値と違えば失敗
       sc.w    t1, a2, (a0)    # 予約が有効なら書き込む（成功で t1 = 0）
       bnez    t1, cas         # 書き込みに失敗したら最初からやり直す
       li      a0, 0
       ret
   fail:
       li      a0, 1
       ret

カウンタを増やすだけなら、AMO 命令を使って 1 命令で書けます。

.. code-block:: text
   :linenos:

   # a0 = カウンタのアドレス
   li        t0, 1
   amoadd.w  t1, t0, (a0)   # (a0) に t0 を不可分に加え、元の値を t1 に返す

AMO 命令には ``.aq``\ （acquire）や ``.rl``\ （release）の指定を付けられ、前後のメモリ操作との順序を同時に指定できます。たとえば ``amoswap.w.aq`` はロックの獲得に、``amoswap.w.rl`` や ``sw`` の前の ``fence`` はロックの解放に使われます。

アトミック命令は便利ですが、高価な操作です。多数のコアが 1 つのカウンタに ``amoadd`` を繰り返すと、そのキャッシュラインがコアの間を行き来し続けます。本当にデータを共有している（true sharing）点は異なりますが、false sharing と同じように無効化とラインの転送が繰り返されます。並列プログラムでは、共有データへの書き込みの頻度そのものを減らすことが重要です。

NUMA
----

コア数が多いサーバーでは、1 つのメモリコントローラですべてのコアのメモリ帯域をまかなうことができません。そこで、複数のプロセッサチップ（ソケット）がそれぞれのメモリコントローラと主記憶を持ち、チップ間を高速なリンクでつなぎます。各コアから見ると、自分のチップにつながった\ **ローカルメモリ**\ は速く、ほかのチップにつながった\ **リモートメモリ**\ はリンクを経由するので遅くなります。これが **NUMA**\ （Non-Uniform Memory Access）です。キャッシュコヒーレンスを保ったまま NUMA を構成するものを **ccNUMA**\ （cache-coherent NUMA）と呼び、現在のマルチソケットのサーバーはほぼすべてこの方式です。

.. graphviz::
   :caption: 2 ソケットの NUMA 構成
   :align: center

   digraph numa {
     rankdir=LR;
     node [shape=box, fontsize=11];
     subgraph cluster0 {
       label="ノード 0"; style=rounded;
       c0 [label="コア群 + キャッシュ"];
       m0 [label="主記憶 0\n（ローカル）"];
       c0 -> m0 [dir=both];
     }
     subgraph cluster1 {
       label="ノード 1"; style=rounded;
       c1 [label="コア群 + キャッシュ"];
       m1 [label="主記憶 1\n（ローカル）"];
       c1 -> m1 [dir=both];
     }
     c0 -> c1 [dir=both, label="ソケット間リンク", fontsize=10];
   }

リモートメモリへのアクセスは、ローカルメモリに比べて、レイテンシが 1.5〜2 倍程度になるのが目安です（構成によって異なります）。そこで OS は、スレッドが最初に書き込んだページを、そのスレッドが動いているノードのメモリに割り当てる\ **ファーストタッチ**\ （first touch）方式などで、データをなるべくローカルに置こうとします。プログラムの側でも、データを初期化するスレッドと使うスレッドを同じノードに置く、スレッドをコアに固定するなどの工夫が性能に影響します。最近では、1 つのソケットの中でも複数のチップレットやメモリコントローラがあり、NUMA の性質を持つプロセッサもあります。

アムダールの法則の再確認
------------------------

「:doc:`04_performance`」で説明したアムダールの法則を、並列化の観点から確認します。プログラムのうち並列化できる部分の割合を :math:`p`\ 、コア数を :math:`n` とすると、速度向上率は次のとおりです。

.. math::

   S(n) = \frac{1}{(1 - p) + \dfrac{p}{n}}

たとえば :math:`p = 0.95`\ （95% が並列化できる）とすると、64 コアでの速度向上率は :math:`1 / (0.05 + 0.95/64) \approx 15.4` 倍にとどまり、コアをいくら増やしても :math:`1/0.05 = 20` 倍を超えられません。並列化できない 5% の部分が全体の性能を決めてしまうのです。

実際の並列プログラムでは、さらに次のようなオーバーヘッドが加わり、速度向上率はアムダールの法則の値より小さくなります。

* スレッドの生成や仕事の分配にかかる時間
* ロックやバリアなどの同期の待ち時間
* キャッシュコヒーレンスによる通信（true sharing と false sharing）
* 仕事の量がスレッド間で偏ること（負荷の不均衡）
* メモリ帯域の不足（コアを増やしても主記憶の帯域は増えない）

一方、1988 年に John Gustafson は、コア数が増えると人々はより大きな問題を解こうとするので、問題の大きさをコア数に合わせて大きくすれば並列化の効果は大きくなる、と指摘しました。これを\ **グスタフソンの法則**\ （Gustafson's law）と呼びます。並列化できない部分の時間が問題の大きさに依存しないなら、コア数 :math:`n` での速度向上率は、並列実行時の逐次部分の時間の割合を :math:`s` として :math:`s + (1 - s)\,n` になります。アムダールの法則は問題の大きさを固定した場合（強スケーリング）、グスタフソンの法則は 1 コアあたりの仕事量を固定した場合（弱スケーリング）の見方です。

分散メモリとクラスタ
--------------------

共有メモリ型の構成は、コヒーレンスを保つための通信量が増えるため、数百コア程度より大きくするのは困難です。それ以上の規模では、それぞれが独自の主記憶を持つ計算機（ノード）を高速なネットワークでつないだ\ **分散メモリ型**\ （distributed memory）の構成が使われます。このような計算機の集まりを\ **クラスタ**\ （cluster）と呼びます。

分散メモリ型では、ほかのノードのメモリを直接読み書きできないので、データはネットワークを通じたメッセージで明示的に送受信します。科学技術計算では、そのための標準的なライブラリとして **MPI**\ （Message Passing Interface）が使われます。ノード間の通信には InfiniBand や高速な Ethernet が使われ、通信のレイテンシは同じノード内のメモリアクセスより桁違いに大きいので、通信を減らし、計算と重ね合わせることが性能の鍵になります。

現在のスーパーコンピューターは、多数のノードをつないだクラスタであり、各ノードはマルチコアの CPU と、多くの場合 GPU を備えています。つまり、ノード内では共有メモリ型の並列化と SIMD や GPU によるデータ並列化を、ノード間ではメッセージによる並列化を組み合わせる、階層的な並列性が使われています。

この章のまとめ
--------------

* デナード・スケーリングが 2000 年代半ばに終わり、消費電力の制約（電力の壁）からクロック周波数を上げられなくなったため、増えたトランジスタはマルチコアや SIMD などの並列化に使われるようになりました。
* 並列性にはデータ並列性とタスク並列性があり、ハードウェアは ILP、DLP、TLP、リクエストレベル並列性の階層でこれを利用します。フリンの分類では、現在の計算機の多くは各コアが SIMD 命令を持つ MIMD です。
* SIMD 命令は 1 命令で複数の要素を処理します。x86 の SSE、AVX、AVX-512 は世代ごとに幅が増え、SVE や RISC-V の V 拡張はベクトル長に依存しないプログラムを書けます。コンパイラの自動ベクトル化には ``restrict`` などで依存関係がないことを示すことが有効です。
* キャッシュコヒーレンスは、複数のキャッシュがあっても 1 つのメモリのように見せる仕組みです。スヌープ方式の MESI プロトコルでは、書き込みの前にほかのコピーを無効化します。大規模なシステムではディレクトリ方式が使われます。
* コヒーレンスはライン単位で管理されるため、別々の変数が同じラインに載ると false sharing が起き、性能が大きく低下します。パディングで別のラインに分けるのが対策です。
* メモリ一貫性モデルは、異なるアドレスへの操作の見える順序を定めます。逐次一貫性、x86 の TSO、Arm や RISC-V の弱いモデルがあり、順序が必要な箇所ではメモリバリアや言語のアトミック型を使います。
* 同期には CAS や LL/SC などのアトミック命令を使います。RISC-V の A 拡張は ``lr.w``/``sc.w`` と ``amoadd.w`` などの AMO 命令を提供します。
* 大規模なサーバーは NUMA 構成で、データの配置が性能に影響します。並列化の効果はアムダールの法則で制限され、さらに大規模な計算は MPI を使う分散メモリ型のクラスタで行います。
