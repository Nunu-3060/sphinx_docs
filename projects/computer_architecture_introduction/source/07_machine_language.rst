機械語とプログラム
==================

「:doc:`06_isa`」では、ISA が定める命令とその形式を見ました。この章では、C 言語などの高水準言語で書いたプログラムが、どのような命令列に変換されて実行されるのかを具体的に見ていきます。if 文、for ループ、配列、関数呼び出しが RISC-V の命令でどう表現されるかを確かめたあと、関数呼び出しを支えるスタックと呼び出し規約、プログラムを実行可能にするアセンブラ・リンカ・ローダの役割を説明します。

最後に、コンパイラの最適化がアーキテクチャとどう関係するかを紹介し、実際にコンパイラの出力を確かめる方法を説明します。この章のアセンブリはコンパイラが出力する典型的な形を、読みやすいように手で整えたものです。実際の出力は、コンパイラの種類、バージョン、最適化オプションによって変わります。

C のプログラムと命令列
----------------------

以下の例では、RISC-V の呼び出し規約（後述）に従い、関数の引数はレジスタ a0、a1、…で受け取り、戻り値は a0 で返します。t0、t1 などは一時的な値を置くレジスタです。

if 文
^^^^^

2 つの整数の大きい方を返す関数を考えます。

.. code-block:: c
   :linenos:

   int max(int a, int b) {
       if (a > b)
           return a;
       return b;
   }

.. code-block:: text
   :linenos:

   max:                    # a0 = a、a1 = b
       blt  a1, a0, .L1    # b < a（つまり a > b）なら .L1 へ
       mv   a0, a1         # 戻り値を b にする
   .L1:
       ret                 # a0 を戻り値として呼び出し元へ戻る

if 文は条件分岐命令になります。RISC-V には「より大きい」で分岐する命令がないので、オペランドを入れ替えて blt（より小さい）で表しています。a > b のときは、a0 にすでに a が入っているので何もせずに戻ります。このように、コンパイラは条件を反転したり入れ替えたりして、分岐の数が少なくなるように命令を並べます。

for ループと配列アクセス
^^^^^^^^^^^^^^^^^^^^^^^^

配列の要素の合計を求める関数です。

.. code-block:: c
   :linenos:

   int sum(const int *a, int n) {
       int s = 0;
       for (int i = 0; i < n; i++)
           s += a[i];
       return s;
   }

C のコードを素直に命令に置き換えると、次のようになります。

.. code-block:: text
   :linenos:

   sum:                    # a0 = a（配列の先頭アドレス）、a1 = n
       li   t0, 0          # s = 0
       li   t1, 0          # i = 0
   .Lloop:
       bge  t1, a1, .Ldone # i >= n ならループを抜ける
       slli t2, t1, 2      # t2 = i * 4（int は 4 バイト）
       add  t2, a0, t2     # t2 = &a[i]
       lw   t3, 0(t2)      # t3 = a[i]
       add  t0, t0, t3     # s += a[i]
       addi t1, t1, 1      # i++
       j    .Lloop
   .Ldone:
       mv   a0, t0         # 戻り値は s
       ret

配列の要素 ``a[i]`` のアドレスは「先頭アドレス + i × 要素の大きさ」です。int は 4 バイトなので、2 ビットの左シフト（slli）で 4 倍してから先頭アドレスに足しています（6〜7 行目）。RISC-V のロード命令は「ベース + 定数の変位」しか指定できないので、インデックスの計算は別の命令で行います。

このループは 1 回の繰り返しで 7 命令を実行します。n = 1000 なら約 7000 命令です。後の「コンパイラの最適化とアーキテクチャ」で、最適化によってこれがどこまで減るかを見ます。

関数呼び出し
^^^^^^^^^^^^

別の関数を呼び出す関数の例です。乗算命令 mul を使うので、ここでは M 拡張を含む RV32IM を想定します。

.. code-block:: c
   :linenos:

   int square(int x) {
       return x * x;
   }

   int sum_of_squares(int a, int b) {
       return square(a) + square(b);
   }

.. code-block:: text
   :linenos:

   square:
       mul  a0, a0, a0     # a0 = x * x
       ret

   sum_of_squares:         # a0 = a、a1 = b
       addi sp, sp, -16    # スタックフレームを確保する
       sw   ra, 12(sp)     # 戻りアドレスを保存する
       sw   s0, 8(sp)      # s0、s1 を使うので元の値を保存する
       sw   s1, 4(sp)
       mv   s0, a1         # b を s0 に退避する（呼び出しで a1 は壊れうる）
       call square         # a0 = square(a)
       mv   s1, a0         # 結果を s1 に退避する
       mv   a0, s0
       call square         # a0 = square(b)
       add  a0, s1, a0     # square(a) + square(b)
       lw   ra, 12(sp)     # 保存した値を復元する
       lw   s0, 8(sp)
       lw   s1, 4(sp)
       addi sp, sp, 16     # スタックフレームを解放する
       ret

square のように他の関数を呼ばない関数（\ **葉関数**\ 、leaf function）は、スタックを使わずに済むことが多く、2 命令で終わります。一方、sum_of_squares は他の関数を呼ぶので、次の 2 つの理由からスタックに値を保存しています。

* call は戻りアドレスを ra に書き込むので、sum_of_squares 自身の戻りアドレスが上書きされてしまいます。そこで ra を保存します（7 行目）。
* 呼び出された関数は a0〜a7 や t0〜t6 を自由に使ってよい決まりなので、b や square(a) の結果を呼び出しの前後で保つには、呼び出しで壊されない s0、s1 に移す必要があります。s0、s1 を使う側は、元の値を保存して最後に復元する義務があります（8〜9 行目、17〜18 行目）。

この「どのレジスタを誰が保存するか」という決まりが、次に説明する呼び出し規約です。

スタックとスタックフレーム
--------------------------

関数の呼び出しは入れ子になり、後に呼んだ関数ほど先に戻ります。この後入れ先出し（LIFO）の性質に合わせて、関数ごとの作業領域をメモリ上の\ **スタック**\ （stack）に確保します。1 回の関数呼び出しが使うスタック上の領域を\ **スタックフレーム**\ （stack frame）と呼びます。

RISC-V では、スタックはアドレスの大きい方から小さい方へ伸び、レジスタ sp（x2）がスタックの先頭（最も小さいアドレス）を指します。関数の入口で sp から必要な大きさを引いてフレームを確保し、出口で足して解放します。RISC-V の標準の呼び出し規約では、sp は常に 16 バイトの倍数に揃えておく決まりです。そのため、上の sum_of_squares は 12 バイトしか使いませんが 16 バイトを確保しています。

.. list-table:: sum_of_squares のスタックフレーム（関数の本体を実行中）
   :header-rows: 1
   :widths: 30 70

   * - アドレス
     - 内容
   * - sp + 16 以上
     - 呼び出し元のフレーム
   * - sp + 12
     - 保存した ra（戻りアドレス）
   * - sp + 8
     - 保存した s0
   * - sp + 4
     - 保存した s1
   * - sp + 0
     - 未使用（16 バイトに揃えるための詰め物）

スタックフレームには、ほかにレジスタに収まらないローカル変数や配列、9 個目以降の引数、レジスタが足りないときに一時的に退避した値などが置かれます。関数が呼ばれるたびに新しいフレームが積まれるので、再帰呼び出しでも各呼び出しのローカル変数が独立に保たれます。再帰が深すぎてスタック領域を使い切ることを\ **スタックオーバーフロー**\ （stack overflow）と呼びます。

呼び出し規約
------------

関数の引数や戻り値をどのレジスタで渡すか、どのレジスタを呼び出しの前後で保存するかといった決まりを\ **呼び出し規約**\ （calling convention）と呼びます。呼び出し規約が決まっているので、別々にコンパイルした関数や、異なるコンパイラで作ったライブラリを組み合わせて使えます。RISC-V では、各レジスタに用途を表す\ **ABI 名**\ が付けられていて、アセンブリでは x0〜x31 の代わりに ABI 名で書くのが普通です。

.. list-table:: RISC-V の整数レジスタと呼び出し規約
   :header-rows: 1
   :widths: 16 16 40 28

   * - レジスタ
     - ABI 名
     - 用途
     - 保存の責任
   * - x0
     - zero
     - 常に 0
     - （変更されません）
   * - x1
     - ra
     - 戻りアドレス
     - 呼び出し側
   * - x2
     - sp
     - スタックポインタ
     - 呼び出された側
   * - x3
     - gp
     - グローバルポインタ
     - （変更しません）
   * - x4
     - tp
     - スレッドポインタ
     - （変更しません）
   * - x5〜x7
     - t0〜t2
     - 一時レジスタ
     - 呼び出し側
   * - x8
     - s0（fp）
     - 保存レジスタ、フレームポインタ
     - 呼び出された側
   * - x9
     - s1
     - 保存レジスタ
     - 呼び出された側
   * - x10〜x11
     - a0〜a1
     - 引数、戻り値
     - 呼び出し側
   * - x12〜x17
     - a2〜a7
     - 引数
     - 呼び出し側
   * - x18〜x27
     - s2〜s11
     - 保存レジスタ
     - 呼び出された側
   * - x28〜x31
     - t3〜t6
     - 一時レジスタ
     - 呼び出し側

保存の責任が「呼び出し側」のレジスタを\ **caller-saved**\ （呼び出し側保存）レジスタと呼びます。呼び出された関数はこれらを自由に書き換えてよいので、呼び出し後も値が必要なら、呼び出し側が自分で保存しておく必要があります。「呼び出された側」のレジスタは\ **callee-saved**\ （呼び出された側保存）レジスタと呼び、呼び出された関数がそれを使うなら、元の値を保存して戻る前に復元しなければなりません。

両方の種類を用意しておくのは、どちらか一方だけでは無駄が多いからです。呼び出しをまたいで生き残る必要のない値は t レジスタや a レジスタに置けば保存が不要で、呼び出しをまたぐ値は s レジスタに置けば、呼び出しのたびではなく関数の入口と出口で 1 回ずつ保存するだけで済みます。

引数は a0〜a7 の 8 本で渡し、9 個目以降はスタックで渡します。戻り値は a0（64 ビットの値を RV32 で返す場合などは a0 と a1）で返します。浮動小数点数の引数と戻り値には、F/D 拡張の浮動小数点レジスタ fa0〜fa7 を使います。

ABI
---

呼び出し規約を含め、コンパイル済みのプログラム同士がバイナリのレベルで協調するための約束事全体を\ **ABI**\ （Application Binary Interface）と呼びます。ISA がハードウェアとソフトウェアのインターフェースであるのに対し、ABI はソフトウェア同士のバイナリのインターフェースです。ABI には次のような内容が含まれます。

* 呼び出し規約（引数と戻り値の渡し方、レジスタの保存の責任、スタックの整列）
* データ型の大きさと整列（int、long、ポインタが何バイトか、構造体のメンバーをどう配置するか）
* オブジェクトファイルや実行ファイルの形式（Linux などでは ELF）
* システムコールの呼び出し方（RISC-V の Linux では、a7 にシステムコール番号、a0〜a5 に引数を入れて ecall 命令を実行する）

RISC-V では、ilp32（int、long、ポインタが 32 ビット）、lp64（long とポインタが 64 ビット）などの ABI が定められ、浮動小数点数の引数をレジスタで渡すかどうかで ilp32d、lp64d などの種類があります。同じ ISA でも ABI が違えば、コンパイル済みのライブラリを組み合わせることはできません。システムコールと OS の関係については、本書では詳しく扱いません。

アセンブラ、リンカ、ローダ
--------------------------

C のソースコードが実行されるまでには、いくつかの段階があります。

.. graphviz::
   :caption: ソースコードから実行までの流れ
   :align: center

   digraph toolchain {
       rankdir=LR;
       node [shape=box, fontsize=11];
       edge [fontsize=10];
       src [label="C ソース\n(.c)"];
       asm [label="アセンブリ\n(.s)"];
       obj [label="オブジェクト\nファイル (.o)"];
       lib [label="ライブラリ"];
       exe [label="実行ファイル"];
       mem [label="メモリ上の\nプロセス"];
       src -> asm [label="コンパイラ"];
       asm -> obj [label="アセンブラ"];
       obj -> exe [label="リンカ"];
       lib -> exe;
       exe -> mem [label="ローダ"];
   }

**コンパイラ**\ （compiler）
   C などのソースコードを解析し、最適化を施してアセンブリ言語のプログラムを出力します。

**アセンブラ**\ （assembler）
   アセンブリ言語の各命令を機械語に符号化し、\ **オブジェクトファイル**\ （object file）を出力します。ラベルをアドレスに置き換え、擬似命令（後述）を実際の命令に展開するのもアセンブラの仕事です。ほかのファイルで定義された関数や変数のアドレスはまだ決まらないので、「ここに関数 printf のアドレスを埋める」という\ **再配置情報**\ （relocation）を記録しておきます。

**リンカ**\ （linker）
   複数のオブジェクトファイルとライブラリを結合して 1 つの実行ファイルにします。各関数や変数の最終的なアドレスを決め、再配置情報に従って命令中のアドレスを書き換えます。ライブラリの中身を実行ファイルに取り込むのが静的リンク、実行時に共有ライブラリを結び付けるのが動的リンクです。

**ローダ**\ （loader）
   実行ファイルの命令やデータをメモリに配置し、スタックを用意して、プログラムの入口（エントリーポイント）にジャンプします。通常は OS の一部として働き、動的リンクの場合は共有ライブラリの読み込みも行います。

RISC-V のように即値のビット数が限られる ISA では、アドレスを 1 命令で表せないことがあります。そのため、関数呼び出しは auipc と jalr の 2 命令で表し、リンク時に呼び出し先が十分近いと分かれば jal 1 命令に置き換える、といった最適化（リンカ緩和、linker relaxation）が行われます。

擬似命令
--------

アセンブリ言語には、ISA に実在しない\ **擬似命令**\ （pseudo-instruction）も書けます。アセンブラが 1 つ以上の実際の命令に展開します。x0 が常に 0 であることを利用したものが多くあります。

.. list-table:: RISC-V の主な擬似命令
   :header-rows: 1
   :widths: 25 40 35

   * - 擬似命令
     - 展開後の命令
     - 意味
   * - ``nop``
     - ``addi x0, x0, 0``
     - 何もしません。
   * - ``li rd, imm``
     - ``addi rd, x0, imm``\ （12 ビットに収まる場合）または ``lui`` + ``addi``
     - 定数を読み込みます。
   * - ``mv rd, rs``
     - ``addi rd, rs, 0``
     - レジスタのコピー
   * - ``not rd, rs``
     - ``xori rd, rs, -1``
     - ビット反転
   * - ``neg rd, rs``
     - ``sub rd, x0, rs``
     - 符号反転
   * - ``j label``
     - ``jal x0, label``
     - 無条件ジャンプ
   * - ``call label``
     - ``auipc ra, ...`` + ``jalr ra, ...(ra)``
     - 関数呼び出し
   * - ``ret``
     - ``jalr x0, 0(ra)``
     - 関数からの戻り
   * - ``beqz rs, label``
     - ``beq rs, x0, label``
     - 0 なら分岐
   * - ``bgt rs, rt, label``
     - ``blt rt, rs, label``
     - より大きければ分岐

ほかの擬似命令は「:doc:`appendix_riscv`」にまとめています。

li で 12 ビットに収まらない定数を作る場合、上位 20 ビットを lui で、下位 12 ビットを addi で設定します。

.. code-block:: text
   :linenos:

   # li a0, 0x12345678 の展開
   lui  a0, 0x12345        # a0 = 0x12345000
   addi a0, a0, 0x678      # a0 = 0x12345678

   # li a0, 0x12345FFF の展開
   lui  a0, 0x12346        # a0 = 0x12346000
   addi a0, a0, -1         # a0 = 0x12345FFF

2 つ目の例では、下位 12 ビットの 0xFFF が addi では符号拡張されて :math:`-1` になるので、lui に渡す上位部分を 1 だけ大きくして補正しています。このような細かな処理をアセンブラに任せられるのが擬似命令の利点です。

コンパイラの最適化とアーキテクチャ
----------------------------------

コンパイラの最適化の多くは、アーキテクチャの性質を前提にしています。代表的なものを見てみます。

**レジスタ割り付け**\ （register allocation）
   変数をどのレジスタに置くかを決める最適化です。レジスタはメモリより桁違いに速いので、よく使う変数ほどレジスタに置きます。同時に生きている変数がレジスタの本数より多いと、一部をスタックに退避（\ **スピル**\ 、spill）しなければなりません。最適化をしない（-O0）場合、多くのコンパイラはすべての変数をスタックに置き、使うたびにロードとストアを行います。汎用レジスタが 32 本ある RISC-V は、16 本の x86-64 よりスピルが起きにくい設計です。

**ループ展開**\ （loop unrolling）
   ループの本体を複数回分並べて、繰り返しの回数を減らす最適化です。その前段として、前の sum 関数は最適化によってたとえば次のような形になります。

   .. code-block:: text
      :linenos:

      sum:                    # a0 = a、a1 = n
          li   a2, 0          # s = 0
          blez a1, .Ldone     # n <= 0 なら何もしない
          slli a1, a1, 2
          add  a1, a0, a1     # a1 = 配列の末尾の次のアドレス
      .Lloop:
          lw   a3, 0(a0)      # a3 = *p
          addi a0, a0, 4      # p++
          add  a2, a2, a3     # s += a3
          bne  a0, a1, .Lloop # 末尾でなければ繰り返す
      .Ldone:
          mv   a0, a2
          ret

   インデックス i の代わりにポインタを進め、条件判定をループの末尾に移したことで、1 回の繰り返しが 7 命令から 4 命令に減りました。さらに 4 回分を展開すれば、4 要素あたり「ロード 4、加算 4、ポインタ更新 1、分岐 1」の 10 命令、1 要素あたり 2.5 命令になります。分岐の数が減ることは、パイプラインの分岐ハザード（「:doc:`10_pipeline`」）を減らすことにもつながります。

**命令スケジューリング**\ （instruction scheduling）
   依存関係を壊さない範囲で命令の順序を入れ替える最適化です。上のループでは、lw の直後に addi を置き、ロードの結果を使う add を 1 命令後ろにずらしています。パイプラインのプロセッサではロードの結果が使えるまでに遅れがあるので、間に無関係な命令をはさむとストールを避けられます。

**インライン化**\ （inlining）
   関数呼び出しを、呼び出し先の関数の本体で置き換える最適化です。sum_of_squares で square をインライン化すると、スタックフレームの確保や保存・復元が不要になり、次の 4 命令になります。

   .. code-block:: text
      :linenos:

      sum_of_squares:
          mul  a0, a0, a0     # a * a
          mul  a1, a1, a1     # b * b
          add  a0, a0, a1
          ret

   インライン化前は、square の 2 回の呼び出しを含めて約 20 命令を実行していました。小さな関数ほどインライン化の効果は大きくなります。ただし、やりすぎるとコードが大きくなり、命令キャッシュ（「:doc:`12_memory_hierarchy`」）に収まりにくくなります。

逆アセンブルして確かめる
------------------------

コンパイラが実際にどのような命令を生成するかは、自分で確かめるのが一番です。主な方法は 2 つあります。

1 つ目は、クロスコンパイラとそのツール群を使う方法です。RISC-V 用の GCC（riscv64-unknown-elf-gcc など）を使い、\ ``-S``\ オプションでアセンブリを出力したり、オブジェクトファイルを objdump で逆アセンブル（「:doc:`06_isa`」）したりできます。

.. code-block:: text
   :linenos:

   riscv64-unknown-elf-gcc -march=rv32im -mabi=ilp32 -O2 -S square.c
   riscv64-unknown-elf-gcc -march=rv32im -mabi=ilp32 -O2 -c square.c
   riscv64-unknown-elf-objdump -d square.o

objdump は、アドレス、機械語、逆アセンブル結果を並べて表示します。前の square と sum_of_squares を -O2 でコンパイルした場合の表示の例を示します（見やすさのため一部を省略しています）。

.. code-block:: text
   :linenos:

   00000000 <square>:
      0:   02a50533    mul   a0,a0,a0
      4:   00008067    ret

   00000008 <sum_of_squares>:
      8:   02a50533    mul   a0,a0,a0
      c:   02b585b3    mul   a1,a1,a1
     10:   00b50533    add   a0,a0,a1
     14:   00008067    ret

sum_of_squares の中で square がインライン化されていることが分かります。2 列目は 32 ビットの機械語です。たとえば ret（jalr x0, 0(ra)）は 0x00008067 に符号化されています。-march に C 拡張を含めると（rv32imc など）、ret が 16 ビットの c.jr ra（0x8082）になるなど、命令長が変わる様子も観察できます。

2 つ目は、\ **Compiler Explorer**\ を使う方法です。Web ブラウザでソースコードを入力すると、選んだコンパイラとオプションでコンパイルしたアセンブリをその場で表示してくれます。RISC-V、x86-64、AArch64 など多くのアーキテクチャのコンパイラが用意されているので、同じ C のコードが ISA によってどう変わるかや、最適化オプションによる違いを手軽に比べられます。ソースの各行とアセンブリの対応が色分けされるので、この章の例を自分で確かめるのにも適しています。

この章のまとめ
--------------

* if 文は条件分岐命令に、for ループは条件分岐と後方へのジャンプに、配列アクセスはアドレス計算（シフトと加算）とロード／ストアに変換されます。
* 関数呼び出しは jal（call）と jalr（ret）で行い、戻りアドレスは ra に入ります。
* 関数ごとの作業領域はスタックフレームとしてスタック上に確保します。RISC-V のスタックは下位アドレスへ伸び、sp は 16 バイトに揃えます。
* 呼び出し規約は引数（a0〜a7）、戻り値（a0、a1）、caller-saved（t、a、ra）と callee-saved（s、sp）のレジスタを定めます。
* ABI は呼び出し規約、データ型の大きさ、ファイル形式などを含む、バイナリレベルのインターフェースです。
* アセンブラは命令を符号化し、リンカはアドレスを確定して結合し、ローダはプログラムをメモリに配置して実行を始めます。
* 擬似命令（li、mv、j、ret など）はアセンブラが実際の命令に展開します。
* レジスタ割り付け、ループ展開、命令スケジューリング、インライン化などの最適化は、レジスタ数やパイプラインといったアーキテクチャの性質を利用しています。
* objdump や Compiler Explorer で、コンパイラが生成する命令を確かめられます。
