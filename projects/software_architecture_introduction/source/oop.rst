オブジェクト指向設計
====================

この章では、クラスを設計するときの基本的な考え方として、カプセル化、継承とコンポジション、ポリモーフィズムを説明します。また、Python に特有の仕組みであるダックタイピングと ``typing.Protocol`` を紹介します。

カプセル化
----------

:term:`カプセル化` とは、データと、そのデータを扱う処理を 1 つのクラスにまとめ、クラスの外からはメソッドを通してだけ操作できるようにすることです。カプセル化の目的は、データが常に正しい状態にあることを、クラス自身が保証できるようにすることです。

次の例では、口座の残高を外から自由に書き換えられるので、残高が負になるのを防げません。

.. code-block:: python

   # 悪い例: 残高の規則を、使う側が守らなければならない
   class Account:
       def __init__(self) -> None:
           self.balance = 0

   account = Account()
   account.balance -= 1000   # 残高が負になってしまう

残高を変更する操作をメソッドにし、規則をメソッドの中で確認すると、クラスの外から規則を破ることはできなくなります。

.. code-block:: python

   # 良い例: 残高の規則を、クラス自身が守る
   class Account:
       def __init__(self) -> None:
           self._balance = 0

       @property
       def balance(self) -> int:
           return self._balance

       def withdraw(self, amount: int) -> None:
           if amount <= 0:
               raise ValueError("金額は正の数です")
           if amount > self._balance:
               raise ValueError("残高が足りません")
           self._balance -= amount

``_balance`` のように名前を ``_`` で始めるのは、「クラスの内部用なので、外から直接使わないでください」という Python の慣習です。読み取りだけを許したい属性は、``@property`` で公開します。

尋ねるな、命じよ
~~~~~~~~~~~~~~~~

カプセル化に関連する指針に、:term:`尋ねるな、命じよ` があります。オブジェクトからデータを取り出して呼び出し側で判断するのではなく、オブジェクトに処理を命じ、判断はオブジェクト自身に任せるという指針です。

.. code-block:: python

   # 悪い例: データを尋ねて、呼び出し側で判断している
   if account.balance >= amount:
       account.balance -= amount

   # 良い例: 処理を命じ、判断はオブジェクトに任せる
   account.withdraw(amount)

悪い例のような判断がプログラムの複数の場所に書かれていると、規則が変わったとき（たとえば、一定額まで借り越せるようになったとき）に、すべての場所を直す必要があります。

継承とコンポジション
--------------------

あるクラスの機能を別のクラスで再利用する方法には、:term:`継承` と :term:`コンポジション` の 2 つがあります。

.. list-table::
   :header-rows: 1
   :widths: 20 40 40

   * -
     - 継承
     - コンポジション
   * - 関係
     - 「A は B の一種である」（is-a）
     - 「A は B を持つ」（has-a）
   * - 書き方
     - ``class A(B):``
     - ``A`` の属性として ``B`` のオブジェクトを持つ
   * - 結び付き
     - 強い。サブクラスは基底クラスの実装の詳細に依存します。
     - 弱い。相手のインターフェースだけに依存します。
   * - 組み合わせの変更
     - クラスの定義を変える必要があります（実行時には変えられません）。
     - 渡すオブジェクトを変えるだけで済みます（実行時にも変えられます）。

継承は手軽ですが、次のような問題を起こしがちです。

* 基底クラスの実装を変更すると、サブクラスが予期せず壊れることがあります（脆弱な基底クラスの問題）。
* 機能を組み合わせるたびに、新しいサブクラスが必要になります。

そのため、「継承よりコンポジションを選べ」という指針が広く知られています。継承は、本当に「一種である」関係があり、基底クラスの約束（:doc:`solid` で説明するリスコフの置換原則）をサブクラスが守れる場合に限って使います。

ポリモーフィズム
----------------

:term:`ポリモーフィズム`\ （多態性）とは、同じ呼び出し方で、オブジェクトの種類に応じた異なる処理が実行される性質のことです。前の例の ``Notifier`` は、``self._sender.send(...)`` と呼ぶだけで、渡されたのが ``EmailSender`` ならメールを、``SlackSender`` なら Slack のメッセージを送ります。

ポリモーフィズムを使うと、「種類ごとに処理を分岐する ``if`` 文」を、呼び出し側から取り除けます。種類を追加するときも、呼び出し側を変更する必要がありません。この性質は、:doc:`solid` の開放閉鎖の原則につながります。

ダックタイピングと Protocol
---------------------------

Python では、オブジェクトの型が何であるかではなく、必要なメソッドを持っているかどうかだけで、そのオブジェクトを使えるかが決まります。「アヒルのように歩き、アヒルのように鳴くなら、それはアヒルである」という言葉から、これを :term:`ダックタイピング` と呼びます。前の例の ``EmailSender`` は、``Sender`` を継承していませんが、``send`` メソッドを持っているので ``Sender`` として使えます。

ダックタイピングは柔軟ですが、そのままでは「どのメソッドを持っていればよいのか」がコードに書かれません。``typing.Protocol`` を使うと、必要なメソッドの一覧を型として定義でき、mypy が「必要なメソッドを持っているか」を検査できるようになります。

インターフェースを定義する方法には、``typing.Protocol`` のほかに ``abc.ABC``\ （抽象基底クラス）もあります。

.. list-table::
   :header-rows: 1
   :widths: 25 35 40

   * -
     - ``typing.Protocol``
     - ``abc.ABC``
   * - 満たし方
     - 必要なメソッドを持っていれば満たせます（継承は不要です）。
     - 抽象基底クラスを継承する必要があります。
   * - 検査の時期
     - 主に型チェッカーによる静的な検査です。
     - 抽象メソッドを実装していないクラスは、インスタンスを作るときにエラーになります。
   * - 実装の共有
     - 基本的に行いません。
     - 基底クラスに共通の実装を書けます。
   * - 向いている場面
     - 利用する側が、必要な機能を宣言したい場合。外部のライブラリのクラスや、変更できないクラスにも使えます。
     - 共通の処理の枠組みを提供し、一部だけをサブクラスに実装させたい場合（:doc:`patterns` の Template Method パターン）

本資料では、インターフェースの定義には主に ``Protocol`` を使います。``Protocol`` は **利用する側** が「自分はこういう機能を必要としている」と宣言するものなので、利用される側のクラスは、その ``Protocol`` の存在を知る必要がありません。この性質は、:doc:`dependency` で説明する依存関係の管理で役に立ちます。

まとめ
------

* データとそれを扱う処理をクラスにまとめ、規則はクラス自身に守らせます（カプセル化）。
* 機能の再利用には、継承よりもコンポジションを優先します。
* ポリモーフィズムを使うと、種類ごとの分岐を呼び出し側から取り除けます。
* インターフェースは ``typing.Protocol`` で定義すると、継承を使わずに型の検査ができます。
