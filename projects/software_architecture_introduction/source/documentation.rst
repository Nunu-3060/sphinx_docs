設計の記録と伝達
================

設計は、コードを書いた本人の頭の中にあるだけでは役に立ちません。チームのほかのメンバーや、半年後の自分に伝わって初めて、その設計を守り、発展させることができます。この章では、設計を図で示す方法と、設計の判断を記録する方法を説明します。

何を記録するか
--------------

コードを読めば、システムが **何をしているか** と **どのように実現しているか** は分かります。しかし、次のことはコードからは分かりません。

* なぜこの構成を選んだのか
* ほかにどのような選択肢を検討し、なぜ選ばなかったのか
* どのような制約（期限、性能、既存のシステムとの互換性）があったのか

設計を記録するときは、コードを読めば分かることよりも、コードからは分からない **判断の理由** を重視します。理由が分からないと、あとから来た人は、その設計を安心して変更することも、守ることもできません。

設計を図で示す
--------------

システムの全体の構造や、部品どうしの関係は、文章よりも図のほうが伝わりやすいことがあります。設計の図には、目的に応じてさまざまな種類があります。

.. list-table::
   :header-rows: 1
   :widths: 25 75

   * - 図の種類
     - 表すもの
   * - クラス図
     - クラスと、その属性、メソッド、クラスどうしの関係（継承、保持、依存）。UML で定められた図の 1 つです。
   * - シーケンス図
     - 1 つの処理の中で、オブジェクトどうしがどの順序でメッセージ（メソッドの呼び出し）をやり取りするか。UML で定められた図の 1 つです。
   * - 状態遷移図
     - オブジェクトの状態と、状態を変える操作（:doc:`patterns` の State パターンの例を参照）。
   * - 依存関係の図
     - モジュールやパッケージの依存の向き（:doc:`modules` の循環 import の例を参照）。
   * - C4 モデルの図
     - システムの構造を、4 つの詳細さの段階で表したもの。次の節で説明します。

図は、すべてを描き込もうとすると、かえって分かりにくくなります。1 枚の図では 1 つのことを伝えるようにし、伝えたいことに関係のない要素は省きます。

C4 モデル
~~~~~~~~~

:term:`C4 モデル` は、S. Brown が提唱した、ソフトウェアのアーキテクチャを図で表すための手法です。地図の縮尺を変えるように、同じシステムを次の 4 つの段階の詳細さで描き分けます。

.. list-table::
   :header-rows: 1
   :widths: 25 75

   * - 段階
     - 表すもの
   * - コンテキスト（Context）
     - システムと、その利用者、連携する外部のシステムの関係。システムの内部は描きません。
   * - コンテナー（Container）
     - システムを構成する、独立して動く単位（Web アプリケーション、データベース、バッチ処理など）と、その間の通信。
   * - コンポーネント（Component）
     - 1 つのコンテナーの内部の、主要な部品（モジュールやサービスなど）と、その関係。
   * - コード（Code）
     - 1 つのコンポーネントの内部のクラスの構成。クラス図などで表します。

たとえば、:doc:`domain` の注文のドメインを使った注文システムのコンテキストの図と、コンテナーの図は、次のようになります。

.. graphviz:: diagrams/documentation_container.dot

テキストで図を描く
~~~~~~~~~~~~~~~~~~

設計の図は、描画のツールで描くよりも、テキストで記述して図を生成するツールを使うと、コードと一緒にバージョン管理でき、差分も確認しやすくなります。代表的なツールには、次のものがあります。

.. list-table::
   :header-rows: 1
   :widths: 25 75

   * - ツール
     - 特徴
   * - Graphviz
     - ノードと辺を記述すると、配置を自動で決めて図を描きます。依存関係の図や状態遷移図に向いています。本資料の図は、Sphinx の ``sphinx.ext.graphviz`` 拡張機能を使い、Graphviz で描いています。
   * - PlantUML
     - クラス図やシーケンス図など、UML の図を描けます。
   * - Mermaid
     - Markdown の中に記述でき、GitHub などのサービスで表示できます。

アーキテクチャ決定記録
----------------------

設計の判断の理由を記録する方法として、:term:`アーキテクチャ決定記録`\ （Architecture Decision Record、ADR）があります。ADR は、M. Nygard が 2011 年に提案した方法で、アーキテクチャに関わる重要な判断を 1 つずつ、短い文書として記録します。

ADR は、次の方針で運用します。

* 1 つの判断を、1 つのファイルに記録します。ファイルには、``0001-use-json-for-storage.md`` のように連番と内容を表す名前を付けます。
* ファイルは、コードと同じ Git リポジトリの ``docs/adr/`` などのフォルダーに置き、コードと一緒にバージョン管理します。
* 一度承認した ADR は、書き換えません。判断を変えるときは、新しい ADR を作り、古い ADR の状態を「新しい ADR で置き換え」にします。こうすると、判断の経緯がすべて残ります。

ADR で特に重要なのは、「結果」の節です。選んだ選択肢の利点だけでなく、受け入れた欠点（トレードオフ）と、判断を見直すべき条件を書いておきます。この例では、同時に更新すると問題が起きることと、「利用者が増えた場合は、この決定を見直します」ということを書いているので、あとから来た人は、その条件が満たされたときに、安心して設計を変更できます。

コードの中の記録
----------------

コードそのものも、設計を伝える重要な手段です。

* **docstring**: モジュール、クラス、関数の docstring には、それが **何をするか** と、使う側が知っておくべき約束（送出する例外、引数の条件など）を書きます。
* **型ヒント**: 引数と戻り値の型は、それ自体が関数の約束の記録です（:doc:`functions` を参照）。型ヒントは mypy で検査できるので、コードと食い違う心配がありません。
* **コメント**: コードを読めば分かること（「i に 1 を足す」など）は書きません。コードからは分からない **理由**\ （「外部の API が 1 秒に 1 回までしか呼べないので待つ」など）を書きます。

設計のレビュー
--------------

設計を記録したら、チームのメンバーにレビューしてもらいます。設計のレビューでは、コードの書き方の細部よりも、部品の分け方と依存関係、変更への強さに注目します。レビューで確認する項目の例は、:doc:`checklist` にまとめています。

まとめ
------

* 設計の記録では、コードからは分からない判断の理由を重視します。
* 図は、1 枚で 1 つのことを伝えるように描きます。C4 モデルを使うと、詳細さの段階を描き分けられます。
* 図はテキストで記述するツールで描くと、コードと一緒に管理できます。
* 重要な判断は、ADR として 1 つずつ記録し、書き換えずに残します。
* docstring、型ヒント、コメントも、設計を伝える手段です。
