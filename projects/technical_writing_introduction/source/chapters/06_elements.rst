第 6 章 文以外の要素を使い分ける
================================

技術文書は文だけで構成されるわけではない。箇条書き、表、図、コード例を適切に使うと、文だけで書くよりも正確に、少ない分量で情報を伝えられる。本章では、これらの要素と、注記、リンクの使い方を説明する。

箇条書き
--------

箇条書きは、並列の関係にある複数の項目を示すときに使う。項目に順序がある場合は番号付きの箇条書きを、順序がない場合は記号付きの箇条書きを使う。手順は必ず番号付きにする。

箇条書きの項目は、粒度と形をそろえる。文で書く項目と体言止めの項目を混ぜない。

.. list-table:: 箇条書きの形をそろえる
   :header-rows: 1
   :widths: 50 50

   * - 悪い例
     - 良い例
   * - * ログの解析
       * エラーを検出したら、メールで通知する。
       * レポート出力機能
     - * ログの解析
       * エラーの通知
       * レポートの出力

箇条書きにも限界がある。箇条書きは項目どうしの関係（原因と結果、条件と帰結など）を表せない。論理の流れを伝えたい箇所は、箇条書きにせず文章で書く。また、箇条書きの入れ子は 2 段までにとどめる。

表
--

表は、複数の対象を複数の観点で比較したり、同じ形式の情報を一覧にしたりするときに使う。同じ内容を文章で書くと、読者は頭の中で表を組み立てなければならない。

次の例は、3 種類の料金プランを文章で書いた場合と、表で書いた場合を比べたものである。

悪い例（文章で書いた場合）：

   プラン A は月額 1,000 円でストレージ容量が 10 GB、プラン B は月額 3,000 円で 50 GB、プラン C は月額 8,000 円で 200 GB である。

良い例（表で書いた場合）：

.. list-table:: 料金プランの比較
   :header-rows: 1
   :widths: 30 35 35

   * - プラン
     - 月額（円）
     - ストレージ容量（GB）
   * - A
     - 1,000
     - 10
   * - B
     - 3,000
     - 50
   * - C
     - 8,000
     - 200

表で書くと、プランどうしの違いが一目で分かる。

表を作るときは、次の点に注意する。

* 表には、内容を表すタイトルを付ける。
* 列見出しを必ず付ける。単位は列見出しにまとめて書き、セルには数値だけを書く。
* セルには短い語句を書く。長い文章が必要な場合は、表の外に書く。
* 比較の観点が多すぎる場合は、表を分ける。

図
--

図は、構造（システムの構成など）、流れ（処理や作業の手順など）、関係（データの対応など）を伝えるときに使う。文章では長くなる説明も、図であれば一目で伝わることがある。

図を使うときは、次の点に注意する。

* 1 枚の図で伝えることは一つに絞る。
* 図には番号とキャプションを付け、本文から「:numref:`fig-inverted-pyramid` に示すように」のように参照する。
* 図の要点は本文でも説明する。図だけを置いて説明を読者に任せない。
* 画像には代替テキストを付ける。画像を表示できない環境の読者や、スクリーンリーダーの利用者にも内容が伝わるようにする。

図の元データは、文書と一緒に管理する。画像だけを保存していると、図を修正したくなったときに作り直すことになる。Graphviz、Mermaid、PlantUML のようにテキストから図を生成するツールを使うとよい。図の変更履歴をバージョン管理システムで追跡でき、レビューもしやすくなる。本書の図も、Graphviz と matplotlib を使ってビルド時に生成している。

コード例
--------

コード例は、技術文書の中で最も参照される要素の一つである。読者はコード例をそのまま複製して使うことが多い。そのため、コード例には文章以上の正確さが求められる。

コード例を書くときは、次の点に注意する。

* そのまま実行できる完全な例を示す。実行に必要な import 文や前提となる設定を省略しない。
* やむを得ず省略する場合は、省略したことを明示する。
* 読者が自分の値に置き換える箇所は、``<API_TOKEN>`` のように置き換えるべき箇所であることが分かる書き方にする。
* 書き手自身が実行し、正しく動作することを確認する。
* 本文からコードの特定の行を参照する場合は、行番号を付ける。

.. code-block:: python
   :linenos:

   import json
   from pathlib import Path

   config = json.loads(Path("config.json").read_text(encoding="utf-8"))
   print(config["timeout"])

上のコード例では、4 行目で設定ファイルを読み込み、5 行目でタイムアウトの設定値を表示する。このように行番号を付けておくと、本文から特定の行を正確に参照できる。

コマンドの例では、読者が入力するコマンドと、コマンドが出力する結果を区別する。次の例では、入力するコマンドの先頭にプロンプト記号 ``$`` を付け、出力とは別のコードブロックに分けている。

.. code-block:: console
   :linenos:

   $ python --version

出力例：

.. code-block:: text
   :linenos:

   Python 3.12.4

ただし、プロンプト記号を付けると、読者がコマンドを複製したときに記号まで含まれてしまう。プロンプト記号を付けるかどうかは、文書の中で統一する。

注記
----

注記は、本文の流れから外れるが読者に伝えたい情報を、目立つように示すための要素である。注記には重要度に応じた種類がある。

.. list-table:: 注記の種類と使い分けの例
   :header-rows: 1
   :widths: 20 80

   * - 種類
     - 用途
   * - 注（Note）
     - 補足情報。読まなくても作業はできるが、知っておくと役に立つ情報。
   * - 注意（Caution）
     - 守らないと、作業の失敗や想定外の結果を招くおそれがある事項。
   * - 警告（Warning）
     - 守らないと、データの消失や障害など、重大な結果を招くおそれがある事項。

注記を表示したときの見え方の例を次に示す。

.. note::

   設定ファイルの書式は YAML である。

.. warning::

   このコマンドは、データベースのすべてのテーブルを削除する。実行する前に、接続先が検証環境であることを確認する。

注記には、次の注意点がある。

* **注記を使いすぎない**：注記が多すぎると、読者は注記を読み飛ばすようになり、本当に重要な警告まで見落とす。
* **警告は操作の前に置く**：警告を操作の後に置くと、読者は警告を読む前に操作してしまう。
* **重要度の判断をそろえる**：同じ程度の危険には、文書全体で同じ種類の注記を使う。

リンク
------

リンクは、関連する情報へ読者を案内する。リンクを設けるときは、リンク文字列を読むだけで行き先が分かるようにする。

.. list-table:: リンク文字列の書き方
   :header-rows: 1
   :widths: 50 50

   * - 悪い例
     - 良い例
   * - 認証の詳細は、こちらを参照。
     - 認証の詳細は、「API リファレンス」の「認証」の節を参照。

「こちら」「ここ」のようなリンク文字列は、リンクだけを拾い読みする読者や、スクリーンリーダーでリンクの一覧を聞く読者には意味が伝わらない。

外部のサイトへのリンクは、移転や削除によっていずれ切れる。リンク切れは定期的に検査する（「:doc:`08_review`」を参照）。
