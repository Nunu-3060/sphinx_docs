第 7 章 文書の種類別の書き方
============================

本章では、エンジニアがよく書く文書について、目的、読者、記載すべき項目、よくある失敗を示す。各文書のテンプレートは「:doc:`appendix_b_templates`」に収録した。

README
------

README は、ソフトウェアやリポジトリの入り口となる文書である。初めて訪れた読者が、そのソフトウェアが何をするものかを理解し、使い始められるようにすることを目的とする。

.. list-table:: README に記載すべき項目
   :header-rows: 1
   :widths: 25 75

   * - 項目
     - 内容
   * - 名前と概要
     - ソフトウェアが何をするものかを一文で書く。
   * - 動作環境
     - 対応する OS、言語やランタイムのバージョン、依存するソフトウェアを書く。
   * - インストール
     - インストールの手順をコマンドで示す。
   * - 使い方
     - 最小の使用例を、コマンドと期待される出力の組で示す。
   * - 関連文書
     - チュートリアル、リファレンス、設計書などへのリンクを示す。
   * - 問い合わせ先
     - 不具合の報告方法や質問の窓口を書く。
   * - ライセンス
     - ライセンスの名前を書く。

よくある失敗は次のとおりである。

* 冒頭に、そのソフトウェアが何をするものかが書かれていない。
* インストール手順が、書き手の環境でしか動かない。
* ソフトウェアの更新に README の更新が追いついておらず、記載されたコマンドが動かない。

設計書
------

設計書は、システムや機能をどのように作るか、そしてなぜそのように作るかを共有する文書である。読者は、レビュアー、実装を担当する開発者、そして将来の保守担当者である。

.. list-table:: 設計書に記載すべき項目
   :header-rows: 1
   :widths: 25 75

   * - 項目
     - 内容
   * - 背景と目的
     - この設計が必要な理由と、解決したい課題を書く。
   * - スコープ
     - 対象とすることと、対象としないことを書く。
   * - 要求
     - 満たすべき機能要求と非機能要求（性能、可用性など）を書く。
   * - 設計の概要
     - 全体の構成を図と文章で示す。
   * - 詳細設計
     - コンポーネントの振る舞い、データ構造、インターフェースを書く。
   * - 検討した代替案
     - 検討したほかの案と、採用しなかった理由を書く。
   * - 未解決の課題
     - まだ決まっていないことや、追加の調査が必要なことを書く。

設計書で最も価値が高いのは、「なぜ」の情報である。何を作ったかはコードを読めば分かるが、なぜそのように作ったのか、なぜほかの案を選ばなかったのかは、コードからは分からない。この情報がないと、将来の保守担当者は、設計の前提を知らないまま変更を加えることになる。

よくある失敗は次のとおりである。

* 実装の詳細だけが書かれ、設計の理由や検討した代替案が書かれていない。
* 対象としないことが書かれていないため、レビューで範囲外の議論が続く。
* 設計の変更が反映されず、実装と食い違ったまま放置される。

設計上の重要な判断を、判断ごとに短い文書として記録する :term:`ADR` という手法もある。ADR は、判断の背景、判断の内容、その結果を記録する。

API リファレンス
----------------

API リファレンスは、関数、クラス、エンドポイントなどの仕様を正確に記述する文書である。読者は、API を使う開発者である。読者は API リファレンスを最初から順に読むことはなく、必要な項目を探して参照する。そのため、すべての項目を同じ形式で記述する。

.. list-table:: API リファレンスに記載すべき項目
   :header-rows: 1
   :widths: 25 75

   * - 項目
     - 内容
   * - 名前と形式
     - 関数名と引数の並び、エンドポイントの URL と HTTP メソッドを書く。
   * - 説明
     - その API が何をするかを書く。
   * - パラメーター
     - 各パラメーターの名前、型、必須かどうか、既定値、取りうる値の範囲を書く。
   * - 戻り値
     - 戻り値の型と意味を書く。
   * - エラー
     - 発生しうる例外やエラーコードと、それが発生する条件を書く。
   * - 使用例
     - 典型的な使い方をコード例で示す。

API リファレンスは、ソースコードのコメントから生成すると、コードとの食い違いを防ぎやすい。次の例は、Python の docstring に記述した API リファレンスである。

.. code-block:: python
   :linenos:

   def get_user(user_id: int, include_deleted: bool = False) -> User:
       """ユーザーの情報を取得する。

       Args:
           user_id: 取得するユーザーの ID。1 以上の整数。
           include_deleted: True の場合、削除済みのユーザーも取得の対象にする。

       Returns:
           指定した ID のユーザー。

       Raises:
           UserNotFoundError: 指定した ID のユーザーが存在しない場合。
           ValueError: user_id が 1 未満の場合。
       """

よくある失敗は次のとおりである。

* 説明が名前の言い換えになっている。たとえば、``get_user`` の説明が「ユーザーを取得する」だけで、どのような条件で何が返るのかが書かれていない。
* 境界値やエラーの条件が書かれていない。
* 使用例がない、または使用例が動かない。

手順書
------

手順書は、作業を誤りなく再現するための文書である。読者は作業者であり、書き手とは別の人が作業することを前提に書く。手順書の誤りは、本番環境での障害に直結することがある。

.. list-table:: 手順書に記載すべき項目
   :header-rows: 1
   :widths: 25 75

   * - 項目
     - 内容
   * - 目的
     - この手順で何を達成するかを書く。
   * - 前提条件
     - 必要な権限、ツール、事前に完了しているべき作業を書く。
   * - 所要時間
     - 作業全体の所要時間の目安を書く。
   * - 手順
     - 番号付きの箇条書きで、一つの項目に一つの操作を書く。
   * - 期待結果
     - 各手順が成功したときに表示される内容や、確認できる状態を書く。
   * - 作業後の確認
     - 作業が正しく完了したことを確認する方法を書く。
   * - 切り戻し手順
     - 作業が失敗したときに、作業前の状態に戻す手順を書く。

各手順には、操作と期待結果を組にして書く。期待結果がないと、作業者は操作が成功したかどうかを判断できない。

.. code-block:: text
   :linenos:

   3. 次のコマンドで、アプリケーションのサービスを停止する。

      $ sudo systemctl stop myapp

      期待結果：エラーが表示されずに、プロンプトが戻る。

   4. 次のコマンドで、サービスが停止したことを確認する。

      $ systemctl is-active myapp

      期待結果：「inactive」と表示される。

よくある失敗は次のとおりである。

* 期待結果が書かれていない。
* 「適宜」「必要に応じて」のように、判断を作業者に委ねる表現がある。
* 作業の対象が本番環境なのか検証環境なのかが明記されていない。
* 切り戻し手順がない。

障害報告書
----------

障害報告書は、障害の経緯と原因を記録し、再発を防ぐための文書である。\ :term:`ポストモーテム`\ とも呼ばれる。読者は、開発者、運用担当者、管理者など、障害に関係するすべての人である。

.. list-table:: 障害報告書に記載すべき項目
   :header-rows: 1
   :widths: 25 75

   * - 項目
     - 内容
   * - 概要
     - 何が起き、どのような影響があり、どう解決したかを短く書く。
   * - 影響
     - 影響の期間、範囲、大きさを書く。
   * - 時系列
     - 検知から解決までの出来事を、時刻とともに書く。時刻のタイムゾーンを明記する。
   * - 根本原因
     - 障害の直接の原因と、それが起きた背景を書く。
   * - 対応
     - 障害を解消するために行ったことを書く。
   * - 再発防止策
     - 対策ごとに担当と期限を決めて書く。
   * - 教訓
     - うまくいったことと、うまくいかなかったことを書く。

障害報告書は、個人の責任を追及するためのものではない。人の誤りを前提として、それを防げなかった仕組みの問題を明らかにするために書く。このように個人を責めない姿勢を\ :term:`ブレームレス`\ と呼ぶ。責任追及の場になると、関係者は事実を隠すようになり、正確な記録が残らなくなる。

よくある失敗は次のとおりである。

* 「担当者が手順を誤った」で原因の分析が終わっている。なぜ誤ったのか、なぜ誤りを防げなかったのかまで掘り下げていない。
* 再発防止策が「今後は注意する」のように、具体的な行動になっていない。
* 再発防止策に担当と期限がなく、実行されないまま忘れられる。

Issue、プルリクエスト、コミットメッセージ
------------------------------------------

Issue、プルリクエスト、コミットメッセージは短い文書だが、書かれる回数が多く、開発の記録として長く参照される。

Issue
^^^^^

不具合を報告する Issue には、次の項目を書く。読者である開発者が、不具合を再現できることが目標である。

* 再現手順
* 期待した結果
* 実際の結果
* 環境（OS、バージョンなど）

プルリクエスト
^^^^^^^^^^^^^^

プルリクエストの説明には、次の項目を書く。レビュアーが、変更の意図を理解したうえでレビューできることが目標である。

* 変更の目的（関連する Issue へのリンク）
* 変更の内容
* 動作の確認方法
* レビューで特に見てほしい点

コミットメッセージ
^^^^^^^^^^^^^^^^^^

コミットメッセージは、1 行目に変更の要約を書き、1 行空けて本文を書く形式が広く使われている。1 行目は、コミットの一覧に表示されるため短くまとめる。本文には、変更の内容よりも変更の理由を書く。変更の内容は差分を見れば分かるが、理由は差分からは分からないためである。

.. code-block:: text
   :linenos:

   ログイン時のセッションの有効期限を 30 分から 8 時間に延長する

   業務時間中に何度もログインし直す必要があるという問い合わせが多いため。
   有効期限は、セキュリティ部門と合意した上限である 8 時間とした。

   関連する Issue: #128

コミットメッセージの形式を統一するための規約として、Conventional Commits がある。チームで規約を採用する場合は、規約を文書にして共有する。
