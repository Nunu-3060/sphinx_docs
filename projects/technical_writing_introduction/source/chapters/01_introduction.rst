第 1 章 はじめに
================

本書の目的
----------

エンジニアの仕事は、コードを書くことと同じくらい文章を書くことで成り立っている。技術文書は、チームの知識を蓄えて伝えるための基盤である。たとえば、設計書は設計を共有し、README は使い方を伝え、手順書は作業を再現できるようにし、障害報告書は障害の経緯を残す。

一方で、文章の書き方を体系的に学ぶ機会は少ない。多くのエンジニアは見よう見まねで文書を書いており、「読みにくい」「何が言いたいのか分からない」と指摘されても、どこをどう直せばよいのか分からないことが多い。

本書は、技術文書を「読者が目的を達成するための道具」ととらえ、その道具を設計し、作り、保守するための考え方と技法を解説する。本書を読み終えた読者が次のことをできるようになることを目標とする。

* 読者と目的を定め、それに合った文書の種類と構成を選べる。
* 誤解されにくい文を書き、表記をそろえられる。
* 箇条書き、表、図、コード例を適切に使い分けられる。
* 文書をレビューし、継続的に保守できる。

対象読者
--------

本書は、日常的に技術文書を書いているものの、文章の書き方を体系的に学んだことのないエンジニアを対象とする。本書が扱うのは日本語の技術文書であり、英語の技術文書に固有の書き方は扱わない。

技術文書とは
------------

本書でいう技術文書とは、技術的な情報を、特定の読者が特定の目的を達成できるように伝える文書である。技術文書に求められる性質は、小説やエッセイに求められる性質とは大きく異なる。

.. list-table:: 技術文書と小説・エッセイの違い
   :header-rows: 1
   :widths: 15 45 40

   * - 性質
     - 技術文書
     - 小説・エッセイ
   * - 正確さ
     - 事実と異なる記述は、読者の誤操作や誤った判断につながる。
     - 虚構や誇張が許される。
   * - 再現性
     - 読者が書かれたとおりに作業すれば、同じ結果が得られなければならない。
     - 求められない。
   * - 読まれ方
     - 必要な箇所だけを探して拾い読みされることが多い。
     - 最初から順に読まれることを前提にできる。
   * - 解釈の幅
     - 読者によって解釈が変わってはならない。
     - 解釈の幅が作品の魅力になることがある。

技術文書で最も重要なのは、文章の美しさではない。読者が誤解することなく、少ない労力で目的を達成できることである。

技術文書の種類
--------------

エンジニアが書く主な技術文書を次の表に示す。

.. list-table:: 主な技術文書の種類
   :header-rows: 1
   :widths: 18 37 45

   * - 種類
     - 主な読者
     - 主な目的
   * - README
     - 初めてそのソフトウェアに触れる開発者や利用者
     - ソフトウェアの概要を把握し、使い始める。
   * - 仕様書
     - 開発者、テスト担当者、発注者
     - 何を作るか（要求と振る舞い）について合意する。
   * - 設計書
     - 開発者、レビュアー、将来の保守担当者
     - どのように作るか、なぜそのように作るかを共有する。
   * - API リファレンス
     - API を利用する開発者
     - 関数やエンドポイントの正確な仕様を調べる。
   * - 手順書
     - 運用担当者、作業者
     - 作業を誤りなく再現する。
   * - 障害報告書
     - 開発者、運用担当者、管理者
     - 障害の経緯と原因を共有し、再発を防ぐ。
   * - 議事録
     - 会議の参加者と不参加者
     - 決定事項と今後の作業を記録する。

悪い技術文書が生むコスト
------------------------

悪い技術文書は、書いた本人が気付かないところでコストを生み続ける。

* **問い合わせの増加**：文書で解決できなかった疑問は、書き手やチームへの質問になる。同じ質問に何度も答える時間は、文書を直す時間よりはるかに大きくなりやすい。
* **誤操作と障害**：手順書の曖昧な一文が、本番環境での誤操作を招くことがある。
* **属人化**：文書に残っていない知識は、特定の人の頭の中にしか存在しない。その人が異動や退職をすると、知識は失われる。
* **誤った意思決定**：設計書の前提や制約が正しく伝わらないと、誤った前提の上で議論が進む。

反対に、よい技術文書は書き手がその場にいなくても読者を助け続ける。文書を書く手間は、読者の数と読まれる回数を考えれば十分に回収できる。

本書の構成
----------

技術文書を作る作業は、:numref:`fig-process` に示す流れで進む。本書の各章は、この流れの各段階に対応している。

.. graphviz::
   :caption: 技術文書の作成の流れと本書の章の対応
   :name: fig-process
   :align: center

   digraph process {
       graph [rankdir=TB, bgcolor="transparent", nodesep=0.7, ranksep=0.6];
       node [shape=box, style="rounded,filled", fillcolor="#dbe9f6", color="#2e6da4", fontname="Yu Gothic", fontsize=14, width=1.6];
       edge [color="#555555", fontname="Yu Gothic", fontsize=12];

       prepare [label="準備\n（第 2 章）"];
       structure [label="構成\n（第 3 章）"];
       write [label="執筆\n（第 4～7 章）"];
       review [label="レビュー\n（第 8 章）"];
       publish [label="公開"];
       maintain [label="保守\n（第 8 章）"];

       {rank=same; prepare; structure; write;}
       {rank=same; maintain; publish; review;}

       prepare -> structure -> write;
       write -> review;
       publish -> review [dir=back];
       maintain -> publish [dir=back];
       review -> write [label=" 修正", style=dashed, constraint=false];
       maintain -> write [label=" 更新", style=dashed, constraint=false];
   }

各章の内容は次のとおりである。

.. list-table:: 本書の構成
   :header-rows: 1
   :widths: 30 70

   * - 章
     - 内容
   * - :doc:`02_preparation`
     - 読者と目的を定め、文書の種類を選び、情報を集める。
   * - :doc:`03_structure`
     - 文書全体の構成、見出し、段落を組み立てる。
   * - :doc:`04_sentences`
     - 誤解されにくい文を書く。
   * - :doc:`05_notation`
     - 文体、用語、表記をそろえる。
   * - :doc:`06_elements`
     - 箇条書き、表、図、コード例、注記、リンクを使い分ける。
   * - :doc:`07_document_types`
     - README、設計書、手順書など、文書の種類ごとの書き方を示す。
   * - :doc:`08_review`
     - 文書をレビューし、公開後も正しい状態に保つ。

第 2 章から第 6 章では、すべての技術文書に共通する技法を扱う。第 7 章では、それらの技法を文書の種類ごとに当てはめる。付録には、執筆後の確認に使うチェックリストと、文書のテンプレートを収録した。
