第 8 章 レビューと保守
======================

書き上げた文書には、書き手が気付かない誤りや分かりにくい箇所が必ず残っている。また、公開した文書は、対象のソフトウェアが変わるにつれて古くなる。本章では、文書をレビューする方法と、公開後も正しい状態に保つ方法を説明する。

セルフレビュー
--------------

他者にレビューを依頼する前に、書き手自身が文書を見直す。セルフレビューでは、次の方法が効果的である。

* **時間をおく**：書いた直後は、書いた内容を覚えているため、文章の分かりにくさに気付きにくい。少なくとも数時間、できれば一晩おいてから読み直す。
* **読者になりきる**：「:doc:`02_preparation`」で定めた読者の前提知識だけで理解できるかを確かめる。手順書であれば、実際に手順どおりに操作する。
* **声に出して読む**：音読すると、長すぎる文やリズムの悪い文、助詞の誤りに気付きやすい。
* **表示形式を変える**：エディターで書いた文書を、ビルド後の HTML や印刷物で読み直すと、見落としていた誤りに気付くことがある。

確認する観点は、「:doc:`appendix_a_checklist`」にまとめた。

他者によるレビュー
------------------

書き手にとって自明なことは、読者にとって自明とは限らない。書き手自身では見つけられない問題を見つけるために、他者にレビューを依頼する。

レビューを依頼するときは、次の情報を伝える。

* 文書の目的と想定する読者
* 特に見てほしい観点（たとえば「技術的に正しいか」「初心者が手順どおりに作業できるか」）
* レビューの期限

レビュアーには、想定する読者に近い人を選ぶとよい。初心者向けのチュートリアルを、その分野の専門家だけがレビューすると、初心者がつまずく箇所を見落としやすい。

レビューで指摘するときは、次の点に注意する。

* 問題の箇所と、なぜ問題なのかを具体的に書く。
* 可能であれば、修正の案を示す。
* 必ず直してほしい指摘と、提案にとどまる指摘を区別する。たとえば、指摘の先頭に「必須」「提案」「質問」のような区分を付ける。

指摘を受ける書き手は、読者の誤解を書き手の責任と考える。レビュアーが誤解した箇所は、ほかの読者も誤解する可能性が高い。

ツールによる検査
----------------

表記ゆれや長すぎる文のように、機械的に判定できる問題は、人が目で探すよりもツールで検査するほうが確実である。人のレビューは、ツールでは判定できない問題（内容の正しさや構成の妥当性）に集中させる。

.. list-table:: 文書の検査に使える主なツール
   :header-rows: 1
   :widths: 25 75

   * - ツール
     - 用途
   * - textlint
     - 日本語に対応した文章校正ツール。規則を組み合わせて、文の長さ、表記ゆれ、文体の混在などを検査できる。
   * - Vale
     - スタイルガイドの規則を設定ファイルに記述して検査する文章校正ツール。
   * - リンクチェッカー
     - 文書内のリンク切れを検出する。Sphinx では ``linkcheck`` ビルダーを使う。

ツールの動作を理解するために、本書には Python で書いた簡易的な文章チェッカー ``check_style.py`` を付属した。このチェッカーは、本書で説明した規則のうち、次の 4 種類を検査する。

.. list-table:: check_style.py の検査項目
   :header-rows: 1
   :widths: 25 50 25

   * - 規則名
     - 検査内容
     - 関連する章
   * - long-sentence
     - 一文が上限（既定値は 80 文字）を超えている。
     - :doc:`04_sentences`
   * - spacing
     - 日本語の文字と英数字の間に半角空白がない。
     - :doc:`05_notation`
   * - variant
     - 本書の表記規則と異なる表記がある。
     - :doc:`05_notation`
   * - vague
     - 曖昧な表現がある。
     - :doc:`04_sentences`

.. code-block:: text

   sample_bad.md:3:1: [long-sentence] 一文が 86 文字ある（上限 80 文字）。文を分けられないか検討する。
   sample_bad.md:3:6: [variant] 「サーバ」は「サーバー」と書く。
   sample_bad.md:3:84: [variant] 「下さい」は「ください」と書く。
   sample_bad.md:5:16: [spacing] 日本語と英数字の間に半角空白を入れる。
   sample_bad.md:7:11: [vague] 曖昧な表現「適宜」がある。条件や数値で具体的に書けないか検討する。
   sample_bad.md:9:1: [variant] 「全て」は「すべて」と書く。
   sample_bad.md:9:13: [vague] 曖昧な表現「しばらく」がある。条件や数値で具体的に書けないか検討する。

このチェッカーは、規則の考え方を示すための簡易的な実装である。たとえば一文の長さは行単位で数えるため、一文を複数の行に分けて書いた文書では正しく数えられない。実際のプロジェクトでは、textlint のような実績のあるツールを使うとよい。

Docs as Code
------------

文書をソースコードと同じ方法で管理する考え方を :term:`Docs as Code` と呼ぶ。具体的には、次のように運用する。

* 文書を Markdown や reStructuredText のようなテキスト形式で書く。
* 文書を Git のようなバージョン管理システムで管理する。
* 文書の変更も、プルリクエストを通じてレビューする。
* CI（継続的インテグレーション）で、文書のビルド、文章校正ツールによる検査、リンク切れの検査を自動的に実行する。

文書をソースコードと同じリポジトリに置くと、コードの変更と文書の変更を同じプルリクエストで扱える。その結果、文書の更新漏れをレビューで見つけやすくなる。本書も、reStructuredText で書いた文書を Sphinx でビルドしている。

文書の陳腐化を防ぐ
------------------

文書は、公開した時点から古くなり始める。誤った情報を含む文書は、文書がない状態よりも害が大きい。読者は文書を信じて行動するためである。文書を正しい状態に保つために、次のことを行う。

* **担当者を決める**：文書ごとに更新の責任を持つ担当者やチームを決め、文書に明記する。
* **最終更新日と対象バージョンを書く**：読者が、その文書が現在も有効かどうかを判断できるようにする。
* **更新を作業の完了条件に含める**：仕様を変更するプルリクエストでは、関連する文書の更新も完了条件にする。プルリクエストのテンプレートに確認項目を設けると、更新漏れを防ぎやすい。
* **定期的に見直す**：たとえば四半期に一度、文書の一覧を確認し、古くなった文書を更新する。
* **不要な文書を削除する**：使われなくなった文書は削除するか、古い文書であることを冒頭に明記して保管する。
