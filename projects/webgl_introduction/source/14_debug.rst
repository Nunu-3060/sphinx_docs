.. _chap-debug:

デバッグと最適化
================

この章では、WebGL のプログラムが期待どおりに動かないときの調べ方と、性能を改善するための基本的な考え方を説明します。最後に、本書の次に学ぶ内容を紹介します。

何も表示されないとき
--------------------

WebGL のプログラムでは、誤りがあっても例外が発生せず、単に何も表示されないことがよくあります。何も表示されない場合は、次の順に確認します。

.. list-table:: 何も表示されないときの確認項目
   :header-rows: 1
   :widths: 40 60

   * - 確認項目
     - 確認方法
   * - JavaScript のエラーが出ていないか
     - 開発者ツールのコンソールを確認します
   * - シェーダーのコンパイルとリンクに成功しているか
     - ``gl.getShaderParameter`` と ``gl.getProgramParameter`` の結果を確認し、失敗していれば情報ログを表示します（\ :numref:`chap-shader`\ ）
   * - WebGL の警告が出ていないか
     - コンソールの ``WebGL: INVALID_OPERATION`` などの警告を確認します
   * - クリアの色が表示されるか
     - ``gl.clearColor`` を目立つ色にします。表示されなければ、canvas やコンテキストの取得、描画ループに問題があります
   * - 物体が表示範囲に入っているか
     - 頂点シェーダーで行列を掛けずに ``gl_Position`` を出力して、三角形が表示されるかを確かめます。表示されれば、行列（特にカメラの位置や向き、near と far）に問題があります
   * - 面が裏向きになっていないか
     - ``gl.disable(gl.CULL_FACE)`` でカリングを無効にして確かめます
   * - 深度バッファーをクリアしているか
     - ``gl.clear`` に ``gl.DEPTH_BUFFER_BIT`` を指定しているかを確認します
   * - 色が黒くなっていないか
     - フラグメントシェーダーで固定の色（\ ``vec4(1.0, 0.0, 1.0, 1.0)`` など）を出力して確かめます。テクスチャが黒い場合は、ミップマップの生成漏れや画像の読み込み前の描画を疑います

gl.getError
-----------

WebGL の関数の呼び出しに誤りがあると、エラーコードが記録されます。\ ``gl.getError()`` を呼ぶと、記録されたエラーコードを取得できます（エラーがなければ ``gl.NO_ERROR``\ ）。主なエラーコードを\ :numref:`table-gl-errors` に示します。

.. _table-gl-errors:

.. list-table:: 主なエラーコード
   :header-rows: 1
   :widths: 35 65

   * - エラーコード
     - 主な原因
   * - ``gl.INVALID_ENUM``
     - 定数の引数に、受け付けられない値を渡しました
   * - ``gl.INVALID_VALUE``
     - 数値の引数が範囲外です（負の大きさなど）
   * - ``gl.INVALID_OPERATION``
     - 現在のステートでは実行できない操作をしました（プログラムを選ばずに描画した、バッファーの範囲外を参照する描画をした、など）
   * - ``gl.INVALID_FRAMEBUFFER_OPERATION``
     - 不完全なフレームバッファーに描画しました
   * - ``gl.OUT_OF_MEMORY``
     - メモリが不足しました
   * - ``gl.CONTEXT_LOST_WEBGL``
     - コンテキストが失われています（後述）

``gl.getError`` は GPU の処理の完了を待つことがあり、頻繁に呼ぶと性能が低下します。デバッグ中に、問題のありそうな箇所の前後で呼ぶ程度にとどめます。多くのブラウザーはエラーの内容をコンソールにも表示するので、まずはコンソールを確認するのが手軽です。

デバッグツール
--------------

ブラウザーの開発者ツールに加えて、WebGL 専用のデバッグツールがあります。代表的なものが Spector.js です。ブラウザーの拡張機能として導入でき、1 フレーム分の WebGL の関数呼び出しをすべて記録して、次のような情報を確認できます。

* 呼び出された関数と引数の一覧
* 各描画コールの時点でのステート（バインドされているバッファーやテクスチャ、有効な機能など）
* 各描画コールの後のフレームバッファーの内容
* 使われたシェーダーのソースコードと uniform 変数の値

「どの描画コールで表示がおかしくなったか」を 1 つずつ確認できるので、ステートの設定漏れのような誤りを見つけるのに役立ちます。

コンテキストロスト
------------------

GPU のドライバーの更新や、GPU の負荷が高すぎる場合、他のタブが GPU を大量に使った場合などに、WebGL のコンテキストが失われることがあります。これを\ :term:`コンテキストロスト`\ と呼びます。コンテキストが失われると、それまでに作ったバッファー、テクスチャ、プログラムなどはすべて無効になり、描画できなくなります。

コンテキストロストは、canvas の ``webglcontextlost`` イベントで検知できます。このイベントで ``preventDefault`` を呼んでおくと、ブラウザーがコンテキストを復元できるようになったときに ``webglcontextrestored`` イベントが発生します。復元後は、すべての WebGL のリソースを作り直す必要があります。

.. code-block:: javascript
   :linenos:

   canvas.addEventListener("webglcontextlost", (event) => {
     event.preventDefault();  // 復元を可能にする
     cancelAnimationFrame(frameId);  // 描画ループを止める
   });

   canvas.addEventListener("webglcontextrestored", () => {
     initializeResources();  // シェーダー、バッファー、テクスチャなどをすべて作り直す
     frameId = requestAnimationFrame(render);
   });

リソースを作る処理を 1 つの関数にまとめておくと、復元の処理を書きやすくなります。拡張機能 ``WEBGL_lose_context`` の ``loseContext()`` と ``restoreContext()`` を使うと、コンテキストロストを意図的に起こしてテストできます。なお、本書のサンプルは説明を簡単にするため、コンテキストロストには対応していません。

性能の改善
----------

WebGL のプログラムの処理は、CPU 側（JavaScript と WebGL の関数呼び出し）と GPU 側（頂点とフラグメントの処理）に分かれます。性能を改善するには、まずどちらが遅いのかを見極めることが大切です。例えば、canvas の大きさを小さくして速くなる場合は、GPU 側のフラグメントの処理が原因です。

描画コールと状態変更を減らす
~~~~~~~~~~~~~~~~~~~~~~~~~~~~

WebGL の関数の呼び出しには、ブラウザーによる引数の検査などのオーバーヘッドがあります。特に、描画コールと、プログラムやテクスチャの切り替えは負荷が大きい処理です。次のような方法で回数を減らします。

* 同じ形状を多数描く場合は、インスタンス描画を使います（\ :numref:`chap-advanced`\ ）。
* 同じプログラム、同じテクスチャを使う物体をまとめて描き、切り替えの回数を減らします。
* 小さな画像を 1 枚の大きな画像にまとめ（テクスチャアトラス）、テクスチャの切り替えをなくします。
* 変化しない複数の物体の頂点データを、1 つのバッファーにまとめます。
* 共通の uniform 変数は UBO で共有します（\ :numref:`chap-advanced`\ ）。

GPU とのやり取りを減らす
~~~~~~~~~~~~~~~~~~~~~~~~

* バッファーやテクスチャの作成と転送は初期化時に行い、毎フレーム行いません。データを更新する場合は、作り直さずに ``gl.bufferSubData`` などで内容だけを更新します。
* ``gl.getError``\ 、\ ``gl.readPixels``\ 、\ ``gl.getParameter`` など、GPU の状態を問い合わせる関数は、GPU の処理の完了を待つことがあるため、描画ループの中では避けます。uniform 変数のロケーションなども、初期化時に取得しておきます。

フラグメントの処理を減らす
~~~~~~~~~~~~~~~~~~~~~~~~~~

* 不透明な物体を手前から順に描くと、奥の物体のフラグメントが深度テストで早い段階で捨てられ、フラグメントシェーダーの実行回数が減ることがあります。
* 高 DPI の環境では、描画バッファーのピクセル数が大きく増えます。必要に応じて ``devicePixelRatio`` に上限（例えば 2）を設けます。
* フラグメントシェーダーでの複雑な計算や、テクスチャの読み出しの回数を減らします。

モバイル端末での注意
--------------------

スマートフォンやタブレットでは、PC と比べて次の点に注意が必要です。

* GPU の性能が低く、メモリも少ないです。テクスチャの大きさや頂点の数を控えめにします。
* フラグメントシェーダーで ``highp`` が使えない、または ``mediump`` が 16 ビットで計算される端末があります。\ ``gl.getShaderPrecisionFormat`` で精度を確認できます（\ ``01_check_support.html`` で表示しています）。
* ``devicePixelRatio`` が 3 以上の端末もあり、描画するピクセル数が非常に多くなります。
* 負荷の高い処理を続けると、発熱やバッテリーの消費が大きくなり、端末が性能を落とすこともあります。アニメーションが不要なときは描画ループを止めます。
