ソケットプログラミング
======================

この章では、アプリケーションがネットワークを使うための窓口であるソケットと、それを使ったプログラムの書き方を説明します。ここまでの章で見てきた TCP や UDP の仕組みは、アプリケーションからはソケット API を通して見えます。TCP サーバーとクライアントの基本形から始めて、TCP がバイトストリームであることから生じるフレーミングの問題、タイムアウトとエラー処理、複数のクライアントを同時に扱う方法（スレッド、I/O 多重化、asyncio）を、Python のサンプルコードで確かめます。

ソケットとは
------------

ソケット（socket）は、OS がアプリケーションに提供する、ネットワーク通信のためのインターフェースです。1983 年に配布された 4.2BSD で導入された API（BSD ソケット）が元になっており、現在は Linux、macOS、Windows（Winsock）のいずれでもほぼ同じ形で使えます。Python の ``socket`` モジュールも、この API を薄く包んだものです。

アプリケーションから見ると、ソケットは「OS の中にある通信の端点」を指す番号（Linux などではファイルディスクリプタ）です。アプリケーションがソケットにデータを書き込むと、OS のプロトコルスタックがそれを TCP のセグメントや UDP のデータグラムに詰めて送り出し、届いたデータは OS が受信バッファに蓄えて、アプリケーションが読み出すのを待ちます。再送や順序の整列、フロー制御といった TCP の仕事（「:doc:`n05_transport_layer`」を参照）はすべて OS の中で行われ、アプリケーションは関与しません。

ソケットを作るときは、アドレスファミリ（どの種類のアドレスを使うか）とソケット型（どのような通信をするか）を指定します。

.. list-table:: 主なアドレスファミリとソケット型
   :header-rows: 1
   :widths: 30 25 45

   * - 指定
     - 意味
     - 備考
   * - ``AF_INET``
     - IPv4
     - アドレスは ``("127.0.0.1", 80)`` のような（ホスト、ポート番号）の組
   * - ``AF_INET6``
     - IPv6
     - アドレスは（ホスト、ポート番号、フロー情報、スコープ ID）の組
   * - ``SOCK_STREAM``
     - ストリーム型
     - IP と組み合わせると TCP
   * - ``SOCK_DGRAM``
     - データグラム型
     - IP と組み合わせると UDP

「:doc:`n05_transport_layer`」で説明したとおり、TCP のコネクションは 5 タプル（プロトコル、送信元と宛先の IP アドレスとポート番号）で識別されます。そのため、サーバーは 1 つのポート番号で多数のクライアントと同時に通信でき、ソケットもコネクションごとに別々に作られます（後で説明する接続済みソケット）。

TCP のソケット API
------------------

TCP では、サーバーとクライアントで使う関数の並びが異なります。

.. list-table:: TCP のソケット API の流れ
   :header-rows: 1
   :widths: 22 38 40

   * - 関数
     - 呼ぶ側と役割
     - TCP での動き
   * - ``socket()``
     - 両方。ソケットの作成
     - （通信なし）
   * - ``bind()``
     - 主にサーバー。待ち受ける IP アドレスとポート番号の割り当て
     - （通信なし）
   * - ``listen()``
     - サーバー。接続の受け付けの開始
     - SYN を受け付ける状態（LISTEN）への移行
   * - ``connect()``
     - クライアント。サーバーへの接続
     - 3 ウェイハンドシェイク（完了まで待つ）
   * - ``accept()``
     - サーバー。確立したコネクションの取り出し
     - ハンドシェイクを終えたコネクションの待ち行列からの取り出し
   * - ``send()``、``recv()``
     - 両方。データの送受信
     - 送信バッファへの書き込み、受信バッファからの読み出し
   * - ``shutdown()``
     - 両方。片方向の通信の終了
     - ``SHUT_WR`` の場合は FIN の送信
   * - ``close()``
     - 両方。ソケットの解放
     - FIN の送信（未読のデータが残っている場合は RST になることもあります）

リッスンソケットと接続済みソケット
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

サーバーのプログラムでは、2 種類のソケットを区別することが大切です。``listen()`` を呼んだソケット（リッスンソケット）は接続の受け付け専用で、データの送受信には使いません。``accept()`` を呼ぶと、クライアントとのコネクションごとに新しいソケット（接続済みソケット）が作られて返され、データのやり取りはこちらで行います。リッスンソケットは 1 つで、接続済みソケットはクライアントの数だけできます。

``accept()`` はハンドシェイクを行う関数ではないことにも注意してください。3 ウェイハンドシェイクは OS がアプリケーションとは無関係に済ませ、確立したコネクションを待ち行列に入れておきます。``accept()`` は、その待ち行列からコネクションを 1 つ取り出すだけです。``listen()`` の引数（バックログ）は、この待ち行列の長さの目安です。アプリケーションが ``accept()`` を呼ぶ速さより速く接続が来て待ち行列があふれると、新しい接続の SYN は破棄されたり拒否されたりします（どちらになるかは OS によって異なります）。

送信と受信の意味
~~~~~~~~~~~~~~~~

``send()`` が戻ったことは、データが相手に届いたことを意味しません。OS の送信バッファにコピーされたことを意味するだけです。また ``send()`` は、送信バッファの空きによっては、渡したデータの一部だけを受け付けて、受け付けたバイト数を返すことがあります。すべてを送るまで繰り返す必要があるので、Python では、それを内部で行う ``sendall()`` を使うのが普通です。

``recv(n)`` は、受信バッファにあるデータを最大 ``n`` バイト返します。データがなければ届くまで待ち（ブロックし）、相手が FIN を送ってきて、もう読むデータがないときは空のバイト列を返します。空のバイト列は「相手が送信を終えた」という意味の、重要な合図です。

TCP エコーサーバーとクライアント
--------------------------------

受け取ったデータをそのまま送り返すエコーサーバーは、ソケットプログラミングの最も基本的な例です。サンプルコード :download:`tcp_echo_server.py <../examples/tcp_echo_server.py>` は、クライアントを 1 つずつ順番に処理するエコーサーバーです。

.. literalinclude:: ../examples/tcp_echo_server.py
   :language: python
   :linenos:
   :caption: tcp_echo_server.py

``serve`` 関数の ``socket()``、``bind()``、``listen()``、``accept()`` が、前の節の表の流れに対応しています。待ち受けるアドレスを ``127.0.0.1`` にしているので、同じコンピューターからしか接続できません。``0.0.0.0`` にするとすべてのネットワークインターフェースで待ち受けるので、他のコンピューターからも接続できるようになりますが、意図せずサービスを外部に公開してしまう原因にもなります。

リッスンソケットに ``settimeout()`` で短いタイムアウトを設定しているのは、Windows では ``accept()`` で待っている間に Ctrl+C を押しても、``KeyboardInterrupt`` がすぐには発生しないためです。0.5 秒ごとに待ちを抜けることで、Ctrl+C を受け付けられるようにしています。

``SO_REUSEADDR`` は、サーバーを終了した直後に同じポート番号で再起動するための設定です。「:doc:`n05_transport_layer`」で説明したとおり、先に接続を閉じた側のコネクションはしばらく TIME_WAIT の状態で残ります。Linux などでは、この状態のコネクションがあると、設定なしでは同じポート番号に ``bind()`` できません。一方 Windows の ``SO_REUSEADDR`` は、他のプログラムが使用中のポート番号にも ``bind()`` できてしまうという別の意味を持つため、設定していません。

サンプルコード :download:`tcp_echo_client.py <../examples/tcp_echo_client.py>` は、これに接続するクライアントです。

.. literalinclude:: ../examples/tcp_echo_client.py
   :language: python
   :linenos:
   :caption: tcp_echo_client.py

``socket.create_connection()`` は、名前解決、ソケットの作成、``connect()`` をまとめて行う関数です。名前解決で複数のアドレス（IPv6 と IPv4 など）が得られた場合は、順に接続を試みます。

送信後の ``shutdown(socket.SHUT_WR)`` は、「これ以上送るデータはない」ことを相手に伝える操作で、TCP では FIN が送られます。受信の方向は開いたままなので、クライアントはこの後もサーバーからの返信を受け取れます。サーバーの ``recv()`` は、データを読み終えた後に空のバイト列を返すので、サーバーはそれを見て返信を終え、接続を閉じます。このように片方向だけを閉じることをハーフクローズと呼びます。

2 つの端末を開き、一方でサーバーを、もう一方でクライアントを起動します。

.. code-block:: console
   :linenos:

   > python tcp_echo_server.py
   > python tcp_echo_client.py こんにちは
   > python tcp_echo_client.py "Hello, TCP"

1 行目をサーバーの端末で、2 行目と 3 行目をクライアントの端末で実行します。クライアント側の実行結果は次のとおりです（クライアントのポート番号は実行のたびに変わります）。

.. code-block:: text

   接続: 127.0.0.1:52566 -> 127.0.0.1:50007
   送信 15 バイト: こんにちは
   受信 15 バイト
   サーバーからの返信: こんにちは
   接続: 127.0.0.1:52570 -> 127.0.0.1:50007
   送信 10 バイト: Hello, TCP
   受信 10 バイト
   サーバーからの返信: Hello, TCP

サーバー側の表示は次のとおりです。最後の 2 行は、Ctrl+C を押してサーバーを終了したときのものです。

.. code-block:: text

   待ち受け中: 127.0.0.1:50007（Ctrl+C で終了）
   接続: 127.0.0.1:52566
     受信 15 バイト: b'\xe3\x81\x93\xe3\x82\x93\xe3\x81\xab\xe3\x81\xa1\xe3\x81\xaf'
   切断: 127.0.0.1:52566（合計 15 バイトを返信）
   接続: 127.0.0.1:52570
     受信 10 バイト: b'Hello, TCP'
   切断: 127.0.0.1:52570（合計 10 バイトを返信）

   Ctrl+C を受け付けたので、サーバーを終了します

「こんにちは」の 5 文字が 15 バイトになっているのは、UTF-8 では平仮名 1 文字が 3 バイトで表されるからです。ソケットが扱うのは文字列ではなくバイト列なので、送る側と受け取る側で文字コードを決めておき、``encode()`` と ``decode()`` で変換する必要があります。

サーバーを起動せずにクライアントを実行すると、「接続を拒否されました」と表示されます。サーバーのコンピューターには届いたものの、そのポート番号で待ち受けているプログラムがないため、OS が RST を返したからです。

UDP のソケット
--------------

UDP では、コネクションを確立する手順がありません。``bind()`` したソケットで ``recvfrom()`` を呼んで待ち、送る側は ``sendto()`` で宛先を指定してデータグラムを送ります。

.. code-block:: python
   :linenos:

   import socket

   # 受信側：ポート番号 0 で bind し、OS に番号を選ばせる
   rx = socket.socket(socket.AF_INET, socket.SOCK_DGRAM)
   rx.bind(("127.0.0.1", 0))
   addr = rx.getsockname()

   # 送信側：コネクションを確立せず、宛先を指定して送る
   tx = socket.socket(socket.AF_INET, socket.SOCK_DGRAM)
   tx.sendto(b"apple", addr)
   tx.sendto(b"banana", addr)

   # 1 回の recvfrom() で 1 つのデータグラムを受け取る
   print(rx.recvfrom(4096))
   print(rx.recvfrom(4096))

実行結果の例は次のとおりです。

.. code-block:: text

   (b'apple', ('127.0.0.1', 57847))
   (b'banana', ('127.0.0.1', 57847))

``recvfrom()`` は、データと送信元のアドレスの組を返します。サーバーは、このアドレスに ``sendto()`` で返信します。

UDP と TCP のプログラムの違いとして、次の点に注意が必要です。

* メッセージの境界が保たれます。2 回の ``sendto()`` で送ったデータは、2 回の ``recvfrom()`` で別々に受け取ります。
* データグラムは失われることがあり、順序が入れ替わることもあり、重複することもあります。必要ならアプリケーションが番号を付け、再送やタイムアウトを自分で実装します。
* ``recvfrom()`` に渡すバッファがデータグラムより小さいと、あふれた分は捨てられます（Windows ではエラーになります）。
* データグラムの大きさには上限があります。IPv4 の UDP では理論上 65,507 バイトですが、MTU を超えると IP の断片化が起きて失われやすくなるため、実際にはもっと小さく保つのが普通です。
* UDP のソケットにも ``connect()`` を呼べます。この場合は宛先を固定するだけで、パケットは送られません。ただし Linux などでは、相手のポートが閉じていることを示す ICMP のエラーを、以降の ``recv()`` の例外（``ConnectionRefusedError``）として受け取れるようになります。

バイトストリームとフレーミング
------------------------------

TCP でプログラムを書くときに最もつまずきやすいのが、メッセージの境界の問題です。TCP はアプリケーションに対してバイトの並び（バイトストリーム）を順序どおりに届けますが、送信側が ``send()`` を呼んだ単位は保存しません。3 回に分けて送ったデータが受信側では 1 回の ``recv()`` でまとめて読めることもあれば、逆に 1 回で送ったデータが何回かに分かれて届くこともあります。どう分かれるかは、Nagle のアルゴリズム、MSS、受信側が ``recv()`` を呼ぶタイミングなどによって変わり、アプリケーションからは制御できません。

localhost でのテストでは、たまたま送ったとおりの単位で読めることが多いため、この問題に気付かないまま本番環境で不具合を起こすことがよくあります。

そこで、バイトストリームの中にメッセージの区切りを示す約束を設けます。これをフレーミングと呼びます。代表的な方法は次の 3 つです。

.. list-table:: フレーミングの方法
   :header-rows: 1
   :widths: 20 45 35

   * - 方法
     - 仕組み
     - 使われている例
   * - 区切り文字
     - メッセージの終わりに置く、改行などの決まったバイト列。本文に区切り文字が現れる場合はエスケープが必要
     - SMTP（メールの送信に使うプロトコル）のコマンド、HTTP/1.1 のヘッダー
   * - 長さの前置
     - メッセージの前に置く、決まったバイト数の長さの情報
     - HTTP/1.1 の ``Content-Length``、TLS のレコード、HTTP/2 のフレーム
   * - 固定長
     - すべてのメッセージを同じ長さにそろえる方式
     - 一部の業務システムの電文

長さの前置は、本文にどのようなバイトが含まれていても扱え、受信側が必要なバッファの大きさを事前に知れるため、バイナリのプロトコルでよく使われます。サンプルコード :download:`framing.py <../examples/framing.py>` は、まずフレーミングなしで境界が失われる様子を示し、次に 4 バイトのビッグエンディアンの整数で長さを前置する方法でメッセージを正しく取り出します。

   :language: python
   :linenos:

実行結果は次のとおりです。

.. code-block:: text

   == 1. フレーミングなし ==
     送信: b'apple'
     送信: b'banana'
     送信: b'cherry'
     1 回の recv() で受信: b'applebananacherry'
     -> 3 回の送信の境界は、受信側からは区別できません

   == 2. 長さの前置によるフレーミング ==
     受信 1: 5 バイト 'apple'
     受信 2: 6 バイト 'banana'
     受信 3: 15 バイト 'こんにちは'
     4 つ目のメッセージ（細切れに届く）:
       recv(): 2 バイト（要求 4）
       recv(): 2 バイト（要求 2）
       recv(): 3 バイト（要求 10）
       recv(): 7 バイト（要求 7）
     受信 4: 10 バイト '0123456789'
     -> 送信したとおりの単位でメッセージを取り出せました

前半では、3 回の ``sendall()`` で送ったデータが 1 回の ``recv()`` でつながって読めています。後半の 4 つ目のメッセージでは、送信側がヘッダーの途中で区切って送ったため、4 バイトを要求した ``recv()`` が 2 バイトしか返していません。``recv_exact`` 関数は、要求したバイト数がそろうまで ``recv()`` を繰り返すことで、この状況を正しく処理しています。

長さの前置を実装するときは、次の点に注意します。

* 整数のバイト順（エンディアン）を決めておきます。ネットワークのプロトコルでは、ビッグエンディアン（ネットワークバイトオーダー）を使うのが慣例です。``struct`` モジュールの書式 ``"!I"`` の ``!`` がこれを表します。
* 受け取った長さに上限を設けます。上限がないと、悪意のある相手が巨大な長さを送るだけで、受信側に大量のメモリを確保させられます。
* メッセージの途中で接続が切れた場合と、メッセージの切れ目で接続が切れた場合を区別します。前者は異常、後者は正常な終了です。

区切り文字を使う場合も、受信側は「区切り文字が現れるまでバッファにためる」処理が必要になる点は同じです。Python の ``socket.makefile()`` や asyncio の ``StreamReader.readline()`` は、この処理を代わりに行ってくれます。

タイムアウトとエラー処理
------------------------

ネットワークの通信では、相手が応答しない、途中で接続が切れる、といったことが日常的に起こります。ソケットの関数は既定ではブロッキング（完了するまで待つ）で、タイムアウトもありません。相手のコンピューターが電源ごと落ちた場合などは、``recv()`` が永遠に戻らないこともあります。ネットワークを使う処理には、必ずタイムアウトを設定します。

Python では、``settimeout()`` でソケットにタイムアウトを設定するか、``create_connection()`` の引数 ``timeout`` で指定します。タイムアウトは個々の ``recv()`` や ``send()`` の呼び出しごとの上限で、処理全体の上限ではないことに注意してください。少しずつデータを送ってくる相手に対しては、全体の期限を別に管理する必要があります。

ソケットの操作で起きる主な例外は次のとおりです。

.. list-table:: ソケットの操作で起きる主な例外（Python）
   :header-rows: 1
   :widths: 30 70

   * - 例外
     - 主な原因
   * - ``socket.gaierror``
     - 名前解決の失敗（ホスト名の誤り、DNS サーバーに届かないなど）
   * - ``ConnectionRefusedError``
     - 相手のポートで待ち受けるプログラムの不在（RST を受信）
   * - ``TimeoutError``
     - 設定したタイムアウトまでに操作が未完了（パケットの破棄、相手の停止など）
   * - ``ConnectionResetError``
     - 通信中に相手から RST を受信（相手のプログラムの異常終了など）
   * - ``BrokenPipeError``
     - 相手が閉じたコネクションへの送信
   * - ``OSError``\ （その他）
     - 経路がない、ネットワークに到達できない、ポート番号が使用中など

接続の失敗を「接続拒否」と「タイムアウト」に区別できると、原因の切り分けに役立ちます。この区別を使った疎通確認のサンプルは「:doc:`n10_network_troubleshooting`」で紹介します。

もう 1 つ注意が必要なのは、TCP は何も送っていない間は相手の消失に気付けないことです。相手のコンピューターが突然停止したり、途中の NAT やファイアウォールがコネクションの情報を捨てたりしても、こちらのソケットは開いたままで、待ち続けます。これを防ぐには、TCP のキープアライブ（``SO_KEEPALIVE``）を有効にするか、アプリケーションのプロトコルで定期的にハートビートのメッセージをやり取りし、一定時間応答がなければ切断します。

複数のクライアントを扱う
------------------------

前に示したエコーサーバーは、1 つのクライアントの処理が終わるまで次の ``accept()`` を呼ばないため、あるクライアントが時間のかかる通信をしていると、他のクライアントは待たされます。複数のクライアントを同時に扱う方法は、大きく 3 つあります。

スレッドを使う
~~~~~~~~~~~~~~

最も素直な方法は、コネクションごとにスレッドを作ることです。

.. code-block:: python
   :linenos:

   import socket
   import threading


   def handle(conn: socket.socket) -> None:
       with conn:
           while data := conn.recv(4096):
               conn.sendall(data)


   with socket.create_server(("127.0.0.1", 50007)) as server:
       while True:
           conn, _ = server.accept()
           t = threading.Thread(target=handle, args=(conn,), daemon=True)
           t.start()

各スレッドは、ブロッキングの ``recv()`` を使った単純な逐次処理のコードのまま書けます。一方、コネクションの数だけスレッドが必要で、スレッドごとにスタックのメモリを使い、切り替えの費用もかかります。数千を超えるコネクションを同時に扱うと、資源の消費が問題になります。スレッドの数に上限を設けるには、``concurrent.futures.ThreadPoolExecutor`` などのスレッドプールを使います。

I/O 多重化
~~~~~~~~~~

1 つのスレッドで多数のソケットを扱う方法が I/O 多重化です。ソケットをノンブロッキング（操作をすぐに完了できなければ待たずにエラーを返す）にしておき、「読み込めるようになったソケット」を OS にまとめて問い合わせ、準備のできたものだけを処理します。問い合わせの仕組みには、古くからある ``select`` と ``poll`` のほか、多数のソケットを効率よく扱える OS 固有のもの（Linux の epoll、BSD 系や macOS の kqueue）があります。Python の ``selectors`` モジュールは、これらのうちその OS で最も効率のよいものを選んで使います。

.. code-block:: python
   :linenos:

   import selectors
   import socket

   sel = selectors.DefaultSelector()


   def accept(server: socket.socket) -> None:
       conn, _ = server.accept()
       conn.setblocking(False)
       sel.register(conn, selectors.EVENT_READ, echo)


   def echo(conn: socket.socket) -> None:
       data = conn.recv(4096)
       if data:
           conn.sendall(data)  # 簡略化（下の説明を参照）
       else:
           sel.unregister(conn)
           conn.close()


   server = socket.create_server(("127.0.0.1", 50007))
   server.setblocking(False)
   sel.register(server, selectors.EVENT_READ, accept)
   while True:
       # 読み込める状態になったソケットができるまで待つ（最大 0.5 秒）
       for key, _ in sel.select(timeout=0.5):
           key.data(key.fileobj)

``sel.select()`` は、登録したソケットのうち読み込める状態になったものを返します。リッスンソケットが読み込める状態になったのは新しい接続が来たとき、接続済みソケットが読み込める状態になったのはデータか FIN が届いたときです。登録時に渡した関数（``accept`` または ``echo``）を呼び出して処理します。

この例は短くするために簡略化しています。ノンブロッキングのソケットで ``sendall()`` を呼ぶと、送信バッファがいっぱいのときに ``BlockingIOError`` が起きます。正しくは、送れなかったデータを保存しておき、``EVENT_WRITE`` で書き込めるようになったことを確かめてから続きを送ります。また、受信したデータのフレーミングも、ソケットごとのバッファを持って自分で管理する必要があります。このように、I/O 多重化は効率がよい反面、処理を細切れのコールバックに分けて状態を自分で管理するため、コードが複雑になりやすい方法です。

1 台のサーバーで 1 万のクライアントを同時に扱う難しさは、1999 年にケーゲル（Dan Kegel）が「C10K 問題」として取り上げ、epoll や kqueue のような仕組みが広まるきっかけの 1 つになりました。nginx や Node.js、Redis などは、I/O 多重化を中心に設計されています。なお、Windows では、入出力の完了を通知する IOCP（I/O Completion Port）という別の方式が高性能なサーバーで使われます。

asyncio
~~~~~~~

I/O 多重化の効率を保ったまま、逐次処理に近い読みやすいコードで書けるようにしたのが、Python の ``asyncio`` です。``async def`` で定義したコルーチンの中で ``await reader.readline()`` のように書くと、データが届くまでの間、そのコルーチンは中断され、イベントループが他のコルーチンを実行します。データが届くとイベントループが中断した箇所から再開させます。内部では、前の節で見た I/O 多重化の仕組みが使われています。

サンプルコード :download:`asyncio_chat_server.py <../examples/asyncio_chat_server.py>` は、asyncio を使ったチャットサーバーです。改行区切りのテキストをプロトコルとし、クライアントが最初に送る 1 行を名前として、以降に送った行を参加者全員に配信します。単体で実行すると、サーバーを起動し、3 つのクライアントを接続してメッセージをやり取りする様子を表示して終了します。``--serve`` オプションを付けると、サーバーとして常駐します。

サーバーと 3 つのクライアントは、すべて 1 つのスレッドの 1 つのイベントループの上で動いています。``ChatServer.handle`` は接続ごとに別々のタスクとして実行され、それぞれが ``readline()`` で待っている間も、他のタスクの処理は進みます。

``broadcast`` メソッドの ``await writer.drain()`` は、送信バッファにたまったデータが一定量を超えている場合に、減るまで待つ処理です。これを省くと、受信の遅いクライアントに向けたデータがサーバーのメモリにたまり続けます。ただし、この実装では全員への送信を順に待つため、1 人の受信が極端に遅いと全員への配信が遅れます。実用的なサーバーでは、クライアントごとに送信用のキューとタスクを持ち、キューがあふれたクライアントは切断する、といった工夫をします。

asyncio を使う場合は、コルーチンの中でブロッキングの関数（``time.sleep()`` や、同期的な通信を行うライブラリなど）を呼ばないことが重要です。呼ぶとイベントループ全体が止まり、すべてのクライアントの処理が止まります。

実装上の注意
------------

ここまでの内容を含めて、ソケットを使うプログラムを書くときの注意点をまとめます。

* ``send()`` ではなく ``sendall()`` を使います。``recv()`` は要求より少ないバイト数を返すことがある前提で書きます。
* TCP にはメッセージの境界がないので、プロトコルにフレーミングを必ず定めます。
* すべての通信にタイムアウトを設定します。接続の確立、読み込み、処理全体のそれぞれの期限を考えます。
* ソケットは ``with`` 文や ``finally`` で確実に閉じます。閉じ忘れるとファイルディスクリプタが枯渇し、新しい接続を受け付けられなくなります。
* 受け取るデータの大きさに上限を設け、相手から届くデータは常に検証します。
* 待ち受けるアドレスは必要最小限にします。開発中のサーバーを ``0.0.0.0`` で待ち受けると、同じネットワークの他のコンピューターから接続できてしまいます。
* 小さなメッセージを何度も送って応答を待つプロトコルでは、Nagle のアルゴリズムと遅延 ACK の組み合わせで遅延が増えることがあります（「:doc:`n05_transport_layer`」を参照）。メッセージをまとめて 1 回で送るか、``TCP_NODELAY`` オプションで Nagle のアルゴリズムを無効にします。
* IPv4 のアドレスを決め打ちせず、``getaddrinfo()`` や ``create_connection()`` を使って IPv6 にも対応できるようにします。
* 実際のサービスでは、通信を TLS で暗号化します（「:doc:`n08_network_security`」を参照）。Python では ``ssl`` モジュールでソケットを包みます。

また、HTTP のように既存のプロトコルがある場合は、ソケットで一から実装するよりも、実績のあるライブラリを使う方が安全です。ソケットを直接扱う知識は、そうしたライブラリの挙動を理解したり、問題を調べたりするときに役立ちます。

まとめ
------

* ソケットは OS が提供するネットワーク通信のインターフェースで、TCP では ``socket()``、``bind()``、``listen()``、``accept()``、``connect()`` などの関数を使います。3 ウェイハンドシェイクや再送は OS が行います。
* TCP はバイトストリームでメッセージの境界を保存しないため、区切り文字や長さの前置によるフレーミングが必要です。``recv()`` が一部しか返さない場合にも備えます。
* UDP はメッセージの境界を保ちますが、失われることや順序が入れ替わることを前提に設計します。
* ネットワークの処理には必ずタイムアウトを設定し、名前解決の失敗、接続拒否、タイムアウトなどのエラーを区別して扱います。
* 複数のクライアントを同時に扱うには、スレッド、I/O 多重化、asyncio の方法があり、書きやすさと効率に違いがあります。
