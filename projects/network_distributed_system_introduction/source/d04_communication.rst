分散システムの通信
==================

この章では、分散システムを構成するノードどうしが、ネットワークを通じてどのように協調するかを説明します。リクエストを送って結果を待つ同期的な呼び出しと、メッセージを預けて先に進む非同期的な通信の違いから始め、RPC と gRPC、データのシリアライズ、メッセージキューと pub/sub を取り上げます。後半では、ネットワークが失敗し得ることを前提に、配信保証、冪等性、タイムアウトとリトライ、指数バックオフとジッターといった、安全に通信するための考え方を説明します。

同期的な通信と非同期的な通信
----------------------------

分散システムのノードどうしの通信は、大きく 2 つの形に分けられます。

* 同期的な通信：送信側がリクエストを送り、レスポンスが返るまで待ってから次の処理に進みます。HTTP の API 呼び出しや RPC が代表例です。
* 非同期的な通信：送信側はメッセージを送ったら（あるいは仲介役に預けたら）、相手の処理の完了を待たずに先に進みます。メッセージキューや pub/sub が代表例です。

同期的な通信は、プログラムの流れが分かりやすく、結果をすぐに使えるという利点があります。一方で、呼び出し先が遅かったり停止していたりすると、呼び出し元もその影響を直接受けます。呼び出し先がさらに別のサービスを同期的に呼び出していると、1 つのサービスの遅れが呼び出しの連鎖をさかのぼって広がります。

非同期的な通信では、送信側と受信側が同時に動いている必要がありません。受信側が一時的に停止していても、メッセージは仲介役に蓄えられ、受信側が復帰してから処理されます。これを時間的な結合が弱い（疎結合である）と表現します。その代わり、処理結果がすぐには分からない、メッセージの順序や重複を考える必要がある、といった難しさが生じます。

.. list-table:: 同期的な通信と非同期的な通信の比較
   :header-rows: 1
   :widths: 24 38 38

   * - 観点
     - 同期的な通信
     - 非同期的な通信
   * - 代表例
     - HTTP の API、RPC、gRPC
     - メッセージキュー、pub/sub
   * - 結果の受け取り
     - その場でレスポンスとして受信
     - 後で別の経路（コールバック、別のメッセージ）で通知
   * - 相手の停止の影響
     - 呼び出しが失敗（またはタイムアウトまで待機）
     - メッセージを蓄え、復帰後に処理
   * - 負荷の急増への耐性
     - 呼び出し先に負荷がそのまま波及
     - 仲介役が緩衝材となり、受信側は自分のペースで処理可能
   * - 主な難しさ
     - 遅延と障害の連鎖
     - 順序、重複、結果の追跡

実際のシステムでは両者を組み合わせます。例えば EC サイトでは、在庫の確認のようにユーザーが結果を待つ処理は同期的に行い、確認メールの送信や集計のように後で行えばよい処理は非同期的に行うのが一般的です。

RPC と gRPC
-----------

RPC の考え方
~~~~~~~~~~~~

RPC（Remote Procedure Call）は、別のコンピューターにある関数（手続き）を、手元の関数と同じような書き方で呼び出せるようにする仕組みです。1984 年にバーレル（Andrew D. Birrell）とネルソン（Bruce Jay Nelson）が発表した論文で実装方法が体系的に示され、その後の多くの RPC の基礎となりました（「:doc:`d02_distributed_history`」も参照してください）。

RPC では、呼び出し元にクライアントスタブ、呼び出し先にサーバースタブと呼ばれるコードを置きます。クライアントスタブは、引数をバイト列に変換（シリアライズ）してネットワークに送り、サーバースタブはそれを元に戻して本来の関数を呼び出します。戻り値も同じ手順で呼び出し元に返されます。スタブは、後述するインターフェース定義から自動生成されるのが普通です。

RPC は通信を関数呼び出しに見せかけますが、ネットワーク越しの呼び出しは、ローカルな関数呼び出しとは本質的に異なります。この違いを意識しないことが、分散システムの多くの不具合の原因になります。

.. list-table:: ローカルな関数呼び出しとリモート呼び出しの違い
   :header-rows: 1
   :widths: 22 39 39

   * - 観点
     - ローカルな関数呼び出し
     - リモート呼び出し
   * - 失敗の仕方
     - 戻り値か例外が必ず返ります
     - レスポンスが返らないことがあり、相手が処理したかどうかが分かりません
   * - 所要時間
     - ほぼ一定で短時間（ns 〜 μs）
     - ネットワークと相手の状態によって大きく変動（ms 〜 秒）
   * - 引数の渡し方
     - ポインターや参照の受け渡しが可能
     - 値のシリアライズが必要
   * - 呼び出し先の状態
     - 呼び出し元と同じプロセス内で動作
     - 別のノードで独立に停止・再起動

特に 1 行目の「相手が処理したかどうかが分からない」という性質は重要です。この章の後半で説明する冪等性とリトライは、この問題に対処するための考え方です。

gRPC
~~~~

gRPC は、Google が開発し 2015 年にオープンソースとして公開した RPC のフレームワークです。次のような特徴があります。

* インターフェースとメッセージの形式を Protocol Buffers の定義ファイル（.proto ファイル）で記述し、そこから多数のプログラミング言語のスタブを生成します。
* 通信には HTTP/2 を使います。1 本のコネクションの上で複数の呼び出しを多重化できます（HTTP/2 については「:doc:`n07_http`」を参照してください）。
* 1 回のリクエストに 1 回のレスポンスを返す通常の呼び出し（unary）に加えて、サーバーからのストリーミング、クライアントからのストリーミング、双方向のストリーミングの 4 種類の呼び出し方を持ちます。
* 呼び出しにデッドライン（いつまでに完了すべきか）を設定でき、呼び出し先がさらに別のサービスを呼び出す場合にも、残り時間を伝えられます。

次は、送金サービスを定義した .proto ファイルの例です。``service`` でサービスと呼び出しを、``message`` でやり取りするデータの形式を定義します。

.. code-block:: protobuf
   :linenos:

   syntax = "proto3";

   package payment.v1;

   service PaymentService {
     // 1 回のリクエストに 1 回のレスポンス（unary）
     rpc Transfer(TransferRequest) returns (TransferResponse);
     // 取引の履歴をサーバーからストリーミングで返す
     rpc ListTransactions(ListTransactionsRequest)
         returns (stream Transaction);
   }

   message TransferRequest {
     string idempotency_key = 1;  // 冪等キー（後述）
     string from_account = 2;
     string to_account = 3;
     int64 amount = 4;
   }

   message TransferResponse {
     string transaction_id = 1;
     int64 balance = 2;
   }

   message ListTransactionsRequest {
     string account = 1;
   }

   message Transaction {
     string transaction_id = 1;
     int64 amount = 2;
   }

各フィールドの後ろの ``= 1`` などは、フィールドの名前ではなく、通信上でフィールドを識別するフィールド番号です。

gRPC は、サービス間の通信（マイクロサービスどうしの内部の通信など）で広く使われています。一方、ブラウザーから直接呼び出すには制約があるため、外部に公開する API には JSON を使う HTTP の API（いわゆる REST API）がよく使われます。

.. list-table:: JSON を使う HTTP の API と gRPC の比較
   :header-rows: 1
   :widths: 22 39 39

   * - 観点
     - JSON を使う HTTP の API
     - gRPC
   * - インターフェースの定義
     - 任意（OpenAPI などでの記述が一般的）
     - .proto ファイルが必須
   * - データの形式
     - JSON（テキスト）
     - Protocol Buffers（バイナリ）
   * - 通信
     - HTTP/1.1、HTTP/2、HTTP/3
     - HTTP/2
   * - ストリーミング
     - 標準では限定的
     - 4 種類の呼び出し方に標準で対応
   * - 人間による確認
     - curl やブラウザーで容易
     - 専用のツールが必要
   * - 主な用途
     - 外部に公開する API、ブラウザーからの呼び出し
     - サービス間の内部の通信

シリアライズ
------------

メモリ上のデータ構造（オブジェクト、構造体、辞書など）を、ネットワークで送ったりファイルに保存したりできるバイト列に変換することをシリアライズ（エンコード、マーシャリング）と呼び、その逆をデシリアライズと呼びます。送信側と受信側が異なる言語で書かれていても通信できるよう、言語に依存しない形式を使うのが普通です。

JSON
~~~~

JSON（JavaScript Object Notation）は、人間が読めるテキストの形式で、Web の API で最も広く使われています。上の送金リクエストを JSON で表すと次のようになります。

.. code-block:: json
   :linenos:

   {
     "idempotency_key": "7f3c9a2e-0001",
     "from_account": "A-1001",
     "to_account": "B-2002",
     "amount": 3000
   }

JSON は手軽で、ほぼすべての言語で扱えます。一方で、次のような弱点があります。

* フィールド名を毎回送るため、データが大きくなります。
* 数値の範囲や精度が仕様で決まっていません。多くの JavaScript の実装では数値を倍精度浮動小数点数として扱うため、:math:`2^{53}` を超える整数は正確に表せません。大きな ID を文字列として送る API が多いのはこのためです。
* バイナリデータを直接表せないため、Base64 などで文字列に変換する必要があります。
* スキーマ（どのフィールドがどの型か）が形式の一部ではないため、送信側と受信側の食い違いは実行時まで分かりません。

Protocol Buffers
~~~~~~~~~~~~~~~~

Protocol Buffers は Google が開発したバイナリのシリアライズ形式で、2008 年にオープンソースとして公開されました。.proto ファイルでスキーマを定義し、そこから各言語のコードを生成して使います。通信上ではフィールド名の代わりにフィールド番号を送るため、JSON よりも小さく、解析も高速です。

分散システムでは、すべてのノードを同時に更新することはできません。新しい版と古い版のプログラムが混在する期間があるため、データの形式を変更しても互いに通信できることが重要です。

* 後方互換性：新しい版のプログラムが、古い版が書いたデータを読めること。
* 前方互換性：古い版のプログラムが、新しい版が書いたデータを読めること。

Protocol Buffers では、新しいフィールドを新しい番号で追加しても、古い版のプログラムは知らない番号のフィールドを読み飛ばすので、両方向の互換性を保てます。一方、既存のフィールドの番号や型を変えると互換性が失われます。フィールドを削除する場合は、その番号を ``reserved`` として予約し、別の意味で再利用されないようにします。

.. list-table:: 代表的なシリアライズ形式
   :header-rows: 1
   :widths: 22 18 18 42

   * - 形式
     - 表現
     - スキーマ
     - 特徴
   * - JSON
     - テキスト
     - 不要
     - 人間が読める形式。Web の API で標準的
   * - XML
     - テキスト
     - 任意
     - 冗長だが表現力の高い形式。企業システムで広く利用
   * - Protocol Buffers
     - バイナリ
     - 必須
     - 小さく高速。gRPC の標準の形式
   * - Apache Avro
     - バイナリ
     - 必須
     - スキーマをデータと一緒に扱う形式。大量のデータの処理基盤で利用

なお、Python の ``pickle`` のような言語固有の形式は、他の言語から読めないうえ、信頼できないデータをデシリアライズすると任意のコードを実行される危険があります。ネットワークを越える通信には使わないでください。

メッセージキュー
----------------

メッセージキューは、送信側（プロデューサー）と受信側（コンシューマー）の間に置かれ、メッセージを一時的に蓄える仕組みです。プロデューサーはメッセージをキューに入れたら先に進み、コンシューマーは自分のペースでキューからメッセージを取り出して処理します。代表的なソフトウェアやサービスに、RabbitMQ、Amazon SQS などがあります。

メッセージキューを使うと、次のような利点が得られます。

* 疎結合：プロデューサーはコンシューマーの数や所在を知る必要がなく、コンシューマーが一時的に停止していても送信できます。
* 負荷の平準化：アクセスが急増しても、メッセージがキューに溜まるだけで、コンシューマーは処理能力を超えて呼び出されません。
* 負荷分散：複数のコンシューマーで 1 つのキューを分担して処理すれば、処理能力を増やせます。

メッセージの確認応答と再配信
~~~~~~~~~~~~~~~~~~~~~~~~~~~~

コンシューマーがメッセージを取り出した直後に停止すると、そのメッセージは失われてしまうかもしれません。そこで多くのメッセージキューでは、コンシューマーが処理を終えてから確認応答（ack）を返し、ack を受け取った時点でキューがメッセージを削除します。一定時間内に ack が返らなければ、キューはメッセージを再び配信します（Amazon SQS ではこの時間を可視性タイムアウトと呼びます）。

この仕組みによってメッセージは失われにくくなりますが、代わりに同じメッセージが 2 回以上配信されることがあります。例えば、コンシューマーが処理を終えた直後、ack を返す前に停止すると、そのメッセージは別のコンシューマーに再配信され、もう一度処理されます。したがって、コンシューマーの処理は、同じメッセージを複数回受け取っても問題ないように作る必要があります（後述の冪等性）。

何度処理しても失敗するメッセージ（例えば形式が壊れているもの）を再配信し続けると、キューが詰まってしまいます。そのため、一定回数失敗したメッセージを別のキューに移して後で調べられるようにする、デッドレターキューという仕組みがよく使われます。

pub/sub
-------

pub/sub（publish/subscribe）は、送信側（パブリッシャー）がトピックと呼ばれる宛先にメッセージを発行し、そのトピックを購読しているすべての受信側（サブスクライバー）にメッセージが届けられる方式です。1 つのメッセージを複数の受信側に届ける（ファンアウト）点が、1 つのメッセージを 1 つのコンシューマーが処理するメッセージキューとの主な違いです。

例えば「注文が確定した」というイベントをトピックに発行すれば、在庫の引き当て、メールの送信、売上の集計といった複数のサービスがそれぞれ独立に受け取って処理できます。注文のサービスは、どのサービスがイベントを使っているかを知る必要がなく、新しいサービスを追加するときも注文のサービスを変更せずに済みます。

ログ型のメッセージング
~~~~~~~~~~~~~~~~~~~~~~

Apache Kafka に代表されるログ型のメッセージングシステムでは、トピックを追記専用のログとして保存します。メッセージは読まれても削除されず、設定した期間や容量まで保持されます。各メッセージには、ログの中の位置を表すオフセットが付けられ、受信側は「どのオフセットまで処理したか」を自分で記録しながら読み進めます。

この方式には次のような特徴があります。

* 複数の受信側が、同じログをそれぞれ自分のペースで読めます。
* オフセットを戻せば、過去のメッセージを再処理できます。不具合を修正した後に処理をやり直す場合などに役立ちます。
* トピックを複数のパーティションに分割し、パーティションごとに受信側を割り当てて並列に処理します。順序が保証されるのはパーティションの中だけです。

.. list-table:: メッセージキュー、pub/sub、ログ型の比較
   :header-rows: 1
   :widths: 22 26 26 26

   * - 観点
     - メッセージキュー
     - pub/sub
     - ログ型
   * - 1 つのメッセージの受信者
     - 1 つのコンシューマー
     - すべてのサブスクライバー
     - 受信側のグループごとに 1 つ
   * - 処理後のメッセージ
     - 削除
     - 多くは配信後に削除
     - 保持期間が過ぎるまで保存
   * - 過去のメッセージの再処理
     - 不可
     - 通常は不可
     - オフセットを戻して可能
   * - 主な用途
     - 作業の分担、負荷の平準化
     - イベントの通知
     - イベントの記録、データの連携

配信保証
--------

ネットワークやノードは失敗し得るため、メッセージを「ちょうど 1 回」相手に届けることは簡単ではありません。メッセージの配信について、システムが何を保証するかを配信保証（delivery semantics）と呼び、次の 3 つに分類します。

.. list-table:: 配信保証の 3 つの分類
   :header-rows: 1
   :widths: 20 40 40

   * - 分類
     - 意味と実現方法
     - 起こり得ること・注意点
   * - at-most-once
     - 高々 1 回。失敗してもリトライなし
     - メッセージの消失
   * - at-least-once
     - 少なくとも 1 回。確認応答が得られるまでリトライ
     - メッセージの重複
   * - exactly-once
     - ちょうど 1 回処理されたのと同じ結果
     - 実現にはリトライと重複排除の両方が必要

at-most-once は、メトリクスの送信のように、多少失われても困らないデータに使われます。at-least-once は、多くのメッセージキューの標準的な保証です。

exactly-once という言葉には注意が必要です。送信側は、確認応答が返らないとき、相手がメッセージを受け取っていないのか、受け取ったが確認応答が失われたのかを区別できません。そのため、ネットワーク上でメッセージを物理的にちょうど 1 回だけ届けることは一般にはできません。実際のシステムが exactly-once と呼んでいるものは、at-least-once で届けたうえで、受信側が重複を検出して捨てたり、何度処理しても結果が変わらないようにしたりすることで、結果として 1 回だけ処理されたのと同じ状態にするものです。このため effectively-once（実質的に 1 回）と呼ぶこともあります。Kafka のように、システムの内部で exactly-once の処理を提供するものもありますが、その保証が外部のシステム（メールの送信や他社の API の呼び出しなど）にまで及ぶわけではありません。

冪等性と冪等キー
----------------

冪等性
~~~~~~

ある操作を 1 回行っても、同じ操作を何回繰り返しても、結果が同じになる性質を冪等性（idempotency）と呼びます。冪等な操作は、結果が分からないときに安心してリトライできます。

* 冪等な操作の例：「残高を 7000 円に設定する」「注文 123 を削除する」「ユーザーの住所を X に変更する」
* 冪等でない操作の例：「残高から 3000 円を引く」「カウンターに 1 を足す」「新しい注文を作成する」

HTTP では、GET、PUT、DELETE などのメソッドは冪等と定められており、POST は冪等ではありません（「:doc:`n07_http`」を参照してください）。ただし、これはメソッドの意味の取り決めであり、実際にサーバーの実装が冪等になっているかどうかは別の問題です。

冪等キー
~~~~~~~~

送金や注文の作成のように、本質的に冪等でない操作を安全にリトライするための方法が冪等キー（idempotency key）です。クライアントは、操作ごとに一意な値（例えば UUID（Universally Unique Identifier））を生成してリクエストに付け、リトライするときも同じ値を使います。サーバーは、処理した冪等キーとその結果を記録しておき、同じキーのリクエストが再び届いたら、処理をせずに記録した結果を返します。

HTTP の API では、冪等キーをリクエストヘッダーで送る方式が広く使われており、IETF でも ``Idempotency-Key`` ヘッダーの標準化が検討されています。

.. code-block:: text
   :linenos:

   POST /v1/transfers HTTP/1.1
   Host: api.example.com
   Content-Type: application/json
   Idempotency-Key: 7f3c9a2e-0001

   {"from_account": "A-1001", "to_account": "B-2002", "amount": 3000}

冪等キーをサーバー側で実装するときは、次の点に注意します。

* 冪等キーの記録と、本来の処理（残高の更新など）を同じトランザクションで行います。別々に行うと、間で障害が起きたときに不整合が生じます。
* 同じキーのリクエストが同時に 2 つ届くことがあります。最初のリクエストの処理中に届いたものは、待たせるかエラーを返し、二重に処理しないようにします。
* 同じキーなのにリクエストの内容が異なる場合は、クライアントの誤りとしてエラーを返します。
* 記録をいつまで保持するかを決めます。リトライが起こり得る期間より長くする必要があります。

タイムアウトとリトライ
----------------------

タイムアウトの意味
~~~~~~~~~~~~~~~~~~

リモート呼び出しのレスポンスが返ってこないとき、待ち続けるわけにはいかないので、一定時間で諦めるタイムアウトを設定します。ここで重要なのは、タイムアウトが起きたとき、クライアントには何が起きたのかが分からないことです。「:doc:`d01_distributed_overview`」の部分障害の節で挙げた原因を大きく分けると、次の 3 つになります。

#. リクエストが途中で失われ、サーバーに届いていない場合
#. サーバーが停止している、または処理に時間がかかっている場合
#. サーバーは処理を終えたが、レスポンスが途中で失われた場合

1 番目の場合はリトライすべきですが、3 番目の場合にリトライすると、同じ処理が 2 回行われます。クライアントはこれらを区別できないため、リトライする操作は冪等であるか、冪等キーで保護されている必要があります。この「相手の状態が分からない」という不確実性は、分散システムに固有の部分障害の現れです。

タイムアウトの値は、短すぎると、正常だが少し遅いだけのリクエストまで失敗扱いになり、無駄なリトライが増えます。長すぎると、障害のときにクライアントが長く待たされ、待っている間に使われるスレッドやコネクションなどの資源が枯渇します。通常時のレスポンス時間の分布（例えば 99 パーセンタイル値）を測り、それより少し長い値にするのが一般的な出発点です。タイムアウトの設計については「:doc:`d09_reliability`」でも取り上げます。

リトライすべき失敗
~~~~~~~~~~~~~~~~~~

すべての失敗をリトライすべきではありません。リトライして成功する見込みがあるのは、一時的な原因による失敗だけです。

.. list-table:: HTTP の API でのリトライの判断の目安
   :header-rows: 1
   :widths: 40 15 45

   * - 失敗の種類
     - リトライ
     - 理由
   * - コネクションの確立の失敗、タイムアウト
     - あり
     - 一時的な障害の可能性（冪等な操作に限定）
   * - 503 Service Unavailable
     - あり
     - サーバーが一時的に処理できない状態
   * - 429 Too Many Requests
     - あり
     - レート制限。``Retry-After`` ヘッダーがあればその時間だけ待機
   * - 500 Internal Server Error
     - 状況次第
     - 一時的な原因とは限らないエラー
   * - 400 Bad Request、401 Unauthorized、404 Not Found
     - なし
     - リクエスト自体の問題。何度送っても同じ結果

なお、TCP は失われたセグメントを自動的に再送します（「:doc:`n05_transport_layer`」を参照してください）。しかし、TCP の再送はコネクションの中でのバイト列の配送を保証するだけで、サーバーのアプリケーションが処理を終えたかどうかまでは保証しません。コネクションが切れたりサーバーが再起動したりした場合には、アプリケーションのレベルでのリトライが必要です。

指数バックオフとジッター
------------------------

リトライするときに、失敗した直後にすぐ再送するのは良くありません。サーバーが過負荷で失敗している場合、すぐに再送すると負荷をさらに高めてしまいます。そこで、リトライのたびに待ち時間を倍々に延ばす指数バックオフ（exponential backoff）を使います。最初のリトライを :math:`n = 0` として、:math:`n` 番目のリトライの前の待ち時間の上限 :math:`t_n` を、基準値 :math:`b` と最大値 :math:`c` を使って次のように決めます。

.. math::

   t_n = \min\left(c,\ b \cdot 2^{n}\right)

ただし、すべてのクライアントがこの式どおりに待つと、別の問題が起きます。サーバーの障害で多数のクライアントが同時に失敗すると、それらのクライアントは同じ時刻に一斉にリトライし、復旧しかけたサーバーを再び過負荷にしてしまいます。そこで、待ち時間に乱数の揺らぎ（ジッター）を加えて、リトライの時刻を分散させます。よく使われる full jitter という方式では、0 から :math:`t_n` までの一様乱数を待ち時間とします。

.. math::

   \text{待ち時間} = \mathrm{random}\left(0,\ \min\left(c,\ b \cdot 2^{n}\right)\right)

このほかに、:math:`t_n` の半分を固定で待ち、残りの半分を乱数にする equal jitter などの方式もあります。また、リトライの回数か合計の時間に上限を設け、それを超えたら諦めて呼び出し元に失敗を返します。

サンプルコード :download:`retry_backoff.py <../examples/retry_backoff.py>` は、一定の確率で失敗する模擬サーバーに対して、指数バックオフと full jitter でリトライする例です。さらに、多数のクライアントが同時に失敗したときのリトライの時刻を、ジッターの有無で比べます。最後に、送金のレスポンスが失われてクライアントがリトライしたときに、冪等キーの有無で結果がどう変わるかを示します。待ち時間は実際に ``time.sleep`` で待ちますが、基準値を 10 ms と小さくしているので、すぐに終わります。

リトライストーム
----------------

リトライは一時的な障害を乗り越えるのに役立ちますが、使い方を誤ると、障害を拡大させる原因にもなります。サーバーが過負荷で応答できなくなったとき、クライアントが一斉にリトライすると、サーバーに届くリクエストが増えてさらに過負荷になり、回復できなくなります。このような悪循環をリトライストームと呼びます。

リトライストームは、サービスが何層にも呼び出し合っている場合に特に深刻になります。各層が失敗時に最大 :math:`a` 回の試行（最初の 1 回を含む）を行い、呼び出しが :math:`k` 層にわたっているとすると、最も下の層のサービスが失敗し続けたとき、そこに届くリクエストは最大で次の倍数に増えます。

.. math::

   a^{k}

例えば、3 層のサービスがそれぞれ 3 回まで試行すると、最も下の層には元のリクエストの :math:`3^{3} = 27` 倍のリクエストが届くことがあります。

リトライストームを防ぐには、次のような対策を組み合わせます。

* 指数バックオフとジッターを使い、リトライの間隔を空けて分散させます。
* リトライの回数に上限を設けます。また、リトライは呼び出しの連鎖の 1 か所（例えば最も外側か、障害の起きた層のすぐ上）だけで行い、各層で重ねてリトライしないようにします。
* リトライの予算（retry budget）を設けます。例えば、リトライの数を通常のリクエストの数の 10% までに制限し、それを超えたらリトライせずに失敗を返します。
* サーバーが ``Retry-After`` ヘッダーなどで待つべき時間を示した場合は、それに従います。
* 呼び出し先の失敗が続いたら、しばらく呼び出し自体を止めるサーキットブレーカーを使います（「:doc:`d09_reliability`」を参照してください）。

まとめ
------

* 分散システムの通信には、レスポンスを待つ同期的な通信と、メッセージを預けて先に進む非同期的な通信があり、用途に応じて組み合わせます。
* RPC はリモート呼び出しを関数呼び出しのように見せますが、失敗の仕方や遅延はローカルな呼び出しと本質的に異なります。gRPC は Protocol Buffers と HTTP/2 を使う代表的な RPC のフレームワークです。
* シリアライズの形式は、ノードの版が混在しても通信できるよう、後方互換性と前方互換性を考えて選び、変更します。
* メッセージキューは作業の分担と負荷の平準化に、pub/sub は 1 つのイベントを複数の受信側に届けることに使います。多くの場合、配信保証は at-least-once であり、メッセージの重複に備える必要があります。
* タイムアウトが起きても、クライアントには相手が処理したかどうかが分かりません。リトライする操作は冪等にするか、冪等キーで重複を排除します。
* リトライには指数バックオフとジッターを使い、回数や予算に上限を設けて、リトライストームを防ぎます。
