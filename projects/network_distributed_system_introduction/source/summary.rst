まとめ
======

この章では、本書の内容を振り返り、全体を貫く考え方を整理します。最後に、次に学ぶべきことを紹介します。

第 1 部の振り返り
-----------------

第 1 部では、データがネットワークを通って相手のプログラムに届くまでの仕組みを、層ごとに見てきました。

.. list-table:: 第 1 部の各章の要点
   :header-rows: 1
   :widths: 30 70

   * - 章
     - 要点
   * - :doc:`n01_network_overview`
     - パケット交換は 1 本のリンクを多数の通信で効率よく共有しますが、帯域幅も遅延も保証されません。通信の機能は層に分けて設計され、各層はカプセル化によって自分のヘッダーだけを扱います。小さなデータの転送時間は遅延で決まり、大きなデータでは帯域幅遅延積が重要になります。
   * - :doc:`n02_network_history`
     - パケット交換の発想から ARPANET、TCP/IP が生まれました。単純なネットワークと賢い端というエンドツーエンド原理と、動く実装と開かれた標準が、インターネットの成長を支えました。規模の拡大が生む問題に対して、DNS、輻輳制御、CIDR、NAT、IPv6、QUIC が順に導入されてきました。
   * - :doc:`n03_link_layer`
     - リンク層は、同じ LAN の中でフレームを届けます。スイッチは MAC アドレスを学習して宛先のポートにだけフレームを転送し、ARP は IP アドレスから MAC アドレスを求めます。
   * - :doc:`n04_internet_layer`
     - IP はベストエフォートで、ネットワークをまたいでパケットを届けます。ルーターは最長一致で経路を選び、TTL と ICMP が配送を支えます。NAPT は IPv4 アドレスの不足を補いますが、外からの接続を難しくします。
   * - :doc:`n05_transport_layer`
     - ポート番号でプログラムを区別します。UDP は単純で、TCP はハンドシェイク、シーケンス番号と ACK、再送、フロー制御、輻輳制御で信頼性のあるバイトストリームを提供します。TCP のヘッドオブラインブロッキングを避けるため、QUIC が作られました。
   * - :doc:`n06_dns`
     - DNS は、木構造の名前空間と委任で名前の管理を分散しています。答えは TTL の間キャッシュされるため、変更の反映には時間がかかります。
   * - :doc:`n07_http`
     - HTTP はリクエストとレスポンスからなるプロトコルです。メソッドの冪等性とステータスコードの区別が、キャッシュやリトライの判断の基礎になります。HTTP/2 と HTTP/3 は多重化で遅延を減らします。
   * - :doc:`n08_network_security`
     - TLS は、鍵交換、デジタル署名による認証、認証付き暗号を組み合わせて通信を守ります。証明書の検証を無効にすると、暗号化していても中間者攻撃を防げません。
   * - :doc:`n09_socket_programming`
     - TCP はメッセージの境界を保存しないので、フレーミングが必要です。通信には必ずタイムアウトを設定し、名前解決の失敗、接続拒否、タイムアウトを区別して扱います。
   * - :doc:`n10_network_troubleshooting`
     - 障害は下の層から順に、範囲も絞り込みながら切り分けます。``ping``、``traceroute``、``nslookup``、``netstat``、``curl``、パケットキャプチャを使い分けます。

第 2 部の振り返り
-----------------

第 2 部では、ネットワークでつながった複数のコンピューターが協調して正しく動くための考え方と技術を見てきました。

.. list-table:: 第 2 部の各章の要点
   :header-rows: 1
   :widths: 30 70

   * - 章
     - 要点
   * - :doc:`d01_distributed_overview`
     - 分散システムでは部分障害が普通に起こります。ネットワーク越しの呼び出しは、失われたり遅れたりし、結果が分からないこともあります。障害モデルとシステムモデルは、何を想定して設計するかを明確にするための枠組みです。
   * - :doc:`d02_distributed_history`
     - 集中処理からクライアント・サーバー、Web のスケールアウト、クラウドへと移る中で、論理時計、ビザンチン将軍問題、FLP 不可能性、Paxos などの理論と、GFS、MapReduce、Dynamo、Raft、Spanner などのシステムが生まれました。
   * - :doc:`d03_time_and_order`
     - 物理時計はずれ、巻き戻ることもあるため、出来事の順序を時刻だけで決めるのは危険です。ランポート時計とベクトル時計は、因果関係に基づいて順序を定めます。
   * - :doc:`d04_communication`
     - タイムアウトが起きても、相手が処理したかどうかは分かりません。exactly-once は、at-least-once のリトライと冪等性を組み合わせて実現します。リトライには指数バックオフとジッターを使います。
   * - :doc:`d05_replication`
     - データの複製には、シングルリーダー、マルチリーダー、リーダーレスの方式があります。非同期レプリケーションでは複製の間にずれが生じ、リーダーレス方式では R + W > N を満たすクォーラムで最新の値を読めるようにします。
   * - :doc:`d06_consistency`
     - 一貫性モデルは、システムとプログラムの間の約束事です。強いモデルほどプログラムは書きやすくなりますが、遅延と可用性の代償が大きくなります。CAP 定理は、ネットワーク分断が起きたときの一貫性と可用性の選択を示しています。
   * - :doc:`d07_partitioning`
     - データを分割して、1 台の限界を超えます。剰余による割り当てはノードの増減で大半のキーが移動しますが、コンシステントハッシュと仮想ノードを使えば移動を最小限にでき、負荷の偏りも小さくできます。
   * - :doc:`d08_consensus`
     - FLP 不可能性があるため、実際の合意アルゴリズムは安全性を常に守り、停止性はタイムアウトや乱数で実用上確保します。2 相コミットはコーディネーターの故障で阻塞します。リースによるロックにはフェンシングトークンが必要です。
   * - :doc:`d09_reliability`
     - 単一障害点をなくし、タイムアウト、サーキットブレーカー、バルクヘッド、レート制限で障害の連鎖と過負荷を防ぎます。可観測性と SLO で信頼性を測り、カオスエンジニアリングで確かめます。

本書を貫く考え方
----------------

本書の各章には、繰り返し現れる考え方がいくつかあります。

ネットワークは信頼できない
~~~~~~~~~~~~~~~~~~~~~~~~~~

IP はパケットを届けることを保証しません。パケットは失われ、遅れ、順序が入れ替わり、重複します。TCP は再送によってこれを隠しますが、相手のコンピューターが停止したり、ネットワークが分断されたりすれば、いつまでも届きません。第 1 部で見たこの事実が、第 2 部のほとんどすべての問題の出発点でした。リトライと冪等性、タイムアウトと障害検知、レプリケーションとクォーラム、合意は、どれも「通信が届くとは限らない」という前提の上に組み立てられた技術です。

分からないことを前提に設計する
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

レスポンスが返ってこないとき、リクエストが届かなかったのか、相手が処理した後にレスポンスが失われたのか、相手がまだ処理中なのかは区別できません。また、異なるコンピューターの時計は完全には一致しないので、どちらの出来事が先に起きたのかを時刻だけで決めることもできません。分散システムの設計では、このように「知ることができないこと」を認め、それでも正しく動く仕組みを作る必要があります。冪等キー、論理時計、フェンシングトークンは、その代表的な例です。

トレードオフを選ぶ
~~~~~~~~~~~~~~~~~~

ネットワークと分散システムには、すべてを同時に満たす設計はほとんどありません。TCP の信頼性は遅延の増加と引き換えです。DNS の TTL を長くすれば負荷は減りますが、変更の反映は遅れます。強い一貫性は、遅延と可用性を犠牲にします。レプリカを増やせば可用性は高まりますが、複製の間のずれや運用の手間が増えます。大切なのは、それぞれの技術が何を得て何を失うのかを理解し、自分のシステムの要件に合った選択をすることです。

層と抽象化
~~~~~~~~~~

ネットワークの階層モデルは、複雑な通信を層に分け、各層が下の層の詳細を知らなくても済むようにしたものです。分散システムでも、RPC、メッセージキュー、合意のサービスなどの抽象化が、複雑さを隠してくれます。ただし、抽象化は完全ではありません。遅延や障害は、どの層からも漏れ出してきます。問題が起きたときには、抽象化の下で何が起きているかを想像できることが、エンジニアの力になります。

次に学ぶべきこと
----------------

本書は入門書であり、多くの話題を概要の紹介にとどめています。さらに学ぶには、次のような方向があります。

* ネットワークを深く学ぶ：パケットキャプチャを使って実際の通信を観察しながら、TCP/IP の教科書を読むことをお勧めします。Wireshark で自分のブラウザーの通信を眺めるだけでも、多くの発見があります。
* ネットワークの運用を学ぶ：ルーティングプロトコル、負荷分散装置、クラウドの仮想ネットワーク（VPC など）の設計と運用を学ぶと、インフラストラクチャを扱う力が身に付きます。
* 分散データベースを学ぶ：レプリケーション、パーティショニング、トランザクションが、実際のデータベースでどのように実装されているかを学ぶと、本書の第 2 部の内容がより具体的になります。
* 合意アルゴリズムを実装する：Raft の論文を読み、ログ複製まで含めて小さく実装してみると、分散システムの難しさと面白さを実感できます。
* 信頼性の工学を学ぶ：SRE の考え方、可観測性、障害対応、ポストモーテムを学ぶと、分散システムを運用する力が身に付きます。

参考になる文献は「:doc:`appendix_references`」にまとめています。本書が、ネットワークと分散システムの世界をさらに深く探求するための足がかりとなれば幸いです。
