ネットワークセキュリティ
========================

この章では、ネットワーク上の通信を守る仕組みと、ネットワークの構成による防御を説明します。

ネットワーク上の脅威
--------------------

インターネットの通信は、利用者の端末からサーバーに届くまでに、Wi-Fi のアクセスポイント、インターネットサービスプロバイダー、多数のルーターなどを経由します。経路上の機器を操作できる攻撃者は、通信に対して次のような攻撃を行えます。

.. list-table:: 通信経路上の脅威
   :header-rows: 1
   :widths: 20 50 30

   * - 脅威
     - 内容
     - 損なわれる要素
   * - 盗聴
     - 通信の内容を読み取ります。
     - 機密性
   * - 改ざん
     - 通信の内容を書き換えます（例: Web ページへのマルウェアの埋め込み）。
     - 完全性
   * - なりすまし
     - 正規のサーバーのふりをして、利用者と通信します。
     - 真正性

攻撃者が通信の当事者の間に入り込み、両者になりすまして通信を中継しながら盗聴や改ざんを行う攻撃を\ :term:`中間者攻撃`\ と呼びます。公衆 Wi-Fi の偽のアクセスポイントなどが典型的な例です。これらの脅威から通信を守るのが、次に説明する TLS です。

また、サーバーが外部に公開しているポートやサービスは、すべて攻撃の入口になり得ます。攻撃を受ける可能性のある箇所の総体を\ **攻撃対象領域**\ （アタックサーフェス）と呼びます。使っていないサービスを停止し、公開するポートを最小限にすることは、最も基本的で効果の高い対策です。

TLS
---

:term:`TLS`\ （Transport Layer Security）は、通信を暗号化し、改ざんを検知し、通信相手が本物であることを確認するためのプロトコルです。HTTPS は、HTTP を TLS で保護したものです。

TLS は、:doc:`03_cryptography`\ で説明した技術を組み合わせて、次の 3 つを実現しています。

.. list-table:: TLS が実現すること
   :header-rows: 1
   :widths: 25 40 35

   * - 実現すること
     - 方法
     - 使われる技術
   * - 通信相手の確認
     - サーバーが提示する証明書を検証します。
     - デジタル署名、証明書
   * - 鍵の共有
     - 盗聴されても共通鍵が分からない方法で鍵を共有します。
     - 鍵共有（ECDHE など）
   * - 暗号化と改ざん検知
     - 共有した鍵で通信内容を保護します。
     - 認証付き暗号（AES-GCM など）

現在の TLS 1.3 では、鍵の共有に、接続のたびに使い捨ての鍵ペアを生成する方式が使われます（以前の接続で共有した鍵だけを使って再接続する方式を除きます）。そのため、サーバーの秘密鍵が将来漏えいしても、過去に記録された通信は解読できません。この性質を\ :term:`前方秘匿性`\ と呼びます。

TLS 1.0 と TLS 1.1 は、RFC 8996 で使用が禁止されています。サーバーでは TLS 1.2 以上だけを有効にし、可能であれば TLS 1.3 を優先します。

証明書と PKI
------------

TLS で通信相手を確認するには、受け取った公開鍵が確かにそのサーバーのものであることを確かめる必要があります。そのための仕組みが、証明書と :term:`PKI`\ （公開鍵基盤）です。

**証明書**\ は、「このドメイン名の公開鍵はこれである」という情報に、**認証局**\ （CA）がデジタル署名したものです。認証局の証明書は、さらに上位の認証局によって署名されており、最上位のルート認証局の証明書は、OS やブラウザーにあらかじめ組み込まれています。クライアントは、この連鎖をたどってサーバーの証明書を検証します。

クライアントは、証明書について次の点を検証します。

* 信頼できるルート認証局まで、署名の連鎖をたどれること
* 有効期間内であること
* 証明書に記載されたドメイン名（SAN: Subject Alternative Name）が、接続先のホスト名と一致すること
* 失効していないこと

.. warning::

   開発中に証明書のエラーが出たときに、検証を無効にして回避するのはやめてください。例えば、requests ライブラリの ``verify=False`` や、ssl モジュールの ``check_hostname = False`` がこれに当たります。検証を無効にすると、中間者攻撃を受けても気付けなくなります。このような設定が本番環境に残ってしまう事故も少なくありません。社内の認証局を使っている場合は、検証を無効にするのではなく、その認証局の証明書を信頼する設定を追加します。

現在は、Let's Encrypt のように無料で証明書を自動発行する認証局が普及しています。証明書の期限切れによる障害を防ぐため、証明書の更新は自動化しておきます。また、発行されたすべての証明書は Certificate Transparency という公開ログに記録されるため、自分のドメインに対して身に覚えのない証明書が発行されていないかを監視できます。

HTTPS の徹底と HSTS
^^^^^^^^^^^^^^^^^^^

Web サイトを HTTPS で提供していても、利用者が最初に ``http://`` で接続すると、HTTPS へのリダイレクトの前に中間者攻撃を受けるおそれがあります。これを防ぐのが HSTS（HTTP Strict Transport Security、RFC 6797）です。サーバーが次のヘッダーを返すと、ブラウザーは指定した期間、そのドメインに常に HTTPS で接続します。

.. code-block:: text
   :linenos:

   Strict-Transport-Security: max-age=31536000; includeSubDomains

DNS のセキュリティ
------------------

:term:`DNS` は、ドメイン名を IP アドレスに変換する仕組みです。DNS の応答が偽装されると、利用者は正しいドメイン名を入力しても偽のサーバーに誘導されます。DNS に関する主なリスクと対策を次の表に示します。

.. list-table:: DNS に関する主なリスクと対策
   :header-rows: 1
   :widths: 30 40 30

   * - リスク
     - 内容
     - 対策
   * - DNS キャッシュポイズニング
     - DNS サーバーに偽の応答をキャッシュさせ、多数の利用者を偽のサーバーに誘導します。
     - DNSSEC による応答の署名、DNS サーバーソフトウェアの更新
   * - 通信内容からの情報の推測
     - 暗号化されていない DNS の問い合わせから、閲覧しているサイトを知られます。
     - DNS over HTTPS（DoH）、DNS over TLS（DoT）
   * - サブドメインの乗っ取り
     - 廃止したクラウドのサービスを指す DNS レコードが残っていると、第三者が同じ名前でサービスを作成し、そのサブドメインで任意の内容を公開できます。
     - サービスを廃止するときに DNS レコードも削除します。
   * - ドメインの失効
     - ドメインの更新を忘れて失効すると、第三者に取得されて悪用されます。
     - 自動更新の設定、レジストラーのアカウントの多要素認証

TLS の証明書の検証が正しく行われていれば、DNS が偽装されても、攻撃者は正規のドメインの証明書を持っていないため、利用者は接続時にエラーで気付けます。ここでも、証明書の検証を無効にしないことが重要です。

ファイアウォールとネットワークの分離
------------------------------------

:term:`ファイアウォール`\ は、あらかじめ定めた規則に従って、通信を許可または遮断する仕組みです。IP アドレスやポート番号で通信を制御するものが一般的です。HTTP の内容を検査して、SQL インジェクションなどの攻撃に特徴的なパターンを遮断するものは WAF（Web Application Firewall）と呼ばれます。

ネットワークを設計する際には、役割ごとにネットワークを分け、必要な通信だけを許可します。

* インターネットに公開するのは、Web サーバーやロードバランサーなど、公開が必要なものだけにします。
* データベースは、アプリケーションサーバーからだけ接続できるネットワークに置きます。
* 管理用の画面や SSH の接続は、インターネットに直接公開せず、VPN や専用の接続経路を経由させます。

ネットワークを分離しておくと、1 台のサーバーに侵入されても、攻撃者がそこから他のサーバーへ侵入を広げることを難しくできます。

.. note::

   WAF は既知の攻撃パターンを防ぐのに役立ちますが、アプリケーションの脆弱性そのものを修正するものではありません。:doc:`02_basic_concepts`\ で説明した多層防御の 1 つの層として位置付け、アプリケーションの脆弱性は必ず修正してください。

VPN
---

:term:`VPN`\ （Virtual Private Network）は、インターネットなどの共有のネットワーク上に、暗号化された仮想的な専用の通信路を作る技術です。拠点間の接続や、在宅勤務で社内ネットワークに接続するために使われます。

VPN の機器は、インターネットに公開され、社内ネットワークへの入口となるため、攻撃者に狙われやすい機器です。VPN 機器の脆弱性を突いた侵入は、ランサムウェアの被害の主要な原因の 1 つになっています。VPN 機器のファームウェアは速やかに更新し、ログインには多要素認証を必須にします。

ゼロトラスト
------------

従来のネットワークの防御は、社内ネットワークは安全、インターネットは危険と考え、その境界を守る考え方（境界型防御）でした。しかし、クラウドサービスの利用や在宅勤務が広がり、守るべき資産と利用者の多くが境界の外にある状況になりました。また、VPN などを通じて一度境界の内側に侵入されると、内部の通信が信頼されているために被害が広がりやすいという問題もあります。

そこで広まったのが\ :term:`ゼロトラスト`\ の考え方です。ゼロトラストでは、ネットワーク上の位置によって通信を信頼せず、すべてのアクセスについて、利用者、端末、状況を確認したうえで許可します。米国 NIST は、SP 800-207 でゼロトラストの考え方を整理しています。

.. list-table:: 境界型防御とゼロトラストの比較
   :header-rows: 1
   :widths: 25 35 40

   * - 観点
     - 境界型防御
     - ゼロトラスト
   * - 信頼の前提
     - 社内ネットワークからのアクセスは信頼します。
     - ネットワークの位置にかかわらず信頼しません。
   * - 確認の頻度
     - 境界を通過するときに確認します。
     - リソースにアクセスするたびに確認します。
   * - 確認の内容
     - 主に ID とパスワード
     - 利用者の認証、端末の状態、場所や時刻などの状況
   * - 権限
     - 社内ネットワークの多くのリソースにアクセスできます。
     - リソースごとに最小限の権限を与えます。

ゼロトラストは特定の製品ではなく、:doc:`02_basic_concepts`\ で説明した多層防御と最小権限の原則を、ネットワークの設計に徹底して適用する考え方といえます。
