セキュリティの基本概念
======================

この章では、本書全体で使う考え方と用語を説明します。個々の技術は第 3 章以降で扱います。

情報セキュリティの 3 要素
-------------------------

情報セキュリティとは、情報の\ **機密性**、**完全性**、**可用性**\ を維持することです。3 つの英語の頭文字から CIA と呼ばれます。

.. list-table:: 情報セキュリティの 3 要素
   :header-rows: 1
   :widths: 20 40 40

   * - 要素
     - 意味
     - 損なわれる例
   * - 機密性（Confidentiality）
     - 許可された人だけが情報にアクセスできること
     - 顧客情報の漏えい、通信の盗聴
   * - 完全性（Integrity）
     - 情報が正確で、不正に改ざんされていないこと
     - Web ページの改ざん、送金額の書き換え
   * - 可用性（Availability）
     - 必要なときに情報やサービスを利用できること
     - サービス停止攻撃、ランサムウェアによるデータの暗号化

3 要素に加えて、次の性質が挙げられることもあります。

* **真正性**: 利用者やデータが、主張どおりの本物であること
* **責任追跡性**: 誰がいつ何をしたかを後から追跡できること
* **否認防止**: 行った操作を、後から「やっていない」と否定できないこと
* **信頼性**: システムが意図したとおりに一貫して動作すること

セキュリティ対策を考えるときは、守りたいものが 3 要素のどれに当たるのかを意識すると、必要な対策を整理しやすくなります。例えば、暗号化は主に機密性を、デジタル署名は完全性と真正性を、バックアップは可用性を守るための対策です。

脅威・脆弱性・リスク
--------------------

セキュリティでは、次の 3 つの用語を区別して使います。

.. list-table:: 脅威・脆弱性・リスク
   :header-rows: 1
   :widths: 20 45 35

   * - 用語
     - 意味
     - 例
   * - :term:`脅威`
     - 損害を与える可能性のある事象や、それを引き起こす主体
     - 攻撃者、マルウェア、操作ミス、災害
   * - :term:`脆弱性`
     - 脅威によって悪用される可能性のある弱点
     - SQL インジェクションを許すコード、推測しやすいパスワード
   * - :term:`リスク`
     - 脅威が脆弱性を悪用して損害が発生する可能性と、その影響の大きさ
     - 顧客情報が漏えいし、損害賠償と信用の失墜が生じる可能性

リスクは、発生の可能性と影響の大きさの組み合わせで評価するのが一般的です。

.. math::

   \text{リスク} = \text{発生の可能性} \times \text{影響の大きさ}

この式は厳密な計算式ではなく、考え方を表すものです。実務では、それぞれを「高・中・低」などの段階で評価し、組み合わせて優先度を決めます。

リスクへの対応には、次の 4 つの方法があります。すべてのリスクをなくすことはできないため、対応の費用と効果を比べて選びます。

.. list-table:: リスクへの対応方法
   :header-rows: 1
   :widths: 20 45 35

   * - 対応
     - 内容
     - 例
   * - 低減
     - 対策を講じて、発生の可能性や影響を小さくします。
     - 脆弱性の修正、多要素認証の導入
   * - 回避
     - リスクの原因となる活動そのものをやめます。
     - 不要なクレジットカード番号を保存しません。
   * - 移転
     - リスクを他者と分担します。
     - サイバー保険への加入、決済処理の外部委託
   * - 受容
     - 影響が小さい場合などに、対策をせずにリスクを受け入れます。
     - 影響の小さい社内ツールの軽微な問題を、記録して様子を見ます。

セキュリティ設計の原則
----------------------

個々の対策を選ぶ前に、設計全体の指針となる原則を押さえておきます。本書の各章で説明する対策の多くは、これらの原則を具体化したものです。

多層防御
^^^^^^^^

:term:`多層防御`\ は、複数の対策を重ねて、1 つの対策が破られても被害を防げるようにする考え方です。例えば、Web アプリケーションでは、入力の検証、プレースホルダーによる SQL の組み立て、データベースの権限の制限、通信の暗号化、監視を組み合わせます。どれか 1 つに不備があっても、他の対策で被害を抑えられます。

最小権限の原則
^^^^^^^^^^^^^^

:term:`最小権限の原則`\ は、利用者やプログラムに、目的を果たすために必要な最小限の権限だけを与える考え方です。権限が小さければ、アカウントが乗っ取られたり、プログラムに脆弱性があったりしても、被害の範囲が限られます。データベースの接続ユーザー、クラウドのアクセス権限、AI エージェントに許可するツールなど、あらゆる場面に当てはまります。

安全な初期設定
^^^^^^^^^^^^^^

初期設定の状態で安全であるように設計します。例えば、新しく作成したストレージは非公開にする、デバッグ機能は無効にしておく、といった設計です。利用者が設定を変更し忘れても、危険な状態にはなりません。

セキュアバイデザイン
^^^^^^^^^^^^^^^^^^^^

セキュリティは、完成したシステムに後から付け加えるものではなく、要件定義や設計の段階から組み込むものです。この考え方をセキュアバイデザインと呼びます。設計段階で見つけた問題は、リリース後に見つけた問題よりもはるかに少ない費用で修正できます。設計段階で脅威を洗い出す方法は、:doc:`11_testing_and_threat_modeling`\ で説明します。

主な脅威の全体像
----------------

攻撃の手口はさまざまですが、代表的なものを知っておくと、後の章の内容を位置付けやすくなります。IPA（情報処理推進機構）は、前年に社会的な影響の大きかった脅威を「情報セキュリティ10大脅威」として毎年公開しています。

.. list-table:: 代表的な脅威
   :header-rows: 1
   :widths: 25 75

   * - 脅威
     - 概要
   * - マルウェア
     - 利用者の意図に反して有害な動作をするソフトウェアの総称です。メールの添付ファイルや改ざんされた Web サイト、不正なソフトウェアパッケージなどを通じて感染します。
   * - :term:`ランサムウェア`
     - データを暗号化して使えなくし、復旧と引き換えに金銭を要求するマルウェアです。近年は、暗号化の前にデータを盗み出し、「支払わなければ公開する」と二重に脅迫する手口が一般的です。
   * - :term:`DoS 攻撃`
     - 大量の通信や処理を発生させて、サービスを利用できない状態にする攻撃です。多数の機器から同時に行うものを DDoS 攻撃と呼びます。
   * - 標的型攻撃
     - 特定の組織を狙い、業務に関係するように見せかけたメールなどで侵入し、長期間にわたって情報を盗む攻撃です。
   * - 不正ログイン
     - 他のサービスから漏えいした ID とパスワードの組を使ってログインを試みる攻撃などです。:doc:`04_authentication`\ で詳しく扱います。
   * - Web アプリケーションへの攻撃
     - アプリケーションの脆弱性を突いて、情報を盗んだり改ざんしたりする攻撃です。:doc:`06_web_application`\ で詳しく扱います。
   * - サプライチェーン攻撃
     - 取引先や、利用しているソフトウェアの開発元を経由して侵入する攻撃です。:doc:`08_supply_chain`\ で詳しく扱います。
   * - 内部不正
     - 従業員や元従業員などが、正規の権限を悪用して情報を持ち出す行為です。最小権限の原則と、操作の記録が対策になります。

人的要因
--------

技術的な対策をどれほど整えても、人間をだます攻撃は防ぎきれません。人間の心理や習慣の隙を突いて情報を盗んだり、不正な操作をさせたりする手口を\ :term:`ソーシャルエンジニアリング`\ と呼びます。

.. list-table:: 人間を狙う代表的な手口
   :header-rows: 1
   :widths: 25 75

   * - 手口
     - 概要
   * - :term:`フィッシング`
     - 実在する企業やサービスを装ったメールや SMS で偽のサイトに誘導し、パスワードやクレジットカード番号を入力させます。
   * - ビジネスメール詐欺
     - 取引先や経営者になりすましたメールで、偽の口座への送金を指示します。過去のメールのやり取りを盗み見たうえで、自然な文面で送られてくることがあります。
   * - なりすましの電話
     - ヘルプデスクや社内の担当者を装い、パスワードの再設定や多要素認証の承認をさせます。
   * - 物理的な侵入
     - 関係者の後ろについて入館したり、机の上や廃棄書類から情報を得たりします。

これらへの対策は、技術と運用を組み合わせて行います。

* フィッシングに強い認証方式（:doc:`04_authentication`\ で説明するパスキー）を採用し、だまされてもパスワードが盗まれない仕組みにします。
* 送金先の変更など重要な依頼は、メール以外の手段（登録済みの電話番号など）で本人に確認する手順を定めます。
* 不審なメールを開いてしまった場合に、責められることなくすぐに報告できる体制を作ります。

最後の点は特に重要です。報告が遅れると、被害の拡大を止められなくなります。

法令・規格・ガイドライン
------------------------

組織としてセキュリティに取り組む際には、法令の要求を満たし、標準的な枠組みに沿って対策を整理することが求められます。代表的なものを次の表に示します。

.. list-table:: 主な法令・規格・ガイドライン
   :header-rows: 1
   :widths: 30 70

   * - 名称
     - 概要
   * - 個人情報保護法
     - 個人情報を取り扱う事業者に、利用目的の特定、安全管理措置、漏えい時の個人情報保護委員会への報告と本人への通知などを義務付けています。
   * - GDPR（EU 一般データ保護規則）
     - EU 域内の個人のデータを扱う場合に適用される規則です。日本の企業でも、EU の利用者にサービスを提供していれば対象になることがあります。
   * - ISO/IEC 27001
     - 情報セキュリティマネジメントシステム（ISMS）の要求事項を定めた国際規格です。組織として継続的にセキュリティを管理する仕組みを認証する際の基準になります。
   * - NIST サイバーセキュリティフレームワーク（CSF）
     - 米国国立標準技術研究所（NIST）が公開している、組織のセキュリティ対策を整理するための枠組みです。2.0 版では、統治、識別、防御、検知、対応、復旧の 6 つの機能で対策を分類しています。

エンジニアがこれらの文書を細部まで読む機会は多くありませんが、自分の担当する対策が、組織のどの要求に対応しているのかを意識しておくと、優先度の判断に役立ちます。
