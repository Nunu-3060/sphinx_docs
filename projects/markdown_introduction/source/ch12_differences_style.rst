表示する場所による違いと書き方の指針
====================================

この章では、同じ Markdown のソースが表示する場所によって異なって表示される例をまとめ、そのうえで、どこでも意図どおりに表示され、読みやすいソースを書くための指針を説明する。

同じソースでも表示が異なる
--------------------------

第 1 章で説明したように、Markdown には方言がある。同じソースでも、CommonMark だけに対応した場所と GitHub とでは、表示結果が異なることがある。

.. md-example::

   | 記法 | 分類 |
   | --- | --- |
   | 表 | GFM |

   - [x] タスクリスト

.. md-example::
   :github:

   | 記法 | 分類 |
   | --- | --- |
   | 表 | GFM |

   - [x] タスクリスト

CommonMark だけで変換すると、表は普通の段落になり、タスクリストの ``[x]`` は文字のまま表示される。これまでの章で触れた、表示する場所による違いを次の表にまとめる。

.. list-table:: 表示する場所による主な違い
   :header-rows: 1
   :widths: 25 50 25

   * - 項目
     - 違い
     - 説明した章
   * - 改行
     - ``.md`` ファイルでは 1 回の改行で改行されないが、GitHub のコメント欄では改行される
     - 第 4 章
   * - 段落の直後のリスト
     - 段落の直後に空行なしで書いたリストを、リストとして扱わない方言がある
     - 第 6 章
   * - 入れ子の字下げ
     - 必要な字下げの量が、変換プログラムによって異なることがある
     - 第 6 章
   * - 見出しのアンカー
     - アンカーの作り方（特に日本語の見出し）が場所によって異なる
     - 第 8 章
   * - GFM の記法
     - 表、取り消し線、タスクリスト、拡張自動リンクは、CommonMark だけに対応した場所では使えない
     - 第 5 章、第 6 章、第 8 章、第 9 章
   * - HTML
     - 使えるタグや属性が場所によって異なる。HTML をまったく使えない場所もある
     - 第 10 章
   * - GitHub の独自機能
     - 脚注、数式、アラートなどは、対応していない場所や書き方が異なる場所がある
     - 第 10 章

違いに振り回されないためには、次の 2 点を心がけるとよい。

- 迷ったら空行を入れる。見出し、リスト、コードブロック、表、区切り線の前後に空行を入れておけば、多くの違いは問題にならない。
- 公開する前に、実際に表示される場所でプレビューする。GitHub なら Preview タブ、Qiita や Zenn なら各サービスのプレビュー画面で確かめる。

行末の空白が消える問題
----------------------

第 4 章で説明したように、行末に半角空白を 2 個書くと強制改行になる。しかし、行末の空白は目に見えないうえに、ツールによって自動で削除されることがある。

多くのエディタには、保存するときに行末の空白を自動で削除する機能がある。VS Code では ``files.trimTrailingWhitespace`` という設定を有効にすると、この機能が働く。プログラムを書くときには便利な機能だが、Markdown の文書では強制改行が消えてしまう。また、Git の設定や、文書を検査するツールが行末の空白を警告することもある。

この問題を避ける最も確実な方法は、強制改行に行末の空白を使わず、行末のバックスラッシュを使うことである。どうしても行末の空白を使う必要があるときは、VS Code の設定ファイル（``settings.json``）で、Markdown のファイルに限って自動削除を無効にできる。

.. code-block:: json
   :linenos:
   :caption: Markdown のファイルだけ行末の空白を削除しない設定

   {
       "files.trimTrailingWhitespace": true,
       "[markdown]": {
           "files.trimTrailingWhitespace": false
       }
   }

書き方をそろえる
----------------

Markdown には、同じ表示結果になる書き方が複数ある。箇条書きの記号には ``-``、``*``、``+`` が使え、強調には ``*`` と ``_`` が使える。1 つの文書や 1 つのリポジトリの中で書き方がばらばらだと、ソースが読みにくくなり、複数の人で編集するときに無用な差分が生まれる。

書き方は、たとえば次のように決めて統一するとよい。本書の例もこの書き方にそろえている。

.. list-table:: 書き方の統一の例
   :header-rows: 1
   :widths: 30 30 40

   * - 項目
     - 書き方
     - 理由
   * - 見出し
     - ATX 形式（``#``）
     - すべてのレベルを同じ形で書け、区切り線と紛らわしくない
   * - 箇条書きの記号
     - ``-``
     - 強調の記号（``*``）と区別しやすい
   * - 強調、強い強調
     - ``*``、``**``
     - 日本語の文中でも使える（第 5 章）
   * - 強制改行
     - 行末の ``\``
     - 目に見え、自動で削除されない
   * - コードブロック
     - バッククォートのフェンスと言語名
     - 言語名を指定でき、字下げの量を気にしなくてよい
   * - 空行
     - ブロック要素の前後に 1 行
     - 方言による違いを避けられ、ソースが読みやすい

markdownlint で検査する
-----------------------

書き方のルールを決めても、人の目だけで守り続けるのは難しい。:term:`markdownlint` は、Markdown のソースがルールに沿っているかを検査するツールである。VS Code では、拡張機能「markdownlint」を入れると、ルールに反する箇所に波線が表示され、マウスポインターを重ねると理由が表示される。

markdownlint のルールには、``MD001`` のような番号が付いている。主なルールを次に示す。

.. list-table:: markdownlint の主なルール
   :header-rows: 1
   :widths: 20 80

   * - ルール
     - 内容
   * - ``MD001``
     - 見出しのレベルを 1 段ずつ下げる
   * - ``MD004``
     - 箇条書きの記号をそろえる
   * - ``MD009``
     - 行末に不要な空白を書かない
   * - ``MD022``
     - 見出しの前後に空行を入れる
   * - ``MD025``
     - レベル 1 の見出しを 1 つの文書に 1 つだけにする
   * - ``MD040``
     - コードブロックに言語名を書く

ルールは、検査する文書と同じフォルダか上位のフォルダに置いた ``.markdownlint.json`` などの設定ファイルで、有効にしたり無効にしたりできる。たとえば、行の長さを制限するルール（``MD013``）は、日本語の文章には合わないことが多いので、無効にすることがよくある。

.. code-block:: json
   :linenos:
   :caption: .markdownlint.json の例

   {
       "default": true,
       "MD004": { "style": "dash" },
       "MD013": false
   }

2 行目の ``"default": true`` ですべてのルールを有効にし、3 行目で箇条書きの記号を ``-`` に指定し、4 行目で行の長さのルールを無効にしている。

Prettier で整形する
-------------------

Prettier は、ソースの見た目を自動で整える\ :term:`フォーマッター`\ である。JavaScript や CSS などに加えて Markdown にも対応しており、VS Code の拡張機能として使える。Markdown では、表の ``|`` の位置をそろえる、箇条書きの記号を ``-`` にそろえる、余分な空行を取り除く、といった整形を自動で行う。

ただし、Prettier は強調の ``*`` を、前後の文字によっては ``_`` に書き換えることがある。第 5 章で説明したように、日本語の文中では ``_`` による強調が効かない場合があるので、日本語の文書で Prettier を使うときは、整形した後の表示を確かめるとよい。

markdownlint と Prettier は、併用することもできる。手で書き方をそろえる手間が減り、文書の内容を書くことに集中できる。
