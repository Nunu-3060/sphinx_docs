セキュリティと保護
==================

OS は、利用者やプログラムが互いに干渉しないように保護し、不正な利用から計算機を守る役割を担っています。この章では、利用者と権限の管理、アクセス制御、攻撃に対する防御機構、サンドボックス、起動の検証を説明します。

保護とセキュリティの目標
------------------------

OS の文脈では、保護とセキュリティという 2 つの言葉が使われます。

* 保護：計算機の内部で、プロセスや利用者が、許された資源にだけアクセスするように制御する仕組みです。カーネルモードとユーザーモードの区別、アドレス空間の分離、ファイルのアクセス権などがこれにあたります。
* セキュリティ：外部からの攻撃や不正な利用者も含め、悪意のある行為から計算機とデータを守ることです。保護の仕組みは、セキュリティを実現するための土台になります。

情報セキュリティの目標は、次の 3 つの性質にまとめられます。英語の頭文字をとって CIA と呼ばれます。

.. list-table:: 情報セキュリティの 3 要素
   :header-rows: 1
   :widths: 20 45 35

   * - 性質
     - 内容
     - OS の機能の例
   * - 機密性（Confidentiality）
     - 許可された者だけが情報を読める
     - アクセス権、暗号化
   * - 完全性（Integrity）
     - 情報が不正に書き換えられない
     - アクセス権、起動の検証
   * - 可用性（Availability）
     - 必要なときに情報やサービスを使える
     - 資源の制限、障害からの回復

利用者と権限
------------

利用者の識別と認証
~~~~~~~~~~~~~~~~~~

OS は、計算機を使う利用者を区別して管理します。UNIX 系 OS では、各利用者にユーザー ID（UID）と呼ばれる番号が割り当てられ、プロセスは自分を起動した利用者の UID を持ちます。ファイルへのアクセスなどの可否は、プロセスの UID をもとに判断されます。Windows では、利用者やグループをセキュリティ識別子（SID）で識別し、プロセスはアクセストークンと呼ばれる、権限の情報をまとめたデータを持ちます。

利用者が本人であることを確かめることを認証と呼びます。パスワードのほか、生体認証や、ハードウェアの鍵、複数の方法を組み合わせる多要素認証などが使われます。OS はパスワードそのものではなく、パスワードから計算したハッシュ値を保存しており、万一保存されたデータが漏れても、元のパスワードを簡単には復元できないようにしています。

管理者と最小権限の原則
~~~~~~~~~~~~~~~~~~~~~~

UNIX 系 OS では、UID が 0 の利用者（root）が特別な管理者で、ほとんどすべてのアクセスの制限を受けません。Windows では、Administrators グループに属する利用者が管理者の権限を持ちます。

管理者の権限を持つプロセスに不具合や脆弱性があると、攻撃者に計算機全体を乗っ取られるおそれがあります。そのため、各プロセスには仕事に必要な最小限の権限だけを与えるべきだとされています。これを最小権限の原則と呼びます。

この原則に従い、普段は一般の利用者として作業し、管理者の権限が必要な操作のときだけ一時的に権限を得るのが一般的です。UNIX 系 OS では ``sudo`` コマンドを、Windows ではユーザーアカウント制御（UAC）を使います。

.. code-block:: console
   :linenos:

   $ sudo systemctl restart nginx

さらに Linux では、root の強大な権限を、ケーパビリティと呼ばれる細かな単位に分けて与えられます。例えば、1024 未満のポート番号での待ち受けを許す ``CAP_NET_BIND_SERVICE`` だけを Web サーバーのプログラムに与えれば、root の他の権限を与えずに 80 番ポートを使えます。

アクセス制御
------------

アクセス制御は、「誰が（主体）」「何に（対象）」「どの操作を」行えるかを決める仕組みです。代表的な方式に、任意アクセス制御と強制アクセス制御があります。

.. list-table:: アクセス制御の方式
   :header-rows: 1
   :widths: 25 45 30

   * - 方式
     - 内容
     - 例
   * - 任意アクセス制御（DAC）
     - ファイルなどの所有者が、誰にアクセスを許すかを自分で決める
     - UNIX のアクセス権、Windows の ACL
   * - 強制アクセス制御（MAC）
     - システム全体の方針（ポリシー）によってアクセスの可否が決まり、所有者でも変更できない
     - SELinux、AppArmor、Windows の整合性レベル

任意アクセス制御では、プロセスは自分を起動した利用者の権限をすべて持ちます。そのため、例えば Web サーバーのプログラムが攻撃者に乗っ取られると、Web サーバーを動かしている利用者が読めるファイルはすべて読まれてしまいます。

強制アクセス制御では、「Web サーバーのプロセスは、Web で公開するディレクトリのファイルだけを読める」といった方針をシステム全体で定め、プロセスがどの利用者の権限で動いていても、その方針の範囲を超えるアクセスを禁止します。Linux の SELinux や AppArmor は、カーネルの LSM（Linux Security Modules）と呼ばれる仕組みの上に実装された強制アクセス制御です。

攻撃と防御機構
--------------

OS の上で動くプログラムの不具合は、攻撃の入口になることがあります。ここでは、代表的な攻撃であるバッファオーバーフローと、それに対して OS とハードウェアが用意している防御機構を見ます。

バッファオーバーフロー
~~~~~~~~~~~~~~~~~~~~~~

次の C 言語の関数は、引数で受け取った文字列を、大きさ 16 バイトの配列にコピーします。

.. code-block:: c
   :linenos:

   #include <string.h>

   void greet(const char *name) {
       char buffer[16];
       strcpy(buffer, name);  /* name の長さを確かめずにコピーしている */
   }

``name`` が 16 バイトより長いと、コピーされたデータは配列の外にあふれ、スタック上の隣にあるデータを上書きします。スタックには関数の戻り先のアドレスも置かれているため、攻撃者が細工した文字列を渡すと、戻り先のアドレスを書き換えて、攻撃者が用意した機械語のコードに制御を移すことができてしまいます。これがバッファオーバーフロー攻撃です。

防御機構
~~~~~~~~

こうした攻撃を難しくするため、現代の OS とコンパイラ、ハードウェアは、次のような防御機構を組み合わせています。

.. list-table:: メモリの不正利用に対する主な防御機構
   :header-rows: 1
   :widths: 25 75

   * - 防御機構
     - 内容
   * - スタックカナリア
     - コンパイラが、戻り先のアドレスの手前に特別な値（カナリア）を置き、関数から戻る前にその値が書き換えられていないかを確かめる。書き換えられていたらプログラムを停止する
   * - DEP（実行禁止）
     - スタックやヒープなど、データを置くページを実行禁止にする（「:doc:`08_memory`」で見たページテーブルの実行禁止ビットを使う）。攻撃者がデータとして送り込んだ機械語のコードを実行できなくなる
   * - ASLR
     - プログラム、ライブラリ、スタック、ヒープを置くアドレスを、起動のたびにランダムに変える。攻撃者は、制御を移すべきアドレスを予測しにくくなる
   * - 制御フローの保護
     - 間接的な関数呼び出しや関数からの戻りの行き先が、正当なものかどうかを、ハードウェアやコンパイラの支援で確かめる

これらの防御機構は、どれか 1 つで完全に攻撃を防げるものではありません。例えば DEP があっても、プログラムの中にすでにある正当なコードの断片をつなぎ合わせて悪用する攻撃（ROP：Return-Oriented Programming）が知られています。複数の防御機構を重ねることで、攻撃の難易度を上げるという考え方を多層防御と呼びます。

根本的な対策は、メモリの不正な利用を起こさないプログラムを書くことです。近年は、配列の範囲外へのアクセスなどを言語の仕組みで防ぐ Rust のようなメモリ安全な言語を、OS のカーネルの開発に使う動きも広がっています。

カーネルの保護
~~~~~~~~~~~~~~

カーネル自体も攻撃の対象になります。カーネルのアドレスをランダムにする KASLR、カーネルモードでユーザー空間のコードの実行やデータへのアクセスを禁止する CPU の機能（x86 の SMEP と SMAP など）が使われています。

2018 年には、CPU の投機的実行と呼ばれる高速化の仕組みを悪用して、本来アクセスできないメモリの内容を推測する Meltdown と Spectre という脆弱性が公表されました。これらはハードウェアの設計に起因する問題でしたが、OS の側でも対策が行われました。例えば Meltdown への対策として、ユーザーモードで動いている間はカーネルのメモリをページテーブルからほぼ完全に外しておく KPTI（Kernel Page-Table Isolation）が導入されました。この対策は、システムコールのたびにページテーブルを切り替える費用を伴うため、システムコールの多い処理の性能を低下させました。セキュリティと性能のトレードオフの典型的な例です。

サンドボックス
--------------

サンドボックスは、プログラムを、ほかの部分から隔離された限られた環境に閉じ込めて実行する仕組みです。プログラムが乗っ取られても、被害をその環境の中にとどめられます。

* Linux の seccomp は、プロセスが呼び出せるシステムコールを制限します。例えば、計算だけを行うプロセスに対して、ファイルを開くシステムコールを禁止できます。
* Web ブラウザは、Web ページを表示する処理を、権限を最小限に絞ったプロセスで実行しています。
* スマートフォンの OS は、すべてのアプリケーションをサンドボックスで実行し、カメラや連絡先などへのアクセスには利用者の許可を必要とします（「:doc:`03_history`」を参照）。
* 「:doc:`13_virtualization`」で説明するコンテナや仮想マシンも、隔離された実行環境を作る技術です。

起動の検証
----------

OS の保護の仕組みは、OS 自体が正しいものであることを前提にしています。もし起動の段階でカーネルが改ざんされていれば、カーネルの中の保護の仕組みは役に立ちません。

UEFI のセキュアブートは、ファームウェアが、デジタル署名を検証してから、ブートローダーを起動する仕組みです。ブートローダーも同様にカーネルの署名を検証します。こうして、信頼できるファームウェアから順に、次に起動するものの正しさを確かめていきます。この連鎖を信頼の連鎖と呼びます。

また、TPM（Trusted Platform Module）と呼ばれるセキュリティ用のチップは、起動の各段階で読み込まれたソフトウェアの記録を改ざんできない形で保持し、暗号鍵を安全に保管します。Windows 11 は TPM 2.0 の搭載を動作の条件としています。

更新の重要性
------------

最後に、最も基本的で効果的な対策は、OS とソフトウェアを最新の状態に保つことです。OS には毎月のように脆弱性が見つかり、修正が配布されています。修正が公開されると、その内容から脆弱性が分析され、修正を適用していない計算機が攻撃の標的になります。サーバーの運用では、セキュリティの更新を計画的に適用する仕組みを整えることが欠かせません。

まとめ
------

* OS は、利用者を識別、認証し、プロセスごとに権限を管理します。各プロセスには必要最小限の権限だけを与えるべきです。
* アクセス制御には、所有者が決める任意アクセス制御と、システム全体の方針で決める強制アクセス制御があります。
* バッファオーバーフローなどの攻撃に対して、スタックカナリア、DEP、ASLR などの防御機構を重ねて使います。
* サンドボックスは、プログラムを隔離された環境に閉じ込め、乗っ取られた場合の被害を抑えます。
* セキュアブートと TPM によって、起動するソフトウェアの正しさを検証します。
