CPU スケジューリング
====================

実行可能なスレッドの数は、たいてい CPU コアの数よりも多くなります。どのスレッドに、いつ、どれだけの時間 CPU を割り当てるかを決めることを CPU スケジューリングと呼び、それを担うカーネルの部分をスケジューラと呼びます。この章では、CPU の切り替えの仕組みと、代表的なスケジューリングのアルゴリズム、実際の OS のスケジューラを説明します。

なお、現在の OS が CPU を割り当てる単位はスレッドですが、スケジューリングの議論では伝統的に「プロセス」という言葉が使われるため、この章でもプロセスと呼ぶことがあります。

コンテキストスイッチ
--------------------

CPU で実行するスレッドを切り替える操作をコンテキストスイッチと呼びます。コンテキストスイッチでは、カーネルは次のことを行います。

#. 実行中のスレッドのレジスタの値（プログラムカウンタ、スタックポインタなど）を、そのスレッドの管理領域に保存する。
#. スケジューラが、次に実行するスレッドを選ぶ。
#. 選んだスレッドが別のプロセスに属していれば、アドレス空間を切り替える（ページテーブルを切り替える）。
#. 選んだスレッドの管理領域から、レジスタの値を復元する。
#. 選んだスレッドの実行を再開する。

コンテキストスイッチの間、CPU はアプリケーションの役に立つ仕事をしていません。また、切り替えの直接の費用に加えて、間接的な費用も生じます。切り替え後のスレッドは、CPU のキャッシュや TLB（第 8 章で説明します）に自分のデータが載っていない状態から始めることになり、しばらくの間は処理が遅くなります。コンテキストスイッチ自体はマイクロ秒程度で終わりますが、あまりに頻繁に切り替えると、この費用が無視できなくなります。

スケジューリングの基本
----------------------

CPU バーストと入出力バースト
~~~~~~~~~~~~~~~~~~~~~~~~~~~~

プロセスの実行は、CPU で計算を行う期間（CPU バースト）と、入出力の完了を待つ期間（入出力バースト）を交互に繰り返します。CPU バーストの長さによって、プロセスはおおまかに次の 2 種類に分けられます。

* CPU バウンド：CPU バーストが長いプロセス。科学技術計算、動画のエンコード、コンパイルなど。
* I/O バウンド：CPU バーストが短く、すぐに入出力の待ちに入るプロセス。エディタ、Web サーバー、データベースなど。

I/O バウンドのプロセスには、待ちから戻ったらすぐに CPU を割り当てるのが望ましいといえます。短い計算を済ませて次の入出力を早く始められれば、入出力装置も効率よく使われ、利用者への応答も速くなるからです。

スケジューリングのきっかけ
~~~~~~~~~~~~~~~~~~~~~~~~~~

スケジューラが次に実行するプロセスを選ぶのは、次のような場合です。

#. 実行中のプロセスが待ちの状態に入る（入出力の要求など）。
#. 実行中のプロセスが終了する。
#. 待ちの状態のプロセスが実行可能になる。
#. タイマー割り込みが起きる。

1 と 2 の場合だけスケジューリングを行う方式を非プリエンプティブ（横取りなし）、3 と 4 の場合にも実行中のプロセスから CPU を取り上げることがある方式をプリエンプティブ（横取りあり）と呼びます。現在の汎用 OS のスケジューラはすべてプリエンプティブです。

評価指標
~~~~~~~~

スケジューリングのアルゴリズムの良し悪しは、次のような指標で評価します。

.. list-table:: スケジューリングの評価指標
   :header-rows: 1
   :widths: 25 50 25

   * - 指標
     - 定義
     - 望ましい方向
   * - CPU 利用率
     - CPU が仕事をしている時間の割合
     - 高い
   * - スループット
     - 単位時間あたりに完了するプロセスの数
     - 多い
   * - ターンアラウンド時間
     - プロセスが到着してから終了するまでの時間
     - 短い
   * - 待ち時間
     - プロセスが実行可能キューで待っていた時間の合計
     - 短い
   * - 応答時間
     - プロセスが到着してから、初めて CPU を割り当てられるまでの時間
     - 短い

プロセス :math:`i` の到着時刻を :math:`A_i`、終了時刻を :math:`F_i`、CPU バースト時間を :math:`B_i` とすると、入出力の待ちがない場合、ターンアラウンド時間 :math:`T_i` と待ち時間 :math:`W_i` は次の式で表されます。

.. math::

   T_i = F_i - A_i, \qquad W_i = T_i - B_i

どの指標を重視するかは用途によって異なり、すべての指標を同時に最良にするアルゴリズムはありません。例えば、バッチ処理ではスループットやターンアラウンド時間が、対話的な利用では応答時間が重視されます。

------------------------------

代表的なアルゴリズムを、次の 4 つのプロセスを例に比べます。時間の単位は任意です。

.. list-table:: 例に用いるプロセス
   :header-rows: 1
   :widths: 30 35 35

   * - プロセス
     - 到着時刻
     - CPU バースト時間
   * - P1
     - 0
     - 7
   * - P2
     - 2
     - 4
   * - P3
     - 4
     - 1
   * - P4
     - 5
     - 4

FCFS
~~~~

FCFS（First-Come, First-Served：先着順）は、到着した順に CPU を割り当て、各プロセスを最後まで実行する非プリエンプティブな方式です。実装は単純ですが、CPU バーストの長いプロセスが先に到着すると、後から来た短いプロセスが長く待たされます。この現象は、遅いトラックの後ろに乗用車の列ができる様子にたとえて、護送船団効果（convoy effect）と呼ばれます。上の例では、CPU バースト時間が 1 しかない P3 が、7 も待たされます。

SJF
~~~

SJF（Shortest Job First）は、実行可能なプロセスのうち、CPU バースト時間が最も短いものを選ぶ方式です。到着済みのプロセスの集まりに対して、SJF は平均待ち時間を最小にすることが知られています。短いプロセスを先に片付ければ、待たされるプロセスの数が早く減るからです。

SJF の問題は、CPU バースト時間を事前に知ることが一般にはできない点です。実際には、過去の CPU バースト時間から次の値を予測します。よく使われるのは、次の指数移動平均による予測です。

.. math::

   \tau_{n+1} = \alpha \, t_n + (1 - \alpha) \, \tau_n \qquad (0 \leq \alpha \leq 1)

ここで :math:`t_n` は :math:`n` 回目の CPU バーストの実際の長さ、:math:`\tau_n` はその予測値です。:math:`\alpha` を大きくするほど、直近の実績を重視した予測になります。

また、CPU バースト時間の長いプロセスは、短いプロセスが次々に到着すると、いつまでも実行されない飢餓に陥るおそれがあります。

SJF をプリエンプティブにした方式は、SRTF（Shortest Remaining Time First）と呼ばれます。新しいプロセスが到着したとき、その CPU バースト時間が実行中のプロセスの残り時間より短ければ、CPU を横取りして新しいプロセスに割り当てます。

ラウンドロビン
~~~~~~~~~~~~~~

ラウンドロビン（RR）は、実行可能なプロセスを待ち行列に並べ、先頭のプロセスにタイムクォンタム（タイムスライス）と呼ばれる一定の時間だけ CPU を割り当てる方式です。タイムクォンタムを使い切ったプロセスは、待ち行列の最後尾に戻ります。どのプロセスも一定時間内に必ず順番が回ってくるため、応答時間が短く、対話的な利用に向いています。

ラウンドロビンの性能は、タイムクォンタムの長さに大きく左右されます。

* タイムクォンタムが長すぎると、FCFS に近づき、応答時間が長くなる。
* タイムクォンタムが短すぎると、コンテキストスイッチの回数が増え、その費用の割合が大きくなる。

実際の OS では、タイムクォンタムは数ミリ秒から数十ミリ秒程度に設定されています。

優先度スケジューリング
~~~~~~~~~~~~~~~~~~~~~~

優先度スケジューリングは、プロセスごとに優先度を設定し、最も優先度の高いプロセスに CPU を割り当てる方式です。SJF も、CPU バースト時間が短いほど優先度が高いとみなせば、優先度スケジューリングの一種です。

優先度スケジューリングでも、優先度の低いプロセスが飢餓に陥るおそれがあります。これを防ぐ方法として、待ち時間が長くなるにつれて優先度を徐々に上げるエージングがあります。

多段フィードバックキュー
~~~~~~~~~~~~~~~~~~~~~~~~

多段フィードバックキュー（MLFQ：Multi-Level Feedback Queue）は、優先度の異なる複数の待ち行列を用意し、プロセスのふるまいに応じて待ち行列の間を移動させる方式です。典型的な規則は次のとおりです。

* 新しいプロセスは、最も優先度の高い待ち行列に入る。
* 優先度の高い待ち行列ほど、タイムクォンタムを短くする。
* タイムクォンタムを使い切ったプロセスは、CPU バウンドとみなして 1 つ下の待ち行列に移す。
* タイムクォンタムを使い切る前に入出力の待ちに入ったプロセスは、I/O バウンドとみなして同じ待ち行列にとどめる。
* 一定時間ごとに、すべてのプロセスを最上位の待ち行列に戻す（飢餓の防止）。

この方式では、CPU バースト時間を事前に知らなくても、実際のふるまいから I/O バウンドのプロセスを見分けて優先できます。SJF の考え方を、予測なしに近似しているといえます。多くの OS のスケジューラは、この考え方を土台にしています。

実際の OS のスケジューラ
------------------------

Linux
~~~~~

Linux は、目的の異なる複数のスケジューリングクラスを持っています。主なものを次の表に示します。

.. list-table:: Linux の主なスケジューリングクラス
   :header-rows: 1
   :widths: 25 50 25

   * - ポリシー
     - 内容
     - 用途
   * - ``SCHED_OTHER``、別名 ``SCHED_NORMAL``
     - 通常のプロセス向けの、公平性を重視した方式
     - ほとんどのプロセス
   * - ``SCHED_FIFO``
     - 優先度順で、同じ優先度の中では先着順。横取りされるのは、より優先度の高いプロセスが来たときだけ
     - リアルタイム処理
   * - ``SCHED_RR``
     - ``SCHED_FIFO`` に、同じ優先度の中でのラウンドロビンを加えたもの
     - リアルタイム処理
   * - ``SCHED_DEADLINE``
     - 締め切りに基づく方式（後述の EDF）
     - 周期的なリアルタイム処理

通常のプロセス向けの方式として、Linux は 2007 年のバージョン 2.6.23 から CFS（Completely Fair Scheduler）を使ってきました。CFS は、各プロセスがこれまでに使った CPU 時間を、優先度に応じて重み付けした仮想実行時間（vruntime）として記録し、常に仮想実行時間が最も小さいプロセスを選んで実行します。こうすることで、すべてのプロセスに優先度に応じた公平な CPU 時間を配分します。仮想実行時間の小さいプロセスを素早く見つけるため、実行可能なプロセスは赤黒木と呼ばれる平衡二分探索木で管理されます。

2023 年のバージョン 6.6 からは、CFS に代わって EEVDF（Earliest Eligible Virtual Deadline First）と呼ばれる方式が使われています。EEVDF は公平性の考え方を受け継ぎつつ、応答時間の短さを求めるプロセスをより適切に扱えるようにしたものです。

通常のプロセスの優先度は、nice 値と呼ばれる -20 から 19 までの値で調整できます。nice 値が大きいほど優先度が低くなり（他のプロセスに「親切に（nice）」譲る、という意味です）、受け取る CPU 時間の割合が小さくなります。

.. code-block:: console
   :linenos:

   $ nice -n 10 python heavy_task.py

Windows
~~~~~~~

Windows のスケジューラは、0 から 31 までの 32 段階の優先度に基づくプリエンプティブな優先度スケジューリングです。16 から 31 はリアルタイム用、1 から 15 は通常のスレッド用、0 はシステムが使います。同じ優先度のスレッドの間では、ラウンドロビンで CPU を割り当てます。

また Windows は、入出力が完了したスレッドや、前面に表示されているウィンドウのスレッドの優先度を一時的に引き上げる優先度ブーストを行います。これにより、I/O バウンドのスレッドや利用者が操作しているアプリケーションの応答性を高めています。

マルチコアのスケジューリング
----------------------------

複数の CPU コアを持つ計算機では、「どのスレッドを実行するか」に加えて「どのコアで実行するか」も決める必要があります。

* コアごとの実行可能キュー：すべてのコアが 1 つの待ち行列を共有すると、その待ち行列へのアクセスの奪い合いが性能の妨げになります。そのため現在の OS は、コアごとに実行可能キューを持たせています。
* 負荷分散：コアごとの待ち行列の長さに偏りが生じたら、混んでいるコアから空いているコアにスレッドを移します。
* プロセッサ親和性（アフィニティ）：スレッドを別のコアに移すと、元のコアのキャッシュに載っていたデータが使えなくなります。そのため OS は、なるべく同じコアでスレッドを実行し続けようとします。利用者がスレッドを実行するコアを明示的に指定することもできます。
* 異種コア：近年の CPU には、高性能なコア（P コア）と省電力なコア（E コア）を組み合わせたものがあります。OS は、スレッドの性質や優先度に応じて、適したコアに割り当てる必要があります。

リアルタイムスケジューリング
----------------------------

リアルタイムシステムでは、処理を締め切りまでに完了させることが求められます。締め切りを守れなかった場合の扱いによって、次の 2 つに分けられます。

* ハードリアルタイム：締め切りを 1 度でも守れなければ、システムの失敗とみなす。エアバッグや航空機の制御など。
* ソフトリアルタイム：締め切りを守れないことがまれにあっても許されるが、品質が低下する。動画や音声の再生など。

周期的に実行されるタスクのスケジューリングには、次の 2 つの方式がよく知られています。

* レートモノトニック（RM）：周期の短いタスクほど高い固定の優先度を与える。
* EDF（Earliest Deadline First）：締め切りが最も近いタスクを優先する。優先度は動的に変わる。

タスク :math:`i` の周期を :math:`P_i`、1 周期あたりの実行時間を :math:`C_i` とすると、CPU の利用率 :math:`U` は次の式で表されます。

.. math::

   U = \sum_{i=1}^{n} \frac{C_i}{P_i}

EDF では :math:`U \leq 1` であれば、すべてのタスクが締め切りを守れます。レートモノトニックでは、:math:`n` 個のタスクについて次の条件を満たせば、すべてのタスクが締め切りを守れることが保証されます。

.. math::

   U \leq n \left( 2^{1/n} - 1 \right)

右辺は :math:`n = 1` のとき 1、:math:`n = 2` のとき約 0.83 で、:math:`n` が大きくなると :math:`\ln 2 \approx 0.69` に近づきます。レートモノトニックは実装が単純で振る舞いを予測しやすい一方、EDF は CPU をより無駄なく使えます。

まとめ
------

* コンテキストスイッチは、実行中のスレッドの状態を保存し、別のスレッドの状態を復元する操作です。直接の費用に加えて、キャッシュの効果が失われる間接的な費用もあります。
* スケジューリングのアルゴリズムは、CPU 利用率、スループット、ターンアラウンド時間、待ち時間、応答時間などの指標で評価され、すべてを同時に最良にする方式はありません。
* FCFS は単純だが護送船団効果があり、SJF は平均待ち時間を最小にするが CPU バースト時間の予測が必要で、ラウンドロビンは応答時間を短くできます。
* Linux は公平性を重視した CFS や EEVDF を、Windows は優先度ブーストを伴う優先度スケジューリングを使っています。
* リアルタイムスケジューリングでは、締め切りを守ることが最も重要であり、レートモノトニックや EDF が使われます。
