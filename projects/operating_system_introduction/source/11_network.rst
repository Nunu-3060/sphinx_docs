OS とネットワーク
=================

ネットワーク通信は、OS が提供する最も重要な機能の 1 つです。この章では、アプリケーションがネットワークを使うためのソケット API と、送受信したデータがカーネルの中をどのように流れるかを説明します。ネットワークのプロトコルそのものの詳細ではなく、OS との関わりに焦点を当てます。

ソケット
--------

ソケットは、ネットワーク通信の端点を表す OS の抽象化です。「:doc:`03_history`」で見たように、ソケット API は 1983 年の 4.2BSD で導入され、現在では Windows を含むほぼすべての OS で、ほぼ同じ形で使えます。UNIX 系 OS では、ソケットはファイルディスクリプタとして表され、``read`` や ``write`` でも読み書きできます。

ソケットを作るときは、アドレスファミリーとソケットの種類を指定します。

.. list-table:: 主なアドレスファミリー
   :header-rows: 1
   :widths: 25 75

   * - アドレスファミリー
     - 内容
   * - ``AF_INET``
     - IPv4 による通信
   * - ``AF_INET6``
     - IPv6 による通信
   * - ``AF_UNIX``
     - 同じ計算機の中のプロセス間の通信（UNIX ドメインソケット）。ネットワークのプロトコルの処理を経ないので高速

.. list-table:: 主なソケットの種類
   :header-rows: 1
   :widths: 25 20 55

   * - 種類
     - プロトコル
     - 特徴
   * - ``SOCK_STREAM``
     - TCP
     - 接続を確立してから通信する。データは順序どおりに、欠けることなく届く。データはバイトの流れとして扱われ、送信時の区切りは保たれない
   * - ``SOCK_DGRAM``
     - UDP
     - 接続を確立せずに、データグラム（メッセージ）単位で送受信する。届く順序や、届くこと自体は保証されない

TCP のサーバーとクライアント
~~~~~~~~~~~~~~~~~~~~~~~~~~~~

TCP で通信するサーバーとクライアントは、次の順でシステムコールを呼びます。

.. list-table:: TCP の通信で使うシステムコール
   :header-rows: 1
   :widths: 20 40 40

   * - 段階
     - サーバー
     - クライアント
   * - 準備
     - ``socket`` でソケットを作り、``bind`` でアドレスとポート番号を割り当て、``listen`` で接続の受け付けを始める
     - ``socket`` でソケットを作る
   * - 接続
     - ``accept`` で接続を受け付ける。接続ごとに新しいソケットが返る
     - ``connect`` でサーバーに接続する
   * - 通信
     - ``recv`` と ``send`` でデータを送受信する
     - ``send`` と ``recv`` でデータを送受信する
   * - 終了
     - ``close`` でソケットを閉じる
     - ``close`` でソケットを閉じる

Python では、これらのシステムコールが ``socket`` モジュールの同名のメソッドとして提供されています。例えば、Web サーバーに HTTP の要求を送って応答の先頭を表示するクライアントは、次のように書けます。

.. code-block:: python
   :linenos:

   import socket

   # socket と connect をまとめて行う
   with socket.create_connection(("example.com", 80)) as sock:
       request = (
           b"GET / HTTP/1.1\r\n"
           b"Host: example.com\r\n"
           b"Connection: close\r\n\r\n"
       )
       sock.sendall(request)
       reply = sock.recv(1024)  # 最大 1024 バイトを受け取る
       print(reply.decode(errors="replace").splitlines()[0])

サーバーの例は、「:doc:`10_io_and_device`」のサンプルコード :download:`nonblocking_io.py <../examples/nonblocking_io.py>` を参照してください。

TCP がバイトの流れであることには注意が必要です。送信側が 100 バイトずつ 2 回 ``send`` しても、受信側の 1 回の ``recv`` で 200 バイトが届くこともあれば、50 バイトずつ 4 回に分かれて届くこともあります。メッセージの区切りが必要なら、長さを先頭に付ける、区切り文字を決めるなど、アプリケーションの側で決める必要があります。

ポート番号
~~~~~~~~~~

1 台の計算機の中で、通信の相手となるソケットを区別するのがポート番号です。0 から 65535 までの値で、Web サーバーの 80（HTTP）や 443（HTTPS）のように、よく使われるサービスには決まった番号が割り当てられています。UNIX 系 OS では、1024 未満のポート番号でソケットを待ち受けるには、原則として管理者の権限が必要です。

クライアントのソケットのポート番号は、通常は OS が空いている番号から自動的に割り当てます。サンプルコード :download:`nonblocking_io.py <../examples/nonblocking_io.py>` で、サーバーがポート番号 0 を指定して ``bind`` しているのも、空いている番号を OS に選ばせるためです。

カーネルの中のプロトコルスタック
--------------------------------

ネットワークのプロトコルは、役割ごとに層に分けて設計されています。インターネットで使われる TCP/IP では、次の 4 つの層に分けるのが一般的です。

.. list-table:: TCP/IP の層とその処理を担う部分
   :header-rows: 1
   :widths: 22 30 48

   * - 層
     - 主なプロトコル
     - 処理を担う部分
   * - アプリケーション層
     - HTTP、DNS、SSH
     - アプリケーション（ユーザー空間）
   * - トランスポート層
     - TCP、UDP
     - カーネル
   * - インターネット層
     - IP、ICMP
     - カーネル
   * - リンク層
     - イーサネット、Wi-Fi
     - カーネルのデバイスドライバとネットワークカード

トランスポート層からリンク層までの処理は、カーネルが担っています。この部分をプロトコルスタックと呼びます。アプリケーションは、TCP の再送制御や、IP のルーティング、イーサネットのフレームの組み立てなどを意識せず、ソケットにデータを書き込むだけで通信できます。

送信の流れ
~~~~~~~~~~

アプリケーションが TCP のソケットに ``send`` でデータを書き込むと、カーネルの中では次のように処理が進みます。

#. データを、ユーザー空間のバッファから、ソケットの送信バッファ（カーネルのメモリ）にコピーする。コピーが済めば、``send`` はアプリケーションに戻る。
#. TCP の層が、データを適当な大きさのセグメントに分け、ポート番号や順序番号などを含むヘッダーを付ける。
#. IP の層が、宛先の IP アドレスなどを含むヘッダーを付け、ルーティング表を引いて送出するネットワークインターフェースを決める。
#. リンク層で、宛先の MAC アドレスなどを含むヘッダーを付け、フレームを組み立てる。
#. デバイスドライバがネットワークカードに送信を指示し、ネットワークカードは DMA でメモリからフレームを読み出して送出する。

``send`` が戻った時点では、データはまだ相手に届いておらず、送信バッファに入っただけであることに注意してください。相手からの確認応答が届くまで、TCP はデータを送信バッファに残しておき、失われた場合は再送します。

受信の流れ
~~~~~~~~~~

受信の流れは、送信の逆向きです。

#. ネットワークカードがフレームを受け取り、DMA でメモリに書き込んで、割り込みで CPU に知らせる。
#. デバイスドライバとリンク層が、フレームを取り出して IP の層に渡す。
#. IP の層が、宛先が自分であることを確かめ、TCP の層に渡す。
#. TCP の層が、順序を整え、確認応答を返し、データを該当するソケットの受信バッファに入れる。
#. ``recv`` を呼んで待っていたプロセスがあれば、それを実行可能な状態にする。
#. プロセスの ``recv`` が、受信バッファからユーザー空間のバッファにデータをコピーして戻る。

受信バッファが満杯になると、TCP は相手に送信を控えるよう伝えます（フロー制御）。アプリケーションの処理が遅いと、通信全体の速度もそれに合わせて落ちることになります。

ループバック
~~~~~~~~~~~~

宛先が自分自身の IP アドレス 127.0.0.1（IPv6 では ::1）である通信は、ループバックと呼ばれる仮想的なネットワークインターフェースを通ります。データは実際のネットワークカードを経由せず、カーネルの中で送信側から受信側に折り返されます。サンプルコード :download:`nonblocking_io.py <../examples/nonblocking_io.py>` の通信もループバックを使っています。

ネットワークの高速化
--------------------

ネットワークの速度が毎秒数十から数百ギガビットに達するようになると、カーネルのプロトコルスタックの処理が性能の妨げになる場面が出てきました。そこで、次のような工夫が使われています。

* オフロード：チェックサムの計算や、大きなデータのセグメントへの分割などを、CPU ではなくネットワークカードのハードウェアで行う。
* ゼロコピー：ファイルの内容をネットワークに送るとき、ユーザー空間を経由せずにカーネルの中で直接送る（Linux の ``sendfile`` システムコールなど）。データのコピーの回数が減る。
* カーネルバイパス：DPDK のように、ネットワークカードをユーザー空間のプログラムから直接操作し、カーネルのプロトコルスタックを経由しない。
* カーネル内での処理：Linux の eBPF と XDP のように、利用者が書いた小さなプログラムを、カーネルの中の受信処理のなるべく早い段階で安全に実行させる。

通信の状態を観察する
--------------------

ソケットの状態は、次のコマンドで確かめられます。

.. code-block:: console
   :linenos:

   $ ss -tan
   $ netstat -an

Linux の ``ss`` コマンドは、``-t`` で TCP のソケットを、``-a`` で待ち受け中のものも含むすべてのソケットを、``-n`` でポート番号を名前に変換せずに表示します。Windows でも ``netstat -an`` で同様の情報が得られます。表示される状態のうち、``LISTEN`` は接続の待ち受け中、``ESTABLISHED`` は通信中、``TIME_WAIT`` は接続を閉じた後、遅れて届くパケットに備えてしばらく待っている状態です。

まとめ
------

* アプリケーションは、OS が提供するソケットを通してネットワーク通信を行います。ソケット API は BSD で生まれ、ほぼすべての OS で使われています。
* TCP はバイトの流れを、UDP はメッセージ単位の送受信を提供します。TCP ではメッセージの区切りをアプリケーションが決める必要があります。
* トランスポート層からリンク層までのプロトコルの処理は、カーネルのプロトコルスタックが担っています。
* ``send`` は送信バッファにデータをコピーした時点で戻り、``recv`` は受信バッファからデータをコピーします。
