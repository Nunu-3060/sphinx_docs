仮想化とコンテナ
================

1 台の物理的な計算機の上で、互いに隔離された複数の実行環境を動かす技術は、クラウドやサーバーの運用に欠かせないものになっています。この章では、仮想マシンを実現するハイパーバイザーの仕組みと、より軽量な隔離の方式であるコンテナの仕組みを説明し、両者を比べます。

仮想化とは
----------

本書でここまで見てきた OS の抽象化（プロセス、仮想アドレス空間、ファイル）は、どれも「資源を占有しているかのような幻想」を与えるものでした。仮想化は、この考え方を計算機全体に広げたものといえます。仮想化では、ソフトウェアによって仮想的な計算機（仮想マシン、VM）を作り、その上で OS を丸ごと動かします。仮想マシンの上で動く OS をゲスト OS と呼びます。

仮想化の主な利点は次のとおりです。

* 資源の有効利用：1 台の物理的なサーバーに、複数のサーバーを集約できる。
* 隔離：仮想マシン同士は互いに隔離されており、1 つのゲスト OS の障害や侵害が他に波及しにくい。
* 柔軟な運用：仮想マシンの作成、複製、保存、別の物理サーバーへの移動（ライブマイグレーション）が容易になる。
* 異なる OS の共存：Windows の上で Linux を動かすなど、異なる OS を同時に使える。

ハイパーバイザー
----------------

仮想マシンを作り、管理するソフトウェアをハイパーバイザー（仮想マシンモニタ）と呼びます。ハイパーバイザーは、その動き方によって次の 2 種類に分けられます。

.. list-table:: ハイパーバイザーの種類
   :header-rows: 1
   :widths: 20 50 30

   * - 種類
     - 説明
     - 例
   * - タイプ 1（ベアメタル型）
     - ハードウェアの上で直接動き、その上で複数のゲスト OS を動かす。性能が高く、サーバーやクラウドで使われる
     - VMware ESXi、Microsoft Hyper-V、Xen、KVM
   * - タイプ 2（ホスト型）
     - 通常の OS（ホスト OS）の上でアプリケーションとして動く。手軽に使えるため、開発や検証の用途で使われる
     - VMware Workstation、Oracle VirtualBox

なお、KVM は Linux カーネルの機能としてハイパーバイザーを実現するもので、Linux カーネル自体がハイパーバイザーとして働くため、タイプ 1 に分類されることが多いです。Hyper-V も、有効にすると Windows 自体が Hyper-V の上で動く構成になります。このように、実際の製品では 2 つの種類の境界はあいまいになっています。

CPU の仮想化
~~~~~~~~~~~~

ゲスト OS のカーネルは、自分がカーネルモードで動き、ハードウェアを自由に操作できると考えています。しかし、ゲスト OS に本当の意味でのカーネルモードを与えてしまうと、物理的な計算機全体を操作できてしまい、隔離が成り立ちません。

伝統的な方法は、ゲスト OS のカーネルをユーザーモードで動かし、ゲスト OS が特権命令を実行しようとすると例外が起きることを利用して、ハイパーバイザーがその命令の動作を代わりに模倣するというものです。この方式をトラップアンドエミュレートと呼びます。しかし、x86 の CPU には、ユーザーモードで実行しても例外にならず、黙って異なる動作をする命令があったため、この方式をそのままでは使えませんでした。

この問題に対して、次のような方法が考え出されました。

.. list-table:: x86 の CPU の仮想化の方法
   :header-rows: 1
   :widths: 25 75

   * - 方法
     - 説明
   * - バイナリ変換
     - ゲスト OS のカーネルの機械語を実行前に調べ、問題のある命令を、ハイパーバイザーを呼び出す命令に書き換えて実行する。初期の VMware が採用した
   * - 準仮想化
     - ゲスト OS のソースコードを変更し、問題のある命令の代わりに、ハイパーバイザーを直接呼び出す（ハイパーコール）ようにする。Xen が採用した
   * - ハードウェア支援仮想化
     - CPU に仮想化のための新しい動作モードを追加し、ゲスト OS をそのモードのカーネルモードで動かす。特別な操作を行ったときだけハイパーバイザーに制御が移る。インテル社の VT-x、AMD 社の AMD-V

現在は、ハードウェア支援仮想化が標準的な方法です。

メモリの仮想化
~~~~~~~~~~~~~~

仮想化の環境では、アドレスの変換が 2 段階になります。ゲスト OS は、自分のプロセスの仮想アドレスを、自分が物理アドレスだと思っているアドレス（ゲスト物理アドレス）に変換します。ハイパーバイザーは、それをさらに本当の物理アドレス（ホスト物理アドレス）に変換する必要があります。

現在の CPU は、この 2 段階の変換をハードウェアで行う機能（インテル社の EPT、AMD 社の NPT）を持っており、仮想化によるメモリアクセスの性能の低下を小さくしています。

入出力の仮想化
~~~~~~~~~~~~~~

ゲスト OS から見える装置（ディスクやネットワークカード）は、ハイパーバイザーがソフトウェアで模倣した仮想的な装置です。実在する装置をそのまま模倣すると、ゲスト OS は既存のドライバを使えますが、処理の費用が大きくなります。そこで、仮想化の環境に特化して効率よく動くように設計された装置とドライバ（Linux の virtio など）が使われます。さらに高い性能が必要な場合は、物理的な装置をゲスト OS に直接割り当てる方法（パススルー）もあります。

コンテナ
--------

仮想マシンは強力な隔離を提供しますが、仮想マシンごとにゲスト OS を丸ごと動かすため、メモリやストレージの消費が大きく、起動にも時間がかかります。多くの場合、本当に必要なのは OS 全体の隔離ではなく、アプリケーションとそれが依存するライブラリなどをまとめて、他のアプリケーションから隔離して動かすことです。

コンテナは、このような目的のために、1 つのカーネルを共有したまま、プロセスのグループごとに隔離された環境を作る技術です。コンテナの中のプロセスは、ホストから見ると普通のプロセスですが、自分専用のファイルシステム、ネットワーク、プロセスの一覧などを持っているかのように見えます。

Linux のコンテナは、主にカーネルの次の 2 つの機能で実現されています。

namespace
~~~~~~~~~

namespace（名前空間）は、プロセスから見えるシステムの資源を、グループごとに分離する機能です。

.. list-table:: Linux の主な namespace
   :header-rows: 1
   :widths: 25 75

   * - namespace
     - 分離するもの
   * - PID
     - プロセス ID。コンテナの中の最初のプロセスは、コンテナの中ではプロセス ID 1 に見える
   * - マウント
     - ファイルシステムのマウントの状態。コンテナごとに別のルートファイルシステムを見せられる
   * - ネットワーク
     - ネットワークインターフェース、IP アドレス、ルーティング表、ポート番号
   * - UTS
     - ホスト名
   * - IPC
     - プロセス間通信の資源（共有メモリなど）
   * - ユーザー
     - ユーザー ID。コンテナの中の root を、ホストでは一般の利用者に対応付けられる

cgroup
~~~~~~

cgroup（control group）は、プロセスのグループごとに、使える資源の量を制限し、使用量を計測する機能です。CPU 時間、メモリの使用量、ストレージの入出力の帯域、作れるプロセスの数などを制限できます。例えば、あるコンテナのメモリの上限を 512 MiB に設定すると、コンテナの中のプロセスの使用量の合計がそれを超えたときに、そのコンテナの中だけで OOM Killer（「:doc:`08_memory`」を参照）が働きます。

コンテナイメージ
~~~~~~~~~~~~~~~~

Docker に代表されるコンテナの技術を普及させたもう 1 つの要素が、コンテナイメージです。コンテナイメージは、アプリケーションと、それが動くために必要なライブラリや設定ファイルなどを 1 つにまとめたものです。同じイメージからは、どの計算機でも同じ環境のコンテナを作れるので、「開発者の計算機では動くのに、本番のサーバーでは動かない」という問題を減らせます。

コンテナイメージは、変更の差分を層として積み重ねる構造になっており、共通の層は複数のイメージで共有されます。コンテナの実行時には、読み込み専用のイメージの層の上に、書き込み可能な層を重ねて使います。

コンテナはカーネルを共有するので、コンテナの中で動かせるのは、ホストのカーネルの上で動くプログラムだけです。例えば、Windows や macOS の上で Linux のコンテナを動かす場合、実際には裏で Linux の仮想マシンが動いています。

仮想マシンとコンテナの比較
--------------------------

.. list-table:: 仮想マシンとコンテナの比較
   :header-rows: 1
   :widths: 22 39 39

   * - 観点
     - 仮想マシン
     - コンテナ
   * - 隔離の単位
     - ハードウェア（OS を丸ごと隔離）
     - プロセスのグループ（カーネルは共有）
   * - 隔離の強さ
     - 強い。カーネルの脆弱性の影響が他の仮想マシンに及びにくい
     - 仮想マシンより弱い。カーネルの脆弱性が全コンテナに影響し得る
   * - 起動の時間
     - 数秒から数十秒（OS の起動が必要）
     - 1 秒未満のことが多い（プロセスの起動だけ）
   * - 資源の消費
     - 大きい（ゲスト OS の分が必要）
     - 小さい
   * - 動かせる OS
     - ハイパーバイザーが対応する任意の OS
     - ホストと同じカーネルの上で動くもの

両者は対立するものではなく、組み合わせて使われることがよくあります。クラウドでは、仮想マシンの上でコンテナを動かすのが一般的です。また、コンテナの手軽さと仮想マシンの隔離の強さを両立させるため、コンテナごとにごく軽量な仮想マシンを使う技術（AWS の Firecracker や Kata Containers など）も開発されています。

まとめ
------

* 仮想化は、ハイパーバイザーによって仮想的な計算機を作り、その上でゲスト OS を丸ごと動かす技術です。
* x86 の仮想化は、バイナリ変換や準仮想化を経て、現在は CPU によるハードウェア支援仮想化が標準になっています。メモリの 2 段階のアドレス変換も、ハードウェアで支援されます。
* コンテナは、カーネルを共有したまま、namespace による資源の見え方の分離と、cgroup による資源の量の制限によって、プロセスのグループを隔離します。
* 仮想マシンは隔離が強く、コンテナは軽量です。両者は目的に応じて組み合わせて使われます。
