OS を観察する
=============

ここまでの章で学んだ OS の仕組みは、実際の OS の上で観察できます。この章では、Linux と Windows で OS の状態を観察するための主な道具を紹介し、性能の問題が起きたときに原因を切り分ける考え方を説明します。

観察の道具
----------

Linux と Windows で、OS の状態を観察する主な道具を次の表にまとめます。

.. list-table:: OS の状態を観察する主な道具
   :header-rows: 1
   :widths: 20 40 40

   * - 観察の対象
     - Linux
     - Windows
   * - プロセスの一覧
     - ``ps``、``top``、``htop``
     - タスクマネージャー、PowerShell の ``Get-Process``
   * - CPU とメモリの概況
     - ``top``、``vmstat``、``free``
     - タスクマネージャーの［パフォーマンス］タブ
   * - ストレージの入出力
     - ``iostat``
     - リソースモニター
   * - ネットワーク
     - ``ss``、``ip``
     - ``netstat``、``Get-NetTCPConnection``
   * - 開いているファイル
     - ``lsof``、``/proc/<PID>/fd``
     - リソースモニター、Process Explorer
   * - システムコールの追跡
     - ``strace``
     - Process Monitor
   * - 性能の詳細な分析
     - ``perf``、eBPF を使うツール
     - Windows Performance Recorder と Analyzer
   * - カーネルのログ
     - ``dmesg``、``journalctl``
     - イベントビューアー

Process Explorer と Process Monitor は、マイクロソフト社が無償で配布している Sysinternals と呼ばれるツール群に含まれています。

プロセスを観察する
------------------

ps と top
~~~~~~~~~

Linux の ``ps`` コマンドは、プロセスの一覧を表示します。

.. code-block:: console
   :linenos:

   $ ps -eo pid,ppid,stat,ni,rss,vsz,comm --sort=-rss | head -n 5

このコマンドは、すべてのプロセスについて、プロセス ID、親プロセス ID、状態、nice 値、RSS、VSZ（単位はいずれも KiB）、コマンド名を、RSS の大きい順に表示します。``STAT`` の列の主な値の意味は次のとおりです。

.. list-table:: ps の STAT の列の主な値
   :header-rows: 1
   :widths: 15 45 40

   * - 値
     - 意味
     - 対応する状態（第 5 章）
   * - ``R``
     - 実行中、または実行可能
     - 実行中、実行可能
   * - ``S``
     - 割り込み可能な待ち（シグナルで起こせる）
     - 待ち
   * - ``D``
     - 割り込み不可能な待ち（主にストレージの入出力の待ち）
     - 待ち
   * - ``Z``
     - ゾンビ
     - 終了
   * - ``T``
     - 停止中（Ctrl+Z やデバッガによる）
     - （一時停止）

``top`` コマンドは、プロセスの一覧と CPU やメモリの使用状況を、数秒ごとに更新しながら表示します。

/proc ファイルシステム
~~~~~~~~~~~~~~~~~~~~~~

Linux の ``/proc`` ディレクトリには、カーネルの内部情報がファイルの形で並んでいます（「:doc:`09_storage_and_filesystem`」を参照）。``ps`` や ``top`` も、実はここに並ぶファイルを読んで情報を表示しています。

.. code-block:: console
   :linenos:

   $ cat /proc/self/status
   $ ls -l /proc/self/fd
   $ cat /proc/loadavg
   $ cat /proc/meminfo

``/proc/self`` は、それを読んでいるプロセス自身のディレクトリを指します。``status`` にはプロセスの状態やメモリの使用量が、``fd`` にはそのプロセスが開いているファイルディスクリプタの一覧が、シンボリックリンクとして並んでいます。

システムの概況を観察する
------------------------

ロードアベレージ
~~~~~~~~~~~~~~~~

``uptime`` や ``top`` で表示されるロードアベレージは、直近 1 分、5 分、15 分の、実行可能または実行中のプロセスの数の平均です。Linux では、割り込み不可能な待ち（``D`` の状態）のプロセスも数に含まれます。

ロードアベレージは、CPU コアの数と比べて解釈します。例えば 4 コアの計算機でロードアベレージが 4 なら、ちょうど CPU が埋まっている状態で、8 なら平均して半数のプロセスが CPU の順番を待っている状態です。ただし Linux では入出力の待ちも数に含むため、ロードアベレージが高くても、CPU ではなくストレージが原因であることもあります。

vmstat
~~~~~~

``vmstat`` コマンドは、CPU、メモリ、スワップ、入出力の状況を一定間隔で表示します。

.. code-block:: console
   :linenos:

   $ vmstat 1

出力の主な列の意味は次のとおりです。

.. list-table:: vmstat の主な列
   :header-rows: 1
   :widths: 15 85

   * - 列
     - 意味
   * - ``r``
     - 実行可能なプロセスの数（CPU の順番待ちを含む）
   * - ``b``
     - 割り込み不可能な待ちのプロセスの数
   * - ``si``、``so``
     - スワップ領域からの読み込み量、スワップ領域への書き出し量。0 以外の値が続く場合はメモリ不足を疑う
   * - ``cs``
     - 1 秒あたりのコンテキストスイッチの回数
   * - ``us``、``sy``
     - CPU 時間のうち、ユーザーモードとカーネルモードで使われた割合
   * - ``wa``
     - CPU が入出力の完了を待って空いていた時間の割合
   * - ``id``
     - CPU が空いていた時間の割合

``sy`` が高い場合は、システムコールや割り込みの処理が多いことを示しています。

性能の問題を切り分ける
----------------------

「システムが遅い」という問題に直面したとき、やみくもに設定を変えたり、思い付きでツールを使ったりしても、原因にはなかなかたどり着けません。資源ごとに順に確かめていく体系的な方法が有効です。

USE メソッド
~~~~~~~~~~~~

USE メソッドは、性能の分析で知られるグレッグ（Brendan Gregg）が提唱した方法で、すべての資源について、次の 3 つの観点を順に確かめます。

.. list-table:: USE メソッドの 3 つの観点
   :header-rows: 1
   :widths: 25 75

   * - 観点
     - 内容
   * - 使用率（Utilization）
     - 資源が仕事をしていた時間の割合
   * - 飽和（Saturation）
     - 資源が処理しきれずに、仕事が待たされている度合い（待ち行列の長さなど）
   * - エラー（Errors）
     - エラーの発生回数

対象となる資源と、各観点を確かめる手段の例を次の表に示します（Linux の場合）。

.. list-table:: 資源ごとの確かめ方の例
   :header-rows: 1
   :widths: 16 28 28 28

   * - 資源
     - 使用率
     - 飽和
     - エラー
   * - CPU
     - ``vmstat`` の ``us`` と ``sy``
     - ``vmstat`` の ``r`` がコア数を超えている
     - （まれ）
   * - メモリ
     - ``free`` の使用量
     - ``vmstat`` の ``si`` と ``so``、OOM Killer の記録
     - メモリの割り当ての失敗
   * - ストレージ
     - ``iostat -x`` の ``%util``
     - ``iostat -x`` の待ち行列の長さ
     - ``dmesg`` の入出力エラー
   * - ネットワーク
     - インターフェースの送受信量
     - パケットの破棄、TCP の再送
     - インターフェースのエラーの数

よくある症状と原因
~~~~~~~~~~~~~~~~~~

本書で学んだ知識と結び付けて、よくある症状とその原因の候補を挙げておきます。

.. list-table:: よくある症状と原因の候補
   :header-rows: 1
   :widths: 35 40 25

   * - 症状
     - 原因の候補
     - 関連する章
   * - CPU の ``sy`` が高い
     - システムコールが多すぎる（小さな読み書きの繰り返しなど）
     - 第 4 章
   * - プロセスがエラーを出さずに突然終了した
     - OOM Killer による強制終了（``dmesg`` で確かめる）
     - 第 8 章
   * - ストレージへのアクセスが止まらず、全体が極端に遅い
     - メモリ不足によるスラッシング
     - 第 8 章
   * - 「Too many open files」というエラー
     - ファイルディスクリプタの閉じ忘れ、または上限が小さすぎる
     - 第 9 章
   * - 書き込みは速いのに、電源断でデータが消えた
     - ページキャッシュへの書き込みで止まっていた（``fsync`` がない）
     - 第 9 章
   * - CPU の使用率は低いのに処理が進まない
     - 入出力の待ち、ロックの待ち、デッドロック
     - 第 6 章、第 10 章
   * - ゾンビプロセスが増え続ける
     - 親プロセスが ``wait`` で子プロセスを回収していない
     - 第 5 章

まとめ
------

* Linux では ``ps``、``top``、``vmstat``、``/proc`` などで、Windows ではタスクマネージャーやリソースモニター、Sysinternals のツールなどで、OS の状態を観察できます。
* ロードアベレージや ``vmstat`` の値は、CPU コアの数や OS ごとの定義を踏まえて解釈する必要があります。
* 性能の問題は、USE メソッドのように、資源ごとに使用率、飽和、エラーを順に確かめることで体系的に切り分けられます。
