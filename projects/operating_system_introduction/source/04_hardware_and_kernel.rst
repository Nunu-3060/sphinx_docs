ハードウェアとカーネル
======================

OS は、ハードウェアの支援なしには役割を果たせません。この章では、OS を支える CPU の仕組み（特権モード、割り込み、タイマー）と、アプリケーションがカーネルに処理を依頼するシステムコールの仕組みを説明します。続いて、電源を入れてから OS が動き出すまでの流れと、カーネルの構成の違いを見ます。

CPU の特権モード
----------------

「:doc:`02_what_is_os`」で述べたように、現代の CPU には少なくともカーネルモードとユーザーモードの 2 つの動作モードがあります。ユーザーモードでは、次のような操作が禁止されています。

* 入出力装置を直接操作する命令の実行
* 割り込みを禁止する命令の実行
* メモリ管理の設定（ページテーブルの切り替えなど）の変更
* CPU の動作モードの変更

ユーザーモードのプログラムがこれらの操作を行おうとすると、CPU は例外を発生させ、制御をカーネルに移します。カーネルは通常、その操作を行ったプロセスを強制終了させます。この仕組みにより、アプリケーションがどれほど誤った動作をしても、カーネルや他のプロセスを壊せないようになっています。

CPU のアーキテクチャによって、特権の段階の数や呼び名は異なります。

.. list-table:: CPU アーキテクチャごとの特権の段階
   :header-rows: 1
   :widths: 20 40 40

   * - アーキテクチャ
     - 特権の段階
     - 主な使われ方
   * - x86（x86-64）
     - リング 0 からリング 3 の 4 段階
     - カーネルがリング 0、アプリケーションがリング 3 を使い、リング 1 と 2 はほとんど使われない
   * - Arm（AArch64）
     - EL0 から EL3 の 4 段階（Exception Level）
     - EL0 がアプリケーション、EL1 がカーネル、EL2 がハイパーバイザー、EL3 がセキュアモニタ
   * - RISC-V
     - U、S、M の 3 段階（必要に応じてハイパーバイザー用の拡張あり）
     - U がアプリケーション、S がカーネル、M がファームウェア

割り込みと例外
--------------

CPU は普段、メモリから命令を 1 つずつ取り出して順に実行しています。この流れを中断して、別の処理（ハンドラ）を実行させる仕組みが割り込みです。割り込みは、その原因によって次のように分類されます。

.. list-table:: 割り込みと例外の分類
   :header-rows: 1
   :widths: 22 43 35

   * - 種類
     - 説明
     - 例
   * - ハードウェア割り込み
     - CPU の外の装置が、CPU に事象の発生を知らせる。実行中の命令とは無関係に、非同期に発生する
     - キーボードの入力、ネットワークのパケットの到着、ディスクの転送完了、タイマー
   * - 例外（フォールト）
     - 実行中の命令が正常に実行できなかったことを知らせる。命令の実行に同期して発生する
     - 0 による除算、不正なメモリアクセス、ページフォールト
   * - トラップ
     - プログラムが意図的に発生させる。命令の実行に同期して発生する
     - システムコールの呼び出し、デバッガのブレークポイント

用語の使い方は文献や CPU のアーキテクチャによって異なり、これらを総称して割り込みと呼ぶこともあれば、例外と呼ぶこともあります。本書では、装置から来るものを割り込み、命令の実行に伴って発生するものを例外と呼び分けます。

割り込みや例外が発生すると、CPU は次のことを行います。

#. 実行中のプログラムの状態（次に実行する命令のアドレスなど）を保存する。
#. カーネルモードに切り替える。
#. 割り込みベクタテーブルと呼ばれる表を参照し、原因に応じたハンドラに処理を移す。

ハンドラの処理が終わると、保存しておいた状態を復元し、ユーザーモードに戻って元のプログラムの実行を再開します。割り込みベクタテーブルはカーネルが起動時に設定し、ユーザーモードのプログラムからは変更できません。そのため、ユーザーモードからカーネルモードに移る入口は、カーネルが用意したハンドラだけに限られます。

カーネルは、ユーザーモードのプログラムから見ると「割り込みや例外が起きたときにだけ動くプログラム」ともいえます。カーネルは常に動いているわけではなく、システムコール、装置からの割り込み、例外などをきっかけに呼び出され、処理を終えるとアプリケーションに CPU を返します。

タイマー割り込み
~~~~~~~~~~~~~~~~

割り込みの中でも、OS にとって特に重要なのがタイマー割り込みです。CPU には一定時間ごとに割り込みを発生させるタイマーが備わっています。

もしタイマー割り込みがなければ、ユーザーモードのプログラムが無限ループに陥ったとき、そのプログラムが自分からシステムコールを呼ばない限り、カーネルに制御が戻りません。タイマー割り込みがあれば、カーネルは定期的に制御を取り戻し、必要に応じて実行中のプロセスから CPU を取り上げて、別のプロセスに割り当てられます。「:doc:`03_history`」で見たプリエンプションは、この仕組みによって実現されています。

システムコール
--------------

アプリケーションがカーネルに処理を依頼する仕組みがシステムコールです。システムコールは、通常の関数呼び出しとは異なり、ユーザーモードからカーネルモードへの切り替えを伴います。

システムコールの流れ
~~~~~~~~~~~~~~~~~~~~

x86-64 の Linux を例に、アプリケーションがファイルからデータを読む ``read`` システムコールの流れを見ます。

#. アプリケーションが、C 標準ライブラリの ``read`` 関数を呼び出す。
#. ライブラリの関数は、システムコールの番号（``read`` は 0 番）をレジスタ ``rax`` に、引数（ファイルディスクリプタ、バッファのアドレス、バイト数）を決められたレジスタに設定する。
#. ライブラリの関数が ``syscall`` 命令を実行する。CPU はカーネルモードに切り替わり、カーネルのシステムコールの入口に処理が移る。
#. カーネルは、番号をもとにシステムコールの表を引き、``read`` の処理を呼び出す。
#. カーネルは引数を検査し（ファイルディスクリプタが有効か、バッファのアドレスがそのプロセスのメモリの範囲内かなど）、データを読み出してバッファにコピーする。
#. カーネルは結果（読んだバイト数、またはエラー番号）をレジスタ ``rax`` に設定し、``sysret`` 命令でユーザーモードに戻る。
#. ライブラリの関数が結果を受け取り、アプリケーションに返す。

この流れを C 言語で書くと、アプリケーション側からは次のような普通の関数呼び出しに見えます。

.. code-block:: c
   :linenos:

   #include <unistd.h>

   char buffer[100];
   ssize_t n = read(fd, buffer, sizeof(buffer));  /* システムコールを呼ぶ */
   if (n < 0) {
       /* エラーの場合は errno にエラーの原因が設定される */
   }

カーネルが引数を検査する手順（5）は重要です。アプリケーションはカーネルにとって信頼できない相手であり、カーネルのメモリのアドレスをバッファとして渡すといった不正な依頼をしてくる可能性があります。カーネルは、すべての依頼を疑ってかかる必要があります。

主なシステムコール
~~~~~~~~~~~~~~~~~~

Linux には数百個のシステムコールがあります。主なものを分類して次の表に示します。Windows では、アプリケーションはシステムコールを直接使わず、Win32 API の関数（右の列）を使います。

.. list-table:: 主なシステムコール
   :header-rows: 1
   :widths: 18 32 25 25

   * - 分類
     - 機能
     - Linux
     - Windows（Win32 API）
   * - プロセス
     - プロセスの作成
     - ``fork``、``clone``
     - ``CreateProcess``
   * - プロセス
     - プログラムの実行
     - ``execve``
     - （``CreateProcess`` に含まれる）
   * - プロセス
     - 終了と終了の待ち合わせ
     - ``exit``、``wait4``
     - ``ExitProcess``、``WaitForSingleObject``
   * - ファイル
     - 開く、閉じる
     - ``open``、``close``
     - ``CreateFile``、``CloseHandle``
   * - ファイル
     - 読み書き
     - ``read``、``write``
     - ``ReadFile``、``WriteFile``
   * - メモリ
     - メモリの確保と解放
     - ``mmap``、``munmap``、``brk``
     - ``VirtualAlloc``、``VirtualFree``
   * - 通信
     - ソケットの操作
     - ``socket``、``connect``、``send``
     - Winsock の ``socket``、``connect``、``send``
   * - 情報
     - 時刻やプロセス ID の取得
     - ``clock_gettime``、``getpid``
     - ``GetSystemTime``、``GetCurrentProcessId``

システムコールの費用
~~~~~~~~~~~~~~~~~~~~

システムコールは、通常の関数呼び出しよりもかなり時間がかかります。モードの切り替え、レジスタの保存と復元、引数の検査などが必要なうえ、CPU のキャッシュなどの状態がカーネルの処理によって乱されるからです。そのため、性能が重要なプログラムでは、システムコールの回数を減らす工夫が欠かせません。

代表的な工夫がバッファリングです。例えば 1 バイトずつファイルに書き込む場合、毎回 ``write`` システムコールを呼ぶのではなく、ユーザー空間のバッファにデータを溜めておき、バッファが一杯になったときにまとめて 1 回の ``write`` で書き込みます。C の標準入出力（``printf`` や ``fwrite``）や、Python の ``open`` 関数で開いたファイルは、既定でこのバッファリングを行います。

サンプルコード :download:`syscall_cost.py <../examples/syscall_cost.py>` は、10 万バイトを 1 バイトずつファイルに書き込む処理を、バッファリングなし（毎回 ``os.write`` を呼ぶ）とバッファリングあり（``open`` で開いたファイルに書く）で比べるものです。

.. literalinclude:: ../examples/syscall_cost.py
   :language: python
   :linenos:
   :caption: syscall_cost.py

実行結果の例は次のとおりです。

.. code-block:: text

   書き込んだバイト数      : 100,000
   os.write (バッファなし) : 0.471 秒
   open() (バッファあり)   : 0.013 秒
   速度比                  : 約 37 倍

具体的な数値は環境によって大きく異なりますが、バッファリングによって数十倍の差が生じることが分かります。なお、この差にはシステムコールそのものの費用に加えて、カーネル内のファイルシステムの処理の費用も含まれています。

システムコールを観察する
~~~~~~~~~~~~~~~~~~~~~~~~

Linux では、``strace`` コマンドを使うと、プログラムが呼び出したシステムコールを一覧できます。例えば次のように実行すると、``cat`` コマンドがファイルを読んで表示するまでのシステムコールが表示されます。

.. code-block:: console
   :linenos:

   $ strace cat hello.txt

出力の一部を抜き出すと、次のようになります（引数や値は環境によって異なります）。

.. code-block:: text

   openat(AT_FDCWD, "hello.txt", O_RDONLY) = 3
   fstat(3, {st_mode=S_IFREG|0644, st_size=6, ...}) = 0
   read(3, "hello\n", 131072)              = 6
   write(1, "hello\n", 6)                  = 6
   read(3, "", 131072)                     = 0
   close(3)                                = 0

ファイルを開いてファイルディスクリプタ 3 を得て、そこから読んだデータを標準出力（ファイルディスクリプタ 1）に書き、読むデータがなくなったら（``read`` が 0 を返したら）ファイルを閉じる、という流れが読み取れます。``strace`` は、プログラムがどのファイルを開こうとして失敗しているのか、どこで待たされているのかを調べるのに役立ちます。詳しくは「:doc:`14_practice`」で扱います。

起動の流れ
----------

計算機の電源を入れてから OS が使えるようになるまでの流れを、ブート（boot）と呼びます。「靴ひもを引っぱって自分を持ち上げる（bootstrap）」という不可能なたとえに由来する言葉で、何もない状態から少しずつ大きなプログラムを読み込んでいく様子を表しています。

一般的な PC の起動の流れは次のとおりです。

.. list-table:: PC の起動の流れ
   :header-rows: 1
   :widths: 25 75

   * - 段階
     - 内容
   * - ファームウェア
     - 電源が入ると、CPU はマザーボード上の不揮発性メモリにあるファームウェア（UEFI、古い PC では BIOS）を実行する。ファームウェアはハードウェアを検査、初期化し、起動するストレージ装置を選ぶ
   * - ブートローダー
     - ファームウェアが、ストレージ装置からブートローダーを読み込んで実行する。ブートローダーはカーネルと初期 RAM ディスクをメモリに読み込む。Linux では GRUB、Windows では Windows Boot Manager が使われる
   * - カーネルの初期化
     - カーネルがメモリ管理、割り込み、デバイスドライバなどを初期化し、ルートファイルシステムをマウントする
   * - 最初のユーザープロセス
     - カーネルは最初のユーザープロセスを起動する。Linux では多くの場合 systemd がこの役割を担い、プロセス ID は 1 になる。Windows ではセッションマネージャー（smss.exe）が起動される
   * - サービスとログイン
     - 最初のプロセスが、各種のサービス（デーモン）やログイン画面を起動する

UEFI には、署名されたブートローダーやカーネルだけを起動するセキュアブートという機能もあります。これについては「:doc:`12_security`」で触れます。

カーネルの構成
--------------

カーネルにどこまでの機能を含めるかによって、カーネルの構成はいくつかの方式に分かれます。

モノリシックカーネル
~~~~~~~~~~~~~~~~~~~~

モノリシック（monolithic、「一枚岩の」の意味）カーネルは、プロセス管理、メモリ管理、ファイルシステム、デバイスドライバ、ネットワークなど、OS の主要な機能をすべてカーネルモードで動く 1 つのプログラムとして実装する方式です。

機能同士が普通の関数呼び出しで連携できるため、性能が高いのが利点です。一方で、カーネルが巨大になり、どこか 1 か所の不具合（例えばデバイスドライバの不具合）がカーネル全体を停止させる危険があります。

Linux や従来の UNIX はモノリシックカーネルです。ただし Linux は、デバイスドライバなどを実行中に追加、削除できるローダブルカーネルモジュールの仕組みを持ち、柔軟性を補っています。

マイクロカーネル
~~~~~~~~~~~~~~~~

マイクロカーネルは、カーネルモードで動く部分を最小限（プロセス間通信、基本的なメモリ管理、スケジューリングなど）に絞り、ファイルシステムやデバイスドライバなどは、ユーザーモードで動くサーバープロセスとして実装する方式です。アプリケーションがファイルを読むと、その依頼はマイクロカーネルのプロセス間通信を介して、ファイルシステムのサーバーに送られます。

デバイスドライバなどの不具合がカーネル全体に波及しにくく、信頼性や安全性を高めやすいのが利点です。一方、機能の間のやり取りにプロセス間通信が必要になるため、性能が低下しやすいという欠点があります。

Mach、MINIX 3、QNX、seL4 などがマイクロカーネルの例です。seL4 は、カーネルの実装が仕様どおりに動くことを数学的に証明（形式検証）したことで知られています。

ハイブリッドカーネル
~~~~~~~~~~~~~~~~~~~~

実際の OS の多くは、両者の中間的な構成をとっています。Windows NT のカーネルは、マイクロカーネルの考え方を取り入れた層構造を持ちながら、性能のために多くの機能をカーネルモードで動かしています。macOS の XNU は、Mach のマイクロカーネルと BSD のカーネルを 1 つのカーネルモードのプログラムとして組み合わせています。こうした構成はハイブリッドカーネルと呼ばれます。

.. list-table:: カーネルの構成の比較
   :header-rows: 1
   :widths: 20 30 25 25

   * - 方式
     - カーネルモードで動く範囲
     - 利点
     - 例
   * - モノリシック
     - OS の主要な機能のすべて
     - 性能が高い
     - Linux、FreeBSD
   * - マイクロ
     - 最小限の機能のみ
     - 信頼性、安全性が高い
     - MINIX 3、QNX、seL4
   * - ハイブリッド
     - 両者の中間
     - 両者の利点を狙う
     - Windows、macOS

1992 年のタネンバウムとトーバルズの論争（「:doc:`03_history`」を参照）は、まさにこの選択をめぐるものでした。タネンバウムはマイクロカーネルこそが正しい設計だと主張し、トーバルズはモノリシックカーネルの実用性を擁護しました。この論争に決着はついておらず、汎用の OS ではモノリシックやハイブリッドの構成が主流である一方、高い信頼性が求められる組込み機器などではマイクロカーネルも広く使われています。

まとめ
------

* CPU のカーネルモードとユーザーモードの区別が、カーネルと他のプログラムを守る基盤になっています。
* 割り込みと例外によって、CPU は実行中のプログラムを中断してカーネルに制御を移します。タイマー割り込みは、カーネルが定期的に制御を取り戻すために欠かせません。
* アプリケーションはシステムコールでカーネルに処理を依頼します。システムコールは関数呼び出しよりも費用が大きいため、バッファリングなどで回数を減らす工夫が重要です。
* 電源投入後、ファームウェア、ブートローダー、カーネル、最初のユーザープロセスの順に起動が進みます。
* カーネルの構成には、モノリシックカーネル、マイクロカーネル、ハイブリッドカーネルがあり、性能と信頼性のトレードオフがあります。
