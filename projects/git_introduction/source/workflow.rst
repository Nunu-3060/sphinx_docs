チーム開発のワークフロー
========================

複数人で 1 つのリポジトリを使って開発する場合は、ブランチの使い方や変更の取り込み方について、チームで共通の手順（ワークフロー）を決めておく必要があります。この章では、GitHub を使ったチーム開発で広く使われている GitHub Flow を例に説明します。

GitHub Flow
-----------

GitHub Flow は、次のような単純なルールに基づくワークフローです。

* ``main`` ブランチは、常に動作する状態に保ちます。
* 作業を始めるときは、``main`` ブランチから作業用のブランチを作成します。
* 作業用のブランチの変更は、プルリクエストでレビューを受けてから ``main`` ブランチにマージします。

作業の流れは次のとおりです。

1. ``main`` ブランチを最新の状態にします。

   .. code-block:: console

      $ git switch main
      $ git pull

2. 作業用のブランチを作成します。

   .. code-block:: console

      $ git switch -c feature/add-login

3. 変更を加え、コミットします。作業の区切りごとに、小さな単位でコミットします。

   .. code-block:: console

      $ git add .
      $ git commit -m "Add login form"

4. 作業用のブランチをリモートリポジトリにプッシュします。

   .. code-block:: console

      $ git push -u origin feature/add-login

5. GitHub でプルリクエストを作成し、レビューを依頼します。:doc:`github` で説明する GitHub CLI を使うと、``gh pr create`` でターミナルから作成することもできます。
6. レビューで指摘された点を修正し、同じブランチにコミットしてプッシュします。プルリクエストには、追加したコミットが自動的に反映されます。
7. レビューで承認されたら、GitHub の画面でプルリクエストを ``main`` ブランチにマージします。
8. マージ済みの作業用のブランチを削除し、ローカルの ``main`` ブランチを最新の状態にします。

   .. code-block:: console

      $ git switch main
      $ git pull
      $ git branch -d feature/add-login

   後で説明する「Squash and merge」または「Rebase and merge」でマージした場合、Git はローカルの作業用のブランチがマージ済みであると判断できないため、``-d`` では削除できません。この場合は、変更が ``main`` ブランチに取り込まれていることを確認したうえで ``-D`` で削除します。

プルリクエスト
--------------

プルリクエストは、「自分のブランチの変更を ``main`` ブランチに取り込んでほしい」という依頼を、GitHub 上で行う機能です。プルリクエストの画面では、変更の差分を確認したり、行ごとにコメントを付けてレビューしたりできます。GitLab では、同じ機能をマージリクエストと呼びます。

プルリクエストを作成するときは、次のことを説明に書くと、レビューする人が内容を理解しやすくなります。

* 変更の目的（なぜこの変更が必要なのか）
* 変更の概要（何を変更したのか）
* 動作の確認方法（どのように確認したのか）
* レビューで特に見てほしい点

1 つのプルリクエストに多くの変更を詰め込むと、レビューに時間がかかり、見落としも増えます。プルリクエストは、目的ごとに小さく分けて作成しましょう。

マージの方法
------------

GitHub では、プルリクエストをマージするときに、次の 3 つの方法から選べます。

.. list-table::
   :header-rows: 1
   :widths: 25 45 30

   * - 方法
     - 動作
     - 履歴の特徴
   * - Create a merge commit
     - 作業用のブランチのコミットをすべて残し、マージコミットを作成します。
     - 作業の経緯がすべて残ります。
   * - Squash and merge
     - 作業用のブランチのコミットを 1 つのコミットにまとめて取り込みます。
     - プルリクエスト 1 つにつき 1 コミットになり、履歴が簡潔になります。
   * - Rebase and merge
     - 作業用のブランチのコミットを、マージコミットを作成せずに ``main`` ブランチの後ろに付け替えます。
     - 履歴が 1 本の直線になります。

どの方法を使うかは、チームで統一しておきましょう。

強制プッシュ
------------

リベースや ``git commit --amend`` で、既にプッシュしたコミットを作り直した場合、通常の ``git push`` は拒否されます。このような場合にリモートリポジトリの履歴を上書きするのが強制プッシュです。

.. code-block:: console

   $ git push --force-with-lease

強制プッシュは他の人のコミットを消してしまう危険があるため、原則として自分だけが使っている作業用のブランチに対してだけ行います。``--force`` ではなく ``--force-with-lease`` を使うと、最後にフェッチした後に他の人がプッシュしたコミットがある場合にはプッシュが拒否されるため、他の人のコミットを誤って消してしまうことを防げます。

.. warning::

   ``main`` ブランチなど、複数人で共有しているブランチには強制プッシュしないでください。GitHub では、ブランチの保護ルールを設定して、特定のブランチへの強制プッシュを禁止できます。詳しくは :doc:`github` で説明します。
