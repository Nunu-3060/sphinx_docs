プロンプトの基本
==========================================

Claude への指示文を\ :term:`プロンプト`\ と呼びます。同じモデルでも、プロンプトの書き方によって出力の質は大きく変わります。本章では、対話でも API でも共通して使える、プロンプトの書き方の原則を説明します。

基本の考え方
------------------------------------------

Claude を「優秀だが、あなたの職場の事情をまったく知らない新しい同僚」だと考えると、良いプロンプトを書きやすくなります。新しい同僚に仕事を頼むときに伝えるべきこと、つまり目的、背景、制約、完成形のイメージは、Claude にも伝える必要があります。

書いたプロンプトを、事情を知らない同僚に見せたと想像してみてください。同僚が質問を返してきそうなら、その答えをプロンプトに書き足します。

明確かつ具体的に指示する
------------------------------------------

曖昧な指示からは、平均的で無難な出力しか得られません。何を、誰のために、どのような形で作るのかを具体的に書きます。

.. code-block:: text
   :caption: 改善前
   :linenos:

   このエラーについて説明して。

.. code-block:: text
   :caption: 改善後
   :linenos:

   Python 3.12 の Web アプリケーションで、次のエラーが発生しました。
   原因の候補を可能性の高い順に 3 つ挙げ、それぞれの確認方法と対処法を
   示してください。読み手は Python の経験が 1 年程度のエンジニアです。

   <error>
   sqlalchemy.exc.OperationalError: (psycopg2.OperationalError)
   connection to server at "db" (172.18.0.2), port 5432 failed: timeout expired
   </error>

改善後のプロンプトでは、環境、求める内容と数、順序、読み手の水準を明示しています。

理由と背景を伝える
------------------------------------------

指示には、その理由も書き添えます。理由が分かると、Claude は指示の意図をくみ取り、明示していない場面にも応用できます。

.. code-block:: text
   :caption: 理由のない指示と理由のある指示
   :linenos:

   # 理由のない指示
   箇条書きを使わないでください。

   # 理由のある指示
   この文章は音声読み上げソフトで読まれるため、箇条書きや表、記号は
   使わず、話し言葉として自然な文章で書いてください。

後者の指示を受けた Claude は、箇条書きだけでなく、読み上げに向かない括弧書きや略語も避けるようになります。

「〜しないで」より「〜して」と書く
------------------------------------------

禁止事項だけを並べるより、望ましい振る舞いを肯定形で書くほうが効果的です。「Markdown を使わないで」より「段落に分けた平文で書いて」のほうが、何をすればよいかが明確になります。

例を示す
------------------------------------------

出力の形式や文体を揃えたい場合は、具体例を示すのが最も確実です。プロンプトに入出力の例をいくつか含める手法を :term:`few-shot プロンプト`\ と呼びます。

.. code-block:: text
   :caption: 例を示すプロンプト
   :linenos:

   問い合わせ文を読み、担当部署を判定してください。

   <examples>
   <example>
   <input>請求書の宛名を変更したいです。</input>
   <output>経理部</output>
   </example>
   <example>
   <input>ログイン画面が表示されません。</input>
   <output>システム部</output>
   </example>
   </examples>

   <input>先月分の領収書を再発行してもらえますか。</input>

例は、典型的なものだけでなく、判断に迷いやすい境界的なものも含めると効果が上がります。一方で、例が少なく偏っていると、Claude が例の表面的な特徴（文の長さや言い回し）まで真似ることがあります。例は 3 〜 5 個程度を目安に、多様なものを選んでください。

XML タグで構造化する
------------------------------------------

プロンプトに指示、資料、例など性質の異なる情報が混在する場合は、XML タグで区切ります。タグの名前に決まりはなく、内容が分かる名前を付ければ十分です。

.. code-block:: text
   :caption: XML タグで構造化したプロンプト
   :linenos:

   <contract>
   （契約書の本文）
   </contract>

   <checklist>
   （社内の契約審査チェックリスト）
   </checklist>

   contract の内容を checklist の各項目に照らして審査し、問題のある項目を
   条番号とともに挙げてください。

タグで区切ると、どこまでが資料でどこからが指示かが明確になり、資料の中の文章を指示と取り違える危険も減ります。

長い資料は先頭に、質問は末尾に置く
------------------------------------------

長い文書を渡して質問する場合は、文書をプロンプトの前半に、質問や指示を末尾に置くと、応答の質が上がる傾向があります。複数の文書を渡す場合は、それぞれを ``<document>`` タグで囲み、出典や日付などの情報を添えておくと、Claude が文書を区別しやすくなります。

また、「回答の前に、質問に関係する箇所を文書から引用して」と指示すると、根拠に基づいた回答になりやすく、利用者も根拠を確認できます。

役割を与える
------------------------------------------

「あなたは経験 10 年のセキュリティエンジニアです」のように役割を与えると、その分野にふさわしい観点と語彙で応答するようになります。API では、役割の設定は\ :term:`システムプロンプト`\ に書くのが一般的です（:doc:`api_basics`\ 参照）。

ただし、役割を与えるだけでは不十分です。何を重視して判断してほしいかを、役割と合わせて具体的に書いてください。

出力の形式を指定する
------------------------------------------

出力をプログラムで処理する場合や、決まった様式で受け取りたい場合は、形式を明示します。

* 文章の場合は、見出しの構成、文字数の目安、文体（です・ます調など）を指定します
* JSON などの機械可読な形式が必要な場合は、API の構造化出力（:doc:`api_advanced`\ 参照）を使います。プロンプトで頼むだけでは、形式が崩れる可能性を排除できません

なお、以前は応答の書き出しを指定して形式を誘導する手法（プレフィル）が使われていましたが、現行のモデルでは利用できません。形式の制御には、システムプロンプトでの指示か構造化出力を使ってください。

考える余地を与える
------------------------------------------

複雑な問題では、いきなり結論を求めるより、検討の過程を経てから答えさせるほうが正確になります。Claude Haiku 4.5 を除く現行のモデルは、回答の前に自ら考える\ :term:`適応的思考`\ を備えており、問題の難しさに応じて自動的に思考します。思考の深さは API の effort パラメーターで調整できます（:doc:`api_advanced`\ 参照）。

対話で使う場合も、「結論を出す前に、考えられる選択肢とそれぞれの利点と欠点を整理して」のように、検討の手順を示すと効果があります。

作業を分割する
------------------------------------------

大きな作業は、複数の段階に分けて依頼すると品質が安定します。例えば、報告書の作成なら次のように分けます。

#. 資料から要点を抽出します
#. 抽出した要点をもとに構成案を作ります
#. 構成案に沿って本文を書きます
#. 本文を読み直し、誤りや矛盾を指摘させて修正します

各段階の出力を確認しながら進められるため、問題が起きた段階を特定しやすくなります。API では、各段階を別々の呼び出しにして、前段の出力を次段の入力に渡す構成（プロンプトの連鎖）がよく使われます。

指示を最小限から始める
------------------------------------------

現行のモデルは指示に忠実に従う傾向が強いため、古いモデル向けに書かれた過剰に細かい指示や、「必ず」「絶対に」を多用した強い指示は、かえって振る舞いを不自然にすることがあります。

プロンプトは、まず目的と必要な制約だけを書いた短いものから始め、出力を確認しながら足りない指示を足していくのが効率的です。うまくいかない例が見つかったら、その例を\ :doc:`operations`\ で説明する評価のテストケースに加えておくと、改善の効果を確かめられます。

プロンプトの改善を Claude に手伝わせる
------------------------------------------

プロンプトの改善自体を Claude に依頼するのも有効です。プロンプトと、期待どおりにならなかった出力を示し、「この出力になった原因と、プロンプトの改善案を示して」と頼むと、見落としていた曖昧さを指摘してもらえます。Claude Console には、プロンプトの生成や改善を支援する機能も用意されています。
