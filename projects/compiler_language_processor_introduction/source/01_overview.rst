################################################################
第 1 章 言語処理系の全体像
################################################################

この章では、言語処理系にどのような種類があるか、そしてソースコードがどのような段階を経て実行されるかを概観します。以降の章で作る部品が、全体のどこに位置するかをつかんでください。

言語処理系の種類
================================================================

:term:`言語処理系`\ とは、プログラミング言語で書かれたプログラムを解釈して実行したり、別の形式に変換したりするソフトウェアの総称です。代表的なものを次の表に示します。

.. list-table:: 言語処理系の種類
   :header-rows: 1
   :widths: 20 45 35

   * - 種類
     - 役割
     - 例
   * - :term:`コンパイラ`
     - ソースコードを、実行前にまとめて別の言語（多くは機械語）に変換する
     - GCC、Clang、rustc
   * - :term:`インタプリタ`
     - ソースコード（またはそれを変換したもの）を読みながら、その場で実行する
     - CPython、Ruby（CRuby）
   * - トランスパイラ
     - ソースコードを、同じくらいの抽象度の別の高水準言語に変換する
     - TypeScript コンパイラ（tsc）、Babel
   * - アセンブラ
     - アセンブリ言語を機械語に変換する
     - GNU as、NASM
   * - リンカ
     - 別々にコンパイルされたオブジェクトファイルを結合して実行ファイルを作る
     - GNU ld、lld

コンパイラとインタプリタは対立する概念のように説明されることがありますが、実際の処理系の多くは両者を組み合わせています。たとえば CPython は、ソースコードをまず\ :term:`バイトコード`\ と呼ばれる仮想的な機械語にコンパイルし、それを\ :term:`仮想マシン`\ で解釈実行します。Java の処理系は、バイトコードを解釈実行しながら、頻繁に実行される部分を実行時に機械語へコンパイルします。このように実行時にコンパイルする方式を :term:`JIT コンパイル`\ と呼びます。

.. list-table:: 実行方式の比較
   :header-rows: 1
   :widths: 25 25 25 25

   * - 方式
     - 起動の速さ
     - 実行の速さ
     - 本書での扱い
   * - 構文木を直接解釈する
     - 速い
     - 遅い
     - 第 7 章
   * - バイトコードを解釈する
     - 速い
     - 中程度
     - 第 10 章
   * - 事前に機械語へコンパイルする
     - コンパイルの時間が必要
     - 速い
     - 第 11 章（考え方のみ）
   * - JIT コンパイル
     - 中程度
     - 速い
     - 第 12 章（概要のみ）

処理の流れ
================================================================

コンパイラの処理は、いくつかの段階（:term:`フェーズ`）に分かれています。各フェーズは前のフェーズの出力を受け取り、より扱いやすい形に変換して次のフェーズに渡します。

.. graphviz::
   :caption: コンパイラの処理の流れ（括弧内は本書で扱う章）

   digraph phases {
     rankdir=TB;
     node [shape=box, style=rounded];
     src [label="ソースコード（文字の列）", shape=plaintext];
     lex [label="字句解析（第 3 章）"];
     parse [label="構文解析（第 4・5 章）"];
     sema [label="意味解析（第 6 章）"];
     irgen [label="中間表現の生成（第 8 章）"];
     opt [label="最適化（第 9 章）"];
     cg [label="コード生成（第 10・11 章）"];
     out [label="目的コード", shape=plaintext];
     interp [label="インタプリタ（第 7 章）"];
     src -> lex [label=" 文字の列"];
     lex -> parse [label=" トークンの列"];
     parse -> sema [label=" 抽象構文木"];
     sema -> irgen [label=" 型付きの抽象構文木"];
     irgen -> opt [label=" 中間表現"];
     opt -> cg [label=" 中間表現"];
     cg -> out;
     sema -> interp [style=dashed];
   }

各フェーズの入力と出力をまとめると次のようになります。

.. list-table:: 各フェーズの入力と出力
   :header-rows: 1
   :widths: 20 25 25 30

   * - フェーズ
     - 入力
     - 出力
     - 主な仕事
   * - :term:`字句解析`
     - 文字の列
     - :term:`トークン`\ の列
     - 空白やコメントを読み飛ばし、識別子・数値・記号などの単位に切り分ける
   * - :term:`構文解析`
     - トークンの列
     - :term:`抽象構文木`
     - 文法に従ってプログラムの構造を明らかにする
   * - :term:`意味解析`
     - 抽象構文木
     - 型情報付きの抽象構文木
     - 変数が宣言されているか、型が正しいかを検査する
   * - 中間表現の生成
     - 抽象構文木
     - :term:`中間表現`
     - 機械に近い単純な命令の列に変換する
   * - :term:`最適化`
     - 中間表現
     - 中間表現
     - 意味を変えずに、より速く小さいプログラムに書き換える
   * - :term:`コード生成`
     - 中間表現
     - 目的コード
     - 機械語やバイトコードを生成し、レジスタを割り当てる

たとえば ``let x = 10 * (y + 2);`` という文は、字句解析で ``let``、``x``、``=``、``10``、``*``、``(`` … というトークンの列になり、構文解析で「``x`` を宣言し、``10`` と ``y + 2`` の積で初期化する」という木構造になります。意味解析では ``y`` が宣言済みの整数型の変数であることを確かめ、中間表現の生成では「``y + 2`` を計算して一時変数に入れ、それと ``10`` の積を ``x`` に入れる」という命令の列に変換します。

フロントエンド・ミドルエンド・バックエンド
================================================================

コンパイラのフェーズは、大きく 3 つに分けて呼ばれることがあります。

.. list-table::
   :header-rows: 1
   :widths: 20 40 40

   * - 部分
     - 含まれるフェーズ
     - 依存するもの
   * - フロントエンド
     - 字句解析、構文解析、意味解析、中間表現の生成
     - ソース言語
   * - ミドルエンド
     - 中間表現に対する最適化
     - どちらにも依存しない
   * - バックエンド
     - 命令選択、レジスタ割り当て、コード生成
     - ターゲット（CPU や仮想マシン）

この分割の利点は、共通の中間表現を介することで部品を再利用できる点です。:math:`M` 個の言語と :math:`N` 種類の CPU に対応するコンパイラを個別に作ると :math:`M \times N` 個のコンパイラが必要ですが、共通の中間表現を使えば :math:`M` 個のフロントエンドと :math:`N` 個のバックエンド、つまり :math:`M + N` 個の部品で済みます。LLVM はこの考え方を実現した代表例で、C/C++（Clang）、Rust、Swift などのフロントエンドが LLVM IR という共通の中間表現を出力し、それを LLVM のミドルエンドとバックエンドが最適化して各種 CPU 向けの機械語にします。

CPython の場合
================================================================

身近な例として、CPython がソースコードを実行するまでの流れを見てみましょう。

#. トークナイザがソースコードをトークンの列に変換します（:doc:`第 3 章 <03_lexer>`\ で ``tokenize`` モジュールを紹介します）。
#. PEG 構文解析器がトークンの列から抽象構文木を作ります（:doc:`第 5 章 <05_ast>`\ で ``ast`` モジュールを紹介します）。
#. 記号表を作り、各変数が局所変数か大域変数かなどを決めます（:doc:`第 6 章 <06_semantic>`\ で ``symtable`` モジュールを紹介します）。
#. 抽象構文木を制御フローグラフに変換して簡単な最適化を行い、バイトコードを生成します（:doc:`第 10 章 <10_vm>`\ で ``dis`` モジュールを紹介します）。
#. 仮想マシン（評価ループ）がバイトコードを 1 命令ずつ実行します。

``ast`` モジュールを使うと、構文解析の結果を Python から確認できます。

.. code-block:: pycon
   :linenos:

   >>> import ast
   >>> print(ast.dump(ast.parse("x = 1 + 2 * y"), indent=2))
   Module(
     body=[
       Assign(
         targets=[
           Name(id='x', ctx=Store())],
         value=BinOp(
           left=Constant(value=1),
           op=Add(),
           right=BinOp(
             left=Constant(value=2),
             op=Mult(),
             right=Name(id='y', ctx=Load()))))])

``1 + 2 * y`` が「``1`` と ``2 * y`` の和」という木構造になっており、掛け算が足し算より先に計算されることが構文解析の段階で決まっていることが分かります。本書では、これと同じことを Tiny に対して一から実装していきます。

まとめ
================================================================

* 言語処理系には、コンパイラ、インタプリタ、トランスパイラなどがあり、実際の処理系の多くはそれらを組み合わせています。
* コンパイラの処理は、字句解析、構文解析、意味解析、中間表現の生成、最適化、コード生成というフェーズに分かれます。
* 共通の中間表現を使うと、フロントエンドとバックエンドを独立に作って組み合わせられます。
