ドメインのモデリング
====================

ソフトウェアが扱う業務の領域（注文、在庫、会計など）を :term:`ドメイン` と呼びます。業務の規則が複雑なシステムでは、その規則をコードでどう表すかが、変更のしやすさを大きく左右します。この章では、:term:`ドメイン駆動設計`\ （Domain-Driven Design、DDD）の考え方のうち、コードの設計に直接役立つ部分を紹介します。

ドメイン駆動設計とは
--------------------

ドメイン駆動設計は、E. Evans が 2003 年の書籍で提唱した、ソフトウェアの設計の手法です。その中心にある考え方は、次の 2 つです。

* 業務の専門家と開発者が協力して、業務の知識を **モデル** として整理します。
* そのモデルを、コードにできるだけそのまま表します。

ドメイン駆動設計は、組織やチームの分け方まで含む広い手法です。この章では、そのうち「モデルをコードで表すための部品」（エンティティ、値オブジェクト、集約、リポジトリ、サービス）を中心に説明します。例として、注文を受け付けるシステムのドメインを実装します。

ユビキタス言語
--------------

業務の専門家と開発者が、同じ概念を別の言葉で呼んでいると、誤解が生まれます。たとえば、営業の担当者が「受注」と呼んでいるものを、開発者がコードで ``Request`` と名付けていると、会話とコードの対応を取るたびに翻訳が必要になります。

ドメイン駆動設計では、チームの全員が使う共通の言葉を決め、会話にも、ドキュメントにも、コードのクラス名やメソッド名にも、その言葉を使います。この共通の言葉を :term:`ユビキタス言語` と呼びます。業務の言葉がそのままコードに現れていれば、業務の規則が変わったときに、どこを直せばよいのかがすぐに分かります。

エンティティと値オブジェクト
----------------------------

ドメインの概念を表すオブジェクトは、大きく 2 種類に分けられます。

.. list-table::
   :header-rows: 1
   :widths: 20 40 40

   * -
     - :term:`エンティティ`
     - :term:`値オブジェクト`
   * - 同一性
     - ID で区別します。属性の値が変わっても、同じ ID なら同じものです。
     - 属性の値で区別します。値が同じなら、同じものとみなします。
   * - 変更
     - 状態が変わることがあります（注文の状態が「下書き」から「確定」に変わるなど）。
     - 不変にします。値を変えたいときは、新しいオブジェクトを作ります。
   * - 例
     - 注文、顧客、口座
     - 金額、注文の明細、住所、期間

たとえば、同姓同名の 2 人の顧客は、名前という値が同じでも別の人なので、顧客はエンティティです。一方、「1,000 円」という金額は、どの 1,000 円も区別する必要がないので、値オブジェクトです。

値オブジェクトの考え方と実装の方法は、:doc:`data` で説明しました。注文のドメインでも、金額 ``Money`` と注文の明細 ``OrderLine`` を値オブジェクトとして定義します（この例の ``Money`` は、簡単にするため円だけを扱います）。

集約
----

注文と注文の明細のように、密接に関係し、常に一緒に変更されるオブジェクトのまとまりを :term:`集約` と呼びます。集約には、外部からの窓口となるオブジェクトが 1 つあり、これを :term:`集約ルート` と呼びます。

集約には、次の規則があります。

* 集約の外から、集約の内部のオブジェクト（明細など）を直接変更してはいけません。変更は必ず集約ルートのメソッドを通して行います。
* 集約ルートは、集約の全体が常に業務の規則（:term:`不変条件`）を満たしていることを保証します。
* 集約は、まるごと保存し、まるごと読み込みます。

注文の集約では、``Order`` が集約ルートです。明細の追加や状態の変更は ``Order`` のメソッドを通して行い、``Order`` が次の不変条件を守ります。

* 明細を変更できるのは、下書きの状態のときだけです。
* 明細は最大 10 行です（同じ商品は 1 行にまとめます）。
* 明細のない注文は確定できません。

集約の大きさ
~~~~~~~~~~~~

集約は、できるだけ小さくします。たとえば、注文の集約に顧客の情報まで含めると、顧客の住所を変更するたびに、その顧客のすべての注文を読み込むことになります。別の集約を参照するときは、オブジェクトそのものではなく、ID で参照します。``Order`` が顧客を ``Customer`` のオブジェクトではなく、``customer_id`` という ID で持っているのはこのためです。

リポジトリ
----------

:term:`リポジトリ` は、集約を保存したり、取り出したりするための部品です。アプリケーションの側から見ると、リポジトリは「集約を入れておく箱」のように振る舞い、その裏でデータベースやファイルがどう使われているかは隠されています。

リポジトリのインターフェースは、ドメインの側（またはアプリケーションの側）に ``Protocol`` として定義し、実装とは別のモジュールに置きます。これは、:doc:`architecture` のヘキサゴナルアーキテクチャにおけるポートに当たります。この例では、インターフェースをドメインのモジュール ``model.py`` に、実装を ``repository.py`` に置いています。アプリケーションサービスは ``model.py`` だけを import し、``repository.py`` を知りません。

メモリ版の ``save`` と ``get`` は、``copy.deepcopy`` でオブジェクトの複製を保存し、複製を返します。複製しないと、保存したあとに呼び出し側がオブジェクトを変更したとき、リポジトリの中身まで変わってしまい、データベースに保存した場合と振る舞いが異なってしまうからです。

ドメインサービスとアプリケーションサービス
------------------------------------------

ドメインの処理の中には、特定のエンティティや値オブジェクトのメソッドにするのが不自然なものがあります。たとえば、送料の計算は、注文の合計金額と配送先の地域によって決まりますが、送料の規則は注文そのものの性質ではなく、配送の方針です。このような処理は、独立した関数やクラスにします。これを :term:`ドメインサービス` と呼びます。

   :language: python
   :caption: ch12_domain_model/model.py（ドメインサービス）

一方、ユースケースの手順（リポジトリから集約を取り出し、集約のメソッドを呼び、保存する）を実装するのが :term:`アプリケーションサービス` です。アプリケーションサービスは手順を調整するだけで、業務の規則そのものは持ちません。規則は、エンティティ、値オブジェクト、ドメインサービスに書きます。

``place_order`` では、注文を確定する前に送料を計算しています。配送先の地域を、集約の状態を変更する前に検証し、配送できない地域が指定された場合には、集約の状態が変わらないようにするためです。

``ch12_domain_model`` のすべてのファイルは :doc:`samples/ch12` で閲覧できます。``examples`` フォルダーで ``python -m ch12_domain_model.main`` と実行すると、同じユースケースを、メモリ版と SQLite 版のリポジトリで実行し、確定した注文の変更が拒否されることを確認できます。

境界づけられたコンテキスト
--------------------------

大きなシステムでは、同じ言葉が、部門によって異なる意味を持つことがあります。たとえば「商品」は、販売の部門にとっては価格や説明文を持つものですが、配送の部門にとっては重さや大きさを持つものです。この 2 つを 1 つの ``Product`` クラスで表そうとすると、クラスはどの部門にとっても不要な属性を抱えた、大きなものになります。

ドメイン駆動設計では、モデルが一貫した意味を持つ範囲を :term:`境界づけられたコンテキスト` と呼び、範囲ごとに別のモデルを作ります。販売のコンテキストと配送のコンテキストは、それぞれ独自の ``Product`` を持ち、両者は ID などを使って連携します。

境界づけられたコンテキストは、モジュールやパッケージを分ける単位として、また :doc:`architecture` で説明したマイクロサービスの境界を考える手がかりとしても使えます。

まとめ
------

* 業務の専門家と開発者は、共通の言葉（ユビキタス言語）を使い、コードにもその言葉を使います。
* ID で区別するものはエンティティ、値で区別するものは値オブジェクトとして表します。
* 一緒に変更されるオブジェクトは集約にまとめ、集約ルートを通して変更し、不変条件を守ります。
* 集約の保存と取得はリポジトリに任せ、リポジトリのインターフェースはドメインの側に置きます。
* ユースケースの手順はアプリケーションサービスに、特定のオブジェクトに属さない規則はドメインサービスに書きます。
