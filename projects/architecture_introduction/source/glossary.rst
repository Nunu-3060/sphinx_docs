用語集
======

本資料で使う主な用語をまとめます。英字で始まる用語をアルファベット順に、それ以外の用語を五十音順に並べています。各用語の詳しい説明は、末尾に示した章を参照してください。

英字
----

.. glossary::

   ADR
      :term:`アーキテクチャ決定記録` の略です。

   C4 モデル
      ソフトウェアのアーキテクチャを、コンテキスト、コンテナー、コンポーネント、コードの 4 つの段階の詳細さで描き分ける図の描き方です。（:doc:`documentation`）

   DDD
      :term:`ドメイン駆動設計` の略です。

   DI
      :term:`依存性注入` の略です。

   DRY
      Don't Repeat Yourself の略です。同じ知識を、システムの中の複数の場所に書かないという原則です。（:doc:`metrics`）

   KISS
      Keep It Simple, Stupid の略です。設計は単純に保つべきだという原則です。（:doc:`metrics`）

   MVC
      アプリケーションを、Model（データと業務の規則）、View（表示）、Controller（入力の処理）の 3 つの役割に分ける構成です。（:doc:`architecture`）

   SOLID 原則
      単一責任、開放閉鎖、リスコフの置換、インターフェース分離、依存性逆転の 5 つの、オブジェクト指向設計の原則の総称です。（:doc:`solid`）

   TDD
      :term:`テスト駆動開発` の略です。

   YAGNI
      You Aren't Gonna Need It の略です。今必要でない機能は作らないという原則です。（:doc:`metrics`）

あ行
----

.. glossary::

   アーキテクチャ
      システムの全体の構造と、その構造を決めた重要な判断のことです。（:doc:`architecture`）

   アーキテクチャ決定記録
      アーキテクチャに関わる重要な判断を、背景、選択肢、決定、結果とともに 1 つずつ記録する短い文書です。ADR とも呼びます。（:doc:`documentation`）

   値オブジェクト
      金額や住所のように、値そのものが意味を持ち、値が同じなら同じものとみなせるオブジェクトです。不変にします。（:doc:`data`、:doc:`domain`）

   アダプター
      ヘキサゴナルアーキテクチャで、ポートと具体的な技術（データベース、画面など）をつなぐ部品です。また、Adapter パターンでは、インターフェースを変換する部品を指します。（:doc:`architecture`、:doc:`patterns`）

   アプリケーションサービス
      ユースケースの手順（集約の取り出し、メソッドの呼び出し、保存）を調整する部品です。業務の規則そのものは持ちません。（:doc:`domain`）

   依存オブジェクト
      あるオブジェクトが仕事をするために必要とする、別のオブジェクトです。（:doc:`dependency`）

   依存性注入
      オブジェクトが依存するものを、そのオブジェクトの内部で作るのではなく、コンストラクターや引数で外から渡すことです。（:doc:`dependency`）

   イベント駆動アーキテクチャ
      出来事（イベント）を発行し、そのイベントに関心のある部品が反応して処理を行う構成です。（:doc:`architecture`）

   エンティティ
      ID で区別され、状態が変わっても同じものとみなされるオブジェクトです。（:doc:`domain`）

か行
----

.. glossary::

   過剰設計
      将来必要になるかもしれないという理由で、使われない仕組みや不要な抽象化を作り込んだ設計です。（:doc:`what_is_design`）

   カプセル化
      データと、そのデータを扱う処理を 1 つのクラスにまとめ、外からはメソッドを通してだけ操作できるようにすることです。（:doc:`oop`）

   関心の分離
      プログラムを、それぞれ異なる関心事（業務の規則、保存、表示など）を扱う部分に分けるという原則です。（:doc:`metrics`）

   技術的負債
      設計を犠牲にした実装が、あとの変更のたびに生む余分な手間を、借金の利息になぞらえた言葉です。（:doc:`what_is_design`）

   基本データ型への執着
      金額や住所などの業務上の概念を、``int``、``str``、``dict`` などの基本的な型のまま扱い続けることです。（:doc:`data`）

   境界づけられたコンテキスト
      ドメイン駆動設計で、1 つのモデルが一貫した意味を持つ範囲のことです。（:doc:`domain`）

   凝集度
      1 つの部品の中の要素が、どれだけ強く関連しているかを表す指標です。高いほど良いとされます。（:doc:`metrics`）

   偶有的な複雑さ
      問題の解き方（実装の仕方）によって生じる複雑さです。設計によって減らせます。（:doc:`what_is_design`）

   クリーンアーキテクチャ
      システムを同心円状の層で表し、依存は必ず外側から内側へ向かうという規則を定めた構成です。（:doc:`architecture`）

   クロージャー
      外側の関数の変数を覚えている関数です。（:doc:`patterns`）

   継承
      既存のクラスをもとに、その機能を引き継いだ新しいクラス（サブクラス）を定義することです。「一種である」関係を表します。（:doc:`oop`）

   結合度
      部品と部品が、どれだけ強く依存し合っているかを表す指標です。低いほど良いとされます。（:doc:`metrics`）

   コードの臭い
      長い関数、重複したコードなど、リファクタリングが必要な可能性を示す兆候です。（:doc:`refactoring`）

   コマンドとクエリの分離
      メソッドを、状態を変更するコマンドと、値を返すクエリに分け、両方を兼ねないようにするという原則です。（:doc:`functions`）

   コンポジション
      あるクラスが、別のクラスのオブジェクトを属性として持ち、処理の一部をそれに任せることです。「持つ」関係を表します。（:doc:`oop`）

   コンポジションルート
      オブジェクトの組み立て（どのオブジェクトにどの依存オブジェクトを渡すか）をまとめた、プログラムの入口の付近の 1 か所です。（:doc:`dependency`）

さ行
----

.. glossary::

   集約
      密接に関係し、常に一緒に変更されるオブジェクトのまとまりです。まるごと保存し、まるごと読み込みます。（:doc:`domain`）

   集約ルート
      集約の外部からの窓口となるオブジェクトです。集約の不変条件を守ります。（:doc:`domain`）

   循環 import
      モジュールどうしが、互いを直接または間接に import している状態です。（:doc:`modules`）

   循環的複雑度
      関数の処理の流れの複雑さを表す指標です。1 つの関数では「分岐の数 + 1」に等しくなります。（:doc:`metrics`）

   純粋関数
      同じ引数に対して常に同じ戻り値を返し、副作用を持たない関数です。（:doc:`functions`）

   仕様化テスト
      既存のコードの現在の振る舞いを、そのまま記録するテストです。リファクタリングの前に用意します。（:doc:`refactoring`）

   情報隠蔽
      変更される可能性の高い設計上の決定を、モジュールの内部に隠すという考え方です。（:doc:`metrics`）

   早期リターン
      前提条件を満たさない場合を先に処理して関数を抜け、入れ子を浅くする書き方です。（:doc:`functions`）

た行
----

.. glossary::

   尋ねるな、命じよ
      オブジェクトからデータを取り出して呼び出し側で判断するのではなく、オブジェクトに処理を命じ、判断を任せるという指針です。（:doc:`oop`）

   ダックタイピング
      オブジェクトの型ではなく、必要なメソッドを持っているかどうかで、そのオブジェクトを使えるかが決まるという考え方です。（:doc:`oop`）

   デザインパターン
      ソフトウェアの設計でよく現れる問題と、その解決策に名前を付けてまとめたものです。（:doc:`patterns`）

   テスト駆動開発
      テストを先に書き、テストを成功させるコードを書き、設計を整える、という周期を繰り返す開発の手法です。TDD とも呼びます。（:doc:`testing`）

   テストダブル
      テストのときに、本物の依存オブジェクトの代わりに使うオブジェクトの総称です。ダミー、スタブ、スパイ、モック、フェイクがあります。（:doc:`testing`）

   テストピラミッド
      速い単体テストを数多く、遅い E2E テストを少なく用意するという、テストの割合の考え方です。（:doc:`testing`）

   デメテルの法則
      オブジェクトは、直接の知り合い（自分自身、引数、自分が作ったもの、自分の属性）のメソッドだけを呼ぶべきだという原則です。（:doc:`metrics`）

   ドメイン
      ソフトウェアが扱う業務の領域です。（:doc:`domain`）

   ドメイン駆動設計
      業務の知識をモデルとして整理し、そのモデルをコードにそのまま表すという設計の手法です。DDD とも呼びます。（:doc:`domain`）

   ドメインサービス
      特定のエンティティや値オブジェクトに属さない、ドメインの処理を表す関数やクラスです。（:doc:`domain`）

は行
----

.. glossary::

   パイプとフィルター
      データを処理する部品（フィルター）を、データの流れ（パイプ）でつなぐ構成です。（:doc:`architecture`）

   副作用
      関数が戻り値を返す以外に、外の状態（引数のオブジェクト、グローバル変数、ファイル、画面など）を変えることです。（:doc:`functions`）

   不変オブジェクト
      作ったあとに値を変更できないオブジェクトです。（:doc:`data`）

   不変条件
      オブジェクトや集約が、常に満たしていなければならない条件です。（:doc:`domain`）

   フラグ引数
      関数の動作を切り替えるための、真偽値の引数です。（:doc:`functions`）

   ヘキサゴナルアーキテクチャ
      アプリケーションの中心を外部の技術から切り離し、外部とのやり取りをポートとアダプターを通して行う構成です。ポートとアダプターとも呼びます。（:doc:`architecture`）

   ポート
      ヘキサゴナルアーキテクチャで、アプリケーションの中心が外部とやり取りするために定めたインターフェースです。（:doc:`architecture`）

   ポリモーフィズム
      同じ呼び出し方で、オブジェクトの種類に応じた異なる処理が実行される性質です。多態性とも呼びます。（:doc:`oop`）

   本質的な複雑さ
      解決したい問題そのものが持つ複雑さです。設計によって取り除くことはできません。（:doc:`what_is_design`）

ま行
----

.. glossary::

   マイクロサービス
      システムを、独立して配置できる小さなサービスに分け、ネットワークを通して連携させる構成です。（:doc:`architecture`）

   マジックナンバー
      コードの中に直接書かれた、意味の説明のない数値です。（:doc:`refactoring`）

   モノリス
      システム全体を 1 つのアプリケーションとして作り、1 つの単位で配置する構成です。（:doc:`architecture`）

や行
----

.. glossary::

   ユビキタス言語
      業務の専門家と開発者が共通して使い、コードにも使う言葉です。（:doc:`domain`）

ら行
----

.. glossary::

   リファクタリング
      外部から見た振る舞いを保ったまま、ソフトウェアの内部の構造を改善することです。（:doc:`refactoring`）

   リポジトリ
      集約を保存したり、取り出したりするための部品です。保存の方法を隠します。（:doc:`domain`）

   レイヤードアーキテクチャ
      システムを役割ごとの層に分け、上の層が下の層だけを使うようにする構成です。（:doc:`architecture`）

   列挙型
      取り得る値が決まっているデータを表す型です。Python では ``enum.Enum`` を使います。（:doc:`data`）
