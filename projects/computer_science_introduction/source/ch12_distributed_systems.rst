分散システム
============

Web サービスの裏側では、何台、何百台ものサーバがネットワークでつながり、1 つのシステムとして動いている。データベースは複製されて別のデータセンタにも置かれ、注文の処理は決済、在庫、配送の別々のサービスが分担する。こうしたシステムでは、1 台のコンピュータの上では起こらなかった問題が次々に現れる。メッセージは失われ、時計は合わず、一部のサーバだけが止まる。この章では、まず分散システムに特有の故障の性質を確認し、時刻と順序、レプリケーション、分割（シャーディング）、CAP 定理、合意の順に基本的な考え方を学ぶ。最後に、再試行と冪等性を中心に、障害に強いプログラムを書くための実践的な設計を扱う。ネットワークの仕組みは「:doc:`ch10_networks`」、トランザクションは「:doc:`ch11_databases`」の知識を前提にする。全体の参考書としては [DDIA]_ を挙げておく。

分散システムとは
----------------

なぜ分散させるのか
^^^^^^^^^^^^^^^^^^

ネットワークでつながった複数のコンピュータが、メッセージをやり取りしながら協調して 1 つの仕事をするシステムを\ :term:`分散システム`\ と呼ぶ。1 台で済むなら 1 台の方がはるかに単純だが、次のような理由で複数のコンピュータが必要になる。

* **規模**: データ量やリクエスト数が 1 台の性能や記憶容量を超える。高性能な 1 台に買い替える（スケールアップ）には限界があり、台数を増やす（スケールアウト）方が安く済むことが多い。
* **可用性**: 1 台が故障しても、別のコンピュータが仕事を引き継いでサービスを続けられる。ハードウェアの故障だけでなく、OS の更新のための再起動のような計画的な停止にも対応できる。
* **地理的分散**: 利用者の近くにサーバを置けば遅延を減らせる。東京と米国の間の RTT が 100 ミリ秒程度あることは「:doc:`ch10_networks`」で見た。また、1 つのデータセンタが災害で止まっても、別の地域でサービスを続けられる。

部分故障
^^^^^^^^

1 台のコンピュータでは、ハードウェアに問題があればたいていシステム全体が止まる。動いているか止まっているかのどちらかであり、中間の状態は珍しい。分散システムでは、システムの一部だけが故障し、残りは動き続けるということが日常的に起こる。これを\ :term:`部分故障`\ と呼ぶ。

部分故障が難しいのは、故障を確実に検知できないからである。サーバ A がサーバ B に要求を送り、応答が返ってこないとき、A には次のどれが起きたのか区別できない。

#. 要求がネットワークの途中で失われた。
#. B が停止している、または過負荷で処理が遅れている。
#. B は処理を終えたが、応答がネットワークの途中で失われた、または遅れている。

1 と 3 では B の状態がまったく異なる。3 の場合、B はすでに処理を行っているので、A が要求を送り直すと処理が 2 回行われるおそれがある。A にできるのは、一定時間待って応答が無ければ失敗とみなす\ **タイムアウト**\ だけであり、タイムアウトしても「相手が処理したかどうかは分からない」という事実は変わらない。この問題には「:ref:`ch12-fault-tolerance`」の節で再び取り組む。

分散コンピューティングの落とし穴
^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^

分散システムを初めて作る人が無意識に置きがちな誤った仮定は、「分散コンピューティングの落とし穴」（fallacies of distributed computing）として 8 項目にまとめられている。次の表に、それぞれの仮定と現実を示す。

.. list-table:: 分散コンピューティングの落とし穴
   :header-rows: 1
   :widths: 30 70

   * - 誤った仮定
     - 現実
   * - ネットワークは信頼できる
     - パケットは失われ、接続は途中で切れる。一部のサーバの間だけ通信できなくなることもある。
   * - 遅延はゼロである
     - 大陸間の往復には 100 ミリ秒以上かかり、混雑や再送でときどき桁違いに遅くなる。
   * - 帯域幅は無限である
     - 大量のデータを転送すると回線が飽和し、他の通信も遅くなる。
   * - ネットワークは安全である
     - 経路上で盗聴や改ざんが起こりうる（「:doc:`ch13_security`」を参照）。
   * - ネットワーク構成は変わらない
     - サーバは追加・削除・移動され、IP アドレスも変わる。
   * - 管理者は 1 人である
     - 部署、クラウド事業者、外部サービスなど、管理者が異なる部分が混在する。
   * - 転送コストはゼロである
     - シリアライズには CPU 時間がかかり、クラウドでは転送量に料金がかかる。
   * - ネットワークは均質である
     - 機器、OS、プロトコルのバージョン、回線の品質はまちまちである。

ネットワーク越しの呼び出しは、失敗しうるし、遅くなりうるし、成否が分からないまま終わりうる、という前提で設計する必要がある。

障害の種類
^^^^^^^^^^

分散システムの理論では、どのような故障を想定するかを\ **障害モデル**\ として明示する。代表的なものを次に示す。

* **停止故障**\ （crash failure）: ノード（システムを構成する個々のコンピュータやプロセス）が停止し、以後何もしなくなる。再起動して復帰する場合を含めて考えることも多い。
* :term:`ネットワーク分断`\ : ノード自体は動いているが、ネットワークの故障により、ノードの集まりが互いに通信できない 2 つ以上のグループに分かれる。各グループの中では通信できるので、それぞれが「相手側が停止した」と判断して独自に動き出す危険がある。
* **ビザンチン故障**\ （Byzantine failure）: ノードがバグや悪意によって、嘘の情報を送るなど任意の誤った振る舞いをする。1 つの組織が運用するシステムでは通常想定しない。

この章で扱う手法の多くは、停止故障とネットワーク分断に加え、メッセージの喪失、遅延、順序の入れ替わりを想定している。

時刻と順序
----------

コンピュータの時刻
^^^^^^^^^^^^^^^^^^

多くのシステムは時刻を **Unix 時間**\ で表す。Unix 時間は、1970 年 1 月 1 日 0 時 0 分 0 秒（UTC）からの経過秒数である。32 ビットの符号付き整数で格納すると 2038 年にオーバーフローすることは「:doc:`ch01_data_representation`」で見た。UTC（協定世界時）は世界共通の基準となる時刻で、日本標準時（JST）は UTC より 9 時間進んでいる。システムの内部やデータベースでは UTC（または Unix 時間）で記録し、利用者に見せるときにその地域のタイムゾーンの時刻に変換するのが定石である。地域の時刻のまま記録すると、夏時間の切り替えで同じ時刻が 2 回現れることがある。

地球の自転は一定ではないため、UTC は\ **うるう秒**\ を挿入して天文学的な時刻との差を調整してきた。うるう秒が入る日は 86,401 秒になるが、Unix 時間は 1 日を常に 86,400 秒として数えるので、うるう秒をそのまま表せない。同じ Unix 時間を 2 回繰り返すか、前後の時間で少しずつ時計をずらして吸収する（leap smear）かはシステムによって異なり、うるう秒をきっかけにした障害も起きてきた。なお、2035 年までにうるう秒の挿入をやめる方針が 2022 年に決まっている。

時計のずれと NTP
^^^^^^^^^^^^^^^^

コンピュータの時計は、水晶振動子の振動を数えて時間を測る。振動数は個体差や温度によってわずかに異なるので、時計は少しずつ進んだり遅れたりする。この進み方の誤差を\ **ドリフト**\ と呼び、通常のサーバでは数十 ppm（100 万分の数十）程度である。20 ppm でも 1 日に :math:`86400 \times 20 \times 10^{-6} \approx 1.7` 秒ずれる。

時計を合わせるために広く使われているのが :term:`NTP`\ （Network Time Protocol）である [RFC5905]_。NTP は UDP の 123 番ポートを使い、原子時計や GPS に直結した上位のサーバから階層的に時刻を配る。クライアントは、要求を送った時刻 :math:`t_1`、サーバが要求を受け取った時刻 :math:`t_2`、サーバが応答を送った時刻 :math:`t_3`、応答を受け取った時刻 :math:`t_4` の 4 つから、自分の時計のサーバとのずれ :math:`\theta` と往復の遅延 :math:`\delta` を次のように推定する。:math:`t_1` と :math:`t_4` はクライアントの時計、:math:`t_2` と :math:`t_3` はサーバの時計で測った値である。

.. math::

   \theta = \frac{(t_2 - t_1) + (t_3 - t_4)}{2}, \qquad
   \delta = (t_4 - t_1) - (t_3 - t_2)

この式は、行きと帰りの遅延が等しいと仮定している。経路が混雑して片方向だけ遅れると、その差の半分がそのまま推定の誤差になる。そのため、NTP で合わせた時計でも、同じデータセンタ内で 1 ミリ秒未満、インターネット越しでは数十ミリ秒程度の誤差が残りうる。また、NTP はずれが小さければ時計の進み方を少しずつ調整する（slew）が、ずれが大きいと時刻を一気に書き換える（step）ことがあり、このとき時計は飛んだり\ **逆戻り**\ したりする。

壁時計とモノトニッククロック
^^^^^^^^^^^^^^^^^^^^^^^^^^^^

OS は性質の異なる 2 種類の時計を提供している。\ **壁時計**\ （wall clock）は「今が何年何月何日何時何分か」を表す時計で、NTP による補正や管理者の設定変更で飛んだり戻ったりする。一方、\ :term:`モノトニッククロック`\ は、ある基準点からの経過時間を表し、決して逆戻りしない時計である。基準点（例えば OS の起動時刻）に意味は無く、値の差だけが意味を持つ。別のコンピュータの値とは比べられない。

Python では、``time.time()`` が壁時計の Unix 時間を、``time.monotonic()`` がモノトニッククロックの値を秒単位の浮動小数点数で返す。処理時間の測定やタイムアウトの判定には、必ずモノトニッククロックを使う。

.. code-block:: python
   :linenos:

   import time

   start = time.monotonic()
   do_something()
   elapsed = time.monotonic() - start  # 経過時間は monotonic で測る

   created_at = time.time()  # 記録用の時刻は壁時計（UTC の Unix 時間）

``time.time()`` の差で経過時間を測ると、測定中に NTP が時計を戻した場合に経過時間が負になったり、タイムアウトが永遠に来なかったりする。

時刻で順序を決める危険
^^^^^^^^^^^^^^^^^^^^^^

複数のノードで起きた出来事の前後関係を、各ノードの壁時計の時刻で決めるのは危険である。例えば、2 台のサーバに同じキーへの書き込みが届き、タイムスタンプの新しい方を残す「最後の書き込みが勝つ」（LWW: Last Write Wins）方式で衝突を解決するとする。サーバ X の時計が 50 ミリ秒進んでいれば、Y の書き込みより 10 ミリ秒前に X で行われた書き込みの方が「新しい」とみなされ、後の書き込みが黙って捨てられる。エラーは何も出ない。時計のずれが数ミリ秒でも、その間隔より短い時間に起きた出来事の順序は時刻からは決められない。

論理時計
^^^^^^^^

順序を知りたいのは多くの場合、「ある出来事が別の出来事の原因になりえたか」である。L. Lamport は、物理的な時刻を使わずにこの関係を扱う方法を示した [Lamport1978]_。

出来事（イベント）\ :math:`a` と :math:`b` について、次のいずれかが成り立つとき「:math:`a` は :math:`b` より前に起きた」といい、:math:`a \to b` と書く。この関係を :term:`happened-before 関係`\ と呼ぶ。

#. :math:`a` と :math:`b` が同じプロセスのイベントで、:math:`a` が先に起きた。
#. :math:`a` があるメッセージの送信で、:math:`b` がそのメッセージの受信である。
#. ある :math:`c` について :math:`a \to c` かつ :math:`c \to b` である（推移律）。

:math:`a \to b` でも :math:`b \to a` でもないとき、:math:`a` と :math:`b` は\ **並行**\ であるという。並行な 2 つのイベントは、互いに影響を与えようがなかったので、どちらを先とみなしても矛盾は生じない。

物理的な時刻の代わりに、この関係と矛盾しない数を各イベントに割り当てる仕組みを\ :term:`論理時計`\ と呼ぶ。最も単純なものが\ :term:`ランポート時計`\ で、各プロセスが整数のカウンタを 1 つ持ち、次の規則で更新する。

* ローカルなイベントの前に、カウンタを 1 増やす。
* メッセージを送るときは、カウンタを 1 増やし、その値をメッセージに付ける。
* メッセージを受け取ったら、自分のカウンタとメッセージに付いた値の大きい方に 1 を足した値をカウンタにする。

イベント :math:`a` のランポート時刻を :math:`L(a)` とすると、この規則により :math:`a \to b` ならば :math:`L(a) < L(b)` が成り立つ。次のサンプルは、3 つのプロセスの送受信の筋書きを実行して、各イベントのランポート時刻を表示する。

実行結果の 7 行目では、P2 の時計は 0 だったが、m1 に付いた 2 との大きい方に 1 を足して 3 になる。m1 の送信（L=2）は受信（L=3）より必ず小さい時刻を持つ。11 行目の P1 は、自分の時計が 2 でも m3 に付いた 5 に合わせて 6 に進む。こうして、因果関係でつながったイベントには必ず増加する時刻が付く。

ただし、逆は成り立たない。:math:`L(a) < L(b)` であっても :math:`a \to b` とは限らない。P1 の m1 の送信（L=2）と P3 の m2 の送信（L=3）は、どちらからどちらにもメッセージが届いていない並行なイベントだが、時刻だけを見ると前後関係があるように見える。ランポート時刻が等しいイベントはプロセス名で順序を決めれば（91 行目）、すべてのイベントを矛盾なく 1 列に並べた全順序が得られる。分散システムでの排他制御のように、全員が同じ順序に合意できれば十分な用途には、これで足りる。

並行かどうかまで判定したい場合は\ :term:`ベクタ時計`\ を使う。ベクタ時計では、各プロセスがプロセスの数だけの要素を持つカウンタの配列を持ち、自分の要素を増やし、受信時には要素ごとに大きい方をとる。上の筋書きでは、m1 の送信は :math:`(2, 0, 0)`、m2 の送信は :math:`(0, 0, 3)` になる（要素は P1、P2、P3 の順）。どちらの配列も他方の要素ごとの値以下になっていないので、2 つのイベントは並行だと判定できる。ベクタ時計は、マルチリーダやリーダレスのレプリケーション（次節）で、同時に行われた書き込みの衝突を検出するのに使われる。

レプリケーション
----------------

目的とリーダ型の複製
^^^^^^^^^^^^^^^^^^^^

同じデータの複製（レプリカ）を複数のノードに持たせることを\ :term:`レプリケーション`\ と呼ぶ。目的は、一部のノードが故障してもデータを失わずサービスを続けること（可用性と耐久性）、読み出しを複数のノードに分散すること（性能）、利用者の近くにデータを置くこと（遅延の削減）である。

最も広く使われているのが\ **単一リーダ型**\ （リーダ型）のレプリケーションである。レプリカのうち 1 つをリーダ（プライマリ）とし、書き込みはすべてリーダが受け付ける。リーダは変更を自分のデータに反映するとともに、その内容をログとして他のレプリカであるフォロワ（レプリカ、セカンダリ）に送り、フォロワは同じ順序で変更を適用する。読み出しはリーダでもフォロワでも行える。PostgreSQL や MySQL のレプリケーションはこの方式である。リーダが故障したときは、フォロワの 1 つを新しいリーダに昇格させる\ **フェイルオーバ**\ を行う。

単一リーダ型のほかに、複数のノードが書き込みを受け付ける\ **マルチリーダ型**\ と、リーダを置かずにクライアントが複数のレプリカに直接読み書きする\ **リーダレス型**\ がある。マルチリーダ型は、データセンタごとにリーダを置いて書き込みの遅延を減らせるが、別々のリーダで同じデータが同時に書き換えられる衝突の解決が必要になる。リーダレス型では、:math:`n` 個のレプリカのうち :math:`w` 個に書き込めたら書き込み成功、:math:`r` 個から読めたら読み出し成功とし、:math:`w + r > n` となるように選ぶ。こうすると読み出すレプリカの少なくとも 1 つは最新の書き込みを受け取っている。この :math:`w` と :math:`r` を\ **クォーラム**\ と呼ぶ。

同期と非同期の複製
^^^^^^^^^^^^^^^^^^

リーダがクライアントに書き込み成功を返すタイミングには 2 つの選択肢がある。\ **同期レプリケーション**\ では、フォロワが変更を受け取ったと応答するまで待ってから成功を返す。成功を返した書き込みはフォロワにも存在するので、リーダが故障しても失われない。ただし、フォロワが 1 台でも遅いか故障していると、書き込み全体が止まってしまう。\ **非同期レプリケーション**\ では、フォロワの応答を待たずに成功を返す。書き込みは速く、フォロワの故障の影響を受けないが、リーダが故障したとき、まだフォロワに届いていない書き込みは、成功を返したにもかかわらず失われる。実務では、フォロワのうち 1 台だけを同期にし、残りを非同期にする折衷（準同期）もよく使われる。

フェイルオーバにも落とし穴がある。古いリーダが実は止まっておらず、ネットワーク分断で見えなくなっていただけの場合、新旧 2 つのリーダが同時に書き込みを受け付けてデータが食い違う。この状態を\ **スプリットブレイン**\ と呼ぶ。これを防ぐには、後述の合意の仕組みでリーダを 1 つに決める必要がある。

複製の遅延が引き起こす異常
^^^^^^^^^^^^^^^^^^^^^^^^^^

非同期レプリケーションでは、フォロワはリーダより少し古いデータを持つ。この遅れ（レプリケーションラグ）は通常 1 秒未満だが、負荷が高いときや障害時には数秒から数分に伸びる。読み出しをフォロワに振り分けると、利用者からは次のような奇妙な現象が見える。

* **自分の書き込みが読めない**: プロフィールを更新した直後に再読み込みすると、まだ反映されていないフォロワから古いプロフィールが読まれ、利用者は更新が失敗したと思う。自分が書き込んだデータや、書き込みから一定時間はリーダから読むといった方法で防ぐ。この保証を read-your-writes 一貫性と呼ぶ。
* **時間が逆戻りする**: 1 回目の読み出しは追い付いたフォロワ、2 回目は遅れたフォロワに振り分けられると、1 回目に見えたコメントが 2 回目には消えている。同じ利用者の読み出しは常に同じレプリカに振り分けることで防ぐ。この保証をモノトニックリード一貫性と呼ぶ。
* **因果の逆転**: 質問とその回答が別々に複製されると、回答だけが先に届いたレプリカでは、質問より先に回答が見える。

一貫性のモデル
^^^^^^^^^^^^^^

レプリカがある状態で、読み出しがどの程度新しい値を返すことを保証するかを\ **一貫性モデル**\ と呼ぶ。代表的な 2 つを示す。

\ :term:`線形化可能性`\ （linearizability）は、レプリカがいくつあっても、システムがあたかもデータのコピーが 1 つしかないかのように振る舞うことを保証する。各操作は、呼び出してから応答が返るまでの間のある一瞬に効果を持つとみなせ、ある書き込みが完了した後に始まった読み出しは、必ずその値かそれより新しい値を返す。強い一貫性と呼ばれるのは多くの場合これである。プログラマにとっては最も分かりやすいが、実現するには操作のたびにレプリカ間の調整が必要で、遅延が大きく、ネットワーク分断の間は一部のノードが応答できなくなる（後述の CAP 定理）。

\ :term:`結果整合性`\ （eventual consistency）は、新しい書き込みが止まれば、いずれすべてのレプリカが同じ値に収束することだけを保証する。「いずれ」がいつかは保証せず、それまでの間は古い値が返りうる。非同期レプリケーションの読み出しは結果整合性しか持たない。保証は弱いが、各レプリカが他を待たずに応答できるので、速く、可用性が高い。read-your-writes やモノトニックリードは、その中間にある保証である。

.. note::

   「一貫性」という言葉は文脈によって意味が異なるので注意が必要である。ACID 特性の一貫性（Consistency）は、トランザクションの前後で整合性制約が満たされることを意味し、レプリカの新しさとは関係が無い。また、第 11 章の\ :term:`分離レベル`\ （SERIALIZABLE など）は、複数の行にまたがる\ **トランザクション同士の干渉**\ をどこまで防ぐかの保証であり、線形化可能性は **1 つのデータに対する個々の操作が最新の値を返すか**\ の保証である。両者は独立した概念で、直列化可能であっても線形化可能とは限らない（例えば古いスナップショットから読むトランザクションは、直列化可能でも最新の値を返さない）。両方を満たすものは厳密な直列化可能性（strict serializability）と呼ばれる。

分割（シャーディング）
----------------------

キーの範囲による分割とハッシュによる分割
^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^

レプリケーションはすべてのノードに同じデータを置くので、データ量が 1 台に収まらない場合や、書き込みの負荷が 1 台のリーダでさばけない場合には役に立たない。そこで、データを重ならない部分（パーティション、シャード）に分け、それぞれを別のノードに置く。これを\ :term:`シャーディング`\ （分割、パーティショニング）と呼ぶ。実際には、各シャードをさらにレプリケーションして可用性も確保するのが普通である。シャーディングの要点は、どのキーをどのシャードに置くかの決め方にある。

* **キーの範囲による分割**: 辞書の巻のように、キーの範囲ごとにシャードを決める（A〜F はシャード 1、G〜M はシャード 2、など）。キーが順に並ぶので範囲検索が効率よく行える。一方、キーの分布が偏るとシャードの大きさも偏る。特に、時刻をキーにすると、新しいデータの書き込みがすべて最新の範囲を受け持つ 1 つのシャードに集中する。
* **ハッシュによる分割**: キーの\ :term:`ハッシュ関数`\ の値でシャードを決める。ハッシュ値は元のキーが似ていても大きく異なるので、データと負荷が均等に分散する。その代わりに、隣り合うキーが別々のシャードに散らばるため、範囲検索ではすべてのシャードに問い合わせる必要がある。

偏りとホットスポット
^^^^^^^^^^^^^^^^^^^^

ハッシュで分割しても、1 つのキーへのアクセスが極端に多い場合は避けられない。例えば、SNS で多数のフォロワを持つ有名人の投稿には、読み出しも書き込みも集中する。このように特定のシャードやキーに負荷が集中する箇所を\ **ホットスポット**\ と呼ぶ。対策として、人気のあるキーだけ末尾に乱数を付けて複数のキーに分散させ、読み出し時にそれらを集める、キャッシュを前段に置く、といった方法がとられる。

ノードの追加とコンシステントハッシュ
^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^

ハッシュ値をノード数 :math:`N` で割った余り（:math:`h \bmod N`）でノードを決める方法は単純だが、ノード数が変わるとほとんどのキーの置き場所が変わってしまう。ハッシュ値が一様に分布していれば、:math:`N` を 4 から 5 に増やしたとき、置き場所が変わらないキーは :math:`1/5` だけで、残りの 80% のデータを移動することになる。

\ :term:`コンシステントハッシュ`\ は、ハッシュ値の空間を円環とみなし、ノードもキーも同じハッシュ関数で円環上に配置して、各キーを円環を時計回りにたどって最初に出会うノードに割り当てる方法である。ノードを 1 つ追加しても、移動するのは新しいノードと直前のノードの間にあったキーだけで、平均すると全体の :math:`1/(N+1)` 程度で済む。実際には、1 台のノードを円環上の多数の点（仮想ノード）に配置して、偏りを小さくする。別の方法として、シャードの数をノード数よりはるかに多い固定の値（例えば 1,024 個）にしておき、ノードの増減時にはシャード単位でノードに割り当て直すシステムも多い。

CAP 定理
--------

定理の内容
^^^^^^^^^^

レプリケーションされたデータについて、一貫性と可用性の間には根本的なトレードオフがある。これを述べたのが :term:`CAP 定理`\ である。E. Brewer が 2000 年に予想として示し、2002 年に S. Gilbert と N. Lynch が定式化して証明した [GilbertLynch2002]_。証明で使われた 3 つの性質は次のとおりである。

* **一貫性**\ （Consistency）: 線形化可能性。すべての読み出しが最新の書き込みの値を返し、システムはデータのコピーが 1 つであるかのように振る舞う。
* **可用性**\ （Availability）: 故障していないノードが受け取ったすべての要求に、（エラーではない）応答を返す。
* **分断耐性**\ （Partition tolerance）: ノード間のメッセージが任意に失われても（ネットワーク分断が起きても）、システムが動作を続ける。

定理は「ネットワーク分断が起きているとき、一貫性と可用性を両立するシステムは作れない」ことを示している。理由は単純である。ノード X と Y の間の通信が途絶えている間に、X が書き込みを受け付けたとする。その後 Y に読み出しが届いたとき、Y が応答すれば、X の書き込みを知らないので古い値を返すことになり一貫性が破れる。一貫性を守るには、Y は応答を拒否するか分断が解消するまで待つしかなく、可用性が破れる。

よくある誤解
^^^^^^^^^^^^

CAP 定理は「3 つのうち 2 つを選べる」と説明されることが多いが、これは誤解を招く。ネットワーク分断は選ぶものではなく、分散システムである限り必ず起こりうる。したがって実際の選択は、「分断が起きたときに、一貫性を優先して一部の要求を拒否するか（CP）、可用性を優先して古い値を返すことを許すか（AP）」である。分断が起きていない平常時には、一貫性と可用性は両立できる。「CA のシステム」とは、分断が起きないことを前提にしたシステム、つまり実質的に 1 台のシステムのことである。

また、CAP 定理の「一貫性」は線形化可能性という特定の意味であり、ACID の一貫性とは異なる。「可用性」も、故障していないすべてのノードが応答するという厳しい定義であり、情報セキュリティの\ :term:`可用性`\ や、稼働率で表す日常的な意味の可用性とは異なる。CP を選んだシステムでも、分断されたのが少数のノードだけなら、多数派の側は応答を続けられるので、実用上は十分に高い稼働率を達成できる。さらに、CAP 定理は分断という 1 種類の故障だけを扱い、平常時の遅延については何も述べていない。

この最後の点を補うのが **PACELC** という整理である。分断（Partition）が起きたときは可用性（Availability）と一貫性（Consistency）のどちらかを選び、それ以外（Else）の平常時には遅延（Latency）と一貫性（Consistency）のどちらを優先するかを選ぶ、という意味である [Abadi2012]_。強い一貫性を得るには、分断が無くても操作のたびにレプリカの応答を待つ遅延を払う。実際のシステム選びでは、平常時のこのトレードオフの方が影響が大きいことが多い。

合意
----

合意問題
^^^^^^^^

フェイルオーバでは、どのノードを新しいリーダにするかを、すべてのノードが同じ結論で決めなければならない。2 つのノードがそれぞれ自分をリーダだと思えば、スプリットブレインになる。このように、複数のノードが 1 つの値について同じ結論に達することを\ :term:`合意`\ （consensus）と呼ぶ。合意のアルゴリズムには、次の性質が求められる。

* **合意性**: 決定した値は、すべてのノードで同じである。
* **妥当性**: 決定した値は、いずれかのノードが提案した値である。
* **停止性**: 故障していないノードは、いずれ値を決定する。

リーダ選出、分散ロック（同時に 1 つのノードだけがロックを持つ）、レプリケーションのログの順序の決定は、いずれも合意問題に帰着する。

合意は理論的に難しい問題である。M. Fischer、N. Lynch、M. Paterson が 1985 年に示した **FLP 不可能性**\ は、メッセージの遅延に上限が無い非同期のシステムでは、1 つのノードが停止するかもしれないというだけで、必ず停止する決定的な合意アルゴリズムは存在しないことを示している [FLP1985]_。遅いノードと停止したノードを区別できないからである。実用的なアルゴリズムは、安全性（異なる値に決まらないこと）は常に守り、停止性はタイムアウトを使って「ネットワークがある程度安定していれば」保証する、という形でこの限界を回避している。

Raft の概要
^^^^^^^^^^^

\ :term:`Raft` は、理解しやすさを重視して設計された合意アルゴリズムである [Raft]_。それ以前から使われてきた Paxos と同等の保証を持ちながら、仕組みを「リーダ選出」と「ログ複製」に分けて説明できるようにしてある。Raft は、すべてのノードが同じ順序で同じ命令の列（ログ）を受け取ることを保証し、各ノードがそのログを順に適用すれば同じ状態になる。この考え方をステートマシンレプリケーションと呼ぶ。

**任期**\ （term）: Raft は時間を任期という区間に分け、1, 2, 3, ……と番号を付ける。各任期にはリーダが高々 1 つしか存在しない。各ノードは自分が知っている最新の任期の番号をメッセージに付けて送り、古い任期の番号が付いたメッセージは拒否される。任期の番号は、ランポート時計と同じく、物理的な時刻を使わずに新旧を判断するための論理時計の役割を果たす。

**リーダ選出**\ : 各ノードはフォロワ、候補者、リーダのいずれかの状態にある。リーダは定期的にハートビート（中身の無いログ複製の要求）を送る。フォロワは、一定時間ハートビートを受け取らないと、リーダが故障したとみなして任期の番号を 1 増やし、候補者となって他のノードに投票を依頼する。各ノードは 1 つの任期に 1 回だけ投票でき、過半数の票を得た候補者がその任期のリーダになる。複数の候補者が同時に立候補して票が割れることを防ぐため、タイムアウトの長さは各ノードで乱数で決める（論文では 150〜300 ミリ秒の範囲が例示されている）。

**ログ複製**\ : クライアントからの命令はリーダが受け取り、自分のログに任期の番号とともに追加して、フォロワに複製を依頼する。ログの項目が過半数のノードに保存されると、その項目は\ **コミット**\ されたとみなされ、各ノードで適用してよくなる。また、候補者のログが自分より古い場合は投票しないという規則があるため、コミットされた項目を持たないノードがリーダに選ばれることは無い。

**過半数の考え方**\ : Raft の安全性は過半数（クォーラム）に支えられている。:math:`n` 台のうちの過半数 :math:`\lfloor n/2 \rfloor + 1` 台からなる 2 つの集まりは、必ず少なくとも 1 台を共有する。そのため、同じ任期に 2 人の候補者が両方とも過半数の票を得ることはできず、コミットされた項目は、次にリーダになるノードに投票した過半数のうち少なくとも 1 台が持っている。ネットワーク分断が起きても、過半数の側だけがリーダを選んで書き込みを続けられ、少数派の側の古いリーダはコミットできない。合意は CAP 定理でいう CP の側を選んでいるわけである。:math:`n` 台のクラスタが耐えられる故障は :math:`\lfloor (n-1)/2 \rfloor` 台までで、次の表のようになる。

.. list-table:: クラスタの台数と耐えられる故障の数
   :header-rows: 1
   :widths: 30 35 35

   * - 台数 :math:`n`
     - 過半数 :math:`\lfloor n/2 \rfloor + 1`
     - 耐えられる故障の数
   * - 3
     - 2
     - 1
   * - 4
     - 3
     - 1
   * - 5
     - 3
     - 2
   * - 7
     - 4
     - 3

4 台は 3 台と同じく 1 台の故障にしか耐えられず、過半数をそろえるのに必要な台数だけが増える。そのため、合意を行うクラスタは通常 3 台か 5 台の奇数で構成する。

実用例
^^^^^^

アプリケーションが合意のアルゴリズムを自分で実装することはまれで、合意を提供するミドルウェアを使うのが普通である。etcd は Raft を実装したキーバリューストアで、Kubernetes がクラスタの状態の保存に使っている。Apache ZooKeeper は Zab という独自の合意プロトコルを使い、多くの分散システムでリーダ選出、設定情報の管理、分散ロックに使われてきた。これらはいずれも、少量の重要なデータを強い一貫性で保持するためのものであり、大量のデータを置く用途には向かない。

分散ロックでは、ガベージコレクションなどで長時間止まっている間にロックの有効期限が切れ、別のノードがロックを取得した後で、止まっていたノードがロックを持っているつもりで処理を再開することがある。これを防ぐには、ロックを取得するたびに増加する番号（フェンシングトークン）を発行し、書き込み先がそれより古い番号の要求を拒否するようにする。読んだときの版数を条件に更新する「:doc:`ch11_databases`」の楽観的ロックと同じ考え方である。

障害に強い設計
--------------

タイムアウトの決め方
^^^^^^^^^^^^^^^^^^^^

部分故障を検知する手段はタイムアウトしかない。短すぎると、少し遅いだけの正常なノードを故障とみなして不要なフェイルオーバや再試行を引き起こし、負荷が増えてさらに遅くなる悪循環に陥りうる。長すぎると、本当に故障したときの検知が遅れ、その間呼び出し元は待たされ続ける。

固定の値を勘で決めるのではなく、通常時の応答時間の分布を測り、例えば上位 0.1% の応答時間（99.9 パーセンタイル）に余裕を加えた値を使うのが 1 つの目安である。また、呼び出しが何段にも連なる場合は、利用者に応答すべき期限（デッドライン）を下流に伝え、残り時間が無くなった処理は打ち切る。「:doc:`ch10_networks`」で述べたように、タイムアウトを設定しないことは論外である。

再試行と指数バックオフ
^^^^^^^^^^^^^^^^^^^^^^

ネットワークの一時的な不調やサーバの一時的な過負荷による失敗は、少し待ってやり直せば成功することが多い。ただし、再試行してよいのは、タイムアウトや HTTP の 503 のような一時的な失敗に限られる。400 や 404 のような要求自体の誤りは、何度送っても結果は変わらない。

再試行の間隔は、失敗するたびに 2 倍、4 倍と伸ばしていく\ :term:`指数バックオフ`\ にする。:math:`k` 回目の再試行の前の待ち時間を :math:`b \cdot 2^{k-1}`\ （:math:`b` は基準の待ち時間）とし、上限を設ける。過負荷のサーバに間を置かずに再試行を浴びせると、回復を妨げてしまうからである。さらに、待ち時間に乱数の揺らぎ（\ **ジッタ**\ ）を加える。障害で一斉に失敗した多数のクライアントが同じ間隔で再試行すると、再試行も一斉に届いて再びサーバを圧倒する。0 から :math:`b \cdot 2^{k-1}` までの一様乱数を待ち時間にする方法（フルジッタ）がよく使われる。

再試行の回数にも上限が必要である。特に、呼び出しが多段になっている場合、各段がそれぞれ 3 回ずつ再試行すると（1 回の呼び出しが最大 4 回の試行になる）、3 段では最下段への要求が最大 :math:`4^3 = 64` 倍に増幅される。再試行はなるべく 1 か所に限るのがよい。

冪等性と冪等キー
^^^^^^^^^^^^^^^^

再試行には根本的な問題が残る。「:ref:`ch12-partial-failure`」で見たように、応答が返らなかったとき、相手が処理したかどうかは分からない。処理済みだった場合に再試行すると、同じ処理が 2 回行われる。「:doc:`ch10_networks`」で学んだように、GET や PUT のような\ **冪等**\ な操作なら何度行っても結果は同じなので、安全に再試行できる。問題は、決済や注文のように本質的に冪等でない操作である。

そこで、冪等でない操作を冪等にするために\ :term:`冪等キー`\ を使う。クライアントは 1 つの論理的な操作（例えば 1 件の注文の支払い）ごとに一意な識別子を生成し、要求に付けて送る。再試行するときは同じ識別子を使う。サーバは処理した識別子と結果を記録しておき、同じ識別子の要求が再び届いたら、処理を行わずに記録した結果を返す。

   注文 B: 試行 1 回, 成功, 課金 1 回, 待ち 0 ms

冪等キーが無い場合、実行結果の 6 行目の注文 E は、応答が 2 回失われたために 3 回課金されている。冪等キーがあれば、14 行目のように同じ通信の失敗が起きても課金は 1 回で済む。5 行目と 13 行目の注文 D は 4 回目でようやく成功しているが、課金は 1 回である。最初の 3 回は要求そのものが失われ、サーバに届かなかったからである。2 行目と 10 行目の注文 A は、すべての試行で応答を受け取れず、クライアントは失敗と判断したが、実際には課金されている。冪等キーがあれば、後で同じキーで再び問い合わせて結果を確かめられる。

実際のシステムでは、冪等キーの記録と処理本体を同じ\ :term:`トランザクション`\ で行う必要がある。処理だけが成功してキーの記録が失われると、次の再試行で二重に処理される。データベースの冪等キーの列に一意制約を付けておけば、同じキーの同時の要求も防げる。また、記録をいつまで保持するかの期限（例えば 24 時間）を決め、クライアントはその期間内に再試行を終える。

配送の保証
^^^^^^^^^^

メッセージキューなどでメッセージを届ける仕組みは、どこまで配送を保証するかによって次の 3 つに分けられる。

.. list-table:: メッセージ配送の保証
   :header-rows: 1
   :widths: 22 43 35

   * - 保証
     - 仕組み
     - 起こりうること
   * - 高々 1 回（at-most-once）
     - 再試行しない
     - メッセージが失われる
   * - 少なくとも 1 回（at-least-once）
     - 受信の確認が来るまで再試行する
     - 同じメッセージが重複して届く
   * - ちょうど 1 回（exactly-once）
     - 少なくとも 1 回の配送と、受信側の重複排除（冪等な処理）を組み合わせる
     - 重複排除の記録と処理の原子性が必要になる

ネットワークがメッセージを失いうる以上、送るだけでちょうど 1 回の\ **配送**\ を保証することはできない。「ちょうど 1 回」をうたう製品が実際に保証しているのは、少なくとも 1 回届けたうえで、受信側が重複を取り除くことにより、\ **処理の効果**\ がちょうど 1 回分になることである。上のサンプルの冪等キーは、まさにこの方法である。多くのシステムでは、少なくとも 1 回の配送を選び、受信側の処理を冪等にするのが基本の設計になる。

分散トランザクションとサガ
^^^^^^^^^^^^^^^^^^^^^^^^^^

注文サービスのデータベースと在庫サービスのデータベースのように、複数のノードにまたがる更新を原子的に行いたい場合がある。これを分散トランザクションと呼び、その古典的な方法が\ :term:`二相コミット`\ （2PC: Two-Phase Commit）である。第 11 章の二相ロックとは別のものなので注意してほしい。二相コミットでは、調整役（コーディネータ）が次の 2 段階で各参加者のコミットを取りまとめる。

#. **準備フェーズ**: コーディネータは全参加者に「コミットできるか」を問い合わせる。各参加者は、変更をログに永続化してコミットできる状態にしてから「はい」と答えるか、できなければ「いいえ」と答える。「はい」と答えた参加者は、以後自分の判断でロールバックしてはならない。
#. **コミットフェーズ**: 全員が「はい」ならコーディネータはコミットを決定し、その決定を記録してから全参加者に伝える。1 人でも「いいえ」と答えるか応答が無ければ、ロールバックを伝える。

二相コミットの最大の問題は、準備フェーズで「はい」と答えた後にコーディネータが故障すると、参加者はコミットすべきかロールバックすべきか分からず、ロックを持ったまま待ち続けるしかないことである。その間、関係する行は他のトランザクションからも使えない。また、すべての参加者の応答を待つので遅い。

そのため、サービスごとにデータベースを分ける設計では、\ **サガ**\ （saga）と呼ばれる方法がよく使われる。サガは、全体を各サービスのローカルなトランザクションの列に分け、順に実行する。途中の段階が失敗したら、それまでに完了した段階を取り消す\ **補償トランザクション**\ （例えば、在庫の引き当ての取り消しや返金）を逆順に実行する。サガは長時間のロックを必要としないが、途中の状態が他から見えてしまう（分離性が無い）ので、それを前提とした業務の設計が必要になる。

まとめ
------

* 分散システムは規模、可用性、地理的分散のために使われる。一部だけが故障する部分故障が起こり、応答が無いときに相手が処理したかどうかは分からない。
* ネットワークは信頼できず、遅延はゼロではない。停止故障、ネットワーク分断、メッセージの喪失と遅延を前提に設計する。
* 時刻は UTC の Unix 時間で記録する。時計はドリフトし、NTP で合わせても誤差が残り、逆戻りもする。経過時間の測定にはモノトニッククロックを使い、壁時計の時刻で出来事の順序を決めない。
* ランポート時計は happened-before 関係と矛盾しない論理的な時刻を与える。並行なイベントの判定にはベクタ時計を使う。
* レプリケーションには単一リーダ型、マルチリーダ型、リーダレス型がある。非同期の複製では複製の遅延による異常が見え、結果整合性しか得られない。線形化可能性はトランザクションの分離レベルとは別の概念である。
* シャーディングにはキーの範囲による分割とハッシュによる分割があり、ホットスポットへの対策が必要になる。コンシステントハッシュはノードの増減時に移動するデータを減らす。
* CAP 定理は、ネットワーク分断が起きたときに線形化可能性と可用性を両立できないことを示す。平常時の遅延と一貫性のトレードオフも重要である。
* Raft は任期、リーダ選出、ログ複製と過半数の仕組みで合意を実現する。合意を行うクラスタは 3 台か 5 台の奇数で構成し、etcd や ZooKeeper のような実装を使う。
* タイムアウトは応答時間の分布から決め、再試行は一時的な失敗に限って指数バックオフとジッタで行う。冪等キーにより、冪等でない操作も安全に再試行できる。
* ちょうど 1 回の配送は、少なくとも 1 回の配送と冪等な処理の組み合わせで実現する。二相コミットは調整役の故障で停止しうるため、サービス間ではサガも使われる。
