オペレーティングシステム
========================

プログラムを実行するとき、私たちは CPU が他のプログラムと共有されていることも、メモリの物理的な位置も、ファイルがディスクのどこに置かれているかも意識しない。こうした詳細を引き受けているのが\ :term:`オペレーティングシステム`\ （OS: Operating System）である。この章では、OS の役割とカーネルの仕組み、プロセスとスレッド（Unix の fork と exec、シグナルを含む）、CPU スケジューリング、仮想メモリとページ置換、ファイルシステム（ファイル記述子とジャーナリングを含む）を順に学び、最後に 1 台の計算機の上で複数の OS や実行環境を動かす仮想化とコンテナを紹介する。複数のスレッドや多数の入出力を同時に扱うプログラミングの問題（並行処理と同期、入出力のモデル）は、次の「:doc:`ch09_concurrency_and_io`」で扱う。いずれも、プログラムの性能や不具合の原因を考えるときに欠かせない知識である。全体の参考書としては [OSTEP]_ と [MOS]_ を挙げておく。

OS の役割
---------

抽象化と資源管理
^^^^^^^^^^^^^^^^

OS の役割は大きく 2 つに分けられる。1 つは\ **抽象化**\ である。ハードウェアの細部を隠し、扱いやすい概念を提供する。CPU は「プロセス」、メモリは「アドレス空間」、ディスクは「ファイル」、ネットワークは「ソケット」という抽象として見える。もう 1 つは\ **資源管理**\ である。複数のプログラムが同時に動くとき、CPU 時間、メモリ、ディスク、ネットワークといった資源を公平かつ効率よく割り当て、あるプログラムが他のプログラムの資源を勝手に使えないように保護する。

次の表に、OS が提供する主な抽象と、その背後にあるハードウェア資源の対応を示す。

.. list-table::
   :header-rows: 1
   :widths: 20 25 55

   * - ハードウェア資源
     - OS が提供する抽象
     - 抽象によって得られるもの
   * - CPU
     - プロセス、スレッド
     - CPU が 1 つでも、多数のプログラムがそれぞれ CPU を占有しているかのように動ける
   * - 主記憶（メモリ）
     - 仮想アドレス空間
     - 各プロセスが 0 番地から始まる専用の広いメモリを持っているかのように動ける
   * - 補助記憶
     - ファイル、ディレクトリ
     - ブロック番号ではなく名前でデータを読み書きできる
   * - ネットワーク機器
     - ソケット
     - パケットの送受信を意識せず、バイト列の送受信として通信できる

カーネルとユーザモード
^^^^^^^^^^^^^^^^^^^^^^

OS の中核で、資源管理と保護を担う部分を\ :term:`カーネル`\ と呼ぶ。シェルやデスクトップ環境、各種のユーティリティも OS の一部として配布されるが、それらは通常のプログラムと同じ立場で動き、カーネルの機能を利用する側である。

カーネルが他のプログラムを保護できるのは、CPU がハードウェアとして 2 つ以上の動作モードを持つからである。\ **カーネルモード**\ （特権モード）では、すべての命令を実行でき、すべてのメモリと入出力装置にアクセスできる。\ **ユーザモード**\ では、入出力装置の直接操作やメモリ保護の設定変更といった特権命令が禁止され、許可されたメモリにしかアクセスできない。アプリケーションはユーザモードで動くため、不正な操作をしようとすると CPU が例外を発生させ、制御がカーネルに移る。カーネルはそのプロセスを強制終了させる。Linux でよく見る ``Segmentation fault`` は、許可されていないアドレスにアクセスしたプロセスが、この仕組みによって終了させられたことを表す。

システムコール
^^^^^^^^^^^^^^

ユーザモードのプログラムがファイルを開く、メモリを確保する、データを送信するといった操作をするには、カーネルに依頼する必要がある。この依頼の窓口が\ :term:`システムコール`\ である。プログラムは引数をレジスタに置き、システムコール専用の命令（x86-64 の ``syscall``、RISC-V の ``ecall`` など）を実行する。CPU はカーネルモードに切り替わってカーネル内の決められた入口に飛び、カーネルは引数を検査したうえで処理を行い、結果を返してユーザモードに戻る。

Python の ``open()`` や ``print()`` も、内部では最終的に ``open`` や ``write`` といったシステムコールを呼んでいる。モードの切り替えには通常の関数呼び出しより大きなコストがかかるため、小さな書き込みを何度もシステムコールにすると遅くなる。後述するバッファリングは、このコストを減らすための工夫でもある。Linux では ``strace`` コマンドで、プログラムが発行したシステムコールの一覧を観察できる。

割り込み
^^^^^^^^

\ :term:`割り込み`\ は、実行中の命令の流れを中断して、カーネルの処理に制御を移す仕組みである。キーボードの入力、ディスクの読み込み完了、ネットワークカードへのパケット到着のように、外部の装置が CPU に知らせる\ **ハードウェア割り込み**\ と、ゼロ除算や不正なメモリアクセスのように、実行中の命令が原因で起きる\ **例外**\ がある（ここでいう例外は CPU の仕組みであり、第 7 章で扱うプログラミング言語の例外処理とは別の概念である）。システムコールの命令も、意図的に例外を起こしてカーネルに入る仕組みと見なせる。

特に重要なのが\ **タイマ割り込み**\ である。CPU に付属するタイマは一定間隔で割り込みを発生させ、そのたびにカーネルが制御を取り戻す。これにより、無限ループに陥ったプログラムがあっても、カーネルは CPU を取り上げて別のプログラムに割り当てられる。もし割り込みが無ければ、カーネルはプログラムが自発的にシステムコールを呼ぶまで何もできない。

プロセスとスレッド
------------------

プロセスとアドレス空間
^^^^^^^^^^^^^^^^^^^^^^

\ :term:`プロセス`\ は実行中のプログラムである。ディスク上のプログラムファイルは命令とデータの並びにすぎないが、OS がそれをメモリに読み込み、レジスタの値、プログラムカウンタ、開いているファイルの一覧などの状態を与えて実行を始めると、1 つのプロセスになる。同じプログラムを 2 回起動すれば、2 つの独立したプロセスができる。

各プロセスは自分専用の仮想アドレス空間を持つ。あるプロセスが書き換えられるのは自分のアドレス空間だけであり、他のプロセスのメモリを直接読み書きすることはできない。これを\ **プロセス間の分離**\ と呼ぶ。分離のおかげで、1 つのプロセスがバグで異常終了しても他のプロセスは影響を受けない。プロセス同士でデータをやり取りするには、パイプ、ソケット、共有メモリといった OS が提供するプロセス間通信（IPC: Inter-Process Communication）の機能を明示的に使う。

状態遷移
^^^^^^^^

プロセスは生成されてから終了するまでに、いくつかの状態を行き来する。代表的な状態を次の表に示す。

.. list-table::
   :header-rows: 1
   :widths: 20 80

   * - 状態
     - 意味
   * - 新規（new）
     - 生成中で、まだ実行の候補になっていない
   * - 実行可能（ready）
     - CPU が割り当てられれば、すぐに実行できる
   * - 実行中（running）
     - CPU 上で命令を実行している
   * - 待ち（blocked）
     - 入出力の完了やロックの解放など、何らかの事象を待っており、CPU を割り当てても進めない
   * - 終了（terminated）
     - 実行を終え、親プロセスが終了状態を回収するのを待っている

状態は次のように遷移する。新規のプロセスは準備が整うと実行可能になる。スケジューラが選ぶと実行中になる。実行中のプロセスは、タイマ割り込みによって割り当て時間を使い切ると実行可能に戻り、ファイルの読み込みのように完了を待つ処理を始めると待ちになる。待っていた事象が起きると、待ちから実行可能に移る。待ちから直接実行中に移ることはない点に注意してほしい。事象が起きても、CPU が割り当てられるまでは実行可能の列に並ぶ。

スレッド
^^^^^^^^

\ :term:`スレッド`\ はプロセスの中の実行の流れである。1 つのプロセスは複数のスレッドを持つことができ、それらはアドレス空間、開いているファイル、大域変数を共有する。一方、プログラムカウンタ、レジスタの値、スタックはスレッドごとに持つ。スレッド同士はメモリを共有しているので、データのやり取りは速く簡単だが、同じデータを同時に書き換えると、次章「:doc:`ch09_concurrency_and_io`」で扱う競合状態が起きる。プロセスとスレッドの違いを次の表にまとめる。

.. list-table::
   :header-rows: 1
   :widths: 20 40 40

   * - 観点
     - プロセス
     - スレッド
   * - メモリ
     - 互いに独立している
     - 同じプロセス内で共有する
   * - 生成と切り替えのコスト
     - 大きい
     - 比較的小さい
   * - データのやり取り
     - IPC が必要
     - 共有メモリを直接読み書きできる
   * - 障害の影響範囲
     - そのプロセスに閉じる
     - 1 つのスレッドの異常がプロセス全体を止め得る

コンテキストスイッチ
^^^^^^^^^^^^^^^^^^^^

CPU を別のプロセスやスレッドに切り替える処理を\ :term:`コンテキストスイッチ`\ と呼ぶ。カーネルは、実行中のものの状態（レジスタ、プログラムカウンタ、スタックポインタなど）をメモリに保存し、次に実行するものの状態を読み込んで再開する。別のプロセスに切り替える場合はアドレス空間も切り替わるため、後述する TLB の内容が使えなくなり、さらにキャッシュの内容も入れ替わっていく。そのため、コンテキストスイッチの本当のコストは、保存と復元の時間よりも、切り替え後しばらく続くキャッシュミスにあることが多い。キャッシュについては「:doc:`ch03_computer_architecture`」を参照してほしい。スレッドを必要以上に増やすと、計算よりも切り替えに時間を使うようになる。

.. _ch08-fork-exec:

Unix のプロセス生成: fork と exec
^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^

Unix 系の OS では、新しいプロセスは 2 つのシステムコールの組み合わせで作られる。``fork`` は、呼び出したプロセス（親プロセス）とほぼ同じ複製（子プロセス）を作る。子プロセスは親のアドレス空間、開いているファイル、カレントディレクトリなどを引き継ぎ、``fork`` の呼び出しから戻ったところで実行を続ける。両者を区別するのは戻り値で、親には子のプロセス ID が、子には 0 が返る。アドレス空間の複製は、実際にはすぐにはコピーせず、どちらかが書き込んだページだけをその時点でコピーする\ :term:`コピーオンライト`\ で行う。そのため、大きなプロセスでも ``fork`` 自体は速い。

``exec`` 系のシステムコール（``execve`` など）は、呼び出したプロセスのアドレス空間を捨て、指定したプログラムを読み込んで最初から実行させる（読み込みの手順は「:ref:`ch07-linker-loader`」を参照）。プロセス ID と開いているファイルはそのまま引き継がれる。シェルがコマンドを実行するときは、``fork`` で子を作り、子の中で ``exec`` してコマンドに置き換え、親は ``wait``\ （または ``waitpid``）で子の終了を待つ。生成と置き換えが分かれていることには利点がある。``fork`` と ``exec`` の間で、子は自分の標準出力を別のファイルにつなぎ替えるなどの準備ができる。``ls > out.txt`` のようなリダイレクトや、``ls | wc -l`` のようなパイプは、この隙間で後述の\ :ref:`ファイル記述子 <ch08-file-descriptor>`\ を操作して実現されている [Kerrisk]_。

終了した子プロセスは、親が ``wait`` で終了状態を回収するまで、状態遷移の表の「終了」の状態で残る。この状態のプロセスを\ **ゾンビ**\ と呼ぶ。親が回収を怠るとゾンビがたまり、プロセス表を圧迫する。親が先に終了した子は、Linux では通常 init（プロセス ID 1）などの別のプロセスに引き取られ、そこで回収される。

.. note::

   Windows には ``fork`` に相当する機能が無く、``CreateProcess`` が新しいプロセスの生成とプログラムの読み込みを 1 回で行う。Python の ``os.fork()`` は Unix 系でしか使えないので、移植性のあるプログラムでは ``subprocess`` モジュールを使う。``multiprocessing`` も、Windows と macOS では新しいインタプリタを起動する ``spawn`` 方式が既定であり、Linux では Python 3.14 から ``forkserver`` 方式が既定になった（それまでは ``fork``）。複数のスレッドを持つプロセスで ``fork`` すると、子には呼び出したスレッドだけが複製され、他のスレッドが持っていたロックが取得されたまま残ることがある。これが、``fork`` が既定から外された理由の 1 つである。

シグナル
^^^^^^^^

\ :term:`シグナル`\ は、カーネルがプロセスに非同期に事象を知らせる仕組みである。割り込みがハードウェアからカーネルへの通知だとすれば、シグナルはカーネルからプロセスへの通知にあたる。シグナルを受けたプロセスは、シグナルごとに決まった既定の動作（終了、停止、無視など）をするか、あらかじめ登録したハンドラ関数を実行する。代表的なシグナルを次の表に示す。

.. list-table::
   :header-rows: 1
   :widths: 18 42 40

   * - シグナル
     - 送られる場面
     - 既定の動作と注意
   * - ``SIGINT``
     - 端末で Ctrl+C を押したとき
     - 終了。Python では ``KeyboardInterrupt`` 例外になる
   * - ``SIGTERM``
     - ``kill`` コマンドの既定。サービスの停止時
     - 終了。ハンドラで後始末をしてから終了するのが行儀よい
   * - ``SIGKILL``
     - ``kill -9``、OOM killer
     - 強制終了。捕捉も無視もできない
   * - ``SIGSEGV``
     - 許可されていないアドレスにアクセスしたとき
     - 終了。``Segmentation fault`` の正体である
   * - ``SIGCHLD``
     - 子プロセスが終了したとき
     - 無視。親が ``wait`` する契機に使う
   * - ``SIGPIPE``
     - 読み手のいなくなったパイプやソケットに書き込んだとき
     - 終了。サーバでは無視する設定にすることが多い

ハンドラは、プログラムのどの命令の途中でも割り込んで実行され得るので、ハンドラの中でロックを取ったり複雑な処理をしたりすると、デッドロックや状態の破壊を招く。ハンドラではフラグを立てるだけにして、本来の処理の流れの中でそのフラグを確かめるのが定石である。Python の ``signal`` モジュールのハンドラは、インタプリタがバイトコードの区切りでメインスレッドの中で実行するので、この制約はいくらか緩い。Windows のシグナルは C 言語の標準が定めるごく一部（``SIGINT``、``SIGTERM`` など）しかなく、コンソールの Ctrl+C などは別の仕組みで通知される。
CPU スケジューリング
--------------------

実行可能なプロセスが CPU の数より多いとき、次にどれを実行するかを決めるのが\ :term:`スケジューラ`\ である。スケジューラの評価にはいくつかの指標があるが、ここでは\ **待ち時間**\ 、すなわちプロセスが到着してから終了するまでに、実行可能の列で待っていた時間の合計を用いる。プロセス :math:`i` の到着時刻を :math:`a_i`、実行に必要な CPU 時間（CPU バースト）を :math:`b_i`、終了時刻を :math:`f_i` とすると、待ち時間 :math:`w_i` と平均待ち時間 :math:`\bar{w}` は次の式で表される。

.. math::

   w_i = f_i - a_i - b_i, \qquad \bar{w} = \frac{1}{n} \sum_{i=1}^{n} w_i

代表的な 3 つの方式を次の表に示す。

.. list-table::
   :header-rows: 1
   :widths: 20 45 35

   * - 方式
     - 選び方
     - 特徴
   * - FCFS（First-Come, First-Served）
     - 到着順に選び、終わるまで実行する
     - 単純で公平だが、長いプロセスの後ろに短いプロセスが並ぶと平均待ち時間が長くなる
   * - SJF（Shortest Job First）
     - 到着済みのうち CPU バーストが最短のものを選び、終わるまで実行する
     - 平均待ち時間が短いが、実行時間を事前に知る必要があり、長いプロセスが後回しにされ続けることがある
   * - ラウンドロビン
     - 到着順の列から選び、一定時間（クォンタム）だけ実行して列の末尾に戻す
     - 応答が速く公平だが、切り替えが多く、平均待ち時間は長くなりやすい

FCFS で長いプロセスの後ろに短いプロセスが並ぶ現象は\ **コンボイ効果**\ と呼ばれる。すべてのプロセスが同時に到着する場合、SJF は平均待ち時間を最小にすることが知られている。ただし、実際の OS はプロセスの実行時間を事前に知らないため、過去の実行時間から次の CPU バーストを推定するなどの工夫が必要になる。

\ :term:`ラウンドロビン`\ は、タイマ割り込みで実行中のプロセスから CPU を取り上げる\ **プリエンプティブ**\ な方式である。FCFS と SJF は、ここでは一度実行を始めたら終わるまで取り上げない非プリエンプティブな方式として扱う。対話的なプログラムでは、平均待ち時間よりも、入力してから最初に反応が返るまでの応答時間が重要であり、ラウンドロビンはこれを短く保てる。実際の OS は、優先度を組み合わせたより複雑な方式を使っている。例えば Linux のスケジューラは、各プロセスが受け取った CPU 時間を記録し、受け取りが少ないものを優先することで公平性を保つ。

仮想メモリ
----------

アドレス空間とページング
^^^^^^^^^^^^^^^^^^^^^^^^

\ :term:`仮想メモリ`\ は、プログラムが使うアドレス（仮想アドレス）と、主記憶上の実際の位置（物理アドレス）を分離する仕組みである。プログラムは自分専用の仮想アドレス空間だけを見ており、仮想アドレスから物理アドレスへの変換は、CPU 内の MMU（Memory Management Unit）が命令の実行のたびに行う。変換の規則は OS が設定し、プロセスごとに異なる。そのため、2 つのプロセスが同じ仮想アドレスを使っていても、実際には異なる物理メモリを指しており、互いに干渉しない。これがプロセス間の分離の土台である。

変換は、アドレス空間を固定長の\ **ページ**\ に区切って行う。この方式を\ :term:`ページング`\ と呼ぶ。物理メモリも同じ大きさの\ **ページフレーム**\ に区切られ、仮想ページごとに、どのページフレームに対応するかを記録する。ページの大きさは 4 KiB（:math:`2^{12}` バイト）が一般的である。この場合、仮想アドレスの下位 12 ビットがページ内の位置（オフセット）、残りの上位ビットがページ番号になる。例えば仮想アドレス ``0x12345`` は、ページ番号 ``0x12`` のページの、オフセット ``0x345`` の位置を指す。

.. math::

   p = \left\lfloor \frac{v}{4096} \right\rfloor, \qquad d = v \bmod 4096

ここで :math:`v` は仮想アドレス、:math:`p` はページ番号、:math:`d` はオフセットである。変換ではページ番号だけを置き換え、オフセットはそのまま使う。

ページテーブルと TLB
^^^^^^^^^^^^^^^^^^^^

仮想ページ番号からページフレーム番号への対応表を\ :term:`ページテーブル`\ と呼ぶ。各要素には、フレーム番号のほかに、そのページが主記憶に存在するか、書き込みを許すか、ユーザモードからアクセスできるかといった属性ビットが入る。64 ビットの CPU ではアドレス空間が非常に広いため、1 枚の表にするとそれだけで巨大になる。そこで、ページテーブル自体を木構造にした多段のページテーブルを使い、実際に使っている部分だけを用意する。x86-64 では通常 4 段の表をたどる。

ページテーブルは主記憶に置かれるので、そのままではメモリアクセスのたびに、表を引くための追加のアクセスが何回も発生する。これを避けるため、MMU は最近使った変換結果を :term:`TLB`\ （Translation Lookaside Buffer）と呼ばれる小さなキャッシュに保持する。プログラムのアクセスには局所性があるため、TLB の命中率は通常非常に高い。逆に、広い範囲のメモリにランダムにアクセスするプログラムは、データのキャッシュミスに加えて TLB ミスでも遅くなる。大量のメモリを使うデータベースなどでは、2 MiB のような大きなページ（ヒュージページ）を使って TLB の効率を上げることがある。

ページフォールトとスワップ
^^^^^^^^^^^^^^^^^^^^^^^^^^

アクセスしたページが主記憶に無い、または許可されていない操作をしたとき、MMU は\ :term:`ページフォールト`\ と呼ばれる例外を発生させ、カーネルに制御を移す。カーネルは原因を調べ、正当なアクセスであればページを用意して命令をやり直させ、不正なアクセスであればプロセスを終了させる。ページフォールトは異常ではなく、仮想メモリの通常の動作の一部である。例えば OS は、プログラムを起動したときにすべてのページを読み込まず、初めてアクセスされたときにページフォールトを契機として読み込む。これを\ **デマンドページング**\ と呼ぶ。

主記憶が足りなくなると、OS はしばらく使われていないページの内容を補助記憶上の\ **スワップ領域**\ に書き出し、そのページフレームを別の用途に回す。書き出したページに再びアクセスがあると、ページフォールトが起き、補助記憶から読み戻す。補助記憶へのアクセスは主記憶より桁違いに遅いため、作業に必要なページが主記憶に収まらなくなると、ページの書き出しと読み戻しばかりが続いて処理がほとんど進まなくなる。この状態を\ **スラッシング**\ と呼ぶ。サーバの応答が急に極端に遅くなったときは、メモリ不足によるスワップの発生を疑うとよい。Linux では、それでもメモリが足りなければ、カーネルがプロセスを選んで強制終了させる（OOM killer）。

ページ置換アルゴリズム
^^^^^^^^^^^^^^^^^^^^^^

空いているページフレームが無いときにページフォールトが起きると、OS はどれか 1 つのページを主記憶から追い出して場所を空けなければならない。どのページを追い出すかを決める規則を\ :term:`ページ置換アルゴリズム`\ と呼ぶ。追い出したページがすぐにまた必要になれば、そのたびに補助記憶へのアクセスが発生するので、選び方はそのまま性能に響く。なお、追い出すページが読み込み後に書き換えられていなければ（ページテーブルの変更ビットが立っていなければ）、補助記憶に同じ内容があるので書き出しを省ける。代表的なアルゴリズムを次の表に示す [OSTEP]_。

.. list-table::
   :header-rows: 1
   :widths: 22 43 35

   * - アルゴリズム
     - 追い出すページ
     - 特徴
   * - FIFO
     - 最も早く主記憶に読み込んだページ
     - 実装は簡単だが、よく使われているページも古ければ追い出す
   * - LRU（Least Recently Used）
     - 最後に使われたのが最も古いページ
     - 参照の局所性があれば性能がよい。正確に実装するにはアクセスのたびに記録の更新が必要で重い
   * - 最適置換（OPT）
     - 次に使われるのが最も遠い未来であるページ
     - フォールト回数が理論上最小になるが、未来の参照を知る必要があるので実現できない。他の方式を評価する基準に使う
   * - クロック法
     - 参照ビットが 0 のページを、時計の針のように循環しながら探す
     - LRU の近似。実際の OS で広く使われる

クロック法は、ハードウェアの支援を使って LRU を安く近似する。MMU は、ページにアクセスがあるとページテーブルの要素の\ **参照ビット**\ を 1 にする。OS はページフレームを輪の形に並べ、追い出す候補を探すときは針の位置のページを調べる。参照ビットが 1 なら「最近使われた」とみなして 0 に戻し、針を次へ進める。0 のページが見つかったら、それを追い出す。一巡する間に一度も使われなかったページが選ばれるので、最近使われたページはおおむね残る。

次のサンプルは、同じ参照列に対する FIFO、LRU、OPT のページフォールト回数を数える。参照列は [OSTEP]_ などの教科書でよく使われる例と同じものである。

.. literalinclude:: ../examples/ch08_page_replacement.py
   :language: python
   :linenos:
   :lines: 18-66
   :lineno-match:
   :caption: ch08_page_replacement.py

:download:`ch08_page_replacement.py <../examples/ch08_page_replacement.py>`

FIFO は 21 行目の ``deque`` に読み込んだ順を記録し、28 行目で最も古いものを追い出す。命中しても順序を変えない点が LRU との違いである。LRU は第 4 章の「:ref:`ch04-lru-cache`」と同じく ``OrderedDict`` を使い、40 行目で使ったページを末尾（最新）に移し、44 行目で先頭（最も古い）を追い出す。OPT は 58 行目でこれから先の参照列を取り出し、64 行目で次に参照される位置が最も遠いページを追い出す。二度と参照されないページが複数あるときにどれを選んでも回数は変わらないが、64 行目では ``sorted`` で選び方を一定にしている。実行結果を次に示す。

.. code-block:: text
   :linenos:

   参照列: 7 0 1 2 0 3 0 4 2 3 0 3 2 1 2 0 1 7 0 1
   フレーム数 3: FIFO 15 回, LRU 12 回, OPT 9 回
   フレーム数 4: FIFO 10 回, LRU 8 回, OPT 8 回
   Belady の異常の参照列: 1 2 3 4 1 2 5 1 2 3 4 5
     FIFO, フレーム数 3: 9 回
     FIFO, フレーム数 4: 10 回

最初の参照で空のフレームを埋めるフォールトは、どの方式でも避けられない。この参照列には 6 種類のページがあるので、少なくとも 6 回は起きる。フレーム数 3 では、OPT の 9 回に対して LRU は 12 回、FIFO は 15 回である。LRU は「最近使われたページは近いうちにまた使われる」という参照の局所性に賭けており、過去から未来を推測することで OPT に近づいている。

4〜6 行目は :term:`Belady の異常`\ の例である。直感的にはフレームを増やせばフォールトは減るはずだが、FIFO ではこの参照列でフレームを 3 から 4 に増やすと、フォールトが 9 回から 10 回に増える。LRU と OPT では、フレーム数 :math:`k` のときに主記憶にあるページの集合が、常にフレーム数 :math:`k+1` のときの集合に含まれるという性質があるため、この異常は起きない。

ファイルシステム
----------------

ファイルとディレクトリ
^^^^^^^^^^^^^^^^^^^^^^

補助記憶は、固定長のブロックが番号順に並んだ装置にすぎない。その上に、名前の付いたファイルと、ファイルをまとめるディレクトリの階層を構成するのが\ :term:`ファイルシステム`\ である。ファイルシステムは、どのブロックがどのファイルに属するか、どのブロックが空いているかを管理し、``/home/user/report.txt`` のようなパス名からファイルの中身にたどり着けるようにする。代表的なものに、Linux の ext4 や XFS、Windows の NTFS がある。

i ノードの考え方
^^^^^^^^^^^^^^^^

Unix 系のファイルシステムでは、ファイルの管理情報を :term:`i ノード`\ に格納する。i ノードには、ファイルの大きさ、所有者、アクセス権、更新時刻、そしてデータが置かれたブロックの位置が記録されている。ここで重要なのは、i ノードにはファイルの\ **名前が含まれない**\ ことである。名前は、ディレクトリの中に「名前と i ノード番号の組」として記録されている。つまりディレクトリは、名前から i ノード番号への対応表を中身とする特別なファイルである。

この構造から、いくつかの性質が説明できる。1 つの i ノードを複数のディレクトリ項目から指せば、同じファイルに複数の名前を付けられる。これをハードリンクと呼ぶ。ファイルの名前を変える ``rename`` は、データを動かさずディレクトリ項目を書き換えるだけなので、大きなファイルでも一瞬で終わる。また、ファイルを削除するとディレクトリ項目が消えるが、そのファイルを開いているプロセスがあれば、i ノードとデータは閉じられるまで残る。ログファイルを削除してもディスクの空き容量が増えないときは、まだそのファイルを開いているプロセスがあることを疑うとよい。

.. _ch08-file-descriptor:

ファイル記述子と「すべてはファイル」
^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^

Unix 系の OS では、プロセスがファイルを ``open`` すると、カーネルは小さな非負の整数を返す。これを\ :term:`ファイル記述子`\ と呼ぶ。以後の ``read``、``write``、``close`` は、パス名ではなくこの番号を指定して行う。カーネルの中では、プロセスごとのファイル記述子の表が「開いているファイル」の情報（読み書きの現在位置やモード）を指し、それがさらに i ノードを指している。0 番、1 番、2 番は、それぞれ標準入力、標準出力、標準エラー出力として起動時から開かれている。Python では、ファイルオブジェクトの ``fileno()`` でファイル記述子を取り出せ、``os.read()`` や ``os.write()`` で直接システムコールを呼べる。

ファイル記述子は通常のファイルだけでなく、パイプ、ソケット、端末、デバイス（``/dev/null`` など）にも割り当てられ、どれも同じ ``read`` と ``write`` で読み書きできる。この設計は「すべてはファイル」と表現される。``cat`` のような単純なプログラムが、ファイルにもパイプにも端末にも同じように使えるのはこのためである。ファイル記述子は ``fork`` で子に複製され、``exec`` の後も引き継がれる。「:ref:`ch08-fork-exec`」で触れたシェルのリダイレクト ``> out.txt`` は、子プロセスの中で ``out.txt`` を開き、``dup2`` でそれを 1 番に付け替えてから ``exec`` する、という手順で実現される [Kerrisk]_。また、ソケットもファイル記述子であることは、次章の :ref:`I/O 多重化 <ch09-io-multiplexing>`\ で「多数のファイル記述子のうち、読み書きできるものを教えてもらう」という形で生きてくる。

1 つのプロセスが同時に開けるファイル記述子の数には上限がある。Linux の既定値は 1,024 であることが多く、``ulimit -n`` で確認や変更ができる。多数の接続を同時に受け付けるサーバでは、この上限に達して ``Too many open files`` のエラーになることがあるので、上限を引き上げるとともに、使い終わったファイルやソケットを確実に閉じる（Python では ``with`` 文を使う）ことが大切である。

.. note::

   Windows では、ファイルやプロセスなどのカーネルの資源を\ **ハンドル**\ と呼ばれる値で指す。考え方はファイル記述子に近いが、ソケットとファイルは別の API で扱われ、パイプとソケットとファイルを一様に扱う Unix ほどの統一性は無い。Python の ``fileno()`` は Windows でも使えるが、例えば ``select.select()`` は Windows ではソケットにしか使えない。

バッファリングと fsync
^^^^^^^^^^^^^^^^^^^^^^

プログラムがファイルに書き込んだデータは、すぐには補助記憶に届かない。書き込みは次の段階を経て進む。

.. list-table::
   :header-rows: 1
   :widths: 25 40 35

   * - 段階
     - データの置き場所
     - 次の段階に進める操作
   * - プログラム内のバッファ
     - Python のファイルオブジェクトなど、プロセスのメモリ
     - ``flush()``、``close()``
   * - OS のページキャッシュ
     - カーネルが管理する主記憶
     - ``os.fsync()``\ （または OS による定期的な書き出し）
   * - 補助記憶
     - SSD や HDD
     - ―

各段階のバッファは、小さな書き込みをまとめて、システムコールや装置へのアクセスの回数を減らすためにある。``write()`` や ``close()`` が成功しても、データはまだ OS のページキャッシュにあるだけかもしれない。この状態で電源が落ちたり OS が停止したりすると、データは失われる。プロセスが異常終了しただけなら、ページキャッシュに届いたデータは失われない。

確実に補助記憶へ書き込みたい場合は、``os.fsync()`` を呼ぶ。``fsync`` は、そのファイルのデータがページキャッシュから装置に書き込まれるまで戻らない。設定ファイルの保存のように、書き込み途中で障害が起きても古い内容か新しい内容のどちらかが必ず残ってほしい場合は、一時ファイルに書いて ``fsync`` し、``os.replace()`` で本来の名前に置き換えるのが定石である。

.. code-block:: python
   :linenos:

   import os

   def save_atomically(path: str, text: str) -> None:
       tmp = path + ".tmp"
       with open(tmp, "w", encoding="utf-8") as f:
           f.write(text)
           f.flush()             # Python のバッファから OS へ
           os.fsync(f.fileno())  # OS から補助記憶へ
       os.replace(tmp, path)     # 名前を置き換える

POSIX では、同じファイルシステム内での名前の置き換えは不可分に行われるので、読み手は古いファイルか新しいファイルのどちらかを必ず見る。なお、名前の置き換えはディレクトリの更新なので、置き換え自体を確実に永続化するには、Linux ではディレクトリも開いて ``fsync`` する必要がある。一方で ``fsync`` は装置への書き込みを待つため遅い。ログを 1 行書くたびに ``fsync`` すると、性能が大きく落ちる。データベースは、複数の更新をまとめて 1 回の ``fsync`` で永続化するなどの工夫で、安全性と性能を両立させている。詳しくは「:doc:`ch11_databases`」で扱う。

ジャーナリング
^^^^^^^^^^^^^^

ファイルシステムの 1 つの操作は、補助記憶上の複数の場所の更新からなる。例えばファイルの末尾にデータを 1 ブロック追加するには、データブロックの書き込み、空きブロックを管理する表（ビットマップ）の更新、i ノードの大きさとブロック位置の更新が必要である。これらの書き込みの途中で電源が落ちると、「ビットマップでは使用中なのにどのファイルにも属さないブロック」や「i ノードが、まだ中身の書かれていないブロックを指している」といった不整合が残る。この問題を\ **クラッシュ整合性**\ の問題と呼ぶ。古いファイルシステムは、起動時に ``fsck`` でディスク全体を走査して不整合を修復していたが、ディスクが大きくなると何時間もかかる。

現在の多くのファイルシステム（ext4、XFS、NTFS など）は\ :term:`ジャーナリング`\ でこの問題を解決している。更新を本来の場所に書く前に、これから行う一連の更新をジャーナル（ログ）と呼ばれる専用の領域にまとめて書き、最後に「この更新は完結した」という印（コミット記録）を書く。その後で、本来の場所に書き込む。クラッシュした後は、ジャーナルを調べ、コミット記録まで書かれた更新はやり直し、書かれていない更新は捨てる。こうすれば、一連の更新は「全部行われた」か「まったく行われなかった」かのどちらかになり、確認はジャーナルの範囲だけで済む [OSTEP]_。これは「:doc:`ch11_databases`」で扱うログ先行書き込みと同じ考え方であり、ファイルシステムはメタデータの更新をトランザクションとして扱っていると見なせる。

すべてのデータをジャーナルに書くと、データを 2 回書くことになり遅い。そこで多くのファイルシステムは、i ノードやビットマップなどのメタデータだけをジャーナルに書く\ **メタデータジャーナリング**\ を既定にしている。ext4 の既定の動作では、データブロックを先に本来の場所に書いてから、それを指すメタデータをジャーナルにコミットする。この順序によって、i ノードがゴミの入ったブロックを指すことは避けられる。ただし、ジャーナリングが守るのはファイルシステムの構造の整合性であって、アプリケーションのデータが最新であることまでは保証しない。前の小節で述べた ``fsync`` と ``os.replace()`` の手順は、ジャーナリングのあるファイルシステムでも必要である。

もう 1 つの方式が\ **コピーオンライト型**\ のファイルシステムである。ZFS、Btrfs、macOS の APFS などは、既存のブロックを上書きせず、変更した内容を常に空いている別の場所に書き、最後にファイルシステムの根を指すポインタを 1 か所だけ不可分に切り替える。切り替えの前にクラッシュすれば古い状態が、後なら新しい状態が見えるので、ジャーナルを使わずに整合性を保てる。古いブロックをすぐに解放せずに残しておけば、ある時点の状態をほとんど費用をかけずに保存する\ **スナップショット**\ も実現できる。

仮想化とコンテナ
----------------

ここまでに見たプロセスの分離は、同じ OS の上で動くプログラム同士を分けるものだった。この節では、さらに進んで、1 台の物理的な計算機の上で複数の OS を丸ごと動かす仮想化と、OS のカーネルを共有しながら実行環境を分けるコンテナを紹介する。どちらも、クラウドや現在のソフトウェアの配備を支える基盤技術である。なお、「:doc:`ch07_programming_languages`」で扱った Java 仮想マシンのような言語処理系の仮想マシンとは別のものである。

仮想化の目的とハイパーバイザ
^^^^^^^^^^^^^^^^^^^^^^^^^^^^

\ :term:`仮想化`\ は、ハードウェアを模した\ **仮想マシン**\ （VM: Virtual Machine）をソフトウェアで作り、その上で OS（ゲスト OS）をそのまま動かす技術である。主な目的は次のとおりである。

* 集約: 負荷の低い多数のサーバを 1 台の物理マシンにまとめ、ハードウェアと電力を節約する。
* 分離: 1 つの VM の障害や侵害が、同じ物理マシン上の他の VM に及ばないようにする。
* 柔軟な運用: VM の状態をファイルとして保存（スナップショット）したり、動かしたまま別の物理マシンに移したり（ライブマイグレーション）できる。
* 互換性: Windows の上で Linux を動かすなど、異なる OS を同時に使える。

VM を作り出して管理するソフトウェアを\ :term:`ハイパーバイザ`\ （仮想マシンモニタ、VMM とも呼ぶ）と呼ぶ。ハイパーバイザは、OS がプロセスに CPU やメモリを分け与えるのと同じように、VM に CPU、メモリ、入出力装置を分け与える。ハイパーバイザは、置かれる位置によって 2 種類に分けられる [MOS]_。

.. list-table::
   :header-rows: 1
   :widths: 20 40 40

   * - 種類
     - 構成
     - 例と用途
   * - タイプ 1（ベアメタル型）
     - ハードウェアの上で直接動き、ハイパーバイザ自身が OS の役割を担う
     - Xen、VMware ESXi、Microsoft Hyper-V、Linux の KVM。データセンタやクラウドのサーバ
   * - タイプ 2（ホスト型）
     - 通常の OS（ホスト OS）の上で、1 つのアプリケーションとして動く
     - VirtualBox、VMware Workstation。開発者の手元での検証

KVM は Linux カーネルのモジュールとして動き、Linux 自体をハイパーバイザにするので、どちらに分類するかは見方によるが、ハードウェアを直接制御する点でタイプ 1 に含めることが多い。

仮想化の条件とハードウェア支援
^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^

ゲスト OS は、自分がカーネルモードで動いていると思っている。しかし、本当にカーネルモードで動かすと、ゲスト OS がハードウェアを直接操作し、ハイパーバイザや他の VM を壊してしまう。そこで、ゲスト OS はユーザモード（あるいはそれに準じる低い特権）で動かし、ゲストが特権命令を実行しようとしたら CPU の例外でハイパーバイザに制御を移し、ハイパーバイザがその命令の効果を模倣する。この方式を\ **トラップとエミュレート**\ と呼ぶ。

Popek と Goldberg は 1974 年の論文で、効率のよい仮想マシンモニタが満たすべき性質として、VM 上のプログラムが実機と同じように振る舞うこと（等価性）、VM が自分に割り当てられた資源しか使えないこと（資源の管理）、大部分の命令がハイパーバイザを介さず直接実行されること（効率性）の 3 つを挙げた。そして、システムの状態を読み書きする「センシティブ命令」がすべて、ユーザモードで実行すると例外を起こす特権命令に含まれていれば、トラップとエミュレートでそのような仮想マシンモニタを作れることを示した [PopekGoldberg1974]_。

かつての x86 はこの条件を満たしていなかった。ユーザモードで実行しても例外を起こさず、黙って異なる動作をするセンシティブ命令がいくつかあったからである（例えば ``POPF`` 命令は、ユーザモードでは割り込みの許可フラグの変更を例外を起こさずに無視する）。そのため、初期の x86 の仮想化では、ゲスト OS の問題のある命令を実行前に安全な命令列に書き換える\ **バイナリ変換**\ （VMware）や、ゲスト OS 自体を書き換えて、ハイパーバイザを明示的に呼び出させる\ **準仮想化**\ （Xen）といった工夫が使われた。

2005〜2006 年に、Intel は VT-x、AMD は AMD-V という\ **ハードウェア支援**\ の仕組みを CPU に加えた。これらは、ハイパーバイザ用とゲスト用の実行モードを新たに設け、ゲストがセンシティブな操作をすると CPU が自動的にハイパーバイザに制御を移す。これにより、ゲスト OS を書き換えずにそのまま動かす\ **完全仮想化**\ が、高い効率で実現できるようになった。さらに、ゲストの物理アドレスからホストの物理アドレスへの変換をハードウェアが行う拡張ページテーブル（Intel の EPT、AMD の NPT）により、メモリの仮想化のコストも下がった。現在のクラウドの VM は、このハードウェア支援の上に成り立っている。なお、ディスクやネットワークの入出力については、ゲストに専用の準仮想化ドライバ（virtio など）を入れて高速化するのが一般的である。

コンテナ
^^^^^^^^

\ :term:`コンテナ`\ は、OS のカーネルを共有したまま、プロセスの集まりに独立した実行環境を見せる技術である。VM がハードウェアを仮想化するのに対し、コンテナは OS を仮想化すると言える。コンテナの中のプロセスは、ホストから見れば普通のプロセスにすぎないが、カーネルの次の 2 つの機能によって、他のプロセスから隔てられている（以下は Linux の場合）。

* 名前空間（namespaces）: プロセスから見える資源の範囲を分ける。PID 名前空間ではコンテナの中だけのプロセス ID が振られ（コンテナ内の最初のプロセスは ID 1 になる）、マウント名前空間では独自のファイルシステムの木が、ネットワーク名前空間では独自のネットワークインタフェースとポート番号の空間が見える。ホスト名、ユーザ ID、IPC についての名前空間もある。
* cgroups（control groups）: プロセスの集まりが使える CPU 時間、メモリ、入出力の帯域の上限を決め、使用量を計測する。あるコンテナがメモリを使い尽くしても、他のコンテナに影響しないようにする。

つまり、名前空間は「何が見えるか」を、cgroups は「どれだけ使えるか」を制限する。カーネルを共有しているので、コンテナは OS の起動を伴わず、プロセスの起動と同じくらい速く（通常 1 秒未満で）始まり、主記憶の消費も小さい。その反面、すべてのコンテナが 1 つのカーネルに依存するので、カーネルの脆弱性があれば分離が破られるおそれがあり、VM ほど強い分離は得られない。また、ホストと異なるカーネルは動かせない。Windows や macOS で Linux のコンテナを動かすツールは、実際には裏で Linux の VM を動かしている。

コンテナの中身は\ **イメージ**\ として配布される。イメージは、アプリケーションとそれが必要とするライブラリ、設定ファイルなどを含むファイルシステムの内容であり、読み取り専用の\ **レイヤ**\ を積み重ねた構造になっている。例えば「OS の基本的なファイル」のレイヤの上に「Python の処理系」のレイヤ、その上に「アプリケーションのコード」のレイヤを重ねる。共通のレイヤは複数のイメージで共有でき、更新したレイヤだけを配布すればよい。コンテナを起動すると、イメージの上に書き込み可能なレイヤが 1 枚加わり、ファイルの変更はコピーオンライトでそのレイヤに記録される（Linux では OverlayFS などの重ね合わせのファイルシステムが使われる）。イメージの形式は OCI（Open Container Initiative）という仕様として標準化されており、Docker や Podman などの複数のツールで共通に使える。多数のコンテナを複数のマシンに配置して管理するには、Kubernetes のようなオーケストレーションのシステムを使う。

VM とコンテナの比較
^^^^^^^^^^^^^^^^^^^

VM とコンテナの違いを次の表にまとめる。

.. list-table::
   :header-rows: 1
   :widths: 20 40 40

   * - 観点
     - 仮想マシン（VM）
     - コンテナ
   * - 仮想化する対象
     - ハードウェア
     - OS（カーネルの提供する資源の見え方）
   * - カーネル
     - VM ごとに独自のゲスト OS のカーネルを持つ
     - ホストのカーネルを共有する
   * - 動かせる OS
     - ホストと異なる OS も動かせる
     - ホストと同じカーネルの上で動くものに限られる
   * - 起動時間
     - OS の起動を伴うので数秒〜数十秒
     - プロセスの起動と同程度で、通常 1 秒未満
   * - 大きさと集約度
     - OS 全体を含むので数 GB 程度になり、1 台に載せられる数は少ない
     - アプリケーションと依存物だけなので数十 MB〜数百 MB 程度で、1 台に多数載せられる
   * - 分離の強さ
     - 強い。ハードウェア支援による境界で隔てられる
     - VM より弱い。カーネルの脆弱性が全体に影響し得る
   * - 主な用途
     - クラウドの計算資源の提供、異なる OS の同居、強い分離が必要な環境
     - アプリケーションの配布と配備、開発環境と本番環境の差の解消、マイクロサービス

両者は対立するものではなく、組み合わせて使われることが多い。クラウドでは、利用者ごとに VM で強く分離し、その VM の中で多数のコンテナを動かすのが一般的な構成である。さらに、VM の分離の強さとコンテナの軽さを両立させるため、コンテナごとに小さな VM を割り当てる軽量 VM の技術も使われている。

まとめ
------

* OS は、CPU、メモリ、補助記憶、ネットワークをプロセス、アドレス空間、ファイル、ソケットとして抽象化し、資源を管理・保護する。
* CPU のユーザモードとカーネルモードによって、アプリケーションはシステムコールを通じてのみカーネルの機能を使う。割り込みによって、カーネルは外部の事象に応じて制御を取り戻す。
* プロセスは互いに分離されたアドレス空間を持ち、スレッドは同じプロセス内でメモリを共有する。Unix 系ではプロセスを ``fork`` で複製し ``exec`` でプログラムを置き換えて生成し、カーネルはシグナルでプロセスに事象を知らせる。
* スケジューリングの方式によって平均待ち時間や応答時間が変わる。SJF は平均待ち時間を短くし、ラウンドロビンは応答時間を短く保つ。
* 仮想メモリは、ページテーブルによる仮想アドレスから物理アドレスへの変換で、プロセスの分離とデマンドページングを実現する。TLB は変換を高速化し、主記憶が不足するとスワップが起きる。追い出すページは、OPT を理想として、LRU やその近似であるクロック法で選ぶ。FIFO では Belady の異常が起こり得る。
* ファイルシステムは i ノードとディレクトリで名前とデータを結び付け、プロセスはファイル記述子を通じてファイル、パイプ、ソケットを同じように扱う。書き込みを確実に永続化するには ``fsync`` が必要であり、クラッシュ時の構造の整合性はジャーナリングやコピーオンライトで保たれる。
* 仮想化はハイパーバイザがハードウェアを仮想化して複数の OS を動かし、コンテナは名前空間と cgroups によってカーネルを共有したまま実行環境を分ける。VM は分離が強く、コンテナは軽く速い。
