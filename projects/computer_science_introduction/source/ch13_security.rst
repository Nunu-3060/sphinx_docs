情報セキュリティと暗号
======================

ネットワークにつながったシステムは、常に悪意のある第三者からの攻撃にさらされている。この章では、情報を守るための基本的な考え方と、その道具となる暗号技術を学ぶ。まず情報セキュリティの目標と、脅威・脆弱性という基本的な概念を整理する。次に、共通鍵暗号と公開鍵暗号、ハッシュ関数、メッセージ認証コード、デジタル署名と公開鍵証明書という暗号技術の部品を順に説明し、それらを組み合わせた TLS の役割を概観する。最後に、鍵やトークンの生成に欠かせない暗号学的に安全な乱数を、シミュレーションなどに使う擬似乱数と対比して説明する。これらの道具を使ってパスワード、認証、セッションを安全に扱う方法と、アプリケーションの代表的な脆弱性は、次の「:doc:`ch14_application_security`」で扱う。

暗号技術では、仕組みを理解することと、安全に実装して使うことはまったく別の問題である。この章のサンプルコードは仕組みを理解するためのものであり、実際のシステムでは十分に検証された暗号ライブラリを使わなければならない。全体像については [Anderson]_ を参照してほしい。

情報セキュリティの 3 要素
-------------------------

情報セキュリティの目標は、次の 3 つの性質を保つことであるとされる。英語の頭文字をとって CIA と呼ばれることもある。

* :term:`機密性`\ （Confidentiality）: 許可された者だけが情報にアクセスできること。通信の盗聴や、データベースからの個人情報の漏えいは機密性の侵害である。
* :term:`完全性`\ （Integrity）: 情報が正確であり、許可なく改ざんされていないこと。送金額の書き換えや、Web ページの改ざんは完全性の侵害である。
* :term:`可用性`\ （Availability）: 許可された者が、必要なときに情報やサービスを利用できること。大量の通信を送りつけてサービスを停止させる DoS 攻撃（Denial of Service attack）は、可用性の侵害である。

これらに加えて、情報の発信者が本人であることを確認できる真正性、操作を行った者を後から追跡できる責任追跡性、行った操作を後から否定できないようにする否認防止なども、セキュリティの目標として挙げられる。

3 つの要素は互いに対立することがある。例えば、データを厳重に暗号化して鍵を 1 人だけが管理すれば機密性は高まるが、その人が不在のときにはデータを使えず可用性が下がる。セキュリティ対策は、守るべきものと許容できるコストに応じて、これらの釣り合いをとる作業である。

脅威と脆弱性
------------

セキュリティを議論するときは、次の用語を区別する。

* **資産**: 守るべき対象。顧客情報、ソースコード、サービスの稼働そのものなど。
* **脅威**: 資産に損害を与えうる事象や行為。外部からの攻撃、内部者による持ち出し、操作ミス、災害など。
* :term:`脆弱性`\ : 脅威が実際に損害をもたらすことを可能にする弱点。プログラムの不具合、設定の誤り、推測しやすいパスワード、運用手順の不備など。

脅威があっても脆弱性が無ければ損害は生じにくく、脆弱性があっても脅威が無ければ問題は顕在化しにくい。リスクは、脅威が脆弱性を突いて損害が生じる可能性と、その損害の大きさの組み合わせとして評価する。ソフトウェア開発者が最も直接的に関わるのは、脆弱性を作り込まないことである。

また、攻撃者は防御の最も弱いところを狙う。強力な暗号を使っていても、鍵がソースコードに書かれて公開リポジトリに置かれていれば意味がない。複数の防御を重ねて、1 つが破られても被害を食い止める多層防御や、利用者やプログラムに必要最小限の権限だけを与える最小権限の原則が、設計上の基本的な考え方である。

暗号の基礎
----------

暗号の用語
^^^^^^^^^^

暗号化の前の読めるデータを\ **平文**\ （plaintext）、暗号化した後のデータを\ **暗号文**\ （ciphertext）と呼ぶ。平文を暗号文に変換することを\ **暗号化**\ （encryption）、暗号文を平文に戻すことを\ **復号**\ （decryption）と呼ぶ。暗号化と復号には\ **鍵**\ （key）と呼ばれる秘密の値を使う。

現代の暗号は、暗号化の手順（アルゴリズム）を公開し、鍵だけを秘密にしても安全であるように設計される。この考え方をケルクホフスの原理と呼ぶ。手順を秘密にすることで安全性を保とうとする方式は、手順が漏れた時点で破られ、公開の場で専門家に検証されることもないため、信頼できない。独自の暗号方式を考案して使うべきではない理由の 1 つがここにある。

共通鍵暗号と鍵配送問題
^^^^^^^^^^^^^^^^^^^^^^

暗号化と復号に同じ鍵を使う方式を\ :term:`共通鍵暗号`\ （対称鍵暗号）と呼ぶ。現在最も広く使われているのは AES（Advanced Encryption Standard）であり、128 ビットのブロックを単位に、128、192、256 ビットのいずれかの長さの鍵で暗号化する。共通鍵暗号は高速であり、多くの CPU は AES 専用の命令を備えている。

ブロック暗号で長いデータを暗号化するには、ブロックの処理方法を決める暗号利用モードを組み合わせる。各ブロックを独立に暗号化する ECB モードは、同じ平文のブロックが同じ暗号文のブロックになり、データの模様が透けて見えるため使ってはならない。現在は、暗号化と同時に改ざんの検出も行う認証付き暗号（AEAD: Authenticated Encryption with Associated Data）の AES-GCM や ChaCha20-Poly1305 を使うのが一般的である。

共通鍵暗号の問題は、通信相手と同じ鍵をあらかじめ安全に共有しておかなければならないことである。暗号化されていない通信路で鍵を送れば盗聴されてしまう。これを\ :term:`鍵配送問題`\ と呼ぶ。さらに、:math:`n` 人が互いに秘密の通信をするには、2 人の組ごとに別の鍵が必要なので、鍵の数は :math:`n(n-1)/2` になる。100 人なら 4950 個の鍵を安全に配り、管理しなければならない。

公開鍵暗号
^^^^^^^^^^

:term:`公開鍵暗号`\ （非対称鍵暗号）は、暗号化と復号に異なる鍵を使うことで鍵配送問題を解決する。各利用者は、数学的に対応する\ **公開鍵**\ と\ **秘密鍵**\ の組を作る。公開鍵は誰に知られてもよく、秘密鍵は本人だけが持つ。送信者は受信者の公開鍵で暗号化し、受信者は自分の秘密鍵で復号する。公開鍵から秘密鍵を求めることは計算量的に困難なので、公開鍵を誰に配ってもかまわない。:math:`n` 人の場合でも、必要な鍵の組は :math:`n` 組で済む。

代表的な公開鍵暗号である RSA は、大きな合成数の素因数分解が困難であることを安全性の根拠とする。鍵の生成、暗号化、復号は次のとおりである（:math:`\bmod` は割った余りを表す）。

1. 大きな素数 :math:`p` と :math:`q` を選び、:math:`n = pq` とする。
2. :math:`\varphi(n) = (p-1)(q-1)` を計算する。:math:`\varphi` はオイラーの関数であり、:math:`\varphi(n)` は :math:`1` 以上 :math:`n` 以下で :math:`n` と互いに素な整数の個数である。
3. :math:`\varphi(n)` と互いに素な整数 :math:`e` を選ぶ（実用上は :math:`e = 65537` がよく使われる）。
4. :math:`ed \equiv 1 \pmod{\varphi(n)}` を満たす :math:`d` を求める。つまり :math:`d` は :math:`\varphi(n)` を法とする :math:`e` の逆元である。
5. 公開鍵は :math:`(n, e)`、秘密鍵は :math:`d` である（:math:`p`、:math:`q`、:math:`\varphi(n)` も秘密にする）。

平文 :math:`m`\ （:math:`0 \le m < n` の整数）の暗号化と、暗号文 :math:`c` の復号は次の式で行う。

.. math::

   c = m^{e} \bmod n, \qquad m = c^{d} \bmod n

:math:`ed = 1 + k\varphi(n)`\ （:math:`k` は整数）なので、オイラーの定理（と中国剰余定理）から :math:`c^{d} = m^{ed} = m^{1 + k\varphi(n)} \equiv m \pmod{n}` が成り立ち、復号で元の平文に戻る。:math:`n` を素因数分解できれば :math:`\varphi(n)` が分かり、:math:`d` を計算できてしまう。そのため、実用の :math:`n` は 2048 ビット以上（10 進数で 600 桁以上）にする。なお、:math:`m^{e} \bmod n` は、指数を 2 進数で表して 2 乗と乗算を繰り返すことで、指数のビット数に比例する回数の乗算で計算できる。

ハイブリッド暗号
^^^^^^^^^^^^^^^^

公開鍵暗号は鍵配送問題を解決するが、共通鍵暗号に比べて数百倍から数千倍遅く、大きなデータの暗号化には向かない。そこで実際のシステムでは、両者を組み合わせた\ :term:`ハイブリッド暗号`\ を使う。

1. 送信者は、ランダムな共通鍵（セッション鍵）を生成する。
2. データ本体をセッション鍵で暗号化する（共通鍵暗号なので速い）。
3. セッション鍵を受信者の公開鍵で暗号化する（短いので遅くても問題ない）。
4. 受信者は、自分の秘密鍵でセッション鍵を復号し、そのセッション鍵でデータ本体を復号する。

電子メールの暗号化などはこの形である。TLS では、公開鍵で鍵を暗号化して送る代わりに、後述する鍵交換によって双方が同じセッション鍵を導出する。いずれも、公開鍵暗号の技術で共通鍵を共有し、データ本体は共通鍵暗号で保護するという考え方は同じである。

ハッシュ関数
------------

暗号学的ハッシュ関数の性質
^^^^^^^^^^^^^^^^^^^^^^^^^^

ハッシュ関数は、任意の長さのデータから固定長の値（ハッシュ値、ダイジェスト）を計算する関数である。「:doc:`ch04_data_structures`」のハッシュ表で使うハッシュ関数は値が散らばれば十分だが、セキュリティに使う\ :term:`暗号学的ハッシュ関数`\ は、ハッシュ関数 :math:`H` について次の性質を満たす必要がある。

* **原像計算困難性**\ （一方向性）: ハッシュ値 :math:`h` が与えられたとき、:math:`H(x) = h` となる :math:`x` を見つけることが計算量的に困難である。
* **第 2 原像計算困難性**: 入力 :math:`x` が与えられたとき、:math:`H(x') = H(x)` となる別の入力 :math:`x' \ne x` を見つけることが困難である。
* **衝突困難性**: :math:`H(x) = H(x')` となる異なる入力の組 :math:`x, x'` を、どのようなものでもよいから 1 組見つけることが困難である。

ハッシュ値の長さは固定なので、異なる入力が同じハッシュ値になる衝突は必ず存在する。性質が求めるのは、それを\ **見つけること**\ が現実的な計算量では不可能なことである。出力が :math:`b` ビットの理想的なハッシュ関数では、原像の発見に約 :math:`2^{b}` 回、衝突の発見には誕生日のパラドックスにより約 :math:`2^{b/2}` 回の計算が必要になる。

また、入力が 1 ビットでも変われば、出力のビットのおよそ半分が予測できない形で変わることが望ましい。この性質を\ **雪崩効果**\ と呼ぶ。

SHA-256 と、MD5・SHA-1 を使わない理由
^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^

現在広く使われているのは、SHA-2 系列の SHA-256 である [FIPS180-4]_。出力は 256 ビット（32 バイト）で、衝突の発見には約 :math:`2^{128}` 回の計算が必要とされる。

古いハッシュ関数である MD5（出力 128 ビット）と SHA-1（出力 160 ビット）は、理論上の値よりはるかに少ない計算量で衝突を見つける攻撃法が発見されている。MD5 の衝突は 2004 年に示され、現在では一般的な PC で短時間に作れる。SHA-1 も 2017 年に実際の衝突例が公表された。衝突を作れると、内容の異なる 2 つの文書に同じハッシュ値を持たせ、一方に付けたデジタル署名を他方に流用するといった攻撃が可能になる。そのため、セキュリティ目的で MD5 や SHA-1 を使ってはならない。新しく設計するなら SHA-256 以上、または SHA-3 系列を使う。

.. note::

   ハッシュ化は暗号化ではない。暗号化は鍵を使えば復号して元に戻せるが、暗号学的ハッシュ関数には鍵が無く、ハッシュ値から元のデータに戻す手順も存在しない。「パスワードを SHA-256 で暗号化する」のような表現は誤りであり、後で述べるように、パスワードの保存には単純なハッシュ関数も不十分である。

メッセージ認証コード
--------------------

ハッシュ値をデータと一緒に送れば、通信の途中で偶然に起きた誤りは検出できる。しかし、攻撃者はデータを改ざんしたうえでハッシュ値も計算し直せるので、意図的な改ざんは検出できない。改ざんを検出するには、正しい送信者と受信者だけが知る秘密を使う必要がある。

:term:`メッセージ認証コード`\ （MAC: Message Authentication Code）は、共通の秘密鍵 :math:`K` とメッセージ :math:`m` から計算する短い値（タグ）である。受信者は同じ鍵でタグを計算し直し、受け取ったタグと一致すれば、メッセージが鍵を知る者によって作られ、改ざんされていないと判断できる。つまり MAC は完全性と、送信元の真正性を保証する。

ハッシュ関数を使った MAC の標準的な構成が HMAC である。単純に :math:`H(K \| m)`\ （:math:`\|` は連結）を計算する方法は、SHA-256 のような構造のハッシュ関数では、タグを知っていれば鍵を知らなくても :math:`m` の後ろにデータを追加したメッセージの正しいタグを計算できてしまう（伸長攻撃）。HMAC は、鍵 :math:`K`\ （ハッシュ関数のブロック長に合わせて調整したもの）から作った 2 つの値 :math:`K \oplus \mathit{ipad}` と :math:`K \oplus \mathit{opad}`\ （:math:`\oplus` は排他的論理和、:math:`\mathit{ipad}` と :math:`\mathit{opad}` は定数）を使って、ハッシュ関数を 2 回適用する。

.. math::

   \mathrm{HMAC}(K, m) = H\bigl((K \oplus \mathit{opad}) \,\|\, H((K \oplus \mathit{ipad}) \,\|\, m)\bigr)

上のサンプルの 26〜28 行目では、``hmac.new`` で HMAC-SHA256 のタグを計算している。実行結果の 8〜10 行目のように、正しい鍵とメッセージなら検証に成功し、メッセージを 1 文字変えても、鍵が異なっても検証に失敗する。

33 行目では、タグの比較に ``==`` ではなく ``hmac.compare_digest`` を使っている。``==`` によるバイト列の比較は、最初に異なるバイトが見つかった時点で終わるため、比較にかかる時間から何バイト目まで一致したかが漏れうる。攻撃者はこれを手がかりに、正しいタグを先頭から 1 バイトずつ推測できる（タイミング攻撃）。``compare_digest`` は、内容にかかわらず一定の時間で比較する。

デジタル署名と公開鍵証明書
--------------------------

デジタル署名
^^^^^^^^^^^^

MAC は送信者と受信者が同じ鍵を持つので、受信者もタグを作れる。そのため、第三者に対して「このメッセージは確かに送信者が作った」と証明することはできない。\ :term:`デジタル署名`\ は、公開鍵暗号の技術を使ってこの問題を解決する。

署名者は、メッセージのハッシュ値に対して自分の秘密鍵で署名を計算する。検証者は、署名者の公開鍵を使って、署名がそのメッセージに対するものかを確かめる。秘密鍵を持つのは署名者だけなので、正しい署名を作れるのは署名者だけであり、署名者は後から署名したことを否定できない（否認防止）。メッセージ全体ではなくハッシュ値に署名するのは、公開鍵暗号の計算が遅いためであり、ハッシュ関数の衝突困難性が署名の安全性の前提になる。

RSA による署名は、暗号化と逆に秘密鍵 :math:`d` で :math:`s = h^{d} \bmod n` を計算し（:math:`h` はハッシュ値）、検証では公開鍵 :math:`e` で :math:`s^{e} \bmod n = h` かを確かめる。前のサンプルでは簡単のため :math:`m = 65` に直接署名しており、:math:`65^{2753} \bmod 3233 = 588` が署名になる。:math:`588^{17} \bmod 3233 = 65` なので検証に成功し（実行結果の 7 行目）、66 に対しては失敗する（8 行目）。署名には RSA のほか、楕円曲線を使う ECDSA や Ed25519 が広く使われている。

MAC とデジタル署名の違いを次の表にまとめる。

.. list-table:: MAC とデジタル署名の比較
   :header-rows: 1
   :widths: 25 35 40

   * - 項目
     - MAC
     - デジタル署名
   * - 使う鍵
     - 送信者と受信者が共有する秘密鍵
     - 作成は署名者の秘密鍵、検証は公開鍵
   * - 検証できる者
     - 鍵を共有する者だけ
     - 公開鍵を持つ誰でも
   * - 否認防止
     - できない（受信者もタグを作れる）
     - できる
   * - 計算速度
     - 速い
     - 遅い

公開鍵証明書と認証局
^^^^^^^^^^^^^^^^^^^^

公開鍵暗号にも弱点がある。受け取った公開鍵が本当に通信したい相手のものかを確かめられないことである。攻撃者が通信の途中に割り込み、相手の公開鍵を自分の公開鍵にすり替えれば、攻撃者は暗号文を復号し、内容を読んだうえで本物の相手に転送できる。このような攻撃を中間者攻撃（man-in-the-middle attack）と呼ぶ。

この問題を解決するのが\ :term:`公開鍵証明書`\ である。公開鍵証明書は、「この公開鍵はこの主体（例えばドメイン名 ``example.com``）のものである」という内容に、信頼できる第三者がデジタル署名したデータである。証明書には、主体の名前、公開鍵、有効期間、発行者などが含まれ、形式は X.509 という規格で定められている。証明書を発行する第三者を\ :term:`認証局`\ （CA: Certificate Authority）と呼ぶ。

認証局の公開鍵自体も、上位の認証局が発行した証明書で保証される。この連鎖をたどった先には、自分自身で署名したルート認証局の証明書がある。ルート証明書は OS やブラウザにあらかじめ組み込まれており、利用者はそれを信頼の起点として、サーバの証明書から順に署名を検証する。この仕組み全体を公開鍵基盤（PKI: Public Key Infrastructure）と呼ぶ。秘密鍵が漏えいした場合などに備えて、有効期間内でも証明書を失効させる仕組みもある。

TLS の役割
----------

「:doc:`ch10_networks`」で学んだ HTTPS は、HTTP の通信を :term:`TLS`\ （Transport Layer Security）で保護したものである [RFC8446]_。TLS は TCP などの信頼性のある通信路の上で動作し、アプリケーションに対して次の 3 つを提供する。

* **機密性**: 通信内容を暗号化し、盗聴されても読めないようにする。
* **完全性**: 通信内容の改ざんを検出する。
* **認証**: 証明書によって、接続先のサーバが本物であることを確認する（必要ならクライアントも認証する）。

TLS 1.3 の接続開始時の手順（ハンドシェイク）の概要は次のとおりである。

1. クライアントは、対応する暗号方式の一覧と、鍵交換のための一時的な公開値を送る（ClientHello）。
2. サーバは、使う暗号方式と自分の一時的な公開値を返す（ServerHello）。双方は、相手の公開値と自分の秘密の値から、楕円曲線ディフィー・ヘルマン鍵交換（ECDHE）によって同じ共通の秘密を計算し、そこからセッション鍵を導出する。この値は通信路を流れないので、盗聴者には分からない。
3. サーバは、自分の証明書と、ハンドシェイクの内容に対する自分の秘密鍵による署名を送る。クライアントは、証明書の連鎖を検証し、さらに署名を検証して、サーバが証明書に対応する秘密鍵を持つ（つまり本物である）ことを確認する。また、証明書の主体が接続しようとしたドメイン名と一致することも確認する。
4. 双方がハンドシェイク全体に対する MAC を交換して改ざんが無かったことを確認し、以後のデータを、セッション鍵を使った認証付き暗号（AES-GCM など）で保護する。

ここまでに説明した部品がすべて使われていることが分かる。鍵交換と署名には公開鍵暗号の技術、証明書には PKI、データの保護には共通鍵暗号と MAC の機能を持つ認証付き暗号、鍵の導出には HMAC が使われる。セッション鍵は接続ごとに一時的な値から作られて保存されないので、後でサーバの秘密鍵が漏えいしても、過去の通信は復号できない。この性質を前方秘匿性（forward secrecy）と呼ぶ。

.. note::

   TLS が保護するのは通信路の上のデータだけである。サーバに保存されたデータや、サーバ自体の脆弱性は TLS では守れない。また、HTTPS であることは「接続先が証明書に書かれたドメインである」ことを示すだけで、そのサイトが信頼できることを保証するものではない。

.. _ch13-random:

擬似乱数と暗号学的乱数
----------------------

ここまでに登場した共通鍵、TLS のセッション鍵や鍵交換の秘密の値、後で扱うパスワードのソルトやセッション ID は、どれも攻撃者に予測できない乱数でなければならない。どれほど強い暗号を使っても、鍵が予測できれば意味がない。ここでは、プログラムで使う乱数の 2 つの種類を区別する。

擬似乱数生成器
^^^^^^^^^^^^^^

コンピュータは決められた手順どおりに動くので、計算だけで本当の意味の乱数を作ることはできない。\ :term:`擬似乱数生成器`\ （PRNG: Pseudo-Random Number Generator）は、内部に状態を持ち、状態を一定の規則で更新しながら、乱数のように見える数の列を出力するアルゴリズムである。状態の初期値を決める値を\ :term:`シード`\ と呼ぶ。手順が決まっているので、同じシードからは必ず同じ列が得られる。この再現性は、シミュレーションや試験で結果を再現したいときに便利である。例えば第 11 章のサンプル ``ch11_index.py`` は、シードを固定して毎回同じデータを生成している。

Python の ``random`` モジュールが使うのは、メルセンヌ・ツイスタ（MT19937）と呼ばれる擬似乱数生成器である。周期が :math:`2^{19937} - 1` と非常に長く、統計的な偏りが小さく、高速なので、シミュレーションなどの用途には優れている。内部状態は 32 ビットの値 624 個からなり、出力は状態の値に可逆な変換（ビットのシフトと排他的論理和）を施したものである。

しかし、メルセンヌ・ツイスタは予測されないことを目的に設計されていない。出力の変換は逆にたどれるので、連続する 624 個の 32 ビットの出力を観測すれば内部状態をそのまま復元でき、以後の出力をすべて予測できる。シードを OS から得た値で初期化しても、この性質は変わらない。

暗号学的に安全な乱数
^^^^^^^^^^^^^^^^^^^^

セキュリティの用途に使う乱数には、それまでの出力をいくら観測しても、次の出力を当て推量より高い確率で予測できないことが求められる。この性質を満たす生成器を\ :term:`暗号学的に安全な擬似乱数生成器`\ （CSPRNG: Cryptographically Secure Pseudo-Random Number Generator）と呼ぶ。内部では、ハッシュ関数や共通鍵暗号のような、出力から内部の値を逆算できない部品を使う。さらに、状態がいつか漏れた場合に備えて、過去の出力を復元できないことも求められる。

CSPRNG のシードは予測できない値でなければならない。OS は、割り込みの発生時刻のゆらぎや、CPU が備える乱数生成回路（ハードウェア乱数生成器）などから予測できない値（エントロピー）を集め、それをもとに CSPRNG を動かして、プログラムに乱数を提供する。Linux の ``getrandom`` システムコールや ``/dev/urandom``、Windows の ``BCryptGenRandom`` がこれに当たる。Python では、次の方法で OS の乱数源を使える。

* ``os.urandom(n)``: OS の乱数源から :math:`n` バイトのバイト列を得る。次章の ``ch14_password.py`` のソルトの生成に使っている。
* ``secrets`` モジュール: ``os.urandom`` と同じ乱数源を使い、トークンの生成に便利な関数をまとめたものである [PythonDocs]_。``token_bytes(n)`` はバイト列、``token_hex(n)`` は :math:`n` バイトを 16 進数の文字列、``token_urlsafe(n)`` は :math:`n` バイトを Base64URL の文字列にして返す。``randbelow(k)`` は :math:`0` 以上 :math:`k` 未満の整数を、``choice(seq)`` は列の要素を 1 つ選んで返す。
* ``random.SystemRandom``: ``random`` モジュールと同じ使い方で、OS の乱数源を使うクラスである。シードを指定しても無視され、再現性は無い。

``random`` と ``secrets`` の違いを次の表にまとめる。

.. list-table:: random モジュールと secrets モジュールの比較
   :header-rows: 1
   :widths: 20 40 40

   * - 項目
     - ``random``
     - ``secrets``
   * - 生成器
     - メルセンヌ・ツイスタ（擬似乱数）
     - OS の乱数源（CSPRNG）
   * - シードと再現性
     - 同じシードなら同じ列になる
     - シードは無く、再現できない
   * - 出力からの予測
     - 624 個の出力から以後を予測できる
     - 予測できない
   * - 主な用途
     - シミュレーション、試験データ、ゲーム
     - 鍵、トークン、セッション ID、パスワードの初期値

^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^

まとめ
------

* 情報セキュリティの目標は、機密性・完全性・可用性の 3 要素を保つことである。損害は、脅威が脆弱性を突くことで生じる。
* 共通鍵暗号は高速だが鍵配送問題がある。公開鍵暗号は鍵配送問題を解決するが遅い。実際には両者を組み合わせたハイブリッド暗号を使う。
* RSA は :math:`n = pq` の素因数分解の困難さに基づき、:math:`ed \equiv 1 \pmod{\varphi(n)}` を満たす鍵で暗号化と復号を行う。教科書的 RSA は安全ではなく、パディングと検証済みのライブラリが必要である。
* 暗号学的ハッシュ関数は原像計算困難性・第 2 原像計算困難性・衝突困難性を持つ。SHA-256 を使い、衝突が見つかっている MD5 や SHA-1 は使わない。ハッシュ化は暗号化ではない。
* MAC（HMAC）は共通鍵で完全性と真正性を保証する。タグの比較には ``hmac.compare_digest`` を使う。
* デジタル署名は秘密鍵で作成し公開鍵で検証するので、否認防止ができる。公開鍵の持ち主は、認証局が署名した公開鍵証明書で保証する。
* TLS は、鍵交換、証明書による認証、認証付き暗号を組み合わせて、通信の機密性・完全性・認証を提供する。
* 鍵、トークン、セッション ID、ソルトには、OS の乱数源を使う ``secrets`` や ``os.urandom`` の乱数を使う。``random`` のメルセンヌ・ツイスタはシードから再現でき、624 個の出力から以後を予測できるので、セキュリティの用途に使ってはならない。
