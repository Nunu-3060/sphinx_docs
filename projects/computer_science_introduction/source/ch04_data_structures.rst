データ構造
==========

プログラムが扱うデータは、メモリ上にどのように並べるかによって、同じ操作でもかかる手間が大きく変わる。この章では、配列、連結リスト、スタックとキュー、ハッシュ表、木、ヒープ、グラフという代表的な\ :term:`データ構造`\ を取り上げ、それぞれのデータの格納方法と、各操作にかかる計算量を学ぶ。さらに、ハッシュ表と連結リストを組み合わせた LRU キャッシュを例に、複数のデータ構造を組み合わせて目的の計算量を得る考え方を学び、応用的なデータ構造としてトライ、Union-Find、ブルームフィルタを紹介する。また、Python の ``list``、``dict``、``set``、``collections.deque``、``heapq`` がどのデータ構造で実装されているかを知り、日々のコードで適切な型を選べるようになることを目指す。問題を解く手順（アルゴリズム）と計算量の厳密な定義は「:doc:`ch05_algorithms`」で扱う。

.. _ch04-big-o:

計算量の表し方
--------------

この章では、操作にかかる手間を計算量で表す。計算量は、データの個数 :math:`n` が大きくなったときに処理の手間がどのように増えるかを表す尺度である。例えば :math:`O(n)` は「手間がおおむね :math:`n` に比例して増える」こと、:math:`O(1)` は「:math:`n` によらず一定の手間で済む」こと、:math:`O(\log n)` は「:math:`n` が 2 倍になっても手間が一定量しか増えない」ことを表す。この書き方を O 記法と呼ぶ。O 記法の定義と性質は第 5 章の「:ref:`ch05-big-o`」で詳しく説明するので、ここでは「増え方の目安」として読めば十分である。

以下では、特に断らない限り計算量は\ **最悪の場合**\ の時間計算量を表す。最悪の場合とは、同じ個数のデータのうち最も手間のかかる入力に対する値である。

抽象データ型と実装
------------------

データ構造を学ぶときには、「どのような操作ができるか」と「それをどのように実現するか」を区別すると見通しが良くなる。前者を\ :term:`抽象データ型`\ （ADT: Abstract Data Type）と呼ぶ。例えば「スタック」は、値を積む操作（push）と、最後に積んだ値を取り出す操作（pop）を持つ抽象データ型である。スタックの利用者は、内部で値がどのように並んでいるかを知らなくてよい。

一方、同じスタックを配列で実現することも、連結リストで実現することもできる。これが実装である。実装が異なれば、各操作の計算量やメモリの使い方が異なる。プログラミング言語でいえば、Java の ``List`` インタフェースと ``ArrayList``・``LinkedList`` クラスの関係、Python でいえば ``collections.abc.Sequence`` と ``list``・``tuple`` の関係がこれに当たる。

実務でデータ構造を選ぶときは、まず「どの操作を頻繁に行うか」（末尾への追加か、先頭からの取り出しか、キーによる検索か、最小値の取り出しか）を整理し、それらの操作が速い実装を選ぶ。この章の各節は、この観点で読むと理解しやすい。

配列
----

連続領域とランダムアクセス
^^^^^^^^^^^^^^^^^^^^^^^^^^

:term:`配列`\ は、同じ大きさの要素をメモリ上の連続した領域に順に並べたデータ構造である。先頭のアドレスを :math:`a`、1 要素の大きさを :math:`s` バイトとすると、添字 :math:`i` の要素のアドレスは次の式で求まる。

.. math::

   a + i \times s

この計算は :math:`i` の値によらず一定の手間で済むため、配列は任意の位置の要素に :math:`O(1)` で読み書きできる。このように位置を指定して直接要素に到達できることを\ **ランダムアクセス**\ と呼ぶ。添字が 0 から始まる言語が多いのは、添字が先頭からの距離（オフセット）を表すと考えると、この式が最も簡単になるからである。

連続した領域に並んでいることには、計算量に表れない利点もある。「:doc:`ch03_computer_architecture`」で見たように、CPU はメモリを一定の大きさの塊（キャッシュライン）単位でキャッシュに読み込む。配列を先頭から順に処理すると、隣の要素がすでにキャッシュに載っている可能性が高く、実際の処理は速くなる。

一方、配列の途中に要素を挿入したり、途中の要素を削除したりするには、それより後ろの要素をすべて 1 つずつずらす必要がある。したがって、挿入・削除の計算量は :math:`O(n)` である。また、配列の大きさは確保した時点で決まるため、要素がいくつ入るか分からない用途にはそのままでは使いにくい。

.. _ch04-dynamic-array:

動的配列と償却計算量
^^^^^^^^^^^^^^^^^^^^

要素数が増えると自動的に領域を広げる配列を\ :term:`動的配列`\ と呼ぶ。動的配列は、実際の要素数より大きめの領域（容量）を確保しておき、末尾への追加では空いている場所に書き込むだけで済ませる。容量が尽きたときは、より大きな領域を新たに確保し、すべての要素をコピーしてから追加する。

コピーが発生する追加は :math:`O(n)` かかるが、容量を一定の比率で増やす（例えば 2 倍にする）と、コピーはまれにしか起きない。容量 1 から始めて 2 倍ずつ増やしながら :math:`n` 個の要素を追加する場合を考える。コピーが起きるのは、要素数が 1、2、4、…、:math:`2^k`\ （:math:`2^k < n`）の状態からさらに追加しようとしたときで、コピーされる要素の総数は次のようになる。

.. math::

   1 + 2 + 4 + \cdots + 2^k = 2^{k+1} - 1 < 2n

つまり、:math:`n` 回の追加全体でコピーの手間は :math:`2n` 未満であり、1 回あたりに直すと定数で収まる。このように、一連の操作全体の手間を操作の回数で割って評価した計算量を\ :term:`償却計算量`\ と呼ぶ。動的配列の末尾への追加は、1 回ごとの最悪は :math:`O(n)` であるが、償却計算量は :math:`O(1)` である。なお、容量を「2 倍」ではなく「10 個ずつ」のように一定数ずつ増やすと、コピーの総数は :math:`n^2` に比例してしまい、償却計算量も :math:`O(n)` になる。一定の\ **比率**\ で増やすことが重要である。

Python の list
^^^^^^^^^^^^^^

Python の ``list`` は動的配列である。CPython の ``list`` は、要素のオブジェクトそのものではなく、オブジェクトへの参照（ポインタ）を連続した領域に並べている。そのため、異なる型の値を混在させても、添字による参照は :math:`O(1)` で行える。容量の増やし方は 2 倍ではなく、より小さな比率で余裕を持たせる方式であるが、一定の比率で増やす点は同じであり、``append()`` の償却計算量は :math:`O(1)` である。

``list`` の主な操作の計算量を次の表に示す。

.. list-table::
   :header-rows: 1
   :widths: 35 20 45

   * - 操作
     - 計算量
     - 備考
   * - ``a[i]``、``a[i] = x``
     - :math:`O(1)`
     - ランダムアクセス
   * - ``a.append(x)``
     - 償却 :math:`O(1)`
     - 容量が尽きたときだけコピーが起きる
   * - ``a.pop()``
     - :math:`O(1)`
     - 末尾からの取り出し
   * - ``a.pop(0)``、``a.insert(0, x)``
     - :math:`O(n)`
     - 後ろの要素をすべてずらす
   * - ``x in a``、``a.index(x)``
     - :math:`O(n)`
     - 先頭から順に比較する
   * - ``len(a)``
     - :math:`O(1)`
     - 要素数は別に記録されている

実務で特に注意したいのは ``x in a`` である。見た目は 1 つの演算子であるが、``list`` に対しては先頭から順に比較するため :math:`O(n)` かかる。ループの中で ``list`` に対して ``in`` を使うと、全体として二重ループと同じ手間になる。この問題とその解決方法は「:ref:`ch04-nested-loop`」で改めて扱う。

連結リスト
----------

:term:`連結リスト`\ は、値と「次の要素への参照」を組にした\ **ノード**\ を、参照でつないで並べたデータ構造である。各ノードはメモリ上のどこにあってもよく、配列のように連続した領域を必要としない。次の要素への参照だけを持つものを単方向連結リスト、前の要素への参照も持つものを双方向連結リストと呼ぶ。

連結リストでは、位置が分かっているノードの直後に新しいノードを挿入するとき、参照を 2 つ付け替えるだけで済む。後ろの要素をずらす必要がないため、計算量は :math:`O(1)` である。一方、添字 :math:`i` の要素を得るには先頭から :math:`i` 個のノードを順にたどる必要があり、ランダムアクセスは :math:`O(n)` かかる。値を探す場合も同様である。また、ノードがメモリ上に散らばるため、配列に比べてキャッシュの効果が得にくく、各ノードが参照を持つ分だけメモリも多く使う。

Python には連結リストの組み込み型は無く、実務で連結リストを自作する機会も少ない。それでも連結リストの考え方は、次節の ``collections.deque``、ハッシュ表のチェイン法、OS のプロセス管理（「:doc:`ch08_operating_systems`」）など、多くの場所で使われている。

スタックとキュー
----------------

:term:`スタック`\ は、最後に入れた値を最初に取り出す（LIFO: Last In, First Out）抽象データ型である。関数呼び出しの管理（コールスタック）、括弧の対応の確認、深さ優先探索、エディタの「元に戻す」機能などで使われる。Python では ``list`` の ``append()`` と ``pop()`` がどちらも末尾に対する操作であり、償却 :math:`O(1)` で動くため、``list`` をそのままスタックとして使える。

:term:`キュー`\ は、最初に入れた値を最初に取り出す（FIFO: First In, First Out）抽象データ型である。処理待ちの仕事を到着順にこなす場面（印刷待ち、メッセージキュー、幅優先探索）で使われる。``list`` でキューを作ろうとして ``pop(0)`` で先頭から取り出すと、残りの要素をすべてずらすため 1 回ごとに :math:`O(n)` かかる。キューには ``collections.deque`` を使う。

.. code-block:: python
   :linenos:

   from collections import deque

   queue: deque[str] = deque()
   queue.append("job1")      # 末尾に追加: O(1)
   queue.append("job2")
   first = queue.popleft()   # 先頭から取り出し: O(1)
   print(first, list(queue))  # job1 ['job2']

``deque``\ （double-ended queue、両端キュー）は両端への追加と取り出しがどちらも :math:`O(1)` で行える。CPython の ``deque`` は、固定長の配列（ブロック）を双方向連結リストでつないだ構造で実装されている。そのため両端の操作は速いが、中央付近の要素への添字アクセスは :math:`O(n)` かかる。「両端だけを操作するなら ``deque``、添字で自由にアクセスするなら ``list``」と使い分ける。

ハッシュ表
----------

ハッシュ関数とバケット
^^^^^^^^^^^^^^^^^^^^^^

:term:`ハッシュ表`\ は、キーから値を平均 :math:`O(1)` で検索できるデータ構造である。ハッシュ表は、バケットと呼ぶ格納場所を配列として用意し、キーをバケットの番号に変換してそこに格納する。この変換に使う関数を\ :term:`ハッシュ関数`\ と呼ぶ。ハッシュ関数はキーから整数（ハッシュ値）を計算する関数で、バケット数を :math:`m` とすると、キー :math:`k` を格納するバケットの番号は次のように決める。

.. math::

   h(k) \bmod m

同じキーからは必ず同じハッシュ値が得られなければならない。また、異なるキーのハッシュ値がなるべく偏らずに散らばるほど良いハッシュ関数である。配列の添字が :math:`O(1)` で参照できることと、ハッシュ値の計算の手間がキーの長さだけで決まることから、衝突が少なければ検索は要素数によらない手間で済む。

衝突の解決
^^^^^^^^^^

キーの種類はバケット数より多いのが普通なので、異なるキーが同じバケットに割り当てられることは避けられない。これを\ **衝突**\ と呼ぶ。衝突の解決方法には大きく 2 つある。

* :term:`チェイン法`\ : 各バケットにリスト（連結リストや動的配列）を持たせ、同じバケットに割り当てられたキーをそのリストに並べる。検索ではバケットを決めた後、リストの中を順に比較する。
* :term:`オープンアドレス法`\ : すべての要素をバケットの配列に直接格納する。割り当てられたバケットが埋まっていたら、決められた規則で別のバケットを順に調べ（探査）、空いている場所に格納する。最も簡単な規則は隣のバケットを順に調べる線形探査である。削除した場所を単に空にすると、その先に格納された要素が探査で見つからなくなるため、「削除済み」の印を残す必要がある。

負荷率と再ハッシュ
^^^^^^^^^^^^^^^^^^

格納している要素数を :math:`n`、バケット数を :math:`m` とするとき、:math:`\alpha = n / m` を\ :term:`負荷率`\ と呼ぶ。チェイン法では 1 つのバケットに平均 :math:`\alpha` 個の要素が並ぶので、ハッシュ値が一様に散らばると仮定すると、検索の平均の手間は :math:`O(1 + \alpha)` になる [CLRS]_。負荷率が一定値を超えたらバケット数を増やして全要素を入れ直す（再ハッシュする）ことで、:math:`\alpha` を定数以下に保ち、平均 :math:`O(1)` を維持する。再ハッシュは :math:`O(n)` かかるが、動的配列と同じくバケット数を一定の比率で増やせば、挿入の償却計算量は :math:`O(1)` になる。

ただし、これは\ **平均**\ の話である。すべてのキーが同じバケットに集まると、検索は :math:`O(n)` に悪化する。攻撃者が意図的に衝突するキーを大量に送り込んでサーバを遅くする攻撃（ハッシュフラッディング）も知られており、Python は文字列のハッシュ値の計算に、プロセスごとに変わる乱数を混ぜることでこれを防いでいる。そのため、同じ文字列でも ``hash()`` の値は実行のたびに変わる。

Python の dict と set
^^^^^^^^^^^^^^^^^^^^^

Python の ``dict`` と ``set`` はハッシュ表である。CPython はオープンアドレス法を採用しており、探査の順序はハッシュ値の上位ビットも使って決めることで、線形探査より偏りにくくしている。キーによる参照・追加・削除と ``x in d`` は平均 :math:`O(1)`、最悪 :math:`O(n)` である。また、Python 3.7 以降の ``dict`` は挿入した順序を保つことが言語仕様として保証されている [PythonDocs]_。

``dict`` のキーや ``set`` の要素にできるのは、ハッシュ可能な（``__hash__()`` を持ち、値が変化しない）オブジェクトに限られる。``list`` をキーにできないのは、格納した後に中身が変わるとハッシュ値も変わり、格納したバケットから見つけられなくなるからである。自作クラスで ``__eq__()`` を定義する場合は、「等しいオブジェクトは等しいハッシュ値を持つ」ように ``__hash__()`` も定義しなければならない。

実務での使い分け: 二重ループを避ける
^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^

2 つのデータを突き合わせる処理は、実務で頻繁に現れる。次のコードは、注文の一覧から、有効な会員による注文だけを取り出す。

.. code-block:: python
   :linenos:

   active_ids: list[int] = load_active_member_ids()  # 会員 m 人
   orders: list[tuple[int, int]] = load_orders()      # 注文 n 件

   # 遅い: in が list を先頭から調べるので全体で O(nm)
   valid = [o for o in orders if o[0] in active_ids]

   # 速い: set に変換すれば in は平均 O(1) で、全体で O(n + m)
   active_set = set(active_ids)
   valid = [o for o in orders if o[0] in active_set]

5 行目は ``for`` が 1 つしか無いように見えるが、``in`` の中に隠れたループがあるため、実質は二重ループである。会員が 1 万人、注文が 10 万件なら、最悪で :math:`10^9` 回程度の比較になる。8 行目で ``set`` に変換すると、変換に :math:`O(m)`、検索が 1 件あたり平均 :math:`O(1)` で済む。データベースが索引を使って検索を高速化するのも、同じ発想である（「:doc:`ch11_databases`」）。

木は、ノードとそれらを結ぶ親子関係からなり、階層構造を表すデータ構造である。ファイルシステムのフォルダ、HTML の DOM、組織図、プログラムの構文木など、身の回りの多くのデータが木の形をしている。木に関する基本的な用語を次の表にまとめる。

.. list-table::
   :header-rows: 1
   :widths: 20 80

   * - 用語
     - 意味
   * - 根
     - 親を持たない唯一のノード
   * - 葉
     - 子を持たないノード
   * - 部分木
     - あるノードとその子孫すべてからなる木
   * - 深さ
     - 根からそのノードまでの経路上の辺の数
   * - 高さ
     - 根から最も深い葉までの経路上のノード数（辺の数で定義する流儀もある）
   * - 二分木
     - 各ノードの子が高々 2 つ（左の子と右の子）である木

二分探索木
^^^^^^^^^^

:term:`二分探索木`\ は、すべてのノードについて「左の部分木のキーはすべてそのノードのキーより小さく、右の部分木のキーはすべて大きい」という性質を満たす二分木である。キーを探すときは根から始め、探すキーが小さければ左へ、大きければ右へ進む。1 回の比較ごとに一方の部分木を候補から外せるので、比較の回数は木の高さ :math:`h` 以下であり、探索・挿入・削除の計算量は :math:`O(h)` である。

また、二分探索木を「左の部分木、自分、右の部分木」の順に走査（中間順の走査）すると、キーが小さい順に得られる。ハッシュ表ではキーの順序が失われるが、二分探索木では「ある範囲のキーをすべて列挙する」「指定したキー以上で最小のキーを求める」といった順序に基づく操作もできる。

平衡木の必要性
^^^^^^^^^^^^^^

実行結果から分かるように、二分探索木の高さは挿入の順序によって大きく変わる。1023 個のノードをすき間なく詰めた二分木の高さは 10 であり、一般に :math:`n` 個のノードを持つ二分木の高さは少なくとも :math:`\lceil \log (n+1) \rceil` である。ランダムな順に挿入すると高さは :math:`O(\log n)` 程度に収まることが知られており、この例でも 24 にとどまった。一方、整列済みの順に挿入すると、新しいキーは常に右の子になり、木は一直線に伸びて高さが :math:`n` になる。これは連結リストと同じ形であり、探索は :math:`O(n)` かかる。実務のデータは、日付順や ID 順のようにすでに整列していることが多いため、この最悪の場合は決して珍しくない。

そこで、挿入や削除のたびに木の形を調整し、高さを常に :math:`O(\log n)` に保つ二分探索木が考案されている。これを\ :term:`平衡木`\ と呼ぶ。代表的なものに AVL 木と赤黒木があり、どちらも回転と呼ぶ局所的な付け替えによって左右の偏りを直す。平衡木では探索・挿入・削除が最悪でも :math:`O(\log n)` で行える。Java の ``TreeMap`` は赤黒木で実装されており、C++ の ``std::map`` も一般的な処理系では赤黒木で実装されている。また、データベースの索引で広く使われる B 木（B+ 木）は、1 つのノードに多数のキーを持たせて高さを低くした平衡木で、補助記憶からの読み込み回数を減らすよう工夫されている。平衡化の具体的な手順は本書では扱わないので、詳しくは [CLRS]_ を参照。

Python の標準ライブラリには平衡木が無い。順序付きのデータを扱いたい場合は、整列済みの ``list`` に対して ``bisect`` モジュールで二分探索する方法がよく使われる（「:doc:`ch05_algorithms`」）。

ヒープと優先度付きキュー
------------------------

:term:`優先度付きキュー`\ は、値を追加する操作と、最も優先度の高い（例えば最小の）値を取り出す操作を持つ抽象データ型である。タスクのスケジューリング、イベント駆動のシミュレーション、次章で扱うダイクストラ法などで使われる。整列済みの配列で実現すると取り出しは速いが追加が :math:`O(n)`、整列していない配列では追加は速いが取り出しが :math:`O(n)` になる。両方を :math:`O(\log n)` で行えるのが\ :term:`ヒープ`\ である。

ここでいうヒープ（二分ヒープ）は、次の 2 つの性質を満たす二分木である。なお、プログラムが動的に確保するメモリ領域も「ヒープ」と呼ぶが、それとは無関係である。

* 形の性質: 最下段以外はすべて埋まっており、最下段は左から詰めて並ぶ（完全二分木）。
* 順序の性質: どのノードも、その子以下の値を持つ（最小ヒープの場合）。したがって根が最小値である。

完全二分木はすき間が無いので、ノードを上の段から左から順に配列に並べれば、参照を持たずに表せる。添字 :math:`i` のノードの子は :math:`2i+1` と :math:`2i+2`、親は :math:`\lfloor (i-1)/2 \rfloor` の位置にある。値を追加するときは配列の末尾に置き、親より小さい間は親と交換していく（上方移動）。最小値を取り出すときは、根を取り除いて末尾の値を根に移し、子のうち小さい方より大きい間は交換していく（下方移動）。どちらも木の高さ :math:`O(\log n)` 回の交換で済む。

``heapq`` は ``list`` をそのまま最小ヒープとして扱う関数群であり、``heappush()`` と ``heappop()`` は :math:`O(\log n)`、``heap[0]`` で最小値を見るのは :math:`O(1)`、既存の ``list`` をヒープに並べ替える ``heapify()`` は :math:`O(n)` である。最大ヒープが必要な場合は、値の符号を反転して格納するのが定番の方法である。後半の例のように ``(優先度, 内容)`` のタプルを入れると、タプルの比較規則により優先度の小さい順に取り出せる。ただし優先度が等しいと 2 番目の要素同士が比較されるので、比較できない値を入れる場合は ``(優先度, 通し番号, 内容)`` のように通し番号を挟む。また、「大量のログから上位 10 件だけ欲しい」のような場面では、全体を整列する代わりに ``heapq.nlargest()`` を使うと、:math:`O(n \log k)`\ （:math:`k` は取り出す件数）で済む。

グラフの表現
------------

:term:`グラフ`\ は、頂点の集合と、頂点同士を結ぶ辺の集合からなるデータ構造である。鉄道の路線図（駅が頂点、線路が辺）、SNS のフォロー関係、Web ページのリンク、パッケージの依存関係、ネットワークの経路など、「ものとものの関係」を表すあらゆる場面で使われる。辺に向きがあるものを有向グラフ、無いものを無向グラフと呼ぶ。また、辺に距離や費用などの数値（重み）を持たせたものを重み付きグラフと呼ぶ。木は、閉路（同じ頂点に戻ってくる経路）を持たない連結なグラフの一種である。

頂点数を :math:`V`、辺数を :math:`E` とする。グラフをプログラムで表す代表的な方法は次の 2 つである。

* :term:`隣接行列`\ : :math:`V \times V` の 2 次元配列を用意し、頂点 :math:`u` から :math:`v` への辺があれば :math:`u` 行 :math:`v` 列を 1（重み付きなら重み）、無ければ 0 にする。
* :term:`隣接リスト`\ : 頂点ごとに、辺でつながった頂点の一覧を持つ。Python では ``dict[str, list[str]]`` のように辞書とリストで表すのが手軽である。

例えば、頂点 A、B、C があり、A と B、A と C が辺で結ばれた無向グラフは、隣接リストでは次のように表せる。

.. code-block:: python
   :linenos:

   graph: dict[str, list[str]] = {
       "A": ["B", "C"],
       "B": ["A"],
       "C": ["A"],
   }

2 つの表現の特徴を次の表に示す。

.. list-table::
   :header-rows: 1
   :widths: 40 30 30

   * - 項目
     - 隣接行列
     - 隣接リスト
   * - メモリ使用量
     - :math:`O(V^2)`
     - :math:`O(V + E)`
   * - 辺 :math:`(u, v)` があるかの判定
     - :math:`O(1)`
     - :math:`O(\deg(u))`
   * - 頂点 :math:`u` に隣接する頂点の列挙
     - :math:`O(V)`
     - :math:`O(\deg(u))`
   * - 適したグラフ
     - 辺が多い（密な）グラフ
     - 辺が少ない（疎な）グラフ

ここで :math:`\deg(u)` は頂点 :math:`u` の次数（:math:`u` につながる辺の数）である。実際のグラフの多くは疎である。例えば 100 万人のユーザがいる SNS で、各ユーザが平均 100 人とつながっているとき、隣接行列は :math:`10^{12}` 個の要素を必要とするが、隣接リストなら辺の数に比例する :math:`10^8` 程度で済む。このため、特別な理由が無ければ隣接リストを使う。隣接リストの各頂点の一覧を ``set`` にすれば、辺の有無の判定も平均 :math:`O(1)` にできる。グラフをたどって最短経路などを求める方法は「:doc:`ch05_algorithms`」で扱う。

LRU キャッシュ: データ構造を組み合わせる
----------------------------------------

LRU キャッシュに求められる操作
^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^

ここまでのデータ構造は、それぞれ得意な操作と苦手な操作を持っていた。実務では、複数のデータ構造を組み合わせて、どれか 1 つでは実現できない計算量を得ることがよくある。その代表例が LRU キャッシュである。

キャッシュは、計算や読み込みに時間のかかる結果を手元に保存しておき、次に同じものを求められたときに再利用する仕組みである。保存できる量には限りがあるので、いっぱいになったら何かを捨てなければならない。このとき「最も長い間使われていないもの」を捨てる方式を LRU（Least Recently Used）と呼び、この方式で管理するキャッシュを :term:`LRU キャッシュ`\ と呼ぶ。最近使われたものはまたすぐ使われやすい、という時間的局所性を前提にした方式である。第 3 章の「:doc:`ch03_computer_architecture`」で見た CPU のキャッシュも、セットアソシアティブ方式でセットが埋まったときにどのラインを追い出すかを決める必要があり、LRU やそれを簡略化した方式が使われている。主記憶が足りないときにどのページを補助記憶に追い出すかという OS のページ置換（「:doc:`ch08_operating_systems`」）でも、同じ考え方が使われる。ハードウェアでは厳密な LRU の管理は回路が大きくなるため近似で済ませることが多いが、ソフトウェアでは次に述べる方法で厳密な LRU を効率よく実現できる。

LRU キャッシュには次の操作が必要である。

* 取得: キーに対応する値を返し、そのキーを「最も最近使われた」ものとして記録する。
* 追加: キーと値を格納し、そのキーを「最も最近使われた」ものとする。容量を超えたら、最も長い間使われていないキーを追い出す。

キーによる検索だけならハッシュ表で平均 :math:`O(1)` であるが、ハッシュ表は使われた順序を記録しない。一方、使われた順にキーを並べたリストを持てば、追い出す対象は先頭を見るだけで分かるが、取得のたびにそのキーをリストから探して末尾に移すと :math:`O(n)` かかる。

ハッシュ表と双方向連結リストの組み合わせ
^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^

そこで、使われた順にキーを並べた双方向連結リストと、キーからそのリストのノードへの参照を引くハッシュ表を組み合わせる。リストの先頭は最も長い間使われていないキー、末尾は最も最近使われたキーである。

* 取得: ハッシュ表でキーからノードを平均 :math:`O(1)` で見つける。そのノードをリストから外して末尾につなぎ直す操作は、前後のノードの参照を付け替えるだけなので :math:`O(1)` である。
* 追加: 新しいノードを末尾につなぎ、ハッシュ表に登録する。容量を超えたら、先頭のノードをリストから外し、そのキーをハッシュ表からも削除する。どちらも :math:`O(1)` である。

単方向連結リストでは、あるノードを外すために 1 つ前のノードを先頭からたどって探す必要があり、:math:`O(n)` かかってしまう（「連結リスト」の節の実行結果で、末尾の削除に時間がかかったのと同じ理由である）。各ノードが前のノードへの参照も持つ双方向連結リストにすることで、ハッシュ表から直接たどり着いたノードを :math:`O(1)` で外せる。ハッシュ表が「どこにあるか」を、連結リストが「どの順序か」を受け持つことで、取得と追加の両方が平均 :math:`O(1)` になる。

OrderedDict による実装
^^^^^^^^^^^^^^^^^^^^^^

Python の ``collections.OrderedDict`` は、まさにこの組み合わせで実装された辞書であり、キーの順序を保ったまま、指定したキーを末尾に移す ``move_to_end()`` と、先頭（または末尾）の要素を取り出す ``popitem()`` を :math:`O(1)` で行える [PythonDocs]_。通常の ``dict`` も挿入順を保つが、既存のキーを末尾に移す操作を持たないため、LRU キャッシュには ``OrderedDict`` が適している。``OrderedDict`` を使った LRU キャッシュの例を次に示す。

functools.lru_cache
^^^^^^^^^^^^^^^^^^^

関数の結果をキャッシュするだけなら、自分で実装する必要はない。標準ライブラリの ``functools.lru_cache`` デコレータを関数に付けると、引数をキーとし、戻り値を値とする LRU キャッシュが自動的に用意される。``maxsize`` で容量を指定し（既定は 128）、``cache_info()`` でヒット（キャッシュにあった回数）とミス（実際に計算した回数）を確認できる。サンプルの 47〜50 行目では容量 2 の ``square()`` を定義し、引数 1、2、1、3、2 の順に呼び出している。3 回目の 1 はヒットするが、4 回目の 3 で最も長い間使われていない 2 が追い出されるので、5 回目の 2 は再びミスになる。実行結果の 9 行目の ``hits=1, misses=4`` はこの動作を表している。

第 5 章の「:doc:`ch05_algorithms`」で使う ``functools.cache`` は、容量に上限の無い ``lru_cache(maxsize=None)`` と同じものである。メモ化のように同じ引数が繰り返し現れることが分かっている場合は ``cache`` で十分であるが、Web アプリケーションで外部への問い合わせ結果を保存するような、引数の種類に際限が無い場面では、``lru_cache`` で容量を制限しないとメモリを使い果たすおそれがある。なお、キャッシュのキーにするため、引数はハッシュ可能でなければならない。

応用的なデータ構造

トライ
^^^^^^

:term:`トライ`\ （trie、接頭辞木とも呼ぶ）は、文字列の集合を、文字を 1 つずつたどる木として表すデータ構造である。根から下向きの各辺に 1 文字が対応し、根からあるノードまでたどった文字を並べると、そのノードが表す文字列になる。単語の終わりに当たるノードには印を付けておく。例えば ``car``、``card``、``care``、``cat`` を格納すると、4 つの単語は根から ``c``、``a`` までの経路を共有し、そこから ``r`` と ``t`` に分かれる。

トライで文字列を探すには、根から 1 文字ずつ子をたどればよい。各ノードの子をハッシュ表で持てば、1 文字あたり平均 :math:`O(1)` で次のノードに進めるので、長さ :math:`L` の文字列の検索・挿入は :math:`O(L)` であり、格納している単語の数によらない。トライの最大の特徴は\ **接頭辞検索**\ が得意なことである。ある接頭辞で始まる単語をすべて求めるには、接頭辞の文字をたどって着いたノードの下にある単語を列挙すればよく、手間は接頭辞の長さと結果の量で決まる。ハッシュ表では、接頭辞が同じキーがどこに格納されているかに規則が無いので、すべてのキーを調べるしかない。

この性質から、トライは検索窓のオートコンプリート（入力途中の文字列から候補を示す機能）、辞書や綴りの検査、ルータの経路表で宛先 IP アドレスに最も長く一致する経路を選ぶ処理（最長一致、「:doc:`ch10_networks`」）などに使われる。一方、1 文字ごとにノードを作るのでメモリを多く使う。子が 1 つしかないノードの連なりを 1 つの辺にまとめた基数木（パトリシア木）は、この無駄を減らした変種である。

.. _ch04-union-find:

Union-Find
^^^^^^^^^^

:term:`Union-Find`\ （素集合データ構造）は、要素を互いに重ならないグループ（素集合）に分けて管理し、次の 2 つの操作を高速に行うデータ構造である。

* find: 要素が属するグループの代表を返す。2 つの要素の代表が等しければ、同じグループに属する。
* union: 2 つの要素が属するグループを 1 つに併合する。

グラフに辺を 1 本ずつ加えながら「頂点 :math:`u` と :math:`v` はつながっているか」を判定する問題は、Union-Find で効率よく解ける。辺 :math:`(u, v)` を加えるたびに ``union(u, v)`` を行えば、各グループがそのときの連結成分（互いに経路でつながった頂点の集まり）になる。ネットワークの機器の接続状況の把握、画像の同じ色の領域の検出、最小全域木を求めるクラスカル法の閉路判定などに使われる。

Union-Find は、各グループを 1 本の木で表し、木の根をグループの代表とする。各要素は親への参照だけを持てばよいので、要素を 0 から :math:`n-1` の整数とすれば、親を格納する配列 1 つで表せる。find は親をたどって根を求め、union は一方の根をもう一方の根の子にする。このままでは木が一直線に伸びて find が :math:`O(n)` かかることがあるので、次の 2 つの工夫を組み合わせる。

* ランクによる併合: 各根に木の高さの上限（ランク）を記録し、union ではランクの低い木の根を、ランクの高い木の根の子にする。これにより木の高さは :math:`O(\log n)` に抑えられる。
* :term:`経路圧縮`\ : find で根までたどった後、途中のすべての要素の親を根に付け替える。次に同じ要素で find すると、1 回で根に着く。

両方を組み合わせると、:math:`m` 回の操作全体の手間は :math:`O(m \, \alpha(n))` になることが知られている [CLRS]_。ここで :math:`\alpha(n)` は\ **逆アッカーマン関数**\ と呼ばれる、極めてゆっくり増える関数で、宇宙に存在する原子の数ほどの :math:`n` に対しても 4 を超えない。したがって、実用上は 1 回の操作の償却計算量が「ほぼ定数」であると考えてよい。ただし、Union-Find は併合しかできず、一度併合したグループを分ける操作は効率よく行えない。

ブルームフィルタ
^^^^^^^^^^^^^^^^

:term:`ブルームフィルタ`\ は、「ある要素が集合に含まれるか」を、ごく少ないメモリで判定するデータ構造である [Bloom1970]_。ハッシュ表と違って要素そのものを格納しないので、要素がどれほど長くても、1 要素あたり数ビットから十数ビットで済む。その代わり、判定に誤りが生じることを許す。

ブルームフィルタは、:math:`m` ビットのビット配列（初期値はすべて 0）と、:math:`k` 個の異なるハッシュ関数からなる。各ハッシュ関数は、要素を 0 から :math:`m-1` のビット位置に対応付ける。

* 追加: 要素の :math:`k` 個のハッシュ値が示すビットをすべて 1 にする。
* 判定: 要素の :math:`k` 個のビットを調べ、1 つでも 0 があれば「含まれない」、すべて 1 なら「含まれるかもしれない」と答える。

追加した要素のビットは必ず 1 になっているので、追加した要素を「含まれない」と誤ること（\ **偽陰性**\ ）は決して無い。一方、追加していない要素でも、その :math:`k` 個のビットがたまたま他の要素によってすべて 1 にされていれば、「含まれるかもしれない」と答えてしまう。これを\ :term:`偽陽性`\ と呼ぶ。また、あるビットが複数の要素で共有されているかもしれないので、ビットを 0 に戻して要素を削除することはできない。

:math:`n` 個の要素を追加した後の偽陽性率は、次のように見積もれる。ハッシュ値が一様に散らばると仮定すると、1 回のビットの設定で特定のビットが 1 にならない確率は :math:`1 - 1/m` であり、:math:`kn` 回の設定の後もそのビットが 0 のままである確率は :math:`(1 - 1/m)^{kn} \approx e^{-kn/m}` である。追加していない要素の :math:`k` 個のビットがすべて 1 である確率、つまり偽陽性率は、おおよそ次の式で表せる。

.. math::

   \left(1 - e^{-kn/m}\right)^k

ハッシュ関数を増やす（:math:`k` を大きくする）と、判定で調べるビットが増えて偽陽性になりにくくなる一方、1 にするビットも増えて配列が埋まりやすくなる。この 2 つの効果がつり合う :math:`k = (m/n) \ln 2` のとき、偽陽性率は最小になる。

ブルームフィルタは「含まれない」と分かれば高価な処理を省ける場面で使われる。例えば、多くのキーバリューストアは、補助記憶上のファイルごとにブルームフィルタを主記憶に持ち、目的のキーが無いことが分かったファイルは読まずに済ませる。偽陽性で無駄な読み込みが起きることはあるが、結果が誤ることはない。他にも、Web のクローラが訪問済みの URL を記録する処理や、キャッシュに入れる価値のある（2 回以上要求された）データの選別などに使われる。

最初の表の「―」はその操作を想定していないことを表す。ハッシュ表と木の「検索」はキーによる検索である。整列済みの配列は、二分探索によって :math:`O(\log n)` で検索できる。二分探索の手順と、なぜ :math:`O(\log n)` になるかは「:doc:`ch05_algorithms`」で説明する。平衡化しない二分探索木の値は最悪の場合であり、ランダムな順に挿入した場合の平均は平衡木と同じ :math:`O(\log n)` 程度になる。

この表から分かるように、すべての操作が速いデータ構造は存在しない。例えば、キーで検索するだけならハッシュ表が最も速いが、順序に基づく操作が必要なら平衡木や整列済みの配列が、最小値を繰り返し取り出すならヒープが適している。

まとめ
------

* 抽象データ型は「どのような操作ができるか」を定め、実装は「それをどう実現するか」を定める。同じ抽象データ型でも実装によって各操作の計算量が異なる。
* 配列は連続した領域に要素を並べ、添字による参照が :math:`O(1)` である。途中への挿入・削除は :math:`O(n)` かかる。
* 動的配列は容量を一定の比率で増やすことで、末尾への追加を償却 :math:`O(1)` にしている。Python の ``list`` は動的配列であり、``pop(0)`` や ``x in a`` は :math:`O(n)` である。
* 連結リストは位置が分かっていれば挿入・削除が :math:`O(1)` であるが、添字による参照や検索は :math:`O(n)` かかる。
* スタックは LIFO、キューは FIFO の抽象データ型である。Python ではスタックに ``list``、キューに ``collections.deque`` を使う。
* ハッシュ表はハッシュ関数でキーをバケットに割り当て、検索・挿入・削除を平均 :math:`O(1)` で行う。衝突はチェイン法かオープンアドレス法で解決し、負荷率を一定以下に保つ。Python の ``dict`` と ``set`` はハッシュ表である。
* ループの中で ``list`` に ``in`` を使うと隠れた二重ループになる。検索を繰り返すなら ``set`` や ``dict`` に変換する。
* 二分探索木の操作は木の高さに比例する。挿入順によっては高さが :math:`n` になるため、高さを :math:`O(\log n)` に保つ平衡木が使われる。
* 二分ヒープは配列で表した完全二分木で、優先度付きキューの追加と最小値の取り出しを :math:`O(\log n)` で行う。Python では ``heapq`` を使う。
* グラフは隣接行列か隣接リストで表す。多くの実際のグラフは疎なので、通常は隣接リストを使う。
* LRU キャッシュは、ハッシュ表でキーからノードを引き、双方向連結リストで使われた順序を管理することで、取得と追加を平均 :math:`O(1)` で行う。Python では ``OrderedDict`` で実装でき、関数の結果のキャッシュには ``functools.lru_cache`` を使う。
* トライは文字列を 1 文字ずつたどる木で、検索が文字列の長さだけで決まり、接頭辞検索が得意である。
* Union-Find は経路圧縮とランクによる併合により、グループの併合と同じグループかの判定を実用上ほぼ定数の償却計算量で行う。
* ブルームフィルタはビット配列と複数のハッシュ関数で集合を表し、偽陽性を許す代わりに非常に少ないメモリで「含まれない」ことを確実に判定する。
