コンピュータの構成
==================

前章では、論理ゲートから加算器やレジスタを作れることを見た。この章では、それらの部品を組み合わせて、プログラムを実行する機械としてのコンピュータがどのように構成されているかを学ぶ。まず、現在のほぼすべてのコンピュータの基礎であるノイマン型アーキテクチャを説明し、CPU の内部構成、命令セット、命令実行サイクルを見ていく。簡易 CPU のエミュレータを動かして、命令が 1 つずつ実行される様子も確かめる。続いて、CPU を高速化するパイプラインと分岐予測を紹介し、さらに、性能を大きく左右するメモリ階層とキャッシュを扱う。キャッシュの振る舞いを知ることは、データ量の多い処理を高速化するうえで欠かせない。最後に、複数のコアを持つマルチコアプロセッサと、コアどうしでキャッシュの内容を一致させる仕組み、並列化による高速化の限界を示すアムダールの法則、そして SIMD と GPU による並列処理を紹介する。

ノイマン型アーキテクチャ
------------------------

プログラム内蔵方式
^^^^^^^^^^^^^^^^^^

初期の電子計算機である ENIAC（1946 年）では、計算の手順を変えるたびに配線を差し替える必要があった。これに対して、プログラムをデータと同じようにメモリに格納し、そこから命令を順に読み出して実行する方式が考え出された。これを\ :term:`プログラム内蔵方式`\ （stored-program concept）と呼ぶ。1945 年にジョン・フォン・ノイマンが執筆した EDVAC（ENIAC の後継機）に関する報告書の草稿でこの方式が体系的に記述されたことから、この方式に基づくコンピュータの構成を\ :term:`ノイマン型アーキテクチャ`\ （von Neumann architecture）と呼ぶ。

ノイマン型アーキテクチャのコンピュータは、次の要素から構成される。

* :term:`CPU`\ （Central Processing Unit、中央処理装置）: 命令を解釈して演算を行う。演算装置と制御装置からなる。
* 主記憶（メモリ）: 命令とデータを、区別せずに番地付きで格納する。
* 入出力装置: キーボード、ディスプレイ、ストレージ、ネットワークなどの外部とのやり取りを行う。
* バス: これらの要素の間でアドレス、データ、制御信号を伝える信号線の束である。

プログラム内蔵方式の本質は、命令もデータも同じメモリ上のビット列にすぎない、という点にある。これにより、プログラムを読み込み直すだけで別の計算ができ、さらに、プログラムを生成・変換するプログラム（コンパイラ、ローダ、JIT コンパイラなど）が可能になった。一方で、データとして書き込まれたビット列が命令として実行されうることは、セキュリティ上の弱点にもなる。バッファオーバーフローの脆弱性で外部から送り込まれたデータが命令として実行される攻撃はその典型であり、現在の OS と CPU は、メモリの領域ごとに「書き込み可能だが実行不可」のような属性を付けて対策している（NX ビット。こうした属性を管理するページテーブルは「:doc:`ch08_operating_systems`」で扱う）。

ノイマン・ボトルネック
^^^^^^^^^^^^^^^^^^^^^^

ノイマン型アーキテクチャでは、CPU は命令もデータもバスを通じてメモリから読み出さなければならない。CPU の演算速度が向上するにつれ、CPU とメモリの間のデータ転送が性能の上限を決めるようになった。これをノイマン・ボトルネックと呼ぶ。後述するキャッシュは、この問題を緩和するための仕組みである。

命令用とデータ用のメモリを物理的に分けた構成をハーバード・アーキテクチャと呼ぶ。命令とデータを同時に読み出せるため、組み込み向けのマイクロコントローラや信号処理用のプロセッサで使われている。現在の汎用 CPU は、主記憶は共通にしつつ、CPU に最も近いキャッシュだけを命令用とデータ用に分けた折衷的な構成を取ることが多い。

CPU の構成
----------

CPU の内部は、大きく次の 4 つの要素に分けられる。

.. list-table:: CPU の主な構成要素
   :header-rows: 1
   :widths: 25 75

   * - 要素
     - 役割
   * - ALU（算術論理演算装置）
     - 加算、減算、AND、OR、シフト、比較などの演算を行う組み合わせ回路
   * - レジスタ
     - CPU 内部の高速な記憶領域。演算の入力と結果を一時的に保持する
   * - プログラムカウンタ
     - 次に実行する命令のアドレスを保持するレジスタ
   * - 制御装置
     - 命令を解釈し、各部品に制御信号を送って命令を実行させる

:term:`ALU`\ （Arithmetic Logic Unit、算術論理演算装置）は、前章で見た加算器や論理ゲートを組み合わせた回路である。2 つの入力と、どの演算を行うかを指定する信号を受け取り、演算結果を出力する。同時に、結果が 0 か、負か、桁上げやオーバーフローが生じたかといった情報をフラグとして出力し、これらはステータスレジスタ（フラグレジスタ）に記録される。条件分岐命令は、このフラグを見て分岐するかどうかを決める。

CPU のレジスタには、プログラムが自由に使える汎用レジスタと、特定の用途を持つレジスタがある。x86-64 には 64 ビットの汎用レジスタが 16 個、RISC-V や ARM の AArch64 には 31〜32 個ある。レジスタはフリップフロップで作られ、1 クロックで読み書きできるが、数が限られる。コンパイラは、よく使う変数をできるだけレジスタに割り当てる（レジスタ割り付け）ことで、遅いメモリへのアクセスを減らしている。

:term:`プログラムカウンタ`\ （PC: Program Counter）は、次に実行する命令のアドレスを保持する特別なレジスタである。x86 では命令ポインタ（IP: Instruction Pointer）とも呼ぶ。通常は命令を 1 つ読み出すたびにその命令の長さだけ進み、分岐命令が実行されると分岐先のアドレスに書き換えられる。プログラムの「現在位置」はプログラムカウンタの値そのものである。

:term:`制御装置`\ （control unit）は、メモリから読み出した命令のビット列を解釈（デコード）し、どのレジスタを読み出すか、ALU にどの演算をさせるか、結果をどこに書き込むかといった制御信号を生成する。前章のマルチプレクサの選択信号やレジスタの書き込み許可信号を、命令に応じて切り替えるのが制御装置の仕事である。

命令セット
----------

機械語とアセンブリ言語
^^^^^^^^^^^^^^^^^^^^^^

CPU が直接実行できる命令の集合と、その形式・動作の取り決めを\ :term:`命令セットアーキテクチャ`\ （ISA: Instruction Set Architecture）と呼ぶ。ISA はハードウェアとソフトウェアの間の契約であり、同じ ISA に従う CPU であれば、内部の回路が異なっても同じプログラムを実行できる。x86-64、AArch64（ARM の 64 ビット ISA）、RISC-V が現在の代表的な ISA である。

CPU が実行する命令はビット列であり、これを\ :term:`機械語`\ （machine code）と呼ぶ。機械語は人間には読みにくいため、各命令を英単語の略号（ニーモニック）で表した\ :term:`アセンブリ言語`\ （assembly language）が使われる。アセンブリ言語を機械語に変換するプログラムをアセンブラと呼ぶ。次は、1 から 10 までの和を計算する RISC-V のアセンブリ言語のプログラムである。

.. code-block:: text
   :linenos:

       li   t0, 0         # t0 <- 0（合計）
       li   t1, 10        # t1 <- 10（カウンタ）
   loop:
       add  t0, t0, t1    # t0 <- t0 + t1
       addi t1, t1, -1    # t1 <- t1 - 1
       bnez t1, loop      # t1 が 0 でなければ loop へ分岐

``t0``、``t1`` はレジスタの名前である。4 行目の ``add t0, t0, t1`` は、機械語では 32 ビットの値 ``0x006282b3`` になる。これを 2 進数で書くと ``0000000 00110 00101 000 00101 0110011`` であり、右から順に命令の種類（オペコード、7 ビット）、書き込み先のレジスタ番号（5 ビット、``t0`` は 5 番）、演算の種類の細分（3 ビット）、1 つ目の入力レジスタ番号（5 ビット）、2 つ目の入力レジスタ番号（5 ビット、``t1`` は 6 番）、演算の種類の細分（7 ビット）を表す。制御装置はこれらのビットを切り出して、各部品への制御信号に変換する。

C や Rust などのコンパイラは、ソースコードをこのような機械語に変換する。Python や Java は、まず仮想機械の命令（バイトコード）に変換し、それをインタプリタや JIT コンパイラが実行する。CPython のバイトコードは ``dis`` モジュールで表示でき、そこでも本章と同じく「命令を 1 つずつ取り出して実行する」仕組みが動いている（「:doc:`ch07_programming_languages`」で扱う）。

RISC と CISC
^^^^^^^^^^^^

ISA の設計思想は、大きく 2 つに分けられる。

:term:`CISC`\ （Complex Instruction Set Computer）は、1 つの命令で複雑な処理を行えるようにした設計である。メモリ上の値を直接演算の対象にでき、命令の長さも可変である。x86 はその代表で、命令の長さは 1〜15 バイトと幅がある。メモリが高価で、プログラムを少ない命令で書くことが重視された時代の設計である。

:term:`RISC`\ （Reduced Instruction Set Computer）は、命令を単純で規則的なものに限定した設計である。演算はレジスタ間だけで行い、メモリとの間の転送はロード命令とストア命令に限る（ロード・ストア方式）。命令の長さは固定（RISC-V や AArch64 の基本命令は 32 ビット）で、デコードが容易である。命令数は増えるが、各命令を高速に、かつ後述のパイプラインで効率よく実行できる。ARM、RISC-V、MIPS などがこの設計に属する。

.. list-table:: RISC と CISC の比較
   :header-rows: 1
   :widths: 20 40 40

   * - 観点
     - RISC
     - CISC
   * - 命令の長さ
     - 固定長（例: 32 ビット）
     - 可変長（x86 では 1〜15 バイト）
   * - メモリアクセス
     - ロード命令とストア命令だけ
     - 多くの命令がメモリを直接扱える
   * - 汎用レジスタの数
     - 多い（32 個程度）
     - 少ない（x86-64 で 16 個）
   * - 代表的な ISA
     - AArch64、RISC-V
     - x86-64

ただし、現在では両者の違いは内部の実装では小さくなっている。x86-64 の CPU は、内部で複雑な命令を RISC 風の単純な命令（マイクロ命令、μop）に分解してから実行しており、RISC の ISA にも次第に多くの命令が追加されてきた。実務上の大きな違いは、ISA ごとに機械語が異なるため、プログラムをその ISA 向けにコンパイルしなければならない点である。Apple Silicon の Mac（AArch64）やクラウドの ARM 系インスタンスの CPU は x86-64 向けのバイナリを直接実行できない（Mac の Rosetta 2 のような変換の仕組みを介せば動かせるが、性能は落ちる）。Docker イメージやネイティブ拡張を含む Python パッケージを ISA ごとに用意する必要があるのはこのためである。

命令実行サイクル
----------------

フェッチ・デコード・実行
^^^^^^^^^^^^^^^^^^^^^^^^

CPU は、電源が入っている間、次の手順を繰り返す。これを\ :term:`命令実行サイクル`\ （instruction cycle）と呼ぶ。

#. フェッチ（fetch）: プログラムカウンタが指すアドレスから命令を読み出し、プログラムカウンタを次の命令のアドレスに進める。
#. デコード（decode）: 命令のビット列を解釈し、命令の種類と、使うレジスタやアドレスを特定する。
#. 実行（execute）: ALU で演算を行う、メモリを読み書きする、プログラムカウンタを書き換える（分岐）などの動作を行う。
#. 書き戻し（write back）: 結果をレジスタに書き込む。

教科書によっては、メモリアクセスや書き戻しを実行に含めて「フェッチ・デコード・実行」の 3 段階として説明する。いずれにしても、プログラムの実行とは、この単純なサイクルの繰り返しにすぎない。if 文やループのような制御構造は、条件によってプログラムカウンタを書き換える分岐命令として実現される。関数呼び出しも、戻り先のアドレスを保存してから関数の先頭に分岐し、終わったら保存したアドレスに分岐し直す、という操作である。

簡易 CPU のエミュレータ
^^^^^^^^^^^^^^^^^^^^^^^

次のサンプルは、4 個のレジスタ（``r0``〜``r3``）、プログラムカウンタ、ゼロフラグを持つ簡易 CPU を Python で表したものである。命令は 7 種類で、プログラムとデータは同じリスト（メモリ）に置かれている。

.. list-table:: 簡易 CPU の命令
   :header-rows: 1
   :widths: 25 75

   * - 命令
     - 動作
   * - ``LOADI x, y``
     - レジスタ ``rx`` に値 ``y`` を入れる（即値ロード）
   * - ``LOAD x, y``
     - メモリの ``y`` 番地の値をレジスタ ``rx`` に読み込む
   * - ``STORE x, y``
     - レジスタ ``rx`` の値をメモリの ``y`` 番地に書き込む
   * - ``ADD x, y``
     - ``rx`` に ``rx + ry`` を入れ、結果が 0 ならゼロフラグを立てる
   * - ``SUB x, y``
     - ``rx`` に ``rx - ry`` を入れ、結果が 0 ならゼロフラグを立てる
   * - ``JNZ x, y``
     - ゼロフラグが立っていなければ ``y`` 番地に分岐する（``x`` は使わない）
   * - ``HALT``
     - 停止する

パイプライン
------------

パイプラインの考え方
^^^^^^^^^^^^^^^^^^^^

命令実行サイクルの各段階は、CPU の異なる部分の回路を使う。フェッチは命令メモリ、デコードは制御装置、実行は ALU を使う。1 つの命令が全段階を終えるまで次の命令を待たせると、各段階の回路はほとんどの時間遊んでいることになる。

そこで、命令の処理を複数の段階（ステージ）に分け、ある命令が実行段階にある間に、次の命令のデコードと、さらに次の命令のフェッチを同時に行う。これを\ :term:`パイプライン`\ （pipeline）と呼ぶ。洗濯で、1 回目の洗濯物を乾燥機に入れている間に 2 回目を洗濯機で洗うのと同じ考え方である。典型的な RISC の 5 段パイプラインは、命令フェッチ（IF）、デコードとレジスタ読み出し（ID）、実行（EX）、メモリアクセス（MEM）、レジスタへの書き戻し（WB）の 5 ステージからなる。

     - ID
     - EX
     - MEM
     - WB

1 つの命令にかかる時間（レイテンシ）は 5 サイクルのままだが、パイプラインが満たされた状態では、毎サイクル 1 つの命令が完了する。つまり、単位時間あたりに完了する命令の数（スループット）が最大 5 倍になる。また、各ステージの回路は短くなるので、クロック周期を短くできる。

ハザード
^^^^^^^^

パイプラインが理想どおりに動かず、次の命令を予定どおりに進められなくなる状況を\ :term:`ハザード`\ （hazard）と呼ぶ。ハザードには次の 3 種類がある。

* 構造ハザード: 複数の命令が同じ回路（例えばメモリの読み出し口）を同時に使おうとして衝突する。回路を複製する（命令用とデータ用のキャッシュを分けるなど）ことで避ける。
* データハザード: ある命令が、直前の命令の結果をまだ書き戻される前に必要とする。例えば ``add t0, t0, t1`` の直後に ``t0`` を使う命令があると、その命令の ID ステージの時点では ``t0`` の新しい値がまだレジスタに書き込まれていない。EX ステージの結果を次の命令に直接回すフォワーディング（バイパス）で多くの場合は解決できるが、メモリからのロードの結果を直後に使う場合などは、パイプラインを 1 サイクル以上止める（ストール）必要がある。
* 制御ハザード: 分岐命令の結果が分かるまで、次にどの命令をフェッチすべきかが分からない。

分岐予測
^^^^^^^^

制御ハザードへの対策として、分岐の結果を予想して先の命令の処理を進めておく方法がある。これを\ :term:`分岐予測`\ （branch prediction）と呼ぶ。予測が当たれば遅れは生じず、外れた場合は途中まで進めた命令を破棄して正しい分岐先からやり直す。現在の CPU は、過去の分岐の履歴から規則性を学習する高度な分岐予測器を持ち、ループの繰り返しのような規則的な分岐ではほぼ 100% 予測を的中させる。

現在の高性能な CPU のパイプラインは 15〜20 段程度と深く、さらに 1 サイクルに複数の命令を発行するスーパースカラや、命令の順序を入れ替えて空いている回路を使うアウトオブオーダー実行も組み合わされている。そのため、予測が外れたときの損失（ペナルティ）は 10〜20 サイクル程度、その間に実行できたはずの命令数では数十命令分にもなる。データによって結果が不規則に変わる分岐（例えば、0〜255 のランダムな値の配列に対する ``if x > 128:``）は予測が外れやすく、同じ処理でも配列をあらかじめ並べ替えておくだけで高速になる、という現象が C や Java のプログラムで観察される。性能が重要な内側のループでは、分岐を条件付き転送命令や算術演算で置き換える（分岐をなくす）最適化が行われることもある。

.. note::

   分岐予測と投機的実行（予測に基づいて先の命令を実行しておくこと）は、2018 年に公表された Spectre と呼ばれる脆弱性の原因となった。予測が外れて破棄された命令の実行でも、そのときに読み込まれたデータがキャッシュに痕跡として残るため、アクセス時間の差を測ることで本来読めないはずのデータを推測できる。性能のための仕組みが、思わぬ形で安全性に影響する例である。

メモリ階層とキャッシュ
----------------------

メモリ階層
^^^^^^^^^^

記憶装置には、速いものほど高価で容量が小さく、遅いものほど安価で容量が大きいという関係がある。そこで、CPU に近いところに小さく速い記憶装置を、遠いところに大きく遅い記憶装置を置き、よく使うデータを近くに置くことで、全体として「大きくて速い」記憶装置のように見せる。この構成を\ :term:`メモリ階層`\ （memory hierarchy）と呼ぶ。次の表は、各階層のアクセス時間のおおよその桁を示したものである。具体的な値は製品や世代によって異なるが、桁の感覚を持っておくことが重要である [HP]_。

.. list-table:: メモリ階層とアクセス時間の目安
   :header-rows: 1
   :widths: 25 20 25 30

   * - 階層
     - 容量の目安
     - アクセス時間の目安
     - 備考
   * - レジスタ
     - 数百バイト〜数 KB
     - 1 サイクル未満〜1 サイクル
     - CPU コア内部
   * - L1 キャッシュ
     - 数十 KB
     - 約 1 ns（4 サイクル程度）
     - コアごと。命令用とデータ用に分かれる
   * - L2 キャッシュ
     - 数百 KB〜数 MB
     - 約 3〜5 ns
     - コアごとが多い
   * - L3 キャッシュ
     - 数 MB〜数百 MB
     - 約 10〜20 ns
     - 複数のコアで共有
   * - 主記憶（DRAM）
     - 数 GB〜数 TB
     - 約 50〜100 ns
     -
   * - SSD（NVMe）
     - 数百 GB〜数十 TB
     - 約 10〜100 μs
     - 補助記憶
   * - HDD
     - 数 TB〜数十 TB
     - 約 5〜10 ms
     - 補助記憶。ヘッドの移動を伴う

L1 キャッシュと主記憶の間には約 100 倍、主記憶と SSD の間には約 1000 倍、SSD と HDD の間にもさらに約 100 倍の差がある。L1 キャッシュへのアクセスを 1 秒とすると、主記憶へのアクセスは 1〜2 分、SSD は数時間〜1 日、HDD は数か月に相当する。データベースのインデックスやアプリケーションのキャッシュ（Redis など）が性能に大きく効くのも、遅い階層へのアクセスを減らすという、同じ原理に基づいている。

参照の局所性
^^^^^^^^^^^^

メモリ階層が有効に働くのは、プログラムのメモリアクセスに偏りがあるからである。この性質を\ :term:`参照の局所性`\ （locality of reference）と呼び、次の 2 種類がある。

* 時間的局所性: 一度アクセスしたデータには、近いうちに再びアクセスする可能性が高い。ループの中で繰り返し使う変数や、ループ本体の命令がその例である。
* 空間的局所性: あるアドレスにアクセスすると、その近くのアドレスにも近いうちにアクセスする可能性が高い。配列を先頭から順に処理する場合や、命令を順に実行する場合がその例である。

キャッシュの仕組み
^^^^^^^^^^^^^^^^^^

:term:`キャッシュ`\ （cache）は、主記憶の内容の一部の複製を保持する、小さく高速な記憶装置である。CPU がメモリを読み出すとき、まずキャッシュを調べ、目的のデータがあれば（ヒット）すぐに使い、無ければ（ミス）主記憶から読み込んでキャッシュに格納する。全アクセスのうちヒットした割合をヒット率と呼ぶ。平均アクセス時間は、ヒット時の時間 :math:`t_h`、ミス率 :math:`m`、ミス時の追加の時間（ミスペナルティ）\ :math:`t_p` を使って次のように表せる。

.. math::

   t_{\mathrm{avg}} = t_h + m \times t_p

例えば :math:`t_h = 1` ns、:math:`t_p = 100` ns とすると、ヒット率が 99%（:math:`m = 0.01`）なら平均 2 ns、90% なら平均 11 ns となる。ヒット率のわずかな違いが性能に大きく影響することが分かる。

キャッシュと主記憶の間のデータ転送は、1 バイト単位ではなく、\ :term:`キャッシュライン`\ （cache line）と呼ばれる連続した領域の単位で行われる。多くの CPU ではキャッシュラインの大きさは 64 バイトである。8 バイトの整数の配列を先頭から順に読むと、最初の要素でミスが起きて 64 バイト（8 要素分）がまとめて読み込まれ、続く 7 要素はヒットする。これが空間的局所性を活かす仕組みである。さらに CPU は、連続したアクセスのパターンを検出すると、次のキャッシュラインを先回りして読み込む（ハードウェアプリフェッチ）。

主記憶のどのブロックをキャッシュのどこに置くかの方式には、各ブロックの置き場所を 1 か所に決める直接写像方式、どこにでも置ける完全連想方式、その中間で数か所（例えば 8 か所）のうちのどこかに置けるセットアソシアティブ方式がある。直接写像方式では、アドレスをラインの大きさで割ったブロック番号を、ライン数で割った余りで置き場所を決める。回路は単純だが、置き場所が同じになるブロックに交互にアクセスすると、互いに追い出し合ってミスが続く（競合ミス）。現在の CPU のキャッシュの多くはセットアソシアティブ方式である。

アクセス順序とヒット率
^^^^^^^^^^^^^^^^^^^^^^

2 次元配列の要素を、行ごとに走査する場合と列ごとに走査する場合を比べてみる。C や NumPy（既定の設定）は、2 次元配列を行優先（row-major）でメモリに配置する。つまり ``a[i][j]`` と ``a[i][j+1]`` が隣り合うアドレスになる。この場合、行ごとの走査は連続したアドレスに順にアクセスするが、列ごとの走査は 1 行分の大きさだけ離れたアドレスに飛び飛びにアクセスする。

Python のリストのリストで同じことを試しても、差ははっきりとは現れない。Python のリストは要素のオブジェクトへのポインタの配列であり、オブジェクト自体はメモリ上のあちこちに置かれるうえ、インタプリタの処理にかかる時間が支配的だからである。そこで次のサンプルでは、実行時間を測る代わりに、直接写像方式のキャッシュをシミュレートし、アクセスするアドレスの列からヒット率を計算する。キャッシュの大きさは 32 KiB（64 バイトのラインが 512 個）とし、8 バイトの要素が 512 行 512 列並んだ 2 MiB の配列を走査する。

.. literalinclude:: ../examples/ch03_cache_locality.py
   :language: python
   :linenos:
   :caption: ch03_cache_locality.py

:download:`ch03_cache_locality.py <../examples/ch03_cache_locality.py>`

29〜31 行目で、アドレスからブロック番号、キャッシュ上の位置（インデックス）、同じ位置を共有するブロックを区別するためのタグを計算している。32 行目で、その位置に同じタグのブロックがあればヒットとする。43〜47 行目と 50〜61 行目は、それぞれ行優先と列優先で走査したときのアドレスを順に生成する。実行結果は次のとおりである。

.. code-block:: text
   :linenos:

   配列: 512 x 512、要素 8 バイト、キャッシュ: 64 バイト x 512 ライン
   行優先: ヒット 229376 回、ミス  32768 回、ヒット率 87.5%
   列優先: ヒット      0 回、ミス 262144 回、ヒット率 0.0%
   列優先（詰め物あり）: ヒット 229376 回、ミス  32768 回、ヒット率 87.5%

2 行目の行優先では、8 要素ごとに 1 回ミスが起き、残りの 7 回はヒットするので、ヒット率は :math:`7/8 = 87.5\%` になる。3 行目の列優先では、すべてのアクセスがミスになった。1 行は :math:`512 \times 8 = 4096` バイトで、これはライン 64 個分にあたる。そのため、同じ列を縦にたどると、インデックスは 64 ずつ進み、512 行のアクセスがわずか 8 か所のラインに集中して互いに追い出し合う。次の列の要素は同じキャッシュラインに入っているはずだが、戻ってきたときには既に追い出されている。

4 行目は、各行の末尾に 8 要素（64 バイト）の使わない領域（詰め物、パディング）を置き、行の間隔を 4160 バイト（ライン 65 個分）にした場合である。65 と 512 は互いに素なので、同じ列の 512 行はキャッシュの 512 か所のラインに 1 つずつ散らばり、次の列のアクセスでヒットするようになる。ただし、これはキャッシュの容量にちょうど収まる特別な場合であり、行数が 512 を超えると容量不足によるミスが起きる。列優先の走査が遅いという問題の本質的な解決は、アクセスの順序をデータの配置に合わせることである。

.. note::

   実際の CPU のキャッシュはセットアソシアティブ方式でプリフェッチもあるため、このシミュレーションほど極端な差にはならない。それでも、C や NumPy で大きな 2 次元配列を列優先で走査すると、行優先に比べて数倍以上遅くなることは珍しくない。行列の大きさが 2 の累乗のときに性能が急に悪化する現象も、ここで見た競合ミスによって起こることがある。

キャッシュを意識したデータ配置
^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^

キャッシュの性質は、データ構造やプログラムの書き方の選択に影響する。実務で意識すべき点をいくつか挙げる。

* 配列を走査するループは、メモリ上の配置の順にアクセスする。NumPy では配列が行優先（C 順序）か列優先（Fortran 順序）かを ``flags`` 属性で確認でき、軸の指定によってアクセスの順序が変わる。Fortran、MATLAB、R は列優先で配列を配置する。
* 連結リストや木のように、ポインタでたどるデータ構造は、各ノードがメモリ上に散らばるため空間的局所性が低い。要素数が同じでも、配列の走査より大幅に遅くなることがある（「:doc:`ch04_data_structures`」で扱う）。計算量が同じなら、連続した配列を使うデータ構造の方が速いことが多い。
* 多数のオブジェクトの一部の属性だけを処理する場合、オブジェクトごとに全属性をまとめる配置（AoS: Array of Structures）より、属性ごとに配列を分ける配置（SoA: Structure of Arrays）の方が、必要なデータだけを連続して読める。分析用のデータベースが列指向の格納形式を採用し、Parquet のような列指向のファイル形式が使われるのも同じ理由である。
* 複数のスレッドが、同じキャッシュラインに載った別々の変数を頻繁に書き換えると、コア間でキャッシュラインの所有権が行き来して大幅に遅くなる。これを偽共有（false sharing）と呼ぶ。偽共有が起こる仕組みは「:ref:`ch03-false-sharing`」で説明する。

キャッシュの詳しい解説と、キャッシュを意識したプログラムの書き方は [CSAPP]_ の第 6 章にある。

マルチコアと並列処理
--------------------

マルチコアプロセッサ
^^^^^^^^^^^^^^^^^^^^

2000 年代の前半まで、CPU の性能はおもにクロック周波数の向上と、パイプラインやスーパースカラのような 1 つの命令の流れを速く実行する工夫によって伸びてきた。しかし、クロック周波数を上げると消費電力と発熱が急激に増えるため、周波数は数 GHz で頭打ちになった。そこで、半導体の微細化で増え続けるトランジスタを、1 つの CPU チップに複数の処理装置を載せることに使うようになった。命令を実行する 1 組の回路（パイプライン、レジスタ、ALU、L1・L2 キャッシュなど）を\ **コア**\ （core）と呼び、複数のコアを 1 つのチップに載せたプロセッサを\ :term:`マルチコアプロセッサ`\ （multi-core processor）と呼ぶ。現在では、スマートフォンでも 6〜8 コア、サーバ用の CPU では 100 コアを超える製品がある。

各コアは独立に命令を実行できるので、OS は複数のプロセスやスレッドをそれぞれ別のコアに割り当てて同時に実行させる。メモリ階層の表で見たように、L1 と L2 のキャッシュはコアごとに持つことが多く、L3 キャッシュと主記憶は複数のコアで共有する。スマートフォンや最近の PC の CPU には、高性能なコアと省電力のコアを組み合わせて、処理の重さに応じて使い分けるものもある。

1 つのコアで複数のスレッドを同時に実行する技術もある。これを :term:`SMT`\ （Simultaneous Multithreading、同時マルチスレッディング）と呼び、Intel の CPU では Hyper-Threading という名前で知られている。SMT のコアは、プログラムカウンタやレジスタをスレッドの数（多くは 2 つ）だけ持ち、ALU などの実行用の回路は共有する。一方のスレッドがキャッシュミスで主記憶からのデータを待っている間も、もう一方のスレッドの命令で実行用の回路を埋められる。OS からは 1 つのコアが 2 つのプロセッサ（論理プロセッサ、ハードウェアスレッド）に見えるが、実行用の回路は 1 組なので、性能は 2 倍にはならず、典型的には数十% の向上にとどまる。キャッシュを奪い合って、かえって遅くなる処理もある。Python の ``os.cpu_count()`` が返すのは論理プロセッサの数なので、物理的なコアの数とは異なることがある。

キャッシュコヒーレンシ
^^^^^^^^^^^^^^^^^^^^^^

各コアが自分のキャッシュを持つと、新しい問題が生じる。コア 0 とコア 1 が同じアドレスの値をそれぞれのキャッシュに読み込んだ後、コア 0 がその値を書き換えると、コア 1 のキャッシュには古い値が残ってしまう。複数のキャッシュが同じアドレスについて矛盾した値を持たないようにすることを\ :term:`キャッシュコヒーレンシ`\ （cache coherence、キャッシュの一貫性）と呼び、マルチコアプロセッサはこれをハードウェアで保証している。

代表的な方式である MESI プロトコルでは、各キャッシュの各キャッシュラインが次の 4 つの状態のどれかを取る。

.. list-table:: MESI プロトコルの状態
   :header-rows: 1
   :widths: 20 80

   * - 状態
     - 意味
   * - M（Modified）
     - このキャッシュだけが持ち、書き換えられていて主記憶の内容とは異なる
   * - E（Exclusive）
     - このキャッシュだけが持ち、主記憶の内容と同じ
   * - S（Shared）
     - 複数のキャッシュが持っている可能性があり、主記憶の内容と同じ。読み出しだけができる
   * - I（Invalid）
     - 無効（このキャッシュラインは有効なデータを持たない）

あるコアが S の状態のキャッシュラインに書き込むときは、まず他のコアに無効化を要求して、他のキャッシュの同じラインを I にしてから、自分のラインを M にする。他のコアが M の状態のラインを読もうとすると、そのラインを持つコアが最新の内容を提供し、両方のラインが S になる。E の状態のラインは自分だけが持っていると分かっているので、他のコアと通信せずに書き込んで M にできる。コア間の通信は、すべてのキャッシュがやり取りを監視する方式（スヌープ方式）や、どのキャッシュがどのラインを持っているかを表で管理する方式（ディレクトリ方式）で行う。実際の CPU は、MESI に状態を追加した MESIF や MOESI などを使っている。

ここで重要なのは、コヒーレンシの管理がキャッシュライン単位で行われること、そして他のコアが持っているラインへの書き込みにはコア間の通信が必要で、L1 キャッシュへのアクセスより 1 桁以上遅いことである。複数のコアが同じデータを頻繁に書き換えると、そのキャッシュラインがコアの間を行き来して性能が大きく落ちる。

.. _ch03-false-sharing:

偽共有
^^^^^^

コヒーレンシの管理はキャッシュライン単位なので、複数のスレッドが論理的には別々の変数を書き換えているだけでも、それらの変数が同じキャッシュラインに載っていると、ラインの奪い合いが起こる。これを\ :term:`偽共有`\ （false sharing）と呼ぶ。例えば、8 つのスレッドがそれぞれ自分の担当の要素に件数を加算していくために、8 バイトの整数 8 個の配列を用意したとする。配列全体の 64 バイトがちょうど 1 つのキャッシュラインに収まるため、あるスレッドが自分の要素に書き込むたびに、他のコアのキャッシュの同じラインが無効化される。各スレッドは他のスレッドのデータを一切読んでいないにもかかわらず、加算のたびにキャッシュミスが起き、1 スレッドで実行するより遅くなることさえある。

偽共有を避けるには、スレッドごとに頻繁に書き換える変数を別々のキャッシュラインに置く。変数の間に詰め物を入れる、変数をキャッシュラインの大きさの境界に配置する（C++ の ``alignas``、Java の ``@Contended`` など）、各スレッドが自分の局所変数で集計して最後に一度だけ共有の変数に書き込む、といった方法がある。最後の方法は、共有データへの書き込みの回数そのものを減らすので、偽共有に限らず効果が大きい。なお、Python のオブジェクトはメモリ上のあちこちに置かれ、さらに「:ref:`ch09-gil`」で扱う GIL があるので、純粋な Python のコードで偽共有が問題になることはまずない。C、C++、Rust、Java、Go などで性能を詰めるときに意識すべき現象である。

並列化の限界とアムダールの法則
^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^

コアの数を 2 倍にしても、プログラムが 2 倍速くなるとは限らない。プログラムには、入力の読み込み、結果の集約、処理の順序に依存関係がある部分など、並列に実行できない部分（逐次部分）が必ず含まれるからである。1 コアで実行したときの実行時間のうち、並列化できる部分の割合を :math:`p`\ （:math:`0 \le p \le 1`）とする。この部分を :math:`n` 個のコアで完全に分担でき、逐次部分 :math:`1 - p` はそのまま残るとすると、速度向上率（1 コアのときの実行時間を :math:`n` コアのときの実行時間で割った値）は次の式で表される。これを\ :term:`アムダールの法則`\ （Amdahl's law）と呼ぶ [Amdahl1967]_。

.. math::

   S(n) = \frac{1}{(1 - p) + \dfrac{p}{n}}

コアの数 :math:`n` を無限に大きくしても、:math:`p/n` が 0 に近づくだけで、逐次部分の :math:`1 - p` は残る。したがって、速度向上率には次の上限がある。

.. math::

   \lim_{n \to \infty} S(n) = \frac{1}{1 - p}

例えば :math:`p = 0.95`\ （実行時間の 95% を並列化できる）のとき、8 コアでの速度向上率は :math:`1 / (0.05 + 0.95 / 8) = 1 / 0.16875 \approx 5.93` であり、どれだけコアを増やしても 20 倍を超えられない。次のサンプルは、いくつかの :math:`p` と :math:`n` について速度向上率を計算して表にする。コア 1 個あたりの効率 :math:`S(n)/n` と、目標の速度向上率に必要なコアの数も求める。必要なコアの数は、:math:`S(n) = S` を :math:`n` について解いた :math:`n = p / (1/S - (1 - p))` から求める。

4 行目のとおり、90% を並列化できるプログラムでも、1024 コアで 9.91 倍にしかならない。そのときの効率は 10 行目のとおり 1.0% であり、ほとんどのコアは逐次部分の終わりを待って遊んでいる。6 行目と 12 行目の :math:`p = 0.99` でも、64 コアでの効率は 61.3% まで落ちる。14〜17 行目では、10 倍速にするのに :math:`p = 0.99` なら 11 コアで足りるが、:math:`p = 0.95` では 19 コア必要になり、:math:`p = 0.9` では上限がちょうど 10 倍なので、どれだけコアを増やしても達成できない。わずかな逐次部分が並列化の効果を大きく制限することが分かる。

実際のプログラムでは、スレッドの生成、データの分配と集約、排他制御の待ち、コア間の通信（前述のキャッシュラインの行き来を含む）といった、並列化そのものに伴うオーバーヘッドも加わるので、速度向上率はこの表の値よりさらに低くなる。並列化で高速化したいときは、まずプロファイラで逐次部分がどれだけあるかを測り、そこを減らすことを考えるべきである。

.. note::

   アムダールの法則は、問題の大きさを固定して、コアを増やしたときにどれだけ速くなるかを考えている。これに対し、コアが増えた分だけ大きな問題を同じ時間で解く、という見方もある。この場合、逐次部分の時間が問題の大きさによらず一定なら、並列部分の割合が大きくなるので、コアの数にほぼ比例して処理できる量が増える。この考え方はグスタフソンの法則と呼ばれ、大規模な科学技術計算やデータ処理でコアを増やす意味があることの根拠になっている。

SIMD と GPU
^^^^^^^^^^^

マルチコアは、独立した命令の流れを複数同時に実行する並列処理である。これとは別に、1 つの命令で複数のデータを同時に処理する並列処理もある。これを :term:`SIMD`\ （Single Instruction, Multiple Data）と呼ぶ。SIMD 命令は、128〜512 ビットの幅の広いレジスタに複数の値を詰めて、それらに同じ演算を一度に行う。例えば 256 ビットのレジスタには 32 ビットの浮動小数点数が 8 個入るので、1 つの加算命令で 8 組の加算ができる。x86-64 の SSE、AVX2、AVX-512、ARM の NEON や SVE がこれにあたる。コンパイラは、単純なループを SIMD 命令を使うコードに自動的に変換すること（自動ベクトル化）がある。NumPy の配列演算が Python のループより桁違いに速いのは、インタプリタを介さずに C のループで処理することに加えて、連続したメモリ上のデータを SIMD 命令でまとめて処理できるからでもある。SIMD を活かすにも、データが連続して並んでいること（前節の SoA の配置など）が重要である。

GPU（Graphics Processing Unit）は、もともと画像の描画のために作られた、SIMD の考え方を大規模に推し進めた処理装置である。1 つ 1 つは単純な数千個の演算器を持ち、同じプログラムを大量のデータに対して一斉に実行する。各コアが複雑な分岐予測やアウトオブオーダー実行を持つ CPU が、1 つの命令の流れを速く実行すること（レイテンシ）を重視するのに対し、GPU は、大量の計算を全体として速く終わらせること（スループット）を重視している。行列の積のように、同じ計算を膨大なデータに対して行う処理に向いており、機械学習や科学技術計算で広く使われている。ただし、データを主記憶から GPU のメモリに転送する時間がかかり、分岐が多く処理がデータごとに異なる計算には向かない。

並行処理への橋渡し
^^^^^^^^^^^^^^^^^^

ハードウェアが提供するのは、複数のコアと、同じアドレスについてキャッシュの内容を一致させる仕組みまでである。複数のスレッドが共有データを正しく扱えることまでは保証しない。例えば、2 つのコアが同じカウンタの値を読み、それぞれ 1 を足して書き戻すと、コヒーレンシが保たれていても、加算が 1 回分失われることがある。共有データを安全に扱うには、ソフトウェアの側で排他制御を行う必要があり、そのために CPU は、読み出しと書き込みを不可分に行う特別な命令（アトミック操作）を用意している。また、あるコアが書き込んだ値が、他のコアからどの順序で見えるかという問題（メモリの可視性）もある。排他制御は「:doc:`ch09_concurrency_and_io`」で、アトミック操作は「:ref:`ch09-atomic`」で、メモリの可視性は「:ref:`ch09-memory-model`」で扱う。CPython では、GIL のために Python のコードを実行するスレッドは同時に 1 つに限られ、CPU を多く使う処理で複数のコアを使うにはプロセスを分ける必要がある。これは「:ref:`ch09-gil`」で説明する。

まとめ
------

* ノイマン型アーキテクチャでは、命令とデータを同じメモリに格納し、CPU が命令を順に読み出して実行する（プログラム内蔵方式）。
* CPU は ALU、レジスタ、プログラムカウンタ、制御装置などから構成される。
* 命令セットアーキテクチャはハードウェアとソフトウェアの間の契約であり、機械語の形式と動作を定める。RISC は単純で規則的な命令、CISC は複雑な命令を特徴とするが、現在の実装では差が小さくなっている。
* CPU はフェッチ・デコード・実行のサイクルを繰り返してプログラムを実行する。制御構造や関数呼び出しは、プログラムカウンタの書き換えとして実現される。
* パイプラインは命令の処理を重ね合わせてスループットを上げる。ハザードによって性能が低下し、制御ハザードには分岐予測で対処する。
* メモリ階層は、小さく速い記憶装置と大きく遅い記憶装置を組み合わせる。キャッシュは参照の局所性を利用し、キャッシュライン単位でデータを転送する。データの配置とアクセスの順序をそろえることで、キャッシュのヒット率を高められる。
* マルチコアプロセッサは複数のコアで命令の流れを同時に実行し、SMT は 1 つのコアで複数のスレッドの命令を混ぜて実行する。各コアのキャッシュの内容は、MESI のようなキャッシュコヒーレンシのプロトコルによってキャッシュライン単位で一致させられる。別々の変数でも同じキャッシュラインに載っていると偽共有が起こる。
* アムダールの法則によれば、並列化できる割合が :math:`p` のとき、速度向上率はコアの数によらず :math:`1/(1 - p)` を超えない。逐次部分を減らすことが並列化の第一歩である。
* SIMD は 1 つの命令で複数のデータを処理し、GPU はこの考え方を大規模にしてスループットを高める。

CPU の設計は [PH]_ に、より高度な性能向上の手法やマルチコアのキャッシュコヒーレンシは [HP]_ に詳しい。マルチコアの上での並行プログラミングについては [Herlihy]_ がある。次の「:doc:`ch04_data_structures`」からは、ハードウェアの上で動くソフトウェアの側に移り、データを効率よく格納するための構造を学ぶ。
