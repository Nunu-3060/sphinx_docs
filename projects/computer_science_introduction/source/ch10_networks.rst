コンピュータネットワーク
========================

Web ブラウザでページを開く、API を呼び出す、データベースに接続する。現代のプログラムのほとんどは、ネットワーク越しに他のコンピュータと通信している。この章では、通信を役割ごとの層に分けて考える階層モデルから始め、リンク層、IP、TCP と UDP、DNS、HTTP の順に、データが相手に届くまでの仕組みを学ぶ。最後に、遅延と帯域の観点から通信の問題を切り分ける方法を扱う。全体の参考書としては [Kurose]_ を挙げておく。

階層モデル
----------

プロトコルと階層化
^^^^^^^^^^^^^^^^^^

通信する者同士が守る約束事を\ :term:`プロトコル`\ と呼ぶ。メッセージの形式、送る順序、エラーが起きたときの扱いなどを定めたものである。ネットワーク通信には、電気信号をビットとして送ることから、Web ページを要求することまで、多くの仕事がある。これらを 1 つのプロトコルで扱うのは難しいので、仕事を層に分け、各層は下の層が提供する機能だけを使って上の層に機能を提供する。こうしておけば、例えば有線 LAN を無線 LAN に替えても、上の層のプロトコルは変更せずに済む。

OSI 参照モデルと TCP/IP
^^^^^^^^^^^^^^^^^^^^^^^

層の分け方の代表的な枠組みが、国際標準化機構（ISO）が定めた :term:`OSI 参照モデル`\ の 7 層である。一方、インターネットで実際に使われているのは TCP/IP と呼ばれるプロトコル群で、こちらは通常 4 層で説明される。両者の対応を次の表に示す。

カプセル化
^^^^^^^^^^

送信側では、上の層から受け取ったデータに、各層が自分の制御情報（ヘッダ）を付けて下の層に渡す。これを\ :term:`カプセル化`\ と呼ぶ。受信側では逆に、各層が自分のヘッダを取り除いて上の層に渡す。各層で扱うデータの単位には次のような呼び名がある。

.. list-table::
   :header-rows: 1
   :widths: 25 25 50

   * - 層
     - データの単位
     - 付加される主な情報
   * - アプリケーション層
     - メッセージ
     - HTTP のリクエスト行やヘッダなど
   * - トランスポート層
     - セグメント（TCP）、データグラム（UDP）
     - 送信元と宛先のポート番号、シーケンス番号（TCP）
   * - インターネット層
     - パケット
     - 送信元と宛先の IP アドレス、TTL
   * - リンク層
     - フレーム
     - 送信元と宛先の MAC アドレス、誤り検出用の符号

ヘッダの大きさは、イーサネットが 14 バイト（末尾の誤り検出符号 4 バイトを除く）、IPv4 がオプション無しで 20 バイト、TCP がオプション無しで 20 バイト、UDP が 8 バイトである。イーサネットで 1 回に送れるデータの最大長（MTU: Maximum Transmission Unit）は通常 1,500 バイトなので、IPv4 と TCP のヘッダを除いた 1,460 バイトが、1 つの TCP セグメントで運べるデータの最大長（MSS: Maximum Segment Size）の典型的な値になる。ヘッダに含まれるポート番号やアドレス、長さなどの複数バイトの値は、ビッグエンディアン（ネットワークバイトオーダー）で並べると決められている（「:ref:`ch01-byte-order`」を参照）。また、イーサネットのフレームの末尾には CRC-32 による誤り検出符号が付き、IPv4、TCP、UDP のヘッダにはインターネットチェックサムの欄がある（「:ref:`ch01-coding`」を参照）。

リンク層
--------

リンク層は、同じネットワーク（ケーブルやスイッチで直接つながった範囲）にある機器同士でフレームを届ける。有線 LAN で最も広く使われている規格がイーサネットである。

イーサネットでは、各ネットワークインタフェースに割り当てられた 48 ビットの :term:`MAC アドレス`\ で送信元と宛先を表す。MAC アドレスは ``00:1a:2b:3c:4d:5e`` のように 8 ビットずつ 16 進数で書き、上位 24 ビットは製造者を表す。スイッチと呼ばれる機器は、受け取ったフレームの送信元 MAC アドレスと受信したポートの組を学習し、宛先 MAC アドレスに対応するポートにだけフレームを転送する。

MAC アドレスが意味を持つのは、同じネットワークの中だけである。別のネットワークにある相手に送るときは、宛先 MAC アドレスとして次に中継するルータのものを使い、ルータを通過するたびにリンク層のヘッダは付け替えられる。一方、IP アドレスは通信の始めから終わりまで変わらない（後述の NAT を除く）。IPv4 では、通信相手の IP アドレスから MAC アドレスを調べるために ARP（Address Resolution Protocol）を使う。

IP
--

IPv4 アドレス
^^^^^^^^^^^^^

インターネット層の中心となるプロトコルが IP（Internet Protocol）である [RFC791]_。IP は、ネットワークをまたいでパケットを宛先まで届ける。ただし、届くことは保証しない。パケットは途中で失われることも、順序が入れ替わることも、重複することもある。こうした性質を\ **ベストエフォート**\ と呼ぶ。信頼性が必要なら、上のトランスポート層で補う。

IPv4 の :term:`IP アドレス`\ は 32 ビットの値で、``192.168.10.77`` のように 8 ビットずつ 10 進数で区切って書く。アドレスは、どのネットワークかを表す\ **ネットワーク部**\ と、そのネットワーク内のどの機器かを表す\ **ホスト部**\ に分かれる。

サブネットマスクと CIDR
^^^^^^^^^^^^^^^^^^^^^^^

ネットワーク部とホスト部の境界は、\ **サブネットマスク**\ で表す。サブネットマスクは、ネットワーク部のビットを 1、ホスト部のビットを 0 にした 32 ビットの値である。例えば ``255.255.255.0`` は上位 24 ビットがネットワーク部であることを表す。IP アドレスとサブネットマスクのビットごとの論理積をとると、ネットワークアドレスが得られる。

ネットワーク部のビット数を ``/24`` のようにアドレスの後ろに書く表記を :term:`CIDR`\ （Classless Inter-Domain Routing）表記と呼ぶ。``192.168.10.0/24`` は、上位 24 ビットが ``192.168.10`` である :math:`2^{8} = 256` 個のアドレスの範囲を表す。このうちホスト部がすべて 0 のネットワークアドレスと、すべて 1 のブロードキャストアドレスは機器に割り当てないので、機器に使えるのは 254 個である。一般に、プレフィックス長が :math:`p` のネットワークで機器に割り当てられるアドレスの数は :math:`2^{32-p} - 2` である（:math:`p` が 31 と 32 の特殊な場合を除く）。

ルーティング
^^^^^^^^^^^^

異なるネットワークの間でパケットを中継する機器をルータと呼び、パケットの宛先に応じて次の転送先を決めることを\ :term:`ルーティング`\ と呼ぶ。各ルータは、宛先ネットワークと次の転送先の組を並べた\ **経路表**\ を持つ。宛先アドレスに一致する経路が複数あるときは、プレフィックス長が最も長い、つまり最も具体的な経路を選ぶ。これを\ **最長一致**\ と呼ぶ。どの経路にも一致しない宛先には、``0.0.0.0/0`` で表される\ **デフォルトルート**\ を使う。家庭の PC のデフォルトルートは、通常ブロードバンドルータを指している。

IP ヘッダには TTL（Time To Live）というフィールドがあり、ルータを 1 つ通過するたびに 1 減らされ、0 になったパケットは破棄される。これにより、経路の設定ミスでパケットがループしても、永遠に回り続けることはない。パケットを破棄したルータは、送信元に ICMP のエラーメッセージを返す。``traceroute``\ （Windows では ``tracert``）コマンドは、TTL を 1、2、3、……と増やしながらパケットを送り、返ってくるエラーメッセージから途中のルータを調べる。

IPv6 の概要
^^^^^^^^^^^

IPv4 のアドレスは約 43 億個（:math:`2^{32}`）しかなく、すでに新たな割り当ての余地はほとんど残っていない。そこで設計されたのが IPv6 で、アドレスは 128 ビットある。``2001:0db8:0000:0000:0000:0000:0000:0001`` のように 16 ビットずつ 16 進数で区切って書き、各区切りの先頭の 0 を省略し、0 が続く区間を 1 か所だけ ``::`` で省略して ``2001:db8::1`` と書ける。IPv6 では、ヘッダの構造が単純化され、ブロードキャストが廃止された。また、アドレスが十分にあるため、後述の NAT に頼らず各機器にインターネット上で通用するアドレスを割り当てることが想定されている。現在は IPv4 と IPv6 が併用されており、両方に対応した機器は、名前解決で両方のアドレスが得られたときにどちらで接続するかを選ぶ。

NAT
^^^

プライベートアドレスを使う機器がインターネットと通信できるのは、境界のルータが :term:`NAT`\ （Network Address Translation）を行うからである。ルータは、内側から外へ出るパケットの送信元のプライベートアドレスとポート番号を、自分のグローバルアドレスと空いているポート番号に書き換え、その対応を変換表に記録する。応答が返ってきたら、変換表を引いて元のアドレスとポート番号に戻す。ポート番号まで書き換える方式は NAPT とも呼ばれ、1 つのグローバルアドレスを多数の機器で共有できる。

NAT には実務上注意すべき性質がある。1 つは、外から内側への接続を始められないことである。変換表に対応が無いので、外から届いたパケットの転送先が分からない。もう 1 つは、変換表の項目に有効期限があることである。長時間何も送らない TCP 接続は、途中の NAT やファイアウォールが対応を忘れ、両端が気付かないまま通信できなくなることがある。データベースの接続プールで、しばらく使わなかった接続が突然エラーになるのは、この現象が原因のことがある。定期的に小さなデータを送る\ **キープアライブ**\ を設定するか、使う前に接続を検査することで防ぐ。

トランスポート層
----------------

ポート番号
^^^^^^^^^^

IP アドレスで届くのはコンピュータまでである。そのコンピュータ上のどのプログラムに届けるかを区別するのが、16 ビットの\ :term:`ポート番号`\ である。HTTP は 80、HTTPS は 443、SSH は 22、DNS は 53 のように、よく使うサービスには 0〜1023 のウェルノウンポートが割り当てられている。クライアント側のポート番号は、通常 OS が一時的なポート（エフェメラルポート）の範囲から自動的に選ぶ。この範囲は OS によって異なり、IANA が推奨する範囲は 49152〜65535、Linux の既定は 32768〜60999 である。1 つの TCP 接続は、送信元 IP アドレス、送信元ポート、宛先 IP アドレス、宛先ポート、プロトコルの 5 つの組で識別される。

TCP
^^^

\ :term:`TCP`\ （Transmission Control Protocol）は、信頼性の無い IP の上で、信頼性のあるバイト列の通信を提供する [RFC9293]_。送ったデータは、失われず、重複せず、送った順序で相手に届く。そのために TCP は次のような仕組みを持つ。

* 接続の確立: 通信を始める前に :term:`3 ウェイハンドシェイク`\ を行う。クライアントが SYN を送り、サーバが SYN-ACK（SYN と ACK のフラグが両方立ったセグメント）を返し、クライアントが ACK を返す。この過程で、双方が使うシーケンス番号の初期値を交換する。
* 確認応答と再送: 送るデータの各バイトにはシーケンス番号が付いており、受信側はどこまで受け取ったかを ACK で知らせる。一定時間内に ACK が返らなければ、送信側はデータを再送する。同じ ACK が重複して届いたときは、途中のセグメントが失われたと推定して、タイマを待たずに再送することもある。
* フロー制御: 受信側は、自分の受信バッファの空き容量を\ **ウィンドウ**\ として送信側に知らせる。送信側は、ACK を受け取っていないデータの量がウィンドウを超えないように送る。これにより、速い送信側が遅い受信側を溢れさせることを防ぐ。
* 輻輳制御: ネットワークの途中が混雑しているときに送り過ぎないよう、送信側が送信量を自ら調整する。これを\ :term:`輻輳制御`\ と呼ぶ。接続の開始直後は少量から始めて送信量を急速に増やし（スロースタート）、パケットの損失などで混雑を検知すると送信量を減らす。
* 接続の終了: 双方が FIN を送り、相手から ACK を受け取って接続を閉じる。

TCP が提供するのは\ **バイト列の流れ**\ であり、メッセージの区切りは保存されない。送信側が 100 バイトを 2 回送っても、受信側の 1 回の ``recv()`` で 200 バイトまとめて受け取ることも、30 バイトずつ分かれて受け取ることもある。そのため、アプリケーションのプロトコルは、改行で区切る、先頭に長さを書くなどの方法で、自らメッセージの境界を決める必要がある。

UDP と使い分け
^^^^^^^^^^^^^^

\ :term:`UDP`\ （User Datagram Protocol）は、IP にポート番号と簡単な誤り検出を加えただけのプロトコルである [RFC768]_。接続の確立は無く、届いたかの確認も再送も順序の保証もしない。その代わりにヘッダは 8 バイトと小さく、ハンドシェイクの往復を待たずにすぐ送れる。また、TCP と異なり、1 回の送信が 1 つのデータグラムとして相手に届くので、メッセージの境界が保たれる。TCP と UDP の違いを次の表にまとめる。

.. list-table::
   :header-rows: 1
   :widths: 20 40 40

   * - 観点
     - TCP
     - UDP
   * - 接続
     - 3 ウェイハンドシェイクで確立する
     - 確立しない
   * - 信頼性
     - 再送し、順序を保証する
     - 保証しない
   * - データの単位
     - バイト列の流れ（境界を保存しない）
     - データグラム（境界を保存する）
   * - 制御
     - フロー制御と輻輳制御を行う
     - 行わない
   * - 主な用途
     - HTTP/1.1、HTTP/2、SSH、メール、データベース接続
     - DNS の問い合わせ、音声・映像の配信、オンラインゲーム、QUIC

一般に、データが欠けてはならない通信には TCP を使う。少し遅れたデータは不要になる音声通話のように、再送を待つより新しいデータを優先したい通信や、DNS のように 1 往復で終わる短い問い合わせには UDP が向いている。また、後述の HTTP/3 が使う QUIC は、UDP の上に再送や輻輳制御を独自に実装したプロトコルである。

DNS
---

名前解決の流れ
^^^^^^^^^^^^^^

人間は ``www.example.com`` のような名前を使うが、通信には IP アドレスが必要である。名前から IP アドレスなどの情報を得ることを\ **名前解決**\ と呼び、そのための分散データベースが :term:`DNS`\ （Domain Name System）である [RFC1034]_ [RFC1035]_。名前は右から順に階層をなしており、``www.example.com`` は、ルートの下の ``com``、その下の ``example`` の下にある ``www`` を表す。各階層の情報は、その部分を管理する\ **権威 DNS サーバ**\ が持っている。

プログラムが名前解決を依頼すると、次のように処理が進む。

#. アプリケーションは OS のリゾルバ（スタブリゾルバ）に問い合わせる。OS は、``hosts`` ファイルや自分のキャッシュに答えがあればそれを返す。
#. 無ければ、OS は設定された\ **フルサービスリゾルバ**\ （キャッシュ DNS サーバ。組織や通信事業者が運用する）に問い合わせる。フルサービスリゾルバも、キャッシュに答えがあればそれを返す。
#. キャッシュに無ければ、フルサービスリゾルバはルートサーバに問い合わせ、``com`` を管理するサーバの情報を得る。
#. ``com`` のサーバに問い合わせ、``example.com`` を管理する権威 DNS サーバの情報を得る。
#. ``example.com`` の権威 DNS サーバに問い合わせ、``www.example.com`` の IP アドレスを得る。
#. フルサービスリゾルバは結果をキャッシュし、OS に返す。

DNS の問い合わせには、通常 UDP の 53 番ポートを使う。応答が大きい場合などには TCP も使う。

レコード種別
^^^^^^^^^^^^

DNS が名前に対して保持する情報を\ **リソースレコード**\ と呼び、種類ごとに型がある。代表的なものを次の表に示す。

.. list-table::
   :header-rows: 1
   :widths: 15 85

   * - 型
     - 内容
   * - A
     - 名前に対応する IPv4 アドレス
   * - AAAA
     - 名前に対応する IPv6 アドレス
   * - CNAME
     - 名前の別名。この名前の問い合わせは、別の名前の問い合わせとして扱われる
   * - MX
     - その名前宛てのメールを受け取るサーバと優先度
   * - NS
     - その名前の範囲を管理する権威 DNS サーバ
   * - TXT
     - 任意の文字列。ドメインの所有確認や、送信元メールサーバの認証情報などに使う

TTL とキャッシュ
^^^^^^^^^^^^^^^^

各リソースレコードには、キャッシュしてよい時間を秒数で表す :term:`TTL`\ （Time To Live）が付いている。IP ヘッダの TTL と同じ名前だが、意味は異なる。リゾルバは TTL の間だけ結果をキャッシュし、その間は権威 DNS サーバに問い合わせない。キャッシュのおかげで、DNS は世界中からの膨大な問い合わせをさばける。

一方で、キャッシュはレコードの変更がすぐに反映されない原因にもなる。サーバを移転して A レコードを書き換えても、古い値をキャッシュしたリゾルバは TTL が切れるまで古い IP アドレスを返し続ける。そのため、移転の予定があれば、事前に TTL を短く（例えば 300 秒に）しておき、古い TTL の期間が過ぎてから切り替えるのが定石である。また、キャッシュはフルサービスリゾルバだけでなく OS やアプリケーションの実行環境にもあり、それぞれが独自の規則で保持していることがある。長時間動き続けるプロセスが、名前解決の結果を起動時に一度だけ取得して使い続けると、接続先の IP アドレスが変わったときに追従できない。

HTTP
----

リクエストとレスポンスの構造
^^^^^^^^^^^^^^^^^^^^^^^^^^^^

\ :term:`HTTP`\ （Hypertext Transfer Protocol）は、Web の基盤となるアプリケーション層のプロトコルである。HTTP の意味（メソッドやステータスコードなど）は [RFC9110]_、HTTP/1.1 のメッセージの形式は [RFC9112]_ で定められている。HTTP/1.1 は、クライアントがリクエストを送り、サーバがレスポンスを返すという単純な形をとり、メッセージはテキストで書かれる。

リクエストは、メソッド・パス・バージョンを書いた\ **リクエスト行**\ 、「名前: 値」の形の\ **ヘッダ**\ の並び、空行、必要なら\ **本体**\ からなる。レスポンスは、バージョン・ステータスコード・理由句を書いた\ **ステータス行**\ 、ヘッダの並び、空行、本体からなる。行の区切りは CR LF（``\r\n``）である。HTTP/1.1 では、1 台のサーバが複数のドメインを受け持てるように、リクエストに ``Host`` ヘッダが必須である。

リクエストのメソッドは、対象の資源に対して何をしたいかを表す。主なメソッドを次の表に示す。\ **安全**\ とは、サーバの状態を変更しないことを意味する。\ **冪等**\ とは、同じリクエストを 1 回送っても複数回送っても、サーバの状態への効果が同じになることを意味する。

   * - メソッド

     - 安全

   * - GET
     - 資源の表現を取得する
     - はい
     - はい
   * - HEAD
     - GET と同じだが、本体を返さずヘッダだけを返す
     - はい
     - はい
   * - POST
     - 送ったデータを資源に処理させる（新規作成など）

     - いいえ

冪等性は、タイムアウトしたリクエストを再送してよいかの判断に直結する。GET や PUT は再送しても結果が変わらないが、POST を再送すると、例えば注文が二重に登録されるおそれがある。決済のような API では、クライアントが一意な識別子をリクエストに付け、サーバが同じ識別子のリクエストを一度だけ処理するようにして、再送を安全にすることが多い（「:doc:`ch12_distributed_systems`」で詳しく扱う）。

     - 説明
   * - 200
     - OK

   * - 201
     - Created
     - リクエストが成功し、新しい資源が作成された
   * - 204
     - No Content
     - 成功したが、返す本体が無い
   * - 301

   * - 401

   * - 403

   * - 404

1xx は情報、2xx は成功、3xx はリダイレクト、4xx はクライアント側の誤り、5xx はサーバ側の誤りを表す。障害の調査では、この分類が手がかりになる。例えば、ロードバランサの背後のアプリケーションサーバが落ちていれば 502 や 503、応答が遅すぎれば 504 がロードバランサから返る。4xx が増えた場合は、クライアントの変更やリクエストの形式を疑う。なお、401 の名前は Unauthorized だが、意味するのは認証（誰であるかの確認）の問題であり、認可（権限）の問題は 403 で表す。

ステートレス性
^^^^^^^^^^^^^^

HTTP は\ **ステートレス**\ なプロトコルである。サーバは各リクエストを独立に処理し、前のリクエストの内容を覚えていることを前提としない。そのため、ログイン状態のように複数のリクエストにまたがる情報は、Cookie ヘッダで受け渡すセッション識別子や、``Authorization`` ヘッダで送るトークンのように、リクエストごとに必要な情報を付けて送る（「:doc:`ch14_application_security`」で詳しく扱う）。ステートレスであることは、サーバを何台にも増やして負荷を分散しやすいという利点につながる。どのサーバがリクエストを受けても、同じように処理できるからである。

HTTPS と新しいバージョン
^^^^^^^^^^^^^^^^^^^^^^^^

ここまでの HTTP は平文で送られるため、途中の経路で内容を盗み見たり改ざんしたりできる。HTTP を TLS で暗号化した HTTPS がこれを防ぐ。暗号化と TLS については「:doc:`ch13_security`」で扱う。

HTTP/1.1 では、1 つの接続で同時に処理できるリクエストは 1 つで、前のレスポンスが遅いと後ろのリクエストが待たされる。HTTP/2 は、メッセージをバイナリのフレームに分け、1 つの TCP 接続の上で複数のリクエストとレスポンスを同時に並行して流す（多重化）。ヘッダの圧縮も行う。ただし、TCP の上で動くため、パケットが 1 つ失われると、再送されるまでその接続の全ストリームが待たされる。HTTP/3 は、TCP の代わりに UDP の上に作られた QUIC を使い、ストリームごとに独立して再送することでこの問題を解消した。QUIC は TLS 1.3 を組み込んでおり、接続の確立と暗号化の準備を少ない往復で済ませる。いずれのバージョンでも、メソッドやステータスコードといった HTTP の意味は共通である。

通信のトラブルシューティング
----------------------------

遅延と帯域
^^^^^^^^^^

通信の速さには、性質の異なる 2 つの尺度がある。\ :term:`遅延`\ （レイテンシ）は、データが送られてから相手に届くまでの時間であり、往復にかかる時間を RTT（Round-Trip Time）と呼ぶ。\ :term:`帯域幅`\ は、単位時間あたりに送れるデータ量であり、bit/s で表す。大きさ :math:`S` ビットのデータを、片道の遅延 :math:`L` 秒、帯域幅 :math:`B` bit/s の経路で送るのにかかる時間 :math:`T` は、おおよそ次の式で表される。

.. math::

   T = L + \frac{S}{B}

例えば 1 MB（:math:`8 \times 10^{6}` ビット）のデータを 100 Mbit/s の回線で送ると、送出に 0.08 秒かかる。一方、小さな API 呼び出しでは :math:`S / B` はほぼ無視でき、時間のほとんどは遅延で決まる。東京と米国西海岸の間の RTT は 100 ミリ秒程度あり、光の速さという物理的な制約から、回線を太くしてもこれは縮まらない。

遅延が支配的な場面では、往復の回数を減らすことが効く。HTTPS で新しいサーバに初めてリクエストを送るとき、DNS の名前解決、TCP の 3 ウェイハンドシェイク、TLS のハンドシェイク、HTTP のリクエストとレスポンスのそれぞれに往復が必要になる。接続を使い回す（HTTP の持続的接続や接続プール）、多数の小さな API 呼び出しを 1 回にまとめる、利用者に近い場所にサーバやキャッシュ（CDN）を置く、といった工夫はいずれも往復の回数か RTT を減らすものである。

TCP の場合、ACK を待たずに送れるデータ量はウィンドウで制限されるので、1 本の接続のスループットは最大でもおおよそウィンドウの大きさを RTT で割った値になる。例えばウィンドウが 64 KiB（65,536 バイト）、RTT が 100 ミリ秒なら、:math:`65536 \times 8 / 0.1 \approx 5.2 \times 10^{6}` bit/s、つまり約 5.2 Mbit/s にとどまり、回線が 1 Gbit/s あっても使い切れない。帯域幅と RTT の積を\ **帯域幅遅延積**\ と呼び、回線を使い切るにはこれ以上のウィンドウが必要である。現在の TCP は、ウィンドウを拡大するオプションによって、より大きなウィンドウを使える。

問題の切り分け
^^^^^^^^^^^^^^

通信がうまくいかないときは、階層モデルに沿って下の層から順に確かめると原因を絞り込みやすい。次の表に、症状と確かめる観点、使えるコマンドの例を示す。

.. list-table::
   :header-rows: 1
   :widths: 25 45 30

   * - 症状
     - 確かめる観点
     - コマンドの例
   * - 名前で接続できない
     - 名前解決ができるか、得られた IP アドレスが正しいか、古いキャッシュが残っていないか
     - ``nslookup``、``dig``
   * - IP アドレスに届かない
     - 経路があるか、どこで途切れているか
     - ``ping``、``traceroute``\ （``tracert``）
   * - 接続が拒否される、またはタイムアウトする
     - 相手のポートで待ち受けているか、ファイアウォールで遮断されていないか
     - ``ss``、``netstat``、``curl -v``
   * - 応答はあるが遅い
     - 遅いのは接続の確立か、サーバの処理か、データの転送か
     - ``curl -v``、ブラウザの開発者ツール

接続先のポートで誰も待ち受けていなければ、通常は TCP のリセット（RST）がすぐに返り、「接続が拒否された」というエラーになる。一方、途中のファイアウォールがパケットを黙って捨てていると、何も返ってこず、タイムアウトするまで待たされる。エラーがすぐに返るか、待たされてから返るかは、原因を切り分ける重要な手がかりである。また、遅い原因を調べるときは、平均値だけでなく、遅い側の分布（例えば上位 1% の応答時間）も見るべきである。再送が起きたリクエストは、再送までの待ち時間の分だけ極端に遅くなるので、平均には表れにくい。

まとめ
------

* ネットワークの機能は層に分けて設計されている。OSI 参照モデルは 7 層、TCP/IP は 4 層で説明され、送信側では各層がヘッダを付けてカプセル化する。
* リンク層は MAC アドレスで同じネットワーク内の機器にフレームを届け、IP はルータの経路表に従ってネットワークをまたいでパケットを届ける。
* IPv4 アドレスは 32 ビットで、CIDR 表記でネットワーク部の長さを表す。アドレス不足は NAT と IPv6 で補われている。
* TCP は 3 ウェイハンドシェイク、再送、フロー制御、輻輳制御によって信頼性のあるバイト列の通信を提供する。UDP は軽量だが信頼性を保証しない。
* DNS は階層的な分散データベースで、TTL に基づくキャッシュによって大量の問い合わせをさばく。キャッシュはレコード変更の反映を遅らせる。
* HTTP はステートレスなリクエストとレスポンスのプロトコルで、メソッドの冪等性とステータスコードの分類は、再送の設計と障害の調査に役立つ。
* 通信の速さは遅延と帯域幅で決まる。小さな通信では往復の回数を減らすことが効き、通信には必ずタイムアウトを設定する。
