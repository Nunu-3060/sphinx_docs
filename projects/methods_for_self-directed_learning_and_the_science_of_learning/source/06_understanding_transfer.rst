.. _ch06:

第 6 章 理解と転移
================================================================

技術を学ぶ目的は、教材に書かれたことを再現することではなく、学んだことを新しい問題に使えるようにすることである。チュートリアルの手順を覚えていても、少し違う要件の機能を作ろうとした途端に手が止まるのであれば、学びは役に立っていない。本章では、「覚える」と「理解する」の違い、誤った理解（誤概念）とその修正、類推と抽象化、そして学んだことを別の場面で使えること（転移）を扱う。

「覚える」と「理解する」の違い
--------------------------------

理解とは何か
^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^

ある事柄を「覚えている」とは、それを記憶から取り出せる状態である。一方、「理解している」とは、その事柄がなぜ成り立つのか、他の知識とどう関係するのか、条件が変わると何が起こるのかを説明できる状態である。学習科学の知見をまとめた報告書 How People Learn [Bransford2000]_ は、深い理解を伴う学習の特徴として、事実の知識が、その分野の中心的な概念を軸に整理されていることを挙げている。整理された知識は、新しい状況で必要な知識を取り出しやすく、適用もしやすい。

例えば、Python の辞書について「キーで値を取り出せる」と覚えている状態と、「キーのハッシュ値で格納位置を決めるので、平均的には要素数によらず高速に検索できる。そのため、キーには変更されない（ハッシュ値が変わらない）オブジェクトを使う必要がある」と理解している状態とでは、使える場面の広さが違う。後者の理解があれば、リストを辞書のキーにできない理由や、集合（set）の性質、他の言語のハッシュマップの振る舞いも同じ枠組みで説明できる。

熟達者と初心者の知識の違い
^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^

知識の整理のされ方の違いは、熟達者と初心者の比較研究で明確に示されている。Chi ら [Chi1981]_ は、物理学の問題を、熟達者（大学院生など）と初心者（物理の授業を受けた学部生）に分類させた。初心者は「斜面の問題」「ばねの問題」のように、問題に登場する物体などの表面的な特徴で分類した。一方、熟達者は「エネルギー保存則で解ける問題」「ニュートンの第二法則で解ける問題」のように、解くために使う原理で分類した。

表面的な特徴で整理された知識は、見た目の似た問題にしか使えない。原理で整理された知識は、見た目が違っても同じ原理が当てはまる問題に使える。プログラミングに置き換えると、「Web アプリのログイン機能の作り方」を覚えるのではなく、「認証と認可の違い」「セッションとトークンの仕組み」といった原理で知識を整理することにあたる。熟達者の知識の特徴は :ref:`ch07` でも扱う。

説明深度の錯覚
^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^

人は、自分がどの程度理解しているかを過大に見積もりやすい。Rozenblit と Keil [Rozenblit2002]_ は、ファスナーや水洗トイレなどの身近な仕組みについて、参加者に理解度を自己評価させた後、その仕組みを段階を追って詳しく説明させた。説明を試みた後に改めて自己評価させると、評価は下がった。説明しようとして初めて、自分の理解に穴があることに気付いたのである。これを説明深度の錯覚（illusion of explanatory depth）と呼ぶ。

.. admonition:: 根拠の強さ: 中程度
   :class: evidence evidence-moderate

   仕組みの理解度を、説明を試みる前には過大に見積もる傾向は、複数の実験で確認されている。ただし、錯覚の大きさは対象となる知識の種類によって異なる。

エンジニアは、普段使っている技術について説明深度の錯覚に陥りやすい。毎日 Git を使っていても、「git rebase を実行すると内部で何が起こるか」をコミットとブランチの関係から説明しようとすると、言葉に詰まることがある。毎日使えていることと、仕組みを理解していることは別である。

理解を確かめる方法
^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^

理解しているかどうかは、次のような問いに答えられるかで確かめる。

* **説明**: 何も見ずに、その仕組みを順を追って説明できるか。
* **理由**: なぜそうなっているのか、別の設計ではなぜいけないのかを説明できるか。
* **予測**: 条件を変えたとき（入力を変える、設定を変える）に何が起こるかを、実行する前に予測できるか。
* **適用**: 教材に載っていない問題に使えるか。
* **比較**: 似た技術や概念との違いを説明できるか。

特に「予測」は、エンジニアにとって手軽で強力な方法である。コードを実行する前に結果を予測し、実行して確かめる。予測が外れたら、それは理解が不十分な箇所を示している。この習慣は、次に述べる誤概念の発見にも役立つ。説明による学習は :ref:`ch04` の自己説明や :ref:`ch13` のファインマンテクニックで扱う。

誤概念とその修正
--------------------------------

誤概念とは
^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^

学習者は白紙の状態で学ぶわけではない。既に持っている知識や直感を使って新しい情報を解釈する。そのため、既存の知識が誤っていたり、新しい分野にそのまま当てはまらなかったりすると、誤った理解が生まれる。このような、学習者が持つ体系的な誤った理解を誤概念（misconception）と呼ぶ。

誤概念は、単なる知識の欠落とは異なる。欠落であれば新しい知識を加えればよいが、誤概念は既存の知識と結び付いて一貫した理解を形作っているため、正しい説明を一度聞いただけでは修正されにくい。正しい説明を聞いても、学習者は既存の誤概念に合うように解釈してしまうことがある。

プログラミングにおける誤概念の例
^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^

プログラミングの学習では、次のような誤概念がよく見られる。

.. list-table:: プログラミングにおける誤概念の例
   :name: tbl-ch06-misconceptions
   :header-rows: 1
   :widths: 25 40 35

   * - 誤概念
     - 正しい理解
     - 誤概念が表れる場面
   * - Python の変数は値を入れる箱である
     - 変数はオブジェクトに付けた名前であり、代入はオブジェクトをコピーしない
     - リストを別の変数に代入して変更したら、元の変数の値も変わって驚く
   * - Git のブランチはファイル一式のコピーである
     - ブランチはコミットを指す軽量なポインタである
     - ブランチを作ると容量が増えると考えて、ブランチを作るのをためらう
   * - 非同期処理を使えば処理が並列に実行される
     - async/await は、待ち時間の間に別の処理を進めるための仕組みであり、CPU を使う処理を並列化するものではない
     - 計算の重い処理を async 関数にしても速くならず、原因が分からない
   * - 浮動小数点数は小数を正確に表す
     - 多くの小数は 2 進数で正確に表せず、近似値として扱われる
     - ``0.1 + 0.2 == 0.3`` が False になる理由が分からない

これらの誤概念は、それなりに筋が通っており、単純な場面では問題を起こさない。「変数は箱」というたとえは、整数や文字列だけを扱っている間は正しく働く。問題が表面化するのは、リストのような変更可能なオブジェクトを扱うようになってからである。誤概念は、それが通用しない場面に出会うまで発見されにくい。

概念変化の条件
^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^

誤概念を正しい理解に置き換えることを、概念変化（conceptual change）と呼ぶ。Posner ら [Posner1982]_ は、科学教育の文脈で、概念変化が起こるための条件として次の四つを挙げた。

1. 既存の概念に不満を感じること（既存の概念では説明できない現象に出会う）。
2. 新しい概念が理解可能であること。
3. 新しい概念がもっともらしいこと（既存の他の知識と矛盾しない）。
4. 新しい概念が有用であること（新しい問題の解決や説明につながる）。

この枠組みに従えば、誤概念を修正するには、正しい説明を示す前に、まず既存の概念では説明できない現象を体験することが有効である。「変数は箱」という誤概念であれば、次のようなコードの実行結果を予測させてから実行させる。

.. code-block:: python
   :linenos:
   :caption: 予測してから実行する例

   a = [1, 2, 3]
   b = a
   b.append(4)
   print(a)  # 何が表示されるか、実行する前に予測する

「箱」のモデルで考えると ``[1, 2, 3]`` と予測するが、実際には ``[1, 2, 3, 4]`` が表示される。この予測の失敗が、既存の概念への不満を生み、「名前とオブジェクト」という新しい概念を受け入れる準備になる。

Chi [Chi2008]_ は、概念変化を、個々の信念の修正、メンタルモデルの変換、カテゴリーの移行の三つの種類に分けた。個々の誤った信念を正すのは比較的容易だが、概念を別のカテゴリーに移す必要がある変化（例えば、熱を「物質」ではなく「過程」として捉え直す）は難しいとされる。プログラミングでも、「ブランチはファイルのコピー」を「ブランチはコミットへのポインタ」と捉え直すのは、物の捉え方そのものを変える変化であり、時間がかかる。

.. admonition:: 根拠の強さ: 中程度
   :class: evidence evidence-moderate

   誤概念が正しい説明だけでは修正されにくいこと、既存の概念と矛盾する現象との対面が修正のきっかけになることは、主に科学教育の研究で繰り返し報告されている。ただし、どの方法が最も効果的かは、誤概念の種類や学習者によって異なる。

類推と抽象化
--------------------------------

類推の力と難しさ
^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^

類推（analogy）とは、既に知っている状況（ベース）と新しい状況（ターゲット）の間に共通する構造を見つけ、ベースの知識をターゲットに当てはめることである。新しい技術を学ぶとき、既知の技術との類推は強力な手がかりになる。

しかし、人は類推を自発的には使いにくい。Gick と Holyoak [GickHolyoak1980]_ は、参加者に「腫瘍を放射線で破壊したいが、強い放射線は周囲の健康な組織も傷つける」という問題を解かせた。事前に、構造が同じ物語（要塞を攻めるために、軍を小部隊に分けて四方から同時に集結させる話）を読ませても、物語を問題に使えばよいというヒントを与えない限り、多くの参加者はその物語を解決に使わなかった。ヒントを与えると、多くの参加者が「弱い放射線を複数の方向から当てて腫瘍で集中させる」という解決策にたどり着いた。知識を持っていることと、それを新しい場面で使えることの間には大きな隔たりがある。

比較による抽象化
^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^

この隔たりを埋める方法の一つが、複数の例を比較することである。Gick と Holyoak [GickHolyoak1983]_ は、構造が同じ物語を二つ読ませ、両者の共通点を考えさせると、問題への転移が起こりやすくなることを示した。二つの例を比べることで、表面的な違い（軍と放射線）に隠れた共通の構造（「力を分散させて一点に集める」）が抽象化され、スキーマとして取り出される。

エンジニアの学習に置き換えると、一つのフレームワークのチュートリアルを繰り返すよりも、同じ目的を持つ二つの技術を比べるほうが、背後にある原理を抽出しやすい。例えば、React の状態管理と Vue のリアクティビティを比べると、「状態の変化を検知して画面を更新する」という共通の課題と、それぞれの解き方の違いが見えてくる。デザインパターンも、さまざまなコードに共通する構造を抽象化して名前を付けたものと考えることができる。

.. admonition:: 根拠の強さ: 中程度
   :class: evidence evidence-moderate

   複数の例を比較して共通の構造を考えると類推による転移が起こりやすくなることは、実験室の研究で繰り返し示されている。ただし、実験で使われた課題は比較的単純なものが多い。

学習の転移
--------------------------------

転移とは
^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^

ある場面で学んだことが、別の場面での学習や問題解決に影響することを転移（transfer）と呼ぶ。学習した場面とよく似た場面への転移を近い転移、大きく異なる場面への転移を遠い転移という。Python のリスト内包表記を学んだ後、辞書内包表記を書けるようになるのは近い転移である。チェスの練習で鍛えた思考力が、ソフトウェア設計の能力を高めるとすれば、それは遠い転移である。

Barnett と Ceci [Barnett2002]_ は、転移の「近さ・遠さ」は一つの軸では測れないとして、転移を分類する枠組みを提案した。この枠組みでは、何が転移するか（内容）に加えて、学習した場面と使う場面がどれだけ離れているか（文脈）を、知識の領域、物理的な場所、時間、機能（学問的な課題か実務か）、社会的な状況（一人か協働か）、表現の形式（筆記か口頭かなど）といった複数の次元で捉える。例えば、研修で学んだ設計手法を、半年後に、実際のプロジェクトで、チームでの議論の中で使うのは、複数の次元で離れた転移である。

遠い転移は起こりにくい
^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^

汎用的な能力を鍛えれば、あらゆる分野に効果が及ぶという期待は根強い。しかし、研究の結果は否定的である。Sala と Gobet [SalaGobet2017]_ は、チェス、音楽、作業記憶のトレーニングについてのメタ分析の結果を検討し、これらの訓練が、訓練した領域以外の認知能力や学業成績に及ぼす効果はごく小さいか、ほとんどないと結論づけた。脳トレーニングについても同様である（:ref:`ch05`）。

Tricot と Sweller [Tricot2014]_ は、「問題解決能力」や「批判的思考力」のような汎用的なスキルを、特定の分野の知識と切り離して教えようとする試みがうまくいかない理由を、領域固有の知識の役割から説明している。熟達者の問題解決能力の大部分は、その分野の知識に支えられている。汎用的な思考法を学ぶだけでは、知識のない分野の問題は解けない。

.. admonition:: 根拠の強さ: 強い
   :class: evidence evidence-strong

   チェス、音楽、作業記憶のトレーニングなどによる遠い転移の効果がごく小さいことは、複数のメタ分析で示されている。

この知見は、エンジニアにとって重要な意味を持つ。「アルゴリズムの問題を解けば、どんな開発にも通用する思考力が身に付く」「論理パズルで論理的思考を鍛える」といった学習は、それ自体を目的とするなら有意義だが、別の分野の能力を高める手段としては効率がよくない。身に付けたい能力があるなら、その能力が使われる分野の知識とともに練習するのが確実である。

転移を促す学び方
^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^

遠い転移が起こりにくいとはいえ、学び方によって転移の起こりやすさは変わる。研究から、次のような方法が転移を促すと考えられている。

* **複数の多様な例で学ぶ**: 一つの例だけでは、どこが本質でどこが偶然の特徴か区別できない。異なる文脈の例を複数学ぶと、共通の原理が抽出されやすい [GickHolyoak1983]_。
* **例を比較する**: 例を一つずつ学ぶより、並べて比較し、共通点と相違点を考えるほうが、スキーマが形成されやすい。
* **原理を言葉にする**: 例から抽出した原理を自分の言葉で説明する。これは :ref:`ch04` で扱った自己説明と同じ考え方である。
* **種類の異なる問題を混ぜて練習する**: どの解き方を使うべきかを判断する練習になる。これは :ref:`ch04` で扱った交互学習にあたる。
* **使う場面を想定して学ぶ**: 学んだことを実際に使う場面（業務のコード、実際のデータ）に近い状況で練習する。学習した場面と使う場面が近いほど、転移は起こりやすい。

.. admonition:: 根拠の強さ: 中程度
   :class: evidence evidence-moderate

   多様な例や比較が転移を促すことは、実験室の研究で繰り返し示されている。ただし、多くの研究は短期間の実験であり、長期的な実務での転移を直接測った研究は少ない。

例: 新しいプログラミング言語を学ぶ
--------------------------------------------

既知の言語との対比の利点
^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^

既に一つのプログラミング言語を使える人が新しい言語を学ぶのは、転移の典型的な場面である。変数、条件分岐、繰り返し、関数、データ構造といった概念は、多くの言語で共通している。既知の言語で身に付けたこれらのスキーマを使えるので、二つ目の言語は一つ目よりずっと速く習得できる。既知の言語との対比で学ぶ（「Python の辞書は、Rust では HashMap にあたる」）ことは、新しい知識を既存の知識に結び付けるので、理解と記憶の両方を助ける。

対比の落とし穴: 負の転移
^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^

一方で、既存の知識が新しい学習を妨げることもある。これを負の転移と呼ぶ。見た目が似ているのに意味が違う機能では、既知の言語の知識をそのまま当てはめてしまい、誤概念が生まれる。

.. list-table:: Python の経験者が他の言語を学ぶときの負の転移の例
   :name: tbl-ch06-negative-transfer
   :header-rows: 1
   :widths: 20 40 40

   * - 新しい言語
     - Python での前提
     - 新しい言語での違い
   * - C++
     - 整数はいくらでも大きな値を扱える
     - 整数型には範囲があり、符号付き整数のオーバーフローは未定義動作になる
   * - C++
     - ``7 / 2`` は ``3.5`` になる
     - 整数どうしの ``/`` は整数の除算になり、``7 / 2`` は ``3`` になる
   * - Rust
     - 代入すると、二つの名前が同じオブジェクトを指す
     - 所有権が移動（ムーブ）し、元の変数は使えなくなる型がある
   * - Go
     - エラーは例外として送出され、try 文で捕まえる
     - エラーは関数の戻り値として返し、呼び出し側で明示的に確認する
   * - JavaScript
     - ``==`` は型の異なる値（文字列と数値など）を自動的に変換して比べない
     - ``==`` は型変換を伴って比較するため、``===`` を使うのが一般的である

負の転移を防ぐには、類似点だけでなく **相違点** を意識的に学ぶことが有効である。新しい言語を学ぶときは、「Python と同じところ」と「Python と違うところ」を分けて記録するとよい。特に相違点は、予測してから確かめる方法（「Python と同じように動くはずだ」と予測し、実行して確かめる）で学ぶと、誤概念を早く発見できる。

また、新しい言語には、その言語らしい書き方（イディオム）や設計思想がある。Python の書き方を新しい言語に直訳するだけでは、文法は通っても、その言語の利点を生かせない。Rust の所有権や Go の並行処理のように、その言語に特有の概念は、既知の言語との対比ではなく、その言語の設計思想から学ぶ必要がある。

エンジニアの独学への応用
--------------------------------

本章の内容を独学に当てはめると、次のようになる。

* **理解を行動で確かめる**: 読んで納得したら、何も見ずに説明する、コードの結果を予測する、教材にない問題に使う、のいずれかで理解を確かめる。説明に詰まった箇所や予測が外れた箇所が、次に学ぶべき箇所である。
* **原理で知識を整理する**: 個々の手順ではなく、「なぜそうするのか」という原理を軸に知識をまとめる。ノートには手順だけでなく理由を書く（:ref:`ch13`）。
* **誤概念を前提に学ぶ**: 自分の理解には誤りが含まれている可能性があると考え、予測と検証を繰り返す。驚いた実行結果は、誤概念を修正する好機である。
* **二つ以上を比べる**: 新しい技術は、似た目的の別の技術と比較しながら学ぶ。共通点から原理が、相違点からその技術の特徴が見えてくる。
* **汎用的な能力に過度に期待しない**: 身に付けたい技術があるなら、その技術を、それが使われる文脈で練習する。

まとめ
------

* 理解とは、事柄がなぜ成り立つのか、他の知識とどう関係するのかを説明でき、新しい状況に適用できる状態である。
* 熟達者の知識は原理を軸に整理されており、初心者の知識は表面的な特徴で整理されやすい。
* 人は自分の理解度を過大に見積もりやすい（説明深度の錯覚）。説明・予測・適用によって理解を確かめる。
* 誤概念は正しい説明だけでは修正されにくい。既存の概念では説明できない現象に出会うことが、修正のきっかけになる。
* 類推は自発的には使われにくいが、複数の例を比較すると共通の構造が抽象化され、転移が起こりやすくなる。
* 遠い転移はまれである。汎用的な能力の訓練よりも、身に付けたい技術そのものを、使う文脈に近い形で練習するほうが確実である。
* 新しい言語を学ぶときは、既知の言語との類似点を手がかりにしつつ、相違点を意識的に学んで負の転移を防ぐ。
