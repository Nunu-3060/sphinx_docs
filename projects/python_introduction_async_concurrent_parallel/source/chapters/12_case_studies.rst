第 12 章 ケーススタディ
=======================

この章では、3 つの題材を通して、処理の性質から手法を選び、実装するまでの流れを確認する。いずれのサンプルも、標準ライブラリだけで、外部のネットワークを使わずに動作する。

多数の URL からのデータ取得
---------------------------

課題
~~~~

Web API から 40 件のデータを取得したい。1 件ずつ取得すると、応答を待つ時間が積み重なって時間がかかる。ただし、相手のサーバーに負荷をかけないよう、同時に送る要求は 10 件までにしたい。また、応答が遅い要求があっても、全体が止まらないようにしたい。

手法の選択
~~~~~~~~~~

処理時間の大半は応答を待つ時間であり、I/O バウンドである。同時に扱う要求の数は数十件程度なのでスレッドでも実現できるが、ここでは同時実行数の制限とタイムアウトを簡潔に書ける ``asyncio`` を選ぶ。

実装
~~~~

サンプルでは、取得先の Web API の代わりに、同じプログラムの中で簡単な HTTP サーバーを起動する。サーバーは id によって応答までの時間を変え、10 件に 1 件は 2 秒かかる。クライアントは ``asyncio`` のストリームで HTTP の要求を送り、1 件ごとに 1 秒のタイムアウトを設定する。

実行すると、次の結果になる。

.. code-block:: text

   成功: 36 件, 失敗: 4 件
     id=9: タイムアウト
     id=19: タイムアウト
     id=29: タイムアウト
     id=39: タイムアウト
   経過時間: 1.8 秒（1 件ずつ取得した場合の待ち時間の合計: 10.4 秒）

要点
~~~~

* ``fetch()`` は、``Semaphore`` で同時実行数を制限し、その中で ``asyncio.timeout()`` によって 1 件ごとの待ち時間を制限している。``Semaphore`` の外側でタイムアウトを設定すると、順番を待っている時間もタイムアウトの対象になってしまうため、順序に注意する。
* 失敗した要求は例外を送出せず、``Result`` の ``error`` に記録している。``TaskGroup`` の中で例外を送出すると他のタスクがすべてキャンセルされるため、一部の失敗を許容したい場合は、このようにタスクの中で例外を処理する。
* 1 件ずつ取得すると待ち時間だけで 10 秒以上かかるところを、約 1.8 秒で取得できた。

実務では、HTTP の通信は ``aiohttp`` や ``httpx`` などのライブラリを使い、ステータスコードの確認や再試行（:doc:`11_debugging` の ``retry()`` を参照）も加える。

大量のデータの一括処理
----------------------

課題
~~~~

マンデルブロ集合の画像（800 × 600 画素）を計算したい。画素ごとに複素数の計算を最大 200 回繰り返すため、Python で書くと時間がかかる。

手法の選択
~~~~~~~~~~

処理時間の大半は Python で書かれた計算であり、CPU バウンドである。各行の計算は他の行に依存しないため、行ごとに分けて並列に計算できる。``ProcessPoolExecutor`` を選ぶ。

実装
~~~~

.. literalinclude:: ../../examples/ch12_case_studies/mandelbrot_batch.py
   :language: python
   :linenos:
   :lineno-match:
   :lines: 7-

実行すると、次のような結果になり、実行したディレクトリに ``mandelbrot.pgm`` が保存される。PGM は白黒の画像形式であり、GIMP などの画像編集ソフトで表示できる。

.. code-block:: text

   逐次: 5.44 秒
   プロセス: 1.38 秒 (chunksize=9)

要点
~~~~

* ``compute_row()`` は 1 行分の計算をする関数で、引数は行番号、戻り値は 800 バイトの ``bytes`` である。受け渡すデータが小さいため、プロセス間の受け渡しの負荷が小さい。
* ``chunksize`` は、コア数の 4 倍程度の塊に分かれるように計算している。塊が大きすぎると、計算量の多い行（集合の内部の行）が特定のプロセスに偏り、早く終わったプロセスが遊んでしまう。塊が小さすぎると、受け渡しの回数が増える。
* 逐次処理の結果と並列処理の結果が一致することを ``assert`` で確認している。並列化したときは、結果が変わっていないことを必ず確認する。

I/O と CPU の処理が混在するパイプライン
---------------------------------------

課題
~~~~

12 件のデータをネットワークから取得し、それぞれを解析したい。取得には 1 件あたり 0.3 秒の待ち時間があり、解析は CPU バウンドな計算である。

手法の選択
~~~~~~~~~~

取得は I/O バウンド、解析は CPU バウンドである。1 つの手法では両方を効率よく処理できないため、取得には ``asyncio`` を、解析にはプロセスを使い、``loop.run_in_executor()`` で組み合わせる。

執筆環境では次の結果になった。

.. code-block:: text

   イベントループの中で解析: 3.79 秒
   プロセスプールで解析: 1.36 秒
   解析結果の例: 6ea8810e6841

要点
~~~~

* ``process_blocking()`` は、解析をイベントループの中で直接実行する悪い例である。解析の間はイベントループが止まるため、他のタスクの取得も進まない。
* ``process_offloaded()`` は、``loop.run_in_executor()`` で解析をプロセスプールに任せる。解析の結果を ``await`` で待つ間もイベントループは動き続けるため、他のタスクの取得が進み、さらに複数の解析が並列に実行される。
* ``analyze()`` で使っている ``hashlib.sha256()`` は、大きなデータを処理する間は GIL を解放するが、このサンプルのように 32 バイトの小さなデータを繰り返し処理する場合はほとんど解放しない。そのため、スレッド（``asyncio.to_thread()``）ではなくプロセスを使っている。
* ``ProcessPoolExecutor`` は ``asyncio.run()`` の中で作成し、``with`` 文で確実に終了させている。

このように、1 つのプログラムの中でも、処理の部分ごとに性質を見極めて手法を使い分けることが重要である。
