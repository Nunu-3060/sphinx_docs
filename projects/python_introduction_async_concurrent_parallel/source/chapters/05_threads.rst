第 5 章 スレッドによる並行処理
==============================

この章では、``threading`` モジュールを使ったスレッドによる並行処理を説明する。:doc:`03_gil` で説明したとおり、通常の Python ではスレッドは I/O バウンドな処理に向いている。

スレッドの作成と実行
--------------------

スレッドは ``threading.Thread`` クラスで作成する。``target`` 引数にスレッドで実行する関数を、``args`` 引数にその関数に渡す引数をタプルで指定する。

.. code-block:: python
   :linenos:

   import threading
   import time


   def download(name: str) -> None:
       print(f"{name}: 開始")
       time.sleep(1.0)  # ダウンロードの代わり
       print(f"{name}: 終了")


   threads = [threading.Thread(target=download, args=(f"file{i}",)) for i in range(3)]
   for thread in threads:
       thread.start()  # スレッドの実行を開始する
   for thread in threads:
       thread.join()  # スレッドが終了するまで待つ
   print("すべて終了")

``start()`` メソッドでスレッドの実行が始まり、``join()`` メソッドでスレッドの終了を待つ。3 つのスレッドはそれぞれ 1 秒待つが、待ち時間が重なるため、全体は約 1 秒で終わる。

スレッドで実行した関数の戻り値は、``Thread`` クラスからは受け取れない。戻り値が必要な場合や、多数のタスクを扱う場合は、:doc:`07_futures` で説明する ``ThreadPoolExecutor`` を使うほうが簡単である。``Thread`` クラスを直接使うのは、長時間動き続けるスレッドを作る場合など、スレッドの寿命を自分で管理したい場合である。

競合状態
--------

スレッドは同じプロセスのメモリを共有するため、複数のスレッドから同じデータを読み書きできる。しかし、複数のスレッドが同じデータを同時に書き換えると、実行のタイミングによって結果が変わることがある。このような状態を **競合状態（race condition）** という。

.. code-block:: text

``increment_unsafe()`` では、あるスレッドが値を読み出してから書き込むまでの間に、別のスレッドが同じ値を読み出して書き込むことがある。その結果、2 回分の増加が 1 回分しか反映されず、更新が失われる。このサンプルでは、問題を再現しやすくするため、読み出しと書き込みの間に ``time.sleep(0)`` を入れて、他のスレッドに切り替わりやすくしている。``time.sleep(0)`` が無くても、切り替わるタイミングによっては同じ問題が起こる。発生の頻度が低いだけで、問題があることに変わりはない。

競合状態による不具合は、発生するかどうかが実行のタイミングに依存するため、テストで見つけにくく、再現も難しい。共有するデータを書き換える処理は、次に説明するロックで保護する必要がある。

ロックによる排他制御
--------------------

``threading.Lock`` は、ある範囲のコードを同時に 1 つのスレッドしか実行できないようにする仕組みである。このような制御を **排他制御** という。``with`` 文で ``Lock`` を使うと、ブロックに入るときにロックを獲得し、ブロックを抜けるときに解放する。例外が発生した場合もロックは解放される。

上のサンプルの ``increment_safe()`` では、値の読み出しから書き込みまでを ``with self._lock:`` で囲んでいる。あるスレッドがこのブロックを実行している間、他のスレッドはブロックの入り口で待たされるため、更新が失われない。

ロックで保護する範囲は、必要な処理だけに絞る。ロックを持ったまま時間のかかる I/O を行うと、他のスレッドが待たされ、並行処理の利点が失われる。

``threading`` モジュールには、``Lock`` のほかにも次のような同期の仕組みがある。

.. list-table:: threading モジュールの主な同期の仕組み
   :header-rows: 1
   :widths: 25 75

   * - クラス
     - 用途
   * - ``Lock``
     - 同時に 1 つのスレッドだけが実行できる範囲を作る。
   * - ``RLock``
     - ロックを獲得したスレッドが、解放する前に同じロックをもう一度獲得できる ``Lock``。ロックを獲得するメソッドから、同じロックを獲得する別のメソッドを呼ぶ場合に使う。
   * - ``Semaphore``
     - 同時に実行できるスレッドの数を、指定した数までに制限する。接続先のサーバーへの同時接続数を制限する場合などに使う。
   * - ``Event``
     - あるスレッドから他のスレッドへ、「準備ができた」「停止せよ」などの合図を送る。
   * - ``Condition``
     - 「キューにデータが入った」など、ある条件が満たされるまでスレッドを待たせる。

デッドロック
------------

複数のロックを使う場合は、**デッドロック** に注意する必要がある。デッドロックとは、複数のスレッドが互いに相手の持つロックの解放を待ち、どのスレッドも先に進めなくなる状態である。

.. code-block:: python
   :linenos:

   import threading

   lock_a = threading.Lock()
   lock_b = threading.Lock()


   def worker1() -> None:
       with lock_a:
           with lock_b:  # worker2 が lock_b を持っていると、ここで待ち続ける
               print("worker1")


   def worker2() -> None:
       with lock_b:
           with lock_a:  # worker1 が lock_a を持っていると、ここで待ち続ける
               print("worker2")

``worker1()`` が ``lock_a`` を、``worker2()`` が ``lock_b`` を獲得した時点で、両者は互いのロックの解放を待ち続ける。デッドロックを防ぐには、次の方法がある。

* **ロックを獲得する順序をすべてのスレッドで統一する。**\ 上の例では、``worker2()`` も ``lock_a``、``lock_b`` の順に獲得すれば、デッドロックは起こらない。
* **ロックを持ったまま、別のロックを獲得する処理を呼ばない。**\ ロックを 1 つしか使わない設計にできないかを検討する。
* **タイムアウトを設定する。**\ ``lock.acquire(timeout=1.0)`` のように獲得の待ち時間に上限を設けると、少なくとも永久に止まることは防げる。

Queue による生産者・消費者パターン
----------------------------------

ロックを正しく使い続けるのは難しい。スレッド間でデータを受け渡す場合は、共有データを直接書き換える代わりに、``queue.Queue`` を使うとよい。``Queue`` はスレッドから安全に使えるように作られており、内部で排他制御を行っている。

データを作るスレッド（生産者）が ``Queue`` にデータを入れ、データを処理するスレッド（消費者）が ``Queue`` から取り出す構成を、**生産者・消費者パターン** という。

このサンプルのポイントは次のとおりである。

* ``Queue(maxsize=3)`` のように上限を指定すると、キューが満杯のとき ``put()`` は空きができるまで待つ。生産が消費より速い場合でも、キューにデータがたまり続けてメモリを使い果たすことを防げる。
* ``get()`` はキューが空のとき、データが入るまで待つ。消費者は、データが来るのを待つためのループやロックを自分で書く必要がない。
* 仕事が無くなったことを伝えるため、消費者の数だけ番兵（``None``）を入れている。Python 3.13 以降では、``Queue.shutdown()`` メソッドでキューを閉じる方法もある。
* 結果のリスト ``results`` は複数のスレッドから書き換えるため、``Lock`` で保護している。

デーモンスレッド
----------------

Python のプログラムは、通常、すべてのスレッドが終了するまで終了しない。``Thread(target=..., daemon=True)`` のようにデーモンスレッドとして作成したスレッドは、デーモンでないスレッドがすべて終了した時点で、処理の途中であっても強制的に終了される。

デーモンスレッドは、終了時に後始末を行う機会が無いため、ファイルの書き込みなど途中で止まると困る処理には使わない。スレッドを確実に止めたい場合は、``Event`` などで停止の合図を送り、スレッド自身にループを抜けさせる。

スレッドを使うときの指針
------------------------

スレッドを使うときは、次の指針に従うと不具合を減らせる。

* スレッド間で書き換え可能なデータを共有することは、できるだけ避ける。データの受け渡しには ``Queue`` を使う。
* 共有が避けられない場合は、データとそれを保護するロックを 1 つのクラスにまとめ、クラスの外からはロックを意識せずに使えるようにする。
* ライブラリのオブジェクトをスレッド間で共有する場合は、そのオブジェクトがスレッドセーフかどうかをドキュメントで確認する。たとえば標準ライブラリの ``sqlite3`` の接続オブジェクトは、既定では作成したスレッド以外から使えない。
* 戻り値や例外を受け取る必要がある場合は、``Thread`` クラスを直接使わず、:doc:`07_futures` で説明する ``ThreadPoolExecutor`` を使う。

スレッドが向く場面・向かない場面
--------------------------------

.. list-table:: スレッドが向く場面・向かない場面
   :header-rows: 1
   :widths: 50 50

   * - 向く場面
     - 向かない場面
   * - 同期的な API しか持たないライブラリを使った I/O（HTTP クライアント、データベースのドライバーなど）を並行に実行する
     - Python で書かれた CPU バウンドな処理を速くする（プロセスを使う）
   * - GUI アプリケーションで、時間のかかる処理を画面の更新と並行して行う
     - 数千以上の接続を同時に扱う（``asyncio`` を使う）
   * - GIL を解放する C 拡張（NumPy など）の計算を並列に実行する
     - 多数のスレッドが同じデータを頻繁に書き換える
