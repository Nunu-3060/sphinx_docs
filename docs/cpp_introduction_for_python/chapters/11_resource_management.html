11. リソース管理

本章では、メモリなどのリソースを C++ でどのように管理するかを説明します。Python ではガベージコレクションがメモリを自動的に解放しますが、C++ では RAII と呼ばれる考え方でリソースを管理します。

11.1. new と delete

C++ では、new でヒープ領域にオブジェクトを生成し、delete で解放できます。

int* p = new int(42);  // ヒープ領域に int を生成する
std::cout << *p << '\n';
delete p;              // 解放する

new で生成したオブジェクトは、delete するまで解放されません。delete を忘れるとメモリリーク（使わないメモリが解放されずに残り続けること）になり、同じオブジェクトを 2 回 delete すると未定義動作になります。また、new と delete の間で関数から return したり例外が送出されたりすると、delete が実行されません。

このように new と delete を正しく対応させるのは難しいため、現代的な C++ では new と delete を直接使わず、次節以降で説明する RAII とスマートポインターを使います。

11.2. RAII

RAII（Resource Acquisition Is Initialization）は、リソースの取得をオブジェクトの初期化（コンストラクター）で行い、解放をデストラクターで行う考え方です。ここでいうリソースには、メモリのほか、ファイル、ネットワーク接続、ロックなど、使い終わったら解放が必要なものすべてが含まれます。

C++ では、ローカル変数のオブジェクトは、宣言したブロックを抜けるときに必ずデストラクターが呼ばれます。これは、return でブロックを抜ける場合も、例外が送出された場合も同じです。そのため、解放の処理をデストラクターに書いておけば、解放忘れが起こりません。

examples/ch11/raii.cpp
#include <iostream>
#include <string>

class Resource {
public:
    Resource(const std::string& name) : name_(name) {
        std::cout << "acquire " << name_ << '\n';
    }
    ~Resource() {
        std::cout << "release " << name_ << '\n';
    }

private:
    std::string name_;
};

int main() {
    Resource a("a");
    {
        Resource b("b");
        std::cout << "inside block\n";
    }  // ここで b のデストラクターが呼ばれる
    std::cout << "end of main\n";
    return 0;
}  // ここで a のデストラクターが呼ばれる
実行結果
acquire a
acquire b
inside block
release b
end of main
release a

RAII は、Python の with 文と同じ目的を持つ仕組みです。Python では with open("data.txt") as f: と書くと、ブロックを抜けるときにファイルが閉じられます。C++ でファイルを扱う std::ofstream や std::ifstream は、デストラクターでファイルを閉じるため、with 文に相当する構文を書かなくても、変数のスコープを抜けるとファイルが閉じられます。

std::string や std::vector も、内部で確保したメモリをデストラクターで解放しています。これまでのサンプルコードで delete を書く必要がなかったのは、このためです。

11.3. スマートポインター

ヒープ領域にオブジェクトを生成する必要がある場合は、new の代わりにスマートポインターを使います。スマートポインターは、RAII に基づいて、指しているオブジェクトを自動的に解放するクラスです。<memory> ヘッダーで提供されます。

型

特徴

std::unique_ptr

オブジェクトを単独で所有するポインター。コピーできず、ムーブで所有権を移すことだけができる。std::make_unique で生成する

std::shared_ptr

参照カウントで所有権を共有するポインター。最後の所有者が破棄されたときにオブジェクトを解放する。std::make_shared で生成する

std::weak_ptr

std::shared_ptr が管理するオブジェクトを、所有権を持たずに参照するポインター。循環参照を避けるために使う
examples/ch11/smart_ptr.cpp
#include <iostream>
#include <memory>
#include <utility>

struct Data {
    int value = 0;
};

int main() {
    std::unique_ptr<Data> p = std::make_unique<Data>();
    p->value = 42;
    // std::unique_ptr<Data> q = p;          // エラー: コピーできない
    std::unique_ptr<Data> q = std::move(p);  // 所有権を q に移す
    std::cout << (p == nullptr) << ' ' << q->value << '\n';  // 1 42

    std::shared_ptr<Data> s1 = std::make_shared<Data>();
    {
        std::shared_ptr<Data> s2 = s1;        // 所有権を共有する
        std::cout << s1.use_count() << '\n';  // 2
    }
    std::cout << s1.use_count() << '\n';      // 1
    return 0;
}  // 所有者がいなくなった時点で、オブジェクトは自動的に解放される
実行結果
1 42
2
1

std::shared_ptr の仕組みは、CPython の参照カウントによるオブジェクト管理に似ています。ただし、C++ には循環参照を回収するガベージコレクションがないため、std::shared_ptr 同士が互いを指すと解放されなくなります。

まずは std::unique_ptr を使い、所有権の共有が本当に必要な場合にだけ std::shared_ptr を使ってください。

11.4. コピーとムーブ

「ポインターと参照」で説明したとおり、C++ の代入や初期化では値がコピーされます。std::vector や std::string のコピーでは、すべての要素が複製されるため、大きなデータではコストが大きくなります。

ムーブは、コピーを作らずに、リソースの所有権を別のオブジェクトへ移す操作です。例えば std::string のムーブでは、文字列を格納しているメモリの所有権だけが移るため、文字列の長さに関係なく高速です。変数を std::move で囲むと、その変数の中身をムーブしてよいことをコンパイラーに伝えられます。

examples/ch11/move.cpp
#include <iostream>
#include <string>
#include <utility>
#include <vector>

int main() {
    std::vector<std::string> names;
    std::string first = "Alice";
    std::string second = "Bob";

    names.push_back(first);              // コピー: first の値はそのまま残る
    names.push_back(std::move(second));  // ムーブ: second の中身が names に移される

    std::cout << first << '\n';         // Alice
    std::cout << names.size() << '\n';  // 2
    // ムーブ後の second の値は未規定なので、再代入するまで使わない
    return 0;
}
実行結果
Alice
2

警告

ムーブ後の変数は、有効ではあるものの値が未規定の状態になります。ムーブした変数は、新しい値を代入するまで使わないでください。

関数から std::vector などのオブジェクトを値で返す場合は、コンパイラーが自動的にムーブやコピーの省略を行うため、std::move を書く必要はありません。

11.5. Rule of Zero

自作のクラスでは、コピーやムーブの動作（コピーコンストラクター、ムーブコンストラクターなど）とデストラクターを、コンパイラーが自動的に生成します。メンバー変数が std::string、std::vector、std::unique_ptr などの RAII に基づく型だけであれば、自動生成された動作で正しくコピー、ムーブ、解放が行われます。

そのため、リソースの管理は標準ライブラリのクラスに任せ、自作のクラスではこれらの特殊なメンバー関数を定義しないのが最善です。この指針を Rule of Zero と呼びます。これまでに示した Point クラスも、この指針に従っています。
