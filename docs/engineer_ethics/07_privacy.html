7. プライバシーと個人情報

ソフトウェアは、利用者の行動や属性に関する大量のデータを扱います。この章では、プライバシーを守るための法令上の義務と、設計上の考え方を説明します。

7.1. プライバシーと個人情報の違い

プライバシーとは、私生活をみだりに公開されない権利や、自分に関する情報の流れを自分でコントロールする権利を指します。個人情報は、プライバシーを守るために法令で保護の対象とされる情報です。

法令上は個人情報に当たらない情報でも、扱い方によってはプライバシーを侵害します。たとえば、個人を特定しない閲覧履歴であっても、それを使って利用者の健康状態や思想を推測し、本人が望まない広告を表示すれば、利用者は不快に感じます。技術者は、法令を守るだけでなく、利用者の期待を裏切らない扱い方を考える必要があります。

7.2. 個人情報保護法の要点

日本では、個人情報保護法（個人情報の保護に関する法律）が、個人情報を扱う事業者の義務を定めています。技術者が知っておくべき主な義務は次のとおりです。

義務

内容

利用目的の特定と通知

個人情報を何に使うかをできる限り具体的に定め、本人に通知または公表します。特定した目的の範囲を超えて使う場合は、原則として本人の同意が必要です。

適正な取得

うそや不正な手段で個人情報を取得しません。

安全管理措置

漏えい、滅失、毀損を防ぐために、組織的・人的・物理的・技術的な対策を講じます。

漏えい時の報告

一定の重大な漏えい（要配慮個人情報の漏えい、1,000 人を超える漏えいなど）が発生した場合は、個人情報保護委員会への報告と本人への通知を行います。

第三者提供の制限

個人データを第三者に提供する場合は、原則として本人の同意を得ます。

本人からの請求への対応

本人から開示、訂正、利用停止などを求められた場合に対応します。

欧州連合（EU）の GDPR（一般データ保護規則）は、EU 域内の人の個人データを扱う事業者に、日本の事業者も含めて適用されることがあります。GDPR は、違反に対して高額の制裁金を定めているため、海外向けのサービスを開発する場合は特に注意が必要です。

7.3. プライバシー・バイ・デザイン

プライバシー・バイ・デザインは、プライバシーの保護を、問題が起きてから対処するのではなく、システムの企画・設計の段階から組み込むという考え方です。カナダ・オンタリオ州の情報・プライバシー・コミッショナーであった Ann Cavoukian が提唱しました。GDPR でも、データ保護・バイ・デザインとして事業者の義務になっています。

プライバシー・バイ・デザインを実践するための具体的な方法には、次のようなものがあります。

データ最小化

目的の達成に必要なデータだけを集めます。「いつか使うかもしれない」という理由でデータを集めません。

保存期間の設定

データごとに保存期間を決め、期間が過ぎたら削除します。

既定値でのプライバシー保護

利用者が何も設定しなくても、プライバシーが保護される状態を既定値にします。たとえば、位置情報の共有は、利用者が明示的に有効にするまで無効にしておきます。

アクセス権限の制限

個人情報にアクセスできる人やシステムを、業務上必要な範囲に限定します。

ログへの配慮

障害調査用のログに、個人情報をそのまま出力しません。

7.4. ログに出力する個人情報のマスキング

ログは多くの人が閲覧し、長期間保存されるため、個人情報の漏えい経路になりやすい場所です。次のコードは、Python の logging モジュールのフィルターを使い、メールアドレスと電話番号を伏せ字にしてからログに出力する例です。

16# メールアドレス（例: taro.yamada@example.com）
17EMAIL_PATTERN = re.compile(r"[\w.+-]+@[\w-]+(?:\.[\w-]+)+")
18
19# ハイフン区切りの国内電話番号（例: 090-1234-5678, 03-1234-5678）
20PHONE_PATTERN = re.compile(r"\b0\d{1,4}-\d{1,4}-\d{3,4}\b")
21
22
23def mask_email(match: re.Match[str]) -> str:
24    """メールアドレスのローカル部を先頭 1 文字だけ残して伏せます。"""
25    local, domain = match.group(0).split("@", 1)
26    return f"{local[0]}***@{domain}"
27
28
29def mask_phone(match: re.Match[str]) -> str:
30    """電話番号の末尾 4 桁だけを残し、それ以外の数字を伏せます。"""
31    phone = match.group(0)
32    head, tail = phone[:-4], phone[-4:]
33    return re.sub(r"\d", "*", head) + tail
34
35
36def mask_pii(text: str) -> str:
37    """文字列に含まれるメールアドレスと電話番号をマスキングします。"""
38    text = EMAIL_PATTERN.sub(mask_email, text)
39    return PHONE_PATTERN.sub(mask_phone, text)
40
41
42class PiiMaskingFilter(logging.Filter):
43    """ログレコードのメッセージから個人情報を取り除くフィルターです。"""
44
45    def filter(self, record: logging.LogRecord) -> bool:
46        # 引数を埋め込んだ後のメッセージをマスキングし、引数は破棄します。
47        record.msg = mask_pii(record.getMessage())
48        record.args = None
49        return True

このプログラムを実行すると、taro.yamada@example.com は t***@example.com に、090-1234-5678 は ***-****-5678 に置き換えて出力されます。プログラム全体は、サンプルコード一覧の「個人情報のマスキング」で確認できます。

正規表現によるマスキングは、想定した形式の情報しか検出できません。ログに出力する項目そのものを最小限にすることが、最も確実な対策です。

7.5. 仮名化と匿名化

個人情報を分析などに使うときは、個人を識別しにくい形に加工することが有効です。代表的な加工の方法は次の 2 つです。

方法

内容

注意点

仮名化

氏名や電話番号などの識別子を、別の値（仮名）に置き換えます。同じ人のデータには同じ仮名が付くため、データを突き合わせた分析ができます。

置き換えの対応表や鍵があれば元に戻せるため、引き続き個人情報として管理する必要があります。

匿名化

特定の個人を識別できず、元の情報に戻せないように加工します。

珍しい属性の組み合わせ（年齢・職業・居住地など）から個人が特定されることがあります。識別子を削除しただけでは匿名化として不十分です。

個人情報保護法には、仮名化に相当する仮名加工情報と、匿名化に相当する匿名加工情報の制度があり、それぞれ加工の基準や取り扱いのルールが定められています。

仮名化の実装では、識別子を単純なハッシュ値に置き換えるだけでは不十分です。電話番号のように取り得る値の種類が少ない識別子は、すべての候補のハッシュ値を計算すれば元の値を突き止められるからです。次のコードは、秘密鍵を使う HMAC で識別子を仮名に置き換える例です。

41def pseudonymize(identifier: str, key: bytes) -> str:
42    """識別子を HMAC-SHA256 で仮名に置き換えます。
43
44    同じ鍵と同じ識別子からは常に同じ仮名が得られるため、
45    仮名化した後もデータどうしを突き合わせて分析できます。
46    """
47    digest = hmac.new(key, identifier.encode("utf-8"), hashlib.sha256)
48    return digest.hexdigest()[:TOKEN_LENGTH]

鍵はデータとは別の場所で管理し、データの受け渡し先には渡しません。プログラム全体は、サンプルコード一覧の「識別子の仮名化」で確認できます。

7.6. この章のまとめ

  • 法令上の個人情報に当たらない情報でも、扱い方によってはプライバシーを侵害します。

  • 個人情報保護法は、利用目的の特定、安全管理措置、漏えい時の報告、第三者提供の制限などを定めています。

  • プライバシー・バイ・デザインの考え方に基づき、企画・設計の段階からプライバシーの保護を組み込みます。

  • 仮名化したデータは引き続き個人情報として扱い、識別子の置き換えには鍵付きの HMAC を使います。
