6. セキュリティ

情報システムへの攻撃は、利用者の財産やプライバシーを直接脅かします。この章では、セキュリティに関わる技術者の責任、依存するソフトウェアを通じた攻撃への備え、開発したソフトウェアが悪用されたときの責任、脆弱性や攻撃技術を扱うときの注意点を説明します。

6.1. セキュリティは技術者の責任

セキュリティの対策は、専門の部署だけが担うものではありません。設計や実装に携わるすべての技術者が、次の点に責任を持ちます。

  • 既知の攻撃手法（SQL インジェクション、クロスサイトスクリプティングなど）への対策を実装します。

  • パスワードなどの認証情報を安全に保存します。

  • 利用しているライブラリの脆弱性情報を確認し、必要に応じて更新します。

  • 秘密鍵やパスワードを、ソースコードやログに含めません。

セキュリティの不備は、技術者自身が気付かないうちに利用者に損害を与えます。「知らなかった」では済まされないため、基本的な対策を学び続けることが求められます。

6.2. セキュアコーディングの例

6.2.1. SQL インジェクション

SQL インジェクションは、利用者の入力を SQL 文に直接埋め込むことで、攻撃者が任意の SQL を実行できてしまう脆弱性です。

次のコードは、入力を文字列連結で SQL 文に埋め込む悪い例です。

30def find_user_unsafe(conn: sqlite3.Connection,
31                     name: str) -> list[tuple[str, str]]:
32    """【悪い例】入力を文字列連結で SQL 文に埋め込みます。"""
33    sql = f"SELECT name, email FROM users WHERE name = '{name}'"
34    return conn.execute(sql).fetchall()

入力として ' OR '1'='1 を与えると、SQL 文の条件が常に真になり、すべての利用者の情報が返されます。

次のコードは、プレースホルダーを使う良い例です。入力は SQL の一部ではなく、常に値として扱われます。

37def find_user_safe(conn: sqlite3.Connection,
38                   name: str) -> list[tuple[str, str]]:
39    """【良い例】プレースホルダーを使って入力を値として渡します。"""
40    sql = "SELECT name, email FROM users WHERE name = ?"
41    return conn.execute(sql, (name,)).fetchall()

プログラム全体は、サンプルコード一覧の「SQL インジェクションの比較」で確認できます。

6.2.2. パスワードの保存

パスワードは、平文で保存してはいけません。また、MD5 や SHA-256 のような高速なハッシュ関数を 1 回適用しただけの値も、総当たりで復元されやすいため不適切です。パスワードの保存には、利用者ごとに異なるソルトを付け、意図的に計算コストを高めたハッシュ関数（Argon2id、scrypt、bcrypt など）を使います。

次のコードは、Python 標準ライブラリの hashlib.scrypt を使ってパスワードをハッシュ化する例です。

44def hash_password(password: str) -> str:
45    """パスワードを保存用の文字列に変換します。
46
47    戻り値は「方式$N$r$p$ソルト$ハッシュ値」の形式です。
48    パラメーターも一緒に保存しておくと、将来コストを引き上げたときにも
49    古いハッシュ値を照合できます。
50    """
51    salt = secrets.token_bytes(SALT_BYTES)
52    key = _derive_key(password, salt, SCRYPT_N, SCRYPT_R, SCRYPT_P)
53    return "$".join(
54        ["scrypt", str(SCRYPT_N), str(SCRYPT_R), str(SCRYPT_P),
55         salt.hex(), key.hex()]
56    )

照合するときは、比較にかかる時間の差から情報が漏れないよう、hmac.compare_digest で比較します。

59def verify_password(password: str, stored: str) -> bool:
60    """入力されたパスワードが保存済みのハッシュ値と一致するか調べます。"""
61    scheme, n, r, p, salt_hex, key_hex = stored.split("$")
62    if scheme != "scrypt":
63        raise ValueError(f"未対応の方式です: {scheme}")
64    key = _derive_key(password, bytes.fromhex(salt_hex), int(n), int(r),
65                      int(p))
66    # 比較にかかる時間から情報が漏れないよう、定数時間で比較します。
67    return hmac.compare_digest(key, bytes.fromhex(key_hex))

プログラム全体は、サンプルコード一覧の「パスワードの安全な保存」で確認できます。

6.3. 脆弱性を見つけたとき

他社の製品やウェブサイトの脆弱性を見つけた場合、その情報を公開すれば利用者に注意を促せますが、修正前に公開すると攻撃者に悪用されるおそれがあります。そこで、まず製品の開発者に非公開で連絡し、修正の準備が整ってから公表する方法が広く採られています。これを責任ある開示（協調的な脆弱性開示）といいます。

日本では、情報セキュリティ早期警戒パートナーシップという枠組みがあり、ソフトウェア製品やウェブサイトの脆弱性を IPA（情報処理推進機構）に届け出ることができます。IPA と JPCERT/CC（JPCERT コーディネーションセンター）が、届出者と開発者の間を調整します。

脆弱性を見つけたときに注意すべき点は次のとおりです。

  • 脆弱性の有無を確かめるために、他人のシステムに無断で攻撃を試みません。不正アクセス禁止法などに違反するおそれがあります。

  • 脆弱性を通じて得た情報（個人情報など）を、保存したり第三者に渡したりしません。

  • 修正される前に、脆弱性の詳細を SNS などで公開しません。

6.4. ソフトウェアサプライチェーンのセキュリティ

現代のソフトウェアは、多数の OSS パッケージや外部のサービスを組み合わせて作られています。自分が書いたコードが安全でも、依存しているパッケージが侵害されれば、利用者に被害が及びます。ソフトウェアが作られて利用者に届くまでの一連の流れをソフトウェアサプライチェーンといい、この流れのどこかに悪意のあるコードを紛れ込ませる攻撃が増えています。

代表的な攻撃の手口は次のとおりです。

手口

内容

なりすましのパッケージ

有名なパッケージと紛らわしい名前の、悪意のあるパッケージを公開し、入力の誤りを狙います。

保守者のアカウントの乗っ取り

パッケージの保守者のアカウントを乗っ取り、正規のパッケージの新しい版として悪意のあるコードを配布します。

保守者になりすました長期的な侵入

時間をかけてプロジェクトに貢献して信頼を得たうえで、悪意のあるコードを混入させます。

利用者の立場でできる対策には、次のようなものがあります。

  • 依存するパッケージを必要最小限にし、信頼できる提供元かどうかを確認します。

  • 利用するパッケージの版を固定し、更新するときは変更の内容を確認します。

  • 依存関係を一覧にした SBOM（ソフトウェア部品表）を作成し、脆弱性が公表されたときに影響の有無をすぐに調べられるようにします。

  • 依存するパッケージの脆弱性情報を、ツールなどを使って継続的に確認します。

コラム：1 人のエンジニアの気付きが防いだバックドア

2024 年 3 月 29 日、Linux で広く使われているデータ圧縮のソフトウェア xz utils の新しい版（5.6.0 と 5.6.1）に、外部から遠隔でコードを実行できるバックドアが仕込まれていることが公表されました。

このプロジェクトは、長年ほぼ 1 人の保守者によって支えられていました。攻撃者は数年をかけて協力者として信頼を得て、保守の権限を手に入れたうえで、バックドアを混入させていました。

発見したのは、別のソフトウェアを開発していたエンジニアでした。SSH でのログインにわずかに時間がかかり、CPU の使用量が多いことを不審に思って調査し、問題を突き止めました。多くの Linux ディストリビューションの安定版に取り込まれる前に発見されたため、被害は限定的でした。

この事例は、OSS を保守する人の負担という構造的な問題（知的財産とライセンスを参照）と、小さな異常を見過ごさずに調べて報告することの価値を示しています。

6.5. 開発したソフトウェアが悪用されたとき

自分が開発したソフトウェアが、他人によって犯罪に使われることがあります。このとき、開発者は責任を問われるのでしょうか。日本では、この問題を考えるうえで重要な 2 つの判例があります。

事件

概要

判決

Winny 事件

ファイル共有ソフト Winny の開発者が、利用者による著作権侵害を手助けしたとして、著作権法違反の幇助の罪で起訴されました。

一審は有罪でしたが、2011 年 12 月に最高裁で無罪が確定しました。最高裁は、ソフトウェアが違法な用途にも適法な用途にも使える場合、一般的な悪用の可能性を認識していただけでは幇助は成立しないと判断しました。

Coinhive 事件

ウェブサイトの運営者が、閲覧者の PC の計算能力を使って仮想通貨を採掘するプログラムを、閲覧者に知らせずにサイトに設置し、不正指令電磁的記録に関する罪で起訴されました。

二審は有罪でしたが、2022 年 1 月に最高裁で無罪となりました。最高裁は、閲覧者の意図に反するプログラムであったとしても、閲覧者への影響の程度などから、社会的に許容し得ない不正なプログラムとまではいえないと判断しました。

これらの判例から、次のことがいえます。

  • 技術そのものは中立であり、悪用される可能性があるというだけで、開発者が刑事責任を問われるわけではありません。

  • ただし、無罪となったことは、倫理的に問題がなかったことを意味しません。法と倫理は別であることは、技術者倫理とはで説明したとおりです。たとえば Coinhive 事件では、閲覧者に知らせずに計算資源を使ったことの是非が、技術者の間でも議論になりました。

  • ソフトウェアを公開するときは、想定される悪用の方法と、その影響を減らす工夫（利用者への説明、悪用されにくい設計など）を考えることが、技術者としての責任です。

6.6. 攻撃技術の扱い

攻撃の手法を理解することは、防御のために欠かせません。一方で、攻撃技術は悪用されれば大きな被害をもたらします。攻撃技術を学んだり検証したりするときは、次の点を守ってください。

  • 検証は、自分が管理する環境か、所有者から書面で許可を得た環境だけで行います。

  • 許可を得た範囲（対象のシステム、期間、手法）を超えません。

  • 正当な理由なく、利用者の意図に反して動作する不正なプログラム（コンピューターウイルスなど）を作成・提供することは、刑法の不正指令電磁的記録に関する罪に当たるおそれがあります。

  • 攻撃ツールや検証コードを公開する場合は、悪用された場合の影響を考慮します。

6.7. この章のまとめ

  • セキュリティは、設計や実装に携わるすべての技術者の責任です。

  • 入力はプレースホルダーで値として扱い、パスワードはソルトと計算コストの高いハッシュ関数で保存します。

  • 脆弱性を見つけたら、責任ある開示の手順に従い、IPA への届出などを利用します。

  • 依存するパッケージも攻撃の経路になるため、依存関係を把握し、継続的に確認します。

  • ソフトウェアが悪用される可能性があるだけで刑事責任を問われるわけではありませんが、悪用の影響を減らす工夫は技術者の責任です。

  • 攻撃技術の検証は、許可を得た環境と範囲だけで行います。
