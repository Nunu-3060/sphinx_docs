7. プロファイリング

プロファイリングとは、プログラムの処理時間やメモリの使用量を計測し、ボトルネックを特定する作業です。本章では、Unity の Profiler と関連するツールの使い方を説明します。

7.1. Profiler の概要

Profiler ウィンドウは、フレームごとの処理時間やメモリの使用量などを記録し、グラフで表示するツールです。メニューの Window ‣ Analysis ‣ Profiler（Ctrl+7）で開きます。

Profiler ウィンドウを開いた状態で再生すると、計測が始まります。ツールバーの記録ボタンで、計測の開始と停止を切り替えられます。グラフ上をクリックするとそのフレームが選択され、ウィンドウ下部に詳細が表示されます。

Profiler は、計測する分野ごとにモジュールで構成されています。主なモジュールは次のとおりです。

モジュール

計測する内容

CPU Usage

CPU の処理時間。スクリプト、物理演算、描画の指示など、処理の内訳を確認できます。最もよく使うモジュールです。

GPU Usage

GPU の処理時間。対応していないプラットフォームやグラフィックス API もあります。

Rendering

ドローコールの数、SetPass コールの数、描画したポリゴン数など、描画に関する統計情報。

Memory

メモリの使用量の概要と、GC アロケーションの量。

Physics

物理演算で処理しているオブジェクトの数や、衝突の数など。

UI

uGUI の処理時間や、Canvas の再構築の回数など。

Audio

再生中の音声の数や、音声処理の負荷。

7.2. CPU Usage モジュール

CPU Usage モジュールを選択すると、ウィンドウ下部に選択したフレームの処理の内訳が表示されます。表示方法は、左上のメニューで切り替えます。

7.2.1. Timeline 表示

メインスレッドやレンダースレッドなど、スレッドごとの処理を時間軸に沿って帯で表示します。処理同士の前後関係や、どのスレッドが何を待っているかを把握するのに適しています。CPU バウンドか GPU バウンドかの判断にも使います（CPU バウンドと GPU バウンドの見分け方）。

7.2.2. Hierarchy 表示

処理を呼び出し関係に沿って階層で表示します。各列の意味は次のとおりです。

列

意味

Total

その処理が、フレーム全体の処理時間に占める割合。その処理から呼び出された処理の時間も含みます。

Self

その処理自身が占める割合。呼び出した処理の時間は含みません。

Calls

そのフレームで呼び出された回数。

GC Alloc

そのフレームで発生した GC アロケーションの量（ガベージコレクションと GC アロケーションの削減）。

Time ms

Total を時間で表したもの。

Self ms

Self を時間で表したもの。

列の見出しをクリックすると、その列で並べ替えられます。Time ms で並べ替えると処理時間の長い処理を、GC Alloc で並べ替えると GC アロケーションの多い処理を見つけられます。

7.2.3. Deep Profile

Profiler は、既定では Unity のエンジン内部の処理と、Update などのイベント関数の単位でしか処理時間を計測しません。ツールバーの Deep Profile を有効にすると、スクリプトのすべてのメソッドの呼び出しが計測されるようになります。

ただし、Deep Profile は計測自体の負荷が非常に大きく、表示される処理時間が実際よりも大幅に長くなります。Deep Profile は重い処理がどこにあるかの見当をつけるために使い、正確な時間は次の ProfilerMarker で計測してください。

7.3. ProfilerMarker による独自区間の計測

ProfilerMarker を使うと、スクリプトの任意の区間に名前を付けて、Profiler に表示できます。Deep Profile を使わずに、知りたい処理の時間だけを計測できます。

ProfilerMarkerExample.cs
using Unity.Profiling;
using UnityEngine;

/// <summary>
/// ProfilerMarker を使って、任意の処理区間を Profiler に表示するサンプルです。
/// </summary>
/// <remarks>
/// 再生中に Profiler ウィンドウの CPU Usage モジュールを開き、
/// 「ProfilerMarkerExample.」で始まる項目を探してください。
/// ProfilerMarker の計測処理は、Development Build ではないビルドでは自動的に取り除かれます。
/// </remarks>
public class ProfilerMarkerExample : MonoBehaviour
{
    // マーカーは生成にコストがかかるため、static readonly フィールドとして一度だけ生成します。
    private static readonly ProfilerMarker s_CalculateMarker =
        new ProfilerMarker("ProfilerMarkerExample.Calculate");

    private static readonly ProfilerMarker s_ApplyMarker =
        new ProfilerMarker("ProfilerMarkerExample.Apply");

    [SerializeField, Tooltip("1 フレームあたりの計算回数。増やすと処理が重くなります。")]
    private int iterationCount = 100000;

    private float result;

    private void Update()
    {
        // using ブロックを使う方法です。ブロックを抜けると自動的に計測が終了します。
        using (s_CalculateMarker.Auto())
        {
            result = Calculate();
        }

        // Begin と End を明示的に呼び出す方法です。End の呼び出し忘れに注意してください。
        s_ApplyMarker.Begin();
        transform.localScale = Vector3.one * (1f + Mathf.Abs(result) * 0.0001f);
        s_ApplyMarker.End();
    }

    /// <summary>
    /// 計測対象とする、意図的に重くした処理です。
    /// </summary>
    private float Calculate()
    {
        float sum = 0f;
        for (int i = 0; i < iterationCount; i++)
        {
            sum += Mathf.Sin(i * 0.001f);
        }

        return sum;
    }
}

ProfilerMarkerExample.cs をダウンロード

ProfilerMarker の計測処理は、Development Build ではないビルドでは自動的に取り除かれます。そのため、計測用のコードを製品のコードに残しておいても、性能への影響はありません。

7.4. Frame Debugger による描画処理の確認

Frame Debugger は、1 フレームの描画が、どのような順序の描画命令で行われているかを確認するツールです。メニューの Window ‣ Analysis ‣ Frame Debugger で開き、Enable をクリックすると、再生が一時停止して描画命令の一覧が表示されます。

一覧から描画命令を選択すると、その命令までの描画結果が Game ビューに表示されます。また、描画命令ごとに、使われたシェーダーやマテリアルの設定、前の描画命令とまとめて描画（バッチング）されなかった理由を確認できます。描画の最適化（描画（GPU）の最適化）を行う際に、効果を確認するために使います。

7.5. Memory Profiler パッケージ

Profiler の Memory モジュールではメモリの使用量の概要しか分かりませんが、Memory Profiler パッケージを使うと、どのオブジェクトがどれだけのメモリを使っているかを詳しく調べられます。

Package Manager で Memory Profiler パッケージを導入し、メニューの Window ‣ Analysis ‣ Memory Profiler で開きます。Capture をクリックすると、その時点のメモリの状態（スナップショット）が保存されます。スナップショットでは、テクスチャ、メッシュ、スクリプトのオブジェクトなど、種類ごとのメモリの使用量を確認できます。

2 つのスナップショットを比較することもできます。たとえば、あるシーンに入る前と、そのシーンから出た後のスナップショットを比較すると、解放されずに残っているオブジェクト（メモリリーク）を見つけられます。

7.6. Profile Analyzer による比較

Profiler は 1 フレームずつ詳細を確認するのには適していますが、多数のフレームを通した傾向を把握するのは苦手です。Profile Analyzer パッケージを使うと、Profiler で記録した複数フレームのデータを集計し、処理ごとの中央値や最大値を確認できます。

Package Manager で Profile Analyzer パッケージを導入し、メニューの Window ‣ Analysis ‣ Profile Analyzer で開きます。改善前と改善後のデータを読み込んで比較すると、最適化の効果を数値で確認できます。

7.7. エディターでの計測と実機での計測の違い

エディターで再生したゲームを計測すると、ゲームの処理に加えて、エディター自体の処理（Inspector ウィンドウや Scene ビューの更新など）も含まれます。また、開発用のパソコンは多くの場合、対象の端末よりも高性能です。そのため、エディターでの計測結果は実機の性能を正しく表しません。

エディターでの計測は、「改善前と改善後で処理時間がどう変わったか」といった相対的な比較や、GC アロケーションの有無の確認に使います。性能の目標を満たしているかどうかは、Development Build を実機で動かして計測してください（実機でのデバッグ）。

注釈

Profiler ウィンドウの接続先のメニューで Edit Mode を選ぶと、ゲームではなくエディター自体の処理を計測できます。エディターの動作が重い原因を調べる場合に使います。
