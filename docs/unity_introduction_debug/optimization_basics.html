6. 最適化の基礎

本章から最適化に入ります。個々の手法を学ぶ前に、最適化をどのような考え方と手順で進めるべきかを説明します。

6.1. 最適化の心構え

6.1.1. 推測せずに計測する

最適化で最も重要なのは、処理が遅い原因を推測で決めつけず、計測して特定することです。「このコードが重そうだ」という直感は外れることが多く、実際には負荷の小さい部分を改善しても、全体の処理時間はほとんど変わりません。一般に、処理時間の大部分は、プログラムのごく一部に集中しています。この処理時間の大部分を占める部分を、ボトルネックと呼びます。

6.1.2. 早すぎる最適化を避ける

最適化されたコードは、読みにくく、変更しにくくなりがちです。問題が起きていない段階で、効果の分からない最適化を行うことは避けましょう。ただし、対象とする端末で性能の目標を満たせるかどうかは、開発の早い段階から定期的に確認することが重要です。開発の終盤になって大きな問題が見つかると、設計からやり直すことになりかねません。

6.2. フレーム時間の予算

ゲームは、1 秒間に何回も画面を更新して動きを表現します。1 秒間の更新回数をフレームレートと呼び、fps（frames per second）という単位で表します。目標のフレームレートを \(f\) [fps] とすると、1 フレームの処理に使える時間 \(T\) は次の式で求められます。

\[T = \frac{1000}{f} \quad \text{[ms]}\]

主なフレームレートと、1 フレームあたりの時間は次のとおりです。

目標のフレームレート

1 フレームあたりの時間

30 fps

約 33.33 ms

60 fps

約 16.67 ms

90 fps

約 11.11 ms

120 fps

約 8.33 ms

この時間を、フレーム時間の予算と考えます。スクリプト、物理演算、アニメーション、描画など、1 フレームに行うすべての処理を予算内に収める必要があります。1 つでも予算を超えるフレームがあると、画面の更新が遅れ、カクつき（スパイク）として感じられます。

スマートフォンでは、高い負荷が続くと端末が発熱し、温度を下げるために CPU や GPU の動作速度が落とされることがあります。長時間安定して動作させるには、予算を使い切らずに余裕を残しておくことが重要です。

注釈

Android と iOS では、Application.targetFrameRate を設定しない場合、既定で 30 fps で動作します。60 fps で動作させたい場合は、スクリプトで Application.targetFrameRate = 60; のように設定します。

6.3. CPU バウンドと GPU バウンドの見分け方

1 フレームの処理は、主に CPU と GPU が分担して並行して行います。

  • CPU は、スクリプト、物理演算、アニメーションなどの処理と、GPU に描画を指示する処理を行います。

  • GPU は、CPU の指示に従って、実際に画面を描画します。

フレーム時間は、CPU と GPU のうち遅い方に合わせて決まります。CPU の処理が原因で遅くなっている状態を CPU バウンド、GPU の処理が原因で遅くなっている状態を GPU バウンドと呼びます。どちらのバウンドかによって有効な対策がまったく異なるため、最適化の最初にこれを見分けます。

確認方法

判断の目安

Profiler の CPU Usage モジュールの Timeline 表示（CPU Usage モジュール）

メインスレッドで Gfx.WaitForPresentOnGfxThread などの待機が長い場合は、GPU（または描画を指示するレンダースレッド）の処理を待っているため、GPU バウンドの可能性があります。スクリプトなどの処理が長い場合は、CPU バウンドです。

描画の解像度を下げる

URP Asset の Render Scale を下げてフレームレートが改善する場合は、GPU バウンドの可能性が高いと判断できます。

なお、Timeline 表示に WaitForTargetFPS が表示される場合、これは目標のフレームレートや垂直同期に合わせるための待ち時間です。処理の負荷ではなく、予算に余裕があることを示しています。

6.4. 最適化の手順

最適化は、次の手順を繰り返して進めます。

  1. 目標を決める: 対象とする端末と、目標のフレームレートやメモリの使用量を決めます。

  2. 計測する: 対象の端末で、Profiler を使って現状を計測します（プロファイリング）。

  3. ボトルネックを特定する: CPU バウンドか GPU バウンドかを見分け、処理時間の大部分を占めている部分を特定します。

  4. 対処する: ボトルネックに対して改善を行います。効果を正しく評価できるように、一度に行う変更は 1 つにします。

  5. 再計測する: 同じ条件で計測し、改善の効果を確認します。効果がなかった変更は、コードが複雑になるだけなので元に戻します。

第 8 章以降では、ボトルネックの種類ごとに、代表的な改善手法を紹介します。
