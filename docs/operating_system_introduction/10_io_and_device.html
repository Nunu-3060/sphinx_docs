10. 入出力とデバイス

計算機には、ストレージ、ネットワーク、キーボード、ディスプレイ、USB 機器など、多種多様な入出力装置（デバイス）がつながっています。この章では、OS がこれらの装置をどのように制御しているかと、アプリケーションが入出力を行う方式の違いを説明します。

10.1. デバイスドライバ

入出力装置の操作方法は、装置の種類やメーカーごとに異なります。OS は、装置ごとの違いを吸収するために、装置を操作するプログラムを部品として分離しています。これをデバイスドライバと呼びます。

デバイスドライバは、OS の他の部分に対しては、装置の種類ごとに決められた共通のインターフェースを提供し、装置に対しては、その装置固有の方法で命令を送ります。例えば、どのメーカーのネットワークカードのドライバも「パケットを送る」「受け取ったパケットを渡す」という同じインターフェースを持つので、カーネルのネットワークの処理は、装置の違いを意識せずに済みます。

デバイスドライバは、OS のソースコードの中で最も大きな割合を占める部分です。Linux カーネルのソースコードでは、その半分以上をドライバが占めています。また、ドライバはカーネルモードで動くことが多いため、ドライバの不具合は OS 全体の停止につながります。OS の不具合の原因の多くがドライバにあることは、マイクロカーネルの考え方（「ハードウェアとカーネル」を参照）を支持する根拠の 1 つにもなっています。

10.1.1. デバイスの種類

UNIX 系 OS では、装置をおおまかに次の 3 種類に分けて扱います。

表 10.1 デバイスの種類

種類

特徴

例

ブロックデバイス

決まった大きさのブロック単位で、任意の位置を読み書きできる

HDD、SSD

端末、シリアルポート、マウス

ブロックデバイスとキャラクタデバイスは、/dev ディレクトリの下にデバイスファイルとして現れ、通常のファイルと同じように open や read で扱えます。例えば /dev/sda は 1 台目のストレージ装置、/dev/null は書き込んだデータをすべて捨てる特殊な装置です。

10.2. CPU と装置のやり取り

装置には、CPU から読み書きできる制御用のレジスタがあります。ドライバは、これらのレジスタに命令やデータを書き込み、状態を読み出すことで装置を操作します。レジスタにアクセスする方法には、専用の入出力命令を使うポートマップト I/O と、レジスタをメモリのアドレス空間の一部に割り当て、通常のメモリアクセスの命令で読み書きするメモリマップト I/O があります。現在は後者が主流です。

装置に仕事を頼んだ後、その完了を CPU が知る方法には、次の 3 つがあります。

表 10.2 入出力の完了を知る方法

方法

説明

向いている場面

ポーリング

CPU が装置の状態レジスタを繰り返し読み、完了を確かめる

完了までの時間が非常に短い場合

割り込み

装置が完了したときに割り込みを発生させ、CPU に知らせる。CPU はその間、別の仕事ができる

完了までの時間が長い、または予測できない場合

DMA

装置とメモリの間のデータ転送を、DMA コントローラが CPU を介さずに行う。転送の完了は割り込みで知らせる

大量のデータを転送する場合

割り込みを使えば CPU は待たずに済みますが、割り込みの処理にも費用がかかります。高速なネットワークカードのように、毎秒数百万個のパケットを受け取る装置では、パケットのたびに割り込みを起こすと、CPU が割り込みの処理だけで手一杯になってしまいます。そのため、負荷が高いときは割り込みを止めてポーリングに切り替えるといった、両者を組み合わせた方式も使われています（Linux の NAPI など）。

また、割り込みの処理中は、他の割り込みが待たされることがあります。そのためカーネルは、割り込みの処理を、すぐに行う必要がある最小限の部分（トップハーフ）と、後で行えばよい部分（ボトムハーフ）に分け、割り込みハンドラの中では前者だけを実行するようにしています。

10.3. 入出力スケジューリング

ストレージ装置に対する入出力の要求は、複数のプロセスから同時に届きます。どの順序で装置に送るかを決めることを、入出力スケジューリングと呼びます。

HDD では、ヘッドの移動距離を減らすことが性能に直結します。そこで、要求をブロックの番号の順に並べ替え、ヘッドを一方向に動かしながら順に処理する方式（エレベーターアルゴリズム）などが使われてきました。一方、SSD にはヘッドの移動がないため、並べ替えの効果は小さく、むしろ並べ替えの処理が負担になることがあります。Linux では、装置の種類に応じて入出力スケジューラを選べるようになっており、高速な NVMe の SSD では並べ替えを行わない設定（none）がよく使われます。

10.4. アプリケーションから見た入出力の方式

ここからは、アプリケーションが入出力を行う方式を見ます。特に、ネットワークのサーバーのように、多数の通信相手を同時に扱うプログラムでは、方式の選び方が性能を大きく左右します。

10.4.1. ブロッキング I/O

最も基本的な方式は、ブロッキング I/O です。read を呼んだとき、読めるデータがなければ、データが届くまでスレッドは待ちの状態になり、システムコールから戻りません。プログラムは単純に書けますが、1 つのスレッドで扱える通信相手は同時に 1 つだけです。多数の相手を扱うには、相手ごとにスレッドを用意する必要があります。

スレッドを使う方式は分かりやすい一方、同時に扱う相手が数万になると、スレッドのスタックのメモリやコンテキストスイッチの費用が問題になります。1 台のサーバーで 1 万の同時接続を扱うことの難しさは、1999 年に C10K 問題として提起されました。

10.4.2. ノンブロッキング I/O

ファイルディスクリプタをノンブロッキングモードに設定すると、read を呼んだときに読めるデータがなければ、待たずにすぐにエラー（「今は読めない」という意味）で戻ります。スレッドは止まりませんが、データが届いたかどうかを知るには、繰り返し read を呼んで確かめる必要があり、これでは CPU が無駄になります。

10.4.3. I/O 多重化

そこで使われるのが、I/O 多重化です。多数のファイルディスクリプタをまとめて OS に渡し、「どれかが読み書きできる状態になるまで待つ」システムコールを使います。システムコールから戻ったら、準備ができたファイルディスクリプタだけを処理します。こうすれば、1 つのスレッドで多数の通信相手を効率よく扱えます。

表 10.3 I/O 多重化のシステムコール

システムコール

OS

特徴

select、poll

UNIX 系 OS（select は Windows にもある）

呼び出しのたびに、監視するファイルディスクリプタの一覧をすべて渡す。数が多いと遅くなる

epoll

Linux

監視するファイルディスクリプタをカーネルに登録しておき、準備ができたものだけを受け取る。数が多くても速い

kqueue

macOS、BSD 系 OS

epoll と同様の仕組み

IOCP（I/O 完了ポート）

Windows

入出力の「準備ができた」ことではなく「完了した」ことを通知する（後述の非同期 I/O）

この方式で作られたプログラムは、準備ができたファイルディスクリプタを待ち、届いた事象を処理し、また待つ、というループを中心に動きます。このループをイベントループと呼びます。Web サーバーの nginx や、JavaScript の実行環境の Node.js、Python の asyncio は、イベントループを中心に作られています。

サンプルコード nonblocking_io.py は、selectors モジュールを使い、1 つのスレッドで複数のクライアントの接続を扱うエコーサーバーです。selectors.DefaultSelector は、その OS で最も効率のよい I/O 多重化の仕組み（Linux では epoll）を自動的に選びます。動作を確かめるため、同じプログラムの中で 3 つのクライアントを起動しています。

リスト 10.1 nonblocking_io.py
 1"""I/O 多重化を使ったエコーサーバーのサンプル。
 2
 31 つのスレッドで複数のクライアントの接続を同時に扱うサーバーです。
 4selectors モジュールは、OS が提供する I/O 多重化の仕組み
 5(Linux では epoll、macOS では kqueue、Windows では select) を使い、
 6「読み書きできる状態になったソケット」だけを教えてくれます。
 7
 8動作を確かめるため、同じプログラムの中でクライアントを 3 つ起動し、
 9サーバーとの間でメッセージをやり取りします。
10
11実行方法::
12
13    python nonblocking_io.py
14"""
15
16import selectors
17import socket
18import threading
19
20HOST = "127.0.0.1"
21CLIENTS = 3
22
23
24def serve(server: socket.socket, stop: threading.Event) -> None:
25    """接続を受け付け、受け取ったデータをそのまま送り返す。"""
26    selector = selectors.DefaultSelector()
27    print(f"サーバー: {type(selector).__name__} を使用")
28    server.setblocking(False)
29    selector.register(server, selectors.EVENT_READ)
30    while not stop.is_set():
31        # 準備ができたソケットが現れるまで最大 0.1 秒待つ
32        for key, _ in selector.select(timeout=0.1):
33            sock = key.fileobj
34            assert isinstance(sock, socket.socket)
35            if sock is server:
36                conn, address = server.accept()  # 新しい接続
37                conn.setblocking(False)
38                selector.register(conn, selectors.EVENT_READ)
39                print(f"サーバー: {address} から接続")
40                continue
41            data = sock.recv(1024)
42            if data:
43                sock.sendall(data.upper())  # 大文字にして送り返す
44            else:  # 相手が接続を閉じた
45                selector.unregister(sock)
46                sock.close()
47    selector.close()
48
49
50def client(port: int, number: int) -> None:
51    """サーバーに接続し、メッセージを送って応答を受け取る。"""
52    with socket.create_connection((HOST, port)) as sock:
53        message = f"message from client {number}"
54        sock.sendall(message.encode())
55        reply = sock.recv(1024).decode()
56        print(f"クライアント {number}: {reply!r} を受信")
57
58
59def main() -> None:
60    with socket.socket(socket.AF_INET, socket.SOCK_STREAM) as server:
61        server.bind((HOST, 0))  # ポート番号 0 は空いている番号を OS が選ぶ
62        server.listen()
63        port = server.getsockname()[1]
64        stop = threading.Event()
65        server_thread = threading.Thread(target=serve, args=(server, stop))
66        server_thread.start()
67
68        clients = [
69            threading.Thread(target=client, args=(port, i))
70            for i in range(1, CLIENTS + 1)
71        ]
72        for t in clients:
73            t.start()
74        for t in clients:
75            t.join()
76
77        stop.set()
78        server_thread.join()
79
80
81if __name__ == "__main__":
82    main()

10.4.4. 非同期 I/O

I/O 多重化は「準備ができた」ことを知らせるだけで、実際の読み書きはアプリケーションが改めてシステムコールで行います。これに対して非同期 I/O は、入出力の処理そのものを OS に依頼し、処理が「完了した」ことを後で通知してもらう方式です。

Windows の IOCP は、この方式の代表例です。Linux では、2019 年のバージョン 5.1 から io_uring と呼ばれる仕組みが使えるようになりました。io_uring は、アプリケーションとカーネルが共有するメモリ上に、要求を入れるキューと完了の通知を入れるキューを置きます。アプリケーションはキューに要求を書き込むだけでよく、システムコールの回数を大幅に減らせます。

10.5. まとめ

  • デバイスドライバは、装置ごとの違いを吸収し、OS の他の部分に共通のインターフェースを提供します。OS のソースコードの大部分を占めます。

  • CPU は、ポーリング、割り込み、DMA を使い分けて装置とやり取りします。

  • アプリケーションの入出力の方式には、ブロッキング I/O、ノンブロッキング I/O、I/O 多重化、非同期 I/O があります。

  • 多数の接続を扱うサーバーでは、epoll などの I/O 多重化を使ったイベントループや、IOCP や io_uring などの非同期 I/O が使われます。
