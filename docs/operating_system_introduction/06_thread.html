6. スレッドと並行性

この章では、1 つのプロセスの中で複数の処理の流れを同時に進めるためのスレッドと、複数の処理が同じデータを扱うときに生じる問題を説明します。競合状態、排他制御、デッドロックは、マルチスレッドのプログラムで起きる不具合の多くに関わる重要な概念です。

6.1. スレッドとは

スレッドは、プロセスの中の処理の流れ（実行の単位）です。どのプロセスも少なくとも 1 つのスレッドを持っており、プログラムは必要に応じてスレッドを追加できます。

同じプロセスに属するスレッドは、プロセスの資源を共有します。一方で、各スレッドは自分専用の実行状態を持っています。

表 6.1 スレッド間で共有するものと、スレッドごとに持つもの

プロセス内のスレッドで共有するもの

スレッドごとに持つもの

アドレス空間（コード、大域変数、ヒープ）

プログラムカウンタとレジスタの値

開いているファイル

スタック（局所変数、関数の呼び出しの履歴）

プロセス ID、所有者などの属性

スレッド ID、スケジューリングの状態

6.1.1. なぜスレッドを使うのか

複数の処理を同時に進めるだけなら、複数のプロセスを使っても実現できます。スレッドを使う利点は次のとおりです。

  • データの共有が簡単：同じアドレス空間を共有しているので、大域変数やヒープ上のオブジェクトを介して、プロセス間通信を使わずにデータをやり取りできる。

  • 作成と切り替えが軽い：新しいアドレス空間を用意する必要がないので、プロセスよりも作成が速い。また、同じプロセスのスレッド間の切り替えでは、アドレス空間を切り替える必要がない。

  • マルチコアの活用：複数のスレッドを異なる CPU コアで同時に実行できる。

  • 応答性の向上：時間のかかる処理を別のスレッドで行えば、画面の操作などを止めずに済む。

一方、データを共有していることは欠点にもなります。あるスレッドの不具合（例えば不正なメモリアクセス）はプロセス全体を終了させますし、複数のスレッドが同じデータを同時に変更すると、次に述べる競合状態が起きます。

6.1.2. 並行と並列

複数の処理を扱うことを表す言葉に、並行（concurrent）と並列（parallel）があります。

  • 並行：複数の処理が、時間的に重なり合って進行している状態です。1 つの CPU コアで、複数のスレッドを短い時間ずつ交代で実行する場合も並行です。

  • 並列：複数の処理が、物理的に同時に実行されている状態です。複数の CPU コアが必要です。

並列は並行の特別な場合です。この章で扱う競合状態などの問題は、並列でなくても、並行でさえあれば起こります。

6.2. ユーザースレッドとカーネルスレッド

スレッドの実装には、カーネルが直接管理するカーネルスレッドと、ユーザー空間のライブラリが管理するユーザースレッドがあります。両者の対応の仕方によって、次の 3 つのモデルに分けられます。

表 6.2 スレッドの実装モデル

モデル

説明

例

1 対 1

ユーザーのスレッド 1 つをカーネルスレッド 1 つに対応させる。マルチコアを活用できるが、スレッドの作成や切り替えにシステムコールが必要になる

Linux と Windows のスレッド、Java のプラットフォームスレッド

多対 1

多数のユーザースレッドを 1 つのカーネルスレッドの上で動かす。切り替えは速いが、マルチコアを活用できず、1 つのスレッドがシステムコールで待つと全体が止まる

初期の Java の Green Threads

多対多

多数のユーザースレッドを、少数のカーネルスレッドの上に割り当てる。両者の利点を狙うが、実装は複雑になる

Go の goroutine、Java の仮想スレッド

現在の Linux や Windows のスレッドは 1 対 1 のモデルです。一方、多数の軽量な処理を扱うために、Go や Java などの言語の実行環境では多対多のモデルが使われています。

6.3. 競合状態

複数のスレッドが共有データを読み書きするとき、各スレッドの実行のタイミングによって結果が変わってしまう状況を競合状態（race condition）と呼びます。

例えば、2 つのスレッドが共有変数 counter に 1 を足す場合を考えます。counter += 1 という 1 行の処理も、CPU のレベルでは「メモリから読む」「1 を足す」「メモリに書く」という複数の段階からなります。2 つのスレッドの処理が次の順で進むと、1 を 2 回足したのに、結果は 1 しか増えません。

表 6.3 更新が失われる例（counter の初期値は 0）

スレッド A

スレッド B

counter の値

counter を読む（0）

0

counter を読む（0）

0

1 を足して書く（1）

1

1 を足して書く（1）

1

この順序で処理が進むのは、スレッド A が読んでから書くまでの間に、OS がスレッド B に切り替えた場合（あるいは別の CPU コアでスレッド B が同時に動いた場合）です。切り替えのタイミングは実行のたびに変わるため、競合状態による不具合は再現しにくく、発見の難しい不具合の代表です。

サンプルコード race_condition.py は、4 つのスレッドがそれぞれ 1,000 回ずつ共有変数に 1 を足すものです。競合状態を起こりやすくするため、変数を読んだ直後に time.sleep(0) を呼んで、意図的に CPU を手放しています。

リスト 6.1 race_condition.py
 1"""競合状態を再現し、ロックで解消するサンプル。
 2
 3複数のスレッドが共有変数 counter を「読む → 1 を足す → 書く」の
 43 段階で更新します。段階の途中で別のスレッドに切り替わると、
 5更新が失われます (競合状態)。
 6
 7切り替えを起こりやすくするため、読んだ直後に time.sleep(0) を
 8呼んで CPU を手放しています。
 9
10実行方法::
11
12    python race_condition.py
13"""
14
15import threading
16import time
17from collections.abc import Callable
18
19# スレッドの数と、各スレッドが足す回数
20THREADS = 4
21ITERATIONS = 1_000
22
23counter = 0
24lock = threading.Lock()
25
26
27def increment_unsafe() -> None:
28    """ロックを使わずに counter を増やす。"""
29    global counter
30    for _ in range(ITERATIONS):
31        value = counter  # 読む
32        time.sleep(0)  # ここで別のスレッドに切り替わりやすくする
33        counter = value + 1  # 書く
34
35
36def increment_safe() -> None:
37    """ロックで保護して counter を増やす。"""
38    global counter
39    for _ in range(ITERATIONS):
40        with lock:  # クリティカルセクションの開始
41            value = counter
42            time.sleep(0)
43            counter = value + 1
44        # with を抜けるとロックが解放される
45
46
47def run(func: Callable[[], None]) -> int:
48    """func を複数のスレッドで実行し、最終的な counter の値を返す。"""
49    global counter
50    counter = 0
51    threads = [threading.Thread(target=func) for _ in range(THREADS)]
52    for t in threads:
53        t.start()
54    for t in threads:
55        t.join()
56    return counter
57
58
59def main() -> None:
60    print(f"期待される値    : {THREADS * ITERATIONS}")
61    print(f"ロックなしの結果: {run(increment_unsafe)}")
62    print(f"ロックありの結果: {run(increment_safe)}")
63
64
65if __name__ == "__main__":
66    main()

実行結果の例は次のとおりです。ロックなしの結果は、実行するたびに変わります。

期待される値    : 4000
ロックなしの結果: 1158
ロックありの結果: 4000

6.4. クリティカルセクションと排他制御

共有データにアクセスするコードのうち、同時に複数のスレッドが実行してはならない部分をクリティカルセクションと呼びます。上のサンプルコードでは、counter を読んでから書くまでがクリティカルセクションです。

競合状態を防ぐには、クリティカルセクションを同時に 1 つのスレッドしか実行できないようにします。これを排他制御（相互排除、mutual exclusion）と呼びます。

6.4.1. アトミック命令

排他制御を実現するには、ハードウェアの支援が必要です。現代の CPU は、「メモリの値を読み、条件に応じて書き換える」という操作を、途中で他の CPU コアに割り込まれずに 1 つの不可分な操作として行うアトミック命令を備えています。代表的なものに、比較交換（CAS：Compare-And-Swap）があります。CAS は「メモリの値が期待した値と等しければ、新しい値に置き換える」という操作を不可分に行い、置き換えに成功したかどうかを返します。

後述するミューテックスなどの同期機構は、このアトミック命令を使って実装されています。

6.4.2. ミューテックス

ミューテックス（mutex：mutual exclusion の略）は、排他制御のための最も基本的な仕組みで、ロックとも呼ばれます。ミューテックスには「施錠」と「解錠」の 2 つの状態があり、次の 2 つの操作を持ちます。

  • 取得（lock、acquire）：ミューテックスが解錠されていれば施錠して先に進む。施錠されていれば、解錠されるまで待つ。

  • 解放（unlock、release）：ミューテックスを解錠する。待っているスレッドがあれば、そのうちの 1 つが取得できるようになる。

クリティカルセクションの前で取得し、後で解放すれば、クリティカルセクションを実行できるのは同時に 1 つのスレッドだけになります。上のサンプルコードの increment_safe 関数がその例です。Python の with lock: は、ブロックに入るときに取得し、ブロックを抜けるときに（例外が起きた場合も含めて）必ず解放します。

ロックの取得を待つ方法には、次の 2 種類があります。

  • スピンロック：ロックが解放されるまで、ループで繰り返し状態を確かめ続ける。待ち時間が非常に短いと分かっている場合に有効で、カーネル内部でよく使われる。

  • ブロッキング：ロックが解放されるまで、スレッドを待ちの状態にして CPU を手放す。待ち時間が長い場合に CPU を無駄にしない。

実際の実装の多くは、最初の短い時間だけスピンして、それでも取得できなければ待ちの状態に入るという、両者の組み合わせになっています。

6.4.3. セマフォ

セマフォは、ダイクストラが考案した同期機構で、0 以上の整数のカウンタを持ちます。

  • P 操作（wait、acquire）：カウンタが 1 以上なら 1 減らして先に進む。0 なら、1 以上になるまで待つ。

  • V 操作（signal、release）：カウンタを 1 増やす。待っているスレッドがあれば、そのうちの 1 つを先に進ませる。

カウンタの初期値を \(n\) にすると、同時に \(n\) 個までのスレッドが先に進めます。例えば、データベースへの同時接続数を 10 までに制限したい場合は、初期値 10 のセマフォを使います。初期値を 1 にしたセマフォは、ミューテックスと同じように使えます。

6.4.4. 条件変数

条件変数は、「ある条件が成り立つまで待つ」ための同期機構です。ミューテックスと組み合わせて使い、次の操作を持ちます。

  • wait：ミューテックスを解放して待ちの状態に入る。通知を受けて起きたら、ミューテックスを再び取得してから戻る。

  • notify（signal）：待っているスレッドの 1 つを起こす。notify_all（broadcast）はすべてを起こす。

条件変数の典型的な使い道が、生産者・消費者問題です。容量に上限のあるバッファを、データを作る生産者とデータを使う消費者が共有するとき、生産者はバッファが満杯なら空きができるまで、消費者はバッファが空ならデータが入るまで待つ必要があります。

サンプルコード producer_consumer.py は、容量 3 のバッファを使って、生産者が 8 個のデータを作り、消費者がそれを使う例です。生産者の方が速いため、バッファが満杯になると生産者が待たされます。

リスト 6.2 producer_consumer.py
 1"""条件変数を使って生産者・消費者問題を解くサンプル。
 2
 3容量に上限のあるバッファを、生産者スレッドと消費者スレッドが
 4共有します。
 5
 6* 生産者はバッファが満杯なら、空きができるまで待つ
 7* 消費者はバッファが空なら、データが入るまで待つ
 8
 9待ち合わせには threading.Condition (条件変数) を使います。
10
11実行方法::
12
13    python producer_consumer.py
14"""
15
16import threading
17import time
18from collections import deque
19
20CAPACITY = 3  # バッファの容量
21ITEMS = 8  # 生産するデータの個数
22
23
24class BoundedBuffer:
25    """容量に上限のあるスレッドセーフなバッファ。"""
26
27    def __init__(self, capacity: int) -> None:
28        self._items: deque[int] = deque()
29        self._capacity = capacity
30        self._condition = threading.Condition()
31
32    def put(self, item: int) -> None:
33        """データを追加する。満杯なら空きができるまで待つ。"""
34        with self._condition:
35            while len(self._items) >= self._capacity:
36                print(f"生産者: 満杯なので待つ (データ {item})")
37                self._condition.wait()  # ロックを解放して眠る
38            self._items.append(item)
39            print(f"生産: {item}  バッファ={list(self._items)}")
40            self._condition.notify_all()  # 待っている消費者を起こす
41
42    def get(self) -> int:
43        """データを取り出す。空ならデータが入るまで待つ。"""
44        with self._condition:
45            while not self._items:
46                self._condition.wait()
47            item = self._items.popleft()
48            print(f"消費: {item}  バッファ={list(self._items)}")
49            self._condition.notify_all()  # 待っている生産者を起こす
50            return item
51
52
53def producer(buffer: BoundedBuffer) -> None:
54    for item in range(1, ITEMS + 1):
55        buffer.put(item)
56        time.sleep(0.01)  # 生産は速い
57
58
59def consumer(buffer: BoundedBuffer) -> None:
60    for _ in range(ITEMS):
61        buffer.get()
62        time.sleep(0.05)  # 消費は遅い
63
64
65def main() -> None:
66    buffer = BoundedBuffer(CAPACITY)
67    threads = [
68        threading.Thread(target=producer, args=(buffer,)),
69        threading.Thread(target=consumer, args=(buffer,)),
70    ]
71    for t in threads:
72        t.start()
73    for t in threads:
74        t.join()
75
76
77if __name__ == "__main__":
78    main()

put メソッドと get メソッドで、条件を if ではなく while で確かめていることに注意してください。待っていたスレッドが起こされても、ミューテックスを再び取得するまでの間に、別のスレッドが条件を変えてしまうことがあります。また、通知がないのにスレッドが起きる見せかけの起床（spurious wakeup）も起こり得ます。そのため、起きた後に条件をもう一度確かめる必要があります。

6.5. デッドロック

排他制御を使うと、別の問題が起きることがあります。複数のスレッドが、互いに相手が持っている資源の解放を待ち続け、どのスレッドも先に進めなくなる状態です。これをデッドロックと呼びます。

典型的な例は、2 つのスレッドが 2 つのロック A と B を、逆の順序で取得しようとする場合です。

  1. スレッド 1 がロック A を取得する。

  2. スレッド 2 がロック B を取得する。

  3. スレッド 1 がロック B を取得しようとするが、スレッド 2 が持っているので待つ。

  4. スレッド 2 がロック A を取得しようとするが、スレッド 1 が持っているので待つ。

この時点で、どちらのスレッドも永遠に待ち続けることになります。

6.5.1. デッドロックの 4 条件

デッドロックは、次の 4 つの条件がすべて成り立つときに起こります。これらはコフマン（E. G. Coffman）らによって 1971 年に示されたもので、コフマンの条件と呼ばれます。

表 6.4 デッドロックの 4 条件

条件

内容

相互排除

資源は同時に 1 つのスレッドしか使えない

保持と待ち

スレッドが資源を保持したまま、別の資源を待つ

横取り不可

他のスレッドが保持している資源を、強制的に奪えない

循環待ち

スレッドの間で、資源の待ちの関係が循環している

6.5.2. デッドロックへの対処

デッドロックへの対処法は、大きく次の 4 つに分けられます。

  • 予防：4 条件のいずれかが成り立たないように、プログラムの設計を工夫する。最も実用的なのは、すべてのロックに順序を決め、どのスレッドも必ずその順序で取得するようにして、循環待ちを防ぐ方法である。

  • 回避：資源を割り当てる前に、その割り当てによってデッドロックが起きる可能性がないかを確かめ、危険なら割り当てを遅らせる。ダイクストラの銀行家のアルゴリズムが有名だが、各スレッドが必要とする資源の最大量を事前に知る必要があるため、汎用の OS ではほとんど使われない。

  • 検出と回復：デッドロックの発生を許し、発生したら検出して、関係するスレッドの 1 つを中止するなどして回復する。データベース管理システムでよく使われる。

  • 無視：デッドロックはまれにしか起きないとみなし、特に対処しない。汎用の OS はアプリケーションのデッドロックについて基本的にこの立場をとっており、対処はアプリケーションの開発者に任されている。

サンプルコード deadlock.py は、2 つのスレッドがロックを逆の順序で取得してデッドロックに陥る様子と、取得の順序をそろえて回避する様子を示すものです。プログラムが止まったままにならないよう、2 つ目のロックの取得にはタイムアウトを設定しています。

リスト 6.3 deadlock.py
 1"""デッドロックを再現し、ロックの取得順序をそろえて回避するサンプル。
 2
 32 つのスレッドが 2 つのロック A と B を使います。
 4
 5* 順序がばらばらの場合: スレッド 1 は A → B、スレッド 2 は B → A の
 6  順に取得しようとするので、互いに相手のロックを待ち続けます。
 7* 順序をそろえた場合: どちらのスレッドも A → B の順に取得するので、
 8  デッドロックは起きません。
 9
10プログラムが止まったままにならないよう、2 つ目のロックの取得には
11タイムアウトを設定し、タイムアウトしたらデッドロックと判定します。
12
13実行方法::
14
15    python deadlock.py
16"""
17
18import threading
19import time
20
21TIMEOUT = 1.0  # 2 つ目のロックを待つ最大時間 (秒)
22
23
24def worker(
25    name: str,
26    first: threading.Lock,
27    second: threading.Lock,
28    results: dict[str, bool],
29) -> None:
30    """first → second の順にロックを取得して作業する。"""
31    with first:
32        # 相手のスレッドが 1 つ目のロックを取るまで少し待ち、
33        # デッドロックが起きやすい状況を作る
34        time.sleep(0.1)
35        acquired = second.acquire(timeout=TIMEOUT)
36        if acquired:
37            time.sleep(0.01)  # 2 つのロックを使った作業の代わり
38            second.release()
39        results[name] = acquired
40
41
42def run(same_order: bool) -> dict[str, bool]:
43    """2 つのスレッドを実行し、各スレッドが作業を完了できたかを返す。"""
44    lock_a = threading.Lock()
45    lock_b = threading.Lock()
46    if same_order:
47        orders = [(lock_a, lock_b), (lock_a, lock_b)]
48    else:
49        orders = [(lock_a, lock_b), (lock_b, lock_a)]
50    results: dict[str, bool] = {}
51    threads = [
52        threading.Thread(
53            target=worker,
54            args=(f"スレッド {i + 1}", first, second, results),
55        )
56        for i, (first, second) in enumerate(orders)
57    ]
58    for t in threads:
59        t.start()
60    for t in threads:
61        t.join()
62    return results
63
64
65def main() -> None:
66    for same_order in (False, True):
67        label = "順序をそろえた場合" if same_order else "順序がばらばらの場合"
68        print(f"{label}:")
69        for name, ok in sorted(run(same_order).items()):
70            status = "完了" if ok else "タイムアウト (デッドロック)"
71            print(f"  {name}: {status}")
72
73
74if __name__ == "__main__":
75    main()

  スレッド 2: タイムアウト (デッドロック)
順序をそろえた場合:
  スレッド 1: 完了
  スレッド 2: 完了

6.6. その他の問題

排他制御に関わる問題には、デッドロックのほかに次のようなものがあります。

  • 飢餓（starvation）：あるスレッドが、他のスレッドに資源を取られ続けて、いつまでも先に進めない状態です。

  • ライブロック：スレッドは動き続けているのに、互いに相手に譲り合うなどして、処理がまったく進まない状態です。狭い廊下ですれ違おうとした 2 人が、同じ方向によけ続ける状況に似ています。

  • 優先度逆転：優先度の低いスレッドがロックを持っているために、そのロックを待つ優先度の高いスレッドが、中くらいの優先度のスレッドよりも後回しにされてしまう現象です。1997 年に火星に着陸した探査機マーズ・パスファインダーでは、この現象によってシステムのリセットが繰り返し起きました。ロックを持つスレッドの優先度を一時的に引き上げる優先度継承という方法で対処できます。

6.7. Python のスレッドと GIL

Python（CPython）のスレッドは、OS のスレッドと 1 対 1 に対応しています。ただし従来の CPython には GIL（Global Interpreter Lock）と呼ばれるロックがあり、Python のバイトコードを実行できるのは同時に 1 つのスレッドだけに制限されています。そのため、計算が中心の処理では、スレッドを増やしても複数の CPU コアを活用できません。

一方、ファイルやネットワークの入出力を待っている間などは GIL が解放されるので、入出力が中心の処理ではスレッドが有効です。計算が中心の処理で複数の CPU コアを使いたい場合は、multiprocessing モジュールや concurrent.futures.ProcessPoolExecutor で複数のプロセスを使うのが一般的です。

なお、Python 3.13 から GIL を持たないビルド（フリースレッド版）が試験的に提供され、Python 3.14 で正式にサポートされる構成になりました。また、GIL があっても、上のサンプルコードで見たとおり、Python のコードのレベルでの競合状態は起こり得ます。GIL の有無にかかわらず、共有データには適切な排他制御が必要です。

6.8. まとめ

  • スレッドはプロセスの中の処理の流れで、同じプロセスのスレッドはアドレス空間などの資源を共有します。

  • 複数のスレッドが共有データを同時に変更すると、実行のタイミングによって結果が変わる競合状態が起きます。

  • 競合状態は、クリティカルセクションをミューテックスなどで排他制御することで防ぎます。条件が成り立つまで待つには条件変数を使います。

  • 排他制御を使うと、デッドロックが起きることがあります。ロックの取得順序をそろえることが、最も実用的な予防策です。
