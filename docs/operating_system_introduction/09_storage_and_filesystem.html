9. ストレージとファイルシステム

この章では、データを永続的に保存するストレージ装置と、その上でデータをファイルとして管理するファイルシステムについて説明します。ファイルディスクリプタの仕組み、ファイルシステムのデータ構造、キャッシュとクラッシュへの備えを順に見ていきます。

9.1. ストレージ装置

メモリ（DRAM）は電源を切ると内容が失われますが、ストレージ装置は電源を切っても内容を保持します。現在の主なストレージ装置は HDD と SSD です。

表 9.1 HDD と SSD の比較

HDD では、ランダムアクセスと連続アクセスの速度差が非常に大きいため、OS やファイルシステムは、関連するデータをなるべく連続した位置に置き、入出力の要求を並べ替えてヘッドの移動を減らす工夫をしてきました。

SSD のフラッシュメモリは、書き込みはページ（数 KiB から十数 KiB）単位で行えますが、消去はそれより大きなブロック単位でしか行えません。そのため SSD の内部には、FTL（Flash Translation Layer）と呼ばれる制御の仕組みがあり、論理的な位置と物理的な位置の対応を管理しながら、書き込みを空いている場所に振り分けています。OS は TRIM と呼ばれる命令で、使わなくなった領域を SSD に知らせ、FTL の効率を高めます。また、NVMe と呼ばれる SSD 向けのインターフェースは、多数の要求を並列に処理できるように設計されています。

9.1.1. ブロックデバイス

OS から見ると、ストレージ装置は、決まった大きさのブロック（セクタ）を番号で指定して読み書きする装置です。このような装置をブロックデバイスと呼びます。ブロックデバイスは「何番のブロックに何が書いてあるか」しか知りません。ブロックの集まりを、名前の付いたファイルやディレクトリとして見せるのがファイルシステムの役割です。

1 台のストレージ装置は、パーティションと呼ばれる複数の領域に分割でき、パーティションごとに別のファイルシステムを作れます。

9.2. ファイルとディレクトリ

9.2.1. ファイル

ファイルは、名前の付いたデータの入れ物です。UNIX 系 OS や Windows では、ファイルの中身は単なるバイトの列であり、それが文章なのか画像なのかといった解釈はアプリケーションに任されています。

ファイルには、中身のデータのほかに、メタデータと呼ばれる付随的な情報が記録されています。

  • 大きさ

  • 所有者とアクセス権

  • 作成時刻、最終更新時刻、最終アクセス時刻

  • データが置かれているブロックの位置

9.2.2. ディレクトリ

ディレクトリ（フォルダー）は、ファイルの名前と、ファイルの実体を結び付ける表です。ディレクトリの中にディレクトリを置けるので、ファイルは木構造で整理されます。ファイルの位置は、木の根から目的のファイルまでのディレクトリの名前を区切り文字でつないだパスで表します。

  • UNIX 系 OS では、根は / で、区切り文字も / です（例：/home/user/report.txt）。すべてのストレージ装置のファイルシステムが、1 つの木構造の中に組み込まれます。

  • Windows では、ストレージ装置のパーティションごとにドライブ文字（C: など）が割り当てられ、区切り文字は \ です（例：C:\Users\user\report.txt）。

9.2.3. リンク

UNIX 系 OS のファイルシステムでは、ファイルの実体と名前が分かれており、1 つのファイルの実体に複数の名前を付けられます。

  • ハードリンク：同じファイルの実体を指す、別の名前です。どの名前も対等で、すべての名前を削除したときに初めてファイルの実体が削除されます。

  • シンボリックリンク：別のファイルのパスを中身として持つ、特別なファイルです。Windows のショートカットに似ていますが、OS がパスを自動的にたどる点が異なります。リンク先が削除されると、シンボリックリンクは無効になります。

9.3. ファイルディスクリプタ

UNIX 系 OS では、プロセスがファイルを開くと、カーネルはファイルディスクリプタと呼ばれる小さな整数を返します。以降の読み書きでは、この整数でファイルを指定します。Windows ではハンドルと呼ばれる値が同じ役割を果たします。

プロセスが起動したとき、ファイルディスクリプタの 0、1、2 には、それぞれ標準入力、標準出力、標準エラー出力が割り当てられています。新しくファイルを開くと、空いている最小の番号が使われるので、通常は 3 から順に割り当てられます。

ファイルディスクリプタの背後では、カーネルが次の 3 段階の表を使ってファイルを管理しています。

表 9.2 ファイルディスクリプタを支えるカーネルの表

単位

同じファイルを 2 回開くと、オープンファイルの表のエントリが 2 つ作られるので、読み書きの位置はそれぞれ独立します。一方、dup システムコールでファイルディスクリプタを複製したり、fork で子プロセスに引き継いだりした場合は、同じオープンファイルの表のエントリを共有するので、読み書きの位置も共有されます。

サンプルコード file_descriptor.py は、この違いを確かめ、ファイルのメタデータを表示するものです。

リスト 9.1 file_descriptor.py
 1"""ファイルディスクリプタとファイルのメタデータを調べるサンプル。
 2
 3OS のシステムコールに近い os モジュールの関数でファイルを開き、
 4次のことを確かめます。
 5
 6* ファイルを開くとファイルディスクリプタ (小さな整数) が返る
 7* 同じファイルを 2 回開くと、別のファイルディスクリプタになる
 8* dup で複製したファイルディスクリプタは読み書きの位置を共有する
 9* fstat でファイルのメタデータ (inode 番号、サイズ、アクセス権など) が分かる
10
11実行方法::
12
13    python file_descriptor.py
14"""
15
16import os
17import stat
18import tempfile
19import time
20
21
22def main() -> None:
23    with tempfile.TemporaryDirectory() as directory:
24        path = os.path.join(directory, "sample.txt")
25        with open(path, "w", encoding="utf-8") as f:
26            f.write("0123456789")
27
28        fd1 = os.open(path, os.O_RDONLY)
29        fd2 = os.open(path, os.O_RDONLY)
30        fd3 = os.dup(fd1)  # fd1 を複製する
31        print(f"fd1={fd1}, fd2={fd2}, fd3 (fd1 の複製)={fd3}")
32
33        # fd1 で 3 バイト読むと、読み書きの位置は fd1 と fd3 で共有される
34        print(f"fd1 から読む: {os.read(fd1, 3)!r}")
35        print(f"fd3 から読む: {os.read(fd3, 3)!r}  (fd1 の続きから)")
36        print(f"fd2 から読む: {os.read(fd2, 3)!r}  (先頭から)")
37
38        info = os.fstat(fd1)
39        print(f"inode 番号 : {info.st_ino}")
40        print(f"サイズ     : {info.st_size} バイト")
41        print(f"種類と権限 : {stat.filemode(info.st_mode)}")
42        print(f"リンク数   : {info.st_nlink}")
43        print(f"更新時刻   : {time.ctime(info.st_mtime)}")
44
45        for fd in (fd1, fd2, fd3):
46            os.close(fd)
47
48
49if __name__ == "__main__":
50    main()

Windows での実行結果の例は次のとおりです。

fd1=3, fd2=4, fd3 (fd1 の複製)=5
fd1 から読む: b'012'
fd3 から読む: b'345'  (fd1 の続きから)
fd2 から読む: b'012'  (先頭から)
inode 番号 : 19984723347574863
サイズ     : 10 バイト
種類と権限 : -rw-rw-rw-
リンク数   : 1
更新時刻   : Sun Oct  4 18:37:54 2026

fd1 と fd3 は読み書きの位置を共有しているので、fd3 からは fd1 の続きが読めます。一方、別に開いた fd2 は先頭から読めます。Windows には inode はありませんが、Python はファイルを一意に識別する番号を inode 番号として返します。また、Windows ではアクセス権の管理方法が UNIX 系 OS と異なるため、権限は読み書きの可否だけをもとに表示されます。Linux で実行すると、inode 番号は小さな値になり、権限は -rw-r--r-- のようにファイルの実際の設定が表示されます。

ファイルディスクリプタの数には、プロセスごとに上限があります。Linux では ulimit -n コマンドで上限を確かめられ、既定値は 1024 であることが多いです。ファイルやソケットを閉じ忘れるプログラムは、いずれ「Too many open files」というエラーで失敗します。

9.4. ファイルシステムの構造

ファイルシステムは、ブロックデバイスの上に、ファイルを管理するためのデータ構造を作ります。UNIX 系 OS の伝統的なファイルシステム（ext4 など）を例に、主な構成要素を見ます。

9.5. ページキャッシュと書き込み

ストレージ装置はメモリよりもはるかに低速なので、OS はファイルの内容をメモリにキャッシュしておきます。これをページキャッシュ（Windows ではファイルキャッシュ）と呼びます。一度読んだファイルを再び読むと速いのは、2 回目はページキャッシュから読めるからです。OS は空いているメモリの多くをページキャッシュに使い、メモリが必要になればキャッシュを捨てて明け渡します。Linux の free コマンドで「空き」のメモリが少なく見えても、その多くはページキャッシュで、必要に応じて解放できる領域です。

書き込みについても、OS は通常、データをページキャッシュに書き込んだ時点で write システムコールを完了させ、ストレージ装置への実際の書き込みは後でまとめて行います。この方式をライトバックと呼びます。書き込みが速くなる一方、ストレージ装置に書き込まれる前に電源が切れると、データが失われます。

データを確実にストレージ装置に書き込みたい場合は、fsync システムコール（Windows では FlushFileBuffers 関数）を呼びます。データベースのように、書き込んだデータが失われてはならないアプリケーションは、重要な時点で fsync を呼んでいます。fsync はストレージ装置への書き込みの完了を待つので、時間がかかります。

9.6. クラッシュへの備え

ファイルを 1 つ作るだけでも、ファイルシステムは複数の場所を書き換えます。inode の確保、空き領域の管理情報の更新、ディレクトリへのエントリの追加、データブロックへの書き込みなどです。これらの書き込みの途中で電源が切れると、ファイルシステムのデータ構造が矛盾した状態（例えば、どのディレクトリからも指されていないのに使用中の inode がある状態）になります。

古いファイルシステムでは、起動時に fsck などのプログラムでファイルシステム全体を検査し、矛盾を修復していました。しかし、ストレージ装置の容量が大きくなるにつれて、検査に何時間もかかるようになりました。

9.6.1. ジャーナリング

現在の主なファイルシステムは、ジャーナリングという方式でこの問題に対処しています。ファイルシステムを書き換える前に、これから行う変更の内容をジャーナル（ログ）と呼ばれる専用の領域に書き込んでおきます。ジャーナルへの書き込みが完了してから、実際の場所を書き換えます。

途中で電源が切れた場合は、起動時にジャーナルを調べます。ジャーナルに完全に記録されている変更は、もう一度最後まで実行し、ジャーナルへの記録が途中で終わっている変更は捨てます。こうすることで、変更は「すべて行われた」か「まったく行われなかった」かのどちらかになり、ファイルシステムが矛盾した状態になることを防げます。検査の範囲はジャーナルだけなので、復旧は短時間で済みます。

多くのファイルシステムは、既定ではメタデータの変更だけをジャーナルに記録します。データも含めて記録すると安全性は高まりますが、同じデータを 2 回書くことになるので性能が下がるからです。

9.6.2. コピーオンライトのファイルシステム

別の方式として、データを決して上書きせず、変更したデータは常に新しい場所に書き込むコピーオンライトのファイルシステムがあります。変更が完了したら、新しいデータを指すようにポインタを切り替えます。ポインタの切り替えは 1 か所の書き込みで済むので、途中で電源が切れても、古い状態か新しい状態のどちらかが残ります。

古いデータが残る性質を利用して、ある時点のファイルシステム全体の状態を瞬時に保存するスナップショットの機能を、少ない費用で実現できるのも特徴です。Btrfs、ZFS、APFS がこの方式を採用しています。

9.7.1. 仮想ファイルシステム

1 つの OS で複数の種類のファイルシステムを扱えるように、カーネルは仮想ファイルシステム（VFS）と呼ばれる共通の層を持っています。アプリケーションの open や read の要求は、まず VFS が受け取り、そのファイルが置かれているファイルシステムの実装に振り分けます。アプリケーションは、ファイルシステムの種類を意識せずに、同じシステムコールでファイルを扱えます。

UNIX 系 OS では、ストレージ装置のファイルシステムを、木構造の任意のディレクトリに接ぎ木するように組み込めます。この操作をマウントと呼びます。また Linux の /proc や /sys は、ストレージ装置を持たず、カーネルの内部情報をファイルの形で見せる特殊なファイルシステムです（「OS を観察する」で使います）。

9.8. アクセス権

複数の利用者が使う計算機では、ファイルを誰が読み書きできるかを管理する必要があります。

UNIX 系 OS の伝統的なアクセス権は、ファイルの所有者、所有グループ、その他の利用者の 3 者のそれぞれに対して、読み込み（r）、書き込み（w）、実行（x）の可否を設定するものです。ls -l コマンドで表示される -rw-r--r-- は、先頭の文字がファイルの種類（- は通常のファイル、d はディレクトリ）を、続く 9 文字が 3 者のアクセス権を表しています。この例では、所有者は読み書きでき、グループとその他の利用者は読むことだけができます。

アクセス権は、3 者のそれぞれについて r を 4、w を 2、x を 1 として足し合わせた 8 進数 3 桁で表すこともあります。-rw-r--r-- は 644 です。

1$ chmod 600 secret.txt
2$ ls -l secret.txt
3-rw------- 1 user user 42 Oct  4 10:00 secret.txt

Windows の NTFS では、ファイルごとにアクセス制御リスト（ACL）を持ち、利用者やグループごとに、読み取り、書き込み、変更、フル コントロールなどの細かな権限を設定できます。UNIX 系 OS でも、多くのファイルシステムが ACL に対応しています。アクセス制御については「セキュリティと保護」でも扱います。

9.9. まとめ

  • HDD はランダムアクセスが遅く、SSD は上書きができないなど、ストレージ装置にはそれぞれ特性があり、OS とファイルシステムはそれに合わせた工夫をしています。

  • ファイルシステムは、ブロックデバイスの上に、inode、ディレクトリ、空き領域の管理情報などのデータ構造を作り、ファイルとディレクトリを実現します。

  • プロセスはファイルディスクリプタでファイルを扱います。カーネルの中では、ファイルディスクリプタの表、オープンファイルの表、inode の表の 3 段階で管理されています。

  • OS はページキャッシュとライトバックで入出力を高速化します。確実に保存するには fsync が必要です。

  • ジャーナリングやコピーオンライトによって、電源断などのクラッシュの後もファイルシステムの整合性が保たれます。
