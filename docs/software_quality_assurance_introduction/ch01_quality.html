1. ソフトウェア品質とは

品質保証を学ぶには、まず「品質」という言葉が何を指すのかをはっきりさせる必要があります。この章では、品質の定義、品質を整理するための枠組み、品質保証とテストの関係、欠陥が生まれてから表に出るまでの流れ、そして品質にかかるコストについて説明します。

1.1. 品質の定義

「品質がよいソフトウェア」と聞いて思い浮かべるものは、人によって異なります。バグが少ないこと、動作が速いこと、使いやすいこと、改修しやすいことなど、さまざまな側面があります。品質の定義には、大きく分けて次の 2 つの考え方があります。

考え方

説明

要求への適合

仕様書や要求に書かれたとおりに動作していれば、品質がよいとみなします。検査しやすい一方で、仕様そのものが誤っている場合には品質の低さを見逃します。

利用者にとっての価値

利用者や関係者（ステークホルダー）が必要とすることを満たしていれば、品質がよいとみなします。品質管理の分野で知られる「品質とは、ある人にとっての価値である」という G. M. Weinberg の言葉は、この考え方を表しています。

実務では両方の考え方が必要です。仕様どおりに作ることは品質の前提ですが、仕様どおりに作っても利用者の役に立たなければ、品質がよいとはいえません。この 2 つの観点は、第 2 章で説明する検証と妥当性確認に対応します。

1.2. 品質特性モデル ISO/IEC 25010

品質のさまざまな側面を漏れなく検討するために、国際規格 ISO/IEC 25010 は製品品質を 9 つの品質特性に分類しています。2023 年の改訂版では、それまでの 8 特性に「安全性」が加わり、「使用性」は「インタラクション能力」に、「移植性」は「柔軟性」に名称が変わりました。なお、利用者が実際に使う場面での品質（利用時の品質）は、別の規格 ISO/IEC 25019 で扱われるようになりました。

ISO/IEC 25010:2023 の製品品質特性

品質特性

主な副特性

Python での開発における例

機能適合性

機能完全性、機能正確性、機能適切性

計算結果が正しいか、必要な機能がそろっているか

性能効率性

時間効率性、資源効率性、容量満足性

応答時間、メモリー使用量、同時に処理できる要求の数

互換性

共存性、相互運用性

ほかのシステムと決められた形式でデータを交換できるか

インタラクション能力

習得性、運用操作性、ユーザーエラー防止性、包括性など

エラーメッセージが分かりやすいか、誤操作を防げるか

信頼性

無欠陥性、可用性、障害許容性、回復性

外部 API が停止しても全体が止まらないか

セキュリティ

機密性、インテグリティ、否認防止性、責任追跡性、真正性、耐攻撃性

認証、入力値の検証、ログの記録

保守性

モジュール性、再利用性、解析性、修正性、試験性

変更の影響範囲が小さいか、テストしやすいか

柔軟性

適応性、拡張性、設置性、置換性

OS や Python のバージョンが変わっても動作するか

安全性

運用制約性、リスク識別性、フェールセーフ性、危険警告性、安全統合性

異常時に人や財産に危害を与えない状態へ移行するか

すべての品質特性を同じ重さで追求することはできません。例えば、セキュリティを高めるための暗号化は性能効率性を下げることがあります。どの品質特性を重視するかは、ソフトウェアの用途と利用者によって決まります。品質特性モデルは、重視すべき特性を関係者で話し合う際の「チェックリスト」として使うと効果的です。

1.3. 品質保証・品質管理・テストの違い

品質に関わる活動を表す言葉として、品質保証、品質管理、テストがよく使われます。これらは互いに関係していますが、指す範囲が異なります。

用語

説明

品質保証（QA: Quality Assurance）

求められる品質を満たしていると関係者が確信できるようにするための、計画的で体系的な活動の全体です。プロセスの整備、標準の策定、教育、レビュー、監査などを含み、欠陥の「予防」に重点を置きます。

品質管理（QC: Quality Control）

作られた成果物が品質の要求を満たしているかを確認し、満たしていなければ是正する活動です。成果物の「評価」に重点を置きます。

テスト

ソフトウェアを動作させるなどして欠陥を見つけ、品質を評価する活動です。品質管理の主要な手段の 1 つです。

つまり、テストは品質管理の手段の 1 つであり、品質管理は品質保証の一部です。テストだけでは品質は上がりません。テストは欠陥を見つけますが、欠陥を作り込まないための仕組み（予防）がなければ、同じ種類の欠陥が繰り返し生まれます。

1.4. 誤り・欠陥・故障

ソフトウェアの不具合は、一般に「バグ」と呼ばれます。品質保証では、不具合が生まれてから表に出るまでの段階を区別して、次の 3 つの用語を使います。

用語

説明

誤り（error、mistake）

人が犯す間違いです。仕様の読み違い、思い込み、入力ミスなどが該当します。

欠陥（defect、fault、bug）

誤りの結果として成果物（コード、設計書など）に入り込んだ不備です。

故障（failure）

欠陥を含むコードが実行された結果、ソフトウェアが期待どおりに動作しない現象です。

例えば、「65 歳以上はシニア料金」という仕様を開発者が「65 歳より上」と読み違えた場合、これが誤りです。その結果、コードに age > 65 と書いてしまうと、これが欠陥です。そして、65 歳の利用者に大人料金が請求されると、これが故障です。

この区別は、次の 2 つの点で重要です。

  • 欠陥があっても、そのコードが実行されなければ故障は起きません。テストで故障が観察されなかったからといって、欠陥がないとは限りません。

  • 故障を直すには欠陥を修正しますが、再発を防ぐには、その欠陥を生んだ誤りの原因（仕様が曖昧だった、確認の手順がなかったなど）に対処する必要があります。これを根本原因分析と呼び、第 13 章で説明します。

1.5. 欠陥のコストとシフトレフト

欠陥は、作り込まれてから発見されるまでの時間が長いほど、修正にかかるコストが大きくなります。要求の段階で見つかった誤りは文書を直すだけで済みますが、リリース後に見つかった場合は、設計・コード・テストの修正に加えて、利用者への影響の調査、緊急リリース、場合によっては補償まで必要になります。

このため、品質保証の活動をできるだけ開発の早い段階（工程を左から右に並べた図の「左」）に移すことが推奨されています。これをシフトレフトと呼びます。要求のレビュー（第 3 章）、静的解析（第 4 章）、コードレビュー（第 5 章）、開発者による単体テスト（第 8 章）は、いずれもシフトレフトのための活動です。

一方で、リリース後の本番環境でしか分からない品質の問題もあります。本番環境の監視や利用状況の分析によって品質の情報を得て、開発に反映させる考え方をシフトライトと呼びます。これについては第 11 章で説明します。

1.6. 品質コスト

品質を高めるための活動にはコストがかかります。品質にかかるコスト（COQ: Cost of Quality）は、一般に次の 4 つに分類されます。この分類は PAF モデル（Prevention、Appraisal、Failure）と呼ばれます。

分類

説明

例

予防コスト

欠陥を作り込まないためのコストです。

教育、コーディング規約の整備、設計レビュー、静的解析の導入

評価コスト

欠陥を見つけるためのコストです。

テストの設計と実行、コードレビュー、テスト環境の維持

内部失敗コスト

リリース前に見つかった欠陥に対処するコストです。

欠陥の修正、再テスト、スケジュールの遅れ

外部失敗コスト

リリース後に見つかった欠陥に対処するコストです。

障害対応、緊急リリース、問い合わせ対応、信用の低下、補償

予防コストと評価コストを適切にかけると、失敗コストを大きく減らせます。特に外部失敗コストは、信用の低下のように金額で測りにくいものを含むため、実際の損失は見積もりより大きくなりがちです。品質保証への投資を判断する際は、目に見える予防コスト・評価コストだけでなく、それによって避けられる失敗コストも考慮する必要があります。

1.7. この章のまとめ

  • 品質には「要求への適合」と「利用者にとっての価値」の 2 つの側面があります。

  • ISO/IEC 25010 の品質特性は、重視すべき品質を関係者で話し合うためのチェックリストとして使えます。

  • テストは品質管理の手段の 1 つであり、品質保証は予防を含むより広い活動です。

  • 誤り・欠陥・故障を区別すると、テストの限界と再発防止の考え方を正しく理解できます。

  • 欠陥は早く見つけるほど修正のコストが小さくなります。予防と評価への投資は、失敗コストを減らすために行います。
