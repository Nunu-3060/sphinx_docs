5. レビュー

レビューとは、作成者以外の人が成果物を読んで、欠陥や改善点を見つける活動です。レビューはプログラムを実行しないため、静的解析と同じく静的な品質確認の手法に分類されます。静的解析が機械的に判定できる問題を見つけるのに対し、レビューは人の知識と判断が必要な問題を見つけます。この章では、レビューの種類と進め方、そして生成 AI が書いたコードのレビューについて説明します。

5.1. レビューの種類

レビューは、形式の度合いによっていくつかの種類に分けられます。

種類

説明

向いている場面

インスペクション

最も形式的なレビューです。司会者、作成者、記録者、レビュアーなどの役割を決め、事前に成果物を読み込んだうえで会議を開きます。指摘の件数やかけた時間を記録し、プロセス改善に使います。

重要な要求仕様書や設計書、安全に関わるコード

ウォークスルー

作成者が成果物を説明し、参加者が質問や指摘をする形式です。知識の共有や教育の目的も兼ねます。

新しい設計の共有、新しいメンバーの教育

テクニカルレビュー

技術的な専門家が、技術的な妥当性を評価します。

方式設計、技術選定

ピアレビュー（コードレビュー）

同僚同士で成果物を確認します。形式は比較的自由です。

日常的なコードの変更

現在のソフトウェア開発では、プルリクエストを使ったコードレビューが最も一般的な形式です。一方で、重要な要求や設計については、より形式的なレビューを行う価値があります。第 1 章で説明したとおり、要求や設計の段階で欠陥を見つけるほど、修正のコストは小さくなるからです。

5.2. レビューの観点とチェックリスト

レビューの品質は、レビュアーの経験に大きく左右されます。観点をチェックリストにまとめておくと、経験の浅いレビュアーでも一定の水準のレビューができ、経験のあるレビュアーの見落としも減らせます。コードレビューの観点の例を次に示します。

コードレビューの観点の例

観点

確認すること

正しさ

要求を満たしているか。境界値（0、空、上限）、異常な入力、例外の扱いは正しいか。

設計

責務は適切に分かれているか。既存の仕組みと重複していないか。変更の影響範囲は妥当か。

読みやすさ

名前は内容を正しく表しているか。複雑すぎる処理はないか。コメントは「なぜそうしたか」を説明しているか。

テスト

変更に対応するテストが追加されているか。テストは正常系だけでなく異常系も確認しているか。

セキュリティ

外部からの入力を検証しているか。秘密情報をコードやログに書いていないか。

性能

ループの中で重い処理（データベースへの問い合わせなど）を繰り返していないか。

運用

障害時に原因を調べるためのログが出力されるか。設定値を変えるのにコードの変更が必要になっていないか。

ドキュメント

docstring や利用者向けの文書が更新されているか。

チェックリストは、一度作って終わりにせず、実際に見逃した欠陥をもとに見直します。また、項目が多すぎると形だけの確認になるため、チームで本当に重要な項目に絞ります。

5.3. プルリクエストを用いたレビューの進め方

プルリクエストによるコードレビューを効果的に行うために、作成者とレビュアーのそれぞれが心がけることを示します。

5.3.1. 作成者が心がけること

  • 変更を小さく保ちます。変更が大きいほど、レビュアーの集中力が続かず、欠陥を見落としやすくなります。1 つのプルリクエストには 1 つの目的だけを含め、数百行程度に収めるのが目安です。

  • 説明を書きます。何のために、何を変更したのか、どのように確認したのかを書きます。関連する課題のチケット番号も記載します。

  • 自分で先にレビューします。提出する前に差分を自分で読み直すと、単純な誤りの多くは自分で見つけられます。

  • 機械的な検査を先に通します。静的解析とテストが成功していることを確認してから、レビューを依頼します。

5.3.2. レビュアーが心がけること

  • 人ではなくコードについて述べます。「あなたの書き方は悪い」ではなく「この関数は 2 つの責務を持っているので、分けると読みやすくなります」のように書きます。

  • 指摘の重要度を明示します。修正が必須の指摘と、好みの範囲の提案を区別します。例えば、提案には「nit:」（細かい指摘）や「提案:」のような接頭辞を付けます。

  • 理由を添えます。なぜ修正が必要なのかを説明すると、作成者が納得しやすく、同じ指摘を繰り返さずに済みます。

  • 待たせないようにします。レビューが滞ると、作成者は別の作業に移り、指摘への対応に余計な時間がかかります。チームでレビューにかける目標の時間を決めておくとよいでしょう。

5.4. レビューで指摘すべきことと自動化に任せること

人によるレビューは貴重な資源です。機械で判定できることは機械に任せ、人は人にしかできない判断に集中すべきです。

自動化に任せること

人がレビューで確認すること

インデントや空白などの書式（フォーマッター）

要求を正しく理解して実装しているか

コーディング規約の違反（リンター）

設計は妥当か、将来の変更に耐えられるか

型の不一致（型検査器）

名前やコメントが意図を正しく伝えているか

既存の機能が壊れていないか（自動テスト）

テストケースの選び方は十分か

既知の危険な書き方（セキュリティの静的解析）

業務上の例外的な状況が考慮されているか

インデントの崩れのような指摘をレビューで繰り返している場合は、その確認を自動化すべきだという合図です。自動化の仕組みは、第 10 章で説明する継続的インテグレーションと pre-commit で実現します。

5.5. AI が生成したコードのレビュー

コード生成 AI を使った開発は一般的になりました。AI はもっともらしいコードを短時間で生成しますが、そのコードが正しいとは限りません。AI が生成したコードには、次のような特有の問題が起こりやすいことが知られています。

問題

説明

存在しない API の使用

実在しない関数や引数を、実在するかのように使うことがあります。型検査とテストで検出できる場合が多くあります。

存在しないパッケージの指定

実在しないパッケージ名を提案することがあります。攻撃者がその名前で悪意のあるパッケージを公開している場合、インストールするだけで被害を受けます。追加される依存パッケージは、実在すること、信頼できる提供元であることを必ず確認します。

仕様の読み違い

指示の曖昧な部分を、AI が独自に解釈して補います。境界値や異常時の扱いが、要求と食い違っていることがあります。

古い書き方や非推奨の API

学習したデータの時点の書き方を使うため、非推奨になった API や、脆弱性が知られている書き方を使うことがあります。

実装をなぞるだけのテスト

AI に実装とテストの両方を書かせると、テストが実装の誤りをそのまま正解としてしまうことがあります。

AI が生成したコードをレビューする際は、次の点に注意します。

  • 人が書いたコードと同じ基準でレビューします。AI が書いたからといって、基準を緩めることも、必要以上に厳しくすることもしません。プルリクエストに、AI を使った箇所を記載するルールを設けるチームもあります。

  • 最終的な責任は、コードを提出した人が負います。提出者は、生成されたコードの内容をすべて理解し、説明できる状態にしてから提出します。

  • テストの期待値は仕様から導きます。テストの期待値を実装の出力から決めると、実装の誤りを見逃します。期待値は、要求や受け入れ基準から人が決めます。

  • 機械的な検査を必ず通します。静的解析、型検査、依存パッケージの脆弱性の検査は、AI が生成したコードに対して特に効果があります。

5.6. この章のまとめ

  • レビューには、インスペクションのような形式的なものから、日常的なコードレビューまで、さまざまな種類があります。

  • チェックリストを使うと、レビューの品質を一定に保てます。

  • プルリクエストは小さく保ち、指摘は人ではなくコードについて、重要度と理由を添えて述べます。

  • 機械で判定できることは自動化に任せ、人は設計や要求の理解など、人にしかできない判断に集中します。

  • AI が生成したコードも、人が書いたコードと同じ基準でレビューします。最終的な責任は提出者が負います。
