10. 継続的インテグレーションと自動化

第 4 章の静的解析と第 8 章の自動テストは、実行されて初めて意味を持ちます。しかし、人が手作業で実行するようにしておくと、忙しいときに省略されたり、実行し忘れたりします。この章では、品質の検査を自動で、確実に、毎回実行するための仕組みである継続的インテグレーションについて説明します。

10.1. CI の目的と構成

継続的インテグレーション（CI: Continuous Integration）とは、開発者がコードの変更を頻繁に（少なくとも 1 日に 1 回）共有のブランチへ統合し、そのたびにビルドとテストを自動で実行する手法です。

CI がない開発では、各開発者が長期間それぞれのブランチで作業し、最後にまとめて統合します。すると、統合の時点で大量の衝突や不整合が見つかり、どの変更が原因なのかを特定するのに多くの時間がかかります。CI によって小さな変更をすぐに検査すれば、問題が見つかったときの原因は直前の小さな変更にあると分かり、すぐに修正できます。

CI の典型的な流れは次のとおりです。

  1. 開発者が変更をリポジトリにプッシュするか、プルリクエストを作成します。

  2. CI サーバーが変更を検知し、検査用の環境を用意します。

  3. CI サーバーが静的解析、型検査、テスト、カバレッジ測定などを順に実行します。

  4. 結果を開発者に通知し、プルリクエストの画面に成功または失敗を表示します。

CI の効果を得るためには、次の約束事をチームで守ることが大切です。

  • CI が失敗したら、ほかの作業よりも優先して直します。失敗したまま放置すると、その後の変更の検査結果も信頼できなくなります。

  • CI の実行時間を短く保ちます。目安として 10 分以内です。実行に時間がかかると、結果を待たずに次の作業に移るようになり、フィードバックが遅れます。

  • CI を通過しないコードは統合しません。

10.2. 品質ゲート

品質ゲートとは、変更を統合したりリリースしたりするために満たさなければならない品質の条件です。CI では、次のような品質ゲートを設定します。

CI で設定する品質ゲートの例

検査

合格の条件

リンター（flake8）

規約違反が 0 件であること

型検査（mypy）

型エラーが 0 件であること

テスト（pytest）

すべてのテストが成功すること

カバレッジ（pytest-cov）

カバレッジが 80 % 以上であること

依存パッケージの脆弱性の検査（pip-audit）

既知の脆弱性が 0 件であること（第 12 章を参照）

GitHub や GitLab などのリポジトリのサービスでは、ブランチの保護の設定によって、品質ゲートを通過しないプルリクエストをマージできないようにできます。これにより、品質ゲートが「守るべき約束」から「守らざるをえない仕組み」に変わります。

既存のプロジェクトに品質ゲートを導入する場合は、最初から厳しい条件を設定すると、既存の違反が多すぎて誰も CI を通過できなくなります。まず現状の水準を下回らないこと（違反を増やさないこと）を条件とし、徐々に厳しくするのが現実的です。

10.3. pre-commit による手元での自動チェック

CI は変更をプッシュした後に実行されるため、単純な誤りでも、気付くまでに数分かかります。より早く気付くために、コミットの直前に手元で検査を自動実行する仕組みが pre-commit です。pre-commit は、Git のフック（特定の操作の前後に実行されるスクリプト）を管理するツールです。

ch10_pre-commit-config.yaml（実際のファイル名は .pre-commit-config.yaml）
 1# 第 10 章のサンプル: pre-commit の設定ファイルです。
 2# 実際に使う場合はリポジトリ直下に .pre-commit-config.yaml として配置し、
 3# pre-commit install を実行します。
 4repos:
 5  - repo: https://github.com/pre-commit/pre-commit-hooks
 6    rev: v6.0.0
 7    hooks:
 8      - id: trailing-whitespace
 9      - id: end-of-file-fixer
10      - id: check-yaml
11  - repo: https://github.com/PyCQA/flake8
12    rev: 7.4.1
13    hooks:
14      - id: flake8
15  - repo: https://github.com/pre-commit/mirrors-mypy
16    rev: v2.4.0
17    hooks:
18      - id: mypy
19        args: [--strict]
20        additional_dependencies: [pytest, hypothesis]

ch10_pre-commit-config.yaml をダウンロード

この設定では、行末の空白の削除（8 行目）、ファイル末尾の改行の確認（9 行目）、YAML の文法の確認（10 行目）、flake8（14 行目）、mypy（18 行目）を、コミットのたびに実行します。各 rev には、使用するツールのバージョン（Git のタグ）を指定します。

pre-commit は次のように導入します。

1$ python -m pip install pre-commit
2$ pre-commit install            # Git のフックを登録します。
3$ pre-commit run --all-files    # すべてのファイルに対して手動で実行します。

pre-commit は開発者の手元の環境で動くため、無効にしてコミットすることもできます。そのため、pre-commit は CI の代わりにはなりません。pre-commit は早く気付くための仕組み、CI は確実に守るための仕組みとして、両方を使います。

10.4. CI ツールに依存しない検査の定義

CI の設定ファイル（GitHub Actions のワークフローや Jenkins の Jenkinsfile）に検査の手順を直接書くと、次の問題が起きます。

  • 同じ検査を手元で実行する方法が分からず、CI で失敗した原因を手元で再現しにくくなります。

  • CI ツールを移行するときに、検査の手順をすべて書き直す必要があります。

そこで本書では、検査の手順を nox という Python のツールの設定ファイル（noxfile.py）にまとめ、CI からはそれを呼び出すだけにします。nox は、検査（セッション）ごとに独立した仮想環境を作成し、その中でツールをインストールして実行します。

noxfile.py
 1"""第 10 章のサンプル: 品質検査の手順を定義する nox の設定ファイルです。
 2
 3手元でも CI でも nox コマンド 1 つで同じ検査を実行できます。
 4"""
 5
 6import nox
 7
 8nox.options.sessions = ["lint", "typecheck", "tests"]
 9REQUIREMENTS = "requirements-dev.txt"
10
11
12@nox.session
13def lint(session: nox.Session) -> None:
14    """flake8 で規約違反と複雑すぎる関数を検出します。"""
15    session.install("-r", REQUIREMENTS)
16    session.run("flake8", ".")
17
18
19@nox.session
20def typecheck(session: nox.Session) -> None:
21    """mypy で型の誤りを検出します。"""
22    session.install("-r", REQUIREMENTS)
23    session.run("mypy", ".")
24
25
26@nox.session
27def tests(session: nox.Session) -> None:
28    """pytest でテストを実行し、カバレッジが 80 % 未満なら失敗させます。"""
29    session.install("-r", REQUIREMENTS)
30    session.run(
31        "pytest",
32        "--cov=.",
33        "--cov-report=term-missing",
34        "--cov-fail-under=80",
35        "--junitxml=reports/junit.xml",
36    )

noxfile.py をダウンロード

このファイルでは、lint（12 行目～16 行目）、typecheck（19 行目～23 行目）、tests（26 行目～36 行目）の 3 つのセッションを定義しています。各セッションでは、requirements-dev.txt に書かれたバージョンのツールをインストールします。tests セッションでは、カバレッジが 80 % 未満であれば失敗するように --cov-fail-under=80 を指定し、Jenkins などで結果を表示するために JUnit 形式の XML ファイルを出力しています（35 行目）。

flake8、mypy、coverage.py の設定は、setup.cfg にまとめています。

setup.cfg
 1# Settings for flake8, mypy and coverage.py.
 2# ch04_before.py is an intentionally bad example, so it is excluded.
 3# (Comments are kept ASCII-only because mypy may read this file
 4#  with the platform default encoding.)
 5
 6[flake8]
 7exclude = .git,.nox,.venv,__pycache__,reports,ch04_before.py
 8max-complexity = 10
 9
10[mypy]
11strict = True
12exclude = (ch04_before\.py|\.nox/|\.venv/)
13
14[coverage:run]
15branch = True
16omit =
17    ch04_before.py
18    noxfile.py
19    test_*.py
20
21[coverage:report]
22show_missing = True

setup.cfg をダウンロード

requirements-dev.txt をダウンロード

nox コマンドを実行すると、3 つのセッションが順に実行されます。

1$ python -m pip install nox
2$ nox
3（途中省略）
4nox > Ran 3 sessions in 2 minutes:
5nox > * lint: success, took 35 seconds
6nox > * typecheck: success, took 34 seconds
7nox > * tests: success, took 38 seconds

特定のセッションだけを実行する場合は、nox -s tests のようにセッション名を指定します。手元で nox が成功すれば、CI でも同じ検査が成功します。同様の目的のツールとして、tox や Makefile、タスクランナーなども使えます。大切なのは、検査の手順を CI ツールの設定ファイルではなく、リポジトリ内の 1 か所で定義することです。

10.5. クラウド型の例: GitHub Actions

GitHub Actions は、GitHub が提供するクラウド型の CI サービスです。リポジトリの .github/workflows ディレクトリに YAML 形式のワークフロー定義を置くと、指定したタイミングで GitHub が用意した実行環境（ランナー）上で処理が実行されます。

ch10_github_actions.yml（実際の配置先は .github/workflows/quality.yml）
 1# 第 10 章のサンプル: GitHub Actions のワークフロー定義です。
 2# 実際に使う場合は .github/workflows/quality.yml として配置します。
 3name: quality
 4
 5on:
 6  push:
 7    branches: [main]
 8  pull_request:
 9
10jobs:
11  check:
12    runs-on: ubuntu-latest
13    strategy:
14      matrix:
15        python-version: ["3.12", "3.13"]
16    steps:
17      - uses: actions/checkout@v4
18      - uses: actions/setup-python@v5
19        with:
20          python-version: ${{ matrix.python-version }}
21      - name: Install nox
22        run: python -m pip install nox==2026.8.17
23      - name: Run quality checks
24        run: nox
25      - name: Upload test report
26        if: always()
27        uses: actions/upload-artifact@v4
28        with:
29          name: junit-${{ matrix.python-version }}
30          path: reports/junit.xml

ch10_github_actions.yml をダウンロード

主な設定の意味は次のとおりです。

  • 5 行目～8 行目: main ブランチへのプッシュと、プルリクエストの作成・更新のたびに実行します。

  • 13 行目～15 行目: Python 3.12 と 3.13 の 2 つのバージョンで、同じ検査を並行して実行します（マトリクスビルド）。

  • 17 行目～20 行目: リポジトリのコードを取得し、指定したバージョンの Python を用意します。

  • 21 行目～24 行目: nox をインストールし、noxfile.py に定義した検査を実行します。

  • 25 行目～30 行目: 検査が失敗した場合も含めて（if: always()）、テスト結果のファイルを保存します。

検査の手順そのものは noxfile.py に任せているため、ワークフロー定義は短く保たれています。

10.6. オンプレミスの例: Jenkins

企業では、社内のネットワークの制約や、ソースコードを社外に出せないといった理由から、CI を自社のサーバー（オンプレミス）で運用することがあります。その代表的なツールが、オープンソースの CI サーバーである Jenkins です。

Jenkins では、パイプラインの定義を Jenkinsfile というファイルに書き、リポジトリに含めて管理できます。次の例は、宣言型パイプラインと呼ばれる書き方で、GitHub Actions の例と同じ検査を行います。

ch10_Jenkinsfile（実際のファイル名は Jenkinsfile）
 1// 第 10 章のサンプル: Jenkins の宣言型パイプラインです。
 2// 実際に使う場合はリポジトリ直下に Jenkinsfile として配置します。
 3// Linux のエージェントに Python 3.12 以上がインストールされていることを前提とします。
 4pipeline {
 5    agent { label 'python' }
 6
 7    options {
 8        timeout(time: 30, unit: 'MINUTES')
 9        disableConcurrentBuilds()
10    }
11
12    stages {
13        stage('Setup') {
14            steps {
15                sh 'python3 -m venv .venv'
16                sh '.venv/bin/python -m pip install nox==2026.8.17'
17            }
18        }
19        stage('Quality checks') {
20            steps {
21                sh '.venv/bin/nox'
22            }
23        }
24    }
25
26    post {
27        always {
28            junit allowEmptyResults: true, testResults: 'reports/junit.xml'
29        }
30        failure {
31            echo '品質検査に失敗しました。ログを確認してください。'
32        }
33    }
34}

ch10_Jenkinsfile をダウンロード

主な設定の意味は次のとおりです。

  • 5 行目: python というラベルを付けたエージェント（実際に処理を実行するマシン）で実行します。Python をインストールしたマシンに、あらかじめこのラベルを付けておきます。

  • 7 行目～10 行目: 30 分を超えたら中断し、同じパイプラインが同時に実行されないようにします。

  • 13 行目～18 行目: 仮想環境を作成し、nox をインストールします。

  • 19 行目～23 行目: noxfile.py に定義した検査を実行します。

  • 27 行目～29 行目: 成功・失敗にかかわらず、JUnit 形式のテスト結果を Jenkins に取り込みます。Jenkins の画面で、テストの成功・失敗の推移をグラフで確認できます。

  • 30 行目～32 行目: 失敗した場合にメッセージを出力します。実際の運用では、ここでチャットツールやメールへの通知を行います。

GitHub Actions の例と比べると、実行環境の用意（13 行目～18 行目）を自分で書く必要があることが分かります。一方で、検査の内容は nox の 1 行（21 行目）で済んでいます。検査の手順を nox にまとめておいたことで、CI ツールが変わっても検査の定義を書き直す必要がありません。

なお、オンプレミスで CI を運用する選択肢は Jenkins だけではありません。GitLab のセルフマネージド版（GitLab CI/CD）や、GitHub Actions のセルフホストランナー（自社のマシンを GitHub Actions の実行環境として登録する仕組み）もあります。

10.7. クラウド型とセルフホスト型の比較

CI の実行環境は、サービスの提供者が用意するクラウド型と、自分たちで用意するセルフホスト型に分けられます。どちらを選ぶかによって、品質保証の仕組みを維持するための責任の範囲が変わります。

観点

クラウド型（GitHub Actions など）

セルフホスト型（Jenkins など）

初期構築

設定ファイルを置くだけで始められます。

サーバーの用意、インストール、認証の設定が必要です。

保守の負担

実行環境の更新はサービスの提供者が行います。

OS、Jenkins 本体、プラグインの更新とセキュリティ対策を自分たちで行います。

ネットワークの制約

社内ネットワークにしかないシステムやデータには、そのままでは接続できません。

社内のシステムやデータに接続しやすく、ソースコードを社外に出さずに済みます。

コスト

利用量に応じた料金がかかります。公開リポジトリは無料の範囲が広く設定されています。

サーバーの費用と、運用する人の人件費がかかります。

拡張性

必要に応じて実行環境が自動で用意されます。

実行環境を増やすには、エージェントのマシンを追加する必要があります。

特殊な環境

提供されている OS や機器の種類に限られます。

特殊なハードウェアや、ライセンスの必要なソフトウェアを使えます。

セルフホスト型を選ぶ場合は、CI サーバー自体が品質保証の重要な基盤になることに注意が必要です。CI サーバーが停止すると、すべての変更の検査が止まります。また、CI サーバーはソースコードや本番環境への認証情報を扱うため、攻撃の標的になりやすく、プラグインを含めて継続的に更新する必要があります。認証情報は Jenkinsfile に直接書かず、Jenkins の認証情報の管理機能を使って渡します。

10.8. この章のまとめ

  • CI は、変更を頻繁に統合し、そのたびに検査を自動で実行することで、問題を早く、原因の特定しやすい状態で見つけます。

  • 品質ゲートとブランチの保護を組み合わせると、品質の基準を仕組みとして守れます。

  • pre-commit は早く気付くための仕組み、CI は確実に守るための仕組みです。

  • 検査の手順は nox などでリポジトリ内に定義し、CI からはそれを呼び出すだけにすると、手元と CI で同じ検査を実行でき、CI ツールの移行も容易になります。

  • クラウド型とセルフホスト型では、初期構築、保守の負担、ネットワークの制約が異なります。セルフホスト型では、CI サーバー自体の保守とセキュリティ対策も品質保証の一部になります。
