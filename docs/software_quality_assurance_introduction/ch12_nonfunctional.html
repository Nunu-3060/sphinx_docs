12. 非機能品質の保証

ここまでの章では、主にソフトウェアが「正しく動くか」という機能の品質を扱ってきました。しかし、第 1 章の品質特性モデルが示すとおり、品質には性能、セキュリティ、使いやすさ、保守性など、機能以外の側面もあります。これらを非機能品質と呼びます。非機能品質の問題は、機能のテストでは見つからず、本番環境で初めて明らかになることが多くあります。この章では、代表的な非機能品質を保証するための考え方を概説します。それぞれの分野には専門的な知識の体系があるため、ここでは入り口となる考え方に絞って説明します。

12.1. 性能テスト

性能テストは、応答時間、処理能力（スループット）、資源の使用量が要求を満たすかを確認するテストです。目的によって、次のような種類があります。

種類

目的

負荷テスト

想定される通常の負荷とピーク時の負荷で、性能の要求を満たすかを確認します。

ストレステスト

想定を超える負荷をかけ、どこで限界に達するか、限界を超えたときにどのように振る舞うか（エラーを返して持ちこたえるか、停止するか）を確認します。

耐久テスト（ロングランテスト）

長時間にわたって負荷をかけ続け、メモリーリークなど、時間とともに悪化する問題がないかを確認します。

スパイクテスト

急激な負荷の増加（例えば、テレビで紹介された直後のアクセスの集中）に耐えられるかを確認します。

性能テストを行うには、まず性能の要求を測定できる形で定める必要があります。第 3 章で説明したとおり、「応答が速いこと」ではテストできません。「同時に 500 人が利用している状態で、95 パーセンタイル（95 % の要求が収まる値）の応答時間が 1 秒以内」のように定めます。応答時間を平均値だけで評価すると、一部の利用者が経験する極端に遅い応答を見逃すため、パーセンタイルで評価するのが一般的です。

Python では、Locust というツールで、利用者の操作を Python のコードとして記述し、負荷をかけられます。また、関数単位の性能の劣化を検出するには、pytest-benchmark などを使ってベンチマークを継続的に測定する方法もあります。

性能テストの結果は、テスト環境と本番環境の違い（サーバーの台数や性能、データの量）に大きく左右されます。テスト環境の結果を本番環境にそのまま当てはめられるとは限らないため、第 11 章で説明した本番環境の監視と組み合わせて評価します。

12.2. セキュリティテスト

セキュリティテストは、ソフトウェアが攻撃に耐えられるか、情報が不正に読み取られたり書き換えられたりしないかを確認するテストです。セキュリティの品質保証は、開発の全工程にわたって行います。

工程

主な活動

要求と設計

守るべき情報と想定される攻撃を洗い出し（脅威分析）、対策を設計に組み込みます。

実装

安全なコーディングの規約に従い、静的解析（第 4 章の bandit など）で危険な書き方を検出します。

テスト

動作しているシステムに攻撃を模した要求を送り、脆弱性を検出します（動的解析）。専門家による侵入テスト（ペネトレーションテスト）を行うこともあります。

運用

依存パッケージの脆弱性を監視し、セキュリティの更新を適用します。不正なアクセスを監視します。

Web アプリケーションで特に注意すべき脆弱性の種類は、OWASP（Open Worldwide Application Security Project）が公開している OWASP Top 10 にまとめられています。アクセス制御の不備、インジェクション（SQL インジェクションなど）、暗号化の不備などが含まれます。セキュリティのテストの観点を決める際の出発点として役立ちます。

12.3. ソフトウェアサプライチェーンの品質

現在のソフトウェアの大部分は、自分たちが書いたコードではなく、外部のパッケージで構成されています。そのため、依存パッケージの品質と安全性も、自分たちのソフトウェアの品質の一部です。ソフトウェアが作られ、届けられるまでの経路全体をソフトウェアサプライチェーンと呼びます。

12.3.1. 依存パッケージの脆弱性の検査

依存パッケージに既知の脆弱性がないかを検査するツールとして、pip-audit があります。pip-audit は、インストールされているパッケージや requirements.txt に書かれたパッケージを、公開されている脆弱性のデータベースと照合します。

1$ python -m pip install pip-audit
2$ pip-audit                         # 現在の環境のパッケージを検査します。
3$ pip-audit -r requirements.txt     # requirements.txt のパッケージを検査します。

脆弱性は、パッケージのリリース後に発見されることもあります。昨日まで問題がなかったパッケージに、今日脆弱性が見つかることがあるため、CI で変更のたびに検査するだけでなく、定期的（例えば毎日）にも検査します。

12.3.2. 依存パッケージを追加するときの確認

依存パッケージを追加する際は、次の点を確認します。

  • パッケージ名が正しいか。有名なパッケージに似た名前の偽物（タイポスクワッティング）や、AI が提案した実在しない名前（第 5 章を参照）に注意します。

  • 継続的に保守されているか。最終更新日、未解決の課題の数、保守している人の数などを確認します。

  • ライセンスが、自分たちのソフトウェアの使い方と矛盾しないか。

  • 本当に必要か。小さな機能のためだけに依存パッケージを追加すると、保守とセキュリティの負担が増えます。

12.3.3. SBOM

SBOM（Software Bill of Materials、ソフトウェア部品表）は、ソフトウェアに含まれるすべての部品（パッケージ、そのバージョン、ライセンスなど）を一覧にしたものです。SBOM があれば、新しい脆弱性が公表されたときに、影響を受けるソフトウェアをすばやく特定できます。SBOM の形式には SPDX や CycloneDX があり、Python の環境からは CycloneDX の公式ツール（cyclonedx-bom）などで生成できます。製品の調達の条件として SBOM の提出を求める動きも広がっています。

12.4. ユーザビリティとアクセシビリティ

ユーザビリティ（使いやすさ）は、利用者が目的を、効果的に、効率よく、満足して達成できる度合いです。機能が仕様どおりに動いていても、利用者が使い方を理解できなければ、そのソフトウェアは価値を提供できません。ユーザビリティは、実際の利用者（またはそれに近い人）に操作してもらい、その様子を観察するユーザビリティテストで評価するのが効果的です。少人数でも、多くの問題を見つけられることが知られています。

アクセシビリティは、高齢者や障害のある人を含む、さまざまな人が利用できる度合いです。Web のアクセシビリティについては、国際的なガイドラインである WCAG（Web Content Accessibility Guidelines）が広く使われており、日本では JIS X 8341-3 として規格化されています。画像の代替テキスト、キーボードだけでの操作、十分な色のコントラストなどが求められます。一部の項目は自動の検査ツールで確認できますが、スクリーンリーダーで実際に操作するなどの手動の確認も必要です。

12.5. 保守性と技術的負債

保守性は、ソフトウェアを修正・改良しやすい度合いです。保守性は利用者から直接は見えませんが、変更の速さと、変更時に欠陥を作り込む可能性に影響します。

開発を急ぐために、本来あるべき設計や実装を後回しにすると、その分だけ将来の変更にかかるコストが増えます。これを、借金にたとえて技術的負債と呼びます。重複したコード、複雑すぎる関数、テストのないモジュール、古くなった依存パッケージなどが、技術的負債の例です。

技術的負債は、すべてが悪いわけではありません。リリースの期限を守るために、意図的に負債を負う判断もありえます。問題になるのは、負債を負ったことが記録されず、返済されないまま利子（変更のたびの余計なコスト）が膨らみ続けることです。技術的負債に対処するには、次のような方法があります。

  • 負債を見える化します。課題管理システムに登録し、静的解析の指標（第 4 章の循環的複雑度など）やカバレッジの推移を記録します。

  • 返済の時間を計画に含めます。例えば、各イテレーションの作業時間の一定の割合を、リファクタリングに充てます。

  • ボーイスカウトの規則（来たときよりも美しく）に従い、変更する箇所の周辺を少しずつ改善します。

12.6. この章のまとめ

  • 性能の要求は測定できる形で定め、応答時間は平均値ではなくパーセンタイルで評価します。

  • セキュリティの品質保証は、脅威分析から運用中の監視まで、全工程にわたって行います。

  • 依存パッケージの脆弱性は pip-audit などで継続的に検査し、SBOM で部品を把握します。

  • ユーザビリティとアクセシビリティは、実際の利用者による評価やガイドラインに基づいて確認します。

  • 技術的負債は見える化し、返済の時間を計画に含めます。
