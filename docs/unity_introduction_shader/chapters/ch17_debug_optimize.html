第 17 章 デバッグと最適化

シェーダーには、C# のようにブレークポイントを置いて変数の値を確かめる手段が限られている。この章では、シェーダーの不具合を調べる方法と、シェーダーを高速にするための考え方を説明する。

この章のサンプルコードは、examples/chapter17 フォルダーにある。

値を色で確かめる

シェーダーの中の値を確かめる最も簡単な方法は、その値を色として出力することである。例えば、法線が正しく計算されているかを確かめたいときは、法線をそのまま色として返す。

次のシェーダーは、マテリアルの設定に応じて、法線、UV 座標、カメラからの距離のいずれかを色で表示する。

DebugView.shader
 1// 第 17 章：法線や UV 座標を色として表示し、
 2// シェーダーの中の値を目で確かめるためのシェーダー。
 3Shader "Introduction/Chapter17/DebugView"
 4{
 5    Properties
 6    {
 7        // マテリアルの Inspector でドロップダウンから表示内容を選ぶ。
 8        // 選んだ項目に応じて、_MODE_NORMAL などのキーワードのうち 1 つが有効になる。
 9        [KeywordEnum(Normal, UV, Depth)] _Mode ("Mode", Float) = 0
10        // Depth モードで白になる距離（カメラからの距離）
11        _MaxDistance ("Max Distance", Float) = 20
12    }
13
14    SubShader
15    {
16        Tags
17        {
18            "RenderType" = "Opaque"
19            "Queue" = "Geometry"
20            "RenderPipeline" = "UniversalPipeline"
21        }
22
23        Pass
24        {
25            Name "DebugView"
26            Tags { "LightMode" = "UniversalForward" }
27
28            HLSLPROGRAM
29            #pragma vertex Vert
30            #pragma fragment Frag
31
32            // マテリアルで選ばれたキーワードのバリアントだけがビルドに含まれる
33            #pragma shader_feature_local_fragment _MODE_NORMAL _MODE_UV _MODE_DEPTH
34
35            #include "Packages/com.unity.render-pipelines.universal/ShaderLibrary/Core.hlsl"
36
37            struct Attributes
38            {
39                float4 positionOS : POSITION;
40                float3 normalOS : NORMAL;
41                float2 uv : TEXCOORD0;
42            };
43
44            struct Varyings
45            {
46                float4 positionCS : SV_POSITION;
47                float3 positionWS : TEXCOORD0;
48                float3 normalWS : TEXCOORD1;
49                float2 uv : TEXCOORD2;
50            };
51
52            CBUFFER_START(UnityPerMaterial)
53                float _MaxDistance;
54            CBUFFER_END
55
56            Varyings Vert(Attributes input)
57            {
58                Varyings output;
59                output.positionWS = TransformObjectToWorld(input.positionOS.xyz);
60                output.positionCS = TransformWorldToHClip(output.positionWS);
61                output.normalWS = TransformObjectToWorldNormal(input.normalOS);
62                output.uv = input.uv;
63                return output;
64            }
65
66            half4 Frag(Varyings input) : SV_Target
67            {
68            #if defined(_MODE_UV)
69                // U を赤、V を緑で表示する。frac で 0 ～ 1 の範囲に収め、
70                // タイリングの繰り返しも見えるようにする。
71                return half4(frac(input.uv), 0.0, 1.0);
72            #elif defined(_MODE_DEPTH)
73                // カメラからの距離を、近いほど黒、遠いほど白で表示する
74                float distanceToCamera = length(GetCameraPositionWS() - input.positionWS);
75                return half4(saturate(distanceToCamera / _MaxDistance).xxx, 1.0);
76            #else
77                // 法線の各成分（-1 ～ 1）を 0 ～ 1 に変換して、xyz を RGB として表示する
78                float3 normalWS = normalize(input.normalWS);
79                return half4(normalWS * 0.5 + 0.5, 1.0);
80            #endif
81            }
82            ENDHLSL
83        }
84    }
85}

DebugView.shader をダウンロード

マテリアルの Mode で表示内容を切り替えられる。それぞれの見方は、次のとおりである。

Mode

見方

Normal

法線の x、y、z を、0～1 に変換して R、G、B で表示する。ワールド空間で右（+x）を向いた面は赤っぽく、上（+y）を向いた面は緑っぽく、奥（+z）を向いた面は青っぽくなる。

UV

U を赤、V を緑で表示する。UV 座標の左下（0, 0）は黒、右下（1, 0）は赤、左上（0, 1）は緑、右上（1, 1）は黄色になる。

Depth

カメラからの距離を、近いほど黒く、遠いほど白く表示する。Max Distance の距離で白になる。

色として出力できるのは、0～1 の範囲の値である。範囲外の値を確かめたいときは、* 0.5 + 0.5 や frac 関数、saturate 関数などで 0～1 の範囲に変換してから出力する。また、return (value > 0.5) ? half4(1, 0, 0, 1) : half4(0, 0, 0, 1); のように、条件を満たすピクセルだけを赤くする方法も有効である。

KeywordEnum とシェーダーのバリアント

Mode プロパティには、[KeywordEnum(Normal, UV, Depth)] 属性を付けている。この属性を付けると、Inspector ウィンドウにドロップダウンが表示され、選んだ項目に応じて _MODE_NORMAL、_MODE_UV、_MODE_DEPTH のいずれかのキーワードが有効になる。キーワードの名前は、プロパティ名を大文字にしたものと、項目名を大文字にしたものを _ でつないだ形になる。

HLSL のコードでは、#pragma shader_feature_local_fragment でこれらのキーワードを宣言し、#if defined(_MODE_UV) のように処理を切り替えている。

shader_feature と multi_compile は、どちらもシェーダーのバリアントを作る命令であるが、ビルドに含まれるバリアントが異なる。

命令

ビルドに含まれるバリアント

multi_compile

宣言したすべてのキーワードのバリアント。実行時に URP などが切り替えるキーワード（第 11 章の影のキーワードなど）に使う。

shader_feature

プロジェクトのマテリアルで使われているキーワードのバリアントだけ。マテリアルの設定で決まるキーワードに使う。

名前の _local は、キーワードをこのシェーダーの中だけで有効にすることを表す。_fragment は、フラグメントシェーダーのバリアントだけを作ることを表す（第 11 章を参照）。

Frame Debugger

Frame Debugger は、1 フレームの描画を、ドローコール 1 回ずつに分けて確かめられる Unity の機能である。Window ‣ Analysis ‣ Frame Debugger で開き、Enable を押すと、再生中のゲームが一時停止し、そのフレームの描画の一覧が表示される。

Frame Debugger では、次のことを確かめられる。

  • オブジェクトがどの順番で描画されているか（第 12 章の描画の順序の確認）

  • 各ドローコールで、どのシェーダーのどのパスが使われているか

  • 有効になっているキーワード（どのバリアントが使われているか）

  • マテリアルのプロパティに、どの値が渡されているか

  • SRP Batcher でまとめられたドローコールと、まとめられなかった理由

オブジェクトが表示されないときは、まず Frame Debugger でそのオブジェクトが描画されているかを確かめるとよい。描画されていなければ、パスの LightMode タグや Queue タグの設定を疑う。描画されていれば、シェーダーの計算か描画の設定（深度テスト、ブレンドなど）を疑う。

RenderDoc

RenderDoc は、GPU の描画を詳しく調べるための外部のツールである。Unity と連携して、ドローコールごとの頂点シェーダーの入出力の値や、特定のピクセルのフラグメントシェーダーの実行過程を確かめられる。Frame Debugger で原因が分からない場合に使う。RenderDoc の使い方は、本資料では扱わない。

よくある不具合

症状

主な原因

オブジェクトがマゼンタ色になる

シェーダーのコンパイルエラー。または、ほかのレンダーパイプライン向けのシェーダーを使っている（第 5 章を参照）。

オブジェクトが表示されない

パスの LightMode タグの誤り。Deferred のレンダリングパスで使っている（第 5 章を参照）。頂点アニメーションでメッシュの範囲の外に頂点を動かしている（第 13 章を参照）。

陰影が平らなまま

法線をワールド空間に変換していない。補間された法線を正規化していない（第 9 章を参照）。

影が表示されない

ShadowCaster パスがない。影のキーワードを multi_compile で宣言していない（第 11 章を参照）。

表面に縞模様の影が出る

シャドウアクネ。ライトの Bias の設定を調整する（第 11 章を参照）。

半透明のオブジェクトの前後関係がおかしい

Queue や ZWrite の設定の誤り。または、半透明の描画の順序の制限（第 12 章を参照）。

SRP Batcher に対応していない

プロパティが UnityPerMaterial に入っていない。パスによって UnityPerMaterial の内容が異なる（第 5 章を参照）。

スマートフォンで表示が崩れる

half の精度不足（第 6 章を参照）。

最適化の考え方

シェーダーの処理の重さは、実行される回数と 1 回あたりの処理の量で決まる。

計算を頂点シェーダーに移す

フラグメントシェーダーは、多くの場合、頂点シェーダーよりはるかに多く実行される（第 4 章を参照）。ピクセルごとに変わらない計算や、頂点の間で線形に補間しても結果がほとんど変わらない計算は、頂点シェーダーで行い、結果をフラグメントシェーダーに渡すと速くなる。例えば、UV 座標の Tiling と Offset の計算は、頂点シェーダーで行っている。

精度を下げる

スマートフォンの GPU では、half の計算は float より高速なことが多い。色や、正規化した方向ベクトルなど、精度がそれほど必要ない値には half を使う。ただし、位置、UV 座標、時間など、大きな値や細かい値を扱う変数には float を使う。

テクスチャーの読み取りを減らす

テクスチャーの読み取りは、メモリへのアクセスを伴うため、計算より時間がかかることが多い。複数の白黒のテクスチャーを使う場合は、R、G、B、A のチャンネルに 1 つずつまとめて、1 回の読み取りで済ませる方法がよく使われる。また、ミップマップを有効にすると、遠くのオブジェクトで読み取るデータが小さくなり、高速になる（第 8 章を参照）。

分岐に注意する

GPU は、近くのピクセルをまとめて同じ命令で処理する。if 文の条件がまとめて処理されるピクセルの間で異なると、両方の処理を実行することになり、遅くなる場合がある。マテリアルの設定で決まる分岐は、shader_feature のバリアントで切り替えると、実行時の分岐をなくせる。一方で、step 関数や lerp 関数で書き換えられる単純な分岐は、そのままでも大きな問題にならないことが多い。

バリアントを増やしすぎない

バリアントの数は、キーワードの組み合わせの数だけ増える。例えば、2 つのキーワードを持つ multi_compile を 10 行書くと、\(2^{10} = 1024\) 個のバリアントになる。バリアントが多すぎると、ビルドの時間、ビルドのサイズ、実行時のメモリの使用量が増える。次の点に注意する。

  • マテリアルの設定で決まるキーワードには、multi_compile ではなく shader_feature を使う。

  • フラグメントシェーダーでしか使わないキーワードには、_fragment の付いた命令を使う。

  • 使わない機能のキーワードは宣言しない。

オーバードローを減らす

同じピクセルに何度も描画することを、オーバードローという。特に、半透明のオブジェクトは深度を書き込まないため、重なった数だけフラグメントシェーダーが実行される。パーティクルなどで大きな半透明の板を多数重ねると、画面の解像度が高いほど重くなる。半透明の部分を小さくする、必要な部分だけを覆うメッシュを使うなどの工夫が有効である。

メッシュの LOD を使う

遠くにあって小さく表示されるオブジェクトを、頂点の多いメッシュのまま描画すると、頂点シェーダーの処理が無駄になる。また、1 ピクセルより小さい三角形が多いと、GPU の処理の効率が下がる。そこで、カメラからの距離に応じて、頂点の少ないメッシュに切り替える。この方法を LOD（Level of Detail）という。

Unity では、LOD Group コンポーネントで、画面上の大きさの割合ごとに使うメッシュ（LOD 0、LOD 1、…）を設定する。LOD の切り替えはメッシュ単位で行われるため、シェーダーを変更する必要はない。シェーダーの処理の重さを環境に応じて切り替えたい場合は、サブシェーダーの LOD を使う（第 6 章を参照）。

計測してから最適化する

最適化は、実際に計測して、遅い原因を確かめてから行う。原因が CPU（ドローコールの数など）にある場合、シェーダーを速くしても効果はない。Unity の Profiler（Window ‣ Analysis ‣ Profiler）で CPU と GPU のどちらに時間がかかっているかを確かめ、対象の環境（特にスマートフォン）の実機で計測することが重要である。
