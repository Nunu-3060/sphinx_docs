4.1. C

4.1.1. 基本情報

登場年

1972 年

設計者

デニス・リッチー（ベル研究所）

標準仕様

ISO/IEC 9899。C89/C90、C99、C11、C17 を経て、最新は C23（ISO/IEC 9899:2024）

主な処理系

GCC、Clang、Microsoft Visual C++（MSVC）

2026 年時点の状況

C23 への対応が主要なコンパイラで進んでいる。次期規格（通称 C2y）の策定作業が行われている。

4.1.2. 誕生の背景と設計思想

C は、ベル研究所で UNIX を開発する過程で生まれた。UNIX は当初アセンブリ言語で書かれていたが、リッチーは BCPL とその後継の B を発展させて C を設計し、1973 年に UNIX のカーネルの大部分を C で書き直した。OS を高水準言語で記述したことで、UNIX は異なるハードウェアへ移植しやすくなり、C も UNIX とともに広まった。

C の設計思想は「プログラマを信頼する」ことにある。言語仕様は小さく、メモリやハードウェアを直接操作する手段を提供する一方、安全性の検査の多くはプログラマに委ねられている。1978 年にカーニハンとリッチーが著した『プログラミング言語 C』（通称 K&R）は、長く事実上の仕様書として扱われた。

4.1.3. 主な特徴

  • 静的型付け：型は静的に検査されるが、ポインタの型変換や整数と浮動小数点数の暗黙の変換が許されるなど、型による保護は比較的弱い。

  • AOT コンパイル：ソースコードは機械語に直接コンパイルされ、ランタイムはほぼ不要である。実行性能が高く、実行ファイルも小さい。

  • 手動のメモリ管理：ヒープ領域は malloc と free で明示的に確保・解放する。ポインタによってメモリを直接操作できるが、範囲外アクセスや解放後の使用は未定義動作となる。

  • プリプロセッサ：#include や #define によるテキスト置換でソースコードを組み立てる。

  • 最小限の標準ライブラリ：文字列処理、入出力、メモリ操作などに限られ、連想配列や動的配列のようなデータ構造は標準では提供されない。

C は、OS の API や多くのライブラリが公開するインタフェースの事実上の標準でもある。ほかの言語から既存のライブラリを呼び出す FFI は、多くの場合 C の呼び出し規約（ABI）を介して行われる。

C23 では、nullptr、bool・true・false のキーワード化、typeof、constexpr （オブジェクトのみ）、#embed によるバイナリファイルの埋め込み、2 進数リテラルなどが追加された。

4.1.4. コード例

リスト 4.1 word_count.c
 1/* 文章中の単語の出現回数を数え、上位の単語を表示するサンプル */
 2#include <ctype.h>
 3#include <stdio.h>
 4#include <stdlib.h>
 5#include <string.h>
 6
 7#define MAX_WORDS 64
 8#define MAX_WORD_LEN 32
 9
10typedef struct {
11    char word[MAX_WORD_LEN];
12    int count;
13} WordCount;
14
15/* 単語を表に追加する。既に登録済みなら出現回数を 1 増やす。
16   word の長さは MAX_WORD_LEN - 1 以下であること */
17static void add_word(WordCount *table, size_t *size, const char *word) {
18    for (size_t i = 0; i < *size; i++) {
19        if (strcmp(table[i].word, word) == 0) {
20            table[i].count++;
21            return;
22        }
23    }
24    if (*size < MAX_WORDS) {
25        memcpy(table[*size].word, word, strlen(word) + 1);
26        table[*size].count = 1;
27        (*size)++;
28    }
29}
30
31/* 出現回数の降順、同数なら単語の昇順に並べるための比較関数 */
32static int compare_word_count(const void *a, const void *b) {
33    const WordCount *x = a;
34    const WordCount *y = b;
35    if (x->count != y->count) {
36        return (x->count < y->count) - (x->count > y->count);
37    }
38    return strcmp(x->word, y->word);
39}
40
41int main(void) {
42    const char *text = "The quick brown fox jumps over the lazy dog. The dog sleeps.";
43    WordCount table[MAX_WORDS];
44    size_t size = 0;
45    char word[MAX_WORD_LEN];
46    size_t len = 0;
47
48    /* 英字の並びを 1 単語として切り出し、小文字にそろえて登録する */
49    for (const char *p = text;; p++) {
50        if (isalpha((unsigned char)*p)) {
51            if (len < MAX_WORD_LEN - 1) {
52                word[len++] = (char)tolower((unsigned char)*p);
53            }
54            continue;
55        }
56        if (len > 0) {
57            word[len] = '\0';
58            add_word(table, &size, word);
59            len = 0;
60        }
61        if (*p == '\0') {
62            break;
63        }
64    }
65
66    qsort(table, size, sizeof table[0], compare_word_count);
67    for (size_t i = 0; i < size && i < 3; i++) {
68        printf("%s: %d\n", table[i].word, table[i].count);
69    }
70    return EXIT_SUCCESS;
71}

C の標準ライブラリには連想配列がないため、10〜13 行目で単語と出現回数の組を構造体として定義し、17〜29 行目で配列を線形探索して出現回数を数えている。単語の切り出し（49〜64 行目）も、正規表現を使わずに 1 文字ずつ判定して行う。並べ替えには標準ライブラリの qsort を使い、比較関数を関数ポインタとして渡す（66 行目）。

格納できる単語の数と長さを固定長の配列（7〜8 行目）で制限している点にも注意してほしい。可変長にするには malloc や realloc でメモリを確保し、使い終わったら free で解放する必要がある。ほかの言語の実装と比べると、C では低水準の処理を自分で書く必要があることが分かる。

4.1.5. 主な用途

  • OS のカーネル（Linux、Windows や macOS のカーネルの大部分）

  • 組込みソフトウェア、マイコンのファームウェア

  • データベース（SQLite、PostgreSQL）や Web サーバ（nginx）などのミドルウェア

  • ほかの言語の処理系（CPython、Ruby の処理系 CRuby、PHP の Zend Engine）

  • 高性能な数値計算ライブラリ

4.1.6. エコシステム

  • ビルドツール：Make、CMake、Meson

  • パッケージマネージャ：言語標準のものはない。OS のパッケージ管理（apt など）や、C/C++ 向けの vcpkg、Conan が使われる。

  • 静的解析・検査：clang-tidy、Clang Static Analyzer、AddressSanitizer などのサニタイザ

4.1.7. 長所と短所

長所

  • 実行性能が高く、メモリ使用量と実行ファイルのサイズが小さい。

  • ほぼすべてのプラットフォームにコンパイラが存在し、移植性が高い。

  • ハードウェアや OS の機能を直接扱える。

  • 言語仕様が小さく、生成される機械語を予測しやすい。

短所

  • メモリ安全ではなく、バッファオーバーフローなどの脆弱性を生みやすい。

  • 抽象化の手段（ジェネリクス、名前空間、例外など）が乏しく、大規模な開発では記述量が増える。

  • 未定義動作が多く、コンパイラの最適化によって予期しない挙動となることがある。

  • 標準的なパッケージ管理の仕組みがない。
