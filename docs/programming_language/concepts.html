2. プログラミング言語の基礎概念

本章では、後の章で言語を比較するための共通の観点を説明する。ここで述べる観点は互いに独立ではなく、たとえば実行方式とメモリ管理の方式は性能特性に、型システムとエラー処理の方式は安全性に、それぞれ同時に影響する。

2.1. パラダイム

プログラミングパラダイムとは、プログラムをどのような考え方で組み立てるかという様式である。大きく命令型と宣言型に分けられる。

表 2.1 主なパラダイム

パラダイム

考え方

代表的な言語

手続き型

処理の手順を順に記述し、変数の状態を書き換えながら計算を進める。命令型の基本形である。

C、Pascal、FORTRAN

オブジェクト指向

データとそれを操作する手続きをオブジェクトとしてまとめ、カプセル化・継承・ポリモーフィズムによって構造化する。

Smalltalk、Java、C#、C++、Ruby

関数型

副作用のない関数の組み合わせで計算を表す。関数を値として扱い（第一級関数）、不変のデータを基本とする。

Haskell、ML、LISP、Erlang

論理型

事実と規則を記述し、問い合わせに対する解を処理系が探索する。

Prolog

宣言型（問い合わせ）

「何が欲しいか」を記述し、「どう求めるか」は処理系に任せる。

SQL

現在の主要な言語の多くは、複数のパラダイムを取り入れたマルチパラダイム言語である。たとえば Java や C# はオブジェクト指向を軸としつつ、ラムダ式やストリーム処理によって関数型の書き方も取り入れている。Rust、Kotlin、Swift、Scala などは、オブジェクト指向と関数型の要素を最初から組み合わせて設計されている。

2.2. 型システム

型システムは、値の種類（型）を区別し、型に合わない操作を検出する仕組みである。型システムの違いは、誤りを検出できる時期、記述の簡潔さ、実行性能に影響する。

2.2.1. 静的型付けと動的型付け

静的型付けの言語では、コンパイル時（実行前）に型の検査を行う。型の誤りを実行前に検出でき、エディタによる補完やリファクタリングの支援も受けやすい。C、C++、Java、C#、Go、Rust、Kotlin、Swift、TypeScript が該当する。

動的型付けの言語では、実行時に値そのものが型の情報を持ち、操作の時点で型を検査する。型の宣言が不要で記述が簡潔になる一方、型の誤りは該当する箇所を実行するまで発見できない。Python、JavaScript、Ruby、PHP が該当する。

次の例は、Python で文字列と整数を加算しようとした場合である。この誤りは、実行してはじめて TypeError として検出される。

1def total(price, quantity):
2    return price * quantity + " 円"   # 実行時に TypeError となる
3
4total(100, 3)

同じ処理を TypeScript で書くと、型注釈によって誤りをコンパイル時に検出できる。

1function total(price: number, quantity: number): number {
2  return price * quantity + " 円";  // コンパイルエラー: string は number に代入できない
3}

近年は、動的型付けの言語に任意の型注釈を加えて静的に検査する漸進的型付けが広まっている。Python の型ヒントと mypy、Ruby の RBS、PHP の型宣言、そして JavaScript に対する TypeScript がその例である。

2.2.2. 強い型付けと弱い型付け

型付けの「強さ」は、型の異なる値の間で暗黙の変換をどの程度許すかを表す。たとえば JavaScript では "5" * 2 が 10 になるように暗黙の型変換が広く行われるため、弱い型付けの言語とされることが多い。一方、Python では "5" * 2 は文字列の繰り返し（"55"）であり、"5" + 2 はエラーとなるため、動的型付けでありながら強い型付けの言語とされる。ただし「強い」「弱い」には厳密な定義がなく、文脈によって意味が異なる点に注意が必要である。

2.2.3. 型推論

型推論は、型注釈を省略しても、式や文脈から処理系が型を決定する仕組みである。静的型付けの安全性を保ちながら記述量を減らせるため、C++ の auto、Java の var、C# の var、Go の :=、Kotlin や Swift の val・let など、多くの静的型付け言語が取り入れている。ML や Haskell は、関数の引数まで含めてプログラム全体の型を推論できる Hindley-Milner 型推論を備える。

2.2.4. 名目的部分型と構造的部分型

ある型を別の型として扱えるかどうかの判定方法には 2 種類ある。名目的部分型では、implements や継承のように明示的に宣言された関係によって判定する。Java、C#、Kotlin、Swift、Rust がこの方式である。構造的部分型では、必要なメソッドやプロパティを備えているかどうかという構造によって判定する。Go のインタフェースと TypeScript の型がこの方式であり、宣言なしに既存の型をインタフェースに適合させられる。

2.2.5. null 安全

null（値が存在しないことを表す特別な値）の参照は、多くの言語で実行時エラーの主要な原因となってきた。null 参照の考案者であるアントニー・ホーアは、これを「10 億ドルの過ち」と呼んだ。Kotlin、Swift、Rust、TypeScript（strictNullChecks 有効時）、C#（null 許容参照型の有効時）は、null になり得る型とそうでない型を型システムで区別し、null の扱い漏れをコンパイル時に検出する。この性質を null 安全という。

2.2.6. ジェネリクス

ジェネリクスは、型を引数として受け取り、さまざまな型に対して同じ処理を記述する仕組みである。実現方式は言語によって異なる。

  • 型消去：Java や Kotlin（JVM 上）、TypeScript は、コンパイル時に型を検査したあと型引数の情報を消去する（型消去）。実行時に型引数を参照できない。

  • 単相化：C++ のテンプレートや Rust は、使われた型引数ごとに専用のコードを生成する（単相化）。実行は高速だが、生成されるコードの量が増える。

  • 実行時の型情報の保持：C# は、実行時にも型引数の情報を保持する。

Go は長らくジェネリクスを持たなかったが、2022 年の Go 1.18 で導入した。

2.3. 実行方式

ソースコードを実行する方式は、性能、起動時間、移植性、配布のしやすさに影響する。主な方式を図 2.1 に示す。

AOT コンパイル

実行前にソースコードを対象 CPU の機械語に変換する方式である。実行時の変換が不要なため、起動が速く実行性能も高い。一方、CPU や OS ごとにコンパイルし直す必要がある。C、C++、Rust、Go、Swift が代表的である。

仮想マシンとバイトコード

ソースコードを特定の CPU に依存しないバイトコードに変換し、それを仮想マシン（VM）が実行する方式である。Java の JVM や .NET の CLR がこれにあたり、同じバイトコードを異なるプラットフォームで実行できる。現代の VM は、頻繁に実行される部分を実行時に機械語へ変換する JIT コンパイルによって高い性能を得ている。

インタプリタ

ソースコードを読み込みながら逐次実行する方式である。実際には、CPython や Ruby の処理系も内部でソースコードをバイトコードに変換してから実行しており、純粋な逐次解釈ではない。JavaScript の主要なエンジン（V8 など）は高度な JIT コンパイラを備え、動的型付けの言語としては非常に高い性能を持つ。

トランスパイル

ある言語のソースコードを別の言語のソースコードに変換する方式である。TypeScript は JavaScript に変換されてから実行される。

これらの区別は言語そのものではなく処理系の性質である点に注意が必要である。たとえば Java には事前に機械語へ変換する GraalVM Native Image があり、C# には Native AOT がある。Python にも PyPy のような JIT コンパイラを備えた処理系が存在する。

2.4. メモリ管理

プログラムが使うメモリ（特にヒープ領域）を誰がいつ解放するかは、言語の性能と安全性を大きく左右する。

表 2.2 主なメモリ管理の方式

方式

仕組み

長所と短所

代表的な言語

手動管理

プログラマが明示的に確保と解放（malloc・free など）を行う。

制御の自由度が最も高いが、解放忘れ（メモリリーク）や解放後の使用といった誤りが起きやすい。

C

RAII

オブジェクトの寿命（スコープ）に資源の確保と解放を結び付け、デストラクタで自動的に解放する。

実行時のコストが小さい。手動管理の誤りを大きく減らせるが、完全には防げない。

C++

参照カウント

オブジェクトを参照している数を数え、0 になった時点で解放する。

解放の時期が予測しやすい。循環参照を自動では解放できない。

Swift（ARC）、CPython（循環検出用の GC を併用）

トレーシング GC

実行時に到達可能なオブジェクトをたどり、到達できないものをまとめて解放する。

プログラマの負担が最も小さい。GC の実行による一時停止やメモリ使用量の増加がある。

Java、C#、Go、JavaScript、Kotlin、Ruby

所有権

各値の所有者を 1 つに限定し、所有者がスコープを抜けた時点で解放する。参照（借用）の有効性をコンパイル時に検査する。

GC なしでメモリ安全性を保証できる。規則を習得するまでの学習コストが高い。

Rust

次の Rust のコードは、所有権の移動（ムーブ）を示す。2 行目で s1 の所有権が s2 に移動するため、それ以降 s1 を使うとコンパイルエラーとなる。これにより、同じメモリを二重に解放する誤りがコンパイル時に排除される。

1let s1 = String::from("hello");
2let s2 = s1;              // 所有権が s1 から s2 に移動する
3println!("{s1}");         // コンパイルエラー: 移動済みの値を使用している
4println!("{s2}");         // s2 は有効

C や C++ では、範囲外のメモリへのアクセスや解放済みメモリの使用は未定義動作となり、深刻な脆弱性の原因となる。こうした誤りを言語の仕組みで防ぐ性質をメモリ安全性という。GC を持つ言語の多くと Rust（unsafe を使わない範囲）はメモリ安全である。言語ごとの違いは言語の比較で比較する。メモリ安全性をめぐる近年の動向は今後の動向で述べる。

2.5. 並行処理と並列処理

並行処理（concurrency）は複数の処理を論理的に同時に進めることであり、並列処理（parallelism）は複数の処理を物理的に同時に（複数の CPU コアで）実行することである。言語によって、並行処理を記述するための仕組みが大きく異なる。

表 2.3 主な並行処理のモデル

モデル

概要

代表的な言語

OS スレッドとロック

OS が管理するスレッドを生成し、共有データをロック（ミューテックス）で保護する。最も基本的なモデルだが、デッドロックやデータ競合を起こしやすい。

C、C++、Java、C#

async/await

待ち時間の発生する処理（I/O など）を非同期関数として記述し、await で結果を待つ。見た目は逐次的なコードのまま、少ないスレッドで多数の処理を並行に進められる。

C#、JavaScript、TypeScript、Python、Rust、Swift、Kotlin（コルーチン）

グリーンスレッド

言語のランタイムが管理する軽量なスレッドを多数生成し、少数の OS スレッドに割り当てて実行する。

Go（goroutine）、Java（仮想スレッド）

CSP

処理同士がメモリを共有せず、チャネルを通じてメッセージを送り合う。

Go（チャネル）

アクターモデル

状態を持つアクターがメッセージを受け取って逐次処理する。アクターの内部状態には外部から直接アクセスできない。

Erlang、Elixir、Swift（actor）

次の Go のコードは、goroutine とチャネルによる並行処理の例である。3 つの goroutine がそれぞれ計算結果をチャネルに送り、main 関数がそれを受け取って合計する（package 宣言と import は省略している）。

 1func square(n int, results chan<- int) {
 2    results <- n * n
 3}
 4
 5func main() {
 6    results := make(chan int)
 7    for _, n := range []int{1, 2, 3} {
 8        go square(n, results) // goroutine として並行に実行する
 9    }
10    sum := 0
11    for range 3 {
12        sum += <-results // チャネルから結果を受け取る
13    }
14    fmt.Println(sum) // 14
15}

並列処理の可否も言語や処理系によって異なる。CPython や CRuby には、同時に 1 つのスレッドしか Python や Ruby のコードを実行できないようにする GIL（Ruby では GVL と呼ぶ）があり、CPU を多く使う処理をスレッドで並列化しにくい。JavaScript はシングルスレッドのイベントループを基本とし、並列処理には Web Worker などの別の仕組みを使う。

Rust と Swift 6 は、データ競合をコンパイル時に検出する仕組みを備えている。Rust は所有権と Send・Sync トレイトによって、Swift は actor と Sendable プロトコルによって、スレッド間で安全に共有できない値の受け渡しを禁止する。

Rust、Swift（Result と throws を併用）

Java には、メソッドが送出し得る例外を宣言させ、呼び出し側に処理を強制する検査例外（checked exception）がある。検査例外は安全性を高める一方で記述が煩雑になるため、Java の後に登場した C# や Kotlin は採用していない。

 6}
