演習問題と発展課題の解答例

各章の演習問題と発展課題の解答例を示す。記述式の問題は、ここに示した以外の解答も考えられる。考え方が合っていれば正解としてよい。

第 1 章の解答例

問題 1-1：例えば次の 2 つが挙げられる。1 つ目は、OS やライブラリ、ハードウェアなどの実行環境が変化し、それに対応しなければ動作しなくなるためである。2 つ目は、利用者の業務や法制度が変化し、ソフトウェアに求められる機能が変わるためである。このほか、リリース後に発見された不具合の修正も必要になる。

問題 1-2：例えば、ソースコードの規模（LOC）やファンクションポイントを測定して工数を見積もること、テストのカバレッジや発見された不具合の数を測定して品質を評価することが挙げられる（第 10 章、第 11 章）。

問題 1-3：(a) と (c) は本質的な困難（(a) は複雑性、(c) は可変性）であり、(b) は偶有的な困難である。(b) はビルド環境の改善などの道具の改良で解消できるが、(a) と (c) はソフトウェアが扱う問題そのものに由来するため、道具の改良では解消できない。

発展課題 1-A：解答は調べた事例によって異なる。次の観点で整理するとよい。

  • 本質的な困難の例: 業務や制度が複雑で要求を正しく定義できなかった（複雑性）、開発中に要求が大きく変わった（可変性）、進捗や品質の問題が見えないまま終盤まで進んだ（不可視性）。

  • 偶有的な困難の例: 開発環境やツールが不十分であった、テストの自動化ができておらず回帰テストに時間がかかった。

  • 防げた可能性がある技法の例: 要求の検証とトレーサビリティ（第 3 章）、反復型開発による早期のフィードバック（第 2 章）、継続的インテグレーション（第 8 章）、メトリクスによる進捗と品質の可視化（第 10 章）、見積もりの不確実性を考慮した計画とリスク管理（第 11 章）。

本質的な困難は技法によって「なくす」ことはできず、「早く見つけて小さく対処する」ことしかできない点に注意して論じるとよい。

第 2 章の解答例

問題 2-1：(a) はウォーターフォールモデルまたは V 字モデルが適している。要求が安定しており、規制のために工程ごとの文書が必要だからである。特に V 字モデルを用いると、各工程に対応するテストの計画を早い段階で立てられる。(b) はアジャイル開発が適している。要求が不確実であり、短い反復で動くソフトウェアを提供して利用者からのフィードバックを得る必要があるからである。

問題 2-2：ドキュメントが不要という意味ではない。宣言には「左記のことがらに価値があることを認めながらも、私たちは右記のことがらにより価値をおく」とあり、ドキュメントにも価値があることを認めたうえで、動くソフトウェアをより優先するという優先順位を示している。

問題 2-3：スプリントレビューは、スプリントで作成した成果物（インクリメント）を対象とし、利害関係者に示してフィードバックを得るイベントである。スプリントレトロスペクティブは、チームの進め方（プロセス、人間関係、ツールなど）を対象とし、次のスプリントに向けた改善策を決めるイベントである。前者は「何を作ったか」、後者は「どのように作ったか」を振り返る。

発展課題 2-A：利点と欠点の例を次に示す。

表 2 スプリントの長さの比較

長さ

利点

欠点

1 週間

フィードバックを頻繁に得られ、方向の修正が早い。計画の誤差が小さく、問題が早く表面化する。

スプリントプランニングやレビューなどのイベントの時間が開発時間に対して相対的に大きくなる。1 週間で完成させられる大きさに作業を分割する必要がある。

4 週間

まとまった機能を 1 つのスプリントで完成させやすい。イベントにかかる時間の割合が小さい。

フィードバックが得られるまでの期間が長く、誤った方向に進んだ場合の損失が大きい。スプリントの途中で要求が変わりやすい。

要求が頻繁に変わる新規の Web サービスでは、1 週間（または 2 週間）を選ぶのが妥当である。利用者の反応を早く確認し、プロダクトバックログの優先順位を頻繁に見直すことの価値が、イベントにかかる時間の負担を上回るからである。

第 3 章の解答例

問題 3-1：(a) と (c) は機能要求、(b) と (d) は非機能要求である。(b) は性能効率性、(d) はセキュリティに関する非機能要求である。

問題 3-2：「曖昧でない」と「検証可能である」を満たしていない。何をもって「使いやすい」とするかが人によって異なり、満たしているかを判定できないからである。例えば「初めて利用する会員の 90 % 以上が、説明書を読まずに 3 分以内に商品の注文を完了できる」のように、測定できる形に書き換える。

問題 3-3：ユーザーストーリーの例を次に示す。

1ポイント会員として、ポイントを使うかどうかを決めるために、買い物の前に自分のポイント残高を確認できる機能がほしい。

受け入れ基準の例を次に示す。

1Given ポイント会員のポイント残高が 1200 ポイントである
2When  会員がマイページを開く
3Then  「ポイント残高: 1200 ポイント」と表示される

発展課題 3-A：要求の例を次に示す。

  • 機能要求の例: 利用者は書名、著者名、ISBN で蔵書を検索できる。利用者は検索結果から蔵書の所在（館と書架）と貸出状況を確認できる。利用者は貸出中の蔵書を予約できる。利用者は自分の貸出・予約の状況を確認できる。職員は蔵書を登録・削除できる。

  • 非機能要求の例: 検索結果は 95 % の要求について 2 秒以内に表示する。開館時間中の稼働率は 99.5 % 以上とする。利用者の貸出履歴は職員のうち権限を持つ者だけが閲覧できる。

自己レビューでは、例えば「検索が速いこと」は検証可能でないため、上の例のように時間と割合で書き直す。「利用者は蔵書を検索・予約できる」のように 1 つの要求に複数の事柄が含まれている場合は、「単一である」を満たすように分ける。ユースケース図では、アクターとして「利用者」「職員」を、ユースケースとして上の機能要求に対応するものを描く。他の図書館システムと連携する場合は、それも外部システムのアクターとして描く。

第 4 章の解答例

問題 4-1：解答例を次に示す。既存のクラスは変更する必要がなく、新しいクラスを追加するだけで対応できた。単一責任の原則に従って責任を分割していたためである。

リスト 1 ex04_csv_formatter.py
 1"""演習問題 4-1 の解答例: CSV 形式で整形するクラスの追加（第 4 章）.
 2
 3``ch04_srp_after.py`` の既存のクラスは一切変更せずに、
 4新しい整形クラスを追加するだけで CSV 形式の出力に対応できる。
 5"""
 6
 7import csv
 8import io
 9
10from ch04_srp_after import SalesSummary
11
12
13class CsvFormatter:
14    """売上データを CSV 形式に整形する."""
15
16    def format(self, summary: SalesSummary) -> str:
17        """見出し行と各商品の行、合計行からなる CSV 文字列を返す."""
18        buffer = io.StringIO()
19        writer = csv.writer(buffer, lineterminator="\n")
20        writer.writerow(["商品", "金額"])
21        for name, amount in summary.sales.items():
22            writer.writerow([name, amount])
23        writer.writerow(["合計", summary.total()])
24        return buffer.getvalue()
25
26
27if __name__ == "__main__":
28    summary = SalesSummary({"りんご": 1200, "みかん": 800})
29    print(CsvFormatter().format(summary))

問題 4-2：引数 mode によって関数内の処理を切り替えているため、制御結合である。呼び出し側が関数の内部の処理を知っている必要があり、出力方法を追加するたびにこの関数を修正しなければならない。結合度を下げるには、出力方法ごとに print_report と save_report のような別の関数に分ける。または、第 5 章の Strategy パターンのように、出力方法を表すオブジェクトを引数として渡す。

問題 4-3：見た目が似ているだけで、本来は別々の理由で変更されるコードまで 1 つの共通部品にまとめてしまうと、その共通部品は複数の目的を持つことになり、凝集度が下がる。また、無関係なモジュール同士が共通部品を通じて結合するため、一方の都合で共通部品を変更すると、もう一方にも影響が及ぶ。DRY で避けるべきなのは「同じ知識」の重複であり、偶然同じ形をしているコードの重複ではない。

発展課題 4-A：解答例を次に示す。整形方法を Formatter、保存先を Writer という抽象（Protocol）として定義し、ReportService はこれらの抽象だけに依存する。

リスト 2 adv04_report_service.py
 1"""発展課題 4-A の解答例: 保存先を差し替えられるレポート出力（第 4 章）.
 2
 3``ReportService`` は整形方法（``Formatter``）と保存先（``Writer``）の
 4どちらにも、具体的なクラスではなく抽象に依存する。
 5そのため、テストではファイルを作らずにメモリー上で結果を確認できる。
 6"""
 7
 8from pathlib import Path
 9from typing import Protocol
10
11from ch04_srp_after import SalesSummary, TextFormatter
12
13
14class Formatter(Protocol):
15    """売上データを文字列に整形する手段の抽象."""
16
17    def format(self, summary: SalesSummary) -> str:
18        """整形済みの文字列を返す."""
19        ...
20
21
22class Writer(Protocol):
23    """文字列を保存する手段の抽象."""
24
25    def write(self, name: str, text: str) -> None:
26        """``text`` を ``name`` という名前で保存する."""
27        ...
28
29
30class FileWriter:
31    """指定したフォルダーにファイルとして保存する."""
32
33    def __init__(self, directory: Path) -> None:
34        self.directory = directory
35
36    def write(self, name: str, text: str) -> None:
37        (self.directory / name).write_text(text, encoding="utf-8")
38
39
40class MemoryWriter:
41    """保存した内容をメモリー上に保持する（テスト用）."""
42
43    def __init__(self) -> None:
44        self.files: dict[str, str] = {}
45
46    def write(self, name: str, text: str) -> None:
47        self.files[name] = text
48
49
50class ReportService:
51    """売上レポートを整形して保存する."""
52
53    def __init__(self, formatter: Formatter, writer: Writer) -> None:
54        self.formatter = formatter
55        self.writer = writer
56
57    def publish(self, summary: SalesSummary, name: str) -> None:
58        """レポートを整形し、``name`` という名前で保存する."""
59        self.writer.write(name, self.formatter.format(summary))
60
61
62if __name__ == "__main__":
63    memory = MemoryWriter()
64    service = ReportService(TextFormatter(), memory)
65    service.publish(SalesSummary({"りんご": 1200, "みかん": 800}), "report.txt")
66    print(memory.files["report.txt"])

ダウンロード: adv04_report_service.py

テストでは、ファイルに書き込む FileWriter の代わりに、内容をメモリー上に保持する MemoryWriter を渡す。整形方法として演習問題 4-1 の CsvFormatter も、ReportService を変更せずに利用できる。

第 5 章の解答例

問題 5-1：解答例を次に示す。Checkout クラスや既存の戦略クラスは変更していない。

リスト 4 ex05_tiered_rate.py
 1"""演習問題 5-1 の解答例: 段階的な送料の戦略の追加（第 5 章）.
 2
 3重さ 2 kg までは 400 円、2 kg を超えた分は 1 kg ごとに 200 円を加算する
 4（1 kg 未満の端数は切り上げる）。``Checkout`` を変更せずに追加できる。
 5"""
 6
 7import math
 8
 9from ch05_strategy import Checkout
10
11
12class TieredRate:
13    """一定の重さまでは定額、超えた分は 1 kg ごとに加算する送料."""

15    ("flake8", ["-m", "flake8", "."]),

22    """1 つの検査を実行し、成功したら True を返す."""
23    result = subprocess.run(
24        [sys.executable, *args],
25        cwd=directory,
26        capture_output=True,
27        text=True,
28    )

30    print(f"[{'OK' if passed else 'NG'}] {name}")

40    results = [run_check(name, args, directory) for name, args in CHECKS]
41    failed = results.count(False)
42    print(f"{len(results)} 件中 {failed} 件の検査が失敗した")
43    return 1 if failed else 0

リファクタリング後のコードを次に示す。会員割引と送料の規則を billed_amount 関数と名前付きの定数で表し、元のコードでは読み取りにくかった仕様が分かるようにした。

 1"""発展課題 9-A の解答例: リファクタリング後の請求書の作成（第 9 章）.

17    """請求明細の 1 行."""
18
19    name: str
20    unit_price: int
21    quantity: int
22
23    @property
24    def amount(self) -> int:
25        """単価と数量から求めた金額."""
26        return self.unit_price * self.quantity
27

29        """明細を 1 行の文字列にする."""
30        return f"{self.name} x{self.quantity} = {self.amount}"

33def billed_amount(subtotal: int, is_member: bool) -> int:
34    """小計に会員割引または送料を適用した請求額を返す.
35
36    会員は小計がしきい値以上なら割引される（送料は常に無料）。
37    非会員は小計がしきい値未満なら送料がかかる。
38    """
39    if is_member:
40        if subtotal >= MEMBER_DISCOUNT_THRESHOLD:
41            return subtotal * (100 - MEMBER_DISCOUNT_PERCENT) // 100
42        return subtotal
43    if subtotal < FREE_SHIPPING_THRESHOLD:
44        return subtotal + SHIPPING_FEE
45    return subtotal

50    subtotal = sum(item.amount for item in items)
51    lines = [item.to_line() for item in items]
52    lines.append(f"合計 {billed_amount(subtotal, is_member)}")
53    return "\n".join(lines)

問題 11-1：経路は A → B → D → E → F（3 + 4 + 2 + 3 + 2 = 14 日）と A → C → E → F（3 + 7 + 3 + 2 = 15 日）の 2 つである。したがって、クリティカルパスは A → C → E → F であり、プロジェクト全体の所要日数は 15 日である。クリティカルパス上にない作業 B と D には 1 日の余裕がある。ただし、この余裕は B と D で共有しているため、B が 1 日遅れると D の余裕はなくなる。

問題 11-2：工数と開発期間は次のとおりである。

\[E = 2.4 \times 100^{1.05} \approx 302.1 \text{（人月）}, \qquad D = 2.5 \times 302.1^{0.38} \approx 21.9 \text{（月）}\]

50 KLOC の場合の工数は約 145.9 人月であるから、規模が 2 倍になると工数は \(2^{1.05} \approx 2.07\) 倍になる。規模に比例する以上に工数が増える、規模の不経済の例である。

問題 11-4：(a) は軽減、(b) は回避、(c) は転嫁である。

発展課題 11-A：解答例を次に示す。標準ライブラリの random.triangular で三角分布に従う乱数を生成している。

リスト 16 adv11_monte_carlo.py
 1"""発展課題 11-A の解答例: モンテカルロ法によるスケジュールの見積もり（第 11 章）.
 2
 3各作業の所要日数を 1 つの値ではなく、楽観値・最頻値・悲観値の 3 点で見積もる。
 4所要日数を三角分布に従う乱数として多数回シミュレーションし、
 5プロジェクト全体の所要日数の分布を求める。作業の構成は演習問題 11-1 と同じである。
 6"""
 7
 8import random
 9import statistics
10
11# 作業名: (楽観値, 最頻値, 悲観値)（日）
12ESTIMATES: dict[str, tuple[float, float, float]] = {
13    "A": (2, 3, 5),
14    "B": (3, 4, 8),
15    "C": (5, 7, 12),
16    "D": (1, 2, 4),
17    "E": (2, 3, 6),
18    "F": (1, 2, 3),
19}
20
21# 作業名: 先行作業の一覧（先行作業が先に現れる順に並べる）
22PREDECESSORS: dict[str, list[str]] = {
23    "A": [],
24    "B": ["A"],
25    "C": ["A"],
26    "D": ["B"],
27    "E": ["C", "D"],
28    "F": ["E"],
29}
30
31
32def project_duration(durations: dict[str, float]) -> float:
33    """各作業の所要日数から、プロジェクト全体の所要日数を求める."""
34    finish: dict[str, float] = {}
35    for task, predecessors in PREDECESSORS.items():
36        start = max((finish[p] for p in predecessors), default=0.0)
37        finish[task] = start + durations[task]
38    return max(finish.values())
39
40
41def simulate(trials: int, seed: int) -> list[float]:
42    """シミュレーションを ``trials`` 回行い、全体の所要日数の一覧を返す."""
43    rng = random.Random(seed)
44    results = []
45    for _ in range(trials):
46        durations = {
47            task: rng.triangular(low, high, mode)
48            for task, (low, mode, high) in ESTIMATES.items()
49        }
50        results.append(project_duration(durations))
51    return results
52
53
54def percentile(values: list[float], ratio: float) -> float:
55    """``values`` のうち、小さいほうから ``ratio`` の位置にある値を返す."""
56    ordered = sorted(values)
57    index = min(len(ordered) - 1, int(len(ordered) * ratio))
58    return ordered[index]
59
60
61if __name__ == "__main__":
62    most_likely = project_duration(
63        {task: mode for task, (_, mode, _) in ESTIMATES.items()}
64    )
65    results = simulate(trials=10_000, seed=1)
66    print(f"最頻値だけで計算した所要日数: {most_likely:.1f} 日")
67    print(f"シミュレーションの平均: {statistics.mean(results):.1f} 日")
68    print(f"50 % の確率で終わる日数: {percentile(results, 0.5):.1f} 日")
69    print(f"90 % の確率で終わる日数: {percentile(results, 0.9):.1f} 日")
70    on_time = sum(1 for value in results if value <= most_likely)
71    print(f"最頻値の日数以内に終わる確率: {on_time / len(results):.1%}")

実行結果を次に示す（乱数の種を 1 に固定した場合）。

1最頻値だけで計算した所要日数: 15.0 日
2シミュレーションの平均: 17.5 日
350 % の確率で終わる日数: 17.5 日

5最頻値の日数以内に終わる確率: 6.9%

最頻値だけで計算した 15 日以内に終わる確率は、わずか 7 % 程度である。これには 2 つの理由がある。1 つ目は、各作業の見積もりが悲観値の側に長く伸びた非対称な分布であり、平均が最頻値より大きいことである。2 つ目は、作業 E の開始が C と D の両方の完了を待つため、どちらか一方が遅れるだけで E が遅れることである（遅いほうの経路に合わせて進むため、経路が合流するたびに遅れやすくなる）。このように、最もありそうな値を積み上げた見積もりは楽観的になりやすい。見積もりは「90 % の確率で 20 日以内」のように、確率と幅を伴って示すことが望ましい。
