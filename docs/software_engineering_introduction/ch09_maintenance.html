9. 保守とリファクタリング

ソフトウェアはリリースして終わりではない。リリース後も不具合の修正や環境の変化への対応、機能の追加が続き、多くの場合、その期間とコストは最初の開発を上回る。本章では、保守の種類と、保守を難しくする要因、およびコードの構造を改善するリファクタリングを説明する。

9.1. 保守の分類

ソフトウェア保守とは、リリース後のソフトウェアを修正する活動である。国際規格 ISO/IEC 14764 [ISO14764] では、保守を目的によって次の 4 つに分類している。

表 9.1 保守の分類

分類

内容

例

是正保守

リリース後に発見された不具合を修正する。

計算結果の誤りを修正する。

適応保守

実行環境の変化に対応する。

OS やライブラリの更新、法改正による税率の変更に対応する。

完全化保守

性能や保守性を改善する、または利用者の新たな要求に応える。

処理を高速化する、新しい帳票を追加する。

予防保守

潜在的な不具合が実際の障害になる前に、検出して修正する。

将来の障害につながるおそれのあるコードを修正する。

是正保守と予防保守は不具合への対応、適応保守と完全化保守は改良にあたる。一般に、保守の大部分は不具合の修正ではなく、環境の変化や新たな要求への対応、つまり改良が占めるとされる。

9.2. ソフトウェア進化の法則

Lehman は、実際の業務で使われるソフトウェアの長期的な変化を観察し、ソフトウェア進化の法則としてまとめた [Lehman1980]。その中でも特に重要なのが次の 2 つである。

  • 継続的変化の法則：実世界で使われるソフトウェアは、継続的に変更されなければ、次第に役に立たなくなる。

  • 複雑性増大の法則：ソフトウェアは変更されるにつれて複雑になる。複雑さを抑える作業を行わない限り、この傾向は続く。

この 2 つの法則は、ソフトウェアは変更し続けなければならないが、変更するほど変更しにくくなるという保守の根本的な難しさを示している。そのため、機能の変更とは別に、構造を改善する作業を継続的に行う必要がある。

9.3. 技術的負債

技術的負債は、Cunningham が 1992 年に用いた比喩である [Cunningham1992]。開発を急ぐために、設計やコードの品質について理想的ではない選択をすると、その場の開発は早く進む。しかし、その後の変更のたびに余分な手間（利子）がかかるようになる。これを金銭の借り入れに例えたものが技術的負債である。

技術的負債は、必ずしも悪いものではない。市場への投入を急ぐために意図的に負債を抱え、後で返済するという判断は合理的な場合もある。問題になるのは、負債の存在が認識されず、返済されないまま蓄積していくことである。負債が大きくなると、利子の支払い（変更のたびに発生する余分な作業）に開発の大部分が費やされ、新しい機能をほとんど追加できなくなる。

技術的負債の例として、次のものが挙げられる。

  • 重複したコードや、長すぎる関数・クラス

  • 自動テストの不足

  • 古いバージョンのライブラリへの依存

  • 実装と食い違った設計書

技術的負債を返済する代表的な手段が、次に説明するリファクタリングである。

9.4. リファクタリング

リファクタリングは、ソフトウェアの外部から見た振る舞いを変えずに、内部の構造を改善することである [Fowler2018]。リファクタリングの目的は、コードを理解しやすく、変更しやすくすることである。機能の追加や不具合の修正とは区別し、同時に行わないことが重要である。

9.4.1. リファクタリングの例

次のコードは、注文明細から支払額を計算して表示する関数である。正しく動作するが、読みやすさに問題がある。

リスト 9.1 ch09_refactoring_before.py
 1"""リファクタリング前のコード（第 9 章）.
 2
 3動作はするが、次のような問題がある。
 4
 5* 関数名と変数名から意図が読み取れない
 6* 消費税率や割引の条件がマジックナンバーとして埋め込まれている
 7* 1 つの関数に計算と表示が混在している
 8"""
 9
10
11def calc(d: list[tuple[str, int, int]]) -> None:
12    t: float = 0
13    for x in d:
14        t += x[1] * x[2]
15    if t >= 10000:
16        t = t * 0.9
17    t = t * 1.1
18    print("合計: " + str(int(t)) + " 円")
19
20
21if __name__ == "__main__":
22    calc([("ノート", 300, 10), ("ペン", 150, 50)])

ダウンロード: ch09_refactoring_before.py

calc、d、t、x といった名前からは、それぞれが何を表すのかが分からない。x[1] * x[2] が単価と数量の積であることや、0.9 が割引、1.1 が消費税を表すことは、コードを詳しく読まなければ分からない。また、計算と表示が 1 つの関数に混在しているため、計算結果だけをテストすることもできない。

このコードを、振る舞いを変えずにリファクタリングした結果を次に示す。

リスト 9.2 ch09_refactoring_after.py
 1"""リファクタリング後のコード（第 9 章）.
 2
 3``ch09_refactoring_before.py`` と同じ結果を出力するが、次の改善を行った。
 4
 5* 意図が分かる名前に変更した（名前の変更）
 6* マジックナンバーを名前付き定数に置き換えた
 7* 計算と表示を別の関数に分けた（関数の抽出）
 8* 明細をデータクラスで表した
 9"""
10
11from dataclasses import dataclass
12
13TAX_RATE = 0.10
14DISCOUNT_THRESHOLD = 10_000
15DISCOUNT_RATE = 0.10
16
17
18@dataclass(frozen=True)
19class LineItem:
20    """注文明細の 1 行."""
21
22    name: str
23    unit_price: int
24    quantity: int
25
26    @property
27    def amount(self) -> int:
28        """単価と数量から求めた金額."""
29        return self.unit_price * self.quantity
30
31
32def subtotal(items: list[LineItem]) -> int:
33    """明細の金額の合計を返す."""
34    return sum(item.amount for item in items)
35
36
37def apply_discount(amount: float) -> float:
38    """しきい値以上の金額に割引を適用する."""
39    if amount >= DISCOUNT_THRESHOLD:
40        return amount * (1 - DISCOUNT_RATE)
41    return amount
42
43
44def total_with_tax(items: list[LineItem]) -> int:
45    """割引と消費税を適用した支払額（円未満切り捨て）を返す."""
46    return int(apply_discount(subtotal(items)) * (1 + TAX_RATE))
47
48
49def print_total(items: list[LineItem]) -> None:
50    """支払額を表示する."""
51    print(f"合計: {total_with_tax(items)} 円")
52
53
54if __name__ == "__main__":
55    print_total([LineItem("ノート", 300, 10), LineItem("ペン", 150, 50)])

ダウンロード: ch09_refactoring_after.py

ここでは、次のリファクタリングの手法を適用した。

表 9.2 適用したリファクタリングの手法

手法

適用した内容

名前の変更

calc を total_with_tax と print_total に、d を items にするなど、意図が分かる名前に変更した。

マジックナンバーの定数化

割引率、消費税率、割引を適用する金額のしきい値を、DISCOUNT_RATE、TAX_RATE、DISCOUNT_THRESHOLD という名前付きの定数にした。

関数の抽出

小計の計算、割引の適用、税込金額の計算、表示を、それぞれ別の関数に分けた。

データ構造の導入

タプルを LineItem データクラスに置き換え、x[1] のような添字ではなく unit_price という名前で参照できるようにした。

リファクタリング後のコードは行数こそ増えているが、各関数が何をするかは名前を読むだけで分かる。また、total_with_tax は値を返すため、表示を伴わずに計算結果をテストできる。

9.4.2. リファクタリングとテスト

リファクタリングでは「振る舞いを変えない」ことが前提である。そのため、リファクタリングの前に、対象のコードの振る舞いを確認する自動テストを用意しておく必要がある。テストがあれば、変更のたびにテストを実行することで、振る舞いが変わっていないことをすぐに確認できる。

また、リファクタリングは一度に大きく行わず、小さな変更を 1 つずつ行い、そのたびにテストを実行する。第 7 章で説明したテスト駆動開発では、この作業が開発の周期に組み込まれている。

9.5. レガシーコードへの対処

長年保守されてきたソフトウェアには、構造が複雑で、設計の意図を知る人もおらず、変更が困難になったコードが含まれていることが多い。このようなコードはレガシーコードと呼ばれる。Feathers は、レガシーコードを「テストのないコード」と定義した [Feathers2004]。テストがなければ、変更によって既存の振る舞いが壊れていないかを確認できず、安全にリファクタリングできないためである。

レガシーコードを改善する基本的な手順は次のとおりである。

  1. 変更が必要な箇所を特定する。

  2. その箇所の現在の振る舞いを記録するテストを書く。このテストは、仕様として正しいかどうかではなく、現在の振る舞いをそのまま記録するものであり、仕様化テスト（characterization test）と呼ばれる。

  3. テストを書けるように、依存関係を断ち切る最小限の変更を行う（例: 第 4 章の依存性の注入を用いて、データベースへのアクセスを差し替え可能にする）。

  4. テストで保護された状態で、目的の変更とリファクタリングを行う。

すべてを一度に書き直すのではなく、変更が必要になった箇所から少しずつテストを追加し、改善していくことが現実的である。

9.6. まとめ

  • 保守は是正・適応・完全化・予防の 4 種類に分類され、その多くは改良が占める。

  • ソフトウェアは変更し続けなければならないが、変更するほど複雑になる。

  • 技術的負債は、後の変更のコストを増やす。存在を認識し、計画的に返済する。

  • リファクタリングは、自動テストで振る舞いが変わらないことを確認しながら、小さな単位で行う。

9.7. 演習問題

解答例は「第 9 章の解答例」にある。

問題 9-1：次の (a)〜(d) は、それぞれ ISO/IEC 14764 のどの保守にあたるか。

(a) 消費税率の改正に合わせて計算処理を変更する。

(b) 利用者から報告された、合計金額の計算の誤りを修正する。

(c) 利用者の要望に応えて、検索結果を並べ替える機能を追加する。

(d) 現時点で障害は起きていないが、将来データが増えると桁あふれが起こる箇所を修正する。

問題 9-2：リファクタリングと機能の追加を同時に行うべきでないのはなぜか。

問題 9-3：次の関数を、振る舞いを変えずにリファクタリングせよ。

1def f(s: list[int]) -> float:
2    a = 0
3    for i in s:
4        a = a + i
5    if len(s) == 0:
6        return 0.0
7    return a / len(s)

9.8. 発展課題

演習問題より発展的な課題である。正解が 1 つに定まらないものも含む。解答例や解答の方針は「第 9 章の解答例」にある。

発展課題 9-A：adv09_invoice_before.py の関数 inv は、テストのないレガシーコードである。本章の手順に従って、まず現在の振る舞いを記録する仕様化テストを書き、次にテストで保護された状態でリファクタリングせよ。リファクタリング後の関数が、元の関数と同じ結果を返すことをテストで確認すること。
