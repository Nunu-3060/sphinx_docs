6. 実装とコード品質

実装は、設計に基づいてプログラムを作成する活動である。ソースコードは書かれる回数よりも読まれる回数のほうがはるかに多い。そのため、動くだけでなく、他の人（将来の自分を含む）が読んで理解しやすいコードを書くことが重要である。本章では、コードの品質を保つための規約・技法・ツールを説明する。

6.1. コーディング規約

コーディング規約は、命名、インデント、空白、コメントの書き方などについてチームで定めたルールである。規約に従ってコードの見た目をそろえると、読み手は書き方の違いに気を取られず、内容の理解に集中できる。

Python には、公式のスタイルガイドである PEP 8 [PEP8] がある。主なルールを次に示す。

表 6.1 PEP 8 の主なルール

項目

ルール

インデント

1 レベルあたり半角空白 4 文字とする。

1 行の長さ

最大 79 文字とする。

空行

トップレベルの関数とクラスの定義の前後は 2 行、クラス内のメソッドの定義の前後は 1 行空ける。

import 文

ファイルの先頭に置き、標準ライブラリ、サードパーティ、自作モジュールの順にまとめる。

関数名・変数名

小文字とアンダースコアを用いる（例: average_salary）。

クラス名

単語の先頭を大文字にする（例: SalesSummary）。

定数名

大文字とアンダースコアを用いる（例: TAX_RATE）。

規約を人手で守るのは負担が大きいため、後述するリンターやフォーマッターで自動的に確認・整形するのが一般的である。

6.2. 読みやすいコード

規約を守るだけでは、読みやすいコードにはならない。読みやすさを高めるための代表的な指針を次に示す。

意図が伝わる名前を付ける。変数名や関数名は、それが何を表すか、何をするかが分かるように付ける。d、tmp、calc のような名前ではなく、line_items、total_with_tax のように具体的に書く。名前が長くなりすぎる場合は、その関数が多くのことをしすぎている兆候であることが多い。

関数を小さく保つ。1 つの関数は 1 つのことだけを行うようにする。関数が長くなったら、まとまった処理を別の関数として抽出する。小さな関数は名前によって処理の意図を説明でき、テストもしやすい。

マジックナンバーを避ける。コード中に直接書かれた意味の分からない数値（マジックナンバー）は、TAX_RATE = 0.10 のように名前付きの定数にする。

コメントには「なぜ」を書く。コードが「何をしているか」はコード自体で表現し、コメントにはコードからは読み取れない「なぜそうしているか」（設計上の判断、制約、注意点など）を書く。

これらの指針を適用したコードの例は、第 9 章のリファクタリングの例で示す。

6.3. 型ヒントと静的型検査

Python は動的型付け言語であり、変数や引数の型を宣言しなくてもプログラムは動作する。しかし、Python 3.5 以降では、型ヒント（型注釈）によって関数の引数や戻り値の型を記述できる。型ヒントは実行時の動作には影響しないが、次の利点がある。

  • 関数の入出力の型が明示され、コードを読む人に意図が伝わる。

  • エディターによる入力補完やエラー表示が正確になる。

  • mypy などの型検査器が、実行前に型の誤りを検出できる。

型ヒントを付けたコードの例を次に示す。

リスト 6.1 ch06_type_hints.py
 1"""型ヒントと静的型検査の例（第 6 章）.
 2
 3型ヒントを付けると、関数の入出力が読み手に伝わるだけでなく、
 4mypy などの型検査器が実行前に誤りを検出できる。
 5"""
 6
 7from dataclasses import dataclass
 8
 9
10@dataclass(frozen=True)
11class Employee:
12    """社員を表す."""
13
14    name: str
15    salary: int
16
17
18def average_salary(employees: list[Employee]) -> float:
19    """社員の平均給与を返す。社員がいなければ 0.0 を返す."""
20    if not employees:
21        return 0.0
22    return sum(e.salary for e in employees) / len(employees)
23
24
25def find_by_name(employees: list[Employee], name: str) -> Employee | None:
26    """名前が一致する社員を返す。見つからなければ None を返す."""
27    for employee in employees:
28        if employee.name == name:
29            return employee
30    return None
31
32
33if __name__ == "__main__":
34    staff = [Employee("佐藤", 300_000), Employee("鈴木", 360_000)]
35    print(f"平均給与: {average_salary(staff):,.0f} 円")
36
37    found = find_by_name(staff, "鈴木")
38    # found は Employee | None 型なので、None でないことを確認してから使う。
39    # この確認を省略すると mypy が誤りとして報告する。
40    if found is not None:
41        print(f"{found.name} の給与: {found.salary:,} 円")

ダウンロード: ch06_type_hints.py

find_by_name の戻り値の型 Employee | None は、「Employee または None を返す」ことを表す。40 行目の if found is not None: を省略して found.name を参照すると、found が None の場合に実行時エラーになる。mypy はこの誤りを実行前に検出し、次のように報告する（出力の一部を示す）。

1error: Item "None" of "Employee | None" has no attribute "name"  [union-attr]

このように、実行してみなければ分からない誤りを、プログラムを実行する前に機械的に検出する手法を静的型検査と呼ぶ。mypy は次のコマンドで実行できる [mypy]。--strict オプションを付けると、型ヒントの付け忘れなども含めて厳しく検査する。

1python -m pip install mypy
2python -m mypy --strict examples

6.4. 静的解析とリンター

静的解析とは、プログラムを実行せずにソースコードを解析し、誤りや問題を検出することである。静的型検査も静的解析の一種である。コーディング規約の違反や、誤りの可能性が高い書き方を検出するツールをリンターと呼ぶ。

Python の代表的なリンターに flake8 [flake8] がある。flake8 は、PEP 8 への違反（pycodestyle）、未使用の import や未定義の名前などの論理的な誤り（pyflakes）、関数の複雑すぎる構造（mccabe）を検出する。

1python -m pip install flake8
2python -m flake8 examples

例えば、未使用の import がある場合は次のように報告される。

1examples/sample.py:1:1: F401 'os' imported but unused

本書のサンプルコードは、すべて flake8 と mypy の --strict オプションで違反が検出されないことを確認している。

また、コードを規約に従って自動的に整形するツールをフォーマッターと呼ぶ。フォーマッターを使うと、書式に関する議論やレビューの指摘が不要になる。リンターとフォーマッターは、エディターの保存時や、第 8 章で説明する継続的インテグレーションで自動的に実行するとよい。

6.5. コードレビュー

コードレビューは、作成者以外の開発者がソースコードを読んで確認する活動である。コードレビューには次の目的がある。

  • 不具合や設計上の問題を早い段階で発見する。

  • コードの読みやすさや、規約・設計方針との整合性を確認する。

  • 知識をチームで共有し、特定の人しか理解していないコードを減らす。

効果的なレビューのためには、1 回のレビューの対象を小さく保つことが重要である。数千行の変更を一度に確認するのは難しく、問題を見落としやすい。また、書式などの機械的に確認できる事項はリンターやフォーマッターに任せ、人間は設計や意図の妥当性など、人間にしか判断できない事項に集中する。指摘はコードに対して行い、作成者個人を批判しないことも大切である。

6.6. まとめ

  • ソースコードは読まれる回数が多いため、読みやすさを重視して書く。

  • コーディング規約（Python では PEP 8）に従い、意図が伝わる名前と小さな関数を心がける。

  • 型ヒントと静的型検査（mypy）、リンター（flake8）により、誤りを実行前に機械的に検出する。

  • コードレビューで不具合を早期に発見し、知識をチームで共有する。
