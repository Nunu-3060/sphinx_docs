第 11 章 実行時環境とネイティブコード生成

コンパイラが生成したコードは、それだけでは動きません。関数を呼び出すための約束事、局所変数を置く場所、不要になったメモリを回収するしくみなど、実行を支える環境が必要です。この章では、このような実行時環境を説明し、続いて機械語を生成する場合の中心的な問題であるレジスタ割り当てを実装します。

記憶領域の構成

プログラムの実行中、メモリはおおむね次のような領域に分けて使われます。

領域

置かれるもの

寿命

コード

機械語の命令

プログラムの実行中ずっと

静的データ

大域変数、文字列定数

プログラムの実行中ずっと

スタック

局所変数、引数、戻り番地

関数の呼び出しから戻りまで

ヒープ

実行時に確保したオブジェクト（Tiny の配列など）

確保してから解放されるまで

スタックに置いたデータは関数から戻ると自動的に捨てられますが、ヒープに置いたデータはいつ不要になるかが一般には分かりません。ヒープの管理は、プログラマが明示的に解放する方式（C の free）と、処理系が自動的に回収する方式（ガベージコレクション）があります。

呼び出しスタックとスタックフレーム

第 10 章の仮想マシンでは、関数呼び出しごとにフレームを作り、局所変数を値スタックに置きました。機械語を実行する場合も考え方は同じですが、より多くの情報をフレームに置きます。

call 命令は戻り番地（呼び出しの次の命令の番地）をスタックに積んでから関数の先頭に飛び、ret 命令はスタックから戻り番地を取り出してそこに戻ります。関数の先頭（プロローグ）では、呼び出し元のフレームポインタを保存し、局所変数のための領域を確保します。関数の末尾（エピローグ）ではその逆を行います。

呼び出し規約

引数をどこに置くか、戻り値をどこに返すか、どのレジスタの値を呼び出しの前後で保存しなければならないか、といった約束事を呼び出し規約と呼びます。呼び出し規約が一致していれば、別々のコンパイラで作ったコードどうしでも関数を呼び出せます。x86-64 の代表的な呼び出し規約を示します。

x86-64 の呼び出し規約（整数の引数と戻り値）

規約

引数を渡すレジスタ

戻り値

System V（Linux、macOS など）

rdi、rsi、rdx、rcx、r8、r9（7 番目以降はスタック）

rax

Microsoft x64（Windows）

rcx、rdx、r8、r9（5 番目以降はスタック）

レジスタは、呼び出された側が値を保存して元に戻す義務を負うもの（callee-saved）と、呼び出し側が必要なら保存しておくもの（caller-saved）に分けられます。呼び出しをまたいで生存する変数を caller-saved のレジスタに置くと、呼び出しのたびに保存と復元が必要になります。

ネイティブコードの生成

機械語を生成するバックエンドは、主に次の 3 つの仕事をします。

  • 命令選択：IR の命令を、対象の CPU の命令に対応させます。CPU には mov rax, [rbx + rcx * 8] のように、複数の IR の命令（乗算、加算、読み出し）をまとめて行える命令があるので、IR の命令の木を CPU の命令のパターンで覆うように選びます。

  • レジスタ割り当て：IR の無数の変数を、CPU の有限個のレジスタに割り当てます。

  • 命令スケジューリング：CPU のパイプラインが止まらないように、意味を変えない範囲で命令の順序を入れ替えます。

関数 sum を x86-64 の機械語（アセンブリ言語、Intel 記法）で書くと、たとえば次のようになります。すべての変数がレジスタに割り当てられており、メモリの読み書きがありません。

 1sum:                    ; 引数 n は edi レジスタに渡される
 2    xor  eax, eax       ; s = 0（s は eax に割り当てる）
 3    mov  ecx, 1         ; i = 1（i は ecx に割り当てる）
 4.cond:
 5    cmp  ecx, edi       ; i と n を比較し
 6    jg   .end           ; i > n ならループを抜ける
 7    add  eax, ecx       ; s = s + i
 8    add  ecx, 1         ; i = i + 1
 9    jmp  .cond
10.end:
11    ret                 ; 戻り値は eax で返す

次の節では、レジスタ割り当てを実装します（tiny_regalloc.py）。

レジスタ割り当て

レジスタはメモリより桁違いに速いので、よく使う変数をできるだけレジスタに置くことが性能上重要です。しかし、レジスタの数は限られています（x86-64 の汎用レジスタは 16 個）。2 つの変数が同時に生存していなければ、同じレジスタを使い回せます。第 9 章の生存変数解析が、ここで役に立ちます。

干渉グラフとグラフ彩色

同時に生存する 2 つの変数は「干渉する」といいます。変数を節点とし、干渉する変数どうしを辺で結んだグラフを干渉グラフと呼びます。次の図は、最適化前の関数 sum の干渉グラフです。

隣り合う節点が同じ色にならないように、\(k\) 色で節点を塗り分けることをグラフの \(k\) 彩色と呼びます。色をレジスタとみなせば、レジスタ割り当ては干渉グラフの彩色問題になります。この図では n、s、i、%1 が互いに干渉しているので、4 つのレジスタが必要です。

s = %2 というコピー命令の s と %2 は干渉していません。コピー元とコピー先は同じ値なので、コピーの直後に両方が生存していても干渉とはみなさないからです。そこで s と %2 に同じレジスタを割り当てると、コピー命令は「同じレジスタへのコピー」となり、削除できます。干渉しない 2 つの変数を 1 つの節点にまとめて、このようにコピーを消すことをコピーの合併と呼びます。

グラフの彩色は一般に NP 困難ですが、Chaitin らの方法に代表される発見的なアルゴリズムで、実用上十分な結果が得られます。塗り分けられない場合は、一部の変数をメモリに置きます。これをスピルと呼びます。

線形走査法

グラフ彩色による割り当ては質が高い一方、干渉グラフの構築と彩色に時間がかかります。JIT コンパイラのようにコンパイル時間を短くしたい場合には、Poletto と Sarkar による線形走査法がよく使われます [Poletto1999]。本書でもこの方法を実装します。

線形走査法では、命令を一列に並べて通し番号を付け、各変数が生存する範囲を「最初の番号から最後の番号まで」の 1 つの区間（生存区間）で近似します。

tiny_regalloc.py（生存区間の計算）
32def live_intervals(func: Function) -> list[Interval]:
33    """各変数の生存区間を（1 つの連続した区間として）求める。"""
34    live_in, live_out = liveness(func)
35    first: dict[str, int] = {}
36    last: dict[str, int] = {}
37
38    def touch(var: str, pos: int) -> None:
39        first[var] = min(first.get(var, pos), pos)
40        last[var] = max(last.get(var, pos), pos)
41
42    for param in func.params:
43        touch(param, 0)
44    # 基本ブロックを並べた順に、命令へ通し番号 pos を付ける。
45    pos = 0
46    for block in func.blocks.values():
47        start = pos
48        for instr in block.instrs:
49            for var in used_vars(instr):
50                touch(var, pos)
51            dst = defined_var(instr)
52            if dst is not None:
53                touch(dst, pos)
54            pos += 1
55        for var in used_vars(block.terminator):
56            touch(var, pos)
57        # ブロックの入口・出口で生存している変数は、区間をそこまで広げる。
58        for var in live_in[block.label]:
59            touch(var, start)
60        for var in live_out[block.label]:
61            touch(var, pos)
62        pos += 1
63    intervals = [Interval(v, first[v], last[v]) for v in first]
64    return sorted(intervals, key=lambda i: (i.start, i.end))

生存区間を開始位置の順に処理し、空いているレジスタを割り当てていきます。処理中の区間の開始位置より前に終わった区間のレジスタは空きに戻します。空きがなければ、処理中の区間を含めて最も遠くまで生存する区間をスピルします。遠くまで生存する区間をメモリに追い出せば、その分長い間レジスタが空くからです。

tiny_regalloc.py（線形走査法）
67def linear_scan(intervals: list[Interval], num_registers: int) -> int:
68    """Poletto と Sarkar の線形走査法。使った退避領域の数を返す。"""
69    free = [f"r{i}" for i in range(num_registers)]
70    active: list[Interval] = []  # レジスタを持つ区間（end の昇順）
71    spill_count = 0
72
73    def spill_slot() -> str:
74        nonlocal spill_count
75        spill_count += 1
76        return f"[fp-{spill_count}]"
77
78    for current in intervals:
79        # 終わった区間のレジスタを解放する。
80        for old in list(active):
81            if old.end < current.start:
82                active.remove(old)
83                free.append(old.location)
84        if free:
85            current.location = free.pop(0)
86            active.append(current)
87        else:
88            # 最も遠くまで生きる区間をスピルする。
89            victim = active[-1]
90            if victim.end > current.end:
91                current.location = victim.location
92                victim.location = spill_slot()
93                active.remove(victim)
94                active.append(current)
95            else:
96                current.location = spill_slot()
97        active.sort(key=lambda i: i.end)
98    return spill_count

実行例

最適化した関数 sum を SSA 形式から戻し、4 個のレジスタ（r0 ～ r3）で割り当てた結果を示します。[fp-1] などはスタック上の退避領域です。

 5    i.2' = 1

11    branch %1, body1, endwhile1
12body1:

14    %3 = i.2 + 1
15    s.2' = %2
16    i.2' = %3

18endwhile1:
19    return s.2

24    [fp-2] = 1

26cond1:
27    [fp-1] = [fp-3]

（main 関数の出力は省略しています。）レジスタが 4 個あるにもかかわらず、3 つの変数がスピルされました。原因は 2 つあります。

  • SSA 形式から戻したときに追加した s.2' と s.2 のようなコピー命令の組が、ループ全体にわたる長い生存区間を作っています。生存区間を 1 つの連続した区間で近似しているため、実際には生存していない隙間（ループ内で値を使い終えてから次の代入までの間）も占有したことになっています。

  • コピー元とコピー先を同じ場所に割り当てる工夫（コピーの合併）をしていないため、コピー命令がそのまま残り、変数の数が減りません。

実用的な線形走査法では、生存区間を隙間のある複数の区間の集まりとして扱い、レジスタが足りなくなったら区間を途中で分割して、一部だけをスピルします。また、コピーで結ばれた区間には同じレジスタを優先して割り当てます。LLVM は、以前は線形走査法を使っていましたが、現在は区間の分割を積極的に行う貪欲法による割り当てを標準で使っています。-k オプションでレジスタの数を変えて、結果がどう変わるかを試してみてください。

本書の擬似的な機械では、命令の被演算子にメモリ（[fp-1] など）を直接書けるものとし、関数の呼び出しでレジスタの値は壊れないものとしています。実際の機械では、メモリにある値は演算の前にレジスタに読み込む必要があり、呼び出しをまたいで生存する変数は呼び出し規約に従って保存する必要があります。

ガベージコレクション

Tiny の配列はヒープに置かれ、どこからも参照されなくなったら回収する必要があります。本書の処理系は Python で書かれているので、この仕事は Python のメモリ管理に任せています。ここでは、言語処理系が自前でヒープを管理する場合の代表的なガベージコレクション（GC）の方式を、シミュレーション（gc_sim.py）で確かめます。GC の方式を網羅的に知りたい場合は [Jones2023] を参照してください。

GC では、局所変数や大域変数のように、プログラムが直接参照できる場所をルートと呼びます。ルートから参照をたどって到達できるオブジェクトは生きており、到達できないオブジェクトはごみです。

参照カウント

参照カウントは、各オブジェクトに「自分を指している参照の数」を持たせ、それが 0 になった時点でオブジェクトを解放する方式です。ごみになった瞬間に回収できるので、メモリの使用量が少なく、停止時間も短いという利点があります。CPython の基本的なメモリ管理は参照カウントです。

gc_sim.py（参照カウント）
14class RefCountHeap:
15    """各オブジェクトが「自分を指す参照の数」を持つヒープ。"""
16
17    def __init__(self) -> None:
18        self.refs: dict[str, list[str]] = {}  # オブジェクト → 参照先
19        self.count: dict[str, int] = {}
20
21    def new(self, name: str) -> None:
22        self.refs[name] = []
23        self.count[name] = 0
24
25    def increment(self, name: str) -> None:
26        self.count[name] += 1
27
28    def decrement(self, name: str) -> None:
29        self.count[name] -= 1
30        if self.count[name] == 0:
31            print(f"  {name} を解放")
32            for child in self.refs.pop(name):
33                self.decrement(child)
34            del self.count[name]
35
36    def add_ref(self, src: str, dst: str) -> None:
37        self.refs[src].append(dst)
38        self.increment(dst)

参照カウントの弱点は、循環参照を回収できないことです。C と D が互いに参照し合っていると、ルートからの参照がなくなっても、互いの参照によってカウントが 0 になりません。

1== 参照カウント
2ルートから A への参照を消す
3  A を解放
4  B を解放
5ルートから C への参照を消す
6  解放されずに残ったオブジェクト: ['C', 'D']

CPython は、この問題を補うために、循環参照を検出する GC を参照カウントと併用しています。

マーク & スイープ

マーク & スイープは、ルートから到達できるオブジェクトに印を付け（マーク）、印のないオブジェクトをすべて解放する（スイープ）方式です。到達可能性を直接調べるので、循環参照も回収できます。第 9 章の不要コード除去と同じ考え方です。

gc_sim.py（マーク & スイープ）
60def mark_and_sweep(refs: dict[str, list[str]], roots: list[str]) -> list[str]:
61    """ルートから到達できないオブジェクトを refs から取り除き、その名前を返す。"""
62    marked: set[str] = set()
63    stack = list(roots)
64    while stack:  # マーク: ルートからたどれるものに印を付ける
65        name = stack.pop()
66        if name not in marked:
67            marked.add(name)
68            stack.extend(refs[name])
69    garbage = [name for name in refs if name not in marked]
70    for name in garbage:  # スイープ: 印のないものを解放する
71        del refs[name]
72    return garbage

1== マーク & スイープ
2  解放: ['C', 'D', 'E']
3  残り: ['A', 'B']

E は B を参照していますが、E 自身はルートから到達できないので回収されます。

コピー GC

コピー GC は、ヒープを 2 つの領域に分け、生きているオブジェクトだけを一方の領域からもう一方の領域へ詰めてコピーする方式です。コピーの後は元の領域全体が空きになるので、解放の処理が要らず、空き領域が断片化しません。Cheney のアルゴリズム [Cheney1970] は、コピー先の領域自体を幅優先探索の待ち行列として使うことで、追加のメモリなしにコピーを行います。オブジェクトをコピーしたら元の場所に移動先（転送アドレス）を書いておき、同じオブジェクトを 2 度コピーしないようにします。

gc_sim.py（Cheney のコピー GC）
 93def copying_collect(from_space: list[Cell],
 94                    roots: list[int]) -> tuple[list[Cell], list[int]]:
 95    """Cheney のアルゴリズム。生きているオブジェクトを新しい領域に詰めて写す。
 96
 97    新しい領域と、書き換えたルート（新しいアドレス）を返す。
 98    """
 99    to_space: list[Cell] = []
100
101    def copy(address: int) -> int:
102        cell = from_space[address]
103        if cell.forward is None:
104            to_space.append(Cell(cell.name, list(cell.fields)))
105            cell.forward = len(to_space) - 1
106        return cell.forward
107
108    new_roots = [copy(r) for r in roots]
109    scan = 0
110    while scan < len(to_space):  # 写したオブジェクトの参照先を順に写す
111        cell = to_space[scan]
112        cell.fields = [copy(f) for f in cell.fields]
113        scan += 1
114    return to_space, new_roots

1== コピー GC
2  コピー前: 0:A->[3], 1:X->[], 2:Y->[1], 3:B->[4], 4:C->[0]
3  コピー後: 0:A->[1], 1:B->[2], 2:C->[0]  ルート=[0]

A、B、C だけが新しい領域の先頭に詰めて配置され、参照先のアドレスも新しい場所に書き換えられています。

世代別 GC

多くのプログラムでは、「ほとんどのオブジェクトは確保されてすぐに不要になる」という傾向があります（世代別仮説）。世代別 GC は、ヒープを若い世代と古い世代に分け、若い世代だけを頻繁に回収します。若い世代の回収にはコピー GC を使い、何度かの回収を生き延びたオブジェクトを古い世代に移します。Java の多くの GC や、CPython の循環参照を検出する GC が、世代の考え方を取り入れています。

まとめ

  • 実行時のメモリは、コード、静的データ、スタック、ヒープの領域に分けて使われます。

  • 関数呼び出しはスタックフレームで管理し、引数や戻り値の受け渡しは呼び出し規約で決まります。

  • レジスタ割り当ては干渉グラフの彩色問題として定式化でき、高速な近似として線形走査法があります。

  • コピーで結ばれた変数を同じレジスタに割り当てると、コピー命令を削除できます。

  • ガベージコレクションには、参照カウント、マーク & スイープ、コピー GC、世代別 GC などの方式があります。
