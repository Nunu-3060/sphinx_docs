11. アーキテクチャパターン

これまでの章では、関数、クラス、モジュールといった比較的小さな単位の設計を説明しました。この章では、システム全体をどのような部分に分け、部分どうしをどうつなぐかという、アーキテクチャ の設計を扱います。

11.1. アーキテクチャとは

ソフトウェアのアーキテクチャとは、システムの全体の構造と、その構造を決めた重要な判断のことです。どの部分に分けるか、部分どうしがどの向きに依存するか、データベースや画面などの外部とどこで接するか、といったことを決めます。

アーキテクチャは、あとから変更するのが最も難しい設計です。そのため、アーキテクチャを決めるときは、機能の要求だけでなく、次のような 品質特性 を考慮します。

品質特性

例

保守性

変更しやすいか、テストしやすいか

性能

応答の速さ、処理できる量

可用性

障害が起きても使い続けられるか

拡張性

利用者やデータが増えたときに対応できるか

セキュリティ

不正な利用を防げるか

品質特性は互いに対立することがあります（たとえば、性能を上げるための工夫が、保守性を下げることがあります）。アーキテクチャの設計とは、システムにとってどの品質特性が重要なのかを見極め、その釣り合いを取ることです。

この章では、よく知られたアーキテクチャのパターンを紹介します。例として、タスクの追加、完了、一覧の表示ができる小さな ToDo アプリを、2 つのパターンで実装します。

11.2. レイヤードアーキテクチャ

レイヤードアーキテクチャ は、システムを役割ごとの層（レイヤー）に分け、上の層が下の層だけを使うようにする構成です。最もよく知られたアーキテクチャのパターンで、一般に次の 4 つの層に分けます。

層

役割

プレゼンテーション層

利用者からの入力を受け取り、結果を表示します（画面、コマンドライン、Web API の入口など）。

アプリケーション層

ユースケース（利用者がシステムを使ってしたいこと）の手順を実装します。

ドメイン層

業務の概念と規則を表します。

インフラストラクチャ層

データベースへの保存や、外部のサービスとの通信など、技術的な詳細を扱います。

ToDo アプリをレイヤードアーキテクチャで実装すると、アプリケーション層の TaskService は、インフラストラクチャ層の TaskTable（データベースのテーブルの代わり）に直接依存します。

ch11_layered/application.py
from .domain import Task, TaskError
from .infrastructure import TaskRow, TaskTable


class TaskService:
    """タスクの追加、完了、一覧のユースケースです."""

    def __init__(self, table: TaskTable) -> None:
        self._table = table

    def add(self, title: str) -> Task:
        """タスクを追加します."""
        task = Task(self._table.next_id(), title)
        self._table.upsert(_to_row(task))
        return task

    def complete(self, task_id: int) -> Task:
        """タスクを完了にします."""
        row = self._table.select(task_id)
        if row is None:
            raise TaskError(f"タスク {task_id} はありません")
        task = _to_task(row)
        task.complete()
        self._table.upsert(_to_row(task))
        return task

    def list_all(self) -> list[Task]:
        """すべてのタスクを返します."""
        return [_to_task(row) for row in self._table.select_all()]


def _to_row(task: Task) -> TaskRow:
    """タスクをテーブルの行に変換します."""
    return {"task_id": task.task_id, "title": task.title, "done": task.done}


def _to_task(row: TaskRow) -> Task:
    """テーブルの行をタスクに変換します."""
    return Task(row["task_id"], row["title"], row["done"])

レイヤードアーキテクチャは分かりやすく、多くの開発者が知っているという利点があります。しかし、この構成では、業務の手順を表すアプリケーション層が、保存の方法という技術的な詳細に依存しています。そのため、次のような問題が起きやすくなります。

  • 保存先をデータベースから別のものに変えると、アプリケーション層も変更が必要になります。

  • アプリケーション層をテストするには、インフラストラクチャ層（本物のデータベースなど）を用意する必要があります。

  • テーブルの行と Task の変換（_to_row、_to_task）のような、保存の方法に関するコードがアプリケーション層に入り込みます。

ch11_layered のすべてのファイルは 11 章　アーキテクチャパターン で閲覧できます。サンプルコード一覧 の zip ファイルを展開し、examples フォルダーで python -m ch11_layered.main と実行すると、動作を確認できます。

11.3. ヘキサゴナルアーキテクチャ

ヘキサゴナルアーキテクチャ は、A. Cockburn が提唱した構成で、ポートとアダプター とも呼ばれます。アプリケーションの中心（ドメインとユースケース）を外部の技術から切り離し、外部とのやり取りは、すべて「ポート」と「アダプター」を通して行います。

要素

説明

ポート

アプリケーションの中心が、外部とやり取りするために定めたインターフェースです。アプリケーションの中心の側で定義します。

アダプター

ポートと、具体的な技術（データベース、ファイル、画面、Web API など）をつなぐ部品です。

駆動する側のアダプター

外部からアプリケーションを呼び出すアダプターです（コマンドライン、Web API の入口、テストなど）。

駆動される側のアダプター

アプリケーションから呼び出されるアダプターです（データベース、メールの送信など）。

ToDo アプリでは、保存先のポートを TaskRepository として定義します。

ch11_hexagonal/ports.py
class TaskRepository(Protocol):
    """タスクの保存先のポートです（駆動される側）."""

    def next_id(self) -> int:
        """次に使う ID を返します."""
        ...

    def save(self, task: Task) -> None:
        """タスクを保存します（同じ ID があれば上書きします）."""
        ...

    def get(self, task_id: int) -> Task | None:
        """ID に一致するタスクを返します. なければ None を返します."""
        ...

    def list_all(self) -> list[Task]:
        """すべてのタスクを ID の順に返します."""
        ...

ユースケースを実装する TaskService は、このポートだけに依存します。ユースケースの手順を実装するこのようなクラスを アプリケーションサービス と呼びます（ドメインのモデリング で詳しく説明します）。レイヤードアーキテクチャの例とは異なり、保存の方法に関するコードは含まれていません。

ch11_hexagonal/service.py
from .domain import Task, TaskError
from .ports import TaskRepository


class TaskService:
    """タスクの追加、完了、一覧のユースケースです."""

    def __init__(self, repository: TaskRepository) -> None:
        self._repository = repository

    def add(self, title: str) -> Task:
        """タスクを追加します."""
        task = Task(self._repository.next_id(), title)
        self._repository.save(task)
        return task

    def complete(self, task_id: int) -> Task:
        """タスクを完了にします."""
        task = self._repository.get(task_id)
        if task is None:
            raise TaskError(f"タスク {task_id} はありません")
        task.complete()
        self._repository.save(task)
        return task

    def list_all(self) -> list[Task]:
        """すべてのタスクを返します."""
        return self._repository.list_all()

保存先のアダプターとして、メモリに保存する InMemoryTaskRepository と、JSON ファイルに保存する JsonFileTaskRepository を用意します。どちらを使うかは、コンポジションルートの main.py で決めます。

ch11_hexagonal/main.py
def run(repository: TaskRepository) -> None:
    """指定した保存先でアプリケーションを組み立て、コマンドを実行します."""
    adapter = TextCommandAdapter(TaskService(repository))
    for command in COMMANDS:
        print(f"> {command}")
        print(adapter.handle(command))


def main() -> None:
    """メモリと JSON ファイルの 2 種類の保存先で実行します."""
    print("=== メモリに保存 ===")
    run(InMemoryTaskRepository())

    print("=== JSON ファイルに保存 ===")
    with tempfile.TemporaryDirectory() as directory:
        path = Path(directory) / "tasks.json"
        run(JsonFileTaskRepository(path))
        print(f"--- {path.name} の内容 ---")
        print(path.read_text(encoding="utf-8"))


if __name__ == "__main__":
    main()

examples フォルダーで python -m ch11_hexagonal.main と実行すると、同じ TaskService が、2 種類の保存先で同じように動くことを確認できます。

ヘキサゴナルアーキテクチャの利点は、次のとおりです。

  • アプリケーションの中心を、データベースや画面を用意せずにテストできます（メモリのアダプターを使います）。

  • 保存先や画面の技術を変えても、アプリケーションの中心は変更しません。

  • 技術の選択（どのデータベースを使うかなど）を、開発の後半まで先送りできます。

一方で、ポートの定義とアダプターの分だけコードが増えます。外部とのやり取りがほとんどない小さなプログラムでは、この構成は大げさです。

11.4. クリーンアーキテクチャ

クリーンアーキテクチャ は、R. C. Martin が、ヘキサゴナルアーキテクチャなどの複数のアーキテクチャに共通する考え方をまとめたものです。システムを同心円状の層で表し、依存は必ず外側から内側へ向かう（内側の層は外側の層について何も知らない）という規則（依存性のルール）を定めています。

層（内側から順に）

役割

エンティティ

業務の最も基本的な概念と規則です。アプリケーションが変わっても変わらないものです。

ユースケース

アプリケーションに固有の業務の手順です。

インターフェースアダプター

ユースケースで扱いやすい形式と、外部の技術で扱いやすい形式の間で、データを変換します。

フレームワークとドライバー

Web フレームワーク、データベース、画面などの、具体的な技術です。

内側の層が外側の層の機能（データベースへの保存など）を使う必要がある場合は、SOLID 原則 の依存性逆転の原則を使います。内側の層にインターフェースを定義し、外側の層がそれを実装します。ヘキサゴナルアーキテクチャのポートとアダプターと同じ考え方です。

ヘキサゴナルアーキテクチャとクリーンアーキテクチャは、用語や層の数は異なりますが、「業務の規則を中心に置き、技術的な詳細を外側に追い出す」「依存を中心に向ける」という点で共通しています。

11.5. MVC

MVC（Model-View-Controller）は、利用者とやり取りするアプリケーションを、次の 3 つの役割に分ける構成です。もともとは T. Reenskaug が Smalltalk の GUI のために考案したものです。

役割

説明

Model

アプリケーションのデータと、業務の規則です。

View

Model の内容を、利用者に表示します。

Controller

利用者の入力を受け取り、Model の操作や View の切り替えを行います。

MVC は、主に「画面の周り」の構成を決めるパターンです。Web アプリケーションのフレームワークの多くは、MVC、またはその派生の構成を採用しています。たとえば Django は、同様の役割分担を Model、Template、View と呼んでいます（Django の View は、MVC の Controller に近い役割です）。

MVC の Model に業務の規則もデータベースへの保存もすべて詰め込むと、Model が肥大化します。規模が大きくなったら、Model の部分をヘキサゴナルアーキテクチャのように、さらに分けることを検討します。

11.6. パイプとフィルター

パイプとフィルター は、データを処理する部品（フィルター）を、データの流れ（パイプ）でつなぐ構成です。各フィルターは、入力を受け取り、変換して出力するだけで、前後のフィルターのことを知りません。UNIX のコマンドを | でつなぐ使い方が代表的な例です。

Python では、ジェネレーターを使うと、パイプとフィルターを簡潔に書けます。

from collections.abc import Iterable, Iterator

def read_lines(path: str) -> Iterator[str]:
    with open(path, encoding="utf-8") as file:
        yield from file

def strip_comments(lines: Iterable[str]) -> Iterator[str]:
    for line in lines:
        if not line.startswith("#"):
            yield line

def to_upper(lines: Iterable[str]) -> Iterator[str]:
    for line in lines:
        yield line.upper()

# フィルターを組み合わせる。データは 1 行ずつ流れる
for line in to_upper(strip_comments(read_lines("input.txt"))):
    print(line, end="")

フィルターの追加、削除、並べ替えが容易なので、データの変換や集計の処理（データを抽出（Extract）、変換（Transform）し、別のシステムに格納（Load）する ETL の処理など）に向いています。一方、利用者とのやり取りが多い処理には向きません。

11.7. イベント駆動アーキテクチャ

イベント駆動アーキテクチャ は、「注文が確定した」「在庫が不足した」といった出来事（イベント）を発行し、そのイベントに関心のある部品が反応して処理を行う構成です。デザインパターン の Observer パターンを、システム全体の規模に広げたものと考えられます。

イベントを発行する側は、誰が反応するのかを知らないので、部品どうしの結合度を低くできます。大規模なシステムでは、イベントをメッセージキューなどの仕組みで非同期に届け、処理の負荷を分散させることもあります。

一方で、処理の流れがイベントの発行と購読に分散するので、全体の流れを追いにくくなります。また、非同期に届く場合は、イベントの順序や重複への対処も必要になります。

11.8. モノリスとマイクロサービス

システム全体を 1 つのアプリケーションとして作り、1 つの単位で配置（デプロイ）する構成を モノリス と呼びます。一方、システムを独立して配置できる小さなサービスに分け、ネットワークを通して連携させる構成を マイクロサービス と呼びます。

モノリス

マイクロサービス

開発の始めやすさ

すぐに始められます。

サービスの分け方や、サービス間の通信の設計が必要です。

配置

全体をまとめて配置します。

サービスごとに独立して配置できます。

拡張性

全体をまとめて増強します。

負荷の高いサービスだけを増強できます。

障害の影響

一部の不具合が、全体に影響することがあります。

影響を 1 つのサービスに閉じ込めやすくなります。

運用の負担

小さく済みます。

大きくなります（監視、ネットワークの障害への対処、データの整合性の維持が必要です）。

マイクロサービスは、大きな組織で、複数のチームがそれぞれのサービスを独立して開発・配置したい場合に効果を発揮します。しかし、運用の負担は大きく、サービスの分け方を誤ると、変更のたびに複数のサービスを同時に修正する羽目になります。

多くの場合、まずはモノリスで作り、その内部を機能ごとのモジュールにきちんと分けておく（モジュラーモノリスと呼ばれます）のが現実的です。モジュールの境界が健全であれば、必要になったときに、モジュールを独立したサービスとして切り出せます。

11.9. アーキテクチャの選び方

どのアーキテクチャが最適かは、システムの規模、寿命、チームの状況、重視する品質特性によって異なります。次の表は、選び方の目安です。

状況

候補

小さなスクリプト、使い捨てのツール

特別なアーキテクチャは不要です。関数に分ければ十分です。

画面が中心で、業務の規則が少ないアプリケーション

フレームワークの標準の構成（MVC など）、レイヤードアーキテクチャ

業務の規則が複雑で、長く保守するアプリケーション

ヘキサゴナルアーキテクチャ、クリーンアーキテクチャ（ドメインのモデリング の手法と組み合わせる）

データの変換や集計が中心の処理

パイプとフィルター

多くの部品が、出来事に応じて独立して反応するシステム

イベント駆動アーキテクチャ

複数のチームが独立して開発・配置する大規模なシステム

マイクロサービス（まずはモジュラーモノリスから）

アーキテクチャを決めたら、その理由を記録しておきます。記録の方法は 設計の記録と伝達 で説明します。

11.10. まとめ

  • アーキテクチャは、システム全体の構造と、その構造を決めた重要な判断です。

  • レイヤードアーキテクチャは分かりやすい反面、業務の手順が技術的な詳細に依存しやすくなります。

  • ヘキサゴナルアーキテクチャとクリーンアーキテクチャは、業務の規則を中心に置き、依存を中心に向けます。

  • アーキテクチャは、システムの規模や重視する品質特性に合わせて選びます。
