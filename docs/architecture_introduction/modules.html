9. モジュールとパッケージの設計

プログラムが大きくなると、1 つのファイルにすべてのコードを書くことはできなくなります。この章では、コードをモジュール（ファイル）とパッケージ（フォルダー）に分けるときの考え方と、モジュールの間の依存関係を健全に保つ方法を説明します。

9.1. 公開するものと隠すもの

モジュールは、良い設計の指標 で説明した情報隠蔽の単位です。モジュールの中身は、ほかのモジュールから使われることを想定した 公開の部分 と、モジュールの内部だけで使う 非公開の部分 に分けます。公開の部分を小さく保つほど、モジュールの内部を自由に変更できます。

Python では、次の慣習で公開と非公開を区別します。

方法

意味

名前を _ で始める

モジュールの内部用であることを示します。_yen のような関数は、ほかのモジュールから使わないでください、という意図を表します。言語として禁止されるわけではありません。

__all__ を定義する

from モジュール import * で読み込まれる名前の一覧です。モジュールの公開の範囲を明示する役割もあり、ドキュメントの生成ツールなどもこれを参照します。

__init__.py で名前を読み込む

パッケージの利用者向けに、パッケージの中のモジュールから公開する名前を読み込み、パッケージ名.名前 で使えるようにします。利用者は、パッケージ内部のモジュール構成を知らずに済みます。

ch09_circular_good パッケージの __init__.py では、公開する 3 つの名前を読み込み、__all__ に列挙しています。

ch09_circular_good/__init__.py
from .customers import Customer
from .orders import Order
from .reports import total_spent

__all__ = ["Customer", "Order", "total_spent"]

このパッケージの利用者は、from ch09_circular_good import Customer のように書けます。あとでパッケージ内部のモジュールの分け方を変えても、__init__.py の読み込みを直せば、利用者のコードは変更せずに済みます。

9.2. パッケージの分け方

コードをパッケージに分ける方法には、大きく 2 つの考え方があります。

分け方

例

特徴

技術の種類別

models/、views/、services/、repositories/

小さなアプリケーションでは分かりやすい構成です。しかし、1 つの機能を変更するたびに、すべてのパッケージにまたがってファイルを修正することになります。

機能別

orders/、customers/、inventory/

1 つの機能に関するコードが 1 つのパッケージにまとまるので、変更の影響がそのパッケージに収まりやすくなります。機能どうしの依存関係も、パッケージの依存関係として見えるようになります。

小さなアプリケーションは技術の種類別で始めても構いませんが、機能が増えてきたら、機能別に分けることを検討します。機能別のパッケージの中で、さらに技術の種類別にモジュールを分けることもできます。

9.3. 循環 import

モジュール A がモジュール B を import し、モジュール B もモジュール A を import している状態を、循環 import と呼びます。循環 import は、実行時のエラーの原因になるだけでなく、2 つのモジュールが互いに依存していて、一方だけを理解したり、テストしたり、再利用したりできない状態を表しています。

次の例では、顧客のモジュール customers が注文のクラス Order を、注文のモジュール orders が顧客のクラス Customer を、互いに import しています。

ch09_circular_bad/customers.py（悪い例）
from dataclasses import dataclass, field

from .orders import Order  # orders も customers を import している


@dataclass
class Customer:
    """顧客です. 自分の注文の一覧を持ちます."""

    name: str
    orders: list[Order] = field(default_factory=list)

    def total_spent(self) -> int:
        """これまでの注文の合計金額を返します."""
        return sum(order.amount for order in self.orders)
ch09_circular_bad/orders.py（悪い例）
from dataclasses import dataclass

from .customers import Customer  # customers も orders を import している


@dataclass
class Order:
    """注文です. 注文した顧客を持ちます."""

    order_id: str
    amount: int
    customer: Customer

    def label(self) -> str:
        """表示用のラベルを返します."""
        return f"{self.order_id}（{self.customer.name} 様）"

これを実行すると、次のエラーになります（表示を一部省略しています）。

$ python -m ch09_circular_bad.main
ImportError: cannot import name 'Customer' from partially initialized module
'ch09_circular_bad.customers' (most likely due to a circular import)

customers の読み込みの途中で orders の読み込みが始まり、orders は、まだ Customer が定義されていない（初期化の途中の）``customers`` から Customer を読み込もうとして失敗します。

依存関係を図にすると、次のようになります。customers と orders の間で、依存の矢印が循環しています。

9.3.1. 循環 import の解消の方法

循環 import を解消するには、次のような方法があります。上にあるものほど、根本的な解決になります。

  1. 依存の向きを決め直します。 どちらのモジュールがより基本的な概念なのかを考え、依存を一方向にそろえます。両方に依存する処理は、第 3 のモジュールに移します。

  2. 共通の部分を別のモジュールに抜き出します。 2 つのモジュールが共通して使うクラスや定数を、両方から依存される新しいモジュールに移します。

  3. 型ヒントのためだけの import を分けます。 型ヒントにだけ使うクラスは、if typing.TYPE_CHECKING: の中で import すると、実行時には読み込まれなくなります。ただし、依存関係そのものは残ります。

  4. 関数の中で import します。 実行時の読み込みの順序の問題は避けられますが、依存関係が見えにくくなるので、最後の手段にします。

ch09_circular_good では、1 の方法を使いました。顧客は注文を知らなくても成り立つ基本的な概念なので、Customer から注文の一覧を取り除きます。顧客ごとの合計金額を求める処理は、顧客と注文の両方に依存するので、新しいモジュール reports に移します。

ch09_circular_good/customers.py
from dataclasses import dataclass


@dataclass(frozen=True)
class Customer:
    """顧客です. 注文の一覧は持ちません."""

    customer_id: str
    name: str
ch09_circular_good/reports.py
from collections.abc import Iterable

from .customers import Customer
from .orders import Order


def total_spent(customer: Customer, orders: Iterable[Order]) -> int:
    """顧客のこれまでの注文の合計金額を返します."""
    return sum(order.amount for order in orders
               if order.customer.customer_id == customer.customer_id)


def format_total(customer: Customer, orders: Iterable[Order]) -> str:
    """顧客の合計金額を表示用の文字列にします."""
    return f"{customer.name} 様: {_yen(total_spent(customer, orders))}"


def _yen(amount: int) -> str:
    """金額を円の表記にします（モジュールの内部だけで使います）."""
    return f"{amount:,} 円"

書き換えたあとの依存関係は、次のように一方向になります（破線は、main が __init__.py を通して Customer と Order を使っていることを表します）。

2 つのパッケージのすべてのファイルは 9 章　モジュールとパッケージの設計 で閲覧できます。サンプルコード一覧 の zip ファイルを展開し、examples フォルダーで次のように実行します。

$ python -m ch09_circular_good.main

9.4. 依存関係の原則

    1. Martin は、パッケージ（コンポーネント）の間の依存関係について、次の 3 つの原則を挙げています。

原則

内容

非循環依存関係の原則（ADP）

パッケージの依存関係のグラフに、循環があってはなりません。

安定依存の原則（SDP）

依存は、安定している（変更されにくい）パッケージの方向に向けます。

安定度・抽象度等価の原則（SAP）

安定しているパッケージほど、抽象的であるべきです。

安定依存の原則の「安定している」とは、変更しにくいという意味です。多くのパッケージから依存されているパッケージは、変更するとその影響が多くのパッケージに及ぶので、簡単には変更できません。頻繁に変更したいパッケージが、このような変更しにくいパッケージから依存されていると、変更のたびに多くの影響が出ます。そこで、変更されやすいパッケージが、変更されにくいパッケージに依存するように、依存の向きをそろえます。

9.4.1. 安定度と抽象度の指標

Martin は、これらの原則を確かめるための指標も提案しています。あるパッケージについて、次の値を数えます。

  • \(C_a\)（求心性の結合）: このパッケージの中のクラスに依存している、パッケージの外のクラスの数

  • \(C_e\)（遠心性の結合）: パッケージの外のクラスに依存している、このパッケージの中のクラスの数

  • \(N_c\): このパッケージのクラスの数

  • \(N_a\): このパッケージの抽象クラス（インターフェース）の数

これらを使って、不安定度 \(I\) と 抽象度 \(A\) を次のように定義します。

\[I = \frac{C_e}{C_a + C_e}, \qquad A = \frac{N_a}{N_c}\]

\(I\) は 0 から 1 の値を取り、0 に近いほど安定しています（ほかから依存されるだけで、自分は何にも依存しない）。\(A\) も 0 から 1 の値を取り、1 に近いほど抽象的です。

安定度・抽象度等価の原則によれば、安定したパッケージ（\(I\) が 0 に近い）は抽象的（\(A\) が 1 に近い）であるべきで、不安定なパッケージ（\(I\) が 1 に近い）は具体的（\(A\) が 0 に近い）であってよいことになります。つまり、理想的なパッケージは、\(A + I = 1\) の直線（主系列）の近くにあります。主系列からの距離 \(D\) は、次の式で求めます。

\[D = |A + I - 1|\]

位置

\((I, A)\)

意味

苦痛の領域

\((0, 0)\) の付近

多くのパッケージから依存されているのに、具体的な実装ばかりのパッケージです。変更すると多くの影響が出るのに、抽象を通して拡張することもできません。

無用の領域

\((1, 1)\) の付近

抽象的なのに、どこからも依存されていないパッケージです。使われていないインターフェースの集まりです。

主系列

\(A + I = 1\) の付近

安定度と抽象度の釣り合いが取れたパッケージです。

たとえば、\(C_a = 3\)、\(C_e = 1\) のパッケージの不安定度は \(I = 1 / (3 + 1) = 0.25\) です。このパッケージのクラスが 4 つで、そのうち 2 つが抽象クラスなら \(A = 2 / 4 = 0.5\) なので、\(D = |0.5 + 0.25 - 1| = 0.25\) になります。

Python で抽象クラスを数える場合は、abc.ABC を継承したクラスと typing.Protocol を抽象クラスとみなすとよいでしょう。これらの指標を正確に計算する必要はありませんが、「多くのモジュールから import されているモジュールが、具体的な実装や外部のライブラリに強く依存していないか」を確かめる視点として役立ちます。

9.5. まとめ

  • モジュールの公開の部分は小さく保ち、非公開の名前は _ で始めます。

  • パッケージは、機能が増えてきたら機能別に分けることを検討します。

  • 循環 import は、依存の向きを決め直して解消します。

  • 依存は、安定した（変更されにくい）モジュールの方向に向けます。

  • 安定したモジュールほど、抽象的にします。
