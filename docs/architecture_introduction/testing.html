13. テストと設計

テストは、プログラムが正しく動くことを確かめるだけのものではありません。テストを書こうとすると、コードの設計の問題が浮かび上がります。この章では、テストしやすい設計と、テストで依存オブジェクトの代わりに使うテストダブルを説明します。

13.1. テストしやすい設計は良い設計

ある関数の単体テストを書こうとして、次のような状況に陥ることがあります。

  • テストの準備として、データベースを用意し、データを投入しなければなりません。

  • 結果が実行した日時によって変わるので、期待する値を決められません。

  • 関数が結果を画面に表示するだけなので、結果を確かめられません。

  • 関数の中で別の大きな処理が呼ばれていて、その準備だけで数十行かかります。

これらはいずれも、良い設計の指標 で説明した結合度の高さや、関数の設計 で説明した副作用の混在が原因です。つまり、テストが書きにくいのは、設計の問題のサイン です。逆に、依存するものを外から渡せるようにし、副作用を分離すれば、テストは書きやすくなり、同時に設計も良くなります。

テストしにくいコードの特徴と、その対処をまとめると次のようになります。

テストしにくくする原因

対処

関数の中で現在時刻や乱数を直接取得している

時計や乱数の生成器を引数などで渡します（依存関係の管理）。

関数の中でファイル、データベース、ネットワークに直接アクセスしている

アクセスする部分をインターフェースの背後に隠し、テストでは差し替えます。

計算の結果を表示するだけで、値を返さない

計算と表示を分けます（関数の設計）。

グローバル変数や Singleton の状態に依存している

状態を引数で受け取るようにします。

1 つの関数が多くのことをしている

関数を分割し、それぞれをテストします。

13.2. 例: 会計の処理

17 時から 19 時の間は 10% 割引し、会計が済んだら領収書をメールで送る処理を考えます。次の実装は、現在時刻を直接取得し、メールも直接送っています（ここでは表示で代用しています）。

ch13_testing/checkout.py（テストしにくい例）
def hard_to_test_checkout(email: str, amount: int) -> int:
    """会計を行い、支払額を返します（テストしにくい例）.

    現在時刻を直接取得し、メールの送信も直接行う（ここでは表示で代用）
    ため、テストの結果が実行する時刻によって変わり、送信内容も確認できません。
    """
    now = datetime.now().time()
    if HAPPY_HOUR_START <= now < HAPPY_HOUR_END:
        amount = int(amount * (1 - HAPPY_HOUR_DISCOUNT_RATE))
    print(f"[mail] to={email}: お支払い金額は {amount:,} 円です。")
    return amount

この関数の割引が正しく動くかを確かめるには、17 時から 19 時の間にテストを実行するしかありません。また、どのような内容のメールが送られたのかを、テストで確かめることもできません。

時計と領収書の送信先を、コンストラクターで受け取るように書き直します（依存関係の管理 の依存性注入です）。時計の引数には、既定値として datetime.now を指定しているので、本番のコードでは時計を渡す必要はありません。

ch13_testing/checkout.py（テストしやすい例）
class ReceiptSender(Protocol):
    """領収書の送信先のインターフェースです."""

    def send(self, email: str, body: str) -> None:
        ...


class CheckoutService:
    """会計のサービスです. 時計と領収書の送信先を外から受け取ります."""

    def __init__(self, sender: ReceiptSender,
                 clock: Callable[[], datetime] = datetime.now) -> None:
        self._sender = sender
        self._clock = clock

    def is_happy_hour(self) -> bool:
        """現在が割引の時間帯かどうかを返します."""
        return HAPPY_HOUR_START <= self._clock().time() < HAPPY_HOUR_END

    def checkout(self, email: str, amount: int) -> int:
        """会計を行い、支払額を返します."""
        if amount < 0:
            raise ValueError(f"amount must not be negative: {amount}")
        if self.is_happy_hour():
            amount = int(amount * (1 - HAPPY_HOUR_DISCOUNT_RATE))
        self._sender.send(email, f"お支払い金額は {amount:,} 円です。")
        return amount

13.3. テストダブル

テストのときに、本物の依存オブジェクトの代わりに使うオブジェクトを テストダブル と呼びます。映画の撮影で、俳優の代わりに危険な場面を演じるスタントダブルになぞらえた呼び名です。G. Meszaros は、テストダブルを目的によって次の 5 種類に分類しています。

種類

説明

例

ダミー

引数を埋めるためだけに渡し、実際には使われないオブジェクトです。

使われない引数に渡す None やオブジェクト

スタブ

呼ばれたら、あらかじめ決めた値を返します。テストの対象に、決まった入力を与えるために使います。

常に 17 時を返す時計

スパイ

呼ばれた内容を記録します。テストの対象が、依存オブジェクトをどう呼んだかをあとで確かめるために使います。

送信した内容をリストに記録する送信先

モック

期待する呼ばれ方をあらかじめ設定しておき、そのとおりに呼ばれたかを検証します。

unittest.mock.Mock

フェイク

本物と同じように動作する、簡易的な実装です。

メモリ上に保存するリポジトリ（ドメインのモデリング の InMemoryOrderRepository）

実際の会話では、これらをまとめて「モック」と呼ぶこともありますが、違いを知っておくと、テストの意図を正確に伝えられます。

会計の処理のテストでは、スタブ、スパイ、モックを使います。時計のスタブは、固定の時刻を返す関数です。

ch13_testing/test_checkout.py（スタブとスパイ）
def fixed_clock(hour: int, minute: int = 0) -> datetime:
    """指定した時刻の datetime を返します（スタブの時計の中身）."""
    return datetime(2026, 4, 1, hour, minute)


class SpyReceiptSender:
    """送信した内容を記録するだけの ReceiptSender です（スパイ）."""

    def __init__(self) -> None:
        self.sent: list[tuple[str, str]] = []

    def send(self, email: str, body: str) -> None:
        self.sent.append((email, body))

割引の境界（16 時 59 分、17 時 0 分、19 時 0 分）でのテストは、次のようになります。時刻を自由に決められるので、境界の値を確実にテストできます。

ch13_testing/test_checkout.py（割引の境界のテスト）
def make_service(self, hour: int, minute: int = 0,
                 sender: ReceiptSender | None = None) -> CheckoutService:
    """時刻を固定した CheckoutService を作ります."""
    return CheckoutService(sender or SpyReceiptSender(),
                           clock=lambda: fixed_clock(hour, minute))

def test_no_discount_before_happy_hour(self) -> None:
    service = self.make_service(16, 59)
    self.assertEqual(service.checkout("a@example.com", 1000), 1000)

def test_discount_at_start_of_happy_hour(self) -> None:
    service = self.make_service(17, 0)
    self.assertEqual(service.checkout("a@example.com", 1000), 900)

def test_no_discount_at_end_of_happy_hour(self) -> None:
    service = self.make_service(19, 0)
    self.assertEqual(service.checkout("a@example.com", 1000), 1000)

領収書の内容は、スパイで記録した内容を確かめるか、unittest.mock.Mock で呼ばれ方を検証します。Mock(spec=ReceiptSender) のように spec にインターフェースを指定すると、そのインターフェースに存在しないメソッドを呼んだときにエラーになるので、メソッド名の誤りに気付けます。

ch13_testing/test_checkout.py（スパイとモック）
def test_receipt_is_recorded_by_spy(self) -> None:
    sender = SpyReceiptSender()
    service = self.make_service(18, sender=sender)
    service.checkout("a@example.com", 2000)
    self.assertEqual(
        sender.sent,
        [("a@example.com", "お支払い金額は 1,800 円です。")])

def test_receipt_is_sent_once_with_mock(self) -> None:
    sender = Mock(spec=ReceiptSender)
    service = self.make_service(12, sender=sender)
    service.checkout("a@example.com", 2000)
    sender.send.assert_called_once_with(
        "a@example.com", "お支払い金額は 2,000 円です。")

テストは、examples フォルダーで次のように実行します。

$ python -m unittest ch13_testing.test_checkout -v

checkout.py、test_checkout.py

13.3.1. モックの使いすぎに注意する

モックは便利ですが、使いすぎると、テストが「どのメソッドが、どの順序で呼ばれたか」という実装の詳細に依存するようになります。そのようなテストは、振る舞いを変えないリファクタリングをしただけで失敗してしまいます。

テストでは、できるだけ 戻り値や、最終的な状態 を確かめます。依存オブジェクトの呼ばれ方を確かめるのは、メールの送信のように、呼ばれること自体が求められている振る舞いである場合に限ります。また、状態を持つ依存オブジェクト（リポジトリなど）には、モックよりもフェイクを使うと、テストが実装の詳細に依存しにくくなります。

13.4. テストの種類と割合

テストは、その対象の範囲によって、大きく次の 3 種類に分けられます。

種類

対象

実行の速さ

推奨される数

単体テスト

1 つの関数やクラス

速い

多い

結合テスト

複数の部品の組み合わせ、データベースなどの外部との接続

中程度

中程度

E2E テスト

システム全体を、利用者と同じ操作で動かす

遅い

少ない

  1. Cohn は、この割合を三角形で表し、テストピラミッド と呼びました。速くて安定した単体テストを土台として数多く用意し、遅くて壊れやすい E2E テストは、重要な操作の確認に絞るという考え方です。

ヘキサゴナルアーキテクチャのように、業務の規則を外部の技術から切り離しておくと、業務の規則のほとんどを単体テストで確かめられます。アダプター（データベースへの保存など）は、結合テストで確かめます。

13.5. テスト駆動開発

テスト駆動開発（Test-Driven Development、TDD）は、K. Beck が広めた開発の手法で、コードを書く前にテストを書きます。次の 3 つの段階を短い周期で繰り返します。

段階

内容

レッド

実現したい振る舞いを確かめるテストを 1 つ書きます。まだ実装がないので、テストは失敗します。

グリーン

テストが成功する、最も単純なコードを書きます。

リファクタリング

テストが成功する状態を保ったまま、重複を取り除き、設計を整えます。

テストを先に書くと、コードを書く前に「この関数を、どのように呼び出して使いたいか」を考えることになります。利用する側の視点で関数の名前や引数を決めることになるので、自然と使いやすく、テストしやすい設計になります。

TDD を常に厳密に実践する必要はありませんが、「テストしにくいと感じたら、設計を見直す」という姿勢は、どのような開発にも役立ちます。

13.6. まとめ

  • テストが書きにくいのは、設計の問題のサインです。

  • 時計、乱数、外部とのやり取りは、外から渡せるようにします。

  • テストダブルには、ダミー、スタブ、スパイ、モック、フェイクがあります。

  • テストでは、できるだけ戻り値や最終的な状態を確かめ、モックの使いすぎを避けます。

  • 速い単体テストを数多く用意し、遅いテストは重要なものに絞ります。
