2. ソフトウェア設計とは

この章では、ソフトウェアの設計とは何を決めることなのか、なぜ設計が必要なのかを説明します。

2.1. 設計とは何を決めることか

ソフトウェアの設計とは、プログラムを どのような部品に分け、部品どうしをどのようにつなぐか を決めることです。部品には、関数、クラス、モジュール、パッケージ、さらにはサーバーやデータベースといった単位があります。

同じ仕様を満たすプログラムでも、部品の分け方やつなぎ方は無数にあります。どの分け方でも、プログラムは同じように動きます。違いが現れるのは、プログラムを 読むとき と 変更するとき です。

2.2. 設計の目的

設計の目的は、主に次の 3 つです。どれも、プログラムが「今動くかどうか」ではなく、「これから先も扱い続けられるかどうか」に関わるものです。

目的

説明

変更しやすさ

仕様の変更や機能の追加に、少ない修正で対応できること。修正の影響が、予想できる範囲に収まること。

理解しやすさ

コードを読んだ人が、何をしているのか、どこを直せばよいのかを短い時間で理解できること。コードは書かれる回数よりも読まれる回数のほうがはるかに多いため、読みやすさは重要です。

テストしやすさ

部品を単独で動かして、正しく動くことを確かめられること。テストしやすいコードは、変更したときに壊れていないことを確認しやすいので、変更しやすさにもつながります。

ソフトウェアは、一度作って終わりになることはほとんどありません。使われ続けるソフトウェアには、必ず変更の要求が寄せられます。設計は、その変更にかかる費用を小さくするための活動です。

2.3. 複雑さとの戦い

変更しにくいプログラムの根本的な原因は、複雑さ です。F. P. Brooks は論文「銀の弾などない」で、ソフトウェアの複雑さを 2 種類に分けました。

種類

説明

本質的な複雑さ

解決したい問題そのものが持つ複雑さです。たとえば、税率が商品の種類によって異なるという業務の規則は、どう実装してもなくなりません。

偶有的な複雑さ

問題の解き方（実装の仕方）によって生じる複雑さです。役割の混ざった関数、どこからでも書き換えられる変数、意味の分からない名前などが生む複雑さです。

本質的な複雑さは取り除けませんが、偶有的な複雑さは設計によって減らせます。また、本質的な複雑さも、適切に部品に分ければ、一度に考えなければならない量を減らせます。設計とは、複雑さを「分けて、隠す」ことだと言えます。

2.4. 技術的負債

急いで機能を追加するために、設計を犠牲にした実装をすることがあります。このような実装は、あとで変更するときに余分な手間を生みます。この余分な手間を、借金の利息になぞらえて 技術的負債 と呼びます。

技術的負債は、必ずしも悪いものではありません。期限に間に合わせるために、意識して負債を抱える判断もあり得ます。問題になるのは、負債を抱えていることに気付かないまま、利息（変更のたびにかかる余分な手間）を払い続けることです。本資料で扱う設計の原則や リファクタリング は、負債に気付き、返済するための道具でもあります。

2.5. 例: 1 本のスクリプトと分割した構成

具体的な例で考えます。次のスクリプトは、CSV 形式の売上データを読み込み、カテゴリごとの売上を集計して表示します。

ch02_report_script.py（悪い例）
import csv
import io

SALES_CSV = """date,category,product,price,quantity
2026-04-01,food,apple,120,10
2026-04-01,drink,tea,150,4
2026-04-02,food,bread,200,3
2026-04-02,drink,coffee,300,5
2026-04-03,food,apple,120,-1
2026-04-03,goods,pen,100,7
"""

totals: dict[str, int] = {}
reader = csv.DictReader(io.StringIO(SALES_CSV))
for row in reader:
    q = int(row["quantity"])
    if q > 0:
        if row["category"] in totals:
            totals[row["category"]] = (
                totals[row["category"]] + int(row["price"]) * q
            )
        else:
            totals[row["category"]] = int(row["price"]) * q
    else:
        print("skip:", row)
print("=== 売上レポート ===")
grand = 0
for k in sorted(totals, key=lambda c: totals[c], reverse=True):
    print(f"{k:<8}{totals[k]:>8,} 円")
    grand = grand + totals[k]
print(f"{'合計':<7}{grand:>8,} 円")

ch02_report_script.py

このスクリプトは正しく動きます。しかし、次のような変更を求められたとき、どこを直せばよいでしょうか。

  • 数量が 0 以下のデータの扱いの変更（たとえば、返品として売上から差し引く）

  • 集計結果の出力先の変更（画面ではなくファイルに出力する）

  • 集計の処理が正しいことを確かめるテストの追加

どの変更でも、スクリプト全体を読んで、読み込み、集計、表示のどの部分が関係するのかを見極める必要があります。集計の処理だけをテストすることもできません。集計の途中に print があり、データはスクリプトの中に埋め込まれているからです。

同じ処理を、役割ごとの関数に分けて書き直したのが次のコードです。

ch02_report_structured.py（良い例）
import csv
import io
from collections.abc import Iterable
from dataclasses import dataclass

SALES_CSV = """date,category,product,price,quantity
2026-04-01,food,apple,120,10
2026-04-01,drink,tea,150,4
2026-04-02,food,bread,200,3
2026-04-02,drink,coffee,300,5
2026-04-03,food,apple,120,-1
2026-04-03,goods,pen,100,7
"""


@dataclass(frozen=True)
class Sale:
    """1 件の売上を表します."""

    category: str
    product: str
    price: int
    quantity: int

    @property
    def amount(self) -> int:
        """売上金額（単価 × 数量）を返します."""
        return self.price * self.quantity


def load_sales(text: str) -> list[Sale]:
    """CSV の文字列を読み込み、Sale のリストを返します."""
    reader = csv.DictReader(io.StringIO(text))
    return [
        Sale(
            category=row["category"],
            product=row["product"],
            price=int(row["price"]),
            quantity=int(row["quantity"]),
        )
        for row in reader
    ]


def is_valid(sale: Sale) -> bool:
    """集計の対象にする売上かどうかを返します（数量が正のものだけ）."""
    return sale.quantity > 0


def total_by_category(sales: Iterable[Sale]) -> dict[str, int]:
    """カテゴリごとの売上金額の合計を返します."""
    totals: dict[str, int] = {}
    for sale in sales:
        totals[sale.category] = totals.get(sale.category, 0) + sale.amount
    return totals


def format_report(totals: dict[str, int]) -> str:
    """集計結果を、売上の多い順に並べたレポートの文字列にします."""
    lines = ["=== 売上レポート ==="]
    for category, amount in sorted(
        totals.items(), key=lambda item: item[1], reverse=True
    ):
        lines.append(f"{category:<8}{amount:>8,} 円")
    lines.append(f"{'合計':<7}{sum(totals.values()):>8,} 円")
    return "\n".join(lines)


def main() -> None:
    """売上を読み込み、不正なデータを除いて集計し、レポートを表示します."""
    sales = load_sales(SALES_CSV)
    for sale in sales:
        if not is_valid(sale):
            print("skip:", sale)
    totals = total_by_category(sale for sale in sales if is_valid(sale))
    print(format_report(totals))


if __name__ == "__main__":
    main()

ch02_report_structured.py

各関数の関係を図にすると、次のようになります。

行数は増えましたが、先ほどの 3 つの変更は、それぞれ次のように対応できます。

変更の内容

修正する箇所

数量が 0 以下のデータの扱いの変更

is_valid（数量が負の売上も集計の対象にします。Sale.amount は負の金額になるので、total_by_category は変更不要です）

集計結果の出力先の変更

main（format_report が返す文字列を、ファイルに書き込みます）

集計の処理のテストの追加

修正は不要です。total_by_category に Sale のリストを渡して、戻り値を確かめるだけで済みます。

どちらの書き方が良いかは、状況によります。一度しか実行しない集計であれば、最初のスクリプトで十分です。しかし、このスクリプトを何か月も使い続け、変更を重ねていくのであれば、分割した構成のほうが変更にかかる手間は小さくなります。

2.6. 設計の粒度

設計は、さまざまな大きさの単位で行います。本資料では、次の順に小さい単位から説明します。

単位

主に決めること

本資料の章

関数

名前、引数と戻り値、副作用の有無、エラーの伝え方

関数の設計

データとクラス

データの型、不変条件、責任の分け方、継承とコンポジションの使い分け

データの設計、オブジェクト指向設計、SOLID 原則、デザインパターン

モジュールとパッケージ

公開するものと隠すもの、依存関係の向き

モジュールとパッケージの設計、依存関係の管理

システム全体

層やコンポーネントへの分け方、外部（データベース、画面、ネットワーク）との境界

アーキテクチャパターン、ドメインのモデリング

単位が大きくなるほど、あとから変更するのが難しくなります。関数の名前は数分で変えられますが、システム全体の構成を変えるには数か月かかることもあります。

2.7. 設計しすぎの害

設計は多ければ多いほど良いというものではありません。「将来必要になるかもしれない」という理由で、使われない拡張の仕組みや、何層もの抽象化を作り込むと、かえってコードは読みにくくなります。このような設計を 過剰設計 と呼びます。

過剰設計を避けるには、次の点を意識します。

  • 今分かっている要求に対して、最も単純な設計を選びます。

  • 同じ種類の変更が実際に 2 回、3 回と起きてから、その変更に備えた仕組みを作ります。

  • 抽象化（インターフェースや基底クラス）を作るときは、それがなければ何が困るのかを説明できるようにします。

これは、良い設計の指標 で説明する KISS や YAGNI の考え方です。設計の目的は、美しい構造を作ることではなく、変更にかかる費用を小さくすることです。

2.8. まとめ

  • 設計とは、プログラムを部品に分け、部品どうしのつなぎ方を決めることです。

  • 設計の目的は、変更しやすさ、理解しやすさ、テストしやすさです。

  • 設計によって減らせるのは、実装の仕方によって生じる偶有的な複雑さです。

  • 設計は、プログラムの規模や寿命に見合った量にとどめます。
