14. リファクタリング

最初から完璧な設計を作ることはできません。要求は変わり、理解は深まり、昨日の良い設計が今日の悪い設計になることもあります。設計は、コードを書いたあとも改善し続けるものです。この章では、既存のコードの設計を安全に改善する技法であるリファクタリングを説明します。

14.1. リファクタリングとは

リファクタリング とは、M. Fowler の定義によれば、外部から見た振る舞いを保ったまま、ソフトウェアの内部の構造を改善すること です。

この定義で重要なのは、「振る舞いを保ったまま」という部分です。機能の追加や不具合の修正は、振る舞いを変える変更なので、リファクタリングではありません。リファクタリングと振る舞いの変更を同時に行うと、問題が起きたときに、どちらの変更が原因なのかを切り分けられなくなります。そのため、2 つの作業ははっきりと分けて行います。

リファクタリングを行うのは、主に次のようなときです。

  • 機能を追加する前に、追加しやすい構造に整えるとき

  • 不具合を直す前に、原因を見つけやすい構造に整えるとき

  • コードを読んで理解したことを、名前や構造に反映させるとき

14.2. リファクタリングの前提はテスト

振る舞いを保っていることを確かめるには、テストが必要です。テストのないコードを書き換えるのは、命綱なしで高い所を歩くようなものです。

テストのない既存のコードをリファクタリングする場合は、まず現在の振る舞いをそのまま記録するテストを書きます。このテストを 仕様化テスト（characterization test）と呼びます。仕様化テストは、「正しい振る舞い」ではなく「現在の振る舞い」を記録します。現在の振る舞いに不具合が含まれていたとしても、それを直すのはリファクタリングが終わってからです。

14.3. コードの臭い

リファクタリングが必要な箇所の兆候を、Fowler と K. Beck は コードの臭い と呼びました。臭いは、必ずしも問題があることを意味しませんが、調べてみる価値のある兆候です。代表的なものを次に示します。

14.4. 代表的なリファクタリングの手法

Fowler の書籍には、多くのリファクタリングの手法が、名前と手順付きでまとめられています。よく使われるものを次に示します。

手法

内容

関数の抽出

コードの一部を、意味の分かる名前を付けた関数に切り出します。

変数の抽出

複雑な式の一部を、名前を付けた変数に置き換えます。

名前の変更

変数、関数、クラスの名前を、役割が分かるものに変えます。

引数オブジェクトの導入

いつも一緒に渡される引数を、1 つのデータクラスにまとめます。

マジックナンバーの定数への置き換え

意味の分からない数値（マジックナンバー）を、名前の付いた定数に置き換えます。

条件の分解

複雑な条件式を、条件の意味を表す名前の関数や変数に置き換えます。

フラグ引数の除去

真偽値の引数で動作を切り替える関数を、動作ごとの関数に分けます。

14.5. 例: 請求書を作る処理

次の関数は、顧客と明細から請求書の文字列を作ります。動作はしますが、多くのコードの臭いがあります。

ch14_refactoring/before.py
def make_invoice(customer: dict[str, str], items: list[dict[str, Any]],
                 ja: bool) -> str:
    s = ""
    t = 0.0
    for i in items:
        if i["type"] == "food":
            p = i["price"] * i["qty"]
            tax = p * 0.08
        else:
            p = i["price"] * i["qty"]
            tax = p * 0.1
        t += p + tax
        s = s + i["name"] + " x" + str(i["qty"]) + " " + str(int(p + tax))
        s = s + "\n"
    if customer["rank"] == "gold":
        t = t * 0.95
    if customer["rank"] == "gold" and t > 10000:
        t = t - 500
    if ja:
        s = s + "合計: " + str(int(t)) + " 円"
        s = customer["name"] + " 様\n" + s
    else:
        s = s + "Total: " + str(int(t)) + " JPY"
        s = "Dear " + customer["name"] + "\n" + s
    return s

臭い

この関数での現れ方

長い関数

税額の計算、会員の割引、請求書の整形が、すべて 1 つの関数にあります。

マジックナンバー

0.08、0.1、0.95、10000、500 の意味が書かれていません。

重複したコード

小計の計算 i["price"] * i["qty"] が、if と else の両方にあります。

意味の分からない名前

s、t、p、i が何を表すのか分かりません。

フラグ引数

ja によって出力の言語が変わります。

基本データ型への執着

顧客や明細を、辞書のまま扱っています。

14.5.1. 手順 1: 仕様化テストを書く

書き換えを始める前に、現在の振る舞いを記録するテストを用意します。会員のランク、税率の異なる明細、割引の境界（割引後の金額が 10000 円をわずかに超える場合と超えない場合）を組み合わせて、書き換える前の関数（before）と書き換えたあとの関数（after）の出力が一致することを確かめます。

ch14_refactoring/test_invoice.py
ITEM_SETS: list[list[dict[str, Any]]] = [
    [],
    [{"name": "りんご", "type": "food", "price": 120, "qty": 3}],

     {"name": "ノート", "type": "goods", "price": 250, "qty": 2}],
    # ゴールド会員の割引後に 10000 円をわずかに超える / 超えない
    [{"name": "椅子", "type": "goods", "price": 9570, "qty": 1}],
    [{"name": "椅子", "type": "goods", "price": 9569, "qty": 1}],
    [{"name": "米", "type": "food", "price": 4999, "qty": 3},
     {"name": "机", "type": "goods", "price": 33333, "qty": 1}],

class InvoiceCharacterizationTest(unittest.TestCase):
    """before と after の出力を比較します."""

    def test_same_output(self) -> None:
        for customer in CUSTOMERS:
            for items in ITEM_SETS:
                for ja in (True, False):
                    with self.subTest(customer=customer["name"],
                                      items=len(items), ja=ja):
                        self.assertEqual(
                            before.make_invoice(customer, items, ja),
                            after.make_invoice(customer, items, ja))

14.5.2. 手順 2: 小さな段階に分けて書き換える

書き換えは、一度に行わず、小さな段階に分けて進めます。1 つの段階が終わるたびにテストを実行し、振る舞いが変わっていないことを確かめます。テストが失敗したら、直前の段階だけを見直せば済みます。

  1. マジックナンバーを、名前の付いた定数に置き換えます。

  2. 重複した小計の計算を 1 か所にまとめます。

  3. 辞書を、データクラス（Customer、LineItem）に置き換えます。

  4. 明細の計算、会員の特典、請求書の整形を、それぞれ別の関数に抽出します。

  5. フラグ引数をやめ、言語ごとの関数に分けます。

書き換えた結果は、次のとおりです。

ch14_refactoring/after.py
REDUCED_TAX_RATE = 0.08  # 食品に適用する軽減税率
STANDARD_TAX_RATE = 0.1
REDUCED_TAX_TYPES = frozenset({"food"})

GOLD_DISCOUNT_FACTOR = 0.95  # ゴールド会員は 5% 引き
GOLD_BONUS_THRESHOLD = 10000  # この金額を超えると、さらに値引きする
GOLD_BONUS = 500


@dataclass(frozen=True)
class Customer:
    """請求先の顧客です."""

    name: str
    rank: str

    @property
    def is_gold(self) -> bool:
        return self.rank == "gold"


@dataclass(frozen=True)
class LineItem:
    """請求書の明細です."""

    name: str
    item_type: str
    price: int
    quantity: int

    @property
    def subtotal(self) -> int:
        """税抜きの小計を返します."""
        return self.price * self.quantity

    @property
    def tax(self) -> float:
        """消費税額を返します."""
        rate = (REDUCED_TAX_RATE if self.item_type in REDUCED_TAX_TYPES
                else STANDARD_TAX_RATE)
        return self.subtotal * rate

    @property
    def total(self) -> float:
        """税込みの金額を返します."""
        return self.subtotal + self.tax


def apply_member_benefits(amount: float, customer: Customer) -> float:
    """会員の特典を適用した金額を返します."""
    if not customer.is_gold:
        return amount
    amount = amount * GOLD_DISCOUNT_FACTOR
    if amount > GOLD_BONUS_THRESHOLD:
        amount = amount - GOLD_BONUS
    return amount


def invoice_total(customer: Customer, items: Iterable[LineItem]) -> int:
    """請求額を返します."""
    amount = 0.0
    for item in items:
        amount += item.total
    return int(apply_member_benefits(amount, customer))


def _format_lines(items: Iterable[LineItem]) -> str:
    return "".join(f"{item.name} x{item.quantity} {int(item.total)}\n"
                   for item in items)


def format_invoice_ja(customer: Customer, items: list[LineItem]) -> str:
    """日本語の請求書を返します."""
    total = invoice_total(customer, items)
    return f"{customer.name} 様\n{_format_lines(items)}合計: {total} 円"


def format_invoice_en(customer: Customer, items: list[LineItem]) -> str:
    """英語の請求書を返します."""
    total = invoice_total(customer, items)
    return f"Dear {customer.name}\n{_format_lines(items)}Total: {total} JPY"


def make_invoice(customer: dict[str, str], items: list[dict[str, Any]],
                 ja: bool) -> str:
    """元の関数と同じ呼び出し方を残すための関数です.

    呼び出し側をすべて format_invoice_ja と format_invoice_en に移行したら
    削除します。
    """
    converted_customer = Customer(customer["name"], customer["rank"])
    converted_items = [LineItem(i["name"], i["type"], i["price"], i["qty"])
                       for i in items]
    if ja:
        return format_invoice_ja(converted_customer, converted_items)
    return format_invoice_en(converted_customer, converted_items)

before.py、after.py、test_invoice.py

テストは、examples フォルダーで次のように実行します。

$ python -m unittest ch14_refactoring.test_invoice -v

14.5.3. 書き換えの注意点

この例では、次の点に注意しています。

  • 元の呼び出し方を残しました。 make_invoice の呼び出し側は、プログラムのあちこちにあるかもしれません。そこで、make_invoice は元と同じ引数で呼べるようにしたまま、中で新しい関数を呼ぶだけの関数にしました。呼び出し側を少しずつ新しい関数に移行し、すべて移行したら make_invoice を削除します。

  • 端数の扱いや計算の順序は変えていません。 金額の計算に浮動小数点数を使い、int で切り捨てるのは、本来は見直すべき点です。しかし、これを整数での計算や四捨五入に変えると、出力が変わる可能性があります。浮動小数点数の計算は、足し算の順序を変えるだけでも結果が変わることがあるので、合計の計算の順序も元のコードに合わせています。計算の方法を改めるのは、振る舞いを変える変更として、リファクタリングとは別に行います。

14.6. ツールを活用する

リファクタリングは、ツールの助けを借りると、より安全に行えます。

  • エディターの機能: 多くのエディターや IDE には、名前の変更や関数の抽出を自動で行う機能があります。手作業での書き換えよりも、書き換え漏れが起きません。

  • flake8: --max-complexity オプションで、循環的複雑度の高い関数を見つけられます（良い設計の指標 を参照）。リファクタリングの候補を探すのに役立ちます。

  • mypy: 型ヒントを付けておくと、関数の引数を変えたときに、修正の漏れた呼び出し側を検出できます。型ヒントのない既存のコードでも、リファクタリングする範囲から少しずつ型ヒントを追加していくと、安全に書き換えられる範囲が広がります。

14.7. まとめ

  • リファクタリングは、外部から見た振る舞いを保ったまま、内部の構造を改善することです。

  • リファクタリングと振る舞いの変更は、分けて行います。

  • テストのないコードは、まず現在の振る舞いを記録する仕様化テストを書きます。

  • コードの臭いを手がかりに、改善すべき箇所を見つけます。

  • 小さな段階に分けて書き換え、段階ごとにテストを実行します。
