設計チェックリスト

設計のレビューや、自分のコードを見直すときに使う確認項目です。すべての項目を満たす必要はありません。当てはまらない項目があれば、その理由を説明できるかを確かめてください。各項目の詳しい説明は、見出しに示した章を参照してください。

関数（関数の設計）

  • 関数の名前は、何をするかを表していますか。

  • 関数が何をするのかを、「〜と〜をする」とつなげずに 1 文で説明できますか。

  • 1 つの関数の中で、処理の抽象度がそろっていますか。

  • 引数が多すぎませんか。真偽値の引数で動作を切り替えていませんか。

  • 可変なオブジェクトをデフォルト引数にしていませんか。

  • 引数のオブジェクトを、呼び出し側が予想しない形で書き換えていませんか。

  • 計算の処理と、入出力（ファイル、画面、ネットワーク）の処理が分かれていますか。

  • 引数と戻り値に型ヒントが付いていますか。

  • エラーを、特別な戻り値ではなく例外で伝えていますか。例外を握りつぶしていませんか。

データ（データの設計）

  • 業務上の概念を、辞書や基本的な型のまま持ち回っていませんか。

  • 変更する必要のないデータは、不変になっていますか。

  • 値に関する規則（負にならない、など）は、値オブジェクトの中で確かめていますか。

  • 取り得る値が決まっているデータは、列挙型で表していますか。

  • あり得ない組み合わせのデータを作れてしまう型になっていませんか。

クラス（オブジェクト指向設計、SOLID 原則、デザインパターン）

  • クラスのデータの規則は、クラス自身が守っていますか（外から自由に書き換えられませんか）。

  • クラスに変更を求める人や組織（アクター）は、1 つに絞られていますか。

  • 継承は、本当に「一種である」関係の場合に限って使っていますか。コンポジションで代えられませんか。

  • サブクラスは、基底クラスの代わりに使えますか（基底クラスの約束を破っていませんか）。

  • インターフェースは、利用者が必要とするメソッドだけを持っていますか。

  • 種類ごとの if 文が、あちこちに繰り返し現れていませんか。

  • 解決したい問題がないのに、デザインパターンを使っていませんか。

モジュールと依存関係（モジュールとパッケージの設計、依存関係の管理）

  • 公開する名前と、内部用の名前（_ で始まる名前）が区別されていますか。

  • 循環 import はありませんか。

  • 依存は、変更されにくいモジュールの方向に向いていますか。

  • 上位の方針のコードが、下位の詳細（データベース、外部のサービス）に直接依存していませんか。

  • 依存オブジェクトを内部で直接作らず、外から受け取っていますか。

  • オブジェクトの組み立てと、環境変数や設定ファイルの読み込みが、プログラムの入口の付近にまとまっていますか。

  • グローバル変数や Singleton に依存していませんか。

アーキテクチャ（アーキテクチャパターン、ドメインのモデリング）

  • システムにとって重要な品質特性は何かが、明らかになっていますか。

  • 業務の規則が、画面やデータベースの技術から切り離されていますか。

  • 業務の言葉と、コードのクラス名やメソッド名が一致していますか。

  • 集約の内部のオブジェクトを、集約ルートを通さずに変更していませんか。

  • アーキテクチャは、システムの規模と寿命に見合っていますか（大げさすぎませんか）。

テストと保守（テストと設計、リファクタリング、設計の記録と伝達）

  • 業務の規則を、データベースやネットワークを使わずにテストできますか。

  • 現在時刻や乱数に依存する処理を、固定した値でテストできますか。

  • テストが、実装の詳細（メソッドの呼ばれる順序など）に依存しすぎていませんか。

  • リファクタリングと、振る舞いの変更を分けて行っていますか。

  • 重要な設計の判断と、その理由が記録されていますか。
