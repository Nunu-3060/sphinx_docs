12. ドメインのモデリング

ソフトウェアが扱う業務の領域（注文、在庫、会計など）を ドメイン と呼びます。業務の規則が複雑なシステムでは、その規則をコードでどう表すかが、変更のしやすさを大きく左右します。この章では、ドメイン駆動設計（Domain-Driven Design、DDD）の考え方のうち、コードの設計に直接役立つ部分を紹介します。

12.1. ドメイン駆動設計とは

ドメイン駆動設計は、E. Evans が 2003 年の書籍で提唱した、ソフトウェアの設計の手法です。その中心にある考え方は、次の 2 つです。

  • 業務の専門家と開発者が協力して、業務の知識を モデル として整理します。

  • そのモデルを、コードにできるだけそのまま表します。

ドメイン駆動設計は、組織やチームの分け方まで含む広い手法です。この章では、そのうち「モデルをコードで表すための部品」（エンティティ、値オブジェクト、集約、リポジトリ、サービス）を中心に説明します。例として、注文を受け付けるシステムのドメインを実装します。

12.2. ユビキタス言語

業務の専門家と開発者が、同じ概念を別の言葉で呼んでいると、誤解が生まれます。たとえば、営業の担当者が「受注」と呼んでいるものを、開発者がコードで Request と名付けていると、会話とコードの対応を取るたびに翻訳が必要になります。

ドメイン駆動設計では、チームの全員が使う共通の言葉を決め、会話にも、ドキュメントにも、コードのクラス名やメソッド名にも、その言葉を使います。この共通の言葉を ユビキタス言語 と呼びます。業務の言葉がそのままコードに現れていれば、業務の規則が変わったときに、どこを直せばよいのかがすぐに分かります。

12.3. エンティティと値オブジェクト

ドメインの概念を表すオブジェクトは、大きく 2 種類に分けられます。

エンティティ

値オブジェクト

同一性

ID で区別します。属性の値が変わっても、同じ ID なら同じものです。

属性の値で区別します。値が同じなら、同じものとみなします。

変更

状態が変わることがあります（注文の状態が「下書き」から「確定」に変わるなど）。

不変にします。値を変えたいときは、新しいオブジェクトを作ります。

例

注文、顧客、口座

金額、注文の明細、住所、期間

たとえば、同姓同名の 2 人の顧客は、名前という値が同じでも別の人なので、顧客はエンティティです。一方、「1,000 円」という金額は、どの 1,000 円も区別する必要がないので、値オブジェクトです。

値オブジェクトの考え方と実装の方法は、データの設計 で説明しました。注文のドメインでも、金額 Money と注文の明細 OrderLine を値オブジェクトとして定義します（この例の Money は、簡単にするため円だけを扱います）。

ch12_domain_model/model.py（値オブジェクト）
@dataclass(frozen=True)
class Money:
    """金額（円）を表す値オブジェクトです."""

    amount: int

    def __post_init__(self) -> None:
        if self.amount < 0:
            raise DomainError(f"金額は 0 以上です: {self.amount}")

    def __add__(self, other: "Money") -> "Money":
        return Money(self.amount + other.amount)

    def __mul__(self, times: int) -> "Money":
        return Money(self.amount * times)

    def __str__(self) -> str:
        return f"{self.amount:,} 円"


@dataclass(frozen=True)
class OrderLine:
    """注文の明細を表す値オブジェクトです."""

    product_id: str
    unit_price: Money
    quantity: int

    def __post_init__(self) -> None:
        if self.quantity <= 0:
            raise DomainError(f"数量は 1 以上です: {self.quantity}")

    @property
    def subtotal(self) -> Money:
        """小計を返します."""
        return self.unit_price * self.quantity

エンティティの Order は、ID（order_id）で同一かどうかを判断するように、__eq__ と __hash__ を定義します。

ch12_domain_model/model.py（エンティティの同一性）
# エンティティは、属性の値ではなく ID で同一かどうかを判断する
def __eq__(self, other: object) -> bool:
    return isinstance(other, Order) and other.order_id == self.order_id

def __hash__(self) -> int:
    return hash(self._order_id)

12.4. 集約

注文と注文の明細のように、密接に関係し、常に一緒に変更されるオブジェクトのまとまりを 集約 と呼びます。集約には、外部からの窓口となるオブジェクトが 1 つあり、これを 集約ルート と呼びます。

集約には、次の規則があります。

  • 集約の外から、集約の内部のオブジェクト（明細など）を直接変更してはいけません。変更は必ず集約ルートのメソッドを通して行います。

  • 集約ルートは、集約の全体が常に業務の規則（不変条件）を満たしていることを保証します。

  • 集約は、まるごと保存し、まるごと読み込みます。

注文の集約では、Order が集約ルートです。明細の追加や状態の変更は Order のメソッドを通して行い、Order が次の不変条件を守ります。

  • 明細を変更できるのは、下書きの状態のときだけです。

  • 明細は最大 10 行です（同じ商品は 1 行にまとめます）。

  • 明細のない注文は確定できません。

ch12_domain_model/model.py（集約ルート）
class Order:
    """注文です. 明細を含む集約のルートです.

    明細の追加や状態の変更は、必ずこのクラスのメソッドを通して行います。
    これにより、次の規則（不変条件）を常に守ります。

    * 明細を変更できるのは、下書きの状態のときだけ
    * 明細は最大 MAX_LINES 行（同じ商品は 1 行にまとめる）
    * 明細のない注文は確定できない
    """

    def __init__(self, order_id: str, customer_id: str) -> None:
        self._order_id = order_id
        self._customer_id = customer_id
        self._lines: list[OrderLine] = []
        self._status = OrderStatus.DRAFT

    @classmethod
    def restore(cls, order_id: str, customer_id: str, status: OrderStatus,
                lines: Iterable[OrderLine]) -> "Order":
        """保存されていたデータから注文を復元します（リポジトリ用）."""
        order = cls(order_id, customer_id)
        order._lines = list(lines)
        order._status = status
        return order

    @property
    def order_id(self) -> str:
        return self._order_id

    @property
    def customer_id(self) -> str:
        return self._customer_id

    @property
    def status(self) -> OrderStatus:
        return self._status

    @property
    def lines(self) -> tuple[OrderLine, ...]:
        """明細を返します. タプルなので、外から書き換えられません."""
        return tuple(self._lines)

    @property
    def total(self) -> Money:
        """合計金額を返します."""
        result = Money(0)
        for line in self._lines:
            result = result + line.subtotal
        return result

    def add_line(self, product_id: str, unit_price: Money,
                 quantity: int) -> None:
        """明細を追加します. 同じ商品があれば数量を加算します."""
        self._ensure_draft()
        for index, line in enumerate(self._lines):
            if line.product_id == product_id:
                self._lines[index] = OrderLine(
                    product_id, unit_price, line.quantity + quantity)
                return
        if len(self._lines) >= MAX_LINES:
            raise DomainError(f"明細は {MAX_LINES} 行までです")
        self._lines.append(OrderLine(product_id, unit_price, quantity))

    def place(self) -> None:
        """注文を確定します."""
        self._ensure_draft()
        if not self._lines:
            raise DomainError("明細のない注文は確定できません")
        self._status = OrderStatus.PLACED

    def cancel(self) -> None:
        """注文を取り消します."""
        if self._status is OrderStatus.CANCELLED:
            raise DomainError("注文は取り消し済みです")
        self._status = OrderStatus.CANCELLED

    def _ensure_draft(self) -> None:
        if self._status is not OrderStatus.DRAFT:
            raise DomainError(
                f"状態が {self._status.value} の注文は変更できません")

lines プロパティは、明細のリストそのものではなく、タプルに変換して返します。外部から order.lines.append(...) のように明細を直接追加されると、不変条件を確かめる機会がなくなるからです。

12.4.1. 集約の大きさ

集約は、できるだけ小さくします。たとえば、注文の集約に顧客の情報まで含めると、顧客の住所を変更するたびに、その顧客のすべての注文を読み込むことになります。別の集約を参照するときは、オブジェクトそのものではなく、ID で参照します。Order が顧客を Customer のオブジェクトではなく、customer_id という ID で持っているのはこのためです。

12.5. リポジトリ

リポジトリ は、集約を保存したり、取り出したりするための部品です。アプリケーションの側から見ると、リポジトリは「集約を入れておく箱」のように振る舞い、その裏でデータベースやファイルがどう使われているかは隠されています。

リポジトリのインターフェースは、ドメインの側（またはアプリケーションの側）に Protocol として定義し、実装とは別のモジュールに置きます。これは、アーキテクチャパターン のヘキサゴナルアーキテクチャにおけるポートに当たります。この例では、インターフェースをドメインのモジュール model.py に、実装を repository.py に置いています。アプリケーションサービスは model.py だけを import し、repository.py を知りません。

ch12_domain_model/model.py（リポジトリのインターフェース）
class OrderRepository(Protocol):
    """注文のリポジトリのインターフェースです."""

    def next_id(self) -> str:
        """新しい注文の ID を返します."""
        ...

    def save(self, order: Order) -> None:
        """注文を保存します（同じ ID があれば上書きします）."""
        ...

    def get(self, order_id: str) -> Order | None:
        """ID に一致する注文を返します. なければ None を返します."""
        ...

実装として、メモリに保存する InMemoryOrderRepository と、SQLite に保存する SqliteOrderRepository を用意しました。SQLite 版は、注文と明細を 2 つのテーブルに分けて保存しますが、アプリケーションの側からは、注文の集約をまるごと保存し、まるごと取り出すように見えます。

ch12_domain_model/repository.py（SQLite 版の保存）
def save(self, order: Order) -> None:
    # 注文と明細を 1 つのトランザクションで保存する
    with self._connection:
        self._connection.execute(
            "INSERT OR REPLACE INTO orders VALUES (?, ?, ?)",
            (order.order_id, order.customer_id, order.status.value))
        self._connection.execute(
            "DELETE FROM order_lines WHERE order_id = ?",
            (order.order_id,))
        self._connection.executemany(
            "INSERT INTO order_lines VALUES (?, ?, ?, ?, ?)",
            [(order.order_id, line_no, line.product_id,
              line.unit_price.amount, line.quantity)
             for line_no, line in enumerate(order.lines, start=1)])
ch12_domain_model/repository.py（SQLite 版の取得）
def get(self, order_id: str) -> Order | None:
    row = self._connection.execute(
        "SELECT customer_id, status FROM orders WHERE order_id = ?",
        (order_id,)).fetchone()
    if row is None:
        return None
    customer_id, status = row
    cursor = self._connection.execute(
        "SELECT product_id, unit_price, quantity FROM order_lines"
        " WHERE order_id = ? ORDER BY line_no", (order_id,))
    lines = [OrderLine(product_id, Money(unit_price), quantity)
             for product_id, unit_price, quantity in cursor]
    return Order.restore(order_id, customer_id, OrderStatus(status),
                         lines)

メモリ版の save と get は、copy.deepcopy でオブジェクトの複製を保存し、複製を返します。複製しないと、保存したあとに呼び出し側がオブジェクトを変更したとき、リポジトリの中身まで変わってしまい、データベースに保存した場合と振る舞いが異なってしまうからです。

12.6. ドメインサービスとアプリケーションサービス

ドメインの処理の中には、特定のエンティティや値オブジェクトのメソッドにするのが不自然なものがあります。たとえば、送料の計算は、注文の合計金額と配送先の地域によって決まりますが、送料の規則は注文そのものの性質ではなく、配送の方針です。このような処理は、独立した関数やクラスにします。これを ドメインサービス と呼びます。

ch12_domain_model/model.py（ドメインサービス）
FREE_SHIPPING_THRESHOLD = Money(5000)
SHIPPING_FEES = {"local": Money(500), "remote": Money(1200)}


def shipping_fee(order: Order, region: str) -> Money:
    """注文と配送先の地域から送料を求めます.

    送料の規則は注文そのものの性質ではなく配送の方針なので、Order の
    メソッドにはせず、ドメインサービスとして独立させます。
    """
    if region not in SHIPPING_FEES:
        raise DomainError(f"配送できない地域です: {region}")
    if order.total.amount >= FREE_SHIPPING_THRESHOLD.amount:
        return Money(0)
    return SHIPPING_FEES[region]

一方、ユースケースの手順（リポジトリから集約を取り出し、集約のメソッドを呼び、保存する）を実装するのが アプリケーションサービス です。アプリケーションサービスは手順を調整するだけで、業務の規則そのものは持ちません。規則は、エンティティ、値オブジェクト、ドメインサービスに書きます。

ch12_domain_model/service.py
class OrderService:
    """注文の作成、商品の追加、確定のユースケースです."""

    def __init__(self, repository: OrderRepository) -> None:
        self._repository = repository

    def create_order(self, customer_id: str) -> str:
        """新しい注文を作り、その ID を返します."""
        order = Order(self._repository.next_id(), customer_id)
        self._repository.save(order)
        return order.order_id

    def add_item(self, order_id: str, product_id: str, unit_price: int,
                 quantity: int) -> None:
        """注文に商品を追加します."""
        order = self._get(order_id)
        order.add_line(product_id, Money(unit_price), quantity)
        self._repository.save(order)

    def place_order(self, order_id: str, region: str) -> Money:
        """注文を確定し、送料を含む請求額を返します."""
        order = self._get(order_id)
        fee = shipping_fee(order, region)
        order.place()
        self._repository.save(order)
        return order.total + fee

    def _get(self, order_id: str) -> Order:
        order = self._repository.get(order_id)
        if order is None:
            raise DomainError(f"注文 {order_id} はありません")
        return order

place_order では、注文を確定する前に送料を計算しています。配送先の地域を、集約の状態を変更する前に検証し、配送できない地域が指定された場合には、集約の状態が変わらないようにするためです。

ch12_domain_model のすべてのファイルは 12 章　ドメインのモデリング で閲覧できます。examples フォルダーで python -m ch12_domain_model.main と実行すると、同じユースケースを、メモリ版と SQLite 版のリポジトリで実行し、確定した注文の変更が拒否されることを確認できます。

12.7. 境界づけられたコンテキスト

大きなシステムでは、同じ言葉が、部門によって異なる意味を持つことがあります。たとえば「商品」は、販売の部門にとっては価格や説明文を持つものですが、配送の部門にとっては重さや大きさを持つものです。この 2 つを 1 つの Product クラスで表そうとすると、クラスはどの部門にとっても不要な属性を抱えた、大きなものになります。

ドメイン駆動設計では、モデルが一貫した意味を持つ範囲を 境界づけられたコンテキスト と呼び、範囲ごとに別のモデルを作ります。販売のコンテキストと配送のコンテキストは、それぞれ独自の Product を持ち、両者は ID などを使って連携します。

境界づけられたコンテキストは、モジュールやパッケージを分ける単位として、また アーキテクチャパターン で説明したマイクロサービスの境界を考える手がかりとしても使えます。

12.8. まとめ

  • 業務の専門家と開発者は、共通の言葉（ユビキタス言語）を使い、コードにもその言葉を使います。

  • ID で区別するものはエンティティ、値で区別するものは値オブジェクトとして表します。

  • 一緒に変更されるオブジェクトは集約にまとめ、集約ルートを通して変更し、不変条件を守ります。

  • 集約の保存と取得はリポジトリに任せ、リポジトリのインターフェースはドメインの側に置きます。

  • ユースケースの手順はアプリケーションサービスに、特定のオブジェクトに属さない規則はドメインサービスに書きます。
