3. 良い設計の指標

設計の良し悪しを「なんとなく読みやすい」「なんとなく気持ち悪い」という感覚だけで判断していると、人によって意見が分かれ、議論が進みません。この章では、設計を評価するときの共通の物差しとなる指標と原則を説明します。以降の章では、ここで説明する言葉を使って、書き換えによって何が良くなったのかを説明します。

3.1. 凝集度

凝集度 は、1 つの部品（関数、クラス、モジュール）の中にある要素が、どれだけ強く関連しているかを表す指標です。凝集度は高いほど良い とされます。凝集度の高い部品は、1 つの目的のために存在しているので、理解しやすく、変更の理由も 1 つに絞られます。

凝集度は、低いものから高いものへ、次の 7 段階に分類されます。

種類

説明と例

低

偶発的凝集

たまたま同じ場所に置かれているだけで、要素の間に関連がありません。例: utils.py に、日付の整形、メールの送信、税額の計算が並んでいます。

論理的凝集

論理的に似た処理を 1 つにまとめ、引数のフラグで切り替えます。例: export(data, kind) が kind によって CSV、JSON、PDF のどれかを出力します。

時間的凝集

同じ時点で実行するという理由だけでまとめています。例: 起動時の処理として、設定の読み込み、ログの初期化、キャッシュの削除をまとめた initialize()。

手順的凝集

実行する順序が決まっているという理由でまとめています。データの受け渡しはありません。

通信的凝集

同じデータを扱う処理をまとめています。例: 同じ顧客のデータから、請求書と送り状を作ります。

逐次的凝集

ある処理の出力が、次の処理の入力になっています。例: 読み込み → 検証 → 変換を順に行います。

高

機能的凝集

すべての要素が、1 つの明確な機能のために協力しています。例: 税込み価格を計算する price_with_tax()。

実際の開発では、7 段階のどれに当たるかを厳密に判定する必要はありません。「この関数（クラス）は何をするものか」を 1 文で説明してみて、「〜と〜をする」のように「と」でつなぐ必要があれば、凝集度が低い可能性があります。

3.2. 結合度

結合度 は、部品と部品が、どれだけ強く依存し合っているかを表す指標です。結合度は低いほど良い とされます。結合度の低い部品は、ほかの部品のことを知らなくても理解でき、ほかの部品を変更しても影響を受けにくくなります。

結合度は、強いものから弱いものへ、次のように分類されます。

種類

説明と例

強

内容結合

ほかの部品の内部のデータを直接参照したり、変更したりします。例: ほかのクラスの _ で始まる属性を書き換えます。

共通結合

グローバル変数など、共有のデータを通してやり取りします。どこから書き換えられるか分からないので、影響の範囲を追えません。

外部結合

外部で決められたデータの形式や通信の手順（ファイルの形式、プロトコル）を共有します。

制御結合

相手の動作を切り替えるためのフラグを渡します。呼び出し側が、呼び出される側の内部の処理を知っている必要があります。

スタンプ結合

データ構造の全体を渡しますが、受け取る側はその一部しか使いません。受け取る側は、使わない部分も含めたデータ構造に依存します。

弱

データ結合

必要なデータだけを、引数と戻り値でやり取りします。

凝集度と結合度は、表裏の関係にあります。関連の強い要素を 1 つの部品にまとめると（凝集度を上げると）、部品の間でやり取りする必要が減り、結合度は下がります。高凝集・低結合 は、あらゆる規模の設計に共通する目標です。

3.2.1. 例: 結合度を下げる

会員の購入金額に応じてポイントを付与する処理を例にします。悪い例の bad_calc_points は、グローバル変数 config を読み（共通結合）、会員のデータ全体を受け取って、その内部の構造に依存しています（スタンプ結合）。

ch03_coupling.py（悪い例）
# どこからでも書き換えられるグローバルな設定
config: dict[str, float] = {"point_rate": 0.01}


@dataclass
class Member:
    """会員を表します."""

    name: str
    rank: str
    history: list[int] = field(default_factory=list)


def bad_calc_points(member: Member) -> int:
    """最後の購入金額に対するポイントを返します（悪い例）.

    グローバル変数 config を読み、会員のデータ全体を受け取って、その
    内部の構造（購入履歴のリストの末尾が最新であること）に依存しています。
    config や Member の実装を変更すると、この関数も壊れます。
    """
    rate = config["point_rate"]
    if member.rank == "gold":
        rate = rate * 2
    return int(member.history[-1] * rate)

良い例の calc_points は、計算に必要な値（購入金額と会員ランク）だけを引数で受け取ります（データ結合）。

ch03_coupling.py（良い例）
RANK_MULTIPLIER: dict[str, int] = {"regular": 1, "gold": 2}


def calc_points(amount: int, rank: str, base_rate: float = 0.01) -> int:
    """購入金額と会員ランクから、付与するポイントを返します（良い例）.

    計算に必要な値だけを引数で受け取るので、呼び出し側のデータ構造や
    グローバルな状態に依存しません。
    """
    return int(amount * base_rate * RANK_MULTIPLIER[rank])

ch03_coupling.py

サンプルを実行すると、config を別の場所で書き換えたときに、悪い例の結果だけが変わることを確認できます。良い例の calc_points は、Member クラスの構造が変わっても影響を受けず、会員以外の購入（たとえば、ゲストの購入）にもそのまま使えます。

3.3. 情報隠蔽

情報隠蔽 は、D. L. Parnas が 1972 年の論文で提唱した考え方です。Parnas は、モジュールを処理の手順ごとに分けるのではなく、変更される可能性の高い設計上の決定ごとに分け、その決定をモジュールの内部に隠す べきだと主張しました。

たとえば、データをファイルに保存するか、データベースに保存するかは、あとで変わる可能性のある決定です。この決定を 1 つのモジュールの中に隠し、ほかのモジュールには「保存する」「取り出す」という操作だけを見せておけば、保存の方法を変えても、影響はそのモジュールだけに収まります。

Python には、アクセスを強制的に禁止する仕組み（Java の private など）はありません。代わりに、名前を _ で始めることで「内部用なので外から使わないでください」という意図を示す慣習があります。この慣習は モジュールとパッケージの設計 で詳しく説明します。

3.4. 関心の分離

関心の分離 は、プログラムを、それぞれ異なる関心事（気にかけるべき事柄）を扱う部分に分けるという原則です。代表的な関心事には、次のようなものがあります。

  • 業務の規則（税額の計算、在庫の引き当てなど）

  • データの保存と読み込み

  • 画面への表示や、利用者からの入力

  • 外部のサービスとの通信

ソフトウェア設計とは の売上レポートの例で、読み込み、集計、表示を別の関数に分けたのは、関心の分離の実践です。関心ごとに分けておくと、ある関心事の変更（表示の形式の変更など）が、ほかの関心事（集計の規則など）に影響しません。

3.5. DRY、KISS、YAGNI

設計の原則として、短い標語の形で広く知られているものがあります。

原則

説明

DRY（Don't Repeat Yourself）

同じ知識を、システムの中の複数の場所に書かないという原則です。消費税率を複数の関数に 0.1 と直接書いていると、税率が変わったときにすべてを直す必要があり、直し忘れが不具合になります。

KISS（Keep It Simple, Stupid）

設計は単純に保つべきだという原則です。同じ要求を満たせるなら、より単純な方法を選びます。

YAGNI（You Aren't Gonna Need It）

今必要でない機能は作らないという原則です。将来の要求を予想して作った仕組みは、多くの場合使われないか、実際の要求と合わずに作り直すことになります。

DRY について、よくある誤解があります。DRY が禁じているのは 知識の重複 であり、見た目が似たコード ではありません。たとえば、「送料の上限」と「ポイントの上限」がたまたま同じ 1000 という値でも、この 2 つは異なる知識なので、1 つの定数にまとめるべきではありません。まとめてしまうと、一方だけを変更したいときに困ります。

3.6. デメテルの法則

デメテルの法則 は、「直接の知り合いとだけ話せ」と要約される原則です。あるメソッドの中から呼び出してよいのは、次のもののメソッドだけだとします。

  • 自分自身（self）

  • 引数として受け取ったオブジェクト

  • 自分が作ったオブジェクト

  • 自分の属性として持っているオブジェクト

次のコードは、この法則に反しています。

# 悪い例: 注文 → 顧客 → 住所 → 郵便番号と、内部の構造をたどっている
zip_code = order.customer.address.zip_code

このコードは、注文が顧客を持ち、顧客が住所を持ち、住所が郵便番号を持つという構造のすべてに依存しています。どれか 1 つの構造が変わると、このコードも変更が必要です。必要な情報を返すメソッドを Order に用意すれば、呼び出し側は注文の内部の構造を知らずに済みます。

# 良い例: 注文に、配送先の郵便番号を尋ねる
zip_code = order.shipping_zip_code()

ただし、dataclass のように、データを保持することが目的のオブジェクトや、"a,b".split(",")[0].strip() のように、標準の型のメソッドをつなげて呼ぶ場合は、この法則を気にする必要はありません。この法則が避けようとしているのは、振る舞いを持つオブジェクトの内部の構造 への依存です。

3.7. 循環的複雑度

循環的複雑度 は、T. J. McCabe が 1976 年に提案した、プログラムの複雑さを数値で表す指標です。関数の処理の流れを、処理を節点、処理の移り変わりを辺とするグラフ（制御フローグラフ）で表したとき、循環的複雑度 \(M\) は次の式で求められます。

\[M = E - N + 2P\]

ここで、\(E\) は辺の数、\(N\) は節点の数、\(P\) は連結成分の数（1 つの関数だけを考える場合は 1）です。

たとえば、次の関数を考えます。

def sign(x: float) -> str:
    if x > 0:
        return "正"
    elif x < 0:
        return "負"
    return "ゼロ"

この関数の制御フローグラフは、次のようになります。

辺は 7 本、節点は 6 個なので、\(M = 7 - 6 + 2 \times 1 = 3\) です。1 つの関数の場合、循環的複雑度は「分岐の数 + 1」に等しくなります。この関数には if と elif の 2 つの分岐があるので、\(2 + 1 = 3\) と求めることもできます。

循環的複雑度は、その関数の線形独立な経路（基本経路）の数を表し、基本経路をすべて通すために必要なテストの数の目安にもなります。なお、これは「すべての経路」の数ではありません。たとえば、入れ子になっていない if 文が \(n\) 個並んだ関数の循環的複雑度は \(n + 1\) ですが、経路の組み合わせは \(2^n\) 通りあります。McCabe は、1 つの関数の循環的複雑度を 10 以下に抑えることを推奨しました。

3.7.1. 例: 複雑度を下げる

配送料を計算する次の関数は、分岐が入れ子になっており、循環的複雑度は 8 です。

ch03_complexity.py（悪い例）
def bad_shipping_fee(region: str, weight_kg: float, is_member: bool) -> int:
    """配送料を返します（悪い例）."""
    if region == "local":
        if weight_kg <= 5:
            fee = 500
        else:
            fee = 800
    elif region == "remote":
        if weight_kg <= 5:
            fee = 1000
        else:
            fee = 1500
    elif region == "island":
        if weight_kg <= 5:
            fee = 2000
        else:
            fee = 3000
    else:
        raise ValueError(f"unknown region: {region}")
    if is_member:
        fee = fee // 2
    return fee

料金の値を表（辞書）に分離すると、関数に残る分岐は 3 つになり、循環的複雑度は 4 に下がります。地域の追加や料金の改定は、表を変更するだけで済み、関数を変更する必要はありません。

ch03_complexity.py（良い例）
LIGHT_WEIGHT_LIMIT_KG = 5.0

# 地域ごとの（軽量の料金, 重量の料金）
FEE_TABLE: dict[str, tuple[int, int]] = {
    "local": (500, 800),
    "remote": (1000, 1500),
    "island": (2000, 3000),
}


def shipping_fee(region: str, weight_kg: float, is_member: bool) -> int:
    """配送料を返します（良い例）.

    料金の値は FEE_TABLE にまとめたので、地域の追加や料金の改定では
    この関数を変更する必要がありません。
    """
    if region not in FEE_TABLE:
        raise ValueError(f"unknown region: {region}")
    light_fee, heavy_fee = FEE_TABLE[region]
    fee = light_fee if weight_kg <= LIGHT_WEIGHT_LIMIT_KG else heavy_fee
    return fee // 2 if is_member else fee

ch03_complexity.py

flake8 に --max-complexity オプションを付けると、循環的複雑度が指定した値を超える関数を検出できます。

$ python -m flake8 --max-complexity 5 ch03_complexity.py
ch03_complexity.py:16:1: C901 'bad_shipping_fee' is too complex (8)

flake8 が使う mccabe は、条件式（a if 条件 else b）を分岐として数えません。そのため、良い例の shipping_fee の循環的複雑度は、この節で数えた 4 ではなく 2 と報告されます。条件式を使っても分岐がなくなるわけではないので、数値だけで判断しないようにしてください。

3.8. 指標との付き合い方

この章で紹介した指標は、設計を振り返るための道具であり、目標そのものではありません。循環的複雑度を下げるためだけに、意味のない小さな関数に分けると、かえって読みにくくなります。指標が悪い値を示したら、「なぜこの値になっているのか」「変更しにくくなっていないか」を考えるきっかけにしてください。

3.9. まとめ

  • 凝集度は高く、結合度は低くします。

  • 変更される可能性の高い決定は、1 つの部品の内部に隠します（情報隠蔽）。

  • 異なる関心事は、異なる部品に分けます（関心の分離）。

  • DRY が禁じるのは知識の重複であり、見た目が似たコードではありません。

  • 循環的複雑度は、関数の分岐の多さを表し、テストの数の目安にもなります。
