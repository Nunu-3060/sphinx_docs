5. データの設計

プログラムが扱うデータをどのような型で表すかは、関数の設計と同じくらい重要です。この章では、辞書やタプルでデータを持ち回ることの問題と、データクラス、値オブジェクト、列挙型を使ってデータを表す方法を説明します。

5.1. 辞書で持ち回る問題

Python の辞書は手軽なので、データをまとめるのによく使われます。次の関数は、辞書で表した注文の合計金額を求めます。

ch05_data.py（悪い例）
def bad_order_total(order: dict[str, Any]) -> int:
    """注文の合計金額を返します（悪い例）.

    キーの名前や値の型は、辞書を作った箇所を読まないと分かりません。
    キーの綴りを誤っても、実行するまで気付けません。
    """
    total = 0
    for line in order["lines"]:
        total += line["price"] * line["qty"]
    return total

この関数には、次のような問題があります。

  • 辞書にどのようなキーがあり、値がどのような型なのかは、辞書を作った箇所を探して読まないと分かりません。

  • キーの綴りを誤っても（"qty" を "quantity" と書くなど）、実行するまで気付けません。型チェッカーも検出できません。

  • 数量が負の値であるなど、不正なデータが紛れ込んでも、気付かずに計算が進みます。

このように、業務上の概念（金額、注文の明細など）を、int、str、dict といった基本的な型のまま扱い続けることを 基本データ型への執着 と呼びます。

5.2. データの型を定義する

Python には、データをまとめる型を定義する方法がいくつかあります。

方法

特徴

向いている場面

dataclasses.dataclass

属性を宣言するだけで、__init__、__repr__、__eq__ が自動で作られます。メソッドを追加でき、frozen=True で不変にできます。

アプリケーションのデータの多く

typing.NamedTuple

タプルとしても扱えるので、アンパックやインデックスでのアクセスができます。常に不変です。

関数から複数の値を返す場合や、タプルを使っている既存のコードの置き換え

typing.TypedDict

実体は辞書のままで、キーと値の型だけを型チェッカーに伝えます。

JSON など、外部との境界で辞書として扱う必要があるデータ

特に理由がなければ、dataclass を使います。前の例を dataclass で書き直すと、次のようになります。金額を表す Money と、注文の状態を表す OrderStatus は、この章の後半で説明します。

ch05_data.py（良い例）
class OrderLine:
    """注文の明細です."""

    product: str
    unit_price: Money
    quantity: int

    def __post_init__(self) -> None:
        if self.quantity <= 0:
            raise ValueError(f"quantity must be positive: {self.quantity}")

    @property
    def subtotal(self) -> Money:
        """小計を返します."""
        return self.unit_price * self.quantity


@dataclass
class Order:
    """注文です."""

    order_id: str
    lines: list[OrderLine] = field(default_factory=list)
    status: OrderStatus = OrderStatus.DRAFT

    @property
    def total(self) -> Money:
        """合計金額を返します."""
        result = Money(0)
        for line in self.lines:
            result = result + line.subtotal
        return result

OrderLine の __post_init__ は、dataclass が作る __init__ の最後に呼ばれるメソッドです。ここで数量を検証しているので、数量が 0 以下の明細は作ることすらできません。不正なデータを、作られた時点で防げます。

5.3. 不変オブジェクト

作ったあとに値を変更できないオブジェクトを 不変オブジェクト と呼びます。dataclass に frozen=True を指定すると、属性への代入が FrozenInstanceError になり、不変オブジェクトになります。

不変オブジェクトには、次のような利点があります。

  • 関数に渡しても書き換えられる心配がないので、関数の中身を読まずに安心して渡せます。

  • 複数の場所から同じオブジェクトを参照していても、ある場所での変更が別の場所に影響しません。

  • 作った時点で検証すれば、その後ずっと正しい状態が保たれます。

  • 辞書のキーや集合の要素として使えます（frozen=True の dataclass は __hash__ を持ちます）。

値を変えたい場合は、dataclasses.replace などで新しいオブジェクトを作ります。データを変更する必要が特にない場合は、不変にしておくのが安全です。

5.4. 値オブジェクト

金額、日付の範囲、メールアドレスのように、値そのものが意味を持ち、値が同じなら同じものとみなせる オブジェクトを 値オブジェクト と呼びます。値オブジェクトは不変にし、その値に関する規則と操作をまとめて持たせます。

次の Money は、金額を表す値オブジェクトです。

ch05_data.py
@dataclass(frozen=True)
class Money:
    """金額を表す値オブジェクトです.

    負の金額を作れないようにし、通貨の異なる金額どうしの計算を禁止します。
    """

    amount: int
    currency: str = "JPY"

    def __post_init__(self) -> None:
        if self.amount < 0:
            raise ValueError(f"amount must not be negative: {self.amount}")

    def __add__(self, other: "Money") -> "Money":
        self._check_currency(other)
        return Money(self.amount + other.amount, self.currency)

    def __mul__(self, times: int) -> "Money":
        return Money(self.amount * times, self.currency)

    def _check_currency(self, other: "Money") -> None:
        if self.currency != other.currency:
            raise ValueError(
                f"currency mismatch: {self.currency} and {other.currency}"
            )

    def __str__(self) -> str:
        return f"{self.amount:,} {self.currency}"

Money を使うと、次のことが保証されます。

  • 負の金額は作れません。

  • 通貨の異なる金額どうしを足すと、エラーになります（int のままだと、円とドルを足しても気付けません）。

  • 金額の表示の形式が 1 か所にまとまります。

値オブジェクトを使うと、規則を確認するコードがプログラムのあちこちに散らばらず、値オブジェクトの中に集まります。金額を扱う関数は、受け取った Money が正しいことを前提にできます。

5.5. 列挙型で状態を表す

注文の状態（下書き、確定、発送済み、取り消し）のように、取り得る値が決まっているデータは、文字列ではなく 列挙型（enum.Enum）で表します。

ch05_data.py
class OrderStatus(Enum):
    """注文の状態です."""

    DRAFT = "draft"
    PLACED = "placed"
    SHIPPED = "shipped"
    CANCELLED = "cancelled"

文字列で "shiped" と綴りを誤っても実行時まで気付けませんが、OrderStatus.SHIPED と書けば、mypy がエラーとして検出します。また、状態の一覧が 1 か所にまとまるので、どのような状態があり得るのかが一目で分かります。

5.6. 不正な状態を表現できない型

データの型を設計するときは、あり得ない組み合わせを、そもそも表現できないようにする と、多くの不具合を防げます。

たとえば、配送の状態を次のように表すとします。

# 悪い例: 状態と追跡番号の組み合わせに矛盾が起こり得る
@dataclass
class Shipment:
    status: str                    # "preparing" または "shipped"
    tracking_number: str | None    # 発送済みのときだけ値がある

この型では、「準備中なのに追跡番号がある」「発送済みなのに追跡番号がない」という矛盾したデータを作れてしまいます。状態ごとに型を分けると、矛盾したデータは作れなくなります。

# 良い例: 状態ごとに型を分ける
@dataclass(frozen=True)
class Preparing:
    pass

@dataclass(frozen=True)
class Shipped:
    tracking_number: str       # 発送済みなら必ず追跡番号がある

Shipment = Preparing | Shipped

Shipment を受け取る関数は、isinstance や match 文で状態を判定します。Shipped と判定されたあとでは、tracking_number が必ず存在することを、mypy も理解します。

5.7. まとめ

  • 業務上の概念は、辞書や基本的な型のまま持ち回らず、型を定義して表します。

  • データの型は、特に理由がなければ dataclass で定義します。

  • 変更する必要のないデータは、frozen=True で不変にします。

  • 値に関する規則と操作は、値オブジェクトにまとめます。

  • 取り得る値が決まっているデータは、列挙型で表します。

  • あり得ない組み合わせを表現できない型を設計します。
