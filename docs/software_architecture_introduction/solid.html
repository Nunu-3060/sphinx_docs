7. SOLID 原則

SOLID 原則 は、R. C. Martin がまとめた、オブジェクト指向設計の 5 つの原則の総称です。5 つの原則の頭文字を並べた「SOLID」という呼び名は、M. Feathers が付けたものです。どの原則も、変更に強い設計を目指すという点で共通しています。

頭文字

原則

要約

S

単一責任の原則（Single Responsibility Principle）

クラスを変更する理由は 1 つだけであるべきです。

O

開放閉鎖の原則（Open-Closed Principle）

ソフトウェアの部品は、拡張に対して開いていて、変更に対して閉じているべきです。

L

リスコフの置換原則（Liskov Substitution Principle）

サブクラスは、基底クラスの代わりに使えるべきです。

I

インターフェース分離の原則（Interface Segregation Principle）

利用者に、使わないメソッドへの依存を強いるべきではありません。

D

依存性逆転の原則（Dependency Inversion Principle）

上位の方針は、下位の詳細に依存すべきではありません。どちらも抽象に依存すべきです。

この章では、各原則について、原則に反する例と、原則に従って改善した例を示します。

7.1. 単一責任の原則（SRP）

単一責任の原則は、「クラスを変更する理由は 1 つだけであるべき」という原則です。Martin はのちに、「変更する理由」とは、そのクラスに変更を求める 人や組織（アクター） のことだと説明しています。つまり、1 つのクラスは、1 つのアクターに対してだけ責任を負うべきだということです。

次の BadEmployee クラスは、給与の計算、勤務時間の報告、保存用のデータの作成という 3 つの責任を持っています。

ch07_srp.py（悪い例）
class BadEmployee:
    """従業員（悪い例）."""

    def __init__(self, name: str, hourly_wage: int, hours: float) -> None:
        self.name = name
        self.hourly_wage = hourly_wage
        self.hours = hours

    def calculate_pay(self) -> int:
        """給与を計算します（経理部門が変更を求める）."""
        return int(self.hourly_wage * self.hours)

    def report_hours(self) -> str:
        """勤務時間の報告を作ります（人事部門が変更を求める）."""
        return f"{self.name}: {self.hours} 時間"

    def to_json(self) -> str:
        """保存用の JSON を作ります（システム管理者が変更を求める）."""
        return json.dumps(self.__dict__, ensure_ascii=False)

この 3 つのメソッドは、変更を求めるアクターがそれぞれ異なります。給与の計算の方法は経理部門が、勤務時間の報告の形式は人事部門が、保存の形式はシステムの管理者が変更を求めます。1 つのクラスにまとめていると、経理部門の要求で給与の計算を変更したときに、人事部門の報告まで壊してしまう危険があります。また、複数の人が同じファイルを同時に変更することになり、変更の衝突も起きやすくなります。

責任ごとにクラスを分けると、ある部門の要求による変更は、その部門に対応するクラスだけに収まります。

ch07_srp.py（良い例）
@dataclass(frozen=True)
class Employee:
    """従業員のデータだけを持ちます."""

    name: str
    hourly_wage: int
    hours: float


class PayCalculator:
    """給与を計算します."""

    def calculate(self, employee: Employee) -> int:
        """給与を返します."""
        return int(employee.hourly_wage * employee.hours)


class HourReporter:
    """勤務時間の報告を作ります."""

    def report(self, employee: Employee) -> str:
        """勤務時間の報告の文字列を返します."""
        return f"{employee.name}: {employee.hours} 時間"


class EmployeeJsonSerializer:
    """従業員のデータを JSON に変換します."""

    def dumps(self, employee: Employee) -> str:
        """JSON の文字列を返します."""
        return json.dumps(asdict(employee), ensure_ascii=False)

7.2. 開放閉鎖の原則（OCP）

開放閉鎖の原則は、「ソフトウェアの部品は、拡張に対して開いていて、変更に対して閉じているべき」という原則です。B. Meyer が 1988 年に提唱しました。新しい機能を追加するときに、既存のコードを変更するのではなく、新しいコードを追加することで対応できるようにする、という意味です。

次の bad_total_area は、図形の種類ごとに分岐して面積を計算しています。三角形を追加するには、この関数を変更しなければなりません。

ch07_ocp.py（悪い例）
def bad_total_area(shapes: Iterable[BadShape]) -> float:
    """面積の合計を返します（悪い例）."""
    total = 0.0
    for shape in shapes:
        if shape.kind == "rectangle":
            total += shape.width * shape.height
        elif shape.kind == "circle":
            total += math.pi * shape.radius ** 2
        # 三角形を追加するには、ここに分岐を追加する必要がある
    return total

良い例では、図形が自分自身の面積を計算する area メソッドを持ち、total_area は area を呼ぶだけです。三角形を追加しても、total_area は変更しません。

ch07_ocp.py（良い例）
class Shape(Protocol):
    """図形のインターフェースです."""

    def area(self) -> float:
        """面積を返します."""
        ...


@dataclass(frozen=True)
class Rectangle:
    """長方形です."""

    width: float
    height: float

    def area(self) -> float:
        return self.width * self.height


@dataclass(frozen=True)
class Circle:
    """円です."""

    radius: float

    def area(self) -> float:
        return math.pi * self.radius ** 2


@dataclass(frozen=True)
class Triangle:
    """三角形です. 追加しても total_area 関数は変更しません."""

    base: float
    height: float

    def area(self) -> float:
        return self.base * self.height / 2


def total_area(shapes: Iterable[Shape]) -> float:
    """面積の合計を返します（良い例）."""
    return sum(shape.area() for shape in shapes)

ch07_ocp.py

すべての変更に対して閉じた設計を作ることはできません。この例でも、図形の種類の追加には閉じていますが、「すべての図形に周囲の長さを求める機能を追加する」という変更には閉じていません。どの種類の変更に対して閉じるべきかは、実際に起きた変更や、起きることが予想される変更をもとに判断します。

7.3. リスコフの置換原則（LSP）

リスコフの置換原則は、B. Liskov が 1987 年に提唱した原則です。基底クラスの型のオブジェクトを使っているプログラムで、そのオブジェクトをサブクラスのオブジェクトに置き換えても、プログラムが正しく動き続けなければならない、というものです。

この原則を守るには、サブクラスは基底クラスの約束を破ってはなりません。具体的には、次のようなことをしてはいけません。

  • 基底クラスよりも厳しい条件を、引数に課すこと（事前条件を強めること）

  • 基底クラスが保証していた結果を保証しないこと（事後条件を弱めること）

  • 基底クラスの利用者が想定していない種類の例外を送出すること

次の BadReadOnlyFile は、読み書きできるファイル BadFile を継承していますが、write を呼ぶと例外を送出します。BadFile を受け取る関数に BadReadOnlyFile を渡すと、その関数は実行時に失敗します。型の上では正しい呼び出しなので、mypy もこの誤りを検出できません。

ch07_lsp.py（悪い例）
class BadFile:
    """読み書きできるファイル（悪い例）."""

    def __init__(self) -> None:
        self._data = ""

    def read(self) -> str:
        return self._data

    def write(self, text: str) -> None:
        self._data += text


class BadReadOnlyFile(BadFile):
    """読み込み専用のファイル（悪い例）. write の約束を破っています."""

    def write(self, text: str) -> None:
        raise PermissionError("read-only file")


def bad_append_log(file: BadFile, message: str) -> None:
    """ファイルにログを追記します. 型の上では BadReadOnlyFile も渡せます."""
    file.write(message + "\n")

良い例では、「読める」と「書ける」を別々の Protocol に分けます。読み込み専用のファイルは Readable だけを満たし、書き込みの必要な関数は Writable を受け取ります。読み込み専用のファイルを append_log に渡すと、実行する前に mypy がエラーとして検出します。

ch07_lsp.py（良い例）
class Readable(Protocol):
    """読み込みのできるもの."""

    def read(self) -> str:
        ...


class Writable(Protocol):
    """書き込みのできるもの."""

    def write(self, text: str) -> None:
        ...


class MemoryFile:
    """読み書きできるファイルです（Readable と Writable の両方を満たす）."""

    def __init__(self, data: str = "") -> None:
        self._data = data

    def read(self) -> str:
        return self._data

    def write(self, text: str) -> None:
        self._data += text


class ReadOnlyFile:
    """読み込み専用のファイルです（Readable だけを満たす）."""

    def __init__(self, data: str) -> None:
        self._data = data

    def read(self) -> str:
        return self._data


def append_log(file: Writable, message: str) -> None:
    """ファイルにログを追記します. ReadOnlyFile を渡すと mypy が検出します."""
    file.write(message + "\n")


def show(file: Readable) -> None:
    """ファイルの内容を表示します. どちらのファイルも渡せます."""
    print(repr(file.read()))

ch07_lsp.py

リスコフの置換原則の例として、「正方形は長方形の一種なので、Square は Rectangle を継承する」という設計もよく取り上げられます。Rectangle に幅と高さを別々に変更するメソッドがあると、Square はその約束（幅だけを変えても高さは変わらない）を守れません。数学的に「一種である」ことと、プログラムの上で置き換えられることは、別の問題です。

7.4. インターフェース分離の原則（ISP）

インターフェース分離の原則は、「利用者に、使わないメソッドへの依存を強いるべきではない」という原則です。大きなインターフェースを 1 つ作るのではなく、利用者ごとに必要なメソッドだけを持つ小さなインターフェースに分けます。

次の BadMachine は、印刷、スキャン、ファクスのすべてを要求する抽象基底クラスです。印刷しかできないプリンターも、使わないメソッドを実装しなければならず、実装の中身は例外を送出するだけになります。これは、リスコフの置換原則にも反しています。

ch07_isp.py（悪い例）
class BadMachine(ABC):
    """複合機のインターフェース（悪い例）."""

    @abstractmethod
    def print_document(self, document: str) -> None:
        ...

    @abstractmethod
    def scan(self) -> str:
        ...

    @abstractmethod
    def fax(self, number: str, document: str) -> None:
        ...


class BadSimplePrinter(BadMachine):
    """印刷しかできないプリンター（悪い例）."""

    def print_document(self, document: str) -> None:
        print(f"[print] {document}")

    def scan(self) -> str:
        raise NotImplementedError("scan is not supported")

    def fax(self, number: str, document: str) -> None:
        raise NotImplementedError("fax is not supported")

良い例では、印刷とスキャンを別々の Protocol に分けます。print_report は印刷の能力だけを要求するので、印刷しかできないプリンターも、複合機も渡せます。

ch07_isp.py（良い例）
class Printer(Protocol):
    """印刷のできるもの."""

    def print_document(self, document: str) -> None:
        ...


class Scanner(Protocol):
    """スキャンのできるもの."""

    def scan(self) -> str:
        ...


class SimplePrinter:
    """印刷しかできないプリンターです. 使わないメソッドを持ちません."""

    def print_document(self, document: str) -> None:
        print(f"[print] {document}")


class MultiFunctionPrinter:
    """印刷とスキャンのできる複合機です."""

    def print_document(self, document: str) -> None:
        print(f"[mfp print] {document}")

    def scan(self) -> str:
        return "scanned document"


def print_report(printer: Printer) -> None:
    """レポートを印刷します. 印刷の能力だけを要求します."""
    printer.print_document("月次レポート")


def copy_document(scanner: Scanner, printer: Printer) -> None:
    """スキャンした文書を印刷します."""
    printer.print_document(scanner.scan())

7.5. 依存性逆転の原則（DIP）

依存性逆転の原則は、次の 2 つの文で表されます。

  • 上位のモジュールは、下位のモジュールに依存すべきではありません。どちらも抽象に依存すべきです。

  • 抽象は、詳細に依存すべきではありません。詳細が、抽象に依存すべきです。

ここで「上位」とは、アプリケーションの方針（何をするか）を決める部分、「下位」とは、それを実現する詳細（どうやってするか）を担う部分のことです。たとえば、パスワードの再設定の手順は上位の方針で、メールを SMTP で送信する処理は下位の詳細です。

次の悪い例では、上位の BadPasswordReset が、下位の SmtpMailer を直接作って使っています。

ch07_dip.py（悪い例）
class SmtpMailer:
    """SMTP でメールを送信します（ここでは表示するだけ）."""

    def send_mail(self, address: str, subject: str, body: str) -> None:
        print(f"[smtp] {address} / {subject} / {body}")


class BadPasswordReset:
    """パスワードの再設定（悪い例）."""

    def __init__(self) -> None:
        self._mailer = SmtpMailer()  # 具体的なクラスを直接生成している

    def request(self, address: str) -> None:
        token = "abc123"
        self._mailer.send_mail(address, "パスワードの再設定",
                               f"確認コード: {token}")

この設計では、送信の方法を SMTP から別のサービスに変えるたびに BadPasswordReset を変更する必要があります。また、BadPasswordReset をテストすると、本物のメールが送信されてしまいます。

良い例では、上位の PasswordReset が、自分に必要な機能を MessageSender という抽象（Protocol）として定義し、それだけに依存します。下位の SmtpSender は、この抽象を満たすように実装します。

ch07_dip.py（良い例）
class MessageSender(Protocol):
    """パスワードの再設定が必要とする、メッセージ送信の抽象です."""

    def send(self, to: str, title: str, body: str) -> None:
        ...


class PasswordReset:
    """パスワードの再設定（良い例）. 抽象だけに依存します."""

    def __init__(self, sender: MessageSender) -> None:
        self._sender = sender

    def request(self, address: str) -> None:
        token = "abc123"
        self._sender.send(address, "パスワードの再設定",
                          f"確認コード: {token}")


class SmtpSender:
    """SMTP による MessageSender の実装です（ここでは表示するだけ）."""

    def send(self, to: str, title: str, body: str) -> None:
        print(f"[smtp] {to} / {title} / {body}")


class RecordingSender:
    """送信内容を記録するだけの MessageSender です（テスト用）."""

    def __init__(self) -> None:
        self.sent: list[tuple[str, str, str]] = []

    def send(self, to: str, title: str, body: str) -> None:
        self.sent.append((to, title, body))

ch07_dip.py

依存の向きを図にすると、次のようになります。悪い例では、上位から下位へ依存の矢印が向いています。良い例では、下位の SmtpSender から抽象に向かって矢印が向いています。上位から下位へ向かっていた依存の向きが 逆転 しているので、依存性逆転の原則と呼ばれます。

抽象の MessageSender は、上位の PasswordReset の側で定義する点が重要です。抽象の形は、それを使う上位の都合で決まります。下位の都合（SMTP のメソッドの名前や引数）が上位に漏れ出さないので、2 つ目の文の「抽象は、詳細に依存すべきではない」も満たされます。

依存性逆転の原則は、依存関係の管理 の依存性注入や、アーキテクチャパターン のヘキサゴナルアーキテクチャとクリーンアーキテクチャの土台になっています。

7.6. 原則を適用するときの注意

SOLID 原則は強力ですが、すべてのコードに最大限に適用すればよいわけではありません。

  • 変更が起きていない箇所に、先回りして適用しないようにします。 小さなスクリプトのすべてのクラスに Protocol を用意すると、コードは読みにくくなるだけです。同じ種類の変更が実際に起きたときや、テストのために差し替えが必要になったときに適用します。

  • 原則の間の釣り合いを取ります。 単一責任の原則を突き詰めてクラスを細かく分けすぎると、処理の流れを追うために多くのファイルを行き来することになります。

  • Python の機能を活用します。 Java などの言語ではクラスとインターフェースで実現することも、Python では関数を引数に渡すだけで実現できることがあります（デザインパターン を参照）。

7.7. まとめ

  • 単一責任の原則: クラスは 1 つのアクターに対してだけ責任を負います。

  • 開放閉鎖の原則: 機能の追加は、既存のコードの変更ではなく、新しいコードの追加で行えるようにします。

  • リスコフの置換原則: サブクラスは基底クラスの約束を守り、基底クラスの代わりに使えるようにします。

  • インターフェース分離の原則: 利用者ごとに、必要なメソッドだけを持つ小さなインターフェースにします。

  • 依存性逆転の原則: 上位の方針が定めた抽象に、下位の詳細を従わせます。
