ライフタイム

この章では、Rust の中でも特に難しく感じられやすい「ライフタイム」について学びます。ライフタイムは新しい機能というよりも、これまで暗黙のうちにコンパイラが行っていたチェックを、私たちが明示的に読み書きできるようにしたものです。

ライフタイムとは何か

Rust には Python のようなガベージコレクタ(GC)がありません。値がいつメモリから解放されるかは、所有者がスコープを抜けるタイミングで静的に決まります。ここで問題になるのが「参照」です。ある値への参照 &T を持ち回っているとき、その参照先の値が先に解放されてしまうと、参照は無効なメモリを指す「ダングリング参照」になってしまいます。

具体的に見てみましょう。次のコードは、ブロックの中で生成した String への参照を、ブロックの外に返そうとしています。

fn dangling_reference() -> &String {
    let s = String::from("hello");
    &s
} // s はここでスコープを抜けて解放される

fn main() {
    let r = dangling_reference(); // コンパイルエラー
}

s はこの関数を抜けると同時にメモリから解放されるため、戻り値の参照 &s は無効なメモリを指すことになります。Rust のコンパイラはこれを検出し、「missing lifetime specifier」といったエラーを出してコンパイルを拒否します。このように、借用チェッカーが実際に何を防いでいるのかを具体的に確認したところで、次にその仕組みを支える「ライフタイム」という概念を見ていきましょう。

Rust の借用チェッカーは、すべての参照について「その参照は有効な期間内でしか使われていないか」をコンパイル時に検証します。この「参照が有効な期間」のことを ライフタイム と呼びます。ライフタイムは実行時には一切コストがかからない、コンパイル時だけの概念です。

多くの場合、ライフタイムは変数のスコープから自動的に推論されるため、私たちが明示的に書く必要はありません。しかし、関数が複数の参照を受け取り、その参照を戻り値として返すような場合には、どの引数とどの戻り値が同じ有効期間を共有するのかを明示しなければならないことがあります。

ライフタイム注釈の書き方

ライフタイム注釈は 'a のようにアポストロフィに続けて短い名前を書きます。たとえば、2つの文字列スライスのうち長い方を返す関数を考えてみましょう。

fn longest<'a>(x: &'a str, y: &'a str) -> &'a str {
    if x.len() > y.len() {
        x
    } else {
        y
    }
}

fn main() {
    let s1 = String::from("long string is long");
    let s2 = String::from("short");

    let result = longest(s1.as_str(), s2.as_str());
    println!("longest string is {}", result);
}

この 'a は「新しいライフタイムを作り出す」ものではありません。むしろ、「引数 x、y、そして戻り値はすべて同じライフタイム 'a を共有する」という制約をコンパイラに伝えているだけです。言い換えると、戻り値の参照は x と y のうち短い方の有効期間よりも長くは生きられない、ということを保証しています。もしこの注釈がなければ、コンパイラは戻り値の参照がどの引数に由来するのか判断できず、コンパイルエラーになります。

ライフタイム省略規則

実際には、関数定義の多くでライフタイム注釈を書く必要はありません。Rust には「ライフタイム省略規則(lifetime elision rules)」と呼ばれる推論ルールがあり、典型的なパターン(引数が1つだけ参照を取る、&self を取るメソッドであるなど)については、コンパイラが自動的にライフタイムを補ってくれます。

// 引数が1つなので、ライフタイム注釈を省略できる
fn first_word(s: &str) -> &str {
    s.split_whitespace().next().unwrap_or("")
}

ライフタイム注釈が必要になるのは、longest のように複数の参照の関係が曖昧になる場合に限られます。まずは「エラーが出たら注釈を追加する」くらいの気持ちで学習を進めるとよいでしょう。

Python 経験者向けメモ

ライフタイムは Python には存在しない概念です。Python では GC がすべてのオブジェクトの生存期間を実行時に管理してくれるため、参照先がいつまで有効かを意識する必要がありません。Rust では GC の代わりに、参照が指すデータがどの範囲まで有効であるかをコンパイラに伝える仕組みが必要であり、それがライフタイムの役割です。実行時のオーバーヘッドを払わずに安全性を保証する、Rust らしい設計だといえます。

なお、ライフタイムの中には 'static という特別なものがあります。これはプログラム全体の実行期間を通じて有効なライフタイムを表し、文字列リテラルなど一部の値はこの 'static ライフタイムを持ちます。詳細は必要になったときに学べば十分です。

また、関数だけでなく構造体のフィールドが参照を持つ場合にも、同様にライフタイム注釈が必要になります。次のように、フィールドが参照である構造体には <'a> を付け、そのフィールドが少なくとも構造体自身と同じだけ長く生きることをコンパイラに伝えます。

struct Important<'a> {
    part: &'a str,
}

このような構造体にメソッドを実装する場合、impl ブロックにも同じライフタイム注釈を書く必要があります。

impl<'a> Important<'a> {
    fn announce(&self) -> &str {
        println!("お知らせ: {}", self.part);
        self.part
    }
}

impl<'a> Important<'a> の <'a> は、構造体定義で使ったライフタイムパラメータをこの impl ブロックでも使うことを示しています。メソッドの引数や戻り値のライフタイムの多くはライフタイム省略規則によって自動的に推論されるため、この書き方さえ覚えてしまえば難しいことはありません。

まとめ

  • ライフタイムは、参照が有効な期間を借用チェッカーに伝えるための仕組みです。

  • 'a のような注釈は、複数の参照や戻り値が同じ有効期間を共有することを表します。

  • fn longest<'a>(x: &'a str, y: &'a str) -> &'a str のように、関数シグネチャにライフタイムパラメータを書くことがあります。

  • ライフタイム省略規則により、多くの関数では注釈を省略できます。

  • struct Important<'a> { part: &'a str } のように、参照をフィールドに持つ構造体にもライフタイム注釈が必要です。

  • そのような構造体に impl ブロックを書く場合も、impl<'a> Important<'a> のように同じライフタイムパラメータを付けます。

  • Python の GC には無い、コンパイル時のみのコストで安全性を保証する仕組みです。
