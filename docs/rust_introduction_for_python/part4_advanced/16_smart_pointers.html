スマートポインタ(概論)

これまで扱ってきた参照(&T)は、あくまで既存の値を「借用」するだけの仕組みでした。この章では、値の所有権や生存期間そのものを管理する「スマートポインタ」と呼ばれる型を、代表的なものに絞って概論として紹介します。細部の実装までは踏み込まず、それぞれが「何のために使うのか」を押さえることを目標とします。あわせて、章の後半では実行時ポリモーフィズムを実現する「トレイトオブジェクト(dyn)」についても扱います。

Box<T>: ヒープへの単純な確保

Box<T> は最も単純なスマートポインタで、値をスタックではなくヒープに確保します。中身へのアクセスは通常の参照とほとんど変わりませんが、サイズがコンパイル時に決まらないデータや、大きなデータを所有権ごと移動させたい場合に便利です。

代表的な用途が、再帰的なデータ構造です。次のような連結リストは、Box がなければ型のサイズが無限になってしまい定義できません。

enum List {
    Cons(i32, Box<List>),
    Nil,
}

use List::{Cons, Nil};

fn main() {
    let list = Cons(1, Box::new(Cons(2, Box::new(Cons(3, Box::new(Nil))))));
    // list はヒープ上に確保された値へのポインタを内部に持つ
    if let Cons(value, _) = list {
        println!("先頭の値: {}", value);
    }
}

Box<List> によって「次の要素へのポインタ」のサイズだけを List が持てばよくなるため、コンパイラは List 全体のサイズを決定できるようになります。

Rc<T>: 複数所有を許す参照カウント型

Rust の所有権システムでは、通常1つの値の所有者は1つだけです。しかし、グラフ構造のように「複数の場所から同じデータを参照したい」場面もあります。そこで使うのが Rc<T> (reference counted の略)です。

use std::rc::Rc;

fn main() {
    let a = Rc::new(String::from("shared data"));
    println!("参照カウント: {}", Rc::strong_count(&a)); // 1

    let b = Rc::clone(&a);
    println!("参照カウント: {}", Rc::strong_count(&a)); // 2

    let c = Rc::clone(&a);
    println!("参照カウント: {}", Rc::strong_count(&a)); // 3

    drop(b);
    drop(c);
    println!("参照カウント: {}", Rc::strong_count(&a)); // 1
}

Rc::clone はデータそのものをコピーするのではなく、参照カウントを増やすだけの軽い操作です。カウントが0になったときに初めてヒープ上のデータが解放されます。ただし Rc<T> はスレッド間で安全に共有できない点に注意してください(スレッド間で共有したい場合は、次章で扱う Arc<T> を使います)。

なお、Rc<T> 同士が親子関係のように互いを参照し合う構造を作ると、それぞれの参照カウントがいつまでも0にならず、メモリが解放されない「循環参照」が起こることがあります。これを避けるために、所有権を持たない(参照カウントを増やさない)弱い参照である Weak<T> が用意されています。たとえば親から子への参照には Rc<T>、子から親への参照には Weak<T> を使うことで、循環を断ち切ることができます。

RefCell<T>: 実行時借用チェックによる内部可変性

通常、借用ルール(不変参照は複数、可変参照はただ1つ)はコンパイル時にチェックされます。しかし RefCell<T> を使うと、このチェックを実行時に遅らせることができます。これを「内部可変性」と呼びます。

use std::cell::RefCell;

fn main() {
    let cell = RefCell::new(5);

    {
        let mut value = cell.borrow_mut();
        *value += 1;
    }

    println!("値: {}", cell.borrow());
}

borrow() は不変参照、borrow_mut() は可変参照を実行時に取得します。もし同時に複数の可変参照を取得しようとすると、コンパイルは通ってしまいますが、実行時にパニックします。コンパイル時の借用チェックでは表現しきれないパターン(例えば Rc<RefCell<T>> として複数箇所から共有しつつ中身を書き換えたい場合など)で活躍します。

RefCell<T> の兄弟にあたる型として Cell<T> もあります。Cell<T> は Copy を実装した型に対して、get と set というメソッドだけで内部可変性を提供するシンプルな型です。参照を取得する仕組みを持たないため、RefCell<T> のような実行時の借用チェック(および違反時のパニック)のコストが一切かかりません。

Python 経験者向けメモ

Python のオブジェクトはすべて内部的に参照カウントで管理されており、複数の変数から同じオブジェクトを指すことはごく普通に行われます。一方 Rust では、値は基本的に1つの所有者にしか属せず、複数の場所から同じデータを所有したい場合にだけ Rc<T> のような型を明示的に選択します。つまり Python が「常に参照カウント」なのに対し、Rust は「必要なときだけ参照カウント」という考え方です。同様に RefCell<T> も、Python では意識すらしない「実行時に借用ルールを守っているかチェックする」という仕組みを、明示的な型として表現したものだと捉えると理解しやすいでしょう。

トレイトオブジェクト(dyn)

ジェネリクスとトレイトの章では、fn notify<T: Summary>(item: &T) のようにジェネリクスとトレイト境界を組み合わせる書き方を学びました。その章と、エラーハンドリングの章に登場した Box<dyn Error> について、いずれも「dyn (トレイトオブジェクト)については、スマートポインタの章で詳しく説明します」と予告していました。ここでその内容を説明します。

fn notify<T: Summary>(item: &T) のようなジェネリクスを使った関数は、コンパイル時に呼び出し側の具体的な型ごとに専用のコードが生成されます。これを 静的ディスパッチ と呼びます。どのメソッドを呼び出すかがコンパイル時に確定しているため、実行速度の面で有利です。

これに対して dyn を使うと、fn notify(item: &dyn Summary) のように「Summary を実装した何らかの型」を表す書き方ができます。この場合、item の具体的な型は実行時になるまで分からず、summarize の呼び出しは実行時に解決されます。これを 動的ディスパッチ と呼び、&dyn Summary や Box<dyn Summary> のような書き方全般を「トレイトオブジェクト」と呼びます。

trait Summary {
    fn summarize(&self) -> String;
}

// ジェネリクス版: 静的ディスパッチ(型ごとにコードが生成される)
fn notify_static<T: Summary>(item: &T) {
    println!("速報(静的): {}", item.summarize());
}

// トレイトオブジェクト版: 動的ディスパッチ(実行時に実装が決まる)
fn notify_dynamic(item: &dyn Summary) {
    println!("速報(動的): {}", item.summarize());
}

トレイトオブジェクトが特に役立つのは、実行時までどの具体的な型が来るか分からない場合です。代表的な例が、性質の異なる複数の型を1つの Vec にまとめて格納したいケースです。Vec<T> の要素はすべて同じ型 T でなければなりませんが、要素の型を Box<dyn Summary> にすれば、Summary さえ実装していれば異なる構造体を同じ Vec に混在させられます。

struct Article {
    title: String,
}

impl Summary for Article {
    fn summarize(&self) -> String {
        format!("記事: {}", self.title)
    }
}

struct Tweet {
    username: String,
}

impl Summary for Tweet {
    fn summarize(&self) -> String {
        format!("ツイート by {}", self.username)
    }
}

fn main() {
    let items: Vec<Box<dyn Summary>> = vec![
        Box::new(Article { title: String::from("Rust入門") }),
        Box::new(Tweet { username: String::from("rustlang") }),
    ];

    for item in &items {
        println!("{}", item.summarize());
    }
}

Article と Tweet はまったく別の型ですが、どちらも Summary を実装しているため、Box<dyn Summary> として同じ Vec にまとめられます。それぞれの Box の中身は実行時にしか分からない別々の型であり、summarize を呼び出すたびに、実際に入っている型に応じた実装が動的に選ばれます。

エラーハンドリングの章で登場した Box<dyn Error> も、このトレイトオブジェクトの一種です。

fn main() -> Result<(), Box<dyn std::error::Error>> {
    Ok(())
}

関数の中で起こりうるエラーの型が複数ある場合(ファイルI/Oのエラー、パースのエラーなど)、それぞれの型を毎回列挙するのは大変です。Box<dyn Error> は「Error トレイトさえ実装していれば、どんな種類のエラーでも受け取れる箱」として使うことで、複数の異なるエラー型を1つの戻り値の型でまとめて表現できるようにしています。

Python 経験者向けメモ

Python は動的型付けの言語なので、obj.summarize() のようなメソッド呼び出しは、実行時にならないとどのクラスの実装が呼ばれるか分かりません。つまり Python のメソッド呼び出しは、実質的に常に「動的ディスパッチ」だといえます。Rust ではこれとは逆に、基本的には静的ディスパッチが使われ、コンパイル時にどの実装を呼ぶかが決まります。dyn を明示的に使ったときだけ、Python のメソッド呼び出しに近い「実行時に実装を決める」動的ディスパッチになる、と捉えると理解しやすいでしょう。

まとめ

  • Box<T> は値をヒープに確保するシンプルなスマートポインタで、再帰的なデータ構造の定義などに使います。

  • Rc<T> は参照カウント方式で複数所有を実現し、clone するたびにカウントが増え、参照がなくなるとカウントが減ります。

  • RefCell<T> は借用ルールのチェックを実行時に行うことで、内部可変性を実現します。

  • Rc<RefCell<T>> のように組み合わせることで、複数箇所から共有しつつ中身を書き換えるデータ構造を表現できます。

  • ジェネリクスは静的ディスパッチ(コンパイル時に型ごとのコードを生成)、dyn を使ったトレイトオブジェクトは動的ディスパッチ(実行時に実装を決定)という違いがあります。

  • Box<dyn Trait> は、Vec<Box<dyn Summary>> のように異なる型をまとめて扱いたい場合や、Box<dyn Error> のようにどんな種類のエラーでも受け取りたい場合によく使われます。

  • 本章はあくまで概論であり、より高度な使い方や Weak<T> などは必要になったときに個別に学ぶとよいでしょう。
