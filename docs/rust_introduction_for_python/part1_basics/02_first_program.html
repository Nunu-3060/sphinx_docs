最初のプログラム

前章で環境構築が終わったら、いよいよ最初の Rust プログラムを作成します。Rust のプロジェクト作成やビルドには cargo というツールを使うのが一般的です。cargo は Python でいう pip と venv と setuptools を合わせたような役割を持つ、Rust の公式パッケージマネージャ兼ビルドツールです。

Hello World の作成

新しいプロジェクトを作るには、任意のディレクトリで次のコマンドを実行します。

cargo new hello_rust
cd hello_rust

このコマンドを実行すると、hello_rust という名前のディレクトリが作成され、その中に雛形一式が生成されます。生成直後の src/main.rs には、すでに「Hello, world!」を表示するプログラムが書かれています。

fn main() {
    println!("Hello, world!");
}

fn main() はプログラムの実行開始地点となる関数(エントリポイント)です。println! は文字列を標準出力に改行付きで表示するマクロで、末尾の ! はこれが通常の関数ではなくマクロであることを示しています。

関数とマクロの違い

Rust のコンパイルは、大まかに次の2段階で進みます。

  1. マクロ展開: ソースコード中のマクロ呼び出し(println!(...) や vec![...] など)を、すべて実際の Rust コードに置き換える

  2. 通常のコンパイル: 展開が終わったコードに対して、型チェック・借用チェック・コード生成を行う

つまりマクロを使うということは、コードを全部自分で書く代わりに、決まったパターンのコードをコンパイラに自動生成してもらう、ということです。例えば vec![1, 2, 3] は、コンパイラの内部では次のようなコードに置き換わってから、通常のコンパイルが進みます(実際の展開結果はもう少し複雑ですが、考え方はこの通りです)。

// vec![1, 2, 3] は、概ね次のようなコードに展開される
let v = {
    let mut temp_vec = Vec::new();
    temp_vec.push(1);
    temp_vec.push(2);
    temp_vec.push(3);
    temp_vec
};

vec![1, 2, 3] という短い呼び出しは、実際には存在しない架空の「関数」であり、コンパイラがその場で push を必要な回数だけ並べたコードに書き換えているだけです。

なぜ関数ではなくマクロが使われるのでしょうか。Rust の関数は、引数の個数と型があらかじめ固定されています。fn foo(a: i32, b: i32) は常にちょうど2つの i32 しか受け取れません。ところが println!("{} {} {}", a, b, c) のように、引数の個数も型も呼び出しごとに変わるものは、通常の関数シグネチャでは表現できません。マクロは実行時の「値」ではなく、呼び出し時に書かれた「コードの並び」そのものを受け取って展開するため、こうした可変個・可変型の呼び出しを実現できます。また、後の章で登場する assert_eq! が失敗時に x、y といった変数名や式そのものをエラーメッセージに含められるのも、マクロが実行時の値だけでなく書かれた文字列(トークン)自体を扱えるためです。

独自にマクロを定義する方法(macro_rules! など)は本書では扱いませんが、興味があれば公式ドキュメントを参照してください。

Python 経験者向けメモ

Python には、Rust のようにコンパイル時にコードを展開する「マクロ」という仕組み自体がありません。Python の関数は *args/**kwargs によって可変長の引数を受け取れるため、マクロの必要性を感じる場面は少ないかもしれません。あえて近い概念を挙げるなら、Python のデコレータやメタクラスが「コードの振る舞いを変える」という点で似ていますが、これらは実行時(またはインポート時)に働く仕組みであり、Rust のマクロのようにコンパイル前の段階でコードそのものを書き換えるものではありません。

Cargo.toml と src/main.rs

cargo new で生成されるプロジェクトには、主に次の2つのファイルが含まれます。

  • Cargo.toml: プロジェクトの名前・バージョン・依存クレート(ライブラリ)などを記述する設定ファイルです。Python の pyproject.toml や requirements.txt に近い役割を持ちます。

  • src/main.rs: 実行可能プログラムのソースコード本体です。Rust では慣習的にソースコードを src ディレクトリ以下に置きます。

[package]
name = "hello_rust"
version = "0.1.0"
edition = "2021"

[dependencies]

外部クレートを追加する際にはこのセクションに記述します。これは Python の requirements.txt に外部パッケージ名を書くことに相当します。

ビルド・実行・チェック

cargo には、プロジェクトを操作するための複数のサブコマンドが用意されています。

cargo build   # コンパイルして実行ファイルを生成する
cargo run     # コンパイルしてすぐに実行する
cargo check   # コンパイルはせず、文法・型エラーだけを高速にチェックする

cargo build を実行すると、target/debug/ ディレクトリの下に実行可能ファイルが生成されます。cargo run は内部的に cargo build を実行したうえで、その実行ファイルを起動する便利なコマンドです。開発中にとにかく型エラーや文法ミスだけを素早く確認したい場合は、実行ファイルを生成しない cargo check を使うと高速です。

Python 経験者向けメモ

Python では python script.py を実行すればソースコードがその場でインタプリタにより解釈・実行されますが、Rust では cargo run を実行しても、裏側では必ず一度ソースコードがネイティブコードへコンパイルされてから実行されます。また Python ではソースコード以外に成果物が残ることは少ないですが、Rust では cargo build を実行すると target/ というディレクトリに中間ファイルや実行可能ファイルが蓄積されていきます。この target/ ディレクトリは自動生成物なのでバージョン管理対象からは除外するのが一般的です(.gitignore に追加します)。

コードの整形と静的解析: cargo fmt と cargo clippy

Rust には、コードの見た目や書き方を統一するための公式ツールが標準で付属しています。プロジェクトを作った直後から使える習慣として、ここで紹介しておきます。

cargo fmt      # コードを公式のスタイルに従って自動整形する
cargo clippy   # より良い書き方を提案してくれる公式のリンター(静的解析ツール)

cargo fmt はインデントや改行、スペースの入れ方などを公式のスタイルガイドに沿って自動的に整形するコマンドです。チームで開発する際にコードの見た目で揉めることがなくなり、Python でいう black に近い役割を果たします。

cargo clippy は、コンパイラだけでは指摘されない「もっと良い書き方」や「ありがちな間違い」を教えてくれるリンターです。Python の pylint や flake8 に相当し、cargo build が通るコードでも、clippy はさらに踏み込んだ改善提案をしてくれます。実務の Rust プロジェクトでは、cargo fmt と cargo clippy の両方を通すのがほぼ標準的な習慣になっています。

まとめ

  • cargo new プロジェクト名 で新しい Rust プロジェクトを作成できます

  • 関数は引数の個数・型が固定ですが、マクロ(println! など)はコンパイル時にコードへ展開されるため可変個の引数を扱えます

  • Cargo.toml はプロジェクト設定と依存関係を管理し、src/main.rs にプログラム本体を書きます

  • cargo build はビルドのみ、cargo run はビルドと実行、cargo check は型・文法チェックのみを行います

  • ビルド成果物は target/ ディレクトリに生成されます

  • cargo fmt でコードを自動整形し、cargo clippy でより良い書き方の提案を受けられます

  • Rust は実行前に必ずコンパイルが必要な言語です
