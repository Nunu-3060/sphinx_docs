10. テストしやすい設計

テストを書こうとして、「このコードはどうテストすればよいのか分からない」と感じることがある。その原因の多くは、テストの技術ではなく、コードの設計にある。この章では、テストしにくいコードの特徴と、それをテストしやすくする設計の方法を学ぶ。

10.1 テストしにくいコード

年末セールの割引率とクーポンコードを告知する関数を例にする。

ch10_testable_design/campaign_before.py
 1"""テストしにくい書き方の例（改善前）."""
 2
 3import random
 4from datetime import date
 5
 6
 7def announce_discount() -> None:
 8    """本日の割引率と、抽選で決まるクーポンコードを表示する."""
 9    today = date.today()
10    if today.month == 12 and today.day >= 20:
11        rate = 0.2
12    else:
13        rate = 0.0
14    code = "".join(random.choice("ABCDEFGHJKLMNPQRSTUVWXYZ") for _ in range(6))
15    print(f"本日の割引率: {rate:.0%}")
16    print(f"クーポンコード: {code}")

この関数は短く、動作も分かりやすい。しかし、テストしようとすると次の問題に突き当たる。

問題

理由

結果が日付によって変わる

今日の日付を関数の中で取得している（9 行目）。12 月 20 日の動作を確かめるには、その日にテストを実行するか、日付を差し替える必要がある。

結果が毎回変わる

クーポンコードを乱数で作っている（14 行目）。期待値を決められない。

結果を戻り値で受け取れない

結果を print で表示するだけで（15～16 行目）、戻り値がない。表示された文字列を取り出す必要がある。

複数の処理が 1 つの関数に入っている

割引率の判定、コードの生成、文章の組み立て、表示が混ざっている。割引率の判定だけをテストすることができない。

9 章の patch を使えば、日付と乱数を差し替えてテストすることはできる。しかし、date.today のような組み込みの型のメソッドは直接差し替えられないなど、テストが複雑になる。テストが書きにくいと感じたら、テストの工夫より先に、コードの設計を見直すとよい。

10.2 テストしやすくする方法

テストしにくさの原因は、主に次の 2 つである。

  • 制御できない入力：現在の時刻、乱数、環境変数、ファイルやネットワークからの入力など、テストから値を指定できないもの。

  • 観察できない出力：画面への表示、ファイルへの書き込み、メールの送信など、戻り値として受け取れないもの。

これらを副作用と呼ぶことがある。テストしやすくするには、副作用を扱う部分と、計算の部分を分ける。計算の部分は、引数だけから結果が決まり、副作用を持たない純粋関数にする。純粋関数は、引数を与えて戻り値を確かめるだけでテストできる。

副作用を扱う部分では、時刻や乱数、出力先を関数の中で作らず、外から受け取るようにする。これを依存性の注入（dependency injection）と呼ぶ。9 章の OrderNotifier が、メールの送信機能をコンストラクターの引数で受け取っていたのも、依存性の注入の例である。

10.3 改善後のコード

10.2 節の方法で、告知の関数を書き直すと次のようになる。

ch10_testable_design/campaign.py
 1"""テストしやすい書き方の例（改善後）."""
 2
 3import random
 4from collections.abc import Callable
 5from datetime import date
 6from typing import TextIO
 7
 8YEAR_END_SALE_RATE = 0.2
 9"""年末セール（12 月 20 日から 31 日まで）の割引率."""
10
11CODE_CHARS = "ABCDEFGHJKLMNPQRSTUVWXYZ"
12"""クーポンコードに使う文字（見間違えやすい I と O を除く）."""
13
14
15def discount_rate(today: date) -> float:
16    """指定した日の割引率を返す（純粋関数）."""
17    if today.month == 12 and today.day >= 20:
18        return YEAR_END_SALE_RATE
19    return 0.0
20
21
22def make_coupon_code(rng: random.Random, length: int = 6) -> str:
23    """乱数生成器を受け取り、クーポンコードを作る."""
24    return "".join(rng.choice(CODE_CHARS) for _ in range(length))
25
26
27def format_announcement(rate: float, code: str) -> str:
28    """告知文を組み立てる（純粋関数）."""
29    return f"本日の割引率: {rate:.0%}\nクーポンコード: {code}\n"
30
31
32class Campaign:
33    """時刻・乱数・出力先を外から差し替えられる、告知を行うクラス."""
34
35    def __init__(self, clock: Callable[[], date] = date.today,
36                 rng: random.Random | None = None) -> None:
37        self._clock = clock
38        self._rng = rng if rng is not None else random.Random()
39
40    def announce(self, out: TextIO) -> None:
41        """告知文を out に書き出す."""
42        rate = discount_rate(self._clock())
43        code = make_coupon_code(self._rng)
44        out.write(format_announcement(rate, code))

改善した点は次のとおりである。

  • 割引率の判定を純粋関数にした：discount_rate（15～19 行目）は日付を引数で受け取る。どの日付の動作も、引数を変えるだけで確かめられる。

  • 乱数生成器を引数で受け取る：make_coupon_code（22～24 行目）は random.Random のオブジェクトを受け取る。テストでシードを固定した乱数生成器を渡せば、結果が毎回同じになる。

  • 文章の組み立てを分けた：format_announcement（27～29 行目）は文字列を返すだけの純粋関数である。

  • 時刻・乱数・出力先を外から渡せるようにした：Campaign クラス（32～44 行目）は、日付を返す関数（clock）と乱数生成器をコンストラクターで、出力先を announce メソッドの引数で受け取る。引数を省略すると、本物の date.today と新しい乱数生成器を使う（35～38 行目）ため、普段使うときの手間は増えない。

announce の出力先の型 TextIO は、ファイルや標準出力のように文字列を書き込めるオブジェクトを表す。本番では sys.stdout を、テストでは io.StringIO を渡せる。

 4import random

14    ("today", "expected"),

16        (date(2026, 12, 19), 0.0),  # セール開始の前日

33def test_coupon_code_uses_allowed_chars() -> None:
34    code = make_coupon_code(random.Random(0), length=100)
35    assert len(code) == 100
36    assert set(code) <= set(CODE_CHARS)
37
38
39def test_format_announcement() -> None:
40    assert format_announcement(0.2, "ABCDEF") == (
41        "本日の割引率: 20%\nクーポンコード: ABCDEF\n")
42
43
44def test_announce_writes_to_given_stream() -> None:
45    campaign = Campaign(clock=lambda: date(2026, 12, 24),
46                        rng=random.Random(42))
47    out = io.StringIO()
48
49    campaign.announce(out)
50
51    expected_code = make_coupon_code(random.Random(42))
52    assert out.getvalue() == format_announcement(0.2, expected_code)

discount_rate のテスト（13～23 行目）では、セールの期間の境界の前後の日付を、4 章の境界値分析に従って選んでいる。日付を引数で渡せるため、patch は不要である。

Campaign のテスト（44～52 行目）では、clock に決まった日付を返す関数を、rng にシードを固定した乱数生成器を渡している。出力先には io.StringIO を渡し、書き込まれた文字列を getvalue で取り出して確かめている。

改善後のコードでは、テストの大部分が純粋関数のテストになった。副作用を扱う Campaign のテストは 1 つだけで済んでいる。

10.5 テストしやすい設計の指針

ここまでの内容を、設計の指針としてまとめる。

指針

内容

計算と副作用を分ける

判定や計算のロジックを純粋関数に切り出し、入出力は薄い外側の層に集める。

依存先は外から受け取る

時刻、乱数、データベース、外部サービスなどを関数やクラスの中で作らず、引数で受け取る。

結果は戻り値で返す

print やファイルへの書き込みの代わりに値を返し、出力は呼び出し側に任せる。

1 つの関数に 1 つの役割

役割ごとに関数を分けると、それぞれを個別にテストできる。

グローバルな状態を避ける

モジュールの変数を書き換えるコードは、テストの実行順によって結果が変わる原因になる。

テストしやすいコードは、多くの場合、再利用しやすく、変更しやすいコードでもある。たとえば discount_rate は、告知以外の場面（注文の金額の計算など）でもそのまま使える。テストを書くことは、設計の問題を早く知らせてくれる手段でもある。15 章のテスト駆動開発は、この効果を積極的に利用する開発の方法である。

10.6 まとめ

  • テストしにくさの主な原因は、制御できない入力と観察できない出力である。

  • 計算の部分を純粋関数に切り出すと、引数と戻り値だけでテストできる。

  • 時刻や乱数、出力先を外から受け取る（依存性の注入）と、テストで決まった値や差し替え用のオブジェクトを渡せる。

  • テストが書きにくいと感じたら、テストの工夫より先に、コードの設計を見直す。
