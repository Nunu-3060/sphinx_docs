4. ブラックボックステストの設計技法

2 章で見たとおり、すべての入力を試すことはできない。そこで、少ない数で欠陥を見つけやすいテストケースを選ぶ必要がある。この章では、仕様に基づいてテストケースを選ぶ代表的な技法を、題材の送料計算と注文の状態管理を使って説明する。ここで設計したテストケースは、8 章で pytest のテストコードとして実装する。

4.1 題材の仕様

送料計算の関数 calc_shipping_fee の仕様は次のとおりである。

  • 引数は、注文金額（円、整数）、プレミアム会員かどうか、配送先が離島かどうかの 3 つである。

  • 注文金額が負の場合は、エラー（ValueError）とする。

  • 基本送料は 500 円である。

  • 一般会員は注文金額が 5,000 円以上、プレミアム会員は 3,000 円以上のとき、基本送料が無料になる。

  • 配送先が離島の場合は、基本送料が無料かどうかにかかわらず、1,000 円を加算する。

この仕様を実装したコードは次のとおりである。ブラックボックステストではコードを見ずにテストケースを設計するが、参考のために示しておく。

shop/shipping.py
 1"""送料を計算する."""
 2
 3BASE_FEE = 500
 4"""基本送料（円）."""
 5
 6REMOTE_SURCHARGE = 1000
 7"""離島への配送で加算する料金（円）."""
 8
 9FREE_THRESHOLD = 5000
10"""一般会員の送料無料となる注文金額（円）."""
11
12MEMBER_FREE_THRESHOLD = 3000
13"""プレミアム会員の送料無料となる注文金額（円）."""
14
15
16def calc_shipping_fee(subtotal: int, is_premium: bool,
17                      is_remote: bool) -> int:
18    """注文金額と条件から送料を求める.
19
20    Args:
21        subtotal: 注文金額（円）。0 以上とする。
22        is_premium: プレミアム会員なら True。
23        is_remote: 配送先が離島なら True。
24
25    Returns:
26        送料（円）。
27
28    Raises:
29        ValueError: 注文金額が負の場合。
30    """
31    if subtotal < 0:
32        raise ValueError(f"注文金額が負です: {subtotal}")
33    threshold = MEMBER_FREE_THRESHOLD if is_premium else FREE_THRESHOLD
34    fee = 0 if subtotal >= threshold else BASE_FEE
35    if is_remote:
36        fee += REMOTE_SURCHARGE
37    return fee

4.2 同値分割

同値分割は、入力の範囲を、プログラムが同じように扱うと考えられるグループ（同値クラス）に分け、各グループから代表の値を 1 つずつ選ぶ技法である。同じ同値クラスの値は同じように処理されるはずなので、1 つの値で試せばそのクラス全体を試したとみなす。

一般会員で配送先が離島でない場合、注文金額は次の 3 つの同値クラスに分けられる。

仕様で受け付けないとされる入力の範囲を無効同値クラス、受け付ける入力の範囲を有効同値クラスと呼ぶ。無効同値クラスのテストを忘れると、不正な入力を与えたときの動作が確かめられないまま残る。

同値分割は、無数にある入力を少数のクラスにまとめることで、テストケースの数を大きく減らす。ただし、クラスの分け方を誤ると、見落としが生じる。クラスの分け方は仕様から導くものであり、仕様が曖昧であれば、その点を仕様の作成者に確認する必要がある。

4.3 境界値分析

欠陥は、同値クラスの境界に集中しやすい。2 章で例に挙げた >= と > の書き間違いは、その典型である。境界値分析は、同値クラスの境界の値と、それに隣接する値をテストケースとして選ぶ技法である。

一般会員の注文金額の境界は、無効と有効の間（0 の前後）と、送料ありと送料無料の間（5,000 の前後）の 2 か所にある。

プレミアム会員についても、同様に 2,999 と 3,000 を選ぶ。

このように、境界を挟む 2 つの値を選ぶ方法を 2 値境界値分析と呼ぶ。境界の値とその両隣の 3 つの値を選ぶ 3 値境界値分析もある。3 値の場合、送料無料の境界では 4,999、5,000、5,001 の 3 つを選ぶ。

境界値分析のテストケースで、2 章の欠陥（subtotal > 5000）を見つけられるかを確かめてみる。注文金額 5,000 円では、正しいコードは 0 円を、欠陥のあるコードは 500 円を返すため、故障が起きて欠陥が見つかる。一方、同値分割の代表値（2,000 と 8,000）では、どちらのコードも同じ結果を返すため、この欠陥は見つからない。同値分割と境界値分析は組み合わせて使うのが基本である。

4.4 デシジョンテーブル

送料は、会員の種類、注文金額、配送先の 3 つの条件の組み合わせで決まる。このように、複数の条件の組み合わせで結果が決まる場合は、デシジョンテーブル（決定表）を使って組み合わせを漏れなく洗い出す。

条件が 3 つあり、それぞれ Y と N の 2 通りであるため、規則は \(2^3 = 8\) 通りになる。各規則から 1 つずつテストケースを作る。たとえば規則 2 は、一般会員、注文金額 4,000 円（基準の 5,000 円未満）、離島の組み合わせで、期待結果は 1,500 円である。

デシジョンテーブルを作ると、仕様の漏れにも気付きやすくなる。たとえば、「送料無料のときも離島料金はかかるのか」という点は、規則 4 と規則 8 の列を埋めようとしたときに初めて問題になる。仕様にこの点が書かれていなければ、仕様の作成者に確認する。

条件の数が増えると、規則の数は \(2^n\) で増える。結果に影響しない条件がある規則をまとめて表を簡単にしたり、4.6 節の組み合わせテストを使ったりして、テストケースの数を抑える。

4.5 状態遷移テスト

注文は、「受付済み」から「支払い済み」「発送済み」へと状態が変わり、同じ操作でも状態によって結果が異なる。たとえば、取り消しは発送前ならできるが、発送後はできない。このように、状態によって振る舞いが変わる対象には、状態遷移テストを使う。

状態遷移図は、有効な遷移を見やすく表せる。一方、「どの状態でどの操作が許されないか」は図から読み取りにくい。そこで、状態と操作のすべての組み合わせを表にした状態遷移表を作る。「－」は、その状態ではその操作ができない（エラーになる）ことを表す。

状態遷移テストでは、次の 2 種類のテストケースを作る。

  • 有効な遷移のテスト：表で遷移先が書かれた 5 つのマスについて、操作の後に正しい状態になることを確かめる。すべての有効な遷移を 1 回ずつ通すことを、0 スイッチカバレッジと呼ぶ。

  • 無効な遷移のテスト：表で「－」の 15 のマスについて、操作がエラーになり、状態が変わらないことを確かめる。

無効な遷移のテストは忘れられやすいが、「発送済みの注文を取り消せてしまう」といった深刻な欠陥を見つけるために重要である。

有効な遷移を 2 回続けた組み合わせ（「受付済み→支払い済み→発送済み」など）をすべて通すことを 1 スイッチカバレッジと呼ぶ。状態の組み合わせによって振る舞いが変わる場合は、このような連続した遷移もテストする。

4.6 組み合わせテスト

すべての組み合わせは \(3 \times 2 \times 2 \times 2 = 24\) 通りである。項目や値が増えれば、組み合わせの数はさらに急速に増える。

経験上、多くの欠陥は 1 つの項目の値か、2 つの項目の値の組み合わせによって引き起こされる。そこで、任意の 2 項目について、値のすべての組み合わせが少なくとも 1 回は現れるようにテストケースを選ぶ。これをペアワイズテスト（オールペア法）と呼ぶ。上の例では、次の 6 通りで、すべての 2 項目の組み合わせを網羅できる。

ペアワイズテストは、3 つ以上の項目の特定の組み合わせでだけ起きる欠陥を見逃す可能性がある。重要な組み合わせは、個別にテストケースとして追加する。項目が多い場合の組み合わせ表は手作業では作りにくいため、専用のツールを使うことが多い。

4.7 エラー推測

エラー推測は、経験や知識から欠陥が潜んでいそうな入力を推測してテストする、経験ベースの技法である。体系的な技法で作ったテストケースに加えて使う。よく試される入力の例を次に示す。

分類

入力の例

数値

0、負の数、非常に大きな数、小数、浮動小数点の誤差が出る値（0.1 + 0.2 など）

文字列

空文字列、空白だけの文字列、非常に長い文字列、全角文字、絵文字、改行やタブを含む文字列

コレクション

空のリスト、要素が 1 つだけのリスト、重複する要素

日付と時刻

月末、うるう年の 2 月 29 日、年の変わり目、タイムゾーンの違い

欠けた値

None、必須の項目がない入力、存在しないファイル

操作

同じ操作の 2 回続けての実行、操作の途中での中断

チームで過去に見つかった欠陥の記録は、エラー推測の貴重な材料になる。見つかった欠陥の傾向をチェックリストにまとめておくと、個人の経験に頼らずにエラー推測を行える。

4.9 まとめ

  • 同値分割は、入力を同じように扱われるクラスに分け、各クラスから代表値を選ぶ。無効同値クラスも忘れずにテストする。

  • 境界値分析は、欠陥が集中しやすい境界とその隣の値を選ぶ。

  • デシジョンテーブルは、条件の組み合わせを漏れなく洗い出し、仕様の漏れにも気付かせる。

  • 状態遷移テストでは、有効な遷移と無効な遷移の両方をテストする。

  • ペアワイズテストは、2 項目の組み合わせを網羅しながらテストケースの数を抑える。

  • エラー推測は、経験に基づいて体系的な技法を補う。
