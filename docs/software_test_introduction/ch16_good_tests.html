16. よいテストの書き方

テストコードも、テスト対象のコードと同じように読まれ、保守される。読みにくいテストや壊れやすいテストは、やがて誰も直さなくなり、無視されるか削除される。この章では、長く役に立つテストを書くための指針と、避けるべきアンチパターンを学ぶ。

16.1 AAA パターン

AAA パターンは、1 つのテストを次の 3 つの部分に分けて書く方法である。

部分

内容

Arrange（準備）

テスト対象と入力のデータを用意する。

Act（実行）

テスト対象の操作を 1 つ実行する。

Assert（検証）

結果が期待どおりであることを確かめる。

3 つの部分を空行で区切ると、テストの構造がひと目で分かる。

ch16_good_tests/test_good_practices.py
 1"""よいテストの書き方の例（AAA パターンと、振る舞いを表すテスト名）."""
 2
 3import pytest
 4
 5from shop.cart import Cart, Item
 6from shop.shipping import calc_shipping_fee
 7
 8
 9def make_cart(*prices: int) -> Cart:
10    """指定した単価の商品を 1 個ずつ入れたカートを作る."""
11    cart = Cart()
12    for i, price in enumerate(prices):
13        cart.add(Item(f"商品{i}", price))
14    return cart
15
16
17def test_regular_member_gets_free_shipping_at_5000_yen() -> None:
18    # Arrange（準備）
19    cart = make_cart(3000, 2000)
20
21    # Act（実行）
22    fee = calc_shipping_fee(cart.subtotal(), is_premium=False,
23                            is_remote=False)
24
25    # Assert（検証）
26    assert fee == 0
27
28
29def test_remote_surcharge_applies_even_when_shipping_is_free() -> None:
30    cart = make_cart(5000)
31
32    fee = calc_shipping_fee(cart.subtotal(), is_premium=False,
33                            is_remote=True)
34
35    assert fee == 1000
36
37
38def test_removing_item_decreases_subtotal() -> None:
39    cart = Cart()
40    apple = Item("りんご", 150)
41    cart.add(apple, 2)
42    cart.add(Item("メロン", 2000))
43
44    cart.remove(apple)
45
46    # 内部の辞書（cart._quantities）ではなく、公開された振る舞いで検証する
47    assert cart.subtotal() == 2000
48    assert cart.quantity_of(apple) == 0
49
50
51def test_adding_negative_quantity_is_rejected() -> None:
52    cart = Cart()
53
54    with pytest.raises(ValueError):
55        cart.add(Item("りんご", 150), -1)
56
57    assert cart.is_empty()

17～26 行目のテストでは、説明のために各部分にコメントを付けている。慣れてくれば、2 つ目以降のテストのように、空行で区切るだけで十分である。

Act の部分は、原則として 1 つの操作にする。Act が複数あると、テストが失敗したときに、どの操作が原因かが分かりにくくなる。

16.2 テストの名前

テストの名前は、テストが失敗したときに最初に目にする情報である。名前から「どのような条件で、何が起きるべきか」が分かるようにする。

名前

評価

test_shipping

何を確かめるテストか分からない。

test_calc_shipping_fee_2

番号では内容が分からない。

test_regular_member_gets_free_shipping_at_5000_yen

条件（一般会員、5,000 円）と期待される結果（送料無料）が分かる。

名前は、関数の名前ではなく、確かめる振る舞いを表すようにする。そうすれば、関数の名前を変えるリファクタリングをしても、テストの名前を変える必要がない。名前が長くなることは気にしなくてよい。テストの名前は、コードの中で呼び出されることがないためである。

16.3 FIRST 原則

よい単体テストが備えるべき性質は、頭文字をとって FIRST 原則としてまとめられている。

性質

内容

Fast（速い）

すぐに実行できる。遅いテストは実行されなくなる。

Independent（独立している）

ほかのテストに依存せず、どの順序で実行しても、1 つだけ実行しても同じ結果になる。

Repeatable（繰り返せる）

どの環境で何度実行しても同じ結果になる。時刻、乱数、ネットワークに左右されない。

Self-validating（自己検証できる）

成功か失敗かを、テスト自身が判定する。出力を人が目で見て確かめる必要がない。

Timely（適時に書く）

テスト対象のコードと同時か、その前に書く。後回しにすると、テストしにくい設計になりやすい。

16.4 1 つのテストで 1 つの観点を確かめる

1 つのテストに多くのことを詰め込むと、最初の assert で失敗したときに、残りの確認が行われない。また、テストの名前で内容を表しきれなくなる。1 つのテストでは、1 つの振る舞い（観点）を確かめるようにする。

これは、assert 文を 1 つに限るという意味ではない。16.1 節の test_removing_item_decreases_subtotal（38～48 行目）は、「商品を取り除く」という 1 つの振る舞いの結果を、2 つの assert で確かめている。

16.5 アンチパターン

よく見られる、避けるべきテストの書き方を紹介する。

検証のないテスト

1def test_subtotal() -> None:
2    cart = Cart()
3    cart.add(Item("りんご", 150), 3)
4    cart.subtotal()  # 結果を確かめていない

例外が起きなければ成功するため、subtotal が誤った値を返しても気付けない。カバレッジは上がるため、5.8 節で述べたとおり、数値だけを見ていると見落とす。

実装の詳細に依存するテスト

1def test_add() -> None:
2    cart = Cart()
3    apple = Item("りんご", 150)
4    cart.add(apple, 2)
5    assert cart._quantities == {apple: 2}  # 非公開の属性を見ている

Cart が商品を辞書ではなくリストで保持するように変わると、振る舞いは同じでもテストが失敗する。このようなテストはリファクタリングの妨げになる。16.1 節の test_removing_item_decreases_subtotal のように、公開されたメソッドで結果を確かめる。

テスト対象と同じ計算で期待値を求めるテスト

1def test_fee() -> None:
2    subtotal = 4000
3    expected = 0 if subtotal >= FREE_THRESHOLD else BASE_FEE  # テスト対象と同じ式
4    assert calc_shipping_fee(subtotal, False, False) == expected

テスト対象と同じ式で期待値を求めると、その式が誤っていれば期待値も同じように誤るため、テストは成功してしまう。期待値は、500 のように仕様から求めた具体的な値で書く。

ロジックを含むテスト

1def test_fees() -> None:
2    for subtotal in [4999, 5000]:
3        fee = calc_shipping_fee(subtotal, False, False)
4        if subtotal < 5000:
5            assert fee == 500
6        else:
7            assert fee == 0

テストの中に if 文やループがあると、テスト自体に欠陥が入り込む余地が生まれ、どの値で失敗したかも分かりにくくなる。複数の値を試す場合は、8 章のパラメーター化を使う。

互いに依存するテスト

 1cart = Cart()  # モジュール全体で共有している
 2
 3
 4def test_add() -> None:
 5    cart.add(Item("りんご", 150))
 6    assert not cart.is_empty()
 7
 8
 9def test_subtotal() -> None:
10    assert cart.subtotal() == 150  # test_add が先に実行されることを前提にしている

test_subtotal だけを実行したり、実行の順序が変わったりすると失敗する。テストに必要な準備は、各テストか fixture の中で行う。

不安定なテスト

コードを変えていないのに、成功したり失敗したりするテストを不安定なテスト（flaky test）と呼ぶ。主な原因は次のとおりである。

  • 現在の時刻や乱数に依存している（10 章の方法で制御する）。

  • time.sleep で処理の完了を待ち、待ち時間が足りないことがある。

  • 外部のサービスやネットワークに依存している（9 章と 11 章の方法で切り離す）。

  • テストの実行順序や、ほかのテストが残した状態に依存している。

不安定なテストがあると、テストが失敗しても「またいつものことか」と無視されるようになり、本当の欠陥を知らせる失敗も見逃される。不安定なテストを見つけたら、優先して原因を取り除く。

モックの使い過ぎ

9.7 節で述べたとおり、依存先の呼び出しを細かく検証するテストは、実装を少し変えただけで失敗する。テストダブルは外部との境界に限って使い、結果はなるべく値や状態で確かめる。

16.6 テストコードも保守する

テストコードは、テスト対象のコードと同じ品質の基準で扱う。

  • テストコードもレビューの対象にする（13 章）。

  • 重複する準備の処理は fixture や補助関数にまとめる。ただし、まとめ過ぎてテストの中から前提が見えなくなると、かえって読みにくくなる。テストでは、多少の重複よりも、そのテストだけを読んで意図が分かることを優先する。

  • 仕様が変わってテストが失敗したら、期待値を機械的に書き換えるのではなく、テストの意図が今の仕様に合っているかを考えて直す。

  • 意味がなくなったテストは削除する。

16.7 まとめ

  • AAA パターンでテストを準備、実行、検証に分けると、構造が分かりやすくなる。

  • テストの名前は、条件と期待される結果が分かるように付ける。

  • よい単体テストは、FIRST 原則（速い、独立している、繰り返せる、自己検証できる、適時に書く）を満たす。

  • 検証のないテスト、実装の詳細に依存するテスト、テスト対象と同じ計算で期待値を求めるテスト、ロジックを含むテスト、互いに依存するテスト、不安定なテストを避ける。

  • テストコードもレビューし、保守する。
