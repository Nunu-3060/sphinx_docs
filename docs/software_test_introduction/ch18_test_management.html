18. テストの計画と管理

ここまでは、個々のテストの設計と実装を扱ってきた。しかし、実際の開発では、限られた時間と人員の中で、何をどこまでテストするかを決め、進み具合を把握する必要がある。この章では、2.6 節で紹介したテストの活動のうち、計画と管理の部分を扱う。

18.1 テスト計画

テスト計画は、テストの目的と進め方を決め、関係者の間で合意する活動である。その結果をまとめた文書を、テスト計画書と呼ぶ。テスト計画書には、主に次の項目を書く。

項目

内容

目的

このテストで何を確かめるか。例：「送料の計算の変更が、既存の注文の流れを壊していないことを確かめる」

範囲

テストの対象とする機能と、対象としない機能。対象としないものも明記する。

方法

テストレベルとテストタイプ、使う設計技法、自動化するテストと手作業で行うテスト。

環境

テストを実行する環境、使うツール、テストデータ。

体制とスケジュール

担当者、役割、期間、ほかの作業との依存関係。

開始基準と終了基準

テストを始めてよい条件と、終えてよい条件（18.4 節）。

リスク

テストの進行を妨げるおそれのある事柄と、その対策。

小さなチームや短い開発の周期では、テスト計画書を詳細に書く必要はない。しかし、少なくとも「何をテストし、何をテストしないか」と「どうなったら終わりとするか」は、関係者の間で合意しておく。これが曖昧だと、テストがいつまでも終わらないか、必要なテストが行われないまま終わる。

18.2 リスクに基づくテスト

2 章の原則のとおり、すべてをテストすることはできない。限られた時間で効果を上げるには、リスクの大きい部分にテストの労力を集中させる。これをリスクに基づくテストと呼ぶ。

リスクの大きさは、故障が起きる可能性と、起きたときの影響の大きさの組み合わせで評価する。

小

中

大

中

故障が起きる可能性は、コードの複雑さ（5 章の循環的複雑度など）、変更の大きさ、過去の欠陥の多さ、開発者の経験などから見積もる。影響の大きさは、金銭や個人情報に関わるか、利用者の数、代わりの手段の有無などから見積もる。

たとえば題材のネットショップでは、送料と金額の計算は、誤ると利用者に直接の金銭的な損害を与えるため、影響が大きい。一方、商品の一覧の並び順の誤りは、影響が比較的小さい。リスクの評価に応じて、金額の計算には境界値分析とデシジョンテーブルによる網羅的なテストを行い、並び順には代表的なテストケースだけを用意する、といった強弱を付ける。

18.3 テストケースの記述

自動化しないテスト（手作業で行うシステムテストや受け入れテスト）では、テストケースを文書として記述する。テストケースには、主に次の項目を書く。

項目

記入例

ID

TC-SHIP-005

テスト条件

一般会員の注文金額が、送料無料の基準ちょうどの場合

前提条件

一般会員としてログインしている。配送先は離島でない。

手順

  1. 単価 5,000 円の商品を 1 個カートに入れる。

  2. 注文の確認画面を表示する。

期待結果

送料が 0 円と表示される。合計金額が 5,000 円と表示される。

実際の結果

（実行時に記入）

判定

（実行時に「合格」または「不合格」を記入）

期待結果は、誰が確かめても同じ判定になるように、具体的な値で書く。「送料が正しく表示される」のような書き方では、何が正しいかが実行する人によって変わる。

テストケースは、テスト条件の出どころ（仕様書の項目や、4 章の技法で作った表のどの行か）と対応付けておく。これをトレーサビリティ（追跡可能性）と呼ぶ。仕様が変わったときに見直すべきテストケースを特定でき、仕様の項目のうちテストされていないものも見つけられる。

18.4 開始基準と終了基準

開始基準はテストを始めてよい条件、終了基準はテストを終えてよい条件である。あらかじめ決めておくことで、テストの開始や終了を客観的に判断できる。

基準

例

開始基準

テスト環境が用意されている。テスト対象のビルドが完了し、単体テストがすべて成功している。

終了基準

計画したテストケースをすべて実行した。重大度が「高」の未解決の欠陥がない。分岐網羅率が 90 % 以上である。

終了基準を満たせない場合は、残っているリスクを明らかにしたうえで、リリースを延期するか、リスクを受け入れてリリースするかを関係者が判断する。テストの役割は、その判断のための情報を提供することである（2.1 節）。

18.5 欠陥の報告

テストで故障を見つけたら、欠陥として報告する。報告を受けた開発者が、故障を再現し、原因を調べられるように、次の項目を書く。

項目

記入例

タイトル

一般会員の注文金額がちょうど 5,000 円のとき、送料が 500 円になる

環境

バージョン 1.4.2、テスト環境、Chrome 140

再現手順

  1. 一般会員でログインする。

  2. 単価 5,000 円の商品を 1 個カートに入れる。

  3. 注文の確認画面を表示する。

期待結果

送料が 0 円と表示される（仕様書 3.2 節「5,000 円以上で送料無料」）。

実際の結果

送料が 500 円と表示される。

重大度

高（利用者に余分な料金を請求する）

補足

5,001 円では 0 円になる。境界の比較の誤りの可能性がある。関連するテストケース：TC-SHIP-005

欠陥の報告では、次の点に注意する。

  • 事実を書く：観察した事実と、推測（「補足」の欄の原因の可能性など）を区別して書く。

  • 再現手順を具体的に書く：誰が実行しても同じ故障が起きるように、手順と入力の値を具体的に書く。

  • 1 件の報告に 1 つの欠陥：複数の欠陥を 1 件にまとめると、一部だけが直ったときに状態を管理しにくい。

  • 人ではなく成果物を対象にする：欠陥の報告は、コードの問題を指摘するものであり、書いた人を非難するものではない。

欠陥は、報告から修正、確認テスト（3 章）を経て、解決までの状態を管理する。多くのチームでは、課題管理のツールを使って管理する。

18.6 テストのメトリクス

テストの進み具合や品質を把握するために、数値で表した指標（メトリクス）を使う。代表的なメトリクスを次に示す。

メトリクス

内容

テストケースの消化率

計画したテストケースのうち、実行を終えたものの割合。進み具合を表す。

テストの合格率

実行したテストケースのうち、合格したものの割合。

欠陥の件数の推移

日ごとに見つかった欠陥と、解決した欠陥の件数の推移。

欠陥密度

コードの規模あたりの欠陥の件数。モジュールごとに比べると、欠陥が集中している箇所が分かる。

カバレッジ

14 章で扱った、コードの実行の網羅率。

欠陥密度は、たとえば次のように計算する。

\[\text{欠陥密度} = \frac{\text{見つかった欠陥の件数}}{\text{コードの行数（千行単位）}}\]

欠陥の件数の推移は、テストの終わりが近づいているかを判断する材料になる。新たに見つかる欠陥の件数が減り、未解決の欠陥の件数が十分に少なくなれば、品質が安定してきたと考えられる。逆に、テストの終盤になっても欠陥が見つかり続ける場合は、テストの範囲や方法を見直す必要がある。

メトリクスは、それ自体を目標にすると意味を失う。欠陥の件数で開発者を評価すれば欠陥が報告されなくなり、テストケースの消化率を目標にすれば簡単なテストケースから消化されるようになる。メトリクスは状況を把握するための道具として使い、数値の背後にある事実を確かめる。

18.7 まとめ

  • テスト計画では、目的、範囲、方法、終了基準などを決め、関係者の間で合意する。

  • リスクに基づくテストでは、故障の可能性と影響の大きさで優先度を決め、リスクの大きい部分に労力を集中させる。

  • テストケースと欠陥の報告は、誰が読んでも同じ結果になるように、具体的な値と手順で書く。

  • 開始基準と終了基準を事前に決めておくと、テストの開始と終了を客観的に判断できる。

  • メトリクスは状況の把握に使い、目標そのものにしない。
