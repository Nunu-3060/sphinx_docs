9. テストダブル

テスト対象の多くは、ほかの部品やデータベース、外部のサービスを使って動く。この章では、それらの依存先を、テスト用の代役に置き換えるテストダブルの考え方と、Python の unittest.mock の使い方を学ぶ。

9.1 テストダブルが必要な理由

発送を知らせるメールを送る機能をテストすることを考える。本物のメール送信の機能をそのまま使うと、次の問題が起きる。

  • テストのたびに、実際にメールが送られてしまう。

  • メールサーバーに接続できない環境では、テストが実行できない。

  • 通信に時間がかかり、テストが遅くなる。

  • 「送信に失敗した場合」のような状況を、意図して作り出すのが難しい。

  • テストが失敗したとき、原因がテスト対象にあるのか、メールサーバーにあるのかを区別できない。

依存先をテストダブルに置き換えると、テスト対象を依存先から切り離し、速く、確実に、繰り返し実行できるテストを書ける。テストダブルという名前は、映画の危険な場面で俳優の代わりを務めるスタントダブルに由来する。

9.2 テストダブルの種類

テストダブルは、役割によって次の 5 種類に分けられる。

種類

役割

例

ダミー

引数を埋めるためだけに渡す。実際には使われない。

呼ばれたら例外を送出するオブジェクト

スタブ

決まった値を返し、テスト対象への入力を制御する。

常に同じメールアドレスを返す顧客情報

スパイ

呼び出しを記録し、後でテストから検証できるようにする。

送信を依頼されたメールを記録する送信機能

モック

期待される呼び出しをあらかじめ設定し、そのとおりに呼ばれたかを検証する。

unittest.mock.Mock

フェイク

本物と同じように動くが、簡易な方法で実装されたもの。

辞書にデータを保存する顧客情報、インメモリのデータベース

スタブはテスト対象への「入力」を、スパイとモックはテスト対象からの「出力」（依存先の呼び出し）を扱う。実際の会話では、これらをまとめて「モック」と呼ぶことも多いが、役割を区別しておくと、テストで何を確かめているかを明確にできる。

9.3 題材のコード

発送の通知を担当する OrderNotifier を題材にする。

ch09_test_double/order_notifier.py
 1"""注文の発送を顧客にメールで知らせる."""
 2
 3from typing import Protocol
 4
 5
 6class CustomerDirectory(Protocol):
 7    """顧客情報を調べる機能."""
 8
 9    def email_of(self, customer_id: int) -> str | None:
10        """顧客のメールアドレスを返す（登録がなければ None を返す）."""
11        ...
12
13
14class MailSender(Protocol):
15    """メールを送信する機能."""
16
17    def send(self, to: str, subject: str, body: str) -> None:
18        """メールを送信する（失敗したら OSError を送出する）."""
19        ...
20
21
22class OrderNotifier:
23    """発送の通知を担当するクラス."""
24
25    def __init__(self, directory: CustomerDirectory,
26                 sender: MailSender) -> None:
27        self._directory = directory
28        self._sender = sender
29
30    def notify_shipped(self, customer_id: int, order_id: int) -> bool:
31        """発送の通知メールを送る.
32
33        Returns:
34            送信できたら True、メールアドレスが未登録か送信に失敗したら False。
35        """
36        email = self._directory.email_of(customer_id)
37        if email is None:
38            return False
39        subject = f"ご注文（注文番号 {order_id}）を発送しました"
40        body = "商品の到着まで今しばらくお待ちください。"
41        try:
42            self._sender.send(email, subject, body)
43        except OSError:
44            return False
45        return True

OrderNotifier は、顧客情報を調べる機能（CustomerDirectory）とメールを送る機能（MailSender）を、コンストラクターの引数で受け取る。自分で本物の機能を作らず、外から受け取るようにしておくことで、テストでは代役を渡せる。この設計の考え方は 10 章で詳しく扱う。

CustomerDirectory と MailSender は typing.Protocol で定義している。Protocol は、「このメソッドを持つオブジェクトなら何でもよい」ことを型ヒントで表す仕組みである。本物の実装もテストダブルも、同じメソッドを持っていれば継承なしで渡せ、mypy で型を検査できる。

9.4 テストダブルを手で書く

テストダブルは、特別なライブラリを使わなくても、普通のクラスとして書ける。

ch09_test_double/test_order_notifier.py
 1"""テストダブルを使って OrderNotifier をテストする."""
 2
 3from unittest.mock import Mock
 4
 5from order_notifier import CustomerDirectory, MailSender, OrderNotifier
 6
 7
 8# ---- ダミー: 引数を埋めるためだけに渡し、使われないことを前提とする ----
 9class DummySender:
10    def send(self, to: str, subject: str, body: str) -> None:
11        raise AssertionError("このテストでは呼ばれないはず")
12
13
14# ---- スタブ: 決まった値を返して、テスト対象への入力を制御する ----
15class StubDirectory:
16    def __init__(self, email: str | None) -> None:
17        self._email = email
18
19    def email_of(self, customer_id: int) -> str | None:
20        return self._email
21
22
23# ---- スパイ: 呼び出しを記録して、テスト対象からの出力を検証する ----
24class SpySender:
25    def __init__(self) -> None:
26        self.sent: list[tuple[str, str, str]] = []
27
28    def send(self, to: str, subject: str, body: str) -> None:
29        self.sent.append((to, subject, body))
30
31
32# ---- フェイク: 本物と同じように動く簡易な実装 ----
33class InMemoryDirectory:
34    def __init__(self) -> None:
35        self._emails: dict[int, str] = {}
36
37    def register(self, customer_id: int, email: str) -> None:
38        self._emails[customer_id] = email
39
40    def email_of(self, customer_id: int) -> str | None:
41        return self._emails.get(customer_id)
42
43
44def test_unregistered_customer_is_not_notified() -> None:
45    notifier = OrderNotifier(StubDirectory(None), DummySender())
46    assert notifier.notify_shipped(customer_id=1, order_id=100) is False
47
48
49def test_mail_is_sent_to_registered_address() -> None:
50    spy = SpySender()
51    notifier = OrderNotifier(StubDirectory("sato@example.com"), spy)
52
53    assert notifier.notify_shipped(customer_id=1, order_id=100) is True
54    assert len(spy.sent) == 1
55    to, subject, _ = spy.sent[0]
56    assert to == "sato@example.com"
57    assert "100" in subject
58
59
60def test_with_fake_directory() -> None:
61    directory = InMemoryDirectory()
62    directory.register(1, "sato@example.com")
63    spy = SpySender()
64    notifier = OrderNotifier(directory, spy)
65
66    assert notifier.notify_shipped(customer_id=1, order_id=100) is True
67    assert notifier.notify_shipped(customer_id=2, order_id=101) is False
68    assert [to for to, _, _ in spy.sent] == ["sato@example.com"]

各テストダブルの使い方は次のとおりである。

  • test_unregistered_customer_is_not_notified（44～46 行目）：顧客が未登録の場合、メールは送られないはずである。そこで、送信機能には呼ばれたら失敗する DummySender を渡している。顧客情報には None を返す StubDirectory を渡し、「未登録」という状況を作っている。

  • test_mail_is_sent_to_registered_address（49～57 行目）：SpySender が送信を依頼されたメールを記録するため、テストの後で宛先と件名を確かめられる。

  • test_with_fake_directory（60～68 行目）：InMemoryDirectory は、辞書で顧客情報を管理するフェイクである。登録した顧客とそうでない顧客の両方を、1 つのテストダブルで扱える。

9.5 unittest.mock

テストダブルを毎回手で書くのは手間がかかる。標準ライブラリの unittest.mock の Mock クラスを使うと、テストダブルをその場で作れる。

ch09_test_double/test_order_notifier.py（続き）
71def test_with_mock() -> None:
72    # spec を指定すると、MailSender にない属性を使ったときにエラーになる
73    sender = Mock(spec=MailSender)
74    directory = Mock(spec=CustomerDirectory)
75    directory.email_of.return_value = "sato@example.com"
76    notifier = OrderNotifier(directory, sender)
77
78    notifier.notify_shipped(customer_id=1, order_id=100)
79
80    directory.email_of.assert_called_once_with(1)
81    sender.send.assert_called_once_with(
82        "sato@example.com",
83        "ご注文（注文番号 100）を発送しました",
84        "商品の到着まで今しばらくお待ちください。",
85    )
86
87
88def test_send_failure_returns_false() -> None:
89    # side_effect に例外を指定すると、呼び出したときにその例外を送出する
90    sender = Mock(spec=MailSender)
91    sender.send.side_effect = ConnectionError("接続できません")
92    notifier = OrderNotifier(StubDirectory("sato@example.com"), sender)
93
94    assert notifier.notify_shipped(customer_id=1, order_id=100) is False

Mock の主な機能は次のとおりである。

機能

内容

m.method.return_value = 値

m.method() を呼び出したときの戻り値を設定する（スタブとして使う）。

m.method.side_effect = 例外

m.method() を呼び出したときに例外を送出させる。関数やリストを設定することもできる。

m.method.assert_called_once_with(...)

指定した引数で、ちょうど 1 回呼ばれたことを検証する。

m.method.assert_not_called()

一度も呼ばれていないことを検証する。

m.method.call_args_list

呼び出されたときの引数を、呼び出しの順に記録したリスト（スパイとして使う）。

Mock(spec=MailSender) のように spec を指定することが重要である（73 行目）。spec を指定しない Mock は、どのような名前の属性でも受け付ける。そのため、テスト対象が sender.sned(...) のように名前を打ち間違えていても、エラーにならずにテストが成功してしまう。spec を指定すると、MailSender にない属性を使ったときに AttributeError が送出される。

side_effect に例外を設定すると（91 行目）、送信の失敗という、本物の機能では再現しにくい状況を簡単に作れる。

9.6 patch による差し替え

テスト対象が依存先を引数で受け取らず、モジュールの中で直接使っている場合は、unittest.mock.patch でその名前を一時的に差し替える。

ch09_test_double/lottery.py
 1"""購入者に抽選でクーポンを配る."""
 2
 3from random import random
 4
 5WIN_PROBABILITY = 0.1
 6"""当選確率."""
 7
 8
 9def draw_coupon() -> str | None:
10    """抽選を行い、当選したらクーポンコードを、外れたら None を返す."""
11    if random() < WIN_PROBABILITY:
12        return "SAVE10"
13    return None
ch09_test_double/test_lottery.py
 1"""unittest.mock.patch で乱数を差し替えて、抽選をテストする."""
 2
 3from unittest.mock import patch
 4
 5import pytest
 6
 7import lottery
 8
 9
10def test_win() -> None:
11    # lottery.py は from random import random としているため、
12    # random モジュールではなく lottery モジュールの名前 random を差し替える
13    with patch("lottery.random", return_value=0.05):
14        assert lottery.draw_coupon() == "SAVE10"
15
16
17def test_lose() -> None:
18    with patch("lottery.random", return_value=0.5):
19        assert lottery.draw_coupon() is None
20
21
22def test_boundary_is_lose(monkeypatch: pytest.MonkeyPatch) -> None:
23    # monkeypatch.setattr でも同じように差し替えられる
24    monkeypatch.setattr(lottery, "random", lambda: 0.1)
25    assert lottery.draw_coupon() is None

patch("lottery.random", return_value=0.05) は、with のブロックの中だけ、lottery モジュールの名前 random を、0.05 を返す Mock に置き換える（13 行目）。ブロックを抜けると元に戻る。

patch を使うときは、「差し替える名前が使われる場所」を指定する。lottery.py は from random import random として、random 関数を自分のモジュールの名前として取り込んでいる（3 行目）。そのため、random.random を差し替えても、lottery モジュールの random は元の関数を指したままであり、効果がない。一方、lottery.py が import random として random.random() と呼び出していれば、random.random を差し替える必要がある。

pytest の monkeypatch fixture でも、同じように差し替えられる（24 行目）。

9.7 モックの使い過ぎに注意する

テストダブルは便利だが、使い過ぎると次の問題が起きる。

  • 実装の詳細に依存したテストになる：「どのメソッドがどの順に呼ばれたか」を細かく検証すると、振る舞いを変えないリファクタリングでもテストが失敗するようになる。

  • 本物との食い違いに気付けない：テストダブルは、本物の振る舞いについての思い込みで作られる。本物の仕様が変わっても、テストダブルが古いままであれば、テストは成功し続ける。

  • テストが読みにくくなる：準備のコードの大半がモックの設定になると、何を確かめているテストなのかが分かりにくくなる。

次の方針で使うとよい。

  • テストダブルに置き換えるのは、遅いもの、不安定なもの、副作用のあるもの（外部サービス、メール、時刻、乱数など）に限る。自分たちが書いた計算のロジックは、本物を使ってテストする。

  • 検証は、なるべく結果の値や状態で行う。依存先の呼び出しを検証するのは、メールの送信のように「呼び出すこと」自体が目的の場合に限る。

  • 置き換えた部分は、11 章の結合テストで、本物を使って確かめる。

9.8 まとめ

  • テストダブルは、依存先をテスト用の代役に置き換え、テストを速く確実にする。

  • ダミー、スタブ、スパイ、モック、フェイクの 5 種類があり、スタブは入力を、スパイとモックは出力を扱う。

  • unittest.mock.Mock でテストダブルをその場で作れる。spec を指定して、存在しない属性の使用を防ぐ。

  • patch は、差し替える名前が使われる場所を指定する。

  • テストダブルを使い過ぎると、実装に依存した壊れやすいテストになる。置き換えるのは外部との境界に限る。
