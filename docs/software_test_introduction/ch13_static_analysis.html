13. 静的テスト

3 章で見たとおり、テストにはプログラムを実行する動的テストと、実行しない静的テストがある。この章では、静的テストのうち、コードレビューと、Python の静的解析ツールである flake8 と mypy の使い方を学ぶ。

13.1 静的テストの利点

静的テストには、動的テストにない次の利点がある。

  • 実行しなくても欠陥を見つけられる：テストが書かれていない箇所や、テストでは通りにくい経路の欠陥も見つけられる。

  • 早い段階で行える：コードを書いている最中や、仕様書の段階でも行える。

  • 欠陥の原因を直接指摘できる：動的テストは故障（結果の誤り）を見つけ、原因は人が調べる。静的解析は、原因となるコードの箇所を直接示す。

  • 保守性の問題も見つけられる：動作には影響しないが、読みにくいコードや複雑すぎる関数も見つけられる。

13.2 コードレビュー

コードレビューは、書いたコードを別の人が読んで、欠陥や改善点を指摘する活動である。テストの観点では、テスト対象のコードだけでなく、テストコードもレビューの対象にする。テストコードのレビューでは、次の点を確かめるとよい。

観点

確かめる内容

テストケースの十分さ

境界値や無効な入力、エラーの場合がテストされているか。4 章の技法で導けるテストケースが漏れていないか。

期待値の正しさ

期待値が仕様に基づいているか。テスト対象の実行結果をそのまま期待値に写していないか。

検証の有無

実行するだけで assert のないテストや、常に成功する assert がないか。

独立性

テストの実行順や、ほかのテストが作ったデータに依存していないか。

読みやすさ

テストの名前から、何を確かめるテストかが分かるか（16 章）。

書式の統一や単純な誤りの検出は、次に説明するツールに任せる。ツールで機械的に見つけられる問題をレビューで指摘し合うのは、時間の無駄であるうえ、人間関係の摩擦の原因にもなる。人のレビューは、仕様との整合性や設計の妥当性など、ツールでは判断できない点に集中させる。

13.3 flake8

flake8 は、Python のコードの規約違反と、単純な誤りを検出するツールである。内部で次の 3 つのツールを組み合わせて使っている。

コード

ツール

検出する内容

E、W

pycodestyle

Python の標準のコーディング規約である PEP 8 への違反（行の長さ、空白、空行など）

F

pyflakes

使われていない import や変数、未定義の名前など、論理的な誤り

C90

mccabe

循環的複雑度（5 章）が指定した値を超える関数

次のコードを検査してみる。このコードは、説明のために誤りを含めたものであり、サンプルコードには含めていない。

 2
 3
 4def total_price(prices: list[int], tax_rate: float) -> int:
 5    total = sum(prices)
 6    return total * (1 + tax_rate)

10    for name in names:
11        if keyword in name:
12            return name

1$ python -m flake8 price.py

price.py:1:1: F401 'os' imported but unused
price.py:1:1: F401 'sys' imported but unused
price.py:1:10: E401 multiple imports on one line

出力の各行は、「ファイル名:行:列: コード メッセージ」の形式である。使われていない import（F401）と、1 行に複数の import を書いていること（E401）が指摘された。

flake8 の設定は、setup.cfg などのファイルに書ける。本書のサンプルコードでは、次の設定を使っている。

setup.cfg
1# flake8 の設定。examples フォルダーで次のように実行する。
2#   python -m flake8 .
3
4[flake8]
5max-line-length = 79
6exclude = __pycache__,.pytest_cache,.mypy_cache,.hypothesis,.venv

循環的複雑度の検査は、--max-complexity オプションで上限を指定したときに有効になる。5 章の member_rank の循環的複雑度は 3 なので、上限を 2 にすると次のように指摘される。

1$ python -m flake8 --max-complexity 2 shop/member.py

shop/member.py:4:1: C901 'member_rank' is too complex (3)

実際のプロジェクトでは、上限を 10 程度に設定し、それを超える関数を分割の候補とすることが多い。

13.4 mypy

mypy は、型ヒントに基づいて、型の誤りを検出するツールである。13.3 節の price.py を mypy で検査すると、flake8 では見つからなかった 2 つの誤りが指摘される。

1$ python -m mypy --strict price.py

price.py:6: error: Incompatible return value type (got "float", expected "int")  [return-value]
price.py:17: error: Item "None" of "str | None" has no attribute "upper"  [union-attr]
Found 2 errors in 1 file (checked 1 source file)

1 つ目は、int を返すはずの total_price が、税率を掛けた float を返していることの指摘である。2 つ目は、None を返す可能性のある find_item の結果に対して、None かどうかを確かめずに upper を呼び出していることの指摘である。

2 つ目の誤りは、テストでは見つけにくい。この例では "メ" を含む名前が見つかるため、実行しても故障は起きない。見つからない場合をテストしなければ、欠陥は残り続ける。mypy は、実行する入力に関係なく「None になりうる」ことを指摘できる。

--strict オプションは、型ヒントのない関数を許さないなど、多くの検査をまとめて有効にする。本書のサンプルコードでは、pyproject.toml に strict = true を設定し、すべてのファイルを --strict 相当で検査している。

1$ python -m flake8 .
2$ python -m mypy .

型ヒントは、テストコードにも書くとよい。テストコードの型の誤り（fixture の戻り値の型の誤りなど）も検出できるうえ、テスト対象の関数の使い方が型ヒントと合っているかも確かめられる。

13.5 静的解析とテストの役割分担

静的解析とテストは、見つけやすい欠陥の種類が異なる。

欠陥の種類

静的解析

テスト

使われていない import や変数

見つけやすい

見つけにくい

型の不一致、None の扱い漏れ

見つけやすい

テストした入力に限る

計算の誤り、仕様の読み違え

見つけにくい

見つけやすい

境界の条件の誤り

見つけにくい

見つけやすい

規約違反、複雑すぎる関数

見つけやすい

見つけにくい

静的解析は、計算の結果が仕様どおりかは判断できない。一方、テストは、試した入力についてしか判断できない。両者を組み合わせることで、少ない労力で多くの種類の欠陥を見つけられる。17 章では、これらをまとめて自動で実行する方法を扱う。

13.6 まとめ

  • 静的テストは、実行せずに欠陥の原因を直接見つけられ、早い段階から行える。

  • コードレビューでは、テストコードもレビューし、テストケースの十分さや期待値の正しさを確かめる。

  • flake8 は規約違反、単純な誤り、複雑すぎる関数を検出する。

  • mypy は型ヒントに基づいて型の誤りを検出し、None の扱い漏れのようなテストでは見つけにくい欠陥を指摘する。

  • 静的解析とテストは得意な欠陥が異なるため、組み合わせて使う。
