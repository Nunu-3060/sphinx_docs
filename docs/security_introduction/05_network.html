5. ネットワークセキュリティ

この章では、ネットワーク上の通信を守る仕組みと、ネットワークの構成による防御を説明します。

5.1. ネットワーク上の脅威

インターネットの通信は、利用者の端末からサーバーに届くまでに、Wi-Fi のアクセスポイント、インターネットサービスプロバイダー、多数のルーターなどを経由します。経路上の機器を操作できる攻撃者は、通信に対して次のような攻撃を行えます。

通信経路上の脅威

脅威

内容

損なわれる要素

盗聴

通信の内容を読み取ります。

機密性

改ざん

通信の内容を書き換えます（例: Web ページへのマルウェアの埋め込み）。

完全性

なりすまし

正規のサーバーのふりをして、利用者と通信します。

真正性

攻撃者が通信の当事者の間に入り込み、両者になりすまして通信を中継しながら盗聴や改ざんを行う攻撃を中間者攻撃と呼びます。公衆 Wi-Fi の偽のアクセスポイントなどが典型的な例です。これらの脅威から通信を守るのが、次に説明する TLS です。

また、サーバーが外部に公開しているポートやサービスは、すべて攻撃の入口になり得ます。攻撃を受ける可能性のある箇所の総体を攻撃対象領域（アタックサーフェス）と呼びます。使っていないサービスを停止し、公開するポートを最小限にすることは、最も基本的で効果の高い対策です。

5.2. TLS

TLS（Transport Layer Security）は、通信を暗号化し、改ざんを検知し、通信相手が本物であることを確認するためのプロトコルです。HTTPS は、HTTP を TLS で保護したものです。

TLS は、暗号技術の基礎で説明した技術を組み合わせて、次の 3 つを実現しています。

TLS が実現すること

実現すること

方法

使われる技術

通信相手の確認

サーバーが提示する証明書を検証します。

デジタル署名、証明書

鍵の共有

盗聴されても共通鍵が分からない方法で鍵を共有します。

鍵共有（ECDHE など）

暗号化と改ざん検知

共有した鍵で通信内容を保護します。

認証付き暗号（AES-GCM など）

現在の TLS 1.3 では、鍵の共有に、接続のたびに使い捨ての鍵ペアを生成する方式が使われます（以前の接続で共有した鍵だけを使って再接続する方式を除きます）。そのため、サーバーの秘密鍵が将来漏えいしても、過去に記録された通信は解読できません。この性質を前方秘匿性と呼びます。

TLS 1.0 と TLS 1.1 は、RFC 8996 で使用が禁止されています。サーバーでは TLS 1.2 以上だけを有効にし、可能であれば TLS 1.3 を優先します。

5.3. 証明書と PKI

TLS で通信相手を確認するには、受け取った公開鍵が確かにそのサーバーのものであることを確かめる必要があります。そのための仕組みが、証明書と PKI（公開鍵基盤）です。

証明書は、「このドメイン名の公開鍵はこれである」という情報に、認証局（CA）がデジタル署名したものです。認証局の証明書は、さらに上位の認証局によって署名されており、最上位のルート認証局の証明書は、OS やブラウザーにあらかじめ組み込まれています。クライアントは、この連鎖をたどってサーバーの証明書を検証します。

クライアントは、証明書について次の点を検証します。

  • 信頼できるルート認証局まで、署名の連鎖をたどれること

  • 有効期間内であること

  • 証明書に記載されたドメイン名（SAN: Subject Alternative Name）が、接続先のホスト名と一致すること

  • 失効していないこと

次のサンプルでは、Python の ssl モジュールでサーバーに TLS 接続し、証明書の情報を表示します。ssl.create_default_context() で作成したコンテキストは、これらの検証を自動的に行います。

tls_certificate_check.py
 1"""TLS 接続を確立し、サーバー証明書の情報を表示するサンプル.
 2
 3ssl.create_default_context() が作るコンテキストは、証明書の検証と
 4ホスト名の検証を自動で行います。検証に失敗すると接続は中断されます。
 5
 6実行方法:
 7    python tls_certificate_check.py [ホスト名]
 8    （ホスト名を省略すると www.python.org に接続します）
 9
10注意:
11    指定したホストの 443 番ポートに接続します（インターネット接続が必要です）。
12
13必要なライブラリ:
14    なし（標準ライブラリのみ）
15"""
16
17import socket
18import ssl
19import sys
20from typing import Any
21
22PORT = 443
23TIMEOUT = 10.0
24
25
26def name_to_text(name: Any) -> str:
27    """getpeercert() が返す識別名を「CN=...」形式の文字列にする."""
28    parts = [f"{key}={value}" for rdn in name for key, value in rdn]
29    return ", ".join(parts)
30
31
32def check(hostname: str) -> None:
33    """hostname に TLS で接続し、証明書の情報を表示する."""
34    context = ssl.create_default_context()
35    print("[コンテキストの設定]")
36    print(f"  証明書の検証    : {context.verify_mode.name}")
37    print(f"  ホスト名の検証  : {context.check_hostname}")
38    print(f"  最小 TLS バージョン: {context.minimum_version.name}")
39
40    with socket.create_connection((hostname, PORT), timeout=TIMEOUT) as sock:
41        with context.wrap_socket(sock, server_hostname=hostname) as tls:
42            cert = tls.getpeercert()
43            if not cert:
44                raise ssl.SSLError("サーバー証明書を取得できませんでした")
45            print("[接続結果]")
46            print(f"  TLS バージョン  : {tls.version()}")
47            cipher = tls.cipher()
48            print(f"  暗号スイート    : {cipher[0] if cipher else '不明'}")
49            print(f"  サブジェクト    : {name_to_text(cert['subject'])}")
50            print(f"  発行者          : {name_to_text(cert['issuer'])}")
51            print(f"  有効期限        : {cert['notAfter']}")
52            san = cert.get("subjectAltName", ())
53            names = [str(entry[1]) for entry in san
54                     if isinstance(entry, tuple)]
55            print(f"  SAN（先頭 5 件）: {', '.join(names[:5])}")
56
57
58def main() -> None:
59    hostname = sys.argv[1] if len(sys.argv) > 1 else "www.python.org"
60    try:
61        check(hostname)
62    except ssl.SSLCertVerificationError as error:
63        print(f"証明書の検証に失敗したため接続を中断しました: {error}")
64    except OSError as error:
65        print(f"接続できませんでした: {error}")
66
67
68if __name__ == "__main__":
69    main()

警告

開発中に証明書のエラーが出たときに、検証を無効にして回避するのはやめてください。例えば、requests ライブラリの verify=False や、ssl モジュールの check_hostname = False がこれに当たります。検証を無効にすると、中間者攻撃を受けても気付けなくなります。このような設定が本番環境に残ってしまう事故も少なくありません。社内の認証局を使っている場合は、検証を無効にするのではなく、その認証局の証明書を信頼する設定を追加します。

現在は、Let's Encrypt のように無料で証明書を自動発行する認証局が普及しています。証明書の期限切れによる障害を防ぐため、証明書の更新は自動化しておきます。また、発行されたすべての証明書は Certificate Transparency という公開ログに記録されるため、自分のドメインに対して身に覚えのない証明書が発行されていないかを監視できます。

5.3.1. HTTPS の徹底と HSTS

Web サイトを HTTPS で提供していても、利用者が最初に http:// で接続すると、HTTPS へのリダイレクトの前に中間者攻撃を受けるおそれがあります。これを防ぐのが HSTS（HTTP Strict Transport Security、RFC 6797）です。サーバーが次のヘッダーを返すと、ブラウザーは指定した期間、そのドメインに常に HTTPS で接続します。

1Strict-Transport-Security: max-age=31536000; includeSubDomains

5.4. DNS のセキュリティ

DNS は、ドメイン名を IP アドレスに変換する仕組みです。DNS の応答が偽装されると、利用者は正しいドメイン名を入力しても偽のサーバーに誘導されます。DNS に関する主なリスクと対策を次の表に示します。

DNS に関する主なリスクと対策

リスク

内容

対策

DNS キャッシュポイズニング

DNS サーバーに偽の応答をキャッシュさせ、多数の利用者を偽のサーバーに誘導します。

DNSSEC による応答の署名、DNS サーバーソフトウェアの更新

通信内容からの情報の推測

暗号化されていない DNS の問い合わせから、閲覧しているサイトを知られます。

DNS over HTTPS（DoH）、DNS over TLS（DoT）

サブドメインの乗っ取り

廃止したクラウドのサービスを指す DNS レコードが残っていると、第三者が同じ名前でサービスを作成し、そのサブドメインで任意の内容を公開できます。

サービスを廃止するときに DNS レコードも削除します。

ドメインの失効

ドメインの更新を忘れて失効すると、第三者に取得されて悪用されます。

自動更新の設定、レジストラーのアカウントの多要素認証

TLS の証明書の検証が正しく行われていれば、DNS が偽装されても、攻撃者は正規のドメインの証明書を持っていないため、利用者は接続時にエラーで気付けます。ここでも、証明書の検証を無効にしないことが重要です。

5.5. ファイアウォールとネットワークの分離

ファイアウォールは、あらかじめ定めた規則に従って、通信を許可または遮断する仕組みです。IP アドレスやポート番号で通信を制御するものが一般的です。HTTP の内容を検査して、SQL インジェクションなどの攻撃に特徴的なパターンを遮断するものは WAF（Web Application Firewall）と呼ばれます。

ネットワークを設計する際には、役割ごとにネットワークを分け、必要な通信だけを許可します。

  • インターネットに公開するのは、Web サーバーやロードバランサーなど、公開が必要なものだけにします。

  • データベースは、アプリケーションサーバーからだけ接続できるネットワークに置きます。

  • 管理用の画面や SSH の接続は、インターネットに直接公開せず、VPN や専用の接続経路を経由させます。

ネットワークを分離しておくと、1 台のサーバーに侵入されても、攻撃者がそこから他のサーバーへ侵入を広げることを難しくできます。

注釈

WAF は既知の攻撃パターンを防ぐのに役立ちますが、アプリケーションの脆弱性そのものを修正するものではありません。セキュリティの基本概念で説明した多層防御の 1 つの層として位置付け、アプリケーションの脆弱性は必ず修正してください。

5.6. VPN

VPN（Virtual Private Network）は、インターネットなどの共有のネットワーク上に、暗号化された仮想的な専用の通信路を作る技術です。拠点間の接続や、在宅勤務で社内ネットワークに接続するために使われます。

VPN の機器は、インターネットに公開され、社内ネットワークへの入口となるため、攻撃者に狙われやすい機器です。VPN 機器の脆弱性を突いた侵入は、ランサムウェアの被害の主要な原因の 1 つになっています。VPN 機器のファームウェアは速やかに更新し、ログインには多要素認証を必須にします。

5.7. ゼロトラスト

従来のネットワークの防御は、社内ネットワークは安全、インターネットは危険と考え、その境界を守る考え方（境界型防御）でした。しかし、クラウドサービスの利用や在宅勤務が広がり、守るべき資産と利用者の多くが境界の外にある状況になりました。また、VPN などを通じて一度境界の内側に侵入されると、内部の通信が信頼されているために被害が広がりやすいという問題もあります。

そこで広まったのがゼロトラストの考え方です。ゼロトラストでは、ネットワーク上の位置によって通信を信頼せず、すべてのアクセスについて、利用者、端末、状況を確認したうえで許可します。米国 NIST は、SP 800-207 でゼロトラストの考え方を整理しています。

境界型防御とゼロトラストの比較

観点

境界型防御

ゼロトラスト

ゼロトラストは特定の製品ではなく、セキュリティの基本概念で説明した多層防御と最小権限の原則を、ネットワークの設計に徹底して適用する考え方といえます。
