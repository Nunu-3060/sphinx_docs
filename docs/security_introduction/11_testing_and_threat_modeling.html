11. セキュリティテストと脅威モデリング

これまでの章では、個々の脆弱性と対策を説明してきました。この章では、自分たちのシステムにどのような脅威があるかを洗い出す方法と、脆弱性を見つけるためのテストの方法を説明します。

11.1. 開発工程の早い段階で取り組む

脆弱性は、発見が遅れるほど修正の費用が大きくなります。設計段階であれば設計書を直すだけで済む問題も、リリース後に見つかれば、緊急の修正、再リリース、場合によっては利用者への通知や被害の補償が必要になります。そのため、セキュリティの活動を開発工程のできるだけ早い段階に組み込むことが推奨されています。この考え方をシフトレフトと呼びます。

開発工程ごとのセキュリティ活動

工程

主な活動

要件定義・設計

セキュリティ要件の定義、脅威モデリング

実装

セキュアコーディング、静的解析、コードレビュー、依存関係のスキャン

テスト

動的解析、ファジング、セキュリティのテストケースの実行

リリース前

ペネトレーションテスト（重要なシステムの場合）

運用

脆弱性の監視、ログの監視、インシデント対応（運用とインシデント対応を参照）

11.2. 脅威モデリング

脅威モデリングは、システムの設計をもとに、どのような脅威が考えられるかを体系的に洗い出し、対策を決める活動です。脅威モデリングでは、次の 4 つの問いに順に答えていきます。

  1. 何を作っていますか。

  2. 何がうまくいかなくなる可能性がありますか。

  3. それに対して何をしますか。

  4. 十分にうまくできましたか。

1 つ目の問いには、システムの構成要素とデータの流れを図に描いて答えます。このとき重要なのが信頼境界です。信頼境界とは、信頼の度合いが異なる領域の境目で、例えば、インターネットとサーバーの間、アプリケーションとデータベースの間、自社のシステムと外部のサービスの間などです。脅威の多くは、データが信頼境界を越えるところで発生します。

11.2.1. STRIDE

2 つ目の問いに答えるための手がかりとして広く使われているのが、STRIDE です。STRIDE は、脅威を 6 つの種類に分類したもので、それぞれの頭文字をつなげた名前です。データの流れ図の各要素について、6 つの脅威が当てはまらないかを順に検討します。

STRIDE の 6 つの脅威

脅威

損なわれる性質

例

なりすまし（Spoofing）

真正性

盗んだパスワードで他人としてログインします。

改ざん（Tampering）

完全性

通信内容やデータベースのデータを書き換えます。

否認（Repudiation）

否認防止

操作の記録がないため、行った操作を「やっていない」と主張されます。

情報漏えい（Information Disclosure）

機密性

エラーメッセージや、アクセス制御の不備から情報が漏れます。

サービス拒否（Denial of Service）

可用性

大量のリクエストや ReDoS でサービスを停止させます。

権限昇格（Elevation of Privilege）

認可

一般の利用者が管理者の機能を使えるようになります。

例として、パスワードの再設定機能に STRIDE を当てはめると、次のような脅威が見つかります。

パスワードの再設定機能への STRIDE の適用例

脅威

考えられる脅威

対策

なりすまし

再設定用のトークンを推測され、他人のパスワードを変更されます。

トークンを secrets モジュールで生成し、有効期限を短くします。

改ざん

再設定のリクエストのメールアドレスを書き換えて、他人のトークンを自分に送らせます。

送信先は、登録済みのメールアドレスだけにします。

否認

不正な再設定が行われたことを確認できません。

再設定を記録し、利用者にも通知します。

情報漏えい

「このメールアドレスは登録されていません」という応答から、登録の有無を知られます。

登録の有無にかかわらず同じ応答を返します。

サービス拒否

再設定のメールを大量に送らせ、利用者への迷惑や送信費用の増大を引き起こします。

送信回数を制限します。

権限昇格

トークンを使い回して、管理者のパスワードを変更します。

トークンは一度だけ有効にし、対象のアカウントに結び付けます。

脅威モデリングは、専門家だけで行うものではなく、システムを最もよく知る開発者が参加して行うことが重要です。完璧を目指すよりも、設計のレビューの一部として、新しい機能を作るたびに短時間でも行うほうが効果的です。

11.3. 静的解析

静的解析（SAST: Static Application Security Testing）は、プログラムを実行せずに、ソースコードを解析して脆弱性の可能性がある箇所を見つける手法です。開発の早い段階で、すべてのコードを自動的に検査できる利点があります。

Python では、bandit が利用できます。次のコマンドで、本書のサンプルコードのディレクトリ全体を検査できます。

1python -m bandit -r .

本書のサンプルコードに対して実行した結果を、1 行ずつの形式で示します。

本書で悪い例として示した shell=True（B602）、ECB モード（B305）、文字列連結による SQL 文（B608）、pickle.loads()（B301）が、いずれも検出されています。

一方で、静的解析には次のような限界があることも分かります。

  • 誤検知があります。simple_fuzzer.py の random モジュール（B311）は、テスト用の入力を作るためのもので、セキュリティの用途ではありません。password_hashing.py の文字列（B105）も、説明用の値です。検出された箇所を確認し、問題がないと判断したものは、理由を添えて除外（bandit では # nosec のコメント）します。

  • 見逃しがあります。access_control.py のアクセス制御の不備や、flask_security_demo.py の /search-unsafe の XSS は検出されていません。アクセス制御のように、アプリケーションの仕様に依存する脆弱性は、静的解析では見つけにくいものです。

静的解析は、CI のパイプラインに組み込んで、変更のたびに自動的に実行するのが効果的です。新たに検出されたものだけを確認する運用にすると、誤検知の確認の負担も抑えられます。

11.4. 動的解析

動的解析（DAST: Dynamic Application Security Testing）は、動作しているアプリケーションに、攻撃を模したリクエストを送って、脆弱性を見つける手法です。ソースコードがなくても検査でき、設定のミスなど、実行環境に依存する問題も見つけられます。OWASP が開発を始めた ZAP などのツールが広く使われています。

動的解析のツールは、実際に攻撃に近いリクエストを大量に送るため、データの破壊やサービスの停止を引き起こすことがあります。はじめにで説明したとおり、自分が管理するテスト環境に対してだけ実行してください。

11.5. ファジング

ファジングは、ランダムに生成した入力や、正常な入力を少しずつ変化させた入力を大量にプログラムに与えて、異常な動作（例外、クラッシュ、タイムアウトなど）を引き起こす入力を探す手法です。開発者が想定していない入力によるバグを見つけるのに優れています。

次のサンプルは、ファジングの考え方を示す簡単なファザーです。クエリ文字列を解析する関数に、ランダムな入力を与えて、例外が発生する入力を探します。

simple_fuzzer.py
 1"""ファジングの考え方を確認する簡単なファザーのサンプル.
 2
 3ランダムに生成した入力を関数に大量に与え、想定外の例外が発生する入力を
 4探します。開発者が思いつかない入力によるバグを見つけるのに役立ちます。
 5
 6実行方法:
 7    python simple_fuzzer.py
 8
 9必要なライブラリ:
10    なし（標準ライブラリのみ）
11"""
12
13import random
14from collections.abc import Callable
15
16ALPHABET = "ab=&%2 "  # 対象の関数が特別に扱う文字を多めに含める
17ITERATIONS = 10000
18
19
20def parse_query_buggy(query: str) -> dict[str, str]:
21    """「key=value&key=value」形式を解析する（バグあり）."""
22    result: dict[str, str] = {}
23    for pair in query.split("&"):
24        key, value = pair.split("=")  # 「=」がない、または複数あると失敗する
25        result[key] = value
26    return result
27
28
29def parse_query_fixed(query: str) -> dict[str, str]:
30    """「key=value&key=value」形式を解析する（修正版）."""
31    result: dict[str, str] = {}
32    for pair in query.split("&"):
33        if not pair:
34            continue
35        key, _, value = pair.partition("=")
36        result[key] = value
37    return result
38
39
40def fuzz(target: Callable[[str], object], seed: int) -> str | None:
41    """target に例外を発生させる入力を探し、見つかればその入力を返す."""
42    rng = random.Random(seed)  # シードを固定し、結果を再現できるようにする
43    for _ in range(ITERATIONS):
44        length = rng.randint(0, 12)
45        text = "".join(rng.choice(ALPHABET) for _ in range(length))
46        try:
47            target(text)
48        except Exception as error:  # 想定外の例外をすべて捕捉する
49            print(f"  例外を発生させる入力: {text!r}")
50            print(f"  例外: {type(error).__name__}: {error}")
51            return text
52    print(f"  {ITERATIONS} 回の試行で例外は発生しませんでした。")
53    return None
54
55
56def main() -> None:
57    print("[バグのある関数]")
58    fuzz(parse_query_buggy, seed=1)
59    print("[修正版の関数]")
60    fuzz(parse_query_fixed, seed=1)
61
62
63if __name__ == "__main__":
64    main()

実行結果
[バグのある関数]
  例外を発生させる入力: '% '
  例外: ValueError: not enough values to unpack (expected 2, got 1)
[修正版の関数]
  10000 回の試行で例外は発生しませんでした。

バグのある関数は、= を含まない入力を想定しておらず、例外が発生しています。Web アプリケーションであれば、このような想定外の例外はエラー画面の表示やサービスの停止につながり、C で書かれたプログラムであれば、メモリ安全性の問題として任意のコードの実行につながることもあります。

実際のファジングには、プログラムのどの部分が実行されたかを観測しながら、新しい部分を実行させる入力を優先的に生成する、効率の良いツールを使います。Python では Atheris や、プロパティベーステストのライブラリである Hypothesis が利用できます。Google の OSS-Fuzz は、重要なオープンソースのソフトウェアを継続的にファジングし、多くの脆弱性を見つけています。

11.6. ペネトレーションテスト

ペネトレーションテストは、専門家が攻撃者の視点で、実際にシステムへの侵入を試みて、脆弱性と、それによって起こり得る被害を評価するテストです。ツールによる自動的な検査では見つけにくい、仕様や業務の流れに関わる脆弱性や、複数の脆弱性を組み合わせた攻撃を見つけられます。

ペネトレーションテストは費用がかかるため、重要なシステムのリリース前や、大きな変更の後に、外部の専門業者に依頼して行うのが一般的です。依頼の際には、テストの範囲、期間、禁止する行為などを、事前に書面で取り決めます。

また、外部のセキュリティ研究者に脆弱性を探してもらい、報告に報奨金を支払うバグバウンティ制度を設ける組織も増えています。

11.7. コードレビューの観点

コードレビューは、静的解析では見つけにくい、アプリケーションの仕様に依存する脆弱性を見つける有効な手段です。セキュリティの観点でレビューする際の主な確認項目を、本書の内容からまとめます。

セキュリティの観点でのコードレビューの確認項目

観点

確認項目

認証と認可

すべての API で認証を確認していますか。データごとに、利用者にアクセスする権限があるかを確認していますか。

入力の扱い

SQL 文、コマンド、HTML、ファイルのパス、URL に、入力をそのまま埋め込んでいませんか。

暗号

推奨されるアルゴリズムとライブラリを使っていますか。乱数に secrets モジュールを使っていますか。

シークレット

ソースコードやログに、シークレットが含まれていませんか。

エラー処理

利用者に詳細なエラー情報を表示していませんか。エラーが発生したときに、安全な側に倒れますか。

依存関係

新しく追加したパッケージは信頼できるものですか。バージョンは固定されていますか。

また、セキュリティに関わる重要な処理には、単体テストを書いておくことをお勧めします。例えば、「他人の請求書を参照しようとするとエラーになる」ことを確認するテストを書いておけば、後の変更でアクセス制御が壊れたときにすぐに気付けます。
