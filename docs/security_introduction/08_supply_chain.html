8. ソフトウェアサプライチェーン

現在のソフトウェアは、自分たちで書いたコードよりも、オープンソースのライブラリなど他者が作ったコードのほうがはるかに多い構成になっていることが珍しくありません。この章では、ソフトウェアの部品と、それを組み立てて届ける過程（サプライチェーン）に由来するリスクと対策を説明します。

8.1. サプライチェーンに由来するリスク

ソフトウェアのサプライチェーンには、ライブラリ、ビルドツール、パッケージの配布サイト、CI/CD のパイプライン、コンテナイメージなど、多くの要素が含まれます。そのどこか 1 つが侵害されると、それを利用するすべてのソフトウェアに影響が及びます。

サプライチェーンに関する主な事例

年

事例

概要

2020 年

SolarWinds

ネットワーク管理製品のビルド環境が侵害され、正規の更新プログラムにバックドアが仕込まれました。更新を適用した多数の政府機関や企業が影響を受けました。

2021 年

Log4Shell

Java の広く使われているログ出力ライブラリ Log4j に、ログに記録された文字列によって任意のコードを実行される脆弱性（CVE-2021-44228）が見つかりました。自分のシステムのどこで Log4j が使われているかを把握できず、対応に苦労した組織が多くありました。

2024 年

xz Utils

Linux で広く使われている圧縮ライブラリに、長期間にわたって開発に参加し信頼を得た人物によってバックドアが仕込まれました（CVE-2024-3094）。主要な Linux ディストリビューションの安定版に取り込まれる前に、偶然発見されました。

これらの事例から、サプライチェーンのリスクは次の 2 種類に分けられます。

  • 既知の脆弱性: 利用しているライブラリに脆弱性が見つかる（Log4Shell など）。

  • 意図的な侵害: ライブラリや配布経路そのものに、悪意のあるコードが仕込まれる（SolarWinds、xz Utils など）。

8.2. 依存関係の管理

アプリケーションが直接利用するライブラリを直接依存、そのライブラリがさらに利用しているライブラリを推移的依存と呼びます。推移的依存を含めると、数個のライブラリを導入しただけで、数十から数百のパッケージに依存することも珍しくありません。依存関係を管理するうえでの基本的な方針は、次のとおりです。

  • 依存するパッケージを必要最小限にしてください。数行で書ける機能のために、ライブラリを追加しないようにします。

  • 導入前にパッケージを評価してください。継続的に保守されているか、利用者は多いか、脆弱性への対応の実績はあるか、といった点を確認します。

  • バージョンを固定してください。推移的依存も含めて、使用するバージョンをロックファイルに記録します。これにより、いつ、どのバージョンをビルドしても同じ結果になり、意図しない更新や、侵害された新しいバージョンが自動的に取り込まれることを防げます。

  • ハッシュ値を検証してください。ロックファイルにパッケージのハッシュ値も記録し、ダウンロードしたファイルが記録時と同じであることを確認します。pip では --require-hashes オプションで有効にできます。

  • 定期的に更新してください。バージョンを固定したまま放置すると、脆弱性のある古いバージョンを使い続けることになります。更新を自動的に提案するツール（Dependabot など）を使い、テストを通したうえで定期的に更新します。

本書のサンプルコードで使うライブラリも、requirements.txt にバージョンを固定して記載しています。

requirements.txt
1# Additional libraries used by the sample code in this book.
2# Install: python -m pip install -r requirements.txt
3argon2-cffi==25.1.0
4bandit==1.9.4
5cryptography==50.0.2
6Flask==3.1.3
7pip-audit==2.10.1
8PyJWT==2.15.1

8.3. 脆弱性情報の読み方

公開された脆弱性には、CVE（Common Vulnerabilities and Exposures）という識別番号が割り当てられます。CVE-2021-44228 のように、年と連番で表されます。CVE の番号を使えば、ベンダーのお知らせ、セキュリティ製品の検出結果、ニュース記事などの情報を、同じ脆弱性について述べたものとして突き合わせられます。日本では、JVN（Japan Vulnerability Notes）が国内の製品を中心に脆弱性情報を日本語で公開しています。

脆弱性の深刻度を表す指標として、CVSS（Common Vulnerability Scoring System）が広く使われています。CVSS では、攻撃の難しさや影響の大きさなどの要素から、深刻度を 0.0 から 10.0 の数値で表します。

CVSS の深刻度の区分

スコア

深刻度

0.0

なし（None）

0.1 ～ 3.9

低（Low）

4.0 ～ 6.9

中（Medium）

7.0 ～ 8.9

高（High）

9.0 ～ 10.0

緊急（Critical）

ただし、CVSS のスコアは脆弱性そのものの性質を表すもので、自分のシステムでの危険度とは限りません。脆弱な機能を使っていなければ影響はありませんし、インターネットに公開されているシステムでは危険度が高くなります。対応の優先度を決める際には、次の情報も参考にします。

  • 悪用の実績: 米国の CISA は、悪用が確認された脆弱性の一覧（KEV カタログ）を公開しています。

  • 悪用される可能性の予測: EPSS（Exploit Prediction Scoring System）は、30 日以内に悪用される確率を推定した値を公開しています。

8.4. 脆弱性スキャン

利用しているパッケージに既知の脆弱性がないかを人手で調べ続けることは困難です。パッケージの一覧を脆弱性データベースと照合するツールを使って、自動的に確認します。

Python では、pip-audit が利用できます。requirements.txt を指定して実行すると、記載されたパッケージとその依存パッケージを、Python のパッケージの脆弱性データベースと照合します。

1python -m pip_audit -r requirements.txt

本書の requirements.txt に対して実行した結果は、次のとおりです。

実行結果（2026 年 10 月時点）
No known vulnerabilities found

比較のため、古いバージョンを指定したファイルに対して実行すると、次のように脆弱性が報告されます。Fix Versions 列は、その脆弱性が修正されたバージョンです。

古いバージョン（Flask 2.2.0、PyJWT 2.3.0）に対する実行結果（抜粋）
Found 20 known vulnerabilities in 2 packages
Name  Version ID              Fix Versions

脆弱性データベースは日々更新されるため、同じファイルに対しても、実行する日によって結果が変わります。脆弱性スキャンは一度きりではなく、CI のパイプラインに組み込んで、変更のたびと定期的に実行します。

8.5. SBOM

Log4Shell の際には、多くの組織が「自分たちのどのシステムで Log4j が使われているか」をすぐに答えられませんでした。この問題に対処するのが SBOM（Software Bill of Materials、ソフトウェア部品表）です。SBOM は、ソフトウェアに含まれるすべての部品（パッケージ名、バージョン、ライセンス、提供元など）を、機械で処理できる形式で列挙したものです。

SBOM の代表的な形式には、SPDX と CycloneDX があります。SBOM をビルドのたびに生成して保管しておけば、新しい脆弱性が公開されたときに、影響を受けるシステムを短時間で特定できます。Python のプロジェクトでは、cyclonedx-bom などのツールで生成できます。

8.6. 悪意のあるパッケージ

パッケージの配布サイトには、誰でもパッケージを公開できます。これを悪用して、悪意のあるパッケージを利用者に導入させる攻撃があります。

悪意のあるパッケージを導入させる主な手口

手口

内容

タイポスクワッティング

有名なパッケージとよく似た名前（requests に対する reqeusts など）で悪意のあるパッケージを公開し、入力の誤りによって導入させます。

依存関係の混乱（Dependency Confusion）

社内で使っている非公開パッケージと同じ名前のパッケージを公開の配布サイトに公開し、パッケージ管理ツールに誤って公開版を導入させます。

アカウントの乗っ取り

正規のパッケージの開発者のアカウントを乗っ取り、悪意のあるコードを含む新しいバージョンを公開します。

開発の引き継ぎ

保守されなくなったパッケージの開発を引き継ぎ、信頼を得た後に悪意のあるコードを加えます。

Python のパッケージは、導入時に任意のコードを実行できる場合があるため、導入しただけで被害を受けることがあります。対策として、次の点を守ります。

  • パッケージ名は、公式のドキュメントからコピーするなどして、正確に指定します。

  • 社内のパッケージを使う場合は、パッケージの取得元を明示的に設定し、公開の配布サイトの同名パッケージが優先されないようにします。

  • パッケージを公開する側は、配布サイトのアカウントに多要素認証を設定します。PyPI の Trusted Publishing のように、長期間有効な API トークンを使わずに CI から公開する仕組みを利用します。

8.7. CI/CD パイプラインのセキュリティ

CI/CD のパイプラインは、ソースコードを取得し、ビルドし、本番環境に配置する権限を持っています。パイプラインが侵害されると、正規の手順で悪意のあるコードが本番環境に配置されてしまいます。SolarWinds の事例も、ビルド環境の侵害によるものでした。

CI/CD パイプラインの主なリスクと対策

リスク

対策

シークレットの漏えい

パイプラインに渡すシークレットを必要最小限にし、ログに出力されないようにします。外部からのプルリクエストで実行されるジョブには、シークレットを渡しません。

過剰な権限

パイプラインに与えるトークンの権限を最小限にします。クラウドへの配置には、長期間有効なアクセスキーではなく、OpenID Connect による一時的な認証情報を使います。

サードパーティの部品の改ざん

GitHub Actions などで外部のアクションを使う場合は、タグ（v4 など）ではなくコミットのハッシュ値でバージョンを固定します。タグは後から別のコミットを指すように変更できるためです。

成果物の改ざん

ビルドした成果物に署名し、配置の前に検証します。Sigstore などの仕組みで、どのソースコードからどの手順でビルドされたかの証明（来歴情報）を付けます。

ビルドの来歴を検証可能にする取り組みは、SLSA（Supply-chain Levels for Software Artifacts）という枠組みとして整理されています。
