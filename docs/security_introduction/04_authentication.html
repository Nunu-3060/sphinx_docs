4. 認証と認可

この章では、利用者が誰なのかを確かめる仕組みと、その利用者に何を許すのかを決める仕組みを説明します。

4.1. 認証と認可の違い

認証と認可は、名前は似ていますが別の処理です。

認証と認可の違い

処理

確かめること

例

認証（Authentication）

相手が主張どおりの本人であるか

パスワードやパスキーによるログイン

認可（Authorization）

認証された相手に、その操作を許可してよいか

一般の利用者は自分の注文だけを、管理者はすべての注文を参照できます。

認証が正しくても、認可に不備があれば、ログインした利用者が他人のデータを参照できてしまいます。両方を正しく実装する必要があります。

本人であることを確かめる手がかりは、次の 3 種類に分けられます。これを認証の 3 要素と呼びます。

認証の 3 要素

要素

内容

例

知識情報

本人だけが知っているもの

パスワード、暗証番号

所持情報

本人だけが持っているもの

スマートフォン、セキュリティキー

生体情報

本人の身体的な特徴

指紋、顔

異なる要素を 2 つ以上組み合わせる認証を多要素認証と呼びます。パスワードを 2 回入力させるような、同じ要素の組み合わせは多要素認証ではありません。

4.2. パスワードの安全な保存

パスワードをそのまま（平文で）データベースに保存してはいけません。データベースが漏えいした場合に、すべての利用者のパスワードが知られてしまいます。多くの人は複数のサービスで同じパスワードを使い回しているため、被害は他のサービスにも及びます。

4.2.1. ハッシュ関数をそのまま使う問題

パスワードのハッシュ値を保存すれば元のパスワードは分からない、と考えるかもしれません。しかし、SHA-256 のような汎用のハッシュ関数をそのまま使うことには、次の 2 つの問題があります。

  • 同じパスワードは同じハッシュ値になります。よく使われるパスワードのハッシュ値をあらかじめ計算した表（レインボーテーブルなど）を使えば、表を引くだけで元のパスワードが分かります。

  • 計算が速すぎます。GPU を使えば、1 秒間に数十億回以上のハッシュ値を計算でき、短いパスワードは総当たりですぐに見つかります。

4.2.2. ソルトとストレッチング

1 つ目の問題には、利用者ごとに異なるランダムな値（ソルト）をパスワードに加えてからハッシュ値を計算することで対処します。ソルトが異なれば、同じパスワードでもハッシュ値が変わるため、事前に計算した表が使えなくなります。

2 つ目の問題には、ハッシュ値の計算を意図的に重くすることで対処します。これをストレッチングと呼びます。正規の利用者がログインする際の 0.1 秒程度の遅れは問題になりませんが、総当たりを試みる攻撃者にとっては、試行できる回数が大幅に減ります。

パスワードの保存には、これらを組み込んだ専用の関数を使います。現在、OWASP が第一に推奨しているのは Argon2id です。Argon2id は計算時間だけでなく大量のメモリを必要とするため、GPU や専用のハードウェアによる並列計算も難しくなっています。

次のサンプルでは、argon2-cffi ライブラリを使って、ソルトなしの SHA-256 と Argon2id を比較します。

Argon2id の出力には、アルゴリズム名、パラメーター（m はメモリ量の KiB、t は反復回数、p は並列度）、ソルト、ハッシュ値がすべて含まれています。そのため、この文字列をそのまま保存すれば、後からパラメーターを強化しても、古いハッシュ値を検証できます。check_needs_rehash() が True を返した場合は、ログインに成功したときに新しいパラメーターでハッシュ値を計算し直して保存します。

この例では、1 回の計算に約 70 ミリ秒かかっています。SHA-256 と比べて 3 万倍以上遅く、攻撃者が同じ時間で試せるパスワードの数もそれだけ少なくなります。

4.2.3. パスワードの要件

利用者に求めるパスワードの要件も、近年考え方が変わっています。米国 NIST のガイドライン SP 800-63B では、次のような方針が示されています。

  • 長さを重視します。長いパスワード（パスフレーズ）を入力できるようにします。

  • 大文字・小文字・記号の組み合わせなど、文字種の規則を強制しません。

  • 定期的な変更を強制しません。漏えいの疑いがある場合にだけ変更させます。

  • 過去に漏えいしたパスワードや、よく使われるパスワードの一覧と照合し、該当するものは拒否します。

文字種の規則や定期的な変更を強制すると、利用者は「Password1!」のような推測しやすいパターンを使ったり、末尾の数字だけを変えたりするようになり、かえって安全性が下がることが分かってきたためです。

4.3. ログイン処理への攻撃と対策

パスワードを安全に保存していても、ログイン画面から直接パスワードを試す攻撃は防げません。代表的な攻撃を次の表に示します。

ログイン処理への代表的な攻撃

攻撃

内容

総当たり攻撃

1 つのアカウントに対して、考えられるパスワードを順に試します。

パスワードスプレー攻撃

よく使われる少数のパスワードを、多数のアカウントに対して試します。アカウントごとの失敗回数が少ないため、アカウント単位の制限では検知しにくい攻撃です。

パスワードリスト攻撃

他のサービスから漏えいした ID とパスワードの組をそのまま試します。パスワードの使い回しを狙った攻撃で、成功率が高いことが知られています。

これらの攻撃には、次のような対策を組み合わせます。

  • 試行回数を制限してください。アカウント単位と接続元 IP アドレス単位の両方で、短時間の失敗回数を制限します。

  • 多要素認証を導入してください。パスワードが知られても、それだけではログインできなくなります。

  • 漏えいパスワードと照合してください。パスワードの登録時や変更時に、既知の漏えいパスワードと照合します。

  • エラーメッセージを統一してください。「ユーザー名が存在しません」と「パスワードが違います」を区別すると、攻撃者に有効なユーザー名を教えてしまいます。どちらの場合も「ユーザー名またはパスワードが違います」と表示します。

  • 異常を検知してください。普段と異なる国や端末からのログインを検知し、追加の確認を求めたり、利用者に通知したりします。

試行回数を制限する方法の 1 つに、失敗が続くたびに次の試行までの待ち時間を延ばす方法があります。一定回数の失敗でアカウントを完全にロックする方法は、攻撃者が正規の利用者を意図的にロックアウトさせる攻撃に悪用されるおそれがあるため、待ち時間を延ばす方法のほうが扱いやすい場合があります。次のサンプルでは、連続して 3 回失敗した後は、待ち時間を 2 秒、4 秒、8 秒、と倍に延ばしていきます。

login_throttle.py
 1"""ログイン試行の制限（スロットリング）のサンプル.
 2
 3同じアカウントへのログイン失敗が続いた場合に、次に試行できるまでの
 4待ち時間を指数関数的に延ばします。総当たり攻撃の速度を大きく落とせます。
 5
 6実行方法:
 7    python login_throttle.py
 8
 9必要なライブラリ:
10    なし（標準ライブラリのみ）
11"""
12
13from dataclasses import dataclass, field
14
15FREE_ATTEMPTS = 3  # 待ち時間なしで許す連続失敗回数
16BASE_DELAY = 1.0  # 待ち時間の基準値（秒）
17MAX_DELAY = 900.0  # 待ち時間の上限（秒）
18
19
20@dataclass
21class AccountState:
22    """アカウントごとの失敗回数と、次に試行できる時刻."""
23
24    failures: int = 0
25    locked_until: float = 0.0
26
27
28@dataclass
29class LoginThrottle:
30    """アカウント単位でログイン試行を制限する."""
31
32    states: dict[str, AccountState] = field(default_factory=dict)
33
34    def is_allowed(self, account: str, now: float) -> bool:
35        """現在時刻 now にログインを試行してよいか判定する."""
36        state = self.states.get(account)
37        return state is None or now >= state.locked_until
38
39    def record_failure(self, account: str, now: float) -> float:
40        """失敗を記録し、次に試行できるまでの待ち時間（秒）を返す."""
41        state = self.states.setdefault(account, AccountState())
42        state.failures += 1
43        over = state.failures - FREE_ATTEMPTS
44        delay = 0.0 if over <= 0 else min(BASE_DELAY * 2 ** over, MAX_DELAY)
45        state.locked_until = now + delay
46        return delay
47
48    def record_success(self, account: str) -> None:
49        """成功したら失敗回数をリセットする."""
50        self.states.pop(account, None)
51
52
53def main() -> None:
54    throttle = LoginThrottle()
55    duration = 3600  # 攻撃者が 1 秒に 1 回、1 時間試行し続けたとする
56    accepted = 0
57
58    # 説明のため、時刻は実時間ではなく数値で進める
59    for now in range(duration):
60        if not throttle.is_allowed("alice", now):
61            continue  # ロック中の試行はパスワードを照合せずに拒否する
62        accepted += 1
63        delay = throttle.record_failure("alice", now)
64        print(f"{now:5d} 秒: 照合して失敗。次の試行まで {delay:4.0f} 秒待つ")
65
66    print(f"制限なしの場合に照合される回数: {duration} 回")
67    print(f"制限ありの場合に照合された回数: {accepted} 回")
68
69
70if __name__ == "__main__":
71    main()

多要素認証の代表的な方式を次の表に示します。

仕組み

注意点

4.4.1. TOTP の仕組み

認証アプリが表示する 6 桁のコードは、TOTP（Time-based One-Time Password、RFC 6238）という方式で計算されています。サーバーと認証アプリは、登録時に QR コードなどで秘密鍵を共有しておきます。その後は、双方が現在時刻と秘密鍵から同じコードを計算します。

コードの計算に使う値は、現在の UNIX 時刻 \(t\) を 30 秒ごとに区切った番号です。

\[T = \left\lfloor \frac{t}{30} \right\rfloor\]

この \(T\) を入力として秘密鍵で HMAC を計算し、その一部を 10 進数の 6 桁に変換したものがコードになります。次のサンプルでは、TOTP を標準ライブラリだけで実装し、RFC 6238 に記載されたテストベクターで正しさを確認しています。

totp.py
 1"""ワンタイムパスワード（TOTP、RFC 6238）の実装サンプル.
 2
 3認証アプリが表示する 6 桁のコードは、共有の秘密鍵と現在時刻から
 4HMAC を使って計算されています。
 5
 6実行方法:
 7    python totp.py
 8
 9必要なライブラリ:
10    なし（標準ライブラリのみ）
11"""
12
13import base64
14import hashlib
15import hmac
16import secrets
17import struct
18import time
19
20TIME_STEP = 30  # コードが切り替わる間隔（秒）
21
22
23def hotp(key: bytes, counter: int, digits: int = 6) -> str:
24    """カウンター値からワンタイムパスワードを計算する（RFC 4226）."""
25    digest = hmac.new(key, struct.pack(">Q", counter), hashlib.sha1).digest()
26    # 動的切り出し: 最後のバイトの下位 4 ビットを開始位置にする
27    offset = digest[-1] & 0x0F
28    code = struct.unpack(">I", digest[offset:offset + 4])[0] & 0x7FFFFFFF
29    return str(code % 10 ** digits).zfill(digits)
30
31
32def totp(key: bytes, unix_time: float, digits: int = 6) -> str:
33    """時刻からワンタイムパスワードを計算する（RFC 6238）."""
34    return hotp(key, int(unix_time // TIME_STEP), digits)
35
36
37def verify_totp(key: bytes, code: str, unix_time: float,
38                window: int = 1) -> bool:
39    """前後 window ステップの時刻のずれを許して検証する."""
40    for step in range(-window, window + 1):
41        candidate = totp(key, unix_time + step * TIME_STEP, len(code))
42        if hmac.compare_digest(candidate, code):
43            return True
44    return False
45

49    rfc_key = b"12345678901234567890"

51    print(f"RFC 6238 のテストベクター: {result}（期待値 94287082）")
52
53    # 新しい秘密鍵を作り、認証アプリに登録する形式（Base32）で表示する
54    key = secrets.token_bytes(20)
55    print(f"秘密鍵（Base32）: {base64.b32encode(key).decode('ascii')}")
56
57    now = time.time()
58    code = totp(key, now)
59    print(f"現在のコード: {code}")
60    print(f"現在の検証結果: {verify_totp(key, code, now)}")
61    print(f"5 分後に同じコードで検証: {verify_totp(key, code, now + 300)}")

verify_totp() は、端末の時計のずれを考慮して、前後 1 区間（30 秒）のコードも受け付けています。実際のシステムでは、これに加えて、一度使われたコードを再び受け付けないようにし、コードの試行回数も制限します。6 桁のコードは 100 万通りしかないため、制限がなければ総当たりで突破されるおそれがあるからです。

4.5. パスキー

パスキーは、パスワードの代わりに公開鍵暗号を使ってログインする仕組みで、FIDO Alliance と W3C が策定した FIDO2（WebAuthn）という規格に基づいています。

パスキーによる認証は、次のように行われます。

  1. 登録時に、利用者の端末がそのサービス専用の鍵ペアを生成し、公開鍵だけをサーバーに登録します。秘密鍵は端末の中に保管されます。

  2. ログイン時に、サーバーはランダムな値（チャレンジ）を送ります。

  3. 端末は、指紋や顔、PIN などで利用者本人であることを確認したうえで、秘密鍵でチャレンジに署名します。

  4. サーバーは、登録済みの公開鍵で署名を検証します。

パスキーには、パスワードに比べて次の利点があります。

  • サーバーに秘密の情報がありません。サーバーに保存されるのは公開鍵だけなので、データベースが漏えいしても、ログインに悪用される情報は含まれません。

  • 使い回しがありません。サービスごとに異なる鍵ペアが作られます。

  • フィッシングに強い方式です。鍵ペアは登録したサービスのドメインに結び付けられており、ブラウザーが接続先のドメインを確認します。偽サイトでは、そもそも正規サイトの鍵が使われません。

最後の点が特に重要です。TOTP などの確認コードは、利用者が偽サイトに入力してしまえば、攻撃者がそれを正規サイトに転送してログインできます。パスキーでは、利用者がだまされても認証が成立しません。

4.6. セッション管理

HTTP は、リクエストごとに独立したプロトコルです。ログインした状態を維持するために、サーバーはログインに成功した利用者にセッション ID を発行し、以降のリクエストではブラウザーが Cookie でセッション ID を送ります。セッション ID を盗まれると、パスワードを知られなくても、本人になりすまされます。セッション管理では、次の点に注意します。

セッション管理の注意点

項目

内容

推測できない値

セッション ID は、暗号技術の基礎で説明した secrets モジュールなど、暗号論的に安全な乱数で生成します。連番や時刻から作ってはいけません。

ログイン時の再発行

ログインの前後で同じセッション ID を使い続けると、攻撃者があらかじめ用意したセッション ID を利用者に使わせ、ログイン後にそのセッションを乗っ取る攻撃（セッション固定攻撃）が成立します。ログインに成功したら、新しいセッション ID を発行します。

有効期限

一定時間操作がなければセッションを無効にします。重要な操作の前には、パスワードの再入力などで本人を再確認します。

ログアウト時の無効化

ブラウザーの Cookie を消すだけでなく、サーバー側でもセッションを無効にします。

Cookie の属性

Secure、HttpOnly、SameSite の各属性を設定します。詳しくは Web アプリケーションのセキュリティで説明します。

URL に含めないこと

セッション ID を URL に含めると、ログやリファラー（遷移元の情報）を通じて漏えいします。

4.7. トークンによる認証（JWT）

API では、セッション ID の代わりに、署名付きのトークンを使うことがあります。代表的な形式が JWT（JSON Web Token、RFC 7519）です。JWT は、ヘッダー、ペイロード（クレームと呼ばれる情報の集まり）、署名の 3 つの部分を Base64URL でエンコードし、ピリオドでつないだ文字列です。

1eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIiOiJhbGljZSJ9.署名

JWT を扱う際には、次の点に注意します。

  • ペイロードは暗号化されていません。署名は改ざんを防ぐだけで、内容は誰でもデコードして読めます。秘密にすべき情報を入れてはいけません。

  • 許可するアルゴリズムを固定してください。JWT のヘッダーには署名アルゴリズムが書かれていますが、この値は攻撃者が自由に書き換えられます。ヘッダーの alg を none（署名なし）に書き換えた偽造トークンを受け入れてしまう実装や、公開鍵を HMAC の鍵として使わせる攻撃（アルゴリズム混同攻撃）が知られています。検証時には、サーバー側で許可するアルゴリズムを明示します。

  • クレームを検証してください。有効期限（exp）、発行者（iss）、想定する受信者（aud）などを検証します。

  • 有効期限を短くしてください。JWT は、サーバーに状態を持たずに検証できる反面、発行後に個別に無効化することが困難です。有効期限を短くし、必要に応じて別のリフレッシュトークンで更新する設計にします。

次のサンプルでは、PyJWT ライブラリを使ってトークンを発行・検証し、期限切れのトークンや alg=none の偽造トークンが拒否されることを確認します。

21SECRET_KEY = secrets.token_bytes(32)

25def issue_token(user_id: str, lifetime: timedelta) -> str:
26    """ユーザー ID を含むトークンを発行する."""
27    now = datetime.now(timezone.utc)
28    payload = {
29        "sub": user_id,
30        "iss": ISSUER,
31        "iat": now,
32        "exp": now + lifetime,
33    }
34    return jwt.encode(payload, SECRET_KEY, algorithm="HS256")
35
36
37def verify_token(token: str) -> dict[str, Any]:
38    """トークンを検証し、問題がなければペイロードを返す."""
39    return jwt.decode(
40        token,
41        SECRET_KEY,
42        algorithms=["HS256"],  # 許可するアルゴリズムを固定する
43        issuer=ISSUER,
44        options={"require": ["exp", "iss", "sub"]},
45    )

48def unsafe_decode(token: str) -> dict[str, Any]:
49    """署名を検証せずにデコードする（悪い例）."""
50    return jwt.decode(token, options={"verify_signature": False})

53def b64url(data: dict[str, Any]) -> str:
54    """辞書を JSON にして Base64URL でエンコードする."""
55    raw = json.dumps(data).encode("utf-8")
56    return base64.urlsafe_b64encode(raw).rstrip(b"=").decode("ascii")

59def forge_none_token(user_id: str) -> str:
60    """alg=none を指定した、署名のない偽造トークンを作る."""
61    header = {"alg": "none", "typ": "JWT"}
62    payload = {"sub": user_id, "iss": ISSUER, "exp": 4102444800}
63    return f"{b64url(header)}.{b64url(payload)}."

66def try_verify(label: str, token: str) -> None:
67    """検証を試み、結果を表示する."""
68    try:
69        payload = verify_token(token)
70        print(f"{label}: 成功（sub={payload['sub']}）")
71    except jwt.InvalidTokenError as error:
72        print(f"{label}: 拒否（{type(error).__name__}）")

76    try_verify("正規のトークン", issue_token("alice", timedelta(minutes=15)))
77    try_verify("期限切れのトークン", issue_token("alice", timedelta(seconds=-1)))
78
79    forged = forge_none_token("admin")
80    try_verify("alg=none の偽造トークン", forged)
81    print(f"署名を検証しない場合（悪い例）: {unsafe_decode(forged)}")

4.8. OAuth 2.0 と OpenID Connect

「Google アカウントでログイン」のように、外部のサービスと連携する仕組みには、OAuth 2.0 と OpenID Connect が使われます。両者は目的が異なります。

OAuth 2.0 と OpenID Connect の違い

規格

目的

発行されるもの

OAuth 2.0

利用者の同意に基づいて、アプリケーションに API へのアクセス権限を与えます（認可）。

アクセストークン

OpenID Connect

OAuth 2.0 の上に、利用者が誰であるかを伝える仕組みを加えます（認証）。

ID トークン（JWT 形式）

OAuth 2.0 のアクセストークンは「この API を呼び出してよい」という許可を表すもので、利用者が誰であるかを証明するものではありません。アクセストークンを受け取ったことをもってログインしたとみなす実装は、他のアプリケーション向けに発行されたトークンを使ったなりすましを許すおそれがあります。ログインに使う場合は、OpenID Connect の ID トークンを検証します。

Web アプリケーションやスマートフォンアプリでは、認可コードフローに PKCE（RFC 7636）を組み合わせて使うのが標準的です。認可サーバーとの間でやり取りする state パラメーターも検証し、CSRF を防ぎます。これらは自分で実装せず、実績のあるライブラリや、認証サービスが提供する SDK を使うことをお勧めします。

4.9. アクセス制御

認可を実装する方法をアクセス制御と呼びます。代表的なモデルを次の表に示します。

アクセス制御の代表的なモデル

モデル

内容

例

RBAC（ロールベース）

利用者にロール（役割）を割り当て、ロールごとに権限を決めます。

「編集者」は記事を編集できます。

ABAC（属性ベース）

利用者、データ、環境の属性を組み合わせた規則で判断します。

「所属部署が同じで、勤務時間内なら」参照できます。

どのモデルを使う場合も、次の原則を守ります。

  • サーバー側で判定してください。画面のボタンを非表示にするだけでは、アクセス制御になりません。攻撃者は API を直接呼び出せます。

  • 既定では拒否してください。明示的に許可された操作だけを許可し、それ以外はすべて拒否します。

  • データごとに判定してください。「ログインしているか」だけでなく、「このデータにアクセスする権限があるか」をリクエストごとに確認します。

最後の原則が守られていないことによる脆弱性は非常に多く見られます。具体例は Web アプリケーションのセキュリティで説明します。
