12. 運用とインシデント対応

どれほど注意して開発しても、脆弱性を完全になくすことはできず、新しい攻撃手法も次々に現れます。この章では、運用中のシステムを守り、問題が起きたときに被害を最小限に抑えるための活動を説明します。

12.1. ログと監視

ログは、攻撃の兆候を検知し、問題が起きたときに何が起きたのかを調べるための重要な手がかりです。ログがなければ、侵害されたことにすら気付けず、気付いても被害の範囲を特定できません。

12.1.1. 記録すべきもの

セキュリティの観点では、次のようなイベントを記録します。

  • ログインの成功と失敗、ログアウト、パスワードや多要素認証の設定の変更

  • アクセス制御によって拒否された操作

  • 管理者による操作（権限の変更、設定の変更、データの一括出力など）

  • 入力の検証で拒否されたリクエスト

  • アプリケーションのエラー

各イベントには、日時、利用者、接続元の IP アドレス、操作の対象、結果を含めます。セキュアコーディングで説明したとおり、パスワードなどの機密情報は記録しません。

12.1.2. ログを有効に使うための注意点

  • 時刻を同期してください。複数のサーバーのログを突き合わせて調べるため、すべてのサーバーの時刻を NTP で同期し、タイムゾーンを統一（または明記）します。

  • 1 か所に集めてください。サーバーに侵入した攻撃者は、痕跡を消すためにログを削除しようとします。ログはすぐに別のログ管理システムに転送し、改ざんや削除ができないように保管します。

  • 十分な期間保存してください。侵害は、発生から発覚までに数か月かかることも珍しくありません。法令や業界の基準も考慮して、保存期間を決めます。

  • ログを見る仕組みを作ってください。ログは記録するだけでは役に立ちません。異常を自動的に検知して担当者に通知する仕組みを作ります。複数のシステムのログを集めて相関分析を行う SIEM（Security Information and Event Management）という製品もあります。

12.1.3. 検知の例

次のサンプルは、認証のログから、短時間にログインの失敗を繰り返している接続元と、失敗が続いた後にログインに成功した接続元を検知します。後者は、パスワードの総当たりが成功した可能性があるため、特に注意が必要です。

auth_log_monitor.py
 1"""認証ログから不審なアクセスを検知するサンプル.
 2
 3一定時間内にログイン失敗を繰り返している接続元と、失敗が続いた後に
 4ログインに成功した接続元（不正ログインの可能性がある）を検出します。
 5
 6実行方法:
 7    python auth_log_monitor.py
 8
 9必要なライブラリ:
10    なし（標準ライブラリのみ）
11"""
12
13import re
14from collections import defaultdict, deque
15from dataclasses import dataclass
16from datetime import datetime, timedelta
17
18SAMPLE_LOG = """\
192026-10-05T09:00:01 LOGIN_SUCCESS user=alice ip=192.0.2.10
202026-10-05T09:01:00 LOGIN_FAILURE user=admin ip=203.0.113.7
212026-10-05T09:01:02 LOGIN_FAILURE user=admin ip=203.0.113.7
222026-10-05T09:01:04 LOGIN_FAILURE user=root ip=203.0.113.7
232026-10-05T09:01:06 LOGIN_FAILURE user=bob ip=203.0.113.7
242026-10-05T09:01:08 LOGIN_FAILURE user=bob ip=203.0.113.7
252026-10-05T09:01:10 LOGIN_SUCCESS user=bob ip=203.0.113.7
262026-10-05T09:05:00 LOGIN_FAILURE user=carol ip=198.51.100.3
272026-10-05T09:30:00 LOGIN_SUCCESS user=carol ip=198.51.100.3
28"""
29
30LINE = re.compile(
31    r"(?P<time>\S+) (?P<event>LOGIN_SUCCESS|LOGIN_FAILURE) "
32    r"user=(?P<user>\S+) ip=(?P<ip>\S+)"
33)
34WINDOW_MINUTES = 5  # 失敗回数を数える時間幅（分）
35WINDOW = timedelta(minutes=WINDOW_MINUTES)
36THRESHOLD = 5  # この回数以上の失敗で警告する
37
38
39@dataclass(frozen=True)
40class Event:
41    """ログの 1 行を表す."""
42
43    time: datetime
44    success: bool
45    user: str
46    ip: str
47
48
49def parse(log: str) -> list[Event]:
50    """ログを解析する。形式に合わない行は無視する."""
51    events = []
52    for line in log.splitlines():
53        match = LINE.fullmatch(line.strip())
54        if match is None:
55            continue
56        events.append(Event(
57            time=datetime.fromisoformat(match["time"]),
58            success=match["event"] == "LOGIN_SUCCESS",
59            user=match["user"],
60            ip=match["ip"],
61        ))
62    return events
63
64
65def detect(events: list[Event]) -> list[str]:
66    """不審なアクセスを検知し、警告メッセージの一覧を返す."""
67    alerts: list[str] = []
68    failures: dict[str, deque[datetime]] = defaultdict(deque)
69    for event in events:
70        recent = failures[event.ip]
71        # 時間幅より古い失敗の記録を捨てる
72        while recent and event.time - recent[0] > WINDOW:
73            recent.popleft()
74        if not event.success:
75            recent.append(event.time)
76            if len(recent) == THRESHOLD:
77                alerts.append(f"{event.time} {event.ip}: "
78                              f"{WINDOW_MINUTES} 分以内に {THRESHOLD} 回の失敗")
79        elif len(recent) >= THRESHOLD:
80            alerts.append(f"{event.time} {event.ip}: 失敗が続いた後に "
81                          f"{event.user} としてログイン成功（要調査）")
82            recent.clear()
83    return alerts
84
85
86def main() -> None:
87    for alert in detect(parse(SAMPLE_LOG)):
88        print(f"[警告] {alert}")
89
90
91if __name__ == "__main__":
92    main()

実行結果
[警告] 2026-10-05 09:01:08 203.0.113.7: 5 分以内に 5 回の失敗
[警告] 2026-10-05 09:01:10 203.0.113.7: 失敗が続いた後に bob としてログイン成功（要調査）

接続元 203.0.113.7 は、複数のアカウントに対して短時間にログインを試み、最後に bob としてログインに成功しています。一方、198.51.100.3 の 1 回の失敗は、利用者の入力ミスとみなして警告していません。このように、しきい値を調整して、対応が必要な事象だけを通知することが、警告の見逃しを防ぐうえで重要です。警告が多すぎると、担当者は警告を確認しなくなってしまいます。

12.2. パッチ管理

公開された脆弱性は、修正プログラム（パッチ）が公開された後、短期間で悪用が始まることがあります。パッチを速やかに適用するための仕組みを整えておくことが重要です。

  • 資産を把握してください。どのサーバーで、どのソフトウェアのどのバージョンが動いているかを把握していなければ、パッチの要否を判断できません。ソフトウェアサプライチェーンで説明した SBOM も役立ちます。

  • 優先度を決めてください。すべてのパッチを即座に適用することは難しいため、インターネットに公開されているシステム、悪用が確認されている脆弱性（KEV カタログに掲載されたものなど）を優先します。

  • 適用を自動化してください。OS のパッケージの自動更新や、コンテナイメージの定期的な再作成など、人手を介さずに適用できる仕組みを作ります。テストを自動化しておくと、更新による不具合を恐れずに適用できます。

  • サポートの終了を管理してください。サポートが終了した OS やソフトウェアには、脆弱性が見つかってもパッチが提供されません。サポートの終了日を把握し、計画的に移行します。

12.3. バックアップ

バックアップは、障害や操作ミスだけでなく、ランサムウェアからの復旧のためにも欠かせません。近年のランサムウェアは、復旧を妨げるために、暗号化の前にバックアップを探して削除することが知られています。そのため、バックアップは次のように設計します。

ランサムウェアを想定したバックアップの設計

項目

内容

3-2-1 ルール

データのコピーを 3 つ以上持ち、2 種類以上の媒体に保存し、そのうち 1 つは別の場所に保管します。

オフライン・変更不可

少なくとも 1 つのバックアップは、ネットワークから切り離すか、一定期間削除や変更ができない設定（イミュータブルストレージ）で保管します。

認証情報の分離

バックアップを管理する権限を、通常の管理者アカウントとは分けます。管理者アカウントを乗っ取られても、バックアップを削除できないようにします。

復旧の訓練

定期的に実際に復旧を試し、手順と所要時間を確認します。復旧できないバックアップは、ないのと同じです。

12.4. インシデント対応

セキュリティを損なう事象、またはその疑いのある事象をインシデントと呼びます。インシデントが発生したときに、被害を最小限に抑えられるかどうかは、事前の準備でほぼ決まります。インシデント対応は、一般に次の流れで進めます。

インシデント対応の流れ

段階

主な活動

準備

対応の体制（CSIRT など）と連絡先を決め、対応手順を文書にし、訓練を行います。ログとバックアップの仕組みを整えます。

検知・分析

監視の警告や外部からの連絡で異常を検知し、インシデントかどうか、影響の範囲と深刻度を判断します。

封じ込め

被害の拡大を防ぎます。感染した端末をネットワークから切り離す、漏えいした認証情報を無効にする、などです。

根絶

侵入の原因となった脆弱性を修正し、攻撃者が残したマルウェアやアカウントを取り除きます。

復旧

安全を確認したうえで、システムを通常の運用に戻します。必要に応じてバックアップから復元します。

事後対応

原因と対応を振り返り、再発防止策を決めます。対応手順の改善点も洗い出します。

インシデントの対応では、次の点に注意します。

  • 証拠を保全してください。原因の調査や法的な手続きのために、ログやディスクの内容を保存します。慌ててサーバーを初期化したり再起動したりすると、メモリ上の痕跡などの重要な証拠が失われることがあります。

  • 記録を取ってください。いつ、誰が、何を判断し、何を行ったかを時系列で記録します。

  • 関係者に連絡してください。経営層、法務、広報などと連携します。個人データの漏えいの場合は、個人情報保護法に基づいて、個人情報保護委員会への報告と本人への通知が必要になることがあります。

  • 個人を責めないでください。事後の振り返りは、個人の責任を追及するのではなく、仕組みの改善を目的に行います。責められることを恐れて報告が遅れると、次のインシデントの被害が大きくなります。

12.5. 脆弱性の報告と開示

自社の製品やサービスの脆弱性を、外部のセキュリティ研究者や利用者が見つけることがあります。そのような報告を受け付ける窓口を用意しておくことも、運用の重要な一部です。

窓口を知らせる標準的な方法として、security.txt（RFC 9116）があります。Web サイトの /.well-known/security.txt に、次のような内容のファイルを置きます。

security.txt の例
1Contact: mailto:security@example.com
2Expires: 2027-10-01T00:00:00.000Z
3Preferred-Languages: ja, en
4Policy: https://example.com/security-policy

報告を受けたら、受領したことを速やかに報告者に伝え、修正の予定を共有します。修正が完了するまで脆弱性の詳細を公開せず、修正後に報告者と調整して公開する進め方を、調整された開示（Coordinated Vulnerability Disclosure）と呼びます。

一方、自分が他社の製品や Web サイトの脆弱性を見つけた場合は、その組織の窓口に報告するか、日本では IPA に届け出ます。IPA と JPCERT/CC は「情報セキュリティ早期警戒パートナーシップ」という枠組みで、届け出られた脆弱性の情報を開発者や運営者に伝え、対応を調整しています。はじめにで説明したとおり、脆弱性の存在を確かめるために、許可なく攻撃を試みてはいけません。
