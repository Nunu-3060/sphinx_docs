7. セキュアコーディング

この章では、特定の種類のアプリケーションに限らず、コードを書くときに一般的に注意すべき点を説明します。Web アプリケーションのセキュリティで説明した脆弱性の多くも、ここで説明する原則を守ることで防げます。

7.1. 入力検証と出力エンコード

外部から受け取るデータは、すべて信頼できないものとして扱います。利用者がフォームに入力した値だけでなく、HTTP ヘッダー、Cookie、アップロードされたファイル、外部の API の応答、データベースから読み出した値（他の利用者が登録したもの）も含みます。信頼できないデータに対しては、次の 2 つの処理を、それぞれ適切な場所で行います。

入力検証と出力エンコード

処理

行う場所

内容

入力検証

データを受け取ったとき

型、長さ、範囲、形式が想定どおりであることを確認し、想定外のデータは拒否します。

出力エンコード

データを出力するとき

出力先（HTML、SQL、シェル、URL など）で特別な意味を持つ文字を無害化します。

入力検証では、「危険な文字を含まないこと」を確認する拒否リスト方式よりも、「許可した形式に合致すること」を確認する許可リスト方式を使います。危険な文字や表現をすべて列挙することは困難で、拒否リストは見落としによって回避されやすいためです。例えば、郵便番号であれば「数字 3 桁、ハイフン、数字 4 桁」の形式に合致するかを確認します。

入力検証と出力エンコードは、どちらか一方で済ませることはできません。入力検証は、想定外のデータを早い段階で拒否し、処理の誤りを防ぐためのものです。一方、名前の欄に引用符を含む「O'Brien」のような正当なデータもあるため、入力検証だけで SQL インジェクションや XSS を防ぐことはできません。出力先に応じたエンコード（プレースホルダーやエスケープ）を必ず行います。

7.2. エラー処理

エラーの処理を誤ると、情報の漏えいや、セキュリティ機能の回避につながります。OWASP Top 10:2025 でも、例外的な状況の不適切な処理が新たな項目として加えられました。

  • 詳細なエラー情報を利用者に表示しないでください。スタックトレース、SQL 文、ファイルのパス、ライブラリのバージョンなどは、攻撃者に有用な情報を与えます。利用者には一般的なメッセージだけを表示し、詳細はサーバーのログに記録します。

  • 安全な側に倒してください。認可の判定中に例外が発生したときに、処理を続行して許可してしまうような実装は危険です。エラーが発生したら、拒否する側に倒します。

  • すべての例外を握りつぶさないでください。except Exception: pass のように例外を無視すると、攻撃の兆候や異常な状態に気付けなくなります。

  • リソースを確実に解放してください。エラーが発生した場合も、ファイルやデータベースの接続を with 文などで確実に閉じます。解放漏れが積み重なると、サービス停止の原因になります。

7.3. シークレットの管理

パスワード、API キー、暗号鍵などの秘密の情報（シークレット）をソースコードに直接書いてはいけません。ソースコードは、リポジトリを通じて多くの人に共有され、履歴にも残ります。公開リポジトリに誤って登録されたシークレットは、数分のうちに攻撃者の自動化されたツールに発見され、悪用されることが知られています。

シークレットは、次のような方法でアプリケーションに渡します。

  • 環境変数で渡します。

  • クラウドのシークレット管理サービスや、専用のシークレット管理ツールから実行時に取得します。

  • 設定ファイルを使う場合は、そのファイルをリポジトリに登録しません（.gitignore に追加します）。

コードのリポジトリサービスの多くは、登録されたシークレットを検出する機能（シークレットスキャン）を提供しています。これを有効にしておくと、誤って登録した場合にすぐに気付けます。

シークレットをリポジトリに登録してしまった場合は、履歴から削除するだけでは不十分です。すでに第三者に複製されている可能性があるため、ただちにそのシークレットを無効にし、新しいものを発行します。

7.5. タイミング攻撃と定数時間比較

文字列を == で比較すると、多くの実装では、先頭から順に比較し、異なる文字が見つかった時点で処理を終えます。そのため、一致している文字数が多いほど、比較にわずかに長い時間がかかります。攻撃者はこの時間差を大量に測定することで、トークンや MAC などの秘密の値を 1 文字ずつ推測できます。このように、処理時間の違いから秘密の情報を推測する攻撃をタイミング攻撃と呼びます。

秘密の値を比較するときは、一致している位置に関係なく処理時間がほぼ一定になる、hmac.compare_digest()（または同等の secrets.compare_digest()）を使います。実際の時間差は非常に小さく、測定には大量の試行が必要なため、次のサンプルでは、比較した文字数を数えることで処理量の違いを示します。

constant_time_compare.py
 1"""タイミング攻撃と定数時間比較のサンプル.
 2
 3先頭から 1 文字ずつ比較し、異なる文字が見つかった時点で終了する比較では、
 4一致している文字数によって処理時間が変わります。攻撃者はこの差を測定して、
 5秘密の値を 1 文字ずつ推測できます。
 6
 7実際の時間差は小さく測定の誤差に埋もれやすいため、このサンプルでは
 8比較した文字数を数えることで処理量の違いを示します。
 9
10実行方法:
11    python constant_time_compare.py
12
13必要なライブラリ:
14    なし（標準ライブラリのみ）
15"""
16
17import hmac
18
19
20def naive_compare(secret: str, guess: str) -> tuple[bool, int]:
21    """早期終了する比較。結果と比較した文字数を返す（悪い例）."""
22    steps = 0
23    if len(secret) != len(guess):
24        return False, steps
25    for a, b in zip(secret, guess):
26        steps += 1
27        if a != b:
28            return False, steps
29    return True, steps
30
31
32def main() -> None:
33    secret = "s3cr3t-t0ken"
34    guesses = ["xxxxxxxxxxxx", "sxxxxxxxxxxx", "s3cxxxxxxxxx", "s3cr3t-t0kex"]
35
36    print("[早期終了する比較（悪い例）]")
37    for guess in guesses:
38        matched, steps = naive_compare(secret, guess)
39        print(f"  {guess}: 結果={matched!s:5s} 比較した文字数={steps:2d}")
40    print("  -> 先頭の一致が長いほど処理量が増え、推測の手がかりになります。")
41
42    print("[hmac.compare_digest()（良い例）]")
43    for guess in guesses:
44        print(f"  {guess}: 結果={hmac.compare_digest(secret, guess)}")
45    print("  -> 一致している位置に関係なく、処理時間がほぼ一定になります。")
46

49    main()

7.6. 競合状態

複数の処理が同時に実行されるときに、実行の順序によって結果が変わってしまう不具合を競合状態と呼びます。セキュリティの観点では、確認した時点と使用する時点の間に状態が変わることを悪用する攻撃（TOCTOU: Time of Check to Time of Use）が問題になります。

競合状態の例と対策

例

問題

対策

クーポンの利用

「未使用か確認する」と「使用済みにする」の間に、同じクーポンで複数のリクエストを同時に送ると、何度も使えます。

データベースのトランザクションと行ロック、一意性制約で、確認と更新を一体の処理にします。

残高の引き出し

残高の確認と引き落としの間に、同時に引き出しを行うと、残高以上に引き出せます。

UPDATE ... SET balance = balance - ? WHERE balance >= ? のように、条件付きの更新を 1 つの SQL 文で行います。

ファイルの操作

ファイルの存在や権限を確認してから開くまでの間に、そのファイルを別のファイルへのシンボリックリンクに差し替えられます。

確認せずに開き、開いたファイルに対して処理を行います。エラーは例外として処理します。

競合状態は、通常のテストでは再現しにくく、見つけにくい不具合です。お金やポイント、在庫、回数制限など、「1 回だけ」や「上限まで」という制約がある処理では、同時に実行されることを前提に設計します。

7.7. 正規表現によるサービス拒否

正規表現の書き方によっては、特定の入力に対して照合に膨大な時間がかかり、サーバーの CPU を占有されることがあります。これを ReDoS（Regular expression Denial of Service）と呼びます。(a+)+ のように量指定子が入れ子になっている正規表現は、一致しない入力に対して、文字の分け方のすべての組み合わせを試すため、入力の長さに対して処理時間が指数関数的に増えます。

redos.py
 1"""正規表現によるサービス拒否（ReDoS）のサンプル.
 2
 3量指定子を入れ子にした正規表現は、一致しない入力に対して
 4バックトラックの回数が入力の長さに対して指数関数的に増えます。
 5
 6実行方法:
 7    python redos.py
 8    （入力が長くなるにつれて、数秒かかることがあります）
 9
10必要なライブラリ:
11    なし（標準ライブラリのみ）
12"""
13
14import re
15import time
16
17VULNERABLE = re.compile(r"^(a+)+$")  # 量指定子が入れ子になっている
18SAFE = re.compile(r"^a+$")  # 同じ文字列に一致し、入れ子がない
19MAX_INPUT_LENGTH = 64  # 対策: 入力の長さもあわせて制限する
20
21
22def measure(pattern: re.Pattern[str], text: str) -> float:
23    """パターンの照合にかかった時間（秒）を返す."""
24    start = time.perf_counter()
25    pattern.match(text)
26    return time.perf_counter() - start
27
28
29def is_valid(text: str) -> bool:
30    """長さを制限したうえで、入れ子のないパターンで検証する（良い例）."""
31    return len(text) <= MAX_INPUT_LENGTH and SAFE.match(text) is not None
32
33
34def main() -> None:
35    print("長さ  入れ子あり（秒）  入れ子なし（秒）")
36    for length in range(14, 25, 2):
37        # 最後に一致しない文字を置き、すべての組み合わせを試させる
38        text = "a" * length + "!"
39        slow = measure(VULNERABLE, text)
40        fast = measure(SAFE, text)
41        print(f"{length:4d}  {slow:16.4f}  {fast:16.6f}")
42    print("入れ子ありは、長さが 2 増えるたびに時間が約 4 倍になります。")
43    print(f"is_valid('aaaa') = {is_valid('aaaa')}")
44    print(f"is_valid('a' * 100) = {is_valid('a' * 100)}")
45
46
47if __name__ == "__main__":
48    main()

わずか 25 文字の入力で 1 秒以上かかっています。この割合で増えると、31 文字の入力では 1 回の照合に 1 分以上かかる計算になります。対策は次のとおりです。

  • 量指定子を入れ子にしない、選択肢が重なり合う表現（(a|a)* など）を使わない、といった方法で、バックトラックが爆発しない正規表現を書きます。

  • 照合の前に、入力の長さに上限を設けます。

  • 入力の長さに比例した時間で照合することを保証する正規表現エンジン（RE2 など）を使います。

7.8. 一時ファイルの扱い

一時ファイルを、/tmp/myapp.tmp のような推測できる固定の名前で作成すると、同じサーバーの他の利用者に、先回りしてファイルやシンボリックリンクを作られるおそれがあります。一時ファイルは、tempfile モジュールの mkstemp()、NamedTemporaryFile()、TemporaryDirectory() で作成します。これらは推測できない名前でファイルを安全に作成し、作成者だけがアクセスできる権限を設定します。Web アプリケーションのセキュリティのパストラバーサルのサンプルでも、TemporaryDirectory() を使っています。

7.9. ログと機密情報

ログは、障害の調査やインシデントの検知に欠かせませんが、ログに機密情報が含まれていると、ログ自体が漏えいの原因になります。ログは、多くの開発者や運用者が閲覧でき、外部のログ管理サービスに送られ、長期間保存されるためです。

パスワード、トークン、API キー、クレジットカード番号、個人を特定できる情報などは、ログに出力しないようにします。リクエスト全体をログに記録する処理や、例外の発生時に変数の内容を出力する処理で、意図せず出力されることがよくあります。

次のサンプルは、Python の logging モジュールのフィルターで、ログに書き込む前に機密情報を伏せ字に置き換えます。あわせて、API キーを環境変数から読み込む例も示しています。

log_masking.py
 1"""ログに機密情報を出力しないためのサンプル.
 2
 3logging のフィルターで、パスワードやトークンなどをログに書き込む前に
 4伏せ字に置き換えます。シークレットはソースコードに書かず、
 5環境変数などから読み込みます。
 6
 7実行方法:
 8    python log_masking.py
 9
10必要なライブラリ:
11    なし（標準ライブラリのみ）
12"""
13
14import logging
15import os
16import re
17
18# 伏せ字にする項目のパターン（キー名=値、キー名: 値 の形式）
19SENSITIVE = re.compile(
20    r"(?P<key>password|passwd|token|api_key|secret)"
21    r"(?P<sep>\s*[=:]\s*)(?P<value>[^\s,&]+)",
22    re.IGNORECASE,
23)
24CARD_NUMBER = re.compile(r"\b(?:\d[ -]?){12}(?P<last>\d{4})\b")
25
26
27class MaskingFilter(logging.Filter):
28    """ログメッセージに含まれる機密情報を伏せ字にするフィルター."""
29
30    def filter(self, record: logging.LogRecord) -> bool:
31        message = record.getMessage()
32        message = SENSITIVE.sub(r"\g<key>\g<sep>****", message)
33        message = CARD_NUMBER.sub(r"****-****-****-\g<last>", message)
34        record.msg = message
35        record.args = None
36        return True
37
38
39def load_api_key() -> str:
40    """API キーを環境変数から読み込む（ソースコードに書かない）."""
41    api_key = os.environ.get("DEMO_API_KEY")
42    if api_key is None:
43        # 説明用の値。実際のアプリケーションではエラーとして扱う
44        api_key = "sk-demo-1234567890"
45    return api_key
46
47
48def main() -> None:
49    logging.basicConfig(level=logging.INFO, format="%(levelname)s %(message)s")
50    logger = logging.getLogger("demo")
51    logger.addFilter(MaskingFilter())
52
53    api_key = load_api_key()
54    logger.info("login request: user=alice password=P@ssw0rd")
55    logger.info("calling API with api_key=%s", api_key)
56    logger.info("payment: card=4111 1111 1111 1111 amount=1200")
57
58
59if __name__ == "__main__":
60    main()

このようなフィルターは、出力してしまった場合の最後の防御として有効ですが、すべての形式を網羅することはできません。まず、機密情報をログに渡さないようにコードを書くことが基本です。

また、利用者の入力をログにそのまま書き込むと、入力に含まれる改行によって偽のログ行を作られることがあります（ログインジェクション）。ログを JSON などの構造化された形式で出力すると、この問題を避けやすくなります。

7.10. メモリ安全性

C や C++ では、プログラマーがメモリを直接管理します。配列の範囲外への書き込み（バッファオーバーフロー）や、解放済みのメモリの使用（use-after-free）などの誤りがあると、攻撃者に任意のコードを実行されるおそれがあります。大規模なソフトウェアで見つかる深刻な脆弱性の多くは、この種類のメモリ安全性の問題であると報告されています。

Python、Java、Go、Rust などの言語は、メモリを自動的に管理したり、コンパイル時に検査したりすることで、これらの誤りを防ぎます。このような言語をメモリ安全な言語と呼びます。米国の CISA などの政府機関は、新しいソフトウェアの開発にメモリ安全な言語を採用するよう推奨しています。

Python で書いたプログラムでも、C で書かれた拡張モジュールや、ライブラリが内部で使っているネイティブのコード（画像処理や圧縮のライブラリなど）にメモリ安全性の問題があれば、その影響を受けます。ソフトウェアサプライチェーンで説明するように、ライブラリを最新の状態に保つことが重要です。
