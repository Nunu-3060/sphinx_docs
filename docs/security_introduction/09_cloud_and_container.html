9. クラウドとコンテナのセキュリティ

クラウドサービスを使うと、物理的なサーバーの管理から解放され、必要なときに必要なだけリソースを使えます。一方で、設定 1 つでデータを全世界に公開できてしまうため、設定のミスが重大な事故に直結します。この章では、クラウドとコンテナを安全に使うための考え方を説明します。

9.1. 責任共有モデル

クラウドのセキュリティは、クラウド事業者と利用者が分担して担います。この考え方を責任共有モデルと呼びます。どこまでを事業者が担うかは、サービスの種類によって異なります。

どの種類のサービスでも、データとアクセス権限の設定は利用者の責任です。クラウドで起きる情報漏えいの多くは、クラウド事業者の基盤の問題ではなく、利用者の設定のミスが原因です。

9.2. IAM と最小権限

クラウドでは、誰が（どのプログラムが）どのリソースに対してどの操作を行えるかを、IAM（Identity and Access Management）で管理します。IAM の設定は、クラウドのセキュリティの中心です。

  • 管理者アカウントを日常的に使わないでください。クラウドのアカウントを作成したときの最上位のアカウント（AWS のルートユーザーなど）には多要素認証を設定し、日常の作業には使いません。

  • 長期間有効なアクセスキーを避けてください。プログラムには、仮想マシンやコンテナに割り当てるロールなど、自動的に更新される一時的な認証情報を使わせます。アクセスキーをソースコードや設定ファイルに書くことは、漏えいの大きな原因です。

  • 権限を最小限にしてください。「とりあえずすべての権限を与える」設定は、開発中の手間を省くために行われがちですが、その認証情報が漏えいしたときの被害が最大になります。

IAM のポリシーは JSON などで記述します。次のサンプルは、AWS の IAM ポリシーと同じ形式の JSON から、ワイルドカード（*）による過剰な権限を検出します。実際のクラウドには接続しません。

iam_policy_check.py
 1"""クラウドの IAM ポリシーから過剰な権限を検出するサンプル.
 2
 3AWS の IAM ポリシーと同じ形式の JSON を読み込み、ワイルドカード（*）による
 4過剰な権限など、最小権限の原則に反する記述を指摘します。
 5実際のクラウドには接続しません。
 6
 7実行方法:
 8    python iam_policy_check.py
 9
10必要なライブラリ:
11    なし（標準ライブラリのみ）
12"""
13
14import json
15from typing import Any
16
17POLICY_JSON = """
18{
19  "Version": "2012-10-17",
20  "Statement": [
21    {
22      "Sid": "ReadReports",
23      "Effect": "Allow",
24      "Action": ["s3:GetObject"],
25      "Resource": "arn:aws:s3:::example-reports/*"
26    },
27    {
28      "Sid": "DeveloperShortcut",
29      "Effect": "Allow",
30      "Action": "*",
31      "Resource": "*"
32    },
33    {
34      "Sid": "ManageQueues",
35      "Effect": "Allow",
36      "Action": "sqs:*",
37      "Resource": "*"
38    },
39    {
40      "Sid": "EverythingExceptIam",
41      "Effect": "Allow",
42      "NotAction": "iam:*",
43      "Resource": "*"
44    }
45  ]
46}
47"""
48
49
50def as_list(value: Any) -> list[str]:
51    """文字列または文字列のリストを、リストにそろえる."""
52    if isinstance(value, str):
53        return [value]
54    return [str(item) for item in value]
55
56
57def check_statement(statement: dict[str, Any]) -> list[str]:
58    """1 つのステートメントを検査し、指摘事項の一覧を返す."""
59    if statement.get("Effect") != "Allow":
60        return []
61    findings: list[str] = []
62    actions = as_list(statement.get("Action", []))
63    resources = as_list(statement.get("Resource", []))
64
65    if "*" in actions:
66        findings.append("すべての操作（Action: *）を許可しています")
67    for action in actions:
68        if action != "*" and action.endswith(":*"):
69            findings.append(f"サービスの全操作（{action}）を許可しています")
70    if "NotAction" in statement:
71        findings.append("NotAction と Allow の組み合わせは、"
72                        "列挙した操作以外のすべてを許可します")
73    if "*" in resources:
74        findings.append("すべてのリソース（Resource: *）が対象です")
75    return findings
76
77
78def main() -> None:
79    policy = json.loads(POLICY_JSON)
80    for statement in policy["Statement"]:
81        sid = statement.get("Sid", "（Sid なし）")
82        findings = check_statement(statement)
83        if not findings:
84            print(f"[OK]   {sid}")
85            continue
86        print(f"[警告] {sid}")
87        for finding in findings:
88            print(f"         - {finding}")
89
90
91if __name__ == "__main__":
92    main()

実行結果
[OK]   ReadReports
[警告] DeveloperShortcut
         - すべての操作（Action: *）を許可しています
         - すべてのリソース（Resource: *）が対象です
[警告] ManageQueues
         - サービスの全操作（sqs:*）を許可しています
         - すべてのリソース（Resource: *）が対象です
[警告] EverythingExceptIam
         - NotAction と Allow の組み合わせは、列挙した操作以外のすべてを許可します
         - すべてのリソース（Resource: *）が対象です

最初のステートメントは、特定のバケットのオブジェクトの読み取りだけを許可しており、最小権限の原則に沿っています。他の 3 つは、いずれも必要以上の権限を与えています。特に 4 つ目の NotAction は、「IAM 以外のすべての操作」を許可するもので、一見すると制限しているように見えるため見落とされがちです。

実際のクラウドでは、事業者が提供するポリシーの分析機能を使うと、より正確に検査できます。また、実際に使われた操作の記録から、不要な権限を洗い出す機能もあります。

9.3. 設定のミス

クラウドでよく見られる設定のミスを次の表に示します。

クラウドでよく見られる設定のミス

設定のミス

起こり得る被害

対策

ストレージ（オブジェクトストレージなど）の公開設定

保存したファイルを誰でもダウンロードできます。

アカウント全体で公開を禁止する設定を有効にし、公開が必要なものは CDN などを経由させます。

SSH やデータベースのポートをインターネット全体に公開

暗号化の無効化

記録媒体やバックアップから、データが漏えいします。

公開されている初期パスワードで管理画面にログインされます。

設定のミスは、手作業でリソースを作成・変更したときに起きやすくなります。後で説明する IaC で設定をコードとして管理し、自動的に検査すると効果的です。クラウドの設定を継続的に検査して、推奨される設定との違いを指摘するサービス（CSPM: Cloud Security Posture Management）も利用できます。

9.4. メタデータサービスと SSRF

Web アプリケーションのセキュリティで説明したように、クラウドの仮想マシンの中から 169.254.169.254 にアクセスすると、その仮想マシンに割り当てられたロールの一時的な認証情報を取得できます。アプリケーションに SSRF の脆弱性があると、攻撃者はこの認証情報を盗み出し、クラウドのリソースを操作できるようになります。2019 年に米国の金融機関で起きた大規模な情報漏えいは、この手口によるものでした。

クラウド側の対策として、次の点が重要です。

  • メタデータサービスの新しい方式を使ってください。AWS の IMDSv2 では、認証情報を取得する前に、PUT リクエストでセッション用のトークンを取得する必要があります。単純な SSRF では PUT リクエストを送らせることが難しいため、攻撃を大きく困難にできます。

  • 仮想マシンのロールの権限を最小限にしてください。認証情報が盗まれても、できることが限られるようにします。

9.5. シークレットの管理

クラウドで動くアプリケーションのシークレット（データベースのパスワード、外部の API キーなど）は、クラウドのシークレット管理サービスに保存し、アプリケーションの実行時に、ロールの権限で取得させます。こうすると、シークレットがソースコードやコンテナイメージに含まれず、誰がいつシークレットを取得したかも記録されます。シークレットを自動的に更新する機能を使えば、漏えいした場合の被害の期間も短くできます。

9.6. コンテナのセキュリティ

コンテナは、アプリケーションと、その実行に必要なライブラリなどをまとめて、どの環境でも同じように動かせるようにする技術です。コンテナを安全に使うためには、次の点に注意します。

コンテナの主な注意点

項目

内容

小さなベースイメージ

必要最小限のパッケージだけを含むイメージ（slim 版や distroless など）を使います。含まれるパッケージが少ないほど、脆弱性も少なくなります。

イメージの脆弱性の検査

イメージに含まれる OS のパッケージやライブラリを、脆弱性スキャナーで検査します。イメージは一度作れば終わりではなく、ベースイメージの更新に合わせて定期的に作り直します。

イメージの固定

python:3.14 のようなタグは、後から別の内容を指すように更新されます。再現性が必要な場合は、イメージのダイジェスト（@sha256:...）で指定します。

root 以外のユーザーでの実行

コンテナ内のプロセスを、root ではない一般のユーザーで実行します。コンテナから脱出する脆弱性があった場合の被害を抑えられます。

シークレットの扱い

イメージの各層は、後の層でファイルを削除しても残ります。シークレットは、実行時に環境変数やシークレット管理サービスから渡します。

過剰な権限の回避

特権モード（--privileged）での実行や、Docker のソケットのマウントは、ホストを乗っ取られるのと同等の権限を与えるため避けます。

Kubernetes のようなコンテナの管理基盤を使う場合は、その基盤自体の設定（API の認証と認可、コンテナ間の通信の制限など）も重要です。管理基盤の設定項目は多岐にわたるため、マネージドサービスを利用し、公開されているセキュリティの推奨設定に従うことをお勧めします。

9.7. Infrastructure as Code

サーバーやネットワーク、権限の設定などのインフラストラクチャーを、コードとして記述して管理する手法を IaC（Infrastructure as Code）と呼びます。Terraform や、各クラウド事業者が提供するツールが使われます。

IaC には、セキュリティの面でも次の利点があります。

  • 設定の変更がコードのレビューを通るため、危険な設定に気付きやすくなります。

  • 静的解析ツールで、公開設定のストレージや、過剰な権限などの設定のミスを、適用する前に自動的に検出できます。

  • 変更の履歴が残るため、いつ誰が設定を変えたかを追跡できます。

  • 侵害や障害の後に、既知の正しい状態の環境を再構築できます。

一方で、IaC のコードや、ツールが管理する状態ファイルには、リソースの構成やシークレットが含まれることがあります。状態ファイルは、アクセスを制限した場所に暗号化して保存します。また、IaC で管理しているリソースを画面から手作業で変更すると、コードと実際の環境が食い違うため、変更は必ずコードを通して行う運用にします。
