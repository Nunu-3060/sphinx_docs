7. HTTP と Web

この章では、Web を支えるプロトコルである HTTP（Hypertext Transfer Protocol）を説明します。HTTP は、ブラウザーが Web ページを取得するためだけでなく、スマートフォンのアプリとサーバーの通信や、サーバー同士の API の呼び出しにも広く使われており、現代のアプリケーション層で最も重要なプロトコルの 1 つです。URL とメッセージの形式から始めて、メソッド、ステータスコード、ヘッダー、コネクションの使い方を見たあと、HTTP/2 と HTTP/3 の改良点、キャッシュ、Cookie、REST、プロキシと CDN、WebSocket を取り上げます。

7.1. URL

Web 上の資源（リソース）は、URL（Uniform Resource Locator）で指し示します。URL は、次のような部分からなります。この例では、スキームが https、ホストが shop.example.com、ポートが 8443、パスが /items/search、クエリーが q=book&page=2、フラグメントが reviews です。

1https://shop.example.com:8443/items/search?q=book&page=2#reviews

7.2. HTTP/1.1 のメッセージ

HTTP は、クライアントがリクエストを送り、サーバーがそれに対するレスポンスを返す、という単純なリクエスト・レスポンス型のプロトコルです。HTTP/1.1 までのメッセージは人間が読めるテキストで、次の形をしています。

1GET /items/search?q=book HTTP/1.1
2Host: shop.example.com
3User-Agent: Mozilla/5.0 ...
4Accept: text/html
5Accept-Language: ja

リクエストの 1 行目はリクエスト行で、メソッド、リクエストの対象（パスとクエリー）、HTTP のバージョンを空白で区切って並べます。2 行目からがヘッダーで、名前: 値 の形の行が並びます。各行は CR LF（\r\n）で終わり、空行でヘッダーが終わります。その後にボディ（本体）が続くことがあります。GET のリクエストには、通常ボディはありません。

Host ヘッダーは HTTP/1.1 で必須です。1 台のサーバー（1 つの IP アドレス）で複数のドメインの Web サイトを運用する場合（バーチャルホスト）、サーバーは Host ヘッダーを見て、どのサイトへのリクエストかを判断します。

1HTTP/1.1 200 OK
2Content-Type: text/html; charset=utf-8
3Content-Length: 1256
4Cache-Control: max-age=60
5
6<!DOCTYPE html>
7<html> ...

レスポンスの 1 行目はステータス行で、HTTP のバージョン、ステータスコード、理由を表す語句からなります。続くヘッダーと空行、ボディの形はリクエストと同じです。

7.2.1. ボディの終わりの判断

TCP はバイトストリームであり、メッセージの区切りを持ちません（「トランスポート層」を参照）。そのため HTTP は、ボディがどこで終わるかを自分で示す必要があります。HTTP/1.1 では、主に次の方法を使います。

  • Content-Length ヘッダー：ボディのバイト数を事前に示します。受信側は、ヘッダーの後にそのバイト数だけ読めばボディの終わりが分かります。

  • チャンク形式（Transfer-Encoding: chunked）：ボディを「長さ + データ」の塊（チャンク）の並びとして送り、長さ 0 のチャンクで終わりを示します。動的に生成するページのように、送り始める時点で全体の長さが分からない場合に使います。

このように、ストリームの中でメッセージの区切りを決める工夫をフレーミングと呼びます。フレーミングは HTTP に限らず、TCP の上に独自のプロトコルを作るときに必ず必要になります（「ソケットプログラミング」で説明します）。

7.6. キープアライブ

初期の HTTP（HTTP/1.0）では、原則として 1 つのリクエストとレスポンスのたびに TCP のコネクションを確立し、レスポンスを返したら閉じていました。しかし Web ページは、HTML のほかに多数の画像、CSS、JavaScript のファイルからなります。ファイルごとに 3 ウェイハンドシェイクの 1 往復がかかり、さらに TCP のスロースタートによって、コネクションの最初のうちは速く送れません。HTTPS では TLS のハンドシェイクの往復も加わります。

そこで HTTP/1.1 では、1 つのコネクションで複数のリクエストとレスポンスを順にやり取りするキープアライブ（持続的接続、persistent connection）が既定になりました。どちらかが Connection: close ヘッダーを送るか、一定時間やり取りがないと、コネクションは閉じられます。

7.6.1. サンプルで確かめる

サンプルコード http_raw_client.py は、Python の http.server モジュールで小さな Web サーバーをスレッドで起動し、ソケットを使って生の HTTP/1.1 のリクエストを送るものです。1 本のコネクションで 2 回リクエストを送り、2 回目には Connection: close を付けます。localhost で完結するので、インターネット接続は不要です。

リスト 7.1 http_raw_client.py
  1"""ソケットで生の HTTP/1.1 リクエストを送り、レスポンスを読むサンプル。
  2
  3``http.server`` を使った小さな Web サーバーをスレッドで localhost に
  4起動し、そこへ TCP のソケットで HTTP/1.1 のリクエストを文字列として
  5送ります。返ってきたレスポンスのステータス行、ヘッダー、ボディを

 25class Handler(BaseHTTPRequestHandler):
 26    """/hello にだけ応答し、それ以外は 404 を返すハンドラー。"""
 27
 28    protocol_version = "HTTP/1.1"  # キープアライブを有効にする
 29    server_version = "SampleServer/1.0"
 30
 31    def version_string(self) -> str:
 32        # Server ヘッダーに Python のバージョンを含めない
 33        return self.server_version
 34
 35    def do_GET(self) -> None:
 36        if self.path == "/hello":
 37            status, body = 200, "こんにちは、HTTP!\n"
 38        else:
 39            status, body = 404, "見つかりません\n"
 40        data = body.encode("utf-8")
 41        self.send_response(status)
 42        self.send_header("Content-Type", "text/plain; charset=utf-8")
 43        # ボディの長さを知らせないと、クライアントはボディの終わりが
 44        # 分からない (キープアライブでは特に重要)
 45        self.send_header("Content-Length", str(len(data)))
 46        self.end_headers()
 47        self.wfile.write(data)
 48
 49    def log_message(self, format: str, *args: object) -> None:
 50        pass  # サーバーのアクセスログは表示しない
 51
 52
 53def read_response(reader: BinaryIO) -> tuple[str, list[str], bytes]:
 54    """レスポンスを 1 つ読み、(ステータス行, ヘッダー行, ボディ) を返す。"""
 55    status_line = reader.readline().decode("ascii").rstrip("\r\n")
 56    if not status_line:
 57        raise ConnectionError("サーバーがコネクションを閉じました")
 58    headers: list[str] = []
 59    length = 0
 60    while True:
 61        line = reader.readline().decode("latin-1").rstrip("\r\n")
 62        if line == "":  # 空行でヘッダーが終わる
 63            break
 64        headers.append(line)
 65        name, _, value = line.partition(":")
 66        if name.strip().lower() == "content-length":
 67            length = int(value.strip())
 68    # ボディは Content-Length のバイト数だけ読む
 69    body = reader.read(length)
 70    return status_line, headers, body
 71
 72
 73def send_and_show(
 74    sock: socket.socket, reader: BinaryIO, path: str, close: bool
 75) -> None:
 76    """GET リクエストを送り、レスポンスを表示する。"""
 77    host, port = sock.getpeername()[:2]
 78    lines = [
 79        f"GET {path} HTTP/1.1",
 80        f"Host: {host}:{port}",
 81        "User-Agent: http_raw_client.py",
 82    ]
 83    if close:
 84        lines.append("Connection: close")
 85    # 各行は CRLF で終わり、空行 (CRLF だけの行) でヘッダーが終わる
 86    request = "\r\n".join(lines) + "\r\n\r\n"
 87    local_port = sock.getsockname()[1]
 88    print(f"--- リクエスト (クライアント側ポート {local_port}) ---")
 89    print(request.replace("\r\n", "\\r\\n\n"), end="")
 90    sock.sendall(request.encode("ascii"))
 91
 92    status_line, headers, body = read_response(reader)
 93    print("--- レスポンス ---")
 94    print(f"ステータス行: {status_line}")
 95    for h in headers:
 96        print(f"ヘッダー    : {h}")
 97    print(f"ボディ      : {body.decode('utf-8')!r}")
 98    print()

102    # ポート 0 を指定して、空いているポートを OS に選ばせる

104    thread = threading.Thread(target=server.serve_forever, daemon=True)
105    thread.start()

107    print(f"サーバーを {host}:{port} で起動しました\n")
108
109    try:

111            with sock.makefile("rb") as reader:
112                # 1 回目: キープアライブ (HTTP/1.1 の既定) で送る
113                send_and_show(sock, reader, "/hello", close=False)
114                # 2 回目: 同じコネクションで送り、閉じるよう依頼する
115                send_and_show(sock, reader, "/missing", close=True)
116                # サーバーが閉じたので、これ以上読むと EOF (空) になる
117                rest = reader.read()
118                print(f"2 回目の後に読んだデータ: {rest!r} "
119                      "(サーバーがコネクションを閉じました)")
120    finally:
121        server.shutdown()
122        server.server_close()

7.6.2. HTTP/1.1 の限界

キープアライブを使っても、HTTP/1.1 では 1 つのコネクションでは前のレスポンスを受け取り終わるまで次のレスポンスを受け取れません。リクエストを続けて送るパイプラインという仕組みも規定されましたが、レスポンスはリクエストの順に返す必要があるため、前のレスポンスの生成が遅いと後ろがすべて待たされます。これを HTTP のヘッドオブラインブロッキングと呼びます。実装上の問題も多く、パイプラインはブラウザーではほとんど使われませんでした。

そのためブラウザーは、1 つのサーバーに対して複数（一般に 6 本程度）のコネクションを並行して張り、同時に複数のファイルを取得します。しかし、コネクションごとにハンドシェイクと輻輳制御が独立に行われるので効率が悪く、サーバーの負担も増えます。また、テキストのヘッダーは、同じ内容（User-Agent や Cookie など）をリクエストのたびに繰り返し送るので無駄が多いという問題もありました。

7.7. HTTP/2

HTTP/2 は、これらの問題を解決するために設計され、2015 年に RFC 7540 として標準化されました（現在の仕様は RFC 9113）。HTTP/2 はメソッド、ステータスコード、ヘッダーといった意味（セマンティクス）は HTTP/1.1 と同じまま、それをネットワーク上でどう運ぶかを変えています。そのため、アプリケーションから見た HTTP の使い方は変わりません。

  • バイナリのフレーム：メッセージを、テキストではなく、長さと種類を持つバイナリのフレームに分けて送ります。区切りが明確なので、解析が速く確実です。

  • ストリームによる多重化：1 本の TCP コネクションの中に、ストリームと呼ばれる論理的な通信路を多数作ります。リクエストとレスポンスの 1 組が 1 つのストリームに対応し、各ストリームのフレームは混ぜ合わせて送れます。前のレスポンスを待たずに、複数のレスポンスを並行して受け取れます。

  • HPACK によるヘッダー圧縮：送ったヘッダーを両端で表として覚えておき、同じヘッダーは表の番号だけで送ります。新しい値もハフマン符号で短くします。繰り返しの多いヘッダーの量が大幅に減ります。

  • 優先度とフロー制御：ストリームごとに優先度やフロー制御を設定できます。

HTTP/2 では、1 つのサーバーに対して 1 本のコネクションを使うのが基本です。また、ブラウザーは実質的に TLS の上でしか HTTP/2 を使いません。TLS のハンドシェイクの中で、ALPN（Application-Layer Protocol Negotiation）という拡張を使って HTTP/2 を使うかどうかを決めます。なお、サーバーがリクエストを待たずにリソースを送り付けるサーバープッシュという機能も規定されましたが、効果が限られていたため、現在は主要なブラウザーで使われなくなっています。

HTTP/2 にも弱点が残りました。HTTP のレベルでは多重化しても、その下の TCP は 1 本のバイトストリームなので、パケットが 1 つ失われると、そのパケットと関係のないストリームまで再送を待たされます。これは TCP のレベルのヘッドオブラインブロッキングです（「トランスポート層」を参照）。パケットの損失が多いモバイル回線などでは、HTTP/1.1 の複数コネクションより遅くなることさえあります。

7.8. HTTP/3

HTTP/3 は、TCP の代わりに QUIC の上で HTTP を運ぶもので、2022 年に RFC 9114 として標準化されました。QUIC は UDP の上に作られたトランスポートプロトコルで、ストリームの多重化、再送、輻輳制御、TLS 1.3 による暗号化を 1 つにまとめています。QUIC の仕組みは「トランスポート層」で説明したので、ここでは HTTP から見た利点をまとめます。

  • ストリームごとに損失から回復するので、あるストリームのパケットが失われても他のストリームは待たされず、TCP のヘッドオブラインブロッキングが解消されます。

  • トランスポートの接続確立と TLS のハンドシェイクを一緒に行うので、初回は 1 往復で暗号化した通信を始められます（TCP と TLS 1.3 では 2 往復）。以前に接続したサーバーには、0 往復でデータを送り始めることもできます。

  • コネクションを IP アドレスとポート番号の組ではなくコネクション ID で識別するので、スマートフォンが無線 LAN からモバイル回線に切り替わって IP アドレスが変わっても、コネクションを維持できます。

ヘッダーの圧縮には、HPACK を QUIC 向けに改めた QPACK を使います。ブラウザーは、最初は TCP で HTTP/1.1 や HTTP/2 を使って接続し、サーバーが Alt-Svc ヘッダーなどで HTTP/3 に対応していることを知らせると、次から HTTP/3 を試すのが一般的です。UDP がファイアウォールで遮断されている環境もあるため、HTTP/3 が使えない場合は TCP に戻れるようになっています。

7.9. キャッシュ

同じリソースを何度もサーバーから取得するのは無駄です。HTTP には、レスポンスを保存しておき再利用するキャッシュの仕組みが組み込まれています。キャッシュは、ブラウザーの中（プライベートキャッシュ）と、プロキシや CDN の中（共有キャッシュ）にあります。

キャッシュの方法は、主にサーバーが Cache-Control ヘッダーで指示します。

7.9.1. 条件付きリクエスト

有効期間が切れたレスポンスも、内容が変わっていなければまだ使えます。そこで、キャッシュはサーバーに「手元のものはまだ有効か」を確認します。これを再検証と呼び、条件付きリクエストで行います。

1GET /logo.png HTTP/1.1
2Host: www.example.com
3If-None-Match: "a1b2c3"

"a1b2c3" は、前回のレスポンスの ETag ヘッダーで受け取った、リソースの版を表す識別子です。リソースが変わっていなければ、サーバーはボディなしの 304 Not Modified を返し、キャッシュは手元のレスポンスを使い続けます。変わっていれば、通常どおり 200 OK と新しい内容を返します。最終更新日時を使う Last-Modified と If-Modified-Since の組み合わせもあります。再検証でも 1 往復はかかりますが、大きなボディを送り直さずに済みます。

実務では、ファイル名に内容のハッシュ値を含めて（例えば app.3f9a2c.js）長い max-age を指定し、内容を変えたらファイル名ごと変える方法がよく使われます。HTML のように URL を変えられないものは、短い有効期間か no-cache にします。

7.10. Cookie とセッション

HTTP はステートレスなプロトコルです。サーバーは、各リクエストを独立に処理し、以前に同じクライアントから来たリクエストを覚えていません。しかし、ログインの状態やショッピングカートの中身のように、一連のリクエストにまたがって状態を保ちたい場面は多くあります。そのために使われるのが Cookie です。

サーバーはレスポンスの Set-Cookie ヘッダーで、名前と値の組をブラウザーに保存させます。ブラウザーは、以降の同じサイトへのリクエストに Cookie ヘッダーでその値を付けて送ります。

1HTTP/1.1 200 OK
2Set-Cookie: session_id=8f2a9c...; Path=/; Secure; HttpOnly; SameSite=Lax; Max-Age=3600
3
4GET /cart HTTP/1.1
5Host: shop.example.com
6Cookie: session_id=8f2a9c...

典型的なセッション管理では、ログインに成功したときにサーバーが推測できない乱数のセッション ID を発行して Cookie に入れ、サーバー側でセッション ID と利用者の情報を対応付けて保存します。セッション ID を盗まれると、その利用者になりすまされてしまうため、Cookie には次のような属性を付けて守ります。

  • Secure：HTTPS の通信でだけ送ります。平文の通信での盗聴を防ぎます。

  • HttpOnly：JavaScript から読めなくします。スクリプトを埋め込む攻撃（XSS：Cross-Site Scripting）で盗まれるのを防ぎます。

  • SameSite：他のサイトから発生したリクエストに Cookie を付けるかどうかを制御します。他のサイトから利用者の意図しない操作を送らせる攻撃（CSRF：Cross-Site Request Forgery）を防ぐのに役立ちます。

サーバーを複数台に増やすと、セッションの情報をどのサーバーが持つかが問題になります。特定の利用者のリクエストを常に同じサーバーに送る方法（スティッキーセッション）もありますが、そのサーバーが止まるとセッションが失われます。多くの場合、セッションの情報はデータベースや分散キャッシュに保存し、どのサーバーでもリクエストを処理できるようにします。サーバー自身が状態を持たないようにすることは、スケールアウトの基本です（「分散システムとは」を参照）。

7.11. REST

REST（Representational State Transfer）は、フィールディング（Roy Fielding）が 2000 年の博士論文で示した、Web のようなシステムの設計の考え方（アーキテクチャスタイル）です。現在では、HTTP の仕組みを素直に使って設計した Web API を、REST API（RESTful API）と呼ぶのが一般的です。

  • 操作の対象をリソースとして URL で表します（/users/42、/users/42/orders など）。

  • 操作の種類は、URL ではなく HTTP のメソッドで表します。GET /users/42 で取得、PUT /users/42 で更新、DELETE /users/42 で削除します。

  • 処理の結果はステータスコードで表します。作成に成功したら 201、存在しなければ 404 を返します。

  • 各リクエストは、処理に必要な情報をすべて含み、サーバーはリクエストの間で状態を持ちません（ステートレス）。

  • データの形式には、JSON がよく使われます。

HTTP のメソッドの安全性や冪等性、ステータスコード、キャッシュの仕組みに沿って API を設計すると、プロキシ、キャッシュ、クライアントのライブラリなど、HTTP のために作られた既存の仕組みをそのまま活用できます。REST 以外の API の方式（gRPC など）は「分散システムの通信」で説明します。

7.12. プロキシとリバースプロキシ

HTTP のクライアントとサーバーの間には、通信を中継するサーバーが入ることがあります。どちらの側に置かれ、誰のために働くかによって、2 種類に分けられます。

  • フォワードプロキシ（単にプロキシとも呼びます）：クライアントの側に置かれ、クライアントの代わりに外部のサーバーにアクセスします。企業のネットワークで、外部へのアクセスの制御、記録、キャッシュに使われます。HTTPS の通信では、クライアントは CONNECT メソッドでプロキシに接続先を伝え、プロキシは暗号化された通信を中身を見ずにそのまま中継します。

  • リバースプロキシ：サーバーの側に置かれ、外部からのリクエストを受けて、内部のサーバー（オリジンサーバー、バックエンド）に振り分けます。クライアントからは、リバースプロキシが Web サーバーそのものに見えます。

リバースプロキシは、現代の Web サービスの構成で中心的な役割を持ちます。

  • 負荷分散：複数のバックエンドにリクエストを振り分けます（L7 のロードバランサー。「信頼性の高いシステムの設計」を参照）。

  • TLS の終端：TLS の暗号化と復号をリバースプロキシで行い、バックエンドの負担を減らします。証明書の管理も 1 か所にまとまります。

  • キャッシュと圧縮：静的なファイルのレスポンスをキャッシュし、圧縮して返します。

  • ルーティング：パスやホスト名に応じて、異なるバックエンドに振り分けます（/api は API のサーバーへ、など）。

  • 保護：リクエストの数の制限や、攻撃的なリクエストの遮断を行います。

リバースプロキシを経由すると、バックエンドから見た接続元はリバースプロキシの IP アドレスになります。そこで、リバースプロキシは元のクライアントの IP アドレスを X-Forwarded-For や Forwarded などのヘッダーに入れて渡します。ただし、これらのヘッダーはクライアントが偽装して送ることもできるので、信頼できるプロキシが付けたものだけを使うように注意する必要があります。

7.13. CDN

CDN（Content Delivery Network）は、世界中の多数の拠点にキャッシュのサーバー（エッジサーバー）を置き、利用者に近い拠点からコンテンツを配信する仕組みです。リバースプロキシとキャッシュを、世界規模に分散させたものと考えることができます。

物理的な距離による遅延は、光の速さで決まるため減らせません。例えば東京と米国東海岸の間の RTT は、おおよそ 150 ms 以上になります。1 回の Web ページの表示に何往復も必要なことを考えると、近い拠点から返すことの効果は大きくなります。利用者を近い拠点に導く方法には、DNS で拠点ごとに異なる IP アドレスを返す方法（「名前解決と DNS」で見た CNAME の先がこれにあたります）と、エニーキャストで同じ IP アドレスを複数の拠点から広告する方法があります。

CDN は、遅延を減らすだけでなく、オリジンサーバーの負荷を大幅に減らし、大量のアクセスや DDoS 攻撃を多数の拠点で受け止める役割も持ちます。一方で、CDN のキャッシュに古い内容が残る問題があるため、キャッシュの有効期間の設計や、キャッシュを明示的に消す操作（パージ）が重要になります。

7.14. WebSocket

HTTP は、クライアントがリクエストを送らない限りサーバーからデータを送れません。チャットや株価の表示のように、サーバーから任意のタイミングでデータを送りたい場合、以前はクライアントが定期的に問い合わせる（ポーリング）などの工夫が必要でした。

WebSocket は、1 本の TCP のコネクションの上で、クライアントとサーバーが任意のタイミングで双方向にメッセージを送り合えるようにするプロトコルで、2011 年に RFC 6455 として標準化されました。WebSocket の通信は、HTTP のリクエストから始まります。

1GET /chat HTTP/1.1
2Host: chat.example.com
3Upgrade: websocket
4Connection: Upgrade
5Sec-WebSocket-Key: dGhlIHNhbXBsZSBub25jZQ==
6Sec-WebSocket-Version: 13

サーバーが 101 Switching Protocols を返すと、それ以降そのコネクションは HTTP ではなく WebSocket のフレームをやり取りするのに使われます。最初に HTTP を使うので、既存の Web サーバーやプロキシと同じポート番号（80、443）で運用できます。Sec-WebSocket-Key は、サーバーが WebSocket を理解していることを確かめるための値で、サーバーはこれから計算した値を Sec-WebSocket-Accept ヘッダーで返します。

WebSocket のコネクションは長時間開いたままになるため、サーバーは多数のコネクションを同時に保持する必要があります。また、途中のプロキシやロードバランサーが、やり取りのないコネクションをタイムアウトで切ってしまうことがあるので、定期的に小さなメッセージ（ping）を送って維持するのが一般的です。サーバーからクライアントへの一方向の通知だけで十分な場合は、通常の HTTP のレスポンスを少しずつ送り続ける Server-Sent Events という、より簡単な方法もあります。

7.15. まとめ

  • HTTP はリクエスト・レスポンス型のプロトコルで、メソッド、ステータスコード、ヘッダー、ボディでやり取りします。HTTP/1.1 のメッセージはテキストで、Content-Length などでボディの終わりを示します。

  • メソッドの安全性と冪等性、ステータスコードの分類（4xx と 5xx）は、キャッシュやリトライの判断の基礎になります。

  • HTTP/1.1 のキープアライブはコネクションを再利用しますが、レスポンスの順番待ちが残ります。HTTP/2 は 1 本の TCP コネクションでストリームを多重化し、HTTP/3 は QUIC の上で TCP のヘッドオブラインブロッキングも解消します。

  • Cache-Control と条件付きリクエストでキャッシュを制御し、Cookie でステートレスな HTTP の上にセッションを実現します。

  • リバースプロキシと CDN は、負荷分散、TLS の終端、キャッシュ、遅延の削減などを担い、現代の Web サービスの構成の中心にあります。
