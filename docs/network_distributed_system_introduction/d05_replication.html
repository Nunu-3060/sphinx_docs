5. レプリケーション

この章では、同じデータの複製（レプリカ）を複数のノードに持たせるレプリケーションを説明します。レプリケーションの目的から始め、最も広く使われているシングルリーダー方式と、そのフェイルオーバーやレプリケーション遅延の問題を取り上げます。続いて、マルチリーダー方式とリーダーレス方式、リーダーレス方式の要となるクォーラムの条件、書き込みの競合の解決、レプリカの差分を埋めるアンチエントロピーを説明します。

5.1. レプリケーションの目的

レプリケーションには、主に次の 3 つの目的があります。

  • 可用性：一部のノードが停止しても、他のレプリカを使ってサービスを続けられます。

  • 読み込みの性能：読み込みのリクエストを複数のレプリカに分散して、処理できる量を増やせます。

  • 遅延の短縮：ユーザーの近くの地域にレプリカを置けば、ネットワークの往復時間を短くできます。

データが変更されないのであれば、レプリケーションは単にコピーを配るだけで済みます。難しさは、すべて「変更をどうやって各レプリカに伝えるか」にあります。ネットワークは遅延し、メッセージは失われ、ノードは停止します。その中で、各レプリカの内容がずれたときにどう振る舞うかが、レプリケーションの方式を決める中心的な問題です。

なお、データが 1 台のノードに収まらないほど大きい場合は、データを分割して複数のノードに分けるパーティショニングを使います（「パーティショニング」を参照してください）。実際のシステムでは、パーティショニングとレプリケーションを組み合わせ、各パーティションを複数のノードにレプリケーションするのが一般的です。

5.2. シングルリーダー方式

最も広く使われているのが、シングルリーダー方式（リーダー・フォロワー方式、プライマリ・セカンダリ方式とも呼びます）です。PostgreSQL や MySQL の標準的なレプリケーションはこの方式です。

  • レプリカの 1 つをリーダーとし、書き込みはすべてリーダーが受け付けます。

  • リーダーは、データの変更を自分の記憶装置に書き込むとともに、変更の記録（レプリケーションログ）をフォロワーに送ります。

  • 各フォロワーは、レプリケーションログを受け取った順に適用して、リーダーと同じ状態になります。

  • 読み込みは、リーダーとフォロワーのどちらでも受け付けられます。

すべての書き込みが 1 つのノードを通るため、書き込みの順序が自然に 1 つに決まり、書き込みの競合が起きません。これがシングルリーダー方式の最大の利点です。一方で、書き込みの性能はリーダー 1 台の能力に制限され、リーダーが停止すると書き込みができなくなります。

レプリケーションログの形式には、SQL 文をそのまま送る方式、記憶装置の先行書き込みログ（WAL：Write-Ahead Log）を送る方式、行単位の変更を論理的な形式で送る方式（論理レプリケーション）などがあります。SQL 文をそのまま送る方式は、現在時刻や乱数を使う文がレプリカごとに異なる結果になるといった問題があるため、行単位の方式が主流です。

5.2.1. 同期レプリケーションと非同期レプリケーション

リーダーが書き込みの完了をクライアントに返すタイミングには、2 つの選択肢があります。

5.2.2. 新しいフォロワーの追加

フォロワーを追加するときは、リーダーのデータのスナップショットを取ってフォロワーにコピーし、スナップショットを取った時点以降のレプリケーションログを適用して追いつかせます。スナップショットとログの位置を正確に対応付けることが重要です。

5.3. フェイルオーバーとスプリットブレイン

リーダーが停止したとき、フォロワーの 1 つを新しいリーダーに昇格させることをフェイルオーバーと呼びます。自動的なフェイルオーバーは、おおむね次の手順で行われます。

  1. リーダーの停止を検出します。一定時間ハートビートの応答がなければ、停止したとみなすのが一般的です。

  2. 新しいリーダーを選びます。最も新しいデータを持つフォロワーを選ぶのが普通です。

  3. クライアントとほかのフォロワーが、新しいリーダーに書き込みを送るように設定を切り替えます。

フェイルオーバーには、次のような難しい問題があります。

  • 書き込みの消失：非同期レプリケーションでは、古いリーダーが完了を返した書き込みのうち、フォロワーに届いていなかったものが失われます。古いリーダーが後で復帰しても、その書き込みは新しいリーダーの書き込みと衝突するため、多くの場合は破棄されます。

  • 停止の誤検出：タイムアウトが短すぎると、負荷が高くて応答が遅れただけのリーダーを停止したと誤って判断し、不要なフェイルオーバーを起こします。長すぎると、本当に停止したときに復旧が遅れます。ネットワーク越しには、停止と遅延を確実に区別できません（「分散システムとは」を参照してください）。

  • スプリットブレイン：古いリーダーが実は停止しておらず、ネットワーク分断などで連絡が取れなかっただけの場合、古いリーダーと新しいリーダーの両方が自分がリーダーだと思って書き込みを受け付けることがあります。この状態をスプリットブレインと呼び、データの不整合や破壊につながります。

スプリットブレインを防ぐには、リーダーの選出に過半数の合意を求めることと、古いリーダーからの書き込みを拒否する仕組みが欠かせません。代表的な手法は、リーダーの任期を表す番号（エポックや Raft の term など）を書き込みに添え、古い番号の書き込みをストレージ側で拒否するフェンシングです。これらは合意アルゴリズムと深く関わるため、「合意と分散トランザクション」で説明します。

5.4. レプリケーション遅延と起こる異常

非同期レプリケーションでは、フォロワーはリーダーより少し遅れた状態になります。この遅れをレプリケーション遅延と呼びます。通常は 1 秒未満ですが、負荷が高いときやネットワークに問題があるときは、数秒から数分に及ぶこともあります。読み込みをフォロワーに分散すると、この遅延によって、ユーザーから見て不自然な現象が起こります。

5.4.1. 自分の書き込みが読めない

ユーザーがプロフィールを更新した直後にページを再読み込みしたとき、読み込みがまだ更新の届いていないフォロワーに送られると、更新前のプロフィールが表示されます。ユーザーには、更新が失われたように見えます。

5.4.2. 読み込むたびに時間が巻き戻る

ユーザーが 2 回続けて読み込み、1 回目は遅延の小さいフォロワー、2 回目は遅延の大きいフォロワーに送られると、1 回目に見えていた新しいコメントが 2 回目には消えている、という現象が起こります。ユーザーから見ると、時間が巻き戻ったように見えます。対策としては、同じユーザーの読み込みを常に同じレプリカに送る方法があります（ただし、そのレプリカが停止したら切り替える必要があります）。

5.4.3. 因果関係の逆転

ある人の質問と別の人の回答が、異なる経路でレプリケーションされると、第三者からは回答が質問より先に見えることがあります。これは、データがパーティショニングされていて、パーティションごとに独立にレプリケーションされている場合に起こりやすい現象です。

これらの異常をどこまで防ぐかは、システムが提供する一貫性モデルによって決まります。ここで挙げた異常と、それを防ぐセッション保証や因果一貫性については、「一貫性モデル」で整理します。

5.5. マルチリーダー方式

シングルリーダー方式では、書き込みはすべて 1 台のリーダーを通ります。複数のデータセンターにまたがるシステムでは、遠くのデータセンターのユーザーの書き込みも、リーダーのあるデータセンターまで届ける必要があり、遅延が大きくなります。また、データセンターの間のネットワークが分断されると、リーダーのない側では書き込みができなくなります。

マルチリーダー方式では、複数のノード（典型的にはデータセンターごとに 1 つ）がリーダーとして書き込みを受け付け、互いに変更を非同期にレプリケーションし合います。次のような場面で使われます。

  • 複数のデータセンターでの運用：各データセンターのユーザーは、近くのリーダーに書き込めます。

  • オフラインで動くクライアント：スマートフォンのカレンダーアプリのように、各端末をそれぞれ 1 つのリーダーとみなし、ネットワークにつながったときに変更を同期する場合です。

  • 共同編集：複数のユーザーが同じ文書を同時に編集する場合です。

マルチリーダー方式の最大の問題は、書き込みの競合です。2 つのリーダーで同じデータが同時に別の値に変更されると、どちらも自分の書き込みを正しいものとして受け付けてしまいます。競合は書き込みの後で非同期に検出されるため、ユーザーに「その変更はできません」と伝えることもできません。競合の解決方法は後で説明します。

5.6. リーダーレス方式

リーダーレス方式では、リーダーを置かず、どのレプリカも書き込みを受け付けます。クライアント（またはクライアントの代わりに働くコーディネーターのノード）は、書き込みを複数のレプリカに並行して送り、読み込みも複数のレプリカに並行して送ります。Amazon が 2007 年に論文で発表した Dynamo がこの方式を採用したことで広く知られるようになり、Apache Cassandra や Riak などがこの流れをくんでいます。

リーダーレス方式では、レプリカが 1 台停止していても、フェイルオーバーを行わずに、残りのレプリカで読み書きを続けられます。停止していたレプリカは、復帰した時点では古いデータを持っています。そこで、読み込みのときに複数のレプリカから値を集め、最も新しいものを選ぶ必要があります。そのために、各値にはバージョン番号を付けて保存します。

5.7. クォーラム

リーダーレス方式で、最新の値を確実に読むための条件を考えます。各データを \(N\) 個のレプリカに保存し、書き込みは \(W\) 個のレプリカが受け付けた時点で成功とし、読み込みは \(R\) 個のレプリカから応答を得た時点で結果を返すとします。このとき、次の条件が成り立てば、読み込みの対象となるレプリカのうち少なくとも 1 つは、最新の書き込みを受け付けたレプリカになります。

\[R + W > N\]

これは、書き込んだ \(W\) 個のレプリカの集合と、読み込んだ \(R\) 個のレプリカの集合が、必ず重なることを意味します。もし重ならないとすると、2 つの集合は合わせて \(R + W\) 個の異なるレプリカを含むことになりますが、レプリカは \(N\) 個しかないので \(R + W \le N\) でなければなりません。これは条件に反します。このように、互いに必ず重なる集合をクォーラムと呼び、\(W\) と \(R\) を書き込みクォーラム、読み込みクォーラムと呼びます。

読み込んだ値の中から、バージョンの最も新しい値を選べば、最新の値が得られます。一般的な設定は \(N = 3, W = 2, R = 2\) や \(N = 5, W = 3, R = 3\) のように、\(N\) を奇数にして \(W = R = \lceil (N + 1) / 2 \rceil\) とするものです。

\(W\) と \(R\) の選び方によって、性能と耐障害性のバランスを調整できます。稼働中のレプリカが \(W\) 個以上あれば書き込みが、\(R\) 個以上あれば読み込みができるので、書き込みは \(N - W\) 個、読み込みは \(N - R\) 個までのレプリカの停止に耐えられます。

サンプルコード quorum_sim.py は、\(N\) 個のレプリカを持つリーダーレスなキー・バリューストアを模擬し、\((N, W, R)\) の組み合わせによって最新の値が読めるかどうかを調べるものです。最初は全レプリカがバージョン 1 の値を持っている状態から、バージョン 2 の値を書き込み、その後に読み込みます。最悪の場合を考えるため、書き込みは \(W\) 個のレプリカだけに届き、残りのレプリカには届かなかったものとしています。読み込みのときに古い値を返したレプリカには、最新の値を書き戻します（読み込み修復、後述）。

 92            ver, val = rep.get(key)
 93            mark = "" if rep.up else "(停止)"
 94            parts.append(f"{rep.name}=v{ver}:{val}{mark}")
 95        return "  ".join(parts)

 98def trace(n: int, w: int, r: int, seed: int, down: str) -> None:
 99    """1 回分の書き込みと読み込みの経過を表示する."""
100    cond = "R+W>N" if r + w > n else "R+W<=N"
101    print(f"--- N={n}, W={w}, R={r} ({cond}) ---")
102    cluster = Cluster(n, w, r, random.Random(seed))
103    for rep in cluster.replicas:  # 初期状態：全レプリカが v1 を持つ
104        rep.put("x", (1, "old"))
105    for rep in cluster.replicas:
106        rep.up = rep.name not in down
107    print(f"  初期状態     : {cluster.show('x')}")
108    written = cluster.write("x", (2, "new"))
109    print(f"  書き込み v2  : {', '.join(written)} が受け付けて成功")
110    for rep in cluster.replicas:  # 停止していたレプリカが復帰する
111        rep.up = True
112    print(f"  書き込み後   : {cluster.show('x')}")
113    print("  読み込み:")
114    ver, val = cluster.read("x", verbose=True)
115    result = "最新" if ver == 2 else "古い値"
116    print(f"  読み込み結果 : v{ver} {val} ({result})")
117    print(f"  読み込み後   : {cluster.show('x')}")
118    print()

121def stale_rate(n: int, w: int, r: int, trials: int, seed: int) -> float:
122    """古い値を読む割合を、試行を繰り返して求める."""
123    rng = random.Random(seed)
124    stale = 0
125    for _ in range(trials):
126        cluster = Cluster(n, w, r, rng)
127        for rep in cluster.replicas:
128            rep.put("x", (1, "old"))
129        cluster.write("x", (2, "new"))
130        if cluster.read("x")[0] < 2:
131            stale += 1
132    return stale / trials

最初の例では、C が停止している間に書き込みが行われ、C は古い値のまま復帰しています。読み込みで B と C から応答を得ると、B の値の方がバージョンが新しいので、最新の値が返り、C には読み込み修復で最新の値が書き戻されます。2 番目の例は \(R + W \le N\) の場合で、書き込みを受け付けた C 以外のレプリカから読んだため、古い値が返っています。

最後の表のとおり、\(R + W > N\) を満たす組み合わせでは古い値を読むことはありません。満たさない組み合わせで古い値を読む確率は、読み込む \(R\) 個のレプリカがすべて、書き込みの届かなかった \(N - W\) 個の中から選ばれる確率で、次の式で表されます。

\[\frac{\binom{N - W}{R}}{\binom{N}{R}}\]

5.7.1. クォーラムの限界

\(R + W > N\) を満たしていても、常に最新の値が読めるとは限りません。実際のシステムでは、次のような場合に古い値が見えることがあります。

  • 書き込みと読み込みが同時に行われた場合：書き込みが一部のレプリカにしか届いていない途中で読み込むと、新しい値と古い値のどちらが返るかは決まりません。

  • 書き込みが一部のレプリカでだけ成功した場合：\(W\) 個に届かず書き込みが失敗しても、届いたレプリカから値が取り消されるとは限りません。後の読み込みで、失敗したはずの値が見えることがあります。

  • 同じデータへの同時の書き込み：どちらの値を新しいとみなすかを、後述の LWW（Last Write Wins）のようにタイムスタンプで決めると、ノード間の時計のずれによって新しい書き込みが捨てられることがあります。

  • sloppy quorum を使った場合：一部のシステムでは、本来のレプリカに届かないとき、一時的に別のノードに書き込みを預け（hinted handoff）、本来のレプリカが復帰したら渡します。可用性は高まりますが、読み込みの集合と書き込みの集合が重なる保証はなくなります。

このため、クォーラムによる読み書きは、「一貫性モデル」で説明する線形化可能性を保証するものではありません。読み込み修復を同期的に行うなどの工夫で強い保証に近づけることはできますが、強い一貫性が必要な場合は、合意アルゴリズムを使うシステムを検討するのが一般的です。

5.8. 書き込みの競合の解決

マルチリーダー方式やリーダーレス方式では、同じデータに対する並行した書き込みが起こり得ます。まず、2 つの書き込みが一方の後に他方が起きたものか、並行に起きたものかを判定する必要があります。この判定にはバージョンベクトルなどが使われます（ベクトル時計による並行性の判定は「時刻と順序」を参照してください）。並行な書き込みの間で値をどう決めるかには、次のような方法があります。

5.8.1. LWW（Last Write Wins）

各書き込みにタイムスタンプを付け、最も新しいタイムスタンプを持つ値を残し、ほかを捨てる方法です。実装が簡単で、全レプリカが最終的に同じ値にそろいます。一方で、並行に書き込まれた値のうち 1 つ以外は黙って失われます。また、ノードの時計がずれていると、実際には後に書き込まれた値が捨てられることもあります。データが失われてもかまわない場合や、キーを一度しか書き込まない（UUID をキーにして追記だけを行う）場合に適しています。

5.8.2. アプリケーションによる解決

並行な値をすべて保存しておき（Dynamo ではこれを兄弟（sibling）と呼びます）、次に読み込んだアプリケーションに渡して統合させる方法です。例えば、ショッピングカートであれば、2 つのカートの商品の和集合を取ります。ただし、単純な和集合では、削除した商品が復活してしまうといった問題があります。

5.8.3. CRDT

CRDT（Conflict-free Replicated Data Type）は、並行に更新しても、更新を受け取った順序にかかわらず、すべてのレプリカが最終的に同じ状態に収束するように設計されたデータ構造です。2011 年にシャピロ（Marc Shapiro）らによって体系化されました。

最も簡単な例は、増加だけが可能なカウンタ（G-Counter）です。各レプリカ \(i\) は自分が足した数 \(c_i\) だけを自分の要素として持ち、カウンタの値は全要素の和 \(\sum_i c_i\) とします。2 つのレプリカの状態を統合するときは、要素ごとに最大値を取ります。最大値を取る操作は、何回行っても、どの順序で行っても結果が変わらないため、レプリカの状態はどのような順序で交換しても同じ値に収束します。このほかに、増減できるカウンタ、集合、リスト、テキストなどの CRDT が考案されており、共同編集のアプリケーションなどで使われています。

5.9. アンチエントロピー

リーダーレス方式では、停止していたレプリカや、書き込みが届かなかったレプリカに、古いデータが残ります。これを修復する仕組みには、次のものがあります。

  • 読み込み修復（read repair）：読み込みのときに複数のレプリカから値を集め、古い値を返したレプリカに最新の値を書き戻します。よく読まれるデータはすぐに修復されますが、ほとんど読まれないデータは古いまま残ります。

  • hinted handoff：前述のように、停止中のレプリカ宛ての書き込みを別のノードが預かり、復帰したときに渡します。

  • アンチエントロピー：バックグラウンドのプロセスが、定期的にレプリカどうしのデータを比較し、差分を見つけて修復します。読まれないデータも修復できます。

アンチエントロピーでレプリカ全体のデータをそのまま比較すると、大量の通信が必要になります。そこで Dynamo や Cassandra では、マークル木（Merkle tree）を使います。マークル木は、データの範囲ごとのハッシュ値を葉とし、子のハッシュ値をまとめたハッシュ値を親とする木です。2 つのレプリカは、まず根のハッシュ値を比べ、一致すれば全体が一致していると判断します。一致しなければ子をたどり、ハッシュ値の異なる範囲だけを詳しく比較します。これにより、差分が少ないときの通信量を大幅に減らせます。

5.10. まとめ

  • レプリケーションの目的は、可用性、読み込みの性能、遅延の短縮です。難しさは、すべて変更の伝え方にあります。

  • シングルリーダー方式は書き込みの競合が起きない一方、フェイルオーバーでは書き込みの消失、停止の誤検出、スプリットブレインに注意が必要です。

  • 非同期レプリケーションのフォロワーから読むと、自分の書き込みが読めない、時間が巻き戻る、といった異常が起こります。

  • リーダーレス方式では、\(R + W > N\) を満たすクォーラムで読み書きすると、読み込みの集合と書き込みの集合が必ず重なり、最新の値を読めます。ただし、並行な書き込みや部分的な失敗などがあるため、線形化可能性までは保証されません。

  • 並行な書き込みの競合は、LWW、アプリケーションによる解決、CRDT などで解決します。古いレプリカは、読み込み修復とアンチエントロピーで修復します。
