6. 一貫性モデル

この章では、レプリケーションされたデータを読み書きするとき、プログラムからどのような結果が見え得るのかを定める一貫性モデルを説明します。具体的な操作の履歴を例に、線形化可能性、逐次一貫性、因果一貫性、結果整合性の違いを比べ、セッション保証を紹介します。続いて、よく誤解される CAP 定理の正しい意味と、通常時の遅延も考慮した PACELC を説明し、最後にデータベースのトランザクション分離レベルとの違いを整理します。

6.1. 一貫性とは

「レプリケーション」で見たように、データを複数のレプリカに持たせると、変更が各レプリカに伝わるまでの間、レプリカによって見える値が異なります。そのため、あるクライアントが書き込んだ直後に別のクライアントが読み込んだとき、新しい値が返るのか、古い値が返ってもよいのかを決めておく必要があります。

一貫性モデル（consistency model）は、データを保存するシステムとそれを使うプログラムの間の約束事です。システムは「この範囲の結果しか返さない」と約束し、プログラムはその約束を前提に正しく動くように書かれます。約束が強い（返り得る結果の範囲が狭い）ほどプログラムは書きやすくなりますが、システムの実装にはレプリカ間の調整が多く必要になり、遅延や可用性の面で代償を払うことになります。

表 6.4 主な一貫性モデル（上ほど強い）

モデル

概要

線形化可能性

全体が 1 つのコピーであるかのような振る舞い。実時間の順序も維持

逐次一貫性

全操作が 1 つの順序に整列。ただし実時間の順序は不問

因果一貫性

因果関係のある操作の順序だけを、全員が同じ順序で観測

結果整合性

更新が止まれば、最終的に全レプリカが同じ値に収束

なお、線形化可能性を満たせば逐次一貫性を、逐次一貫性を満たせば因果一貫性を満たします。つまり、強いモデルは弱いモデルの保証をすべて含みます。

6.2. 操作の履歴で考える

一貫性モデルの違いは、具体的な操作の履歴（ヒストリー）で考えると分かりやすくなります。以下では、1 つの値を保持する変数（レジスタ）として \(x\) と \(y\) を考え、初期値はどちらも 0 とします。各クライアントの操作は、リクエストを送った時刻からレスポンスを受け取った時刻までの区間として、次のように表します。w(x,1) は \(x\) に 1 を書き込む操作、r(x)->0 は \(x\) を読み込んで 0 が返った操作を表します。

6.2.1. 例 1：書き込みの完了後に古い値を読む

クライアント A の書き込みが完了した後に、クライアント B が読み込みを始め、古い値 0 を受け取った履歴です。

time   0    1    2    3    4    5
A      [--w(x,1)--]
B                       [--r(x)->0--]

6.2.2. 例 2：書き込みの途中に 2 回読む

クライアント A の書き込みに時間がかかっている間に、クライアント B が 2 回読み込んだ履歴です。2a では 0、1 の順に、2b では 1、0 の順に値が返っています。

time   0    1    2    3    4    5    6
A      [------------w(x,1)-------------]
B (2a)      [r(x)->0]  [r(x)->1]
B (2b)      [r(x)->1]  [r(x)->0]

6.2.3. 例 3：並行な書き込みを異なる順序で観測する

クライアント A と B が、互いに関係なく同時に \(x\) に異なる値を書き込み、それをクライアント C と D が異なる順序で観測した履歴です。

time   0    1    2    3    4    5    6
A      [w(x,1)]
B      [w(x,2)]
C                [r(x)->1]  [r(x)->2]
D                [r(x)->2]  [r(x)->1]

6.2.4. 例 4：因果関係が逆転して見える

クライアント A が \(x\) に 1 を書き込み、それを読んだクライアント B が \(y\) に 2 を書き込みます。B の書き込みは A の書き込みを見たうえで行われたので、A の書き込みに因果的に依存しています。ところが、クライアント C は \(y\) の新しい値 2 を見た後に、\(x\) の古い値 0 を見ています。質問（\(x\)）を見ずに回答（\(y\)）だけが見えている状態です。

time   0    1    2    3    4    5    6    7
A      [w(x,1)]
B                [r(x)->1] [w(y,2)]
C                                   [r(y)->2] [r(x)->0]

6.3. 線形化可能性

線形化可能性（linearizability）は、1990 年にハーリヒー（Maurice Herlihy）とウィング（Jeannette Wing）が定式化した、最も強い一貫性モデルの 1 つです。データが実際には複数のレプリカにあっても、クライアントからは 1 つのコピーしかないかのように見えることを保証します。

正確には、各操作が、リクエストを送ってからレスポンスを受け取るまでの間のどこかの一瞬で、不可分に実行されたかのように見えることを要求します。この一瞬を線形化点と呼びます。すべての操作の線形化点を時刻順に並べた順序で、1 つのコピーに対して操作を実行したときと同じ結果になれば、その履歴は線形化可能です。

  • 例 1 は許されません。A の書き込みは時刻 3 より前に完了しているので、その線形化点も時刻 3 より前にあります。B の読み込みは時刻 3 より後に始まっているので、その線形化点は書き込みの線形化点より後になり、1 が返らなければなりません。

  • 例 2a は許されます。読み込みが書き込みと時間的に重なっている（並行である）場合、その読み込みは書き込みの前とも後とも見なせるので、0 と 1 のどちらが返ってもかまいません。1 回目の読み込みの線形化点を書き込みの前に、2 回目を後に置けば説明できます。

  • 例 2b は許されません。1 回目の読み込みで 1 が返ったということは、その時点で書き込みの線形化点を過ぎています。それより後の 2 回目の読み込みで 0 が返ることはありません。つまり、誰かが新しい値を一度でも読んだら、それ以降は誰も古い値を読めないということです。

  • 例 3 と例 4 も許されません。例 3 では、全操作を 1 つの順序に並べたとき、\(x\) が 1 から 2 に変わったのか 2 から 1 に変わったのかが C と D で食い違っています。例 4 は、後で説明するように、より弱い因果一貫性でも許されないので、線形化可能性でも許されません。

線形化可能性が必要になる典型的な場面は、リーダーの選出のためのロック、ユーザー名の一意性の制約、在庫の引き当てのように、全員が同じ最新の状態を見て判断しなければならない場合です。線形化可能なシステムは、シングルリーダー方式で常にリーダーから読み書きするか（ただし、リーダーが自分が今もリーダーであることを確かめる仕組みが必要です）、Raft などの合意アルゴリズム（「合意と分散トランザクション」を参照してください）を使って実現します。その代償として、操作のたびにレプリカ間の通信が必要になり、遅延が大きくなります。また、後述の CAP 定理のとおり、ネットワーク分断が起きると一部のノードは応答できなくなります。

6.4. 逐次一貫性

逐次一貫性（sequential consistency）は、1979 年にランポート（Leslie Lamport）がマルチプロセッサーのメモリの正しさの条件として定義したモデルです。すべてのクライアントの操作を 1 つの順序に並べることができ、その順序の中で各クライアントの操作が、そのクライアントが実行した順序のとおりに並んでいれば、逐次一貫性を満たします。

線形化可能性との違いは、異なるクライアントの操作の間の実時間の順序を守らなくてよい点です。

  • 例 1 は許されます。B の読み込みを A の書き込みより前に並べた順序「B の r(x)->0、A の w(x,1)」は、各クライアントの操作の順序を守っており、結果も矛盾しません。実時間では A の書き込みが先に完了していますが、逐次一貫性はそれを問いません。

  • 例 2b、例 3、例 4 は許されません。例 3 では、全員が同じ 1 つの順序を見る必要があるのに、C と D の観測した \(x\) の変化の順序が逆になっています。

逐次一貫性は、すべてのクライアントが同じ順序で変化を観測することを保証しますが、その順序が実時間とずれることを許します。分散システムのデータストアよりも、マルチコア CPU のメモリモデルの議論でよく使われる概念です。

6.5. 因果一貫性

因果一貫性（causal consistency）は、因果関係のある操作についてだけ、全員が同じ順序で観測することを保証するモデルです。操作 \(a\) が操作 \(b\) に因果的に先行するのは、次のいずれかの場合です（「時刻と順序」の happened-before 関係に対応します）。

  • 同じクライアントが \(a\) の後に \(b\) を実行した場合

  • \(b\) が、\(a\) の書き込んだ値を読み込んだ場合

  • 上の関係をたどって \(a\) から \(b\) に到達できる場合

因果関係のない操作（並行な操作）については、クライアントによって異なる順序で観測してもかまいません。

  • 例 3 は許されます。A と B の書き込みは互いに関係のない並行な操作なので、C と D が異なる順序で観測してもかまいません。

  • 例 4 は許されません。B の \(y\) への書き込みは、\(x = 1\) を読んだうえで行われているので、A の書き込みに因果的に依存しています。C が \(y = 2\) を見たのであれば、その原因である \(x = 1\) も見えていなければなりません。

  • 例 2b も許されません。B は 1 回目の読み込みで A の書き込みを観測しているので、それより後の B の読み込みに、上書きされる前の値 0 が返ってはいけません。

因果一貫性は、ネットワーク分断が起きても各ノードが応答を続けながら実現できる一貫性モデルの中で、最も強いものの 1 つであることが知られています。SNS のコメントと返信のように、因果関係の逆転がユーザーを混乱させる場面で役立ちます。実装には、ベクトル時計などで操作の依存関係を追跡する必要があります。

6.6. 結果整合性

結果整合性（eventual consistency）は、新しい書き込みが止まれば、いずれすべてのレプリカが同じ値に収束することだけを保証するモデルです。収束するまでの間にどの値が読めるかについては、何も保証しません。そのため、ここで挙げた例はすべて、最終的に値が収束しさえすれば許されます。

結果整合性は、リーダーレス方式や非同期のマルチリーダー方式など、可用性と遅延を重視するシステムの多くが提供するモデルです。2008 年にフォーゲルス（Werner Vogels）が Amazon での経験をもとにこの言葉を広めました。保証が非常に弱いため、結果整合性のシステムを使うアプリケーションは、古い値や順序の入れ替わりが起き得ることを前提に設計する必要があります。また、「いずれ」がどのくらいの時間なのかも保証されないため、実際の運用では、レプリケーション遅延を監視することが重要です。

6.7. セッション保証

結果整合性はアプリケーションにとって扱いにくいため、1 人のユーザー（1 つのセッション）から見たときの不自然さだけでも防ぎたい、という要求があります。そのための保証が、1994 年にテリー（Douglas Terry）らが分散データベース Bayou の研究で提案したセッション保証（session guarantees）です。

表 6.6 4 つのセッション保証

保証

内容

自分の書き込みの読み込み（read your writes）

セッションの読み込みに、同じセッションが以前に行った書き込みが反映されていること

単調な読み込み（monotonic reads）

一度ある書き込みを反映した値を読んだら、それより後の読み込みで、それより古い値が返らないこと

単調な書き込み（monotonic writes）

同じセッションの書き込みが、どのレプリカでも実行した順序のとおりに適用されること

読み込みに続く書き込み（writes follow reads）

セッションが読んだ値の元になった書き込みより後に、そのセッションの新しい書き込みが適用されること

「レプリケーション」で挙げた「自分の書き込みが読めない」異常は read your writes の違反、「読み込むたびに時間が巻き戻る」異常は monotonic reads の違反です。例 2b も、B のセッションから見て monotonic reads に違反しています。

セッション保証は、クライアントが自分の読み書きしたバージョンを覚えておき、それより新しいレプリカからだけ読む、といった方法で、システム全体の強い一貫性なしに実現できます。4 つの保証をすべて満たすと、おおむね因果一貫性に相当する保証になります。

6.8. CAP 定理

6.8.1. CAP 定理の内容

CAP 定理は、2000 年にブリュワー（Eric Brewer）が講演で予想として示し、2002 年にギルバート（Seth Gilbert）とリンチ（Nancy Lynch）が証明したものです。定理で使われる 3 つの性質は、次のように定義されています。

  • C（Consistency）：線形化可能性。

  • A（Availability）：停止していないノードが受け取ったリクエストには、必ず（エラーでない）レスポンスを返すこと。

  • P（Partition tolerance）：ネットワーク分断、つまりノード間のメッセージが任意に失われる状況でも、システムが動作を続けること。

CAP 定理が述べているのは、「ネットワーク分断が起き得るシステムでは、分断が起きたときに、一貫性（C）と可用性（A）を同時に満たすことはできない」ということです。

理由は簡単です。2 つのノード N1 と N2 にデータがレプリケーションされていて、両者の間のネットワークが分断されたとします。クライアントが N1 に \(x = 1\) を書き込んだ後、別のクライアントが N2 に \(x\) を読みに来ました。N2 は N1 と連絡が取れないので、N1 で書き込みがあったかどうかを知る方法がありません。このとき N2 の選択肢は 2 つだけです。

  • 手元の値（古いかもしれない値）を返す：可用性は保たれますが、線形化可能性は失われます（AP）。

  • 分断が解消するまで待つか、エラーを返す：線形化可能性は保たれますが、可用性は失われます（CP）。

つまり、CAP 定理の正しい理解は、「ネットワーク分断が起きたときに、一貫性と可用性のどちらを選ぶか」という選択を迫るものです。分断が起きていない通常時には、両方を満たすことに何の矛盾もありません。

6.8.2. CAP 定理についてのよくある誤解

CAP 定理は広く知られていますが、誤解も多くあります。代表的なものを挙げます。

  • 誤解 1「3 つのうち好きな 2 つを選べる」：複数のノードからなるシステムでは、ネットワーク分断は選んで避けられるものではなく、いつか必ず起きます。したがって P を捨てて CA を選ぶという選択肢は、実質的にはありません。「CA のシステム」と呼べるのは、1 台のノードで動くシステムか、分断が起きないと仮定しているシステムだけです。ブリュワー自身も、2012 年の論文で「3 つのうち 2 つ」という言い方は誤解を招くと述べています。

  • 誤解 2「CAP の C は ACID の C と同じ」：ACID（Atomicity、Consistency、Isolation、Durability）の C は、残高が負にならないといったアプリケーションの不変条件が保たれることを指し、CAP の C（線形化可能性）とはまったく別の概念です。

  • 誤解 3「CAP の A は高可用性のことである」：CAP の A は、停止していないすべてのノードが応答することを求める、非常に厳しい定義です。例えば、分断時に過半数の側のノードだけが応答を続けるシステムは、CAP の意味では A を満たしませんが、利用者から見れば十分に可用性が高いことがあります。逆に、CAP の意味で A を満たしても、障害時に実用的な速さで応答するとは限りません。

  • 誤解 4「データベースの製品は CP か AP のどちらかに分類できる」：多くの製品は、設定や操作ごとに一貫性の強さを選べます。また、「レプリケーション」で見たクォーラムによる読み書きのように、線形化可能性も CAP の意味での可用性も満たさない設定も多くあります。製品全体に CP や AP のラベルを貼るより、どの操作がどの保証を持つかを確かめる方が有益です。

  • 誤解 5「一貫性を選ぶと常に可用性が低い」：CAP 定理が可用性を犠牲にすることを求めるのは、分断が起きている間だけです。

6.9. PACELC

CAP 定理は分断が起きたときだけを扱っており、通常時の性質について何も述べていません。しかし実際には、分断がないときにも、一貫性を強くするほどレプリカ間の通信が増え、遅延が大きくなるというトレードオフがあります。むしろ、システムの設計で日常的に問題になるのはこちらです。

アバディ（Daniel Abadi）が提唱し、2012 年の論文でまとめた PACELC は、この点を補ったものです。

  • P（Partition）が起きたときは、A（Availability）と C（Consistency）のどちらを選ぶか

  • E（Else）、つまり通常時は、L（Latency）と C（Consistency）のどちらを選ぶか

分類

意味

例

合意アルゴリズムで全操作の順序をそろえるデータベース

PA/EC

分断時は可用性、通常時は一貫性を優先

通常時はリーダーから読み、分断時はフォロワーからの読み込みを許すシステム

PACELC も単純化された分類であり、CAP と同様に、製品全体のラベルではなく、設定や操作ごとの性質として考えるのが適切です。

6.10. トランザクション分離レベルとの違い

データベースには、トランザクションの分離レベル（read committed、スナップショット分離、直列化可能性など）という、一貫性モデルとよく似た概念があります。両者は混同されやすいのですが、別の問題を扱っています。

  • トランザクションの分離レベルは、複数のオブジェクトを読み書きする複数のトランザクションが並行に実行されたとき、互いの途中の状態がどこまで見えるかを定めます。ACID の I（Isolation）に当たります。

  • この章で扱った一貫性モデルは、主に 1 つのオブジェクトに対する個々の操作について、レプリカの存在や実時間の順序を踏まえて、どの値が見えるかを定めます。

例えば、直列化可能性（serializability）は、トランザクションの結果が、それらを何らかの順序で 1 つずつ実行した結果と同じになることを保証します。しかし、その順序が実時間の順序と一致することまでは求めません。そのため、直列化可能であっても、完了したはずのトランザクションの結果が後のトランザクションから見えないことがあり得ます。直列化可能性と線形化可能性を両方満たすものを厳密な直列化可能性（strict serializability）と呼びます。Google の Spanner は、TrueTime を使ってこれに相当する保証（外部一貫性）を提供しています。

表 6.8 「一貫性」という言葉の使われ方

文脈

意味

ACID の C

アプリケーションの不変条件（制約）が保たれること

CAP の C

線形化可能性

一貫性モデル

レプリケーションされたデータの読み書きで、どの結果が見え得るかの約束事

結果整合性

更新が止まれば、最終的に全レプリカが同じ値に収束すること

「一貫性」という言葉は文脈によって意味が大きく異なります。設計や議論の場では、どの意味で使っているのかを明確にすることが大切です。

6.11. まとめ

  • 一貫性モデルは、データを保存するシステムとプログラムの間の約束事で、強いモデルほどプログラムは書きやすくなりますが、遅延や可用性の代償が大きくなります。

  • 線形化可能性は 1 つのコピーしかないかのように振る舞い、実時間の順序も守ります。逐次一貫性は全員が同じ順序を見ますが実時間の順序は守らず、因果一貫性は因果関係のある操作の順序だけを守ります。結果整合性は最終的な収束だけを保証します。

  • セッション保証（read your writes、monotonic reads など）は、1 つのセッションから見た不自然さを防ぎます。

  • CAP 定理は、ネットワーク分断が起きたときに一貫性（線形化可能性）と可用性のどちらを選ぶかを迫るものです。「3 つのうち 2 つを選ぶ」という理解は誤りで、分断がないときは両立できます。

  • PACELC は、通常時にも遅延と一貫性のトレードオフがあることを加えたものです。トランザクションの分離レベルは一貫性モデルとは別の問題を扱っています。
