4. 性能の測り方

アーキテクチャの設計でも、ソフトウェアのチューニングでも、「速くなったか」を正しく測り、「どこを改良すれば速くなるか」を見積もることが出発点になります。この章では、性能を定量的に議論するための道具をまとめます。

まず、実行時間、スループット、レイテンシといった性能の指標を定義します。次に、実行時間を命令数、CPI、クロック周期の 3 つの要因に分解する CPU 性能の式を学びます。続いて、MIPS や FLOPS といった指標の落とし穴、ベンチマークと平均の取り方、改良の効果の上限を示すアムダールの法則、消費電力の式、そしてメモリと演算のどちらが性能を制約しているかを判断するルーフラインモデルを説明します。最後に、これらを Python のサンプルで計算します。

4.1. 性能の指標

4.1.1. 実行時間と応答時間

ユーザーにとって最も分かりやすい性能の指標は、プログラムを実行し始めてから終わるまでの時間です。これを実行時間（execution time）、または応答時間（response time）と呼びます。実行時間には、CPU で計算している時間のほか、ディスクやネットワークの入出力を待つ時間、他のプログラムに CPU を譲っている時間も含まれます。このように待ち時間まで含めた時間であることを強調して、経過時間（elapsed time、wall-clock time）とも呼びます。

これに対し、そのプログラムのために CPU が実際に命令を実行していた時間を CPU 時間（CPU time）と呼びます。CPU 時間は、プログラム自身のコードを実行していたユーザー CPU 時間と、プログラムのために OS が働いていたシステム CPU 時間に分けられます。Linux の time コマンドが表示する real、user、sys は、それぞれ経過時間、ユーザー CPU 時間、システム CPU 時間です。本章で扱うプロセッサの性能は、主にユーザー CPU 時間に関わるものです。

性能と実行時間は逆数の関係にあります。

\[\text{性能} = \frac{1}{\text{実行時間}}\]

「X は Y より \(n\) 倍速い」とは、次の関係が成り立つことを意味します。

\[n = \frac{\text{性能}_X}{\text{性能}_Y} = \frac{\text{実行時間}_Y}{\text{実行時間}_X}\]

たとえば、あるプログラムの実行時間が X で 10 秒、Y で 15 秒なら、X は Y より 1.5 倍速いと言います。

4.1.2. スループットとレイテンシ

1 つの処理にかかる時間をレイテンシ（latency）、単位時間あたりに完了する処理の量をスループット（throughput）と呼びます。応答時間はレイテンシの一種です。

レイテンシとスループットは、必ずしも一緒に改善するとは限りません。

  • プロセッサのコアを 2 倍にすると、同時に処理できるリクエストが増えるので、Web サーバーのスループットは上がります。しかし、1 つのリクエストの処理が速くなるわけではないので、レイテンシは変わりません。

  • 「パイプライン」で説明するパイプラインは、命令の処理を複数の段に分けて重ねて実行することで、スループット（1 秒あたりに完了する命令の数）を上げます。1 つの命令の処理にかかる時間は、むしろ少し長くなります。

  • メモリの性能も、1 回のアクセスにかかる時間（レイテンシ、DRAM では数十〜100 ns 程度）と、1 秒あたりに転送できるデータの量（帯域幅、bandwidth）を分けて考えます。帯域幅は比較的簡単に上げられますが、レイテンシを下げるのは困難です。

どちらの指標が重要かは用途によります。対話的なアプリケーションではレイテンシが、バッチ処理やサーバーではスループットが重視されます。

4.2. CPU 性能の式

4.2.1. クロックとサイクル

ほとんどのプロセッサは、一定の周期で 0 と 1 を繰り返すクロック（clock）信号に同期して動きます。クロックの 1 周期をクロックサイクル、または単にサイクルと呼び、その時間をクロック周期（clock period、cycle time）と呼びます。クロック周期の逆数がクロック周波数（clock frequency、clock rate）です。

\[\text{クロック周期} = \frac{1}{\text{クロック周波数}}\]

たとえば、クロック周波数が 4 GHz のプロセッサのクロック周期は \(1 / (4 \times 10^9) = 0.25\ \text{ns}\) です。

4.2.2. 命令数、CPI、クロック周期

プログラムの CPU 時間は、そのプログラムの実行に要したサイクル数とクロック周期の積です。サイクル数を、実行した命令の数と、1 命令あたりの平均のサイクル数に分解すると、次の式が得られます。

(4.1)\[\text{CPU 時間} = \text{命令数} \times \text{CPI} \times \text{クロック周期} = \frac{\text{命令数} \times \text{CPI}}{\text{クロック周波数}}\]

ここで、命令数（instruction count：IC）は、プログラムの実行中に実際に実行された命令の数です。ループの中の命令は繰り返しの回数だけ数えるので、プログラムのファイルに含まれる命令の数とは異なります。CPI（Cycles Per Instruction）は 1 命令あたりの平均のクロックサイクル数です。その逆数を IPC（Instructions Per Cycle）と呼び、1 サイクルに複数の命令を実行するプロセッサではこちらを使うことも多くあります。

式 (4.1) を単位で書くと、各項の意味がよく分かります。

\[\frac{\text{秒}}{\text{プログラム}} = \frac{\text{命令}}{\text{プログラム}} \times \frac{\text{サイクル}}{\text{命令}} \times \frac{\text{秒}}{\text{サイクル}}\]

数値例で確かめます。あるプログラムの命令数が \(2 \times 10^9\)、CPI が 1.5、クロック周波数が 3 GHz なら、CPU 時間は次のようになります。

\[\frac{2 \times 10^9 \times 1.5}{3 \times 10^9\ \text{Hz}} = 1.0\ \text{秒}\]

4.2.3. 命令の種類ごとの CPI

命令の種類によって必要なサイクル数は異なります。たとえば、加算は 1 サイクルで終わっても、ロードはキャッシュミスを起こすと数百サイクルかかることがあります。命令の種類 \(i\) の CPI を \(\text{CPI}_i\)、全命令に占める割合を \(F_i\) とすると、平均の CPI は次の加重平均になります。

4.3. MIPS と FLOPS の落とし穴

4.3.1. MIPS

実行時間の代わりに、1 秒あたりに実行した命令の数で性能を表すことがあります。100 万命令を単位として表したものを MIPS（Million Instructions Per Second）と呼びます（ISA の名前の MIPS とは別のものです）。

\[\text{MIPS} = \frac{\text{命令数}}{\text{実行時間} \times 10^6} = \frac{\text{クロック周波数}}{\text{CPI} \times 10^6}\]

MIPS は分かりやすい指標ですが、次の問題があります。

  • 命令数を考慮していません。ISA が異なると、同じ処理に必要な命令の数が違うので、MIPS では比べられません。

  • 同じプロセッサでも、プログラムによって CPI が変わるので、MIPS も変わります。

  • MIPS が高いほうが遅い、ということが起こります。

4.3.2. FLOPS

科学技術計算や機械学習では、1 秒あたりに実行した浮動小数点演算の回数である FLOPS（FLoating-point Operations Per Second）がよく使われます。\(10^9\) FLOPS を 1 GFLOPS、\(10^{12}\) FLOPS を 1 TFLOPS と書きます。本書では単位を明確にするため、GFLOP/s のようにも書きます。

FLOPS は MIPS より実際の仕事量に近い指標ですが、やはり注意が必要です。

  • 製品の仕様に書かれた FLOPS は、すべての演算器が休みなく動いたと仮定したピーク性能（理論性能）です。実際のプログラムが達成する性能は、メモリからデータを供給する速度で制限され、ピークの数 % にとどまることも珍しくありません。この関係は、後で説明するルーフラインモデルで分析できます。

  • 演算の精度が違えば、FLOPS は比べられません。倍精度（FP64）、単精度（FP32）、AI 向けの FP16 や FP8 では、同じハードウェアでもピーク性能が数倍から数十倍違います。仕様を見るときは、どの精度の値かを必ず確認します。

  • 積和演算（\(a \times b + c\)）を 1 命令で行う FMA（Fused Multiply-Add）は、通常 2 演算と数えます。

ピーク性能は、次の式で計算できます。

\[\text{ピーク性能} = \text{コア数} \times \text{クロック周波数} \times \text{1 サイクル・1 コアあたりの演算数}\]

たとえば、64 コア、2.0 GHz で、各コアが 1 サイクルに 512 ビット幅の倍精度の FMA を 2 つ実行できるプロセッサなら、1 サイクル・1 コアあたりの演算数は \(2\ (\text{FMA}) \times 8\ (\text{要素}) \times 2\ (\text{演算}) = 32\) なので、ピーク性能は \(64 \times 2.0 \times 10^9 \times 32 \approx 4.1\ \text{TFLOP/s}\) になります。

4.4.2. 平均の取り方

ベンチマークは複数のプログラムからなるので、結果を 1 つの数値にまとめるには平均を取る必要があります。SPEC CPU では、各プログラムについて、基準となる計算機の実行時間との比（SPECratio）を求め、その幾何平均（geometric mean）を最終的なスコアとします。

4.5. アムダールの法則

4.5.1. 法則の内容

システムの一部を改良したとき、全体がどれだけ速くなるかを見積もる式がアムダールの法則（Amdahl's law）です。1967 年にジーン・アムダールが、並列処理の効果の限界を論じる中で示した考え方に基づいています。

改良前の実行時間のうち、改良の対象となる部分の割合を \(f\)、その部分の速度向上率を \(s\) とします。改良の対象でない部分 \(1 - f\) の時間は変わらないので、改良後の実行時間は \((1 - f) + f / s\) 倍になります。したがって、全体の速度向上率 \(S\) は次の式で表されます。

(4.2)\[S = \frac{1}{(1 - f) + \dfrac{f}{s}}\]

\(s\) を無限大にしても、\(S\) は \(1 / (1 - f)\) を超えません。改良できない部分が、全体の速度向上の上限を決めるのです。

4.5.2. 数値例

あるプログラムの実行時間の 60% を占める行列演算を、アクセラレーターで 10 倍速くしたとします。全体の速度向上率は次のとおりです。

\[S = \frac{1}{(1 - 0.6) + \dfrac{0.6}{10}} = \frac{1}{0.46} \approx 2.17\]

10 倍速いアクセラレーターを使っても、全体では約 2.2 倍にしかなりません。行列演算を無限に速くしても、上限は \(1 / 0.4 = 2.5\) 倍です。さらに速くするには、残りの 40% を改良する必要があります。

アムダールの法則は、並列化の効果を見積もるときに特に重要です。並列化できる部分の割合を \(f\)、コア数を \(N\) とすると、\(s = N\) として式 (4.2) を使えます。後のサンプルで計算するように、95% を並列化できるプログラムでも、1,024 コアを使って 20 倍弱にしかなりません。逐次実行の部分が 5% あるだけで、それが全体の上限を決めてしまうのです。

アムダールの法則の教訓は、「よく使われる場合を速くせよ」（make the common case fast）ということです。改良の効果は、改良する部分が実行時間に占める割合に比例して大きくなります。最適化を始める前には、プロファイラで実行時間の内訳を測り、時間を多く使っている部分から手を付けるべきです。

4.5.3. グスタフソンの法則

アムダールの法則は、問題の大きさを固定したまま、コアを増やしたときの効果を表しています。しかし実際には、コアが増えれば、より大きな問題を解こうとすることが多いでしょう。たとえば、天気予報のシミュレーションでは、計算機が速くなれば、同じ時間でより細かい格子を計算します。

1988 年にジョン・グスタフソンは、実行時間を固定して問題を大きくする場合を考えました。\(N\) コアでの実行時間のうち、並列に実行した部分の割合を \(f\) とすると、同じ仕事を 1 コアで実行すると \((1 - f) + f N\) 倍の時間がかかります。したがって速度向上率は次のようになります。

\[S = (1 - f) + f N\]

この式では、\(N\) に比例して速度向上率が伸びます。これをグスタフソンの法則（Gustafson's law）と呼びます。2 つの法則は矛盾するわけではなく、問題の大きさを固定するか（強スケーリング）、コアあたりの問題の大きさを固定するか（弱スケーリング）という前提の違いを表しています。

4.6. 電力とエネルギー

4.6.1. 動的電力

現在のプロセッサは、CMOS と呼ばれる種類のトランジスタの回路で作られています。CMOS の回路は、信号が 0 から 1、1 から 0 に切り替わるときに、配線やトランジスタの持つ容量を充電・放電するために電力を消費します。これを動的電力（dynamic power）と呼び、次の式で表されます。

\[P_{\text{dynamic}} = \alpha \, C \, V^2 f\]

ここで、\(C\) は切り替わる回路の容量、\(V\) は電源電圧、\(f\) はクロック周波数、\(\alpha\) は 1 サイクルあたりに信号が切り替わる割合（活動率）です。動的電力は電圧の 2 乗に比例するので、電圧を下げることが電力の削減に最も効きます。

電圧とクロック周波数は独立ではありません。一般に、トランジスタを速く動かすには高い電圧が必要です。そこで、負荷に応じて電圧とクロック周波数を一緒に変える DVFS（Dynamic Voltage and Frequency Scaling）が広く使われています。電圧とクロック周波数をともに 15% 下げると、動的電力は \(0.85^3 \approx 0.61\) 倍、つまり約 40% 減ります。性能はクロック周波数に比例して 15% 下がるだけです。

4.6.2. 静的電力

トランジスタは、オフの状態でもわずかな電流（リーク電流、leakage current）を流します。これによる電力を静的電力（static power）と呼びます。

\[P_{\text{static}} = V \, I_{\text{leak}}\]

静的電力は、回路が動いていなくても電源が入っている限り消費されます。トランジスタの微細化とともにリーク電流が増え、静的電力は消費電力の無視できない部分を占めるようになりました。そのため、使っていない回路の電源そのものを切るパワーゲーティング（power gating）も使われています。

4.6.3. 電力の壁

「アーキテクチャの歴史」で述べたように、2000 年代の半ばまでは、トランジスタを縮小するたびに電源電圧も下げることができました（デナード・スケーリング）。電圧が下がれば、\(V^2\) の効果で、クロック周波数を上げてトランジスタを増やしても、チップの消費電力をほぼ一定に保てました。

しかし、電圧を下げるとリーク電流が急増するため、電圧は 1 V 程度から下げにくくなりました。電圧が下がらないまま、クロック周波数とトランジスタの数を増やせば、消費電力は増え続けます。一方、空冷で取り除ける熱は、パソコンやサーバーのプロセッサで 1 チップあたり 100〜数百ワット程度が限界です。こうして、消費電力がクロック周波数の上限を決めるようになりました。これが電力の壁（power wall）です。

電力の壁の結果、プロセッサの設計は、クロック周波数を上げる方向から、マルチコア化、電力あたりの性能の高いコアの組み合わせ、特定の処理に特化したアクセラレーターの利用へと向かいました。さらに、チップ上のトランジスタをすべて同時に最大のクロック周波数で動かすことは電力の制約からできなくなっており、一部の回路は常に止めておかざるをえません。この状態をダークシリコン（dark silicon）と呼びます。

4.6.4. エネルギー

電池で動く機器では、電力（ワット）よりも、処理を終えるまでに消費するエネルギー（ジュール）が重要です。

\[\text{エネルギー} = \text{電力} \times \text{時間}\]

消費電力が 2 倍でも、処理が 3 倍速く終わってすぐに省電力の状態に入れるなら、エネルギーは少なくて済みます。性能と電力をあわせて評価する指標として、性能 / ワット（たとえば GFLOP/s/W）がよく使われます。

4.7. ルーフラインモデル

4.7.1. 演算強度

プログラムの性能が、演算器の速さで決まっているのか、メモリからデータを運ぶ速さで決まっているのかを判断するための図式がルーフラインモデル（roofline model）です。2009 年にサミュエル・ウィリアムズ、アンドリュー・ウォーターマン、パターソンが提案しました。

ルーフラインモデルでは、まずプログラム（またはその中の計算の核となる部分。カーネルと呼ぶ）の演算強度（arithmetic intensity、operational intensity）を求めます。

\[I = \frac{\text{浮動小数点演算の回数}}{\text{メモリとの間で転送するバイト数}} \quad [\text{FLOP/バイト}]\]

たとえば、単精度の浮動小数点数の配列で a[i] = b[i] + c[i] を計算する場合、1 要素あたり加算が 1 回で、b[i] と c[i] の読み出しに 8 バイト、a[i] の書き込みに 4 バイトを転送します。演算強度は \(I = 1 / 12 \approx 0.083\) FLOP/バイトです。一方、大きな行列の積は、キャッシュをうまく使えば同じデータを何度も再利用できるので、演算強度を高くできます。

4.7.2. 到達可能な性能

演算のピーク性能を \(P_{\text{peak}}\)（FLOP/s）、メモリの帯域幅を \(B\)（バイト/s）とします。演算強度 \(I\) のカーネルは、1 秒あたり最大 \(B\) バイトしかデータを受け取れないので、\(B \times I\) FLOP/s を超える性能は出せません。また、演算器のピーク性能も超えられません。したがって、到達可能な性能 \(P\) の上限は次の式になります。

(4.3)\[P = \min(P_{\text{peak}},\ B \times I)\]

横軸に演算強度、縦軸に性能をとって両対数のグラフに描くと、この上限は、傾いた直線（メモリの帯域幅の制約）と水平な直線（ピーク性能の制約）をつないだ屋根の形になります。これがルーフライン（屋根の線）という名前の由来です。2 本の直線が交わる点の演算強度 \(P_{\text{peak}} / B\) をリッジポイント（ridge point）と呼びます。

  • 演算強度がリッジポイントより小さいカーネルはメモリ律速（memory-bound）です。演算器を速くしても性能は上がりません。メモリの帯域幅を上げるか、データの再利用を増やして演算強度を上げる必要があります。

  • 演算強度がリッジポイントより大きいカーネルは演算律速（compute-bound）です。SIMD 命令や並列化で演算器を有効に使うことが重要です。

数値例として、ピーク性能が 1,000 GFLOP/s、メモリの帯域幅が 100 GB/s の計算機を考えます。リッジポイントは \(1000 / 100 = 10\) FLOP/バイトです。先ほどの単精度のベクトル加算（\(I \approx 0.083\)）の到達可能な性能は \(100 \times 0.083 \approx 8.3\) GFLOP/s で、ピーク性能の 1% にも届きません。このカーネルを速くするには、演算器ではなくメモリの帯域幅が鍵になります。

ルーフラインモデルは単純ですが、ハードウェアの仕様（ピーク性能と帯域幅）とカーネルの性質（演算強度）だけから性能の上限を見積もれるので、CPU だけでなく GPU やアクセラレーターの性能を分析するときにも広く使われています。実際には、キャッシュの階層ごとに帯域幅の異なる複数の屋根を描くこともあります。

4.9. この章のまとめ

  • 性能は実行時間の逆数です。レイテンシ（1 つの処理にかかる時間）とスループット（単位時間あたりの処理量）を区別して考えます。

  • CPU 時間は「命令数 × CPI × クロック周期」で表されます。3 つの要因はアルゴリズム、コンパイラ、ISA、マイクロアーキテクチャ、製造技術の影響を受け、互いにトレードオフの関係にあります。比較では 3 つの積だけが意味を持ちます。

  • MIPS は命令数を無視するため、性能と逆転することがあります。FLOPS は、ピーク性能か実測か、どの精度かを確認する必要があります。

  • ベンチマークの比の平均には幾何平均を使います。算術平均では基準の選び方で結論が変わります。

  • アムダールの法則 \(S = 1 / ((1 - f) + f / s)\) は、改良できない部分が全体の速度向上の上限を決めることを示します。問題を大きくする場合はグスタフソンの法則で考えます。

  • 動的電力は \(\alpha C V^2 f\) に比例し、静的電力はリーク電流によって生じます。デナード・スケーリングの終わりによって電力の壁が生じ、マルチコアやアクセラレーターへの転換が起きました。

  • ルーフラインモデル \(P = \min(P_{\text{peak}}, B \times I)\) を使うと、カーネルがメモリ律速か演算律速かを判断でき、性能の上限を見積もれます。
