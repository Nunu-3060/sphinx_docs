11. 命令レベル並列性

「パイプライン」のパイプラインは、理想的には 1 サイクルに 1 命令を完了させ、CPI を 1 に近づけます。現代の高性能プロセッサは、さらに 1 サイクルに複数の命令を発行し、命令の順序を入れ替え、分岐の結果を待たずに先の命令を実行することで、CPI を 1 より小さく（IPC を 1 より大きく）しています。この章では、プログラムに含まれる命令どうしの並列性である命令レベル並列性と、それを引き出すためのハードウェアの技術を学びます。

まず、パイプラインを命令で満たし続けるために欠かせない分岐予測を詳しく説明します。次に、スーパースカラ、Tomasulo のアルゴリズムによる動的スケジューリング、レジスタリネーミング、リオーダーバッファと投機実行という、アウトオブオーダー実行を支える仕組みを順に組み立てます。最後に、VLIW と SMT という別のアプローチ、ILP の限界、そしてソフトウェアを書く側への示唆を述べます。

11.1. 命令レベル並列性とは

次の 3 つの命令を考えます。

1add  x1, x2, x3
2sub  x4, x5, x6
3mul  x7, x1, x4

1 行目と 2 行目は互いに依存しないので、同時に実行できます。3 行目は両方の結果を使うので、それらの後でなければ実行できません。このように、プログラム中の命令のうち同時に実行できるものがどれだけあるかを命令レベル並列性（Instruction-Level Parallelism：ILP）と呼びます。

ILP を制限するのは、命令間の依存関係です。「パイプライン」で説明したデータの依存（RAW）のほかに、分岐命令の結果によって実行するかどうかが決まる制御依存（control dependence）があります。整数のプログラムでは、およそ 5〜7 命令に 1 回の割合で分岐が現れることが多く、分岐で区切られた直線的な命令列（基本ブロック、basic block）の中だけでは、引き出せる ILP はわずかです。多くの ILP を引き出すには、分岐を越えて先の命令を実行する必要があり、そのためには分岐の結果を正確に予測することが欠かせません。

ILP を引き出す方法は、大きく 2 つに分けられます。

  • ハードウェアが実行時に依存関係を調べ、実行できる命令から実行する（動的スケジューリング）。現代の汎用プロセッサの主流です。

  • コンパイラがコンパイル時に命令を並べ替え、同時に実行できる命令を明示する（静的スケジューリング）。VLIW がこの方式です。

11.2. 分岐予測

分岐命令の結果を、その分岐が実行される前に予測する仕組みを分岐予測（branch prediction）と呼びます。予測には、分岐の方向（成立か不成立か）の予測と、分岐先アドレスの予測の 2 つが必要です。

11.2.1. 静的予測

プログラムの実行中に変化しない規則で予測する方式を静的予測（static prediction）と呼びます。

  • 常に不成立と予測する。次の命令をそのままフェッチすればよいので、ハードウェアが最も簡単です。

  • 常に成立と予測する。ループの末尾の分岐は大部分が成立するので、不成立と予測するより当たることが多いです。

  • 後ろ向きの分岐（分岐先のアドレスが分岐命令より前）は成立、前向きの分岐は不成立と予測する（BTFN：Backward Taken, Forward Not taken）。ループの末尾の分岐は後ろ向きなので、ループに強い方式です。

コンパイラがプロファイル情報などをもとに、よく通る側を分岐しない側（fall-through）に並べ替えることも、静的予測と組み合わせてよく使われます。

11.2.2. 1 ビットと 2 ビットの飽和カウンタ

実行時の履歴を使って予測する方式を動的予測（dynamic prediction）と呼びます。最も簡単なものは、分岐命令のアドレスの下位ビットで引く表（分岐履歴テーブル、branch history table）に、その分岐が前回成立したかどうかを 1 ビットで記録し、次も同じ結果になると予測する方式です。

1 ビットの予測器には、ループを 1 回実行し終えるたびに 2 回ずつ予測を外すという弱点があります。10 回まわるループの末尾の分岐は「成立 9 回、不成立 1 回」を繰り返します。ループを抜けるときの不成立で 1 回外れ、記録が「不成立」に変わるので、次にループに入って最初の成立でもう 1 回外れます。的中率は 80% です。

この弱点を改善したのが2 ビット飽和カウンタ（2-bit saturating counter）です。0〜3 の値をとるカウンタを分岐ごとに持ち、成立したら 1 増やし（3 で止まる）、不成立なら 1 減らします（0 で止まる）。カウンタが 2 以上なら成立、1 以下なら不成立と予測します。予測を変えるには 2 回続けて外れる必要があるので、ループを抜けるときの 1 回の不成立では予測が変わらず、上のループの的中率は 90% になります。

11.2.3. 相関分岐予測と gshare

分岐の結果は、ほかの分岐の結果と関係していることがよくあります。次の C のコードでは、1 つ目と 2 つ目の if が成立したら、3 つ目の if の条件は必ず偽になります。

1if (a == 2) a = 0;
2if (b == 2) b = 0;
3if (a != b) { /* ... */ }

分岐ごとの履歴だけを見る 2 ビットカウンタでは、このような分岐間の関係を利用できません。そこで、直近の分岐の結果（成立を 1、不成立を 0）をシフトレジスタに並べた大域分岐履歴（global branch history）を使い、履歴ごとに別のカウンタを使って予測する方式が考えられました。これを相関分岐予測（correlating branch prediction）や 2 レベル適応型分岐予測と呼びます。

その代表的な実装が、1993 年にマクファーリング（Scott McFarling）が発表したgshareです。gshare は、分岐命令のアドレスと大域分岐履歴の排他的論理和（XOR）で 2 ビットカウンタの表を引きます。

\[\text{添字} = (\text{分岐命令のアドレス} \oplus \text{大域分岐履歴}) \bmod \text{表の大きさ}\]

XOR を使うことで、表の大きさを増やさずに、アドレスと履歴の両方の情報を添字に反映できます。gshare は、ループの回数のような規則的なパターンも、履歴の長さが足りれば学習できます。

11.2.4. 分岐先バッファとリターンアドレススタック

方向を予測できても、分岐先のアドレスが分からなければ、次のサイクルに分岐先の命令をフェッチできません。分岐先のアドレスは命令をデコードしないと分からないからです。そこで、IF 段で PC を使って引く小さなキャッシュに、過去に分岐した命令のアドレスと分岐先アドレスの組を記録しておきます。これを分岐先バッファ（Branch Target Buffer：BTB）と呼びます。PC が BTB にヒットし、方向の予測が成立なら、次のサイクルには BTB に記録された分岐先から命令をフェッチします。BTB は、関数ポインタや仮想関数の呼び出しのような間接分岐の分岐先の予測にも使われます。

関数からの戻り（RISC-V では jalr x0, 0(ra)、擬似命令 ret）は、呼び出し元によって戻り先が変わるので、BTB では当てにくい分岐です。そこで、関数呼び出しのたびに戻りアドレスをプッシュし、戻り命令のときにポップして予測に使う小さなスタックを持ちます。これをリターンアドレススタック（Return Address Stack：RAS）と呼びます。呼び出しの深さがスタックのエントリ数以内であれば、戻り先をほぼ確実に当てられます。

11.2.5. 現代の分岐予測器

現代の高性能プロセッサは、さらに高度な予測器を使っています。長さの異なる複数の履歴で引いた表を組み合わせる TAGE 系の予測器や、パーセプトロン（単純なニューラルネットワーク）を使う予測器が知られています。製品の予測器の詳細は公開されていないことが多いですが、一般的なプログラムで 95% を大きく超える的中率を達成していると考えられています。

11.2.6. 分岐予測ミスのペナルティ

予測が外れると、予測に従ってフェッチ・実行した命令をすべて捨てて、正しい分岐先からやり直します。このとき失うサイクル数を分岐予測ミスのペナルティ（branch misprediction penalty）と呼びます。深いパイプラインを持つ現代のプロセッサでは、ペナルティは 15〜20 サイクル程度になります。分岐予測ミスによる CPI の増加は次の式で求められます。

\[\Delta\text{CPI} = \text{分岐の割合} \times \text{予測ミス率} \times \text{ペナルティ}\]

数値例として、命令の 20% が分岐、予測の的中率が 95%、ペナルティが 15 サイクルとします。

\[\Delta\text{CPI} = 0.20 \times 0.05 \times 15 = 0.15\]

1 サイクルに 4 命令を完了できるプロセッサの理想的な CPI は 0.25 なので、0.15 の増加は CPI を 0.40 に、つまり性能を 0.25 / 0.40 = 0.625 倍に下げます。的中率が 99% なら増加は 0.03 で、CPI は 0.28 です。1 サイクルに多くの命令を実行するプロセッサほど、わずかな的中率の差が大きく効くことが分かります。

11.2.7. サンプル：分岐予測器の比較

常に成立と予測する方式、1 ビット、2 ビット飽和カウンタ、gshare の 4 つの予測器に同じ分岐列を与え、的中率を比べるサンプルです。

リスト 11.1 branch_predictor.py

  2
  3常に成立と予測する方式、1 ビットカウンタ、2 ビット飽和カウンタ、
  4gshare の 4 つの予測器に同じ分岐列を与え、的中率を表にして表示します。

 17class Predictor:
 18    """分岐予測器の基底クラス（常に成立と予測する）。"""
 19
 20    name = "常に成立"
 21
 22    def predict(self, pc: int) -> bool:
 23        """アドレス pc の分岐が成立するかを予測する。"""
 24        return True
 25
 26    def update(self, pc: int, taken: bool) -> None:
 27        """実際の結果 taken で内部状態を更新する。"""
 28
 29
 30class OneBit(Predictor):
 31    """前回の結果をそのまま予測に使う 1 ビットの予測器。"""
 32
 33    name = "1 ビット"
 34
 35    def __init__(self, bits: int = 10) -> None:
 36        self.mask = (1 << bits) - 1
 37        self.table = [True] * (1 << bits)
 38
 39    def predict(self, pc: int) -> bool:
 40        return self.table[(pc >> 2) & self.mask]
 41
 42    def update(self, pc: int, taken: bool) -> None:
 43        self.table[(pc >> 2) & self.mask] = taken
 44
 45
 46class TwoBit(Predictor):
 47    """2 ビット飽和カウンタ（0, 1: 不成立と予測、2, 3: 成立と予測）。"""
 48
 49    name = "2 ビット"
 50
 51    def __init__(self, bits: int = 10) -> None:
 52        self.mask = (1 << bits) - 1
 53        self.table = [2] * (1 << bits)  # 初期値は「弱く成立」
 54
 55    def index(self, pc: int) -> int:
 56        """カウンタ表の添字を求める。"""
 57        return (pc >> 2) & self.mask
 58
 59    def predict(self, pc: int) -> bool:
 60        return self.table[self.index(pc)] >= 2
 61
 62    def update(self, pc: int, taken: bool) -> None:
 63        i = self.index(pc)
 64        if taken:
 65            self.table[i] = min(self.table[i] + 1, 3)
 66        else:
 67            self.table[i] = max(self.table[i] - 1, 0)
 68
 69
 70class Gshare(TwoBit):
 71    """大域分岐履歴とアドレスの XOR で 2 ビットカウンタを選ぶ予測器。"""
 72
 73    name = "gshare"
 74
 75    def __init__(self, bits: int = 10) -> None:
 76        super().__init__(bits)
 77        self.history = 0  # 直近の分岐結果（1 = 成立）を並べたビット列
 78
 79    def index(self, pc: int) -> int:
 80        return ((pc >> 2) ^ self.history) & self.mask
 81
 82    def update(self, pc: int, taken: bool) -> None:
 83        super().update(pc, taken)  # 履歴を更新する前の添字で更新する
 84        self.history = ((self.history << 1) | int(taken)) & self.mask

 88    """全角文字を幅 2 として、text を幅 width にそろえる。"""

113        "乱数 50% 成立": [(0x500, rng.random() < 0.5) for _ in range(n)],

118    """分岐列 trace に対する予測器 pred の的中率を返す。"""
119    hits = 0
120    for pc, taken in trace:
121        hits += pred.predict(pc) == taken
122        pred.update(pc, taken)
123    return hits / len(trace)

  • 30〜43 行目の OneBit は、アドレスの下位ビット（命令は 4 バイト単位なので 2 ビット右にずらしたもの）で表を引き、前回の結果をそのまま予測にします。

  • 95〜114 行目で、ループ、交互、相関あり、乱数の 5 種類の分岐列を作ります。「相関あり」は、乱数で決まる分岐の直後に、同じ条件で決まる分岐があるパターンです（104〜107 行目）。

3交互                 50.0%      0.0%     50.0%    100.0%
4相関あり             49.8%     50.5%     50.7%     74.6%

11.3. スーパースカラ

1 サイクルに複数の命令をフェッチ・デコード・発行し、複数の演算器で同時に実行するプロセッサをスーパースカラ（superscalar）プロセッサと呼びます。1 サイクルに最大 \(w\) 命令を発行できるとき、\(w\) を発行幅と呼び、理想的な CPI は \(1/w\) になります。CPI が 1 より小さくなると扱いにくいので、その逆数である IPC（Instructions Per Cycle：1 サイクルあたりの実行命令数。「性能の測り方」を参照）がよく使われます。

スーパースカラを実現するには、複数の命令を同時にフェッチ・デコードする回路、複数の演算器、多くの読み出し・書き込みポートを持つレジスタファイル、そして同時に発行する命令どうしの依存関係を調べる回路が必要です。依存関係の検査は、同時に発行する命令の組すべてについて行うので、発行幅の 2 乗に比例して複雑になります。

命令をプログラムの順に発行するインオーダーのスーパースカラでは、先頭の命令がデータを待ってストールすると、その後ろの独立な命令も発行できません。たとえば、キャッシュミスしたロードの値を待つ命令の後ろに、ロードと無関係な命令が何十個も並んでいても、それらは待たされます。この問題を解決するのが、次に述べる動的スケジューリングです。現代の高性能プロセッサは、1 サイクルに 4〜8 命令程度をデコードするアウトオブオーダーのスーパースカラです。

11.4. 動的スケジューリングとアウトオブオーダー実行

命令をプログラムの順に取り込み（発行し）、オペランドがそろった命令からプログラムの順序と関係なく実行する方式を動的スケジューリング（dynamic scheduling）、またはその実行をアウトオブオーダー実行（out-of-order execution）と呼びます。

最初に動的スケジューリングを本格的に実装したのは、1964 年に出荷された CDC 6600 のスコアボード（scoreboard）です（「アーキテクチャの歴史」）。スコアボードは各演算器とレジスタの状態を一元的に管理し、RAW の依存がなくなった命令から実行を始めます。ただし、WAR や WAW のハザードがあると、命令の実行開始や結果の書き込みを待たせるしかありませんでした。

11.4.1. Tomasulo のアルゴリズム

1967 年、IBM のロバート・トマスロ（Robert Tomasulo）は、IBM System/360 Model 91 の浮動小数点演算装置のために、WAR と WAW のハザードもハードウェアで解消する方式を発表しました。これをTomasulo のアルゴリズム（Tomasulo's algorithm）と呼びます。その主な構成要素は次の 2 つです。

リザベーションステーション（reservation station）

演算器の前に置く、命令の待合室です。発行された命令は、空いているリザベーションステーションに入り、オペランドの値がそろうのを待ちます。オペランドの値がまだできていない場合は、値の代わりに「その値を作る命令がいるリザベーションステーションの番号」（タグ、tag）を記録します。

共通データバス（Common Data Bus：CDB）

演算器が計算した結果を、タグとともにすべてのリザベーションステーションとレジスタファイルに一斉に送るバスです。自分が待っているタグの値が CDB に流れてきたら、各リザベーションステーションはその値を取り込みます。

命令の処理は次の 3 段階からなります。

  1. 発行（issue）：命令をプログラムの順に取り出し、空いているリザベーションステーションに入れます。ソースレジスタの値が使えればその値を、まだ計算中ならそれを作るリザベーションステーションのタグを記録します。そして、宛先レジスタの状態表に「このレジスタの最新の値は、このリザベーションステーションが作る」と記録します。

  2. 実行（execute）：オペランドの値がすべてそろったら演算器で実行します。命令の順序とは関係なく、そろったものから実行します。

  3. 結果の書き込み（write result）：演算結果をタグとともに CDB に流します。待っていたリザベーションステーションと、そのタグを最新として記録しているレジスタがその値を受け取ります。

発行のときにソースレジスタの値（またはタグ）を読み取ってしまうので、後の命令が同じレジスタに書き込んでも（WAR）、すでに読んだ値は影響を受けません。また、レジスタの状態表は常に「最後に発行された書き込み命令」を指すので、古い命令が後から結果を書いても（WAW）、レジスタの最新の値を上書きしません。つまり、リザベーションステーションのタグが、次に説明するレジスタリネーミングの役割を果たしています。

一方、この実行では命令が完了する順序がプログラムの順序と異なります。もし fdiv.d がゼロ除算などの例外を起こしたら、その後ろの fadd.d はすでにレジスタに結果を書いてしまっています。この問題を解決するのが、後で説明するリオーダーバッファです。

11.5. レジスタリネーミング

WAR と WAW は、同じレジスタ名を使い回したことによる見かけ上の依存（名前依存）なので、名前を付け替えれば取り除けます。これをレジスタリネーミング（register renaming）と呼びます。次の例では、2 行目が読む f8 に 3 行目が書くので WAR、2 行目と 4 行目がともに f6 に書くので WAW の依存があります。

1fdiv.d  f0, f2, f4
2fadd.d  f6, f0, f8
3fsub.d  f8, f10, f14
4fmul.d  f6, f10, f8

宛先レジスタを、ISA のレジスタ（論理レジスタ、アーキテクチャレジスタ）とは別に用意した多数の物理レジスタ（physical register）に割り当て直すと、次のようになります（物理レジスタを p で表します）。

1fdiv.d  p1, f2, f4
2fadd.d  p2, p1, f8
3fsub.d  p3, f10, f14
4fmul.d  p4, f10, p3

fsub.d の書き込み先は p3 になり、fadd.d が読む f8（元の物理レジスタ）とは別物になったので WAR は消えます。同様に、fadd.d と fmul.d の書き込み先も p2 と p4 に分かれ、WAW も消えます。残るのは本物の依存（RAW）だけです。

現代のプロセッサは、論理レジスタ番号から物理レジスタ番号への対応表（リネームテーブル、register alias table とも呼ばれます）と、空いている物理レジスタの一覧（フリーリスト）を持ち、デコードの直後にすべての命令をリネームします。物理レジスタは論理レジスタよりずっと多く、整数用・浮動小数点数用それぞれ百数十〜数百個程度を持つのが一般的です。

11.6. リオーダーバッファとインオーダーコミット

アウトオブオーダー実行では、命令はばらばらの順序で完了します。しかし、プログラムから見える状態（レジスタとメモリの内容）は、命令がプログラムの順に 1 つずつ実行されたかのように変化しなければなりません。そこで、命令の実行の完了と、結果をプログラムから見える状態に反映することを分けます。後者をコミット（commit）またはリタイア（retire）と呼びます。

リオーダーバッファ（Reorder Buffer：ROB）は、発行した命令をプログラムの順に並べて保持する循環バッファです。命令は発行時に ROB の末尾に入り、実行を終えると ROB に結果を記録します。ROB の先頭の命令が実行を終えていれば、その結果をレジスタやメモリに反映して ROB から取り除きます。これをインオーダーコミット（in-order commit）と呼びます。命令の処理は次のように流れます。

ストア命令も、コミットするまではメモリに書かず、ストアバッファ（store buffer）に保持します。後続のロードがストアバッファにある同じアドレスのデータを読む場合は、ストアバッファから値を受け取ります。ROB のエントリ数は、アウトオブオーダー実行で命令の順序を入れ替えられる範囲（命令ウィンドウ）の大きさを決めます。現代の高性能コアの ROB は数百エントリ程度です。

11.7. 投機実行

ROB があれば、分岐予測に従って分岐の先の命令を、分岐の結果が決まる前に実行できます。これを投機実行（speculative execution）と呼びます。投機的に実行した命令の結果は ROB の中にとどまり、分岐の予測が正しかったと確定してからコミットされます。予測が外れていたら、その分岐より後ろの ROB のエントリをすべて捨て、リネームテーブルを分岐の時点の状態に戻して、正しい分岐先からやり直します。プログラムから見える状態は変わっていないので、予測が外れても結果は正しく保たれます。

投機実行によって、ハードウェアは分岐をまたいで何百命令も先まで見通し、キャッシュミスしたロードの待ち時間の間に、後ろの独立な命令を実行できます。ただし、捨てた命令もキャッシュなどのマイクロアーキテクチャの状態には痕跡を残します。これを悪用した攻撃が Spectre で、「セキュリティと信頼性」で説明します。

11.8. 正確な例外

「プロセッサの設計」で述べたように、例外を起こした命令より前の命令はすべて完了し、その命令と後の命令はまったく実行されていないかのような状態で例外処理に入ることを正確な例外と呼びます。正確な例外であれば、OS は例外の原因を取り除いた後（たとえばページフォールトでページを読み込んだ後）、その命令から実行を再開できます。

ROB を持つプロセッサでは、命令が例外を起こしても、その場では ROB に「例外あり」と記録するだけにします。その命令が ROB の先頭に来てコミットされるときに初めて例外を処理し、後ろの命令をすべて捨てます。こうすれば、例外は必ずプログラムの順序で、正確に処理されます。投機的に実行した命令が例外を起こしても、その命令が予測ミスで捨てられれば例外は起こらなかったことになります。

11.9. VLIW

依存関係の検査と命令の並べ替えをコンパイラに任せ、同時に実行できる複数の操作を 1 つの長い命令にまとめる方式をVLIW（Very Long Instruction Word）と呼びます。たとえば、1 命令に整数演算 2 つ、浮動小数点演算 2 つ、メモリアクセス 2 つ、分岐 1 つ分の「スロット」を持たせ、コンパイラが各スロットを埋めます。埋められないスロットには nop を置きます。

VLIW はハードウェアを単純にできる一方、次のような課題があります。

  • 同時に実行できる操作が見つからないと nop が増え、コードが大きくなります。

  • キャッシュミスのように実行時にしか分からない遅延にコンパイラが対応できず、全体が止まりやすくなります。

  • 演算器の数や遅延が変わると再コンパイルが必要になり、世代間でのバイナリの互換性を保ちにくくなります。

1980 年代の Multiflow などを経て、Intel と HP は VLIW の考え方を発展させた EPIC（Explicitly Parallel Instruction Computing）に基づく IA-64 を開発し、2001 年に Itanium として製品化しました。しかし、汎用プロセッサの市場ではアウトオブオーダー実行の x86 系に及ばず、Itanium は姿を消しました。一方、実行時の挙動が予測しやすい信号処理向けの DSP などでは、VLIW が今も広く使われています。

11.10. SMT（同時マルチスレッディング）

1 つのスレッドだけでは、依存関係やキャッシュミスのために、スーパースカラの演算器をすべて埋めることはまれです。そこで、1 つのコアで複数のスレッドの命令を同時に発行し、空いている演算器を別のスレッドの命令で埋める方式をSMT（Simultaneous Multithreading：同時マルチスレッディング）と呼びます。

SMT では、スレッドごとに PC と論理レジスタの状態（リネームテーブル）を持ち、演算器、キャッシュ、物理レジスタ、ROB などはスレッド間で共有します。アウトオブオーダー実行の仕組みがもともと「命令の出どころによらず、オペランドのそろった命令から実行する」ものなので、少ない追加のハードウェアで実現できます。Intel は 2002 年に Pentium 4 系の Xeon で、SMT をハイパースレッディング（Hyper-Threading）の名前で導入しました。現在の x86-64 のプロセッサや IBM の POWER などが SMT を備えています。

SMT による性能向上は、プログラムによって大きく異なります。演算器やメモリ帯域の使い方が異なるスレッドの組み合わせでは効果がありますが、同じ資源を奪い合うスレッドどうしでは効果が小さく、キャッシュの取り合いでかえって遅くなることもあります。2 スレッドの SMT で 2 倍の性能になるわけではありません。

11.11. ILP の限界

ハードウェアを大きくすれば、ILP はいくらでも引き出せるわけではありません。限界をもたらす主な要因は次のとおりです。

  • プログラム自体に含まれる並列性：本物の依存（RAW）の連鎖は、どんな技術でも短くできません。

  • 分岐予測の精度：命令ウィンドウを大きくしても、その中に予測ミスがあれば後ろの命令は捨てられます。

  • メモリのレイテンシ：主記憶へのアクセスには数百サイクルかかり、その間を埋めるだけの独立な命令が見つかりません（「メモリ階層とキャッシュ」で説明します）。

  • ハードウェアの複雑さ：発行幅や命令ウィンドウを大きくすると、依存関係の検査、リネーム、CDB への結果の配布などの回路が急速に複雑になり、クロック周波数と消費電力に悪影響を与えます。

1990 年代から 2000 年代の初めにかけて、プロセッサは発行幅の拡大とパイプラインの深化で ILP を追求しました。しかし、得られる性能に対して消費電力と回路の複雑さが見合わなくなり、2000 年代半ば以降は、1 つのチップに複数のコアを載せてスレッドレベルの並列性を使う方向へ転換しました。これは「並列アーキテクチャ」のテーマです。

11.12. ソフトウェアへの示唆

ILP を引き出すハードウェアは、ソフトウェアの書き方によって効果が大きく変わります。

11.12.1. 予測しにくい分岐を避ける

次の関数は、配列の要素のうち 128 以上のものの合計を求めます。

 1long sum_large(const unsigned char *data, int n)
 2{
 3    long sum = 0;
 4    for (int i = 0; i < n; i++) {
 5        if (data[i] >= 128) {  /* 予測しにくい分岐 */
 6            sum += data[i];
 7        }
 8    }
 9    return sum;
10}

data の値が 0〜255 の乱数なら、5 行目の分岐は約半分の確率で成立し、どの予測器でも半分近くを外します。ところが、同じデータをあらかじめソートしておくと、分岐は前半ではずっと不成立、後半ではずっと成立となり、ほぼ完全に予測できるようになります。このため、ソート済みのデータに対しては、同じ計算が何倍も速くなることがあります。

分岐をなくす書き方もあります。5〜7 行目を次のように書き換えると、条件によらず同じ命令を実行するので、分岐予測ミスは起こりません。

1sum += (data[i] >= 128) ? data[i] : 0;

コンパイラは、このようなコードを条件付き転送命令（x86-64 の cmov など）や、比較結果のビット演算で分岐のない機械語に変換できます。ただし、コンパイラの最適化によって元のコードでもすでに分岐のない機械語になっていることもあるので、実際の効果は計測して確かめる必要があります。

11.12.2. 依存の連鎖を短くする

配列の合計を 1 つの変数 sum に足し込むループでは、すべての加算が直前の加算の結果に依存します。浮動小数点数の加算のレイテンシが 4 サイクルなら、アウトオブオーダー実行のプロセッサでも 4 サイクルに 1 回しか加算できません。合計を 4 つの変数に分けて足し込み、最後に合計すれば、4 つの独立な依存の連鎖ができ、加算器を休まず使えます。浮動小数点数の加算は結合法則が厳密には成り立たないので、コンパイラは指示がない限りこの変換を自動では行いません。

11.13. この章のまとめ

  • 命令レベル並列性（ILP）は、同時に実行できる命令がどれだけあるかを表します。ILP を制限するのはデータの依存と制御依存です。

  • 分岐予測には静的予測と動的予測があります。2 ビット飽和カウンタはループの分岐に強く、gshare は大域分岐履歴を使って分岐間の相関やパターンを学習します。

  • 分岐先は BTB、関数の戻り先はリターンアドレススタックで予測します。現代の予測器には TAGE 系などがあります。

  • 分岐予測ミスによる CPI の増加は「分岐の割合 × 予測ミス率 × ペナルティ」で、発行幅の大きいプロセッサほど影響が大きくなります。

  • スーパースカラは 1 サイクルに複数の命令を発行し、IPC を 1 より大きくします。

  • Tomasulo のアルゴリズムは、リザベーションステーションと共通データバスにより、オペランドのそろった命令から実行します。

  • レジスタリネーミングは、論理レジスタを物理レジスタに割り当て直して、WAR と WAW の名前依存を取り除きます。

  • リオーダーバッファにより、アウトオブオーダーに実行した命令をプログラムの順にコミットし、投機実行と正確な例外を実現します。

  • VLIW は並列性の発見をコンパイラに任せる方式で、汎用プロセッサでは主流になりませんでしたが、DSP などで使われています。

  • SMT は、1 つのコアで複数のスレッドの命令を同時に実行し、空いている演算器を活用します。

  • ILP には限界があり、性能向上の主役はマルチコアによるスレッドレベルの並列性へ移りました。

  • 予測しにくい分岐を避けることや、依存の連鎖を短くすることで、ソフトウェアは ILP をより引き出せます。
