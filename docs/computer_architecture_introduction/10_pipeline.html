10. パイプライン

「プロセッサの設計」で設計した単一サイクルのプロセッサは、1 命令の処理を 1 クロックサイクルで終えます。このため、クロック周期は最も時間のかかる命令（ロード命令）に合わせて長くせざるを得ず、回路の大部分はほとんどの時間に遊んでいます。この章では、命令の処理をいくつかの段に分け、複数の命令を少しずつずらして同時に処理するパイプライン（pipeline）を学びます。

パイプラインは、現代のほぼすべてのプロセッサが使っている基本的な高速化の手法です。まず洗濯の例えで考え方をつかみ、RISC-V の 5 段パイプラインを具体的に組み立てます。次に、パイプラインの流れを乱すハザード（hazard）の種類と、それを解消するフォワーディングやストールの仕組みを説明します。最後に、パイプラインの性能を CPI で評価し、パイプラインを深くすることの得失を考えます。

10.1. 洗濯の例え

洗濯物を「洗う」「乾かす」「たたむ」「しまう」の 4 つの作業で片付ける場合を考えます。各作業に 30 分かかり、洗濯物が 4 回分あるとします。1 回分の洗濯物をすべての作業が終わるまで片付けてから次の洗濯物に取りかかると、1 回分に 2 時間、4 回分で 8 時間かかります。

ところが、1 回目の洗濯物を乾燥機に入れたら、すぐに 2 回目の洗濯物を洗濯機に入れることができます。このように各作業を担当する装置を同時に動かすと、30 分ごとに 1 回分の洗濯物が片付くようになり、4 回分は 3.5 時間で終わります。1 回分の洗濯物にかかる時間（2 時間）は変わらないのに、全体としての処理の速さが上がっている点が重要です。

パイプラインは、個々の命令のレイテンシ（latency：1 つの処理の開始から終了までの時間）を短くするのではなく、スループット（throughput：単位時間あたりに完了する処理の数）を高める技術です。洗濯物が十分に多ければ、作業の数（段数）が 4 なので、処理の速さはほぼ 4 倍に近づきます。

10.2. RISC-V の 5 段パイプライン

RISC-V の基本的な整数命令の処理は、次の 5 つの段（stage）に分けることができます。これは「プロセッサの設計」で見た命令実行の 5 段階をそのまま段にしたもので、ヘネシーとパターソンの教科書で用いられている古典的な構成です。

処理の内容

ID

各段の間には、前の段の結果を次のクロックまで保持するパイプラインレジスタ（pipeline register）を置きます。パイプラインレジスタは、IF/ID、ID/EX、EX/MEM、MEM/WB のように、両側の段の名前を並べて呼びます。命令はクロックごとにパイプラインレジスタからパイプラインレジスタへと 1 段ずつ進み、それぞれの段は別々の命令を同時に処理します。

命令の種類によっては使わない段もあります。たとえば add は MEM 段で何もせず、ストア命令 sw は WB 段で何もしません。それでも、すべての命令が同じ 5 段を同じ順に通るようにそろえると、段どうしの資源の取り合いが起きにくくなり、制御が簡単になります。RISC-V の命令が 32 ビットの固定長で、ソースレジスタの番号のフィールド位置が命令形式によらず同じなのは、IF と ID を単純にしてパイプライン化しやすくするためでもあります。

10.4. 理想的な速度向上

段数を \(k\)、命令数を \(n\) とします。各段の処理時間が等しく 1 サイクルであれば、最初の命令が完了するまでに \(k\) サイクル、その後は 1 サイクルに 1 命令ずつ完了するので、全体のサイクル数は \(k + (n - 1)\) です。パイプラインを使わずに 1 命令ずつ \(k\) サイクルかけて処理する場合と比べた速度向上は次のとおりです。

\[\text{速度向上} = \frac{n k}{k + n - 1} \;\longrightarrow\; k \quad (n \to \infty)\]

命令数が十分に多ければ、速度向上は段数 \(k\) に近づきます。ただし、実際には次の理由で段数どおりにはなりません。

  • 各段の処理時間がそろわず、クロック周期は最も遅い段で決まります。

  • パイプラインレジスタの遅延とクロックのばらつき（スキュー）が、各段に上乗せされます。

  • ハザードによってパイプラインが止まります（ストールします）。

数値例で確かめます。単一サイクルの実装で、各段に相当する回路の遅延が IF 200 ps、ID 100 ps、EX 200 ps、MEM 200 ps、WB 100 ps だとします。単一サイクルの実装ではクロック周期は合計の 800 ps です。パイプライン化すると、クロック周期は最も遅い段の 200 ps にパイプラインレジスタの遅延（ここでは 20 ps とします）を加えた 220 ps になります。ハザードがなければ 1 命令あたりの時間は 800 ps から 220 ps になり、速度向上は約 3.6 倍で、段数の 5 倍には届きません。

10.5. パイプラインハザード

次のサイクルで次の命令を予定どおり実行できなくなる状況をパイプラインハザード（pipeline hazard）と呼びます。ハザードは原因によって 3 種類に分けられます。

原因

主な対策

10.5.1. 構造ハザード

命令とデータが 1 つのメモリにあり、そのメモリに 1 サイクルに 1 回しかアクセスできないとします。すると、ロード命令が MEM 段でデータを読むサイクルに、後続の命令の IF 段が命令を読めなくなります。これが構造ハザード（structural hazard）です。現代のプロセッサでは、L1 キャッシュを命令キャッシュとデータキャッシュに分けることで、この構造ハザードを避けています。キャッシュの階層では命令とデータを分けたハーバード型、主記憶ではノイマン型という構成です。

レジスタファイルも、ID 段の読み出しと WB 段の書き込みが同じサイクルに起こります。読み出しポートを 2 つ、書き込みポートを 1 つ用意したうえで、サイクルの前半で書き込み、後半で読み出すように設計すると、同じサイクルに WB で書いた値を ID で読めます。本章のパイプライン図とサンプルは、この設計を前提にしています。

10.5.2. データハザード：RAW・WAR・WAW

命令どうしのデータの依存関係によって起こるハザードをデータハザード（data hazard）と呼びます。先行する命令 i と後続の命令 j の関係によって、次の 3 種類があります。

表 10.4 データハザードの 3 種類

種類

内容

例（i が先、j が後）

RAW（Read After Write）

j が、i が書くレジスタを読みます。真の依存（true dependence）。

i: add x1, x2, x3 / j: sub x4, x1, x5

WAR（Write After Read）

j が、i が読むレジスタを書きます。逆依存（anti-dependence）。

i: sub x4, x1, x5 / j: add x1, x2, x3

WAW（Write After Write）

j が、i が書くのと同じレジスタを書きます。出力依存（output dependence）。

i: add x1, x2, x3 / j: lw x1, 0(x10)

RAW は、値の受け渡しそのものなので、本質的な依存です。一方、WAR と WAW は、同じレジスタ名を使い回したために生じる見かけ上の依存で、名前依存（name dependence）とも呼ばれます。本章の 5 段パイプラインでは、命令はプログラムの順に進み、レジスタの読み出しは必ず ID 段、書き込みは必ず WB 段で行うので、WAR と WAW は起こりません。問題になるのは RAW だけです。WAR と WAW は、命令の順序を入れ替えて実行するアウトオブオーダー実行で問題になります。その解決方法であるレジスタリネーミングは「命令レベル並列性」で説明します。

次の命令列を考えます。

1add  x1, x2, x3
2sub  x4, x1, x5
3and  x6, x1, x7

add の結果は WB 段（サイクル 5）でレジスタファイルに書き込まれますが、sub はサイクル 3 の ID 段で x1 を読もうとします。何もしなければ、sub は古い x1 の値を読んでしまいます。ハードウェアで対処しない場合は、sub の ID 段を add の WB 段と同じサイクルまで遅らせる必要があり、2 サイクルのストール（stall）が生じます。ストールとは、後続の命令を止めて、パイプラインに何もしない「泡」（バブル、bubble）を流すことです。

10.6. フォワーディング

よく見ると、add の結果はサイクル 3 の EX 段の終わりにはできあがっています。sub が実際にその値を必要とするのは、サイクル 4 の EX 段の始めです。そこで、レジスタファイルを経由せずに、EX/MEM パイプラインレジスタにある演算結果を、次の命令の ALU の入力へ直接送る経路を設けます。これをフォワーディング（forwarding）またはバイパス（bypassing）と呼びます。

フォワーディングは、ALU の 2 つの入力の前にマルチプレクサを置き、「ID/EX レジスタに読んであった値」「EX/MEM レジスタの値（1 つ前の命令の結果）」「MEM/WB レジスタの値（2 つ前の命令の結果）」の中から選ぶことで実現します。選択を決めるフォワーディングユニット（forwarding unit）は、たとえば 1 つ目の入力について次の条件を調べます。

1if (EX/MEM.RegWrite and EX/MEM.rd != 0 and EX/MEM.rd == ID/EX.rs1)
2    ALU 入力 1 <- EX/MEM の演算結果
3else if (MEM/WB.RegWrite and MEM/WB.rd != 0 and MEM/WB.rd == ID/EX.rs1)
4    ALU 入力 1 <- MEM/WB の書き込み値
5else
6    ALU 入力 1 <- ID/EX に読んであったレジスタの値

条件 rd != 0 は、RISC-V の x0 が常に 0 で、書き込みが無視されるために必要です。EX/MEM を先に調べるのは、同じレジスタに続けて書く命令があったとき、より新しい値を使うためです。2 つ目の入力（rs2）についても同じ回路を用意します。このフォワーディングにより、上の add、sub、and の命令列はストールなしで実行できます。

10.7. ロード使用ハザードとストール

フォワーディングでもすべてのデータハザードを解消できるわけではありません。ロード命令の値は、MEM 段の終わりにデータメモリから読み出されて初めてできあがります。ロードの直後の命令がその値を使う場合、直後の命令の EX 段の始めには、まだ値がありません。これをロード使用ハザード（load-use hazard）と呼びます。

ストールは ID 段にあるハザード検出ユニット（hazard detection unit）が行います。ID/EX にある命令がロード（MemRead が 1）で、その宛先レジスタが ID 段の命令のソースレジスタと一致したら、次の 2 つを行います。

  • PC と IF/ID レジスタの更新を止め、IF 段と ID 段の命令をその場にとどめます。

  • ID/EX レジスタの制御信号をすべて 0 にして、EX 段以降にバブル（何もしない命令。nop と同じ働き）を送り込みます。

次のサイクルにはロードが MEM 段を終えているので、止めていた命令は通常どおりフォワーディングで値を受け取って EX 段に進みます。

ロード使用ハザードは、コンパイラが命令の順序を入れ替えて避けることもできます。「機械語とプログラム」で紹介した命令スケジューリングです。ロードの直後に、そのロードの結果を使わない別の命令を置けば、ストールは起きません。

10.8. 制御ハザードと分岐の扱い

分岐命令 beq の場合、分岐するかどうか（分岐の成立・不成立）と分岐先のアドレスが決まるのは EX 段です。しかし、IF 段は毎サイクル次の命令を読まなければなりません。分岐の結果が決まる前に、どの命令をフェッチすべきか分からないことを制御ハザード（control hazard）または分岐ハザードと呼びます。

分岐が EX 段で決まる場合、分岐の後ろでフェッチした 2 命令は、分岐が成立したら取り消す（フラッシュ、flush）必要があり、2 サイクルが無駄になります。対策には次のようなものがあります。

ストール

分岐の結果が決まるまでフェッチを止めます。最も単純ですが、分岐のたびに数サイクル失います。分岐の比較を ID 段に移す（レジスタを読んだ直後に専用の比較器で比べる）と、無駄を 1 サイクルに減らせますが、ID 段の遅延が増え、比較に使う値のためのフォワーディングも別に必要になります。

分岐予測

分岐の結果を予測して、予測した側の命令を先にフェッチします。予測が当たれば無駄はなく、外れたらフェッチした命令をフラッシュして正しい側から読み直します。最も単純な予測は「常に不成立と予測する」もので、これは次のアドレスの命令をそのまま読み続けることに相当します。現代のプロセッサは過去の分岐の履歴を使って 95% 以上の的中率を達成することが多く、その仕組みは「命令レベル並列性」で詳しく説明します。

遅延分岐

分岐命令の直後の命令（遅延スロット、delay slot）を、分岐の成否にかかわらず必ず実行すると ISA で定める方式です。コンパイラが遅延スロットに有用な命令を置ければ、無駄はなくなります。MIPS や SPARC などの初期の RISC が採用しました。しかし、パイプラインが深くなったりスーパースカラになったりすると、1 命令分の遅延スロットでは無駄を隠しきれず、マイクロアーキテクチャの都合を ISA に固定してしまう欠点だけが残りました。RISC-V、AArch64 は遅延分岐を採用していません。

例外と割り込みも、制御の流れを変えるという点では制御ハザードの一種です。パイプラインでは、例外を起こした命令より前の命令はすべて完了させ、後の命令はすべて取り消す必要があります。このような例外を正確な例外（「プロセッサの設計」）と呼び、アウトオブオーダー実行でそれを実現する仕組みは「命令レベル並列性」で説明します。

10.9. サンプル：パイプラインのストールの計算

命令列を入力に、フォワーディングなし／ありでのストール数、総サイクル数、CPI を計算し、パイプライン図を表示するサンプルです。各命令は、宛先レジスタの番号、ソースレジスタの番号の組、ロード命令かどうかで表します。分岐による制御ハザードは扱いません。

リスト 10.1 pipeline_sim.py
  1"""5 段パイプラインのストール数とサイクル数を計算するサンプル。
  2
  3命令列（宛先レジスタ、ソースレジスタ、ロード命令かどうか）を入力に、
  4フォワーディングなし／ありの 2 通りでデータハザードによるストール数、
  5総サイクル数、CPI を計算し、パイプライン図をテキストで表示します。
  6分岐命令（制御ハザード）は扱いません。
  7
  8実行方法: python pipeline_sim.py
  9"""
 10
 11from dataclasses import dataclass
 12
 13
 14@dataclass(frozen=True)
 15class Instr:
 16    """パイプラインに流す命令。"""
 17
 18    text: str  # 表示用のアセンブリ
 19    dest: int  # 宛先レジスタ番号（書き込まない命令は 0）
 20    srcs: tuple[int, ...]  # ソースレジスタ番号
 21    is_load: bool = False  # ロード命令なら True
 22
 23
 24def ex_cycles(prog: list[Instr], forwarding: bool) -> list[int]:
 25    """各命令が EX 段を実行するサイクルを返す（1 番目の命令の IF が 1）。"""
 26    ex: list[int] = []
 27    for i, ins in enumerate(prog):
 28        # ハザードがなければ、前の命令の次のサイクルに EX を実行する
 29        t = 3 if i == 0 else ex[i - 1] + 1
 30        for j in range(i - 1, -1, -1):  # 直前の命令から順にさかのぼる
 31            p = prog[j]
 32            if p.dest == 0 or p.dest not in ins.srcs:
 33                continue
 34            if not forwarding:
 35                # 前半で WB、後半で ID の読み出しをするので、
 36                # 生産者の WB（EX + 2）と同じサイクルに ID ができる
 37                t = max(t, ex[j] + 3)
 38            elif p.is_load:
 39                # ロードの値は MEM の終わりにできる
 40                t = max(t, ex[j] + 2)
 41            else:
 42                # ALU の結果は EX の終わりにでき、次の EX へ送れる
 43                t = max(t, ex[j] + 1)
 44            break  # 最も近い生産者だけを見ればよい
 45        ex.append(t)
 46    return ex
 47
 48
 49def diagram(prog: list[Instr], ex: list[int]) -> list[list[str]]:
 50    """各命令の、サイクルごとの段の名前の表を作る。"""
 51    total = ex[-1] + 2  # 最後の命令が WB を終えるサイクル
 52    rows: list[list[str]] = []
 53    # ID に入るサイクル（前の命令が EX に進むサイクル）
 54    id_start = [2] + ex[:-1]
 55    for i in range(len(prog)):
 56        row = [""] * (total + 1)
 57        # 前の命令が ID を出るまでは IF にとどまる
 58        if_start = 1 if i == 0 else id_start[i - 1]
 59        for c in range(if_start, id_start[i]):
 60            row[c] = "IF"
 61        for c in range(id_start[i], ex[i]):
 62            row[c] = "ID"  # ストール中は ID にとどまる
 63        row[ex[i]] = "EX"
 64        row[ex[i] + 1] = "MEM"
 65        row[ex[i] + 2] = "WB"
 66        rows.append(row[1:])
 67    return rows
 68
 69
 70def report(title: str, prog: list[Instr], forwarding: bool) -> None:
 71    """パイプライン図とサイクル数、CPI を表示する。"""
 72    ex = ex_cycles(prog, forwarding)
 73    n = len(prog)
 74    total = ex[-1] + 2
 75    stalls = total - (n + 4)  # 理想は n + 4 サイクル
 76    fw = "あり" if forwarding else "なし"
 77    print(f"--- {title}（フォワーディング{fw}）---")
 78    header = "".join(f"{c:>4}" for c in range(1, total + 1))
 79    print(f"{'命令':<18}{header}")
 80    for ins, row in zip(prog, diagram(prog, ex)):
 81        cells = "".join(f"{s:>4}" for s in row)
 82        # 命令は ASCII 文字だけなので、文字数で桁がそろう
 83        print(f"{ins.text:<20}{cells}".rstrip())
 84    cpi = (n + stalls) / n
 85    print(f"命令数 {n}, ストール {stalls}, 総サイクル {total}, "
 86          f"CPI {cpi:.2f}（パイプラインを満たす 4 サイクルを除く）")
 87    print()
 88
 89
 90def main() -> None:
 91    """ロード使用ハザードを含む命令列と、並べ替えた命令列を比べる。"""
 92    original = [
 93        Instr("lw   x1, 0(x10)", 1, (10,), is_load=True),
 94        Instr("add  x2, x1, x3", 2, (1, 3)),
 95        Instr("sub  x4, x2, x5", 4, (2, 5)),
 96        Instr("sw   x4, 4(x10)", 0, (4, 10)),
 97        Instr("lw   x6, 8(x10)", 6, (10,), is_load=True),
 98        Instr("add  x7, x6, x8", 7, (6, 8)),
 99    ]
100    # 2 つ目のロードを前に移し、ロードの直後に使わないようにする
101    reordered = [original[0], original[4], original[1],
102                 original[2], original[3], original[5]]
103    for forwarding in (False, True):
104        report("元の命令列", original, forwarding)
105    report("並べ替えた命令列", reordered, True)

108if __name__ == "__main__":
109    main()

要点は次のとおりです。

  • 24〜46 行目の ex_cycles が、各命令が EX 段を実行するサイクルを求めます。ハザードがなければ前の命令の次のサイクルです（29 行目）。

  • 30〜44 行目で、ソースレジスタを書く直前の命令（生産者）をさかのぼって探し、その生産者の EX のサイクルから、自分の EX を何サイクル以降にできるかを決めます。フォワーディングなしでは生産者の WB と同じサイクルに ID ができるので EX + 3（37 行目）、フォワーディングありではロードなら EX + 2（40 行目）、それ以外なら EX + 1（43 行目）です。

  • 49〜67 行目の diagram がパイプライン図を作ります。ストール中の命令は ID 段に、その後ろの命令は IF 段にとどまるので、同じ段の名前が続けて表示されます。

  • 75 行目で、理想的なサイクル数 \(n + 4\) との差をストール数とします。CPI はパイプラインを満たすまでの 4 サイクルを除いて求めています（84 行目）。

  • 101〜102 行目では、2 つ目のロードを前に移した命令列を作り、命令スケジューリングの効果を確かめます。

フォワーディングなしでは、依存のある隣り合った命令のたびに 2 サイクルずつストールし、CPI は 2.33 です。フォワーディングを入れると、残るのは 2 か所のロード使用ハザードによる 1 サイクルずつのストールだけになり、CPI は 1.33 に下がります。さらに 2 つ目のロードを前に移すと、どのロードの直後にもその結果を使う命令がなくなり、ストールはゼロになります。lw x6, 8(x10) を sw x4, 4(x10) より前に移せるのは、両者のアドレスが異なることが分かっているからです。アドレスが同じかもしれない場合、コンパイラはロードとストアの順序を入れ替えられません。

10.10. パイプラインの性能と CPI

ストールがなければパイプラインの CPI は 1 です。ストールがある場合の CPI は、1 命令あたりの平均ストールサイクル数を足して求めます。

\[\text{CPI} = 1 + \text{1 命令あたりの平均ストールサイクル数}\]

数値例として、命令の 25% がロード、そのうち 40% の直後にロードの値を使う命令があり（1 サイクルのストール）、命令の 15% が分岐で、分岐予測の外れが分岐の 10% あり、予測が外れると 2 サイクルを失うとします。

\[\text{CPI} = 1 + 0.25 \times 0.4 \times 1 + 0.15 \times 0.1 \times 2 = 1 + 0.10 + 0.03 = 1.13\]

分岐予測を使わずに分岐のたびに 2 サイクルストールする場合は、分岐の項が \(0.15 \times 2 = 0.30\) になり、CPI は 1.40 です。「性能の測り方」の CPU 性能の式（実行時間 = 命令数 × CPI × クロック周期）にあてはめると、パイプライン化の効果は、クロック周期の短縮と、ストールによる CPI の増加の兼ね合いで決まることが分かります。

10.11. 深いパイプラインの得失

各段の処理を細かく分けて段数を増やすと、1 段あたりの論理回路が減ってクロック周期を短くできます。これを深いパイプライン（deep pipeline）と呼びます。しかし、段数を増やすほど次のような問題が大きくなります。

  • パイプラインレジスタの遅延とクロックスキューは段数によらず各段にかかるので、段を細かくするほどクロック周期に占める割合が大きくなります。

  • 分岐予測が外れたときに捨てる命令の数（分岐予測ミスのペナルティ）が、分岐を判定する段までの段数に比例して増えます。

  • ロードの結果や演算結果が使えるようになるまでのサイクル数が増え、データハザードによるストールが増えます。

  • パイプラインレジスタが増え、高いクロック周波数とあいまって消費電力が増えます。

歴史的な例として、Intel の Pentium 4 は 20 段（後期の Prescott コアでは 31 段）という深いパイプラインで高いクロック周波数を目指しましたが、分岐予測ミスのペナルティと消費電力の増加に悩まされました。その後継の Core マイクロアーキテクチャでは、段数を 14 段程度に減らしています。現代の高性能プロセッサの整数パイプラインは、おおむね 10〜20 段程度です。消費電力の制約については「性能の測り方」で説明したデナード・スケーリングの終焉とも関係します。

CPI を 1 より小さくするには、1 サイクルに複数の命令を発行するスーパースカラや、命令の順序を入れ替えるアウトオブオーダー実行が必要です。これらは「命令レベル並列性」で説明します。

10.12. この章のまとめ

  • パイプラインは、命令の処理を段に分けて複数の命令を重ねて処理し、レイテンシではなくスループットを高める技術です。

  • RISC-V の古典的な 5 段パイプラインは IF、ID、EX、MEM、WB からなり、段の間にパイプラインレジスタを置きます。

  • \(k\) 段のパイプラインの理想的な速度向上は \(k\) 倍ですが、段の不均衡、パイプラインレジスタの遅延、ハザードのために実際はそれより小さくなります。

  • ハザードには構造ハザード、データハザード（RAW、WAR、WAW）、制御ハザードがあります。インオーダーの 5 段パイプラインで問題になるデータハザードは RAW だけです。

  • フォワーディングは、演算結果をパイプラインレジスタから次の命令の ALU へ直接送り、多くの RAW ハザードをストールなしで解消します。

  • ロードの直後にその値を使うロード使用ハザードでは、フォワーディングがあっても 1 サイクルのストールが必要です。コンパイラの命令スケジューリングで避けられることがあります。

  • 制御ハザードには、ストール、分岐予測、遅延分岐で対処します。遅延分岐は初期の RISC で使われましたが、現代の ISA では採用されていません。

  • パイプラインの CPI は「1 + 1 命令あたりの平均ストールサイクル数」です。

  • 深いパイプラインはクロック周波数を上げられる一方、分岐予測ミスのペナルティや消費電力が増えます。
