14. 認証とアプリケーションのセキュリティ

「情報セキュリティと暗号」では、暗号、ハッシュ関数、メッセージ認証コード、デジタル署名、TLS、乱数といった情報セキュリティの道具を学んだ。この章では、それらの道具を使ってアプリケーションを守る方法を学ぶ。まず、パスワードを安全に保存する方法と、認証と認可の違いを整理する。次に、ステートレスな HTTP の上でログイン状態を引き継ぐセッション管理と、Cookie、トークン、OAuth 2.0・OpenID Connect・JWT を扱う。最後に、SQL インジェクション、XSS、CSRF という Web アプリケーションの代表的な脆弱性と、C などで書かれたプログラムのメモリ安全性に関わる脆弱性を学ぶ。

前章と同じく、この章のサンプルコードは仕組みを理解するためのものであり、実際のシステムでは十分に検証されたライブラリやフレームワークを使わなければならない。全体像については [Anderson] を参照してほしい。

14.1. パスワードの保存

14.1.1. なぜ単純なハッシュ値では不十分か

利用者のパスワードを平文でデータベースに保存してはならない。データベースが漏えいすれば、すべてのパスワードがそのまま知られ、同じパスワードを使い回している他のサービスにも被害が及ぶ。暗号化して保存するのも適切ではない。復号するための鍵がサーバ上にあり、鍵も一緒に漏えいすれば元に戻せるからである。そもそも照合するだけなら、元のパスワードに戻せる必要はない。

そこで、パスワードからハッシュ関数で計算した値を保存し、ログイン時には入力されたパスワードから同じ計算をして比較する。しかし、SHA-256 のハッシュ値をそのまま保存するだけでは、次の理由で不十分である。

  • 事前計算による攻撃: よく使われるパスワードのハッシュ値をあらかじめ計算した表（レインボーテーブルなど）を用意しておけば、漏えいしたハッシュ値を表で引くだけでパスワードが分かる。

  • 同じパスワードが分かる: 同じパスワードを使う利用者は同じハッシュ値になるので、1 人のパスワードが分かれば全員分が分かる。

  • 計算が速すぎる: SHA-256 は高速であるように設計されており、GPU を使えば 1 秒間に数十億回以上計算できる。人間が覚えられる程度のパスワードは、総当たりですぐに見つかる。

14.1.2. ソルトとストレッチング

これらの問題には、次の 2 つの対策を組み合わせる。

  • ソルト: 利用者ごとにランダムに生成した値（16 バイト程度）をパスワードに加えてからハッシュ値を計算する。ソルトはハッシュ値と一緒に保存してよく、秘密にする必要はない。ソルトが利用者ごとに異なるので、事前計算した表は使えず、同じパスワードでも保存される値が異なる。

  • ストレッチング: ハッシュ値の計算を何十万回も繰り返すなどして、1 回の照合にかかる計算量を意図的に増やす。正規の利用者がログインするときの 0.1 秒程度の遅れは問題にならないが、何十億通りものパスワードを試す攻撃者にとっては大きな負担になる。

これらを実装したパスワード用の鍵導出関数として、PBKDF2、scrypt、bcrypt、Argon2 がある。PBKDF2 は HMAC を指定した回数だけ繰り返す方式である。scrypt と Argon2 は計算に大量のメモリを必要とするように設計されており（メモリハード）、GPU や専用回路で並列に計算する攻撃をより難しくする。Python の標準ライブラリでは、hashlib.pbkdf2_hmac と hashlib.scrypt が使える。

ch14_password.py
 1"""ソルトとストレッチングを用いたパスワードの保存と照合を示すサンプル。
 2
 3hashlib.pbkdf2_hmac（PBKDF2-HMAC-SHA256）と hashlib.scrypt で
 4パスワードから導出した値を保存し、ログイン時に照合する。
 5ソルトは os.urandom で毎回ランダムに生成するため、表示される
 6ソルトと導出値は実行ごとに異なる。
 7
 8実行方法: python ch14_password.py
 9関連する章: 第 14 章「認証とアプリケーションのセキュリティ」
10"""
11
12import hashlib
13import hmac
14import os
15
16PBKDF2_ITERATIONS = 600_000  # 反復回数（ストレッチングの強さ）
17SALT_BYTES = 16
18
19
20def hash_pbkdf2(password: str) -> str:
21    """PBKDF2 で導出した値を「方式$反復回数$ソルト$導出値」で返す。"""
22    salt = os.urandom(SALT_BYTES)  # ユーザごとに異なるソルト
23    dk = hashlib.pbkdf2_hmac(
24        "sha256", password.encode("utf-8"), salt, PBKDF2_ITERATIONS)
25    return f"pbkdf2_sha256${PBKDF2_ITERATIONS}${salt.hex()}${dk.hex()}"
26
27
28def verify_pbkdf2(password: str, stored: str) -> bool:
29    """入力されたパスワードが保存値と一致するかを調べる。"""
30    _, iterations, salt_hex, dk_hex = stored.split("$")
31    dk = hashlib.pbkdf2_hmac(
32        "sha256", password.encode("utf-8"),
33        bytes.fromhex(salt_hex), int(iterations))
34    # 比較にかかる時間から情報が漏れないよう定数時間で比較する
35    return hmac.compare_digest(dk, bytes.fromhex(dk_hex))
36
37
38def hash_scrypt(password: str, salt: bytes) -> bytes:
39    """scrypt で導出した 32 バイトの値を返す。"""
40    # n: CPU・メモリコスト、r: ブロックサイズ、p: 並列度
41    return hashlib.scrypt(
42        password.encode("utf-8"), salt=salt, n=2**14, r=8, p=1, dklen=32)
43
44
45def main() -> None:
46    """保存形式の表示と、照合の結果を表示する。"""
47    print("[PBKDF2-HMAC-SHA256]")
48    stored1 = hash_pbkdf2("correct horse")
49    stored2 = hash_pbkdf2("correct horse")  # 同じパスワードを再度保存
50    print("保存値:", stored1[:56] + "...")
51    print("同じパスワードの保存値が一致するか:", stored1 == stored2)
52    print("正しいパスワード:", verify_pbkdf2("correct horse", stored1))
53    print("誤ったパスワード:", verify_pbkdf2("correct horsf", stored1))
54
55    print("[scrypt]")
56    salt = os.urandom(SALT_BYTES)
57    dk = hash_scrypt("correct horse", salt)
58    print("導出値の長さ:", len(dk), "バイト")
59    same = hmac.compare_digest(dk, hash_scrypt("correct horse", salt))
60    print("同じソルトで再計算すると一致するか:", same)
61

22 行目で os.urandom により暗号学的に安全な乱数からソルトを生成している。「擬似乱数と暗号学的乱数」で述べたように、random モジュールの乱数は予測可能であり、セキュリティの用途に使ってはならない。23〜24 行目で PBKDF2-HMAC-SHA256 を 16 行目の反復回数（60 万回）だけ繰り返し、25 行目で方式・反復回数・ソルト・導出値を $ で区切った文字列にして保存する。方式と反復回数を一緒に保存しておくと、将来反復回数を増やしたり方式を変えたりしても、古い保存値を照合できる。28〜35 行目の verify_pbkdf2 は、保存値からソルトと反復回数を取り出して同じ計算を行い、hmac.compare_digest で比較する。41〜42 行目は scrypt の例であり、n がコスト（必要なメモリ量と計算量）を決める。実行結果の例を次に示す。

1[PBKDF2-HMAC-SHA256]
2保存値: pbkdf2_sha256$600000$07547cbf37df8bf0c89087bbd3e23bc7$d1...
3同じパスワードの保存値が一致するか: False
4正しいパスワード: True
5誤ったパスワード: False
6[scrypt]
7導出値の長さ: 32 バイト
8同じソルトで再計算すると一致するか: True

ソルトは実行のたびにランダムに生成されるので、実行結果の 2 行目のソルトと導出値は実行ごとに異なる。3 行目は、同じパスワードでもソルトが異なるため保存値が一致しないことを示す。それでも 4 行目のように、保存したソルトを使って計算し直せば照合できる。

注釈

反復回数やコストのパラメータの推奨値は、ハードウェアの性能向上に合わせて引き上げられてきた。サンプルの値は執筆時点の一般的な推奨に基づく例であり、実際に使う場合は最新の指針を確認し、可能であれば Argon2 など実績のあるライブラリが提供する方式を使う。

14.2. 認証と認可

認証（authentication）は「相手が誰であるか」を確かめることであり、認可（authorization）は「その相手に何を許すか」を決めることである。ログイン画面でパスワードを確かめるのは認証であり、ログインした利用者が他人の注文履歴を見られないように制御するのは認可である。「コンピュータネットワーク」で述べたように、HTTP のステータスコードの 401 Unauthorized は名前に反して認証の問題を、403 Forbidden は認可の問題を表す。

認証に使う要素は、次の 3 種類に分けられる。

  • 知識: 本人だけが知っていること。パスワード、暗証番号など。

  • 所持: 本人だけが持っているもの。スマートフォンのアプリが生成するワンタイムパスワード、IC カード、ハードウェアキーなど。

  • 生体: 本人の身体的な特徴。指紋、顔など。

異なる種類の要素を 2 つ以上組み合わせる方式を多要素認証と呼ぶ。パスワードが漏えいしても、所持の要素が無ければログインできない。公開鍵暗号を使い、サーバに秘密を保存しないパスキー（FIDO2）のような方式も普及しつつある。

認可でよくある脆弱性は、権限の確認漏れである。例えば /orders/123 という URL で注文を表示するとき、ログインしているかどうかだけを確かめ、注文 123 がその利用者のものかを確かめなければ、番号を変えるだけで他人の注文が見えてしまう。認可の判定は、画面にボタンを表示するかどうかではなく、サーバ側で要求ごとに必ず行う。

14.3. セッション管理とトークン

14.3.1. HTTP のステートレス性とセッション

「コンピュータネットワーク」で述べたように、HTTP はステートレスなプロトコルであり、サーバは各リクエストを独立に処理する。そのため、ログイン画面で一度認証しても、次のリクエストが同じ利用者から来たことは HTTP だけでは分からない。複数のリクエストにまたがって「誰がログインしているか」を引き継ぐ仕組みをセッション管理と呼ぶ。セッションを引き継ぐための値を毎回のリクエストに付けて送る方法には、大きく分けて Cookie によるセッション ID と、トークンの 2 つがある。

14.3.2. Cookie によるセッション管理

Cookie は、サーバがレスポンスの Set-Cookie ヘッダで指定した名前と値の組を、ブラウザが保存し、以後の同じサイトへのリクエストの Cookie ヘッダに付けて送り返す仕組みである [RFC6265]。典型的なセッション管理では、次のように使う。

  1. 利用者がパスワードなどで認証に成功すると、サーバは推測できないランダムな値（セッション ID）を生成し、「セッション ID \(\to\) 利用者 ID、有効期限など」の対応をサーバ側に保存する。保存先には主記憶やデータベース、キーバリューストアを使う。

  2. サーバは Set-Cookie ヘッダでセッション ID をブラウザに渡す。

  3. ブラウザは、以後のリクエストにセッション ID を Cookie として付けて送る。サーバはセッション ID から利用者を特定する。

  4. ログアウトすると、サーバは保存していた対応を削除する。以後、そのセッション ID は使えない。

セッション ID を知っている者は、パスワードを知らなくても本人になりすませる。そのため、セッション ID は「擬似乱数と暗号学的乱数」で述べた secrets などの暗号学的に安全な乱数で、128 ビット以上の長さに生成する。連番や、利用者 ID と時刻から計算した値は推測されるので使ってはならない。また、セッション ID を盗まれにくくするため、Set-Cookie には次の属性を指定する。

1Set-Cookie: session_id=4f3c9a...; Secure; HttpOnly; SameSite=Lax; Path=/; Max-Age=3600
セッション ID の Cookie に指定する主な属性

属性

意味

Secure

HTTPS の通信でだけ Cookie を送る。暗号化されていない HTTP の通信路で盗聴されるのを防ぐ。

HttpOnly

JavaScript から document.cookie などで Cookie を読めなくする。XSS の脆弱性があってもセッション ID が盗まれにくくなる。

SameSite

他のサイトから始まったリクエストに Cookie を付けるかを決める。Strict は付けない、Lax は他のサイトのリンクをたどるような通常のページ移動に限って付ける、None は常に付ける（Secure が必要）。CSRF の対策になる。

Max-Age、Expires

Cookie の有効期間。指定しなければブラウザを閉じるまで有効なセッション Cookie になる。

Domain、Path

Cookie を送る宛先の範囲。Domain を指定するとサブドメインにも送られるので、必要がなければ指定しない。

SameSite 属性は RFC 6265 の後に提案され、その改訂作業の中で規定が進められているもので、主要なブラウザが実装している。指定しない場合の扱いはブラウザによって異なるので、明示的に指定する。

セッション管理に特有の攻撃にセッション固定攻撃（session fixation）がある。攻撃者は、まず自分でサイトにアクセスしてセッション ID を入手し、何らかの方法（セッション ID を含む URL を踏ませる、サブドメインから Cookie を設定するなど）で、そのセッション ID を被害者のブラウザに使わせる。被害者がそのままログインすると、サーバがログイン前と同じセッション ID をログイン済みとして扱う実装では、攻撃者は手元のセッション ID で被害者としてアクセスできてしまう。対策は、ログインに成功した時点で必ず新しいセッション ID を発行し、古いものを無効にすることである。権限が変わる操作（管理者権限への切り替えなど）の後も同様にする。また、セッション ID を URL に含めて受け付けない。

14.3.3. トークンベースの認証

ブラウザ以外のクライアント（スマートフォンのアプリ、他のサーバ、コマンドラインのツール）が API を呼び出す場合には、Cookie の代わりに、リクエストの Authorization ヘッダでトークンを送る方式が広く使われる。

1Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...

Bearer は「持参人」を意味し、このトークンを持っている者なら誰でも使えることを表す。つまり、トークンは盗まれればそのまま悪用される。TLS で通信路を保護し、URL のクエリ文字列にトークンを入れない（ログやブラウザの履歴に残るため）ことが前提になる。

トークンには 2 つの種類がある。1 つは、セッション ID と同じように意味を持たないランダムな文字列であり、サーバは受け取るたびに保存しておいた情報を引いて検証する。もう 1 つは、利用者 ID や有効期限などの情報そのものをトークンに含め、改ざんされていないことを署名で保証する自己完結型のトークンである。自己完結型のトークンは、サーバが保存した情報を引かずに署名の検証だけで処理できるので、多数のサーバで処理を分担しやすい。その代表が後述の JWT である。

14.3.4. OAuth 2.0 と OpenID Connect

「写真の印刷サービスに、クラウドストレージにある自分の写真を読ませたい」という場面を考える。印刷サービスにクラウドストレージのパスワードを教えると、印刷サービスは写真の読み出し以外のこと（ファイルの削除、パスワードの変更）もでき、後から印刷サービスだけの権限を取り消すこともできない。OAuth 2.0 は、利用者がパスワードを渡さずに、あるアプリケーションに対して、自分のリソースへの限られた範囲のアクセスを許可するための枠組みである [RFC6749]。つまり OAuth 2.0 は認可の委譲の仕組みである。

OAuth 2.0 には次の 4 つの役割が登場する。

  • リソースオーナー: リソースの持ち主である利用者。

  • クライアント: 利用者のリソースにアクセスしたいアプリケーション（上の例の印刷サービス）。

  • 認可サーバ: 利用者を認証し、利用者の同意を得てアクセストークンを発行するサーバ。

  • リソースサーバ: リソースを保持し、アクセストークンを受け取って要求に応じるサーバ（上の例のクラウドストレージ）。

Web アプリケーションで最もよく使われる認可コードフローの流れは次のとおりである。

  1. クライアントは、利用者のブラウザを認可サーバへ移動（リダイレクト）させる。このとき、クライアントの識別子、求める権限の範囲（スコープ、例えば「写真の読み出し」）、処理後に戻る URL、CSRF 対策のためのランダムな値（state）を付ける。

  2. 認可サーバは利用者を認証し、「印刷サービスに写真の読み出しを許可するか」の同意を求める。

  3. 利用者が同意すると、認可サーバはブラウザをクライアントの URL へ戻し、短時間だけ有効な認可コードを渡す。

  4. クライアントは、ブラウザを経由せずに認可サーバと直接通信し、認可コードとクライアント自身の認証情報を渡してアクセストークンを受け取る。

  5. クライアントは、アクセストークンを付けてリソースサーバに要求する。

アクセストークンが表すのは「このトークンを持つ者に、ある範囲の操作を許す」ということであり、「このトークンを示した者は利用者 X である」ということではない。アクセストークンはリソースサーバに向けて発行されたものであり、クライアントがその宛先や発行の経緯を確かめる手段も規定されていない。そのため、アクセストークンを受け取れたことを「利用者 X がログインした」証拠として扱うと、別のクライアントに発行されたトークンを持ち込まれてなりすましを許すなどの問題が起きる。OAuth 2.0 は認可の仕組みであって、認証の仕組みではない。

「Google アカウントでログイン」のように、他のサービスの認証結果を使ってログインする機能には、OAuth 2.0 の上に認証の機能を加えた OpenID Connect を使う [OIDC]。OpenID Connect では、認可サーバ（OpenID プロバイダと呼ぶ）がアクセストークンに加えて ID トークンを発行する。ID トークンは、発行者（iss）、利用者の識別子（sub）、宛先のクライアント（aud）、有効期限（exp）、リプレイ攻撃を防ぐための値（nonce）などを含み、発行者が署名した JWT である。クライアントは署名と各項目を検証することで、「この発行者が、自分に宛てて、利用者 X を認証した」ことを確かめられる。

14.3.5. JWT の構造

JWT（JSON Web Token）は、JSON で表した情報（クレーム）を、URL に含めても問題のない文字列として受け渡すための形式である [RFC7519]。署名付きの JWT は、次の 3 つの部分をピリオド（.）でつないだものである。

  • ヘッダ: 署名のアルゴリズムなどを表す JSON。例えば {"alg":"HS256","typ":"JWT"}。

  • ペイロード: クレームを表す JSON。発行者 iss、主体 sub、宛先 aud、有効期限 exp、発行時刻 iat などの登録済みのクレームと、アプリケーションが独自に定める role のようなクレームを含められる。時刻は Unix 時間（1970 年 1 月 1 日 0 時 0 分 0 秒（UTC）からの経過秒数）で表す。

  • 署名: 「ヘッダ.ペイロード」という文字列に対して計算した署名。

ヘッダとペイロードと署名は、それぞれ Base64URL で符号化する。Base64URL は、Base64 の + と / を URL で特別な意味を持たない - と _ に置き換えたもので、JWT では末尾の埋め草の = も取り除く。署名のアルゴリズムには、前に説明した HMAC を使う HS256（HMAC-SHA256、共通鍵）や、デジタル署名を使う RS256（RSA）、ES256（ECDSA）などがある。HS256 は発行者と検証者が同じ鍵を共有する必要があるが、RS256 や ES256 なら公開鍵を配るだけで誰でも検証でき、発行者だけが署名を作れる。OpenID Connect の ID トークンのように、発行者と検証者が別の組織である場合は、デジタル署名の方式を使う。

次のサンプルは、標準ライブラリだけで HS256 の JWT を作成・検証する。

警告

このサンプルは JWT の構造を理解するための学習用である。実際のシステムでは、検証済みの JWT ライブラリを使い、許可するアルゴリズム、exp、iss、aud などの検証をライブラリの機能で確実に行うこと。また、鍵をソースコードに書いてはならない。

ch14_jwt.py
  1"""HS256 の JWT を作成・検証し、改ざんを検出するサンプル（学習用）。
  2
  3標準ライブラリの hmac・base64・json だけで JWT（JSON Web Token）の
  4構造を確かめる。ヘッダ・ペイロードは署名で改ざんを検出できるが、
  5暗号化されてはおらず、鍵が無くても誰でも読めることも示す。
  6実際のシステムでは、検証済みの JWT ライブラリを使うこと。
  7
  8結果を再現できるよう、鍵と時刻は固定値にしている。実際の鍵は
  9secrets.token_bytes(32) などで生成し、ソースコードに書かない。
 10
 11実行方法: python ch14_jwt.py
 12関連する章: 第 14 章「認証とアプリケーションのセキュリティ」
 13"""
 14
 15import base64
 16import hashlib
 17import hmac
 18import json
 19from typing import Any
 20
 21KEY = b"demo-key-for-learning-only-32byt"  # 学習用の固定鍵
 22NOW = 1_700_000_000  # 現在時刻とみなす Unix 時間（秒）
 23
 24
 25def b64url_encode(data: bytes) -> str:
 26    """Base64URL で符号化し、末尾の = を取り除く。"""
 27    return base64.urlsafe_b64encode(data).rstrip(b"=").decode("ascii")
 28
 29
 30def b64url_decode(text: str) -> bytes:
 31    """取り除かれた = を補ってから Base64URL を復号する。"""
 32    return base64.urlsafe_b64decode(text + "=" * (-len(text) % 4))
 33
 34
 35def encode_part(obj: dict[str, Any]) -> str:
 36    """辞書を JSON にして Base64URL で符号化する。"""
 37    raw = json.dumps(obj, separators=(",", ":")).encode("utf-8")
 38    return b64url_encode(raw)
 39
 40
 41def sign(signing_input: str, key: bytes) -> str:
 42    """「ヘッダ.ペイロード」に対する HMAC-SHA256 の署名を返す。"""
 43    mac = hmac.new(key, signing_input.encode("ascii"), hashlib.sha256)
 44    return b64url_encode(mac.digest())
 45
 46
 47def create_token(payload: dict[str, Any], key: bytes) -> str:
 48    """HS256 の JWT を作成する。"""
 49    signing_input = encode_part({"alg": "HS256", "typ": "JWT"}) + "." \
 50        + encode_part(payload)
 51    return signing_input + "." + sign(signing_input, key)
 52
 53
 54def verify_token(token: str, key: bytes, now: int) -> dict[str, Any]:
 55    """JWT を検証してペイロードを返す。不正なら ValueError を送出する。"""
 56    header_b64, payload_b64, sig_b64 = token.split(".")
 57    header = json.loads(b64url_decode(header_b64))
 58    if header.get("alg") != "HS256":  # alg=none などを受け付けない
 59        raise ValueError(f"許可しないアルゴリズム: {header.get('alg')}")
 60    expected = sign(header_b64 + "." + payload_b64, key)
 61    if not hmac.compare_digest(expected, sig_b64):
 62        raise ValueError("署名が一致しない")
 63    payload: dict[str, Any] = json.loads(b64url_decode(payload_b64))
 64    if payload["exp"] <= now:
 65        raise ValueError("有効期限切れ")
 66    return payload
 67
 68
 69def check(label: str, token: str, now: int = NOW) -> None:
 70    """検証結果を 1 行で表示する。"""
 71    try:
 72        payload = verify_token(token, KEY, now)
 73        print(f"{label}: 成功 {payload}")
 74    except ValueError as e:
 75        print(f"{label}: 拒否（{e}）")
 76
 77
 78def main() -> None:
 79    """作成、デコード、検証、改ざん検出を順に示す。"""
 80    token = create_token(
 81        {"sub": "alice", "role": "user", "exp": NOW + 900}, KEY)
 82    header_b64, payload_b64, sig_b64 = token.split(".")
 83    print("[作成した JWT]")
 84    print("ヘッダ    :", header_b64)
 85    print("ペイロード:", payload_b64)
 86    print("署名      :", sig_b64)
 87    print("[鍵が無くても読める]")
 88    print(b64url_decode(payload_b64).decode("utf-8"))
 89    print("[検証]")
 90    check("正しいトークン", token)
 91    forged = encode_part({"sub": "alice", "role": "admin",
 92                          "exp": NOW + 900})
 93    check("role を書き換え", f"{header_b64}.{forged}.{sig_b64}")
 94    none_header = encode_part({"alg": "none", "typ": "JWT"})
 95    check("alg=none", f"{none_header}.{forged}.")
 96    check("16 分後", token, now=NOW + 960)
 97
 98
 99if __name__ == "__main__":
100    main()

ch14_jwt.py

25〜32 行目が Base64URL の符号化と復号である。32 行目では、取り除かれた = を補ってから復号している。47〜51 行目の create_token は、ヘッダとペイロードを符号化してピリオドでつなぎ、41〜44 行目の sign で HMAC-SHA256 の署名を付ける。54〜66 行目の verify_token は、58 行目でヘッダの alg が HS256 であることを確かめ、60〜62 行目で署名を計算し直して hmac.compare_digest で比較し、64 行目で有効期限を確かめる。結果を再現できるよう、21〜22 行目で鍵と現在時刻を固定している。実行結果は次のとおりである。

 1[作成した JWT]
 2ヘッダ    : eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9
 3ペイロード: eyJzdWIiOiJhbGljZSIsInJvbGUiOiJ1c2VyIiwiZXhwIjoxNzAwMDAwOTAwfQ
 4署名      : 3IFdb-s53E_rFlXm4vS3E0ZjPRVsHtxu3ArV_QjRkjE
 5[鍵が無くても読める]
 6{"sub":"alice","role":"user","exp":1700000900}
 7[検証]
 8正しいトークン: 成功 {'sub': 'alice', 'role': 'user', 'exp': 1700000900}
 9role を書き換え: 拒否（署名が一致しない）
10alg=none: 拒否（許可しないアルゴリズム: none）
1116 分後: 拒否（有効期限切れ）

実行結果の 6 行目は、ペイロードを鍵を使わずに Base64URL で復号しただけで、中身がそのまま読めることを示す。9 行目では、ペイロードの role を admin に書き換えたが、署名は元のままなので一致せず、改ざんが検出された。10 行目と 11 行目は、次に述べる alg=none の偽造と、有効期限（発行から 15 分）を過ぎたトークンが拒否されることを示す。

JWT を使うときは、次の点に注意する。

  • 署名は改ざんの検出であり、暗号化ではない: 実行結果の 6 行目のように、ペイロードは誰でも読める。パスワードや個人情報のような秘密を JWT のペイロードに入れてはならない。内容を秘匿したい場合は、暗号化の形式（JWE）を使うか、そもそも秘密をトークンに含めない。

  • alg=none: JWT の仕様には、署名の無いことを表す "alg":"none" がある。トークンのヘッダに書かれた alg をそのまま信じて検証の方法を選ぶ実装では、攻撃者がヘッダを none に書き換え、署名を空にしたトークンが受け付けられてしまう。同様に、RS256 の公開鍵を HS256 の共通鍵として使わせる攻撃もある。検証側は、ヘッダの値にかかわらず、受け付けるアルゴリズムと鍵を自分で固定する（サンプルの 58 行目）。

  • 失効が難しい: 自己完結型のトークンは、サーバに問い合わせずに検証できることが利点だが、その裏返しとして、一度発行すると有効期限まで有効であり続ける。ログアウトしたり、トークンが盗まれたことが分かったりしても、サーバ側で無効にできない。失効させたいトークンの一覧をサーバ側で管理すれば無効にできるが、それは状態を持たないという利点を一部捨てることになる。そのため、アクセストークンの有効期限を数分から数十分と短くし、新しいアクセストークンを得るためのリフレッシュトークン（サーバ側で管理し、失効させられるもの）と組み合わせるのが一般的である。

  • クレームを検証する: 署名が正しくても、exp が過ぎていないか、iss が想定した発行者か、aud が自分宛てかを確かめなければ、期限切れのトークンや他のサービス向けのトークンを受け付けてしまう。

なお、ブラウザでトークンを JavaScript から読める場所（localStorage など）に保存すると、XSS の脆弱性があったときに盗まれる。HttpOnly 属性を付けた Cookie に保存すればスクリプトからは読めないが、CSRF への対策が必要になる。

14.4. 代表的な脆弱性

ここでは、Web アプリケーションの代表的な脆弱性を 3 つ紹介し、最後に C などで書かれたプログラムに多いメモリ安全性に関わる脆弱性を扱う。前の 3 つは、いずれも外部から受け取ったデータを、それが解釈される文脈（SQL、HTML、利用者の意図）に対して適切に扱わないことから生じる。

14.4.1. SQL インジェクション

SQL インジェクションは、利用者の入力を文字列連結で SQL に埋め込むことで、入力の一部が SQL の構文として解釈されてしまう脆弱性である。データの漏えい、改ざん、削除につながる。対策は、「データベース」の「プレースホルダと SQL インジェクション」で示したように、プレースホルダを使って SQL の構造と値を分離することである。データベースの接続に必要最小限の権限だけを与えておけば、万一の被害を小さくできる。

14.4.2. クロスサイトスクリプティング（XSS）

クロスサイトスクリプティング（XSS: Cross-Site Scripting）は、攻撃者が用意したスクリプトが、脆弱なサイトのページの一部として利用者のブラウザで実行されてしまう脆弱性である。例えば掲示板が投稿内容をそのまま HTML に出力すると、<script> タグを含む投稿を閲覧した利用者のブラウザで、そのスクリプトがサイトの権限で実行される。スクリプトは、Cookie に保存されたセッション ID を盗んだり、利用者になりすまして操作したりできる。

対策の基本は、HTML に出力する値を、出力する場所の文脈に応じてエスケープすることである。Python では html.escape で HTML の特殊文字を文字参照に置き換えられる。

1import html
2
3comment = '<script>alert("XSS")</script>'
4print(html.escape(comment))

1&lt;script&gt;alert(&quot;XSS&quot;)&lt;/script&gt;

< や " が文字参照に置き換えられ、ブラウザはこれをタグではなく文字列として表示する。実際には、自動的にエスケープするテンプレートエンジンを使うのが確実である。さらに、実行を許すスクリプトの出所を制限する CSP（Content Security Policy）や、スクリプトから Cookie を読めなくする HttpOnly 属性を併用して、被害を軽減する。

14.4.3. クロスサイトリクエストフォージェリ（CSRF）

クロスサイトリクエストフォージェリ（CSRF: Cross-Site Request Forgery）は、利用者が脆弱なサイトにログインしたまま攻撃者の用意したページを開くと、そのページから脆弱なサイトへ、利用者の意図しない要求（送金、パスワード変更など）が送られてしまう脆弱性である。ブラウザは、要求がどのページから送られたかにかかわらず、宛先のサイトの Cookie を自動的に付けて送るため、サイトからは正規の要求と区別できない。

対策には、次のものがある。

  • 状態を変更する要求のフォームに、攻撃者が知りえないランダムな値（CSRF トークン）を埋め込み、サーバ側で照合する。

  • Cookie に SameSite 属性を指定し、他のサイトから送られる要求に Cookie を付けないようにする。

  • 要求の Origin ヘッダを確認し、自サイト以外からの要求を拒否する。

  • 状態を変更する操作に GET を使わない。

XSS が「サイトに攻撃者のスクリプトを実行させる」攻撃であるのに対し、CSRF は「利用者のブラウザに、攻撃者が望む要求を送らせる」攻撃である。XSS の脆弱性があると CSRF トークンもスクリプトから読まれてしまうため、両方への対策が必要である。

14.4.4. メモリ安全性に関わる脆弱性

ここまでの 3 つは Web アプリケーションの脆弱性だったが、OS、ブラウザ、ネットワーク機器のソフトウェア、暗号ライブラリなど、C や C++ で書かれたプログラムでは、メモリの誤った扱いに起因する脆弱性が大きな割合を占める。プログラムが、自分に割り当てられた範囲の、まだ有効なメモリだけを正しく読み書きすることが保証される性質をメモリ安全性と呼ぶ。「プログラミング言語処理系」で述べたように、C ではプログラマがメモリを手動で管理し、配列の添字が範囲内かどうかも検査されないので、メモリ安全性は言語によって保証されない。

バッファオーバーフロー（buffer overflow）は、配列などの領域（バッファ）に、その大きさを超えるデータを書き込んでしまう誤りである。次の C の関数は、引数の文字列を長さを確かめずに 16 バイトの配列にコピーしている（説明のための例であり、本書では実行しない）。

1#include <stdio.h>
2#include <string.h>
3
4void greet(const char *name)
5{
6    char buf[16];
7    strcpy(buf, name);  /* name の長さを確かめていない */
8    printf("Hello, %s\n", buf);
9}

6 行目の buf は局所変数なので、「プログラミング言語処理系」で述べたスタックフレームに置かれる。スタックフレームには、関数から戻るときの戻り先のアドレスも格納されている。多くの環境ではスタックはアドレスの小さい方へ伸び、配列には小さいアドレスから順に書き込むので、buf より大きいアドレス側に戻り先のアドレスがある。7 行目で name が 16 バイト以上あると、あふれたデータが戻り先のアドレスを上書きする。関数から戻る命令は、スタックから取り出したアドレスを「コンピュータの構成」で学んだプログラムカウンタに設定するので、攻撃者は入力の内容によって、プログラムの実行を任意のアドレスへ移せる。ノイマン型のコンピュータでは命令とデータが同じメモリに置かれるので、攻撃者が入力に機械語の命令を含めておき、そこへ実行を移させれば、任意のコードを実行させることもできる。ヒープ上のバッファがあふれた場合も、隣接するデータや管理情報が壊され、同様の攻撃につながる。

書き込みだけでなく、読み出しの境界検査の欠如も深刻である。2014 年に OpenSSL で見つかった Heartbleed と呼ばれる脆弱性は、TLS の拡張機能の処理で、相手が申告したデータの長さを実際の長さと照合せずにその長さだけメモリを読んで返していたもので、サーバのメモリにあった秘密鍵やパスワードが読み出されるおそれがあった。また、確保する大きさの計算が「情報の表現」で学んだ整数のオーバーフローを起こして小さな領域しか確保されず、その後の書き込みがあふれる、という形の脆弱性も多い。Python や Java では、範囲外の添字は例外（IndexError など）になり、メモリが壊れることはない。

解放後使用（use-after-free）は、free で解放した領域を、解放前に指していたポインタ（ダングリングポインタ）を通じて使い続ける誤りである。

1struct session *s = malloc(sizeof *s);
2/* ... s を使う ... */
3free(s);
4/* ... この間に別の malloc が同じ領域を再利用しうる ... */
5if (s->is_admin) {  /* 解放済みの領域を読んでいる */
6    grant_admin_menu();
7}

解放した領域は、次の malloc で別の目的に再利用されることがある。攻撃者がその領域に自分の用意したデータを置けるように仕向けると、5 行目の判定の結果を操作したり、領域内の関数ポインタを書き換えて実行を乗っ取ったりできる。同じ領域を 2 回解放する二重解放も、メモリ管理の情報を壊して同様の攻撃につながる。

これらの攻撃を難しくするため、OS、コンパイラ、CPU は次のような緩和策を備えている。

  • スタックカナリア: コンパイラが、スタックフレームの局所変数と戻り先のアドレスの間に、実行ごとにランダムな値（カナリア）を置き、関数から戻る直前にその値が変わっていないかを確かめる。バッファオーバーフローで戻り先のアドレスを上書きすると、途中にあるカナリアも書き換わるので、プログラムを異常終了させて乗っ取りを防ぐ。GCC や Clang の -fstack-protector 系のオプションで有効になる。

  • NX ビット: 「オペレーティングシステム」で学んだページテーブルの属性の 1 つで、そのページの内容を命令として実行することを禁止する。スタックやヒープのようなデータの領域を実行不可にしておけば、入力として送り込まれた機械語は実行されない。CPU の機能として NX（No eXecute）ビットや XD ビットと呼ばれ、それを使う OS の機能は DEP（Data Execution Prevention）とも呼ばれる。

  • ASLR（Address Space Layout Randomization、アドレス空間配置のランダム化）: プログラムを起動するたびに、スタック、ヒープ、共有ライブラリ、プログラム本体（位置独立実行形式としてコンパイルした場合）を置く仮想アドレスをランダムに変える。攻撃者は、実行を移すべきアドレスを事前に知ることができなくなる。

NX ビットに対しては、プログラムやライブラリの中にすでにある命令の断片をつなぎ合わせて目的の処理を行わせる攻撃（ROP: Return-Oriented Programming）が考案され、ASLR に対しては、別の脆弱性でアドレスを漏えいさせてから攻撃する手法がある。緩和策は攻撃を難しくするが、誤りそのものを無くすわけではないので、複数を組み合わせて使う（多層防御）。

根本的な対策は、メモリ安全性の誤りを作り込まないことである。C では、長さを指定する関数（snprintf など）を使い、境界を確かめる習慣を徹底したうえで、AddressSanitizer のような実行時の検査ツールや、ランダムな入力を大量に与えて異常を探すファジングで誤りを見つける。さらに効果的なのが、メモリ安全な言語を使うことである。Python、Java、Go などは、範囲外アクセスを実行時に検査し、ガベージコレクションによって解放後使用を起こさない。Rust は、所有権と借用の規則をコンパイル時に検査することで、ガベージコレクションを使わずに解放後使用や二重解放を防ぐ。ただし、Python のプログラムでも、C で書かれた拡張モジュールや ctypes を使う部分にはこれらの脆弱性が入り込みうる。

14.5. まとめ

  • パスワードは、ソルトとストレッチングを行う PBKDF2 や scrypt などで導出した値を保存する。

  • 認証は相手が誰かを確かめ、認可は何を許すかを決める。認可の判定はサーバ側で要求ごとに行う。

  • ステートレスな HTTP でログイン状態を引き継ぐには、Cookie のセッション ID（Secure・HttpOnly・SameSite 属性を付け、ログイン時に再発行する）や、Authorization ヘッダのトークンを使う。

  • OAuth 2.0 は認可の委譲の仕組みであり、認証には OpenID Connect の ID トークンを使う。JWT の署名は改ざんを検出するが暗号化ではなく、検証側はアルゴリズムを固定し、失効の難しさを短い有効期限で補う。

  • SQL インジェクションにはプレースホルダ、XSS には出力時のエスケープ、CSRF にはトークンや SameSite 属性で対策する。

  • C などではバッファオーバーフローや解放後使用がメモリ安全性を損なう。スタックカナリア、NX ビット、ASLR は攻撃を難しくする緩和策であり、根本的な対策はメモリ安全な言語の利用や境界の検査である。
