11. データベース

多くのアプリケーションの中心には、永続化されたデータがある。銀行口座の残高、EC サイトの注文、SNS の投稿は、プログラムが終了しても、サーバが再起動しても失われてはならず、多数のユーザから同時に読み書きされても矛盾してはならない。この章では、こうした要求に応えるソフトウェアであるデータベース管理システムについて、関係モデルと SQL、正規化、インデックス、結合のアルゴリズムとクエリ最適化、トランザクションの順に基本的な考え方を学ぶ。トランザクションの節では、アプリケーションの側から同時更新の異常を防ぐ楽観的ロックと悲観的ロックも扱う。最後に、関係データベース以外のデータベースを簡単に紹介する。複数のサーバにデータを複製・分散する方法は「分散システム」で扱う。

この章のサンプルコードは、Python の標準ライブラリに含まれる sqlite3 モジュールを使う。SQLite はサーバを持たず、1 つのファイル（またはメモリ）にデータベース全体を格納する組み込み型の DBMS である [SQLite]。体系的な解説は [DSC] を、大規模なデータシステムの設計については [DDIA] を参照してほしい。

11.1. データベース管理システムの役割

11.1.1. ファイルでデータを管理する場合の問題

小さなプログラムでは、データを CSV や JSON のファイルに保存すれば十分なことが多い。しかし、データの量や利用者が増えると、次のような問題が起きる。

  • 検索が遅い: 条件に合う行を探すたびにファイル全体を読む必要がある。速くするには、プログラムごとに索引の仕組みを作り込まなければならない。

  • 同時更新で壊れる: 2 つのプロセスが同じファイルを読み、それぞれ書き換えて保存すると、一方の更新が失われる。「並行処理と入出力」で学んだ排他制御を、アプリケーション側ですべて正しく実装する必要がある。

  • 障害時に中途半端な状態が残る: 書き込みの途中で電源が落ちると、ファイルの半分だけが新しい内容になることがある。

  • 整合性を保証できない: 「注文に記録された顧客 ID は顧客一覧に必ず存在する」のような規則を、すべてのプログラムが守る保証がない。

  • データ形式とプログラムが密結合になる: ファイルの形式を変えると、それを読むすべてのプログラムを修正しなければならない。

11.1.2. DBMS が提供するもの

データベース管理システム（DBMS: Database Management System）は、これらの問題を解決するために、データの格納、検索、更新、同時実行の制御、障害からの回復を一手に引き受けるソフトウェアである。アプリケーションは「何がほしいか」を問い合わせ言語で宣言するだけでよく、それを「どのように」取り出すか（どのファイルのどの位置を読むか、どの索引を使うか）は DBMS が決める。このように、データの論理的な構造と物理的な格納方法を分離することをデータ独立性と呼ぶ。

代表的な DBMS には、PostgreSQL、MySQL、Oracle Database、SQL Server などのサーバ型と、SQLite のような組み込み型がある。いずれも次に説明する関係モデルに基づいており、関係データベース（RDB: Relational Database）と呼ばれる。

表の列を属性（attribute）、行をタプル（tuple）と呼ぶ。各属性が取りうる値の集合を定義域（domain）という。数学的には、関係は定義域の直積の部分集合、つまりタプルの集合である。集合であるから、同じタプルが 2 つ存在することはなく、タプルの順序にも意味がない。SQL の表は重複した行を許す点でこの定義と異なるが、通常の設計では次に述べる主キーによって重複を防ぐ。

11.2.2. 主キーと外部キー

関係の中でタプルを一意に識別できる属性（または属性の組）を候補キーと呼び、その中から代表として選んだものを主キー（primary key）と呼ぶ。上の例では emp_id が主キーである。主キーの値は重複してはならず、NULL（後述）であってもならない。

ある関係の属性が、別の関係の主キーを参照するとき、その属性を外部キー（foreign key）と呼ぶ。例えば employee の dept_id が部署を表す関係 department の主キー dept_id を参照していれば、dept_id は外部キーである。DBMS は外部キー制約によって、存在しない部署を参照する社員が登録されないことを保証する。この性質を参照整合性と呼ぶ。

11.2.3. 関係代数

関係代数は、関係を入力として受け取り、関係を出力する演算の体系である。出力も関係であるため、演算を組み合わせて複雑な問い合わせを表現できる。基本的な演算を次に示す。

  • 選択（selection）: 条件を満たすタプルだけを取り出す。\(\sigma_{\mathrm{salary} > 420}(\mathrm{employee})\) は給与が 420 を超える社員の関係を返す。表の行を絞り込む操作である。

  • 射影（projection）: 指定した属性だけを残す。\(\pi_{\mathrm{name}}(\mathrm{employee})\) は社員名だけからなる関係を返す。表の列を絞り込む操作である。結果は集合なので、重複したタプルは 1 つにまとめられる。

  • 結合（join）: 2 つの関係のタプルの組のうち、条件を満たすものをつなげる。\(\mathrm{employee} \bowtie_{\mathrm{employee.dept\_id} = \mathrm{department.dept\_id}} \mathrm{department}\) は、社員とその所属部署を 1 つのタプルにまとめた関係を返す。

このほかに、和（\(\cup\)）、差（\(-\)）、直積（\(\times\)）、属性名の変更などの演算がある。結合は直積と選択の組み合わせ \(R \bowtie_{\theta} S = \sigma_{\theta}(R \times S)\) として定義できる。例えば「給与が 420 を超える社員の名前と部署名」は \(\pi_{\mathrm{employee.name},\, \mathrm{department.name}}(\sigma_{\mathrm{salary} > 420}(\mathrm{employee} \bowtie \mathrm{department}))\) と書ける。

関係代数の式は、同じ結果を返す別の式に書き換えられることが多い。例えば上の式は、結合の前に選択を行っても結果が変わらない。結合する前にタプルを減らしておけば計算は速くなる。DBMS の問い合わせ最適化器（オプティマイザ）は、このような書き換えとインデックスの有無、データ量の統計情報をもとに、実行の手順（実行計画）を選ぶ。結合の計算方法と実行計画の選び方は「結合のアルゴリズムとクエリ最適化」で説明する。

11.3. SQL

SQL は関係データベースを操作するための標準的な言語である。SQL の文は大きく 2 種類に分けられる。

  • DDL（Data Definition Language、データ定義言語）: CREATE TABLE、ALTER TABLE、DROP TABLE、CREATE INDEX など、表や索引の構造を定義する。

  • DML（Data Manipulation Language、データ操作言語）: SELECT、INSERT、UPDATE、DELETE など、データを検索・更新する。

このほか、権限を管理する GRANT などを DCL（Data Control Language）と呼ぶことがある。

11.3.1. SELECT の基本

SELECT 文の基本形は次のとおりである。

1SELECT d.name, COUNT(e.emp_id) AS members
2FROM employee AS e
3JOIN department AS d ON e.dept_id = d.dept_id
4WHERE e.salary >= 400
5GROUP BY d.name
6HAVING COUNT(e.emp_id) >= 2
7ORDER BY members DESC;

SQL は書かれた順ではなく、概念的には次の順に評価される。FROM と JOIN（2〜3 行目）で対象の表を結合し、WHERE（4 行目）で行を選択し、GROUP BY（5 行目）で同じ値を持つ行をグループにまとめ、HAVING（6 行目）でグループを選択し、SELECT（1 行目）で出力する列を計算し、最後に ORDER BY（7 行目）で並べ替える。WHERE では集計関数を使えず HAVING では使えるのは、この評価順による。WHERE は選択、SELECT の列指定は射影、JOIN は結合にほぼ対応する。

結合には、条件に一致する行の組だけを返す内部結合（JOIN または INNER JOIN）と、一致する相手が無い行も残す外部結合（LEFT JOIN など）がある。LEFT JOIN では、左側の表の行に一致する右側の行が無い場合、右側の列は NULL になる。

GROUP BY とともに使う集計関数には COUNT、SUM、AVG、MIN、MAX がある。COUNT(*) は行数を数えるが、COUNT(列) や AVG(列) はその列が NULL の行を無視する。

11.3.2. NULL と三値論理

SQL の NULL は「値が存在しない」または「値が不明である」ことを表す特別な印であり、0 や空文字列とは異なる。NULL との比較は真（TRUE）でも偽（FALSE）でもなく、不明（UNKNOWN）になる。salary = NULL は、salary が NULL の行に対しても UNKNOWN であり、真にはならない。WHERE 句は条件が TRUE の行だけを残すため、この条件では 1 行も選ばれない。NULL かどうかを調べるには IS NULL または IS NOT NULL を使う。

11.3.4. プレースホルダと SQL インジェクション

上のサンプルの 74〜77 行目の find_unsafe は、利用者の入力 name を文字列として SQL に埋め込んでいる。88 行目の入力 ' OR '1'='1 を渡すと、組み立てられる SQL は次のようになる。

1SELECT name FROM employee WHERE name = '' OR '1'='1'

入力に含まれる引用符が文字列リテラルを閉じ、その後ろの OR '1'='1' が SQL の一部として解釈されてしまう。条件は全行で真になり、実行結果の 15 行目のように全社員の名前が返る。入力を工夫すれば、他の表の読み出しやデータの削除も起こりうる。このような攻撃を SQL インジェクションと呼ぶ。

11.4.2. 第 1〜第 3 正規形

正規化の段階を正規形と呼ぶ。代表的な第 1〜第 3 正規形を次に示す。

  • 第 1 正規形（1NF）: すべての属性の値が、それ以上分解できない単一の値（原子値）である。1 つのセルに「ノート, ペン」のように複数の値を詰め込んだり、「商品 1」「商品 2」のような繰り返しの列を持ったりしない。上の表は第 1 正規形である。

  • 第 2 正規形（2NF）: 第 1 正規形であり、かつ主キーでない属性が、主キー（候補キー）の一部だけに関数従属しない（部分関数従属が無い）。上の表では商品名が主キーの一部である商品番号だけで決まり、顧客番号と顧客名は注文番号だけで決まるので、第 2 正規形ではない。表を「注文明細（注文番号, 商品番号, 数量）」「注文（注文番号, 顧客番号, 顧客名）」「商品（商品番号, 商品名）」に分割すると第 2 正規形になる。

  • 第 3 正規形（3NF）: 第 2 正規形であり、かつ主キーでない属性が、主キー以外の属性を介して主キーに関数従属しない（推移的関数従属が無い）。「注文」表では「注文番号 \(\to\) 顧客番号 \(\to\) 顧客名」という推移的関数従属があるので、「注文（注文番号, 顧客番号）」と「顧客（顧客番号, 顧客名）」に分割する。

第 3 正規形まで分割すると、商品名や顧客名はそれぞれ 1 か所にしか現れず、変更は 1 行の更新で済む。新商品は注文が無くても「商品」表に登録でき、注文を削除しても顧客の情報は残る。元の表は、分割した表を結合すれば復元できる。このように情報を失わずに分割することを無損失分解という。第 3 正規形をさらに厳しくしたボイス・コッド正規形（BCNF）や、多値従属を扱う第 4 正規形もあるが、実務ではまず第 3 正規形を目標にすることが多い。

11.4.3. 意図的な非正規化

正規化すると表の数が増え、検索のたびに結合が必要になる。読み出しの性能が特に重要な場合は、あえて重複を持たせる非正規化を行うことがある。例えば、注文の合計金額を明細から毎回集計せずに注文表に保存しておく、集計用の表を別に用意する、といった方法である。

非正規化は性能と引き換えに、更新時異常を防ぐ責任をアプリケーションやトリガに負わせる。また、注文時点の商品価格のように、後で商品の価格が変わっても変えてはならない値を明細に複製するのは、非正規化ではなく、別の事実（その時点の価格）を記録する正しい設計である。重複が「同じ事実の重複」か「別の事実」かを見極めることが重要である。

11.5. インデックス

11.5.1. B+ 木

インデックスが無い表から条件に合う行を探すには、すべての行を調べる全件走査が必要であり、時間計算量は行数 \(N\) に対して \(O(N)\) になる。インデックス（索引）は、特定の列の値から行の位置を素早く引くための補助的なデータ構造である。

多くの DBMS は、インデックスに B+ 木を使う。B+ 木は、「データ構造」の二分探索木を一般化した平衡木で、1 つの節点に多数のキーを持つ。主な特徴は次のとおりである。

  • 1 つの節点は補助記憶の 1 ページ（数 KB〜十数 KB）に対応し、数百個のキーと子へのポインタを格納する。1 つの節点が持つ子の数を分岐数と呼ぶ。

  • 内部節点はキーと子へのポインタだけを持ち、行の位置（または行そのもの）は葉にだけ格納する。

  • すべての葉は根から同じ深さにあり、挿入や削除の際に節点の分割・併合を行って平衡を保つ。

  • 葉どうしはキーの順に連結リストでつながっており、範囲検索や並べ替えでは葉を順にたどればよい。

分岐数を \(m\) とすると、木の高さは \(O(\log_m N)\) であり、検索・挿入・削除の時間計算量はいずれも \(O(\log N)\) である。範囲検索は、条件に合う行の数を \(k\) として \(O(\log N + k)\) で行える。分岐数が大きいので木は非常に低い。例えば \(m = 500\) なら、高さ 3 の木で \(500^3 = 1.25 \times 10^8\) 個のキーを扱える。上位の節点は主記憶にキャッシュされることが多いため、1 回の検索で補助記憶を読む回数は数回で済む。二分探索木ではなく B+ 木を使うのは、補助記憶の読み出しがページ単位で行われ、1 回の読み出しの遅延が大きいからである（「コンピュータの構成」のメモリ階層を参照）。詳しい構造は [CLRS] の B 木の章を参照。

インデックスは検索を速くする代わりに、格納領域を消費し、行の挿入・更新・削除のたびにインデックスも更新する必要があるため書き込みを遅くする。よく検索条件や結合条件に使われる列に絞って作成する。なお、多くの DBMS は主キーや UNIQUE 制約に対して自動的にインデックスを作る。SQLite では、表自体も rowid（INTEGER PRIMARY KEY の列はその別名になる）をキーとする B 木の一種に格納される [SQLite]。

11.5.3. インデックスが効かない典型例

インデックスを作っても、問い合わせの書き方によっては使われない。代表的な例を次に示す。

  • 列に関数や演算を適用する: lower(customer) = 'c01234' や amount * 2 > 100 は、インデックスに格納された値そのものと比較できないため、全件走査になる（実行結果の 8 行目）。式そのものに対するインデックス（式インデックス）を作るか、amount > 50 のように列を裸のまま比較する形に書き換える。

  • 先頭にワイルドカードがある LIKE: LIKE '%1234' は、値の先頭が決まらないので B+ 木をたどれない（実行結果の 9 行目）。全文検索用の機能を使う必要がある。

  • 複合インデックスの先頭の列を使わない: (a, b) の順に作った複合インデックスは、a で並べた後に b で並べた構造なので、b だけの条件では基本的に使えない。電話帳を名で引けないのと同じである。

  • 型の不一致: 文字列の列を数値と比較するなど、暗黙の型変換が必要な比較では、インデックスが使われないことがある。

  • 選択性が低い: 性別のように値の種類が少ない列では、インデックスで絞り込んでも大部分の行を読むことになるため、オプティマイザは全件走査を選ぶことがある。

注釈

SQLite の LIKE は既定で ASCII の英字の大文字・小文字を区別しない。そのため、LIKE 'C01%' のような前方一致であっても、通常の（大文字・小文字を区別する）インデックスは使われない。他の DBMS では前方一致の LIKE にインデックスが使われることが多いが、照合順序などの条件がある。インデックスが使われるかどうかは推測せず、実行計画で確認することが大切である。

11.6. 結合のアルゴリズムとクエリ最適化

関係代数の節で述べたように、SQL の問い合わせは「何がほしいか」を宣言するだけであり、結合を「どのように」計算するかは DBMS が決める。ここでは、関係 \(R\)（\(N\) 行）と関係 \(S\)（\(M\) 行）を R.k = S.k という条件で結合する等価結合を例に、代表的な 4 つの結合方式と、その中から方式を選ぶ仕組みを説明する。計算量の考え方は「アルゴリズムと計算量」の O 記法に従う。

11.6.1. 入れ子ループ結合

最も単純な方式が入れ子ループ結合（nested loop join）である。外側のループで \(R\) の各行を取り出し、内側のループで \(S\) の全行と結合条件を比較する。比較の回数は常に \(NM\) であり、時間計算量は \(O(NM)\) である。1 万行どうしの結合なら 1 億回の比較になる。

その代わり、結合条件が等号でなくてもよく、R.start <= S.t AND S.t < R.end のような任意の条件に使える。また、一方の表が数行しかない場合には、準備の手間が無いこの方式が最も速いこともある。実際の DBMS は、外側の表を 1 行ずつではなく主記憶に読み込めるだけまとめて読み、そのまとまりごとに内側の表を 1 回走査する（ブロック入れ子ループ結合）ことで、内側の表を補助記憶から読む回数を減らしている。

11.6.2. インデックスを使う入れ子ループ結合

内側の表 \(S\) の結合列にインデックスがあれば、内側のループで全行を調べる代わりに、インデックスで一致する行を直接探せる。B+ 木のインデックスなら 1 回の検索は \(O(\log M)\) なので、全体の時間計算量は \(O(N \log M)\) になる（一致する行の数を除く）。これをインデックス入れ子ループ結合と呼ぶ。

この方式は、外側の行が少ないときに特に有効である。例えば「顧客 C01234 の注文と、その注文の商品名」を求める問い合わせでは、WHERE で絞り込んだ数件の注文それぞれについて、商品表の主キーのインデックスを引けばよい。商品表がどれほど大きくても、読むのは数件分のページだけで済む。逆に、外側の行が多いと、インデックスの検索が毎回ランダムな位置のページを読むため、次に述べる方式より遅くなることがある。

11.6.3. ハッシュ結合

ハッシュ結合（hash join）は、「データ構造」のハッシュ表を使う方式であり、2 つの段階からなる。

  1. 構築: 小さい方の表（ここでは \(S\)）の全行を読み、結合列の値をキーとするハッシュ表を主記憶に作る。

  2. 探索: もう一方の表 \(R\) の各行について、結合列の値でハッシュ表を引き、一致する行と結合する。

ハッシュ表の挿入と検索は平均 \(O(1)\) なので、時間計算量は平均 \(O(N + M)\) である。インデックスが無い大きな表どうしの等価結合では、最も速いことが多い。ただし、ハッシュ値は値の一致しか判定できないので、不等号の条件には使えない。また、構築側の表が主記憶に収まらない場合は、両方の表を結合列のハッシュ値で複数の区画に分割して補助記憶に書き出し、区画ごとに結合する。このように分割しても、各行を読み書きする回数は定数回で済む。

11.6.4. ソートマージ結合

ソートマージ結合（sort-merge join）は、両方の表を結合列でソートしてから、「マージソート」のマージと同じように、2 つの列の先頭から並行にたどって値の一致する行を突き合わせる方式である。ソートに \(O(N \log N + M \log M)\)、マージに \(O(N + M)\) かかるので、全体では \(O(N \log N + M \log M)\) である（同じキーを持つ行が両側に多数ある場合は、出力の行数に比例する時間が加わる）。

ソートの手間がかかるので、何も前提が無ければハッシュ結合より遅いことが多い。しかし、両方の表が結合列のインデックスによってすでに順序どおりに読める場合や、問い合わせの ORDER BY のためにどのみちソートが必要な場合には、マージの \(O(N + M)\) だけで済む。結果がキーの順に出てくるため、後続の処理でソートを省ける利点もある。

 22

 27def nested_loop(r: list[Row], s: list[Row], c: Counter) -> list[Pair]:
 28    """R の各行について S の全行と比較する。"""
 29    result = []
 30    for rk, rv in r:
 31        for sk, sv in s:
 32            c.count += 1
 33            if rk == sk:
 34                result.append((rv, sv))
 35    return result

 38def index_nested_loop(r: list[Row], s: list[Row],
 39                      c: Counter) -> list[Pair]:
 40    """S のキーの索引（ソート済み配列）を二分探索で引く。
 41
 42    S のキーは一意（主キー）と仮定する。索引の構築は事前に
 43    済んでいるものとして数えない。
 44    """
 45    index = sorted(s)
 46    result = []
 47    for rk, rv in r:
 48        lo, hi = 0, len(index)
 49        while lo < hi:  # 二分探索
 50            mid = (lo + hi) // 2
 51            c.count += 1
 52            if index[mid][0] < rk:
 53                lo = mid + 1
 54            else:
 55                hi = mid
 56        if lo < len(index) and index[lo][0] == rk:
 57            result.append((rv, index[lo][1]))
 58    return result
 59
 60
 61def hash_join(r: list[Row], s: list[Row], c: Counter) -> list[Pair]:
 62    """小さい S からハッシュ表を作り（構築）、R の各行で引く（探索）。"""
 63    table: defaultdict[int, list[int]] = defaultdict(list)
 64    for sk, sv in s:  # 構築: S の行数だけ挿入する
 65        c.count += 1
 66        table[sk].append(sv)
 67    result = []
 68    for rk, rv in r:  # 探索: R の行数だけ引く
 69        c.count += 1
 70        for sv in table.get(rk, []):
 71            result.append((rv, sv))
 72    return result
 73
 74
 75def sort_merge(r: list[Row], s: list[Row], c: Counter) -> list[Pair]:
 76    """両方をキーでソートし、先頭から並行にたどって突き合わせる。"""
 77    def cmp(x: Row, y: Row) -> int:
 78        c.count += 1
 79        return (x[0] > y[0]) - (x[0] < y[0])
 80
 81    rs = sorted(r, key=cmp_to_key(cmp))
 82    ss = sorted(s, key=cmp_to_key(cmp))
 83    result = []
 84    i = j = 0
 85    while i < len(rs) and j < len(ss):
 86        c.count += 1
 87        if rs[i][0] < ss[j][0]:
 88            i += 1
 89        elif rs[i][0] > ss[j][0]:
 90            j += 1
 91        else:  # S のキーは一意なので、R 側だけを進める
 92            result.append((rs[i][1], ss[j][1]))
 93            i += 1
 94    return result

11.6.5. コストベースのクエリ最適化

1 つの問い合わせを実行する手順を実行計画と呼ぶ。実行計画には、各表をどのように読むか（全件走査か、どのインデックスを使うか）、どの順に結合するか、それぞれの結合にどの方式を使うか、といった選択が含まれる。候補は非常に多い。結合順序だけでも、\(n\) 個の表を 1 つずつ順に結合する並べ方は \(n!\) 通りあり、10 個の表なら約 363 万通りになる。

多くの DBMS は、候補となる実行計画ごとに、読むページの数や処理する行の数から実行にかかる費用（コスト）を見積もり、最も安いものを選ぶ。これをコストベース最適化と呼ぶ。すべての候補を調べることはできないので、「アルゴリズムと計算量」の動的計画法を使って、部分的な結合の最良の計画を表に記録しながら組み立てたり、表の数が多いときは探索を打ち切ったりする。

コストの見積もりで最も重要なのは、各段階で何行が残るかの推定である。この推定には、DBMS が表ごとに保持する統計情報を使う。統計情報には、表の行数とページ数、列ごとの異なる値の数、NULL の割合、値の分布を表すヒストグラムなどが含まれる。例えば、列 customer に 5 万種類の値があり、表が 20 万行なら、customer = ? の条件で残る行は約 \(200000 / 50000 = 4\) 行と推定でき、インデックスを使う計画が有利だと判断できる。前節で述べた「選択性が低い列ではインデックスが使われない」ことも、この見積もりの結果である。

統計情報は、データを変更するたびに自動で正確に保たれるわけではない。統計情報を集め直すのが ANALYZE 文である。PostgreSQL の ANALYZE は表の標本を調べて統計情報を更新し（自動実行の仕組みもある）、SQLite の ANALYZE は結果を sqlite_stat1 などの内部の表に保存してオプティマイザが参照する [SQLite]。大量のデータを読み込んだ直後などに統計情報が古いままだと、オプティマイザは行数を大きく見誤り、ハッシュ結合を使うべきところで入れ子ループ結合を選ぶといった極端に遅い計画を選ぶことがある。

遅い問い合わせを調べるときは、まず EXPLAIN で実行計画を確認する。PostgreSQL の EXPLAIN ANALYZE のように実際に実行して各段階の実際の行数を表示する機能があれば、推定行数と実際の行数を比べる。両者が桁違いにずれている箇所があれば、統計情報が古いか、列どうしの相関のように統計情報では表しにくい性質が原因であることが多い。

11.7. トランザクション

11.7.1. ACID 特性

トランザクションは、データベースに対する一連の操作をひとまとまりとして扱う単位である。口座 A から口座 B への送金は「A の残高を減らす」と「B の残高を増やす」の 2 つの更新からなるが、片方だけが実行されると、お金が消えたり増えたりしてしまう。トランザクションは BEGIN で始まり、COMMIT（確定）または ROLLBACK（取り消し）で終わる。

トランザクションが満たすべき性質は、頭文字をとって ACID 特性と呼ばれる。

  • 原子性（Atomicity）: トランザクションの操作は、すべて実行されるか、まったく実行されないかのどちらかである。途中で失敗したら、それまでの変更を取り消す。

  • 一貫性（Consistency）: トランザクションの前後で、データベースは整合性制約（主キー、外部キー、CHECK 制約など）を満たす。

  • 分離性（Isolation）: 同時に実行される複数のトランザクションが、互いに干渉しない。理想的には、何らかの順に 1 つずつ実行した場合と同じ結果になる。

  • 永続性（Durability）: コミットされたトランザクションの結果は、その後に障害が起きても失われない。

11.7.2. 同時実行時の異常

多数のトランザクションを 1 つずつ順番に実行すれば分離性は自明に保たれるが、それでは性能が出ない。並行に実行すると、分離が不十分な場合に次のような異常が起きる。ここでは 2 つのトランザクションを T1、T2 とする。

  • ダーティリード（dirty read）: T1 がまだコミットしていない変更を T2 が読む。その後 T1 がロールバックすると、T2 は存在しなかった値に基づいて処理したことになる。

  • ファジーリード（fuzzy read、ノンリピータブルリードとも呼ぶ）: T1 が同じ行を 2 回読む間に、T2 がその行を更新してコミットする。T1 の 1 回目と 2 回目で値が異なる。

  • ファントムリード（phantom read）: T1 が条件に合う行の集合を 2 回読む間に、T2 がその条件に合う行を挿入（または削除）してコミットする。T1 の 2 回目の読み出しで、1 回目に無かった行（幻の行）が現れる。

このほか、2 つのトランザクションが同じ値を読んで更新し、一方の更新が上書きされて失われる更新の喪失（lost update）もよく知られた異常である。

11.7.4. ロックと MVCC

分離性を実現する代表的な方法がロックである。読み出しには共有ロック、書き込みには排他ロックを取得し、排他ロックは他のロックと同時に保持できないようにする。トランザクションがロックを取得する段階と解放する段階を分け、一度解放を始めたら新たにロックを取得しない方式を二相ロック（2PL: Two-Phase Locking）と呼び、これによって直列化可能性が保証される（ファントムリードまで防ぐには、個々の行だけでなく検索条件に当たる範囲もロックする必要がある）。ロックを使うと、「並行処理と入出力」で学んだデッドロックが起こりうる。DBMS は、どのトランザクションがどのトランザクションのロックを待っているかを表す待ちグラフを管理し、閉路が生じたらデッドロックと判断して、閉路上の 1 つのトランザクションを強制的にロールバックする。ロールバックされた側のアプリケーションにはエラーが返るので、トランザクションを最初からやり直す処理を用意しておく。

ロックだけで分離を実現すると、読み出しと書き込みが互いを待たせる。そこで多くの DBMS は MVCC（Multi-Version Concurrency Control、多版型同時実行制御）を採用している。MVCC では、行を更新するときに古い版を残したまま新しい版を作る。各トランザクションは、開始時点（または文の開始時点）にコミット済みだった版からなるスナップショットを読むため、読み出しは書き込みを待たず、書き込みも読み出しを待たない。不要になった古い版は後で回収する（PostgreSQL の VACUUM など）。書き込みどうしの衝突は、ロックや衝突の検出によって別に処理する。

11.7.5. 楽観的ロックと悲観的ロック

ロックや MVCC は DBMS の内部で分離性を実現する仕組みだが、アプリケーションの書き方によっては、それだけでは防げない異常がある。その代表が、前に挙げた更新の喪失である。ここでは、アプリケーションの側から更新の喪失を防ぐ 2 つの考え方を説明する。

11.7.5.1. 更新の喪失の例

在庫が 10 個の商品について、利用者 A が 3 個、利用者 B が 5 個の注文を同時に処理する場合を考える。アプリケーションが「在庫を読む」「新しい在庫を計算する」「書き戻す」の 3 段階で処理すると、次の順に実行されたとき、A の更新が失われる。

  1. A が在庫を読む（10 個）。

  2. B が在庫を読む（10 個）。

  3. A が \(10 - 3 = 7\) を書き込む。

  4. B が \(10 - 5 = 5\) を書き込む。A が書いた 7 は上書きされる。

正しい在庫は 2 個のはずだが、5 個になってしまう。これは「並行処理と入出力」の競合状態と同じ構造である。UPDATE item SET stock = stock - 3 WHERE id = 1 のように、読み出しと書き込みを 1 つの SQL 文で行えば、DBMS がその文を不可分に実行するので更新は失われない。しかし、読んだ値を画面に表示して利用者に編集させてから保存する場合のように、読み出しと書き込みの間にアプリケーションの処理や利用者の操作が挟まる場合は、この方法を使えない。特に Web アプリケーションでは、読み出しと書き込みが別々の HTTP リクエストになり、別々のトランザクションで実行されるので、DBMS の分離レベルでは防げない。

11.7.5.2. 悲観的ロック

悲観的ロック（pessimistic locking）は、競合が起きるものと考え、データを読む時点でロックを取得して、他者が更新できないようにする方法である。多くの DBMS では SELECT ... FOR UPDATE を使う。

1BEGIN;
2SELECT stock FROM item WHERE id = 1 FOR UPDATE;
3UPDATE item SET stock = 7 WHERE id = 1;
4COMMIT;

2 行目の FOR UPDATE は、読んだ行に排他的なロックを掛ける。ロックは 4 行目でトランザクションが終わるまで保持され、その間に別のトランザクションが同じ行を FOR UPDATE で読もうとしたり更新しようとしたりすると、待たされる。B は A のコミット後に 7 を読むことになるので、更新は失われない。

SQLite には SELECT ... FOR UPDATE が無い。SQLite のロックはデータベース全体を単位とするので、トランザクションを BEGIN IMMEDIATE で開始して、最初に書き込みのためのロックを取得する。ある接続が BEGIN IMMEDIATE で開始したトランザクションを終えるまで、他の接続は BEGIN IMMEDIATE や書き込みを始められず、待つか database is locked のエラーになる（読み出しは続けられる）[SQLite]_。

悲観的ロックは確実だが、ロックを保持している間は他者が待たされる。ロックを保持したまま利用者の入力を待つと、利用者が席を外しただけで他の全員が止まってしまう。また、複数の行を異なる順にロックするとデッドロックが起こりうる。

11.7.5.3. 楽観的ロック

楽観的ロック（optimistic locking）は、競合はめったに起きないものと考え、読むときにはロックを取らず、書き込むときに「読んだ後に他者が更新していないか」を確かめる方法である。実際にはロックを使わないので、楽観的同時実行制御とも呼ぶ。一般的な実装では、表に版数を表すバージョン列を加え、更新のたびに 1 増やす。

1SELECT stock, version FROM item WHERE id = ?;
2UPDATE item SET stock = ?, version = version + 1
3WHERE id = ? AND version = ?;

1 行目で在庫とバージョンを読み、2〜3 行目で、読んだときのバージョンを WHERE の条件に加えて更新する。読んだ後に他者が更新していればバージョンが変わっているので、条件に一致する行が無く、更新件数は 0 になる。アプリケーションは更新件数を調べ、0 なら競合が起きたと判断して、最新の値を読み直して処理をやり直すか、「他の利用者が先に更新した」ことを利用者に伝える。条件の確認と更新は 1 つの UPDATE 文の中で行われるので、確認と更新の間に他者が割り込むことはない。

次のサンプルは、2 つの接続 A と B で同じ商品の在庫を減らす処理を、上の例と同じ順序で実行する。ロックなしの場合、悲観的ロックの場合、楽観的ロックの場合を順に示す。

  2
  31 つのデータベースファイルに 2 つの接続 A と B を開き、同じ商品の
  4在庫を同時に減らす状況を、処理の順序を固定して再現する。
  5
  61. ロックなし: 両者が同じ値を読んで書き戻し、一方の更新が失われる。
  72. 悲観的ロック: BEGIN IMMEDIATE で書き込みロックを先に取得する。
  83. 楽観的ロック: バージョン列を条件に UPDATE し、更新件数が 0 なら
  9   競合とみなして読み直し、再試行する。
 10

 13"""
 14
 15import sqlite3
 16import tempfile
 17from pathlib import Path
 18
 19
 20def connect(path: Path) -> sqlite3.Connection:
 21    """自動コミットモードで接続する（トランザクションは明示的に書く）。
 22
 23    timeout=0 なので、ロックを取得できないときは待たずに例外になる。
 24    """
 25    return sqlite3.connect(path, timeout=0, isolation_level=None)
 26
 27
 28def reset(path: Path) -> None:
 29    """商品表を作り直し、在庫 10、バージョン 1 の商品を登録する。"""
 30    conn = connect(path)
 31    conn.execute("DROP TABLE IF EXISTS item")
 32    conn.execute(
 33        "CREATE TABLE item (id INTEGER PRIMARY KEY,"
 34        " stock INTEGER NOT NULL, version INTEGER NOT NULL)")
 35    conn.execute("INSERT INTO item VALUES (1, 10, 1)")
 36    conn.close()
 37
 38
 39def read_item(conn: sqlite3.Connection) -> tuple[int, int]:
 40    """商品 1 の（在庫, バージョン）を返す。"""
 41    row = conn.execute(
 42        "SELECT stock, version FROM item WHERE id = 1").fetchone()
 43    return int(row[0]), int(row[1])
 44
 45
 46def lost_update(path: Path) -> None:
 47    """A が 3 個、B が 5 個を減らす。どちらも古い値をもとに書き戻す。"""
 48    a, b = connect(path), connect(path)
 49    stock_a, _ = read_item(a)  # A が 10 を読む
 50    stock_b, _ = read_item(b)  # B も 10 を読む
 51    a.execute("UPDATE item SET stock = ? WHERE id = 1", (stock_a - 3,))
 52    b.execute("UPDATE item SET stock = ? WHERE id = 1", (stock_b - 5,))
 53    print(f"最終在庫: {read_item(a)[0]}（正しくは 2）")
 54    a.close()
 55    b.close()
 56
 57
 58def pessimistic(path: Path) -> None:
 59    """BEGIN IMMEDIATE で書き込みロックを取ってから読み、更新する。"""
 60    a, b = connect(path), connect(path)
 61    a.execute("BEGIN IMMEDIATE")  # A が書き込みロックを取得する
 62    stock_a, _ = read_item(a)
 63    try:
 64        b.execute("BEGIN IMMEDIATE")  # B はロックを取得できない
 65    except sqlite3.OperationalError as e:
 66        print(f"B: {e}（A のコミットを待つ）")
 67    a.execute("UPDATE item SET stock = ? WHERE id = 1", (stock_a - 3,))
 68    a.execute("COMMIT")
 69    b.execute("BEGIN IMMEDIATE")  # A の終了後なら取得できる
 70    stock_b, _ = read_item(b)  # A の更新後の値 7 を読む
 71    b.execute("UPDATE item SET stock = ? WHERE id = 1", (stock_b - 5,))
 72    b.execute("COMMIT")
 73    print(f"最終在庫: {read_item(a)[0]}")
 74    a.close()
 75    b.close()
 76
 77
 78def decrement_optimistic(conn: sqlite3.Connection, name: str, amount: int,
 79                         snapshot: tuple[int, int],
 80                         max_retries: int = 3) -> None:
 81    """読み出し時のバージョンを条件に在庫を減らす。
 82
 83    更新件数が 0 なら、読んだ後に他者が更新したと判断して読み直す。
 84    """
 85    stock, version = snapshot
 86    for attempt in range(1, max_retries + 1):
 87        cur = conn.execute(
 88            "UPDATE item SET stock = ?, version = version + 1"
 89            " WHERE id = 1 AND version = ?", (stock - amount, version))
 90        if cur.rowcount == 1:
 91            print(f"{name}: {attempt} 回目で成功"
 92                  f"（在庫 {stock} -> {stock - amount}、"
 93                  f"バージョン {version} -> {version + 1}）")
 94            return
 95        print(f"{name}: {attempt} 回目は更新件数 0"
 96              f"（バージョン {version} は古い）")
 97        stock, version = read_item(conn)  # 最新の値を読み直す
 98    raise RuntimeError("再試行の上限に達した")
 99
100
101def optimistic(path: Path) -> None:
102    """A と B が同じバージョンを読み、先に更新した A だけが成功する。"""
103    a, b = connect(path), connect(path)
104    snap_a = read_item(a)  # A が (10, 1) を読む
105    snap_b = read_item(b)  # B も (10, 1) を読む
106    decrement_optimistic(a, "A", 3, snap_a)
107    decrement_optimistic(b, "B", 5, snap_b)
108    print(f"最終在庫: {read_item(a)[0]}")
109    a.close()
110    b.close()
111
112
113def main() -> None:
114    """3 つの方式を順に実行する。"""
115    with tempfile.TemporaryDirectory() as tmp:
116        path = Path(tmp) / "shop.db"
117        for title, demo in [("ロックなし（更新の喪失）", lost_update),
118                            ("悲観的ロック", pessimistic),
119                            ("楽観的ロック", optimistic)]:
120            print(f"[{title}]")
121            reset(path)
122            demo(path)
123
124
125if __name__ == "__main__":
126    main()

25 行目で isolation_level=None を指定して、sqlite3 モジュールが自動的にトランザクションを開始しないようにし、トランザクションを BEGIN と COMMIT で明示的に書けるようにしている。timeout=0 は、ロックを取得できないときに待たずに例外を発生させる指定である。46〜55 行目の lost_update は、49〜50 行目で両者が在庫を読んだ後、51〜52 行目でそれぞれ計算した値を書き戻す。58〜75 行目の pessimistic では、61 行目で A が BEGIN IMMEDIATE によってロックを取得しているので、64 行目の B の BEGIN IMMEDIATE は失敗する。B は A のコミット（68 行目）の後にロックを取得し直し、A の更新後の値を読む。78〜98 行目の decrement_optimistic は、87〜89 行目でバージョンを条件とする UPDATE を実行し、90 行目で更新件数を確かめる。更新件数が 0 なら、97 行目で最新の値を読み直して再試行する。実行結果は次のとおりである。

 1[ロックなし（更新の喪失）]
 2最終在庫: 5（正しくは 2）
 3[悲観的ロック]
 4B: database is locked（A のコミットを待つ）
 5最終在庫: 2
 6[楽観的ロック]
 7A: 1 回目で成功（在庫 10 -> 7、バージョン 1 -> 2）
 8B: 1 回目は更新件数 0（バージョン 1 は古い）
 9B: 2 回目で成功（在庫 7 -> 2、バージョン 2 -> 3）
10最終在庫: 2

実行結果の 2 行目は、ロックなしでは A の更新が失われることを示す。4 行目は、悲観的ロックでは B がロックを取得できずに待たされること（このサンプルでは待つ代わりにエラーにしている）を示す。7〜9 行目では、A と B はどちらもバージョン 1 を読んでいるが、先に更新した A がバージョンを 2 に上げたので、B の 1 回目の UPDATE は条件に一致せず、更新件数が 0 になる。B は在庫 7、バージョン 2 を読み直して再試行し、成功する。どちらの方式でも最終在庫は正しく 2 になる。

11.7.6. ログによる障害回復

原子性と永続性を障害時にも保つために、DBMS はログを使う。代表的な方式はログ先行書き込み（WAL: Write-Ahead Logging）である。データのページを補助記憶に書き込む前に、「どのページをどう変更したか」を記録したログを先に補助記憶へ書き出す。コミットは、そのトランザクションのログが補助記憶に確実に書き込まれた（fsync などで永続化された）時点で完了とみなす。

障害の後に再起動すると、DBMS はログを読み、コミット済みのトランザクションのうちデータファイルに反映されていない変更をやり直し（REDO）、コミットされていないトランザクションの変更を取り消す（UNDO）。ログが際限なく伸びないよう、ある時点までの変更をデータファイルに反映したことを記録するチェックポイントを定期的に作る。ログは追記だけで書けるため、ランダムな位置にあるデータページをその都度書き込むより速いという利点もある。さらに、fsync は装置への書き込みを待つため遅いので、同時期にコミットされた複数のトランザクションのログをまとめて 1 回の fsync で永続化するグループコミットによって、fsync の回数を減らす。SQLite は、変更前の内容を保存するロールバックジャーナル方式と、WAL 方式のどちらかを選べる [SQLite]。

11.9. まとめ

  • DBMS は、データの格納・検索、同時実行の制御、障害からの回復を引き受け、データの論理構造と物理的な格納方法を分離する。

  • 関係モデルではデータをタプルの集合である関係として表す。主キーはタプルを一意に識別し、外部キーは他の関係の主キーを参照して参照整合性を保つ。

  • 関係代数の選択・射影・結合は、SQL の WHERE、SELECT の列指定、JOIN にほぼ対応する。

  • SQL の NULL との比較は UNKNOWN になる。NULL の判定には IS NULL を使い、NOT IN の落とし穴に注意する。

  • SQL に外部からの値を含めるときはプレースホルダを使い、SQL インジェクションを防ぐ。

  • 正規化は関数従属に着目して表を分割し、更新時異常を取り除く。性能のために意図的に非正規化することもある。

  • B+ 木のインデックスは検索を \(O(\log N)\) にするが、書き込みを遅くする。列に関数を適用するなど、インデックスが使われない書き方があるので、実行計画で確認する。

  • 結合には入れ子ループ結合（\(O(NM)\)）、インデックス入れ子ループ結合（\(O(N \log M)\)）、ハッシュ結合（平均 \(O(N + M)\)）、ソートマージ結合（\(O(N \log N + M \log M)\)）などの方式がある。オプティマイザは統計情報をもとにコストを見積もって実行計画を選ぶので、ANALYZE で統計情報を新しく保つ。

  • トランザクションは ACID 特性を満たす。分離レベルは許容する異常の種類で決まり、実際の振る舞いは DBMS ごとに異なる。

  • 分離はロックや MVCC で、原子性と永続性はログ先行書き込みなどのログで実現される。

  • 読み出しと書き込みの間にアプリケーションの処理が挟まると、更新の喪失が起こりうる。悲観的ロック（SELECT ... FOR UPDATE、SQLite では BEGIN IMMEDIATE）は読む時点でロックし、楽観的ロックはバージョン列を条件に更新して、更新件数が 0 なら再試行する。

  • 用途によっては、キーバリューストアやドキュメントデータベースなど RDB 以外のデータベースが適する。
