7. プログラミング言語処理系

この章では、私たちが書いたプログラムが、どのようにして計算機で実行できる形になり、実行されるのかを学ぶ。まず、プログラムの書き方の流儀であるプログラミングパラダイムと、プログラムの誤りを実行前に見つける仕組みである型システムを概観し、1 つのコードを複数の型に使うための多相とジェネリクスを学ぶ。次に、コンパイラとインタプリタがソースコードを処理する流れを追い、CPython が生成するバイトコードを実際に観察する。さらに、処理の入口である字句解析と構文解析を、四則演算の式を評価する小さなインタプリタを作りながら詳しく見る。続いて、コンパイルされた部品を 1 つの実行ファイルにまとめるリンカと、それを読み込んで実行を始めるローダを扱う。最後に、実行時のメモリ管理、関数呼び出しにおける名前の解決、例外処理の仕組みを扱う。

字句解析と構文解析は、第 6 章「計算理論」で学んだ正規言語と文脈自由文法の応用である。本章では理論の説明は繰り返さず、それが処理系でどう使われるかに焦点を当てる。コンパイラについてより詳しく学びたい場合は [Dragon] を、プログラムの構造と解釈について学びたい場合は [SICP] を参照するとよい。

7.1. プログラミングパラダイム

プログラミングパラダイムとは、プログラムをどのような考え方で組み立てるかという流儀である。代表的なパラダイムを次の表に示す。

パラダイム

考え方

代表的な言語・技術

手続き型

状態（変数）を変更する命令を順に並べて処理を記述する

C、Pascal、シェルスクリプト

オブジェクト指向

データとそれを操作する手続きをオブジェクトとしてまとめ、オブジェクト同士のやり取りとして処理を記述する

Java、C#、Smalltalk

関数型

値を受け取って値を返す関数の組み合わせとして処理を記述し、状態の変更を避ける

Haskell、OCaml、Lisp 系言語

宣言型

「どのように求めるか」ではなく「何を求めるか」を記述し、手順は処理系に任せる

SQL、正規表現、HTML、Prolog

手続き型は、第 3 章「コンピュータの構成」で学んだ CPU の動作（メモリの値を読み、計算し、書き戻す）に最も近いパラダイムである。オブジェクト指向では、カプセル化（内部の状態を隠し、決められた操作だけを公開する）、継承、ポリモーフィズム（同じ呼び出しで、オブジェクトの種類に応じた処理を行う）によって、大きなプログラムを部品に分けて管理しやすくする。

関数型プログラミングでは、同じ引数に対して常に同じ値を返し、外部の状態を変更しない純粋関数を中心にプログラムを組み立てる。関数を値として受け渡す高階関数や、一度作った値を変更しない不変なデータ構造をよく使う。状態の変更がないので、プログラムの一部を切り出してテストしたり、並列に実行したりしやすい。

宣言型の典型は SQL である。SELECT name FROM users WHERE age >= 20 は「20 歳以上のユーザの名前」という結果の条件だけを書いており、表をどの順で読むか、索引を使うかといった手順はデータベース管理システムが決める（第 11 章「データベース」を参照）。論理型（Prolog など）は宣言型の一種であり、関数型を宣言型に含めることもある。

これらは排他的なものではなく、Python、JavaScript、Scala、Rust など現代の多くの言語は複数のパラダイムを取り入れている。例えば、Python で 1 から 10 までの偶数の 2 乗の和を求める処理は、次のように手続き型でも関数型の流儀でも書ける。

1# 手続き型: 変数 total を更新していく
2total = 0
3for i in range(1, 11):
4    if i % 2 == 0:
5        total += i * i
6
7# 関数型の流儀: 状態を変更せず、式の組み合わせで書く
8total = sum(i * i for i in range(1, 11) if i % 2 == 0)

パラダイムは問題に応じて使い分けるものであり、どれか 1 つが常に優れているわけではない。

7.2. 型システム

型とは、値の種類と、その値に許される操作を定めたものである。例えば整数どうしは足し算できるが、整数と関数を足すことには意味がない。言語の型システムは、プログラム中の式に型を割り当て、型の合わない操作（型エラー）を検出する規則の集まりである。

7.2.1. 静的型付けと動的型付け

型の検査をいつ行うかによって、言語は大きく 2 つに分けられる。

静的型付けの言語（C、Java、Rust、Go、Haskell など）では、プログラムを実行する前（コンパイル時）に型を検査し、型エラーがあればプログラムを実行させない。変数や式の型は実行前に決まっている。動的型付けの言語（Python、Ruby、JavaScript など）では、型は変数ではなく実行時の値が持ち、型の検査は操作を実行する時点で行う。

観点

静的型付け

動的型付け

型エラーの検出

実行前に、実行されない分岐も含めて検出できる

その操作が実際に実行されるまで検出されない

性能

型に応じた機械語を生成でき、高速にしやすい

実行時に型を調べる手間がかかる

記述の手軽さ

型の記述が必要な場合がある

型を書かずに済み、試行錯誤しやすい

開発支援

補完、リファクタリング、定義へのジャンプが正確に行える

ツールが型を推測する必要があり、精度が劣る

静的型付けでも、すべての誤りを実行前に検出できるわけではない。第 6 章の「実務への影響」で述べたように、プログラムの振る舞いに関する自明でない性質は判定不能なので、型検査器は「型エラーが起こりうる」プログラムを安全側に倒して拒否する。そのため、実行すれば問題なく動くプログラムが型検査を通らないこともある。

注釈

言語を「強い型付け」と「弱い型付け」に分類することもあるが、この用語には広く合意された定義がない。暗黙の型変換が多い言語を「弱い」と呼ぶことが多いが、どの程度で「弱い」とするかは論者によって異なる。例えば JavaScript では "1" + 1 が文字列 "11" になるが、Python では TypeError になる。C では整数をポインタに変換するような、型の安全性を損なう操作が許される。議論の際は「強い・弱い」という言葉を使わず、「どのような暗黙の型変換を許すか」「型の安全性を破る操作ができるか」のように具体的に述べる方がよい。

7.2.2. 型推論

静的型付けの言語でも、すべての変数に型を書く必要があるとは限らない。型推論は、プログラムの書き方から式の型を処理系が自動的に導く機能である。例えば Rust の let x = 1 + 2; では、x の型を書かなくても整数型と推論される。Java の var、C++ の auto、TypeScript、Kotlin、Go なども、局所的な型推論を備えている。Haskell や OCaml は、Hindley-Milner 型推論と呼ばれる方式により、関数の引数や戻り値の型まで含めて、ほとんど型を書かずに静的な型検査を受けられる。

7.2.3. Python の型ヒントと mypy

Python は動的型付けの言語であるが、関数の引数や戻り値、変数に型ヒント（型注釈）を書ける。型ヒントは実行時には検査されず、mypy のような外部の型検査器が実行前に検査する。このように、動的型付けの言語に、必要な箇所から段階的に静的な型検査を導入する考え方を漸進的型付けと呼ぶ。TypeScript も同じ考え方で JavaScript に型を導入している。

次の average.py を考える。

1def average(values: list[float]) -> float:
2    return sum(values) / len(values)
3
4
5print(average([1.0, 2.0, 3.0]))
6print(average("123"))

6 行目は文字列を渡しているので誤りである。このファイルを実行すると、5 行目で 2.0 が表示された後、6 行目の呼び出しの中の sum で TypeError が発生する。型ヒントがあってもプログラムは実行でき、誤りは実行時まで分からない。一方、mypy で検査すると、実行せずに誤りを指摘できる。

1$ python -m mypy --strict average.py
2average.py:6: error: Argument 1 to "average" has incompatible type "str"; expected "list[float]"  [arg-type]
3Found 1 error in 1 file (checked 1 source file)

本書のサンプルコードは、すべて mypy の strict モードで検査している。

7.2.4. 多相の 3 つの種類

静的型付けの言語では、型ごとに同じような関数を何度も書かずに済ませたい。1 つのコードを複数の型の値に対して使えるようにする性質を多相（ポリモーフィズム）と呼ぶ。前節のオブジェクト指向の説明で触れたポリモーフィズムは、その一種である。多相は、仕組みの違いから次の 3 種類に分けて考えると整理しやすい。

種類

考え方

例

パラメトリック多相

型を引数のように受け取り、どの型に対しても同じ 1 つのコードが同じように動く

Java・C# のジェネリクス、C++ のテンプレート、Rust・Haskell の型パラメータ

部分型多相

ある型を期待する場所に、その部分型（派生クラスなど）の値を渡せる。実際の処理は値の型に応じて実行時に選ばれる

継承とメソッドのオーバーライド、インタフェース

アドホック多相

同じ名前に、型ごとに別々の実装を用意する

関数や演算子のオーバーロード、Haskell の型クラス

パラメトリック多相の典型は「リストの先頭の要素を返す関数」である。この関数は、要素が整数でも文字列でも同じ処理をし、要素の型が何であるかに関心を持たない。そこで要素の型を \(T\) という変数（型パラメータ）で表し、「\(T\) のリストを受け取って \(T\) を返す」と書く。このように型パラメータを持つ関数や型を定義できる言語機能をジェネリクスと呼ぶ。list[int] と list[str] のように、list 自体も要素の型をパラメータとするジェネリックな型である。

部分型多相では、型 \(S\) が型 \(T\) の部分型であるとき、\(T\) の値を期待する場所に \(S\) の値を使える。例えば図形を表す Shape クラスに面積を求める area() があり、Circle と Square がそれを継承して別々に実装していれば、Shape を受け取る関数は、渡された値の実際のクラスに応じた area() を呼ぶ。どの実装を呼ぶかは実行時に決まる（動的ディスパッチ）。Python の typing.Protocol のように、継承関係ではなく「必要なメソッドを持っているか」で部分型を判定する方式を構造的部分型と呼ぶ。

アドホック多相は、名前は同じでも型ごとに中身が異なるものである。Python の + は整数では加算、文字列では連結を行う。Java や C++ では、引数の型が異なる同名の関数を複数定義でき（オーバーロード）、どれを呼ぶかはコンパイル時に引数の型から決まる。Python は引数の型による関数のオーバーロードを持たないが、__add__() などの特殊メソッドで演算子の意味を型ごとに定義できるほか、functools.singledispatch で第 1 引数の型に応じて実装を切り替えられる。

7.2.5. Python のジェネリクス

Python の型ヒントでも、型パラメータを使ったジェネリックな関数やクラスを書ける。以前は typing.TypeVar で型変数を作ってから使う必要があったが、Python 3.12 からは関数名やクラス名の直後に [T] と書く型パラメータ構文が使える。

 1from typing import TypeVar
 2
 3T = TypeVar("T")
 4
 5
 6def first_old(xs: list[T]) -> T:  # Python 3.11 までの書き方
 7    return xs[0]

10def first[T](xs: list[T]) -> T:  # Python 3.12 以降の書き方

7.2.6. ジェネリクスの実装方式

ジェネリクスを処理系がどのように実現するかには、大きく 2 つの方式がある。

1 つは型消去で、型パラメータはコンパイル時の型検査にだけ使い、検査が済んだら取り除いて、すべての型に共通の 1 つのコードを生成する。Java のジェネリクスはこの方式で、List<String> も List<Integer> も実行時には同じ List であり、要素は Object として扱われる。生成されるコードが 1 つで済み、ジェネリクス導入前のコードとの互換性も保てる。その代わり、実行時には型引数が分からないので、T の新しいインスタンスを作ったり、値が List<String> かどうかを実行時に調べたりできない。また、int のような基本型はそのままでは型引数にできず、オブジェクトに包む（ボクシング）必要がある。Python の型ヒントも、実行時にはほぼ無視される点で型消去に近い。Stack[int] と書いても、実行時に文字列を積むことは妨げられない。

もう 1 つは具体化（特殊化）で、使われた型引数ごとに専用のコードを生成する。C++ のテンプレートや Rust のジェネリクスはこの方式で、std::vector<int> と std::vector<double> はコンパイル時に別々のコードになる。それぞれの型に最適化された機械語が得られ、実行時の手間はかからないが、型引数の種類だけコードが増えて実行ファイルが大きくなり、コンパイルにも時間がかかる。C# は中間の方式をとり、実行時にも型引数の情報を保持したうえで、値型の型引数に対しては専用のコードを生成する。

7.3. コンパイラとインタプリタ

7.3.1. 処理系の 2 つの方式

CPU が直接実行できるのは機械語だけである（「コンピュータの構成」を参照）。人間が書いたソースコードを実行するには、それを機械語に変換するか、ソースコードを読みながら動作を真似するプログラムが必要になる。

コンパイラは、ソースコードを実行前にまとめて別の言語（多くの場合は機械語）に翻訳するプログラムである。翻訳結果は単独で実行でき、実行時には翻訳の手間がかからないので高速である。C、C++、Rust、Go などが典型的なコンパイル型の言語である。インタプリタは、ソースコード（またはそれを変換したもの）を読み込み、その意味に従って直接実行するプログラムである。翻訳の待ち時間がなく、インタプリタさえ用意すれば CPU の種類によらず同じソースコードを実行できる代わりに、実行速度は一般に遅い。

もっとも、現実の処理系の多くは、この 2 つを組み合わせている。後で見るように、CPython はソースコードをいったんバイトコードにコンパイルしてから、それをインタプリタで実行する。言語そのものが「コンパイル型」か「インタプリタ型」かが決まっているわけではなく、それは処理系の実装方式の違いである。

7.3.2. コンパイラの処理の流れ

コンパイラは、ソースコードを次のような段階を順に経て処理する。前半の字句解析から意味解析までをフロントエンド、後半のコード生成をバックエンドと呼ぶ（間の中間コード生成と最適化をミドルエンドと呼ぶこともある）。

中間表現（IR: Intermediate Representation）を挟むのは、ソース言語と対象 CPU の組み合わせごとにコンパイラを作らずに済むようにするためである。\(m\) 種類の言語と \(n\) 種類の CPU に対応する場合、言語ごとのフロントエンドと CPU ごとのバックエンドを中間表現でつなげば、\(m \times n\) 個ではなく \(m + n\) 個の部品で済む。最適化の多くも中間表現の上で行うので、すべての言語と CPU が恩恵を受けられる。LLVM はこの構成の代表例であり、Clang（C/C++）、Rust、Swift などのコンパイラが LLVM の中間表現を経由して機械語を生成する。

最適化の例としては、定数の計算をコンパイル時に済ませる定数畳み込み（60 * 60 * 24 を 86400 に置き換える）、結果が使われない計算を取り除く不要コード除去、ループの中で値の変わらない計算をループの外に出すループ不変式の移動、小さな関数の呼び出しを関数の本体で置き換えるインライン展開などがある。

7.3.3. バイトコードと仮想マシン

Java や Python の多くの処理系は、ソースコードを機械語ではなくバイトコードに翻訳する。バイトコードは、実在の CPU ではなく、ソフトウェアで実装された仮想的な計算機（仮想マシン）のための命令列である。仮想マシンは、バイトコードの命令を 1 つずつ読んで実行するインタプリタである。Java の場合、javac が生成したバイトコード（.class ファイル）を Java 仮想マシン（JVM）が実行する。仮想マシンさえ移植すれば、同じバイトコードが異なる CPU や OS の上で動く。なお、ここでいう仮想マシンは、1 台の計算機の上で複数の OS を動かすための仮想マシン（仮想化技術。第 8 章「オペレーティングシステム」で扱う）とは別のものである。

CPython（標準の Python 処理系）も、ソースコードをバイトコードにコンパイルしてから実行している。インポートしたモジュールのバイトコードは __pycache__ フォルダの .pyc ファイルに保存され、次回の起動時に再利用される。標準ライブラリの dis モジュールを使うと、関数のバイトコードを人間が読める形で表示できる。

7.3.4. JIT コンパイル

インタプリタでバイトコードを 1 命令ずつ実行すると、命令の読み取りと振り分けの手間がかかるので、機械語を直接実行するより遅い。そこで、実行中に頻繁に実行される部分（ホットスポット）を検出し、その部分だけを実行時に機械語へコンパイルする方式が考えられた。これを JIT コンパイル（Just-In-Time コンパイル）と呼ぶ。

JIT コンパイラは、実行時に得られる情報を最適化に使える点で、実行前にコンパイルする方式（AOT: Ahead-Of-Time）より有利な場合もある。例えば、動的型付けの言語で「この変数には実際には常に整数が入っている」と観測できれば、整数に特化した機械語を生成できる。前提が崩れた場合は、特化したコードを捨ててインタプリタに戻る（脱最適化）。Java の HotSpot VM、JavaScript の V8、Python の別実装である PyPy などが JIT コンパイルを使っている。CPython にも、Python 3.13 から実験的な JIT コンパイラが追加されている（既定では無効）。

7.4. 字句解析と構文解析

ここからは、コンパイラのフロントエンドの入口である字句解析と構文解析を、四則演算の式を評価する小さなインタプリタを作りながら見ていく。このインタプリタは、字句解析でトークンの列を作り、構文解析で抽象構文木を作り、その木をたどって値を計算する。コード生成を行わず、木を直接評価する方式のインタプリタである。

7.4.1. 字句解析

字句解析は、ソースコードの文字の並びを、トークン（字句）の列に変換する処理である。トークンは、識別子、数値リテラル、演算子、キーワード、括弧のような、文法上の最小単位である。例えば 2 * (3 + 4) - 5 は、2、*、(、3、+、4、)、-、5 の 9 個のトークンになる。空白やコメントは、字句解析の段階で取り除かれることが多い。

各種類のトークンの形は、ほとんどの言語で正規言語になる。例えば「数字が 1 個以上並び、その後に小数点と数字の並びが続いてもよい」という数値リテラルの形は、正規表現 \d+(\.\d+)? で表せる。そのため字句解析器は、第 6 章の「決定性有限オートマトン」で学んだ DFA として実装でき、入力の長さに比例する時間で動作する。lex や flex のような字句解析器の生成ツールは、トークンの種類ごとの正規表現から DFA を自動的に作る。

本章のサンプルでは、Python の re モジュールを使って字句解析器を作る。

7.4.2. 構文解析と抽象構文木

構文解析は、トークンの列が言語の文法に従っているかを調べ、その構造を木の形で表す処理である。括弧の対応のような入れ子構造は正規言語では表せないので、構文の記述には第 6 章で学んだ文脈自由文法を使う。本章の四則演算の式の文法を、EBNF で次に示す。{ ... } は 0 回以上の繰り返し、| は「または」を表す。

1expr   ::= term   { ("+" | "-") term }
2term   ::= factor { ("*" | "/") factor }
3factor ::= NUMBER | "(" expr ")" | "-" factor

1 行目は「式（expr）は項（term）を + または - でつないだもの」、2 行目は「項は因子（factor）を * または / でつないだもの」、3 行目は「因子は数値、括弧で囲んだ式、または符号を反転した因子のどれか」と読む。この文法は、演算子の優先順位を規則の階層で表している。* と / は term の中で + や - より深い位置でまとめられるので、1 + 2 * 3 では 2 * 3 が先にまとまる。また、3 行目の factor の定義に expr が現れる再帰によって、括弧の入れ子を何重にでも書ける。

構文解析の結果は抽象構文木（AST: Abstract Syntax Tree）で表す。AST は、プログラムの意味に関係する構造だけを残した木である。例えば括弧は計算の順序を決めるために必要だが、順序が木の形に反映されれば、括弧そのものを木に残す必要はない。文法規則をそのまま木にした構文木（解析木）から、こうした不要な情報を取り除いたものが AST である。2 * (3 + 4) - 5 の AST は次のようになる。

1     -
2    / \
3   *   5
4  / \
5 2   +
6    / \
7   3   4

木の根に近い演算ほど後で計算される。- が根にあるのは、2 * (3 + 4) を計算した後で 5 を引くからである。Python 自身も、ソースコードを AST に変換してからバイトコードを生成している。標準ライブラリの ast モジュールを使うと、Python の AST を見られる。

7.4.3. 再帰下降構文解析

文脈自由文法から構文解析器を作る方法はいくつかあるが、手で書く場合に最も分かりやすいのが再帰下降構文解析である。再帰下降構文解析では、文法の非終端記号 1 つに 1 つの関数を対応させる。各関数は、規則の右辺に終端記号があればそのトークンを読み、非終端記号があればその関数を呼び出す。規則が再帰的なら、関数も再帰的に呼び出し合う。サンプルの構文解析器と AST の定義を次に示す。

ch07_calc_interpreter.py（抽象構文木と構文解析）

 83# ---- 構文解析（再帰下降） ----------------------------------------------

 85
 86class Parser:
 87    """文法の非終端記号 1 つに 1 つのメソッドを対応させた構文解析器."""
 88
 89    def __init__(self, tokens: list[Token]) -> None:
 90        self.tokens = tokens
 91        self.pos = 0
 92
 93    def peek(self) -> str:
 94        """次のトークンの文字列を、読み進めずに返す."""
 95        return self.tokens[self.pos].text
 96
 97    def advance(self) -> Token:
 98        """次のトークンを返し、1 つ読み進める."""
 99        token = self.tokens[self.pos]
100        self.pos += 1
101        return token
102
103    def parse(self) -> Node:
104        """式全体を解析し、入力が残っていればエラーにする."""
105        node = self.expr()
106        if self.tokens[self.pos].kind != "END":
107            raise SyntaxError(f"余分なトークン: {self.peek()!r}")
108        return node
109
110    def expr(self) -> Node:
111        """expr ::= term { ("+" | "-") term }."""
112        node = self.term()
113        while self.peek() in ("+", "-"):
114            op = self.advance().text
115            node = BinOp(op, node, self.term())  # 左結合になる
116        return node
117
118    def term(self) -> Node:
119        """term ::= factor { ("*" | "/") factor }."""
120        node = self.factor()
121        while self.peek() in ("*", "/"):
122            op = self.advance().text
123            node = BinOp(op, node, self.factor())
124        return node
125
126    def factor(self) -> Node:
127        """factor ::= NUMBER | "(" expr ")" | "-" factor."""
128        token = self.advance()
129        if token.kind == "NUM":
130            return Num(float(token.text))
131        if token.text == "(":
132            node = self.expr()
133            if self.advance().text != ")":
134                raise SyntaxError("')' がない")
135            return node
136        if token.text == "-":
137            return Neg(self.factor())
138        raise SyntaxError(f"予期しないトークン: {token.text!r}")

57〜80 行目が AST の節点の定義で、数値リテラル Num、単項マイナス Neg、二項演算 BinOp の 3 種類がある。110 行目の expr、118 行目の term、126 行目の factor が、それぞれ文法の 1〜3 行目に対応している。EBNF の繰り返し { ... } は while 文に、選択 | は if 文に、非終端記号はメソッドの呼び出しになっている。132 行目で factor が expr を呼び出すところが、括弧の入れ子を扱う再帰である。

115 行目では、それまでに作った木 node を左の子にして新しい BinOp を作っている。これにより、1 - 2 - 3 は (1 - 2) - 3 と解釈され、引き算が左結合になる。もし文法を expr ::= term "-" expr と書いて素直に再帰で実装すると、1 - (2 - 3) と右結合に解釈されて結果が誤る。一方、左結合を表すために expr ::= expr "-" term と書くと、expr 関数が何もトークンを読まずに自分自身を呼び出して無限に再帰してしまう（左再帰の問題）。そこで、再帰下降構文解析では左再帰を繰り返しに書き換えるのが定石である。

注釈

再帰下降構文解析は、1 つ先のトークンを見るだけでどの規則を使うかを決められる文法（LL(1) 文法など）に適している。より広い文法を扱える方式として、トークンを積み上げながら木を下から組み立てる LR 構文解析があり、yacc や bison のような構文解析器の生成ツールが使っている。CPython は 3.9 以降、PEG（Parsing Expression Grammar）という形式で書いた文法から生成した構文解析器を使っている。

7.4.4. 評価

AST ができれば、評価は木を根から再帰的にたどるだけである。

7.5. リンカとローダ

コンパイラが機械語を生成しても、それだけではまだプログラムを実行できない。実際のプログラムは多数のソースファイルとライブラリから組み立てられており、それらを 1 つにまとめ、主記憶に読み込んで実行を始める仕組みが必要である。前者を受け持つのがリンカ、後者がローダである [Levine] [CSAPP]。

7.5.1. 分割コンパイルとオブジェクトファイル

C や C++ では、ソースファイルを 1 つずつ別々にコンパイルする。これを分割コンパイルと呼ぶ。1 つのファイルを修正したときにそのファイルだけをコンパイルし直せばよいので、大きなプログラムでもビルドの時間を短くできる。make などのビルドツールは、ファイルの更新日時や依存関係を調べて、コンパイルし直す必要のあるファイルだけを選ぶ。

各ソースファイルをコンパイルした結果をオブジェクトファイルと呼ぶ（Linux では .o、Windows では .obj）。オブジェクトファイルには、機械語のコードと初期値を持つデータのほかに、次の情報が含まれる。

  • シンボル表: そのファイルで定義している関数や大域変数の名前（シンボル）と位置、およびそのファイルが使っているが定義していないシンボルの一覧。

  • 再配置情報: 他のファイルにある関数の呼び出しのように、最終的なアドレスがまだ決まっていないために仮の値を入れてある箇所の一覧。

例えば main.c が util.c で定義された関数 parse() を呼び出す場合、main.c をコンパイルした時点では parse() がどのアドレスに置かれるか分からない。そこでコンパイラは呼び出し先を空けておき、「ここに parse のアドレスを入れる」という記録を再配置情報に残す。

7.5.2. リンカとシンボルの解決

リンカは、複数のオブジェクトファイルとライブラリを結合して、1 つの実行ファイルを作るプログラムである。リンカの主な仕事は 2 つある。

  • シンボルの解決: 各オブジェクトファイルが参照している未定義のシンボルを、いずれかのオブジェクトファイルやライブラリにある定義と対応付ける。定義がどこにも無ければ undefined reference to `parse' のようなエラーに、同じシンボルが複数のファイルで定義されていれば多重定義のエラーになる。これらはコンパイルではなくリンクの段階で起きるエラーである。

  • 再配置: 各ファイルのコードとデータを 1 つのアドレス空間に並べて最終的なアドレスを決め、再配置情報に従って仮の値を実際のアドレスに書き換える。

C++ では、同じ名前でも引数の型が異なる関数（オーバーロード）を区別するため、コンパイラが引数の型をシンボル名に埋め込む。これを名前修飾（マングリング）と呼ぶ。C++ から C のライブラリを呼ぶときに extern "C" と書くのは、この名前修飾を止めて C と同じシンボル名にするためである。

7.5.3. 静的リンクと動的リンク

ライブラリを結合する方法には 2 つある。静的リンクは、リンクの時点でライブラリから必要なコードを取り出し、実行ファイルの中にコピーする方式である（静的ライブラリは Linux では .a、Windows では .lib）。動的リンクは、実行ファイルには「どのライブラリのどのシンボルを使うか」だけを記録しておき、プログラムの読み込み時または実行中に、ライブラリと結合する方式である。動的リンクで使うライブラリを共有ライブラリと呼び、Linux では .so、Windows では .dll、macOS では .dylib という拡張子を持つ。

一方、動的リンクには依存関係の問題がある。実行する環境に必要な共有ライブラリが無ければプログラムは起動せず、あっても版が異なり、関数の引数やデータ構造の配置が変わっていれば誤動作する。Windows で複数のアプリケーションが異なる版の同名の DLL を必要として衝突する問題は「DLL 地獄」と呼ばれた。そのため、共有ライブラリの名前に互換性を表す版番号を含める（libssl.so.3 など）、アプリケーションごとに必要なライブラリを同梱する、といった対策がとられている。Go のように、標準で静的リンクを基本とし、共有ライブラリにほとんど依存しない実行ファイルを作る言語もある。コンテナ（Docker など）でアプリケーションとライブラリをまとめて配布するのも、同じ問題への対策の 1 つである。

Python も動的リンクと無縁ではない。NumPy のように C で書かれた拡張モジュールは共有ライブラリ（Linux では .so、Windows では .pyd）であり、import したときに CPython が動的に読み込んでいる。pip install で入れたパッケージが「共有ライブラリが見つからない」というエラーで動かない場合は、この仕組みが原因である。

7.5.4. ローダ

ローダは、実行ファイルを補助記憶から読み込み、実行を開始する仕組みであり、多くの場合 OS の一部である。実行ファイルは、OS ごとに決められた形式に従っている。Linux などでは ELF（Executable and Linkable Format）、Windows では PE（Portable Executable）、macOS では Mach-O が使われる。これらの形式は、ファイルの先頭のヘッダに、コードやデータの各領域がファイルのどこにあり、主記憶のどこに配置すべきか、実行を開始するアドレス（エントリポイント）はどこか、どの共有ライブラリが必要か、といった情報を持つ。

プログラムを起動すると、ローダはおおよそ次の手順を踏む。

  1. 実行ファイルのヘッダを読み、プロセスの仮想アドレス空間に、コード、データ、スタックの領域を用意する。Unix 系の OS では、exec のシステムコールがそれまでのアドレス空間を捨てて、この手順で作り直す（第 8 章の「Unix のプロセス生成: fork と exec」を参照）。ファイルの内容はすぐにすべて読み込むのではなく、仮想メモリの仕組み（デマンドページング）で必要になったときに読み込まれる。

  2. 動的リンクを使う実行ファイルであれば、動的リンカ（Linux では ld.so）を起動し、必要な共有ライブラリを同じアドレス空間に配置して、シンボルを解決させる。

  3. コマンドライン引数や環境変数をスタックに置き、エントリポイントに制御を移す。C のプログラムであれば、そこから初期化処理を経て main 関数が呼ばれる。

なお、CPython で python script.py と実行したとき、ローダが読み込むのは CPython のインタプリタの実行ファイルであり、script.py はインタプリタが読むデータにすぎない。インタプリタ型の処理系では、リンカとローダの仕事の一部を、import によるモジュールの読み込みが受け持っている。

7.6. メモリ管理

7.6.1. スタックとヒープ

プログラムの実行中に使うメモリ領域のうち、データを置く主な場所がスタックとヒープである。

スタックは、関数呼び出しのたびに局所変数や戻り先のアドレスを格納する領域（スタックフレーム）を積み、関数から戻るときに取り除く領域である。確保と解放は、スタックの先頭を指すポインタを動かすだけなので非常に高速である。ただし、関数から戻ると領域は自動的に解放されるので、関数の実行が終わった後も使い続けたいデータは置けない。また、大きさが限られており、再帰が深すぎるとスタックオーバーフローを起こす。

ヒープは、プログラムが任意の時点で任意の大きさの領域を確保し、不要になったら解放する領域である。関数の終了後も残るデータや、実行時まで大きさが分からないデータを置ける。その代わり、確保と解放にはスタックより手間がかかり、「いつ解放するか」を誰かが管理しなければならない。なお、ここでいうヒープは、第 4 章「データ構造」で扱うデータ構造のヒープとは別のものである。

7.6.2. 手動管理

C では、プログラマが malloc でヒープの領域を確保し、free で明示的に解放する。手動管理は無駄がなく、解放の時期を完全に制御できるが、誤りやすい。解放を忘れると使われない領域がたまり続けるメモリリークが起き、解放済みの領域をポインタ経由で使い続けると（ダングリングポインタ）、別の目的で再利用された領域を壊してしまう。同じ領域を 2 回解放する二重解放も深刻な不具合になる。さらに C は配列の添字が範囲内かどうかを検査しないので、範囲外の読み書きも起こりうる。これらの誤りはセキュリティ上の脆弱性の主要な原因でもある（第 14 章「認証とアプリケーションのセキュリティ」を参照）。C++ はオブジェクトの寿命が尽きたときに自動で解放する RAII という手法で、Rust は所有権という規則をコンパイル時に検査することで、実行時の負担を増やさずにこうした誤りを防いでいる。

一方、Java、Python、JavaScript、Go などの多くの言語では、不要になった領域を処理系が自動的に見つけて解放する。この仕組みをガベージコレクション（GC: Garbage Collection）と呼ぶ。GC の方式は、大きく参照カウントとトレーシング GC に分けられる。

7.6.3. 参照カウント

参照カウントは、各オブジェクトに「自分を参照している箇所の数」を記録しておき、参照が増えれば 1 を足し、減れば 1 を引いて、0 になった時点でオブジェクトを解放する方式である。不要になったオブジェクトがすぐに解放されるので、メモリの使用量が予測しやすく、プログラムが長時間止まることもない。CPython や Swift（ARC と呼ばれる）が参照カウントを使っている。

参照カウントの弱点は循環参照である。例えば 2 つのオブジェクトが互いに相手を参照していると、プログラムのどこからも使われなくなっても、それぞれの参照カウントは 1 のまま 0 にならず、いつまでも解放されない。また、参照を変更するたびにカウントを更新する手間がかかり、複数のスレッドから同時に更新する場合は排他制御も必要になる。

7.6.4. トレーシング GC

トレーシング GC は、グローバル変数や各スタックフレームの局所変数のように、プログラムから直接たどれる場所（ルート）を起点に、参照をたどって到達できるオブジェクトをすべて調べる。到達できなかったオブジェクトは二度と使われないので解放する。到達できるオブジェクトに印を付け、印のないものを解放する方式をマークアンドスイープと呼ぶ。

トレーシング GC は到達可能性で判断するので、循環参照していても、ルートから到達できなければ正しく解放できる。一方、GC の処理中にプログラムを一時停止する必要がある場合があり、応答時間が重要なシステムでは問題になる。そのため、多くのオブジェクトは作られてすぐ不要になるという経験則を利用して新しいオブジェクトを重点的に調べる世代別 GC や、プログラムの実行と並行して GC を進める方式などが工夫されている。

CPython は、参照カウントを基本としつつ、循環参照を回収するためのトレーシング GC を併用している。標準ライブラリの gc モジュールで、この GC を手動で実行したり、設定を変えたりできる。

7.7. 関数呼び出しと名前の解決

プログラム中の名前（変数名や関数名）が、どの定義を指すかを決めることを名前の解決と呼ぶ。名前が有効な範囲をスコープと呼ぶ。現在の主要な言語の多くは、ソースコード上の位置（入れ子の構造）によってスコープが決まる静的スコープ（レキシカルスコープ）を採用している。関数呼び出しの順序によって決まる動的スコープを採用する言語は少ない。

Python では、名前を内側から順に、局所スコープ（Local）、外側の関数のスコープ（Enclosing）、モジュールのスコープ（Global）、組み込みのスコープ（Built-in）の順で探す。頭文字を取って LEGB 規則と呼ばれる。

関数の中で定義した関数が、外側の関数の局所変数を参照していると、外側の関数から戻った後もその変数が保持される。このように、関数とその関数が参照する外側の変数の環境を組にしたものをクロージャと呼ぶ。

7.8. 例外処理の仕組み

7.8.1. 戻り値によるエラーの通知

ファイルが見つからない、入力の形式が誤っている、通信が切れたなど、プログラムは実行中にさまざまなエラーに出会う。エラーを呼び出し元に知らせる最も素朴な方法は、戻り値で知らせることである。C の標準ライブラリの多くの関数は、失敗すると -1 や NULL を返し、原因を大域変数 errno に設定する。Go は、関数が本来の戻り値とエラーの 2 つを返し、呼び出し元が if err != nil で調べる流儀をとっている。

戻り値による方法は、仕組みが単純で、どこでエラーが起こりうるかがコードから見て分かるという利点がある。一方で、呼び出し元が戻り値を調べ忘れると、エラーは黙って無視され、後の処理が誤った値で進んでしまう。また、エラーを処理できるのが何段も上の呼び出し元である場合、途中のすべての関数が「エラーなら自分もエラーを返す」というコードを書かなければならない。さらに、-1 が正常な値としてもありうる関数では、エラーと正常な値を区別できない。

7.8.2. 例外の伝播とスタックの巻き戻し

例外処理は、エラーを通常の戻り値とは別の経路で伝える仕組みである。エラーを検出した箇所で例外を送出する（Python では raise）と、通常の処理の流れはそこで中断される。処理系は、その時点で積まれているスタックフレームの列（コールスタック）を呼び出し元の方向にさかのぼり、その例外を処理する except（他の言語では catch）を持つ関数を探す。途中の関数は、例外を処理する記述を持っていなければ、そのまま実行を打ち切られ、スタックフレームが取り除かれる。この処理をスタックの巻き戻しと呼ぶ。最後まで処理する箇所が見つからなければ、プログラムは終了し、Python であればトレースバック（例外が通ってきた呼び出しの履歴）が表示される。

例外を使うと、エラーを検出する箇所と処理する箇所を離して書け、途中の関数はエラーを中継するコードを書かずに済む。また、処理されない例外は無視されずにプログラムを止めるので、エラーが黙って見過ごされることが無い。その代わり、ある関数呼び出しがどの例外を送出しうるかがコードの見た目からは分かりにくい。Java は、メソッドが送出しうる一部の例外を throws で宣言させ、呼び出し側に処理か宣言を強制する検査例外を持つ。Rust は例外を使わず、成功の値かエラーかのどちらかを表す Result 型を戻り値として返し、処理し忘れを型検査で防ぐ。

実行時の手間について、C++ や Python 3.11 以降の CPython は、例外が発生しない限り try による手間がほぼかからない方式（ゼロコスト例外）で実装されている。その代わり、例外が実際に送出されたときには、どこに処理する箇所があるかを表から探す手間がかかる。例外は名前のとおり例外的な状況のための仕組みであり、頻繁に起こる通常の分岐に使うと遅くなることがある。

6呼び出し元で捕捉: invalid literal for int() with base 10: 'abc'

2 回目の呼び出しでは、2 行目の int("abc") が ValueError を送出する。parse_price と total はこの例外を処理しないので実行を打ち切られるが、total から抜ける前に 9 行目の finally の中の 10 行目が実行され、実行結果の 5 行目が表示される。その後、例外は 16 行目の except で捕捉される。15 行目の print は実行されない。

ファイルやロックのように「獲得したら必ず解放する」資源には、with 文を使うのが Python の定石である。

1with open("data.txt", encoding="utf-8") as f:
2    first_line = f.readline()
3# ここに来た時点で、例外が起きたかどうかにかかわらず f は閉じられている

with 文は、ブロックに入るときにオブジェクトの __enter__() を呼び、ブロックを抜けるときに、正常終了でも例外でも __exit__() を呼ぶ。ファイルオブジェクトの __exit__() はファイルを閉じるので、上のコードは try / finally で f.close() を呼ぶのと同じ意味になる。第 11 章「データベース」の with conn: が、例外が起きたらトランザクションをロールバックするのも、この仕組みによる。C++ の RAII（メモリ管理の節を参照）は、スタックの巻き戻しの際に局所変数のデストラクタが呼ばれることを利用して、同じ後始末を実現している。

最後に、例外の扱いで避けるべき書き方を挙げておく。except Exception: pass のようにすべての例外を捕捉して何もしないと、戻り値の調べ忘れと同じく、エラーが黙って無視される。例外は、処理の方法が分かる箇所で、想定する種類だけを捕捉する。捕捉した例外を別の例外に変換して送出し直すときは、raise NewError(...) from e と書くと、元の例外の情報がトレースバックに残る。

7.9. まとめ

  • プログラミングパラダイムには手続き型、オブジェクト指向、関数型、宣言型などがあり、現代の多くの言語は複数のパラダイムを取り入れている。

  • 静的型付けは実行前に、動的型付けは実行時に型を検査する。「強い・弱い型付け」は定義が曖昧なので、具体的な性質で議論する。型推論により、型を書かずに静的な型検査を受けられる。Python では型ヒントと mypy で静的な型検査を段階的に導入できる。

  • 多相にはパラメトリック多相（ジェネリクス）、部分型多相、アドホック多相（オーバーロード）がある。Python 3.12 以降は def first[T](xs: list[T]) -> T: の形でジェネリックな関数を書ける。ジェネリクスの実装には、Java のような型消去と、C++ のテンプレートのような具体化がある。

  • コンパイラは字句解析、構文解析、意味解析、中間コード生成、最適化、コード生成の段階を経てソースコードを翻訳する。中間表現により、言語と CPU の組み合わせごとにコンパイラを作らずに済む。

  • CPython はソースコードをバイトコードにコンパイルし、スタックマシン型の仮想マシンで実行する。dis モジュールでバイトコードを観察できる。JIT コンパイルは、実行中に頻繁に実行される部分を機械語にコンパイルして高速化する。

  • 字句解析は正規言語の、構文解析は文脈自由文法の応用である。再帰下降構文解析では、文法の非終端記号ごとに関数を作り、左再帰を繰り返しに書き換えて左結合を実現する。

  • 分割コンパイルで作ったオブジェクトファイルを、リンカがシンボルの解決と再配置によって 1 つの実行ファイルにまとめる。静的リンクはライブラリを実行ファイルにコピーし、動的リンクは共有ライブラリを実行時に結合する。動的リンクは更新や主記憶の共有に有利だが、依存関係の問題を伴う。ローダは ELF や PE の形式の実行ファイルを仮想アドレス空間に配置して実行を始める。

  • メモリ管理には手動管理、参照カウント、トレーシング GC がある。参照カウントは循環参照を回収できないので、CPython はトレーシング GC を併用している。

  • 名前はスコープの規則に従って解決される。クロージャは、関数と、その関数が参照する外側の変数の環境を組にしたものである。

  • 戻り値によるエラーの通知は単純だが、調べ忘れや中継のコードが問題になる。例外はコールスタックをさかのぼって処理する箇所に伝播し、途中のスタックフレームは巻き戻される。後始末は try / finally や with 文で確実に行う。
