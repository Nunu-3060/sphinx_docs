9. 並行処理と入出力

「オペレーティングシステム」では、OS がプロセスとスレッドを作り、CPU を割り当てる仕組みを見た。この章では、複数のスレッドや多数の入出力を同時に扱うプログラムを、正しく効率よく書くための考え方を学ぶ。まず、Python で並行処理を書くときの前提となる GIL と、スレッドとプロセスの使い分けを確認する。次に、複数のスレッドが共有データを更新するときに起きる競合状態と、それを防ぐ排他制御、条件変数、デッドロック、そしてそれらの土台となるアトミック操作とメモリモデルを扱う。最後に、多数の通信を少ないスレッドでさばくための入出力のモデル（ノンブロッキング I/O、I/O 多重化、イベントループ）と Python の asyncio を学ぶ。マルチコアのハードウェアについては「コンピュータの構成」を、ここで学ぶ考え方を複数のコンピュータに広げた話題は「分散システム」を参照してほしい。全体の参考書としては [OSTEP] と [Herlihy] を挙げておく。

なお、複数の処理が時間的に重なり合って進むことを並行（concurrency）、複数の処理が物理的に同じ瞬間に実行されることを並列（parallelism）と呼ぶ。コアが 1 つでも、スレッドを切り替えながら進めれば処理は並行に進むが、並列に実行するには複数のコアが必要である。

9.1. Python の GIL とマルチプロセス

Python の標準的な処理系である CPython には、GIL（Global Interpreter Lock）と呼ばれるロックがある。GIL を持つスレッドだけが Python のバイトコードを実行できるため、CPU を多く使う計算を複数のスレッドに分けても、同時に動くのは 1 つだけで速くならない。ただし、ファイルやネットワークの入出力を待っている間は GIL が解放されるので、入出力待ちが中心の処理ではスレッドが有効である。なお、Python 3.13 からは GIL を持たないフリースレッド版のビルドも提供されるようになったが、本書執筆時点で広く使われているのは GIL のある通常のビルドである。

実務では次のように使い分けるとよい。

  • 入出力待ちが中心の処理（多数の HTTP リクエストの送信、ファイルの読み書き）: threading モジュールや concurrent.futures.ThreadPoolExecutor、または asyncio を使う（asyncio は後述の「入出力のモデル」で扱う）。

  • CPU を多く使う処理（画像処理、大量の数値計算）: multiprocessing モジュールや concurrent.futures.ProcessPoolExecutor で複数のプロセスに分け、複数の CPU コアを使う。プロセス間でデータを受け渡すには直列化（pickle）が必要になるので、渡すデータは小さく保つ。

  • 障害を隔離したい処理（不安定な外部ライブラリの呼び出しなど）: プロセスを分ければ、異常終了しても呼び出し元は生き残る。

GIL があるからといって、スレッドを使うプログラムで排他制御が不要になるわけではない。GIL はインタプリタ内部のデータ構造を守るためのものであり、利用者のプログラムの複数の処理をまとめて不可分にするものではない。この点は後述の競合状態のサンプルで確かめる。

9.2. 並行処理

9.2.1. 競合状態とクリティカルセクション

複数のスレッドが共有データにアクセスし、その結果が実行の順序やタイミングによって変わってしまう状況を競合状態（レースコンディション）と呼ぶ。典型例は、共有カウンタに 1 を加える処理である。count += 1 は 1 つの操作に見えるが、実際には「値を読み出す」「1 を加える」「書き戻す」の 3 段階からなる。2 つのスレッドがどちらも 5 を読み出し、それぞれ 6 を書き戻すと、2 回加えたのに値は 1 しか増えない。

共有データにアクセスする、同時に 1 つのスレッドしか実行してはならないコードの区間をクリティカルセクションと呼ぶ。競合状態を防ぐには、クリティカルセクションに同時に入れるスレッドを 1 つに制限する。これを排他制御と呼ぶ。

次のサンプルは、4 つのスレッドが共有カウンタに 1,000 回ずつ 1 を加える。ロック無しの increment_unsafe では、読み出しと書き込みの間で time.sleep(0) を呼んでいる。これは他のスレッドに実行を譲る指示であり、GIL のある Python でも、読み出しと書き込みの間に他のスレッドが割り込む状況を確実に作り出す。

28 行目で読み出した値に、29 行目で他のスレッドが実行している間に行われた更新は反映されず、30 行目で古い値に 1 を加えたものが書き戻される。34 行目の with self.lock: はロックを取得し、ブロックを抜けるときに解放する。ロックを持つスレッドが time.sleep(0) で実行を譲っても、他のスレッドは 34 行目で待たされるので、読み出しから書き込みまでが不可分になる。実行結果の例を次に示す。

1ロック無し: 期待値 4000, 実際 1115, 失われた更新 2885
2ロック有り: 期待値 4000, 実際 4000, 失われた更新 0

ロック無しの値はスレッドの切り替わり方に依存するため、実行するたびに変わる。筆者の環境では 3 回の実行で 1115、1319、1065 となった。ロック有りの値は常に 4000 になる。time.sleep(0) を取り除くと、ロック無しでも 4000 になることが多い。しかしそれは、切り替えがたまたま危険な位置で起きにくいというだけであり、正しさが保証されたわけではない。競合状態によるバグは、テストでは再現せず本番環境の高負荷時にだけ現れることがあるため、共有データの更新は最初からロックで守るべきである。

9.2.2. ミューテックスとセマフォ

排他制御のための基本的な道具がミューテックス（mutex: mutual exclusion）である。ミューテックスはロックとも呼ばれ、「取得」と「解放」の 2 つの操作を持つ。あるスレッドが取得している間、他のスレッドの取得は解放されるまで待たされる。上のサンプルの threading.Lock がこれにあたる。ミューテックスは、取得したスレッド自身が解放するのが原則である。

セマフォは、整数のカウンタを持つ同期の道具である。取得操作（P 操作、wait）はカウンタが正なら 1 減らして進み、0 なら待つ。解放操作（V 操作、signal）はカウンタを 1 増やし、待っているスレッドがあれば 1 つ起こす。カウンタの初期値を \(n\) にすると、同時に \(n\) 個までのスレッドが資源を使えるように制限できる。初期値が 1 のセマフォはミューテックスと似た働きをするが、取得したスレッドとは別のスレッドが解放してもよい点が異なる。実務では、データベースへの同時接続数や、外部 API への同時リクエスト数を制限するのに使う。Python では threading.Semaphore が使える。

9.2.3. 条件変数と生産者・消費者問題

ミューテックスは「同時に入らない」ことを保証するが、「ある条件が成り立つまで待つ」ことには向かない。例えば、キューが空の間は取り出しを待ちたいとき、ロックを取ってキューを調べ、空ならロックを外して少し待ってまた調べる、という繰り返し（ポーリング）では、CPU を無駄に使ううえに反応も遅れる。そこで使うのが条件変数である。条件変数はミューテックスと組にして使い、次の 2 つの操作を持つ。

  • wait: 保持しているロックを解放して眠り、起こされたらロックを再び取得してから戻る。ロックの解放と眠りに入ることは不可分に行われるので、その隙間に送られた通知を取りこぼさない。

  • notify（signal）: その条件変数で眠っているスレッドを 1 つ起こす。notify_all（broadcast）はすべてを起こす。

起こされたスレッドは、ロックを再取得するまでの間に他のスレッドが先に条件を崩しているかもしれない。また、実装によっては通知が無くても起きること（見せかけの起床）がある。そのため、待つ条件は if ではなく while で確かめ直すのが鉄則である [OSTEP]。

条件変数の典型的な使い道が生産者・消費者問題である。データを作る生産者スレッドと、それを処理する消費者スレッドが、容量に限りのあるバッファを介して受け渡しをする。生産者はバッファが満杯なら空きができるまで待ち、消費者はバッファが空なら品物が来るまで待たなければならない。Web サーバで接続を受け付けるスレッドと処理するスレッドの間、ログを生成する処理と書き出す処理の間など、実務のいたるところに現れる形である。容量に限りがあるので、生産者が速すぎても主記憶を使い尽くさず、自然に速度が抑えられる（これを背圧と呼ぶ）。

次のサンプルは、Python の queue.Queue を使う方法と、threading.Condition でバッファを自作する方法の 2 通りで、生産者 2 つと消費者 3 つを動かす。queue.Queue は内部でロックと条件変数を使って実装されたスレッド安全なキューであり、実務ではこれを使えば十分である [PythonDocs]。

24class BoundedBuffer:
25    """条件変数で実装した容量付きの FIFO バッファ。"""
26
27    def __init__(self, capacity: int) -> None:
28        self.items: deque[int | None] = deque()
29        self.capacity = capacity
30        self.cond = threading.Condition()  # ロックと待ち行列を兼ねる
31        self.max_seen = 0  # 観測した最大の要素数
32
33    def put(self, item: int | None) -> None:
34        """空きができるまで待ってから item を入れる。"""
35        with self.cond:
36            while len(self.items) >= self.capacity:  # if ではなく while
37                self.cond.wait()  # ロックを手放して眠り、起きたら再取得
38            self.items.append(item)
39            self.max_seen = max(self.max_seen, len(self.items))
40            self.cond.notify_all()  # 待っている消費者を起こす
41
42    def get(self) -> int | None:
43        """品物が来るまで待ってから 1 つ取り出す。"""
44        with self.cond:
45            while not self.items:
46                self.cond.wait()
47            item = self.items.popleft()
48            self.cond.notify_all()  # 待っている生産者を起こす
49            return item
50

56    """

70            with lock:
71                consumed.append(item)

74                 for p in range(PRODUCERS)]

76    for t in producers + consumers:

threading.Condition は、内部にロックを持つ条件変数である。35 行目と 44 行目の with self.cond: でロックを取り、36〜37 行目では満杯の間、45〜46 行目では空の間、wait で眠る。品物を入れたり取り出したりしたら、40 行目と 48 行目の notify_all で待っているスレッドを起こす。ここで notify ではなく notify_all を使っているのは、生産者と消費者が同じ条件変数で待っているからである。notify で 1 つだけ起こすと、消費者が別の消費者を起こしてしまい、起こすべき生産者が眠ったまま全員が待ち続けることがあり得る。queue.Queue は「空でない」と「満杯でない」の 2 つの条件変数を使い分けて、この無駄を避けている。

59〜60 行目で、2 つの方法のどちらの put と get を使うかを切り替えている。消費者は 69 行目で品物を受け取り続け、終了の合図として None を受け取ると終わる。80〜81 行目で、すべての生産者の終了を待ってから消費者の数だけ None を送るので、品物が残ったまま消費者が終わることはない。実行結果を次に示す。

1[queue.Queue]
2  生産 100 個, 消費 100 個, 欠落・重複なし: True
3[threading.Condition]
4  生産 100 個, 消費 100 個, 欠落・重複なし: True
5  バッファの最大要素数が容量 2 以下: True

どの消費者がどの品物を受け取るか、受け取る順序はどうなるかは、スレッドの切り替わり方によって実行ごとに変わる。そのため、サンプルでは順序に依存しない結果（個数、品物の集合の一致、容量を超えなかったこと）だけを表示しており、出力は毎回同じになる。並行プログラムのテストでは、このように「どの実行順序でも成り立つべき性質」を確かめるのが基本である。

なお、生産者・消費者問題はセマフォでも解ける。空きの数を数えるセマフォ（初期値は容量）、品物の数を数えるセマフォ（初期値は 0）、バッファを守るミューテックスの 3 つを使う方法が古典的である。

9.2.4. デッドロック

複数のスレッドが互いに相手の持つ資源の解放を待ち、どれも先に進めなくなった状態をデッドロックと呼ぶ。例えば、スレッド 1 がロック X を取得してからロック Y を待ち、同時にスレッド 2 がロック Y を取得してからロック X を待つと、2 つのスレッドは永遠に待ち続ける。デッドロックは、次の 4 つの条件がすべて成り立つときにだけ起きる。

条件

意味

崩し方の例

相互排除

資源を同時に 1 つのスレッドしか使えない

読み取り専用にして共有する

保持と待機

資源を保持したまま、別の資源を待つ

必要な資源をまとめて一度に取得する

横取り不可

他のスレッドが保持している資源を強制的に奪えない

タイムアウト付きで取得し、失敗したら保持している資源を解放してやり直す

循環待ち

待ちの関係が輪になっている

すべてのロックに順序を決め、常にその順に取得する

4 つのうち 1 つでも崩せば、デッドロックは起きない。実務で最もよく使われるのは循環待ちを崩す方法で、例えば「口座のロックは口座番号の小さい順に取る」のように、ロックを取得する順序をプログラム全体で統一する。Python の Lock.acquire(timeout=1.0) のように、タイムアウト付きで取得して失敗を検出する方法も有効である。データベースはトランザクション間のデッドロックを検出し、一方を中止させて解消する。この話題も「データベース」で再び登場する。

9.2.5. アトミック操作と CAS

ロックそのものは、どのように不可分性を実現しているのだろうか。ロックの取得も「ロックが空いているか調べる」「使用中にする」の 2 段階であり、普通の読み出しと書き込みで作ると、count += 1 と同じ競合状態が起きてしまう。そこで CPU は、メモリ上の値の読み出し、変更、書き込みを、他のコアから割り込まれずに 1 命令で行うアトミック操作を提供している。代表的なものに、値を読んで加算する fetch-and-add、値を 1 にして元の値を返す test-and-set、そして CAS（Compare-And-Swap）がある。

CAS は、アドレス、期待する値、新しい値の 3 つを受け取り、「アドレスの値が期待する値と等しければ新しい値に書き換えて成功を返し、等しくなければ何もせず失敗を返す」という操作を不可分に行う。x86-64 では lock cmpxchg 命令がこれにあたり、ARM や RISC-V では、読み出しと条件付き書き込みの 2 命令の組（LL/SC: Load-Linked / Store-Conditional）で同等のことを実現する（ARM は ARMv8.1 以降、CAS 命令も持つ）。CAS を使うと、共有カウンタへの加算はロック無しで次のように書ける。ここでの load と compare_and_swap は説明のための仮想的な関数であり、Python の標準ライブラリにはこのような操作は無い。

1def increment(counter: Cell) -> None:
2    while True:
3        old = load(counter)                        # 現在の値を読む
4        if compare_and_swap(counter, old, old + 1):
5            return                                 # 誰にも割り込まれなかった
6        # 他のスレッドが先に書き換えたので、読み直してやり直す

2〜6 行目は、読み出してから書き込むまでの間に他のスレッドが値を変えていれば、4 行目の CAS が失敗して読み直す、という繰り返しである。ロックを使わないので、あるスレッドがロックを持ったまま中断されて他の全員が待たされる、ということが起きない。どこかのスレッドの CAS は必ず成功するので、システム全体としては常に処理が進む。このように、ロックを使わずアトミック操作だけで共有データ構造を正しく更新する手法をロックフリーと呼ぶ。Java の java.util.concurrent.atomic、C++ の std::atomic、Go の sync/atomic などがこの種の操作を提供しており、高性能なキューやカウンタの実装に使われる。

ただし、ロックフリーのデータ構造を正しく設計するのは非常に難しい。代表的な落とし穴が ABA 問題である。値が A から B に変わり、また A に戻った場合、CAS は「変わっていない」と判断して成功してしまう。ポインタを CAS で付け替える連結リストなどでは、これが構造の破壊につながる。対策として、値と一緒に更新回数を記録して比較するなどの方法がある。ロックフリーの理論と実装については [Herlihy] が詳しい。実務では、まずロックや queue.Queue のような既製の同期の道具を使い、性能の測定で必要性が示されたときにだけ検討するのがよい。

9.2.6. メモリの可視性と命令の並べ替え

並行プログラムには、競合状態とは別の落とし穴がある。あるスレッドが書き込んだ値が、別のスレッドからいつ、どの順序で見えるかが、プログラムに書いた順序と一致するとは限らないのである。次の擬似コードで、スレッド 1 はデータを用意してから旗を立て、スレッド 2 は旗が立つのを待ってからデータを読む。

1共有変数: data = 0, ready = false
2
3スレッド 1:            スレッド 2:
4  data = 42              while not ready: 何もしない
5  ready = true           print(data)

直感的には 42 が表示されるはずだが、C や C++ でこれを素朴に書くと、0 が表示されたり、スレッド 2 が永遠に旗に気付かなかったりすることがある。原因は 2 つある。1 つはコンパイラで、1 つのスレッドの中だけで見て結果が変わらない限り、最適化のために読み書きの順序を入れ替えたり、ループ内の ready の読み出しを 1 回にまとめてレジスタに置いたりしてよい。もう 1 つは CPU で、書き込みをいったんコア内のバッファにためてから後でキャッシュに反映するなどの理由で、他のコアから見た書き込みの順序が入れ替わることがある。「コンピュータの構成」で見たキャッシュコヒーレンシは、同じアドレスについてコアの間で値が食い違わないことを保証するが、異なるアドレスへの書き込みが他のコアからどの順序で見えるかまでは保証しない。

どのような並べ替えが起こり得て、読み出しがどの値を返してよいかを定めた規則をメモリモデルと呼ぶ。最も直感的なのは、すべてのスレッドの操作が何らかの 1 つの順序で交互に実行されたかのように見える逐次一貫性であるが、これを常に守ると最適化の余地が大きく減るので、実際の CPU や言語はもっと弱いモデルを採用している。x86-64 は比較的強いモデルで、多くの並べ替えを禁止しているが、ARM はより多くの並べ替えを許す。そのため、x86-64 では偶然動いていたプログラムが、ARM のサーバや Apple Silicon の Mac で壊れることがある。

並べ替えを禁止したい箇所には、メモリバリア（メモリフェンス）を置く。メモリバリアは、その前の読み書きがその後の読み書きより先に他のコアから見えることを保証する命令である。プログラマが直接バリアを書くことはまれで、通常は言語が用意する仕組みを使う。C++ の std::atomic、Java の volatile は、必要なバリアを処理系が自動的に入れる。そして重要なのは、ロックの取得と解放にもバリアが含まれていることである。ロックで守った区間の中の書き込みは、同じロックを後から取得したスレッドから必ず見える。共有データへのアクセスをすべてロックで守っていれば、メモリモデルの細部を意識する必要はない。上の例のようにロックを使わずに旗でスレッド間の合図をしたくなったら、Python なら threading.Event、他の言語なら言語が提供するアトミック変数を使うべきである。

9.3. 入出力のモデル

ネットワークのサーバは、多数のクライアントとの通信を同時に扱わなければならない。それぞれの通信は、ほとんどの時間を相手からのデータの到着を待って過ごす。この「待ち」を OS の上でどのように扱うかによって、サーバの作り方と、同時に扱える接続の数が大きく変わる。この節では、入出力のシステムコールの振る舞いから始めて、イベントループと Python の asyncio までを順に見ていく。ソケットやプロトコルそのものについては「コンピュータネットワーク」を参照してほしい。

9.3.1. ブロッキング I/O とノンブロッキング I/O

ソケットから read するとき、まだデータが届いていなければ、既定ではスレッドはデータが届くまで待ちの状態になる。これをブロッキング I/O と呼ぶ。プログラムは素直に書けるが、1 つのスレッドは一度に 1 つの待ちしか扱えない。そのため、ブロッキング I/O で多数のクライアントを扱うには、接続ごとにスレッド（またはプロセス）を割り当てることになる。

ファイル記述子をノンブロッキングに設定すると（Unix 系では O_NONBLOCK を指定する）、データが無いときの read は待たずに直ちに戻り、「今は読めるものが無い」ことを表すエラー（EAGAIN または EWOULDBLOCK）を返す。これをノンブロッキング I/O と呼ぶ。1 つのスレッドで多数のソケットを順に試せるようになるが、どれも読めないときに試し続けると、CPU を使い切るだけで何も進まない。必要なのは「どれかが読めるようになるまで眠り、読めるようになったものを教えてもらう」仕組みである。

9.3.2. I/O 多重化

1 回のシステムコールで多数のファイル記述子をまとめて監視し、読み書きできる状態になったものだけを教えてもらう仕組みを I/O 多重化と呼ぶ。ファイル記述子が「すべてはファイル」の考え方でソケットにもパイプにも割り当てられているので、同じ仕組みで種類の異なる入出力をまとめて待てる。主な API を次の表に示す [Kerrisk]。

API

1999 年ごろ、1 台のサーバで 1 万（10K）の同時接続を扱うことの難しさが C10K 問題として論じられた。接続ごとにスレッドを割り当てると、1 万のスレッドのスタックが主記憶を圧迫し、コンテキストスイッチのコストも増える。一方、select や poll では、ほとんどの接続が何もしていなくても、呼び出しのたびに 1 万の記述子を調べることになる。epoll や kqueue は、まさにこの問題を解決するために導入された。現在では、少数のスレッドが I/O 多重化で多数の接続をさばく設計が、nginx や Node.js をはじめとする高性能なサーバの基本になっている。Python の selectors モジュールは、OS に応じて最適な仕組みを選んで同じインタフェースで使えるようにしたものである。

9.3.3. 非同期 I/O とイベントループ

I/O 多重化は「読み書きできる状態になった」ことを知らせる準備完了通知型の仕組みであり、実際の読み書きはその後でプログラム自身が行う。これに対し、読み書きの開始だけを依頼して直ちに戻り、カーネルが処理を終えてから「完了した」ことを知らせる完了通知型の仕組みもある。Windows の IOCP（I/O Completion Port）や Linux の io_uring がこれにあたり、狭い意味ではこちらを非同期 I/O と呼ぶ。

どちらの仕組みを使う場合も、プログラムの構造はイベントループと呼ばれる形になる。イベントループは次の手順を繰り返す。

  1. 監視しているすべての入出力とタイマについて、準備完了か完了の通知が来るまで眠る（I/O 多重化の呼び出し）。

  2. 通知が来たものについて、登録されている処理（コールバック）を順に呼ぶ。

  3. 処理が新しい入出力やタイマを登録したら、それを監視対象に加えて 1. に戻る。

イベントループの上の処理は、入出力を待つ間に自分から制御をループに返す。したがって、1 つのスレッドでも、待ちが多い処理であれば何千もの処理を並行して進められる。その代わり、ある処理が長い計算をしたりブロッキング I/O を呼んだりすると、その間はループ全体が止まり、他のすべての処理が待たされる。Web ブラウザの JavaScript も、同じくイベントループの上で動いている。

9.3.4. Python の asyncio

コールバックを連ねてイベントループのプログラムを書くと、処理の流れが細切れになり読みにくい。そこで多くの言語は、途中で実行を中断して後から再開できる関数であるコルーチンを用意し、非同期の処理を普通の逐次的なコードのように書けるようにしている。Python では async def で定義した関数がコルーチンになる。コルーチンの中で await を書くと、待っている処理が終わるまでそのコルーチンの実行を中断し、制御をイベントループに返す。ループは他のコルーチンを進め、待っていた処理が終わると、中断したところから再開させる。標準ライブラリの asyncio が、このイベントループとソケット、タイマなどの部品を提供している [PythonDocs]。

次のサンプルは、localhost に asyncio でエコーサーバを立て、5 つのクライアントを 1 つずつ順に動かした場合と、同時に動かした場合の所要時間を比べる。サーバは応答の前に 0.2 秒待つ。これは、データベースへの問い合わせのような遅い処理の代わりである。ポート番号に 0 を指定して OS に空いているポートを選ばせ、外部とは通信しない。

ch09_asyncio_echo.py
20async def handle(reader: asyncio.StreamReader,
21                 writer: asyncio.StreamWriter) -> None:
22    """1 つの接続を担当するコルーチン。1 行受け取り、大文字にして返す。"""
23    line = await reader.readline()  # データが届くまで待つ（他は動ける）
24    await asyncio.sleep(DELAY)  # 遅い処理の代わり
25    writer.write(line.upper())
26    await writer.drain()
27    writer.close()
28    await writer.wait_closed()

31async def client(port: int, name: str) -> str:
32    """サーバに接続し、1 行送って応答を受け取る。"""
33    reader, writer = await asyncio.open_connection("127.0.0.1", port)
34    writer.write(f"hello from {name}\n".encode())
35    await writer.drain()
36    reply = await reader.readline()
37    writer.close()
38    await writer.wait_closed()
39    return reply.decode().strip()

42async def main_async() -> None:
43    """サーバを起動し、逐次実行と並行実行の所要時間を比べる。"""
44    server = await asyncio.start_server(handle, "127.0.0.1", 0)
45    port = server.sockets[0].getsockname()[1]  # OS が割り当てたポート
46    names = [f"c{i}" for i in range(CLIENTS)]
47    async with server:
48        start = time.perf_counter()
49        for name in names:  # 1 つずつ終わるのを待ってから次へ
50            await client(port, name)
51        sequential = time.perf_counter() - start
52
53        start = time.perf_counter()
54        replies = await asyncio.gather(*(client(port, n) for n in names))
55        concurrent = time.perf_counter() - start
56    for reply in replies:
57        print(reply)
58    print(f"逐次実行: 約 {sequential:.1f} 秒")
59    print(f"並行実行: 約 {concurrent:.1f} 秒")

20〜28 行目の handle は、接続 1 つを担当するコルーチンである。サーバは接続を受け付けるたびに、handle を新しいタスクとしてイベントループに登録する。23 行目の await reader.readline() は、データが届くまでこのタスクを中断し、その間に他の接続のタスクを進めさせる。24 行目の asyncio.sleep も、time.sleep と違ってスレッドを止めず、タイマを登録して制御をループに返す。49〜50 行目は、クライアントを 1 つずつ await するので、前のクライアントが終わるまで次のクライアントは始まらない。54 行目の asyncio.gather は 5 つのクライアントを同時に開始し、すべての結果がそろうまで待つ。結果のリストは、終わった順ではなく渡した順に並ぶ。実行結果の例を次に示す。

1HELLO FROM C0
2HELLO FROM C1
3HELLO FROM C2
4HELLO FROM C3
5HELLO FROM C4
6逐次実行: 約 1.1 秒
7並行実行: 約 0.2 秒

逐次実行では 0.2 秒の待ちが 5 回積み重なり、接続の確立などの時間も加わって 1 秒あまりかかる。並行実行では 5 つの待ちが重なり合うので、ほぼ 1 回分の 0.2 秒で終わる。所要時間は環境によって多少変わるが、両者の比はおおむねこのようになる。ここで、スレッドは 1 つしか使っていない点に注意してほしい。サーバの 5 つのタスクとクライアントの 5 つのコルーチンは、すべて同じスレッドの上で、await のたびに交代しながら進んでいる。Linux では asyncio のイベントループは epoll を、Windows では既定で IOCP を使う。

asyncio では、タスクが切り替わるのは await の位置だけである。この方式を協調的マルチタスクと呼ぶ。タイマ割り込みでいつ切り替わるか分からないスレッドと違い、await を挟まない区間は他のタスクに割り込まれないので、競合状態を考えるべき場所が限られる。逆に言えば、await をしない長い処理は、イベントループ全体を止める。asyncio のコルーチンの中で time.sleep や、asyncio に対応していないライブラリのブロッキング I/O を呼んではならない。どうしても必要な場合は、asyncio.to_thread() で別のスレッドに任せる。

9.3.5. スレッド、asyncio、プロセスの使い分け

「Python の GIL とマルチプロセス」で述べたとおり、CPython の GIL のもとでは、入出力待ちが中心の処理はスレッドか asyncio、CPU を多く使う処理はプロセスで並行化する。3 つの方式の特徴を次の表にまとめる。

既存のライブラリの多くがブロッキング I/O で書かれているため、少数の並行処理なら ThreadPoolExecutor を使うのが手軽である。多数の接続を扱うネットワークサーバやクローラでは asyncio が有利になる。両者は組み合わせることもでき、asyncio のプログラムから asyncio.to_thread() でブロッキングする処理をスレッドに任せたり、run_in_executor で重い計算をプロセスプールに任せたりできる。

9.4. まとめ

  • 共有データの更新には排他制御が必要である。条件が成り立つまで待つには条件変数を使い、生産者・消費者問題は queue.Queue で簡潔に解ける。デッドロックは 4 つの条件がすべて成り立つときに起き、ロックの取得順序を統一することで防げる。

  • ロックは CAS などのアトミック操作の上に作られている。コンパイラと CPU は読み書きの順序を入れ替え得るので、スレッド間の可視性はロックやアトミック変数（メモリバリア）で保証する。

  • 多数の入出力の待ちは、I/O 多重化（epoll や kqueue）とイベントループで少数のスレッドにさばかせられる。Python の asyncio は、コルーチンと await によって 1 つのスレッドで多数の待ちを並行して進める。

  • GIL のもとでは、CPU を多く使う処理はプロセス、入出力待ちが中心の処理はスレッドか asyncio で並行化する。
