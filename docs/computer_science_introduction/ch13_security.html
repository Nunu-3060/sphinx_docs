13. 情報セキュリティと暗号

ネットワークにつながったシステムは、常に悪意のある第三者からの攻撃にさらされている。この章では、情報を守るための基本的な考え方と、その道具となる暗号技術を学ぶ。まず情報セキュリティの目標と、脅威・脆弱性という基本的な概念を整理する。次に、共通鍵暗号と公開鍵暗号、ハッシュ関数、メッセージ認証コード、デジタル署名と公開鍵証明書という暗号技術の部品を順に説明し、それらを組み合わせた TLS の役割を概観する。最後に、鍵やトークンの生成に欠かせない暗号学的に安全な乱数を、シミュレーションなどに使う擬似乱数と対比して説明する。これらの道具を使ってパスワード、認証、セッションを安全に扱う方法と、アプリケーションの代表的な脆弱性は、次の「認証とアプリケーションのセキュリティ」で扱う。

暗号技術では、仕組みを理解することと、安全に実装して使うことはまったく別の問題である。この章のサンプルコードは仕組みを理解するためのものであり、実際のシステムでは十分に検証された暗号ライブラリを使わなければならない。全体像については [Anderson] を参照してほしい。

13.1. 情報セキュリティの 3 要素

情報セキュリティの目標は、次の 3 つの性質を保つことであるとされる。英語の頭文字をとって CIA と呼ばれることもある。

  • 機密性（Confidentiality）: 許可された者だけが情報にアクセスできること。通信の盗聴や、データベースからの個人情報の漏えいは機密性の侵害である。

  • 完全性（Integrity）: 情報が正確であり、許可なく改ざんされていないこと。送金額の書き換えや、Web ページの改ざんは完全性の侵害である。

  • 可用性（Availability）: 許可された者が、必要なときに情報やサービスを利用できること。大量の通信を送りつけてサービスを停止させる DoS 攻撃（Denial of Service attack）は、可用性の侵害である。

これらに加えて、情報の発信者が本人であることを確認できる真正性、操作を行った者を後から追跡できる責任追跡性、行った操作を後から否定できないようにする否認防止なども、セキュリティの目標として挙げられる。

3 つの要素は互いに対立することがある。例えば、データを厳重に暗号化して鍵を 1 人だけが管理すれば機密性は高まるが、その人が不在のときにはデータを使えず可用性が下がる。セキュリティ対策は、守るべきものと許容できるコストに応じて、これらの釣り合いをとる作業である。

13.2. 脅威と脆弱性

セキュリティを議論するときは、次の用語を区別する。

  • 資産: 守るべき対象。顧客情報、ソースコード、サービスの稼働そのものなど。

  • 脅威: 資産に損害を与えうる事象や行為。外部からの攻撃、内部者による持ち出し、操作ミス、災害など。

  • 脆弱性: 脅威が実際に損害をもたらすことを可能にする弱点。プログラムの不具合、設定の誤り、推測しやすいパスワード、運用手順の不備など。

脅威があっても脆弱性が無ければ損害は生じにくく、脆弱性があっても脅威が無ければ問題は顕在化しにくい。リスクは、脅威が脆弱性を突いて損害が生じる可能性と、その損害の大きさの組み合わせとして評価する。ソフトウェア開発者が最も直接的に関わるのは、脆弱性を作り込まないことである。

また、攻撃者は防御の最も弱いところを狙う。強力な暗号を使っていても、鍵がソースコードに書かれて公開リポジトリに置かれていれば意味がない。複数の防御を重ねて、1 つが破られても被害を食い止める多層防御や、利用者やプログラムに必要最小限の権限だけを与える最小権限の原則が、設計上の基本的な考え方である。

13.3. 暗号の基礎

13.3.1. 暗号の用語

暗号化の前の読めるデータを平文（plaintext）、暗号化した後のデータを暗号文（ciphertext）と呼ぶ。平文を暗号文に変換することを暗号化（encryption）、暗号文を平文に戻すことを復号（decryption）と呼ぶ。暗号化と復号には鍵（key）と呼ばれる秘密の値を使う。

現代の暗号は、暗号化の手順（アルゴリズム）を公開し、鍵だけを秘密にしても安全であるように設計される。この考え方をケルクホフスの原理と呼ぶ。手順を秘密にすることで安全性を保とうとする方式は、手順が漏れた時点で破られ、公開の場で専門家に検証されることもないため、信頼できない。独自の暗号方式を考案して使うべきではない理由の 1 つがここにある。

13.3.2. 共通鍵暗号と鍵配送問題

暗号化と復号に同じ鍵を使う方式を共通鍵暗号（対称鍵暗号）と呼ぶ。現在最も広く使われているのは AES（Advanced Encryption Standard）であり、128 ビットのブロックを単位に、128、192、256 ビットのいずれかの長さの鍵で暗号化する。共通鍵暗号は高速であり、多くの CPU は AES 専用の命令を備えている。

ブロック暗号で長いデータを暗号化するには、ブロックの処理方法を決める暗号利用モードを組み合わせる。各ブロックを独立に暗号化する ECB モードは、同じ平文のブロックが同じ暗号文のブロックになり、データの模様が透けて見えるため使ってはならない。現在は、暗号化と同時に改ざんの検出も行う認証付き暗号（AEAD: Authenticated Encryption with Associated Data）の AES-GCM や ChaCha20-Poly1305 を使うのが一般的である。

共通鍵暗号の問題は、通信相手と同じ鍵をあらかじめ安全に共有しておかなければならないことである。暗号化されていない通信路で鍵を送れば盗聴されてしまう。これを鍵配送問題と呼ぶ。さらに、\(n\) 人が互いに秘密の通信をするには、2 人の組ごとに別の鍵が必要なので、鍵の数は \(n(n-1)/2\) になる。100 人なら 4950 個の鍵を安全に配り、管理しなければならない。

13.3.3. 公開鍵暗号

公開鍵暗号（非対称鍵暗号）は、暗号化と復号に異なる鍵を使うことで鍵配送問題を解決する。各利用者は、数学的に対応する公開鍵と秘密鍵の組を作る。公開鍵は誰に知られてもよく、秘密鍵は本人だけが持つ。送信者は受信者の公開鍵で暗号化し、受信者は自分の秘密鍵で復号する。公開鍵から秘密鍵を求めることは計算量的に困難なので、公開鍵を誰に配ってもかまわない。\(n\) 人の場合でも、必要な鍵の組は \(n\) 組で済む。

代表的な公開鍵暗号である RSA は、大きな合成数の素因数分解が困難であることを安全性の根拠とする。鍵の生成、暗号化、復号は次のとおりである（\(\bmod\) は割った余りを表す）。

  1. 大きな素数 \(p\) と \(q\) を選び、\(n = pq\) とする。

  2. \(\varphi(n) = (p-1)(q-1)\) を計算する。\(\varphi\) はオイラーの関数であり、\(\varphi(n)\) は \(1\) 以上 \(n\) 以下で \(n\) と互いに素な整数の個数である。

  3. \(\varphi(n)\) と互いに素な整数 \(e\) を選ぶ（実用上は \(e = 65537\) がよく使われる）。

  4. \(ed \equiv 1 \pmod{\varphi(n)}\) を満たす \(d\) を求める。つまり \(d\) は \(\varphi(n)\) を法とする \(e\) の逆元である。

  5. 公開鍵は \((n, e)\)、秘密鍵は \(d\) である（\(p\)、\(q\)、\(\varphi(n)\) も秘密にする）。

平文 \(m\)（\(0 \le m < n\) の整数）の暗号化と、暗号文 \(c\) の復号は次の式で行う。

\[c = m^{e} \bmod n, \qquad m = c^{d} \bmod n\]

\(ed = 1 + k\varphi(n)\)（\(k\) は整数）なので、オイラーの定理（と中国剰余定理）から \(c^{d} = m^{ed} = m^{1 + k\varphi(n)} \equiv m \pmod{n}\) が成り立ち、復号で元の平文に戻る。\(n\) を素因数分解できれば \(\varphi(n)\) が分かり、\(d\) を計算できてしまう。そのため、実用の \(n\) は 2048 ビット以上（10 進数で 600 桁以上）にする。なお、\(m^{e} \bmod n\) は、指数を 2 進数で表して 2 乗と乗算を繰り返すことで、指数のビット数に比例する回数の乗算で計算できる。

次のサンプルは、小さな素数を使って RSA の鍵生成、暗号化・復号、署名（後述）を行う。

警告

このサンプルは RSA の仕組みを理解するための学習用であり、実運用には絶対に使ってはならない。\(n = 3233\) のような小さな鍵は一瞬で素因数分解できる。また、ここで示す「教科書的 RSA」は、同じ平文が常に同じ暗号文になるため推測した平文の確認に使われるなど、多くの攻撃に弱い。実際の RSA では、暗号化に OAEP、署名に PSS というランダム性を加える方式（パディング）を組み合わせる [RFC8017]。暗号は自分で実装せず、検証済みのライブラリを使うこと。

ch13_toy_rsa.py
 1"""小さな素数を使った教科書的 RSA による暗号化・復号・署名のサンプル。
 2
 3警告: これは仕組みを理解するための学習用コードであり、実運用には
 4絶対に使ってはならない。鍵が小さすぎて瞬時に素因数分解できるうえ、
 5パディング（OAEP や PSS）を行わない教科書的 RSA は、同じ平文が
 6常に同じ暗号文になるなど多くの攻撃に弱い。実際のシステムでは、
 7検証済みの暗号ライブラリを使うこと。
 8
 9実行方法: python ch13_toy_rsa.py
10関連する章: 第 13 章「情報セキュリティと暗号」
11"""
12
13from math import gcd
14from typing import NamedTuple
15
16
17class KeyPair(NamedTuple):
18    """RSA の鍵の組。公開鍵は (n, e)、秘密鍵は (n, d)。"""
19
20    n: int
21    e: int
22    d: int
23
24
25def generate_keys(p: int, q: int, e: int) -> KeyPair:
26    """素数 p, q と公開指数 e から鍵の組を作る。"""
27    n = p * q
28    phi = (p - 1) * (q - 1)  # オイラーの関数 φ(n)
29    if gcd(e, phi) != 1:
30        raise ValueError("e と φ(n) が互いに素ではない")
31    d = pow(e, -1, phi)  # e·d ≡ 1 (mod φ(n)) を満たす d
32    return KeyPair(n, e, d)
33
34
35def encrypt(m: int, key: KeyPair) -> int:
36    """公開鍵で平文 m（0 <= m < n）を暗号化する。"""
37    return pow(m, key.e, key.n)
38
39
40def decrypt(c: int, key: KeyPair) -> int:
41    """秘密鍵で暗号文 c を復号する。"""
42    return pow(c, key.d, key.n)
43
44
45def sign(m: int, key: KeyPair) -> int:
46    """秘密鍵で m に署名する（実際には m のハッシュ値に署名する）。"""
47    return pow(m, key.d, key.n)
48
49
50def verify(m: int, s: int, key: KeyPair) -> bool:
51    """公開鍵で署名 s が m に対するものかを検証する。"""
52    return pow(s, key.e, key.n) == m
53
54
55def main() -> None:
56    """鍵生成、暗号化・復号、署名・検証の結果を表示する。"""
57    p, q = 61, 53
58    key = generate_keys(p, q, e=17)
59    print(f"p = {p}, q = {q}, n = {key.n}, phi = {(p - 1) * (q - 1)}")
60    print(f"公開鍵 (n, e) = ({key.n}, {key.e})")
61    print(f"秘密鍵 d = {key.d}")
62    print(f"e * d mod phi = {key.e * key.d % ((p - 1) * (q - 1))}")
63
64    m = 65
65    c = encrypt(m, key)
66    print(f"平文 {m} -> 暗号文 {c} -> 復号 {decrypt(c, key)}")
67    print(f"同じ平文を再度暗号化: {encrypt(m, key)}")
68
69    s = sign(m, key)
70    print(f"署名 s = {s}, 検証: {verify(m, s, key)}")
71    print(f"改ざんした m = {m + 1} の検証: {verify(m + 1, s, key)}")
72
73
74if __name__ == "__main__":
75    main()

ch13_toy_rsa.py

25〜32 行目の generate_keys が鍵生成である。31 行目の pow(e, -1, phi) は、Python 3.8 以降で使える、法 phi における e の逆元を求める書き方である。37 行目と 42 行目の pow(x, y, n) は \(x^{y} \bmod n\) を効率よく計算する。実行結果は次のとおりである。

1p = 61, q = 53, n = 3233, phi = 3120
2公開鍵 (n, e) = (3233, 17)
3秘密鍵 d = 2753
4e * d mod phi = 1
5平文 65 -> 暗号文 2790 -> 復号 65
6同じ平文を再度暗号化: 2790
7署名 s = 588, 検証: True
8改ざんした m = 66 の検証: False

\(p = 61\)、\(q = 53\) から \(n = 3233\)、\(\varphi(n) = 60 \times 52 = 3120\) となる。\(e = 17\) に対して \(d = 2753\) であり、\(17 \times 2753 = 46801 = 15 \times 3120 + 1\) なので \(ed \equiv 1 \pmod{3120}\) を満たす（実行結果の 4 行目）。平文 \(m = 65\) は \(65^{17} \bmod 3233 = 2790\) に暗号化され、\(2790^{2753} \bmod 3233 = 65\) と復号される（5 行目）。6 行目は、同じ平文を暗号化すると必ず同じ暗号文になるという、教科書的 RSA の弱点を示している。

13.3.4. ハイブリッド暗号

公開鍵暗号は鍵配送問題を解決するが、共通鍵暗号に比べて数百倍から数千倍遅く、大きなデータの暗号化には向かない。そこで実際のシステムでは、両者を組み合わせたハイブリッド暗号を使う。

  1. 送信者は、ランダムな共通鍵（セッション鍵）を生成する。

  2. データ本体をセッション鍵で暗号化する（共通鍵暗号なので速い）。

  3. セッション鍵を受信者の公開鍵で暗号化する（短いので遅くても問題ない）。

  4. 受信者は、自分の秘密鍵でセッション鍵を復号し、そのセッション鍵でデータ本体を復号する。

電子メールの暗号化などはこの形である。TLS では、公開鍵で鍵を暗号化して送る代わりに、後述する鍵交換によって双方が同じセッション鍵を導出する。いずれも、公開鍵暗号の技術で共通鍵を共有し、データ本体は共通鍵暗号で保護するという考え方は同じである。

13.4. ハッシュ関数

13.4.1. 暗号学的ハッシュ関数の性質

ハッシュ関数は、任意の長さのデータから固定長の値（ハッシュ値、ダイジェスト）を計算する関数である。「データ構造」のハッシュ表で使うハッシュ関数は値が散らばれば十分だが、セキュリティに使う暗号学的ハッシュ関数は、ハッシュ関数 \(H\) について次の性質を満たす必要がある。

  • 原像計算困難性（一方向性）: ハッシュ値 \(h\) が与えられたとき、\(H(x) = h\) となる \(x\) を見つけることが計算量的に困難である。

  • 第 2 原像計算困難性: 入力 \(x\) が与えられたとき、\(H(x') = H(x)\) となる別の入力 \(x' \ne x\) を見つけることが困難である。

  • 衝突困難性: \(H(x) = H(x')\) となる異なる入力の組 \(x, x'\) を、どのようなものでもよいから 1 組見つけることが困難である。

ハッシュ値の長さは固定なので、異なる入力が同じハッシュ値になる衝突は必ず存在する。性質が求めるのは、それを見つけることが現実的な計算量では不可能なことである。出力が \(b\) ビットの理想的なハッシュ関数では、原像の発見に約 \(2^{b}\) 回、衝突の発見には誕生日のパラドックスにより約 \(2^{b/2}\) 回の計算が必要になる。

また、入力が 1 ビットでも変われば、出力のビットのおよそ半分が予測できない形で変わることが望ましい。この性質を雪崩効果と呼ぶ。

13.4.2. SHA-256 と、MD5・SHA-1 を使わない理由

現在広く使われているのは、SHA-2 系列の SHA-256 である [FIPS180-4]。出力は 256 ビット（32 バイト）で、衝突の発見には約 \(2^{128}\) 回の計算が必要とされる。

古いハッシュ関数である MD5（出力 128 ビット）と SHA-1（出力 160 ビット）は、理論上の値よりはるかに少ない計算量で衝突を見つける攻撃法が発見されている。MD5 の衝突は 2004 年に示され、現在では一般的な PC で短時間に作れる。SHA-1 も 2017 年に実際の衝突例が公表された。衝突を作れると、内容の異なる 2 つの文書に同じハッシュ値を持たせ、一方に付けたデジタル署名を他方に流用するといった攻撃が可能になる。そのため、セキュリティ目的で MD5 や SHA-1 を使ってはならない。新しく設計するなら SHA-256 以上、または SHA-3 系列を使う。

注釈

ハッシュ化は暗号化ではない。暗号化は鍵を使えば復号して元に戻せるが、暗号学的ハッシュ関数には鍵が無く、ハッシュ値から元のデータに戻す手順も存在しない。「パスワードを SHA-256 で暗号化する」のような表現は誤りであり、後で述べるように、パスワードの保存には単純なハッシュ関数も不十分である。

13.5. メッセージ認証コード

ハッシュ値をデータと一緒に送れば、通信の途中で偶然に起きた誤りは検出できる。しかし、攻撃者はデータを改ざんしたうえでハッシュ値も計算し直せるので、意図的な改ざんは検出できない。改ざんを検出するには、正しい送信者と受信者だけが知る秘密を使う必要がある。

メッセージ認証コード（MAC: Message Authentication Code）は、共通の秘密鍵 \(K\) とメッセージ \(m\) から計算する短い値（タグ）である。受信者は同じ鍵でタグを計算し直し、受け取ったタグと一致すれば、メッセージが鍵を知る者によって作られ、改ざんされていないと判断できる。つまり MAC は完全性と、送信元の真正性を保証する。

ハッシュ関数を使った MAC の標準的な構成が HMAC である。単純に \(H(K \| m)\)（\(\|\) は連結）を計算する方法は、SHA-256 のような構造のハッシュ関数では、タグを知っていれば鍵を知らなくても \(m\) の後ろにデータを追加したメッセージの正しいタグを計算できてしまう（伸長攻撃）。HMAC は、鍵 \(K\)（ハッシュ関数のブロック長に合わせて調整したもの）から作った 2 つの値 \(K \oplus \mathit{ipad}\) と \(K \oplus \mathit{opad}\)（\(\oplus\) は排他的論理和、\(\mathit{ipad}\) と \(\mathit{opad}\) は定数）を使って、ハッシュ関数を 2 回適用する。

\[\mathrm{HMAC}(K, m) = H\bigl((K \oplus \mathit{opad}) \,\|\, H((K \oplus \mathit{ipad}) \,\|\, m)\bigr)\]

上のサンプルの 26〜28 行目では、hmac.new で HMAC-SHA256 のタグを計算している。実行結果の 8〜10 行目のように、正しい鍵とメッセージなら検証に成功し、メッセージを 1 文字変えても、鍵が異なっても検証に失敗する。

33 行目では、タグの比較に == ではなく hmac.compare_digest を使っている。== によるバイト列の比較は、最初に異なるバイトが見つかった時点で終わるため、比較にかかる時間から何バイト目まで一致したかが漏れうる。攻撃者はこれを手がかりに、正しいタグを先頭から 1 バイトずつ推測できる（タイミング攻撃）。compare_digest は、内容にかかわらず一定の時間で比較する。

13.6. デジタル署名と公開鍵証明書

13.6.1. デジタル署名

MAC は送信者と受信者が同じ鍵を持つので、受信者もタグを作れる。そのため、第三者に対して「このメッセージは確かに送信者が作った」と証明することはできない。デジタル署名は、公開鍵暗号の技術を使ってこの問題を解決する。

署名者は、メッセージのハッシュ値に対して自分の秘密鍵で署名を計算する。検証者は、署名者の公開鍵を使って、署名がそのメッセージに対するものかを確かめる。秘密鍵を持つのは署名者だけなので、正しい署名を作れるのは署名者だけであり、署名者は後から署名したことを否定できない（否認防止）。メッセージ全体ではなくハッシュ値に署名するのは、公開鍵暗号の計算が遅いためであり、ハッシュ関数の衝突困難性が署名の安全性の前提になる。

RSA による署名は、暗号化と逆に秘密鍵 \(d\) で \(s = h^{d} \bmod n\) を計算し（\(h\) はハッシュ値）、検証では公開鍵 \(e\) で \(s^{e} \bmod n = h\) かを確かめる。前のサンプルでは簡単のため \(m = 65\) に直接署名しており、\(65^{2753} \bmod 3233 = 588\) が署名になる。\(588^{17} \bmod 3233 = 65\) なので検証に成功し（実行結果の 7 行目）、66 に対しては失敗する（8 行目）。署名には RSA のほか、楕円曲線を使う ECDSA や Ed25519 が広く使われている。

13.6.2. 公開鍵証明書と認証局

公開鍵暗号にも弱点がある。受け取った公開鍵が本当に通信したい相手のものかを確かめられないことである。攻撃者が通信の途中に割り込み、相手の公開鍵を自分の公開鍵にすり替えれば、攻撃者は暗号文を復号し、内容を読んだうえで本物の相手に転送できる。このような攻撃を中間者攻撃（man-in-the-middle attack）と呼ぶ。

この問題を解決するのが公開鍵証明書である。公開鍵証明書は、「この公開鍵はこの主体（例えばドメイン名 example.com）のものである」という内容に、信頼できる第三者がデジタル署名したデータである。証明書には、主体の名前、公開鍵、有効期間、発行者などが含まれ、形式は X.509 という規格で定められている。証明書を発行する第三者を認証局（CA: Certificate Authority）と呼ぶ。

認証局の公開鍵自体も、上位の認証局が発行した証明書で保証される。この連鎖をたどった先には、自分自身で署名したルート認証局の証明書がある。ルート証明書は OS やブラウザにあらかじめ組み込まれており、利用者はそれを信頼の起点として、サーバの証明書から順に署名を検証する。この仕組み全体を公開鍵基盤（PKI: Public Key Infrastructure）と呼ぶ。秘密鍵が漏えいした場合などに備えて、有効期間内でも証明書を失効させる仕組みもある。

13.7. TLS の役割

「コンピュータネットワーク」で学んだ HTTPS は、HTTP の通信を TLS（Transport Layer Security）で保護したものである [RFC8446]。TLS は TCP などの信頼性のある通信路の上で動作し、アプリケーションに対して次の 3 つを提供する。

  • 機密性: 通信内容を暗号化し、盗聴されても読めないようにする。

  • 完全性: 通信内容の改ざんを検出する。

  • 認証: 証明書によって、接続先のサーバが本物であることを確認する（必要ならクライアントも認証する）。

TLS 1.3 の接続開始時の手順（ハンドシェイク）の概要は次のとおりである。

  1. クライアントは、対応する暗号方式の一覧と、鍵交換のための一時的な公開値を送る（ClientHello）。

  2. サーバは、使う暗号方式と自分の一時的な公開値を返す（ServerHello）。双方は、相手の公開値と自分の秘密の値から、楕円曲線ディフィー・ヘルマン鍵交換（ECDHE）によって同じ共通の秘密を計算し、そこからセッション鍵を導出する。この値は通信路を流れないので、盗聴者には分からない。

  3. サーバは、自分の証明書と、ハンドシェイクの内容に対する自分の秘密鍵による署名を送る。クライアントは、証明書の連鎖を検証し、さらに署名を検証して、サーバが証明書に対応する秘密鍵を持つ（つまり本物である）ことを確認する。また、証明書の主体が接続しようとしたドメイン名と一致することも確認する。

  4. 双方がハンドシェイク全体に対する MAC を交換して改ざんが無かったことを確認し、以後のデータを、セッション鍵を使った認証付き暗号（AES-GCM など）で保護する。

ここまでに説明した部品がすべて使われていることが分かる。鍵交換と署名には公開鍵暗号の技術、証明書には PKI、データの保護には共通鍵暗号と MAC の機能を持つ認証付き暗号、鍵の導出には HMAC が使われる。セッション鍵は接続ごとに一時的な値から作られて保存されないので、後でサーバの秘密鍵が漏えいしても、過去の通信は復号できない。この性質を前方秘匿性（forward secrecy）と呼ぶ。

注釈

TLS が保護するのは通信路の上のデータだけである。サーバに保存されたデータや、サーバ自体の脆弱性は TLS では守れない。また、HTTPS であることは「接続先が証明書に書かれたドメインである」ことを示すだけで、そのサイトが信頼できることを保証するものではない。

13.8. 擬似乱数と暗号学的乱数

ここまでに登場した共通鍵、TLS のセッション鍵や鍵交換の秘密の値、後で扱うパスワードのソルトやセッション ID は、どれも攻撃者に予測できない乱数でなければならない。どれほど強い暗号を使っても、鍵が予測できれば意味がない。ここでは、プログラムで使う乱数の 2 つの種類を区別する。

13.8.1. 擬似乱数生成器

コンピュータは決められた手順どおりに動くので、計算だけで本当の意味の乱数を作ることはできない。擬似乱数生成器（PRNG: Pseudo-Random Number Generator）は、内部に状態を持ち、状態を一定の規則で更新しながら、乱数のように見える数の列を出力するアルゴリズムである。状態の初期値を決める値をシードと呼ぶ。手順が決まっているので、同じシードからは必ず同じ列が得られる。この再現性は、シミュレーションや試験で結果を再現したいときに便利である。例えば第 11 章のサンプル ch11_index.py は、シードを固定して毎回同じデータを生成している。

Python の random モジュールが使うのは、メルセンヌ・ツイスタ（MT19937）と呼ばれる擬似乱数生成器である。周期が \(2^{19937} - 1\) と非常に長く、統計的な偏りが小さく、高速なので、シミュレーションなどの用途には優れている。内部状態は 32 ビットの値 624 個からなり、出力は状態の値に可逆な変換（ビットのシフトと排他的論理和）を施したものである。

しかし、メルセンヌ・ツイスタは予測されないことを目的に設計されていない。出力の変換は逆にたどれるので、連続する 624 個の 32 ビットの出力を観測すれば内部状態をそのまま復元でき、以後の出力をすべて予測できる。シードを OS から得た値で初期化しても、この性質は変わらない。

13.8.2. 暗号学的に安全な乱数

セキュリティの用途に使う乱数には、それまでの出力をいくら観測しても、次の出力を当て推量より高い確率で予測できないことが求められる。この性質を満たす生成器を暗号学的に安全な擬似乱数生成器（CSPRNG: Cryptographically Secure Pseudo-Random Number Generator）と呼ぶ。内部では、ハッシュ関数や共通鍵暗号のような、出力から内部の値を逆算できない部品を使う。さらに、状態がいつか漏れた場合に備えて、過去の出力を復元できないことも求められる。

CSPRNG のシードは予測できない値でなければならない。OS は、割り込みの発生時刻のゆらぎや、CPU が備える乱数生成回路（ハードウェア乱数生成器）などから予測できない値（エントロピー）を集め、それをもとに CSPRNG を動かして、プログラムに乱数を提供する。Linux の getrandom システムコールや /dev/urandom、Windows の BCryptGenRandom がこれに当たる。Python では、次の方法で OS の乱数源を使える。

  • os.urandom(n): OS の乱数源から \(n\) バイトのバイト列を得る。次章の ch14_password.py のソルトの生成に使っている。

  • secrets モジュール: os.urandom と同じ乱数源を使い、トークンの生成に便利な関数をまとめたものである [PythonDocs]。token_bytes(n) はバイト列、token_hex(n) は \(n\) バイトを 16 進数の文字列、token_urlsafe(n) は \(n\) バイトを Base64URL の文字列にして返す。randbelow(k) は \(0\) 以上 \(k\) 未満の整数を、choice(seq) は列の要素を 1 つ選んで返す。

  • random.SystemRandom: random モジュールと同じ使い方で、OS の乱数源を使うクラスである。シードを指定しても無視され、再現性は無い。

13.8.3. random をトークン生成に使ってはならない理由

パスワード再設定用の URL に含めるトークンや、セッション ID を random で生成すると、攻撃者は自分宛てのトークンを多数発行させて出力を観測し、生成器の状態を復元できる。そうなれば、他の利用者に発行されるトークンも予測できてしまう。処理系によっては、シードが起動時刻などから作られ、シード自体を総当たりで推測できる場合もある。次のサンプルは、random の再現性と予測可能性を確かめ、secrets の使用例を示す。

ch13_random.py

 2
 3random モジュールはメルセンヌ・ツイスタ（MT19937）であり、同じシードから

13import secrets
14

16
17
18def undo_right(y: int, shift: int) -> int:
19    """y ^= y >> shift の逆変換。"""
20    x = y
21    for _ in range(32 // shift + 1):
22        x = y ^ (x >> shift)
23    return x & MASK32
24
25
26def undo_left(y: int, shift: int, mask: int) -> int:
27    """y ^= (y << shift) & mask の逆変換。"""
28    x = y
29    for _ in range(32 // shift + 1):
30        x = y ^ ((x << shift) & mask)
31    return x & MASK32
32
33
34def untemper(y: int) -> int:
35    """MT19937 の出力変換（tempering）を逆にたどり、内部状態の値に戻す。"""
36    y = undo_right(y, 18)
37    y = undo_left(y, 15, 0xEFC60000)
38    y = undo_left(y, 7, 0x9D2C5680)
39    return undo_right(y, 11)
40
41
42def clone(outputs: list[int]) -> random.Random:
43    """連続する 624 個の 32 ビット出力から、同じ状態の生成器を作る。"""
44    state = tuple(untemper(y) for y in outputs) + (624,)
45    rng = random.Random()
46    rng.setstate((3, state, None))
47    return rng
48
49

52    print("[シードによる再現性]")
53    for _ in range(2):
54        rng = random.Random(2024)
55        print([rng.randrange(100) for _ in range(5)])
56
57    print("[出力からの予測]")
58    victim = random.Random()  # シードは OS の乱数源から設定される
59    observed = [victim.getrandbits(32) for _ in range(624)]
60    attacker = clone(observed)
61    predicted = [attacker.getrandbits(32) for _ in range(5)]
62    actual = [victim.getrandbits(32) for _ in range(5)]
63    print("予測と実際が一致:", predicted == actual)
64    print("予測したトークン:", attacker.getrandbits(128).to_bytes(16).hex())
65    print("実際のトークン  :", victim.getrandbits(128).to_bytes(16).hex())
66
67    print("[secrets モジュール]")
68    print("token_hex(16)    :", secrets.token_hex(16))
69    print("token_urlsafe(16):", secrets.token_urlsafe(16))
70    print("randbelow(100)   :", secrets.randbelow(100))

18〜39 行目は、メルセンヌ・ツイスタが出力の直前に施す変換（tempering）の逆変換である。42〜47 行目の clone は、観測した 624 個の出力を逆変換して内部状態を組み立て、setstate で新しい生成器に設定する。58 行目の victim はシードを指定していないので、OS の乱数源から得た値で初期化される。59 行目でその出力を 624 個観測し、60 行目で状態を復元している。実行結果の例を次に示す。

実行結果の 2〜3 行目は、同じシード 2024 から同じ列が得られることを示す。6〜7 行目と 9〜11 行目の値は実行のたびに変わるが、6 行目と 7 行目は常に一致する。シードを知らなくても、観測した出力だけから、次に発行される 128 ビットのトークンを完全に予測できたのである。トークンには secrets を使い、長さは推測を防ぐのに十分な 128 ビット（16 バイト）以上にする。token_hex(16) は 32 文字の 16 進数、token_urlsafe(16) は 22 文字の文字列になる。

13.9. まとめ

  • 情報セキュリティの目標は、機密性・完全性・可用性の 3 要素を保つことである。損害は、脅威が脆弱性を突くことで生じる。

  • 共通鍵暗号は高速だが鍵配送問題がある。公開鍵暗号は鍵配送問題を解決するが遅い。実際には両者を組み合わせたハイブリッド暗号を使う。

  • RSA は \(n = pq\) の素因数分解の困難さに基づき、\(ed \equiv 1 \pmod{\varphi(n)}\) を満たす鍵で暗号化と復号を行う。教科書的 RSA は安全ではなく、パディングと検証済みのライブラリが必要である。

  • 暗号学的ハッシュ関数は原像計算困難性・第 2 原像計算困難性・衝突困難性を持つ。SHA-256 を使い、衝突が見つかっている MD5 や SHA-1 は使わない。ハッシュ化は暗号化ではない。

  • MAC（HMAC）は共通鍵で完全性と真正性を保証する。タグの比較には hmac.compare_digest を使う。

  • デジタル署名は秘密鍵で作成し公開鍵で検証するので、否認防止ができる。公開鍵の持ち主は、認証局が署名した公開鍵証明書で保証する。

  • TLS は、鍵交換、証明書による認証、認証付き暗号を組み合わせて、通信の機密性・完全性・認証を提供する。

  • 鍵、トークン、セッション ID、ソルトには、OS の乱数源を使う secrets や os.urandom の乱数を使う。random のメルセンヌ・ツイスタはシードから再現でき、624 個の出力から以後を予測できるので、セキュリティの用途に使ってはならない。
