12. 公開後の運用

ゲームを公開したら終わりではない。公開直後には、開発中には見つからなかった不具合や、想定していなかった遊び方が必ず見つかる。この章では、公開後に行う作業と、次の作品につなげるための振り返りを扱う。

12.1. フィードバックを集める

プレイヤーの声を集める窓口を用意しておく。

  • 配布先のコメント欄やレビュー、掲示板（itch.io のコメント、Steam のレビューとディスカッションなど）

  • SNS での感想や、ゲームの名前での検索結果

  • 不具合報告用のフォームや、Discord などのコミュニティー

寄せられた声のうち、不具合の報告は、発生した環境（OS、画面の解像度など）と操作の手順が分からないと再現できない。報告フォームに入力欄を用意する、ゲームが記録したログファイルの場所を案内するなど、必要な情報を集めやすくしておく。

12.2. 不具合を直してアップデートする

報告された不具合は、すべてをすぐに直せるとは限らない。影響の大きさで優先度を付ける。

表 12.1 不具合の優先度の例

優先度

基準

例

最優先

起動できない、進行できない、データが消える

特定の環境で起動直後に落ちる。セーブデータが壊れる

高

多くのプレイヤーが遊びにくさを感じる

特定のステージで必ず処理落ちする

低

遊ぶうえで支障が小さい

文字の誤り、まれにしか起きない表示の乱れ

修正版を配布するときは、次の点に注意する。

  • バージョン番号を付ける: 1.0.1 のような番号を付け、タイトル画面などに表示する。不具合報告を受けたときに、どの版で起きたかが分かる。

  • パッチノートを書く: 何を直し、何を変えたかを配布ページで告知する。変更の一覧をパッチノートと呼ぶ。

  • セーブデータの互換性を保つ: 新しい版で古い版のセーブデータを読めなくなると、プレイヤーの進行が失われる。セーブデータに形式のバージョンを記録しておき、古い形式を変換できるようにする。

  • 変更する前の版を残す: Git でタグを付けておけば、配布した各版のコードにいつでも戻れる。

公開後に新しい要素を追加することもできるが、企画で決めたスコープの考え方はここでも有効である。追加要素の要望にすべて応えようとすると、いつまでも次の作品に進めない。どこまで対応するかを決め、その方針をプレイヤーにも伝えておくとよい。

12.3. 振り返り

公開から一段落したら、制作全体を振り返る。ゲーム業界では、制作の振り返りをポストモーテムと呼ぶ。もともとは「検死」を意味する言葉である。

次のような観点で、うまくいったこととうまくいかなかったことを書き出す。

  • 見積もった制作期間と、実際にかかった期間はどれだけ違ったか。どの作業に予想以上の時間がかかったか。

  • スコープは適切だったか。途中で削った要素、追加した要素は何か。

  • プレイテストで分かったことは何か。もっと早く分かっていればよかったことは何か。

  • 公開と宣伝で、反応があったこと、無かったことは何か。

振り返りの結果は、次の作品の企画と見積もりに活かす。1 本目で得た「自分はどの作業にどれだけ時間がかかるか」という感覚は、2 本目以降のスコープを決めるうえで最も信頼できる材料になる。

12.4. おわりに

本書では、企画、ゲームエンジンの選定、ブロック崩しの制作、アセット、品質の改善、ビルド、公開、運用という、ゲーム制作の一連の流れを見てきた。

最初の 1 本を完成させて公開することは、思っているよりも難しい。しかし、一度その流れを経験すれば、2 本目からは何をすればよいかが見えるようになる。小さく作り、早く遊んでもらい、完成させることを繰り返してほしい。
