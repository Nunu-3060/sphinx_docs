3. Jenkins の基本操作（Freestyle ジョブ）

Pipeline に入る前に、Jenkins の基本的な操作感を Freestyle ジョブを通じて把握します。

3.1. ダッシュボードとジョブの概念

Jenkins にログインすると表示されるダッシュボードには、これまでに作成したジョブ（Job）の一覧が並びます。ジョブは「何を、どう実行するか」を定義したものであり、プログラミングにおける「関数の定義」に近い存在です。

ジョブを実行すると、その実行 1 回ごとにビルド（Build）が生成されます。関数定義と、それを呼び出した際の 1 回の実行（呼び出しスタック上の 1 フレーム）の関係になぞらえると理解しやすいでしょう。各ビルドには番号が振られ、コンソールログや実行結果（成功・失敗・不安定）が個別に記録されます。

ジョブが実行される際、Jenkins はエージェント上にワークスペース（Workspace）と呼ばれる作業用ディレクトリを用意します。ソースコードのチェックアウトやビルドの中間生成物は、原則としてこのワークスペース内に置かれます。同じジョブを 2 回実行すると、デフォルトでは同じワークスペースが再利用される点に注意してください（前回の実行で生成されたファイルが残っている可能性があります）。

3.2. 最初のジョブを作成する

ダッシュボードから「新しいジョブを作成」を選び、ジョブタイプとして「フリースタイル・プロジェクトのビルド」を選択します。

「ビルド」セクションで「シェルの実行」（Windows 環境では「Windows バッチコマンドの実行」）を追加し、次のような内容を入力してみましょう。

echo "Hello, Jenkins!"
date

「保存」してジョブを作成したら、「ビルド実行」をクリックします。ビルド履歴に実行結果が追加されるので、番号をクリックし、「コンソール出力」を開いてください。シェルに渡したコマンドの実行結果がそのまま表示されます。

これが Jenkins における最も基本的なフィードバックループです。以降のすべての機能（Pipeline、通知連携、テスト結果の集計など）は、この「コマンドを実行し、その結果を記録する」という仕組みの上に成り立っています。

3.3. ソースコード管理との連携

実際のプロジェクトでは、ジョブ実行前にリポジトリからソースコードを取得する必要があります。ジョブの設定画面で「ソースコード管理」を「Git」に変更し、リポジトリの URL とブランチ（例: main）を指定すると、ビルド開始時に自動でチェックアウトが行われます。

注釈

プライベートリポジトリに接続する際は認証情報（Credentials）の登録が必要になります。ここでは Jenkins UI から最小限の登録を行うにとどめ、仕組みの詳細は 外部ツールとの連携 で扱います。

プライベートリポジトリの場合、認証情報の選択欄で新しい Credential を追加します。SSH の秘密鍵、または GitHub の Personal Access Token を登録しておけば、以降はプルダウンから選択するだけで再利用できます。

3.4. ビルドトリガーの種類

ジョブは手動実行だけでなく、次のようなトリガーで自動実行できます。

  • 定期実行（cron 形式） ── 「定期的に実行」を選び、H/15 * * * * のような cron 形式でスケジュールを指定します。先頭の H は Jenkins が負荷分散のために実際の分をハッシュ値から自動決定する記法です。

  • SCM ポーリング ── 「SCM をポーリング」を選ぶと、指定した間隔でリポジトリに新しいコミットがあるかを確認し、あれば自動でビルドします。手軽ですが、ポーリング間隔の分だけフィードバックが遅れます。

  • Webhook トリガー ── GitHub/GitLab 側からの push イベントを Jenkins に直接通知させる方式。ポーリングと異なり、push した瞬間にビルドが始まるため、実運用ではこちらが推奨されます。

  • 他のジョブからのトリガー ── 「他のプロジェクトのビルド後に実行」により、ジョブ同士を数珠つなぎにできます。ただし、依存関係が複雑になると管理が難しくなるため、後述する Pipeline に置き換えることが多くなります。

3.5. Freestyle ジョブの限界

Freestyle ジョブは UI 上のフォームに設定を積み重ねていく方式のため、次のような限界があります。

  • 設定がコードとして残らない ── ビルド手順は Jenkins の内部データベース（ジョブ定義の XML）に保存されるため、Git でのレビューや差分管理ができません。誰がいつ何を変更したかを Jenkins の外から追跡できません。

  • 条件分岐・並列実行の表現が難しい ── 「テストが通ったらステージング環境にデプロイし、失敗したら Slack に通知する」といった分岐や、複数タスクの並列実行を UI 上のプラグイン設定だけで表現するのは煩雑になりがちです。

  • 再利用がしづらい ── 似たようなビルド手順を持つジョブが増えるたびに、同じ設定を UI 上でコピーする必要があり、DRY（Don't Repeat Yourself）の原則に反した状態になりやすいです。

これらの限界を解決するのが、次章から扱う Jenkins Pipeline です。ビルド手順そのものを「コード」として記述することで、バージョン管理・レビュー・再利用が可能になります。
