10. ベストプラクティスとトラブルシューティング

Jenkins Pipeline を実運用する上での指針と、よくあるトラブルへの対処法をまとめます。

注釈

sample-app/Jenkinsfile（ダウンロード、全文は Declarative Pipeline 構文の詳細 末尾に掲載）の options ブロック（timeout/buildDiscarder/disableConcurrentBuilds）は、本章で説明するベストプラクティスの多くをそのまま反映した例になっています。

10.1. Pipeline 設計のベストプラクティス

  • 冪等性を意識する ── 同じ Pipeline を 2 回実行しても同じ結果になるように設計します。例えば「ファイルを追記する」処理は再実行すると内容が重複しますが、「ファイルを生成し直す」処理であれば何度実行しても同じ結果になります。リトライ（後述）を安全に行うための前提条件です。

  • ステージの粒度を揃える ── stage はステージビュー上での可視化単位でもあります。1 つの stage に処理を詰め込みすぎると、どこで時間がかかっているか、どこで失敗したかが見えにくくなります。「ビルド」「単体テスト」「静的解析」「デプロイ」のように、意味のある単位で分割してください。

  • 失敗時のリトライは範囲を絞る ── Declarative Pipeline 構文の詳細 で扱った retry を Pipeline 全体にかけると、そもそも失敗する処理（バグのあるテストなど）まで無駄に再実行してしまいます。ネットワーク越しのダウンロードなど、一時的な不調が想定される処理だけを retry で囲むようにします。

  • Jenkinsfile はできるだけ薄く保つ ── 複雑なロジックを Groovy でそのまま書くのではなく、実体はシェルスクリプトや Python スクリプトとしてリポジトリに置き、Jenkinsfile 側はそれを呼び出すだけにすると、ローカル環境でも同じスクリプトを実行して動作確認ができます。

10.2. パフォーマンスとスケーリング

  • エージェントのスケールアウト ── ビルドが混雑してキューが溜まる場合、インストールとセットアップ で扱ったエージェントを増やすことで対応します。クラウド上では、ビルド需要に応じてエージェントを動的に起動・破棄するプラグイン（Kubernetes プラグインなど）を使うと、アイドル時のコストを抑えつつスケールできます。

  • 並列化による高速化 ── Declarative Pipeline 構文の詳細 で扱った parallel/matrix を使い、独立したテストスイートを並列実行するだけで、Pipeline 全体の実行時間を大きく短縮できることがあります。ただし、並列数を増やすほど同時に使うエージェントリソースも増える点に注意してください。

  • ビルドキャッシュの活用 ── 依存パッケージのダウンロードなど、毎回同じ結果になる処理はキャッシュを活用します。Docker エージェントを使う場合は、ベースイメージに依存関係を事前インストールしたカスタムイメージを用意しておくと、ステージ実行ごとのインストール時間を削減できます。

10.3. セキュリティ上の注意点

  • スクリプトセキュリティ ── Scripted Pipeline や script { } ブロックの中では、Groovy の任意のコードが実行できます。Jenkins には「Script Security」の仕組みがあり、管理者の承認を得ていない Groovy のメソッド呼び出しはデフォルトでブロックされます。むやみに承認を増やすと、Jenkinsfile を書き換えられる人が実質的にコントローラー上で任意のコードを実行できる状態になるため注意が必要です。

  • 権限管理（RBAC） ── 「誰がどのジョブを実行・編集できるか」を、Role-based Authorization Strategy のようなプラグインで管理します。特に、フォークからのプルリクエストをビルドする設定（マルチブランチパイプライン 参照）では、外部から送られてきたコードが実行される前提で権限を絞る必要があります。

  • Credentials の漏えい防止 ── 外部ツールとの連携 で触れたとおり、秘密情報は必ず Credentials プラグイン経由で参照し、ログへの出力を避けます。加えて、Credentials の利用範囲（グローバル／特定フォルダのみ等）を必要最小限に絞ることで、関係のない Pipeline から秘密情報が参照される事態を防げます。

10.4. よくあるエラーと対処法

  • CPS 起因のシリアライズエラー ── Scripted Pipeline と Groovy の基礎 で触れたとおり、Jenkins は Pipeline の実行状態をシリアライズできる形に変換（CPS 変換）しています。java.io.NotSerializableException が発生した場合、多くはシリアライズできないオブジェクト（クロージャの中で保持した複雑なオブジェクトなど）をステージをまたいで保持しようとしています。該当処理を @NonCPS を付けたメソッドに切り出すか、シリアライズ可能な単純な値だけを受け渡すようにします。

  • ワークスペースの競合 ── 同じジョブの複数ビルドが同時に走ると、デフォルトでは同じワークスペースを共有するため、ファイルの競合が発生することがあります。Declarative Pipeline 構文の詳細 の options で扱った disableConcurrentBuilds() で同時実行そのものを禁止するか、ws() ステップで一時的に別のワークスペースを使うことで解決します。

  • タイムアウト ── ネットワーク越しの処理がハングし、ビルドが終わらなくなることがあります。options { timeout(...) } をすべての Pipeline に設定しておくと、異常終了ではなく「タイムアウトによる失敗」として検知でき、原因調査の初動が早くなります。

  • ディスク容量の圧迫 ── ビルド履歴・成果物・ワークスペースが蓄積し、エージェントのディスクを圧迫することがあります。外部ツールとの連携 で扱った buildDiscarder の設定と、不要になったワークスペースを cleanWs() ステップで明示的に削除する運用を組み合わせて防ぎます。

10.5. Pipeline 開発を効率化する仕組み

Jenkinsfile を 1 行直すたびにコミット・push してビルドを回すのは非効率です。Jenkins には、これを補うための仕組みがいくつか用意されています。

  • Replay ── 過去のビルドの Jenkinsfile をその場で編集し、コミットせずに再実行できる機能です。ビルド履歴の画面から「Replay」を選ぶと、実際に使われた Jenkinsfile がエディタで開かれ、修正してすぐに試せます。デバッグ用の echo を一時的に挟みたい場合などに便利です。

  • Declarative Pipeline の構文検証 ── Jenkins の管理画面（Manage Jenkins > System > Pipeline-as-code Lint）や、curl で /pipeline-model-converter/validate エンドポイントに Jenkinsfile を送る方法で、実際にビルドを起動せずに構文エラーを検出できます。

  • エディタ・IDE 側での構文チェック ── VS Code の「Jenkins Pipeline Linter Connector」拡張機能などを使うと、保存するたびにエディタから Jenkins へ構文チェックを問い合わせ、エラー箇所を表示できます。

これらを使うと、「コミット → Jenkins でビルド → 失敗 → 修正」というサイクルを毎回繰り返さずに済み、Jenkinsfile の開発効率を上げられます。

10.6. CI/CD をさらに発展させるために

本書では Jenkinsfile によるビルド・テスト・デプロイの記述を中心に扱いましたが、Jenkins 自体の設定（プラグインの構成、認可設定など）もコード化できます。Jenkins Configuration as Code（JCasC）は、Jenkins Pipeline の基礎 で触れた Pipeline as Code の考え方を Jenkins そのものの設定にまで広げ、YAML ファイルから Jenkins の構成を再現できるようにする仕組みです。手作業でのセットアップに再現性がないという課題を、Jenkins の外側（アプリケーションコード）だけでなく内側（Jenkins の設定そのもの）にまで適用したものと言えます。

さらに一歩進めると、デプロイ先のインフラ状態を Git 管理下のマニフェストで表現し、その差分を自動的に反映する GitOps という運用モデルもあります。Jenkins Pipeline は「変更を検知してアクションを起こす」エンジンとして、GitOps の実現手段の一つにもなります。

本書はあくまで入門書としての範囲にとどめていますが、Jenkinsfile の書き方に慣れてきたら、これらのキーワードを起点に発展的なトピックへ読み進めてみてください。
