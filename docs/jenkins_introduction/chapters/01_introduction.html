1. Jenkins とは

この章では、CI/CD の基本的な考え方と、その代表的な実装である Jenkins の位置づけについて解説します。

注釈

本書は Python などのプログラミング経験がある読者を想定しています。基本的な構文（変数、条件分岐、関数、クラス）の説明は省略します。

1.1. CI/CD とは何か

CI（Continuous Integration、継続的インテグレーション）とは、複数人が書いたコードの変更を頻繁に統合し、その都度ビルドとテストを自動的に実行する開発プラクティスです。

手動でテストを実行する運用を想像してみてください。pytest をターミナルで叩くのを忘れる、ローカル環境でしか通らないテストがある、レビュー前にビルドが壊れていることに誰も気づかない ── こうした問題は、「コードを変更したら必ず、決まった環境で、決まった手順が実行される」という仕組みを機械に委ねることで解消できます。CI はまさにこの「必ず実行される」という保証を、人手に頼らず提供するための仕組みです。

CD には 2 つの意味があります。

  • Continuous Delivery（継続的デリバリー） ── ビルド・テストを通過したコードを、常に「いつでも本番へリリースできる状態」に保つこと。実際にリリースするかどうかの最終判断は人間が行います。

  • Continuous Deployment（継続的デプロイメント） ── テストを通過したコードを、人手を介さず自動的に本番環境へ反映すること。

日本語ではどちらも「継続的デプロイ」と訳されがちですが、「リリース判断を人間が行うか、自動化するか」という重要な違いがあるため、本書では英語表記で区別します。

これらの一連の処理（ビルド → テスト → パッケージング → デプロイ）を連結したものをパイプラインと呼びます。UNIX のパイプ（cmd1 | cmd2 | cmd3）が標準出力を次のコマンドの標準入力へ渡すように、CI/CD のパイプラインでは、あるステージの出力（ビルド済みのアーティファクトやテスト結果）が次のステージへ引き渡されていきます。この「パイプライン」という概念こそが、次章以降で扱う Jenkins Pipeline の名前の由来であり、本書全体を通じての中心的なテーマです。

1.2. Jenkins の特徴と歴史

Jenkins は、Sun Microsystems のエンジニアであった川口耕介氏が開発した Hudson という OSS プロジェクトを前身としています。2011 年、Oracle による Sun 買収後の商標問題を経て、コミュニティは Hudson からフォークし、Jenkins という名前で開発を継続することになりました。現在は Linux Foundation 傘下の Continuous Delivery Foundation がプロジェクトを支えています。

Jenkins 自体は Java（JVM）上で動作するアプリケーションです。Servlet コンテナへの配置も可能ですが、組み込みの Jetty サーバーを使って単体で起動するのが一般的です。

Jenkins の最大の特徴は、プラグインアーキテクチャにあります。コア部分が提供する機能は比較的小さく、Git や GitHub との連携、Slack への通知、Docker との統合、UI の拡張など、実用上必要な機能のほとんどはプラグインとして提供されます。エコシステムには 1,800 を超えるプラグインが公開されており、この柔軟性の高さが Jenkins が長年デファクトスタンダードの地位を保っている理由の一つです。一方で、プラグイン同士の依存関係やバージョン互換性の管理は、運用上の課題になりやすい点でもあります。

もう一つの特徴が、コントローラー／エージェントによる分散ビルドアーキテクチャです（旧称はそれぞれ Master／Slave）。ジョブの管理や UI の提供を担うコントローラーと、実際にビルドを実行するエージェントを分離できるため、OS やハードウェア要件の異なる複数の実行環境を一つの Jenkins から管理できます。詳細は インストールとセットアップ で扱います。

1.3. Jenkins が向いているユースケース

近年は GitHub Actions、GitLab CI/CD、CircleCI といった SaaS 型の CI サービスも広く使われています。これらは設定が容易で、パブリックな GitHub/GitLab リポジトリであれば追加インフラなしに使い始められるという強みがあります。

Jenkins が選ばれるのは、主に次のような場面です。

  • セルフホストが前提となる環境 ── 社内ネットワーク内のリソース（オンプレミスのデータベース、社内専用のデプロイ先など）へのアクセスが必要な場合、自分たちで管理するエージェントを社内に置ける Jenkins が有利です。

  • 特殊なビルド環境が必要な場合 ── 組み込み機器向けのクロスコンパイル環境、GPU を要する機械学習の学習ジョブなど、SaaS 側が用意する標準的な実行環境では対応しづらいハードウェア要件がある場合。

  • 高度にカスタマイズされたパイプラインが必要な場合 ── プラグインや共有ライブラリ（共有ライブラリ 参照）を用いて、組織固有の複雑なワークフローを構築・再利用したい場合。

  • 既存の Jenkins 資産がある組織 ── すでに多数のジョブや Jenkinsfile が運用されている環境では、移行コストよりも Jenkins を使い続けるメリットが大きいことが多いです。

逆に、単一のパブリックリポジトリをクラウドサービスへデプロイするだけ、といったシンプルな構成であれば、インフラの運用コストがかからない SaaS 型 CI の方が合理的な場合も少なくありません。Jenkins は「自由度」と「運用の手間」を引き受けることで、SaaS 型 CI では対応しづらい要件を満たせるツールだと理解しておくとよいでしょう。

1.4. 本書で扱う範囲

本書は、次のような流れで Jenkins と Jenkins Pipeline を学びます。

  1. インストールとセットアップ ～ Jenkins の基本操作（Freestyle ジョブ） ── Jenkins をインストールし、Freestyle ジョブを通じて UI 操作の感覚を掴みます。

  2. Jenkins Pipeline の基礎 ～ Scripted Pipeline と Groovy の基礎 ── Jenkinsfile による Pipeline as Code の書き方を、Declarative Pipeline を中心に、Scripted Pipeline や Groovy の基礎まで含めて学びます。

  3. マルチブランチパイプライン ～ 共有ライブラリ ── 複数ブランチでの Pipeline 運用や、コードの再利用の仕組みを学びます。

  4. 外部ツールとの連携 ～ ベストプラクティスとトラブルシューティング ── Docker や Credentials などの外部ツール連携、実運用のベストプラクティスとトラブルシューティングを学びます。

Jenkins 固有の概念（Groovy の文法、Pipeline DSL、プラグインの用語など）はその都度本書内で説明します。すでにプログラミング経験のある読者を想定し、変数や条件分岐、関数といった基礎的な説明は省略していますので、その分の紙面は Jenkins ならではの考え方の解説に充てています。
