5. コメントと docstring

コメントは、コードだけでは伝わらない情報を読む人に伝えるためのものである。ただし、コメントは多ければよいというものではない。不要なコメントや間違ったコメントは、かえって読む人を混乱させる。

5.1. 悪い例

次のコードは、注文金額から送料を求める。

リスト 5.1 ch05_comments_bad.py
 1"""第 5 章「コメントと docstring」の悪い例。"""
 2
 3
 4def shipping_fee(total: int) -> int:
 5    # total が 3000 以上なら 0 を返す
 6    if total >= 5000:
 7        return 0
 8    # 500 を返す
 9    return 500
10
11
12if __name__ == "__main__":
13    print(shipping_fee(4000))
14    print(shipping_fee(6000))

ch05_comments_bad.py をダウンロードする

このコードには次の問題がある。

  • 5 行目のコメントは「3000 以上なら」と書いているが、6 行目のコードは 5000 以上かどうかを調べている。コードを変更したときにコメントを直し忘れたと考えられる。どちらが正しいのか、読む人には判断できない。

  • 8 行目のコメント「500 を返す」は、9 行目のコードを日本語に言い換えただけで、新しい情報が無い。

  • 5000 と 500 がマジックナンバーになっている。

  • 関数が何をするのか、引数と戻り値が何を表すのかの説明が無い。

5.2. 良い例

リスト 5.2 ch05_comments_good.py
 1"""第 5 章「コメントと docstring」の良い例。"""
 2
 3import math
 4
 5FREE_SHIPPING_THRESHOLD = 5000
 6STANDARD_SHIPPING_FEE = 500
 7
 8
 9def shipping_fee(total: int) -> int:
10    """注文金額から送料を求める。
11
12    Args:
13        total: 注文金額（円）。
14
15    Returns:
16        送料（円）。注文金額が送料無料の基準額以上なら 0 を返す。
17    """
18    if total >= FREE_SHIPPING_THRESHOLD:
19        return 0
20    return STANDARD_SHIPPING_FEE
21
22
23def round_half_up(price: float) -> int:
24    """0 以上の金額を小数第 1 位で四捨五入し、整数にする。"""
25    # 組み込み関数 round() は偶数丸め（round(2.5) は 2）になるため、
26    # 店頭での表示に合わせて四捨五入を自前で行う。
27    return math.floor(price + 0.5)
28
29
30if __name__ == "__main__":
31    print(shipping_fee(4000))
32    print(shipping_fee(6000))
33    print(round(2.5), round_half_up(2.5))

ch05_comments_good.py をダウンロードする

shipping_fee では、マジックナンバーを定数にしたことで、コードを言い換えただけのコメントが不要になった。代わりに、10 行目から 17 行目の docstring で、関数の目的、引数、戻り値を説明している。

round_half_up の 25 行目と 26 行目のコメントは、「なぜ組み込み関数 round() を使わないのか」を説明している。このような理由は、コードを読んだだけでは分からない。

5.3. コメントに書くべきこと

コードを読めば分かることは、コメントに書く必要はない。コメントには、コードだけでは伝わらないことを書く。

使わなくなったコードをコメントにして残したもの

コメントを書きたくなったときは、まず「名前を変えたり、関数に分けたりすれば、コメントが無くても伝わるのではないか」と考えるとよい。

リスト 5.3 悪い例
1# 合格かどうかを調べる
2if score >= 60:
3    ...
リスト 5.4 良い例
1if score >= PASSING_SCORE:
2    ...

良い例では、定数の名前によって「合格点以上かどうか」を調べていることが分かるため、コメントが不要になっている。

使わなくなったコードをコメントにして残しておくのも避ける。残す理由が分からないコードは、読む人を迷わせる。昔のコードが必要になったときは、第 11 章で紹介するバージョン管理システムの履歴から取り出せる。

5.4. コメントをコードと一致させる

コメントは、コードと違って実行されないため、内容が間違っていてもエラーにならない。そのため、コードを変更したときにコメントを直し忘れやすい。コードと食い違ったコメントは、コメントが無いよりも有害である。

コードを変更するときは、周りのコメントも一緒に見直す習慣を付ける。

5.5. docstring を書く

Python では、関数、クラス、モジュールの先頭に書いた文字列リテラルを docstring と呼ぶ。docstring には、それが何をするのか、どう使うのかを書く。docstring は help() 関数で表示でき、多くのエディターでも関数の説明として表示される。

docstring の書き方は PEP 257 で定められている。主な規則は次のとおりである。

  • 3 つの二重引用符（"""）で囲む。

  • 1 行目には、何をするのかを 1 文で簡潔に書く。

  • 説明を続けて書く場合は、1 行目の後に空行を 1 行入れる。

引数や戻り値の書き方には決まった形式がいくつかある。良い例で使った Args:、Returns: などの見出しを使う形式は、Google のスタイルガイドで使われている形式であり、広く使われている。どの形式を使う場合も、1 つのプロジェクトの中ではそろえる。

短く、名前から内容が明らかな関数にまで、必ず docstring を書く必要はない。本書のサンプルコードでも、説明が必要な関数を中心に docstring を書いている。ただし、他の人が使うことを想定した関数やモジュールには、docstring を書くのが望ましい。

5.6. まとめ

  • コメントには、コードだけでは伝わらない理由や注意点を書く。

  • コードを言い換えただけのコメントは書かない。名前を改善してコメントを不要にできないか考える。

  • コードを変更したら、コメントも見直す。コードと食い違ったコメントは有害である。

  • 関数やモジュールの目的や使い方は docstring に書く。
