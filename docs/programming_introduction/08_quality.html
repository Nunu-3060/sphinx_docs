8. よいプログラムを書くために

正しく動くことは、プログラムに求められる最低限の条件である。実際の開発では、プログラムは書かれたあとも何度も読まれ、修正される。この章では、読みやすく、誤りの少ないプログラムを書き、それを保つための手法を説明する。

8.1. 可読性

プログラムは、書かれる回数よりも読まれる回数の方がはるかに多い。読むのは、他のメンバーや、数か月後の自分である。読みやすいプログラムは、誤りを見つけやすく、修正もしやすい。

8.1.1. 命名

変数や関数の名前は、その役割が分かるように付ける。

 1# 悪い例：名前から役割が分からない
 2def f(a: list[int]) -> int:
 3    t = 0
 4    for x in a:
 5        t += x
 6    return t
 7
 8
 9# よい例：名前から役割が分かる
10def total_price(prices: list[int]) -> int:
11    total = 0
12    for price in prices:
13        total += price
14    return total

2 つの関数は同じ処理を行うが、2 つ目の関数は名前を読むだけで、何をする関数なのかが分かる。

8.1.2. コーディング規約

インデントの幅、空白の入れ方、名前の付け方などの書き方を、チームや言語のコミュニティで統一するための決まりをコーディング規約と呼ぶ。書き方が統一されていれば、読む人は書き方の違いに気をとられず、内容に集中できる。Python では、PEP 8 [PEP8] が標準的なコーディング規約として広く使われている。

PEP 8 の規則の例

例

インデントは空白 4 個とする。

if 文や関数の本体を 4 個の空白で字下げする。

関数名と変数名は小文字の単語を _ でつなぐ。

total_price、linear_search

クラス名は単語の先頭を大文字にしてつなぐ。

Shape、BinarySearchTest

トップレベルの関数やクラスの定義の前後には空行を 2 行入れる。

8.2. テスト

プログラムが意図どおりに動くことを確かめる作業をテストと呼ぶ。テストのうち、関数やクラスなどの小さな単位を個別に確かめるものを単体テストと呼ぶ。単体テストをプログラムとして書いておけば、プログラムを修正するたびに自動で繰り返し実行でき、修正によって既存の機能が壊れていないことを確かめられる。

次のサンプルコードは、アルゴリズムと計算量の binary_search 関数に対する単体テストである。Python の標準ライブラリに含まれる unittest モジュールを使っている。

 1"""binary_search 関数の単体テスト。"""
 2
 3import unittest
 4
 5from binary_search import binary_search
 6
 7
 8class BinarySearchTest(unittest.TestCase):
 9    """binary_search 関数の振る舞いを確かめる。"""
10
11    def test_found_in_middle(self) -> None:
12        """中ほどにある要素の位置を返す。"""
13        self.assertEqual(binary_search([1, 3, 5, 7, 9], 5), 2)
14
15    def test_found_at_both_ends(self) -> None:
16        """先頭と末尾の要素の位置を返す。"""
17        self.assertEqual(binary_search([1, 3, 5, 7, 9], 1), 0)
18        self.assertEqual(binary_search([1, 3, 5, 7, 9], 9), 4)
19
20    def test_not_found(self) -> None:
21        """存在しない要素には -1 を返す。"""
22        self.assertEqual(binary_search([1, 3, 5, 7, 9], 4), -1)
23
24    def test_empty(self) -> None:
25        """空のリストには -1 を返す。"""
26        self.assertEqual(binary_search([], 1), -1)
27
28
29if __name__ == "__main__":
30    unittest.main()

各メソッドは、特定の入力に対して期待する戻り値が得られることを assertEqual メソッドで確かめる。目的の値が中ほどにある場合だけでなく、先頭や末尾にある場合（15〜18 行目）、存在しない場合（20〜22 行目）、リストが空の場合（24〜26 行目）のように、誤りが起こりやすい境界の条件もテストする。

binary_search.py と同じフォルダーで次のように実行すると、テストの結果が表示される。

 1$ python -m unittest -v test_binary_search
 2test_empty (test_binary_search.BinarySearchTest.test_empty)
 3空のリストには -1 を返す。 ... ok
 4test_found_at_both_ends (test_binary_search.BinarySearchTest.test_found_at_both_ends)
 5先頭と末尾の要素の位置を返す。 ... ok
 6test_found_in_middle (test_binary_search.BinarySearchTest.test_found_in_middle)
 7中ほどにある要素の位置を返す。 ... ok
 8test_not_found (test_binary_search.BinarySearchTest.test_not_found)
 9存在しない要素には -1 を返す。 ... ok
10
11----------------------------------------------------------------------
12Ran 4 tests in 0.000s
13
14OK

テストは、誤りがあることを示せても、誤りがないことは示せない。それでも、適切に設計したテストを積み重ねることで、プログラムの信頼性を大きく高められる。

8.3. デバッグ

プログラムの誤り（バグ）を見つけて修正する作業をデバッグと呼ぶ。やみくもにプログラムを書き換えるのではなく、次の手順で進めると効率がよい。

  1. 再現：バグが起こる条件を特定し、確実に再現できるようにする。

  2. 切り分け：入力を単純にしたり、途中の値を表示したりして、誤りのある箇所を絞り込む。デバッガを使えば、プログラムを 1 行ずつ実行しながら変数の値を確認できる。

  3. 修正：原因を理解したうえで修正する。症状だけを抑える修正は、別のバグを生みやすい。

  4. 確認：バグが直ったこと、他の機能が壊れていないことをテストで確かめる。同じバグが再発しないよう、そのバグを検出するテストを追加するとよい。

8.4. 静的解析

プログラムを実行せずに、ソースコードを解析して問題を見つけることを静的解析と呼ぶ。Python では、次のツールがよく使われる。

ツール

検出する問題

flake8 [Flake8]

PEP 8 に違反する書き方、使われていない変数や import 文、未定義の名前など。

mypy [Mypy]

型ヒントと矛盾する値の使い方。たとえば、int 型を返すと宣言した関数が文字列を返している箇所など。

本書のサンプルコードは、次のコマンドで違反が検出されないことを確認している。

1$ python -m flake8 examples
2$ python -m mypy --strict examples
3Success: no issues found in 14 source files

静的解析は、人間が見落としやすい単純な誤りを機械的に見つけられる。テストと組み合わせて使うことで、誤りを早い段階で発見できる。

8.5. バージョン管理

ファイルの変更の履歴を記録し、過去の状態に戻したり、変更の内容を比べたりできるようにする仕組みをバージョン管理と呼ぶ。現在は Git [Git] が広く使われている。バージョン管理を使うと、次のことができる。

  • いつ、誰が、なぜ変更したのかを記録し、あとから確認できる。

  • 誤った変更を取り消し、過去の正しい状態に戻せる。

  • 複数の人が同じプログラムを並行して変更し、その結果を統合できる。

プログラムを書くときは、小さな変更ごとに、変更の意図を説明するメッセージを付けて記録するとよい。
